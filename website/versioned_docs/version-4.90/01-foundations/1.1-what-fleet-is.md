# How Fleet works

Fleet gives you a common place to work with devices that communicate in different ways. When you ask for a software update or a configuration change, the Fleet server coordinates the request, keeps track of the intended setup, and receives information from the devices involved. Understanding that relationship helps you plan a rollout and follow its progress.

The server stores device data and the configuration you want, then communicates with hosts through agents and operating-system management channels. This central service is the **control plane**. The operating-system channels are commonly called **mobile device management (MDM)**, a name you will encounter for desktop and laptop management too.

This chapter introduces those components and follows the work from a device observation to a requested change and its result. If you would like a broader introduction first, [What Fleet is](../00-Introduction/0.2-what-fleet-is.md) describes the everyday work they support.

## The main components, and what each one does

![Explanation](../_assets/icons/explanation.svg) You will see several component names in installers, logs, and troubleshooting instructions. Knowing each component’s job helps you work out where to look when a task stops progressing.

**fleetd** is the bundle you install on macOS, Windows, and Linux. It contains Orbit and osquery, with Fleet Desktop included when the package is built with it. When an instruction refers to a fleetd installation, those are the components it is putting on the device.

**Fleetd for Chrome** is the browser extension used on ChromeOS. You force-install it through Google Admin, which continues to manage the extension. Its service worker enrolls in Fleet and answers live reports from virtual tables. ChromeOS has no scheduled reports or native fleetd processes; [3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md) covers the setup and its limits.

**osquery** reads information from the running host. It gives Fleet a way to ask the same question of many devices and collect their answers, which is the basis for much of the inventory and reporting work.

**Orbit** manages osquery’s version and configuration and handles agent-side actions such as installing software and running scripts. It also updates fleetd. When a report works but a script does not, these separate responsibilities help you narrow the investigation.

**Fleet Desktop** is the part people using the device interact with. It shows policy information, offers self-service software, and presents dialogs when a workflow needs user input.

**The OS MDM client** applies the platform’s native management instructions. Apple and Microsoft supply the device clients; Fleet handles enrollment, builds profiles and commands, queues the work, and processes the responses on the server.

**The Fleet service** brings these components together. It holds the desired state, receives device results, and coordinates the work between administrators and hosts.

## From device observations to completed work

To find out what is on a device, you can read its **host vitals**, the hardware, OS, and network facts Fleet collects, or look through its software inventory. Reports let you ask a question across many devices, either live or on a schedule. For example, a live report can ask online hosts which browser version they have installed and bring their answers together.

As you read those answers, keep the time of observation in mind. An offline laptop may still show the browser version it reported before it disconnected. Last-seen time and a report row’s fetch time help you judge how current the information is. Some values, including custom vitals set through the API, have no timestamp, so the value alone cannot tell you when it was last true.

The configuration you enter has a different role: it records the **desired state**, such as a profile you want a device to have. Fleet also retains history for selected data, including uptime and vulnerabilities. For scheduled reports, though, storage keeps the newest result for each host and query, replacing that host’s previous rows.

If you need report history outside Fleet, plan how the results will leave it and where they will be retained. Report storage, result forwarding, and activity auditing each have their own settings:

| Behaviour | What it does | What turns it off |
|---|---|---|
| Report storage | Replaces the previous result rows for each host and query | `discard_reports_data` disables storage server-wide and deletes stored rows; `discard_data` disables it for a report. Storage also requires snapshot logging. A fixed threshold rejects all results from a host returning more than 1000 rows. The configurable `report_cap` trims across hosts and marks the report clipped; treat clipped coverage and freshness as unknown ([4.2](../04-know-your-devices/4.2-run-queries-and-reports.md)) |
| Result forwarding | Sends results to the configured result-log destination for external retention | Automations is off by default for each query; enable it for routine forwarding. Server-wide storage disablement and unrecognized queries bypass this filter ([4.2](../04-know-your-devices/4.2-run-queries-and-reports.md#getting-results-out-of-fleet)) |
| Activity audit | Records administrative actions on the server, on its own independent settings | Its own separate configuration |

To keep report results in an external system, configure a server log destination and enable Automations for the queries you want to forward. For a recognized query while server-wide report storage is enabled, that setting controls which received results Fleet forwards.

When storage is disabled server-wide, Fleet forwards incoming results without the Automations filter. Results for unrecognized queries also pass through. Query scheduling is a separate decision: these forwarding rules govern results that have already arrived. [2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md) walks through the log-delivery setup.

You can also export stored report rows through the REST API on a schedule. When choosing a command for that job, watch the distinction between definitions and results: `fleetctl report` runs a new live report, while `fleetctl get reports` lists report definitions. Neither retrieves the stored result rows.

Once you know which devices need attention, labels, policies, fleets, and vulnerability data help you select them. You might identify devices with an outdated application, for example, then choose how to deliver the update.

Fleet can deliver software, run scripts, apply profiles, send MDM commands, and manage OS settings and disk encryption. The right method depends on the change and the platform. After you request it, Fleet determines the targets, delivers the work, and receives evidence of what happened.

Following that evidence is part of making the change. The activity record and the device’s reported result describe different points in the process, and the timing depends on the delivery path.

For an MDM command sent by hand, Fleet writes the activity when it successfully queues the command. For a configuration profile, it writes the activity when you save the desired state. A **reconciler**, a background process that compares stored state and issues the matching commands, works out the per-device work afterward. Android profiles take another path: Fleet updates a policy at Google, then checks the policy version the device reports.

In each of these cases, the activity confirms that Fleet accepted the instruction. You still need the device’s result to confirm completion. A queued command can wait days for a device to check in, or the device can refuse it after delivery. If a change stalls, [8.1](../08-troubleshooting/8.1-diagnostic-method.md) helps you find where that happened.

## What Fleet can do on each platform

![Reference](../_assets/icons/reference.svg) Fleet brings several platforms into one administrative workflow. The channel available on each device determines the work you can send to it: a laptop running fleetd can run agent-side tasks, while a phone uses its platform’s management facilities. The table below connects those device types to their data and management paths.

When planning a task, check the requirements that make it available. The same checks help explain a missing control or a refused request:

1. **Platform support.** Linux has no MDM channel for configuration profiles.
2. **Fleet implementation.** The Chrome extension supports live reports but has no scheduled-result upload path.
3. **Licence.** Premium requirements apply per feature. A request may return a licence error, while the UI may omit the control entirely.
4. **Prerequisites.** The feature may require MDM enrollment or a particular fleetd version.
5. **Configuration and permissions.** For example, the server’s `scripts_disabled` setting refuses every script run. Your role must also permit the action.

| Device class | Device-data path | Agent action path | Platform-management path |
|---|---|---|---|
| macOS | fleetd and osquery | Orbit: scripts, installer-based software, fleetd updates | Apple MDM: profiles, MDM commands, App Store apps via the Volume Purchasing Program (VPP) |
| Windows | fleetd and osquery | Orbit: scripts, installer-based software, fleetd updates, **and lock, which is a script here rather than an MDM command** | Windows device management (OMA-DM): profiles, MDM commands, wipe |
| Linux | fleetd and osquery | Orbit: scripts, installer-based software, disk-encryption (LUKS) key escrow, lock and wipe as scripts | **none** |
| iOS / iPadOS | MDM-reported inventory | **none** | Apple MDM: profiles, commands, App Store apps via the Volume Purchasing Program (VPP) |
| Android | Android Management API (AMAPI)-reported inventory | A narrow Fleet app for certificate delivery only | Android Management API: policy, managed applications |
| ChromeOS | Fleetd for Chrome, a force-installed extension | **none** | **none**; Google Admin manages the Chromebook |

macOS, Windows, and Linux get osquery through fleetd. iOS, iPadOS, and Android mainly supply inventory through their management channels. A host record can also exist before the device has contacted Fleet: Apple Business Manager sync can create a pending host. Seeing the record is therefore only the start of confirming enrollment ([1.2](1.2-how-fleet-reaches-a-device.md), [3.5](../03-connect-devices/3.5-enroll-ios-and-ipados-devices.md)).

Some features use several paths together. **FileVault** on macOS is one example: an MDM profile enables encryption and initial escrow, and osquery retrieves the encrypted recovery key. When the key needs rotating, Orbit runs Escrow Buddy and osquery retrieves the new key. A FileVault investigation may therefore need evidence from all three components.

For a script or installer-based software deployment that did not complete, start with Orbit and the agent path. The table helps you choose which channel to investigate before you begin reading its logs.

Licence requirements also follow individual features. Named fleets and software installation require Premium. Scripts are available on Free, but running them within a named fleet requires Premium. Profiles have separate requirements for fleet scope, label targeting, and content, while MDM commands have requirements specific to the command.

Profile variables illustrate how those requirements can differ by platform. They require Premium in Apple and Windows profiles, with Apple also validating individual variables and certificates. Android accepts supported variables on Free, while particular profile content, currently `systemUpdate`, requires Premium.

When you are planning a particular task, use [a.2](../09-appendices/a.2-platform-capability-matrix.md) to check its platform support, licence, and prerequisites. Then follow the feature’s chapter for the procedure. Part III covers getting each platform enrolled and ready for that work.

## Fleet in your environment

![Explanation](../_assets/icons/explanation.svg) Fleet will work alongside systems you already use for identity, configuration, security, and asset records. Deciding what each system owns makes both setup and later troubleshooting easier.

Your **identity provider** authenticates administrators, while Fleet keeps their accounts, roles, sessions, and API tokens. With Premium just-in-time provisioning, Fleet can create an account at the person’s first sign-in. Without it, an SSO-enabled account with a matching email must already exist in Fleet. Plan how people receive roles and how their access is removed, and keep a break-glass account that can sign in when the IdP is unavailable. [2.5](../02-administer-and-deploy-fleet/2.5-identity-providers-sso-scim-and-role-sync.md) covers the connection; [2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md) covers the accounts.

Your **configuration-management tools** can keep doing work that Fleet observes. An existing tool might own a headless Linux server’s configuration while Fleet supplies inventory and reports about it. Linux has no Fleet MDM channel, so keep that boundary in mind when deciding how to apply settings.

**Security information and event management (SIEM) systems, data lakes, and security tools** give exported Fleet data a place for longer retention and analysis. For example, you may want to compare device results over time or read administrative activity alongside identity events. Fleet’s own history covers specific features, so decide which records you need to keep and for how long.

Set up the log streams individually. osquery results and status logs use their own plugins; administrative activity uses a separate Premium audit plugin that is off by default. For routine scheduled reporting, also enable result forwarding on the queries you want to export; the storage and forwarding section above explains the exceptions. These choices let you send different records to the destinations that need them ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)).

**Platform-management services** carry work through Apple MDM, Windows OMA-DM (Open Mobile Alliance Device Management), and Google’s Android Management API. Fleet prepares the instruction, and the device’s management client applies it. For a Mac profile, for example, Fleet composes the profile and the Apple MDM client on the Mac handles installation.

Your **IT asset system** can remain the authority for procurement, financial ownership, contracts, and lifecycle records. Fleet contributes facts reported by devices, alongside desired configuration such as profiles and settings. It also holds device-to-person mappings from an IdP or an assigned email.

Fleet policies help you act on those device facts. A policy asks a yes/no question and returns pass or fail; an attached automation can respond to a failure. Keep the commercial asset record in the system that owns it, and use Fleet to understand and manage the device’s reported state.
