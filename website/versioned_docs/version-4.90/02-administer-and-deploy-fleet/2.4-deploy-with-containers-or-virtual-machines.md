# Deploy with containers or virtual machines

Fleet can run on the infrastructure your administrators are comfortable operating, from a small virtual machine to a Kubernetes cluster. Each option uses the same Fleet server and core dependencies. The useful differences are how you provide persistent storage and TLS, and how the deployment runs database migrations during an upgrade.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers running Fleet without a cloud provider's managed services underneath it: Docker Compose, Kubernetes, ordinary virtual machines, and Proxmox. How large to make any of it is [2.2](2.2-self-hosting-architecture-and-capacity.md). The two clouds Fleet publishes reference architectures for are [2.3](2.3-deploy-on-aws-or-gcp.md). Handing the finished thing to whoever operates it is [7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md).

These paths overlap with the previous chapter more than the titles suggest. Kubernetes on a managed cluster is a container deployment that happens to be on a cloud, and the object storage and database advice from [2.3](2.3-deploy-on-aws-or-gcp.md) applies unchanged.

Use this chapter to plan the first launch and ongoing operation of your chosen packaging. It explains where migrations run, how TLS is arranged, and which resources you need to supply.

Prepare the server private key, TLS certificate and termination point, persistent storage and backups, DNS, any load balancer, and the secrets needed to connect them. Fleet’s Compose and Helm examples provide starting configurations you can adapt. Use [2.2](2.2-self-hosting-architecture-and-capacity.md) for sizing and [7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md) for the readiness review.

## What the packaging choice changes

![Explanation](../_assets/icons/explanation.svg) Your packaging choice lets you use familiar deployment and monitoring tools. Fleet’s application behavior stays the same: the server needs the MySQL, Redis, and TLS configuration described in [2.2](2.2-self-hosting-architecture-and-capacity.md).

Fleet's published container image is small and deliberately plain: an Alpine base pinned by digest, the Fleet binary, and a command that runs `fleet serve`. It creates its own unprivileged user and runs as that user rather than as root.

Docker creates volumes owned by root, so the Fleet user may initially be unable to write to its log directory. Fleet’s Compose deployment includes an initialization container that corrects ownership and then exits. An `Exited (0)` status for that helper confirms successful completion.

The image's own command is `fleet serve`, which does not migrate. Whether your deployment migrates on start therefore depends on whether something overrides that command, and the published packagings differ on exactly this point. It is covered under upgrades below.

## Fleet will substitute one of its datastores and not the other

![Explanation](../_assets/icons/explanation.svg) Fleet supports a specific set of datastore implementations. Its Kubernetes guidance recommends Valkey for the cache, while the durable database must remain supported MySQL.

**Valkey is the recommended cache for Kubernetes deployments.** It is a Linux Foundation-governed, Redis-compatible project. Fleet’s Helm chart includes an optional Valkey sub-chart, and Fleet’s guide points to Valkey’s own chart for larger deployments.

**MariaDB and other MySQL drop-in replacements remain unsupported**, as [2.2](2.2-self-hosting-architecture-and-capacity.md) records, to the point that known problems with them may not be fixed.

The stores have different responsibilities. MySQL is the system of record, and Fleet depends on its behavior under concurrency, migrations, and schema changes. The cache holds work in progress through a smaller command surface, which Valkey can provide. Much of that work can be retried after cache loss, although pending failing-policy deliveries and recorded error history cannot be reconstructed ([7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md)). Keep the supported datastore choices in place even when another product advertises compatibility.

## Docker Compose

![How-to](../_assets/icons/howto.svg) Fleet publishes a Compose deployment, and it is the shortest path to a working server on hardware you control.

It brings up three services and one initialization container: MySQL for the durable state, Redis for the work in progress, Fleet itself, and the permissions helper described above. The published file maps host port 1337 to Fleet, so that is what devices connect to and what your firewall needs to allow inbound. If you put a reverse proxy in front to terminate TLS, that mapping becomes internal and the port devices actually use is the proxy's.

**Generate the server private key properly and keep it.** Fleet refuses to start if the key is present but shorter than 32 bytes, and the check runs after any secrets manager lookup, so a short value fetched from a secret store is caught the same way. This is the key that encrypts the secrets Fleet stores in MySQL, including the escrowed Linux disk encryption data that [7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md) covers and integration credentials. It does not encrypt session tokens, which are stored as they are; losing the private key is not recoverable by regenerating it.

For TLS you either give Fleet a certificate and key directly or terminate TLS at a reverse proxy in front of it and turn Fleet's own TLS off. **The two arrangements need opposite settings**, so a half-configured one produces certificate errors on first start: Fleet either has a certificate it is not meant to serve, or is meant to serve one it does not have. Check which of the two you intended before reading the error.

Compose can support a small production deployment when you provide the necessary operational controls. As it grows, Fleet recommends managed MySQL and Redis, multiple Fleet containers behind a load balancer, trusted certificates, pinned image versions, backups, and log forwarding. The architecture in [2.2](2.2-self-hosting-architecture-and-capacity.md) provides a path for adding those capabilities.

## Proxmox is a virtual machine with Docker on it

![Explanation](../_assets/icons/explanation.svg) Fleet’s Proxmox guide runs the Compose deployment inside an Ubuntu virtual machine. It walks through creating the VM and installing Docker, making it a useful starting point if Proxmox is where you already operate services.

The Compose requirements and operating procedures apply inside the VM. You can use the same arrangement on another hypervisor.

What the guide does provide, and what is hard to find elsewhere, is a floor. **Four gigabytes of memory, two virtual CPUs and twenty gigabytes of disk** run a complete Fleet deployment including its database and cache. Set against the five thousand host configurations in [2.2](2.2-self-hosting-architecture-and-capacity.md), that gives you both ends of the range.

One requirement is easy to skip and expensive to discover later: **you need a domain name or a local DNS entry pointing at the machine.** A bare IP address will not do, because the certificate has to match the hostname the agents use, and device management enrollment depends on that name.

## Virtual machines and systemd

![How-to](../_assets/icons/howto.svg) Running the Fleet binary under systemd is a supported option for organizations that already manage services directly on virtual machines. It gives you the same server capabilities without adding a container runtime.

Fleet publishes a sample systemd unit. Run it as a dedicated unprivileged user rather than root, exactly as you would any web server, and raise the open file limit, since Fleet holds a great many connections at once and the default on many distributions is too low. Logs go to the journal, so `journalctl` is where you follow a failing start. Changing the unit needs a daemon reload before a restart, or systemd keeps running the old definition and the change appears to have done nothing.

Pass credentials through environment variables or a configuration file when adapting the sample systemd unit. The sample’s command-line password flag can expose the value in process listings and Fleet debug archives. Review the unit’s credential handling before using it in production.

## Kubernetes

![How-to](../_assets/icons/howto.svg) There are two supported routes, a Helm chart and a Terraform module, and they deploy the same thing. Pick whichever matches how the rest of your cluster is managed.

The chart can bring up MySQL and Valkey as sub-charts, which is the fastest way to a working cluster deployment. **Those sub-charts are for development and testing.** Fleet says so directly, and the reasoning is the same as everywhere else in this part: running a highly available database inside Kubernetes is a real undertaking, and a managed database service is almost always the better trade. For anything you intend to keep, point Fleet at a database and cache that live outside the cluster.

Credentials go in Kubernetes secrets in the deployment's namespace, and the addresses Fleet needs are ordinary in-cluster service names.

## Rolling updates are the wrong strategy for Fleet

![Explanation](../_assets/icons/explanation.svg) Plan upgrades around Fleet’s requirement to run database migrations while the server is stopped. Each packaging handles part of that sequence differently, so establish the procedure before the first upgrade.

[2.2](2.2-self-hosting-architecture-and-capacity.md) establishes that migrations run with the server offline. On Kubernetes that requirement collides with the default behaviour of a deployment, which is to keep old pods serving while new ones start. Fleet needs no active connections to the database when migrations run, and a rolling update guarantees the opposite.

**Scale the deployment to zero replicas first**, let the pods terminate, then upgrade. Fleet's Helm chart runs migrations as a job wired into the install and upgrade lifecycle, so the migration itself is handled, but the chart cannot stop your running pods for you. That step is yours.

Fleet’s published Compose file runs `fleet prepare db --no-prompt` before `fleet serve`. Pulling a new image and starting the single Fleet container therefore performs the migration during startup. With that single-container arrangement, no other Fleet instance is serving traffic during the migration.

The Terraform path replaces the deployment explicitly as part of the apply, which achieves the same stop before the migration runs.

There is a subtlety in the chart worth knowing if you use the built-in database sub-chart: the migration job is only wired in as a pre-install and pre-upgrade hook when you are pointing at an external database. With the sub-chart enabled the ordering differs, because the database it would migrate is being created by the same release.

## Moving vulnerability processing off the serving instances

![Explanation](../_assets/icons/explanation.svg) The Helm chart can give vulnerability processing its own scheduled job and resources. This helps keep periodic analysis from competing with instances serving agent traffic.

Vulnerability processing is periodic, heavy, and unrelated to serving agent traffic. The chart can run it as its own scheduled job, on its own resource allocation, instead of inside the instances that are answering hosts. Turning that on does two things at once, and both are necessary: it creates the scheduled job, and it sets the server instances to stop running the work themselves. Doing only the first would leave the work happening twice.

The setting that suppresses the in-server schedule exists on every deployment, not just Kubernetes, and is documented for exactly this case: use it when something outside Fleet is scheduling that job. If you are running Fleet on plain machines and vulnerability processing is competing with agent traffic, that is the lever, and you would build the external schedule yourself.

## Verification and ownership

<!-- SCREENSHOT-REUSE: SS-2.2-01. Reuse the first-run setup form when explaining the first browser visit. Keep container listings and systemd output as selectable text rather than screenshots. -->

![How-to](../_assets/icons/howto.svg) On Kubernetes, confirm the deployment and pods are running and then reach the URL you configured. On Compose, check the containers and remember that the initialization container should have exited cleanly rather than be running. Reaching the URL for the first time on any of these paths lands on the setup screen; [2.2](2.2-self-hosting-architecture-and-capacity.md#complete-first-run-setup) covers creating the first administrator there or with `fleetctl setup`.

Also test software delivery by uploading an installer and downloading it to a host. As [2.2](2.2-self-hosting-architecture-and-capacity.md) explains, `/healthz` checks MySQL and Redis but does not exercise object storage. Confirm shared storage before adding a second instance, because local fallback files are only available to the instance that received them.

Ownership on these paths tends to be concentrated rather than divided, and the risk is the opposite of the cloud case. One person builds it, it works, and nothing is written down. The specific things worth recording before you move on are where the server private key lives, what the certificate is and when it expires, whether object storage is configured or falling back, and what the upgrade sequence is on this particular packaging, since it differs meaningfully between Compose, systemd and Kubernetes. That list is the input to [7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md).

## Precedence and edge cases

![Reference](../_assets/icons/reference.svg) Keep these packaging details with your deployment runbook so another operator can recognize expected behavior and perform the next upgrade.

The Compose initialization container should finish with `Exited (0)` after correcting volume ownership.

The Compose deployment listens on 1337 while Fleet's own default is 8080, so guidance written for one will name a port the other does not use.

Pin the image version. An unpinned image tag means an unplanned upgrade, and an unplanned Fleet upgrade means unplanned database migrations against a server that was not stopped for them.

The migration step exists in every packaging. What differs is whether it is arranged for you, as in Fleet's Compose file and Helm chart, or left to you, as with a plain binary under systemd. Find out which before your first upgrade rather than during it.

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.0. Helm chart values, image contents and the published Compose file all move independently of Fleet releases, so treat the structure as durable and the specific keys as things to confirm against the version you deploy.

Valkey being the recommended cache for Kubernetes is Fleet's guidance at this release, and the guidance is what may move. The underlying reason, that Redis holds work in flight while MySQL holds the record, is a property of the design rather than of a release.
