# Production readiness checklist and handoff

![Explanation](../_assets/icons/explanation-light.svg) A good handoff gives the next operator enough context to keep Fleet dependable. Along with access to the service, they need the recovery procedure, renewal calendar, monitoring responsibilities, and the evidence gathered during the pilot.

## Purpose and scope

![Explanation](../_assets/icons/explanation-light.svg) Use this chapter to review readiness before enrolling production hosts or transferring responsibility for an existing deployment. It brings together the deployment guidance in Part II and the operating procedures in 7.1–7.6, with a focus on the decisions and records a successor needs.

## What is being handed over

![Explanation](../_assets/icons/explanation-light.svg) The operator takes responsibility for the service and its dependencies. Make those responsibilities visible in the handoff, including work that may not be due for several months.

Account for the three data stores and the consequences of losing each. Include credentials held in external consoles, the certificate-renewal order that preserves agent trust, the tested upgrade procedure, and checks that establish whether background jobs are progressing.

If you run a Fleet MCP server for an assistant, include it as a service dependency. Record its Fleet API token and, for SSE, its shared client bearer; its monitoring; and its rotation and retirement procedures. [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md), [7.4](7.4-observe-progress-and-service-health.md), and [7.6](7.6-maintain-credentials-certificates-and-access.md) explain those requirements. Its liveness probe checks the process, so the handoff also needs the authenticated read used to verify its connection to Fleet.

Walk through this information with the incoming operator. A service URL and administrator credential provide access, but the procedures and ownership records make that access usable during maintenance or an incident.

## The go-live decision

![How-to](../_assets/icons/howto-light.svg) Review the following evidence with the people responsible for the deployment. Each row should have an owner who can show how it was verified and record any remaining gap.

| Area | Readiness evidence | Supporting guidance |
|---|---|---|
| Infrastructure | Database backups run on a defined schedule | [7.2](7.2-back-up-and-restore-service-state.md) |
| Infrastructure | At least one restore has been completed and its recovery time measured | [7.2](7.2-back-up-and-restore-service-state.md) |
| Infrastructure | Fleet's database account can perform the required schema changes | [Database permissions](#database-permissions-for-migrations), below |
| Infrastructure | Object storage is explicitly configured and an installer has been uploaded and downloaded end to end | [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md) |
| Infrastructure | The organization can recover the server private key independently of the person who created it | [7.2](7.2-back-up-and-restore-service-state.md), [7.6](7.6-maintain-credentials-certificates-and-access.md) |
| Operational | The load balancer uses Fleet's health endpoint | [7.4](7.4-observe-progress-and-service-health.md) |
| Operational | Metrics collection is enabled and receiving data | [7.4](7.4-observe-progress-and-service-health.md) |
| Operational | Changes in enrolment counts reach a responsible operator through an alert | [7.4](7.4-observe-progress-and-service-health.md) |
| Operational | The deployment's upgrade procedure has been exercised in a maintenance window | [7.3](7.3-upgrade-fleet-and-fleetd.md) |
| Ownership | Each credential has a named owner and a recorded management console | [External ownership](#ownership-that-reaches-outside-your-organization), below |
| Ownership | Someone in the organization can reach an administrator of each external console | [External ownership](#ownership-that-reaches-outside-your-organization), below |
| Ownership | The runbook contains the deployment's actual hostnames and procedures | [Dependency failure runbooks](#runbooks-for-dependency-failures), below |

The [pilot](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md) is an opportunity to gather this evidence before a wider rollout. Use its results for the go-live decision, then retain them with the ongoing responsibilities described below.



<a id="backup-and-restore-have-no-fleet-procedure"></a>

## Hand over a tested backup and restore procedure

![Explanation](../_assets/icons/explanation-light.svg) Fleet's backup guidance points to MySQL procedures or managed cloud backups. The deployment still needs its own recovery runbook, using [7.2](7.2-back-up-and-restore-service-state.md) as a guide. Include the actual hostnames, storage locations, required secrets, and measured restore time.

The recovery set extends beyond MySQL. Losing MySQL loses configuration, history, and the enrolled estate. Redis also contains pending failing-policy deliveries and recorded error history that cannot be reconstructed. Object storage may contain completed file-carve evidence as well as replaceable installers and icons. Decide whether carve evidence needs protection based on its value and retention requirements. [1.6](../01-foundations/1.6-the-fleet-server.md) and [7.2](7.2-back-up-and-restore-service-state.md) describe the state held by each store.

Fleet provides no coordinated snapshot across all three stores. Document the capture times and the reconciliation required after restoring them, including your decision about Redis persistence. A restored database can refer to objects from a different point in time.

Preserve the server private key outside the database and name its recovery location in the handoff. [7.2](7.2-back-up-and-restore-service-state.md) explains which escrow chains depend on it and which also require other material, including the Windows enrolment identity. A complete database backup cannot compensate for a missing decryption key.

Include the result of a completed restore rehearsal. The measured recovery time and verification results let the incoming operator assess the deployment's recovery capability and any gap against its objectives.

## Upgrades

![How-to](../_assets/icons/howto-light.svg) Hand over the procedure your deployment has tested. Fleet's documented upgrade stops every instance, while its bundled Helm chart uses a different lifecycle. [7.3](7.3-upgrade-fleet-and-fleetd.md) covers preparation, migration, acceptance, and recovery. [A.6](../09-appendices/a.6-glossary-and-release-compatibility.md) records the semantic-versioning commitment and its three exceptions.

Within the current major version, Fleet supports skipping intermediate releases, such as upgrading directly from an older 4.x release to a later 4.x release. For a major-version boundary, use stages: reach the last release of the old major, migrate and test, then proceed to the next major. Record the tested source and target versions so a successor can plan from known results.

Fleet's guidance describes migrations as taking seconds to minutes and a typical complete upgrade as taking five to ten minutes of downtime. The latter also includes replacing the binary or image and restarting. Use both as context, then budget the actual window from your rehearsal, including acceptance checks, as described in 7.3.

Agents buffer collected results while the server is unavailable and submit them when it returns. That buffer is finite: osquery discards the oldest entries once the limit is exceeded, with a default limit of one million log entries. A short interruption may delay delivery; a longer one can lose buffered records. Include that possibility when agreeing on the maintenance window.

<a id="the-database-user-needs-more-permission-than-a-careful-dba-will-grant"></a>

## Database permissions for migrations

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) The account used for migrations needs permission to create, alter, and drop tables, and to create temporary tables. Data read and write permissions alone can support normal operation while leaving an upgrade unable to prepare the schema.

Verify these permissions before handoff and record them with the recovery procedure. Preparing a freshly restored database has the same requirement. This gives the database owner a concrete permission set to review before the maintenance window.

<a id="rotating-the-certificate-can-disconnect-every-agent"></a>

## Preserve agent trust during certificate renewal

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Record who renews the served certificate and how they coordinate agent trust changes. If agents were deployed with an explicit certificate chain, distribute the new chain before the server begins presenting its replacement certificate. Otherwise, agents can fail verification and stop reporting while the Fleet server remains healthy.

Use the renewal order and hostname checks in [7.6](7.6-maintain-credentials-certificates-and-access.md). Include them in the handoff to the certificate owner so they are part of the scheduled renewal procedure.

## What to monitor, and who answers

![How-to](../_assets/icons/howto-light.svg) Record which conditions require a response, how an alert reaches the operator, and who covers that responsibility. [7.4](7.4-observe-progress-and-service-health.md) explains collection, coverage, and alert testing.

Fleet's suggested alerts include changes in host enrolment levels, rising endpoint latency, and increasing endpoint errors. Include the host signal alongside infrastructure monitoring: a deployment can pass infrastructure checks while devices stop reporting.

Assign a named accountable owner and a response arrangement for each alert. Make host reporting an explicit responsibility so it does not fall between database, certificate, and platform ownership.

For an MCP deployment, record its owner in the same operating model ([7.1](7.1-define-the-service-operating-model.md)). Verify both its liveness probe and its authenticated connection to Fleet, following [7.4](7.4-observe-progress-and-service-health.md).

<a id="a-runbook-for-the-failures-that-are-not-obviously-fleet"></a>

## Runbooks for dependency failures

![Reference](../_assets/icons/reference-light.svg) Include the dependency checks that help an incoming operator investigate a Fleet symptom. Use the following starting points with the broader diagnostic method; a symptom can have more than one cause.

| Symptom | Initial check |
|---|---|
| Slow after a database change | Compare per-instance connection limits multiplied by instance count with database capacity ([2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md)) |
| Unknown-column error after an upgrade | Verify that the database was prepared for the deployed binary |
| Too many open files | Check the process file-descriptor limit and service definition ([2.4](../02-administer-and-deploy-fleet/2.4-deploy-with-containers-or-virtual-machines.md)) |
| Agents fail to verify the server | Check the certificate chain and certificate hostname |
| Installer delivery fails while health checks pass | Check object storage, which is outside the health endpoint's coverage ([2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md)) |
| Hosts appear and disappear, or share an identity | Investigate duplicate enrolment, including cloned images containing an enrolled agent ([3.1](../03-connect-devices/3.1-enrollment-design-and-host-lifecycle.md)) |
| Windows hosts report management off | Check whether enrolment is waiting for a user sign-in ([2.11](../02-administer-and-deploy-fleet/2.11-configure-windows-management.md)) |

## Ownership that reaches outside your organization

![Explanation](../_assets/icons/explanation-light.svg) Some Fleet capabilities depend on accounts and credentials managed in another console. Record that relationship even when the console belongs to another group or provider.

The Apple push certificate expires annually and requires manual renewal. Create it under an organization-controlled account, following [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md). The Entra application registration and permissions need a Microsoft identity owner. Android Enterprise needs an owner with access to the Google organization.

Include the consequences of external changes. Deleting the Android enterprise in Google's console ends management of enrolled Android devices without a confirmation step in Fleet; Google also removes the work profile on personally owned devices ([2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md)).

For each dependency, record its console, administrator, renewal date where applicable, and the affected capability. Confirm that the incoming operator can reach the responsible administrator.

## Precedence and edge cases

![Reference](../_assets/icons/reference-light.svg) MySQL replication is supported and recommended for production availability. Keep backups as well: a replica reproduces deletions along with other writes.

Record the choices that are difficult to reverse, especially the server URL and Windows key material ([2.1](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md)). Fleet accepts a server-URL change while Google continues delivering to the previous address, which can break Android management ([2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md)). The Windows enrolment key pair also protects BitLocker escrow ([2.11](../02-administer-and-deploy-fleet/2.11-configure-windows-management.md)).

Include database preparation in every upgrade procedure, regardless of packaging. Make the migration step explicit in the deployment tooling and verify its result.
