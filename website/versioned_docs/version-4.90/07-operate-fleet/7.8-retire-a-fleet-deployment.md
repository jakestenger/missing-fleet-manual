# Retire a Fleet deployment

![Explanation](../_assets/icons/explanation-light.svg) Retiring Fleet involves handing off devices, closing external connections, and preserving the information your organization still needs. Plan that work while the service is available so device users and the next management system have a clear transition.

Use the [recovery set in 7.2](7.2-back-up-and-restore-service-state.md) for the final backup and the [credential inventory in 7.6](7.6-maintain-credentials-certificates-and-access.md) to identify access that must be revoked.

## Retire a deployment deliberately

![How-to](../_assets/icons/howto-light.svg) Complete device and external-service work before shutting Fleet down. Enrolments, credentials, and provider assignments can remain active after the server stops answering.

Use this sequence as a retirement plan:

1. Decide which activity history, escrowed credentials, and inventory must be retained, and for how long. Export required information while Fleet is running; later access may require a restore.
2. Release devices or transfer them to their next management system. Follow the platform-specific procedures below.
3. Release external assignments and connections, including enrolment profiles, purchased-app tokens, and calendar and ticket integrations.
4. Revoke external credentials, including identity-provider access and credentials used by an MCP server, as described below.
5. Take a final backup and preserve the key material needed to read it. Verify the recovery set using [7.2](7.2-back-up-and-restore-service-state.md).
6. Decommission the service, then delete retained state according to the agreed schedule.

Confirm device release and provider-side changes before decommissioning. Those steps can require access or communication paths that will no longer be available afterwards.

### Retire an MCP connection

If a Fleet MCP server uses this deployment, revoke its Fleet API-only token, stop and decommission the MCP process, and destroy its stored client bearer and all client copies ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)).

The API token remains a Fleet credential until revoked, including against any surviving Fleet instance that accepts it. The client bearer belongs to the MCP process; Fleet has no record of it to revoke. If you keep that process running for another purpose, replace the bearer everywhere and restart the process so previous holders lose access.



## Release devices, per platform

![Reference](../_assets/icons/reference-light.svg) Each platform has its own release path. Check both the device state and any upstream provider assignment before declaring the transition complete.

### macOS, iOS, and iPadOS

Turn off MDM for each host through Fleet's Actions menu. The [per-host action](../05-manage-devices/5.7-control-devices-and-send-mdm-commands.md#turn-mdm-off-for-one-host) works on Mac, iPhone, and iPad: it queues the removal command and marks the host unenrolled in Fleet.

On macOS, a local fallback is the destructive `profiles remove` procedure in [8.4.4](../08-troubleshooting/8.4-host-side-investigation.md#844-macos-mdm-truth-from-the-host), or a wipe. iOS and iPadOS have no equivalent local command.

Also remove the server assignment in Apple Business. Deleting the [Apple Business token from Fleet](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md#connecting-apple-business) removes Fleet's connection record without calling Apple. Devices stay assigned to the server in Apple Business until that MDM server entry is removed there. Complete both the device release and the provider-side removal.

### Windows

Follow the combined shutdown and uninstall sequence in [2.11](../02-administer-and-deploy-fleet/2.11-configure-windows-management.md#turning-windows-mdm-off). It covers the effects of turning Windows MDM off and the uninstall operation that unregisters MDM and removes fleetd in the same run.

### Android

[Turning Android MDM off](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md#turning-android-mdm-off-deletes-your-enterprise) requests deletion of the Android Enterprise at Google, clears Fleet's connection record, and marks Android hosts unenrolled.

The sequence stops at the first error and does not read back Google's result. A partial teardown can therefore leave Fleet and Google in different states. Confirm in the Google Admin console that the enterprise was removed before completing retirement.

### ChromeOS

The reporting extension is managed through Chrome policy in the Google Admin console ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)). Remove its force-install policy or move the device out of the scoped organizational unit to stop reporting. Fleet provides no device-management or release action for ChromeOS.

### Linux

Remove fleetd to end Linux reporting. Fleet's `uninstall-fleetd-linux.sh`, under `it-and-security/lib/linux/scripts/uninstall-fleetd-linux.sh` in its repository, stops and disables the service and removes its files and package.

Run it as root on the device, or save it as a Fleet script and [batch-run it](../05-manage-devices/5.3-run-and-manage-scripts.md#running-it-on-many-at-once) across the Linux hosts. Linux has no MDM enrolment profile to revoke.

### Verify release

Check the platform's own state: Apple Business device assignments, the Google Admin console, or Windows MDM enrolment status. Fleet can show a host as unenrolled while a provider still holds an assignment.

For fleetd removal, confirm that both the agent process and its service or scheduled-task entry are gone. A successful command exit alone does not establish complete removal.

## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) [7.2](7.2-back-up-and-restore-service-state.md) lists the final backup and key material to retain. [7.6](7.6-maintain-credentials-certificates-and-access.md) covers credentials and certificates to review for revocation.
