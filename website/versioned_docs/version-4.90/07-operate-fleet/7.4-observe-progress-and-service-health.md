# Observe progress, performance, and service health

![Explanation](../_assets/icons/explanation-light.svg) Good monitoring helps you see whether administrators can use Fleet, devices are reporting, and requested work is progressing. Fleet supplies health checks and telemetry for part of that picture. You combine them with device status, delivery evidence, and dependency monitoring to assess the service as a whole.

A passing health check confirms database and Redis connectivity. Agents, scheduled work, or log delivery can still be failing. This chapter explains the available signals, their limits, and ways to test whether your monitoring detects the conditions you care about.

Use your observability platform to build dashboards, route alerts, and page the responsible operators. Those choices belong to your service's operating model.

<a id="measure-service-progress-not-only-uptime"></a>

## Measure service progress across the deployment

![Explanation](../_assets/icons/explanation-light.svg) Track the outcomes from [7.1](7.1-define-the-service-operating-model.md) separately because each can fail while the others continue working.

| Outcome | Signs of a problem |
|---|---|
| **Administrative access** | The interface or API becomes slow or returns errors |
| **Agent reporting** | Hosts stop checking in and inventory ages |
| **Device-management delivery** | Commands and profiles remain queued |
| **Scheduled processing** | Vulnerability, app, or maintenance work stops advancing |
| **Data freshness** | Reporting continues, but the reported information is old |

None of these outcomes is verified by the database and Redis health checks. Give each the additional evidence described below, and document where Fleet does not expose enough information to measure it directly.

## Collect Fleet-native telemetry

![How-to](../_assets/icons/howto-light.svg) Fleet exposes a metrics endpoint and a separate export pipeline. Their coverage overlaps, but neither contains everything from the other.

The metrics endpoint includes HTTP request information, a service-layer subset of administrative methods, and runtime defaults. It has no business metrics for hosts, policies, queues, or freshness.

Configure the endpoint before trying to scrape it. Without configured credentials or an explicit opt-out of authentication, the route is absent. A request can fall through to the web interface instead of returning a metrics-specific error. Verify that you receive metric data as part of setup.

The export pipeline carries traces and metrics, including database-pool statistics, error counters, and cache counters absent from the metrics endpoint. Choose which signals you need from each pipeline.

Add a stable node identity from your platform when collecting telemetry. Fleet regenerates its own instance identifier on every start, so that identifier alone cannot follow the same node across restarts.

### The six metric families and the series you query

Once mounted, `/metrics` exposes six Fleet-registered metric families: four for HTTP handling and two for the service layer. Additional metrics come from the Go runtime, process defaults, or the scrape handler.

The family type determines which Prometheus series to query. Counters use the family name directly. Histograms expose `_bucket`, `_sum`, and `_count` series. Fleet's summary has no quantile targets, so it exposes only `_sum` and `_count`.

| Family | Type | Series you query | Labels |
|---|---|---|---|
| `http_requests_total` | counter | `http_requests_total` | `method`, `code`, `handler` |
| `http_request_duration_seconds` | histogram | `http_request_duration_seconds_bucket`, `_sum`, `_count` | `handler` |
| `http_response_size_bytes` | histogram | `http_response_size_bytes_bucket`, `_sum`, `_count` | `handler` |
| `http_request_size_bytes` | histogram | `http_request_size_bytes_bucket`, `_sum`, `_count` | `handler` |
| `api_service_request_count` | counter | `api_service_request_count` | `method`, `error` |
| `api_service_request_latency_microseconds` | summary | `api_service_request_latency_microseconds_sum`, `_count` | `method`, `error` |

The HTTP `handler` label identifies the route. The service-layer `method` label uses a hand-written name for each wrapped call, and only a subset of administrative methods is wrapped. Its coverage is therefore narrower than the HTTP metrics.

Despite its name, `api_service_request_latency_microseconds` records values in seconds. Use seconds when setting thresholds or interpreting its series.

The separate OpenTelemetry pipeline exports over OTLP. It carries these additional metrics, which do not appear on `/metrics`:

- Request-error counters: `fleet.http.client_errors` and `fleet.http.server_errors`.
- Pre-authentication rejections: `fleet.osquery.preauth_rejections`.
- Host-cache counters: `fleet.host_cache.lookups`, `fleet.host_cache.errors`, and `fleet.host_cache.invalidations`.
- Database connection-pool metrics under `db.client.connection.*`.

## Know the coverage and sampling gaps

![Reference](../_assets/icons/reference-light.svg) Account for the limits of each signal when building a dashboard or alert:

- The health check covers the database and Redis. Object storage is neither included nor probed at startup.
- The overall health result does not identify the failed dependency. Poll the individual checks when you need that distinction.
- Health checks do not test the server private key or the readability of encrypted data ([7.2](7.2-back-up-and-restore-service-state.md)).
- Traces are sampled, so totals derived from them are estimates.

<a id="two-signals-that-report-success-when-they-should-not"></a>

### Interpret freshness and latency carefully

Fleet updates the vulnerability freshness field even when a run returns an empty set. A recent timestamp shows that the pipeline produced a result; by itself, it cannot establish that vulnerability data was found or refreshed.

For service-layer latency, remember the unit mismatch described above. `api_service_request_latency_microseconds` emits seconds. A threshold calculated in microseconds would be wrong by a factor of one million and could prevent the expected alert from firing.



## Monitor operational dependencies

![Reference](../_assets/icons/reference-light.svg) Combine Fleet telemetry with the monitoring provided by each dependency.

| Dependency | Fleet signal | Provider signals to collect |
|---|---|---|
| **MySQL** | Connection-pool statistics through the export pipeline | Connections, replication lag, storage, CPU, and slow queries |
| **Redis** | Limited Fleet-side detail | Memory, evictions, connections, and replication |
| **Object storage** | No Fleet-side health signal | Latency, errors, and availability |

Monitor object storage directly. Fleet does not signal that it is slow or unavailable through its health check; the first visible effect may be an installer that fails or hangs. Storage-side monitoring can help you detect the dependency problem earlier.

## Monitor the Fleet MCP server, if you run one

![Reference](../_assets/icons/reference-light.svg) Pair the MCP server's liveness check with an authenticated read. The SSE liveness endpoint confirms that the process is running, but it does not check Fleet connectivity or continued token validity.

Use a periodic read through the assistant or a scripted tool call, following the setup verification in [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md). This exercises the connection the assistant relies on. Use the MCP logs for operational context and the more verbose request-route logging when investigating a failure; their audit coverage and data-handling limits are also described in 6.6.

## Monitor queues, scheduled work, and feeds

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) To assess background work, look for progress in the data it should produce. Schedule registration and completion records have important limits.

Fleet has around three dozen possible scheduled jobs, with registration depending on edition and configuration. Free registers substantially fewer than Premium. Some schedules, including device-management schedules, register even when the feature is not configured.

No supported endpoint or command exposes a schedule's own run record. That state is written to the database. Even with direct database access, a completed run can contain jobs that all failed, so completion alone does not establish success.

Use these output-oriented checks where available:

| Work | Evidence to examine |
|---|---|
| Vulnerability processing | Freshness field, accounting for empty results as described above |
| Maintained-app and purchased-app refresh | No supported freshness surface was established at this release; record this as a monitoring gap |
| Host vitals, policy results, and software inventory | Per-host update times |
| Queued device work | Queue age from each host's view |

If you use an indirect signal where direct evidence is unavailable, label what it actually measures. This keeps a proxy from appearing to verify more than it does.

Watch queue age alongside volume. A large queue that continues draining may need less attention than a small queue whose oldest item never completes. [7.3](7.3-upgrade-fleet-and-fleetd.md) describes how an activated item can block later work indefinitely.

## Monitor log and integration delivery

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Measure arrivals at external destinations to confirm that logs and webhook deliveries are reaching their consumers. Fleet-side evidence is incomplete, and some delivery failures are easy to miss ([6.5](../06-automate-fleet/6.5-integrations-webhooks-and-external-workflows.md)).

Failures sending osquery status and result logs to an external destination are classified as client errors. They are logged at debug level and excluded from the error store and exception reporting. Monitoring those surfaces alone will miss the delivery failure.

That classification is specific to these osquery log deliveries. Fleet activity, audit delivery, and webhooks have their own failure behavior, described in 6.5. For each destination, track incoming records so you can verify receipt independently.

## Establish baselines and leading capacity signals

![How-to](../_assets/icons/howto-light.svg) Record a baseline before each change. Useful candidates include request latency and error rates, host counts and check-in freshness, queue ages, and provider-side database and cache metrics. Choose the set and expected ranges for your deployment.

These measurements support the upgrade acceptance checks in [7.3](7.3-upgrade-fleet-and-fleetd.md). Without a recorded baseline, an operator has little evidence for deciding whether the service has returned to its earlier behavior.

Use the export pipeline for visibility into resource pressure inside Fleet. The metrics endpoint mainly describes requests; internal pool, cache, and error instrumentation travels through the separate pipeline.

Look for rising latency, connection-pool waits, and growing queue age before errors and timeouts become frequent. [7.5](7.5-maintain-capacity-and-availability.md) explains how to use those leading signals in capacity planning.

## Define and test alerts

![How-to](../_assets/icons/howto-light.svg) Derive alert thresholds from the service objectives in [7.1](7.1-define-the-service-operating-model.md). For each alert, identify the condition it detects, the owner, and the response it should prompt.

A manageable starting set covers administrative errors and latency, agent check-in freshness, device-work queue age, vulnerability freshness, destination log arrivals, and provider dependency signals. Adapt that selection to your deployment and the measurement limits above; it is an operating recommendation, not a set of thresholds supplied by Fleet.

Test the delivery path as well as the rule configuration. Fleet's failing-policy notification path can exercise a real delivery: reset the policy automations and trigger the schedule. A successful trigger response confirms only that the schedule was requested. Require both a new automation activity in Fleet and an arrival at the destination to confirm that the path worked.

For other alerts, exercise your monitoring platform's own delivery test and record its scope. It verifies your alerting path without necessarily exercising the Fleet behavior that would trigger it.

When an alert breaches without an explained change, use the evidence it collected to begin the diagnostic process in [Part VIII](../08-troubleshooting/8.1-diagnostic-method.md).
