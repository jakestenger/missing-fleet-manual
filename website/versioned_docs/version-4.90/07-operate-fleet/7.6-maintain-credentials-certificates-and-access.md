# Maintain credentials, certificates, and privileged access

![Explanation](../_assets/icons/explanation-light.svg) Regular credential maintenance keeps administrators connected, device-management commands flowing, and recovery credentials available when someone needs them. A useful routine combines an inventory, renewal lead times, access reviews, and checks that exercise the affected workflow after each change.

Certificate renewal also needs to account for the key material that protects stored data. Depending on the platform, changing a certificate or replacing a key can affect access to existing disk-recovery credentials. [5.8](../05-manage-devices/5.8-enforce-disk-encryption-and-manage-recovery-credentials.md) explains those credentials; this chapter covers how to preserve their usability during service maintenance.

## Inventory operational trust material

![Reference](../_assets/icons/reference-light.svg) Record the credentials and certificates your deployment uses, their owners, where they are stored, and the workflow affected by expiry or loss.

| Item | Purpose | Effect of expiry or loss |
|---|---|---|
| **HTTPS certificate** | Establishes server trust for agents and administrators | Agents stop connecting when server trust fails |
| **Fleet server private key** | Encrypts stored database assets, including Apple certificate authority material and Linux escrow; supplied separately from MySQL | Losing the key makes those encrypted assets unreadable; issuing a replacement does not recover them |
| **Apple push certificate** | Enables contact with Apple devices | Commands stop arriving ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md)); removing Apple MDM has additional consequences described below |
| **Apple MDM certificate authority** | Protects macOS escrow; stored in MySQL, encrypted under the server private key | Retrieval fails while the authority is inactive |
| **Windows enrolment identity** | Supports Windows enrolment and BitLocker escrow retrieval | Retrieval fails without a corresponding failure in Fleet's availability indicator |
| **Apple Business Manager and App Store tokens** | Support enrolment assignment and purchased apps | Assignment and installation stop |
| **Identity-provider and integration secrets** | Support sign-in, tickets, calendars, and webhooks | The affected integration stops |
| **Fleet MCP API-only token and client bearer** | Allow an assistant to call Fleet through one identity, with a shared client secret over SSE | Neither expires automatically; schedule review and replacement using [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Premium licence** | Establishes entitlement to Premium features | Features continue after expiry at this release; see the version-specific behavior below |

## Monitor expiry, advisories, and entitlement

![How-to](../_assets/icons/howto-light.svg) Use Fleet's renewal warnings where available and maintain an external calendar for the full inventory.

Fleet warns about the Apple push certificate, Apple Business token, and each Volume Purchasing token starting thirty days before expiry and again after expiry. The interface provides an app-wide banner and a coloured Renew date column ([2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md)).

The remaining credentials and keys in the table have no equivalent advance warning through a metric, webhook, email, or in-app alert. Track certificate dates and provider-managed deadlines from the relevant material or external console. For secrets without an automatic expiry, set your own review and rotation schedule.

Add an owner and preparation lead time to each calendar item, following [7.1](7.1-define-the-service-operating-model.md). This gives operators time to obtain access, coordinate consumers, and verify the renewal before the deadline.

<a id="the-licence-is-a-special-case-worth-understanding"></a>

### Track licence expiry independently

At this release, an expired Premium licence does not demote Fleet. Validation deliberately ignores expiry, and the internal entitlement interface cannot ask whether the licence has expired. Premium features therefore continue to work.

Fleet exposes several indicators:

- The configuration endpoint returns the expiry timestamp to any authenticated role. This is the only advance signal.
- A response header marks the licence as expired after the date passes.
- The command-line client and server startup emit warnings.
- The interface can show an after-expiry banner, with lower priority than several other banners.

Poll the timestamp and compare it with the current date to schedule renewal. Treat continued operation after expiry as this release's behavior, without assuming a promised grace period.

Assign someone to monitor security advisories as well. When an advisory requires a release change, use the [upgrade procedure](7.3-upgrade-fleet-and-fleetd.md) with a deadline appropriate to that advisory.

## Renew HTTPS trust without disconnecting agents

![How-to](../_assets/icons/howto-light.svg) Agents validate Fleet's server certificate. A renewal that breaks the trusted chain can stop check-ins across the estate, even if an administrator's browser accepts the certificate.

Use this order:

1. Preserve the hostname and a compatible certificate chain. If the hostname changes, plan a migration so every agent learns the new address.
2. For a private trust root, distribute the new root and confirm that agents have received it before switching the served chain.
3. Replace the served certificate.
4. Verify connectivity from representative agents on every platform.

Watch check-in counts and freshness to confirm that the estate remains connected ([7.4](7.4-observe-progress-and-service-health.md)). If the result differs between your browser and an agent, the connection checks in [8.5](../08-troubleshooting/8.5-fleetctl-debug.md) help distinguish served-chain, reachability, and agent-bundle trust problems.



## Renew MDM certificates and tokens in the safe order

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Renew the Apple push certificate by uploading it over the existing configuration. Keep Apple MDM configured throughout the renewal.

Removing Apple MDM also deactivates its certificate authority material, immediately stopping FileVault credential retrieval. Configuring it again creates a new authority key, leaving escrow protected by the previous key unreachable through Fleet's normal retrieval path.

If Apple MDM has already been removed, pause before reconfiguring it. Preserve the database, backups, and server private key, and handle the loss of retrieval as an incident. Creating a new configuration complicates recovery of the earlier state.

<a id="the-three-escrow-populations-do-not-renew-alike"></a>

### Plan certificate changes for each escrow population

| Population | Material used for decryption | Certificate rollover behavior |
|---|---|---|
| **macOS FileVault** | Apple certificate authority key, with current and historical certificates | Supports rollover while the same authority key is retained |
| **Windows BitLocker** | Current enrolment certificate and key | No historical certificate fallback |
| **Linux LUKS** | Fleet server private key | No certificate is involved; replacing the key loses readability |

macOS provides a safe certificate-rollover path only while the authority key remains the same. Replacing the key that protects an escrow population loses access through that chain on every platform.

This table describes retrieval of existing escrow through Fleet. Device-side recovery options and material preserved outside Fleet may provide additional options during an incident.

Renewing the Windows enrolment certificate makes existing BitLocker escrow unreadable through Fleet even if you retain the same key pair. Retrieval matches the current certificate and does not fall back to historical certificates.

Fleet can continue to show that escrow as available. Windows credentials are marked usable when received and are excluded from the verification job that checks the other platforms. The status therefore retains the result from before the certificate change.

Before renewing, preserve and verify the old certificate and key alongside the recovery set. That material is needed to recover the earlier population. Re-escrowing before the change does not move it to the new certificate, because the old certificate still protects any escrow received then.

After the change, readable credentials require new escrow under the new certificate. Fleet has no single supported operation that re-escrows an existing population on demand. Plan that work for your deployment and verify a post-change credential retrieval. Until retrieval succeeds, treat the new Windows escrow state as unverified regardless of the availability indicator.

## Protect key continuity and recovery credentials

![Reference](../_assets/icons/reference-light.svg) Back up the actual server private key and Windows enrolment identity separately from MySQL ([7.2](7.2-back-up-and-restore-service-state.md)). The Apple certificate authority material is already in the database, but it still needs the server private key for decryption.

Each platform depends on its own chain. Preserving only some of the required material can produce a restore that serves records successfully while leaving part of the recovery-credential population unreadable.

Verify key continuity by retrieving a stored credential from each relevant platform. Existing availability counts describe recorded state and do not exercise decryption; Windows status is especially misleading after a certificate change.

A successful retrieval establishes that Fleet can decrypt that particular stored value. It does not prove that every credential is readable or that the value will unlock a device. Those require separate checks, described in [5.8](../05-manage-devices/5.8-enforce-disk-encryption-and-manage-recovery-credentials.md). You can confirm successful retrieval without displaying or using the secret.

Per-host privileged credentials have their own reveal and rotation procedures. Use the guidance for the [managed local administrator password](../05-manage-devices/5.5-design-setup-and-self-service-experiences.md#retrieve-and-rotate-the-managed-local-administrator-password), and for [Recovery Lock and disk-encryption credentials](../05-manage-devices/5.8-enforce-disk-encryption-and-manage-recovery-credentials.md#reveal-validate-and-repair-disk-recovery-credentials-safely).

## Rotate service and integration secrets

![How-to](../_assets/icons/howto-light.svg) Identify every consumer before changing a secret. The one-identity-per-workflow convention in [6.1](../06-automate-fleet/6.1-automation-design-and-change-control.md) helps make that inventory manageable.

Where the provider supports two credentials at once, create the replacement, distribute it to all consumers, and verify the complete workflow. Revoke the previous credential after those checks pass.

Where only one credential can be active, plan a brief interruption. Agree on a window, prepare the consumers for the new value, switch them, and verify immediately. Include every consumer in the plan so an overlooked job does not fail later.

The Fleet MCP server's API token has no built-in overlap transition. Update the server configuration, restart it, and repeat the verification in [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md). Reissue its client bearer when a client that held it should lose access. Update the server and SSE client configuration, restart, and check accepted and rejected authentication. For stdio, supply the replacement through the client's launch configuration.

## Review privileged access

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Reconcile Fleet access with the people and workflows that still need it. List every user and API-only identity with its role and fleet scope, then compare that list with the workflow inventory from [6.1](../06-automate-fleet/6.1-automation-design-and-change-control.md).

Review session creation times and any endpoint restrictions. This helps identify old tokens and permissions that no longer match the workflow. For identity-provider access, review the group mapping and use the provider's own membership records as the authority for who belongs to each group.

Account for the evidence Fleet does not expose:

| Question | Available evidence |
|---|---|
| When was a token last used? | Fleet records this internally, but no interface returns it |
| Where did a session originate? | No source address, client, or user-agent record is available |
| Which token performed an action? | Multiple tokens on one identity are indistinguishable in the activity record |

Fleet has no dedicated API-token rotation operation. A token is a session credential shown once at creation. Replacing it requires revoking it and authenticating again with a password you control, or recreating the identity ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)).

API-only sessions do not expire automatically. Use periodic review to account for their continued access, and revoke identities that no longer have a justified owner or purpose. The absence of a last-used signal means you cannot establish inactivity from the interface alone.

## Prepare for compromise

![How-to](../_assets/icons/howto-light.svg) Prepare the response before a credential is exposed, including who can revoke it and how to inspect work already requested under it.

1. **Contain access.** Revoke the credential. Revocation stops its next request but does not cancel queued work, so identify outstanding actions separately ([6.1](../06-automate-fleet/6.1-automation-design-and-change-control.md)).
2. **Assess the affected scope.** Review activities with their limits in mind: they identify the account, not the client or individual token, and record only a few sensitive reads.
3. **Replace reachable credentials.** Identify other secrets the compromised credential could access and include them in the response.
4. **Plan any key replacement.** Replacing an exposed server private key makes existing assets encrypted under it unreadable. Account for that recovery consequence before changing it.
5. **Preserve evidence before cleanup.** Keep the relevant database state, server logs, and external log records.
6. **Re-enrol or re-escrow where needed.** Include devices whose trust depended on the compromised material.

Follow queued work through to a known outcome after revocation. It can continue executing under the earlier authorization and needs its own containment decision.
