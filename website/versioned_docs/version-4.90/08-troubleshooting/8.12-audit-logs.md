# Audit logs: who did what, when

Fleet activities help you trace configuration changes, administrative actions, and results reported to the server. They are stored in MySQL and available through the UI and API. With Premium, you can also stream them to an external audit-log destination. This chapter explains what the records contain and how to use them in an investigation.

## 8.12.1 The short answers

| Question | Answer |
|---|---|
| Where do the rows live | `activity_past` in MySQL, with a host join table `activity_host_past` |
| Is it on by default | The rows are always written. **Streaming** them out is off by default (`activity_enable_audit_log` defaults to `false`) |
| Is it Premium | Reading is free. External streaming is Fleet Premium |
| Retention | Unlimited until you enable `activity_expiry_settings.activity_expiry_enabled` |
| Does it cover host-side events | Selected device reports are included, but general host-side history requires other sources: [8.12.6](#8126-coverage-of-device-side-events) |

## 8.12.2 The table

`activity_past` holds the rows themselves:

| Column | Type | Meaning |
|---|---|---|
| `id` | `int unsigned` auto-inc | Row ID. Monotonic, and the pagination cursor the API uses |
| `created_at` | `timestamp(6)` | When the action happened. Microsecond precision. Default `CURRENT_TIMESTAMP(6)` |
| `user_id` | `int unsigned` nullable | FK to `users.id`, `ON DELETE SET NULL` |
| `user_name` | `varchar(255)` nullable | Actor name **snapshotted at write time** |
| `user_email` | `varchar(255)` NOT NULL, default `''` | Actor email, also snapshotted |
| `activity_type` | `varchar(255)` NOT NULL | The type string, e.g. `edited_policy` |
| `details` | `json` nullable | Type-specific payload. Shape differs per type |
| `streamed` | `tinyint(1)` NOT NULL default `0` | Whether the audit streamer has shipped this row |
| `fleet_initiated` | `tinyint(1)` NOT NULL default `0` | `1` when the activity type reported itself as automation. `0` is not evidence a person acted |
| `host_only` | `tinyint(1)` NOT NULL default `0` | `1` hides the row from the global feed |

`activity_host_past` is `(host_id, activity_id)`, primary key on both, with `ON DELETE CASCADE` from `activity_past`. That is the many-to-many link that makes a host's own activity list possible.

Update saved SQL that uses the former table names `activities` and `host_activities`. Their current names are `activity_past` and `activity_host_past`. Index names such as `activities_created_at_idx` and `idx_activities_type_created`, and some REST reference wording, still use the earlier names.

<a id="two-columns-that-will-surprise-you"></a>

### Historical actor values and feed visibility

`user_name` and `user_email` preserve the actor's values at the time of the activity. Deleting the user sets `user_id` to null but leaves those stored values available.

While the user still exists, the API fills `actor_full_name`, `actor_email`, `actor_gravatar`, and `actor_api_only` from the current user record. A later name or email change can therefore make the API response differ from the historical values in MySQL. Read the table directly when you need the original identity values.

After user deletion, the API uses the stored name and email because there is no user record to enrich the response.

An activity type can set `host_only = 1` when writing a row. These rows appear in the host's feed but are excluded from the global feed. If an expected event is absent globally, check the host endpoint or query the table with its host join.

## 8.12.3 Entry shape

The API response and the streamed record are the same object:

| JSON field | Source | Notes |
|---|---|---|
| `id` | `activity_past.id` | Omitted when zero |
| `uuid` | `upcoming_activities.execution_id` | Populated for **upcoming** activities only, not past rows |
| `created_at` | `created_at` | |
| `type` | `activity_type` | |
| `actor_id` | `user_id` | Null when no user was attached, and null when the acting user has since been deleted. Not tied to `fleet_initiated` |
| `actor_full_name` | live lookup on `users.name` | Current name, not the stored copy. Falls back to `activity_past.user_name` when `actor_id` is null |
| `actor_email` | live lookup on `users.email` | Same. Stored as NOT NULL default `''`, so an absent actor is an empty string rather than a null |
| `actor_gravatar` | live lookup on `users.gravatar_url` | |
| `actor_api_only` | live lookup on `users.api_only` | Whether the actor is an API-only user |
| `fleet_initiated` | `fleet_initiated` | |
| `details` | `details` | Raw JSON, shape per type |

The `streamed` bookkeeping column stays inside Fleet and never appears in the output.

A real record:

```json
{
  "created_at": "2023-07-27T14:35:08Z",
  "id": 25,
  "actor_full_name": "Anna Chao",
  "actor_id": 3,
  "actor_gravatar": "",
  "actor_email": "",
  "type": "installed_software",
  "fleet_initiated": false,
  "details": {
    "status": "installed",
    "host_id": 1272,
    "host_display_name": "MacBook Pro",
    "policy_id": null,
    "policy_name": null,
    "install_uuid": "23c18ea1-8cd7-4af4-a1d8-f2666993a66b",
    "self_service": false,
    "software_title": "zoom.us.app",
    "software_package": "ZoomInstallerIT.pkg"
  }
}
```

`details` contains the type-specific payload. Check field names against Fleet's audit-log reference at fleetdm.com/docs/contributing/audit-logs before building a parser or JSON query.

At 4.90.0 the server defines 191 activity types and the reference covers 157, leaving 34 undocumented there. Examples include `ran_automation_webhook`, `ran_custom_mdm_command`, `added_certificate`, `reset_policy`, recovery-lock password types, and conditional-access types. Use the discovery query below to see which types your deployment has recorded.

## 8.12.4 Activity types: the categories

SELECT DISTINCT activity_type FROM activity_past ORDER BY activity_type;

<a id="attribution-has-three-outcomes-not-two"></a>

### Interpreting actor and automation fields

Read the actor fields together with `fleet_initiated`. Only 26 activity types implement the automation self-report, and Fleet sets the flag only when that report returns true. Other events retain `0`, including system and device events without a person behind them.

| What you see | What it means |
|---|---|
| A non-empty actor identity | Attributed to that user. Still true when the user has been deleted, in which case `actor_id` is null and only the stored name and email remain |
| `fleet_initiated: true` | The activity type reported itself as automation. Fleet writes the literal actor name `Fleet` into the stored row |
| No actor and `fleet_initiated: false` | Unattributed. A system or device path with no user behind it. Read the type and the `details` payload; do not name a person |

For example, `mdm_unenrolled` can follow an administrator's action, a device checkout, or reconciliation. The type and a false automation flag do not identify a person; use the actor and details fields to establish attribution.

Some automated paths also retain the user who uploaded an installer. The stored row can contain `fleet_initiated = 1`, `user_name = 'Fleet'`, and a non-null `user_id`. API enrichment then displays the current user's name. Retain the automation flag in reports even when an actor is present.

## 8.12.5 Reading it

### API

| Endpoint | Returns |
|---|---|
| `GET /api/v1/fleet/activities` | Global feed. `host_only = 1` rows are withheld |
| `GET /api/v1/fleet/hosts/:id/activities` | That host's past activities |
| `GET /api/v1/fleet/hosts/:id/activities/upcoming` | Queued activities for that host, still waiting to run |
| `DELETE /api/v1/fleet/hosts/:id/activities/upcoming/:activity_id` | Cancels a queued activity |
| `GET /api/latest/fleet/policies/:id/automation_activities` | Activities generated by one policy's automation |

All five are in Fleet's REST API reference at fleetdm.com/docs/rest-api/rest-api.

Query parameters on the global endpoint:

| Parameter | Use |
|---|---|
| `page`, `per_page` | `per_page` defaults to 10,000 and is capped at 10,000. Set a page size appropriate to the query |
| `order_key`, `order_direction` | `asc` is the default direction. For newest-first results, use `order_key=created_at&order_direction=desc` |
| `after` | Cursor. Requires `order_key`, uses that column |
| `query` | Free text over `actor_full_name` and `actor_email`. The `details` payload is out of its reach |
| `activity_type` | Exact type string |
| `start_created_at`, `end_created_at` | Time-window bounds. This is the parameter pair that makes incident correlation practical |

To read a specific incident window:

```bash
fleetctl api \
  '/api/v1/fleet/activities?order_key=created_at&order_direction=desc&start_created_at=2026-08-19T13:00:00Z&end_created_at=2026-08-19T15:00:00Z&per_page=500'
```

Or with plain `curl`, once `FLEET_URL` and `FLEET_API_TOKEN` are set:

```sh
export FLEET_URL=https://fleet.example.com          # add your URL prefix here if you serve one
export FLEET_API_TOKEN=$(fleetctl config get token | awk '{print $NF}')
```

Handle all three attribution states explicitly. When no actor exists, `actor_email` is an empty string, which a `//` null fallback does not catch:

```bash
curl -sH "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/api/v1/fleet/activities?order_key=created_at&order_direction=desc&start_created_at=2026-08-19T13:00:00Z&end_created_at=2026-08-19T15:00:00Z&per_page=500" \
  | jq -r '.activities[] | [.created_at, .type,
      (if .fleet_initiated then "automation"
       elif (.actor_email // "") != "" then .actor_email
       elif (.actor_full_name // "") != "" then .actor_full_name
       else "unattributed" end)] | @tsv'
```

Use the top-level `fleetctl api` command for activity requests. There is no `get api` subcommand and, through 4.90.0, no dedicated activities command.

The global feed requires a global role. Host activity is authorized against the host's fleet, so a fleet-scoped user can read that host's history without access to the global feed. Direct MySQL access requires separate infrastructure permissions in a self-hosted deployment. Choose the source available to your investigation.

### UI

The home page and each host page have activity feeds. They render `details` as readable descriptions; use the API when you need the full payload. UI placement and presentation are volatile surfaces.

### MySQL

The global feed, last two hours, actor resolved:

```sql
SELECT ap.id,
       ap.created_at,
       ap.activity_type,
       ap.fleet_initiated,
       COALESCE(ap.user_email, '(none)') AS actor,
       ap.details
FROM   activity_past ap
WHERE  ap.host_only = 0
  AND  ap.created_at >= NOW() - INTERVAL 2 HOUR
ORDER  BY ap.created_at DESC;
```

Everything touching one host, including `host_only` rows the global feed hides:

```sql
SELECT ap.created_at, ap.activity_type, ap.user_email, ap.fleet_initiated, ap.details
FROM   activity_past ap
JOIN   activity_host_past ahp ON ahp.activity_id = ap.id
WHERE  ahp.host_id = 1272
ORDER  BY ap.created_at DESC
LIMIT  200;
```

To summarize the kinds of changes in an incident window:

```sql
SELECT activity_type, COUNT(*) AS n, MIN(created_at) AS first, MAX(created_at) AS last
FROM   activity_past
WHERE  created_at BETWEEN '2026-08-19 13:00:00' AND '2026-08-19 15:00:00'
GROUP  BY activity_type
ORDER  BY n DESC;
```

To extract a field from `details`, such as the fleet on a transfer:

```sql
SELECT created_at, user_email,
       details->>'$.team_name' AS team_name,
       JSON_LENGTH(details->'$.host_ids') AS host_count
FROM   activity_past
WHERE  activity_type = 'transferred_hosts'
  AND  created_at >= NOW() - INTERVAL 7 DAY
ORDER  BY created_at DESC;
```

Verify each JSON path against the activity type's payload. MySQL requires valid JSON but does not enforce a shared `details` structure.

To count records waiting for the audit streamer:

```sql
SELECT streamed, COUNT(*), MIN(created_at), MAX(created_at)
FROM   activity_past
GROUP  BY streamed;
```

[8.6](8.6-server-state.md) covers other MySQL state useful during an investigation.

## 8.12.6 Coverage of device-side events

Activities are not a complete history of events on a device. They contain actions and observations for which Fleet writes an activity type.

That includes some device reports: Apple `CheckOut` and Android notifications can produce `mdm_unenrolled`, enrollment produces `mdm_enrolled`, and Orbit script or software results produce activities when they return. Device-originated events may have no user attribution.

Local changes outside these reporting paths, such as removing an agent or turning off encryption at the keyboard, have no corresponding activity. Profile or host-state reconciliation can update Fleet's view without creating a general history of that drift.

Use the following sources for device-side questions:

| You want to know | What the audit log holds | Where the answer is |
|---|---|---|
| How fleetd was removed from a device | An uninstall Fleet performed. A local `sudo` uninstall, an MDM removal outside Fleet, an imaging event, or another management tool taking the package off are all invisible to it | [8.4](8.4-host-side-investigation.md) for on-host state, [8.2](8.2-log-surfaces.md) for agent logs |
| Whether a user deleted a configuration profile locally | Fleet's own profile delivery and removal | [8.4](8.4-host-side-investigation.md), [8.8](8.8-apple-mdm-diagnostics.md) |
| Whether someone disabled FileVault on the machine | The Fleet setting change | [8.4](8.4-host-side-investigation.md) |
| Who ran a command on the host outside Fleet | `ran_script` rows for scripts Fleet dispatched | Host-side OS audit facilities, not Fleet |
| Whether the agent stopped running, and when | Nothing. There is no `agent_stopped` type | [8.4](8.4-host-side-investigation.md); host `seen_time` in [8.6](8.6-server-state.md) |

For a locally removed agent, inspect package receipts, launchd state, and local installer or removal history. Missing Fleet activities alone cannot establish how the agent was removed or who removed it.

An unattributed `mdm_unenrolled` records Fleet's observation and its timing. It may help establish when Fleet learned of the change without identifying the person responsible.

## 8.12.7 Diagnostic use: "what changed"

Use the audit log to check recorded Fleet changes near the onset identified in [8.1](8.1-diagnostic-method.md). Pair it with version, repository, and host-side evidence for changes outside activity coverage.

### Procedure

1. Establish the onset time from the first bad result, failed check-in, or alert. Aim for minute-level precision when the evidence allows it.
2. Start with a focused window, such as the two hours before onset. Widen it if the first query does not cover the likely change.
3. Summarize by `activity_type` using [8.12.5](#8125-reading-it). Look for changes unusual for this deployment, alongside relevant high-volume activity.
4. Inspect automation and actor attribution separately. `fleet_initiated = 1` identifies self-reported automation; rows with `0` can still be system or device events. Use actor fields to identify attributed actions.
5. Compare other change sources in [8.12.9](#8129-other-what-changed-sources), especially if the activity window has no relevant entry. Some Fleet settings and external changes have no activity type.

### High-value types when correlating

| Symptom onset | Types to look for | Why |
|---|---|---|
| Broad, many hosts, all at once | `applied_spec_team`, `applied_spec_policy`, `applied_spec_saved_query`, `edited_agent_options`, `edited_enroll_secrets` | These are the GitOps apply footprint. A burst of `applied_spec_*` at one timestamp is a GitOps run |
| One fleet's hosts only | `applied_spec_team`, `transferred_hosts`, `edited_agent_options` | Configuration scoped to the fleet, or hosts transferred into a different configuration |
| Specific hosts, no pattern | `transferred_hosts` | Check whether the affected host IDs appear in a transfer's `details.host_ids` |
| Policy results flipped | `edited_policy`, `created_policy`, `deleted_policy`, `reset_policy` | An edited query changes pass/fail without anything on the host changing |
| Profiles reinstalling or churning | `edited_macos_profile`, `created_macos_profile`, `deleted_macos_profile`, `resent_configuration_profile_batch`, and the Windows/Android/declaration equivalents | A profile edit triggers redelivery to every matching host |
| Enrollment newly failing | `edited_enroll_secrets`, `disabled_windows_mdm`, `disabled_android_mdm`, `enabled_gitops_mode` | Rotated secrets and disabled MDM both present as enrollment failure |
| Encryption or key access questions | `enabled_macos_disk_encryption`, `disabled_macos_disk_encryption`, `read_host_disk_encryption_key` | The read type also answers the access question |
| Query load spike on hosts | `created_saved_query`, `edited_saved_query`, `live_query` | A newly scheduled expensive report, or someone running live reports at scale |
| Config changes stopped landing | `enabled_gitops_mode` | GitOps mode makes the managed interface surface read-only. It does not restrict the API, so a change arriving that way is not evidence against it |

<a id="two-traps"></a>

### Time zones and delivery confirmation

Set the MySQL session time zone before comparing `created_at` with timestamps from other systems:

```sql
SET time_zone = '+00:00';
```

The API returns RFC3339 with an explicit offset, which is one reason to prefer the API when you are correlating across tools.

An `edited_policy` activity records a saved change. To confirm delivery or application, inspect the state tables in [8.6](8.6-server-state.md) or the host checks in [8.4](8.4-host-side-investigation.md). Before-and-after values are available only if that type includes them in `details`.

## 8.12.8 Streaming it out

The audit log is one of Fleet's log streams, with its own destination plugin, separate from the osquery result and status streams and from the server's own output. Which stream is which is [8.3](8.3-server-logs.md); the full destination list is [8.2](8.2-log-surfaces.md).

### Config

From Fleet's server configuration reference, fleetdm.com/docs/configuration/fleet-server-configuration:

| Setting | Env var | Default | Effect |
|---|---|---|---|
| `activity_enable_audit_log` | `FLEET_ACTIVITY_ENABLE_AUDIT_LOG` | `false` | Master switch. Nothing streams until this is `true` |
| `activity_audit_log_plugin` | `FLEET_ACTIVITY_AUDIT_LOG_PLUGIN` | `filesystem` | Destination. No effect unless the switch above is on |
| `filesystem_audit_log_file` | `FLEET_FILESYSTEM_AUDIT_LOG_FILE` | `/tmp/audit` | Path, `filesystem` plugin only |
| `filesystem_enable_log_rotation` | `FLEET_FILESYSTEM_ENABLE_LOG_ROTATION` | `false` | Rotates the active file at `filesystem_max_size`, default 500 MB. Shared with the osquery result and status files |

`filesystem_max_size` rotates the active file. `filesystem_max_age` and `filesystem_max_backups` limit retained rotated files to 28 days and 3 files by default, subject to whichever limit is reached first. A zero disables the corresponding age or count limit. Fleet also rotates on `SIGHUP`, which can start a fresh capture file.

YAML form:

```yaml
activity:
  enable_audit_log: true
  audit_log_plugin: firehose
```

Choose a persistent destination when enabling streaming. The defaults write unrotated files to `/tmp/audit` on each node, where operating-system cleanup or container replacement can remove them. Set an appropriate file path and rotation policy, or configure an external destination.

### Destinations that carry it

`filesystem`, `firehose`, `kinesis`, `lambda`, `pubsub`, `kafkarest`, `nats`, `splunk`, `stdout`. `stdout` needs no further configuration. Each of the others has its own flag namespace, and the configuration reference gates every one of those flags on `activity_audit_log_plugin` being set to that plugin **and** `activity_enable_audit_log` being `true`.

`webhook` appears as a destination in Fleet's log destinations guide (fleetdm.com/guides/log-destinations) and is absent from the `activity_audit_log_plugin` option list. Treat audit-over-webhook as unsupported.

### Mechanism

| Property | Value |
|---|---|
| Trigger | Cron schedule `activities_streaming`, interval **5 minutes** |
| Selection | Rows with `streamed = 0` **and `host_only = 0`**, ordered by `id` ascending, cursor-paginated on `id`. Streaming reuses the global feed query, so it inherits the global feed's exclusion |
| Batch | 500 rows per fetch, looping until a fetch comes back short |
| Write granularity | **One row per write to the destination**, deliberately, so Fleet can tell which rows landed |
| Payload | The same JSON object the API returns, one object per row |
| Bookkeeping | `streamed` flips to `1` on the rows the destination accepted |
| On error | Stops at the first failed row, marks the ones before it, retries the rest on the next 5-minute tick |
| Licensing | Fleet Premium. Fleet builds the audit logger under a Premium licence and skips it otherwise |

Account for filtering, scheduling, and the initial backlog:

- Rows with `host_only = 1` are excluded from streaming and remain `streamed = 0`. Events visible only on a host page will therefore be absent from this audit stream. [2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md) covers delivery configuration.
- The schedule runs every five minutes. A row can wait nearly a full interval before the next run; destination errors or backlog can add further delay. Account for this when setting alert timing.
- Count the eligible backlog with the streamer's filter, `streamed = 0 AND host_only = 0`, so permanently excluded host-only rows do not inflate it:

  ```sql
  SELECT COUNT(*) FROM activity_past WHERE streamed = 0 AND host_only = 0;
  ```

If that count grows, inspect `activities_streaming` in `cron_stats` and the server's `streamed events` message and `count` attribute ([8.6](8.6-server-state.md)). Check destination errors as well as whether the schedule runs.

Enabling streaming includes existing eligible history. The first run reads global-visible unstreamed rows in 500-row batches, which can create a substantial burst on an older deployment. Allow capacity for this backfill if you intend to retain that history externally.

One node streams per tick using a schedule lock in MySQL's `locks` table. A stuck holder can delay streaming; inspect it as you would another cron lock.

## 8.12.9 Other "what changed" sources

Use these sources to supplement recorded Fleet activities:

| Source | What it covers that the audit log does not | How to read it |
|---|---|---|
| GitOps repository history | The **content** of the change. The audit log records that `applied_spec_team` happened; the repo records what the YAML said before and after, who authored it, and which PR it came from | `git log`, `git diff` on the config repo. Correlate the CI run timestamp against the `applied_spec_*` timestamps |
| Fleet server version | A server upgrade changes behavior without producing any activity row | `GET /api/v1/fleet/version`; the startup banner in the server log ([8.3](8.3-server-logs.md)); `migration_status_tables` in MySQL for the migration floor. Compare the version you find against its release notes at github.com/fleetdm/fleet/releases |
| Agent version | fleetd and osquery version changes are per-host and are not activities | `hosts.osquery_version` and the fleetd version in host details ([8.6](8.6-server-state.md)) |
| Host OS updates | An OS minor version bump changes query results, profile behavior, and MDM behavior. Not an activity | `hosts.os_version` and `operating_systems` ([8.6](8.6-server-state.md)) |

Use `fleetctl debug errors` alongside this timeline for server faults. It does not record configuration changes or client 4xx errors ([8.3](8.3-server-logs.md), [8.5](8.5-fleetctl-debug.md)).

Check server and agent version changes even when the activity window is empty. Neither upgrade creates an activity row. [8.1](8.1-diagnostic-method.md) shows how to combine these sources.

## 8.12.10 Retention and volume

| Property | Value |
|---|---|
| Default retention | **Unlimited.** Rows accumulate for the life of the deployment until expiry is enabled |
| Expiry switch | `activity_expiry_settings.activity_expiry_enabled` |
| Expiry window | `activity_expiry_settings.activity_expiry_window`, in **days** |
| Cleanup job | `cleanup_activities`, inside the `cleanups_then_aggregation` schedule |
| Per-run delete cap | **5,000 rows**, a cap Fleet sizes as adequate for deployments generating about 120,000 activities per day |

Both expiry settings are in Fleet's YAML reference, fleetdm.com/docs/configuration/yaml-files. GitOps form:

```yaml
org_settings:
  activity_expiry_settings:
    activity_expiry_enabled: true
    activity_expiry_window: 30
```

The expiry switch also enables live-report cleanup using the same window.

Activity expiry removes only rows without an `activity_host_past` link. Host-linked activities remain exempt until the link is removed, for example by deleting the host. [1.5](../01-foundations/1.5-audit-and-activity.md) explains the model. A large host-linked history can therefore remain while expiry works normally.

Cleanup removes at most 5,000 eligible rows per run. Applying a shorter window to a large history takes multiple runs to clear the backlog.

Monitor the eligible rows with:

```sql
SELECT COUNT(*) AS eligible
FROM   activity_past ap
LEFT   JOIN activity_host_past ahp ON ahp.activity_id = ap.id
WHERE  ahp.activity_id IS NULL
  AND  ap.created_at < NOW() - INTERVAL 30 DAY;
```

Compare this count across cleanup runs, allowing for newly eligible rows. If the backlog does not drain, check `cleanups_then_aggregation` and its errors in `cron_stats` ([8.6](8.6-server-state.md)). The total table count can stay high because linked rows remain exempt.

If you need existing history at the external destination, enable streaming and let its backlog drain before enabling expiry. Cleanup can delete unstreamed eligible rows, removing them before export.

### Volume drivers

Measure activity volume for your deployment, including policy-triggered installs, automations, and device lifecycle events. Their contribution depends on how you use Fleet:

```sql
SELECT fleet_initiated, user_id IS NOT NULL AS has_actor, COUNT(*)
FROM   activity_past
WHERE  created_at >= NOW() - INTERVAL 7 DAY
GROUP  BY 1, 2;
```

Use that distribution when sizing the destination and investigating a volume change.

`activity_past` carries seven secondary indexes, among them `idx_activities_type_created` on `(activity_type, created_at)`. Filter on those two columns and the query is indexed. Filter on `details` and MySQL scans the whole JSON column.

### `preserve_host_activities_on_reenrollment`

`activity_expiry_settings.preserve_host_activities_on_reenrollment` is read in one place: the **Apple MDM** re-enrollment reset. When it is `false`, that reset deletes the host's `activity_host_past` rows and deactivates its queued MDM commands. When it is `true`, both survive.

The setting preserves activity links and queued commands during the Apple reset. Other host reference tables, including `host_mdm_commands`, are still cleared, so it does not preserve all host history.

Removing `activity_host_past` links leaves the activity rows in MySQL but removes them from the host timeline. It also makes those rows eligible for expiry. With expiry enabled, the records can later disappear from the table as well.

Read the configured value before interpreting a re-enrolled host's history. The migration set it to `true` for deployments that already had users and `false` for installs without users, so deployments on the same version can differ. This setting is not covered by the published configuration reference.

## 8.12.11 Compliance use

For reviews of privileged activity, relevant types include `read_host_disk_encryption_key`, `viewed_host_recovery_lock_password`, `read_managed_local_account`, `changed_user_global_role`, `changed_user_team_role`, `user_logged_in`, `user_failed_login`, and `wiped_host`. Select the types and retention window needed for the review.

For evidence requiring separate retention and access controls, stream eligible activities to a destination configured for those requirements. Fleet's MySQL rows can be changed or deleted by database administrators and removed by expiry. Fleet does not sign or hash-chain them.
