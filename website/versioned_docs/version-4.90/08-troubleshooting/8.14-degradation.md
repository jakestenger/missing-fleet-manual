# Diagnosing degradation

Use this chapter when operations are slow, resource use is high, or Fleet components appear to interfere with another product. The tests compare query cost, configured limits, shared resources, and scale. For a delivery failure, begin with [8.1](8.1-diagnostic-method.md).

Fleet provides server CPU, memory, goroutine, and execution-trace captures through `fleetctl debug`. An archive collected during the slowdown preserves several of these together. Start with a small control test, then use the relevant sections below to collect evidence for the symptom you see.

## 8.14.1 The four causes

| Cause | The question | Distinguishing observation |
|---|---|---|
| **Resource contention** (§8.14.6) | Is Fleet competing with something else for CPU, memory, or I/O? | Compare onset with other products' changes and collect host or node resource evidence alongside Fleet profiles. |
| **Scale ceiling** (§8.14.7) | Does it work small and fail large? | The same operation succeeds against a small target set and fails against a large one. Failure moves with **cardinality**, not with content. |
| **Limits and quotas** (§8.14.4) | Is something silently truncating or refusing? | Partial results with **no error**, or a hard cliff at a round number. Reducing size makes it work. |
| **Query cost** (§8.14.5) | Is the work itself expensive? | The control test passes and the real query does not. Cost visible per query in `osquery_schedule`, or per endpoint in a CPU profile. |

A configured limit and a capacity ceiling can both appear only as volume grows. Check the relevant limits first. If changing a limit resolves the same workload, that helps distinguish the boundary from a broader resource shortage.

## 8.14.2 Establish a control first

For a live-report problem, begin with a query that does very little work:

```sql
SELECT 1 WHERE 1 = 0;
```

Run it as a live report against the affected hosts. Fleet's own live report troubleshooting guide opens with the same test.

Record elapsed time, target and responding-host counts, and rows or bytes returned for both the control and the real query. Full coverage confirms that the tested path completed, but the timing tells you whether it performed adequately. Keep offline or otherwise missing targets visible in that comparison.

| Control | Real query | What that supports |
|---|---|---|
| Fast, 100% | Fast, 100% | Neither the path nor the query is the constraint at this size. Look at result volume, the destination, and whether the reported symptom is somewhere else entirely |
| Fast, 100% | Slow, 100% | Cost in the query itself, or in the volume it returns. §8.14.5 |
| Fast, 100% | Partial | Several possibilities, and they need separating: the query crashing or hanging on some hosts, the osquery watchdog denylisting it, the `FLEET_LIVE_QUERY_REST_PERIOD` deadline, or a result set large enough to hit a buffer limit (§8.14.4). Fleet's guide names the first three |
| Slow or partial | Defer the larger workload | Investigate the shared path using the layer tests below |

A slow control is useful evidence. Its elapsed time becomes the baseline for the layer-by-layer tests that follow.

### Bypass one layer at a time

| Test | Removes from the path | If it now works |
|---|---|---|
| Same query through `fleetctl report --query '…' --hosts '…' --exit` | Browser rendering | Investigate the browser and its network or rendering behavior |
| A different browser | That browser's state | Same |
| The synchronous live report API (below) | **Websockets** | Inspect the websocket path, including upgrades and connection lifetime |
| `/healthz?check=mysql` and `/healthz?check=redis` | Everything but one dependency | Read each result to identify a failing dependency check on this node |

To test the synchronous API, use the following HTTP requests. They assume `FLEET_URL` and `FLEET_API_TOKEN` are set:

```sh
export FLEET_URL=https://fleet.example.com          # add your URL prefix here if you serve one
export FLEET_API_TOKEN=$(fleetctl config get token | awk '{print $NF}')
```

```sh
curl -X POST \
  -H "Authorization: Bearer $FLEET_API_TOKEN" \
  -H "Content-Type: application/json" \
  "$FLEET_URL/api/v1/fleet/reports/<report_id>/run" \
  -d '{"host_ids": [375]}'
```

`POST /api/v1/fleet/reports/:id/run` replaced `GET /api/v1/fleet/queries/run` in Fleet 4.43.0, and the old endpoint still answers. It is a simplified implementation, sized for a handful of hosts rather than thousands (fleetdm.com/docs/rest-api/rest-api).

`/healthz` returns HTTP 200 when the server is up **and** holds healthy MySQL and Redis connections, and 500 otherwise, with detail in the server log. The `check` URL parameter narrows it to one dependency (fleetdm.com/docs/deploy/reference-architectures).

### How long the synchronous API waits

`FLEET_LIVE_QUERY_REST_PERIOD` controls the result deadline and a floor for the server's write timeout. When unset, those paths use different defaults:

| Use | Default when unset |
|---|---|
| Deadline for collecting live report results | **25s** |
| Floor for the HTTP server's write timeout, plus 10s | **90s** (so 100s) |

Setting the variable moves both: the deadline becomes your value, and the write timeout floor becomes your value plus 10 seconds.

The troubleshooting guide's approximately 100-second default describes the HTTP write timeout. The REST reference documents the 25-second result deadline. The server uses a 90-second base plus 10 seconds for the write-timeout floor; keeping that separate allows long uploads to complete.

Allow enough time for hosts to check in. If `distributed_interval` exceeds the result-collection window, the API can finish before hosts receive the query. Compare the effective interval with the deadline before changing either. Fleet recommends a 10-to-30-second distributed interval.

## 8.14.3 Server profiling with `fleetctl debug`

| Command | Produces | Answers |
|---|---|---|
| `fleetctl debug profile` | 30-second CPU profile | Where is the server burning CPU |
| `fleetctl debug heap` | Heap-allocated memory | What is holding memory, and is it growing |
| `fleetctl debug goroutine` | Stack traces of every goroutine, meaning each concurrent task the server has in flight | Deadlocks, stuck workers, runaway concurrency, goroutine leaks |
| `fleetctl debug trace` | 1-second execution trace | Scheduling, blocking, and latency detail |
| `fleetctl debug cmdline` | The server's argv, exactly as the kernel holds it | Shows startup arguments. Inspect environment variables and configuration files separately for settings supplied through those sources. |
| `fleetctl debug errors` | Recorded server errors, from Redis | Recent error classes, non-destructive unless `--flush` |
| `fleetctl debug migrations` | Missing or unknown migrations | Schema drift after an upgrade |
| `fleetctl debug db-locks` | Waiting and blocking transactions | Lock contention in MySQL |
| `fleetctl debug db-innodb-status` | `SHOW ENGINE INNODB STATUS` | InnoDB internals, deadlock history, buffer pool |
| `fleetctl debug db-process-list` | `SHOW PROCESSLIST` | Long-running or piled-up queries, right now |
| `fleetctl debug archive` | Thirteen diagnostic captures in one `.tar.gz` | The usual first capture. **It does not include `migrations`**, so run that separately whenever an upgrade is anywhere near the timeline |

Flags on the capture commands: `--outfile` (`OUTFILE`), `--config`, `--context`, `--debug`. `errors` adds `--stdout` and `--flush`. Two are different: `migrations` takes only `--config` and `--context`, and `connection` takes those two plus `--fleet-certificate`. Neither writes a file, so `--outfile` is not available on either.

Through `fleetctl` the durations are fixed: `profile` samples for 30 seconds and `trace` for 1 second. For a longer sample, call the endpoint directly (below).

`fleetctl debug goroutine` writes binary pprof data, readable with `go tool pprof`. To obtain text stacks for a terminal, call the endpoint with the text option:

```sh
curl -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/debug/pprof/goroutine?debug=2" > goroutines.txt
```

### What `archive` contains

Thirteen files, in this order:

`allocs` · `block` · `cmdline` · `errors` · `goroutine` · `heap` · `mutex` · `profile` · `threadcreate` · `trace` · `db-locks` · `db-innodb-status` · `db-process-list`

Four of those come only from `archive`, with no subcommand of their own:

| Profile | Answers |
|---|---|
| `allocs` | All allocations since start, including freed ones. Heap shows what is live; allocs shows what churned. |
| `block` | **Empty in practice.** Fleet never enables block-profile sampling, so this member carries no samples. An empty file is the expected result, not evidence that nothing is contending |
| `mutex` | **Empty in practice**, for the same reason. Read neither of these as a finding about contention ([8.5.5](8.5-fleetctl-debug.md#855-fleetctl-debug-archive)) |
| `threadcreate` | What is creating OS threads |

The collector continues after an individual item fails and still writes an archive. Record each `Failed <profile>` message, then check the member list so the recipient knows which evidence is missing.

Missing database privileges can cause `Failed db-innodb-status` and `Failed db-locks`. Requests can also time out or be refused. Inspect the reported error for each absent member.

### Consuming the output

Use `go tool pprof` for profile data and `go tool trace` for execution traces. Go's runtime includes function names in the captured profiles. Since Fleet 4.86.0, released binaries omit debug symbols, so supplying the binary alongside a profile does not add those symbols ([8.5](8.5-fleetctl-debug.md)).

Archive member paths begin with the archive filename. Extract into a new directory and strip that prefix to avoid a file/directory name collision ([8.5](8.5-fleetctl-debug.md#855-fleetctl-debug-archive)):

```sh
archive='fleet-profiles-archive-20260819120000Z.tar.gz'
outdir='fleet-profiles'
mkdir -p "$outdir"
tar -xzf "$archive" -C "$outdir" --strip-components=1

# Interactive: 'top', 'list <func>', 'web' (needs graphviz)
go tool pprof "$outdir/profile.prof"

# Browser UI with flame graph, no binary needed
go tool pprof -http=:8081 "$outdir/profile.prof"

# Goroutine dump as plain text, which is usually what you want
go tool pprof -text -nodecount=100 "$outdir/goroutine.prof"

# Execution trace
go tool trace "$outdir/trace.prof"

# Memory growth: the archive holds a single heap.prof, so capture two live
# heaps minutes apart under the same load and diff those instead
fleetctl debug heap --outfile heap-t0.prof
# wait a few minutes, then:
fleetctl debug heap --outfile heap-t1.prof
go tool pprof -http=:8081 -base heap-t0.prof heap-t1.prof
```

`db-locks`, `db-innodb-status`, `db-process-list`, and `errors` are JSON, so `jq` reads them.

For readable goroutine stacks, request `?debug=2` as described in [8.5.8](8.5-fleetctl-debug.md#858-the-pprof-set). Compare repeated stacks and their counts over the incident window. Large numbers waiting on database or Redis connections can direct the investigation toward those pools.

<a id="requirements-and-hazards"></a>

### Access and collection requirements

**Database privileges:** `db-innodb-status` and `db-locks` read InnoDB tables, which needs global `PROCESS` and `SELECT`. The error message names the grant:

```sql
GRANT PROCESS, SELECT ON *.* TO 'fleet'@'%';
```

All three database captures query the writer. Collect replica-specific state separately if the replica is part of the investigation.

The `/debug/` endpoints require a bearer token for a global admin. A fleet-scoped admin receives 403. This requirement is not documented in the published reference.

**Sensitive content:** `cmdline` contains the server's command line. If credentials are passed as CLI arguments rather than environment variables or a config file, they are in the archive. Scrub before sharing. `fleetctl` prints a warning to this effect.

### Pin profiling to a named node

On a multi-node deployment, a load balancer can send successive captures to different nodes. Create a context pinned to a node so you can compare that node's behavior over time:

```sh
fleetctl config set --context server-a --address https://server-a:8080
fleetctl login --context server-a
fleetctl debug archive --context server-a
```

Match the node with `cron_stats.instance` ([8.6](8.6-server-state.md)). Comparing nodes can reveal a problem limited to one instance.

### Raw pprof, for a longer sample

`fleetctl` calls the standard pprof endpoints without duration parameters. To request a longer profile or trace, call the underlying Go handler with `seconds`:

```sh
curl -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/debug/pprof/profile?seconds=120" -o profile-120s.prof
```

This duration option is inferred from Fleet mounting the standard handlers unchanged; Fleet's usage documentation does not describe it.

### Traces, for request-level detail

Fleet exports OpenTelemetry traces with `FLEET_LOGGING_TRACING_ENABLED=true` and `OTEL_EXPORTER_OTLP_ENDPOINT`. Sampling is route-aware and built in, so `OTEL_TRACES_SAMPLER` has no effect on it:

| Tier | Rate | Routes |
|---|---|---|
| Never | 0% | `/healthz`, `/version`, `/metrics` |
| High volume | 0.1% | osquery distributed read/write, config, log upload, orbit config and ping, device ping and desktop |
| Standard | 2% | Admin and UI read endpoints |
| Always | 100% | Enrollment, MDM command flows, SCEP, GitOps applies, cron jobs |

For a short high-resolution window during a reproduction:

Full sampling can produce a large volume of spans. Capture the current setting before changing it so you can restore it after a bounded test:

```sh
ORIGINAL=$(curl -sS --fail-with-body -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/debug/trace_sampler" | jq -r '.force_full')

curl -sS --fail-with-body -X PATCH "$FLEET_URL/debug/trace_sampler" \
  -H "Authorization: Bearer $FLEET_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"force_full": true}'
```

The setting is stored in MySQL and survives restarts. Each node picks it up on its approximately one-minute poll. Confirm the change has reached the nodes you are testing, then restore the saved value when collection ends:

```sh
curl -sS --fail-with-body -X PATCH "$FLEET_URL/debug/trace_sampler" \
  -H "Authorization: Bearer $FLEET_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --argjson v "$ORIGINAL" '{force_full: $v}')"

curl -sS --fail-with-body -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/debug/trace_sampler"
```

Restore the captured value instead of assuming `false`. It may already be enabled for another investigation. Use `--fail-with-body` so a rejected PATCH returns a failing exit status as well as its response body. [8.5.12](8.5-fleetctl-debug.md#8512-trace-sampling-endpoints-only) contains the complete procedure.

## 8.14.4 Check service limits and quotas

Limits can appear as partial results, failed writes, or requests waiting for resources. Use the table to find the relevant configuration and the place where its effect is visible, including Redis metrics, HTTP responses, and database errors.

| Limit | Default | Set where | At the boundary | Confirm with |
|---|---|---|---|---|
| Redis publish/subscribe (pubsub) output buffer | `client-output-buffer-limit pubsub 32mb 8mb 60` | Redis config | Redis **disconnects the subscriber**. The live report stops partway through; Fleet logs the disconnect and pushes a pub/sub error to the client, but nothing retries or resumes the run. | Redis client-output-buffer metrics during a large run |
| Same, on AWS ElastiCache | different parameter names | Parameter group | Same | `client-output-buffer-limit-pubsub-hard-limit`, `-soft-limit`, `-soft-seconds` |
| MySQL `max_allowed_packet` vs `carver_block_size` ([file carving](../09-appendices/a.6-glossary-and-release-compatibility.md#file-carving)) | MySQL 8 default 64MB (`67108864`) | MySQL, and agent options | MySQL **rejects the write**. The carve fails or stalls. | `SHOW VARIABLES LIKE 'max_allowed_packet'` |
| `mysql_max_open_conns` | `50` per Fleet server | `FLEET_MYSQL_MAX_OPEN_CONNS` | Requests queue waiting for a connection. Latency, not errors. | `db-process-list`, connection count on the DB |
| MySQL `max_prepared_stmt_count` | MySQL default | MySQL | Prepared statement errors under load | Must be ≥ `FLEET_MYSQL_MAX_OPEN_CONNS × (number of Fleet servers) × 4` |
| `redis_max_open_conns` | `0` (no limit) | `FLEET_REDIS_MAX_OPEN_CONNS` | With a non-zero value, waits up to `redis_conn_wait_timeout` (default `0`, meaning no wait) then fails | Redis connection metrics |
| `redis_read_timeout` / `redis_write_timeout` | `10s` each | `FLEET_REDIS_READ_TIMEOUT`, `..._WRITE_TIMEOUT` | Operation fails, request errors | Server error log |
| `server_default_max_request_body_size` | `1MiB` | `FLEET_SERVER_DEFAULT_MAX_REQUEST_BODY_SIZE` | HTTP request rejected. The per-endpoint override described in the reference is not registered at this release; use this registered setting. | Server access log status codes |
| `osquery_max_log_write_body_size` | built-in `10MiB` | `FLEET_OSQUERY_MAX_LOG_WRITE_BODY_SIZE` | `/api/osquery/log` rejects the batch. **Only applies when `osquery_allow_body_auth_fallback` is `true` (the default).** | Orbit and osquery status logs on the host |
| `osquery_max_distributed_write_body_size` | built-in `5MiB` | `FLEET_OSQUERY_MAX_DISTRIBUTED_WRITE_BODY_SIZE` | `/api/osquery/distributed/write` rejects the results. Same body-auth condition. | Same |
| `FLEET_LIVE_QUERY_REST_PERIOD` | `25s` deadline | environment only | Synchronous live report returns partial results | §8.14.2 |
| osquery `--events_max` | `50000` rows per evented table | agent options | **Oldest events expire.** Silent data loss. | `SELECT name, events FROM osquery_events;` |
| osquery `--events_expiry` | `86000` seconds | agent options | Rows expire once the table has been queried after generation | Same |
| Login rate limit | 10/min, burst 9 | built in | HTTP 429 | 429s on `/api/v1/fleet/login` in the access log |
| MFA session creation | Shares the login rate, its own bucket | built in | HTTP 429 | 429s on `/api/v1/fleet/sessions`. Check Fleet's session bucket as well as upstream limits |
| Forgot-password rate limit | 10/hour, burst 9 | built in | HTTP 429 | Access log |
| Org-logo endpoint | 60/min, burst 20 | built in | HTTP 429 | Access log |
| SSO and MDM SSO | `auth_sso_rate_limit_per_minute`, `mdm.sso_rate_limit_per_minute` | config | HTTP 429 | Config reference |
| Fleet Desktop device endpoints | 1,000 consecutive **failing** requests per minute, then the source IP is banned for 1 minute | built in | Desktop stops working for everything behind that IP | Access log, 429s clustered by source IP |
| S3 carve parts | 10,000 parts (Fleet-enforced); a minimum part size is imposed by the object store, not Fleet (AWS S3 uses 5 MiB) | agent options and the configured store | Upload rejected | [8.7](8.7-live-query-introspection.md#878-running-and-retrieving-a-file-carve) |
| Individual carve file size | up to 8 GiB, inclusive | n/a | The carve fails | Same |

At 4.90.0, Fleet applies rate quotas to login, MFA session creation, forgot-password, SSO and MDM SSO flows, and the organization-logo endpoint. SSO callbacks use a separate bucket from login. Fleet Desktop endpoints use the failure-triggered IP ban described below.

This list follows the router at the pinned release. If a plain read endpoint returns 429, check the load balancer, WAF, or API gateway as well as Fleet, and confirm which component produced the response.

For devices sharing NAT or corporate egress, the Desktop failure threshold applies to their shared source IP. Stale device tokens on several hosts can therefore cause a temporary ban affecting other devices at that address.

## 8.14.5 Query cost, on the host

Use osquery's accounting tables to identify costly queries on an affected host. You can read them through a live report and compare the results with an unaffected device.

### `osquery_schedule`

Columns: `name`, `query`, `interval`, `executions`, `last_executed`, `denylisted`, `output_size`, `wall_time`, `wall_time_ms`, `last_wall_time_ms`, `user_time`, `last_user_time`, `system_time`, `last_system_time`, `average_memory`, `last_memory`.

Cost ranking, per host:

```sql
SELECT name, interval, executions, output_size, average_memory, last_memory,
       wall_time_ms, last_wall_time_ms, last_executed, denylisted
FROM osquery_schedule
ORDER BY average_memory DESC;
```

To compare CPU cost per execution:

```sql
SELECT name, interval, executions, output_size,
       (user_time / executions)   AS avg_user_time,
       (system_time / executions) AS avg_system_time,
       average_memory, last_executed
FROM osquery_schedule;
```

That second form is the one Fleet itself uses to populate host vitals.

### The denylist

```sql
SELECT name, query FROM osquery_schedule WHERE denylisted = '1';
```

osquery's watchdog denylists a scheduled query that repeatedly exceeds its resource budget. **A denylisted query stays out of the schedule until osquery restarts.**

Denylisting can contribute to a query that returns only 40 to 70 percent of targets despite a healthy server. Check host logs and the query's resource use before assuming every missing response is a delivery failure. Directory traversal and wildcard paths are candidates for excessive work.

Fleet 4.74.0 downgraded the server-side `distributed query is denylisted` message from error to warning, because it reports a host problem rather than a server one, so look for it at warning level. Release notes are at github.com/fleetdm/fleet/releases.

### The watchdog

osquery's watcher process enforces a memory limit and a CPU limit against the worker process, and against each managed extension:

| Flag | Controls |
|---|---|
| `--watchdog_memory_limit` | Maximum memory, in MB |
| `--watchdog_utilization_limit` | Maximum CPU, as `processes.user_time` + `system_time` |
| `--watchdog_latency_limit` | How long CPU may stay over the limit |
| `--watchdog_delay` | Grace period before limits are enforced. Default 60 seconds. |
| `--watchdog_forced_shutdown_delay` | Wait between `SIGTERM` and `SIGKILL` |
| `--watchdog_level` | Preset limit profile |
| `--disable_watchdog` | Turns it off entirely |

Fleet states the default budget as **200 MB of memory and 10% CPU**.

The watcher sends `SIGUSR1`, then `SIGTERM`, and finally `SIGKILL` after `--watchdog_forced_shutdown_delay`. If the worker cannot restart within the respawn limit, osquery shuts down. A host can then stop reporting entirely (fleetdm.com/guides/osquery-watchdog).

Every watchdog flag is a command-line flag, so it goes under `command_line_flags` in agent options and **takes effect on the next fleetd restart**. `distributed_interval`, `logger_tls_period`, `events_max`, `events_expiry`, and `schedule_splay_percent` are accepted in both places, so setting them under `options` applies without a restart.

### Evented tables

```sql
SELECT name, publisher, type, subscriptions, events, active FROM osquery_events;
```

`events` shows buffered rows. Check whether the collected events are being queried; retaining unused events adds resource cost. `subscriptions = 0` means no subscriber is reading that publisher's events.

Choose an event-control change that matches the cause: narrow the query, adjust `--events_max` or `--events_expiry`, disable an unneeded publisher, or disable events entirely. Both osquery and the underlying OS utility can drop events under load. osquery logs its own drops but cannot report drops inside that utility (fleetdm.com/guides/osquery-evented-tables-overview).

### The two agent intervals

| Setting | Fleet's guidance | Lowering it | Raising it |
|---|---|---|---|
| `distributed_interval` | **10 to 30 seconds** | Live reports return faster; more check-in load on the server, multiplied by host count | Live reports time out before hosts check in, per §8.14.2 |
| `logger_tls_period` | not stated as a range | Results arrive sooner; more, smaller uploads | Fewer, larger uploads. Larger batches can hit `osquery_max_log_write_body_size`. |

The Fleet-side counterpart, `buffered_log_max`, sets how much osquery holds locally while Fleet is unreachable. Fleet's availability model depends on it: agents keep running and keep buffering through server downtime.

### Fleet's own cost signal

Fleet displays query performance impact as minimal, considerable, or excessive. Scheduled-report statistics are controlled by `app_enable_scheduled_query_stats`, default `true` (`FLEET_APP_ENABLE_SCHEDULED_QUERY_STATS`). Live-report statistics remain enabled when it is false.

The configuration reference uses `app_enable_report_stats`, which the 4.90.0 server does not register. Use the registered name above.

## 8.14.6 Interference

Other software can compete with Fleet components for resources, scan the files osquery reads, or block execution and network traffic. Compare host and security-product evidence with Fleet's own metrics to identify these interactions.

| Shape | Presentation |
|---|---|
| **Resource contention** | Both agents alive and healthy. Host is slow. Watchdog restarts in Orbit logs. Cost is real but attributed to whichever agent the user notices. |
| **Inspection and scanning** | An endpoint security product scans or intercepts files or syscalls that osquery touches, multiplying the cost of ordinary osquery work. Onset tracks the **other** product's version, or a change in what osquery does. |
| **Blocking** | Application allow-listing or deny-listing prevents a Fleet binary from running, or TLS inspection breaks the certificate chain. This one usually presents as a delivery failure, so treat it under [8.1](8.1-diagnostic-method.md) if nothing is arriving at all. |

### The diagnostic

1. Establish the onset time as precisely as available evidence allows.
2. Record nearby changes to Fleet, fleetd, osquery, the OS, and other products or their policies. Use the timeline to prioritize tests without treating correlation as proof.
3. With the responsible administrator's approval, compare the same workload on a test host with a targeted exclusion or the other product disabled. Repeat the test and change one condition at a time. If performance does not improve, verify that the exclusion covered the relevant behavior before ruling the interaction out.
4. Compare query statistics such as `average_memory` and `wall_time_ms` between runs to measure the change.
5. Inspect the other product's logs for scanning, blocking, or policy decisions that Fleet may not observe.

### Remediating

If testing identifies interference, work with the product administrator on a targeted exclusion. Products may support code-signing publisher and path rules; publisher rules can survive path changes across releases. Confirm Fleet's binaries and working directories for the OS and installer prefix in [8.4](8.4-host-side-investigation.md).

For blocked execution, inspect application allowlist or denylist rules. Item 7 in Fleet's MDM bug checklist asks about products such as Santa and other management software for this reason.

> One reported case followed osquery v5.23.0's use of temporary keychain-file copies. An EDR product flagged the behavior, and host-side contention was initially described as Fleet server performance. Publisher and binary-path exclusions, followed by a Fleet patch, resolved the case. The exact Fleet patch is unverified in the public release notes.

## 8.14.7 Scale

### What Fleet publishes

Fleet's reference architecture gives sizing breakpoints. Reproduced from fleetdm.com/docs/deploy/reference-architectures, for AWS with Fargate, Aurora MySQL 8 and ElastiCache Redis 7.x. These are Fleet's own numbers rather than a benchmark:

| Hosts | Fleet tasks | Per task | `FLEET_MYSQL_MAX_OPEN_CONNS` | Redis | MySQL |
|---|---|---|---|---|---|
| 5,000 | 6 | 1024 CPU units, 4GB | 10 | `cache.t4g.small` ×3 | `db.t4g.medium` ×2 |
| 10,000 | 8 | 1024 / 4GB | 10 | `cache.t4g.medium` ×3 | `db.t4g.large` ×2 |
| 25,000 | 10 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.large` ×2 |
| 50,000 | 15 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.xlarge` ×3 |
| 80,000 | 20 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.2xlarge` ×3 |
| 100,000 | 25 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.2xlarge` ×3 |
| 150,000 | 40 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.4xlarge` ×3 |
| 300,000 | 70 | 1024 / 4GB | 20 | `cache.r6g.xlarge` ×3 | `db.r6g.8xlarge` ×3 |

The guidance adds Fleet tasks while increasing MySQL instance size at larger host counts. Use those values as planning references, then compare Fleet, Redis, and MySQL metrics from the same incident window to identify the resource limiting your workload.

### Constraints on the topology

- Fleet scales **horizontally**: more processes against the same MySQL and Redis, behind a load balancer. All APIs work in that arrangement.
- MySQL must be **single-writer**, one primary with read replicas. Multi-writer and group replication are not supported.
- Fleet servers need a writer **in the same datacenter**. Cross-region replication is for failover; writes stay local.
- Read replica config is set with the `mysql_read_replica_` prefix and inherits **nothing** from the primary. Every required value must be set again. There is no default for `mysql_read_replica_address`, so a partial configuration silently runs everything against the primary.
- With a read replica, set a non-zero `mysql_read_replica_conn_max_lifetime`. Some environments repoint the replica address during auto-scaling, and Fleet notices the new address when idle connections are recycled.
- Minimum MySQL is **8.0.44**. Tested against 8.0.44, 8.4.8, and 9.5.0. **9.6.0 is incompatible.**
- Multiple Fleet deployments sharing one database server need more database resources. Fleet says so without quantifying it, so do not plan on a proportional multiple.

### What to watch as the fleet grows

| Signal | Where | Meaning |
|---|---|---|
| Fleet node CPU and memory **during** a live report | Container metrics | Vertical or horizontal headroom |
| Redis CPU and memory during a live report | Redis metrics | Redis as the bottleneck; check the pubsub buffer before resizing |
| MySQL writer CPU | DB metrics | Check writer load against capacity and slow-query evidence |
| Replica lag | DB metrics | Reads returning stale data, which presents as class 6 in [8.1](8.1-diagnostic-method.md) |
| `db-process-list` during the slowdown | `fleetctl debug` | Which statements are piling up |
| `db-locks` | `fleetctl debug` | Whether it is contention rather than volume |
| Host enrollment count changes | Prometheus | Enrollment storms and duplicate identifiers |
| HTTP latency and error rate per endpoint | Prometheus | Which surface degraded |

Fleet exposes Prometheus-format metrics and suggests alerting on enrollment level changes, endpoint latency, and endpoint error rates. Traces are sampled at the moment a request arrives, at the rates in §8.14.3, so read total request counts and error rates from metrics.

### Settings that trade freshness for server load

| Setting | Default | Effect |
|---|---|---|
| `osquery_label_update_interval` | `1h` | Raising it cuts baseline load. **Lowering it can cause outages**, in Fleet's own words. |
| `osquery_policy_update_interval` | `1h` | Same |
| `osquery_detail_update_interval` | `1h` | Same |
| `osquery_max_jitter_percent` | `10` | Spreads check-ins so hosts do not arrive together |
| `osquery_min_software_last_opened_at_diff` | **`2m`** in the server. Fleet's configuration reference says `1h`, which does not match the value the server registers. Read your own config rather than either number | Suppresses redundant software timestamp writes |
| `redis_host_cache_enabled` | `true` | Fronts host lookups on osquery and orbit auth paths, cutting MySQL load on the highest-volume endpoints |
| `redis_host_cache_ttl` | see note | Longer TTL, less DB reader load, staler host records. Jittered ±10%. |
| `osquery.enroll_cooldown` | `0` (off) | Rejects re-enrollment within the window. Explicitly a **load control for deployments where many hosts share an identifier**. |
| `osquery_host_identifier` | `provided` | `uuid` or `instance` removes the common causes of identifier collision, though neither value is collision-proof: cloned images can duplicate an osquery-generated identifier and hypervisors can duplicate a hardware UUID |
| `discard_reports_data` (server settings, via API or GitOps) | `false` | Setting this to true disables storage and deletes existing report results. Use it only after identifying report writes as relevant and deciding how to retain needed data. Setting it back to false resumes storage without restoring deleted results. `query_reports_disabled` is the deprecated alias. |
| `osquery_enable_async_host_processing` | `false` | **Experimental.** Moves label membership, policy membership, host last-seen, and scheduled query stats through Redis. Less Fleet and MySQL load, more Redis load. |
| `server_gzip_responses` | see config reference | Trades server CPU for bandwidth |

The server's `redis_host_cache_ttl` default is 180 seconds, following the increase recorded in the 4.89.0 release notes. The configuration reference still lists 60 seconds. Check the effective setting on an existing deployment.

Setting `discard_reports_data` to true disables report-result storage and schedules existing stored results for deletion by `query_results_cleanup`. Re-enabling storage does not restore them. If you need to retain results externally, configure the destination before discarding the local copy; result delivery continues when `automations_enabled` is set.

```sh
fleetctl api -X PATCH \
  -F server_settings='{"discard_reports_data":true}' \
  /api/v1/fleet/config
```

Test async host processing before adopting it. When it is enabled alongside the failing-policies webhook, some pass/fail transitions can miss webhook delivery. [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md) explains the workload moved to Redis, batch settings, and validation needed for this capacity change.

### Duplicate enrollment as a scale problem

Hosts with shared identifiers can overwrite one another's enrollment records and contribute to Redis backlog and delayed live-report results. Fleet documents `osquery_host_identifier: uuid` or `instance`, and `osquery.enroll_cooldown`, as mitigations, preferring an identifier change. Check the source of duplicate identifiers as part of that change.

### Row counts, before hardware

Some tables grow with activity volume rather than host count. Check row counts and cleanup behavior for tables in slow statements from `db-process-list`. Fleet has added an index and 24-hour cleanup of completed `distributed_query_campaign_targets`, along with cleanup of live-query campaign activity.

> A reported `distributed_query_campaign_targets` table reached roughly 110 million rows, and removing its accumulated data resolved the slowdown. Use this as a reason to inspect table growth and cleanup, with any data-removal decision based on the table's current use and retention requirements.

<a id="upgrading-is-a-legitimate-remediation"></a>

### Check release fixes

Compare the affected version with relevant performance fixes and regressions. Examples include Windows MDM profile changes and removal of a three-table Orbit check-in join in 4.89.0, improvements to Apple reconciliation and label listing, and per-vendor CVE caching. A MySQL read regression in 4.73.x was fixed in a later patch.

Read the release notes between the last known good and current versions, then compare any matching fix with the evidence you collected (github.com/fleetdm/fleet/releases).

## 8.14.8 What is not documented

The following items have limited published documentation or rely on the source review for this release:

| Item | Status |
|---|---|
| `fleetctl debug profile / heap / goroutine / trace` | All four work. No usage documentation anywhere in Fleet's docs: `archive` is documented, the individual profiles are not. |
| `db-locks`, `db-innodb-status`, `db-process-list` subcommands | All three work. Absent from Fleet's documentation. |
| `allocs`, `block`, `mutex`, `threadcreate` | Produced by `archive` alone. No subcommand, no documentation. |
| Global-admin requirement on `/debug/` | Confirmed behaviour, undocumented. |
| `?seconds=` on the pprof endpoints | Inferred from Fleet mounting Go's standard profile handlers unmodified. Undocumented, and `fleetctl` does not expose it. |
| `FLEET_LIVE_QUERY_REST_PERIOD` | Environment variable, absent from the server configuration reference. The REST reference documents the 25s result deadline; the 90s write-timeout base comes from source. |
| `redis_host_cache_ttl` default | Two published values. Treat the live default as 180s. |
| `osquery_min_software_last_opened_at_diff` default | Two values again, and they disagree by a factor of thirty. Fleet's configuration reference says `1h`; the server registers `2m`. Read the effective value on your own deployment rather than trusting either. |
| `fleetctl debug archive` contents | Fleet documents `archive` without listing its members, and the omission that matters is `migrations`, which has its own subcommand and is not collected. |
| An infrastructure intake questionnaire for self-hosted deployments | Fleet publishes no equivalent to the MDM checklist. Use [8.13](8.13-escalation.md) to collect topology, dependency sizing, versions, replicas, load balancing, TLS, and log destinations. |
| Threshold values for "too slow" | Fleet publishes no universal latency or resource thresholds. Compare the workload with your deployment's baseline. |

## 8.14.9 What to collect

Beyond [8.13](8.13-escalation.md)'s general list, degradation needs:

- `fleetctl debug archive`, taken **during** the degradation, from a named node (`--context`). Two heap profiles minutes apart if memory is the suspicion.
- The `SELECT 1 WHERE 1 = 0;` control result, elapsed time, and target and responding-host counts, alongside the same measurements for the real query.
- Topology: node count, instance sizes, MySQL and Redis versions and sizes, whether a read replica is configured, where TLS terminates.
- The onset date, and every version that changed near it on both sides.
- `osquery_schedule` and `osquery_events` output from an affected host, plus the same from an unaffected one.
- Fleet node, Redis, and MySQL CPU and memory graphs covering the window.
- Row counts for any table appearing in `db-process-list`.

## Version notes

- **4.89.0:** default `FLEET_REDIS_HOST_CACHE_TTL` raised 60s to 180s, and the host-update invalidation path stopped doing reverse-index GETs. Both reduce DB reader load and Redis CPU. Windows MDM profile changes at scale made faster and much lighter on the database. Orbit check-in no longer runs a three-table join per check-in per host.
- **4.84.3:** reduced database load from Fleet Desktop endpoints when invalid or expired device tokens are presented, by resolving the token with a single indexed lookup before the multi-join host-details query.
- **4.74.0:** `distributed query is denylisted` downgraded from error to warning on the server, because it indicates a host problem.
- **4.43.0:** `POST /api/v1/fleet/reports/:id/run` replaced `GET /queries/run` for the synchronous live report. The old endpoint remains for compatibility.

Release notes for each of these are at github.com/fleetdm/fleet/releases.
