# The diagnostic method

Use this chapter to choose a starting point for a Fleet investigation. It helps you identify the affected channel, locate the stage where progress stopped, and select the evidence to collect.

For a delivery problem, compare the intended change with the result: a profile assigned but absent from a Mac, software targeted but missing, a scheduled report with no arriving results, or a policy whose host state differs from the console. The first point of disagreement narrows the investigation.

> **Reports and queries.** Fleet 4.90.0 calls a saved object a **report** and an ad-hoc run a **live report**. These names replaced “query” and “live query” in 4.82.0 across the UI, API, CLI, and GitOps.
>
> This chapter uses **report** for that Fleet object and **query** for osquery's mechanism or Fleet's unchanged storage names. Examples include the distributed query channel, `osquery_schedule`, watchdog query denials, MySQL's `queries` table, and Redis `livequery:` keys. The terminology follows the layer being inspected.

If work arrives but is slow, costly, or interferes with other host software, use the degradation path in §8.1.3.

For an assistant that stops answering or returns the wrong hosts through the [MCP server](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md), use the assistant path before §8.1.4. It follows the operator's client and proxy connection to Fleet.

## 8.1.1 The order of operations

| Step | Action | Section |
|---|---|---|
| 1 | Record the context and observed state | §8.1.2 |
| 2 | Choose delivery failure or degradation | §8.1.3 |
| 3 | Identify the channel carrying the feature on this platform | §8.1.4 |
| 4 | Classify the failure | §8.1.5 |
| 5 | Choose an observation that divides the possible failure stages | §8.1.6 |
| 6 | Trigger the suspected stage and verify that it ran | §8.1.7 |
| 7 | Read the logs for the narrowed scope | §8.1.8 |

Establishing the channel and stage first gives a log search a useful scope: the component, operation, and time window to inspect.

## 8.1.2 Establish the facts before you form a theory

Record the deployment context before choosing a test. Enrolment type affects setup work, agent version affects Windows wake behavior, and a proxy can affect access to Apple. These details determine which code path and prerequisites apply.

Fleet's public MDM triage checklist in `docs/Contributing/product-groups/mdm/` asks thirteen context questions. The following table groups that intake by topic and adds recent changes.

| Axis | What to pin down |
|---|---|
| **Blast radius** | One host, one class of hosts (a fleet, a platform, a region, an OS build), or everything? Does it survive a reboot? |
| **Platform** | OS **and build number**. `macOS 26.2`, `Windows 11 Pro 25H2 (10.0.26200.7462)`, `Android 16` |
| **Hardware** | Model identifier. Recent Apple silicon and recent Windows builds have their own failure modes |
| **Agent** | fleetd version. Fleet Desktop enabled? Any customisation to the installer package? |
| **Enrollment type** | ⭐ macOS: ADE/ABM, or a manual profile as company-owned or personal. iOS/iPadOS: ADE/ABM, an enrollment URL either way, or account-driven, which is **iOS and iPadOS only**. Windows: agent-driven, Autopilot, or Settings-app. Android: work profile, QR, or account, the last **unestablished**, appearing only in Fleet's triage notes rather than as a described path ([3.6](../03-connect-devices/3.6-enroll-android-devices.md)). **Different code paths.** |
| **History** | Previously managed by another MDM? How was it migrated? Is the old agent still installed? Was it told to stop managing? |
| **Interference** | Application allow or deny listing? Conflicting configuration profiles? Other management software? |
| **Network** | Proxy, VPN, or TLS inspection? Are Fleet's server **and update** URLs allowlisted? Are **Apple's** services (APNs, ABM) allowlisted? |
| **Fleet-side** | Are detail queries disabled for this fleet? Is IdP authentication enabled? Was fleetd installed before MDM enrollment? |
| **External credentials** | APNs certificate valid? ABM and VPP tokens current? Any renewed recently? |
| **What changed** | Fleet version, agent version, OS update, a GitOps commit, a certificate or token expiry, near the onset |

Host identifiers (serial numbers, UUIDs) are needed but belong on a private channel, never in a public issue tracker. Full intake lists, including one for self-hosted infrastructure, are in [8.13](8.13-escalation.md).

Compare three states in order: the configuration declared in GitOps or another source, the state Fleet resolved and stored through the API, and the state present on the host. A declaration establishes intent; the API shows what Fleet accepted; the host shows what arrived. The first gap helps identify the failure class.

Read the final state on the host itself. Fleet's displayed state may be stale, which is class 6 below.

## 8.1.3 The fork: delivery failure or degradation?

Did something fail to arrive, or did everything arrive too slowly?

| | Delivery failure | Degradation |
|---|---|---|
| Symptom | "X didn't happen" | "X is slow, heavy, or erratic" |
| Method | §8.1.4 to §8.1.8 | [8.14](8.14-degradation.md) |
| Tools | Queue tables, command results, host state | `fleetctl debug profile`, `heap`, `goroutine`, `trace` |

When work continues to arrive and the problem is its speed or cost, go to [8.14](8.14-degradation.md). Use the delivery path when an operation has stopped progressing.

### The assistant surface, not a host

For assistant symptoms, follow the MCP client, transport, proxy process, and Fleet API connection. This operator-side path is separate from the managed-host channels in §8.1.4 ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)).

Test the request path from the client inward and investigate the first failing stage:

| Stage | A failure here looks like | Read |
|---|---|---|
| **Client to server** | The assistant lists no Fleet tools at all. The client config, the absolute binary path, or on Apple Silicon the binary signature | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Transport** | Over SSE, the client cannot reach the server or a `/healthz` probe fails. Under stdio, the client cannot launch the process | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Bearer and TLS**, SSE only | Every SSE request is refused with 401, or the client rejects the server certificate. Under stdio there is no bearer to test | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **MCP process** | Tools are present but every call errors, and the server's own log shows it never started cleanly or is mid-restart | [8.3](8.3-server-logs.md), the MCP subsection |
| **Fleet token** | The server refuses to start, its log naming the reachability or API-only check on `FLEET_API_KEY` that it failed | [8.3](8.3-server-logs.md), [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Fleet API** | Tools work but a read returns something surprising. A direct-proxy tool derives its answer from one Fleet route without fanning out, projected into the tool's own documented shape; a composed tool may have dropped or capped a component | [6.3](../06-automate-fleet/6.3-use-the-fleet-rest-api.md), [a.11](../09-appendices/a.11-mcp-tool-reference.md) |

For an unexpected direct-proxy result, repeat the underlying [REST request](../06-automate-fleet/6.3-use-the-fleet-rest-api.md) and compare it with the tool's projection and targeting rules in [A.11](../09-appendices/a.11-mcp-tool-reference.md). These tools select fields from one route's result, and some disambiguate targets or regroup values before returning them.

For a composed tool, replay each component route from A.11. Filter intersections and queries across fleets can return incomplete results when a component fails or reaches a cap; inspect the MCP warnings as well.

The CVE-impact tool needs one additional check. A failed estate-count request silently sets the total-systems denominator to zero. Confirm a zero or implausibly small denominator with A.11's estate-count procedure even when the log has no warning.

For live queries with fewer participating hosts than expected, use [8.7](8.7-live-query-introspection.md). The host-delivery procedure below applies to managed-device channels.

## 8.1.4 Identify the channel first

A fully enrolled Mac or Windows computer uses five management channels, each with its own evidence. Three belong to one osquery process and share a node key: a network fault can affect one endpoint, while a stopped or wedged process affects all three.

The channel count depends on the host. Linux has four; MDM-only and agent-only hosts use fewer; iOS, iPadOS, Android, and ChromeOS each have one. Use the [per-platform matrix in 1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) to select the channels present on the affected device.

The device-authenticated `device/...` API uses a per-host token and sits outside this channel count. Fleet Desktop is its main consumer, while Orbit maintains the token even without Desktop installed ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). The diagnostic channel method below does not depend on it.

| # | Channel | Carries | Cadence |
|---|---|---|---|
| 1 | osquery **distributed** | live reports, detail and vitals queries | `distributed_interval`, 10s on a new install |
| 2 | osquery **config TLS** | scheduled report config and the `agent_options.config` block; Orbit's own settings travel on channel 4 | 60s. fleetd starts osquery with `--config_refresh=60` |
| 3 | osquery **logger TLS** | query results outbound | `logger_tls_period`, 10s on a new install |
| 4 | **Orbit API** | software installs, scripts, setup experience, disk-encryption keys, MDM migration | 30s, stretching toward 5 minutes while the fetch keeps failing |
| 5 | **MDM protocol** | profiles, MDM commands, VPP installs, and most lock and wipe operations, though **Windows lock and both Linux operations are scripts** and belong to channel 4 ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)) | APNs push (Apple), SyncML poll or fleetd wake (Windows), AMAPI (Android) |

Allow for channel 2's 60-second refresh when checking an agent-options change. A change absent after forty seconds may still be waiting for the next fetch. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) explains the cadences and which can be configured.

On channel 4, repeated configuration-fetch failures increase the interval exponentially from thirty seconds to a maximum of five minutes. The first successful fetch returns it to thirty seconds. A repaired connection can therefore take up to five minutes to show progress. Look for `running config receivers, backing off` and its next-retry interval to distinguish this backoff from a stopped channel.

Interpret “online” as an osquery signal. After a host has recorded an osquery check-in, any request through channels 1, 2, or 3 updates its last-seen time through shared authentication. A host still shipping logs can remain online while distributed reads fail.

Online status does not establish Orbit or MDM health. A live report can succeed while MDM fails, and vitals can arrive while Orbit is stuck. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) gives the online window; the MDM-only case appears below.

Channel 4 can break channel 5. A Windows host on the relaxed 480 minute MDM poll is woken through Orbit, so a broken Orbit channel delays MDM commands by up to eight hours with nothing wrong in the MDM subsystem. See [8.9](8.9-windows-mdm-diagnostics.md).

### The quick evidence sweep

Use this sweep before feature-specific investigation. The tests share prerequisites, so interpret each result within the limits in the final column.

| Test | A pass proves | What it does not prove, and its prerequisites |
|---|---|---|
| Run a live report against the host | The whole distributed round trip worked: server, MySQL, Redis, the websocket or CLI path, and the host answering on channel 1 | A failure implicates any one of those, not "osquery is not reaching Fleet". Narrow it with the control test in [8.14](8.14-degradation.md#8142-establish-a-control-first) |
| Check when host vitals last updated | The host returned detail-query results **and Fleet ingested them**. They come back on **channel 1**, not channel 2 | Staleness can mean a quiet agent, detail queries disabled for the fleet, a cached view, or results that arrived and failed to ingest. Fleet logs an ingestion error and carries on, so that last one leaves the host looking quiet while it is talking normally |
| `fleetctl run-script` with something trivial | Channel 4 accepted and ran the script | **The command refuses unless Fleet already considers the host online**, so it cannot test Orbit on a host whose osquery is silent. macOS, Windows and Linux only, and scripts must be enabled |
| Load the **My Device** page from the host | The device-authenticated web path works, so Fleet Desktop's token is valid | Nothing about whether the Desktop process is running. It proves the path, not the process |
| `fleetctl mdm run-command` with a benign command | Channel 5 accepted the command for delivery | Acceptance is not delivery: an Apple command sits queued until the device connects back. **macOS and Windows only**, needs a raw payload file, and Android has no equivalent |

To check whether one host picked up an agent-options change, watch that host's `osquery_flags` and `osquery_info.config_hash` before and after the change. Fleet builds configuration per host, including label-scoped content, so different hashes on two hosts in the same fleet can both be correct ([8.7.1](8.7-live-query-introspection.md#871-the-query-library)).

Also inspect `config_valid`: a value of `0` means the host fetched a configuration and rejected it ([8.4.6](8.4-host-side-investigation.md#846-osquery-introspection-tables)). These observations help assess channel 2; there is no inexpensive test that isolates it completely.

Allow time for the sweep's prerequisites. Scripts wait for an Orbit poll and execution; MDM acknowledgements depend on the platform and device availability. Start these checks early and record when each was requested.

For reachability and TLS specifically:

```sh
fleetctl debug connection --fleet-certificate "<ca-cert.pem>" "<fleet-server-address>"
```

Pass the Fleet server address, such as `fleet.example.com` or `fleet.example.com:8080`. The command adds a scheme if omitted. An enrolment-profile URL targets the host named in that URL and is unsuitable for this server check.

The command checks DNS resolution, TCP connection, TLS validation against the supplied root, and the expected Fleet response to an enrolment request with a deliberately invalid secret. It stops at the first failure, identifying the stage to investigate. The final check confirms a Fleet response beyond a reachable load balancer.

The certificate flag applies when an address is supplied. Without an address, the command reads both the address and root CA from the fleetctl context. If neither source supplies a root CA, it reports using the embedded certificate bundle also shipped in fleetd packages.

These checks assess connectivity and server behavior. Inspect the agent separately: Orbit can remain stuck even when every connection check passes.

### The half-enrolled state

A macOS host can complete manual or ADE MDM enrolment while the subsequent `InstallEnterpriseApplication` agent installation fails. Check for this state when MDM works but agent features are absent.

On an ADE fleet with `setup_experience.macos_manual_agent_install` enabled, Fleet deliberately suppresses that command. The bootstrap package must deliver the agent instead ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)); check the configured path before treating a missing agent as an installation failure.

An MDM-enrolled host without an agent can show `On (company-owned)` or `On (manual)` and acknowledge MDM commands, while producing no osquery check-ins, vitals, scripts, or agent-delivered software. If MDM commands also remain unacknowledged, investigate channel 5 separately; the missing agent does not explain that failure.

One deployment reported 20 to 30 affected machines out of 1,000 in `fleetdm/fleet#47793`, which proposes using the declarative protocol for installation. That report is external to the 4.90.0 source review; consult the issue for its current state. The reported proportion describes that deployment. [8.4](8.4-host-side-investigation.md) covers detection and recovery.

## 8.1.5 Classify the failure

Fleet performs much of its work asynchronously through queues. Use the configuration, targeting, queue, and host evidence to place a delivery failure in one of these seven classes.

| # | Class | Meaning | Generic tell | Go to |
|---|---|---|---|---|
| 0 | **Not intended** | The config does not say what you think | Desired state absent at the source | Read the config, not logs |
| 1 | **Not targeted** | Intent exists, does not resolve to this host | Host not in the resolved fleet or label set | [8.6.13](8.6-server-state.md#8613-scoping-which-fleet-which-labels-was-this-host-targeted) |
| 2 | **Not queued** | Targeted, but no work item created | No row for this host and item | The cron that creates it, §8.1.7 |
| 3 | **Queued, not delivered** | Row exists, device never took it | Row present, `activated_at` or sent timestamp NULL | The channel, §8.1.4 |
| 4 | **Delivered, not executed** | Device got it, did not act or did not report | Command sent, no result row | [8.4](8.4-host-side-investigation.md) |
| 5 | **Executed, failed** | It ran and errored | Result row with error or non-zero status | [8.4](8.4-host-side-investigation.md) |
| 6 | **Succeeded, not reflected** | It worked, Fleet's view is stale | Host reality differs from Fleet UI | Refetch. If it is still stale afterwards, the detail results are not being ingested, which is a real failure |

Check host reality early to rule out class 6. If the profile is enforcing on the host or the requested change is already present, focus on how Fleet refreshes and ingests that state. This can avoid investigating a delivery path that has completed successfully.

Also check for an operation that reports success without achieving its intended result. A Linux package manager can exit zero after a no-op, leaving Fleet to record a successful install. This falls outside the seven delivery classes: inspect the operation's exit-code behavior and resulting host state.

### Where the queues live

| Queue | Table |
|---|---|
| Scripts, software installs and uninstalls, VPP and in-house app installs | `upcoming_activities`. `activated_at IS NULL` means queued but not started |
| Apple MDM commands | `nano_commands` holds the command once; `nano_enrollment_queue` ties it to each recipient; results land in `nano_command_results`. Enrollment in `nano_enrollments`, `nano_devices` |
| Windows MDM commands | `windows_mdm_command_queue` then `windows_mdm_command_results`. `windows_mdm_responses` holds only the gzipped session envelope |
| Per-host profile desired vs actual | `host_mdm_apple_profiles`, `host_mdm_windows_profiles`, `host_mdm_apple_declarations`, `host_mdm_android_profiles` |
| Setup experience | `setup_experience_status_results` |
| Async worker jobs | `jobs` |

With read-only database access, inspect these tables using [8.6](8.6-server-state.md). If a managed deployment does not expose that access, collect the available evidence listed in [8.13](8.13-escalation.md) for escalation.

Compare queue depth over time. A shrinking queue indicates progress; a growing queue needs investigation into whether processing is stalled or falling behind. Record the interval with the counts, such as ten pending activities followed by twenty-four an hour later.

## 8.1.6 Bisect, do not walk

Choose an observation that divides the possible failure stages. Checking a queue row or comparing host state with Fleet's view can narrow the investigation more quickly than inspecting every stage in sequence.

| Cut | Left means | Right means |
|---|---|---|
| Is there a queue row for this host and item? | Server-side, classes 0 to 2 | Delivery or execution, classes 3 to 5 |
| Does the host's own state match Fleet's view? | Genuine failure, 3 to 5 | Staleness, class 6 |
| Does it fail on one platform but not another? | Platform, agent, or protocol path | Server-side config or targeting |
| One host, or every host in the fleet? | Host-specific | Targeting or server-side |
| Did the responsible cron run recently and cleanly? | The scheduler | The work the job does |
| **Is the record's own timestamp old, or only its arrival time?** | Produced long ago, arriving late. Look left | Nothing new is being produced. Look right |

### The two-clocks check

When data arrives with an old timestamp, compare the timestamp inside the record with its arrival time.

If the record is old but its arrival is recent, investigate buffered delivery from the host. Fleet writes the results to their destination during the request that delivers them. A failed write returns an error to osquery, which retries on a later log period. Once delivery succeeds, osquery drains locally stored results with their original timestamps. Check whether the affected hosts recently regained connectivity.

If both timestamps are old, check whether anything new is being produced or forwarded. The destination may be reading an existing bucket or stream without receiving new records.

Use individual record timestamps for this check. If the pipeline exposes only average latency, arrange a sample of raw records so you can distinguish buffering from stopped production.

## 8.1.7 Force the stage, then verify it ran

Trigger the suspected stage and inspect whether it advances. Progress after an explicit trigger points toward the normal trigger path; continued failure narrows the investigation to that stage. Verify that the requested run actually occurred before drawing either conclusion.

```sh
fleetctl trigger --name="<schedule>"
```

Fleet 4.90.0 can register 35 schedules: the 34 in its published list plus `mdm_service_discovery`. [8.6.3](8.6-server-state.md#863-the-named-schedules) lists them. Registration on a particular server depends on licence and configuration. Passing an unrecognized name prints that server's registered set.

Relevant targets include `mdm_apple_profile_manager`, `mdm_windows_profile_manager`, `apple_mdm_dep_profile_assigner`, `apple_mdm_apns_pusher`, `maintained_apps`, `vulnerabilities`, `automations`, `integrations`, `refresh_vpp_app_versions`, `upcoming_activities_maintenance`, and `host_vitals_label_membership`.

> ### ⚠️ `fleetctl trigger` reports success for runs that never happen
>
> A trigger can return without starting work when a scheduled run is already pending, a previous trigger is pending or queued, or the internal request channel is momentarily full.
>
> The first two cases return the conflicting run's statistics and make fleetctl print `[!] Conflict`. For a full channel, the server records a debug message but returns no error. fleetctl then prints `[+] Sent request to trigger <name> schedule` even though no trigger was delivered.
>
> Check the run record after requesting a trigger:
>
> ```sql
> SELECT name, instance, stats_type, status, created_at, updated_at, errors
> FROM   cron_stats
> WHERE  name = '<schedule>'
> ORDER  BY created_at DESC
> LIMIT  5;
> ```
>
> A local run moves from `pending` to `completed`. A trigger for a schedule on another node starts as `queued` and becomes `pending` when that node claims it. `expired` and `canceled` are terminal alternatives. Inspect the JSON `errors` field and the `instance` that ran it. These records require database access; no API exposes them.
>
> Compare other schedules as well to distinguish one failing job from a wider scheduler problem ([8.6](8.6-server-state.md)).

Other forceable stages, and whether they are safe on a production host, are in [8.11](8.11-reproducing-and-isolating.md).

## 8.1.8 Read logs last

Use the identified channel, class, stage, and time window to select the log and search terms.

| Want | Go to |
|---|---|
| The full map of every log surface and its path | [8.2](8.2-log-surfaces.md) |
| Fleet server operational logs and error strings | [8.3](8.3-server-logs.md) |
| Host-side agent logs and on-disk state | [8.4](8.4-host-side-investigation.md) |
| `fleetctl debug` and the debug archive | [8.5](8.5-fleetctl-debug.md) |
| Who changed what, and when | [8.12](8.12-audit-logs.md) |

`fleetctl debug errors` reads recorded server faults from Redis. It excludes client 4xx errors, so use the request log for those. Request lines normally appear at debug level unless the error is a non-client error. Increase verbosity before reproducing a failure that needs those lines. [8.3](8.3-server-logs.md) covers both surfaces.

## 8.1.9 When to stop

Escalate when you can identify the failure class and stage, or when the next required stage is inaccessible to you. Record that boundary so the next operator can continue the investigation.

Include the §8.1.2 intake, channel-sweep results, relevant queue rows, `fleetctl debug archive`, and host-side logs for the affected interval. [8.13](8.13-escalation.md) gives the complete collection checklist.

Describe the observations and what they rule out. For example: “Live reports respond; the MDM command remains unacknowledged; an active `nano_enrollment_queue` row has no matching result; `cron_stats` has no recorded error.” This gives the next investigator a specific state to examine.
