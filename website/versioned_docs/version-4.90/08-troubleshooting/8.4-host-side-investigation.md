# Host-side investigation: agent state, Orbit, osquery

Use these checks to inspect the device directly or guide someone who has access to it. Compare that current state with what Fleet last received to determine whether the problem is on the host or in reporting its result.

## 8.4.2 Is the agent running?

Orbit supervises osqueryd and handles enrolment, updates, scripts, and software installations. When osqueryd exits, Orbit exits as well, and the service manager restarts the pair ([8.4.2](#three-restarts-that-are-normal)). Fleet Desktop runs separately in the logged-in user's session; Orbit and osqueryd operate with or without it.

| Platform | Managed by | Name |
|---|---|---|
| macOS | launchd system domain | `com.fleetdm.orbit`, plist at `/Library/LaunchDaemons/com.fleetdm.orbit.plist` |
| Windows | Service Control Manager | `Fleet osquery` |
| Linux | systemd | `orbit.service`, unit at `/usr/lib/systemd/system/orbit.service` |

fleetctl's service-enabled packages use the names above. A package built with `--service=false` registers no daemon, service, or unit. Confirm the package type before interpreting a missing service entry.

### macOS

Orbit runs as a LaunchDaemon on an ordinary package, meaning a system-wide background service that launchd starts at boot, with no user logged in.

```sh
# Loaded? What's its PID and last exit status?
sudo launchctl print system/com.fleetdm.orbit

# Just the processes
ps -ef | grep -E 'orbit|osqueryd|fleet-desktop' | grep -v grep

# Stop, start, restart
sudo launchctl bootout system/com.fleetdm.orbit
sudo launchctl bootstrap system /Library/LaunchDaemons/com.fleetdm.orbit.plist
sudo launchctl kickstart -k system/com.fleetdm.orbit
```

In `launchctl print`, inspect `state`, `last exit code`, and `pid`. Expect `state` to be `running`. A non-zero exit code with `KeepAlive` enabled, or a PID that changes repeatedly, indicates recurring exits. The plist limits respawns to one every ten seconds. Compare those exits with the expected restart paths below.

`Boot-out failed: 36: Operation now in progress` means the boot-out request was accepted and is still completing. Wait for Orbit to exit before bootstrapping again. Fleet's toggle script uses `while pgrep orbit > /dev/null; do sleep 1 ; done` for that wait.

A missing plist can follow an uninstall, a `--service=false` installation, or an incomplete or damaged install. Check the package and file history to distinguish them.

Fleet's uninstall script attempts to remove the plist, `/opt/orbit`, `/var/lib/orbit`, `/usr/local/bin/orbit`, and `/var/log/orbit` without verifying every removal. Remaining files can reflect a partial cleanup; they do not identify which person or tool performed it.

### Windows

```powershell
Get-Service -Name "Fleet osquery"
Get-CimInstance Win32_Service -Filter "Name='Fleet osquery'" | Format-List Name, State, StartMode, PathName

Stop-Service  -Name "Fleet osquery" -Force
Start-Service -Name "Fleet osquery"
Restart-Service -Name "Fleet osquery" -Force
```

`PathName` is the same `ImagePath` the debug toggle edits, so it also tells you which flags this install is running with, including whether `--debug` is on and which `--fleet-url` it was packaged against. The MSI writes those arguments at install time.

The service name and the registry path come from Fleet. The cmdlets are stock Windows.

### Linux

```sh
systemctl status orbit.service
systemctl is-enabled orbit.service
sudo systemctl restart orbit.service
sudo journalctl -u orbit -n 200 --no-pager
```

The Linux unit sets `Restart=always`, `RestartSec=1`, and `CPUQuota=20%`. A rising restart count shows repeated exits. Also include the CPU quota in a performance investigation: the service's control group is limited to twenty percent of one core.

### Three restarts that are normal

Orbit runs its subsystems as a group. When one stops, the group shuts down. Check these three restart paths before classifying repeated starts as a crash loop:

**osquery exits.** Orbit then exits and the service manager restarts the bundle. Read the osquery status log at the same timestamp to identify why the child stopped.

**An update completes.** Orbit deliberately exits so the service restarts on the new binaries. Use §8.4.12 to confirm which target changed.

**Agent options change flags or a channel.** Orbit deliberately exits to apply the new configuration. Compare the restart time with the configuration change.

For unexplained repeated exits, collect the logs in §8.4.10 to establish the cause.

Orbit supervises Fleet Desktop within the logged-in user's session. It retries while a desktop session is unavailable and restarts Desktop if the process exits. Repeated launch attempts while nobody is logged in can therefore reflect the session wait.

## 8.4.3 The Orbit root directory

| Platform | Orbit root |
|---|---|
| macOS | `/opt/orbit` |
| Linux | `/opt/orbit`. `/var/lib/orbit` is a symlink to it only on packages that bundled an Orbit older than `0.0.11`, so do not expect it on a recent host ([8.2](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory)) |
| Windows | `C:\Program Files\Orbit`, or `%ProgramFiles%\Orbit` if that variable is set |

Windows reads that path from the `ProgramFiles` environment variable at startup, so on a non-standard install drive the Orbit root moves with it.

[8.2.7](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory) lists the complete directory. Start with these entries when checking identity and state:

| Entry | Present means | Absent is consistent with |
|---|---|---|
| `secret-orbit-node-key.txt` | Orbit completed orbit-enroll and holds a [node key](../09-appendices/a.6-glossary-and-release-compatibility.md#node-key) | Enrollment never completed **or** the key was cleared. Orbit clears it deliberately, along with the Desktop identifier, the osquery database and its stored hardware UUID, when it detects the agent directory has moved to different hardware, though **that detection is macOS-only in this release** ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)), so on Windows and Linux a migrated directory keeps its key rather than losing it. Check the platform and enrolment history to distinguish these cases |
| `secret.txt` | An enroll secret on disk, **on macOS and Windows only**. Usually the one the package was built with, though a `--use-system-configuration` host writes the same file at runtime once it reads its profile, so presence identifies neither the package type nor the host's health. The Linux packages set `ORBIT_ENROLL_SECRET` in `/etc/default/orbit` instead and never create this file | Interpret absence by package type. On macOS Orbit moves a packaged secret into the Keychain on first launch and deletes the file. A `--use-system-configuration` package starts without one and **writes both `secret.txt` and `fleet_url.txt` once its configuration profile arrives**, so absence can mean the profile has not arrived. On Linux, look in `/etc/default/orbit` |
| `identifier` | Fleet Desktop's auth token, rotated by Orbit even when Desktop is off | Orbit has not reached the point of provisioning a token |
| `osquery.db/` | osquery's local store, an embedded RocksDB database: differential state, event buffers, results pending upload | osqueryd has never started here, **or** the database path was relocated with `--osquery-db` at package time |
| `osquery.flags` | The flag file Orbit reconciles from `command_line_flags` in agent options | Check the effective flags. Packages create it empty and clearing `command_line_flags` empties it again, so both an absent and an empty file are ordinary. Read the flags in effect instead ([8.4.6](#846-osquery-introspection-tables)) |
| `certs.pem` | The CA root bundle fleetd hands osquery via `--tls_server_certs`, embedded in `fleetctl` at package time | `orbit shell` will refuse to start. See [8.4.7](#847-orbit-shell-the-local-osquery-shell) |
| `fleet.pem` | The custom Fleet server CA, present only on packages built with `--fleet-certificate` | Nothing, on a deployment using a publicly trusted certificate |
| `server-overrides.json` | Update-channel overrides the server pushed down, and last-known-good binary paths | Nothing is being overridden. Fleet writes it when the server's channels differ from the package's, so a host taking config normally can still have no file |
| `bin/orbit/<os>/<channel>/orbit` | The Orbit binary for the configured channel | |
| `bin/osqueryd/<platform>/<channel>/<file>` | The osqueryd binary actually installed, to compare with agent options. Use the platform-specific path: both the platform token and filename vary by platform and architecture, and [8.2.7](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory) enumerates them | |
| `bin/desktop/…` | Fleet Desktop was included in the package | Package was built without `--fleet-desktop` |

Fleet documents `certs.pem` at fleetdm.com/guides/certificates-in-fleetd: the bundle is generated from curl's `cacert.pem`, embedded in the `fleetctl` binary, and written into the Orbit root by `fleetctl package`.

`certs.pem` is the public CA bundle; `fleet.pem` is the custom server CA on packages built for that purpose. Use the exact filenames: Fleet creates no `cert.pem`.

```sh
# macOS / Linux
sudo ls -la /opt/orbit /opt/orbit/bin/orbit /opt/orbit/bin/osqueryd
sudo cat /opt/orbit/server-overrides.json
sudo orbit version
```

```powershell
Get-ChildItem 'C:\Program Files\Orbit' -Force
Get-ChildItem 'C:\Program Files\Orbit\bin' -Recurse -Depth 3
```

Use `orbit version` locally or the `orbit_info` table remotely ([8.4.6](#846-osquery-introspection-tables)).

A root containing only `certs.pem` and `bin/` needs further inspection. It may reflect unsuccessful enrolment, an incomplete installation, directory damage, or later file removal. Package builders also create `osquery.flags` before enrolment, so its absence does not isolate the cause. Read the platform's Orbit log next; on macOS, start with `/var/log/orbit/orbit.stderr.log` ([8.2.2](8.2-log-surfaces.md#822-fleetd-orbit-stdout-and-stderr)).

For an MDM-enrolled host with no Orbit root, follow [8.4.5](#845-the-half-enrolled-state-mdm-without-an-agent).

## 8.4.4 macOS MDM truth from the host

```sh
sudo profiles status -type enrollment
```

Inspect these fields in the output. Their formatting varies with macOS version:

| Line | Values you care about |
|---|---|
| `Enrolled via DEP:` | `Yes` means the device came through Automated Device Enrollment ([ADE](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep)), which Apple's older API and this command still call [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep). `No` means manual or user enrollment, whatever Fleet's UI says about it. |
| `MDM enrollment:` | `Yes (User Approved)` is a fully functional enrollment. `Yes` without `(User Approved)` cannot install certain payload types. `No` means not enrolled at all. |
| `MDM server:` | The check-in URL. Confirms *which* MDM owns this device, which is the whole question during a migration. |

Fleet's own uninstall script branches on this output, grepping for `MDM enrollment: Yes` and `MDM enrollment: No`. fleetd uses the sibling command `profiles show -type enrollment` to read the assigned enrollment profile during an MDM migration, and it runs that one as the console user:

```sh
launchctl asuser $(id -u $(stat -f "%u" /dev/console)) profiles show -type enrollment
```

Use `profiles status` for this check. `profiles show` behaves differently outside a user session. Fleet's source does not establish that `profiles status` is session-independent on every macOS version; the recommendation follows its use in Fleet's troubleshooting notes. Fleet-facing documentation does not describe the command.

**The rest of the `profiles` family:**

```sh
# Which enrollment profile is this device assigned in ABM, and from which server
sudo profiles show -type enrollment

# Every installed configuration payload, with identifiers
sudo profiles show -type configuration

# Terse listing
sudo profiles list -all

# Force the device to re-fetch its assigned enrollment profile from Apple
sudo profiles renew -type enrollment
```

Fleet's internal MDM troubleshooting notes use `profiles show -type configuration` and `profiles renew -type enrollment`, and the `com.fleetdm.fleet.mdm.apple` identifier comes from its uninstall script. `profiles list -all` is stock macOS, with no Fleet documentation behind the flag.

**Destructive operation: remove the enrolment profile.** The following command unenrols the device:

```sh
# Remove Fleet's enrollment profile (this un-enrolls the device)
sudo profiles remove -identifier com.fleetdm.fleet.mdm.apple
```

Removing the profile stops MDM management and pending command delivery. Recovery requires ADE or manual re-enrolment; the profile does not reinstall itself. Use a spare or test host and obtain change approval before running this operation.

For a user-guided check, open System Settings > General > Device Management to view the enrolment profile and installed payload sources. The pane varies between macOS versions and does not expose the command's DEP and user-approved distinctions. Use the command when those details are needed.

For a remote check without a shell, query the macOS `mdm` table through a live report:

```sql
SELECT enrolled, server_url, installed_from_dep, user_approved, dep_capable,
       payload_identifier, install_date, has_scep_payload, topic
FROM mdm;
```

The table is macOS-only. Use [8.8](8.8-apple-mdm-diagnostics.md) to investigate MDM activity under the reported enrolment.

## 8.4.5 The half-enrolled state: MDM without an agent

A host can show **MDM status: On**, often `(company-owned)`, while never reporting agent data and showing no Fleet Desktop menu item.

MDM uses the operating system's channel independently of fleetd. A missing agent can leave MDM commands completing normally. If those commands are also unacknowledged, investigate an additional channel 5 failure ([8.8](8.8-apple-mdm-diagnostics.md)).

In this state, the device is MDM-enrolled but fleetd was never installed or was later removed. Fleet's MDM indicator records enrolment and can remain On even if that channel subsequently stops working.

Check `nano_enrollments.last_seen_at` and recent command results before choosing recovery ([8.8.3](8.8-apple-mdm-diagnostics.md#883-is-this-command-queued-delivered-or-answered)). A working MDM channel can deliver an agent reinstall. If that channel is also stalled, repair it or use another delivery path.

Confirm enrolment and agent presence on the host with these commands:

```sh
sudo profiles status -type enrollment    # MDM enrollment: Yes, MDM server: your Fleet
sudo ls -la /opt/orbit                   # missing, or present with no node key
sudo launchctl print system/com.fleetdm.orbit   # "Could not find service"
```

Enrolment with no Orbit root identifies an MDM-only host. An existing root with an unloaded LaunchDaemon points to a later failure in agent installation or startup.

One cause is failure of the `InstallEnterpriseApplication` command that delivers fleetd. Fleet sends it after manual and ADE enrolment and does not retry it. ADE can suppress it through Premium's `setup_experience.macos_manual_agent_install`, which requires a configured bootstrap package ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)). Check that choice as part of the installation path.

An uninstall, imaging step, or another management tool can remove an agent after successful installation and produce the same symptom. The installation failure is discussed in [`fleetdm/fleet#47793`](https://github.com/fleetdm/fleet/issues/47793), with declarative delivery proposed as a replacement for the one-shot command. The issue is external to the 4.90.0 source review; consult it for current status.

The issue reports one deployment with 20 to 30 affected machines out of 1,000. That is an observation from one estate, not a measured cross-deployment rate. Include an agent-presence check after bulk enrolment to find affected hosts. [8.1](8.1-diagnostic-method.md#the-half-enrolled-state) describes the same case.

Recover by reinstalling fleetd. Keep a working MDM enrolment in place and use it to deliver the package. If MDM is also stalled, repair that channel first or choose another installation method.

```sh
fleetctl package --type=pkg \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --fleet-desktop \
  --enable-scripts
```

Install the resulting `.pkg` locally, through a working MDM command, or with another management tool. Fleet's software installer requires Orbit and its osquery connection, so it cannot bootstrap a host with no agent.

For an estate-wide check, query the server for MDM-enrolled hosts with no osquery check-in. [8.6](8.6-server-state.md#8672-half-enrolled-hosts-mdm-live-agent-stale) provides the query.

> Track command acknowledgements and queue depth when judging MDM progress. The enrolment indicator alone does not show whether commands are moving.

## 8.4.6 osquery introspection tables

Run these tables against the service through a live report or the host details page. `orbit shell` starts a separate osquery instance with default configuration and its own database. Its flags, schedule, start time, and logs describe that shell.

The interactive shell also provides a placeholder `orbit_info` row directing you to the running extension; single-query mode starts no extension runner. Use the live agent for Fleet-specific state ([8.4.7](#847-orbit-shell-the-local-osquery-shell)).

Every table below is in Fleet's published table schema (fleetdm.com/tables) and available on macOS, Windows, and Linux unless noted.

### Which agent is this, and is its config valid

```sql
SELECT i.pid, i.version, i.uuid, i.instance_id, i.config_hash, i.config_valid,
       i.build_platform, i.start_time, i.watcher,
       o.version    AS orbit_version,
       o.enrolled   AS orbit_enrolled,
       o.orbit_channel, o.osqueryd_channel, o.desktop_channel,
       o.scripts_enabled, o.update_url, o.last_recorded_error
FROM osquery_info i, orbit_info o;
```

`config_valid = 0` means osquery rejected the configuration served by Fleet and retained its previous configuration. Also read `orbit_info.last_recorded_error` for Orbit's latest recorded error before deciding which log detail is needed.

Compare the Unix timestamp in `osquery_info.start_time` with `time` to calculate uptime:

```sql
SELECT (SELECT unix_time FROM time) - start_time AS osquery_uptime_seconds
FROM osquery_info;
```

For uptime that resets repeatedly, first check updates and configuration changes against the restart paths in §8.4.2. Then inspect the osquery status log for watchdog termination or crashes ([8.2.4](8.2-log-surfaces.md#824-osquery-result-and-status-logs)). Query result logs do not contain those diagnostics.

`orbit_info` carries its own `uptime` column, in seconds, and reading both at once separates the two processes:

```sql
SELECT o.uptime AS orbit_uptime_seconds,
       (SELECT unix_time FROM time) - i.start_time AS osquery_uptime_seconds
FROM orbit_info o, osquery_info i;
```

Orbit exits when its osquery runner ends, and the service manager restarts the bundle. Flag changes and other actions that restart osqueryd use this same Orbit restart path.

The difference between Orbit and osquery uptime measures the startup work before Orbit launched osqueryd. It can include an update check and target-resolution retries. Those retries run every five minutes without an attempt limit, so the gap has no useful fixed upper bound. If the update repository was unreachable for an hour after boot, Orbit can be an hour older than osqueryd.

Correlate the uptime gap with Orbit's update-retry log entries. If retries do not explain it, check for an osqueryd process launched outside Orbit and for host clock disagreement.

### Did the flag actually take

```sql
SELECT name, value, default_value, type
FROM osquery_flags
WHERE name IN ('disable_events','verbose','logger_plugin','logger_path',
               'config_refresh','distributed_interval','watchdog_memory_limit',
               'disable_watchdog','enable_file_events','enable_process_etw_events');
```

```sql
-- Everything you changed from stock, in one screen
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

Inspect the flag's current value in `osquery_flags`. Orbit writes `command_line_flags` into `<orbit root>/osquery.flags`, and they take effect after fleetd restarts. Registered flags appear with current and default values even before a new value takes effect. If a flag is entirely absent, check whether that osquery version registers its name.

A revoked enrol secret affects updates once Orbit needs to re-enrol. Ordinary configuration fetches authenticate with the Orbit node key, so flags continue to arrive while that key remains valid. After authenticated requests have returned 401 beyond Orbit's grace period, re-enrolment requires the secret. Revocation can therefore precede the visible configuration failure by a substantial interval.

### Why a scheduled query produces nothing

```sql
SELECT name, interval, executions, last_executed,
       datetime(last_executed,'unixepoch') AS last_executed_utc,
       denylisted, output_size, average_memory, last_memory,
       wall_time_ms, last_wall_time_ms, system_time, user_time
FROM osquery_schedule
ORDER BY last_executed DESC;
```

| Column | Reads as |
|---|---|
| `denylisted = 1` | osquery's watchdog killed this query for resource use and stopped running it. Fleet's published schema says it stays denylisted until osquery restarts, so treat a restart as the reset rather than waiting for an expiry. |
| `executions = 0` | The query is in the config but has never run. Check `interval` against `osquery_info.start_time`. |
| `last_executed` far in the past | It ran once and stopped, or the schedule was replaced. |
| `average_memory` / `last_memory` high | The candidate for the next watchdog kill. |
| `output_size` large | Check this size against result-log destination limits ([8.2.11](8.2-log-surfaces.md#8211-server-side-log-destinations)). |

If the query is absent from `osquery_schedule`, inspect its server-side targeting and configuration delivery. It may be out of scope, not yet delivered, or waiting for the next channel 2 fetch after a change ([8.1](8.1-diagnostic-method.md#814-identify-the-channel-first)). [8.6](8.6-server-state.md) covers those checks.

### Evented tables

An evented table is filled by a background publisher as events occur, rather than by inspecting the system at the moment a query runs.

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

`active = 0` on everything means eventing is off, which is osquery's default. Fleet documents turning it on through agent options (fleetdm.com/guides/osquery-evented-tables-overview):

```yaml
command_line_flags:
  disable_events: false
```

With `active = 1`, an `events` count of zero means the publisher has emitted no matching event since osquery started. Check whether a relevant event occurred, then examine permissions and platform support. macOS `es_process_events` also requires `--disable_endpointsecurity=false`; Windows `process_etw_events` requires `--enable_process_etw_events=true`; `yara_events` requires `--enable_file_events=true`. Fleet's evented-table guide documents those settings.

### fleetd's own logs, without a shell

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error','warn')
ORDER BY time DESC
LIMIT 100;
```

The `fleetd_logs` table exposes Orbit's in-memory ring of 10,000 entries. Use it for remote collection while the process is running. Each restart clears it, so collect file logs for a crash loop ([8.2.6](8.2-log-surfaces.md#826-reading-fleetds-own-logs-without-shell-access)).

### Clock skew

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Check the device clock when result timestamps appear late or out of order. An incorrect host clock stamps incorrect times into the records received by your SIEM. Use the two-clock comparison in [8.1](8.1-diagnostic-method.md).

### Also useful

| Table | Answers |
|---|---|
| `osquery_extensions` | Whether Fleet's `fleetd_tables` extension is loaded. Missing extension means `orbit_info`, `fleetd_logs`, and the Fleet-added tables all return nothing. |
| `osquery_packs` | Which packs are active, and their discovery-query cache behavior |
| `osquery_registry` | Which tables, plugins, and loggers are registered and active in this instance |
| `managed_policies` | macOS: managed preference values as the OS reports them. Useful for confirming a setting landed, though it reports preferences rather than an inventory of installed profiles; `profiles show -type configuration` is the profile list |

## 8.4.7 `orbit shell`: the local osquery shell

```sh
sudo orbit shell
```

Opens `osqueryi` using the osqueryd binary this host already has, in an interactive shell. Aliased as `orbit osqueryi`.

Read Fleet-specific tables through a live report against the service. The interactive shell's `orbit_info` row is a placeholder, and connecting it to the real extension is undocumented at this release ([8.4.6](#846-osquery-introspection-tables)).

Use `orbit shell` to test osquery behavior in a standalone instance. It loads default configuration and stores its database under `<orbit root>/shell`, separately from the service's RocksDB path. A successful shell test does not establish that Fleet's served configuration is active in the agent.

```sh
# Extra osquery flags go after a bare --
sudo orbit shell -- --verbose
sudo orbit shell -- --disable_events=false

# A single query and exit: the last argument, with no leading --, is treated as SQL
sudo orbit shell -- "SELECT version FROM osquery_info;"

# Pin the osqueryd channel
sudo orbit shell --osqueryd-channel stable
```

For an evented-table test, use the documented `--disable_events=false` form, leave the shell open, generate a matching event, and then query. The shell collects events only during its own lifetime, so a newly opened shell starts without earlier events.

A trailing argument without `--` selects single-query mode, which starts no extension runner. Interactive mode starts the shell's placeholder extension. Neither provides the running service's Fleet state; these shell details are not documented at this release.

If `orbit shell` exits with `cert not found at <root>/certs.pem`, the CA bundle is missing from the Orbit root. Pass a path explicitly with `--fleet-certificate`, or treat it as a damaged install ([8.4.3](#843-the-orbit-root-directory)).

## 8.4.8 Raising verbosity on an installed host

Use the platform controls below for an installed host. [8.2.10](8.2-log-surfaces.md#8210-raising-verbosity-and-putting-it-back) gives the full configuration and restoration procedure.

| Platform | Turn on | Turn off | Restart delay |
|---|---|---|---|
| macOS | `sudo ./toggle-fleetd-debug.sh enable` | `sudo ./toggle-fleetd-debug.sh disable` | 15 s, then bootout/bootstrap |
| Windows | `.\toggle-fleetd-debug.ps1` (toggles) | run it again | none, service restarts inline |
| Linux | `echo 'ORBIT_DEBUG=true' \| sudo tee -a /etc/default/orbit` then `sudo systemctl restart orbit.service` | `sudo sed -i '/^ORBIT_DEBUG=/d' /etc/default/orbit`, restart | none |

Fleet publishes both scripts in its repository, at `docs/solutions/macos/scripts/toggle-fleetd-debug.sh` and `docs/solutions/windows/scripts/toggle-fleetd-debug.ps1` (github.com/fleetdm/fleet/tree/fleet-v4.90.0/docs/solutions). Linux has no supplied script. Its systemd unit carries `EnvironmentFile=/etc/default/orbit`, and a package built with `--debug` writes `ORBIT_DEBUG=true` into that file, which is what the table above does by hand. Before changing Linux logging, save the existing `ORBIT_DEBUG` line and restore it afterwards. The table's deletion command is appropriate only when no prior line existed; see the restoration procedure in 8.2.10.

On a stock macOS package, add `ORBIT_DEBUG` before using the published toggle. The plist includes that key only for a package built with `--debug`, while the script uses `PlistBuddy set` and fails if the key is absent. Use add with a fallback to set:

```sh
plist=/Library/LaunchDaemons/com.fleetdm.orbit.plist
sudo /usr/libexec/PlistBuddy -c 'add EnvironmentVariables:ORBIT_DEBUG string true' "$plist" \
  || sudo /usr/libexec/PlistBuddy -c 'set EnvironmentVariables:ORBIT_DEBUG true' "$plist"
```

Then bootout and bootstrap the daemon as the script would. [8.2.10](8.2-log-surfaces.md#8210-raising-verbosity-and-putting-it-back) has the full discussion.

The macOS script delays its detached job by fifteen seconds so the script result can reach Fleet before Orbit stops. The Windows script restarts the service immediately, so a Fleet-run toggle can lose its result during that restart.

Inspect `/tmp/orbit_debug_script_logs.txt` for output from the macOS background job if the toggle does not take effect.

Confirm the current state without changing it:

```sh
# macOS
sudo /usr/libexec/PlistBuddy -c 'print EnvironmentVariables:ORBIT_DEBUG' \
  /Library/LaunchDaemons/com.fleetdm.orbit.plist
```

```powershell
# Windows: --debug present in ImagePath means debug is on
(Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Services\Fleet osquery' -Name ImagePath).ImagePath
```

```sh
# Linux
grep ORBIT_DEBUG /etc/default/orbit
```

Restore the previous logging setting after collection. Include that step in the same ticket; macOS debug files have no Fleet-managed rotation.

## 8.4.9 Diffing against a known-good host

Compare the affected host with a working host on the same platform, in the same fleet, and connected to the same Fleet server. Collect the following state from both:

| Compare | Broken host | Known-good host | A difference means |
|---|---|---|---|
| `orbit_info.version` and `orbit_channel` | | | The broken host is pinned to, or stuck on, a different channel. Updates are failing. |
| `osquery_info.version` | | | Different osquery versions mean the two hosts are on different `osqueryd` channels, or one has not taken an update. Table behaviour and available columns can differ between versions, so a version gap can explain a query that works on one and not the other |
| `osquery_info.config_valid` | | | `0` indicates a rejected configuration. When comparing hosts, account for the fact that Fleet serves a per-host config, so two correct hosts on one fleet can differ legitimately ([8.7.1](8.7-live-query-introspection.md#871-the-query-library)) |
| `osquery_flags` where `value != default_value` | | | The broken host never got, or never restarted into, the current `command_line_flags` |
| `sudo profiles status -type enrollment` | | | Different `MDM server`, or DEP vs manual, or approved vs not |
| `sudo profiles show -type configuration` | | | A payload present on one and missing on the other localizes the failure to a specific profile |
| `ls -la /opt/orbit` | | | Investigate a missing node key. Interpret `secret.txt` according to the package and platform cases in §8.4.3 |
| `server-overrides.json` | | | The server is telling the two hosts different things |

A live report across both hosts puts the comparison in one result set:

```sh
fleetctl report --hosts "<broken-host>,<known-good-host>" --exit --timeout 2m --query "
SELECT i.version AS osquery_version, i.config_valid,
       o.version AS orbit_version, o.orbit_channel, o.osqueryd_channel, o.enrolled
FROM osquery_info i, orbit_info o;
"
```

Fleet builds configuration from each host's fleet, platform, and label-selected packs. Different selections can produce different `config_hash` values on healthy hosts; identical selections produce the same hash. Compare the relevant settings and `config_valid` to assess whether the intended configuration is active.

Match platform and fleet when choosing the control host. Platform behavior differs, and fleet membership determines the assigned agent options and profiles.

If these observations match while behavior differs, extend the comparison to the network path and server-side state ([8.1](8.1-diagnostic-method.md)).

Start with these logs. [8.2](8.2-log-surfaces.md) lists all paths, rotation rules, and lifetimes.

# macOS: enrollment failures, script runs, update failures. Almost always stderr.

# Linux

## 8.4.11 What the host cannot tell you

| Question | Why the host cannot answer it | Where to go |
|---|---|---|
| Why did the server stop accepting this host's check-ins? | The rejection happens server-side. The host sees a failure, not a reason. | [8.6](8.6-server-state.md) |
| Which MDM commands are queued for this device, and how long have they been queued? | The queue lives in Fleet's database. The device only sees commands it has been handed. | [8.6](8.6-server-state.md) |
| What did Fleet intend this host's profiles or software to be? | Desired state is server-side. The host holds actual state only. | [8.6](8.6-server-state.md) |
| Is this problem specific to this host, or fleet-wide? | One host is a sample of one | [8.6](8.6-server-state.md), [8.7](8.7-live-query-introspection.md) |
| How did the agent get removed, and by whom? | **There is no host-side event history.** Fleet's audit log records server-side actions only, so an agent removed by a local admin, another management tool, or a user leaves no trace Fleet can show you. | [8.12](8.12-audit-logs.md) for what the audit log does cover |
| Did the query results Fleet received match what the host produced? | Requires both ends | [8.1](8.1-diagnostic-method.md), two-clocks comparison |

For agent-removal attribution, use the platform's own audit facilities: the macOS unified log, Windows Event Log, or Linux auditd. Fleet's activity history cannot identify a local removal it did not observe.

## 8.4.12 Agent updates: which channel landed, and why it did not

Orbit downloads bundle updates from a signed TUF repository. To investigate an update, compare the requested channel with the files and versions on the host. Fleet's server mainly sees the reported version; the update activity is in Orbit's log.

Read the requested channels from Orbit's extension table through a live report ([8.4.6](#846-osquery-introspection-tables)):

```sql
SELECT version, orbit_channel, osqueryd_channel, desktop_channel,
       update_url, last_recorded_error
FROM orbit_info;
```

Then look at what landed. Binaries live at `<orbit root>/bin/<target>/<platform>/<channel>/<file>`, so a channel change is visible as a new directory:

| Target | Platform string | File on disk | Executable inside |
|---|---|---|---|
| `orbit` | `macos`, `linux`, `linux-arm64`, `windows`, `windows-arm64` | `orbit`, `orbit.exe` | n/a |
| `osqueryd` | `macos-app` | `osqueryd.app.tar.gz` | `osquery.app/Contents/MacOS/osqueryd` |
| `osqueryd` | `linux`, `linux-arm64` | `osqueryd` | n/a |
| `osqueryd` | `windows`, `windows-arm64` | `osqueryd.exe` | n/a |
| `desktop` | `macos` | `desktop.app.tar.gz` | `Fleet Desktop.app/Contents/MacOS/fleet-desktop` |
| `desktop` | `windows`, `windows-arm64` | `fleet-desktop.exe` | n/a |
| `desktop` | `linux`, `linux-arm64` | `desktop.tar.gz` | `fleet-desktop/fleet-desktop` |

```sh
sudo ls -la /opt/orbit/bin/orbit/*/ /opt/orbit/bin/osqueryd/*/
sudo /opt/orbit/bin/osqueryd/macos-app/stable/osquery.app/Contents/MacOS/osqueryd --version
```

Compare the on-disk state with the requested update:

| On disk | Reads as | Next look |
|---|---|---|
| Requested channel directory **absent** | The channel does not exist in the repository, or the download has not succeeded yet | Grep the Orbit log for `tuf: file not found` (nonexistent channel) or `max retries exceeded, retrying again in` (in cooldown, below) |
| Directory **present**, old version still running | The update landed and the restart did not happen, or is failing | Look for `exiting due to successful update` followed by a start. Absent, the restart never fired |
| Both present, version **flapping** | Downgrade loop. Orbit below 1.20.0 packaged on one channel, with `update_channels` pointing at a channel holding a different side of that boundary | Move one of the two channels across 1.20.0 in the same direction |

A target download gets three attempts, followed by a 24-hour cooldown for that target. The retry key is its content hash, so publishing a new version starts a new retry sequence.

Restarting Orbit clears retry counts and cooldown timestamps because they are stored in the updater's memory. Use a restart when you need to retry before the cooldown ends, accounting for the other work interrupted by that restart.

The startup loop retries every five minutes through the same updater. Within one process, those checks continue to respect the per-target cooldown.

Orbit checks an installed binary by running `<binary> --help` or a target-specific test. On failure it removes the extracted directory, archive, and cached `.sha512`, logs `removed corrupt target for re-download`, and fetches again. During startup, the refetch and recheck occur in the same pass.

Check two version boundaries when channels fail to advance. Orbit below 1.38.1 cannot cross the repository move from `tuf.fleetctl.com` to `updates.fleetdm.com` directly. The log includes `update failed error="lookup failed: lookup orbit: tuf: file not found`. Move the host specifically to 1.38.1, confirm that version, then promote the intended release ([3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md)).

Orbit below 1.20.0 also ignores central `update_channels` settings without logging that choice. Use the supported channel path for that agent version.

Expired TUF `root`, `targets`, or `snapshot` roles prevent target loading. Orbit rechecks each interval and exits once they become valid so the next startup can initialize normally. An expired `timestamp` role does not block startup.

### Forcing an update check

Restarting the service triggers an update check before other subsystems start ([8.4.2](#842-is-the-agent-running)). For a bounded reproduction, shorten `--update-interval`, enable debug, and compare `hash(<target>)=` log lines with TUF metadata ([8.4.8](#848-raising-verbosity-on-an-installed-host)). The first periodic check adds a random delay up to `min(interval, 10 minutes)`; allow for it before treating the check as stalled.

[1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) describes the communication model, and [3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md) covers channel selection and precedence. Central `update_channels` settings require Premium and are rejected without that licence. On Free, configure channels on each host through Orbit's flags or environment variables.
