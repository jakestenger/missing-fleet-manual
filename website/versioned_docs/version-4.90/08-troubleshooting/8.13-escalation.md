# What to collect before escalating

A clear escalation helps the next person continue from what you have already learned. Use this chapter to collect the relevant device, service, and reproduction details, then share them through the appropriate support channel.

| You are | Read this as |
|---|---|
| Opening a ticket or issue | Collect relevant rows as time and access allow; §8.13.1 explains when to escalate immediately |
| Receiving a ticket | Use the missing details to choose focused follow-up questions |

The device and MDM list (8.13.3) is adapted from Fleet's own `docs/Contributing/product-groups/mdm/mdm-bug-checklist.md`. The infrastructure list (8.13.4) has no equivalent in Fleet and is assembled here from the config reference and the deploy docs.

<a id="8131-the-standard-are-you-ready-to-escalate"></a>

## 8.13.1 When to escalate

Aim to identify the channel, failure class, and last completed stage using [8.1](8.1-diagnostic-method.md). If access or visibility prevents the next check, include that limit. For example: "The queue row exists, so the remaining possibilities are classes 3 and 4. I cannot inspect the device or the database beyond these captured rows."

Start the escalation while collecting evidence when:

- Production is down or you suspect a security incident.
- Evidence may expire before collection is complete, including Redis errors, `cron_stats`, and rolling logs.
- The next check requires access you do not have.

Send what is available and identify the checks still outstanding.

When time and access allow, these checks help make the initial report more specific:

| Initial description | Useful next check |
|---|---|
| "It isn't working" | Identify the channel. [8.1](8.1-diagnostic-method.md) §8.1.4 |
| One host, never reproduced | Try a second host in the same fleet. [8.11](8.11-reproducing-and-isolating.md) |
| Fleet's UI disagrees with the host | Check the host first. Investigate class 6 by comparing device state, refetch behavior, and ingestion. [8.1](8.1-diagnostic-method.md) §8.1.5 |
| Slow, expensive, or self-interfering | Use the performance and degradation checks. [8.14](8.14-degradation.md) |
| Cron output missing | Read `cron_stats` for the schedule. [8.6](8.6-server-state.md) §8.6.2 |

<a id="8132-the-header-block-every-ticket"></a>

## 8.13.2 Essential ticket details

Include these fields near the top so the recipient can assess the issue quickly.

| Field | Example value |
|---|---|
| Fleet **server** version now reproducing it | 4.89.2 |
| Server version where first observed, and last known good | Observed 4.88.0; last good 4.87.1 |
| fleetd version on the affected hosts | 1.52 |
| Channel | MDM protocol (Apple) |
| Failure class and stage | Class 3, queued not delivered |
| Affected scope | One fleet, macOS 26.x only, 41 of 44 hosts |
| Operational impact | Rollout blocked; no production outage |
| Onset, and what changed near it | 2026-08-14, same day fleetd went 1.51 to 1.52 |
| Actual behaviour | Profile stays at Pending indefinitely; no error surfaces anywhere in the UI |
| Expected behaviour | Profile reaches Verified within a normal check-in interval |
| Steps to reproduce | Numbered, from a clean install |
| Reproduction status | Confirmed on multiple Fleet instances, **or** describes the workflow but not yet reproduced elsewhere |
| Ruled out | Live reports respond; `cron_stats` clean for `mdm_apple_profile_manager` |

Describe actual behavior and the result you expected separately. Also state whether the steps reproduce on another instance or describe only the affected workflow. Fleet's bug template asks for both distinctions so the recipient can understand the failure and choose the next test (`.github/ISSUE_TEMPLATE/bug-report.md`).

Include affected counts and operational impact. "41 of 44 hosts" gives the scope; "pilot rollout blocked, no production outage" explains its effect on your work.

If CLI behavior is involved, add the `fleetctl` version in a separate field. The client and server can run different versions.

Record both the version where the issue was first observed and the one used to reproduce it, as requested by Fleet's bug template.

## 8.13.3 Device and MDM intake list

The list follows `mdm-bug-checklist.md`, with this manual's additions marked. Gather the applicable details from Fleet and the affected host.

### Host identity and build

|---|---|---|

| Platform | Method | MDM status Fleet should show |
|---|---|---|
| macOS | ADE / ABM | On (company-owned) |
| macOS | Manual, profile-based, enrolled as company-owned | On (manual) |
| macOS | Manual, profile-based, enrolled as personal (BYOD) | On (manual - personal) |
| iOS / iPadOS | ADE / ABM | On (company-owned) |

| Windows | Agent-driven | On (manual) |
| Windows | Autopilot | On (company-owned) |
| Windows | Settings app | On (manual) |

| Android | Google account based | **No expected status established.** See below |

The iOS and iPadOS enrollment rows were added from the tagged code and console. Fleet's checklist discusses those devices but does not separately list their enrollment methods.

The checklist names Google-account-based Android enrollment without establishing a corresponding status or a separate Fleet enrollment path at this tag. If that description appears in a report, record the actual steps and displayed status before classifying the enrollment.

Account-driven user enrollment supports iOS and iPadOS at this release. Fleet rejects macOS with "only iOS and iPadOS devices are supported for account driven user enrollment". If a Mac is described that way, clarify which enrollment steps were used.

Record any mismatch between the described method and the displayed status; it can help explain the failure.

## 8.13.4 Infrastructure intake list, self-hosted

This manual's infrastructure checklist combines setting names from `docs/Configuration/fleet-server-configuration.md` with topology questions from `docs/Deploy/Reference-Architectures.md`. Fleet does not publish an equivalent intake checklist. Entries drawn from other sources are marked.

For Fleet-managed cloud, use the support channel to investigate infrastructure configuration; these server settings are not customer-modifiable. The following checklist applies to self-hosted deployments.

Part VII also links here for collecting self-hosted service details.

### Topology

| Ask | Why it changes the answer |
|---|---|
| Where does Fleet run? | AWS ECS/Fargate, Kubernetes, GCP, Render, systemd on a VM, Docker Compose. Deploy paths in `docs/Deploy/deploy-fleet.md` |
| Is the Terraform reference module in use, modified, or not at all? | `infrastructure/dogfood/terraform/aws-tf-module` in the repo |
| How many Fleet instances (tasks, pods, processes)? | Multiplies every connection pool number below |
| Load balancer in front? | Which one, and its idle timeout. A 30-second CPU profile dies on a short idle timeout ([8.5](8.5-fleetctl-debug.md) §8.5.5) |
| Where does TLS terminate? | At Fleet (`server_tls`, `server_cert`, `server_key`) or at a proxy or load balancer. Both are supported |
| Is `server_url_prefix` set? | Non-root path deployments behave differently in URL construction |
| Is `server_trusted_proxies` set? | Fleet 4.80.1+. Affects which client IP Fleet believes |
| Outbound proxy? | `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`. `NO_PROXY` is an exclusion list, not a fallback |

### MySQL

| Ask | Notes and setting names |
|---|---|
| Version and flavour | Minimum 8.0.44. Tested on 8.0.44, 8.4.8, 9.5.0. **9.6.0 is incompatible.** Drop-in replacements are not officially supported |
| Managed or self-run, and instance size | RDS Aurora MySQL is the AWS recommendation |
| Single writer? | Fleet supports one writable primary plus read replicas. **Multi-writer and group replication are not supported** |
| Read replica configured? | `mysql_read_replica_address` has no default. Replica config is fully independent, nothing is inherited from the primary. All of address, region, TLS, and auth need the `mysql_read_replica_` prefix explicitly |
| Replica connection lifetime | A non-zero `mysql_read_replica_conn_max_lifetime` is recommended where the replica address can change |
| Connection pool, per instance | `mysql_max_open_conns` (default 50), `mysql_max_idle_conns` (default 50), `mysql_conn_max_lifetime` (default 0, unlimited) |
| Database-side connection ceiling | `mysql_max_open_conns` must be below it, with headroom. AWS breakpoint table sets `FLEET_MYSQL_MAX_OPEN_CONNS` to 10 across 6 Fargate tasks at 5000 hosts |
| `max_prepared_stmt_count` on the server | Needs to be at least `FLEET_MYSQL_MAX_OPEN_CONNS * (number of Fleet servers) * 4` |
| Does one DB server host several Fleet databases? | Documented as needing extra resourcing |
| TLS to MySQL | `mysql_tls_ca`, `mysql_tls_cert`, `mysql_tls_key`, `mysql_tls_config`, `mysql_tls_server_name` |
| IAM auth in use? | `mysql_region`, `mysql_sts_assume_role_arn`, `mysql_sts_external_id`. Both `FLEET_MYSQL_REGION` and `FLEET_MYSQL_READ_REPLICA_REGION` are required when a replica exists |

### Redis

| Ask | Notes and setting names |
|---|---|
| Version and instance size | AWS breakpoint table uses Redis 7.x, `cache.t4g.small`, 3 nodes at 5000 hosts |
| Standalone or Cluster mode? | `redis_cluster_follow_redirections` (default true) and `redis_cluster_read_from_replica` (default false) apply **only** to Cluster and are ignored standalone |
| TLS? | `redis_use_tls`, `redis_tls_ca`, `redis_tls_cert`, `redis_tls_key`, `redis_tls_server_name`, `redis_tls_handshake_timeout` |
| Connection pool and timeouts | `redis_max_open_conns`, `redis_max_idle_conns`, `redis_conn_max_lifetime`, `redis_idle_timeout`, `redis_conn_wait_timeout`, `redis_read_timeout`, `redis_write_timeout`, `redis_connect_timeout`, `redis_connect_retry_attempts` |
| Host cache on? | `redis_host_cache_enabled`, `redis_host_cache_ttl` |
| Duplicate results? | `redis_duplicate_results` |

### Object storage

| Ask | Setting names |
|---|---|
| Where do software installers live? | `s3_software_installers_bucket`, `s3_software_installers_prefix`, `s3_software_installers_region` |
| Non-AWS or S3-compatible endpoint? | `s3_software_installers_endpoint_url`, `s3_software_installers_force_s3_path_style`, `s3_software_installers_gcs_iam_auth` |
| CDN in front of installers? | `s3_software_installers_cloudfront_url` plus the two signing settings, `s3_software_installers_cloudfront_url_signing_public_key_id` and `..._signing_private_key` |
| Installer size ceiling | `server_max_installer_size` |
| Where do file carves land? | `s3_carves_bucket`, `s3_carves_prefix`, `s3_carves_region`. Cleanup, S3-backed carves only: `s3_carves_cleanup_disabled`, `s3_carves_cleanup_max_per_run`, `s3_carves_cleanup_concurrency`. MySQL-backed carve blocks are cleaned by a fixed hourly job with no equivalent switch ([8.7.8](8.7-live-query-introspection.md#878-running-and-retrieving-a-file-carve)) |
| Auth method for each bucket | Static keys (`*_access_key_id`, `*_secret_access_key`) or role assumption (`*_sts_assume_role_arn`, `*_sts_external_id`) |

### Log destinations

| Ask | Setting names |
|---|---|
| Where do osquery result logs go? | `osquery_result_log_plugin`. One of `filesystem`, `firehose`, `kinesis`, `lambda`, `pubsub`, `kafkarest`, `nats`, `splunk`, `webhook`, `stdout`. Default `filesystem` |
| Where do osquery status logs go? | `osquery_status_log_plugin`, same option set and default |
| Is audit logging on, and where does it go? | `activity_enable_audit_log`, `activity_audit_log_plugin` |
| If `filesystem` | `filesystem_result_log_file`, `filesystem_status_log_file`, `filesystem_audit_log_file`, plus rotation: `filesystem_enable_log_rotation`, `filesystem_enable_log_compression`, `filesystem_max_size`, `filesystem_max_age`, `filesystem_max_backups`. Include how files persist across container replacement |
| Fleet's own server log settings | `logging_debug`, `logging_json`, `logging_error_retention_period`, `logging_enable_topics`, `logging_disable_topics` |
| Is the error store retention non-default? | `logging_error_retention_period` governs how long `fleetctl debug errors` can still see anything |

Log surface detail is in [8.2](8.2-log-surfaces.md) §8.2.11.

### Version and change history

| Ask | Notes |
|---|---|
| Exact Fleet **server** version now | Use `GET /api/v1/fleet/version` with an authenticated user, or the UI. Record `fleetctl --version` separately: it identifies the local client binary. |
| Exact `fleetctl` version, if the CLI is involved | `fleetctl --version` |
| Version before the last upgrade, and the date | Fleet follows SemVer; breaking changes in a minor or patch are limited to experimental features, security fixes, and default-value changes, all called out in version notes |
| Was the database migration step run, and did it complete? | `fleet prepare db`. Check with `fleetctl debug migrations` |
| Is `allow_missing_migrations` set? | Include its value when investigating migration or startup behavior |
| Any skipped versions in the upgrade path? | |

### How configuration reaches the server

| Ask | Notes |
|---|---|
| YAML file, environment variables, or command-line flags? | All three are supported. Flags can be piped in on stdin |
| Are app-level settings managed by GitOps? | `fleetctl gitops`. If yes, the next apply governs the fields GitOps actually sends. Fields it does not send or default are not reverted, so check which of the two you have ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)) |
| Who can change server config, and how fast? | Server config changes require a Fleet restart |
| Is the license key set? | Record the state of `license_key` without sharing its value. No key starts Free; an invalid key prevents startup; a Premium key whose only validation error is expiry still loads as Premium and is marked expired. On Free, unavailable features can return explicit errors or be ignored or disabled, so include the exact observed behavior. |
| Is `server_private_key` set, and how is it supplied? | Direct value, or `server_private_key_arn` plus region and STS settings. It encrypts material at rest, so a deployment that has lost or changed it will fail on the things that material feeds. **The precise failure surface was not verified**; treat a changed or missing key as a lead, not a diagnosis |

## 8.13.5 Artefacts to attach

Collect the applicable artifacts below. Each reference explains how to obtain and inspect it.

| Artefact | Take it | Reference |
|---|---|---|
| `fleetctl debug archive` | Per node where the deployment has more than one, using a named `--context`. Check the member list before sending | [8.5](8.5-fleetctl-debug.md) §8.5.5 |
| `fleetctl debug errors` | **Before any `--flush`.** These live in Redis and expire; a flush destroys them. The archive already collects an `errors.json`, so a separate file is worth attaching when it captures an earlier window than the archive, or when the archive's copy failed | [8.5](8.5-fleetctl-debug.md) §8.5.6 |
| Host-side agent logs for the incident window | Orbit stdout/stderr, osquery logs, Fleet Desktop log, per platform | [8.2](8.2-log-surfaces.md) §8.2.2 to §8.2.5 |
| The relevant queue rows | `upcoming_activities`, or the `nano_*` and `host_mdm_*` tables for the item in question | [8.6](8.6-server-state.md) §8.6.4 to §8.6.6 |
| `cron_stats` rows for the schedule involved | Name, instance, `stats_type`, status, errors JSON, timestamps. The only record that a background job ran. No read API; database access required | [8.6](8.6-server-state.md) §8.6.2 |

Check archive completeness and collection privileges before sending:

- The archive collector attempts thirteen items and still writes an archive if some fail. Note each `Failed <item>` message and identify missing members in the ticket. `Failed profile` refers to the CPU profile, not a configuration profile.
- Debug endpoints require a global administrator. A fleet-scoped token cannot collect them.
- `db-locks` and `db-innodb-status` require global `PROCESS` and `SELECT` privileges and report missing access. `db-process-list` can succeed without the required visibility while returning only the database user's own threads. State any collection limits alongside the files.

For a Fleet MCP issue, collect the MCP server's stderr for the incident window, its transport and redacted configuration, and the failing tool call. Pair it with the equivalent REST request and response from [6.3](../06-automate-fleet/6.3-use-the-fleet-rest-api.md).

When a tool returns an unexpected answer, compare the Fleet response with the tool's documented projection in [a.11](../09-appendices/a.11-mcp-tool-reference.md). [8.3.13](8.3-server-logs.md#8313-the-fleet-mcp-server-keeps-its-own-log) describes MCP log coverage. Remove `MCP_AUTH_TOKEN` and `FLEET_API_KEY` from attachments.

## 8.13.6 Sensitive data

### Never in a public issue tracker

Share serial numbers, UUIDs, and host IDs privately, and reference that exchange from a public issue. Fleet's checklist names a `fleetdm/confidential` issue or private chat for this purpose. Use customer code names and remove private data, following checklist item 3 and `.github/ISSUE_TEMPLATE/csa-task.md`.

### What can hide in an artefact

| Artefact | Can contain |
|---|---|
| `fleetctl debug archive` | `cmdline.prof` (server argv, highest risk), `db-process-list.json` and `db-innodb-status.json` (in-flight and recent SQL text), `errors.json`. Per-item breakdown: [8.5](8.5-fleetctl-debug.md) §8.5.13 |
| `fleetctl debug errors` | Internal hostnames, URLs, user identifiers, occasionally tokens embedded in a failing request |
| Orbit and osquery logs | Enroll secret paths and values in verbose modes, node keys, internal hostnames, usernames, installed software inventory |
| Queue and MDM table dumps | Serials, UUIDs, user emails, IdP identifiers, enrollment tokens |
| Fleet Desktop log | End-user identity and the device token |
| GitOps YAML or `fleetctl get config` | Enroll secrets, SMTP credentials, integration API tokens, SSO metadata |
| Fleet MCP server config or log | `MCP_AUTH_TOKEN` (the SSE bearer) and `FLEET_API_KEY` in the config; the Fleet base URL, and at debug level the tools invoked and their request routes, in the log |

<a id="redaction-pass-before-anything-leaves"></a>

### Review attachments before sharing

1. List archive members with `tar -tzf`.
2. Render `cmdline.prof` with one argument per line, then read it in full. It contains NUL-separated server arguments, and a viewer that stops at the first NUL may hide credentials in later arguments:

   ```sh
   tr '\0' '\n' < cmdline.prof
   ```
3. Search every attachment for the enroll secret string, any `Bearer` token, any `_KEY`, `_SECRET`, `_TOKEN`, `_PASSWORD` environment variable name, and the organisation's internal domain suffix.
4. Replace serials, UUIDs, and host IDs with stable placeholders (`HOST-A`, `HOST-B`) and keep the mapping on the private channel. Placeholders that stay consistent across attachments preserve the correlation you need.
5. If an enroll secret was in anything shared externally, rotate it. It is a credential.

> **Do not put customer-identifying information in the manual or a public issue; use your private support channel.**

## 8.13.7 Write a report someone can continue

Include the tests you ran, their results, and what each result establishes. For example, a successful live report confirms the osquery distributed path for that run; Orbit and MDM need their own checks ([8.7](8.7-live-query-introspection.md) §8.7.3).

For example:

> macOS configuration profile stuck at Pending on 41 of 44 hosts in one fleet, all macOS 26.2, since 2026-08-14. Rollout blocked; no production outage. Server 4.89.2, last good 4.87.1, fleetd 1.52. Channel is MDM protocol; classes 0 and 1 ruled out, the profile resolves to these hosts and Fleet shows the intent. Class 3: a `nano_enrollment_queue` row exists for each host with no result row in `nano_command_results` and no acknowledgement. `cron_stats` for `mdm_apple_profile_manager` shows completed runs with no errors through 2026-08-19, so the profiles were enqueued rather than never generated. The same hosts answer live reports within seconds, which shows the osquery distributed channel is healthy; the Orbit channel was not separately tested. The three unaffected hosts are the three on macOS 26.1. Attached: debug archive (all thirteen members present), `debug errors` (pre-flush), the queue rows, `cron_stats` rows. Not yet tried: a fresh test host on 26.2, and `apple_mdm_apns_pusher` stats to confirm the schedule is running at all.

This report gives the scope, impact, observed state, and evidence for each completed check. It also identifies the next tests and the OS-version difference between affected and unaffected hosts.

When adding APNs evidence, distinguish a completed pusher run from delivery to a particular device. Apple can reject individual pushes while the job still reports success. Inspect the server's info-level push errors alongside `cron_stats` ([8.3](8.3-server-logs.md)).

A report may initially contain only this:

> Profiles aren't installing for a customer. They say it started last week. Can someone look?

That is enough to start a conversation, especially during an urgent incident. Follow up with affected counts, versions, the expected result, and the evidence available so the recipient can choose a useful next step.

Before sending, check three details:

- Include a time zone and the observation window.
- Give affected and total host counts where available.
- Record recent server and agent version changes, even if their relevance is uncertain.

## 8.13.8 Where to file

Choose the support or issue route that matches the problem:

| You are | Go here first |
|---|---|
| Anything urgent, suspected-security, or customer-identifying | Use your organization's private incident or support channel. |
| A Fleet customer with a support agreement | Your support channel rather than the public tracker. It can take the identifiers a public issue cannot; §8.13.6 covers the other private routes and what may travel on them |
| Self-hosting, or on Fleet Free, and you believe it is a **scrubbed, reproducible** defect | 🦟 Bug report on `fleetdm/fleet`. Review attachments using §8.13.6 before publishing. |
| Self-hosting and it is a scaling or performance problem | 🔧 Reliability, the intake for performance and scaling investigations |
| Not sure it is a bug | fleetdm.com/support or the documentation, both linked from the repository's own issue chooser. Use these to clarify the expected behavior. |
| Asked to open something by a Fleet employee | Use the route they specified; the table below explains other templates. |

The repository also exposes Fleet's internal work templates. They are included below so you can recognize a linked or converted issue; the ownership column identifies which are intended for external submissions.

| Template | For | Yours to open? |
|---|---|---|
| 🦟 Bug report | A bug. Asks for the discovered and reproduced Fleet versions, browser and OS, actual vs expected behaviour, and reproduction steps with a checkbox for whether they reproduce across multiple Fleet instances | Yes |
| 🔧 Reliability | Scaling, performance, and reliability issues, including post-mortem action items. This is the right home for [8.14](8.14-degradation.md) degradation cases | Yes |
| 💡 Feature request | A missing capability or a Fleet-maintained app request | Yes |
| ⚔️ CSA task | Asking a Customer Solutions Architect for research or solutioning help. Explicitly requires private data scrubbed and customer code names used | Only if you have a CSA |
| 🎟 Story | An iterative product change, written as a user story | Fleet's |
| 🧩 Sub-task | A technical piece of exactly one story | Fleet's |
| ✨ Quick win | Too small for a bug, worth doing anyway | Fleet's |
| ⏳ Timebox | Effort capped by a fixed amount of time | Fleet's |
| 🎸 Air guitar | Requesting wireframes | Fleet's |
| 🍽️ Dogfood | A dogfooding issue | Fleet's |
| 🕸️ Website request | fleetdm.com changes | Yes |
| 📝 Article | Proposing an article | Yes |
| Release QA / Release QA - fleetd | Pre-release test checklists, not for reporting problems | Fleet's |

The issue chooser requires a template because `blank_issues_enabled` is false in `config.yml`. It also links to support and documentation for questions that do not need an issue.

Anything customer-identifying goes to the private channel, referenced from the public issue by number.
