# Inspecting server state

Inspect MySQL for queues, per-host desired and reported state, and background-run history. Inspect Redis for live-query campaigns and results, recorded errors, IP bans, rate limits, pending failing-policy sets, and caches. Both stores sit outside the Fleet process, so restarting Fleet leaves their data in place. Redis recovery beyond that depends on its persistence and eviction configuration.

Some state, including `cron_stats`, has no read API. Arrange read-only MySQL access so you can verify scheduled work and trigger results when needed.

## 8.6.1 Safety

Use a read replica where available through `mysql_read_replica_address`, bound time windows, and inspect `EXPLAIN` before running estate-wide queries during an incident. Some filters and aggregations lack supporting indexes, and the missing-disk-key query can scan the host population. The diagnostic queries use `SELECT`; the documented Fleet-data mutation appears below.

Use read-only access except for the documented cursor reset:

| Mutation | Safe? | Effect |
|---|---|---|
| `UPDATE nano_dep_names SET syncer_cursor = NULL, syncer_cursor_at = NULL` | **Yes, at any scale.** Documented by Fleet | Next [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep) sync falls back to a full `fetch-devices`. Does not re-enroll devices, change ABM assignments, or re-push DEP profiles. See §8.6.9 |
| Anything else | **No** | Fleet's queues carry foreign keys, activation ordering, and checksums that the server maintains transactionally. Direct deletion can leave dependent records inconsistent |

Use supported operations, such as activity cancellation or removing a profile from its fleet, to clear work. Those paths maintain related records and ordering. Direct deletion from `upcoming_activities`, `nano_enrollment_queue`, or `host_mdm_apple_profiles` bypasses those compensating writes.

## 8.6.2 `cron_stats`: did the job run?

`cron_stats` records when a schedule ran, which process ran it, and which jobs returned errors. Read it directly from MySQL to verify a trigger; Fleet exposes no read API for this table (§8.6.2.4).

### 8.6.2.1 Schema

| Column | Type | Meaning |
|---|---|---|
| `id` | `int unsigned` | Autoincrement |
| `name` | `varchar(255)` | Schedule name. The same string `fleetctl trigger --name=` takes. §8.6.3 lists them |
| `instance` | `varchar(255)` | The Fleet instance that ran it. See §8.6.2.3 |
| `stats_type` | `varchar(255)` | `scheduled` or `triggered` |
| `status` | `varchar(255)` | `pending`, `completed`, `expired`, `canceled`, `queued` |
| `created_at` | `timestamp` | Start of the run |
| `updated_at` | `timestamp` | For a `completed` row, the end of the run |
| `errors` | `json`, nullable | JSON object keyed by **job ID**, value the error string. `NULL` when the run had no job errors |

Index: `(name, created_at)`.

Use `stats_type` for `scheduled` or `triggered`. Use `status` for the run's progress or terminal state; it never contains those two type values.

### 8.6.2.2 The query

Inspect a schedule’s run times, process IDs, and errors:

```sql
SELECT name, instance, stats_type, status,
       created_at, updated_at,
       TIMESTAMPDIFF(SECOND, created_at, updated_at) AS duration_s,
       errors
FROM   cron_stats
WHERE  name = 'mdm_apple_profile_manager'
ORDER  BY created_at DESC
LIMIT  10;
```

Compare the latest run of every schedule to locate a single stale job or a wider scheduler problem:

```sql
SELECT cs.name, cs.instance, cs.stats_type, cs.status,
       cs.created_at, cs.updated_at, cs.errors
FROM   cron_stats cs
JOIN  (SELECT name, MAX(created_at) AS created_at
       FROM   cron_stats
       GROUP  BY name) latest
  ON   latest.name = cs.name AND latest.created_at = cs.created_at
ORDER  BY cs.created_at ASC;
```

Compare each latest `created_at` with the schedule's interval (§8.6.3). An old latest row identifies work that has not started recently and needs investigation.

Only the runs that errored:

```sql
SELECT name, instance, status, created_at, JSON_KEYS(errors) AS failed_jobs, errors
FROM   cron_stats
WHERE  errors IS NOT NULL
ORDER  BY created_at DESC;
```

`JSON_KEYS(errors)` lists the job IDs that failed. A schedule can complete while individual jobs fail and others continue. Read non-`NULL` `errors` even when `status` is `completed`.

Inspect runs still marked in flight:

```sql
SELECT name, instance, stats_type, status, created_at,
       TIMESTAMPDIFF(MINUTE, created_at, NOW()) AS age_min
FROM   cron_stats
WHERE  status IN ('pending', 'queued')
ORDER  BY created_at ASC;
```

### 8.6.2.3 What `instance` tells you

`instance` is a random identifier generated from 64 bytes at server-process startup. The startup `instance info` log records it as `instanceID`. It has no inherent mapping to a hostname, pod, or task ARN.

- Group errors by `instance` to find a process whose jobs fail while others succeed, such as a node with different Redis or Apple connectivity.
- A different ID on consecutive runs means a different process won the schedule's lock. Confirm a restart through logs or the orchestrator before attributing both IDs to successive processes on one node.

To map an `instance` back to a pod, grep your server logs for the value. That log line is emitted at startup only.

```sql
SELECT instance, COUNT(*) AS runs,
       SUM(errors IS NOT NULL) AS runs_with_errors,
       MIN(created_at) AS first_seen, MAX(created_at) AS last_seen
FROM   cron_stats
WHERE  created_at > NOW() - INTERVAL 6 HOUR
GROUP  BY instance;
```

A high `runs_with_errors` count on one instance helps focus the investigation on that node.

`trigger-api` is a sentinel for a trigger queued for another server's schedule. When the owning node claims it, Fleet replaces that value with the node's instance ID (§8.6.3).

### 8.6.2.4 Status transitions and trigger verification

| Status | Written when |
|---|---|
| `queued` | A trigger was requested for a schedule this node does not run. Waiting for the owning node's poll |
| `pending` | The run has started. Row inserted at start of run |
| `completed` | The run finished. `updated_at` is the end time. `errors` may still be non-`NULL` |
| `canceled` | The run was interrupted by shutdown, or the process was stopped with a run in flight. On graceful shutdown Fleet flips all of that instance's `pending` rows to `canceled` |
| `expired` | Reaped. `pending` or `queued` for more than 2 hours with no live lock in the `locks` table, or more than 12 hours regardless of lock state |

The running process records `canceled` when it handles cancellation or graceful shutdown. The cleanup pass records `expired` when the age and lock rules apply. An expired row can reflect a process that disappeared without closing its run, subject to the exceptions below.

> ### ⚠️ Five schedules can be marked `expired` while they are still running
>
> The two-hour rule spares a run whose schedule still holds a live lock, and it finds that lock by matching the lock's name against the schedule's name. Five schedules take their lock under a different name, so that match never succeeds for them:
>
> | Schedule | Lock name it actually takes |
> |---|---|
> | `cleanups_then_aggregation` | leader |
> | `frequent_cleanups` | leader_frequent_cleanups |
> | `integrations` | worker |
> | `apple_mdm_worker` | apple_mdm |
> | `calendar` | calendar, registered separately from the schedule |
>
> For those five the lock lookup finds nothing, so the reaper falls through to the two-hour timeout and stamps `expired` on a run that is alive and working. The twelve-hour hard cap behaves the same way for everything else.
>
> For example, `cleanups_then_aggregation` contains roughly forty jobs on an hourly schedule. A pass exceeding two hours can still be running after its row is marked expired.
>
> Confirm progress in the owning instance's log. Use row age alongside status; `created_at` retains the run's start time even after expiry is recorded.

`fleetctl trigger --name=<schedule>` returns without triggering in three cases:

1. A `scheduled` run is already `pending`.
2. A `triggered` run is already `pending` or `queued`.
3. The internal trigger channel is busy. Logged as `trigger channel not available`, at debug level.

Cases 1 and 2 surface as an HTTP 409 with a message like `conflicts with current status of <name> schedule: scheduled run started 12.5s ago`. Case 3 looks exactly like success, and at the default log level it leaves no trace.

After requesting a trigger, look for a new `stats_type = 'triggered'` row:

```sql
SELECT id, instance, status, created_at, updated_at, errors
FROM   cron_stats
WHERE  name = 'apple_mdm_dep_profile_assigner'
  AND  stats_type = 'triggered'
ORDER  BY created_at DESC
LIMIT  3;
```

A latest triggered row older than the command provides no evidence of a new run.

### 8.6.2.5 Retention

An hourly cleanup deletes rows older than two days. It runs outside the schedule system so it can maintain the table that schedules use to decide whether to run.

Capture `cron_stats` early. Its two-day retention will not preserve a run for an investigation that starts the following week.

When Fleet asks itself for the latest state of a schedule it reads at most two rows: the newest `scheduled` row with status `pending` or `completed`, and the newest `triggered` row with status `pending`, `completed`, or `queued`. `expired` and `canceled` rows fall outside that window, so read those yourself.

Trigger any of them:

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

Triggering it creates a `queued` row with `instance = 'trigger-api'`. The processing node polls every sixty seconds to claim that row. Allow for the poll, then check the processing node if it remains queued.

## 8.6.4 `upcoming_activities`: the unified per-host queue

One table holds the queue for scripts, software installs, software uninstalls, [VPP](../09-appendices/a.6-glossary-and-release-compatibility.md#vpp) installs, and in-house app installs. Type-specific arguments live in sibling tables (`script_upcoming_activities`, `software_install_upcoming_activities`, `vpp_app_upcoming_activities`, `in_house_app_upcoming_activities`), keyed by `upcoming_activities.id`.

| Column | Type | Meaning |
|---|---|---|
| `id` | `bigint unsigned` | Autoincrement |
| `host_id` | `int unsigned` | Joins `hosts.id` |
| `priority` | `int`, default 0 | Higher runs first. Setup-experience items use a raised priority |
| `user_id` | `int unsigned`, nullable | Who requested it. `NULL` for Fleet-initiated work |
| `fleet_initiated` | `tinyint(1)` | 1 when Fleet queued it, not a user |
| `activity_type` | `enum` | `script`, `software_install`, `software_uninstall`, `vpp_app_install`, `in_house_app_install` |
| `execution_id` | `varchar(255)`, unique | The ID you see in the API, in activity records, and in `host_script_results` / `host_software_installs` |
| `payload` | `json` | Type-dependent. Keys seen in Fleet's own queries include `$.user.name`, `$.user.email`, `$.software_title_name`, `$.installer_filename`, `$.source` |
| `activated_at` | `datetime(6)`, **nullable** | **`NULL` = queued, not started. Non-`NULL` = started** |
| `created_at` / `updated_at` | `datetime(6)` | Enqueue time and last change |

### 8.6.4.1 Activation semantics

Fleet activates **one activity at a time per host**. When an activity reaches a final state, Fleet deletes its row and activates the next one, ordered by:

```
ORDER BY (activated_at IS NOT NULL) DESC, priority DESC, created_at ASC
```

Activation means inserting into the executing table (`host_script_results` for scripts, `host_software_installs` for installs, `host_vpp_software_installs` plus a nano queue entry for VPP) and stamping `activated_at`. Consecutive `vpp_app_install` rows are batch-activated up to **5** at a time to cut push count.

If the first activity has `activated_at IS NULL` and no activity is running, inspect a blocked queue. `upcoming_activities_maintenance` attempts to unblock up to 500 hosts every ten minutes.

### 8.6.4.2 Queries

Everything queued for one host, in execution order:

```sql
SELECT ua.id, ua.activity_type, ua.execution_id, ua.priority,
       ua.fleet_initiated,
       ua.activated_at,
       ua.created_at,
       TIMESTAMPDIFF(MINUTE, ua.created_at, NOW()) AS age_min,
       ua.payload
FROM   upcoming_activities ua
JOIN   hosts h ON h.id = ua.host_id
WHERE  h.uuid = '<host-uuid>'
ORDER  BY (ua.activated_at IS NOT NULL) DESC, ua.priority DESC, ua.created_at ASC;
```

Queue depth by type, fleet-wide:

```sql
SELECT activity_type,
       COUNT(*)                                AS total,
       SUM(activated_at IS NULL)               AS not_started,
       SUM(activated_at IS NOT NULL)           AS in_flight,
       MIN(created_at)                         AS oldest
FROM   upcoming_activities
GROUP  BY activity_type;
```

Find hosts with growing or old pending work:

```sql
SELECT h.id, h.hostname, h.uuid,
       COUNT(*) AS queued,
       MIN(ua.created_at) AS oldest,
       TIMESTAMPDIFF(HOUR, MIN(ua.created_at), NOW()) AS oldest_age_h,
       SUM(ua.activated_at IS NOT NULL) AS activated
FROM   upcoming_activities ua
JOIN   hosts h ON h.id = ua.host_id
GROUP  BY h.id, h.hostname, h.uuid
HAVING oldest_age_h > 2
ORDER  BY queued DESC
LIMIT  50;
```

A large queued count with `activated = 0` indicates blocked activation. With `activated = 1`, inspect the active work's age and `execution_id` in `host_script_results` or `host_software_installs` to determine what is holding later work.

Compare the estate-wide results across an interval, such as twenty minutes. Falling counts show progress. Growing counts require checking whether work has stopped or is arriving faster than it completes.

Find one execution ID anywhere:

```sql
SELECT 'upcoming' AS src, host_id, activity_type, activated_at, created_at
FROM   upcoming_activities WHERE execution_id = '<execution-id>'
UNION ALL
SELECT 'script', host_id, 'script', NULL, created_at
FROM   host_script_results WHERE execution_id = '<execution-id>';
```

## 8.6.5 Apple MDM tables

The Apple MDM stack is NanoMDM. Its tables are prefixed `nano_` and are joined to Fleet's by **`hosts.uuid = nano_enrollments.id`** for the device channel.

| Table | Holds |
|---|---|
| `nano_devices` | One row per device that ever completed `Authenticate`. `id` (UDID), `serial_number`, `identity_cert`, `authenticate` / `authenticate_at`, `token_update` / `token_update_at`, `bootstrap_token_b64` / `bootstrap_token_at`, `unlock_token` / `unlock_token_at`, `platform`, `enroll_team_id` |
| `nano_enrollments` | One row per channel. `id`, `device_id`, `user_id`, `type`, `topic`, `push_magic`, `token_hex`, `enabled`, `token_update_tally`, `last_seen_at`, `enrolled_from_migration`, `hardware_attested` |
| `nano_commands` | The command itself, once, shared across recipients. `command_uuid`, `request_type`, `command` (the raw plist), `subtype` (`None` or `ProfileWithSecrets`), `name` |
| `nano_enrollment_queue` | The per-enrollment queue. `id`, `command_uuid`, `active`, `priority`, `created_at` |
| `nano_command_results` | Device replies. `id`, `command_uuid`, `status`, `result` (raw XML), `not_now_at`, `not_now_tally` |
| `nano_view_queue` | **A view** joining the three above. Use this instead of writing the join |
| `nano_dep_names` | Per-ABM-token DEP state. `name`, OAuth credentials, `access_token_expiry`, `syncer_cursor`, `syncer_cursor_at`, `assigner_profile_uuid`, `assigner_profile_uuid_at` |
| `nano_cert_auth_associations` | Device identity cert binding. `id`, `sha256`, `cert_not_valid_after`, `renew_command_uuid` |
| `nano_push_certs` | APNs push certificate per `topic`. `cert_pem`, `key_pem`, `stale_token` |

`nano_enrollments.type` carries the NanoMDM enrollment type: `Device`, `User`, `User Enrollment (Device)`, `User Enrollment`, `Shared iPad`. Fleet's own queries filter to `type IN ('Device', 'User Enrollment (Device)')` when they want the device channel.

`nano_command_results.status` carries Apple's value: `Acknowledged`, `Error`, `CommandFormatError`, `NotNow`. `Idle` is never stored. A `NotNow` reply leaves the queue row `active` and bumps `not_now_tally`; `not_now_at` records only the **first** `NotNow`.

### 8.6.5.1 Queries

The command queue for a host, with results, using the view:

```sql
SELECT q.command_uuid, q.request_type, q.name,
       q.active, q.priority, q.created_at,
       q.status, q.result_updated_at
FROM   nano_view_queue q
WHERE  q.id = '<host-uuid>'
ORDER  BY q.priority DESC, q.created_at;
```

Inspect commands still awaiting results, using the class 3/4 distinction in §8.1.5:

```sql
SELECT ne.id AS host_uuid, h.hostname,
       nc.request_type, nc.command_uuid,
       neq.created_at,
       TIMESTAMPDIFF(HOUR, neq.created_at, NOW()) AS age_h
FROM   nano_enrollment_queue neq
JOIN   nano_commands nc     ON nc.command_uuid = neq.command_uuid
JOIN   nano_enrollments ne  ON ne.id = neq.id
LEFT  JOIN nano_command_results ncr
       ON ncr.command_uuid = neq.command_uuid AND ncr.id = neq.id
LEFT  JOIN hosts h ON h.uuid = ne.device_id
WHERE  neq.active = 1
  AND  ncr.status IS NULL
ORDER  BY neq.created_at ASC
LIMIT  100;
```

Errors and their raw payload. `result` is a plist, so read it as text:

```sql
SELECT ncr.id AS host_uuid, nc.request_type, ncr.status,
       ncr.updated_at, ncr.not_now_tally,
       CONVERT(ncr.result USING utf8mb4) AS result_xml
FROM   nano_command_results ncr
JOIN   nano_commands nc ON nc.command_uuid = ncr.command_uuid
WHERE  ncr.status = 'Error'
  AND  ncr.updated_at > NOW() - INTERVAL 1 DAY
ORDER  BY ncr.updated_at DESC
LIMIT  50;
```

Find enabled MDM enrolments with stale check-ins. `last_seen_at` advances on every MDM message, including `Idle`, so use this result to investigate the push and return path:

```sql
SELECT ne.id AS host_uuid, h.hostname, h.hardware_serial,
       ne.type, ne.enabled, ne.last_seen_at,
       TIMESTAMPDIFF(DAY, ne.last_seen_at, NOW()) AS days_quiet
FROM   nano_enrollments ne
LEFT  JOIN hosts h ON h.uuid = ne.device_id
WHERE  ne.enabled = 1
  AND  ne.type IN ('Device', 'User Enrollment (Device)')
  AND  ne.last_seen_at < NOW() - INTERVAL 7 DAY
ORDER  BY ne.last_seen_at ASC;
```

To find Apple Business assignments that have not enrolled, start with `host_dep_assignments`, where ABM sync stores the assignment. Starting from `nano_devices` limits the result to devices that already completed MDM `Authenticate`, which answers a different enrolment question.

```sql
SELECT h.id, h.hardware_serial, h.platform,
       hda.added_at, hda.assign_profile_response
FROM   host_dep_assignments hda
JOIN   hosts h ON h.id = hda.host_id
LEFT   JOIN nano_enrollments ne
       ON ne.device_id = h.uuid
      AND ne.enabled = 1
      AND ne.type IN ('Device', 'User Enrollment (Device)')
WHERE  hda.deleted_at IS NULL
  AND  ne.id IS NULL
ORDER  BY hda.added_at;
```

`token_update_at` being `NULL` on a device with a non-`NULL` `authenticate_at` means the device authenticated and then never sent `TokenUpdate`, so Fleet holds no push token for it and cannot deliver a command.

Managed certificates approaching expiry, which is what `renew_host_mdm_managed_certificates` inside `cleanups_then_aggregation` is meant to handle:

```sql
SELECT hmmc.host_uuid, hmmc.type, hmmc.ca_name, hmmc.serial,
       hmmc.not_valid_after,
       DATEDIFF(hmmc.not_valid_after, NOW()) AS days_left,
       hmmc.challenge_retrieved_at
FROM   host_mdm_managed_certificates hmmc
WHERE  hmmc.not_valid_after < NOW() + INTERVAL 30 DAY
ORDER  BY hmmc.not_valid_after ASC;
```

The example's thirty-day window is a quick screen. The renewal job uses the certificate's full validity period: certificates lasting more than thirty days become eligible with thirty days remaining; shorter certificates become eligible with half their lifetime remaining. A ten-day certificate is therefore eligible around day five.

Each pass caps renewals at 1,000 per certificate type, shared across Apple and Windows. The type is the SCEP CA type or the non-proxied bucket for certificates ingested outside Fleet's proxy. Remaining work waits for the next run.

A populated `challenge_retrieved_at` with no `serial` or `not_valid_after` means Fleet inserted the SCEP challenge into the profile but has not matched a subsequently reported certificate. Those fields are filled when host certificate inventory matches the profile's renewal marker. Investigate the stages between challenge retrieval and that inventory match.

Check profile delivery, the SCEP proxy's request to the endpoint, CA issuance, certificate installation, host inventory reporting, and the final match. A delay at any of those stages can leave the same row state.

### 8.6.7.2 Half-enrolled hosts: MDM live, agent stale

Compare agent and Apple MDM timestamps to find a working MDM enrolment with a silent agent. Online/offline uses agent last-seen time, so it groups this host with sleeping laptops. Missing/MIA uses the later of agent and MDM activity, so a fresh MDM check-in can keep a host out even if its agent never reported.

The query uses `host_seen_times.seen_time` for agent activity and `nano_enrollments.last_seen_at` for MDM. The latter advances on every MDM message, including `Idle`.

```sql
-- Example thresholds only; choose them for your estate.
SELECT h.hostname,
       h.uuid,
       h.platform,
       hm.enrollment_status,
       hst.seen_time   AS agent_last_seen,
       ne.last_seen_at AS mdm_last_seen
FROM hosts h
JOIN host_mdm hm
  ON hm.host_id = h.id
JOIN nano_enrollments ne
  ON ne.id = h.uuid
 AND ne.type IN ('Device', 'User Enrollment (Device)')
 AND ne.enabled = 1
LEFT JOIN host_seen_times hst
  ON hst.host_id = h.id
WHERE h.platform = 'darwin'
  AND hm.enrolled = 1
  AND ne.last_seen_at >= NOW() - INTERVAL 7 DAY
  AND (
        hst.seen_time IS NULL
        OR hst.seen_time < NOW() - INTERVAL 7 DAY
      )
ORDER BY ne.last_seen_at DESC;
```

Join `ne.id = h.uuid` using the enrolment-channel key. The device-channel types currently share that value with `ne.device_id`, but `id` remains correct if the filter is expanded to user channels. Adjust the example's seven-day windows for your operating requirements: use a few osquery intervals for agent freshness and the required recent-contact window for MDM.

The `h.platform = 'darwin'` filter limits this detector to macOS. Other platforms require different evidence:

- iOS and iPadOS have no agent, so an absent agent `seen_time` is expected.
- Linux has agent reporting but no `host_mdm` row for this join.
- ChromeOS reports through the Fleetd for Chrome extension into `host_seen_times`, but has neither `host_mdm` nor `nano_enrollments` records ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)).
- Windows has `host_mdm` state but no Apple `nano_enrollments` row. Its `mdm_windows_enrollments` table also lacks a `last_seen_at` column, so it needs a separate detector ([8.6.6](#866-windows-mdm-tables)).

Use this with the [MDM-gone-quiet query](#8651-queries) to compare the two directions: a reporting agent with silent MDM, or responsive MDM with a silent agent. [8.4](8.4-host-side-investigation.md) provides the host-side checks.

Choose the join key by platform. `setup_experience_status_results.host_uuid` stores Fleet's UUID for Apple and Android, but `osquery_host_id` for Windows and Linux. Join through `hosts` as below to look up any platform by its Fleet UUID:

```sql
SELECT sesr.name, sesr.status, sesr.policy_gated, sesr.error,

       sesr.script_execution_id, sesr.nano_command_uuid

       END

ORDER  BY sesr.id;
```

### `jobs`

The async worker queue. Three schedules drain it, each taking a different subset of the `name` column: `integrations` and `apple_mdm_worker` between them handle most of it, while `scheduled_batch_activities` takes the batch-script rows.

Use the schedule name with `fleetctl trigger` and the job name when inspecting queued work. For example, `apple_mdm_worker` is the schedule; it drains jobs named `apple_mdm`, which is also its alternate lock name. `apple_mdm` is not a valid trigger target.

| Column | Meaning |
|---|---|
| `name` | `apple_mdm`, `macos_setup_assistant`, `apple_software`, `software_worker`, `jira`, `zendesk`, `db_migration`, `batch_scripts`, `chart_scrub_dataset_global`, `chart_scrub_dataset_fleet` |
| `args` | `json` |
| `state` | `queued`, `success`, `failure` |
| `retries` | Attempt count |
| `error` | `text`. The full error, unlike `setup_experience_status_results.error` |
| `not_before` | Do not run until this time. **A future `not_before` is backoff, not a stall** |

```sql
SELECT name, state, retries, not_before, created_at, updated_at,
       SUBSTRING(error, 1, 300) AS error
FROM   jobs
WHERE  state != 'success'
ORDER  BY created_at DESC
LIMIT  50;
```

Backlog by name, and whether it is moving:

```sql
SELECT name, state, COUNT(*) AS n,
       MIN(created_at) AS oldest, MAX(not_before) AS latest_not_before
FROM   jobs
GROUP  BY name, state
ORDER  BY n DESC;
```

`cleanup_worker_jobs` inside `cleanups_then_aggregation` removes successful jobs. For an accumulated success backlog, check that schedule's recent runs and errors in `cron_stats`.

## 8.6.9 DEP sync, and the one safe mutation

Fleet syncs ABM-assigned devices through NanoDEP, driven by a cursor stored per ABM token in `nano_dep_names`.

| Cursor state | Apple API Fleet calls |
|---|---|
| `syncer_cursor IS NULL` | `fetch-devices` (full list) |
| `syncer_cursor` set | `sync-devices` (deltas only) |

Mechanics:

- **200 devices per request**, looping until Apple reports no more pages.
- Cadence is `mdm.apple_dep_sync_periodicity`, **default 1 minute**.
- **Apple expires cursors after 7 days.** Fleet recovers on its own by falling back to a full fetch.
- Devices that hit Apple's throttling threshold stop being returned on cursor requests until the cooldown ends.

```sql
SELECT name,
       syncer_cursor IS NOT NULL AS has_cursor,
       syncer_cursor_at,
       TIMESTAMPDIFF(HOUR, syncer_cursor_at, NOW()) AS cursor_age_h,
       access_token_expiry,
       DATEDIFF(access_token_expiry, NOW())          AS token_days_left,
       assigner_profile_uuid_at
FROM   nano_dep_names;
```

A cursor older than 168 hours has passed Apple's expiry and will cause a full fetch on the next sync. A negative `token_days_left` identifies an expired ABM token, which can stop new devices appearing without a UI error.

### Resetting the cursor

The documented reset re-baselines Fleet's assignment list and is supported on large deployments. It leaves device enrolment, ABM assignments, and DEP profile delivery unchanged. Use `nano_dep_names.name`, the token's primary key, to limit the reset to the intended token:

```sql
UPDATE nano_dep_names
SET    syncer_cursor    = NULL,
       syncer_cursor_at = NULL
WHERE  name = '<token-name>';
```

Reset every ABM token at once only if you mean to, by dropping the `WHERE` clause:

```sql
UPDATE nano_dep_names
SET    syncer_cursor    = NULL,
       syncer_cursor_at = NULL;
```

Then force the sync and confirm it ran:

```sh
fleetctl trigger --name=apple_mdm_dep_profile_assigner
```

```sql
SELECT instance, stats_type, status, created_at, updated_at, errors
FROM   cron_stats
WHERE  name = 'apple_mdm_dep_profile_assigner'
ORDER  BY created_at DESC LIMIT 3;
```

## 8.6.10 Redis

Redis holds live-query coordination and results, recorded errors, IP bans and rate limits, pending failing-policy sets, and caches. Losing that data resets the in-flight reports, counters, and error buffer. Pending policy sets also drive Jira, Zendesk, and webhook deliveries; those undelivered notifications are not reconstructed ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)). Account for that transient state alongside the MySQL system of record described in [1.6](../01-foundations/1.6-the-fleet-server.md).

| Key pattern | Holds |
|---|---|
| `livequery:{<campaignID>}` | Bitfield of target host IDs. The braces are literal, and are the cluster hash tag |
| `sql:livequery:{<campaignID>}` | The campaign's SQL |
| `livequery:active` | Set of active campaign IDs |
| `livequery:active:reverse`, `livequery:host:<hostID>` | Reverse targeting model: campaign IDs per host |
| `results_<campaignID>` | A **pub/sub channel** rather than a key. Results stream over it |
| `error:{<hash>}:json` | A recorded server error, JSON |
| `error:{<hash>}:count` | Occurrence count for that error |
| `policies:failing:<policyID>`, `policies:failing_sets` | Hosts failing each policy, awaiting webhook |

### Reading the recorded errors

Save the recorded errors before flushing. This Redis store is shared, so clearing it removes the retained evidence for every operator.

```sh
fleetctl debug errors --outfile errors.json   # capture first: non-destructive, writes a copy
fleetctl debug errors --flush                 # only after that copy exists: reads, then clears Redis
```

Recorded errors use `error:{…}:json` keys and the `logging.error_retention_period` TTL, defaulting to twenty-four hours. [8.5](8.5-fleetctl-debug.md) covers collection and retention.

### The pub/sub buffer limit

Live report results reach the browser as: device → Fleet → Redis pub/sub → the Fleet node holding the websocket → browser. Redis drops a pub/sub subscriber that falls behind its output buffer, and Fleet is that subscriber.

Default:

```
client-output-buffer-limit pubsub 32mb 8mb 60
```

The default hard limit is 32 MB; the soft limit is 8 MB sustained for sixty seconds. A wide live-report result can exceed that buffer and lose its subscriber. Fleet logs the disconnect and sends a pub/sub error through the websocket, allowing the client to mark the run interrupted. It does not retry or resume, so the returned rows remain partial ([1.6](../01-foundations/1.6-the-fleet-server.md#redis-publishsubscribe-the-live-query-buffer-that-fills-first)).

To remove the limits:

```
client-output-buffer-limit pubsub 0 0 0
```

For AWS ElastiCache, configure the three parameter-group settings separately:

| Redis config | ElastiCache parameter |
|---|---|
| hard limit (first value) | `client-output-buffer-limit-pubsub-hard-limit` |
| soft limit (second value) | `client-output-buffer-limit-pubsub-soft-limit` |
| soft seconds (third value) | `client-output-buffer-limit-pubsub-soft-seconds` |

Read back the effective values after changing the parameter group:

```sh
redis-cli CONFIG GET 'client-output-buffer-limit'
```

More on this failure mode, and the rest of the degradation procedure, in [8.14](8.14-degradation.md).

### Redis health at a glance

```sh
redis-cli INFO clients      # connected_clients, blocked_clients, client_output_buffer figures
redis-cli INFO stats        # pubsub_channels, expired_keys, evicted_keys
redis-cli INFO memory       # used_memory, maxmemory, maxmemory_policy
redis-cli INFO replication
```

Rising `evicted_keys` with a policy other than `noeviction` shows memory pressure removing data Fleet expects to retain. That can cause intermittent live-report failures. Inspect Redis memory and eviction settings.

Count campaign keys with the incremental scan below. Avoid the blocking `KEYS` command on production:

```sh
redis-cli --scan --pattern 'livequery:*' | head -50
redis-cli SCARD livequery:active
```

If `livequery:active` keeps growing, inspect campaign cleanup. The `cleanup_live_queries` and `distributed_query_campaigns` jobs run inside `cleanups_then_aggregation`; check its `cron_stats` results.

If Fleet is deployed against a Redis **cluster**, the braces in key names (`error:{<hash>}:json`, `livequery:{<id>}`) are hash tags that keep related keys on one slot. Do not rewrite them.

## 8.6.11 Getting access

Complete database diagnostics in `fleetctl debug archive` require global `PROCESS` and `SELECT` privileges. Without them, database members can fail or return restricted results. Separately, `Failed profile` identifies a failed CPU capture; retain the remaining archive and report the missing member ([8.5](8.5-fleetctl-debug.md)).

The diagnostic SQL below needs `SELECT` on Fleet's schema. Provision that read-only account during setup with the following statements. They change database-server access rather than Fleet application data:

```sql
CREATE USER 'fleet_ro'@'%' IDENTIFIED BY '<password>';
GRANT SELECT ON fleet.* TO 'fleet_ro'@'%';
```

Point it at the read replica if one is configured. Read replica settings are fully independent from the primary, so `mysql_read_replica_address` and its siblings must all be set explicitly.

> Arrange database access before an incident or escalation. Managed deployments may not expose it directly. Confirm who can collect `cron_stats` and the other required rows on your behalf.

<a id="8612-triggering-is-writable-reading-the-result-is-not"></a>

## 8.6.12 Access for triggering and verifying schedules

An authenticated user with schedule-write permission can call `POST /api/v1/fleet/trigger`. Verifying the run through `cron_stats` requires database access because Fleet has no read API for that history. Arrange both capabilities when planning scheduled-work diagnosis.

## 8.6.13 Scoping: which fleet, which labels, was this host targeted

Check targeting before delivery. A host outside the resolved scope has no delivery row or delivery log for the item. The following SELECT queries help identify class 1 from §8.1.5.

| Question | Table |
|---|---|
| Which fleet does Fleet think this host is in | `hosts.team_id`. `NULL` is the no-fleet scope, which is a **sibling** of the named fleets and not their parent |
| Is the host's label state trusted, and how fresh is it | `hosts.label_updated_at`, stamped on every full label report |
| Is the host in this label | `label_membership (host_id, label_id)`, `created_at`, `updated_at`. **No status column**: a stale row and a correct row look identical |
| What kind of label is this | `labels.label_membership_type`: 0 dynamic, 1 manual, 2 host vitals. `labels.label_type = 1` marks a built-in. `labels.team_id` non-NULL confines it to one fleet |
| What scope did the item actually store | `mdm_configuration_profile_labels`, `mdm_declaration_labels`, `software_installer_labels`, `vpp_app_team_labels`, `in_house_app_labels`, `policy_labels`. The pair `exclude` / `require_all` is the scope: `0/0` include-any, `0/1` include-all, `1/0` exclude-any, `1/1` exclude-all (policies only). **`query_labels` is the exception**: it carries `require_all` and no `exclude` column, so a report can be scoped include-any or include-all and never excluded |
| Are host vitals labels being maintained at all | `cron_stats` for `host_vitals_label_membership`, §8.6.2. It runs every 5 minutes and **aborts the whole pass** on the first label that errors |

The host's side of the question, in one query:

```sql
SELECT h.id, h.hostname, h.team_id, h.label_updated_at,
       l.id AS label_id, l.name, l.label_membership_type, l.team_id AS label_team_id,
       l.created_at AS label_created_at, lm.updated_at AS membership_updated_at
FROM   hosts h
LEFT   JOIN label_membership lm ON lm.host_id = h.id
LEFT   JOIN labels l           ON l.id = lm.label_id
WHERE  h.id = <host-id>
ORDER  BY l.name;
```

Use MySQL's NULL-safe `<=>` operator when comparing `team_id`. Ordinary `=` does not match two NULL values and can omit hosts in the unassigned scope.

### The narrowing, in three cuts

**First, compare fleet scope.** Configuration profiles and software titles require an exact `team_id` match with the host under `<=>`. Policies, scheduled reports, and labels can also apply from global scope.

For a mismatch, inspect transfers, enrolment history, and the item's chosen scope. Re-enrolment does not change `team_id`, even with a different enrol secret. A profile or software title created without a fleet reaches unassigned hosts; a global policy, report, or label can apply within named fleets ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Then compare label membership with its freshness and scope:**

| Observation | Reads as |
|---|---|
| Member, scope is an include | Targeting is correct. This is a delivery problem now, class 2 or later |
| Not a member, `label_updated_at` recent | The query genuinely returned zero rows. Re-run the label's SQL as a live query ([8.7](8.7-live-query-introspection.md)) and see |
| Not a member, `label_updated_at` stale | The host has not reported since the label became relevant. Allow for the next evaluation before diagnosing membership |
| Scope is an exclude on a **profile or software title** using a **dynamic** label, and the host got the item anyway | Compare that host's `label_updated_at` against `labels.created_at` for every dynamic label in the exclude list. A label newer than this host's watermark should have withheld delivery from this host; if it did not, something cleared memberships without winding the watermark back |
| Scope is an exclude using a **manual** label, and the host got the item anyway | Manual labels bypass the freshness guard: the query tests `label_membership_type = 0`, the dynamic type, so manual membership is trusted immediately. Check the membership itself |
| Scope is an exclude on a profile or software title, and only some hosts got it | Expected, transiently. **The guard is evaluated per host**, so a host that has reported since the label was created becomes eligible to be judged normally, and the rest are withheld until they report |
| Scope is an exclude on a **policy**, and the host got the item anyway | Policies have no freshness guard, so a policy with a fresh exclusion runs on hosts that have not yet been evaluated for it. Account for this behavior when interpreting policy targeting |

The freshness guard applies to profile and software exclusions. [1.3](../01-foundations/1.3-hosts-fleets-labels.md) describes its per-host behavior and the label types it covers.

**For a population-level mismatch, use the label type to select the next check:**

| Type | Where it fails |
|---|---|
| dynamic | Host-side. `labels.platform` takes one of five values only, and check its exact-match behavior below. A fleet-scoped label is never distributed outside its fleet. A query that **errors** now leaves membership frozen rather than clearing it, so the rows can be a week stale and look fine |
| manual | No host-side path at all. Check whether an apply sent `hosts: []`, which removes every member, and whether the identifiers used are ones Fleet accepts (`id`, `hardware_serial`, `uuid`) |
| host vitals | Check the server-side schedule in `cron_stats`. One failing criteria expression stalls every host vitals label |

<a id="a-dynamic-labels-platform-reaches-fewer-hosts-than-its-name-suggests"></a>

#### Dynamic label platform matching

A label's `platform` accepts exactly five values: the empty string, `darwin`, `windows`, `ubuntu`, and `centos`. Fleet distributes a dynamic label's query to a host when the label's platform is empty, or when it equals **the platform string the host reported for itself**.

Hosts can report many more platform strings than a label accepts. Recognized Linux values include `debian`, `rhel`, `sles`, `kali`, `gentoo`, `amzn`, `pop`, `arch`, `linuxmint`, `void`, `flatcar`, `coreos`, `zorin`, and `cachyos`. A label set to `ubuntu` reaches hosts reporting `ubuntu`, without including those other Linux platforms. `linux` is not an accepted label-platform value.

For a mixed Linux population, leave `platform` empty and filter in the label SQL. Every host then receives that query.

For label distribution, Fleet treats an `rhel` host as `centos` when its OS version string contains “centos”. This permits a `centos` label to reach those CentOS hosts.

The host-list platform filter has a different accepted set from a label's `platform` field. Zorin hosts, introduced in 4.90.0, report `zorin` and can be selected in the host list, but `zorin` remains invalid in a label definition.

Manual labels reject the `platform` field entirely. Remove it from a manual-label specification rather than relying on it to narrow membership.

Compare `label_membership.updated_at` with each host's `label_updated_at`. A large gap confined to one label helps focus the investigation on that label's query.

### Forcing and shrinking

Request a host refetch through the UI or API to bypass the label interval gate. The `refetch_requested` flag causes evaluation on the next distributed read. This mapping follows the flag and gate in the implementation; it is not documented as a label-refresh operation.

For a bounded targeting test, use one host in a test fleet and an include-any manual label containing that host. Manual membership is trusted immediately, removing host-side label evaluation from the test. Follow [8.11](8.11-reproducing-and-isolating.md) for the broader reproduction procedure.
