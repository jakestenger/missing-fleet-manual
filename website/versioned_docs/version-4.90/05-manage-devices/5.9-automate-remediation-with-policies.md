# Automate responses to policy failures

![Explanation](../_assets/icons/explanation-light.svg) Policy automations help turn findings into follow-up work. When a scheduled policy reports that a device needs attention, Fleet can install software, run a script, notify another system, arrange a calendar event, or contribute to an access decision. This connects the compliance checks you maintain with the actions IT and security staff would otherwise start by hand.

Design each automation around a specific, observable result: the response should address the failed check, tolerate repetition where needed, and leave the policy able to confirm success. Fleet offers predefined responses without workflow dependencies, user-controlled branching or ordering, or transactions across responses. You supply the relationship between the finding and the action.

Choose the response that fits the problem. A missing application may call for installation, while a condition requiring a person's judgment may be better handled through a ticket or appointment. Only the endpoint responses directly change the host.

[4.3](../04-know-your-devices/4.3-use-policies-for-compliance.md) explains policy queries and the difference between pass, fail, and no answer. Here, you will connect those results to a response, test the loop, and inspect what ran.

## Start from a scheduled failing policy result

![Explanation](../_assets/icons/explanation-light.svg) Begin by confirming how the result reaches Fleet. Automations respond to scheduled policy results, so a live test of the same query will not start the response.

**Only a scheduled policy result can trigger an automation.** Fleet sends policy queries to a host roughly hourly, and the answers arrive on the host's ordinary check-in. Running a policy live from the interface takes a different path and triggers nothing.

Three outcomes, and only one of them is a trigger:

| The host reports | Meaning | Triggers? |
|---|---|---|
| **Fail** | The query ran and returned no rows | **Yes** |
| **Pass** | The query ran and returned rows | No |
| **No answer** | The query did not run, or errored | **No, and this matters more than it looks** |

Fleet filters out results it never received before evaluating triggers. Investigate no-answer hosts separately; missing evidence does not automatically start a failure response.

> Fleet evaluates software installs, App Store installs, script runs, and Entra compliance during the request that delivers the failing result. That evaluation can queue endpoint work for later execution. Webhooks, tickets, and calendar events are handled by scheduled jobs. Okta evaluates compliance at sign-in.
>
> These paths have different timing. Endpoint decisions follow the host's check-in; the webhook and ticket job runs every 24 hours by default, and the calendar job runs every five minutes. Include those intervals when setting response expectations.

## Choose an endpoint, workflow, calendar, or access response

![Reference](../_assets/icons/reference-light.svg) Fleet provides seven responses across four categories. Compare what each one does and which systems it needs:

| Response | Kind | What it does | Scope |
|---|---|---|---|
| **Install software** | Endpoint | Installs installer-backed software: a custom package or a Fleet-maintained app | Fleet only |
| **Install App Store app** | Endpoint | Installs a purchased Apple app | Fleet only, macOS |
| **Run script** | Endpoint | Runs a saved script | Fleet only |
| **Webhook** | Workflow | POSTs to a URL you choose | Global or per fleet |
| **Jira or Zendesk ticket** | Workflow | Opens one ticket | Global or per fleet |
| **Calendar event** | Calendar | Books a maintenance window on the user's calendar | Named fleets only |
| **Conditional access** | Access | Marks the host non-compliant to your identity provider | Fleet only |

You can attach several response types to one policy, such as installing a package and opening a ticket for the same failure. They operate independently, with no dependency or transaction connecting them. Design each response to make sense even if another has not completed.

Within one scope, choose a webhook, Jira, or Zendesk as the workflow response. Fleet normally allows one of those destinations at a time.

**Calendar has more prerequisites than the others and its own clock.** It needs the Google Calendar integration configured globally, enablement on the fleet, and a user email for the host in the configured domain. Its job runs every five minutes rather than on the webhook and ticket job's daily cycle. A host with no matching email is skipped silently.

Two boundaries to know before you plan around this:

Endpoint responses, conditional access, and continuous mode cannot be attached to an **All fleets** policy; Fleet rejects those combinations. Calendar settings are accepted on All fleets and Unassigned policies, but the event-creation job only visits named fleets, so those settings never produce events. Use a named fleet for calendar responses.

**The App Store option is reached through Install software**, not as a separate choice. It is one selector with two kinds of thing behind it.

![Explanation](../_assets/icons/explanation-light.svg) Choose how often a persistent failure should lead to action. The right mode depends on whether a single attempt is sufficient or the response should keep trying as conditions change.

By default an endpoint response fires on a host's **first failure, or on a pass turning into a fail**. A host that simply keeps failing does not re-trigger it. Turn on **continuous automations** and the same three responses fire on every failing result instead.

**Continuous mode changes only software, App Store apps and scripts.** Webhooks, tickets, calendar events and conditional access are unaffected by it.

<a id="the-asymmetry-that-will-confuse-you-first"></a>

### When Fleet checks the policy again

**A successful install asks the host to refetch, and a successful script does not.**

That one difference sets how fast you learn whether the response worked:

| After a successful… | The policy re-runs | So you see the result |
|---|---|---|
| **Software or App Store install** | On the host's next check-in | **In about ten seconds** |
| **Script** | At the ordinary policy cadence | **In up to about an hour** |

> After a successful script, the policy can continue to show failing until the next scheduled result arrives, roughly an hour later on a healthy reporting host. Allow for that verification interval before treating the unchanged result as a new failure.

A refetch requested for another reason can bring that verification forward. Offline hosts or delayed reporting can extend it beyond the ordinary policy interval.

<a id="the-loop-that-does-not-close"></a>

### When a successful response leaves the policy failing

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Fleet does not check whether a successful response makes the policy pass. It provides no convergence metric, oscillation detector, or circuit breaker, so test the response against the policy's actual success condition.

If a response succeeds but the policy keeps failing, the trigger mode determines what happens next:

- **Transition-based.** The response fires once. The host is already recorded as failing, so no later result is a transition, and **nothing happens again.** No retry, because retries only cover responses that *failed*. No activity, no warning. It stays that way until something re-arms the policy, and the last section lists what does.
- **Continuous.** The response fires again on every failing result, damped differently per type. An install is limited to one per policy interval once it has succeeded. **A script has no such limit** and runs each time.

Transition mode suits work that should start once for a newly observed failure. Continuous mode suits repeatable work that needs another opportunity while the condition persists. Monitor the outcome in either case.

> Make the response safe to repeat ([5.3](5.3-run-and-manage-scripts.md) covers idempotent scripts and [5.4](5.4-manage-software-and-applications.md) covers repeated installs). Choose the trigger mode deliberately. Then write the policy so it passes only after the intended change is visible to osquery. Fleet does not validate those relationships for you.
>
> In the pilot, check both whether the response runs and whether the next policy result confirms the intended change.

### How no-answer re-arms transition mode

An intermittent query error can cause repeated responses even in transition mode.

**A policy whose query intermittently errors on a host alternates between "failing" and "no answer".** Fleet stores the no-answer over the previous value, so the next genuine failure looks like a brand-new first failure. Every recovery re-fires the response and re-registers the host for a webhook or ticket, with no cooldown in the way, because as far as Fleet is concerned this is a fresh transition.

Check for missing tables, intermittently available extensions, or host-specific permissions when a transition-mode automation repeats unexpectedly. Those conditions can make the query alternate between no answer and failure.

## Validate policy, action, scope, and transport compatibility

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Validate the policy, response, and target population together. Save-time checks catch some incompatible combinations; others appear only when a host reports a result or tries to execute the work.

Fleet checks a good deal when you save a policy: that the platform tokens are real, that labels exist and are visible, that the script or installer belongs to the same fleet, that an App Store app is macOS, that conditional access is only on macOS or Windows, that endpoint responses and continuous mode are not on an "All fleets" policy.

Also review these relationships, which Fleet does not validate on save:

| Not checked at save time | What happens instead |
|---|---|
| **Whether the installer's platform matches the policy's** | Accepted. At runtime the host is skipped, at debug log level only |
| **Whether the script's type matches the policy's platform** | The same |
| **Whether the installer's label scope overlaps the policy's** | Accepted. See below, because this one is worse than it sounds |
| **Agent version** | Never checked. A host without fleetd silently gets nothing |

Runtime adds its own gates that have no save-time equivalent: the host needs fleetd, scripts must be enabled both globally and on the host, and an App Store install needs Apple MDM.

> **Fixed in 4.90.1.** On Fleet 4.90.0 a policy automation could act on an App Store app that was added for a platform other than the host's, rather than skipping it. Fleet 4.90.1 fixes this.

> If a failing host falls outside the attached installer's label scope, Fleet changes that policy result to did not run. Host details therefore stop showing that result as a failure.
>
> Conditional access has already evaluated the original failure earlier in the request. The webhook and ticket filter runs later and sees the cleared result.
>
> This can leave a host reported as non-compliant to the IdP while Fleet's interface shows no failure and sends no notification. Only a debug log records the suppression. Align the policy and installer scopes when combining installation with conditional access.

### The configuration contract for tickets

**Jira and Zendesk read their list of policies from the webhook settings block.** Not from the integration's own configuration. If a policy's ID is not in `webhook_settings.failing_policies_webhook.policy_ids`, no ticket is ever created for it, whether or not the webhook itself is enabled.

The interface and the GitOps `webhooks_and_tickets_enabled` shorthand populate that policy list. If you write the YAML fields directly, include the IDs in `webhook_settings.failing_policies_webhook.policy_ids` for ticket delivery too. The configuration reference describes the field in terms of webhooks, so a valid configuration can still omit the list tickets require.

<a id="conditional-access-is-two-systems-wearing-one-checkbox"></a>

### Compare Okta and Entra conditional access

Okta and Entra share controls in Fleet but evaluate and disable access differently. Plan the response for the identity provider you use:

| | **Microsoft Entra** | **Okta** |
|---|---|---|
| What Fleet does | Reports compliance; Microsoft blocks | **Fleet is the identity provider** and refuses the sign-in itself |
| When it evaluates | On policy results arriving | **On every sign-in attempt** |
| What it reads | The current submission | **Stored pass/fail state** |
| Platforms | macOS and Windows | macOS in practice |

Both use the per-policy conditional-access flag. The fleet-level toggle controls Fleet's Entra reporting; Okta continues to evaluate flagged policies independently of that toggle.

> **Turning conditional access off for a fleet stops Fleet reporting to Entra. It does not stop Okta blocking sign-in.** Okta keeps enforcing every policy that carries the flag. To stop that, remove the flag from the policies.
>
> Disabling the fleet toggle leaves Entra with the last compliance state Fleet sent. Reconcile that state in Entra as part of disabling the integration.

Unknown policy results do not block access in either path. Entra ignores policies absent from a submission, and Okta counts recorded failures only. A host that stops answering therefore does not become non-compliant solely because its results are missing.

The end user grants a conditional-access bypass from My Device. It covers one sign-in, despite wording that may suggest a time window. A failing critical conditional-access policy prevents granting or consuming it. If the host is healthy at the next sign-in, the bypass remains unused with no expiry.

### The Okta path trusts a proxy-set certificate serial

Okta conditional access requires Fleet Premium, the server private key, and a correctly configured mutual-TLS proxy. The proxy's certificate handling establishes the device identity used during sign-in. The Entra path uses a different mechanism.

When a device presents a client certificate to a reverse proxy performing mutual TLS, the proxy passes the certificate's serial number to Fleet in the `X-Client-Cert-Serial` header. Fleet's conditional-access sign-in endpoint reads that header, parses it, and maps the serial straight to a host. There is no cryptographic binding between the serial in the header and the request that carries it: Fleet trusts the value as sent, and no part of the product strips or origin-checks an inbound copy of that header.

A caller able to supply this header could name a known conditional-access certificate and have Fleet evaluate its host without the owning device present. Fleet still rejects revoked, expired, and unknown serials and applies the matched host's health or bypass checks. Preventing header substitution depends on your proxy and network configuration.

Configure both parts of that boundary:

- **The trusted mTLS terminator sets the header from the verified peer certificate, and discards every inbound copy.** It derives the serial from the certificate the client actually presented in the handshake, and it overwrites or removes any `X-Client-Cert-Serial` the client tried to send, so no client-supplied value survives to Fleet.
- **Route the conditional-access endpoint only through that terminator.** Restrict origin access so a client cannot bypass the proxy and supply the header directly.

Match the header's encoding to what the proxy sends with `conditional_access.cert_serial_format`, either `hex` (the default) or `decimal`. A mismatch fails every attempt with a serial-format error, which looks like a configuration fault rather than the security one it is adjacent to. The three conditional-access endpoints, and the fact that the sign-in one is expected on the mutual-TLS origin, are in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md).

## Bound queueing, duplicate work, cooldown, and retries

![Reference](../_assets/icons/reference-light.svg) Separate these four mechanisms when investigating repeated or missing work:

**Re-fire** is the policy deciding to act again. **Retry** is one response trying again after failing. **Duplicate suppression** stops two policies queueing the same work. **Cooldown** damps continuous mode. They are independent.

### Retries

| Response | Budget | Shape |
|---|---|---|
| **Script** | **3 attempts total** | The first run plus two retries, immediately, while the policy still reads as failing |
| **Custom package** | **3 attempts total** | The same. A retry re-resolves to the currently active package, so a version change mid-sequence installs the new one |
| **App Store app** | **3 retries after the first send** | A different mechanism at a different layer, with its own counter |

The App Store difference is deliberate and acknowledged in Fleet's own source. **Do not carry the "three attempts" number across to it**, and note that its retries respond to delivery errors rather than to the policy. One case is terminal and never retried: an app the user already installed personally on a BYOD device.

**Continuous mode re-arms the script and package budget before each new run**, so a continuously failing policy can start a fresh three-attempt sequence indefinitely.

**App Store re-firing does not reset the old counter.** It creates a new install record with a counter of its own, which is why the two budgets never have to be reconciled against each other.

### Cooldown

Continuous installation has a cooldown after success: Fleet will not reinstall more than once per policy interval. This prevents a successful install's refetch from immediately causing another install while the policy still reports failure.

**Scripts have no cooldown, deliberately**, because a script does not request a refetch and so cannot form that loop. A failed install is not throttled either; that case belongs to the retry budget.

### Queueing and duplicates

Policy work joins the host's ordinary queue at normal priority, behind anything from a setup experience. Within one check-in the order is fixed: **scripts, then App Store apps, then packages.** You cannot change it, and there is no dependency mechanism.

> **Changed in 4.90.2.** Fleet-initiated activities (policy-automation installs and scripts, and iOS/iPadOS scheduled app updates) are still queued immediately, but from 4.90.2 they are released to hosts at a configurable rate (`FLEET_ACTIVITY_FLEET_INITIATED_RELEASE_PER_MINUTE`, default 1000 hosts per minute; set it to 0 to remove the limit), which spreads the install and result-ingestion load when one automation fires across many hosts at once. User-initiated activities (self-service installs, admin-run scripts, lock, unlock, wipe, and setup experience) are unaffected and take precedence over queued Fleet-initiated work on the same host.

Fleet does suppress some duplicates: the same script already pending on a host, a package install already pending for that installer, an App Store install already queued for that app. **Two policies pointing at one script or one package therefore collapse into a single execution**, and which policy gets recorded as the cause is not defined. What Fleet does not offer is exactly-once semantics across completed runs.

> **Fixed in 4.90.1.** On Fleet 4.90.0 the App Store side of that suppression did not hold when a host's upcoming-activity queue was not draining, so automatic App Store updates and policy automations could still queue a duplicate install. Fleet 4.90.1 skips an app that already has an install waiting, whether or not it has reached the device.

Serialisation has one exception: consecutive App Store installs at the same priority can activate together rather than strictly one at a time ([5.1](5.1-plan-target-and-govern-device-changes.md) has the exact boundary).

### Where to look

Start with the policy's **automation-runs view**. It connects completed attempts to their policy and host, with success or failure and the script or installation output available for that response. It is the most useful view for understanding what a particular automation did.

The host timeline can show that Fleet ran a script without identifying the originating policy. The global feed can filter automation activity types, but displays them as machine text. These views provide additional context; none shows a pending automation because the automation history is based on completed activities.

**That view is one endpoint, and you can query it directly.** It is backed by `GET /api/latest/fleet/policies/{policy_id}/automation_activities`, the row listed in the audit-log reference ([8.12](../08-troubleshooting/8.12-audit-logs.md)). It returns one row per host per attempt, so three failed script retries against a host read as three rows, each with its own outcome, rather than one collapsed result. A `status` filter narrows it to `error` or `success`. Each row carries the outcome and, for script and install activities, the output: the combined script output, and for an install the separate pre-install-query and post-install-script output, since an install can fail at any of those stages. Rows come newest first and paginated.

The endpoint has no separate licence check; the edition and policy scope determine which response types can produce rows. Webhook and ticket responses are Free. A script response is also Free when the policy is in Unassigned, where attachment and execution have no licence gate. The same script response in a named fleet requires Premium because named fleets require Premium. Software installs, App Store installs, calendar, and conditional access remain Premium. Free deployments can therefore show webhook, ticket, and Unassigned script rows, including script output.

The history contains retained, completed activities for hosts that still exist and are visible to the caller. Deleting a host removes it from this view because the query joins against current hosts; retention can also remove older rows. A GitOps-role caller can read the policy and call the endpoint, but receives no rows because that role lacks the required host visibility ([a.4](../09-appendices/a.4-roles-and-permissions-matrix.md)).

> **There is no convergence metric.** Repeated successful runs against one host in the automation-runs view is the signal to look for, though resets, edits, scope changes and re-enrollment can produce repetition too. Pass and fail counts will not help: they are refreshed hourly and they are a level, not a rate.

<a id="the-three-resets-which-are-not-the-same-thing"></a>

### Choose the appropriate reset

|  | **Reset policy** | **Reset automations** | **Edit the policy** |
|---|---|---|---|
| Clears pass/fail history | **Yes, every host** | No | Only if the query, or the attached script, package or App Store app, changed |
| Refills retry budgets | **Yes** | No | **Yes, on any save, even a typo fix** |
| Re-fires webhooks and tickets | Indirectly | **Yes, and only these** | Indirectly |
| Covers installs and scripts | **Yes** | **No** | Yes |
| Records an activity | Yes | **None at all** | Yes |

Consider the effects of an edit before using it to reset work:

Editing a policy description through the ordinary edit path replenishes every host's retry budget for that policy. It starts no response by itself, but makes hosts with exhausted attempts eligible for retries again. The same description edit through GitOps leaves the counters unchanged.

**Re-arming is not the same as re-firing.** Turning on a webhook or a calendar automation for a policy that hosts are already failing does nothing for those hosts, because there is no new transition to see. Continuous mode acts on the next failing result; attaching a *new* script, package or App Store app clears history and so does re-fire. Changing the other settings clears nothing.

<a id="what-re-arms-a-policy-without-you-asking"></a>

### How re-enrollment and fleet moves re-arm policies

Re-enrollment affects policy history differently by channel. An osquery re-enrollment deletes the host's policy history, making subsequent failures eligible as new failures. An Orbit re-enrollment preserves that history.

Neither resets the script and package attempt counters. If that budget was already exhausted, the re-armed policy gets one new attempt and no retries. An App Store response is unaffected, because it starts a new record with a fresh counter.

Moving a host to another fleet deletes its fleet-policy history and **does not cancel work already queued for it.** A package install ordered by the old fleet still runs.

### Stopping something

Nothing here recalls work an agent already holds ([5.1](5.1-plan-target-and-govern-device-changes.md)). These stop what has not been handed over yet:

1. **Turn scripts off globally.** This withholds even already-activated script work that an agent has not collected. It affects every script on every host, so use it as a deployment-wide pause when that scope is appropriate. Installations have no equivalent pause.
2. **Detach the response from the policy.** Stops future triggers, recalls nothing, and **refills every host's retry budget** as a side effect of the save.
3. **Cancel the queued item on the host.** One item at a time, and only work still waiting. **Cancelling a script that has already been activated can cause Fleet to queue it again**, because the retry check treats a cancelled execution as a failed one. The install path does not have this problem.
4. **Delete the policy.** This cancels queued package work and discards unfinished script records. A queued App Store install continues after losing its policy link. Deleting the entire fleet removes its policies without that cleanup, so queued work can survive the fleet's deletion.
5. **Move the host out**, which stops future triggers and leaves the queue alone.

There is no off switch for automations as a class.

### Three limitations to plan around

**Webhook deliveries are not signed**, so a receiver has to authenticate the request some other way. Treat every field as untrusted input, and expect the occasional duplicate: Fleet clears a batch only after it observes success, so a receiver that commits and then times out will see it again. Tickets have no deduplication at all, so every run creates a new one.

**Host display names arrive empty.** The pending set stores only the host's ID and hostname, so `display_name` is blank in every webhook payload and every ticket bullet renders with empty link text. Use the hostname or the ID.

**Tickets list at most 50 hosts** while the title states the full count for that job, with nothing to indicate the list was cut.

One GitOps warning belongs with these: **creating a fleet from a spec silently drops its failing-policies webhook.** A second apply installs it, because that takes the edit path. Check after the first.

---

A useful automation ends with an observable result: the intended device change, a delivered handoff, or the expected access decision. Review the response history alongside the next scheduled policy result, and refine the query or action when they do not agree. This completes the cycle introduced in [5.1](5.1-plan-target-and-govern-device-changes.md): choose a change, deliver it to the right devices, and check what happened.
