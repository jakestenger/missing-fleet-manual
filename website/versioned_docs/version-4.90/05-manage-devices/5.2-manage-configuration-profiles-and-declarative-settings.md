# Manage configuration profiles and declarative settings

![Explanation](../_assets/icons/explanation-light.svg) Configuration profiles let administrators establish consistent settings across a device population and keep them aligned as membership changes. A Wi-Fi configuration, security setting, or certificate profile can follow the fleet and labels you choose, reducing one-off work on individual devices. Fleet continually reconciles those assignments using the desired-state model in [5.1](5.1-plan-target-and-govern-device-changes.md).

This chapter helps you choose between built-in controls, Apple declarations, and custom profiles, then follow delivery to the device. It also explains what happens when scope changes and how each platform’s status supports verification.

## Choosing where a setting lives

![How-to](../_assets/icons/howto-light.svg) The same setting can often be delivered three ways, and the right choice is usually the highest one on this list that can express what you need.

**Fleet's own settings first.** Where Fleet has a built-in control for something, use it. Disk encryption is the clearest example ([5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md)), as are operating system updates ([5.6](5.6-control-operating-system-updates.md)). Fleet understands what these express, and guards them against conflicting custom profiles.

Built-in OS-update enforcement has its own verification path. Its generated Apple and Windows profiles are hidden from profile lists, Host details, and aggregate profile summaries. Check the setting-change activity and subsequent OS-version inventory as described in [5.6](5.6-control-operating-system-updates.md). Disk-encryption profiles remain visible.

**Then a declaration, on Apple platforms.** Apple's declarative device management lets the device hold the desired state and report its own status, rather than waiting to be told. Fleet supports Apple declarations alongside classic profiles.

**Then a classic profile.** The general-purpose mechanism, and the only one for many settings.

Built-in controls let Fleet understand the intended setting and guard certain conflicts. For example, Fleet refuses built-in OS-update settings while a custom declaration already covers them. Use custom content when you need capabilities or targeting beyond the built-in control, and test that arrangement on the device.

## Authoring, by platform

![Reference](../_assets/icons/reference-light.svg) The three platforms take different formats, and the differences are not cosmetic.

**Apple** takes property list profiles, and declarations as JSON. A profile carries an identifier that must be unique on the device; two profiles claiming the same identifier are one profile as far as the device is concerned, and the second replaces the first.

**Windows** takes configuration in the syntax its management protocol uses, addressing settings by path. There is no equivalent of the Apple profile identifier, so replacement is not implicit.

**Android** works through the device's policy rather than through documents you upload. Configuration is a property of the policy Fleet maintains for the device, which is why Android behaves like desired state even more completely than the other two.

Fleet checks document structure and conflicts with settings it manages, but a successful upload cannot establish that the vendor supports every key on your target OS versions. Test the payload’s effect on a pilot device before expanding its scope ([5.1](5.1-plan-target-and-govern-device-changes.md)).

## Declarations: the user channel, and where it can't reach

![Explanation](../_assets/icons/explanation-light.svg) On macOS, a declaration can target the device or an enrolled user channel. Choose the channel that owns the setting, then confirm the enrollment path can provide it.

**The choice is a top-level key in the declaration itself, `PayloadScope`, set to `"System"` or `"User"`.** Leave it out and Fleet defaults to `"System"`, the device channel: the same one every classic profile uses, and where a declaration lands if you never think about scope at all. Two declarations differing only in that key are delivered on entirely independent connections, each with its own acknowledgment and its own status:

```json
{
  "Type": "com.apple.configuration.<setting>",
  "Identifier": "com.example.device-scoped",
  "Payload": { "<key>": "<value>" }
}
```

```json
{
  "Type": "com.apple.configuration.<setting>",
  "PayloadScope": "User",
  "Identifier": "com.example.user-scoped",
  "Payload": { "<key>": "<value>" }
}
```

**iOS and iPadOS refuse a user-scoped declaration outright, immediately, because those platforms have no user channel to route it to.** This is not a delay: the host's record shows the install as failed as soon as reconciliation looks at it, with a message naming the reason. If a declaration needs to reach a setting on those platforms, it has to go on the device channel or not at all.

**On macOS, the user channel exists only for a host that automatically enrolled**, and Fleet is explicit about this in the failure it produces otherwise: a manually enrolled Mac never gets one, so a user-scoped declaration aimed at it fails for the same reason iOS and iPadOS do, just for a different cause. This is a second, independent reason a user-scoped declaration can be unreachable, beyond platform.

Fleet allows two hours after automated device enrollment for the user channel to appear. During that window it holds the user-scoped declaration and checks again during reconciliation. Once the channel is available, typically after sign-in and account setup, delivery proceeds. If the channel is still absent after the window, Fleet marks the declaration failed.

**Removing a user-scoped declaration behaves differently too, when there is no channel to remove it from.** Fleet cannot enqueue a removal on a connection that does not exist, so instead of leaving a permanent pending row, it drops the record outright, the same way it handles other undeliverable user-scoped content ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md) covers the general device/user-channel routing mechanics this builds on).

## Declaration assets

![How-to](../_assets/icons/howto-light.svg) A declaration that has to carry content too large or too binary to sit inline references an *asset* instead: a separate object Fleet stores once and serves to the device when a declaration asks for it. It is an Apple DDM mechanism, it is Premium, and it needs MDM turned on. Fleet keeps the asset apart from the declaration that points at it, so it has its own upload, its own uniqueness rules and its own deletion behaviour.

**An asset is a small JSON object in its own right, not the file it points to.** Its type begins `com.apple.asset.`, it carries an identifier a declaration will reference, and its payload holds a reference to where the real content lives rather than the content itself:

```json
{
  "Type": "com.apple.asset.<type>",
  "Identifier": "com.example.my-asset",
  "Payload": {
    "Reference": {
      "ContentType": "<mime type>",
      "DataURL": "https://<host>/<path>",
      "Hash-SHA-256": "<hex digest>",
      "Size": 12345
    }
  }
}
```

**Fleet validates the asset before it stores it, and the checks catch real mistakes.** The type must begin `com.apple.asset.` and the reference must carry a non-empty, well-formed data URL, or the upload is refused. The identifier may not contain a secret variable, because an identifier is not a place a secret belongs. And the payload may not carry an authentication key at all: Fleet forces MDM authentication when it serves the asset, so an authentication block in the payload is rejected rather than honoured. The whole asset is capped at roughly a megabyte of content.

**The identifier and the name are each unique within a fleet.** Upload a second asset whose identifier or name is already in use on that fleet and Fleet refuses it, naming which one collided. A declaration then references the asset by its identifier, and the two are delivered together.

**Deletion is blocked while a declaration still points at the asset.** Fleet refuses to delete an asset a configuration profile references and tells you to remove the profile first, so you cannot strand a declaration pointing at content that is no longer there.

Asset calls through the UI or API return a license error on Free. GitOps behaves differently: it uploads paths listed in `controls.macos_settings.assets` before declarations, but skips those asset calls without an error on Free or when MDM is off. Confirm assets were uploaded as well as declarations after a GitOps run. [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) catalogs upload, download, and deletion, and [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md#888-ddm-declarations) covers the device’s asset requests.

## Scoping, and what happens at the edges

![Explanation](../_assets/icons/explanation-light.svg) A profile is attached to a fleet, and optionally narrowed by labels.

Fleet continuously evaluates whether each host belongs in the profile’s scope. When a host leaves, Fleet queues removal of that profile. Include those removals when reviewing a fleet transfer or label change.

**Moving a host between fleets is therefore a configuration change**, not just a reporting change. The host loses what the old fleet declared and gains what the new one declares, and both halves happen as MDM work on the device.

**Label scoping inherits the label's behaviour.** Scope to a dynamic label and membership recomputes as hosts change, so a host can install or remove a profile because its own state changed and nobody touched Fleet ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

Allow time for reconciliation and the device’s delivery channel. A saved content or scope change first becomes pending work, then reaches the host when that channel can deliver it.

## Variables and secrets

![How-to](../_assets/icons/howto-light.svg) Variables let one profile carry values that differ by host, while secret references keep stored credentials out of the authored document. Choose the appropriate source for each value.

Fleet variables use `$FLEET_VAR_NAME` or `${FLEET_VAR_NAME}` and are resolved when a profile is sent to a device. Host and identity values and certificate-authority values serve different purposes.

*Host and identity variables* fill in something Fleet already knows about the host or its user: the hardware serial, the host UUID, the platform, and a set of values sourced from your identity provider including the username, the local part of the username, the full name, the department and group membership. These are how one profile serves an estate.

*Certificate authority variables* support issuance through challenges, proxy URLs, and renewal identifiers. Connect the named authority before using its variables. [2.13](../02-administer-and-deploy-fleet/2.13-connect-certificate-authorities.md) covers NDES, DigiCert, Smallstep, custom authorities, and the supported delivery platforms.

**Secrets are different.** A secret variable is a named value you store in Fleet and reference from a profile, so the profile's content in Fleet does not contain the sensitive value. Names are uppercase letters, digits and underscores.

Use secret references for credentials that should remain outside the authored profile. Host and identity substitutions provide device context; they are not a substitute for secret storage.

The Platform SSO registration-token variable resolves to a signed, per-host token when the device fetches the command. Fleet does not store that resolved token or include it in command listings. Its role is limited to authenticating device registration; [5.5](5.5-design-setup-and-self-service-experiences.md#provision-and-sync-the-local-account-with-platform-sso) covers the IdP configuration, password relay, and local-account mapping.

> ### Rotating a secret does not redeliver the profiles that use it
>
> A profile that references secrets carries a second timestamp beside its checksum, recording when its secrets were last updated, and reconciliation does compare it. **That timestamp is stamped when the profile is applied, from the secrets as they stood at that moment.** Changing a secret's value updates the secret and moves nothing on the profile.
>
> So the loop does not close on its own. **Rotate a credential and every device keeps the old one** until something re-applies the profiles that reference it, which means a GitOps run or a re-upload. The checksum will not have changed either, because it covers the document you authored, placeholders and all, rather than the resolved values.
>
> **Re-apply the profiles as part of the rotation**, and treat the rotation as unfinished until you have. What Fleet does re-queue on a secret change is host display names that reference it, which is a much narrower thing and is easy to mistake for the profiles moving.

![How-to](../_assets/icons/howto-light.svg) The display name a host reports can itself be set from a template, resolved per host from the host and identity variables the previous section describes. It is a Premium feature, and it reaches only the Apple devices Fleet manages as company owned. A personally enrolled (BYOD) Mac, iPhone or iPad is left alone, because Apple refuses a device-name command on a personal enrollment.

**You set one template per scope, on a fleet or on Unassigned, never per host.** The template is a line of text with variables in it; Fleet resolves it against each host in the scope and renames the device to the result. Set it in the interface under the fleet's OS settings, through GitOps as `controls.name_template`, or through the API ([a.5](../09-appendices/a.5-interface-index.md) and [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) carry the exact surfaces). Setting the template back to empty stops Fleet enforcing a name; it does not rename anything back to what it was before.

**The variables are the host and identity family, plus secrets.** A template may use the host-identity variables (`$FLEET_VAR_HOST_HARDWARE_SERIAL`, `$FLEET_VAR_HOST_UUID`, and `$FLEET_VAR_HOST_PLATFORM`, which resolves to `macOS`, `iOS` or `iPadOS`) and the identity-provider end-user variables (the username, its local part, the full name, the department and group membership), the same set the section above describes for profiles. A secret variable works too, for the rare name that has to embed a stored value. Any other Fleet variable is refused when you save. It is not the certificate-authority family: those belong to certificate issuance, not to a name.

**Apple caps a device name at 63 bytes, and that limit is enforced in two places.** Fleet rejects a template outright when its fixed text alone, everything in it that is not a variable, already exceeds 63 bytes, because no host could ever resolve it to a usable name. The rest is per host: if a particular host's resolved name comes out over 63 bytes, or the template asks for an identity-provider value that host does not have, that one host's name fails with a stated reason rather than renaming to something wrong. A template can be valid as a whole while individual hosts fail on their own data.

**Enforcement is desired state, and it reports with the five statuses from the next section.** When a host is in scope Fleet enqueues the rename as work on the device channel, and the host gains a synthetic "Host name" entry beside its profiles that moves through pending, verifying and verified exactly as [Reading status honestly](#reading-status-honestly) below describes; a host already carrying the resolved name goes straight to verified with no command sent. Editing the template, or moving a host between fleets, re-queues the name the same way it re-queues a profile. **Resending obeys the profile rule too:** you can resend a host name that is failed or verified, never one that is pending or verifying, and the resend is per host and recorded ([1.5](../01-foundations/1.5-audit-and-activity.md)). The one thing that re-queues names with no re-apply is a secret change, the narrow case the rotation note above already flagged.

## Reading status honestly

![Reference](../_assets/icons/reference-light.svg) Follow the status for each host and profile, including the operation being performed. The same vocabulary is used across platforms, with different evidence behind some transitions.

**The same five states are used for all three platforms.** Apple, Windows and Android profile records all draw their status from one shared set, so the vocabulary below is worth learning once and applies everywhere. What differs between platforms is how Fleet reaches a given state, not what the state is called.

| Status | What it means |
|---|---|
| **Pending** | Fleet is processing this host and the command may be enqueued |
| **Verifying** | The command was applied successfully, and Fleet has **not** independently confirmed it |
| **Verified** | The strongest state, not a terminal one. On macOS Fleet has independently confirmed the profile against the device's own inventory, and a later report that finds it missing or out of date moves it back into delivery or to Failed. On iOS and iPadOS it means the device acknowledged the install, which is the strongest signal those platforms give. **On ordinary Windows profiles it means only that the device reported the write succeeded**, see below; a Fleet-proxied SCEP profile is the exception and is verified for real ([8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md)) |
| **Failed** | The automatic retry budget is spent, so Fleet will not re-deliver on its own. Not terminal either: on macOS a failed profile that a later report shows present and current moves to Verified by itself |
| *No status yet* | The profile needs to be applied or removed and reconciliation has not reached it |

**Verifying** means the device accepted the command. On macOS, **Verified** adds confirmation that the intended setting is in force. A profile that was accepted but then overridden, reverted, or ignored can remain in Verifying.

> **On ordinary Windows profiles, Verified is a weaker claim than the word suggests.** Fleet marks a custom Windows profile verified when the device reports that the write succeeded. **It does not read the value back.** So a Windows profile can sit at Verified while the setting it carried was later overridden by another policy source, and Fleet would not know. Treat Windows Verified as "the device accepted and applied the write", not as "Fleet has confirmed the current state". **The exception is a profile using a Fleet-proxied SCEP certificate** (custom SCEP proxy, NDES or Smallstep): those report Verified only once Fleet has observed the issued certificate on the host, so for those profiles Verified really does mean confirmed; see [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md) for the failure/timeout behavior around it.

**The unnamed state is counted as Pending.** A profile with no status yet is reported as pending in summaries and filters, so the pending count is really "pending plus not yet looked at". This matters when you are watching a rollout and expecting the pending count to fall monotonically.

Reconciliation can move a status back to Pending or to an unset state as circumstances change. On macOS, later inventory can also change Verified or Failed. Check the new device evidence when a rollout count moves backward.

Before marking an installation Failed, Fleet retries an Apple profile up to three times and a Windows profile once. Investigate the failure before initiating a resend. On macOS, later inventory can also move a failed profile to Verified when the device reports that the current profile is present.

Read the operation type, install or remove, beside the status. Pending removal means the profile is waiting to be taken off the host.

## Changing, resending and removing

![How-to](../_assets/icons/howto-light.svg) Four operations, with different consequences.

**Editing the content** makes it a new desired state and reconciliation delivers it. You do not need to remove the old version first.

You can resend a classic Apple or Windows profile when it is Failed or Verified. Pending and Verifying profiles are refused because their current work has not reached a resendable state. Apple declarations and Android profiles have no per-host resend operation.

**Removing the profile from the fleet removes it from the devices.** This is not the same as deleting a file; it enqueues removal work per host, with its own status.

**Narrowing the scope has the same effect for the hosts that fall outside it**, which is the more common accidental removal. Edit a label used by a profile and you have changed configuration on every host whose membership changed.

A profile resend targets one host and records the profile and host in the activity feed. Use that record to follow a deliberate retry ([1.5](../01-foundations/1.5-audit-and-activity.md)).

You can resend a profile-delivered certificate from the host's OS settings without resending the profile itself. Fleet refuses a certificate still pending its first delivery and returns an explicit message. For an eligible certificate, resend provides one additional delivery attempt; it does not replenish a retry budget. If that attempt fails, diagnose the failure before proceeding.

The resend is per host and records the host and certificate name in activity history ([1.5](../01-foundations/1.5-audit-and-activity.md)). See [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) for the endpoint and [4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md) for the host certificate inventory.

## When a profile is not on a device

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) The order to check things, before escalating to Part VIII.

1. **Is the host in scope?** Check fleet membership and every label used by the profile.
2. **Is the host MDM-enrolled**, and on the platform the profile targets ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md))?
3. **What is the status, and what is the operation type?** A remove in progress looks like a failure to install if you do not read the second column.
4. **Has reconciliation run, and has the device checked in since?** Desired state is not instant, and the wait is the channel's rather than Fleet's ([5.1](5.1-plan-target-and-govern-device-changes.md)).
5. **If the status is verifying and staying there**, the device accepted it and Fleet cannot confirm it. Ask what on the device might be overriding it, including another profile claiming the same identifier.
6. **If failed**, it has exhausted its retries. The reason is the useful part, and resending without a hypothesis just consumes another attempt.

Beyond that, profile delivery problems are MDM channel problems ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md), [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md)).
