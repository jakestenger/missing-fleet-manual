# Manage software and applications

![Explanation](../_assets/icons/explanation-light.svg) Fleet brings application delivery into the same workflow as inventory and vulnerability review. Administrators can choose a Fleet-maintained app, upload a custom installer, or connect supported app stores, then make software available to employees or deploy it to a defined population. The source determines who maintains the package and which channel delivers it: the agent, Apple MDM, or Android policy.

Follow each channel through its completion checks. For an agent-delivered package, success means its lifecycle scripts completed; inventory then provides the separate evidence of what is present on the device.

Software management in this chapter requires Fleet Premium. The software service provides uploads, catalog access, installation, and removal. Reading reported software inventory remains available on Free ([4.4](../04-know-your-devices/4.4-understand-software-and-vulnerabilities.md)).

**A script-only package is a custom package**, not a separate kind. Upload a `.sh`, `.ps1` or `.py` and its contents become the install script. It carries the same lifecycle and the same limits as any other custom package, with one difference that matters later: Fleet writes no uninstall script for it.

Fleet-maintained apps stop at macOS and Windows. One `.ipa` upload creates both an iOS and an iPadOS entry. An Android web app is only a managed link and cannot carry managed configuration.

### The three representations, and why they matter to you

Underneath, Fleet keeps those five things as three:

- **Custom packages and Fleet-maintained apps are the same kind of thing.** A Fleet-maintained app is an ordinary installer entry with a pointer to the catalogue. This is why they share a lifecycle, and why they are the only two sources whose install scripts you can read and edit.
- **App Store apps and Android Play apps are the same kind of thing**, despite going to different platforms by different means. Android borrows Apple's storage model without borrowing its licensing: **an Android app consumes no App and Book licence**, because there is no Apple token in the transaction at all.
- **An in-house `.ipa` is its own kind of thing**, even though it is delivered exactly like an App Store app.

You never see those three names in the interface. You see the consequences: why uninstall works for some sources and not others, why a configuration change reaches a device on one channel and not another, and why deleting a library entry removes software from devices in exactly one case.

### Who can do what

![Reference](../_assets/icons/reference-light.svg) Library management and device installation have separate permissions, allowing packaging work and day-to-day support to be delegated independently.

| Capability | Roles |
|---|---|
| Change the library: upload, edit, delete, pin a version | Admin, Maintainer, GitOps |
| Install or uninstall on a host | Admin, Maintainer, **Technician** |
| Read install and uninstall output | Admin, Maintainer, Technician, Observer, **Observer+** |

**A technician can run software on a host but cannot change what the library offers.** GitOps is the mirror image: it defines the library and cannot act on a host. That split is deliberate, and it is the right thing to design around when deciding who gets which role ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)).

Observers can read install output. Keep that audience in mind when writing lifecycle scripts and reviewing the secret-handling guidance below.

### Where the bytes live

Uploaded installers go to an object store, or to the Fleet server's local filesystem when none is configured. **Use shared object storage for any deployment running more than one Fleet server**, because the server that receives an install request is not necessarily the one holding the file. **Fleet does not detect that mismatch for you.** A local store that initialises successfully logs only an informational note that it is not suitable for production; an error appears only when the local store fails to initialise at all. Nothing tells you your topology is wrong ([2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md)).

For **agent-delivered packages**, hosts do not fetch from the object store directly. They fetch through the configured Fleet server URL, normally HTTPS, or from a signed URL when a CDN is configured, and the agent falls back to fetching through Fleet if the signed URL fails. **A CDN failure alone is silent**: only a failure of that fallback surfaces as an error. If installs are slow or erratic behind a CDN, that silence is where to look first.

**In-house apps work differently.** Fleet can fall back to serving the manifest from a Fleet URL if signing fails, but once an Apple device has been handed a valid signed URL, a later failure of that download has no agent-side fallback behind it. The device is not running Fleet's agent, so nothing retries on its behalf.

The maximum installer size is **10 GiB**, and it is configurable.

## Model software titles, packages, platforms, and conflicts

![Explanation](../_assets/icons/explanation-light.svg) A software title groups the installable packages for an application. This lets you provide different builds or rollout versions while keeping the application recognizable in the library.

A **title** is the application as a concept: 1Password, Google Chrome. Fleet identifies it by bundle identifier on Apple platforms, by upgrade code or name on Windows, and by application id on Android, falling back to the name when nothing stronger is available.

A **package** is one installable artifact belonging to that title, with its own version, platform, scripts and label scope.

**A title can hold up to ten custom packages per fleet.** That limit exists so you can ship architecture variants, staged rollout versions, or different builds to different groups of hosts without splitting them across fleets.

Some combinations are refused rather than merged:

- **A custom package and a Fleet-maintained app cannot share a title.** Fleet says so plainly and names the fleet in the message.
- **The same file twice is refused**, by content hash, within a title.
- A replacement package that resolves to a *different* title is refused with a message saying the selected package is for different software. That is the guard against uploading the wrong installer into an existing entry.

An install request selects one compatible, in-scope package for the host. [Target package variants and resolve overlaps](#target-package-variants-and-resolve-overlaps) explains the selection order and how to avoid ambiguous scope.

![Explanation](../_assets/icons/explanation-light.svg) A custom package is not just a file. It is a file plus up to four pieces of logic, run in a fixed order.

1. **Pre-install query**, optional. An osquery query that gates the install.
2. **Install script.** The thing that actually installs.
3. **Post-install script**, optional. Verification or configuration after the fact.
4. **Uninstall script.** Used when you request an uninstall, and used by Fleet as a rollback.

### What Fleet writes for you, and what it does not

![Reference](../_assets/icons/reference-light.svg) **Fleet generates install and uninstall scripts for four formats only: `.pkg`, `.msi`, `.deb` and `.rpm`.** Everything else needs scripts from you, or carries the catalogue's scripts in the Fleet-maintained case.

Review generated scripts before deployment and supply your own where the format requires it. `.exe` and `.tar.gz` installers have no generated default; `.zip` requires explicit install and uninstall scripts.

**Script-only packages get no generated uninstall script at all.** A `.sh`, `.ps1` or `.py` package is uninstallable only if you write the uninstall script yourself. If you do not, the package installs and then cannot be removed through Fleet.

One format note that catches people out: **a custom `.zip` upload is treated as Windows**, always. Fleet-maintained apps may use a macOS `.zip` internally, because their manifest supplies the platform, but you cannot upload one.

`.py` script packages are new in Fleet 4.90.0, for macOS and Linux.

### The pre-install query is a truth test, and its failure is ambiguous

![Reference](../_assets/icons/reference-light.svg) The query passes if it returns **at least one row**. The values do not matter. Zero rows stops the install before any script runs.

**A query that errors and a query that returns nothing are indistinguishable afterwards.** Both arrive as an empty result, both mark the install failed, and Fleet's own message covers both at once: the query returned no result or failed, and the install stopped. If you are relying on a pre-install query to gate a rollout, test it as a live query first ([4.2](../04-know-your-devices/4.2-run-queries-and-reports.md)), because the install record will not tell the two apart.

<a id="exit-codes-and-the-rollback-that-only-fires-one-way"></a>

### Installation results and rollback triggers

![Reference](../_assets/icons/reference-light.svg) The install script's exit code decides the outcome. A non-zero exit is a failed install, and **the post-install script does not run**. Fleet stops there.

If the install script succeeds and the **post-install** script then fails, Fleet does something it does nowhere else: **it runs the package's uninstall script as a best-effort rollback**, to avoid leaving a half-configured application behind.

Account for these limits when designing and verifying rollback:

- **It only fires on post-install failure.** An install script that fails halfway leaves whatever it did in place. There is no rollback for that.
- **Its output is appended to the post-install output**, not recorded separately. If you are reading a failed install and see uninstall-shaped output, that is why.
- **Its exit code does not change the result.** The install stays failed whether the rollback worked or not, so a rollback that quietly failed looks exactly like one that worked.

<a id="timeouts-and-the-one-that-surprises-people"></a>

### Installation and script timeouts

![Reference](../_assets/icons/reference-light.svg)

| Step | Limit |
|---|---|
| Install script | **1 hour** |
| Post-install script | **1 hour** |
| Rollback after a failed post-install | **1 hour** |
| **An uninstall you request** | **5 minutes**, and configurable |

An operator-requested uninstall runs as an ordinary script and uses the timeout from [5.3](5.3-run-and-manage-scripts.md). A post-install-failure rollback uses the installer’s lifetime instead. The same uninstall script can therefore have a different limit depending on how it was invoked.

Download time is not counted against the install limit.

### Secrets and output

![Explanation](../_assets/icons/explanation-light.svg) Two kinds of variable expand inside lifecycle scripts, and one does not.

| Variable | In lifecycle scripts |
|---|---|
| `$FLEET_SECRET_*` | Expands. This is how a script uses a credential without storing it ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md)) |
| `$FLEET_HOST_VITAL_*` | Expands, to the host's value ([4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md)) |
| `$FLEET_VAR_*` | **Does not expand.** It is a configuration-profile mechanism, and a script referencing one gets the literal text |

**Substituted values are not escaped for the shell.** Fleet puts the value in as text, so a secret or a vital containing a quote, a space or a shell metacharacter changes what the script means. Quote every expansion, and do not assume a value that works today will keep working when someone rotates it into something with punctuation in it.

> **Installer output can expose secrets.** Fleet expands secret values before running lifecycle scripts, but does not redact those values if they appear in the output. Treat install and uninstall output as visible to Fleet observers and to the user of the device itself. Do not print secrets, do not enable shell command tracing around them, and do not pass them to tools that echo credentials in normal or error output. If a credential does appear in a result, rotate it.

Output is kept to the last 10,000 characters. That is a size limit, not a safety mechanism.

## Target package variants and resolve overlaps

![Explanation](../_assets/icons/explanation-light.svg) Multiple packages on one title is what makes architecture and staging variants possible. It also carries a limitation serious enough to design around, covered below.

### How Fleet picks

When a host is asked to install a title, Fleet walks that title's active packages **in the order they were added** and takes the first one that passes every test: in scope for that host by label, and compatible with that host's platform.

When multiple packages match, Fleet selects the first-added active package. It does not rank them by version, architecture specificity, or label specificity, so make the scopes mutually exclusive when the choice matters.

There is one deliberate exception to the platform test: **`.sh` and `.py` packages run on any unix-like host**, so a shell package is not restricted to Linux alone.

Label scope has three modes and they do not combine. A package can include hosts in any of its labels, include only hosts in all of them, or exclude hosts in any of them. A package with no labels applies to every host in the fleet ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

One behaviour of exclusion scoping is worth designing around: **a host counts as out of scope for an exclusion-scoped package until it has reported membership for every label that package references.** Create a new label and an exclusion-scoped rollout stalls for hosts that have not yet reported, rather than including them by default. It resolves itself, but in the meantime it looks like a stuck rollout.

Test one host from each intended package scope before expanding the rollout. This confirms that the selection rules produce the build you meant to deliver.

### Uninstall does none of this

> **Uninstall ignores variants.** Install resolves which package applies to a host. **Uninstall does not.** It takes the first-added active package on the title, with no check of label scope, platform, or which package the host actually received.

That first-package rule has two consequences to test before relying on uninstall:

**A valid uninstall can be refused.** On a title holding packages for different platforms, the platform check runs against the wrong package, and Fleet refuses with a message naming a platform that has nothing to do with the host in front of you. There is no way to override it.

**An uninstall can report success having done nothing.** With two same-platform variants, Fleet runs the first package's uninstall script against a host that received the second. The generated uninstall script for a `.pkg` looks for a package receipt, does not find one, prints a warning, and exits zero. Fleet reads exit zero as success. **The activity feed records a successful uninstall while the application is still on the machine.** Inventory may well continue to show it installed, and Fleet never goes back to correct the activity.

There is a related single-package case: **`.sh` and `.py` packages get the unix-like exemption when installing but not when uninstalling**, so a shell package Fleet installed on a Mac cannot be uninstalled from it.

For same-platform variants, make the first-added package’s uninstall script handle every variant and test each one. Otherwise, plan a separate removal method. Keep different-platform packages on separate titles where their identities allow it, or separate fleets, when you need Fleet’s uninstall action.

### Verify before you roll out

![How-to](../_assets/icons/howto-light.svg) Before a broad rollout on a title with variants, install to one host in each scope and confirm on the host itself that the package you expected is the package that arrived ([8.11](../08-troubleshooting/8.11-reproducing-and-isolating.md)). Fleet's record tells you the install succeeded. It does not tell you the choice was the one you intended.

## Configure, deliver, and verify by channel

![Explanation](../_assets/icons/explanation-light.svg) Follow the appropriate delivery sequence below to understand what work Fleet queues and what evidence establishes completion ([8.1](../08-troubleshooting/8.1-diagnostic-method.md)).

Pay particular attention to the last step: each channel establishes completion from different evidence.

### Custom packages and Fleet-maintained apps, by the agent

1. The request enters the host's queue and waits its turn ([5.1](5.1-plan-target-and-govern-device-changes.md)).
2. The agent fetches the package details.
3. The pre-install query runs, if there is one.
4. The agent downloads the installer, from the CDN if configured, otherwise from Fleet.
5. The install script runs, then the post-install script, then the rollback if that failed.
6. The result is reported.
7. On success Fleet requests an inventory refetch.

**"Installed" here means the lifecycle scripts completed successfully**: the install script, and the post-install script when there is one. Fleet does not re-run the pre-install query, does not compare versions, and does not wait for inventory to confirm. **It checks no device state at all.** A script that exits zero without installing anything produces a green result.

After an agent install, Fleet refetches inventory. If later inventory no longer reports the application, Fleet marks it removed from installed counts while preserving the successful execution history. Use the inventory for current presence and the activity for what the installer reported at execution time ([4.4](../04-know-your-devices/4.4-understand-software-and-vulnerabilities.md)).

### Apple App Store apps

1. Fleet checks whether the device already holds a licence, and reserves one if not.
2. Fleet sends the install command, with the managed configuration inlined if there is one.
3. The device acknowledges.
4. Fleet asks the device for its list of installed managed applications, and keeps asking every five seconds.
5. The app appears as installed, or ten minutes pass from the acknowledgement and Fleet fails it.

**Acknowledgement is not success**, and Fleet deliberately does not treat it as such. This is the channel where ordinary delivery actually verifies, by asking the device what it holds. The only other verification in this chapter is the Android setup experience, which waits for the device to report the application installed.

Licensing has two modes and Fleet picks by enrollment type rather than by anything you configure. Account-driven user enrollment gets a user-assigned licence; everything else, **including BYOD enrolled by profile**, gets a device-assigned one.

Three failures worth recognising:

- **No licences available.** Fleet refuses before creating any install record, so there is nothing to retry and nothing in the host's history. The error names the shortage directly.
- **The app is already installed, on a BYOD device.** Terminal, and Fleet does not retry, because Apple will not let management claim a personally installed app and the check in step 4 can never see it. The message tells the user to delete it and reinstall from self-service.
- **Wrong storefront.** An app the token's country does not carry produces a different error from an app that is simply unlicensed, and the distinction is worth reading carefully.

**Managed configuration is delivered only with an install command.** Editing a configuration does not push it. The new configuration goes out the next time Fleet sends an install for that app, so if nothing else is going to trigger one, trigger a reinstall yourself. Configuration is XML for iOS and iPadOS, and **macOS App Store apps silently drop it**.

### In-house apps

The same as the Apple pipeline above, preceded by the device fetching a manifest and then the package. One upload serves both iOS and iPadOS.

### Android

1. Fleet updates the device's policy to include the application.
2. The device applies the policy.
3. The device reports the application's state.

**Fleet does not install a normal Android app; it makes the app available.** Fleet adds it to the device's policy as available, which places it in the managed Play Store for the user to install. Fleet does not push it, and every Android app is forced to self-service for exactly this reason. The only path that actually pushes an app is the setup experience ([5.5](5.5-design-setup-and-self-service-experiences.md)).

At this release, **Fleet records and verifies an Android app install only for setup-experience apps.** There is no ordinary per-host Android install operation to watch, so do not go looking for one.

Editing Android managed configuration updates the device policy without reinstalling the app. Its status returns to Pending until the device reports against the new policy version.

Fleet sets no automatic update mode for Android apps. Updates are Google Play's business.

## Install, retry, uninstall, and remove software

![How-to](../_assets/icons/howto-light.svg) After requesting an installation, follow its automatic retry behavior and the manual controls available when another attempt is needed.

<a id="retries-you-did-not-ask-for"></a>

### Automatic retries

Fleet retries some failures automatically, and the budgets differ by channel.

| Situation | Behaviour | Where the retry happens |
|---|---|---|
| Install from host details or self-service | Up to **3 attempts** in total, immediately, no cooldown | The server queues a fresh attempt |
| Install triggered by a policy | Up to **3 attempts**, immediately, and only while the policy is still failing | The server queues a fresh attempt |
| **Setup experience** | Up to **3 attempts**, with roughly 10 and 20 second delays for transient failures | **Inside the agent**, against the details it already fetched |
| Apple App Store install that returned an error | Up to **3 retries**, so up to 4 sends | The server |
| Anything else | No automatic retry | |

Two details change how you read a failure. **A server-queued retry re-resolves the package**, so if you changed which version is active between the failure and the retry, the retry uses the new one. The setup-experience retries do not: they happen inside the agent against details already in hand, so all three attempts use the version that was current when the work was dispatched.

**No retry waits for a cooldown.** There is a cooldown in this area, but it governs something else: a policy automation set to fire continuously will not re-fire an install more often than once per policy update interval, about an hour by default. That exists to stop a *successful* install requesting a refetch, which re-runs the policy, which triggers another install. It does not delay retries of a failed one, and it does not apply at all to the default transition-based mode. See [5.9](5.9-automate-remediation-with-policies.md).

<a id="retries-you-ask-for"></a>

### Manual retries

The budget above runs without you. When it is spent, or when you would rather not wait for it, you retry by hand.

**Retry and Retry uninstall are the manual controls.** Every failed-install state carries a **Retry** button, and every failed-uninstall state carries **Retry uninstall**. Retry re-sends an install; Retry uninstall re-sends an uninstall. Both are Premium, because the install and uninstall actions they reuse are Premium. There is no retry-specific endpoint, no `fleetctl` command, and no GitOps path: a retry is a console action on top of the ordinary install and uninstall.

**The button appears in two places, and they take different routes.** From the host's software library in host details, a retry goes through the host install route, authenticated as the operator. From the end user's self-service page, it goes through the device-authenticated self-service route, because the user is acting on their own machine rather than through an admin session. Same package, different door, which is the detail to know when you are reading server logs and trying to tell an operator's retry from a user's.

**Who can retry.** From host details, any authorised operator: a global or fleet admin, a maintainer, or a technician, all of whom can write host software actions. From self-service, the end user on that device.

A manual **Retry** from Host details or Self Service clears the prior non-policy attempt state and starts a fresh sequence with up to three automatic attempts. Check the failure reason before retrying, because another click begins another sequence rather than continuing the old budget.

Part VIII lists retry among the forcing actions, and its safety verdict is the one to carry: the attempt itself runs on the user's machine, so it is production-safe with that caveat ([8.11](../08-troubleshooting/8.11-reproducing-and-isolating.md)).

### Uninstall, by source

![Reference](../_assets/icons/reference-light.svg)

| Source | Can you uninstall from a host? |
|---|---|
| Custom package | Yes, subject to the variant limitation above |
| Fleet-maintained app | Yes, the same |
| App Store app (Apple) | **No explicit per-host uninstall** |
| In-house app | **No explicit per-host uninstall** |
| Android Play app | Not per host, but see deletion below |

A successful uninstall does not produce an "uninstalled" status, because there is no such status. The record simply stops counting the software as installed.

<a id="deleting-from-the-library-is-not-uninstalling"></a>

### Delete a title from the software library

**For almost every source, removing something from your library removes nothing from any device.** Hosts keep what they have and lose only the ability to install it again.

Deleting an Android app also removes it from the policies of hosts in scope, causing removal from those devices. Review that device impact before deleting its library entry.

Deleting is refused outright in two cases: when a patch policy references the package, and when it is selected for the setup experience.

### What editing does to work already queued

Editing a package's file, scripts, query or labels **cancels every pending install and uninstall of that package**, for all hosts, not only the hosts your edit affected. Setup-experience installs survive an edit; they do not survive a delete.

Editing only the self-service flag, or only the pinned version, cancels nothing.

Two lifecycle events people expect to cancel work, and which do not:

- **Moving a host to another fleet cancels nothing.** A queued install completes against the package from the fleet the host has left. This is deliberate: the request was legitimate when it was made.
- **A host falling out of a package's label scope cancels nothing and uninstalls nothing.** When the scope changed because label membership changed, no software reconciliation runs at all, and the queued install completes.

## Manage catalog refresh, versions, updates, pins, and rollback

![Explanation](../_assets/icons/explanation-light.svg) Keeping applications current involves three separate steps. Review each when deciding what an automatic update will accomplish:

1. **Catalogue refresh.** What Fleet knows exists upstream.
2. **The active library version.** Which package a future install would use.
3. **What is actually on your devices.**

A catalog refresh discovers upstream metadata. A library update selects the package for future installs. Devices change when an installation or supported app-update workflow runs.

### Catalogue refresh

Once an hour, Fleet refreshes its list of Fleet-maintained apps from Fleet's published manifests. This updates names and identifiers only. **It downloads no installers and changes no versions.**

<a id="automatic-updates-update-your-library-not-your-fleet"></a>

### Automatic updates to the software library

Also hourly, Fleet checks for new versions of the Fleet-maintained apps you have added, caches the new version, and makes it the active one.

Automatic library updates prepare the package that future installs will use. Pair them with a patch policy and install automation when you want devices to converge on that version ([5.9](5.9-automate-remediation-with-policies.md)). Without that deployment step, hosts keep their installed versions.

Install and uninstall scripts you have customised survive an automatic update.

> **Fixed in 4.90.1.** On Fleet 4.90.0 the hourly auto-update job could keep an app's previous install script, which references the old installer filename, so the install then fails; and a new build that reuses the same shortened version did not swap in the new file, though it still updated fields such as the install script. Fleet 4.90.1 fixes both.

### Pinning

Three states, for Fleet-maintained apps only:

| Pin | Meaning |
|---|---|
| None | Always take the newest cached version |
| Major, written `^147` | Newest cached version in that major |
| Exact, written `147.0.1` | That version, and it never advances |

An exact pin also stops Fleet caching new versions at all. Major pins match on the text before the first dot, so they are not semantic-version aware, and a pin cannot be changed in the same request as any other field.

### Rollback is one version deep

Fleet keeps at most **two** versions of a Fleet-maintained app per fleet: the active one and at most one alternative. When a new version arrives, the older spare is evicted.

Fleet's published manifests contain only the current version, so the manifest fallback cannot recover an older build after it leaves the cache. Plan rollback around the retained previous version and verify it is still available before depending on it.

Do not assume the retained alternative is the immediately previous version either. Eviction depends partly on upload recency, and the active version is always protected.

### What changing the active version does

| To | Effect |
|---|---|
| Hosts that already have it installed | Nothing. Only a patch policy moves them |
| Work queued but not yet started | Re-pointed to the new version |
| Work already sent to a host | Fleet cancels its **record**. It cannot recall work already on the host, and it does not generically re-queue a manual request. Automation may queue the new version later |
| Future installs | Get the new version |

### Everything else

Keep custom installers and their previous versions in your own artifact store. Replacing a custom package overwrites its Fleet entry; Fleet provides no custom-package pinning, version history, or retained rollback copy.

Replacing the file also **drops the completed installs from your current counts**, because those records no longer describe the package that is there now. It does not update the software on any host, and it does not remove it. Hosts keep the version they were given until something installs over it.

Multiple custom packages on one title are **variants, not versions**. Fleet treats them as different software that happens to share a name.

**Fleet drives app updates for iOS and iPadOS App Store apps only.** You can set an update window, expressed in the host's local time, at least an hour long, and it may cross midnight. macOS App Store apps, Android apps and custom packages are all outside this: their updates belong to the platform, to Google Play, or to you.

## Handle conflicts, offline hosts, retries, interruption, and limits

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Use these delivery and lifecycle rules when a rollout pauses or a result differs from the intended device state.

**Overlapping variant scope.** First-added wins, silently. If a host matches two packages, nothing warns you and nothing records which one you meant.

**Duplicate work.** A host already holding a pending install or uninstall of the same package refuses another. Work on one host runs one at a time, so a slow install blocks whatever is behind it ([5.1](5.1-plan-target-and-govern-device-changes.md)).

**Offline hosts.** **Fleet defines no age expiry for queued software work at this release.** It waits until the host checks in, unless something else cancels it. A queue that looks stuck across many hosts is more likely an agent problem than a software problem ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)).

**Interrupted installs.** Fleet cancels the *record*, not the work. Anything an install script did before it failed or was cancelled stays done. There is no undo except the rollback described earlier, and that only fires after a failed post-install script.

**Disk space.** Fleet does not check free space before downloading or installing, on either side. A host that runs out fails partway through, and the failure surfaces as whatever the installer said about it. If a rollout fails on a predictable subset of machines, check capacity before inspecting the package ([4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md)).

**Scripts disabled on the host.** Agent-delivered software needs script execution enabled in the host’s effective agent configuration. The platform-specific ways to change that setting are linked from [5.3](5.3-run-and-manage-scripts.md).

**The installer disappeared mid-flight.** If a package is deleted while a host is trying to fetch it, the agent retries for five minutes and then reports that it abandoned the install.

**Apple-specific failures.** Insufficient licences, an app already installed on a BYOD device, a storefront mismatch, and a verification that ran out its ten minutes are four different problems with four different answers. Establish which one you have before acting ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md)).

**Re-enrollment, and which kind.** An Apple device going through *MDM* re-enrollment has all of that host's queued work cancelled. Re-enrolling the agent does not: neither the osquery nor the Orbit path touches the queue, so work ordered before it still runs afterwards ([5.9](5.9-automate-remediation-with-policies.md)). Turning MDM off cancels queued App Store and in-house installs but leaves agent-delivered installs alone, which is correct: those never needed MDM.

**An application in use.** Some installers cannot replace a running application. Fleet has no opinion on this and no mechanism to close anything, so an update that works on an idle machine can fail across a fleet of machines where the application is open all day.
