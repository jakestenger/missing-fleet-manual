# Design safe automation and control change

![Explanation](../_assets/icons/explanation-light.svg) Fleet's automation interfaces let you bring device management into the workflows your organization already uses. You can review configuration in Git, run administrative tasks from a shell, build a custom API client, or send events to another system. A useful workflow connects the change you intended to the evidence that it reached the right devices.

Start by deciding who owns each setting or action, which interface will change it, and how you will check the outcome. For example, a deployment pipeline might apply configuration through GitOps and use API reads to verify the result. Those operations can work together as one workflow when their responsibilities are explicit. Connecting an AI assistant adds another way to read Fleet and run live queries; [6.6](6.6-connect-fleet-to-an-ai-assistant.md) covers that setup and its access controls.

## Choose the automation path and declare ownership

![Explanation](../_assets/icons/explanation-light.svg) Choose the interface around the work you want to perform. GitOps, the REST API, and fleetctl can change Fleet state; webhooks carry events to external receivers. They share the same underlying configuration, so a field changed through one interface can be overwritten through another. The AI assistant path mainly provides reads and live queries, with the additional tool and permission limits described below.

| Path | What it is for | Limits to plan around |
|---|---|---|
| **GitOps** ([6.2](6.2-manage-fleet-with-gitops.md)) | Declared state, reviewed and reapplied | Limited to its schema; unsuitable for actions that need a response |
| **REST API** ([6.3](6.3-use-the-fleet-rest-api.md)) | Requests and reads from custom clients | Your client must check whether the intended state was reached; Fleet provides no general reconciliation loop for API clients |
| **`fleetctl`** ([6.4](6.4-use-fleetctl.md)) | Shell work and pipelines | Server-backed commands inherit the API's limits. Packaging, conversion, and GitOps scaffolding can run locally |
| **Webhooks** ([6.5](6.5-integrations-webhooks-and-external-workflows.md)) | Reacting to events Fleet reports | Delivery is one-way; a receiver needs another interface to request a change |
| **AI assistant, MCP** ([6.6](6.6-connect-fleet-to-an-ai-assistant.md)) | Reading Fleet and running live queries through natural-language requests | No configuration changes; includes one destructive tool. The token's role limits what tools can do |

### There is no owner field

Keep your ownership map in the repository or runbook that governs the automation. Fleet has no field-level ownership annotation, conditional-write token, generation number, or stale-write check. If two writers change the same field, the later write wins without notifying either writer that another change occurred.

Fleet still rejects semantic conflicts such as a duplicate name. It does not provide optimistic concurrency: a client cannot require a write to succeed only if the value has stayed unchanged since its last read.

The activity record identifies the account responsible for a change. If GitOps, fleetctl, and a custom client share one credential, the record cannot tell you which path made the request. Give each workflow its own API-only identity so you can follow its activity ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)). A workflow may use several tools with that identity.

Put these three controls together:

- **Record ownership outside Fleet.** Name the workflow responsible for each setting or action to prevent overlapping responsibilities.
- **Serialize writes within each ownership boundary.** Route them through one workflow so requests cannot interleave.
- **Use a separate identity per workflow.** This makes its changes attributable. The identity alone does not prevent overlap or interleaved writes.

GitOps mode and change-management exceptions support that operating practice, but their enforcement is limited. GitOps mode makes supported interface controls read-only while leaving API authorization unchanged. Change-management exceptions are enforced by the GitOps client, so a different API writer can bypass them. Use role and scope restrictions to control what each identity is allowed to change.

### Verifying with a writer that cannot read

A tightly scoped writing identity may be unable to read the evidence needed to verify its work. Host details, activities, and software-install results each have separate authorization checks.

Use a second, read-only identity for verification when those reads fall outside the writer's role. This lets the workflow inspect its result while keeping the writing credential limited to the changes it needs to make.

### Detecting drift

To check whether configuration has drifted from your repository, you can export it and build a comparison around the result. Fleet's export is a hidden command: it omits sensitive values, leaves some state unsupported, and does not perform the comparison itself. Plan separate checks for the state the export cannot represent. Fleet provides no built-in drift report.

### A note on Terraform

Terraform can appear at several layers of a Fleet deployment. Check which layer a tool manages before including it in your workflow:

1. **Service deployment.** Fleet's Terraform modules provision the infrastructure covered in [Part II](../02-administer-and-deploy-fleet/2.3-deploy-on-aws-or-gcp.md).
2. **Configuration inside Fleet.** Use GitOps or the API for the administrative state discussed here.
3. **Fleet's unpublished provider.** The repository contains a provider with one resource and a note identifying publication as future work. It remains development work and is not a supported option.
4. **Community providers.** These are outside the scope verified by this manual.

## Authenticate automation clients

![Reference](../_assets/icons/reference-light.svg) Use an API-only user for an automated workflow. Its API token is a session key, supplied in the HTTP `Authorization` header after `Bearer`. A regular user's sign-in also returns a session key, but the two account types have different session lifetimes:

| | Regular user | API-only user |
|---|---|---|
| **Session lifetime** | Inactivity timeout, five days by default, measured from last use | Unlimited |
| **What renews it** | Using it | No renewal needed |
| **Reported expiry** | Reflects the session's timeout | Computed from the global setting; does not reflect the unlimited lifetime |

An API-only session's reported expiry is therefore unsuitable for scheduling token rotation. Set your own rotation policy and revoke credentials when they are no longer needed.

fleetctl stores the credential in a named context in a plain-text configuration file. On macOS and Linux it creates the file with owner-only permissions. Windows does not enforce those permission bits, so check the file's filesystem access controls there.

Fleet Premium can further restrict an API-only user to a list of endpoints. The list narrows the actions allowed by its role and scope; it never grants an action the role denies ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)). With no list, there is no additional endpoint restriction. To clear an existing restriction, remove the list: Fleet rejects a submitted empty list.

### Four credentials that are not API credentials

Fleet uses other credentials for enrollment and device communication. Keep these separate from the administrative token your automation uses:

- **Enroll secret:** authorizes a device to enroll, with no administrative management access.
- **Device token:** reaches one device's own pages and has a one-hour freshness requirement.
- **MDM identity certificate:** authenticates a device to device endpoints.
- **Host and agent node keys:** authenticate the agent rather than an administrator.

### Revocation is not cancellation

Revoking a credential prevents subsequent requests, while work already queued continues. A script, installation, or MDM command has no link back to the session that created it, so revoking that session cannot recall the work.

If a credential is compromised, revoke it and assess the requests it already made. The [recovery sequence below](#recovering-from-an-automation-that-did-the-wrong-thing) covers stopping new work, cancellation, and correction.

## Manage automation secrets

![How-to](../_assets/icons/howto-light.svg) Use Fleet secret variables when a script or profile needs a secret at delivery time. Fleet stores their values encrypted with the server private key, omits the values from list responses, and retains a placeholder in the stored script or profile. Configure the server private key before using this feature, and remove unused variables yourself; Fleet does not delete them automatically.

GitOps environment substitution happens earlier, on the client. Fleet receives and stores the substituted value, so an environment variable in a GitOps file does not provide the protections of a Fleet secret variable.

Keep secrets protected across the rest of the workflow too:

- **Database backups contain credential material.** Fleet masks selected third-party credentials in API responses, but only specific stores receive application-level encryption. An API's masked display does not establish that its database value is encrypted ([7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md)).
- **Command output can expose a secret.** Fleet stores script output, install and post-install output, uninstall results, and setup-experience errors as they arrive. Stored inputs retain their placeholders; output has no general redaction. Review commands for possible secret disclosure, including their failure paths. [5.3](../05-manage-devices/5.3-run-and-manage-scripts.md) and [5.4](../05-manage-devices/5.4-manage-software-and-applications.md) cover script and installer authoring.
- **Webhook destinations are visible configuration.** Keep credentials out of destination URLs; they are not masked like other integration values.

## Design for repetition and ambiguous outcomes

![Explanation](../_assets/icons/explanation-light.svg) Plan how the workflow will respond when a request times out or needs to run again. Fleet provides no general idempotency key, client-supplied request identifier, or conditional write. After a timeout, the protocol alone cannot tell you whether the server accepted the change.

Check retry behavior for the specific endpoint and current state. Fleet's declarative endpoints use POST, so the HTTP method is not enough to decide whether repeating a request is safe.

### What to key on instead

Keep the identifiers that let you find the result of a request later. These include numeric resource IDs, profile IDs, script execution IDs, command IDs, and batch execution IDs.

You can also reconcile against documented names: a fleet's name, or a label or secret-variable name at global scope. For other resources, check the endpoint's identity contract before assuming that a name is unique within a fleet.

Keep credentials out of this correlation scheme. Enroll secrets, node keys, and session keys are unsuitable identifiers, as are Fleet's internal deduplication values.

### After an ambiguous write

Read the resource or pending work before deciding whether to retry. A duplicate response may help you find existing work, but it cannot establish which request created it.

For example, Fleet refuses a second installation request for the same installer while one is pending. That pending installation could have come from your request or another writer. Once it leaves the pending state, repeating the request creates new work. Inspect the available evidence before treating “already exists” as confirmation of your original call.

### A successful call is not a converged state

An accepted request is the start of verification. Choose the result you need to observe for each action:

| You call | You get | What it means | Convergence evidence |
|---|---|---|---|
| **Apply profiles** | Success, no content | Fleet accepted the desired state | Per-host profile operation and status, interpreted for that platform ([5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md)) |
| **Run a script asynchronously** | Accepted, plus an execution identifier | The script is queued | The execution's result. An offline host can leave it pending indefinitely; there is no server-side deadline |
| **Install software** | Accepted, with an empty body | The installation is queued. Its execution identifier is absent from the response, but appears in the host's upcoming activities while pending | The execution record shows whether the install ran; inventory shows whether the software is present |

When a later step depends on a script finishing, give the workflow its own deadline and stop condition. It needs a defined response if the host stays offline or the required result never arrives.



## Test before production

![How-to](../_assets/icons/howto-light.svg) Build confidence in stages, beginning with file checks and ending with a small, verified production change:

1. **Check that the YAML parses.** A generic syntax check catches malformed YAML; it does not validate Fleet's schema.
2. **Validate against a reachable Fleet instance.** GitOps validation authenticates, checks the server version, and reads configuration, labels, and fleets before examining your files. Fleet validation requires that connection; there is no offline equivalent.
3. **Exercise the workflow in a separate Fleet instance.** Use it to test changes and recovery without affecting production state.
4. **Test a fleet on the production instance.** Apply the isolation limits below when selecting this test.
5. **Choose a bounded production target.** Define which devices and settings the change should reach.
6. **Promote after verification.** Use the evidence and stop conditions in [Review, verify, and recover](#review-verify-and-recover).

### What a test fleet cannot isolate

Use a separate instance to test global settings, users, or secret variables. These are instance-wide resources, so a test fleet on the production instance shares them with production.

Hosts in a test fleet also run applicable global policies and enabled global scheduled reports. Platform and label targeting can determine whether an item applies, but fleet membership alone cannot opt a host out.

Give test labels distinct names. Label definitions can be fleet-scoped, while their names are unique across the instance. Reusing a production label's name either fails or, when the same GitOps run removes it from production and adds it to test, moves the label.

For a policy, first test its SQL as a live query against a bounded host set. Then apply the policy in an isolated fleet and wait for a scheduled result before promoting it. Fleet has no “run this policy once” operation; [5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md) explains how live and scheduled results differ.

Pin Fleet's preview environment to the release you are testing. Its defaults use the latest server image and preview assets from the development branch, which may differ from that release.

## Review, verify, and recover

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Keep enough evidence to connect a run to its changes and decide what to do if the outcome is wrong. Fleet's activity record supplies part of that history; your workflow needs to retain the run context and verification results.

### What the audit trail does and does not give you

Activities record administrative changes and selected sensitive reads, including access to disk-encryption keys and Recovery Lock credentials ([5.8](../05-manage-devices/5.8-enforce-disk-encryption-and-manage-recovery-credentials.md), [8.12](../08-troubleshooting/8.12-audit-logs.md)). Most reads and all authorization denials are absent. You cannot use the activity feed as a general access log or expect it to show a denied request.

A recorded change includes the account, its name and email, and the change itself. Fleet identifies API-only accounts while those accounts exist. That marker is resolved from the current user record when the activity is read, so deleting the account removes the marker from later reads. Policy-driven work is attributed to Fleet ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)); requests made with a token retain their account attribution.

Activities omit the interface used, the session or token, the client, and the user agent. Source addresses are recorded only for sign-in. Separate identities let you distinguish a pipeline's actions from a person's; sharing an account loses that distinction.

### Recovering from an automation that did the wrong thing

Work through the outstanding requests before applying a correction:

1. **Stop new requests.** Pause the pipeline or schedule. Revoke the credential as well if it is compromised; revocation prevents new calls but leaves queued work in place.
2. **Cancel work where supported.** You can cancel an item on a host's upcoming list or a batch script run. An activated item can still be removed from the queue, but the device may fetch it before cancellation completes. Fleet refuses cancellation of activated lock and wipe actions.
3. **Identify work already executing on devices.** It cannot be recalled. Custom MDM commands have no cancellation route.
4. **Apply the corrective state.** With GitOps, apply a known-good complete commit as a new change. API recovery requires a suitable request to restore the intended state; a read response is usually not a valid restore payload. Preserve pre-change requests or construct the documented corrective request. Neither path provides a general undo.
5. **Verify the outcome.** Check the stored state and the devices against the intended correction.

### The pre-change contract

Before a production change, record the information another operator would need to understand, verify, or stop it:

| Item | Record |
|---|---|
| **Owner and identity** | The workflow responsible for the change and the API-only identity that will execute it |
| **Target and intent** | What will change, which resources or devices it affects, and the intended values |
| **Evidence** | What to read in Fleet and what to check on a device, including the read-only verification identity if needed |
| **Stop condition** | The observation that halts the workflow, its deadline, and who can make that decision |
| **Correction** | The corrective request or known-good complete commit to apply |
| **Correlation** | The change reference, commit, and preserved run output |

Keep the correlation details in your pipeline or change record. Fleet supplies no run or request correlation marker of its own ([6.2](6.2-manage-fleet-with-gitops.md)). Make sure an operator other than the author can use the stop procedure before promoting the workflow to production.
