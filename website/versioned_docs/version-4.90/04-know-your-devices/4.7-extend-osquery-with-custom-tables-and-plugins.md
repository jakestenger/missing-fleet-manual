# Extend Fleet telemetry

![Explanation](../_assets/icons/explanation-light.svg) Fleet’s reporting model can grow with your environment. When the standard inventory does not include a value you need, you can often expose it with an additional query, a table built from an application’s SQLite data, or an osquery extension. That flexibility lets you connect local operational knowledge to the same host records and reports your administrators already use.

Choose the smallest mechanism that answers the question reliably. Configuration-based approaches are usually simpler to deploy and maintain; a custom extension adds code, builds, distribution, and ongoing compatibility work. This chapter helps you compare those choices before committing to one.

## The hierarchy, lightest first

![Explanation](../_assets/icons/explanation-light.svg) Work down this list and stop at the first thing that answers your question.

| | Mechanism | Use when |
|---|---|---|
| 1 | **A saved or scheduled query** | The data exists in a table and you want to see it ([4.2](4.2-run-queries-and-reports.md)) |
| 2 | **A policy or a label** | The answer is a yes-or-no you want to act on or target by ([4.3](4.3-use-policies-for-compliance.md), [1.3](../01-foundations/1.3-hosts-fleets-labels.md)) |
| 3 | **A custom host vital** | The data is not on the device at all. You know it and want it on the host record ([4.1](4.1-understand-hosts-vitals-and-inventory.md)) |
| 4 | **`features.additional_queries`** | The data exists in a table and you want it **on the host record**, refreshed with the host's other details |
| 5 | **`auto_table_construction`** | The data is in a **SQLite file on disk** with no table for it. Makes a real table, no code |
| 6 | **`features.detail_query_overrides`** | A built-in detail query is wrong or harmful for your estate. An escape hatch, not an option |
| 7 | **An osquery extension** | The data genuinely is not reachable any other way |

The first three options use capabilities covered earlier in Part IV. The sections below focus on adding collected fields, constructing tables, overriding detail queries, and distributing extensions.

**The question that separates a report from a host field** is whether you want an answer *about* a host or a field *on* a host. A scheduled report gives you rows you go and read. `additional_queries` puts the result on the host record itself, where it refreshes with everything else and travels with the host.

## `additional_queries`: adding fields to the host record

![Reference](../_assets/icons/reference-light.svg) The mechanism for putting a collected value on the host record rather than in a report.

**What it is.** A JSON object of name-to-SQL pairs in the server's feature settings. Fleet appends each one to the set of detail queries a host is asked, prefixed internally as `fleet_additional_query_<name>`, and stores the returned rows on the host as `additional` data under the name you gave.

**When it runs.** With the host's other detail queries, on the detail update interval, not on a schedule you set. That is the point of the mechanism: the field ages with the rest of the host record rather than on its own clock ([4.1](4.1-understand-hosts-vitals-and-inventory.md)).

Plan around these collection and naming rules:

**It is not platform-gated.** Built-in detail queries carry platform conditions. An additional query is registered with a discovery condition that is **always true**, so it is asked of every host regardless of platform. Where the table does not exist it simply fails, nothing warns you, and the failure is per host ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)). If your query is platform-specific, guard it inside the SQL rather than expecting Fleet to scope it.

A critical-only refetch excludes additional queries. Their values wait for the regular detail-query pass.

**Its scope is per-fleet, but only through one path.** These are feature settings, and they can be set globally or per fleet. The per-fleet route is GitOps `spec/fleets` only: the fleets PATCH endpoint accepts a `features` object but acts on a **narrow subset** of it, and `additional_queries` is not in that subset. So a per-fleet additional query set through the API endpoint is accepted and does nothing. The same is true of `detail_query_overrides` ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

**The name is the contract.** It becomes the key on the host record, so anything reading that key breaks if you rename it.

Use additional queries for a local asset tag, a site or building identifier, or a relevant registry or configuration-file value that you want attached to the host. Collect license information only where it is needed and appropriately protected.

Keep additional queries inexpensive because they run repeatedly with detail collection on every applicable host. Apply the query-design checks in [4.6](4.6-advanced-osquery-queries-and-tables.md) before adding them.

## `auto_table_construction`: a real table, without writing code

![Reference](../_assets/icons/reference-light.svg) Automatic table construction is useful when an application already stores the data you need in a local SQLite file. It can expose that data through osquery using configuration alone.

**The problem it solves.** An application on your devices keeps its state in a SQLite database on disk. The data you need is sitting there in a file, and no osquery table exposes it.

**What it does.** Automatic table construction is an osquery feature Fleet exposes in agent options. You give it a table name and four things: the **path** to the SQLite file, a **query** to run against it, the **columns** to expose, and a **platform**. osquery then presents that as a genuine table, which you can query, join, schedule, or use in a policy exactly like any built-in.

This approach creates a queryable table without building, signing, or distributing an extension binary. Check whether the source data fits its SQLite and path requirements before starting an extension project.

**Its limits are the shape of its inputs.** The source has to be SQLite, and the path has to be predictable enough to write down. A path containing a user directory means one entry per user layout you support, and a file that only exists after the application has run means the table is empty rather than missing on hosts that have not run it.

**It is per platform**, by the `platform` field on each definition, so unlike `additional_queries` it does not need guarding inside the SQL.

<a id="detail_query_overrides-an-escape-hatch-with-sharp-edges"></a>

## Override detail queries with `detail_query_overrides`

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) `detail_query_overrides` replaces or removes Fleet’s built-in collection queries. It is intended for debugging and specific workarounds, because the replacement must still satisfy Fleet’s existing ingestion contract.

**How it behaves,** for each name-to-SQL pair you supply:

- Give it SQL, and Fleet **replaces the query text** for that built-in detail query.
- Give it null or an empty string, and Fleet **deletes that detail query entirely**. The host stops being asked, and whatever it populated stops being updated.
- Name something that is not a real detail query, and Fleet logs an error and **carries on applying the rest**. There is no rejection, so a typo silently does nothing while its neighbours take effect.

**Why it breaks ingestion.** Replacing the SQL does not replace the code that reads the result. Fleet keeps the original ingestion function, which expects specific column names. An override returning a perfectly sensible result set with different columns will be collected and then fail to ingest, and the host field it feeds goes stale while the configuration looks correct.

Match the original query’s expected column names exactly. Inspect its result shape before applying the override.

**Legitimate uses are narrow:** suppressing a detail query that is pathological on your hardware, or working around a known defect on a specific platform. If you are reaching for it to *add* something, you wanted `additional_queries`.

**Record why.** An override is invisible in the interface and changes what every host reports. Six months on, an unexplained override is indistinguishable from a mistake, so it belongs in GitOps with a comment ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

## Add tables with extensions

![Explanation](../_assets/icons/explanation-light.svg) An osquery extension registers new tables from a separate program. Fleet’s managed distribution path lets you deliver a versioned build to supported hosts through the update system.

**The managed path** is the `extensions` key in agent options: a map of extension name to a small object naming a **platform**, a **TUF update channel**, and optionally **labels**. Fleet's updater delivers the binary on that channel and orbit loads it.

Three things to know before planning around it:

- **Label scoping is Fleet Premium.** Naming labels without a licence fails the request outright. That is a genuine refusal, unlike the silent parameter dropping described in [4.5](4.5-monitor-fleet-wide-state.md).
- **A named label must already exist** on that fleet, or the request is rejected. Create the label first.
- **The platform tokens are not the query platform tokens.** An extension's platform is `macos`, where a query's platform is `darwin`. Orbit also accepts `windows`, `linux`, `linux-arm64` and `windows-arm64`, so the architecture-specific builds are addressable. The struct's own documentation comment names only three of these, so read the token list as what orbit resolves rather than what the comment says. A token orbit cannot resolve is an error, but a **valid token for the wrong platform** is simply an extension that never lands anywhere.
- **The filename is inferred, not configured.** Orbit expects `<extension name>.ext`, with `.exe` appended on Windows, under `bin/extensions/<name>/<platform>/<channel>/` in its root directory. The extension name in your configuration is therefore also a filename contract with whatever publishes to your update server.

Orbit maintains the `extensions.load` file passed to osquery through `--extensions_autoload`. It rebuilds that file from the managed configuration for the host’s platform and architecture. If Fleet sends no extensions configuration, Orbit empties the file and restarts osquery to unload the extensions. Hand-added entries therefore do not survive reconciliation.

Use the managed update path for extensions on fleetd hosts. A manually maintained osquery autoload arrangement requires running osquery outside Orbit’s management.

**What you are taking on.** An extension is code running alongside osquery on every machine you deploy it to. It needs building per platform and architecture, distributing through an update server, versioning, and maintaining against osquery's extension interface. It is subject to the same watchdog and denylisting as anything else ([4.6](4.6-advanced-osquery-queries-and-tables.md)).

Before writing an extension, confirm that no existing table or configuration-based approach supplies the data. Define its operational value and assign an owner for future builds, compatibility checks, and retirement.

## Other collection you can turn on without writing code

![Reference](../_assets/icons/reference-light.svg) Two osquery subsystems sit in agent options and produce telemetry without a new table.

**File integrity monitoring** takes sets of paths to watch, path sets defined by query, and exclusions. It produces events rather than snapshot rows, so it belongs in a log destination rather than in a report ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)).

**YARA** takes named signature sets and the paths to scan with them, with the same event-shaped output.

**Decorators** add columns to results rather than adding tables. They come in two kinds in agent options: queries run `always`, and queries run on an `interval`. Their value is provenance: a decorator that stamps every result with an identifier you care about makes results self-describing once they leave Fleet for a log destination.

**Event subscribers** can be enabled or disabled individually. This is the control for turning off an event source that is expensive on your estate without disabling event collection entirely.

File integrity monitoring and YARA can support event-based collection where a repeated filesystem query would be costly. Choose the subsystem that matches the observation you need, then configure its event delivery.

![How-to](../_assets/icons/howto-light.svg) A sequence for a question you cannot currently answer.

1. **Search the table schema for the platform**, not for the concept. The table may exist under a name you would not have guessed.
2. **Ask whether a nearby table answers a slightly different question well enough.** An approximate answer that costs nothing often beats an exact one that costs a watchdog restart ([4.6](4.6-advanced-osquery-queries-and-tables.md)).
3. **Decide whether you want a row or a field.** Rows are a report. Fields on the host record are `additional_queries`.
4. **If a built-in is actively wrong for you**, that is the only case for an override, and match the original's columns exactly.
5. **If nothing has the data**, check whether an existing open-source extension already provides it before writing one.
6. **If you write one**, treat it as software: version it, scope it with labels, roll it out to a small population first, and watch the query statistics on the hosts that have it.

Record the purpose, owner, and relevant constraints beside the configuration. Additional queries, overrides, and extension channels can be difficult to discover from the interface alone, so those notes help the next operator maintain them.
