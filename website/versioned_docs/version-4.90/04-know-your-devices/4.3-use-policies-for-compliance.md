# Use policies for compliance

Fleet policies turn recurring device checks into a shared view of security and operational readiness. Administrators can see which hosts meet a requirement, identify those needing attention, and connect supported checks to remediation. Each result answers a specific yes-or-no question at the time the host evaluated it, so coverage and freshness matter alongside the pass and fail counts.

Policies use Fleet’s distributed-query channel and shared evaluation cadence. Their results are stored as per-host policy state, independently of the scheduling, storage, and forwarding controls used by reports in [4.2](4.2-run-queries-and-reports.md).

<a id="how-a-policy-actually-runs"></a>

## How scheduled policies run

![Explanation](../_assets/icons/explanation.svg) Fleet sends policies to a host in the **distributed query response**, the same channel that carries live reports, rather than putting them in the host's osquery schedule. Results come back on that channel too, not through the result-log path that scheduled reports use.

The evaluation path determines these timing and platform behaviors:

**The cadence is Fleet's, not the policy's.** Policies are evaluated on `policy_update_interval`, one hour by default, with a per-host jitter of up to ten percent. Individual policies do not carry their own intervals. There is also a refetch path that can bring a host's evaluation forward, so a host you have just asked Fleet to refetch does not wait out the hour.

**Report output settings are irrelevant.** Snapshot logging, `discard_data`, `discard_reports_data` and automations govern scheduled reports. None of them applies to a policy.

**ChromeOS answers policies.** The Fleetd for Chrome extension answers the distributed endpoints, so a policy reaches a Chromebook even though scheduled reports never do ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)). What remains true is that iOS, iPadOS and Android have no osquery at all, so policies do not apply to them.

Policies also have no minimum osquery version setting. A report has one; a policy does not.

<a id="three-answers-and-only-two-of-them-are-verdicts"></a>

## Pass, fail, and no answer

![Explanation](../_assets/icons/explanation.svg) For each host and policy, Fleet records one of three things.

| Answer | What produced it |
|---|---|
| **Pass** | The query ran successfully and returned at least one row |
| **Fail** | The query ran successfully and returned **no** rows |
| **No answer** | The query did not run successfully, or has not run yet |

Write the query to describe the desired state. A host passes when the query returns rows and fails when it completes successfully with none. Test both a known passing and a known failing host so the query expresses the requirement as intended.

An unsupported table, SQL error, or platform mismatch produces **no answer**. Fleet excludes that host from both passing and failing counts. Investigate the query or collection path before treating the device as noncompliant or launching remediation.

**"No answer" is not always a stored row.** Fleet does not create a membership row for a host's first errored evaluation, so that host has no row at all. A host that previously answered and then errors keeps its row with the value cleared. Both look identical on the host's policy view, which reports them the same way, so the ordinary surface will not tell you which of the two you are looking at ([8.6](../08-troubleshooting/8.6-server-state.md)).

<a id="the-denominator-is-the-whole-problem"></a>

## Read policy counts against their scope

![Reference](../_assets/icons/reference.svg) Interpret compliance counts against the population you intended to assess. The passing and failing counts include only hosts with a recorded verdict.

Hosts with no answer belong to neither count. Include them when reporting assessment coverage so an unevaluated or erroring device is not inadvertently counted as passing.

Build the denominator deliberately, from four groups:

| Group | How to find it |
|---|---|
| **Out of scope** | Hosts the policy's platform, fleet and label targeting exclude. They are not non-compliant; they were never asked |
| **Passing** | The passing count |
| **Failing** | The failing count |
| **No answer** | The remainder of the in-scope population. This is the group worth investigating |

**The counts are a cached aggregate.** Fleet stores them with a timestamp saying when they were computed, so a policy list can disagree with the host list beneath it. That timestamp is one clue when the two disagree, not a complete explanation; a host whose evaluation has changed since the counts were computed produces the same symptom.

Fleet retains a host’s last pass or fail until another evaluation replaces it, including while the host is offline. Read `policy_updated_at` for the last policy reporting pass when assessing how current that verdict is.

## Two kinds of policy

![Explanation](../_assets/icons/explanation.svg) Fleet has exactly two policy types and they are authored differently.

**A dynamic policy** is the ordinary kind: you write the query and choose the platform.

**A patch policy** is generated. You name a Fleet-maintained app instead of writing a query, and Fleet produces the query, the platform and the default descriptive fields from it. Three constraints come with it: the query and platform fields are not accepted, since Fleet supplies them; the policy **must be scoped to a named fleet** rather than created globally; and because named fleets and the maintained-app catalogue are both involved, it is **Fleet Premium** and is not available for an arbitrary title you package yourself.

A patch policy checks whether the selected title is present at or above a version. Include a host without the application in your test set so you understand how that case affects the result before using the policy across a mixed population.

## Scoping a policy

![How-to](../_assets/icons/howto.svg) **Platform** uses the generic selectors `darwin`, `windows`, `linux` and `chrome`, not the specific value stored on a host, so a Fedora host is selected by `linux` although its inventory reads `rhel` ([4.1](4.1-understand-hosts-vitals-and-inventory.md)). An unscoped policy reaches hosts whose tables do not exist, where it errors and produces no answer rather than a failure.

**Scope** is one of three, not two: the global scope, the unassigned scope, or a named fleet. **A global policy applies to hosts in every fleet**, which is the opposite of how configuration profiles and software behave ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Labels** narrow it further, and **policies are the only item in Fleet supporting all four modes**: include-any, include-all, exclude-any and exclude-all, with one include and one exclude allowed together.

**The freshness guard that protects profiles and software does not exist for policies.** A policy with a newly created dynamic exclusion label will evaluate on hosts that have not yet been assessed for it ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)). Let a label populate before you attach it as an exclusion.

## What each edition gives you

![Reference](../_assets/icons/reference.svg) Fleet Free includes policy assessment. Premium adds targeting and automation capabilities for broader management workflows; the table below identifies the boundaries.

| Capability | Edition |
|---|---|
| Creating and evaluating a policy | Free |
| Platform scoping | Free |
| Named fleets, and therefore fleet-scoped policies | **Premium** |
| Label targeting, in any of the four modes | **Premium** |
| Marking a policy `critical` | **Premium** |
| Attaching a run-script automation | Free in the unassigned scope; **Premium** once the policy is fleet-scoped |
| Attaching a software-install automation | **Premium** |
| Continuous automation, rather than firing on transition | **Premium** |

**The `critical` flag does more than sort.** Beyond marking a policy as one whose failure matters, it participates in conditional access, so treating it as a cosmetic priority label understates what turning it on does.

Two edges of the unassigned scope are settled in this release: creating an ordinary policy there works on Fleet Free, the same as in any other scope, and the Premium gate on label targeting applies there uniformly, in all four modes. A run-script automation attaches and fires in the unassigned scope on Fleet Free too, with no licence gate on that path ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)); a software-install automation needs Premium in any scope, because the installer it points at cannot be uploaded without it. The conditional-access side of `critical` is settled here too: an unassigned-scope policy can carry `critical` and can drive conditional access exactly as a fleet-scoped one does, and only a policy scoped to every fleet is barred from driving conditional access. The one wrinkle specific to the unassigned scope is where you switch conditional access on for its hosts: in Fleet's organization-wide integration settings, not on the unassigned scope's own page.

## Creating a policy that survives contact

![How-to](../_assets/icons/howto.svg) Build the policy around a clear requirement, test representative devices, and write guidance that helps someone act on a failure:

1. **Choose the type.** Dynamic if you are writing the question; patch if you are asserting a software version and can scope to a fleet.
2. **Write the query as the good state.** It passes when it returns rows.
3. **Test it live**, on representative hosts of **every** platform you intend to target ([4.2](4.2-run-queries-and-reports.md)). Read the error count, not only the rows: an error here is a policy that will produce no answer rather than a failure.
4. **Choose the scope**: global, unassigned, or a named fleet. Remember global means every fleet.
5. **Add platform scoping**, and label targeting if you have Premium.
6. **Write the name, description and resolution.** The resolution is what somebody reads at the moment they have to fix a host, so write an instruction rather than a restatement: "Turn on FileVault in System Settings, Privacy and Security" beats "This host does not have FileVault enabled".
7. **Decide on `critical` and on each automation** deliberately. `critical` is Premium and reaches conditional access. The run-script automation is Free in the unassigned scope and Premium once the policy is fleet-scoped; the software-install, App Store, calendar and conditional-access automations are Premium.
8. **Save it, then wait a reporting cycle.** Results do not appear immediately.
9. **Verify** against representative hosts and against the four-group denominator above, not against the failure count alone.

## Editing a policy resets what you have collected

![Reference](../_assets/icons/reference.svg) Plan a new evaluation cycle after editing a query. Its previous answers describe the old question and are cleared when the change is saved.

**Editing a policy's query clears every pass and fail it has collected**, along with its cached statistics, and resets automation attempt state. The results answered a different question, so Fleet discards rather than reinterprets them. Expect the policy to read as entirely unanswered until hosts evaluate it again on their own hourly clocks.

**Editing the platform or the label targeting removes the memberships that are no longer in scope**, which is narrower and usually what you want, but it does mean a scope change is not reversible by changing it back: the discarded results do not return.

## Reading a policy result honestly

![Troubleshooting](../_assets/icons/troubleshooting.svg) Use these checks to give a policy result the scope and timing context it needs:

| Question | Why |
|---|---|
| How many in-scope hosts have **no answer**? | They are in neither count, and they include every host where the query errored |
| Did the query **error** anywhere? | An erroring policy produces no answer, so it vanishes from both counts rather than showing as failure |
| When were the **counts** computed? | They are a cached aggregate with their own timestamp |
| When did each host last **evaluate**? | `policy_updated_at`, which dates the host's last policy reporting pass |
| Is this policy **global**? | If so it is running in every fleet, which may be wider than intended |
| Has the query been **edited** recently? | If so, everything collected before the edit is gone |

**A policy result is evidence about a question at a moment.** For anything that has to hold as an assertion about the estate, quote all four groups: out of scope, passing, failing, and no answer.
