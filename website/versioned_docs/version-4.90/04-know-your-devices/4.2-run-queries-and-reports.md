# Run queries and read reports

Fleet reports let you ask questions specific to your environment: check a setting across laptops, find a software version, or collect a result for an existing monitoring workflow. You can run a question live, schedule it, and choose whether its answers stay in Fleet, go to an external destination, or both. This chapter builds on the inventory in [4.1](4.1-understand-hosts-vitals-and-inventory.md) with those administrator-defined questions.

Fleet calls these **reports**. `queries` remains as a deprecated alias in the API and the command line, so you will meet both; this manual uses the current name.

## Scheduling, and the two output paths

![Explanation](../_assets/icons/explanation.svg) Saving a report gives you a reusable definition. Its interval and output settings determine whether it also runs automatically.

**Saved but not scheduled.** A report with no interval is a stored definition you can run live whenever you like. Nothing runs on its own. This is a perfectly ordinary state and it is where most reports start.

**Scheduled.** Fleet puts a saved report on a host's schedule only when all of these hold:

- its interval is greater than zero;
- the host matches its scope, meaning platform, minimum osquery version and any label targeting;
- **and at least one output path is active**, which means either automations are enabled or stored reporting is on.

Enable at least one output path when scheduling a report. With both automations and storage disabled, Fleet leaves it off the host’s schedule even if an interval is set. It consumes no scheduled-query work and produces no scheduled results in that configuration.

Given that it does run, the two outputs are independent of each other:

| Output | Turned on by | Gives you |
|---|---|---|
| **Stored report** | Snapshot logging, storage not disabled | The newest result per host, readable in Fleet |
| **Forwarded results** | The report's **automations**, off by default | Rows at your log destination ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)) |

A report with automations on and storage off forwards results and shows an empty report page. A report with storage on and automations off gives you a page and an empty destination. Both are working as configured.

## What stops a result being stored

![Reference](../_assets/icons/reference.svg) Fleet keeps the **newest result per host per report**, replacing that host's previous rows rather than accumulating them, so the page shows current answers and never a trend. Four things prevent it.

| What stops storage | Where it is set | Note |
|---|---|---|
| `discard_reports_data` | Server-wide organization settings | Also **deletes** rows already stored, not only future ones. The older spelling `query_reports_disabled` still works |
| `discard_data` | On the individual report | |
| A logging type other than **snapshot** | On the individual report | Differential logging is not stored as a report |
| The row caps | Two of them, below | |

**The three logging types are snapshot, differential, and differential ignoring removals.** The last reports rows that appeared without reporting rows that went away, which is what you want when you care about arrivals and not departures.

## Two row caps, and they are not the same number

![Reference](../_assets/icons/reference.svg) Two separate limits govern stored results. Design the report around both when you need complete results in Fleet, or forward results to a suitable external destination.

**A fixed per-host threshold of 1000 rows.** When a single host's result set exceeds it, Fleet **stores none of that host's rows**, rather than storing the first thousand. This threshold is hard-coded. Fleet passes the configured cap into the same function and does not use it for this decision.

**A configurable estate-wide cap, `report_cap`, defaulting to 1000.** This governs a cleanup that trims rows across all hosts, keeping the most recently inserted, and it sets the **clipped** marker on the report.

The following cases show how those limits affect what remains available:

| Configuration | What happens |
|---|---|
| `report_cap: 2000`, one host returns 1001 rows | That host stores **nothing**, even though it is well under the configured cap |
| `report_cap: 500`, one host returns 800 rows | The rows are inserted, then trimmed later by cleanup rather than rejected outright |

For a host returning more than a thousand rows, narrow or aggregate the SQL, or forward the results. Raising `report_cap` changes the estate-wide cleanup cap but does not change the fixed per-host threshold.

Once a report is marked **clipped**, treat both its coverage and its freshness as unknown and read it through a destination instead.

## Live reports and scheduled reports answer different questions

![Explanation](../_assets/icons/explanation.svg) Use live reports for an immediate investigation or a small test. Use scheduled reports when you want hosts to answer repeatedly over time.

**A live report** goes out now, over the osquery distributed channel, to hosts that are online and answering. It is the right tool for "what is true right now" and for testing a report before scheduling it.

Review response coverage alongside the rows. Fleet tracks targeted and responding hosts, separates responses with and without rows, and displays per-host errors as they arrive:

| What you see | What it means |
|---|---|
| A host returns rows | It ran the report and matched |
| A host responded with no rows | It ran the report and matched nothing. This is a real answer |
| A host returned an error | The report failed there, and the error text is in the result |
| A host is missing from the responders | It did not answer: offline, not reachable on the distributed channel, or outside the report's scope |

Fleet records an activity for a live run, including the report and target count, and updates performance statistics. It does not retain the returned rows as host data. Export results you need to keep; the activity remains available for audit review ([1.5](../01-foundations/1.5-audit-and-activity.md)).

Two limits bound live reports. A server setting, `live_reporting_disabled`, turns them off entirely, which is worth checking before diagnosing an unresponsive interface. And the interface clips a very large live result set rather than rendering it without limit, so a report returning hundreds of thousands of items is one to export rather than read on screen.

A report's `observer_can_run` flag decides whether observer-role users may run it, which is how a deployment lets a support team run a chosen set without broader access ([1.4](../01-foundations/1.4-identity-and-roles.md)).

**Platform coverage differs.** On ChromeOS live reports work and **scheduled reports do not exist**, because the extension answers the distributed endpoints and never posts to the logging endpoint ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)). On iOS, iPadOS and Android there is no osquery, so neither kind applies.

## Reading a stored report

![Reference](../_assets/icons/reference.svg) **A successful empty result is recorded, and whether you can see it depends on which surface you are reading.** When a host runs a snapshot report and matches nothing, Fleet stores a marker carrying that host's fetch time rather than nothing at all.

| Surface | What it shows for a host that matched nothing |
|---|---|
| The estate-wide report | **Nothing.** Those markers are excluded from the row list, so the host is simply absent |
| That host's own report view | The empty result **with its fetch time**, which is positive evidence that the host ran the report and matched nothing |

That difference decides where to look. If you need to distinguish "this host has nothing" from "this host has not run it", the estate view cannot tell you and the host view can.

**A scheduled execution failure is not stored as an empty result.** It leaves no report row of any kind, so on the estate view a failing host and a matching-nothing host look identical, and only the host view separates them. Diagnosing why a scheduled report fails on one host is [8.2](../08-troubleshooting/8.2-log-surfaces.md)'s and [8.7](../08-troubleshooting/8.7-live-query-introspection.md)'s subject.

**Read the per-row fetch time rather than the page.** A stored report is an accumulation of per-host answers taken at different moments.

## Scoping a report

![How-to](../_assets/icons/howto.svg) **Platform** uses the generic selectors `darwin`, `windows`, `linux` and `chrome`, not the specific value stored on a host, so a Fedora host is selected by `linux` although its inventory field reads `rhel` ([4.1](4.1-understand-hosts-vitals-and-inventory.md)). Leaving a report unscoped sends it to hosts whose tables do not exist, which produces errors rather than empty answers.

**Minimum osquery version** keeps a report away from hosts too old to run it, which is better than letting it fail there quietly.

**Fleet scope and labels.** A report belongs to a fleet or to the global scope, and a **global report reaches hosts in every fleet** as well as unassigned hosts ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)). Label targeting narrows it further, with include-any or include-all; reports have **no exclusion mode**. Both named fleets and label targeting for reports are **Fleet Premium**, so on Free a report is global and unlabelled.

Filter, count, or aggregate in SQL to return the answer you need within the per-host threshold. A single count is often more useful than a large inventory that must be filtered after collection.

![How-to](../_assets/icons/howto.svg) Start with a small live test, then add the scope, output paths, and interval that make the report useful in routine operations:

1. **Write it and run it live** against a handful of hosts. Read the responded, no-results and error counts, not only the rows.
2. **Fix the errors** the live run surfaced, which is where a missing table or a platform mismatch shows itself.
3. **Save it**, without an interval. It is now a definition you can re-run.
4. **Scope it**: platform, minimum version, fleet and labels.
5. **Decide the outputs** deliberately. Storage, forwarding, or both. Remember that neither means it will not be scheduled.
6. **Set the interval**, and only then does it join host schedules.
7. **Verify** by reading a single host's own report view, which is the surface that distinguishes an empty answer from no answer.

**Editing a saved report is destructive to its stored results.** Changing the report's SQL invalidates the answers already collected, because they answered a different question. Expect the stored report to empty and refill on the next cycle rather than to update in place.

## What a report costs

![Troubleshooting](../_assets/icons/troubleshooting.svg) Use Fleet’s current performance statistics to compare reports and find expensive queries. The stored figures describe recent performance; Fleet does not retain a time-series history.

Per-host scheduled report statistics are **overwritten on each update**, not retained as a time series, so there is no slope to read. What Fleet gives you is the latest per-host figures, including average wall time and average memory, and an aggregate performance indicator computed from current CPU percentiles and total executions.

So the method is comparison rather than trend: run the report against a representative set of hosts, read the current statistics, and compare them against other reports on the same hosts. A busy server and a laptop with a full disk are more informative than a clean test machine. The osquery watchdog, denylisting, and what to do about an expensive report are [4.6](4.6-advanced-osquery-queries-and-tables.md)'s subject.

## Getting results out of Fleet

![How-to](../_assets/icons/howto.svg) **The API** returns stored report rows, and it is the route for putting them somewhere else on a schedule. Fetch a report's results estate-wide, or a single host's, remembering the difference between those two surfaces described above.

**The command line** runs live reports with `fleetctl report` and lists definitions with `fleetctl get reports`. The older `query` and `get queries` spellings still work as aliases. Neither retrieves stored rows: the first runs a fresh live report, the second lists definitions.

**A log destination** receives forwarded results and is the route to use when you want history, because Fleet's own storage keeps only the newest result per host. **The Fleet row caps do not apply there**, though the destination's own limits and the transport's do: Fleet's result-log endpoint has a request size limit of its own in the legacy authentication mode, and destinations reject oversized writes ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)).

**One exception to the automations rule is worth knowing.** In the steady state Fleet forwards only reports whose automations are enabled. When stored reporting is disabled server-wide, it forwards incoming results without applying that filter, and it also forwards results for reports it does not recognise, which is how an osquery configured outside Fleet still reaches your destination.

## Legacy 2017 packs and how to retire them

![How-to](../_assets/icons/howto.svg) Before Fleet folded scheduling into saved queries, a scheduled query lived in a container called a **pack**: a 2017-era object grouping queries with their own intervals, platforms and logging settings. Packs still exist as a first-class object at this release. The current UI and the modern workflow no longer introduce them, though the legacy pack spec and its apply API can still create or update one, and their modern equivalent is the scheduled report this chapter has described. You meet packs in two situations: a deployment old enough to predate the change still carries them, or you are importing a community osquery pack from outside Fleet. [a.6](../09-appendices/a.6-glossary-and-release-compatibility.md#pack-and-scheduled-report) defines the term.

Three commands touch packs, and they do different jobs, so the distinction to hold is this: `convert` imports a pack **file** from outside, `upgrade-packs` migrates the packs already **inside** your Fleet, and `get packs` just **reads** them.

- **`fleetctl get packs`** reads the 2017 packs stored on your Fleet server, listing them all or printing one by name. Adding `--with-reports`, whose older spelling is `--with-queries`, also prints the queries a pack references. That flag has an output-format caveat when you list every pack: the referenced reports come through only in the JSON or YAML output, not the default table, so ask for `--json` or `--yaml` when you want them. Reading packs needs pack-read authorisation, on any edition.
- **`fleetctl upgrade-packs`** reads the legacy packs already living inside your Fleet and writes a file of portable report specs you then apply. It requires the **Global Admin** role. A pack that targets fleets becomes one scheduled report duplicated per fleet; a pack that targets labels or hosts becomes a global report with **scheduling disabled**, which you re-enable deliberately once you have checked it. It leaves the original packs in place and tells you to disable them at the packs management page after you convert them.
- **`fleetctl convert`** works the other way, and offline. It takes an osquery-format pack file on disk, a JSON `.conf`, and converts it into Fleet report YAML on stdout or to a file, mapping osquery's platform strings to Fleet's. It never contacts a Fleet server and needs no authentication, which makes it the tool for turning a community pack into something you can apply.

`upgrade-packs` describes a future automatic conversion in its output. At Fleet 4.90.0, legacy packs and their endpoints are still present, so use the explicit migration procedure below rather than relying on that future behavior.

Retiring a pack, then, is three steps: convert it with `upgrade-packs` or `convert`, apply and verify the resulting reports through a single host's report view as [From question to scheduled report](#from-question-to-scheduled-report) describes, and disable the old pack at the packs management page so nothing runs twice. The full contract for each command, including its exact permissions and the silent-failure notes, is in [a.7](../09-appendices/a.7-fleetctl-command-reference.md).
