## Derived

- **"One channel and it is MDM"** as the chapter's frame is the deliberate third variation on 3.2's two channels, 3.3's two coupled channels and 3.4's one agent channel.

## Strengthened 2026-08-27, from 3.2's review

3.2's first review established that Fleet's post-enrollment task is per-platform, which made the iOS branch worth reading rather than assuming. Two additions, both from `server/worker/apple_mdm.go`'s non-macOS branch of `runPostManualEnrollment`:

- **The refetch is not triggered by enrollment.** A source comment states this deliberately: refetch is handled by the `apple_mdm_iphone_ipad_refetcher` cron, which picks up freshly enrolled hosts on its next tick, "to avoid tying the host's inventory catch-up to the synchronous enrollment path". So the chapter's "a thin host page is not a broken enrollment" now has a mechanism and a place to check, `cron_stats` for that schedule, instead of being reassurance.
- **What Fleet does do after an iOS enrollment** is install setup-experience App Store apps, on Premium, and nothing else. Worth stating because it is the whole of the post-enrollment work on this platform, and it makes "an iPhone that completes ADE is done" a bounded claim rather than a confident one.

Also corrected: the chapter said the half-enrolled failure "dominates macOS ADE". It is not ADE-specific, per 3.2's rewrite.

## Strengthened again 2026-08-27, before its review, from 3.4's lesson

3.2, 3.3 and 3.4 all came back NOT READY on the chapter's organising claim, so 3.5's was checked against the source rather than against what the manual believed. The framing held: iOS and iPadOS genuinely have one channel and it is MDM. Two things changed anyway.

**The enrollment path decides whether the device can ever be locked, and the chapter did not say so.** Fleet refuses `lock` for **any manually enrolled iPhone or iPad**, company-owned included, with a message naming exactly that case. Personal enrollment on any Apple platform loses lock and wipe both, because the profile was built without those rights. So:

| Path | Lock | Wipe |
|---|---|---|
| ADE | Yes | Yes |
| Enrollment URL, company-owned | No | Yes |
| Enrollment URL, personal | No | No |
| Account-driven | No | No |

This is narrower than the macOS rule, where only personal enrollment loses them, and it is a purchasing decision rather than a configuration one: if remote lock is part of the reason for managing these devices, ADE is the only path that provides it. Source: the lock validation's `MDMEnrollmentStatusManual` branch for `ios`/`ipados`, and the personal-enrollment branch shared with macOS.

**"There will not be one" was withdrawn.** The chapter predicted that fleetd will never exist for these devices. Nothing establishes that; "at this release" is what the source supports and is all the reader needs.

## First independent review, 2026-08-27: NOT READY. Applied.

Ten factual defects. Two of them had been caught before the review arrived, by checking the chapter's organising claim against source after 3.2, 3.3 and 3.4 all failed on theirs. Eight were new, and four changed neighbouring chapters.

**ADE is Fleet Premium, and the chapter called the question undocumented.** Fleet Free returns `ErrMissingLicense` for uploading, listing, renewing and counting Apple Business tokens, so there is no ADE without Premium. The first draft had assembled three licence facts, concluded the matrix was undocumented, and marked it unverified. It was documented in the place the draft did not look: the ABM token surface rather than the enrollment endpoints. **2.7 said Apple Business is Premium all along**, so this was 3.5 contradicting a chapter that was right. Corrected here and in **3.2**, which carried the same unverified framing.

**An ABM token has four default fleets, not three**, and the fourth is the one that matters for the path this chapter is about. `BYODDefaultTeamID` is what places an **account-driven** enrollment: Fleet finds the token from the enrollment challenge and uses that setting. Leave it unset and those devices land unassigned while the administrator inspects the iOS and iPadOS defaults, which have no bearing on them. Corrected in two places here, and **3.1's placement table** rewritten, because it had every Apple path placed by an ABM token and none placed by an enroll secret.

**Account-driven enrollment needs a Managed Apple Account, and there are two authentications.** The chapter described only the SSO half. Fleet writes the assigned Managed Apple Account and a BYOD enrollment mode into the profile it returns; a personal Apple Account is not a substitute. Rollouts planned around "an Apple ID and SSO" discover the second half late, which is exactly the shape of failure a chapter like this exists to prevent.

**Identity is not what distinguishes account-driven enrollment**, which was the chapter's stated reason to prefer it. The enrollment link carries an identity too when end-user authentication is on: `/enroll` goes to the identity provider first and Fleet associates the returned account with the host. **2.2 and 3.2 both say so.** What *does* distinguish the account-driven path is the privacy boundary: Fleet receives an enrollment identifier rather than a serial and UDID, and profiles are user-scoped. The personal **link** path supplies serial and UDID before enrollment despite showing the same `On (manual - personal)` status, and **2.8 collapses the two**; that distinction is now stated here.

**`apple_mdm_iphone_ipad_refetcher` is Premium-only.** It is registered inside `registerPremiumCrons`, which returns immediately without a Premium licence. The chapter had recommended checking its `cron_stats` to a reader it had just told to use the free enrollment link, which sends a Free administrator to troubleshoot a schedule that was never started. **8.6 already labelled it Premium.**

**"No logs you can collect" was false.** A **sysdiagnose** carries the MDM client's logs and Fleet's own troubleshooting guidance names it for command and profile delivery problems. **8.8 already says so.** The chapter told the reader to discard the one piece of device-side evidence Part VIII asks for.

**Post-enrollment work is not only setup-experience apps.** Fleet reconciles configuration profiles first, and on ADE waits on commands, profiles and setup-experience results before releasing the device. The chapter's wording would have a reader dismiss profile delivery and device-release delays as unrelated to enrollment.

**Two cardinality and provenance overstatements.** "One link per fleet" reads as a limit of one link; a fleet can hold up to 50 enroll secrets, so several live links are normal. And "everything Fleet knows arrived over MDM" is contradicted by the chapter's own OTA mechanism, which creates the host from serial, product and UDID *before* enrollment, and by ABM sync creating a `Pending` host. **1.2 carried the same overstatement** and is corrected: what Fleet *does* to an iPhone is an MDM command; what Fleet *knows* has a wider provenance.

### Added from the omissions list

**What the person holding the device actually does**, which the chapter had entirely skipped in favour of protocol internals. Four steps from the enrollment page itself, with the two places people stop: the page refuses any browser but Safari, and iOS shows a red **Not Verified** warning at the install step that is expected. The page's own description of what each ownership choice means for the end user is worth quoting when someone asks before installing.

## Confirming review, 2026-08-27: NOT READY, applied

Most of the first review's ten findings confirmed resolved, including the ADE Premium correction, the fourth ABM default fleet, the Managed Apple Account requirement, the Premium-only refetcher, sysdiagnose, and the user-facing enrollment procedure. Five items remained, and **four of the five were introduced by the corrections themselves**, which is now the expected shape rather than a surprise.

**The worst was a licensing claim in the opposite direction from the one just fixed.** Having established that ADE needs Premium, the chapter then told a reader that owner mapping on the enrollment link is available on the free path. **End-user authentication is itself a Premium setting**, so the link gives you identity without account-driven enrollment and not without a licence. The correct statement, now in the chapter, is that the free link gives you enrollment and not identity. Getting a licence boundary wrong in each direction within one chapter is worth recording as a caution about correcting licensing claims at all: they are cheap to assert and each one lives in a different validation.

**The provenance correction was applied at the opening and contradicted later.** The opening now says what Fleet *does* to an iPhone is MDM while what Fleet *knows* has a wider provenance; the refetcher paragraph still implied everything arrives over the protocol. The paragraph now closes the loop explicitly.

**"Usually waiting on that work"** was a frequency claim written during the previous pass. The worker establishes what the ADE path waits on, not how often a slow Setup Assistant is that rather than something else.

**"The table below has it"** pointed at a table above it, left over from moving the lock-and-wipe table up.

**"It will never run an agent"** is the same roadmap absolute the first review removed from the opening, surviving in a later sentence. Now "runs no agent", which is what the tag supports.

**And one in a neighbour**: 3.2's ADE row read "Fleet Premium, because operating an Apple Business token is", a splice from the licensing correction. Fixed there.

### Lock and wipe licensing, added 2026-08-27

Added after 3.5's confirming review found this chapter's licensing wrong in both directions inside one chapter, which suggested checking every licence claim in the part rather than the one that was flagged.

The boundary, from the free service's own implementations: **`LockHost` returns `ErrMissingLicense` unconditionally**, so lock is Premium on every platform. **`WipeHost` refuses any host whose platform is not `android`**, with a source comment saying wipe for macOS, Windows, Linux and iOS/iPadOS is Premium and that Android on Premium goes through the enterprise implementation instead. So **wipe on a company-owned Android host is the one lock-or-wipe operation Fleet Free has**, and it is worth naming, because a Free deployment that needs a remote-wipe story has exactly one place to get it.

## Third round, 2026-08-27

NOT READY. The consequential finding was not in this chapter at all.

**2.7 said recovering from APNs certificate expiry needs MDM turned off and back on per device.** Fleet's own guidance says the opposite: renewing the **same** certificate restores delivery even after it has lapsed, with nothing to do on the devices. Re-enrolling every device is what happens when the **Apple Account** that created the certificate is lost, because a new certificate breaks trust. Conflating the two would have had someone re-enrol an estate to fix an expiry. Corrected in 2.7 and here.

The rest: App Store and in-house app installation is Premium before the device-scoped against user-scoped licensing distinction matters, so that passage was comparing two Premium deployments while reading as though one were free. The ABM-token prerequisite became a universal, when this release still serves the discovery and account-driven endpoints without a token, so it is a statement about setting the path up today rather than about every working installation. And the decision table still labelled both URL paths simply "No" for Premium when enrolling is free and mapping an owner is not.

**The reviewer retracted its own second-round correction** on link cardinality. "Each link targets exactly one fleet" is wrong because an enroll secret may be global, placing the host in Unassigned. The accurate form is that each link selects one placement *scope*. 3.2 carried the original error and now matches.
