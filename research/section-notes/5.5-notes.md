## Derived

**"Setup can hold a person at a progress screen; self-service never holds anyone anywhere."** The
chapter's organising contrast. Editorial.

**"An item in setup is an item that can fail somebody's first login."** Follows from the blocking
behaviour; the advice to keep the mandatory list short is mine.

**"Two label mechanisms sit inside this one feature and behave oppositely, which is the trap."** Both
mechanisms are source-checked; naming it a trap is editorial.

**Test each enrollment path, not each operating system.** The strongest advice in the chapter, and it
is inference from the verified fact that paths differ in blocking behaviour within one platform.

**"A setup you have never seen fail is a setup whose failure behaviour you are guessing at."**
Editorial.

## Unverified, and phrased as such in the text

**No Fleet-side macOS version check for the PSSO pane.** Written as what the inspected upload and
assignment paths contain, not as a universal claim.

**No administrator setup checklist.** Written as what Fleet exposes rather than as proof none exists,
after review flagged the stronger phrasing.

**The Windows CSP behaviour on future builds.** Written as a possibility with its observable symptom,
since it depends on Windows rather than Fleet.

## Rejected, and why

**My own "no Platform SSO in setup" note.** A false negative from grepping only the setup-experience
source files. PSSO is supported and arrives through another lane. The lesson is recorded because the
failure mode generalises: zero hits is evidence about where you looked.

**"Terminal is not successful" as a heading.** Accurate about consequence, wrong about vocabulary,
because `Verifying` is not terminal in the profile lifecycle and can move backwards. Renamed to
"Release-ready is not successful", which is what the release check actually tests.

**"Labels do not filter setup software on macOS."** True but far too narrow: it holds on every
platform and for store apps too.

**"Only two things affect the Windows hold."** Confused what holds the page with what decides how it
ends. Pending profiles and in-flight software hold it; failure and timeout decide the outcome.

**The device-uninstall authorization detail.** Recorded as S2 in the private defect queue and
deliberately excluded. The manual repo is public, the behaviour is unfixed at this release, and the
passage would function as a method for removing an organisation's endpoint agent. The reviewer was
asked to argue against the omission and agreed with it, noting that omitting it does not mislead
anyone choosing what to publish, because the affected path never consults the self-service flag. The
chapter carries the reviewer's entitlement wording instead, which names a real control rather than
gesturing at a threat.

### Derived

**No lockout, retry limit or cooldown on Fleet's side of a rejected password.** Searched
`ee/server/service/apple_psso*.go` and `server/fleet/apple_psso.go` for rate-limiting or lockout
logic and found none; a failed ROPG call surfaces the IdP's own `error`/`error_description`
unchanged. Written as "no separate lockout on this path" rather than a universal claim about Fleet,
since the IdP's own policy is what actually governs it.

**The offline unlock key described only in general terms.** The key-request/key-exchange mechanism
is real and reachable from the code, but its purpose (letting the account unlock without Fleet or
the IdP being reachable "at that exact moment") is a plain-language reading of the `user_unlock` key
purpose and the ECDH key-exchange comments, not a directly stated behavioural guarantee, so it is
phrased as what the mechanism is for rather than as a timed guarantee.

## 2026-09-02 addendum: Codex read-only review, corrections applied before commit

Per the round4-fix protocol, ran `codex exec -m gpt-5.6-sol -c model_reasoning_effort=high -s
read-only -c 'sandbox_permissions=["disk-full-read-access"]'` against this subsection before
committing. No BLOCKER findings; 6 MAJOR and 4 MINOR, all addressed in the text before commit.

**MAJOR, applied:**

1. **Sync timing was wrong.** The original text said Fleet is contacted "at each sign-in or
   unlock." `docs/Contributing/research/mdm/psso.md:11` documents a four-hour window: macOS checks
   the password against the IdP only when its token is missing, expired, or over four hours old, at
   the next login/unlock, and even a logout/login inside that window doesn't force a check on its
   own. This reverses the "Rejected" note above from the original draft, which had declined to cite
   this doc on the grounds that its wording ("in my testing") made it read as informal. On
   re-reading, the four-hour mechanism itself is stated as a plain known limitation, not hedged as
   testing-only; only one adjacent claim in the same doc (the logout/login edge case) carries that
   qualifier, and the rewritten text keeps that one phrased as an observation rather than a
   guarantee. Rewrote the paragraph to state the window and its consequence: a changed IdP password
   can lag on the Mac by up to the window plus lock time, until the new password is entered.
2. **"Fleet sets its own subject... so a misconfigured or malicious identity provider cannot forge
   the values the device relies on" was false.** Re-checked `buildPSSOIDTokenClaims`
   (`ee/server/service/apple_psso.go:549`): `out["sub"] = idpClaims.Subject` — the subject is the
   IdP's value, forwarded unchanged, not something Fleet sets independently. Fleet sets iss, aud,
   nonce, iat and exp itself; sub and the other identity claims are not among them. This was a
   verification miss in the original pass: the source comment ("so a misconfigured or malicious IdP
   can never override the claims the device validates") was read as covering identity, but the code
   it describes only protects the protocol-binding fields. Rewrote to state plainly that the subject
   and identity claims are the IdP's own values passed through, and that a compromised token
   endpoint can still choose who a device believes it's provisioning for.
3. **Token-validation disclosure was incomplete.** Said only "Fleet does not verify the signature."
   `parseOIDCIDTokenClaims` (`ee/server/service/apple_psso_idp_oidc_ropg.go:120`) uses
   `jwt.WithoutClaimsValidation()` and `ParseUnverified`: issuer, audience, expiry, not-before and
   every other registered claim go unchecked too, not just the signature. Only a non-empty `sub` is
   required. Rewrote to say Fleet trusts the token endpoint's response wholesale, not narrowly
   "skips a signature check."
4. **Registration profile/extension prerequisites were missing.** The original text said "deliver
   that profile the way you deliver any other" without saying which profile. Re-checked
   `validatePSSORegistrationTokenVariable` (`server/service/apple_mdm.go:585`): the registration
   token variable is only accepted inside a `com.apple.extensiblesso` payload whose
   `ExtensionIdentifier` starts `com.fleetdm` (Fleet's own bundled extension, not a third-party IdP
   extension) with `PlatformSSO.UseSharedDeviceKeys` set to `true`; anywhere else in a profile, Fleet
   rejects it. `ExtensionData.BaseURL` must be HTTPS
   (`AuthenticationViewController+Shared.swift:73-84`), and the AASA document needs a
   publicly-trusted certificate — Apple silently rejects self-signed
   (`docs/Contributing/research/mdm/psso.md:89`). Added these as the actual content of "that
   profile" instead of leaving it unspecified.
5. **ROPG's provider-side restrictions were omitted.** `docs/Contributing/research/mdm/psso.md:88`:
   Okta requires Resource Owner Password explicitly enabled on the application; Entra rejects ROPG
   for MFA-required or AD FS-federated users outright. Added both, since an operator hitting this
   would otherwise plausibly misdiagnose it as a Fleet bug.
6. **GitOps's declarative resupply requirement and the a.5 "identically" claim.** Confirmed via
   `appconfig_test.go`'s `"gitops public fields without secret rejected"` case (already-stored secret
   does not satisfy a GitOps apply; the secret must be present in the file every time) and
   `client.go`'s GitOps default-value handling (omitting the section clears the config). Added the
   caveat to 5.5 and corrected a.5's "readable and writable... identically" line (CAP-372 keeps its
   `Full` ratings; GitOps has no read direction and a generated file gets a `TODO` placeholder for the
   secret, confirmed via `generate_gitops.go:1452-1470`) — recorded in `a.5-notes.md`.

**MINOR, applied:** the macOS-26 floor was attributed to "Apple's framework" when it's specifically
Fleet's password-sync implementation (Platform SSO itself is macOS 13+, Fleet's extension code
14+, per `apps/fleet-desktop-macos/README.md:25`) — reattributed; password encryption was described
as something "some deployments configure" when Fleet's extension always applies it and fails
registration rather than falling back to TLS-only (`AuthenticationViewController+Shared.swift:73`)
— reworded to unconditional; email/name/preferred_username were implied guaranteed alongside
subject, when only `sub` is required — added that caveat; the "same shape as a service-account
script" analogy was inaccurate (ROPG is a user-credential grant, not a service-account grant) —
dropped.

No BLOCKER issues; nothing deferred out of the major/minor findings. Full Codex transcript not
retained beyond this session's working files.

## 2026-09-04 fix: reconcile iOS/iPadOS self-service auth (round8 MJ-D)

5.5:410 ("the host identifier ... is what authenticates the device") and 5.5:442 ("by client
certificate instead") assigned two mutually exclusive auth mechanisms. Confirmed at
fleet-v4.90.0: `server/service/endpoint_middleware.go:79-93` uses client-certificate auth when
the `X-Client-Cert-Serial` header is present (`AuthenticateDeviceByCertificate`), else tries the
device token (`AuthenticateDevice`, the Fleet Desktop hot path), else falls back to UUID-via-URL
(`AuthenticateIDeviceByURL`). Softened 410 to "locates the device on that path" and rewrote 442:
cert takes precedence when presented, the UUID-bearing self-service URL is the supported fallback,
and the UUID identifies rather than standing in as a second credential. Matches a.2's "by client
certificate or by an address carrying the host identifier."
