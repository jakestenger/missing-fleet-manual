# 6.4 Operate Fleet with fleetctl, citation ledger

Drafted 2026-08-28. Research consensus in one round with ten corrections, draft, one review round
applied. Working research is held outside this repository, see [`README.md`](README.md).

## A note on how this chapter's research was done

The agent had `fleetctl` 4.90.1 installed at the same revision as the tag, so parts of the research
are **observed behaviour from offline probes against throwaway configuration** rather than source
reading. Those were marked as observations and the reviewer was asked to treat them as evidence
needing confirmation rather than as citations. The distinction matters for anything in this ledger
about output and exit status.

## Derived

**"Know what each command's exit status represents, and where its outcome is exposed."** The
chapter's rule, and the reviewer's correction to my first version of it. My research had counted
roughly twenty commands as failing while exiting zero, which is not a fair description: many are
ordinary informational output, and an asynchronous command correctly reports that work was queued.

**The six-item preflight.** Added at review, and the reviewer's answer to the chapter reading as
relentlessly negative: supply the ordinary safe path rather than soften the warnings.

## Rejected, and why

**"`fleetctl` is a client of the API and nothing more."** False. It also does configuration,
packaging, scaffolding, conversion and update-repository work, none of which touches a server.

**"Every limit 6.3 describes applies here too."** Too broad; 6.3's obligations are written for custom
clients and native commands handle some of them.

**"Roughly twenty commands fail while exiting zero."** Unfair characterisation, per above.

**Stacking three scaffold problems into one.** Two are state hazards that genuinely combine; the
credential exposure is separate and neither causes nor magnifies them.

**"Host actions mirror the interface's semantics and asynchrony."** Not uniformly.

**Pointing at a.7 as the command index.** It is still an outline, so the chapter says so and carries
enough to stand alone.

## Fix-loop round (2026-09-02, round4 RM15)

- **npm install instruction contradicted the chapter's own pinning guidance.** `npm install -g
  fleetctl` was shown unversioned in the same chapter that elsewhere says to pin the client to the
  server's release. `tools/fleetctl-npm/run.js` downloads whatever platform binary its own
  installed `package.json` declares, so an unpinned install gets npm's current registry default,
  not necessarily 4.90.1. Pinned the shown command to `fleetctl@4.90.1` and added a sentence
  making the mechanism explicit. Basis: `tools/fleetctl-npm/run.js` and `package.json` at
  fleet-v4.90.1 (read directly).
