## Deliberately left out

- **Cloud-specific reference architecture contents** (VPC layout, subnets, ACLs, the Terraform module). Belongs to 2.3.
- **Render, GCP and Azure sections.** 2.3 and 2.4.
- **Systemd unit file and binary extraction.** 2.4.
- **Tracing configuration** (OpenTelemetry endpoints, sampling, runtime sampling adjustment). Substantial material at `docs/Deploy/Reference-Architectures.md` Traces; it is an observability topic and fits 7.4 or Part VIII better than a capacity chapter.
- **`fleetctl debug archive` mechanics and per-instance targeting.** Canonical home is 8.5 per STYLE §18; the chapter keeps only the credential-scrubbing consequence, which is a deployment decision.
- **The three-store model, Redis output buffer limits, standalone vs cluster, what is coordinated across instances, and the differing consequences of losing Redis versus MySQL.** All canonical to 1.6; 2.2 builds on them and does not restate them.
- **Redis connection settings** (`redis.max_idle_conns` default 3, `redis.max_open_conns` default 0 meaning no limit). Verified at `server/config/config.go:1360-1362` but omitted: no published sizing guidance tunes them, so including them would imply a decision the reader does not have to make.

## 2026-08-25 review pass: a second factual error, and two missed constraints

Independent reviews on `gpt-5.6-terra` and `gpt-5.6-sol`. Both flagged the object-storage
section; sol verified it at source and found more.

### Corrected: the object-storage fallback claim was wrong

As published: "Both are survivable on one instance. Neither survives the second one, because
local disk is not shared."

Carves fall back to **MySQL**, which is shared, so they survive horizontal scaling perfectly
well. Only the filesystem-backed artifacts break. Verified:

| Artifact | Fallback | Source |
|---|---|---|
| File carves | MySQL | `cmd/fleet/datastore.go:61-64`, `carveStore = mds` unless a bucket is set |
| Apple bootstrap packages | MySQL | `cmd/fleet/serve.go:554` provisions an S3 store only inside the S3 branch; no filesystem equivalent exists in the else branch |
| Software installers | Local filesystem | `cmd/fleet/serve.go:571-578`, defaulting to `os.TempDir()` unless `FLEET_SOFTWARE_INSTALLER_STORE_DIR` is set, logging "not suitable for production use" |
| Software title icons | Local filesystem | `cmd/fleet/serve.go:586-593`, same pattern and same log line |

The section is now conditional rather than universal, and retitled, since a deployment using
neither software distribution nor Apple setup assets faces a database-growth decision rather
than a breakage.

### Added: two ceilings the chapter did not have

| Claim | Source | Confidence |
|---|---|---|
| `max_prepared_stmt_count` must be at least `max_open_conns` x maximum Fleet servers x 4 | `docs/Configuration/fleet-server-configuration.md:160-164` | High |
| A read replica has an independent pool, `mysql_read_replica.max_open_conns`, inheriting nothing from the primary | same, MySQL section introduction | High |

The prepared-statement formula sits in the same MySQL section of the configuration reference
that supplied the connection-limit material originally. It was read past, not absent.

### Calibrated

"Fleet instances never get bigger" and "more of them is always the answer" were stated as
properties of Fleet. What the artifacts support is that per-instance allocation is constant
across the published rows while the count rises from six to seventy. The GCP rows hold constant
too, at 1 CPU / 2GB against AWS's 1 CPU / 4GB, so the sizing table is now labelled as the AWS
reference architecture rather than as "every published configuration".

Removed as unsourced: "the failure modes are considerably worse than a two-minute outage".
Fleet states that migrations run with all instances shut down; it does not characterise what
happens otherwise.

### Cross-reference defect found in a neighbouring chapter

The containers-and-VMs chapter read "as [2.9] notes, escrowed Linux disk encryption data" (quoted under the old numbering, when this chapter was 2.9). This chapter contains no mention of the private key, LUKS or escrow; that material was in the readiness chapter (since moved to 7.7). Repointed there; the 2026-08-30 restructure then moved the escrow mechanics to 7.2 and repointed the citing sentence again.

**`build/check-links.py` reported this file as healthy throughout.** It validates that a link
target exists, not that the target says what the citing sentence claims. Every "as X covers" in
the manual is currently unverified by tooling. Worth closing.

### Declined

Both reviews proposed reordering the chapter around a planning sequence. The current order runs
requirements, scaling shape, connection budget, network, storage, availability, upgrades,
verification, which is already close to that sequence. Revisit if the chapter grows.
