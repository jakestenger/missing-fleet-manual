# 2.2 Identity providers, SSO, SCIM, and role sync — research notes

Verified against: **tag `fleet-v4.90.1`**.
Sources: `docs/Deploy/single-sign-on-sso.md` (298 lines),
`articles/foreign-vitals-map-idp-users-to-hosts.md`.
Written 2026-08-23.

## The finding that shapes the chapter

**SCIM does two unrelated jobs in Fleet, and the stub conflated them.**

1. **Administrator deprovisioning** (`single-sign-on-sso.md`, "Automatically deprovision
   Fleet users"): when SCIM is configured, Fleet deletes a user's *Fleet account* when the
   user is deleted or deactivated in the IdP.
2. **Foreign host vitals** (`foreign-vitals-map-idp-users-to-hosts.md`): maps an *end user's*
   IdP username, groups, and department onto their *hosts*, for use as configuration-profile
   variables and label criteria. Premium.

Same protocol, same endpoint, entirely different audience and outcome. Job 1 is about who
can administer Fleet; job 2 is about what Fleet knows about a device's owner. Writing them
as one feature is the mistake the chapter has to avoid.

## Verified: SSO

- Standard is **SAML**. Documented IdPs: Okta, authentik, Google Workspace, Entra ID, plus
  any SAML IdP.
- Supports **both IdP-initiated and SP-initiated** login, and JIT provisioning.
- UI path: **Settings > Integrations > Single sign-on (SSO)**, which has two tabs:
  **Fleet users** (administrator sign-in) and **End users** (IdP authentication during
  setup experience). Distinct purposes, same page.
- Fields: **Identity provider name** (rendered on the login page), **Entity ID** (a URI,
  e.g. `fleet`, must match the IdP), **Metadata URL**, or **Metadata** (paste XML when the
  IdP offers no URL).
- ACS / callback URL: `https://<fleet_url>/api/v1/fleet/sso/callback`
- For Require IdP authentication (setup experience) the callback differs:
  `https://<fleet_url>/api/v1/fleet/mdm/sso/callback`
- Name ID format: **email address**.

## Verified: JIT provisioning

- **Fleet Premium only.**
- Enabled by **Create user and sync permissions on login**
  (`sso_settings.enable_jit_provisioning`).
- Creates the account on first login; email and full name copied from the SSO response.
- **Default role is Global Observer.**
- Fleet **re-evaluates roles on every login**, not only at creation.
- Requires the IdP to send email as Name ID, and full name as an attribute named one of:
  `name`, `displayname`, `cn`, `urn:oid:2.5.4.3`,
  `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name`.
  Falls back to the email address if none is present.

## Verified: role sync (SAML custom attributes)

- Requires `sso_settings.enable_jit_provisioning: true`.
- Attributes: `FLEET_JIT_USER_ROLE_GLOBAL`, `FLEET_JIT_USER_ROLE_FLEET_<FLEET_ID>`.
- Accepted values: `admin`, `maintainer`, `observer`, `observer_plus`, `technician`, `null`.
- **Setting both a global and a fleet role causes an error at login.** A user is global or
  fleet-scoped, never both. This is the best edge case in the chapter.
- `null`, empty, whitespace-only, or an omitted `<saml:AttributeValue>` are all ignored.
- Multi-valued attributes: **Fleet uses the last value.**
- On login: account absent and attributes present, attributes win; account absent and
  attributes absent, Global Observer; account exists and attributes present, roles updated;
  account exists and attributes absent, **no role change attempted**.

## Verified: SCIM

- Base URL: `https://<fleet_url>/api/v1/fleet/scim`. Endpoints seen: `/scim`, `/scim/`,
  `/scim/details`, `/scim/users`.
- Auth: HTTP Header, using an **API-only user with admin permissions** and access to the
  `/scim/*` endpoints.
- Unique identifier field: `userName`.
- **Required attributes: `userName`, `givenName`, `familyName`.** `department` supported
  and optional.
- **Any other attribute causes Fleet to reject the payload.** Explicit in the guide: "If you
  use attributes other than the supported attributes above, the payload will be rejected."
  Notable and easy to hit, since IdPs map extra attributes by default.
- Fleet UI: **Settings > Integrations > Identity provider (IdP)**.
- Groups arrive via the IdP's push-groups mechanism.

### One discrepancy between the two Fleet docs, unresolved
`single-sign-on-sso.md` says Fleet requires `userName`, **`email`**, `givenName`,
`familyName` for deprovisioning. `foreign-vitals-map-idp-users-to-hosts.md` lists required
as `userName`, `givenName`, `familyName` and does not mention `email`.

Not resolved at this tag. The chapter names `userName`, `givenName`, `familyName` as
required (both docs agree) and notes email is mapped in practice. **Candidate Fleet
documentation bug**; log it with the others in PROJECT_STATUS.

## Verified: 2FA

- **Email 2FA exists for break-glass accounts.** Documented purpose is an account that can
  sign in when the IdP is unavailable.
- Fleet's stated best practice: SSO for everyone else, and enforce 2FA at the IdP.
- **You cannot change the authentication method of the account you are signed in as.**
  Another admin must do it, from Settings > Users.

## Where IdP vitals get collected
Automatically when an end user authenticates during enrollment: automatic enrollment for
Apple (macOS, iOS, iPadOS) and Windows; manual enrollment for Apple, Android, Windows, and
Linux. A host's IdP username can also be set by hand on the Host details page, and Fleet
maps the remaining vitals from it.

**Correction made during the merge.** The Codex draft advised against relying on a manual role
change as a durable exception for a role-synced account. That is true only when the identity
provider sends a role attribute for that person. When no attribute arrives, existing roles are
left alone, so a manual change persists. The chapter now states the condition rather than the
flat warning.

**Not adopted from the draft**, with reasons: the vocabulary table was kept, because a reader
new to Fleet needs Fleet's meaning of four generically familiar terms; "SCIM does two different
jobs" was kept over "supports two independent outcomes" as the plainer phrasing; and the draft's
"For many organizations, the practical rollout sequence is ..." was not carried over, being the
same unsourced generalization it was written to replace (STYLE §25).

Diagnostics the draft dropped and the merge retained: the email-shaped-account-name symptom of a
missing name attribute, the reason `null` exists, the constraint behind the second-administrator
step for the recovery account, and that trimming the SCIM attribute mapping is required rather
than tidying.
