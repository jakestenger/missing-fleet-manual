## Additions

### 1. A 4.90.1 fix that produces a §8.9.9 symptom with no §8.9.9 cause

**Stated**, from the 4.90.1 changelog and the diff of `server/service/microsoft_mdm.go` between the two tags.

Before 4.90.1, a removed Windows profile stayed listed under Host details, OS settings, when every `LocURI` it had covered was still enforced by another profile on the same host. The reconciler's own new comment says why the row never cleared: "there is no `<Delete>` to send and no command ack will ever arrive to clean these rows up." 4.90.1 collects those host rows and deletes them directly. It affects deleting a profile, renaming one, and transferring a host between fleets that both carry a matching profile.

The reason it belongs in this chapter rather than only in a version note is what it does to the reader following §8.9.4. That table's "no row at all" line sends them to the reconcile cron and to scoping. Both come back clean, because nothing was ever queued and nothing was supposed to be. Added under the version table with the reading spelled out: on 4.90.0 and earlier the profile is genuinely gone and only its row is left.

### 2. Certificate renewal is advertised in the provisioning document and is not implemented

**Stated, twice, a few lines apart in Fleet's own source.**

`server/mdm/microsoft/syncml/syncml.go` sets `WstepROBOSupport = "true"` with the comment "Provisioning Doc Server supports ROBO auto certificate renewal", immediately followed by `// TODO: Add renewal support`. `server/mdm/microsoft/wstep.go`'s interface carries a matching TODO listing "certificate lifecycle management (e.g., renewal, revocation)" as unimplemented.

**Deliberately not derived into a prediction.** Certificates are 365 day certificates and the renewal advertisement is live, but what a Windows device actually does as expiry approaches, and whether Fleet's enrollment endpoint happens to serve a renewal request as an ordinary enrollment, is not established anywhere at this tag. Asserting that devices fall off at day 365 would be exactly the correct-reading-wrong-inference failure §27 describes.

What the chapter now says instead is a monitoring instruction, which is defensible on the stated facts alone: a Windows MDM deployment approaching its first anniversary is in undocumented territory, so watch the client-side renewal values on the oldest enrollments, and remember that an expired device certificate and a broken fleetd wake are indistinguishable from the server. Both show queue rows with `acked_at` NULL and no `windows_mdm_responses`. §8.9.8's thumbprint comparison already separates them, and the addition points at it.

## Not verifiable at this tag

- **SyncML status codes and session alert codes** in §8.9.5 are OMA-DM's, not Fleet's. The chapter cites Microsoft's open specification for them. Two values that do appear in Fleet's source were confirmed incidentally (`CmdAlertGeneric = "1226"` and the alert constants around it); the rest were not re-derived.
- **Entra licensing, MDM user scope, JWT audience versions, `dsregcmd`, the registry values, and OOBE diagnostics** are Microsoft's. The chapter attributes them and flags Fleet's own Autopilot documentation as stating its licensing claim as current understanding rather than verified, which is the right register.
- **`80180006`, `0x80180024`, `ZtdDeviceIsNotRegistered`** are Windows-side codes. `binarySecurityToken is empty` is Fleet's and was not re-grepped in this pass.
- **The Windows MDM command queue cleanup cron** is still unnamed. The chapter marks it unverified and that remains accurate: no schedule in Fleet's list is obviously it, and `cleanups_then_aggregation` carries a `cleanup_windows_mdm_command_queue` job, which 8.6 already records. Worth reconciling the two chapters on this when Part VIII gets its structural pass, since 8.6 has the answer 8.9 says it does not have.

## Carried out of this chapter

- **8.9 says the queue-cleanup cron name is undocumented; 8.6 names the job.** 8.6's `cleanups_then_aggregation` row lists `cleanup_windows_mdm_command_queue` among its jobs. That is a job inside a schedule rather than a schedule name, which is probably why the two chapters disagree in tone, but a reader who has read 8.6 will find 8.9's disclaimer confusing. One of them should defer to the other.
- The renewal gap is worth raising with Fleet directly rather than only recording. It is not a documentation error, so it is not on the running Fleet-issues tally; it is unfinished work that an operator cannot see from outside.

## Confirming review, 2026-08-27: NOT READY, now fully applied

Five findings had been skipped entirely and two applied only where the finding pointed. This pass closed all of them, and the self-check afterwards was to grep the chapter for every phrasing of each corrected claim rather than trusting the edit.

**The management authentication model, finished.** The two-path explanation had been added in one place while four others still said mTLS-only, including the blast-radius conclusion. `mTLS` now appears zero times in the chapter; the client certificate is described as one of two paths and as used at `/management` and nowhere else.

**Reserved LocURIs were wrong on two of three rows.** `fleetProvidedLocURIValidationMap` contains **only** BitLocker, and even that is waived when custom disk encryption is enabled. OS updates are handled on a separate path needing Premium and rejecting only when OS updates are already configured for that fleet. **RemoteWipe has no reserved-subtree check at all.** The chapter had presented all three as blanket refusals.

**`<Exec>`** is a valid top-level element, and LocURIs inside it are validated against the SCEP set, so it is not a general-purpose verb.

**fleetd 1.57.0 is the worst version to be on, and the chapter did not say so.** 1.57.0 advertises the on-demand sync capability, which moves the host to the 8 hour relaxed poll, and orbit's own changelog records that it "could not start on-demand Windows MDM sessions on some Windows hosts, leaving queued Windows MDM commands pending for up to 8 hours". 1.58.0 fixes it by recognising the enrollment by any non-zero `EnrollmentState`. So a fleet on 1.57.0 gets the relaxed-poll penalty with none of the wake benefit and presents exactly like a broken Orbit channel. Now a three-row version table, called out as the cheapest thing to rule out.

**The SCEP challenge advice was inverted by 4.90.1.** 4.89.0 added an upload-time rejection of challenges containing non-printable characters; **4.90.1 removed it**, because Apple devices enrol fine with them, and Fleet's notes say the Windows-side fix ships separately. The chapter told the reader Fleet validates the challenge and to re-enter it. Corrected, including that the Windows failure is unfixed at this release.

**`verified` means less on Windows than on Apple.** For ordinary profiles Fleet maps any successful SyncML response to `verified`, including `202 Accepted`, with no read-back. Added, along with the 4.90.1 exception: Fleet-proxied SCEP profiles now report `verified` only once Fleet observes the certificate on the host, and `failed` on an upstream error or a certificate still missing an hour after delivery.

**Two queue claims.** The `acked_at` NULL with a status code pair is not a transitional state, because the result write and the ack are one transaction, so seeing it is a finding. And `has_pending_commands = 1` does not mean wake requests are reaching the host, since the sync request is gated on the capability and on the setup-experience path.

**The queue cleanup job is documented after all**, and the chapter had said otherwise while 8.6 named it. It is `cleanup_windows_mdm_command_queue` inside `cleanups_then_aggregation`, retaining one hour. The two chapters now agree, which closes the discrepancy recorded in the previous ledger entry.

**Withdrawn rather than corrected.** The claim that Fleet parses ADMX fragments and compares them semantically is **not established**: an equality helper exists with no production call sites found. Both instances now say so. This is the right outcome for a claim that cannot be verified either way, and it was appearing twice, once as a stated mechanism and once as a diagnostic conclusion built on it.

**Registry `EnrollmentState`** no longer publishes the Graph-beta numeric mapping. Non-zero means enrolled, which is what fleetd itself reads; the individual values are marked unverified.

**Added:** the Windows MDM diagnostics report (`mdmdiagnosticstool.exe`), which is the Windows counterpart to a sysdiagnose and the artifact to request when you have no access to the device. Both device-side surfaces are now in the summary table.

## Second confirming review, 2026-08-27: NOT READY, now applied

The substantive corrections from both prior rounds were confirmed sound, including the whole authentication model, the certificate dates, the reserved LocURIs, the SCEP release behaviour and the fleetd version table. What remained was **three internal contradictions created by partial replacement**, plus a command that does not run.

**Two places still described the wake as unconditional.** §8.9.2's hop 5 and the delivery table's hop 4 both presented "fleetd is told to sync" as something that simply happens, while a paragraph forty lines later correctly named both gates. The sync request is returned only when the host's fleetd advertises the on-demand capability **and** the host is not part-way through the setup experience, which takes precedence while `awaiting_configuration` is pending or active. Both passages now carry the condition, and the delivery table says outright that an absent sync request is the expected reading on a host that does not qualify.

**The queue table sent the reader to a verification stage that does not exist.** For `acked_at` set with status `200` it said "if the setting still reads wrong on the device, the problem is verification, not delivery" — while §8.9.9 correctly explains that an ordinary Windows profile has no read-back at all and `verified` means only that the device returned a 2xx. The row now says what that combination actually means: Fleet took the device's word for it, the two disagree, and the host is the only place that can settle it.

**The ADMX correction had been applied twice, in consecutive paragraphs**, which is a different symptom of the same habit: replacing each instance of a claim independently and never reading the result. Consolidated into one statement of what is not established plus the two consequences that follow from it.

**`mdmdiagnosticstool.exe` was not executable as written.** PowerShell treats the semicolons in `-area DeviceEnrollment;DeviceProvisioning;Autopilot` as statement separators, so the value has to be quoted. Fixed in the code fence and in the summary table, which carried the same broken form.

**The device-initiated framing appeared six times.** It is the chapter's organising fact and belongs at the top; the three restatements that added nothing are now either pointers or the parts that were actually new — that Fleet cannot reach a device whose agent is silent, and that no single expiring credential can take the estate quiet at once, which is the Apple shape and not this one.
