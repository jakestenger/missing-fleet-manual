## Additions

### 1. A 4.90.1 fix that produces a §8.9.9 symptom with no §8.9.9 cause

**Stated**, from the 4.90.1 changelog and the diff of `server/service/microsoft_mdm.go` between the two tags.

Before 4.90.1, a removed Windows profile stayed listed under Host details, OS settings, when every `LocURI` it had covered was still enforced by another profile on the same host. The reconciler's own new comment says why the row never cleared: "there is no `<Delete>` to send and no command ack will ever arrive to clean these rows up." 4.90.1 collects those host rows and deletes them directly. It affects deleting a profile, renaming one, and transferring a host between fleets that both carry a matching profile.

The reason it belongs in this chapter rather than only in a version note is what it does to the reader following §8.9.4. That table's "no row at all" line sends them to the reconcile cron and to scoping. Both come back clean, because nothing was ever queued and nothing was supposed to be. Added under the version table with the reading spelled out: on 4.90.0 and earlier the profile is genuinely gone and only its row is left.

### 2. Certificate renewal is advertised in the provisioning document and is not implemented

**Stated, twice, a few lines apart in Fleet's own source.**

`server/mdm/microsoft/syncml/syncml.go` sets `WstepROBOSupport = "true"` with the comment "Provisioning Doc Server supports ROBO auto certificate renewal", immediately followed by `// TODO: Add renewal support`. `server/mdm/microsoft/wstep.go`'s interface carries a matching TODO listing "certificate lifecycle management (e.g., renewal, revocation)" as unimplemented.

**Deliberately not derived into a prediction.** Certificates are 365 day certificates and the renewal advertisement is live, but what a Windows device actually does as expiry approaches, and whether Fleet's enrollment endpoint happens to serve a renewal request as an ordinary enrollment, is not established anywhere at this tag. Asserting that devices fall off at day 365 would be exactly the correct-reading-wrong-inference failure §27 describes.

What the chapter now says instead is a monitoring instruction, which is defensible on the stated facts alone: a Windows MDM deployment approaching its first anniversary is in undocumented territory, so watch the client-side renewal values on the oldest enrollments, and remember that an expired device certificate and a broken fleetd wake are indistinguishable from the server. Both show queue rows with `acked_at` NULL and no `windows_mdm_responses`. §8.9.8's thumbprint comparison already separates them, and the addition points at it.

## Not verifiable at this tag

- **SyncML status codes and session alert codes** in §8.9.5 are OMA-DM's, not Fleet's. The chapter cites Microsoft's open specification for them. Two values that do appear in Fleet's source were confirmed incidentally (`CmdAlertGeneric = "1226"` and the alert constants around it); the rest were not re-derived.
- **Entra licensing, MDM user scope, JWT audience versions, `dsregcmd`, the registry values, and OOBE diagnostics** are Microsoft's. The chapter attributes them and flags Fleet's own Autopilot documentation as stating its licensing claim as current understanding rather than verified, which is the right register.
- **`80180006`, `0x80180024`, `ZtdDeviceIsNotRegistered`** are Windows-side codes. `binarySecurityToken is empty` is Fleet's and was not re-grepped in this pass.
- **The Windows MDM command queue cleanup cron** is still unnamed. The chapter marks it unverified and that remains accurate: no schedule in Fleet's list is obviously it, and `cleanups_then_aggregation` carries a `cleanup_windows_mdm_command_queue` job, which 8.6 already records. Worth reconciling the two chapters on this when Part VIII gets its structural pass, since 8.6 has the answer 8.9 says it does not have.

## Carried out of this chapter

- **8.9 says the queue-cleanup cron name is undocumented; 8.6 names the job.** 8.6's `cleanups_then_aggregation` row lists `cleanup_windows_mdm_command_queue` among its jobs. That is a job inside a schedule rather than a schedule name, which is probably why the two chapters disagree in tone, but a reader who has read 8.6 will find 8.9's disclaimer confusing. One of them should defer to the other.
- The renewal gap is worth raising with Fleet directly rather than only recording. It is not a documentation error, so it is not on the running Fleet-issues tally; it is unfinished work that an operator cannot see from outside.
