### Corrected: scheduling a report does not build history in Fleet

As published: "Schedule that report to run on a cadence and you build a historical record of how
that state changed across the estate."

`docs/Get started/FAQ.md:405`: "Currently, Fleet only stores the current state of your hosts",
with the recommendation to export via the API or `fleetctl` to maintain history. A scheduled
report delivers results to the configured log destination; the history accumulates there, not in
Fleet. The chapter now says so and points at 2.5, which owns the destination decision.

This appeared in chapter 1.1, describing the product's core value, and an administrator could
have designed a retention approach around it.

Also removed the unqualified "ten thousand machines ... in seconds". Live reports reach hosts
that are online, and response time varies.

### Corrected: fleetd is a bundle, and the chapter treated its contents as peers

`docs/Get started/anatomy.md:10-14`: fleetd contains osquery, Orbit, and the fleetd Chrome
extension, with Fleet Desktop shipping alongside. The chapter used fleetd, osquery and Orbit
interchangeably and called Orbit "Fleet's agent". Vocabulary now established before the
components are described. Orbit is now described as what it is, an osquery version and
configuration manager that also performs host-side work.

## Correction applied 2026-08-27

**The fleetd bundle's contents, and Fleet Desktop's optionality.** The chapter said the bundle contains "osquery, Orbit, and the fleetd Chrome extension", with Fleet Desktop "alongside". Two things wrong with that, both found while applying 3.7's review rather than by reading this chapter:

- **The Chrome extension is not in the bundle.** *Fleetd for Chrome* is a separate browser extension for the one platform where the bundle does not exist, carrying no Orbit, no osqueryd and no Fleet Desktop. Describing it as bundle content implies a Mac's fleetd contains a Chrome extension.
- **Fleet Desktop is inside the bundle and optional**, which is how Fleet's own `high-level-architecture.md` describes it, and `fleetctl package --fleet-desktop` puts it there.

Corrected here, in 1.2, in 3.1 and in 3.7, which had the same two framings between them.

## Part I re-review, 2026-08-27

NOT READY, with seven factual defects. Where 1.2's defects were universals that only held on a fleetd Mac, 1.1's are **tidy framings that survived because they sounded right**: reading half and writing half, expected state over there and actual state over here, missing capability means the OS cannot do it. Each was a sentence someone would quote approvingly, and each was wrong in a way that changes what an administrator does.

### Corrections applied

| Claim as written | Why it was wrong | Basis |
|---|---|---|
| A scheduled report "does not accumulate a record inside Fleet; it delivers results to whatever log destination you have configured" | Wrong twice. Fleet does store the newest result per host per query, overwriting the previous one, unless `query_reports_disabled`, the query's `discard_data`, non-snapshot logging or the row cap stops it. And delivery to the destination happens **only for queries with automations enabled**, a column that defaults to off. Replaced with a three-row table separating storage, forwarding and activity audit | `server/service/osquery.go` result submission path; `overwriteResultRows`; `automations_enabled` default in `schema.sql`; `DefaultMaxQueryReportRows = 1000` |
| The link for report history pointed at 2.5 | 2.5 covers activity-audit delivery, which is configured independently of the osquery result stream. Reworded so the link is to the delivery machinery rather than an answer to the question | `server/config/config.go`: `osquery.result_log_plugin` against `activity.audit_log_plugin` |
| Fleet's stored data called "current state" throughout | It is the latest thing a host reported, carrying its own fetch timestamp. An offline host shows values it may have stopped being true weeks ago. Reworded, and the first foundational question now says "when it last reported" | `server/fleet/queries.go` `last_fetched`; overwrite-newest behaviour |
| The platform table gave one "Device-management path" per platform | It collapsed two genuinely different paths on macOS and Windows, and put scripts and software in the same cell as MDM. Scripts need an Orbit node key; installer-based software runs the Orbit installation flow. Split into an agent action path and a platform-management path, with the diagnostic consequence stated | `server/service/scripts.go`; `docs/Contributing/architecture/software/software-installation.md` |
| Fleet authenticates administrators against the IdP "rather than maintaining a second directory" | Fleet keeps a `users` row per administrator with an `sso_enabled` flag, and the SSO callback rejects an email it does not already hold as an SSO-enabled user. Premium JIT provisioning changes *when* the account is created, not whether one exists. Roles, sessions and API tokens are Fleet's | `server/service/sessions.go`; the users and SSO-flag migrations |
| ChromeOS row said "Extension management" and "nothing installed on the device at all" | The extension must be force-installed through Google Admin and stays Google's to manage; Fleet does not manage ChromeOS. "No native fleetd bundle" is the accurate phrasing | `ee/fleetd-chrome/README.md`; `articles/chrome-os.md` |
| IT asset systems hold expected state, Fleet holds actual state | Fleet holds a great deal of desired state, every profile, policy and setting, and it carries device-to-person mapping including IdP-derived end users. Narrowed to commercial authority: procurement, ownership, contracts, lifecycle | `docs/REST API/rest-api.md` host user mapping; `high-level-architecture.md` |
| "Assume a missing capability means the platform offers no mechanism" | Assumes the least likely of four explanations. Replaced with an ordered four-way check: OS mechanism, Fleet implementation at this release, edition, prerequisites. The Chrome extension is the clean counterexample, since it implements live reports and not scheduled ones, which is Fleet's boundary rather than Google's | `ee/fleetd-chrome/src/background.ts`; `articles/chrome-os.md` limitations |
| "Fleet does not implement it; the operating system does" | Reads as "Fleet does not implement MDM", which is false. The OS supplies the client; Fleet implements the server: enrollment, profile and command construction, the queue, result handling | `docs/Contributing/architecture/mdm/mdm-overview.md` |

### Additions

A fourth foundational question, **did the device receive and apply it**, with the state ladder desired, queued, delivered, applied, verified. The audit entry is written when a request is successfully queued, so audit proves you asked and nothing more; this was the reviewer's clearest structural point and the one that most changes how the chapter reads against Part VIII.

An explicit statement that the platform table is not an edition promise, with the shape of Fleet's licence gating named: fleets are Premium, software installation is Premium, scripts exist on Free but fleet-scoped execution does not, profile gating splits again by fleet, label, variables and content, and MDM command gates are per command. There is no single rule to learn, which is exactly why a.2 needs to exist.

### Unsourced claims removed

"Almost certainly" two tools and they "rarely" agree; "nearly everything else" serving the reading or writing half, which ignored identity, enrollment, audit and service operation; live results "usually quickly" and osquery answering "in seconds"; configuration management being "frequently" the right owner; "deliberately incurious" and "intentionally designed", which state product intent as fact and are contradicted by how much identity, desired state and result history Fleet actually holds.

### And one I introduced while fixing 1.2

Writing the platform matrix into 1.2 I put the Chrome extension against all three osquery columns. It uses exactly three Fleet endpoints, enroll and distributed read and distributed write, with no config fetch and no logger upload, which is the mechanical reason scheduled queries do not work there. Corrected within the hour, but it is the session's recurring shape: **the correction to a wrong universal is a new claim, and it needs checking like any other.**
