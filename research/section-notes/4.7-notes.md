## Corrected from the first draft

1. **"It is global."** `additional_queries` and `detail_query_overrides` are per-fleet, but only
   through the GitOps fleets spec. The fleets PATCH endpoint accepts a `features` object and acts
   on a narrow subset that excludes them, so a per-fleet override set through the API is accepted
   and does nothing. That is a worse trap than the global claim, and the chapter now names it.
2. **The raw `extensions.load` path was presented as a supported side door.** Orbit owns that file
   and rewrites it from configuration, truncating it to empty and restarting osquery when no
   extensions are configured. The advice would have produced an extension that vanished at the
   next reconciliation.
3. **Three extension platform tokens.** Orbit resolves six. The three in the chapter came from the
   struct's documentation comment, which is incomplete relative to its own code.
4. **The hierarchy was missing two rungs.** Automatic table construction creates a genuine custom
   table from a SQLite file with no code at all, which is exactly the gap between configuration
   and programming that the chapter claimed did not exist. Custom host vitals belong at the top,
   for data that is not on the device to begin with.
5. **The screenshot brief** asked for `additional` values on a host's Vitals card. The storage is a
   JSON blob on the host record and the rendering surface was never established, so the brief was
   withdrawn rather than guessed at.

## Derived

**The five-step hierarchy** is the chapter's organising structure and is editorial. The ordering is
defensible from the mechanisms, but Fleet does not present these as a ranked list anywhere.

**"The mistake this chapter exists to prevent is reaching for the heaviest one first."** Editorial.

**"An override must return exactly the columns the original returned."** Follows necessarily from
the ingestion function being retained while the SQL is replaced. Stated as a rule because the
consequence of getting it wrong is silent.

**The uses and non-uses of `additional_queries`** are editorial. Fleet imposes no such distinction.

**The three questions to ask before writing an extension** are editorial.

## Deliberately not stated

**No extension-writing tutorial.** The structure conversation concluded that building osquery
plugins is too specialised to occupy a seventh of Fleet's reading half, and it is osquery's
subject rather than Fleet's. The chapter covers what Fleet does with an extension once it exists
and what you are signing up for, and sends the reader elsewhere for the code.

**No claim about where `additional` data appears in the interface.** The storage is established;
which surfaces render it was not. The first draft's screenshot brief assumed the Vitals card and
has been withdrawn. **Flag for a later round**: if a surface renders it, the chapter should say so,
and if none does, the chapter should say that instead, because it changes whether the mechanism is
useful to a reader who does not script against the API.

**No claim that extensions are subject to the watchdog.** The first draft asserted it. osquery's
watchdog governs the worker process, and whether an extension in its own process is covered was not
established at the tag. Removed rather than hedged.

**No claim about extension signing requirements.** Platform code-signing policy is not Fleet's, and
the tag does not establish what orbit requires.

**No FIM or YARA configuration detail.** The keys are named as existing. Their semantics are
osquery's, and doing them properly is a chapter's worth of material that belongs with log
destinations rather than here.

**No TUF channel names.** Establishing which channels exist is a moving target and belongs with
agent updates in 3.8.
