### certs.pem / fleet.pem / osquery.db — confirmed
- `orbit/pkg/packaging/packaging.go:381` `//go:embed certs.pem` -> `var OsqueryCerts []byte`;
  `writeOsqueryCertPEM` writes `<orbitRoot>/certs.pem` mode `0o644`. Comment: "Embed the certs
  file that osquery uses so that we can drop it into our installation packages. This file is
  generated and updated by .github/workflows/update-certs.yml."
- `orbit/cmd/orbit/orbit.go:1030-1045`: if `--fleet-certificate` set, that path is loaded,
  `certificate.ValidateConnection` is called (logs "Failed to connect to Fleet server. Osquery
  connection may fail." on error, does NOT abort), and passed as `--tls_server_certs <path>`.
  Else falls back to `<root-dir>/certs.pem` if it exists; if absent, logs
  "No cert chain available. Relying on system store."  <-- so orbit itself does NOT hard-fail
  without certs.pem; only `orbit shell` does (see shell.go:183, error "cert not found at ...").

  https://curl.se/docs/caextract.html, embedded into the `fleetctl` binary, written at package
  time. orbit + Fleet Desktop use the system CA store by default; osqueryd cannot, so it needs
  the file. `--fleet-certificate` makes all three use that CA only. Bundled cert installs to
  `/opt/orbit` (macOS/Linux) and `C:\Program Files\Orbit` (Windows).
- `orbit/cmd/orbit/orbit.go:820`: `osqueryDB := filepath.Join(root-dir, "osquery.db")`,

- Also `update.pem` on Windows for `--update-tls-certificate`.

### Hardware-migration reset (orbit.go 840-900), macOS only
On darwin, orbit reads UUID into a temp osquery DB (to dodge a cached UUID) and compares to
`hardware-uuid.txt`. On mismatch it logs "detected hardware migration", deletes
`hardware-uuid.txt`, `osquery.db`, `secret-orbit-node-key.txt`, and `identifier`, then exits
with "found a new hardware uuid, restarting" so re-enrollment happens on restart.
Refs: fleetdm/fleet#17934, osquery/osquery#7509, fleetdm/fleet#31934.
Orbit also kills pre-existing `osqueryd` processes at startup (orphan cleanup, Windows has no SIGTERM).

### TUF auto-updates (orbit/pkg/update/*, orbit/cmd/orbit/orbit.go flags)
- `update.DefaultURL = "https://updates.fleetdm.com"` (`orbit/pkg/update/update.go:57`).
  Old URL `https://tuf.fleetctl.com` (`OldFleetTUFURL`), migrated at orbit 1.38.0+.
- Local TUF metadata file: `updates-metadata.json` (`MetadataFileName`), previously
  `tuf-metadata.json` (`OldMetadataFileName`). Packages built with fleetctl 4.63.0+ ship both
  (same content) to allow downgrade to orbit <=1.37.0.
- Root keys are **pinned in the orbit binary** (`defaultRootMetadata`, a full TUF root.json with
  ed25519 keys, threshold 1 per role, `consistent_snapshot:false`). So trust is bootstrapped from
  the binary, not from the network.
- Library: `github.com/theupdateframework/go-tuf` (`client`, `data`, `verify`).
- Subdirs of the orbit root used by the updater: `bin` and `staging`
  (`binDir = "bin"`, `stagingDir = "staging"`, update.go:34-36).
- Default root dir on macOS: `/opt/orbit` (`orbit/pkg/update/options_darwin.go`).
- TUF target names: `orbit`, `osqueryd`, `desktop` (+ macOS-only `nudge`, `swiftDialog`,
  `escrowBuddy` per orbit/TUF.md).
- Channels: three independent flags, each defaulting to `stable`:
  `--orbit-channel` / `ORBIT_ORBIT_CHANNEL`, `--osqueryd-channel` / `ORBIT_OSQUERYD_CHANNEL`,
  `--desktop-channel` / `ORBIT_DESKTOP_CHANNEL`.
- `--update-interval` / `ORBIT_UPDATE_INTERVAL`, **default 15 minutes**. Flag usage text
  (verbatim): "How often to check for updates. Note: fleetd checks for updates at startup. The
  next update check adds some randomization and may take up to 10 minutes longer".
- `--disable-updates` / `ORBIT_DISABLE_UPDATES` turns auto-update off entirely.
- `--update-url` / `ORBIT_UPDATE_URL`; `--update-tls-certificate` / `ORBIT_UPDATE_TLS_CERTIFICATE`
  (written as `/opt/orbit/update.pem`); mTLS to the update server via
  `update_client.crt` / `update_client.key`.
- Signature expiry: `RunnerOptions.SignaturesExpiredAtStartup`. If `root`, `targets`, or
  `snapshot` signatures are expired at startup, go-tuf refuses to load targets; the Runner then
  only re-checks expiry each interval and exits when valid so the next orbit start initialises
  normally. An expired `timestamp` role does not block startup. (runner.go:30-40)
- If there is no local TUF snapshot (`client.ErrNoLocalSnapshot`), the runner skips the local-hash
  optimisation, which causes one unnecessary orbit auto-update but lets orbit start when the TUF
  server is unreachable. (runner.go:120-130)
- If a tracked target's channel does not exist remotely (`client.ErrNotFound`), the target is
  skipped rather than erroring. (runner.go:135-142)
- `orbit/TUF.md` is auto-generated by `make fleetd-tuf` and lists currently deployed versions.
  At origin/main: stable and edge both orbit/desktop 1.59.0, osqueryd 5.23.1; macOS-only
  nudge 1.1.10.81462, swiftDialog 2.5.6, escrowBuddy 1.0.0 on stable only.
- `--enroll-secret-path` usage (verbatim): "Path to file containing enroll secret. On macOS and
  Windows, this file will be deleted and secret will be stored in the system keystore".
  So `secret.txt` is transient on macOS/Windows. `ORBIT_DISABLE_KEYSTORE` opts out.

### Channel pinning via agent options (`docs/Configuration/agent-configuration.md` §update_channels, origin/main)
- `agent_options.update_channels` with keys `orbit`, `osqueryd`, `desktop`. **Fleet Premium only.**
- Omitted component => `stable`.
- A channel value can be a **literal version string** (e.g. `osqueryd: '5.10.2'`), which is how you
  pin. Fleet will apply it even if that means a downgrade (doc example: packaged at orbit 1.53.1,
  enrolled with `update_channels.orbit: 1.50.0` -> downgrades).
- If a configured channel does not exist in TUF, fleetd logs errors on the host and does not
  auto-update that component until the channel is valid or someone pushes the component to it.
- Removing `update_channels` from agent options leaves devices on their last configured channels.
- If Fleet Desktop is disabled in fleetd, the `desktop` channel setting is ignored by the host.
- Orbit < 1.38.1 cannot upgrade directly past the tuf.fleetctl.com -> updates.fleetdm.com move.
  Log line documented: `update failed error="lookup failed: lookup orbit: tuf: file not found`.
  Path is: upgrade to 1.38.1 first, wait, then go newer.
- Documented **auto-update startup loop**: fleetd with orbit < 1.20.0 packaged on channel A;
  channel A moves to >= 1.20.0; agent options then set orbit to channel B holding < 1.20.0. Orbit
  starts, changes channel, restarts, repeats. Fix by moving A below 1.20.0 or B to >= 1.20.0.
  This is delivered by `server-overrides.json` (see constant.go).

### Orbit API channel timing (client/orbit_client.go, origin/main)
- `defaultOrbitConfigReceiverInterval = 30 * time.Second` -> confirms 8.1's "30s config receivers".
- Endpoint: `POST /api/fleet/orbit/config`.
- `configCacheTTL = 3 * time.Second` (GetConfig is cached so multiple receivers in one tick share
  one request).
- On network error or HTTP 5xx: one retry after `configRetryOnNetworkError = 30s`
  (`retry.WithMaxAttempts(2)`).
- Sustained failure: exponential backoff from 30s up to `maxConfigBackoff = 5 * time.Minute`,
  ticker reset each cycle; logs "running config receivers, backing off" with `next_retry`, and
  "config receivers succeeded, exiting backoff" on recovery. (issue #45553)
- Network errors are log-rate-limited to once per `netErrInterval = 5 * time.Minute`.
- `downloadStallTimeout = 60 * time.Second` bounds a software-installer download that makes no
  progress; resets on any received bytes.
- `unauthenticatedReenrollGracePeriod = 45 * time.Second`.
- `ssoWindowReopenInterval = 5 * time.Minute`.
- Enroll retry env override: `FLEETD_ENROLL_RETRY_INTERVAL`.

### Host online/offline definition (server side)
`server/datastore/mysql/hosts.go:1721` and `server/chart/internal/types/chart.go:57`: a host counts
as online when `seen_time + LEAST(distributed_interval, config_tls_refresh) + fleet.OnlineIntervalBuffer`
is in the future. So Fleet's "online" is derived from **osquery channels only** (channels 1 and 2),
never from the Orbit API or MDM. Good grounding for "is the host online?" being ill-formed.

### Fleet Desktop token
- `token.NewReadWriter(<root-dir>/identifier, deviceClient.CheckToken)`, `LoadOrGenerate()`.
- Rotated periodically via `trw.StartRotation()`; rotation is unconditional now, not
  Desktop-only. Source comment: "Always keep the device identifier (e.g. /opt/orbit/identifier)
  up to date with periodic rotation, so it's valid for refetch-host, device auth, and Fleet
  Desktop when enabled."
- On startup, if the token is expired or `CheckToken` fails AND the server is reachable, it rotates.
  If the server is unreachable the rotation is skipped (`serverIsReachable := orbitClient.Ping() == nil`).
- `trw.SetRemoteUpdateFunc` pushes the token to the server (`SetOrUpdateDeviceToken`), only if the
  server supports it.

### Process supervision: oklog/run group (orbit/cmd/orbit/orbit.go)
Orbit runs its subsystems in a single `oklog/run.Group` (`addSubsystem`, orbit.go:2528).
Named subsystems, in registration order: "system checker", "update runner", "insecure proxy",
"httpsig localhost proxy", "config receivers", "osqueryd runner", "capabilities checker",
"desktop runner", "signal handler", "osqueryd extension runner".
oklog/run semantics: the first actor to return interrupts all the others and `g.Run()` returns.
So **when osqueryd exits, orbit exits too** ("unexpected exit" is logged), and the platform service
manager restarts the whole bundle: launchd `KeepAlive`+`ThrottleInterval 10` on macOS,
`Restart=always` `RestartSec=1` on Linux, Windows service failure actions restart with a 1s delay.
Inferred from source (oklog/run behaviour + the service definitions), not from docs.

### osqueryd process handling (orbit/pkg/osquery/osquery.go)
- `NewRunner` errors with `osqueryd doesn't exist at path %q` if the binary is missing.
- On construction it removes a leftover extension socket ("In some cases it's not cleaned up
  properly by osquery before exit").
- Extension socket: `<dataPath>/orbit-osquery.em` on macOS/Linux, named pipe
  `\\.\pipe\orbit-osquery-extension` on Windows.
- `--pidfile=<dataPath>/osquery.pid`, `--extensions_socket=<socket>`, `--logger_path=<path>`.
- Shutdown: `proc.WaitOrKill(ctx, 10*time.Second)` -> graceful stop then kill after 10s.
- Runner is single-use: "The process may not be restarted after exit. Instead create a new one."

### `orbit_info` osquery extension table
Orbit registers its own osquery extension over that socket (`registerExtensionRunner`,
`table.WithExtension(orbit_info.New(...))`, orbit.go:1494-1509) exposing orbit channel, osqueryd
channel, desktop channel, desktop version, device token, start time, scripts-enabled, and the
update server URL. This is how Orbit state becomes queryable through osquery.

### Fleet Desktop process
- Executable name `fleet-desktop`; on macOS launched from
  `<desktopPath>/Contents/MacOS/fleet-desktop` (an app bundle).
- Started only when `--fleet-desktop` / `ORBIT_FLEET_DESKTOP` is set. On other platforms the flag
  usage text says "flag currently only used on darwin" (stale text; Linux/Windows Desktop exist,
  see desktopRunner registration which is not darwin-gated).
- Desktop runner errors are pushed to Fleet as `fleet.FleetdError` with `Vital: true`,
  `ErrorSource: "fleet-desktop"`, via `deviceClient.ReportError(<device token>, err)`. Vital errors
  are sent regardless of `FLEET_ENABLE_POST_CLIENT_DEBUG_ERRORS`.
- `executeFleetDesktopWithPermanentError` sleeps 5 minutes so the end user can read the message.

### docs/Contributing/architecture/high-level-architecture.md (origin/main)
fleetd = orbit + osqueryd + Fleet Desktop (Desktop called "optional"). Edges in the mermaid diagram,
which is the cleanest statement of the channel model:
- `orbit -- "Fleet Orbit API" --> fleet_server`
- `orbit -- "Auto update all fleetd components" --> tuf`
- `desktop -- "Fleet Desktop API" --> fleet_server`
- `osqueryd -- "osquery remote API" --> fleet_server`
- `orbit -- "starts" --> desktop`, `orbit -- "starts" --> osqueryd`
- `desktop -- "opens" --> desktop_browser`, `desktop_browser -- "My Device API" --> fleet_server`
- `mdm_client -- "MDM Protocol (OS Specific)" --> fleet_server`  (the OS MDM client, not fleetd)
- `osqueryd -- "mdm_bridge table (Windows)" --> mdm_client`
- `orbit -- "Calls MDM Registration APIs (Windows)" --> mdm_client`
Key structural point confirmed: the MDM channel is spoken by the **operating system's** MDM client,
not by fleetd. fleetd only pokes it (Windows registration APIs, `mdm_bridge` table).
Also: S3/object storage for software installers and carve results; Redis for live query results.

### ChromeOS: fleetd Chrome extension (`ee/fleetd-chrome/README.md`, origin/main)
A Chrome extension with a **service worker** (debug via `chrome://serviceworker-internals/?devtools`
in production, `chrome://extensions` in development). Built with npm; packaged as an unpacked
extension in `./dist`. Config is `FLEET_URL` + `FLEET_ENROLL_SECRET`; the Fleet URL must have a
valid TLS certificate. No orbit, no osqueryd binary. Enrollment doc pointer:

### Android: no fleetd, no osquery
- Management is entirely **AMAPI** (Android Management API) plus **Google Cloud Pub/Sub** for
  device-originated notifications (`docs/Contributing/architecture/high-level-architecture.md`,
  `docs/Contributing/product-groups/mdm/android-mdm.md`). By default Fleet server reaches AMAPI
  through a **fleetdm.com proxy**, which limits each Fleet server URL to one Android enterprise.
  Enterprise ID format `LCxxxxxxxx`, stored in `android_enterprises.enterprise_id`.
- There IS a separate **Fleet Android agent** app (`android/`, package `com.fleetdm.agent`,
  Kotlin/Gradle, distributed through managed Google Play). It is NOT fleetd. Its scope, per
  `docs/Contributing/product-groups/security-compliance/android-certificates.md` and `android/README.md`:
  read **managed configuration**, enroll to Fleet for an `orbit_node_key` using the enroll secret,
  then fetch certificate payloads (`GET /api/fleetd/certificates/:id`) and do **SCEP** (generate
  private key, build CSR, retrieve cert from the SCEP URL, store cert + key in the keystore),
  with up to 3 retries.
- Notable: the default Android policy does NOT contain the agent; a `SoftwareWorker` installs it
  afterwards with managed config.
- App start triggers: install (Android Device Policy assigns the `COMPANION_APP` role, handled by
  `RoleNotificationReceiverService`), `ACTION_BOOT_COMPLETED` (`BootReceiver`), and a worker
  **every 15 minutes**.
- Server config for the agent: `FLEET_MDM_ANDROID_AGENT_PACKAGE` /
  `FLEET_MDM_ANDROID_AGENT_SIGNING_SHA256`, or YAML `mdm.android_agent.package` /
  `mdm.android_agent.signing_sha256`.
- Known limitations (documented): Fleet server URL must be public for Pub/Sub; the URL cannot
  change once set, because Pub/Sub is configured with one URL (issue #29878).

### Disk encryption split (docs/Contributing/architecture/mdm/disk-encryption.md, origin/main)
Grounds the "which component owns this" boundary rule nicely:
- **macOS FileVault**: MDM profile (two payloads: encryption config + escrow config). The key lands
  on disk at `/var/db/filevaultprk.dat` and Fleet reads it **through osquery** as part of vitals.
  Newer path uses Escrow Buddy (`fleet.CapabilityEscrowBuddy`); the older orbit-side
  `DiskEncryptionRunner` steps aside when the server advertises that capability
  (`orbit/pkg/update/disk_encryption.go`, `maxRetries = 2`). Server verifies decryptability on an
  hourly cron.
- **Windows BitLocker**: **orbit** does the work. Server sets
  `notifs.EnforceBitLockerEncryption` in the Orbit config; orbit creates TPM + Numerical Password
  protectors and encrypts the OS volume, or on an already-encrypted disk adds a new Numerical
  Password protector, removes old recovery-key protectors, ensures the TPM protector exists (the
  disk is never decrypted). Key is posted to
  `POST /api/fleet/orbit/disk_encryption_key`. Status is read from osquery's `bitlocker_info`
  (`conversion_status` + `protection_status`); encrypted-but-protection-off shows "Action required".
  Requires a working TPM. Useful registry query given in the doc:
  `SELECT * FROM registry WHERE path LIKE 'HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\FVE\%%';`
  Clean-slate command: `manage-bde -off C:`.
- **Linux LUKS2**: orbit + Fleet Desktop only. Fleet never enables encryption; it escrows a key for
  hosts that already had LUKS2 enabled at install (Ubuntu, Kubuntu, Fedora). Server sets
  `notifs.RunDiskEncryptionEscrow`; Fleet Desktop prompts the user for their passphrase, orbit uses
  it to create a new keyslot with an orbit-generated random passphrase and escrows that.
  Receiver: `luks.New(orbitClient)` (orbit.go:1323).

### Update runner startup sequence (orbit.go 680-790)
1. `update.NewUpdater(opt)`, then `updater.UpdateMetadata()` (failure is logged, not fatal).
2. `updater.SignaturesExpired()` -> `signaturesExpiredAtStartup`.
3. Targets tracked: `orbit`, `osqueryd`, plus `desktop` when `--fleet-desktop`. In `--dev-mode`
   orbit excludes itself.
4. **Early update check before any subsystem starts**: `updateRunner.UpdateAction()`. If it
   updated anything, orbit logs "exiting due to successful early update" and exits so the service
   manager restarts it on the new binaries. Comment: "This is to prevent bugs in other sub-systems
   to mess up with the download of available updates."
5. Fetching targets retries **forever** at a 5 minute interval (`retrypkg.WithInterval(5*time.Minute)`,
   no max attempts); `updater.Get` has its own backoff. Comment notes this replaced older behaviour
   where the first failure returned an error and restarted orbit.
6. With `--disable-updates`: `update.NewDisabled(opt)`; if osqueryd cannot be located locally orbit
   calls `log.Fatal()` and dies. So a bad `--disable-updates` package is fatal, not degraded.
7. Old TUF URL rewrite: if `--update-url` is the old `https://tuf.fleetctl.com`, orbit 1.38.0+
   silently rewrites it to `https://updates.fleetdm.com` (orbit.go ~628).
8. Windows-only: `osservice.SetupServiceManagement(constant.SystemServiceName, ...)` plus a
   "system checker" subsystem, wired up before anything else.

### Update loop and update-failure behaviour (orbit/pkg/update/runner.go, update.go, selfheal.go)
- `Runner.Execute` randomises the **first** interval only: `initialInterval = CheckInterval +
  rand(0, min(CheckInterval, 10 min))`, "so that all agents don't synchronize their updates".
  Subsequent ticks use the plain `CheckInterval`.
- On a successful update the runner logs "exiting due to successful update" and returns, which via
  oklog/run tears down all of orbit; the service manager restarts it on the new binaries.
- On failure it logs "update failed" (log.Info level) and keeps looping. Not fatal.
- `UpdateAction` compares the local file hash against the TUF metadata hash. It also checks whether
  the orbit symlink needs updating (channel change). On Windows a symlink-only update is suppressed
  when the binary itself is unchanged.
- Partial failure is possible: "If it returns (true, non-nil error) then it means some target/s were
  successfully upgraded and some failed to upgrade."
- `UpdateMetadata` failure is explicitly non-fatal: "it will be common to be offline or otherwise
  unable to retrieve the metadata."
- Download retry policy: `retry.NewLimitedWithCooldown(3, 24*time.Hour)` (update.go:193).
  **3 attempts, then a 24 hour cooldown** for that target. The retry key is the TUF target's
  content hash, so a new version published to TUF is downloaded immediately without waiting out the
  cooldown. During cooldown you get `ExcessRetriesError`: "max retries exceeded, retrying again in
  <d>" wrapped as "skipped getting target: ...". See `pkg/retry/limited_with_cooldown.go`.
- Self-heal (`orbit/pkg/update/selfheal.go`): `CheckExec` runs the installed binary
  (`CustomCheckExec` if defined, otherwise `<binary> --help`). On failure `RemoveTarget` deletes the
  extracted directory, the downloaded archive, and the cached `.sha512` hash, so the next `Get`
  re-downloads from TUF rather than re-extracting a possibly-corrupt archive. Log line: "removed
  corrupt target for re-download".

### How the bundle reaches an Apple host (the half-enrolled state mechanism)
- `server/worker/apple_mdm.go:579` `installFleetd` sends
  `InstallEnterpriseApplication` with `manifestURL = fleetdbase.GetPKGManifestURL()` =
  `https://download.fleetdm.com/stable/fleetd-base-manifest.plist`
  (`pkg/fleetdbase/fleetd_base.go`; override `FLEET_DEV_DOWNLOAD_FLEETDM_URL`).
  The manifest holds the pkg checksum and the download URL. `meta.json` at
  `<base>/stable/meta.json` carries `fleetd_base_msi_url`, `fleetd_base_pkg_url`, their sha256s,
  `fleetd_base_manifest_plist_url`, and `version`.
- Apple requires apps installed via `InstallEnterpriseApplication` to be **signed**; an unsigned
  fleetd-base pkg cannot be installed during the ADE flow
  (`docs/Contributing/getting-started/testing-and-local-development.md:888`).
- So: MDM enrollment and agent installation are two different things carried by two different
  channels. That is the structural reason the half-enrolled state exists. Detection and recovery
  live in 8.4; the mechanism is here.
- Bootstrap package uses the same command but with an **embedded** manifest
  (`InstallEnterpriseApplicationWithEmbeddedManifest`, worker/apple_mdm.go:769), from Fleet's own
  URL or a signed CloudFront URL. Status enum `MDMBootstrapPackageStatus`:
  `installed` (Acknowledged), `failed` (Error), `pending` (anything else / no response)
  (`server/fleet/hosts.go:150-161`). Same failure mode, different payload.

### fleetd-base installers and `--use-system-configuration` (macOS)
- fleetd-base pkg/msi have no baked-in `--fleet-url` or `--enroll-secret`
  (`docs/Contributing/getting-started/testing-and-local-development.md:847-890`). Signed builds live
  at `https://download.fleetdm.com` (dev: `https://download-testing.fleetdm.com`).
- Peculiarities, verbatim from the doc: pkg installers require `--use-system-configuration` and read
  config from a configuration profile; msi installers need dummy values and read config at install
  time (`msiexec /i fleetd-base.msi FLEET_URL="..." FLEET_SECRET="..."`).
- The macOS config profile is `PayloadIdentifier` **`com.fleetdm.fleetd.config`**
  (`server/mdm/apple/mobileconfig/mobileconfig.go:34`, const `FleetdConfigPayloadIdentifier`),
  carrying `FleetURL`, `EnrollSecret`, `EnableScripts` (`server/fleet/apple_mdm.go:618-624`,
  `MDMAppleFleetdConfig`).
- With `--use-system-configuration`, orbit **blocks in a loop** reading that profile
  (`profiles.GetFleetdConfig`, orbit.go:499-570): on success it writes `secret.txt` and
  `fleet_url.txt` into the root dir; otherwise it falls back to those files and the keystore; if
  still empty it logs "didn't find configuration values in system profile, trying again in 30
  seconds" and sleeps 30s. Forever. So a macOS host with fleetd installed but no config profile
  sits in this loop and never enrolls.
- `--host-identifier` accepts only `uuid` or `instance`; anything else is a startup error.
- Removing the enroll secret from the macOS MDM profile is tracked in issue #16118.

### `orbit shell` (orbit/cmd/orbit/shell.go)
- Runs its own osqueryd instance with a **separate** data path `<root-dir>/shell` and
  `--database_path <root-dir>/shell/osquery.db`, explicitly "to avoid issues with concurrent
  accesses to files/databases (RocksDB lock and/or Windows file locking)". On Windows the extension
  socket gets a random UUID suffix to avoid colliding with the service's named pipe.
- `getCertPath` **hard-fails**: uses `--fleet-certificate` if given, else `<root-dir>/certs.pem`;
  errors `cert not found at <path>` if missing, `invalid PEM format <path>` if unparseable. Confirms
  the prompt's claim: `orbit shell` requires the cert file even though the daemon degrades to the
  system store.
- In shell mode `orbit_info` is registered as an **empty stub** table whose text is
  `Please connect to orbit-osquery extension socket to query this table: ".connect <pipe>"`.
- Usage note: a trailing argument that does not start with `--` is treated as a single SQL statement.
- Docs reference `sudo orbit shell` as the way to list all available osquery settings
  (`docs/Configuration/agent-configuration.md`).

### osquery.flags reconciliation (orbit/pkg/update/flag_runner.go, docs/Configuration/agent-configuration.md)
- File is `<root-dir>/osquery.flags`, passed to osquery as the flagfile (orbit.go:1430); written at
  package time by `packaging.go:369` from `--osquery-flagfile`.
- Two-tier agent options: `options` apply **without a fleetd restart**; `command_line_flags` apply
  **only on fleetd restart**. Full lists are generated in `server/fleet/agent_options_generated.go`.
- Precedence, verbatim from the docs: "If `command_line_flags` isn't present in your agent options,
  Fleet leaves each host's osquery flags as they are... If `command_line_flags` is set to `{}` or
  `null`, Fleet clears all local osquery flags on your hosts. On each host, fleetd empties the
  `osquery.flags` file and restarts osquery without those flags." Matches the `len(config.Flags) == 0`
  early return in `FlagRunner.Run`.
- Orbit compares the parsed server flag map to the parsed on-disk map with `reflect.DeepEqual` and
  only writes (and restarts) when they differ.
- Flags added by orbit **after** the flagfile cannot be overridden from the flagfile
  (`--extensions_autoload` is placed deliberately after `--flagfile`).
- osquery's own watchdog is configurable through agent options
  (`disable_watchdog`, `watchdog_memory_limit`, `watchdog_utilization_limit`, `watchdog_level`,
  `watchdog_delay`, `watchdog_forced_shutdown_delay`, `watchdog_latency_limit`,
  `enable_watchdog_debug`, `enable_extensions_watchdog` in `agent_options_generated.go`).
  Fleet sets none of them by default (they are absent from `FleetFlags`), so osquery defaults apply.
  The watchdog is internal to osqueryd: the osqueryd watcher process kills and restarts its own
  worker, so orbit is not involved and does not exit. Inferred from source plus osquery's documented
  watchdog design; not stated in Fleet docs.

### desktopRunner supervision (orbit/cmd/orbit/orbit.go 1980-2110)
- Orbit runs as root (Unix) or SYSTEM (Windows service). Fleet Desktop must run as the **logged-in
  GUI user** to register its tray icon, so orbit launches it through `pkg/execuser`.
- Start loop retries every **30s** until a GUI user exists (`user.UserLoggedInViaGui`). On macOS
  launching with no GUI session is an OS-level error (issue #14698); on Linux orbit also waits for a
  GUI session; on Windows `execuser.Run` picks the GUI user itself.
- Before each start it kills pre-existing `fleet-desktop` processes
  (`platform.SignalProcessBeforeTerminate`).
- Monitor loop polls **every 15s** with `platform.GetProcessesByName("fleet-desktop")`; when the
  process is gone it falls back to the start loop. So Fleet Desktop is supervised by orbit, not by
  the OS service manager.
- Environment handed to Desktop: `FLEET_DESKTOP_FLEET_URL`,
  `FLEET_DESKTOP_DEVICE_IDENTIFIER_PATH` (the `identifier` file),
  `FLEET_DESKTOP_DEVICE_URL` (legacy), `FLEET_DESKTOP_FLEET_TLS_CLIENT_CERTIFICATE`,
  `FLEET_DESKTOP_FLEET_TLS_CLIENT_KEY`, `FLEET_DESKTOP_ALTERNATIVE_BROWSER_HOST`,
  `FLEET_DESKTOP_TUF_UPDATE_ROOT`, `FLEET_DESKTOP_FLEET_ROOT_CA`, `FLEET_DESKTOP_INSECURE`.
- My Device URL shape: `<fleetURL>/device/<device token>` (built from `trw.GetCached()`).
