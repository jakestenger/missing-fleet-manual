## Corrections made in this pass

### 1. The websocket path was missing its last segment

**Stated.** `server/service/client_live_query.go` connects to `/api/latest/fleet/results/websocket`. The chapter gave `GET /api/latest/fleet/results`.

This is a small string and it lands in the worst possible place. The chapter's own §8.7.4 says websockets are load bearing and that "infrastructure that drops or does not upgrade websocket connections breaks live reports while leaving the rest of Fleet working". The reader most likely to need that path is writing an ingress rule or grepping an access log for it, and the path as printed matches nothing.

### 2. `fleetctl` does not use the endpoint the chapter names

**Stated.** `client_live_query.go` posts to `/api/latest/fleet/reports/run_by_identifiers`. `server/service/handler.go` registers three campaign-creation routes: `POST .../reports/run`, `POST .../reports/run_by_identifiers`, and `POST .../reports/run_by_names`.

The chapter described the generic `reports/run` for a flow it then illustrates with `fleetctl`. Both are real; they are not the same path, and someone matching an access log against the chapter would not find the CLI's traffic. All three paths are now named together, with which caller uses which.

### 3. The status line format put the wrong number on top of the second fraction

**Stated.** The format string is `" %.f%% responded (%.f%% online) | %d/%d targeted hosts (%d/%d online)"` with arguments `percentTotal, percentOnline, responded, total, responded, online`.

So the last fraction is **responded over online**, not "online over online" as the chapter had it. Corrected, shown as a real rendered line rather than a schema, and the consequence spelled out because it is the useful part: `--exit` waits on `responded >= online`, so a run can exit successfully having heard from 42 percent of the hosts you targeted. That is the same sampling caveat §8.7.2 makes, arriving at the moment a reader is most likely to take the number at face value.

Also completed the targeting error to the full string, `No hosts or labels targeted. Please provide either --hosts or --labels.`

## Checked and deliberately not claimed

**Fleet's 4.90.0 release notes call `POST /api/v1/fleet/reports/run` "the asynchronous live query endpoint".** At the tag, `POST` on that path is `createDistributedQueryCampaignEndpoint`, the campaign creation this chapter describes, and it is `GET` on the same path that maps to `runLiveQueryEndpoint`. On its face the changelog names the wrong verb.

I have not written that down as a Fleet documentation error, because the changelog entry is specifically about adding the endpoint to the catalog that API-only users' endpoint allowlists are built from, and how that catalog spells an entry is a separate question from how the router registers it. Establishing which is right needs the catalog itself, and the claim would be exactly the correct-reading-wrong-inference failure §27 describes. Recorded so it is not re-derived from scratch, and so it is not quietly promoted into the chapter later.
