## The six roles (verbatim from the guide)

| Role | Tier | What the guide says |
|---|---|---|
| **Admin** | Free | "receive all permissions" |
| **Maintainer** | Free | Manages most entities. **Cannot** edit application configuration, fleets, or users |
| **Technician** | **Premium** | Run scripts, view their results, install/uninstall software |
| **Observer** | Free | Read-only. Can run reports with `observer_can_run: true` |
| **Observer+** | **Premium** | Observer plus the ability to run *any* report |
| **GitOps** | **Premium** | **API-only and write-only**, for CI/CD pipelines |

The same six names exist at global scope and at fleet scope. Scope changes reach, not the
role's meaning.

## Findings worth putting in the chapter

**GitOps is write-only.** It is the only role that cannot read most of what it writes. This
is a deliberate CI/CD shape and surprises people who try to use the token to check state.

**Observer can read secrets at fleet scope.** The fleet-level table gives Observer a tick on
"View disk encryption key for macOS hosts" and "View Recovery Lock password for macOS hosts".
Read-only includes reading recovery secrets. Worth stating plainly; administrators assume
read-only means harmless.

**Fleet-level users see global report results only for hosts in fleets they can access.**
Verbatim footnote: "Fleet-level users only see global report results for hosts on fleets
where they have access."

**Technician is narrow and specific.** Scripts and software, not configuration. It is the
role for a help desk.

## API-only users

- UI: **Settings > Users > Create user**, select **API-only**.
- CLI: `fleetctl user create --name 'API User' --api-only`
- `--email` and `--password` are **optional** for API-only users. If omitted Fleet generates
  an email derived from the creator's address, and the user authenticates by token only.
- **The token is shown once** ("will not be shown again"). It can be retrieved later through
  the log in API.
- Premium: `--fleet <fleet_id>:<role>` scopes an API-only user to one fleet.

### Endpoint restriction narrows, never widens
An API-only user can optionally be restricted to a specific list of API endpoints. Verbatim:
this "narrows access without expanding permissions beyond the user's role (for example, a
team admin granted access to the Update configuration endpoint will still receive a `403`
response, because that endpoint is restricted to global admins)."

Good precedence fact: role and restriction are ANDed. The narrower wins.

## 2026-08-25 review pass: Technician scope and API-only defaults

Independent review on `gpt-5.6-sol`. Three corrections, all verified at `fleet-v4.90.1`.

### Corrected: Technician is not a narrow role

As published: "can run scripts, view their results, and install or uninstall software. **Nothing
else.** It is a deliberately narrow role, and it is the natural fit for a help desk."

Its *write* surface is that narrow. Its read surface is not. From the permissions tables in
`articles/role-based-access.md`, Technician within scope can also view all hosts, all software,
all activity, all policies, all reports and their results, users, organization settings, saved
scripts, custom variables and MDM command results; run any report as a live report against all
hosts; run all policies; and **view disk encryption keys for macOS, Windows and Linux hosts and
the macOS Recovery Lock password**.

The published wording could lead an administrator to grant Technician to a help desk in the
belief that it cannot read recovery credentials. It can. The section is rewritten to cover both
Observer and Technician, and the role summaries are now explicitly marked non-exhaustive.

### Corrected: the API-only creation example produced the wrong identity

The example was `fleetctl user create --name 'API User' --api-only`, with no role. With neither
a global role nor a fleet specified, `cmd/fleetctl/fleetctl/user.go:103` assigns
`fleet.RoleObserver`. So the documented command for creating automation identities silently
produced a global observer, which after the correction above is a more privileged outcome than
the text implied. The example now sets `--global-role gitops` and the default is called out.

### Corrected: two claims about tokens

| Claim as published | Status |
|---|---|
| A lost token "can be retrieved again through the log in API, so this is recoverable rather than fatal" | **Wrong.** An API-only identity created without a password cannot sign in, so there is no path back to a lost token. Replacement is deletion and recreation |
| "one expired credential away from having no reachable administrator" | **Wrong mechanism.** API-only tokens do not expire: `server/service/sessions.go:914-915` sets `sessionDuration = 0` with the comment "make API-only tokens unlimited", and `articles/fleetctl.md:121` states the same. The risk is loss, not lapse |

The second is now stated as a loss, and the chapter gains the fact that regular tokens expire
while API-only tokens do not, which is Fleet's own reason for recommending them for automation.

### Not adopted: endpoint restrictions as a Premium capability

The review stated that endpoint restrictions are Premium-gated, citing a guard in
`server/service/users.go`. Could not confirm. `APIOnlyEndpoints` and `api_only_endpoints` return
nothing across `server/` and `ee/`, and `articles/fleetctl.md:129`, the only place the behaviour
is documented, carries no Premium marker. **Left unstated rather than asserted in either
direction.** Worth resolving before the next release pass.
