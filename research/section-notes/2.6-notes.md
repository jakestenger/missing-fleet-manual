## The finding that became the chapter's spine

**MDM's real ongoing cost is credential renewal, and the burden differs in kind by platform,
not just in degree.** The previous draft said "administrators who own platform credentials and
renewal" in passing. That sentence is the chapter.

### Apple, verbatim from `articles/apple-mdm-setup.md`

> Apple requires that APNs certificates are renewed annually.

> If your certificate expires, you must turn MDM off and back on for all Apple hosts. If this
> happens, configuration profile changes and other MDM work do not reach those devices.

> When renewing, be sure to use the same Apple ID from year-to-year. If you don't, you will
> have to turn MDM off and back on for all Apple hosts.

Two separate routes to the same estate-wide failure: letting it lapse, **and renewing it
correctly but under a different Apple ID.** The second is the non-obvious one, and it is the
basis for the chapter's point that this credential belongs to the organization rather than to
a person.

Apple Business Manager tokens expire independently. Fleet shows a warning banner from 30 days
out, and marks status in a **Renew date** column: yellow under 30 days, distinct treatment
once expired.

### Windows
`articles/windows-mdm-setup.md`. Fleet is configured with a certificate and key pair that
**you generate yourself** for WSTEP. The documented example uses a long validity. No external
issuer, so no renewal relationship with a vendor. Deliberately did not state a specific
lifetime in the chapter, because the operator chooses it.

### Android
Binding is to an enterprise, tied to the Fleet server URL, which must be publicly reachable
and cannot be changed after enrollment begins. Carried forward from the 1.2 research rather
than re-derived.

## Public endpoint exposure
`articles/what-api-endpoints-to-expose-to-the-public-internet.md`. Three model-level facts
kept; the path lists themselves routed to `a.8` under §17.

1. The required set **grows with the features you enable**: automatic enrollment, IdP
   authentication during setup, EULA, bootstrap package and Platform SSO each add paths.
2. **Two Apple paths sit outside the `/api` prefix**, and the guide says why: they are not
   RESTful and are not intended for API clients or browsers. A proxy rule assuming everything
   lives under `/api` misses them.
3. **Windows uses four distinct Microsoft protocols** (management, discovery, policy, and
   WSTEP token enrollment) plus a terms-of-service path required for automatic enrollment.

## Platform paths
macOS, iOS and iPadOS via Apple MDM; Windows via OMA-DM; Android via the Android Management
API; ChromeOS via extension management; **Linux has no platform MDM protocol at all**.

## Deliberately left out

- **The endpoint path lists.** Reference material, `a.8` owns it (§17). The chapter states the
  three properties that change a network design decision and points there.
- **A Windows certificate lifetime.** The setup guide's example command uses one value, but
  the operator picks it, so stating a number would read as a requirement.
- **VPP token expiry.** No article matched at this tag under the names searched; not claimed.
- **Whether MDM can be enabled per fleet rather than organization-wide.** Not established, and
  the chapter does not assert either way.

### Corrected: the opening claimed Fleet does not implement device management

As published: "Fleet does not implement device management."

Fleet implements the server side of both the Apple and Windows MDM protocols. What it does not
ship is a management agent, because the operating systems already carry one. The published
sentence would tell a prospective customer something false, and the very next paragraphs
contradict it with the Linux and ChromeOS exceptions. Android does not fit the shape at all,
since Fleet drives Google's management API rather than talking to the device.

Rewritten to say what is true: no agent of Fleet's own, Fleet implements the server side, Android
is the exception.
