# 1.6 The Fleet server, citation ledger


## Part I re-review, 2026-08-27

NOT READY, nine factual defects and a long list of unsupported frequency claims. The chapter's architecture is sound; what it got wrong was almost entirely **the reassuring half of each statement**. Redis loss costs a retry. Hosts buffer during an upgrade. Object loss means re-uploading. Redis drops data silently. In every case the comforting version was true of the common path and false of the case that would hurt you.

| Claim as written | Why it was wrong |
|---|---|
| Losing Redis "costs you a retry, not a fact", and Redis "needs no backup" | Pending failing-policy notification recipients live in Redis sets and are **not reconstructed** if lost before delivery. Fleet's recorded server errors are Redis data too, so an outage erases the evidence of itself. With asynchronous host processing on, Redis also carries pending last-seen, label, policy and query-stat updates. Redis still is not a system of record; "costs a retry" is still too comfortable |
| Hosts "buffer during the window and replay", so an upgrade costs freshness | Fleet's guarantee is about **host logs**, not every device workflow, and every instance must be down for the migration. Fleet's own Apple guidance says an **ADE enrollment in progress can fail outright** during an upgrade, with the remedy being a remote wipe or a physical Recovery reinstall. Do not schedule upgrade windows across provisioning |
| Desired and observed state "never meet directly" | They meet on policy results. When a policy starts failing, Fleet drives scripts, conditional access, VPP and software installs off that observation and registers the webhook. That is the loop closing, and it is why a script can run on a host nobody asked about |
| The in-process cache holds "the application configuration, a fleet's agent options and features" | Also packs, scheduled queries, fleet and default-fleet MDM configuration, query lookups and result counts, YARA rules, MDM assets and Fleet-maintained app names, with expirations to fifteen minutes, plus a separate live-query cache. A stale pack or MDM asset has the same shape as the agent-options case and is not fixed by looking at agent options |
| Four artifact types fall back with no bucket | Five. Organisation logos use the software-installers bucket and fall back to MySQL, and they are the ones left off a migration plan |
| Object loss is repaired by "re-uploading" | True for installers, false for **file carves**, which can live in object storage, were uploaded by the reporting host, and cannot be re-supplied by anyone. If the object goes, reconciliation marks the carve expired. Carve storage belongs in retention and DR requirements |
| "Redis drops the data. Nothing errors." | Fleet returns errors from failed publishes and from publishing with no subscriber, logs receive errors, and deliberately emits an interruption error the interface depends on. The evidence exists; what misleads is the *shape*, since fewer hosts than targeted reads as coverage rather than Redis |
| A half-filled replica section "fails in ways that look like a broken replica" | Two different outcomes. An empty replica **address** means Fleet configures no replica at all and every read goes to the primary, silently, while the replica you are paying for receives nothing. Only a set-but-wrong address gives the broken-replica symptoms |
| "Fleet has no down-migrations" | Migrations can and do carry `Down` functions. What is true is that **Fleet exposes no supported rollback**: the CLI runs forward migrations only, so production rollback means restoring |

### Licence

The no-bucket table needed the gate stated in front of it. Software installers, software title icons and Apple bootstrap packages are all **Premium**, and their stores are constructed only under a Premium licence, so on Free three of the five rows describe artifacts you cannot create. File carves and organisation logos are not gated, and carve storage is initialised outside the Premium block. **Seventh licence defect this session.**

### Frequency claims

The largest sweep of the session: "overwhelmingly", "nearly every request", "most" inconsistent-change reports, carves growing MySQL "particularly" quickly, "far more" reads than writes, "before anything else", "bites first", "most misdiagnosed", "often rename", "the most debugging time", "usually tell", "usually the first thing noticed", and "the only estimate that means anything". Also two design rationales asserted as fact, that live-report coordination is "worthless sixty seconds later" (Fleet gives live-query metadata a seven-day TTL) and that destructive error reads exist "because it bounds memory", and two deployment-dependent absolutes about local storage being lost outright on restart.

## Second round, 2026-08-27

NOT READY. Eight defects introduced or preserved by the corrections, and one reviewer retraction.

| The new claim | Why it was wrong |
|---|---|
| "They meet in exactly one place" | The opposite universal again, in the same sentence that fixed "never meet". The policy-result loop is established; its uniqueness across every Fleet workflow is not |
| A stale **MDM asset** offered as an example of cross-instance cache staleness | Wrong, and the reviewer retracted its own supporting claim here. MDM assets are cached with the **checksum in the cache key**, and Fleet fetches current hashes each time, so an updated asset never reads from the old entry. It is now named as the exception, since looking for a cache-expiry problem there is a dead end |
| "The database-backed **two**" | A splice created by adding organisation logos as a third database-backed row, three lines above |
| Redis unavailability described as data destruction | Three passages conflated **Redis being unreachable** with **Redis losing what it held**. Pending notifications survive an outage and do not survive a flush. "Plan Redis maintenance as a small deliberate data loss" asserted something about how the reader runs Redis that no source establishes. Now a two-column table |
| The local-storage qualification | Applied at one line and left standing in three others as "do not survive a second instance at all", "never shared", and "hold no durable local state". Sharing and persistence both depend on the deployment, since operator-selected directories are permitted |
| "Potentially a bricked setup" | Stronger than Apple's source, which says failed or stuck enrollment that may need a wipe or a Recovery reinstall |
| The failover paragraph | Imported the upgrade section's buffering and ADE caveats into a different failure mode. Those are documented for the upgrade procedure specifically. Failover cost is a property of your database topology, and this manual does not establish it |
| Lines claiming all durable state is in the three stores | The **server private key** lives in the server's configuration, is required for MDM and sensitive settings, and decrypts material held in MySQL. It is neither in the three stores nor recoverable from them, which 2.12 says explicitly |

**The state-model image carries both of the original false summaries**, "loss costs a retry" for Redis and "loss costs a re-upload" for object storage, and the chapter now retracts both. Marked `IMAGE-REGENERATE` with the corrected summaries recorded in the comment. That is the second image in Part I found to be asserting something the prose has withdrawn, which is what the new checker exists for.

## Fourth round, 2026-08-27

NOT READY, four items, three of them my own corrections stopping short.

The Redis table separating unavailability from data loss was right, and **the sentence summarising it and the bullet in the failure list both still said an outage destroys things**. Corrected: an outage costs a retry, stored errors survive it and are readable afterwards, and what you cannot get is a record of the outage itself.

Organisation logos went into the object-storage inventory and left the following sentence calling every object there "big, immutable". Logos and title icons are uploaded, replaced and deleted through the ordinary interface.

The server private key was named in the opening as the fourth thing production must plan for and **left out of the ownership list at the end of the chapter**, which is the list somebody actually works from. Added, with the reason: it is what makes a MySQL restore readable.
