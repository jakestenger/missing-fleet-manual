# 4.1 Understand host data, vitals, and inventory, citation ledger

First draft, 2026-08-27, against `fleet-v4.90.1` (dd0200f062). Structure agreed with the reviewer before drafting; see `research/part4-structure.md`.

## Derived

**"That fixed set is what vitals means."** The source establishes the set and its ingestion; calling it the definition of vitals is the manual's framing, and it is the framing that makes the rest of the chapter work.

**The four-clocks table.** Each field and interval is source-checked individually. Presenting them as four clocks that can disagree is derived, though it follows directly from their being separate fields advanced by separate passes.

**"Online and stale at the same time."** Follows from `seen_time` and `detail_updated_at` being independent, plus 1.2's finding that any authenticated osquery request advances last-seen.

**The absence table.** The individual rows are source-backed; the ordering into "consistent with" readings is editorial.

## Unverified, and marked as such in the chapter

Nothing in this chapter is marked unverified. Two claims are deliberately bounded rather than asserted:

- The number of detail queries is **not** stated. The map contains around forty entries, but several are per-platform variants of one question and at least two (`tpm_pin_config_verify`, `tpm_pin_set_verify`) are conditional, so any count would be a claim about a number the reader would then check and find different. The chapter says "a fixed set" and names examples instead. **This is a deliberate departure from STYLE §26**, which asks that a stated count be enumerable: the fix here was to remove the count rather than to enumerate forty entries a reader does not need.
- The chapter does not say how often mobile device information is refetched. Apple's refetch runs on a Premium-only cron ([3.5](../../manual/03-connect-devices/3.5-enroll-ios-and-ipados-devices.md)), and stating an interval for it would need a separate check.

## Boundaries held

Enrollment mechanics stayed in Part III; the chapter links rather than restates. Single-host diagnosis stayed in 8.4 and log-level evidence in 8.2. The online definition stayed in 1.2 and is cited rather than repeated, which is deliberate: 1.2 took five rounds to get that definition right and it should have exactly one home.

## Review round, 2026-08-27

NOT READY, eighteen required changes, all applied. The chapter was substantially rewritten rather than patched, because the review's first three findings each took out one of its load-bearing claims.

### What the first draft got wrong

| The claim | What the source shows |
|---|---|
| Fleet asks a **fixed set** of detail queries, and that set is what vitals means | The set is assembled **per host**: features add and remove queries, platform restrictions apply, discovery queries decide whether a question is worth asking, some queries are generated dynamically, `additional_queries` are appended, and `detail_query_overrides` can remove Fleet's own. It is an implementation-dependent selection, not a contract |
| The Vitals card shows collected values | Fleet 4.90.1 has **custom host vitals**: administrator-defined, set per host through the API, shown in the same card, available on Free, selectable by host-vitals labels, and carrying **no timestamp**. The draft had no explanation for a value an administrator typed in |
| Four clocks | Six producers and at least six clocks. The draft missed `software_updated_at`, the Apple last-MDM-check-in time, the fact that **directly ingested inventories do not advance `detail_updated_at`**, and that custom vitals have no timestamp at all |
| A recent `detail_updated_at` means the host answered and had nothing to report | It advances when **at least one** ordinary detail result is ingested. It is not field-level proof. And a **failed query is skipped rather than ingested**, so it does not clear the value it failed to refresh: a two-minute-old timestamp can sit above a week-old value |
| Serial and UUID are what Fleet uses to recognise a returning device | Path-dependent. Fleet matches the osquery host identifier first; serial matching is for qualifying Apple MDM hosts; Android matches UUID separately; **Windows deliberately does not use serial matching**. Uniqueness is enforced only on the osquery host identifier, and Fleet's own source says serials are not unique |
| The platform token is what policies and reports are scoped against, and Fedora reads `rhel` | Three different vocabularies. The stored value is `rhel`; the policy and report selector is the generic `linux`; SQL against `os_version.platform` sees whatever osquery reports. Scoping a report to `rhel` is a validation error |
| Network interfaces give the addresses the host can see | Three separate fields. `primary_ip` and `primary_mac` are the default route's interface, selected one row at a time and not an inventory. **`public_ip` is the server's observation of where the request came from**, not a host report |
| The certificate list shows what a host trusts, read against `detail_updated_at` | macOS reads the system and login keychains; **Windows reads the Personal store, not trusted roots**. Presence is not a trust decision. Windows user certificates are visible only while that user's hive is loaded, so Fleet preserves unobserved scopes. Certificates can arrive from Apple MDM too, and the payload does not say which. And direct ingestion does not advance `detail_updated_at`, so that was the wrong clock |
| macOS, Windows and Linux have the "full reading surface" | False twice. A macOS or Windows host can be **MDM-enrolled without osquery**, which is a thin record by configuration rather than a fault. And detail queries are platform-restricted: the certificate queries are macOS and Windows only |
| A stale `label_updated_at` withholds profiles and software | **Dynamic labels only.** I established this in 1.3 and then failed to carry the qualifier into a new chapter, which is the propagation failure this project keeps producing |

### Licence gates the draft omitted

Five, and the reviewer noted that having no Premium or Free label anywhere was itself the signal:

- **iOS and iPadOS scheduled refetch is Premium.** On Free the cron is never registered, so mobile inventory does not refresh on its own. 3.5 already said this and 4.1 contradicted it.
- **Configuration-profile label scoping is Premium**, on both Apple and Windows.
- **Software deployment and its label targeting are Premium.**
- **Setting an identity-provider device mapping through the API is Premium**, while a custom mapping is not, so the two were not the equivalent operations the table implied.
- Fleet end-user authentication, the path that produces some identity-provider mappings, is Premium, though the mapping source has other origins and should not be labelled Premium wholesale.

Confirmed ungated: built-in detail inventory, `enable_host_users`, certificate listing, custom device mappings, and custom host vitals.

### Completeness, which was the question worth asking

The reviewer's judgement was that a reader would finish the first draft able to recognise the vocabulary but not to interpret a real host record safely, because the chapter offered confident shortcuts where it needed a field-by-field method. That is the finding that changed the chapter's shape: it now leads with the four questions to ask of any field, and carries a **worked method** section that applies them, rather than describing the record and trusting the reader to derive one.

### Boundaries confirmed

Enrollment matching detail stays in Part III and 1.3, with a summary here. Report result semantics go to 4.2, software enablement and coverage to 4.4, fleet-wide reading to 4.5, single-host diagnosis to Part VIII. The ChromeOS table list stays in 3.7.

### Departure from STYLE 26, retained

The chapter still does not state a count of detail queries, and the review did not object. The reason is now stronger than when I first made the call: the set is assembled per host, so there is no number that is true of every deployment, let alone of every host.

### Derived (reasoning, not just citation)

| Conclusion | Reasoning |
|---|---|
| "There is no new command, no new schedule and nothing to switch on" | The keys were added to the `<Queries>` array of an existing request type sent by existing senders. No new setting, feature flag or cron entry appears on either path. Stated as an absence found on the two send paths, not as an exhaustive search of the server |
| "A BYOD iPhone is not a device whose vitals failed to arrive" | Combines the two stated halves, the shorter request and the skipped load, into the operational reading. This is the reading the chapter's own method (question 2, "can this host produce it?") demands |
| "The two causes of an omitted field are indistinguishable" | `omitempty` erases the difference between a field never received and a field the device declined to report, because both leave the pointer nil. The eSIM example is the source's own, generalised |
| "Everything here dates from the last device information fetch, not `detail_updated_at`" | These fields are written by the DeviceInformation ack handler, not by the osquery detail path that advances `detail_updated_at`; iOS/iPadOS run no osquery at all, which the chapter already states. Consistent with the chapter's existing producer/clock table |
| Some requested keys (`SupplementalOSVersionExtra`, `WiFiMAC`, `IsMDMLostModeEnabled`) appear in both the BYOD and company-owned request lists | Read off the two lists. The chapter does not enumerate the BYOD nine, because the operational point is the asymmetry rather than the overlap; recorded here so a future editor is not surprised that three names appear on both sides |
