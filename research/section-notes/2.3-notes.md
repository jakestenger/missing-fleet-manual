## The GCP object storage finding

**This is the chapter's main correction and the ledger records it in full.**

`docs/Deploy/Reference-Architectures.md`, GCP section, states: "GCP support for add/install software and file carve features is coming soon." At this tag that is inaccurate in two separate ways.

| Evidence | Source |
|---|---|
| The GCP Terraform provisions a software installers bucket with an HMAC key and wires it into Cloud Run | `infrastructure/dogfood/terraform/gcp/storage.tf`; `cloud_run.tf:109-132` |
| Fleet reaches GCS through its S3 client: `FLEET_S3_SOFTWARE_INSTALLERS_ENDPOINT_URL=https://storage.googleapis.com`, `FORCE_S3_PATH_STYLE=true`, `REGION=auto` | `infrastructure/dogfood/terraform/gcp/cloud_run.tf:121-132` |
| Fleet has first-class GCS support, not merely accidental S3 compatibility: a `gcs` flag on the store and a GCS read-write scope constant | `server/datastore/s3/s3.go:29-41` |
| A documented workload identity path exists for both features: `s3.software_installers_gcs_iam_auth` and `s3.carves_gcs_iam_auth`, using Google Application Default Credentials instead of HMAC keys | `server/config/config.go:1630,1646`; `docs/Configuration/fleet-server-configuration.md:2857-2874, 3037-3054` |
| That option requires the Google endpoint URL and is incompatible with the access key, secret key and STS assume-role settings | `docs/Configuration/fleet-server-configuration.md:2861-2864` |
| On GCE, GKE or Cloud Run, ADC resolves to the workload identity via the metadata server | same, `:2866` |

So: **software installers and file carves both work on GCS**, with complete documented settings including a no-stored-secret option. What is actually absent is narrower: the published GCP Terraform provisions no carves bucket (`grep` for carves across `infrastructure/dogfood/terraform/gcp/` returns nothing), so carves fall back to MySQL on that architecture until an operator adds one.

**Candidate upstream documentation fix.** The "coming soon" sentence should either be removed or narrowed to say the reference Terraform does not yet provision a carves bucket. As written it would reasonably steer a reader off GCP entirely.

## Deliberately left out

- **The full AWS IAM policy JSON.** Reference material, and reproducing a 25-service wildcard policy in prose serves nobody. The chapter characterises it; anyone applying it should read Fleet's published copy.
- **The full sizing tables for both clouds.** 2.2 owns capacity and already carries the AWS pattern. The chapter uses the GCP figures only where they differ structurally from AWS.
- **Render.** `docs/Deploy/Reference-Architectures.md` documents a Render deployment via a community repository. It is neither AWS nor GCP, and the chapter title is specific; it belongs with 2.4 if anywhere.
- **Log destination plugin choice.** Canonical home is 2.8 per STYLE §18. The chapter keeps only the AWS cost consequence.
- **The three-store model, the single-writer constraint, and the sizing pattern.** Canonical to 1.6 and 2.2; referenced, not restated.
- **`infrastructure/loadtesting`.** Exists at the tag and is Fleet's own load-testing harness. Not deployment guidance, and not something an administrator would run against production.
- **GuardDuty and the other `infrastructure/` subdirectories.** Fleet's internal operational tooling rather than published reference architecture.

## 2026-08-25 correction: GCP availability posture

An independent review flagged the availability comparison as wrong. Re-checked at
`fleet-v4.90.1` and the review was correct.

| Claim as published | Status |
|---|---|
| "The GCP configurations specify a single node for each, including at 150,000 hosts. Redis in standalone mode and a single database instance are a working deployment, not a highly available one." | **Wrong for Redis, unverifiable for Cloud SQL. Corrected.** |

**Redis.** `infrastructure/dogfood/terraform/gcp/redis.tf:3` sets `tier = "STANDARD_HA"`, which
is Memorystore's high-availability tier: a replicated instance with automatic failover. The
`Nodes: 1` in the reference architecture table at `docs/Deploy/Reference-Architectures.md:379-388`
counts instances, not servers. The error was mine and it was an inference, not a misquote: I read
one node as meaning no failover. The published table is accurate; the conclusion drawn from it
was not.

**Cloud SQL.** `infrastructure/dogfood/terraform/gcp/mysql.tf` pins `zone = var.db_zone` and
delegates to `GoogleCloudPlatform/sql-db/google//modules/mysql` version `9.0.0` without setting
`availability_type`. That module is not vendored in this checkout, so its default cannot be
established from Fleet's published files. The chapter now says exactly that and names it as the
thing to confirm before treating the GCP reference as production-ready, rather than asserting a
posture in either direction.

**Also corrected in the same pass.** The IMAGE-TODO brief carried the withdrawn labels
("Cloud SQL MySQL 8, single node", "Memorystore Redis, standalone") and a caution mark on both
GCP dependency cells. Fixed before the image was generated; the caution mark now sits only on
Cloud SQL.

**Added.** File carves on GCP need their own bucket and their own credential choice, verified at
`server/config/config.go:1619-1646` (separate carve and installer settings, including separate
GCS IAM-auth flags). The chapter previously noted the Terraform provisions no carves bucket but
gave no action or verification. It now does both, and the verification section says that a
successful installer download proves nothing about the carve path.

**Declined from the same review**, recorded for completeness: a proposal to restructure the
chapter so a compact cloud comparison precedes the AWS material. The existing "not two
equivalent options" section already carries that comparison, and adding a table would duplicate
it. Revisit if the chapter grows.

## AWS deployment section added 2026-09-01

Reverses the prior "production-bootstrap deferred / reading-level" scope decision (owner approved 2026-09-01). New section "Stand up a production Fleet on AWS" gives the runnable deployment. Source: `fleetdm/fleet-terraform` (the Terraform module moved out of the monorepo; `fleet-public/terraform/` is a "Moved" stub at the tag). Fleet-server behaviour still verified against `fleet-public` at fleet-v4.90.1.

**Stated (verified against fleet-terraform, current `main` / the example's pins):**
- The root module deploys VPC + Aurora MySQL + ElastiCache Redis + ECS/Fargate service + ALB. Basis: `README.md` ("creates the VPC, database, cache, ECS cluster, ALB, and Fleet service stack") + `main.tf`, `variables.tf`.
- The canonical deployment is one `module "fleet"` block sourced `github.com/fleetdm/fleet-terraform?depth=1&ref=tf-mod-root-v1.30.0`, with `certificate_arn`, `vpc = { name }`, and `fleet_config = { image, autoscaling, mem, cpu, extra_environment_variables }`. Basis: `example/main.tf` (verbatim block; example uses `image = "fleetdm/fleet:v4.90.2"`, the chapter uses `v4.90.1` to match the book's target — the image tag is how the Fleet version is chosen).
- `required_version >= 1.12.0`, aws provider `>= 6.37.0`. Basis: `example/main.tf`, `example/README.md` Requirements.
- Deploy = edit locals, `terraform apply`; new Route 53 zone → add the `route53_name_servers` output's NS records to the parent zone. Basis: `example/README.md` "To deploy" + Outputs.
- Migrations run as a **separate ECS task via the migrations add-on** (`addons/migrations`, example pins `tf-mod-addon-migrations-v2.3.0`); the root also exposes `migration_config`. Basis: `example/README.md` Modules table; `variables.tf:1066`.
- `mem = 4096` (4 GB) for vulnerability scanning; 512 MB works without. Basis: `example/main.tf` comment.
- MDM add-on (`addons/mdm`) provisions SCEP material; optional. Basis: `example/main.tf` + `example/mdm-secrets.tf`.
- Two independent version pins: the module tag (`tf-mod-root-v*`) and the Fleet image tag. Basis: the two refs in `example/main.tf`.

**Derived (reasoned, flagged):**

Derived from the absence of any admin-creation input in the example and Fleet's standard first-run.
- "Until DNS delegation resolves, the ACM cert does not issue and the site is unreachable" — standard ACM DNS-validation behaviour combined with the example's NS-delegation step; not a line in the module.

**Unverified / notes:**
- The module versions (`tf-mod-root-v1.30.0`, `-addon-migrations-v2.3.0`, `-addon-mdm-v2.2.0`) are what the example currently pins; the exact version paired with Fleet 4.90.1 is not asserted — the chapter states the pinning *pattern* and that the module versions independently of Fleet, which is the honest and durable treatment of the "infra varies" concern.

## Round-3 fixes 2026-09-02 (M8, M9, m10)

**M8/m10 — reproducibility gaps in the new GCP "Stand up a reference deployment" section
(added 2026-09-02, R2-8):** the section told readers to apply from inside the GCP Terraform
directory without ever telling them how to get that directory (no `git clone`), and claimed
"three variables are required" when only `project_id` actually has no default. Fix: added a
pinned `git clone --branch fleet-v4.90.1` step, and corrected the variable-requirement claim —
`variables.tf` shows only `project_id` has no default; `dns_zone`/`dns_name` default to empty
strings that apply without error but leave DNS/cert provisioning nonfunctional, so they're
operationally (not syntactically) required; `prefix`/`image` already default to the values
shown. Also named the file (`terraform.tfvars`) so `-var-file` isn't needed. Basis:
`infrastructure/dogfood/terraform/gcp/variables.tf` at fleet-v4.90.1 (read directly).

**M9 — Cloud SQL availability-type claim, resolved:** the prior text said the external
`GoogleCloudPlatform/sql-db/google//modules/mysql` community module's default availability
type "is not determinable from Fleet's published files." Verified directly against that
module's own source at the pinned version (`v9.0.0`, matching `mysql.tf`'s `version = "9.0.0"`
pin): `variables.tf` defaults `availability_type` to `"REGIONAL"`. Fleet's `mysql.tf` never
sets `availability_type`, so the reference deployment gets a regional (HA) Cloud SQL instance
by default, not a zonal one — contradicting the round-3 gemini lens's speculative "ZONAL"
guess. This is the module's default, not Fleet's, so it can change on a module bump; the
chapter now says to confirm it against whichever module version is actually applied and gives
the explicit override (`availability_type = "REGIONAL"`) for readers who want it guaranteed.
Basis: `https://github.com/terraform-google-modules/terraform-google-sql-db` tag `v9.0.0`,
`modules/mysql/variables.tf:64-68` (external repo, fetched directly since the module isn't
vendored in `fleet-public`).

## Fix-loop round (2026-09-03, round5 C6 — GCP Terraform duplicate HCL attribute won't validate)

The GCP stand-up called the pinned dogfood tree a "worked, complete example" and went
straight to `terraform init` / `terraform apply`, but the tree does not pass `terraform
validate` as published. Verified against `infrastructure/dogfood/terraform/gcp/loadbalancer.tf`
at fleet-v4.90.1: `custom_request_headers = null` is set twice inside the single
`backends.default` object (once as `custom_request_headers  = null` near the top of the block,
line 37, two-space alignment; once again as `custom_request_headers = null` near
`security_policy`, line 54, one-space alignment). Terraform rejects the second as a redefined
argument. Dropped the word "complete", added a caveat that the tree needs a one-line fix to
parse, and added an explicit patch step before `terraform init`:
`sed -i.bak '/^      custom_request_headers = null$/d' loadbalancer.tf` (targets the single-space
line 54 only, leaving the two-space line 37) followed by `terraform validate`. Patch tested
against a copy of the pinned file: 2 occurrences -> 1, remaining line is the intended one.

## Fix-loop round (2026-09-03, round5 m16 — GCP per-instance memory misstated)

Prose said the GCP per-instance allocation is "one CPU and two gigabytes". Verified against
`infrastructure/dogfood/terraform/gcp/variables.tf` at fleet-v4.90.1: `fleet_cpu` defaults to
`"1000m"` (one vCPU, correct) and `fleet_memory` defaults to `"1024Mi"` (one gibibyte, wired
into `cloud_run.tf` as the container memory limit). Changed "two gigabytes" to "one gibibyte".
