## Corrections made in this pass

### 1. The per-request level rule was a two-way switch and is a three-way one

This is the chapter's central claim and it was wrong in a way that contradicted the chapter's own error-string table twelve sections later.

**Stated**, `server/contexts/logging/logging.go`. The level is chosen by a three-branch switch: `error` when a helper says so, otherwise an explicitly forced level when the handler set one, otherwise `debug`.

The chapter said "logged at `error` when the request produced a server fault. Everything else, including every successful request and every single 4xx, is logged at `debug`." That omits the middle branch entirely, and the middle branch is not rare. Grepping for callers of the level-forcing helper finds login, logout and SSO initiation forcing `info`, and deprecated API paths, deprecated field names and deprecated query parameters forcing `warn`. Every one of those is a per-request record, and every one of them survives at the default level.

**The chapter contradicted itself on this.** §8.3.6 lists `deprecated_path` as a warn-level record with per-request attributes, which cannot happen under §8.3.4's rule as written. Both halves had been verified in isolation. This is the §27 within-chapter read catching what per-claim checking cannot.

### 2. The 4xx demotion only applies to a single error

**Stated**, same file. The demotion helper returns "not an error level" only when the request accumulated **exactly one** error and that one error reports itself as a client error. With two or more errors the function returns true without inspecting any of them, so a request that produced two client errors is logged at `error`.

The practical consequence runs opposite to the chapter's warning: the chapter taught the reader that 4xx never appears, and an `error`-level line is therefore not proof of a server fault. Added as its own paragraph, because a diagnostician who has internalised the simple rule will misread the line.

### 3. `err` and `internal` partition the errors, they are not two views of one

**Stated**, same file. The loop tests each error for internal detail: if it has some, its internal text is appended to `internal`; **otherwise** its text is appended to `err`. An error never contributes to both.

The chapter's table implied they were parallel fields on the same error. The corrected reading is more useful for the reader: a line carrying `internal` with no `err` is the normal, and best, case.

### 4. `uuid` can hold more than one value

**Stated.** The uuids collected across the request's errors are joined with commas into one attribute. The chapter described a single UUID.

### 5. Log topic precedence was inverted, and enable-topics does nothing

**Stated**, `cmd/fleet/serve.go`, with a source comment that settles both halves: "Apply log topic overrides from config. Enables run first, then disables, so **disable wins on conflict**. Note that any topic not included in these lists will be considered enabled if it's encountered in a log."

The chapter said the opposite: "A topic in both lists is enabled". So did the equivalent row in **8.2**, which says "Enable wins over disable". Two chapters agreeing on the same wrong fact, which is why `claims.py` on a term neither chapter disputes would not have surfaced it. Only the source did.

The second half matters more. `server/platform/logging/topics.go` keeps a **disabled** set and nothing else: "Topics are enabled by default, only topics in this map are disabled." Fleet disables no topic by default at this release; the one example of doing so in `serve.go` is commented out. So `logging_enable_topics` removes entries from an empty set and changes nothing. A reader trying to switch on the deprecation warnings would set it, see no change, and conclude the feature was broken, when in fact those warnings were already on.

Corrected in 8.3. **8.2's row still says "Enable wins over disable" and was not edited**, because it is outside this chapter; flagged below.

### 6. The deprecation warning's quoting, which matters because the advice is to grep

**Stated.** The path variant formats as ``API `%s` is deprecated, use `%s` instead``, with **backticks**. The chapter reproduced it with apostrophes.

There is also a second variant the chapter did not have: deprecated fields and query parameters emit `'%s' is deprecated, use '%s' instead` with apostrophes and **no** `deprecated_path` attribute. Two shapes, two quote characters, same topic and level. Both now in the table, with the difference called out, since a grep built on the wrong one returns nothing and reads as "no deprecated calls".

### 7. A second, version-specific cause for missing built-in label memberships

**Stated**, from the 4.90.1 changelog and the diff of `server/datastore/mysql/apple_mdm.go` between the two tags.

At 4.90.0 the Apple re-enrollment reset cleared a host's built-in label memberships and did not restore them, which stopped label-scoped profiles, software and OS updates reaching hosts that were configured correctly. 4.90.1 restores the memberships inside the reset transaction, resets `label_updated_at` to the non-zero sentinel so the exclude-any guard treats the cleared memberships as not-yet-reported, and adds migration `BackfillAppleBuiltinLabelMemberships` for hosts already affected.

The chapter had one cause for this symptom, a deleted or renamed built-in label, which produces a log line. The 4.90.0 cause produces **no** log line, needs no misconfiguration, and is fixed by upgrading. Added, because a reader on 4.90.0 following the existing row would go looking for a renamed label that is not there.

This is the clearest thing the sweep found that a same-release re-check would not have: the chapter was verified against `main` around 4.90.0, when the bug was live and undocumented.

### 8. `unlock failed`

**Stated**, `server/service/schedule/schedule.go`, error level, immediately after the `lock failed` the chapter already documents. Added, because the two mean different things: failing to take the lock is contention, failing to release it leaves a schedule locked until the lock expires on its own, and that is the shape behind a `cron_stats` row that never leaves `pending`.

### 9. `logging_disable_banner`

Version note only. Still read into the config struct with no consumer anywhere in the server. Re-confirmed at 4.90.1; the chapter said 4.90.0.
