### Corrected: an activity type that does not exist

As published, 1.5 said "Successful sign-ins, failed sign-ins and multi-factor prompts all
appear", and 8.12 listed `user_mfa_requested` in its authentication row.

**No such activity type exists at `fleet-v4.90.1`.** A search across every Go and Markdown file at
the tag returns nothing for `user_mfa_requested`, `MFARequested` or `mfa_requested`, and no MFA
activity is emitted anywhere. The real authentication activities are `user_logged_in` and

This is a different failure from the over-inference behind most of this week's corrections.
Nothing was misread. The name was invented and then printed in a reference table, which is
precisely where a reader would build a security alert on it. 1.5 now says there is no separate
activity for a second-factor prompt and that those events come from the identity provider.

### New check: `build/check-activity-names.py`

Reads activity names from Fleet's own `activities.go`, so it stays correct across releases, and
reports any name printed alongside verified ones that the source does not define. Schema
identifiers are read from `schema.sql` and used only to suppress a flag, never to decide whether
a line is an activity list, because widening that test makes every SQL example look like one.

Wired into `pr-check`. Skips silently when no Fleet checkout is present, so it is advisory in CI

## Part I re-review, 2026-08-27

NOT READY, seven factual defects, and the first one takes the chapter's organising claim with it.

### The model was wrong

The chapter was built on a clean two-record split: activities record what Fleet and its administrators did, host results record what devices reported, and Fleet "records nothing the device did on its own". **The third of those is false.** Device-originated events become activities routinely: an Apple `CheckOut` writes `mdm_unenrolled`, MDM enrollment writes `mdm_enrolled`, an Android event over Pub/Sub can write an unenrollment row, and software and script results posted by Orbit write their activities **when the result comes back**, not when the work was sent. All of them carry no user, and the datastore accepts a nil actor deliberately.

So `activity_past` is an enumerated event stream drawn from four sources, administrative changes, requested work, automation, and observed outcomes, rather than one side of a partition. **An activity with no actor is a legitimate record, not a corrupted one.** 1.4 had already described it as an enumerated list and 8.12 acknowledged host-initiated rows in two places while asserting the opposite absolute in a third; the book held the right answer in pieces.

The real boundary is between *device-originated* and *invisible*: a device that unenrolls tells Fleet and gets a row, a device whose agent is deleted tells Fleet nothing and gets none. Corrected here, in 8.12 and in 2.8, which had inherited the false model verbatim.

### The rest

| Claim as written | Why it was wrong |
|---|---|
| Streaming is "how the record ends up" in your security systems | The stream reuses the global feed's query, which excludes `host_only` rows unconditionally. `installed_certificate` is always host-only and `ran_script` is host-only when it belongs to a batch. Those never leave Fleet. **Do not trim local history believing the SIEM has everything** |
| Second-factor events "come from the identity provider" | Fleet can run email MFA itself. After the password validates it sends the code and writes **no login activity at all**; `user_logged_in` appears only when the code is accepted; a wrong code writes nothing. So `user_failed_login` does not cover second-factor failures and the IdP has no record either, because the IdP was not involved |
| The activity webhook is "configurable organization-wide or per fleet" | There is one setting, in the organization's own configuration. No per-fleet webhook exists. It is also fired asynchronously *before* the row is stored, omits the activity ID and the Fleet-initiated flag, and retries only `429`, for thirty minutes. A notification, not a copy |
| Host-linked activities "are kept until the host itself is deleted" | On Apple ADE re-enrollment Fleet consults `preserve_host_activities_on_reenrollment`, and when it is off the reset **unlinks the activities without deleting the host**, leaving them eligible for expiry. It defaults **off on fresh installations and on for upgrades**, so two servers of the same version differ by history. 2.7 knew about the setting |
| The activity "identifies the rollout and its scope" | Profile activities carry the profile and the fleet; batch script activities carry a host count and a fleet. Neither carries the labels targeted or the hosts resolved, and a batch profile edit may omit the profile name. The review routine now sends the reader to the item's own targeting for scope |
| The in-product view "needs a Fleet account" | Necessary, not sufficient. The **global feed is readable only by global roles**; a fleet-scoped operator is refused there while still being able to read an individual host's feed, which authorizes against the host instead |

### Unsourced claims removed

A growing queue as "a strong signal that a device has stopped collecting its work", which is one of at least four things it is consistent with; streaming being reached for "for one of three reasons", an exhaustive claim about customer behaviour; and the recovery-secret trade being "a reasonable one to accept", which is the reader's decision rather than the manual's. A wrong cross-reference for queue depth pointed at 8.4, which only says the queue is server-side; the discussion is in 8.1.5.

## Second round, 2026-08-27

NOT READY. The false two-record model is gone, and **the replacement was too tidy in its own way**, which is now the recognisable signature of a correction in this project: the fix is a new claim, and its neatness is the thing to distrust.

| The new claim | Why it was wrong |
|---|---|
| A four-row taxonomy of activity kinds, with "the person who requested it" and "often nobody" | Not four exclusive bins. A `ran_script` row is an observed outcome **and** may be automation, since it reports whether a policy or the setup experience started it. An `installed_software` row can carry the requesting user or no user. "The person" also excludes API-only service identities, which the API distinguishes explicitly, and "often nobody" is an unsupported frequency claim |
| "Every entry is written at the moment it performs an action", listing "running a script" | `ran_script` is written when the **host's result returns**, not when the script was sent, so a script queued against an offline host produces no row until that host comes back. The old timing error survived the rewrite in the very sentence that was supposed to fix the model |
| "Most of the record" reaches the stream | Unestablished. An estate that runs batch scripts routinely could have host-only rows dominate its volume |
| "Stream them out, then trim locally" | Two problems, and it sat immediately after the warning that streaming omits rows. Trimming on that assumption discards host-only rows permanently. And **expiry cannot trim host-linked activities at all**: its query selects only rows with no host link left, so what it prunes is the unlinked remainder |
| Webhook failures are "permanent and silent" | Not silent. An exhausted or permanent failure is written to the Fleet server log |
| Fleet fires the POST "*before* the row is stored" | Fleet *launches* delivery before it attempts storage; asynchronous scheduling guarantees no ordering. The POST can arrive before or after the row exists, or announce an event whose storage then fails |
| "Those now-orphaned rows become eligible for expiry" | An activity can link to several hosts, and expiry accepts a row only once **no** host link remains. The reviewer retracted its own first-round wording here, which had said the same thing |
| "The queue itself distinguishes work not yet activated from work made ready" | Fleet tracks activation internally to order results and strips the derived field from the response, so no activation state is administrator-visible. The reviewer also retracted this, having supplied it in round one |

### Two reviewer retractions

Both were claims I had adopted from the first review verbatim, which is worth recording: **taking a reviewer's proposed wording is not the same as checking it.** The orphaned-rows universal and the upcoming-queue distinction were both wrong, and both went into the chapter on the reviewer's authority rather than on a source read of my own.

### Neighbours corrected

**2.7** guaranteed retention until host deletion, spelled the setting **singular** (`preserve_host_activity_on_reenrollment`) where Fleet uses the plural, and called it universally off by default when the migration sets it off on fresh installations and **on** for upgrades. **2.8** described the record as administrator actions only, promised delivery "solves retention cleanly", said the first run sends the entire unstreamed backlog without the host-only exclusion, and treated a streamed activity's scope as enough to identify affected hosts.

## Third round, 2026-08-27

NOT READY, eight items, all narrow. The chapter's model is now right; what kept failing was the wording around it.

The two that changed meaning: **"a queued script produces no row until the host returns"** is true of a per-host `ran_script` result and false of a batch, which writes its activity immediately whatever state the hosts are in. And **the API distinguishes an API-only actor only while that actor still resolves to a live user**, since deleting the account nulls the link while leaving the stored name and email, so an old row cannot tell you what kind of actor it was.

The rest were survivals: "successful and failed sign-ins both appear" outlived its own correction three lines later about native MFA failures writing nothing, and now says password-stage failures; streaming still "answers retention properly" immediately above the paragraph explaining that some rows never stream; the retention advice implied coordination avoids holding evidence twice, which it cannot for a host-linked row; the webhook passage omitted its tier where both neighbours state theirs; the review routine applied one activity type's payload limitation to all of them; and "global roles" concealed that **global GitOps is excluded** from the global feed.

## Fourth round, 2026-08-27

NOT READY, four items, all narrow and all real.

"Fleet records what Fleet did" survived at the head of a section whose surrounding paragraphs had been rewritten to say the opposite. Now: every activity is written by Fleet's server, and some are written when a device's report arrives.

**Streaming does not supply durability**, which the chapter had promised. The Premium path writes through whichever audit-log plugin you configure; that plugin defaults to `filesystem`, whose own default path is a temporary directory, and `stdout` is a valid choice. Fleet gives you a delivery path and you supply the durable end.

A third constraint on "stream it out, then trim locally" was missing, and it is the alarming one: **a destination can accept a batch and silently drop an oversized record inside it**, as Firehose does above its per-record limit, and return success. Fleet then marks those activities streamed. A row can read as delivered with no copy at the far end.

And the re-enrollment default is not "off on fresh installs, on for upgrades" as a rule; the migration tests `usersCount > 0` once, which produces that outcome but is worth stating as the actual predicate. Corrected here and in 2.7.

## Capped at the review limit, 2026-08-27

Five rounds, every finding from every round applied, last verdict NOT READY. Under the owner's rule the chapter now stays at `drafting` and waits for the whole-part review once Parts IV to VII are drafted.

**What five rounds actually bought.** Round one found fabricated claims. Rounds two and three found the corrections to those claims. Rounds four and five found propagation failures, corrections applied in one passage while the same claim survived in a table, an alt text, an image prompt or a neighbouring chapter. The defect count did not fall to zero and there is no sign it was going to; what changed was the *kind* of defect, from wrong to inconsistent, and inconsistency is cheaper to attack with `claims.py` and a grep than with another review.
