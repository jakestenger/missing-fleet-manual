## 2026-08-25 review pass

Independent review on `gpt-5.6-sol`. This one found a fabrication rather than an inference error.

### Corrected: an activity type that does not exist

As published, 1.5 said "Successful sign-ins, failed sign-ins and multi-factor prompts all
appear", and 8.12 listed `user_mfa_requested` in its authentication row.

**No such activity type exists at `fleet-v4.90.1`.** A search across every Go and Markdown file at
the tag returns nothing for `user_mfa_requested`, `MFARequested` or `mfa_requested`, and no MFA
activity is emitted anywhere. The real authentication activities are `user_logged_in` and
`user_failed_login` (`server/fleet/activities.go:291-305`).

This is a different failure from the over-inference behind most of this week's corrections.
Nothing was misread. The name was invented and then printed in a reference table, which is
precisely where a reader would build a security alert on it. 1.5 now says there is no separate
activity for a second-factor prompt and that those events come from the identity provider.

### New check: `build/check-activity-names.py`

Reads activity names from Fleet's own `activities.go`, so it stays correct across releases, and
reports any name printed alongside verified ones that the source does not define. Schema
identifiers are read from `schema.sql` and used only to suppress a flag, never to decide whether
a line is an activity list, because widening that test makes every SQL example look like one.

Wired into `pr-check`. Skips silently when no Fleet checkout is present, so it is advisory in CI
and authoritative locally.

### Recorded, not fixed

- The chapter's two-record taxonomy, requests and configuration changes, is too tidy. The feed
  also carries observed outcomes such as `mdm_enrolled`, `installed_software` and
  `escrowed_disk_encryption_key`, while still being an enumerated set rather than a log of every
  request. A reader who internalises the binary will misclassify evidence elsewhere in the book.
- "Past activity tells you what happened" invites the inference the chapter otherwise warns
  against. `ran_script` is recorded when a script is **sent**, not when a result returns
  (`docs/Contributing/reference/audit-logs.md:1181-1194`).
- Read access is described as needing "a Fleet account", which is materially incomplete. Global
  roles other than GitOps can read the global feed and fleet-scoped roles cannot

  global list excludes `host_only` entries so it is not the complete in-product view.

Those three are real and want a rewrite of the chapter's model rather than a patch.

## Part I re-review, 2026-08-27

NOT READY, seven factual defects, and the first one takes the chapter's organising claim with it.

### The model was wrong

The chapter was built on a clean two-record split: activities record what Fleet and its administrators did, host results record what devices reported, and Fleet "records nothing the device did on its own". **The third of those is false.** Device-originated events become activities routinely: an Apple `CheckOut` writes `mdm_unenrolled`, MDM enrollment writes `mdm_enrolled`, an Android event over Pub/Sub can write an unenrollment row, and software and script results posted by Orbit write their activities **when the result comes back**, not when the work was sent. All of them carry no user, and the datastore accepts a nil actor deliberately.

So `activity_past` is an enumerated event stream drawn from four sources, administrative changes, requested work, automation, and observed outcomes, rather than one side of a partition. **An activity with no actor is a legitimate record, not a corrupted one.** 1.4 had already described it as an enumerated list and 8.12 acknowledged host-initiated rows in two places while asserting the opposite absolute in a third; the book held the right answer in pieces.

The real boundary is between *device-originated* and *invisible*: a device that unenrolls tells Fleet and gets a row, a device whose agent is deleted tells Fleet nothing and gets none. Corrected here, in 8.12 and in 2.5, which had inherited the false model verbatim.

### The rest

| Claim as written | Why it was wrong |
|---|---|
| Streaming is "how the record ends up" in your security systems | The stream reuses the global feed's query, which excludes `host_only` rows unconditionally. `installed_certificate` is always host-only and `ran_script` is host-only when it belongs to a batch. Those never leave Fleet. **Do not trim local history believing the SIEM has everything** |
| Second-factor events "come from the identity provider" | Fleet can run email MFA itself. After the password validates it sends the code and writes **no login activity at all**; `user_logged_in` appears only when the code is accepted; a wrong code writes nothing. So `user_failed_login` does not cover second-factor failures and the IdP has no record either, because the IdP was not involved |
| The activity webhook is "configurable organization-wide or per fleet" | There is one setting, in the organization's own configuration. No per-fleet webhook exists. It is also fired asynchronously *before* the row is stored, omits the activity ID and the Fleet-initiated flag, and retries only `429`, for thirty minutes. A notification, not a copy |
| Host-linked activities "are kept until the host itself is deleted" | On Apple ADE re-enrollment Fleet consults `preserve_host_activities_on_reenrollment`, and when it is off the reset **unlinks the activities without deleting the host**, leaving them eligible for expiry. It defaults **off on fresh installations and on for upgrades**, so two servers of the same version differ by history. 2.4 knew about the setting |
| The activity "identifies the rollout and its scope" | Profile activities carry the profile and the fleet; batch script activities carry a host count and a fleet. Neither carries the labels targeted or the hosts resolved, and a batch profile edit may omit the profile name. The review routine now sends the reader to the item's own targeting for scope |
| The in-product view "needs a Fleet account" | Necessary, not sufficient. The **global feed is readable only by global roles**; a fleet-scoped operator is refused there while still being able to read an individual host's feed, which authorizes against the host instead |

### Unsourced claims removed

A growing queue as "a strong signal that a device has stopped collecting its work", which is one of at least four things it is consistent with; streaming being reached for "for one of three reasons", an exhaustive claim about customer behaviour; and the recovery-secret trade being "a reasonable one to accept", which is the reader's decision rather than the manual's. A wrong cross-reference for queue depth pointed at 8.4, which only says the queue is server-side; the discussion is in 8.1.5.
