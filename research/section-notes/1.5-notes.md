# 1.5 Audit and activity: citation ledger

## 2026-08-25 review pass

Independent review on `gpt-5.6-sol`. This one found a fabrication rather than an inference error.

### Corrected: an activity type that does not exist

As published, 1.5 said "Successful sign-ins, failed sign-ins and multi-factor prompts all
appear", and 8.12 listed `user_mfa_requested` in its authentication row.

**No such activity type exists at `fleet-v4.90.1`.** A search across every Go and Markdown file at
the tag returns nothing for `user_mfa_requested`, `MFARequested` or `mfa_requested`, and no MFA
activity is emitted anywhere. The real authentication activities are `user_logged_in` and
`user_failed_login` (`server/fleet/activities.go:291-305`).

This is a different failure from the over-inference behind most of this week's corrections.
Nothing was misread. The name was invented and then printed in a reference table, which is
precisely where a reader would build a security alert on it. 1.5 now says there is no separate
activity for a second-factor prompt and that those events come from the identity provider.

### Audited the rest, and found three more inventions

Extracted every backticked token in the manual appearing alongside verified activity names, and
checked each against `activities.go`:

| Invented name | Where | Reality |
|---|---|---|
| `user_mfa_requested` | 1.5 prose, 8.12 table | No MFA activity exists |
| `created_setup_experience_script` | 8.12 table | Only `edited_setup_experience_software` and `canceled_setup_experience` exist |
| `deleted_setup_experience_script` | 8.12 table | as above |
| `released_from_ab` | 8.12 table | No release-from-Apple-Business activity exists |

All four removed. Also rewrote the configuration-profile row, which used a shorthand asking the
reader to construct names themselves; the twelve real names are now described explicitly.

Verified as correct and left alone: `activity_past` and `activity_host_past` are real tables
(`server/datastore/mysql/schema.sql:115,120`), and the claim that Fleet's REST API reference is
stale on the old `activities` name still holds.

### New check: `build/check-activity-names.py`

Reads activity names from Fleet's own `activities.go`, so it stays correct across releases, and
reports any name printed alongside verified ones that the source does not define. Schema
identifiers are read from `schema.sql` and used only to suppress a flag, never to decide whether
a line is an activity list, because widening that test makes every SQL example look like one.

Wired into `pr-check`. Skips silently when no Fleet checkout is present, so it is advisory in CI
and authoritative locally.

### Recorded, not fixed

- The chapter's two-record taxonomy, requests and configuration changes, is too tidy. The feed
  also carries observed outcomes such as `mdm_enrolled`, `installed_software` and
  `escrowed_disk_encryption_key`, while still being an enumerated set rather than a log of every
  request. A reader who internalises the binary will misclassify evidence elsewhere in the book.
- "Past activity tells you what happened" invites the inference the chapter otherwise warns
  against. `ran_script` is recorded when a script is **sent**, not when a result returns
  (`docs/Contributing/reference/audit-logs.md:1181-1194`).
- Read access is described as needing "a Fleet account", which is materially incomplete. Global
  roles other than GitOps can read the global feed and fleet-scoped roles cannot
  (`server/authz/policy.rego:220-227`), per-host activity authorizes against host access, and the
  global list excludes `host_only` entries so it is not the complete in-product view.

Those three are real and want a rewrite of the chapter's model rather than a patch.
