## The container image

| Claim | Source | Confidence |
|---|---|---|
| Alpine base pinned by digest; installs ca-certificates and jq; upgrades openssl | `tools/fleet-docker/Dockerfile` | High |
| Creates its own group and unprivileged user and runs as it (`addgroup -S fleet && adduser -S fleet -G fleet`, `USER fleet`) | same | High |
| Command is `fleet serve`, so migrations require overriding the command | same (`CMD ["fleet", "serve"]`) | High |
| Docker volumes are root-owned, so a non-root Fleet cannot write to them without help; the Compose deployment uses a one-shot init container that fixes ownership and exits, showing as `Exited (0)` | `articles/deploy-fleet-on-docker-compose.md` What's running | High |

The Compose guide states the container user is UID 100. The Dockerfile uses `adduser -S` without specifying a numeric ID, so the number is Alpine's allocation rather than a pinned contract. **The chapter deliberately says "an unprivileged user" and does not quote the UID**, since a reader could otherwise build a volume permission fix around a number Fleet has not promised.

## Deliberately left out

- **Full Helm `values.yaml` and Terraform `main.tf` bodies.** Reference material; STYLE §17. The chapter names the decisions and leaves the keys to Fleet's guide and a.3.
- **Step-by-step Docker and Ubuntu installation commands** from the Proxmox guide. Neither Fleet-specific nor durable.
- **Render, Hetzner, CentOS, cloud.gov and the Ubuntu-with-Elastic guides.** All exist at the tag as articles. Each is a variation on the paths already covered, and enumerating them would pad the chapter without changing a decision.
- **`fleetctl preview` / try-Fleet-locally.** A local evaluation tool, not a deployment path.
- **GKE managed certificate and ingress templates** in the chart. Cloud-specific; 2.3 owns that ground.
- **The three-store model, single-writer constraint, sizing, and the health endpoint's coverage.** Canonical to 1.6 and 2.2; referenced, not restated.

## 2026-08-25 review pass: the migration claim was wrong for Compose

Independent review on `gpt-5.6-sol`.

### Corrected: Compose migrates automatically

As published, the chapter reasoned from the image outward: the image's command is `fleet serve`,
therefore "running database migrations means running the image with a different command", and
"A Fleet upgrade is never only a container replacement."

That is true of the image and false of the deployment Fleet publishes.

| Fact | Source |
|---|---|
| The image command is `fleet serve` | `tools/fleet-docker/Dockerfile` |
| Fleet's Compose file overrides it with `sh -c "/usr/bin/fleet prepare db --no-prompt && /usr/bin/fleet serve"` | `docs/solutions/docker-compose/docker-compose.yml:66` |
| "Fleet automatically runs database migrations on startup" after `docker compose pull fleet && docker compose up -d fleet` | `articles/deploy-fleet-on-docker-compose.md:233-243` |

So on Compose, pulling a new image and bringing the service up genuinely is the whole upgrade.
A reader following the published chapter would have looked for a migration step that the
packaging had already performed, or worse, concluded their upgrade was incomplete.

The single-container shape is what makes automatic migration safe there: no other instance is
serving traffic against a half-migrated schema. That is the same constraint that forces
scale-to-zero on Kubernetes, reaching the opposite conclusion because the topology differs.

### Corrected: the chapter's opening thesis

"How you package Fleet changes almost nothing about how it runs, and exactly one thing about how
you deploy a new version of it."

The chapter then describes different ports, secret handling, initialization behaviour, background
job placement and upgrade orchestration. With the Compose finding above, upgrade handling differs
*between* packagings as well, so "exactly one thing" was wrong twice over. Replaced with what is
actually invariant, the binary and its three dependencies, and what actually varies, who runs the
migration.

### Corrected: port 1337

Stated as though it were Fleet's port. It is the host mapping in the published Compose file. With
a reverse proxy terminating TLS, that mapping becomes internal and devices connect to the proxy.

### Recorded, not fixed

- The review asks for an explicit production-suitability boundary for the Compose example: single
  host, local volumes for database and cache, no application-tier redundancy. The chapter carries
  Fleet's own production list but does not name the failure domain. Worth adding; larger than a
  correction.
- It also notes that Kubernetes is presented as the production route while its convenience
  sub-charts are ruled out for production use, leaving an on-premises reader without a stated
  pattern. Real gap, and it belongs to 2.2 or 2.3 as much as here.
