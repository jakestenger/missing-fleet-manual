# 6.5 Connect integrations, webhooks, and external workflows, citation ledger

Drafted 2026-08-28. Research consensus in one round with eighteen corrections, draft, one review
round applied. Working research is held outside this repository, see [`README.md`](README.md).

## Derived

**"Seven mechanisms that are not variations on one design."** The chapter's organising claim, and the
reason a comparison table is the chapter rather than an appendix to it.

**"Webhook as trigger, API as source of truth."** Qualified at review to recovery of **current state
while it persists**, and explicitly not applicable to the migration press, the log batch and the
calendar callback, which have no supported replay.

## Rejected, and why

**"Two cannot be scoped to a fleet."** Four. And the table contradicted the sentence beneath it.

**"The calendar job delivers the callback."** It arms it.

**"The shared interval governs only host status and failing policies."** True of this chapter's
senders and false of the run, which also drives ticket collection and the reset scan.

**"Fleet does not keep state."** Broader than the operational conclusion: Fleet retains calendar
delivery status internally, and what it lacks is a supported read or replay interface.

**Entity fields as a deduplication key.** They are inputs to a key the receiver owns; a repeated
host-status delivery may be a legitimately new evaluation.

## 4.91: per-fleet activity webhook (IA4)

Verified at `fleet-v4.91.0` (35fc1c0244), 2026-09-08. Changelog bullet: "Added activity automations
for fleets (Fleet Premium): a per-fleet webhook, configured from the Hosts page, that sends a request
to a destination URL whenever an activity linked to one of the fleet's hosts is created."

### Stated (source establishes substance and scope)

| Claim | Basis |
|---|---|
| Stored per fleet as `webhook_settings.host_activities_webhook` (`enable_host_activities_webhook`, `destination_url`), separate from the global `webhook_settings.activities_webhook` | `TeamWebhookSettings.HostActivitiesWebhook` / `HostActivitiesWebhookSettings`, `server/fleet/teams.go`; global `ActivitiesWebhookSettings`, `server/fleet/app.go` |
| Fires only for activities linked to a host, and only for the fleet(s) those hosts belong to | `server/activity/internal/service/new_activity.go`: per-fleet path runs only when the activity implements `types.ActivityHosts` and `len(HostIDs())>0`; `ResolveHostActivitiesWebhooks` groups the activity's hosts by fleet |
| Premium on the fire side: on Free it resolves to nothing; the Teams API itself is EE-only | `GetHostActivitiesWebhookSettings` returns nil unless `license.IsPremium(ctx)`, `server/service/activities.go`; `GetTeam`/`NewTeam`/`ModifyTeam` return `ErrMissingLicense` on Free, `server/service/teams.go` |
| One delivery per fleet, each carrying only that fleet's host IDs; two fleets sharing a URL get two separate scoped requests (not merged); disabled / deleted / empty-URL fleets dropped; "No fleet" hosts use the team-0 default-team config | `ResolveHostActivitiesWebhooks`, `server/fleet/teams.go`, and the table-driven cases in `server/service/activities_test.go` (shared-URL, no-team, deleted, nil/empty) |
| Same firing path and contract as the global activity webhook: async, any 2xx success, 30s timeout, retry on HTTP 429 only up to 30 min, permanent on any other status, destination URL masked in the error log | shared `fireActivityWebhook` (`new_activity.go`) + `PostJSONWithTimeout` (30s `fleethttp` client, 2xx check, `MaskSecretURLParams`/`MaskURLError`), `server/platform/http/post_json.go` |
| Payload fields: `timestamp`, `actor_full_name`, `actor_id`, `actor_email`, `type`, `details` (no activity ID, no fleet-initiated flag) | `webhookPayload`, `new_activity.go` (matches 1.5's stated payload omissions) |
| Per-fleet copy injects a fleet-scoped `host_ids` array into `details` only for activities whose stored details carry no host identifier (batch activities); global copy left as stored | `detailsWithHostIDs`, `new_activity.go` |
| Configurable from the Hosts page (UI) and GitOps `webhook_settings.host_activities_webhook`, including "No Team" (Premium-gated; omitted = applied disabled to clear) | changelog; `extractHostActivitiesWebhook` / `doGitOpsNoTeamWebhookSettings`, `server/service/client.go` |
| Enabling requires a non-empty http/https `destination_url` with a host | `ValidateEnabledHostActivitiesWebhook`, `server/fleet/integrations.go` |
| The dial-time private-address block applies (all `fleethttp` clients use the private-network-blocking dialer) | `pkg/fleethttp`; `PostJSONWithTimeout` uses `fleethttp.NewClient` |
| Changing the per-fleet webhook writes none of `enabled_/edited_/disabled_activity_automations`; those emit only for the global app-config webhook | the three types emit only from `server/service/appconfig.go` (sole non-test emit site); `server/service/teams.go` has no `NewActivity` calls, and no `edited_team` type exists |

### Derived

**A host-linked activity fans out to multiple destinations.** The global webhook (if enabled) plus one
per-fleet delivery per matching fleet all fire for the same activity, because `NewActivity` runs both
paths in sequence. Reasoning from the two independent fire blocks in `new_activity.go`.

**A batch activity across a large fleet delivers a large, unbounded payload**, since the injected
`host_ids` list has no cap, the same way host status carries an unbounded identifier list. Derived from
`detailsWithHostIDs` (no truncation) and its batch comment.
