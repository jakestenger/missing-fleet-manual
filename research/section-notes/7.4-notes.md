# 7.4 Observe progress, performance, and service health, citation ledger

Drafted 2026-08-28. Research consensus with corrections plus a gap round for prioritisation,
dependency handoffs, baselining and alert testing. Draft, one review round applied. Held to Part
VII's four-class evidence rule ([`../part7-structure.md`](../part7-structure.md)).

## Fleet contract, source checked at the tag

| Claim | Note |
|---|---|
| **The health check's registered checks are the database and Redis.** Object storage is not among them and is not probed at startup | **Narrowed at review** from an absolute |
| It does not name which check failed, and does not test the server private key or whether anything encrypted is readable | |
| **The metrics endpoint carries no business metric.** HTTP families, a service-layer family over a subset of administrative methods, and runtime defaults | |
| **It is not mounted by default.** With no credentials and no explicit opt-out the route is absent and an ordinary request falls through to the interface | Not an error and not a refusal |
| The export pipeline carries internal detail the metrics endpoint does not, and **the two are not supersets of each other** | |

| **The vulnerability freshness field is stamped even when the run found nothing** | **Scoped at review**: it proves a result was produced, not that anything was found or refreshed |
| **The service-layer latency metric is named for microseconds and emitted in seconds** | |
| Which schedules register depends on edition and configuration, and **registration is not evidence of work** | |
| **The schedule's run record has no supported reader**, and a run records completion even when every job in it failed | |
| **Failures delivering osquery status and result logs to an external destination are classified as client errors**, which routes them to debug level and excludes them from the error store and exception reporting | **Restricted at review** to those external log deliveries; my draft had broadened it into a general audit-log claim |

## Not established

**Freshness surfaces for maintained-app and purchased-app refresh.** The chapter says so in the table
rather than substituting a proxy that measures something else, which is what the first draft did.

## Operational practice

The five-outcome grouping, the choice of a first alert set, what to record as a baseline and what
counts as normal are all judgement, and are labelled as such.

## Rejected, and why

**"Two status endpoints return success even when the thing they report on failed."** False at this
tag. Deleted.

**Inventing two freshness timestamps** that do not exist, to fill rows in the scheduled-work table.

**Treating a successful trigger response as alert-drill evidence.** It says the schedule was asked to
run. The drill now requires a new automation activity **and** arrival at the destination.

**"The only outbound channel that records both success and failure."** Overclaimed.
