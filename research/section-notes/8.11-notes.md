## Derived

Reasoning the chapter does over verified facts. Fleet does not state these.

- That raising log verbosity is a different act from reading logs, and so does not conflict with 8.1's "logs are step seven". The underlying facts (DEBUG-level per-request lines, no retroactive logging) are verified; the reconciliation is the book's.
- That a control narrows an investigation without closing a branch. Editorial.
- That a stale one-host label will quietly narrow someone else's change later. Consequence of manual label membership persisting, not a documented failure mode.
- That a hostname which matches no host yields an empty label rather than an error. Follows from the identifier being deprecated rather than rejected; **not separately tested**.
- The reading of the differential table generally, and the caution that a platform-only failure makes a platform-path cause likely rather than certain.

## Unverified

Carried forward. None of these are asserted in the chapter as fact.

- The env var spellings `FLEET_MDM_APPLE_DEP_SYNC_PERIODICITY` and `FLEET_SERVER_VPP_VERIFY_REQUEST_DELAY` are inferred from Fleet's config-key convention. The keys and defaults are verified; the spellings are not. The chapter's own "What is not documented" table says so.
- The behaviour of `sudo profiles renew -type enrollment` is Apple's, and Fleet's repository cannot establish it.
- The Windows 480 minute relaxed poll and 1 minute fast poll are carried from 8.9 and were verified there, not re-verified here.
- The revised Compose recipe has not been run end to end from an empty directory. The two edits it prescribes are verified against the published files; the resulting stack was not started.
- Every row of the force-action table in §8.11.6 is behavioural and was not re-tested at 4.90.1.

## Rejected from the review

- **Remove the `[!internal]` callout.** It is a manual-wide convention across Part VIII, used in thirteen chapters to carry support-history context. The reviewer had no way to know that.
- **Remove the "What is not documented" table as publication scaffolding.** The table tells a reader which claims not to lean on, which is worth more in a troubleshooting chapter than a clean surface. The incorrect row in it was fixed rather than the table dropped.
- **Restructure the chapter into a single incident workflow.** 8.1 owns the procedure; this chapter owns the techniques it calls. Duplicating the sequence here would give the reader two orderings to reconcile, which is the failure mode that produced the finding in the first place. The opening now hands off to 8.1 explicitly instead.

## Confirming review, 2026-08-27: three table cells were inverted

The differential-isolation table's middle column is headed "Same result on both makes unlikely". The only thing a same result can make unlikely is **the axis you varied**, and three of six rows named something else: platform said Fleet-side logic, Fleet version said "everything except the version", and network position said the host and payload.

Worse, the first application had appended a bold sentence to each of those rows stating the correct inference, leaving every one of the three rows arguing with itself. That is a worse defect than the original, and it was mine.

All three middle cells now name the varied axis, the contradictory appendages are gone, and the rule is stated once under the table so the next person filling in a row has it: the middle column is always the axis you varied.

## Second confirming review, 2026-08-27: NOT READY, now applied

The differential table this chapter was last corrected for came back fully resolved with no surviving variant. Everything else in the **first** review had never been applied at all, and the confirming pass said so: those defects are "pre-existing, unapplied first-review findings, not consequences of the latest table correction". That is a fair characterisation and a worse failure than a half-applied fix, because nothing about it looked wrong.

**The Docker Compose recipe was described from the wrong file.** The chapter said `FLEET_SERVER_CERT` and `FLEET_SERVER_KEY` point inside the `data` named volume and "nothing in the recipe puts anything there". The recipe bind-mounts `./certs/fleet.crt` and `./certs/fleet.key` onto exactly those two paths, read-only, and `env.example` says in a comment that TLS requires certificates in `./certs/`. So the certificate is the reader's to create, in a directory beside the Compose file, and the chapter had them looking in a volume. Corrected, with the fact that **the mounts are unconditional**: they apply with TLS off too, which is a reason to create the files before the first `up` rather than let Docker invent directories at those paths.

**"fleetd requires TLS" is too absolute**, and the exception is exactly the case this section is about. Orbit's client allows plain HTTP when the host is `localhost` or `127.0.0.1`, and anywhere when the agent was built to skip verification. Neither belongs in production; both are what a disposable instance exists for.

**"Bring the stack up"** now says `docker compose up -d`, which the section had left as an exercise while giving the exact command for everything else around it.

**Two attributions to Fleet that Fleet does not make.** The "about 15 minutes" setup estimate is not in the tagged Compose directory, which contains two files and no such figure; it is now this manual's estimate and labelled as one. And **Windows MDM needing a *publicly* resolvable hostname is not established**: Fleet validates only that the server URL is HTTP or HTTPS with a host, and derives the Windows endpoints from it. The requirement that *is* supportable is the device's view rather than the internet's, since the device does the connecting, and the chapter now says that and marks the stronger claim as unestablished.

**The minimisation section named causes it had not found.** "Whatever still fails is the cause" was followed by six table cells reading "Delivery, not content", "The install pipeline, not the installer" and so on — while §8.11.2 warned twenty lines earlier that a control does not close a branch, and §8.11.9 said isolation does not name a single cause. Three parts of one chapter disagreeing. A minimum that still fails has moved the question from the payload to the path, which is progress and not an answer, and every cell now says which rather than what.

**The one-host claim borrowed a discriminator from 8.14 that 8.14 does not offer.** Removing host count tells you a content problem from something that needed the population. It does not separate a scale ceiling from a configured limit; 8.14's discriminator for that is whether raising the limit fixes it.

**Sixteen repository links were pointing at `blob/main`**, five of them in this chapter after a review had already asked for four of them to be pinned. All are now pinned to `fleet-v4.90.1`, and `build/check-pinned-links.py` fails on any that are not. A link to a moving branch is worse than no link: it looks like a citation and behaves like a guess, and this manual's whole claim is that it states what one release does.


## Third confirming review, 2026-08-27: NOT READY, applied

Everything from all three prior rounds resolved except one table cell and one item that is not a text problem at all.

**The install-script row closed a branch the paragraph above it had just opened.** §8.11.5 had been corrected to say that what still fails at the minimum is where the cause lives, not what the cause is; the row underneath still said "if the timeout still trips, it is not your script". A control that reproduces without the original script shows the original is not **necessary** to produce the failure. It does not show the original is sound, and a script can carry an independent defect that the timeout hides. Reworded to say exactly that, which is the same distinction §8.11.2 draws about controls and §8.11.9 about clean instances. Three sections of this chapter now say the same thing in the same terms.

**The Compose recipe has still not been run from an empty directory**, and that is correctly recorded as unresolved rather than fixed. It is not a text defect: the text now matches the tagged `docker-compose.yml` and `env.example`, and what is missing is a runtime confirmation that the described sequence produces a working instance from nothing. The reviewer's note is fair, and the honest state is that the recipe is verified against the source and not against a run. Left as an outstanding verification item rather than quietly dropped.

Everything else confirmed: the differential table, the certificate mounts, the removal of "fleetd requires TLS", the `docker compose up -d` command, the 4.90.1 schedule inventory with all 34 names matching, the five pinned repository links, the Windows-hostname qualification, and the setup-time estimate attributed to this manual rather than to Fleet.

## Fourth confirming round, 2026-08-27

NOT READY, two blockers. One applied, one cannot be closed here.

**Applied: the Premium gates in the one-host and throwaway workflows.** The chapter told readers to scope a profile, script or installer to a one-host label without saying that **label-scoping a configuration profile is Premium** and **software installers do not exist on Fleet Free at all**; scripts are the only one of the three that works unlicensed. Worse in combination: the recipe's own `env.example` ships `FLEET_LICENSE_KEY` blank, so the chapter was describing a Free instance and calling it sufficient for software testing. ADE, ABM and VPP are Premium too. All now stated, with the decision moved to before the instance is built. **This is the fifth chapter this session with a wrong or missing licence claim, and the second where the wrongness was an omission rather than an assertion**, which is the harder kind to catch because there is no sentence to check.

**Not closed: executing the Compose recipe end to end.** Docker's CLI is present on the author's machine but the daemon is not running, and starting it, pulling images and standing up a Fleet stack is a heavier action than this task warranted taking unprompted. The finding is legitimate and stands. Rather than leave it implicit in this ledger, the chapter now carries the caveat in its own text: the file-level claims are read from the tagged Compose directory and are checked; the runtime outcome, and specifically the first `up` in a directory with no `./certs`, is untested and marked unverified.

That is the honest resolution available without running it, and it is the one blocking item between 8.11 and a `verified` stamp.
