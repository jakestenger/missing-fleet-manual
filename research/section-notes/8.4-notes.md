## Corrections made in this pass

### 1. The half-enrolled failure rate contradicted 8.1

**Cross-chapter contradiction, introduced by this pass's own correction to 8.1.** 8.4 said the 2 to 3 percent figure was "an observed rate from support practice rather than a published figure". It is a published figure: it is written in `fleetdm/fleet#47793`, which 8.4's own preceding paragraph links. 8.1 cited the issue; 8.4 said there was no citation.

Both chapters now say the same thing, which is what the source supports: one deployment reported 20 to 30 machines in 1,000, in a public issue, and that is one estate's observation rather than a rate across deployments. 8.4 links to 8.1's version so the two cannot drift apart again.

Also corrected: "still open as of 4.90.x" is now "open as of 4.90.1", confirmed rather than carried; and "the planned fix" is now "the proposed fix", since the issue is an open proposal with every checklist item unfilled rather than scheduled work.

### 2. The TUF version floor was 1.38.1 in one sentence and 1.38.0 in the next

**Stated.** `orbit/pkg/update/update.go` marks the migration at **1.38.0** in four separate comments, and orbit's changelog files 1.38.0 and 1.38.1 under one heading whose only entry is the migration. Nothing supports 1.38.1 as a floor.

The chapter said "Orbit below 1.38.1 cannot upgrade past the move" and then, two clauses later, "Orbit 1.38.0 and later rewrite a configured `tuf.fleetctl.com` URL". A reader upgrading a fleet would have been told to reach a version one patch higher than the one that actually fixes it, which is harmless, and would also have had no way to reconcile the two numbers.

Corrected to 1.38.0, and the *reason* is now given rather than just the number: 1.38.0 is where the repository URL moves and the on-disk metadata file changes name.

### 3. The second version floor now says what it is a floor for

**Stated.** Orbit 1.20.0's changelog entry is "Allow configuring TUF channels of `orbit`, `osqueryd` and `desktop` from Fleet agent settings". That is the boundary the chapter's downgrade-loop row already referenced without saying what changed at it.

Added the operational consequence: below 1.20.0, `update_channels` in agent options is ignored, so a configured channel and a running channel can differ with nothing logged. That is a silent divergence, which is the class this chapter exists to catch.

### 4. Added: separating Orbit's uptime from osquery's

**Stated.** `orbit_info` carries an `uptime` column. §8.4.6 computed osquery's uptime by subtracting `osquery_info.start_time` from `time` and did not mention Orbit's.

Reading both in one query answers the question the section is actually asking. Orbit's uptime much larger than osquery's means the supervisor is healthy and restarting its child. The two roughly equal means the whole bundle is cycling. Those point at different logs, and §8.4.2 already explains why the distinction matters: the first subsystem to stop tears down the others, so a restart in Orbit's log is routinely osquery's doing.

## Checked and deliberately not claimed

**The pinned TUF root metadata embedded in the binary carries `"expires":"2026-01-08T22:23:47Z"`,** which is in the past as of this verification date. It is tempting to connect that to §8.4.12's paragraph on expired TUF roles blocking startup, and I have not, because the embedded root is a bootstrap value used only when the on-disk metadata file is missing, and what a TUF client does with an expired pinned root when newer root metadata is fetchable from the repository is not established anywhere in Fleet's source. Claiming an operational consequence here would be exactly the correct-reading-wrong-inference failure §27 describes. Recorded so the next person does not have to re-derive that it was considered.

## Carried out of this chapter

- **Orbit 1.20.0 also extended the script execution timeout to 5 minutes**, which is the same number 8.11 gives for ad-hoc scripts and corrects to `script_execution_timeout`. Consistent; noted because the provenance is useful if that claim is ever challenged.
- §8.4.6's osquery table columns (`osquery_flags`, `osquery_schedule`, `osquery_events`, `osquery_info`, `time`, `mdm`, `managed_policies`) come from **osquery**, not Fleet, and are **unverified at this tag** by construction. They are attributed to Fleet's published table schema in the chapter, which is the right sourcing, but no check in `build/` can see them and neither can this ledger.
- The `profiles` command family in §8.4.4 is macOS, not Fleet. The Fleet-side anchors were confirmed: the uninstall script greps `MDM enrollment: Yes`, fleetd runs `profiles show -type enrollment` as the console user during migration, and `com.fleetdm.fleet.mdm.apple` is the identifier the uninstall script removes.
