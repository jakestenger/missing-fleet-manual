## Corrections made in this pass

### 1. The half-enrolled failure rate contradicted 8.1

**Cross-chapter contradiction, introduced by this pass's own correction to 8.1.** 8.4 said the 2 to 3 percent figure was "an observed rate from support practice rather than a published figure". It is a published figure: it is written in `fleetdm/fleet#47793`, which 8.4's own preceding paragraph links. 8.1 cited the issue; 8.4 said there was no citation.

Both chapters now say the same thing, which is what the source supports: one deployment reported 20 to 30 machines in 1,000, in a public issue, and that is one estate's observation rather than a rate across deployments. 8.4 links to 8.1's version so the two cannot drift apart again.

Also corrected: "still open as of 4.90.x" is now "open as of 4.90.1", confirmed rather than carried; and "the planned fix" is now "the proposed fix", since the issue is an open proposal with every checklist item unfilled rather than scheduled work.

### 2. The TUF version floor was 1.38.1 in one sentence and 1.38.0 in the next

**Stated.** `orbit/pkg/update/update.go` marks the migration at **1.38.0** in four separate comments, and orbit's changelog files 1.38.0 and 1.38.1 under one heading whose only entry is the migration. Nothing supports 1.38.1 as a floor.

The chapter said "Orbit below 1.38.1 cannot upgrade past the move" and then, two clauses later, "Orbit 1.38.0 and later rewrite a configured `tuf.fleetctl.com` URL". A reader upgrading a fleet would have been told to reach a version one patch higher than the one that actually fixes it, which is harmless, and would also have had no way to reconcile the two numbers.

Corrected to 1.38.0, and the *reason* is now given rather than just the number: 1.38.0 is where the repository URL moves and the on-disk metadata file changes name.

### 3. The second version floor now says what it is a floor for

**Stated.** Orbit 1.20.0's changelog entry is "Allow configuring TUF channels of `orbit`, `osqueryd` and `desktop` from Fleet agent settings". That is the boundary the chapter's downgrade-loop row already referenced without saying what changed at it.

Added the operational consequence: below 1.20.0, `update_channels` in agent options is ignored, so a configured channel and a running channel can differ with nothing logged. That is a silent divergence, which is the class this chapter exists to catch.

### 4. Added: separating Orbit's uptime from osquery's

**Stated.** `orbit_info` carries an `uptime` column. §8.4.6 computed osquery's uptime by subtracting `osquery_info.start_time` from `time` and did not mention Orbit's.

Reading both in one query answers the question the section is actually asking. Orbit's uptime much larger than osquery's means the supervisor is healthy and restarting its child. The two roughly equal means the whole bundle is cycling. Those point at different logs, and §8.4.2 already explains why the distinction matters: the first subsystem to stop tears down the others, so a restart in Orbit's log is routinely osquery's doing.

## A cross-chapter correction this produced

**Stated.** Orbit's config fetches, which carry `command_line_flags`, authenticate with the **Orbit node key**; `client/orbit_client.go` routes them through `authenticatedRequest`. The enroll secret is used only by `enroll`, and Orbit re-enrols when 401s persist past its grace period.

So the documented behaviour, that a host enrolled with a revoked secret stops receiving flag updates, is true by an indirect route: flags keep flowing on a valid node key, and stop when the host is forced to re-enrol and cannot. **3.1 stated the wrong mechanism** ("because fleetd uses the secret to fetch them") and has been corrected to match. Found by running `claims.py` on "revoked" after applying, which is the discipline added to `HANDOFF.md` step 7 earlier today.

## Second confirming review, 2026-08-27: NOT READY, now applied

Three of the previous round's findings had been applied only where the finding pointed, and one of the three left the chapter contradicting itself. The verification-queue items were closed as well, which the earlier passes had left open without recording a decline.

**The Orbit-root shape was still presented as proof.** The table had been corrected to say absence is one-way evidence, and the summary sentence forty lines above still said a root holding only `certs.pem` and `bin/` **is** a package that failed to enroll. Every platform's packager writes `osquery.flags` whether or not enrollment ever happened, so that shape is equally consistent with an incomplete install, a damaged directory, or later removal. The chapter now says take it as a reason to read the log.

**"The most common cause" replaced a universal with a frequency claim nothing supports.** The tagged source establishes that Fleet enqueues `InstallEnterpriseApplication` and treats an error response as a completed command; it establishes nothing about how often that outranks an agent removed afterwards. Now "one cause, on the ADE path", with the ranking explicitly disclaimed so nobody reads the section as a triage order.

**The uptime comparison was not merely imprecise, it was inverted.** The chapter said Orbit's uptime much larger than osquery's means the supervisor is restarting its child. **Orbit cannot restart osqueryd.** There is a single osquery runner, its `Execute` returns when the process exits, and the source comment says outright that the process may not be restarted afterwards; everything that would restart osqueryd, including an agent options change, triggers an **Orbit** restart. So the two uptimes being roughly equal is the healthy reading, and a large gap is a finding needing a different explanation: something else started an osqueryd, the two rows were read against different processes such as a standalone `orbit shell`, or the clock is wrong.

**Three absolutes closed rather than left in the queue.** "Output is three lines" became a description of what to look for, since the shape moves between macOS versions. `profiles status` reading the same inside and outside a user session is now marked as this manual's observation rather than an established fact, because nothing in Fleet's source establishes it. And the System Settings pane is no longer said to carry the same facts: it does not present the DEP and user-approved distinctions, which are exactly what the command is for.

**Launchd error 36** no longer says "normal on a busy daemon". It means the boot-out was accepted and has not finished, so it is not a failure to retry; whether it is routine is not something this manual can support, and what Fleet's script does is wait.

**`fleetdm/fleet#47793`'s state** is not in the tagged source and can no longer be asserted from it. The number stays, the "open as of 4.90.1" goes, in this chapter and in 8.1, which carried the same sentence.

## Third confirming review, 2026-08-27: NOT READY, applied

Four prior findings partially resolved, three new defects introduced by the last pass, and one pre-existing defect the reviewer found while verifying. The pattern by now is familiar and worth naming precisely: **the previous round replaced wrong absolutes with new absolutes**, which is progress on the facts and no progress on the habit.

**The uptime correction was itself incomplete, and in the same direction as the error it fixed.** The last pass established correctly that Orbit cannot restart osqueryd, then asserted that Orbit "starts osqueryd a moment after starting itself" and that any gap is therefore a finding. `orbit_info.uptime` runs from early in Orbit's startup, and Orbit performs an update check and can retry resolving update targets for minutes before the osquery runner is created. So a few minutes of gap on a freshly started host is ordinary, and only a large gap on a long-running host needs explaining. The chapter now says which, and §8.4.1's "the child it launches and restarts" is corrected too, since it contradicted the rest.

**Three replacement diagnoses had no support.**

- A flag *missing* from `osquery_flags` was said to usually mean a pending restart. The table lists registered flags with their current and default values, so a flag that has not taken yet is present with the old value. A genuinely absent row is more likely a name osquery does not register at this version.
- `events = 0` persisting was said to be "usually" permissions or platform support. The first thing it is consistent with is nothing having happened that the publisher matches, which is not a fault at all.
- `config_hash` "differs between correct hosts, so including it in a diff generates a finding on every run" overstates in the other direction: hosts with identical fleet, platform and label selections do hash the same. The point is that a mismatch means nothing, not that a match is impossible.

**Two operational errors, both of which would waste a reader's time at the worst moment.**

- The recovery paragraph offered **Fleet's own software installer** as a way to deliver the agent to a half-enrolled host. Fleet's software installation is executed by a runner inside Orbit and needs its osquery connection, so on a host with no agent there is nothing to run it. Removed and replaced with an MDM command over the working enrollment.
- The known-good comparison still listed "a missing node key or secret file" as a useful difference, after §8.4.3 had been corrected to say `secret.txt` is routinely absent on a healthy host. Same claim, two places, one corrected.

**And a pre-existing defect surfaced during verification:** a missing launchd plist was treated as proof of uninstall. `fleetctl package --service=false` builds a package that never writes the plist, and a damaged install produces the same absence. One-way evidence, like the Orbit-root shape above it.
