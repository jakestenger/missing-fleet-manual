## Tiering, stated plainly in the docs
> Available in Fleet Premium. Activity information is available for all Fleet Free and Fleet
> Premium instances using the Activities API.

So: **the activity record is available to everyone; streaming it to an external destination
is Premium.** That distinction belongs early in the chapter, because "audit logs are Premium"
is the wrong summary and would mislead a Free reader into thinking they have no record.

## The operational fact that matters most
> The audit events are logged in an asynchronous fashion. **It can take up to 5 minutes for
> an event to be logged.**

Anyone verifying delivery will make a test change and look immediately. Saying this up front
prevents a false negative and a wasted hour.

## Configuration
| Key | Env var | Default |
|---|---|---|
| `activity_enable_audit_log` | `FLEET_ACTIVITY_ENABLE_AUDIT_LOG` | `false` |
| `activity_audit_log_plugin` | `FLEET_ACTIVITY_AUDIT_LOG_PLUGIN` | `filesystem` |
| `filesystem_audit_log_file` | | `/tmp/audit` |

YAML form:
```yaml
activity:
  enable_audit_log: true
  audit_log_plugin: firehose
```

`activity_audit_log_plugin` only takes effect when `activity_enable_audit_log` is `true`.

### The default destination is a trap worth naming
Defaults compose to: **enabled audit logging writes to `/tmp/audit`**. `/tmp` is cleared by
the OS and is local to one Fleet instance, so the default configuration produces a log that
is neither durable nor complete across a multi-instance deployment. Not a Fleet defect (the
default is inert until you enable the feature), but the first thing to change.

## Plugins available at this tag
`filesystem`, `firehose`, `kinesis`, `lambda`, `pubsub`, `kafkarest`, `nats`, `splunk`,
`stdout`. `stdout` needs no additional configuration.

`articles/log-destinations.md` documents: Amazon Kinesis Data Firehose, Webhook, Snowflake,
Splunk (and Splunk via Firehose), Amazon Kinesis Data Streams, AWS Lambda, Google Cloud
Pub/Sub, Apache Kafka, Stdout, Filesystem, plus "Sending logs outside of Fleet".

Note the guide's destination list and the plugin list are not identical: Snowflake and
Webhook appear as destinations reachable via a plugin rather than as plugin names. Chapter
uses the plugin names, which are what you configure.

## 2026-08-25 review pass: the replay claim was wrong

Independent review on `gpt-5.6-sol`. One correction, two additions.

### Corrected: "Nothing is replayed"

As published: "If a destination is unreachable when Fleet tries to write, the record stays in
Fleet and the external copy is simply absent for that window ... the gap will not fill itself in
afterwards."

That is the opposite of what the streaming service does, and it conflates two different
failures.

| Failure | Behaviour | Source |
|---|---|---|
| Destination write returns an error | Fleet stops at that activity, leaves it unmarked, and retries from there on the next run | `server/activity/internal/service/service.go:224-231`, comment reads "We stop streaming upon the first error (will retry on next cron iteration)". Only successfully written IDs reach `MarkActivitiesAsStreamed` at `:239` |
| Plugin drops an oversized record and reports success | Fleet marks it streamed. Never retried, never reported | Drop-and-succeed paths in `server/logging/firehose.go`, `kinesis.go`, `lambda.go`, `pubsub.go`, `splunk.go` |

So an outage delays delivery; a size limit loses data silently. The published wording described
the recoverable case as unrecoverable and said nothing about the genuinely unrecoverable one.
Corrected to distinguish them, with the consequence stated: size the destination for the largest
plausible record, not the typical one.

### Added: enabling delivery replays the entire backlog

`activities.streamed` is `TINYINT(1) NOT NULL DEFAULT FALSE`
(`server/datastore/mysql/migrations/tables/20221220195935_AddStreamedColumnToActivities.go:15`),
and the streaming service selects unstreamed rows in ascending order. Turning delivery on for the
first time therefore drains the whole existing history to the destination, oldest first, rather
than starting from the moment of enablement. On an established deployment that is a large first
burst at a destination that has never received Fleet traffic.

### Added: managed cloud cannot change this

`articles/log-destinations.md:10`: "Currently, only self-hosted users can modify this
configuration. If you're a managed-cloud customer, please reach out to Fleet." The chapter
described the ownership split without saying that on managed cloud the setting is not the
customer's at all.

Also noted: selecting a plugin is not configuring it. Every destination except `stdout` needs its
own settings, and the chapter's YAML example named `firehose` while supplying none of them.
