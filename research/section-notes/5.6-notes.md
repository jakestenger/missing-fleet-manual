# 5.6 Control operating system updates, citation ledger

Drafted 2026-08-28. Research at `research/section-notes/5.6-scratch-*.md`, four files. Process:
outline consensus, research consensus over two rounds and four sweeps, draft, one review round

## A sourcing note, because this chapter departs from the project's normal rule

Everywhere else this manual verifies against `~/Source/Fleet/fleet-public` at tag `fleet-v4.90.1`
(`dd0200f062`) and treats vendor documentation as secondary. **This chapter cannot.** Fleet publishes
an update requirement and the operating system does the rest, so what the OS does afterwards is not
establishable from Fleet's source at any level of effort.

So claims here fall into two classes and the ledger keeps them apart:

- **Fleet behaviour**, verified at the tag as usual.
- **Platform behaviour**, sourced from Microsoft, Apple and Google documentation, with URLs recorded
  in `5.6-scratch-platform-semantics.md`. Three are cited in the chapter's `further_reading`.

Where vendor documentation contradicts itself, the chapter says so rather than picking a side. That
happens twice, and both are recorded below.

## Stated: platform behaviour, from vendor documentation

| Claim | Vendor |
|---|---|
| Windows forced restart is the **later** of discovery plus deadline and restart-pending plus grace, so the clocks overlap rather than queue | Microsoft compliance-deadline guidance |
| Once the effective deadline is reached, Windows can force the restart **regardless of active hours** | Microsoft, same |
| When the feature-specific grace node is absent, the generic grace value governs feature updates too | Microsoft Update CSP reference |
| An atomic block is all-or-nothing; a failure rolls the others back, and **rollback can itself fail**, leaving a device partial | Microsoft OMA-DM status codes |
| Apple's declaration support begins at macOS 14, iOS 17 and iPadOS 17, without requiring supervision | Apple deployment guide |
| At the deadline macOS **force quits every open application regardless of unsaved documents** | Apple enforced-updates guide |
| A passcode-protected iOS or iPadOS device requires the passcode at the enforcement date unless entered earlier | Apple, same |
| A device offline or interrupted at the deadline retries after reconnecting, with an attempt within about an hour | Apple, same |
| Apple's declarative model is **device-autonomous once the declaration is present**, so enforcement continues without connectivity | Apple declarative-management guide. **Corrected in review**: I had written that losing MDM stops enforcement |
| Apple silicon may authorise enforcement with a bootstrap token; without one macOS prompts for credentials | Apple. **Restored in review** |

| The windowed Android mode also constrains Google Play application updates | Google |
| Only a **device owner** can control Android system updates; a profile owner can report but not control | Google |

## Derived

**"Fleet does not install operating system updates."** The chapter's organising claim. Verified in
the sense that no installation path exists in Fleet's source, but the framing is editorial.

**The evidence ladder**, and the observation that built-in enforcement skips its middle rung. The
components are source-checked; presenting them as a ladder is mine.

**"A successful save proves that Fleet accepted the input, not that the target platform can apply
it."** The reviewer's wording, adopted verbatim. It replaced my attempt to name a "silent
acceptance" theme, which the reviewer talked me out of on the grounds that the three instances have
different causes and different remedies.

**The advice to test the Windows payload on every build and edition in scope.** Follows from the
atomic behaviour plus the undocumented unsupported-node case.

## Unverified, and phrased as such in the text

**The Windows `NoAutoReboot` compatibility question.** Written as a documented discrepancy and a risk
to test, never as a failure claim, because Microsoft's own references disagree and none of them
settles the device outcome. Recorded as D27, explicitly as a request for empirical testing.

**What an unsupported policy node returns inside an atomic block.** Microsoft does not document it.
The chapter states the conditional and tells the reader to test.

**Windows offline past the deadline.** Not clearly documented. The chapter says so and offers the one
useful thing that is certain: time offline is not automatically time overdue, because a device that
never discovered the update never started its clock.

## Rejected, and why

**"Everything here is Fleet Premium."** Swept in the Linux inventory and policy alternatives, which
are not.

**"Fleet has no visibility into stage 5 at all."** Contradicted the Nudge exception the chapter had
just established. Narrowed to the Fleet server having no visibility into platform installation or
restart.

**"Fleet strips the suffix before every version comparison."** False, and the falseness is the
finding: the browser comparison does not, which is C10.

**"Losing MDM connectivity stops declarative enforcement."** Too broad. Delivery and revision need
connectivity; enforcement of a declaration already present does not.

**A first-person admission** that I had the Windows deadline model wrong before checking. I asked
whether it read as useful candour or intrusion; the reviewer said to cut it, and the correction
stands on its own without the narrator in it.
