## Corrections made in this pass

### 1. `webhook` was documented as result-only, and it is not

**Stated.** `server/config/config.go` registers two settings, `webhook.status_url` and `webhook.result_url`. `cmd/fleet/logging.go` sets `Webhook.URL` from the status URL before building the status logger and from the result URL before building the result logger. `server/logging/logging.go` handles `webhook` in the same switch as every other plugin, with no gate on which stream is being built.

So the chapter's prose ("Result logs additionally support `webhook`") and its table cell ("Result logs only") were both wrong. Status logs take a webhook.

The corrected list is ten destinations, all ten accepted for all three streams, which is what the dispatch actually does.

### 2. The audit-plus-webhook trap, found while checking the above

**Stated, and worth its own callout.** The audit block in `cmd/fleet/logging.go` mutates the shared logging config for Filesystem, Firehose, Kinesis, Lambda, PubSub, KafkaREST and Nats. It does **not** touch `Webhook.URL`, and there is no `webhook.audit_url` setting to touch. The config value is carried over from the result block.

Two outcomes, both bad, both reachable by a reader following the destination table as it stood:

- No result URL configured: `NewWebhookLogWriter` returns "webhook URL missing", which is wrapped as `create webhook audit logger: webhook URL missing` and passed to `initFatal`. The server does not start, and the error names audit while the setting the operator will go looking for does not exist.
- A result URL configured: the server starts and the audit stream is POSTed to the **result** webhook, interleaved with query results.

This is a Fleet defect rather than a documentation defect. **Not filed**, consistent with the standing instruction; recorded here and in `PROJECT_STATUS.md`.

### 3. Splunk is configured once for the whole server

**Stated.** `splunk.url`, `splunk.token`, `splunk.index`, `splunk.source`, `splunk.source_type` and `splunk.insecure_skip_verify` are the complete set, and none has a per-stream variant. `buildLoggingConfig` fills the Splunk block once and the three per-stream blocks never modify it.

Every other destination does take a per-stream target: stream name for Firehose and Kinesis, function for Lambda, topic for Pub/Sub and Kafka, subject for NATS, file path for `filesystem`. Splunk is the exception, and the consequence is that results, status and audit routed to Splunk land in one index under one source and sourcetype.

Added, because the reader most likely to hit it is exactly the one this chapter serves: someone who has just pointed all three streams at their SIEM and cannot work out why they cannot separate them.

Splunk HEC is new at 4.90.0, per the changelog, which is why nothing in the manual had covered its shape yet.

### 4. Drop thresholds were given for three destinations and withheld for two

**Stated.** Firehose and Kinesis both drop at **1 MB**, logged as "dropping log over 1MB Firehose limit" and "dropping log over 1MB Kinesis limit". The chapter said only "oversized records are dropped" for both while giving exact numbers for Lambda and Pub/Sub, which makes the row unusable for capacity planning and implies the limit is unknown.

Confirmed unchanged: Lambda `6 * 1000 * 1000`, Pub/Sub 10 MB, Splunk 1 MB per event.

### 5. Splunk's retry condition was half right

**Stated.** `sendWithRetry` retries on `503 Service Unavailable` **and** `429 Too Many Requests`, up to `splunkMaxRetries = 8`, with `splunkRetryDelay(try) = 100ms * 2^try`, so the first retry waits 200 ms and the eighth waits 25.6 s. The chapter named only 503.

429 is the response a throttled HEC actually returns, so omitting it was the more consequential half.

### 6. The audit stream's five-minute lag now names the schedule that causes it

**Stated.** `cmd/fleet/cron.go`: the `activities_streaming` schedule runs on a 5 minute interval and its single job calls `StreamActivities` with the audit logger. Results and status logs have no equivalent; they are written inside the request that delivered them.

The chapter had the five minutes as a bare fact. Naming the schedule makes it actionable, because it can be triggered rather than waited on, and it links to 8.1's warning about trigger reporting. This agrees with 8.12, which already gave the schedule and the interval, and with 2.8.

**Also stated, and previously unstated here:** the audit logger is built only when `license.IsPremium() && cfg.Activity.EnableAuditLog`. On a Free licence the setting is accepted and nothing is written, with no startup error. A silent no-op is exactly the kind of thing this chapter exists to surface.

### 7. Two scoping fixes

- The `filesystem` default paths are `filepath.Join(os.TempDir(), ...)`, not the literal `/tmp`. On a Linux Fleet server that is `/tmp` and the point about boot-time clearing holds, so the correction is to say where the value comes from rather than to change the advice.
- `/var/lib/orbit` was scoped to Linux. `orbit/pkg/packaging/macos_templates.go` runs `ln -sf /opt/orbit /var/lib/orbit` too, and `orbit/cmd/orbit/orbit.go` still honours `/var/lib/orbit` as a real root directory for hosts installed before the default moved.

### 8. Added: the debug window is visible from the server

**Stated.** `debug_logging_on_enroll_duration` stamps `hosts.orbit_debug_until`, a nullable `timestamp(6)`, exposed on the host object as `orbit_debug_until`. The chapter documented how to set the window and gave the reader no way to confirm it landed, which for a lever whose whole purpose is capturing a narrow enrollment window is the missing half.

## Confirming review, 2026-08-27: NOT READY on two items, both now closed

Nine of eleven prior findings confirmed resolved. Two were not.

**The manual PlistBuddy sequence still used `set` alone.** The callout warning about the published script was applied, and the "manual equivalent" fifty lines below it was left with the same defect the callout exists to describe. Anyone who skipped the callout and copied the commands hit exactly the failure being warned about. Now uses add-or-set, with a line saying that `set` alone is what the published script does and why that matters.

**Fleet code defect, and the third found by this project.** The chapter said the fate of the rest of a batch after an oversized Pub/Sub message was "not established at this tag". It is establishable and it is worse than a graceful drop.

**Stated**, `server/logging/pubsub.go`: the writer allocates one publish-result slot per log record, `continue`s past an oversized record leaving that slot nil, and then iterates **every** slot calling `Get` on it. A nil slot is therefore waited on.

**Derived, and deliberately bounded:** a single oversized record takes the whole batch's write with it rather than costing only that record. The chapter says that and stops there. I have not asserted the precise runtime outcome, because whether the nil receiver panics and whether Fleet's middleware recovers it are two further questions the logging package does not answer, and the operational advice is the same either way: `dropping log over 10MB PubSub limit` is a batch-level event, not a record-level one.

Not filed, consistent with the standing instruction. Running total: ten Fleet documentation errors, three code defects.

## Second confirming review, 2026-08-27: READY WITH MINOR CHANGES, applied

Both prior rounds' findings confirmed resolved except one, and three new defects the correction pass had introduced. All four applied.

**The osqueryd inventory row named a path that exists on no platform.** The correction pass had fixed the executable-discovery command and left the table's generic `bin/osqueryd/<os>/<channel>/osqueryd` standing. Every segment of it varies: the platform token is `macos-app` on macOS rather than `macos`, the file is `osqueryd.exe` on Windows, and on macOS it is a tarball with the executable nested at `osquery.app/Contents/MacOS/osqueryd`. The row now gives all three explicitly and says the generic form will not be found on disk. Same partial-application pattern as everywhere else in this project: fix the passage the finding cited, leave the identical claim in the table above it.

**`/var/lib/orbit` is not a general compatibility symlink.** Both the macOS and Linux packagers create it only when the bundled Orbit is older than `0.0.11`, so on any recent host the two paths are not interchangeable and looking in `/var/lib/orbit` finds nothing. Orbit's separate compatibility, for a binary genuinely living below that path, is what carries the old hosts. The chapter had said either path works on either platform, which is exactly the sort of thing a reader tries once and gives up on.

**8.4 said the same thing** and had to be corrected with it. Found by `claims.py` after applying, not by the review.

**The webhook audit claim was true but overstated.** The audit block never sets its own webhook URL, so it inherits the result URL left in the shared config struct — that part was right. Whether the audit records arrive *mixed in with query results* depends on whether the result stream is itself routed to `webhook`. If it is not, the audit stream arrives alone at a URL configured for something else, which is a different problem with a different fix.

**"Every other destination takes a per-stream target" contradicted the paragraph above it**, which had just explained that `webhook` has no audit URL. `stdout` takes no target at all. Seven destinations do; the sentence now names the three exceptions rather than implying none.
