## The WSTEP pair as escrow key

| Claim | Source | Confidence |
|---|---|---|
| Escrowed disk encryption keys are encrypted to the WSTEP certificate | `server/service/orbit.go:1374-1382` (`microsoft_mdm.Encrypt(encryptionKey, wstepCert.Leaf)`) | High |
| Decryption path is chosen by platform: LUKS uses server private key; Windows uses WSTEP; everything else uses Apple MDM CA assets | `server/service/hosts.go:3587-3624` | High |
| The Apple path deliberately includes rolled-over CA certs so older escrows still decrypt; the Windows path has no equivalent | `server/service/hosts.go:3615-3617` (`assets.CACertsAndKeyForDecryption`) | High |
| `/api/fleet/orbit/disk_encryption_key` is gated behind `VerifyWindowsMDM()`; LUKS escrow is a separate route | `server/service/handler.go:1062-1065` | High |
| Changing the pair strands previously escrowed keys; recovery is toggling disk encryption off and on | `docs/Configuration/fleet-server-configuration.md:3632` | High |

**Documentation discrepancy, flagged in the chapter as a blockquote.** `docs/Configuration/fleet-server-configuration.md:3632` says the affected hosts are **macOS**. The code at this tag routes Windows hosts through the WSTEP decryption path and Apple hosts through the Apple MDM CA path (`server/service/hosts.go:3587-3624`), so the platform named in that sentence appears to be wrong. The chapter states the code behaviour and notes the discrepancy rather than silently contradicting Fleet's published docs. Candidate upstream doc fix.

## 2026-08-25 review pass: an inherited contradiction, and an overgeneralized heading

Independent review on `gpt-5.6-sol`.

### Corrected: the Android domain-verification paragraph contradicted itself

As published, one paragraph said Microsoft 365 organizations "verify your domain in the Google
Admin console afterwards" and then that "Workspace and Microsoft 365 organizations skip domain
verification".

**The contradiction was inherited.** `articles/android-mdm-setup.md:11` states that Google
Workspace and Microsoft organizations do not need to verify domain ownership; the Microsoft 365
procedure at `:27-28` instructs the administrator to verify it as its final two steps. The source
does not resolve itself, and no other material at the tag settles it.

Handled the way 2.5 handles the SCIM `email` discrepancy: state that the source is inconsistent,
give both readings, and recommend the action that satisfies either. Verifying a domain is
harmless, so the advice is to verify unless already verified.

**Second Fleet documentation inconsistency found in this part.** Worth reporting upstream
alongside the WSTEP platform error and the GCP "coming soon" claim.

### Corrected: a heading claimed more than its own paragraph

Heading: "An Android host has no serial number". Body, correctly: "On a personally owned Android
device enrolled with a work profile ...". `docs/REST API/rest-api.md:4091` scopes the
enterprise-specific ID to hosts with `mdm.enrollment_status` of "On (personal)". Company-owned
enrollment is a separate, Premium path and the claim was never verified for it.

Retitled to match the paragraph. Notable as a defect class: the prose was right and the heading
was wrong, so verifying claims against sources would never have caught it.

### Corrected: "Renewal: None" for the Windows key pair

Accurate as far as it goes, and misleading in a table whose purpose is to compare ongoing cost.
There is no vendor renewal, but the certificate has whatever lifetime you gave it, and the
chapter goes on to explain that replacing the pair strands every escrowed disk encryption key.
The row now says no vendor renewal and that you choose the lifetime; the framing paragraph now
points at the replacement consequence instead of describing both platforms as having "a sharper
edge later".

### Recorded, not fixed

- The review recommends reorganizing into two per-platform runbooks so an administrator can
  follow Windows or Android start to finish. The chapter is currently organized around the
  comparison, which is where its argument lives. A restructure is a larger decision than a
  correction pass; left for Jake.
- The Android agent package, signing fingerprint and batch-size settings are development
  internals the text itself says not to touch. Arguably they interrupt the setup narrative.
  Kept, because "why does Fleet install an app on Android at all" is a question an administrator
  will ask when they see it on a device.

### Licence claims re-checked 2026-08-27, and one was wrong

Part III's confirming reviews found licence claims wrong in both directions inside a single chapter, which made every licence claim in the manual worth re-checking rather than only the flagged ones. Two of this chapter's three hold; one does not.

**Holds.** Windows automatic enrollment is Premium: `windows_entra_tenant_ids` and `windows_entra_client_ids` are both rejected with `ErrMissingLicense` on Free, so the Entra connection cannot be configured at all.

**Holds.** The basic connections are free on both platforms; nothing gates the WSTEP pair or the Android enterprise binding.

**Does not hold as written.** The table said company-owned Android is "Fleet Premium, for fully managed devices". **Nothing in Fleet's Android module checks a licence** at this release, and company-owned enrollment is one query parameter, `fully_managed`, on the same enrollment-token endpoint the work-profile path uses. There is no free-tier implementation shadowing it and no `ee/` counterpart to the Android service.

That does not establish that Fleet sells it at no cost, which is a pricing question this manual cannot answer and should not pretend to. The row now says what the server does and tells the reader to confirm the commercial side against Fleet's pricing. **This is a correction to a chapter stamped `verified`**, and it is the second licence claim in this manual found wrong by looking, after 3.5's.
