## Corrected at Codex round 3 (2026-09-01)

- **Inventory freshness overclaim.** "Refreshed at each check-in" / "as fresh as the last check-in" overstated it. Fleet's detail queries run on the inventory interval and only for enabled platforms/features, so inventory is only as fresh as the last successful collection of that detail. Source-checked by the reviewer (detail-query scheduling on `DetailUpdateInterval`; software/user detail queries gated by feature flags). Corrected, with links to 4.1 and 4.4.
- **SSE launch + `.env` location.** Added an explicit SSE launch block and stated the binary reads `.env` from its working directory (`godotenv.Load()` with no path), not merely "beside the binary". Added a pointer to the tagged stdio smoke test for isolating a server/token fault from a client-config fault.
- **Contradiction fixed.** The token-role paragraph had called the live-query capability "gated by the client's confirmation prompt", contradicting the advisory framing elsewhere. Reworded to advisory. Also qualified "bearer checked on every request" as every MCP request, `/healthz` aside.
- **Cadence.** Removed the count-announcing transitions ("five parts", "three behaviours", "two defaults", "two choices"), trimmed the duplicated platform section, and dropped the security-summary repeat from Version notes.

## Corrected at Codex round 4 (2026-09-01)

- **Edition-aware roles.** The blanket "observer-plus, no admin/maintainer required" is Premium-only. Verified at the tag: an API-only user can be created on Free (core integration suite, `TestCreateAPIOnlyUser`, returns OK; empty `APIEndpoints` = full access); `api_endpoints` allowlists are rejected without Premium (core suite); observer-plus and team-scoped API users are Premium (reviewer-cited integration tests). So: read-only observer works on either edition; live queries need observer-plus (Premium) or a maintainer/admin identity (Free); team scope and endpoint allowlist are Premium; the API-only requirement itself holds on both. Reflected in the security section and version notes. **The MCP does not require Premium** — an important thing to have got right, since the API-only user it depends on is Free-available.
- **Shared-secret boundary.** One server process carries one bearer and one Fleet identity, so the SSE bearer is a shared secret, not per-user login: every holder has the same scope, all activity attributes to the same API-only user, and the server cannot revoke or throttle a single client. Added, with the recommendation to run one identity per trust group or front it with an identity-aware gateway. Softened the body-cap/timeout claim — those are not rate limiting, which belongs at the edge.
- **Completeness ceilings.** "Sample" → "partial first page"; noted that an aggregate that fetches hosts internally stops at a 10,000-host ceiling and reports a lower bound past it, and that a filtered live query previews at most 100 of up to 500 resolved targets. Source-checked by the reviewer.
- **Meta-prose.** Removed "…is in the right place", "what makes the rest trustworthy", and "the boundaries that decide whether an answer is complete".

Kept "Edge cases and precedence" as the heading (the book's standard §4/template section) rather than fragmenting into per-topic headings as the reviewer suggested.

## Derived

**"Read-only is not the same as harmless."** The chapter's organising security claim. `run_live_query` runs arbitrary osquery on devices; the README notes tables such as `curl` / `curl_certificate` / `carves` can make outbound requests or read file content. The inference the chapter draws — that an observer token is the enforced way to remove the capability, because Fleet 403s the write — is stated in source; the framing that the client's confirmation prompt is *not* the real control is derived from the advisory-hint comment.

**"The MCP is a proxy, so diagnosis is diagnosis of the Fleet API path."** Concluded from the stateless-proxy structure, not a sentence in the source. It is the basis for the short Part VIII handoff.

**Some answers are composed across several Fleet calls because a single filter cannot be trusted.** Derived from the README operational-learnings section and the presence of `GetHostsForCVE` / label-intersection compose paths in `fleet_integration.go`. See the lead below — the *reason* (Fleet ignoring the filters) is asserted by Fleet's own code but not independently reproduced here.

## Unverified — leads, not claims

- **Fleet's `GET /hosts` silently ignoring `cve` / `platform` / `label_id` filters, and `?cve=` returning wrong results.** The MCP's own source and README assert this ("as of Fleet 4.85") and deliberately route around it (`GetHostsForCVE`'s 3-step compose; label/platform via `/labels/:id/hosts`). I verified the **workaround exists in source at the tag**; I did **not** independently reproduce Fleet returning the wrong host set, which needs a running Fleet. If real at 4.90.1 this is a Fleet code defect worth a `C` entry in the defect queue — flagged for Jake rather than filed at the queue's "verified independently" bar. The chapter states only that the tool returns the right hosts, which is safe.
- **Exact per-tool argument lists.** Routed to `a.8` rather than enumerated in the chapter; not re-verified argument by argument here.

## Rejected, and why (Codex round 1, 2026-09-01)

The independent review (`reviews/2026-09-01/6.6-sol.out`, verdict NOT READY) caught four factual defects, three source-checked at the tag. All came from trusting the tool's bundled `README.md` over the Go source — the lesson §27 already records, that a `stated` row cites Fleet's source at the tag and nothing else, including not the tool's own prose.

- **"Temporary saved queries (`fleet-mcp-temp-` prefix) swept at startup."** Not in the tagged MCP source at all. `CreateSavedQuery` exists only for `-seed` mode; live queries use the ad-hoc host-query and unsaved-campaign paths above. The README's "saved-query sweeper" bullet describes behaviour the code does not have. Removed from the chapter.
- **"Go 1.25.7."** `go.mod` declares `go 1.26.5`. The README prerequisite is stale relative to its own module file. Corrected.
- **"Everything the assistant does is visible in Fleet's activity feed."** Overclaim. Read tools create no Fleet activity; only activity-producing operations (live queries) are attributed there. Corrected to distinguish attribution from completeness, and to name the MCP server logs as the record of read-tool calls.
- **stdio "authenticates the call."** The bearer is validated at startup but not checked per tool message on stdio; the boundary is process access. Corrected, and the transport comparison now states it.

Also fixed at round 1: the a.8 handoff (a.8 is REST routes, not MCP tool arguments — now points to the tagged `cmd/fleet-mcp` for arguments), the architecture diagram brief (now shows separate stdio/SSE branches and the auth boundary), removal of the volatile Claude Desktop screenshot, and a narrative-cadence pass removing announce-the-next-move transitions and de-duplicated edge cases.

## Fix-loop round (2026-09-02, round3 M4)

Round 1's fix to the stdio "authenticates the call" defect (above) still left the transport
comparison saying the token "is validated when the server starts," which a fresh read parsed as
some form of authentication happening at that moment. Re-verified against `cmd/fleet-mcp/main.go`
at `fleet-v4.90.1`: the startup check (`main.go:87-91`) only confirms `MCP_AUTH_TOKEN` is
non-empty and at least `minMCPAuthTokenLen` (32) characters — it never compares it against
anything, so nothing is actually authenticated. `bearerAuthMiddleware` (`auth.go`) is wired at
`main.go:124`, inside the SSE-only branch after the stdio early-return, and is never invoked under
stdio at all. Reworded to say plainly that `MCP_AUTH_TOKEN` performs no authentication under stdio
— it's a configuration guard (fail closed if unset or weak), not an access control — and that the
entire trust boundary is process access.

## Fix-loop round (2026-09-02, round3 B2 — regression fix)

- **`GET /me` false "always reachable" claim (B2, REGRESSION of this morning's `d5b440f`).** The allowlist section claimed Fleet's catalog treats the identity check as always reachable for an API-only user, so it doesn't need to be in an allowlist. Verified false against source at `fleet-v4.90.1`: `server/api_endpoints/api_endpoints.yml` lists `GET /api/v1/fleet/me` in the catalog like any other route, and `server/service/middleware/auth/api_only.go`'s `apiOnlyEndpointCheck` applies the identical catalog-membership + user-allowlist check to it — no special case. `cmd/fleet-mcp/main.go`'s `requireAPIOnlyUser` calls `WhoAmI` (→ `GET /me`) at startup and exits (`logrus.Fatalf`) if it fails. A restricted API-only user missing `GET /me` from their allowlist gets a 403 and the MCP server refuses to start. Fixed: added `GET /me` to both published allowlist profiles and replaced the false claim with the actual mechanism (no exemption; startup check calls it once regardless of role).

## Fix-loop round (2026-09-02, round3 M13, m8)

- **No worked example for a supervised SSE deployment (M13).** The chapter told readers to "run
  the binary as a supervised service... behind the TLS-terminating proxy" without showing one.
  Added a systemd unit (`Restart=on-failure`, `EnvironmentFile` for the three secrets) plus a
  one-line Caddy `reverse_proxy`, and a three-command `curl` check (`/healthz` unauthenticated
  200, `/sse` without a bearer 401, `/sse` with one 200). Verified the route/middleware chain
  against source: `cmd/fleet-mcp/route_guard.go` passes only `/sse` and `/message` through to
  `cmd/fleet-mcp/auth.go`'s `bearerAuthMiddleware`, which 401s a missing/wrong `Authorization`
  header; `/healthz` is wired on a separate mux entry in `main.go` and never reaches either
  middleware. `main.go`'s signal handling confirmed the binary already exits cleanly on
  SIGTERM/SIGINT, so `Restart=on-failure` is the correct systemd directive rather than a bare
  `Restart=always`.
- **Arbitrary-osquery threat claim stated as if execution-tested (m8).** The file/network/cloud-
  metadata claim about `run_live_query` was accurate but phrased as an established fact rather
  than as something drawn from osquery's schema. Confirmed the underlying tables exist
  (`schema/tables/curl.yml`, `file.yml`, `azure_instance_metadata.yml` in `fleet-public`) but no
  in-tree test executes such a query end-to-end. Reworded to attribute the claim to the schema
  and note it isn't drawn from an executed test, without softening the safety point itself.
