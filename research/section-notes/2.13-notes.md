# 2.13 Connect certificate authorities: citation ledger

Verified against `fleet-v4.90.0` in `~/Source/Fleet/fleet-public`.

## Fix-loop round (2026-09-03, round6 M7 — test-issue verification step named no endpoint/payload/command)

The "Verification and ownership" step 2 told the reader to "use the test-issue endpoint with
a sample signing request" but gave no endpoint, payload, or runnable command, so the one step
that claims to catch what creation cannot test was itself unreachable.

Re-verified at fleet-v4.90.0:
- Route: `POST /api/_version_/fleet/certificate_authorities/{id:[0-9]+}/request_certificate`
  (`server/service/handler.go:923`, `requestCertificateEndpoint`). Runnable form uses literal
  `v1` per the book's copy-and-run convention.
- Payload `RequestCertificatePayload` (`server/fleet/certificate_authorities.go:499-506`): `id`
  from the URL; body `csr` (PEM-encoded CSR, required); optional `return_pem_certificate`
  (true => PEM CERTIFICATE block returned; false/omitted => PEM PKCS7 block). Optional IDP
  fields exist but are not needed for the basic test.
- Scope: the EE handler rejects anything but Hydrant and custom EST with "This API currently
  only supports Hydrant and EST Certificate Authorities."
  (`ee/server/service/request_certificate.go:42-43`). Free tier returns a missing-license
  error (`server/service/certificate_authorities.go:171-174`) — consistent with the chapter's
  existing "the whole surface is Fleet Premium" framing (line 31). So the book's step-2 scoping
  to "Hydrant or custom EST" is correct; custom SCEP is verified by profile install instead.
- Behaviour cross-checked against `ee/server/service/request_certificate_test.go:206` (happy
  path returns a PEM PKCS7 block for `{ID, CSR}`).

Added a runnable block: `openssl req` to mint a throwaway CSR, then `curl --fail-with-body`
POST with `jq -Rs '{csr: ., return_pem_certificate: true}'` to JSON-encode it, using the
book's established `$FLEET`/`$TOKEN` env-var + `--fail-with-body` curl idiom (cf. 8.5).
No product-fact change beyond making the existing claim concrete; links=0, no em-dashes,
no angle-bracket shell placeholders.

## Fix-loop round (2026-09-03, round6 M18 — renewal variable named but never named or placed)

The "Variables carry the authority's name" paragraph closed with "A renewal identifier
variable and a Windows-specific SCEP certificate identifier variable complete the set,"
naming neither, so a reader could deploy a certificate that silently never auto-renews.
Added a dedicated paragraph naming both and stating placement, coverage, and the opt-in
consequence, verified against fleet-v4.90.0:
- Preferred renewal variable `$FLEET_VAR_CERTIFICATE_RENEWAL_ID`; legacy alias
  `$FLEET_VAR_SCEP_RENEWAL_ID` kept for back-compat (both resolve to the same
  `fleet-<profileUUID>` marker). `server/fleet/mdm.go:92-93` (the `SCEP_RENEWAL_ID` const
  is commented "deprecated in favor of FleetVarCertificateRenewalID"); both substituted at
  `server/mdm/apple/profile_processor.go:423-428` via `FleetVarRenewalIDRegexp`.
- Placement: Apple in the SCEP/ACME payload CN or OU (profile_processor.go:424 comment
  "Insert the renewal ID into the SCEP/ACME Payload CN or OU"); Windows requires it in
  `OU=` (`server/service/windows_mdm_profiles.go:322-333` `subjectNameHasRenewalIDMarker`
  matches only `OU=`), with the Windows cert identifier `$FLEET_VAR_SCEP_WINDOWS_CERTIFICATE_ID`
  in `CN=` (testdata `windows-device-scep.xml:81` `CN=…,OU=…`).
- Coverage: proxied SCEP families only — NDES, custom SCEP, Smallstep
  (`server/fleet/certificate_authorities.go:29-36` `ListCATypesWithRenewalIDSupport`).
  Rejected unless SCEP URL + challenge are also present
  (`SCEPRenewalIDWithoutURLChallengeErrMsg`, `server/service/mdm_profiles.go:113`).
- Opt-in: optional, so omitting it still installs a working cert that never renews.
Corrected the round6 finding's uncertainty: the "preferred" name it couldn't find,
`CERTIFICATE_RENEWAL_ID`, does exist at 4.90.0 (the earlier grep predated the rebase).
Variables named in prose are user-facing Fleet profile variables (same class already used
in this paragraph), not §8 code identifiers. No `$FLEET_VAR_…` value printed; links=0, no
em-dashes. 5.2 already routes profile-variable readers here, so the naming lives in 2.13.
