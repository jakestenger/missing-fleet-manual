# 2.10 Apple MDM configuration — research notes

Renumbered from 2.7 on 2026-08-30 (P6 structural moves); same chapter, new number.

Verified at **tag `fleet-v4.90.1`**, 2026-08-24. Autonomous run 3. Source:
`articles/apple-mdm-setup.md` (274 lines). Written from a 26-line outline to 192 lines.

## The organizing finding

**Connecting Fleet to Apple means holding four credentials, not one**, and they fail
differently. Three are renewed by hand; one renews itself, which is why it is the one people
forget exists.

| Credential | Lifetime | Renewed by | Failure |
|---|---|---|---|
| APNs push certificate | 1 year | You, via Apple | Commands stick in Pending; recovery is per-device |
| Apple Business token | expires | You | Automatic enrollment stops |
| Volume Purchasing token | expires | You | App Store delivery stops |
| Host SCEP certificates | 1 year | **Fleet, at 180 days** | Manually enrolled hosts lose MDM; user must re-enroll |

Fleet Premium gates Apple Business and Volume Purchasing. The push certificate does not.

## Two renewal traps, both verbatim from the guide

> When renewing, be sure to use the same Apple ID from year-to-year. If you don't, you will
> have to turn MDM off and back on for all Apple hosts.

> Make sure that the certificate's **Common Name (CN)** matches the one presented in Fleet. If
> you choose a different certificate, you must turn MDM off and back on for all Apple hosts.

They share a shape worth naming in the chapter: **the renewal appears to succeed and the
estate breaks afterwards.** No confirmation step catches either, which is why the CN check
belongs in the written procedure rather than in memory.

Fleet's own mitigation, quoted: use "a shared Apple Developer account to generate the APNs
certificate to make sure it can be renewed regardless of an employee's availability." That
sharpens the argument already made in 2.9.

## The expiry signature
> configuration profile changes and other MDM commands will remain stuck in "Pending" until
> renewal.

Diagnostically useful because Pending is also what an offline device looks like. A whole
estate in Pending while inventory still arrives is the certificate, not the devices.

## The stored-once default enrollment profile

The strongest non-obvious find. The default ADE profile is stored **once per Fleet instance**,
at first automatic-enrollment registration, and is "**not** refreshed by Fleet upgrades, by
adding or removing AB tokens, or by any other normal operation." There is no in-product reset
action.

Consequence stated in the chapter: **a fresh install and a long-running instance on the same
Fleet version can behave differently here**, and nothing surfaces it. Adopting newer defaults
means building a custom profile with those values.

## Other verified facts used

- Default fleet for automatically enrolled hosts is set **per platform** on the AB token; unset
  platforms land in Unassigned. A host can be moved to another fleet **before** it enrolls.
- **Re-enrolling an AB host clears its own stale state**: pending commands, script runs and
  software installs cancelled, completed ones cleared, labels reset. Deleting the host first is
  unnecessary.
- **That clearing is suppressed during MDM migration**, where labels and pending activity are
  preserved deliberately.
- Each VPP token corresponds to **one organization unit** in Apple Business, and is assigned to
  chosen fleets. Renew date column: yellow under 30 days, red once expired.
- One AB and one VPP token is the normal case. Fleet names four exceptions: MSPs (one per
  client), acquirers, umbrella organizations with separate purchasing authority, and
  international organizations.

## Terminology

Fleet now writes **Apple Business (AB)**. Earlier material, including this manual's 2.5
research, uses Apple Business Manager or ABM. The chapter notes the equivalence once so a
reader meeting either is not confused.

## Deliberately left out

- **Step-by-step Apple portal navigation.** Vendor UI, changes without notice, and §17 keeps
  volatile reference out of the narrative. The shape of each procedure is given; exact click
  paths are not.
- **Setup Assistant pane options.** Belongs with setup experience in Part V.
- **Per-country or per-entity token strategy detail.** The chapter names the four situations
  Fleet identifies and stops there; the multi-org guidance is long and reads as consulting
  advice rather than product behaviour.
- **SCEP renewal internals.** The 180-day cadence and the failure consequence are stated; the
  mechanism was not traced.

## 2026-08-25 review pass: an internal contradiction and a missing setup step

Independent review on `gpt-5.6-sol`. All corrections verified against
`articles/apple-mdm-setup.md` at `fleet-v4.90.1`.

### Corrected: the chapter contradicted itself on default fleets

Two statements, both published:

- "that destination is a property of the AB token rather than a global setting" and "You set a
  default fleet **per platform**"
- "**Automatic enrollment defaults are per platform, not per token.**"

The second is wrong. Per `articles/apple-mdm-setup.md:83-92`, the default fleet is set per
platform *within* each token, from that token's Actions menu. With more than one AB token each
carries its own set of per-platform defaults. Corrected, and the multi-token consequence added,
since the chapter separately explains when a second token is legitimate.

### Corrected: the APNs diagnostic works on macOS only

As published: "A whole estate in Pending at once, with hosts still reporting inventory normally,
is the certificate rather than the devices."

True for macOS, where inventory arrives through fleetd and does not depend on the push
certificate. Not true for iOS and iPadOS, which have no agent: Fleet refetches their inventory
using MDM commands (`server/fleet/mdm.go:1145`, "command prefixes are the prefixes used for MDM
commands used to refetch information from iOS/iPadOS devices"). When the certificate lapses those
hosts stop reporting and look exactly like offline devices, which is the state the diagnostic is
meant to rule out. Now qualified to macOS with the reason given.

### Added: two missing pieces of the Apple Business procedure

| Missing | Consequence | Source |
|---|---|---|
| Assigning the new server as the default in Apple Business's **Default Device Assignment** | The token uploads, the connection reports healthy, and no host ever appears | `articles/apple-mdm-setup.md:64` |
| AB token renewal | The chapter's whole premise is that three credentials need manual renewal, and it documented renewal for only one of them | `articles/apple-mdm-setup.md:69-80` |

The first is the more serious. Every visible signal says success while the integration delivers
nothing, which is the hardest kind of failure to diagnose from inside Fleet.

### Recorded, not fixed

The review argues the four-credential framing conflates three organization-level integrations
with a per-host certificate Fleet issues and renews itself, and that ownership differs
accordingly. The table already marks SCEP as the one Fleet renews automatically, and the
distinction is drawn in the prose beneath it. Left as is; revisit if the section is restructured.

## 2026-09-02 new content: "Requiring hardware-attested device identity" (round4 RM9)

Round 4 found the ACME/Managed Device Attestation setting recorded only as a compatibility-table
row in a.6, never taught anywhere. Added a new section covering the setting
(`apple_require_hardware_attestation`, Premium, off by default, at Settings > Organization
settings > Advanced > Host lifecycle), its three eligibility gates, the silent SCEP fallback,
the renewal-driven adoption lag, and certificate discoverability.

Verified against `fleet-v4.90.1` (dd0200f062):
- `server/fleet/app.go:259-261` (`AppleRequireHardwareAttestation` field), `server/service/appconfig.go:1896-1897` (Premium gate).
- `server/service/apple_mdm.go:2683-2784` (`GetMDMAppleEnrollmentProfileByToken` -> `isMDMAppleACMERequired`): the three gates are Apple Silicon + macOS >= 14.0 (`isMacACMESupported`), a non-empty device serial, and a DEP assignment record for that serial (`GetHostDEPAssignmentsBySerial`). Confirmed this endpoint serves both the ADE and the manual-link OTA enrollment paths (`mdmAppleEnrollEndpoint`, `apple_mdm.go:2508-2532`), so the DEP-assignment check is against the assignment record, not the enrollment method chosen.
- `server/service/apple_mdm.go:6490-6587` (`RenewSCEPCertificates`, `scepCertRenewalThresholdDays = 180`, `maxCertsRenewalPerRun = 100`): the same eligibility re-check runs at each 180-day renewal, but only re-checks Apple Silicon/OS version, not DEP assignment. This is also the path that would move a host back to SCEP if the setting is turned off, since it only builds an ACME-required map when the app-config flag is currently true.
- `server/service/apple_mdm.go:5981-6023` (`maybeQueueCertificateListForACMEProfile`): confirms hardware-bound keys are invisible to osquery and Fleet queues an MDM `CertificateList` command after the ACME profile install/removal ack to populate/clear `host_certificates`.
- `frontend/pages/admin/OrgSettingsPage/cards/Advanced/components/HostLifecycleSection/HostLifecycleSection.tsx:66-83`: confirms the exact UI location (Advanced > Host lifecycle), the checkbox label, Premium gating, and Fleet's own help text ("require macOS hosts with Apple Silicon that automatically enroll (DEP) to use ACME with Managed Device Attestation").
- `pkg/spec/gitops.go:194,212` for the `controls.apple_require_hardware_attestation` GitOps key; `cmd/fleetctl/fleetctl/testdata/expectedGetConfigAppConfigYaml.yml:56` and sibling fixtures for classic `fleetctl get/apply config` round-tripping the same field under `mdm:`.

No owning chapter existed; placed in [[2.10-notes]] (Apple MDM configuration) rather than 3.2
(enroll macOS devices) because the setting itself is an org-wide config toggle in the same family
as this chapter's other Apple MDM settings (Apple Business, Volume Purchasing, Setup Assistant

### Stated: verified at the tag

| Claim | Basis |
|---|---|
| It is Fleet Premium | The free implementation is a stub: `(*Service).ReleaseABDevices` in `server/service/apple_mdm.go:4569-4575` skips authorization and returns `fleet.ErrMissingLicense`; the real one is `ee/server/service/apple_mdm.go:387`. The UI gate `canReleaseFromAB` also returns false when `!isPremiumTier` |
| The endpoint is `POST /api/v1/fleet/hosts/release_ab`, taking `{"ids": [...]}` and returning per-host results | `server/service/handler.go:599`; `releaseABDevicesRequest{HostIDs []uint json:"ids"}` and `releaseABDevicesResponse{Results []*fleet.ABReleaseDeviceResponse json:"results"}` at `apple_mdm.go:4548-4556`; each result carries `HostID`, `Status` (`success`/`failed`) and `Error` (`server/fleet/apple_mdm.go:1868-1879`) |
| Fleet calls Apple's Disown Devices API | `depClient.DisownDevices(...)` in `ee/server/service/apple_mdm.go:569`, implemented at `server/mdm/nanodep/godep/device.go:135-145` as `POST /devices/disown`, with the comment "Disowning a device releases it from Apple Business" and a link to Apple's documentation |
| Apple must have "Allow this service to release devices" enabled, and Fleet reports that specific reason | The `client.AuthError` branch at `ee/server/service/apple_mdm.go:571-580` sets the per-host message "Couldn't release host from Apple Business. Apple rejected this request. Confirm that “Allow this service to release devices” is enabled in Apple Business." |
| Authorization is global admin, or admin of the host's fleet, and a host with no fleet needs a global admin | `server/authz/policy.rego:1009-1023`: one rule for `subject.global_role == admin`, one for `team_role(subject, object.team_id) == admin` guarded by `object.team_id != 0`. The service authorizes once per distinct fleet across the requested hosts (`ee/server/service/apple_mdm.go:491-498`) |
| The action is hidden unless Premium, Apple Business enabled and configured, an Apple platform, ADE-enrolled or Pending, DEP-assigned to Fleet, and the user is a global or fleet admin | `canReleaseFromAB` in `frontend/pages/hosts/details/HostActionsDropdown/helpers.tsx:425-465`, six sequential early returns in that order |
| The confirmation is a checkbox naming the host, and the copy states it cannot be undone | `ReleaseFromABModal.tsx`: "This removes <host> from your Apple Business and can't be added back automatically", and the danger checkbox "I understand this action can't be undone for <host>"; the Release button is disabled until it is ticked |
| A host still Pending is deleted from Fleet; an enrolled host is not | `DeleteHostDEPAssignments` in `server/datastore/mysql/apple_mdm.go:2551-2624`: it soft-deletes every matching `host_dep_assignments` row, then calls `deleteHosts` for the subset whose `host_mdm.enrollment_status` is Pending, with the comment "If pending host is no longer in ABM, we should delete it because it will never enroll in Fleet. If the host is later re-added to ABM, it will be re-created." The modal copy says the same to the user |
| The activity type is `released_from_ab`, carrying host id, serial and display name, and is host-linked | `ActivityTypeReleasedDeviceFromAB` in `server/fleet/activities.go:2480-2492`: `ActivityName()` returns `released_from_ab` and `HostIDs()` returns the single host, which is what puts it on the host timeline |
| Per-host failure reasons are distinct, not one batch status | `setErrorResponse` calls in `ee/server/service/apple_mdm.go` cover "Host not found.", "This is not an eligible Apple host.", "Host has no hardware serial.", "This host was not found in Apple Business.", "Host has no associated ABM token.", "ABM token not found.", the Apple-rejection message above, "Couldn't release host from Apple Business.", and "Error releasing device: <status>" |
| Requests are grouped per Apple Business token before being sent | The `dedupedTokenIDs` map and the loop over it at `ee/server/service/apple_mdm.go:552-570`; one disown call per token, with its own error handling, so one token's rejection does not stop the others |

### Derived (reasoning, not just citation)

| Conclusion | Reasoning |
|---|---|
| "An enrolled host stays enrolled, keeps its profiles, inventory and history" | Nothing on the release path touches MDM enrollment, profiles or inventory; the only writes are the soft-deleted assignment rows and, for Pending hosts, the host delete. Stated as what the code does not do, which is a weaker claim than a positive one and is written that way |
| "It will not automatically re-enroll after a wipe, because there is no longer an assignment to enroll it" | Automatic enrollment is driven by the Apple Business assignment (this chapter's own "Where automatically enrolled hosts land"). Removing the assignment removes the mechanism. Consistent with the Pending-host deletion, whose stated rationale is that the host "will never enroll" |
| "Release is not unenroll" (the edge-case bullet) | Contrasts two verified behaviours rather than citing a single source: release removes the assignment and leaves MDM; unenrolling removes MDM and leaves the assignment. Written because the modal's own copy anticipates the confusion |
| "The interface hides the action rather than explaining itself" | `canReleaseFromAB` returns a boolean consumed by the actions-dropdown filter; there is no disabled-with-tooltip path for these six conditions, unlike some neighbouring actions |
