## The framing, and why it is not 3.2's

3.2 opens by insisting the two channels are independent, because on macOS they are. On Windows that framing would mislead, and the chapter says so explicitly: the channels pull each other along in both directions, and the operator's question is which one happened first. That asymmetry is the chapter's organising idea and it is derived from the two mechanisms below rather than from anything Fleet says.

## Derived

- **The two-directions framing** is the book's own, built from the two mechanisms above.
- **"Fleetd first, then Fleet moves the host"** for migration follows from `isEligibleForWindowsMDMMigration` requiring `IsOsqueryEnrolled`, exactly as the enrollment path does.
- **"Two separate egress paths have to work"** is an inference from the server fetching the metadata document and the device fetching the MSI. Fleet does not describe it that way.
- **The `dummy` sentinel being the first thing to check** when hosts land in the wrong fleet is judgement, not a documented failure mode.

## Not claimed

- **`EUA_TOKEN`'s full round trip.** Fleet signs a token binding the Entra UPN to the device ID and the agent sends it back, but what Fleet then does with it on the enrollment side was not traced end to end. The chapter says only that it carries end-user attribution and that Fleet sets it.
- **Minimum supported Windows version.** Not established at the tag.
- **Whether the MSI build requires WiX, and on which host platforms.** `--local-wix-dir` is restricted to Windows and macOS, and the default path was not traced. Deliberately absent rather than guessed.
- **UI click paths**, per STYLE §6.

## First independent review, 2026-08-27: NOT READY. Applied.

Seven factual defects, four unmarked-unverified claims, five contradictions with neighbours. All confirmed in the source before applying.

**BitLocker enforcement was assigned to the wrong channel**, which made the chapter's opening sentence wrong. `EnforceBitLockerEncryption` is set in the **Orbit configuration response** and the agent encrypts locally; MDM enrollment is a gate on Fleet setting it, not the delivery mechanism. So it is not an MDM command, it does not appear in the Windows command queue, and a host with only one channel gets no enforcement whichever channel that is. This also resolved contradiction 1 with 1.2, which had it right.

**The chapter oversold the coupling between the channels**, and 1.2 says they are independent. Both are true in different senses and the chapter now says which: the channels **stay** independent, and what Windows adds is **conditional automation** between them in both directions. That is the durable model; "which one happened first" is now the diagnostic question rather than the architecture.

**The hourly retry throttle is narrower than it reads.** Orbit records the attempt time **only when the registration call succeeds**. A call that errors leaves the timestamp unset, so the next configuration check-in retries — thirty seconds later, not an hour. The hour applies when registration returned success and Fleet still thinks the host is unenrolled. So a persistently failing enrollment produces a **fast** loop in the log, and the chapter had told the reader to expect an hourly one.

**The credential-free MSI advice omitted the build that makes it work.** `fleetctl package` requires `--fleet-url` and `--enroll-secret` together, and the MSI carries the `--enroll-secret-path` argument only when a build-time secret was supplied — so omitting the secret produces a package that writes `secret.txt` at install time and never reads it. Fleet's own contributor documentation builds the base artifact with `--fleet-url=dummy --enroll-secret=dummy`; `dummy` is a sentinel that suppresses writing the secret while keeping the path in place. Both commands are now in the chapter. The section previously showed a build embedding a real secret and then claimed the result had no credential in it.

**The fleetd-presence grace window was described backwards.** A check-in counts as evidence of a working agent if it happened after the enrollment **or up to 90 seconds before it**. The chapter said the check-in had to postdate the enrollment with 90 seconds of slack, which inverts what the window is for: it exists so a device re-enrolling moments after a normal check-in is not sent a redundant installer.

**Two claims about the pushed install were too broad.** A **global enroll secret has to exist** or Fleet logs a warning and builds no install command at all, which is a silent no-op and belongs in the prerequisites; with several, Fleet takes the first the datastore returns. And that secret **places only new hosts** — an existing host keeps its fleet, per 3.1, which the chapter's unqualified wording had lost.

**`dsregcmd` was presented as the MDM answer.** It is Entra evidence: joined or not, and which MDM URL Entra supplied. The device's record of being managed by Fleet is the registry enrollment whose `ProviderID` is `Fleet` with a non-zero `EnrollmentState`, which is what fleetd itself reads. And an empty `MdmUrl` has **two** causes in Fleet's own notes, a missing Entra ID P1 licence *or* an MDM user scope of `None`; the chapter named only the first, which is the one that costs money to act on. 8.9 already had both right, so this was 3.3 contradicting Part VIII.

### Marked unverified rather than asserted

- **Tamper protection.** No implementation or tagged documentation establishes it. Now stated as Fleet's guidance, to confirm on a test machine, **in 2.8 as well** — 2.8 asserted it flatly and is the chapter people will quote.
- **The sign-in requirement and the thirty-second figure.** Fleet's source establishes that the agent check-in *starts* registration, and that Orbit runs as a system service and calls the registration API without inspecting who is logged in. It establishes nothing about when Windows *completes* enrollment. The chapter now draws that boundary explicitly, which also resolves contradiction 3 between 3.3 and 2.8.
- **Entra licensing**, which Fleet's Autopilot notes describe as its current understanding rather than verified.
