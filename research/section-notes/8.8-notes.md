## The finding this sweep existed for

### A 4.90.0 reconciler bug that silently skipped a fixed set of hosts

**Stated**, from the diff of `server/datastore/mysql/apple_mdm_batched.go` between the two tags, the fix's own source comment, and the 4.90.1 changelog.

The Apple profile and declaration reconcilers walk MDM hosts in pages of 5,000 (`reconcileAppleProfilesBatchSize = 5000`), ordered by UUID, carrying a cursor between pages. At 4.90.0 the page-exhausted test counted rows **after** collapsing duplicate UUIDs, and that collapse happens after the SQL `LIMIT`. The fix's comment states the consequence directly: "a full page can come back shorter than batchSize, and treating that as the end of the host universe would wrap the cursor early and starve every host later in the UUID ordering."

**Derived**, and this is why it belongs in a troubleshooting chapter: the failure is silent and stable. Affected hosts are never considered, so no command is enqueued, no `host_mdm_apple_profiles` row leaves NULL, nothing is marked `failed`, and nothing is logged. UUID ordering does not change between runs, so the same hosts are skipped every time. It presents as a group of Macs that simply never get profiles while the rest of the estate is healthy, which is exactly the shape an administrator will attribute to scoping or to the devices.

Both conditions are required: more than 5,000 Apple MDM hosts, and at least one duplicate host UUID. Declarations paginate through the same helper and were affected identically.

Added as a callout in §8.8.7 with the version check placed before anything else in the section, because every other procedure in that section would come back clean.

The same 4.90.1 diff also adds an `EXISTS` guard on `host_mdm.enrolled`, which is the changelog's separate fix for the reconciler queueing profiles for deleted hosts. Not written into the chapter; recorded here.

### 2. The `TIME` column in `fleetctl get mdm-commands` is not the queue time

**Stated.** The table is built from `r.UpdatedAt`, formatted RFC3339. The chapter listed the column without saying which timestamp it carries.

That matters in this chapter more than most, because §8.8.3's whole reading depends on how long a command has been outstanding. A command queued yesterday and answered this morning shows this morning's time and sorts to the top. The chapter now says so and points at `nano_enrollment_queue.created_at` for the age.

Also added the empty-result message, `No MDM commands have been run on this host.`, which is what the reader actually sees when a filter matches nothing.

### 3. The Android profile UUID prefix was missing

**Stated.** `server/fleet/mdm.go`: `d` declaration, `a` Apple profile, `w` Windows, `g` Android. The chapter gave three of four, in a chapter that sends readers to four different per-host profile tables.

## Confirming review, 2026-08-27: NOT READY, and why

The confirming pass returned NOT READY, and the reason is worth recording plainly: **the first application was partial and introduced two new errors.** Both are now fixed.

**Left unfixed the first time.** The state table and the query were corrected, but two other passages still carried the old queue model: hop 6 of the delivery path still said the row stays `active = 1` "until answered", and §8.8.13's narrowing still told the reader that a recent `last_seen_at` alongside a queued command means the command was handed over and has a result to decode. That second one is the exact inference the original finding existed to remove, and it survived in the section a reader reaches last, under pressure.

**Introduced by the fix.**

- **`mdm.allow_all_declarations` was omitted.** The new validation summary presented the rejection rules as absolute. The setting, off by default, turns those safety checks off entirely. The rules are now described as the default boundary with the bypass named.
- **"A manual resend resets it" is wrong.** `ResendHostMDMProfile` sets `status = NULL` and does not touch `retries`. So a resend permits one further delivery on an exhausted profile; it does not replenish the three. Corrected in both places it appeared.

**Also now applied, having been skipped as low priority the first time.** The CLI history window is **20 commands**, not the 1,000 Fleet's guide describes: `MDMListCommands` sets `defaultCommandsPerPage = 20` and does not page further. The chapter previously hedged around a number it could have stated, which is worse than either being wrong or being precise. A command missing from that list is very often just older than the twentieth.
