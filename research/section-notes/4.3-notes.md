## Derived

**"Read passing plus failing against your total."** The three states are source-backed; presenting the remainder as the population worth asking about is the chapter's argument and the reason it leads with the three states rather than two.

**"Write the query for the good state."** Follows directly from pass meaning rows returned, but stating it as an instruction is editorial, and it is the single most useful sentence in the chapter for a new author.

**The reading-honestly table.** Each row rests on a source-checked fact above; the selection and ordering are editorial.

## Deliberately not stated

**No licence gate is claimed for the `critical` flag.** I looked and did not find one, and Fleet's Premium markers around "critical" in the documentation attach to *vulnerability* severity rather than to the policy flag. Rather than assert either way, the chapter describes the flag without a tier. This is the discipline the Part I reviews forced: nine licence claims were wrong before I started checking each one against its own validation.

**No claim about how automations behave beyond the three facts that change how the policy page reads.** Attaching and operating them is 5.7's, and this chapter says so rather than half-covering it.

## Review round, 2026-08-27

NOT READY, eighteen required changes, all applied. Rewritten rather than patched, because the review's first finding took out the chapter's opening premise and its second found me contradicting myself three times.

### The opening was wrong

I wrote that a policy "runs the same way a scheduled report does, on the same channel and the same kind of schedule", and that everything 4.2 says about scope and cost applies. **Policies travel the distributed channel**, the one live reports use, not the scheduled-report path, and their results return the same way rather than through the result-log endpoint. Four things follow that the draft got wrong by inheritance:

- the cadence is `policy_update_interval`, Fleet's, not a per-policy schedule, and a refetch can bring an evaluation forward;
- report output settings, snapshot logging, `discard_data`, `discard_reports_data` and automations, do not govern policies at all;
- reports have a minimum osquery version setting and policies do not;
- **ChromeOS answers policies**, because the extension answers distributed endpoints, even though it has no scheduled reports. The draft implied the opposite by importing 4.2's rules.

### An execution error is not a failure, and I said both

Lines 52, 72 and 95 of the draft said an erroring or unscoped query makes the host fail; line 97 said the opposite. **The source is unambiguous and line 97 was the right one**: a nonzero distributed status is an execution error, ingestion records it as a nil membership result, and only a successful run becomes true or false on whether rows came back. Fleet's own transition code says failure means "executed successfully but didn't return any rows".

The reader consequence is the reason this mattered more than a wording slip: an administrator would classify an unsupported table or a SQL error as device non-compliance and go and remediate the device.

### "No answer" is not always a stored row

I wrote that it is "a stored state with no value in it". Fleet does **not** create a membership row for a host's first errored evaluation, so that host has no row; a host that previously answered and then errors keeps its row with the value cleared. The host-policy surface reports both identically, so the ordinary view cannot tell you which.

### The rest

The compliance denominator needed to be four groups rather than two, separating out-of-scope from no-answer. A host being offline does **not** age its result into no-answer: a stored verdict persists until something replaces it. The cached count timestamp is one clue when counts and host lists disagree, not the explanation. And the draft claimed Free means global-and-unlabelled, when the scope choice is global, unassigned or a named fleet.

### Licence work

The draft named two gates and there are six. Named fleets, label targeting in any mode, **the `critical` flag**, software and script attachment, and continuous automation are all Premium. I had explicitly declined to claim a gate on `critical` after failing to find one; the reviewer found it, and also found that `critical` participates in conditional access, so it is not the cosmetic priority label the draft described. The unassigned-scope creation edge is marked **unverified** rather than guessed.

### Subjects added on the completeness question

**The two policy types.** Fleet has exactly dynamic and patch. A patch policy is generated from a software title, will not accept a query or platform, and must be fleet-scoped. Its trap is that a host without the software at all is not failing to be patched.

**Edit semantics.** Editing the query **clears every pass and fail collected**, along with cached statistics and automation attempt state. Editing platform or labels removes out-of-scope memberships. Neither is reversible by changing the setting back.

**A create-and-verify procedure**, which the agreed structure asked for and the draft did not supply.

### Boundaries held

Remediation execution stayed in 5.7. Single-host diagnosis stayed in Part VIII. Query authoring and cost stayed in 4.2 and 4.6.

## Addendum, Fleet 4.91.0: the CIS benchmark policy library (SE4)

Drafted 2026-09-08 against `fleet-v4.91.0` (35fc1c024490). New `## The CIS benchmark policy library`
section between "Two kinds of policy" and "Scoping a policy". 4.3 had no CIS coverage at all, so the
library is introduced and the 4.91 change is the version table. Changelog line: "Updated the macOS CIS
benchmark policies to the latest CIS releases: macOS 14 Sonoma v3.1.0, macOS 15 Sequoia v2.1.0, and
macOS 26 Tahoe v1.1.0."

### Stated: verified at the tag

| Claim | Basis |
|---|---|
| The library is Fleet Premium | `articles/cis-benchmarks.md`, second line: "_Available in Fleet Premium_." The policies live under `ee/`, Fleet's licensed tree, which the article also states: "All CIS policies are stored under our restricted licensed folder `ee/cis/`" |
| Each recommendation becomes one ordinary policy | The same article: "Where possible, each CIS Benchmark is implemented with a policy in Fleet"; each entry in a benchmark file is a `kind: policy` document with `name`, `platform`, `description`, `resolution` and a query |
| Nothing installs them; they are converted and applied by the administrator | `articles/cis-benchmarks.md`, "How to add CIS Benchmarks": install `yq`, run the transform script over the published YAML, and apply the result as Fleet GitOps YAML. No server-side import path exists |
| Benchmark versions at this tag | Each set's README states its version: macOS 13 Ventura v3.1.0, macOS 14 Sonoma v3.1.0, macOS 15 Sequoia v2.1.0 (`ee/cis/macos-1{3,4,5}/README.md`, "Fleet's policies have been written against vX of the benchmark"), and macOS 26 Tahoe v1.1.0 (`ee/cis/macos-26/README.md`, "Fleet policies for the **CIS Apple macOS 26 Tahoe Benchmark, v1.1.0**", with a "v1.1.0 update" section listing what changed from v1.0.0) |
| Policy counts per set | Counted the `name:` keys in each `cis-policy-queries.yml` at the tag: 111, 105, 108, 90 for macOS 13, 14, 15 and 26 |
| Windows 10, Windows 11 and a Windows 11 Intune variant are published too | `ee/cis/win-10/`, `ee/cis/win-11/`, `ee/cis/win-11-intune/` |
| Some recommendations cannot be checked by a query, and each set says which | The Limitations section of each README, e.g. macOS 14's list of ten including "2.1.2 Audit App Store Password Settings", "2.6.6 Audit Lockdown Mode", "3.7 Audit Software Inventory", and two with reasons given (an osquery table lacking an internal/external indicator, and a CIS Manual audit) |
| The policies assess rather than remediate | `articles/cis-benchmarks.md`: "Because the policy queries alone do not remediate security issues, a host may fail a CIS Benchmark policy if there is no device profile or script in place to enforce the setting" |
