# 4.6 Advanced osquery: query design, tables, and performance, citation ledger

First draft, 2026-08-27, against `fleet-v4.90.1` (dd0200f062).

## Stated

| Claim | Source at the tag |
|---|---|
| Fleet collects per-host scheduled query statistics carrying executions, average memory, system and user time, output size, last executed, interval and a denylisted flag | `server/service/osquery_utils/queries.go`, the schedule-stats ingestion building `fleet.ScheduledQueryStats`; the struct in `server/fleet/scheduled_queries.go` |
| Fleet aggregates CPU time per query as fiftieth and ninety-fifth percentiles, with a total execution count | `server/fleet/scheduled_queries.go`, `AggregatedStats` carrying `SystemTimeP50`, `SystemTimeP95`, `UserTimeP50`, `UserTimeP95` and `TotalExecutions` |
| Per-host statistics are overwritten rather than retained as a series | Established during 4.2's review: `server/datastore/mysql/scheduled_queries.go` overwrites on update |
| osquery denylists queries that repeatedly misbehave, and Fleet surfaces the flag per host | The `denylisted` column ingested above; Fleet's own query comments warn that large queries "can cause performance issues or be denylisted" |
| Fleet's own source avoids expensive host-side work for this reason | `server/service/osquery_utils/queries.go`: a comment noting work is done on the server because doing it on the device "resulted in denylisted queries during testing" |
| A query's platform scope and minimum osquery version are properties of the saved query | `server/fleet/queries.go`, established for 4.2 |
| A host result set above the per-host threshold stores nothing for that host | Established during 4.2's review: `server/datastore/mysql/query_results.go` bails at more than 1000 rows |

## Derived

**"Cost is a design decision, not an optimisation."** The chapter's organising claim, and editorial. It is supported by the denylist behaviour being per host and silent, but stated as advice.

**The six design habits** are editorial. Constraining the expensive table, aggregating on the host, and preferring a cheap table are general osquery practice rather than Fleet behaviour; they are presented as habits rather than as rules the product enforces.

**"The ninety-fifth percentile is the more useful of the two."** Editorial judgement about which number to read. The percentiles themselves are source-checked.

**"Denylisting produces a result set biased toward newer hardware."** Follows from denylisting being per host, but the bias claim is derived and is the reason the chapter raises it at all.

## Deliberately not stated

**No watchdog limits or thresholds.** osquery's watchdog memory and utilisation limits, and the denylist duration, are osquery's rather than Fleet's, and I have not established the values Fleet ships or whether fleetd overrides them. The chapter describes the mechanism and names no numbers. **Flag for review**: if fleetd sets these flags, they belong here.

**No claim about which tables are expensive.** Naming specific tables would be an osquery claim rather than a Fleet one, and it would date. The chapter describes the shape of an expensive table instead.

**No claim about time units per table.** The warning that units differ is real and general; enumerating which table uses which unit is osquery documentation's job.

## Boundaries held

Getting a result out of Fleet stays in 4.2 and is cited rather than repeated. Diagnosing a single host that stopped answering stays in 8.4 and 8.7. Degradation at the server rather than the host is 8.14. Managing queries as code is named and handed to 6.2.
