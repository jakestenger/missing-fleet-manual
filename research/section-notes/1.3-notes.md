# 1.3 Hosts, fleets, labels: citation ledger

## 2026-08-25 review pass

Independent review on `gpt-5.6-sol`.

### Corrected: duplicate identifiers do not always merge

As published: "**Two devices sharing a hardware identifier merge rather than fail** ... Fleet
records this rather than rejecting it, so the symptom is one host record whose details keep
changing, rather than an error anyone notices."

True on the default path and false on another. `server/datastore/mysql/hosts.go:2675-2690` logs a
warning and lets the newer enrollment overwrite, but immediately below, an enrollment carrying a
TPM-backed host identity certificate whose host ID does not match is **rejected** with an error.
The comment is explicit: "We do not support duplicate host identifiers when using TPM-backed host
identity certificates."

So the same underlying problem presents as a silent merge in one deployment and a loud enrollment
failure in another, and the published text told a reader on the second path to look for a symptom
they will never see. Both behaviours are now described, along with what decides which one applies.

Another instance of the recurring pattern: a correct reading of one code path stated as a
universal rule. `build/check-absolutes.py` did not flag "merge rather than fail"; the phrasing is
outside its pattern set.

### Corrected: transfer described as close to a no-op

As published: "a transfer between two similarly configured fleets is close to a no-op on the
device itself."

Profile reconciliation for Apple and Windows is deferred to a periodic job rather than performed
during the transfer (`server/fleet/datastore.go:1657-1666`), so the host settles over the
following minutes. Little is asked of the device, but it is not immediate, and an administrator
verifying a transfer straight afterwards will see an incomplete state that is not a fault.

## Part I re-review, 2026-08-27

NOT READY, and the heaviest of the Part I reviews: nine factual defects, five unsourced claims and five cross-chapter contradictions. Two of the nine were load-bearing enough that the chapter's central advice changed.

### The two that mattered most

**Targeting modes are per item, and no two items agree.** The chapter offered one three-mode table as though targeting were a single control. It is four modes, and each item type supports a different subset with different combination rules: policies alone have `exclude_all` and alone permit one include *and* one exclude together; profiles permit one include mode plus exclude-any; software permits exactly one mode and rejects any combination; reports have no exclusion at all. A reader following the old table would write payloads Fleet refuses. Replaced with a per-item matrix, and the screenshot brief rewritten to capture two controls side by side, since no single capture can stand for all four.

**A fleet does not duplicate everything, and the asymmetry runs both ways.** The chapter said a fleet is a complete configuration set and a host receives its fleet's configuration "and no other". Profiles and software are exact-scope, so that half is right. Policies, scheduled reports and labels are not: the selection accepts a null scope alongside the host's own, so a global one applies inside every fleet. The chapter's advice therefore had readers copying global policies into each fleet, running every check twice, which is the exact drift it warned against.

### The rest

| Claim as written | Why it was wrong |
|---|---|
| The exclusion freshness guard applies to "the item" | It is implemented for profiles and software. **Policy selection has no equivalent**, so a fresh exclusion on a policy is not fail-closed |
| "An installed profile does not un-install itself when the truth arrives" | It does. Fleet queues installed profiles for removal when label membership takes a host out of scope. The reason to withhold delivery is the slow visible round trip, not permanence |
| "Devices being evaluated or newly enrolled land" in Unassigned | Placement happens at enrollment and follows the path: the secret carries a fleet, an Apple Business token has per-platform defaults, Android and ChromeOS differ again. Unassigned is where a host lands when nothing said otherwise, not a staging area |
| Four mutually exclusive label "kinds" | Two independent fields. Three membership types (dynamic, manual, host vitals) and a separate owner field (regular, built-in). Built-ins have membership types like anything else, and Fleet ships more than one kind |
| Stale membership means "anything targeting it still delivers" | An include over-delivers and an **exclude under-delivers**, and the second is invisible because there is no failure to see. The membership timestamps are the signal, and 8.6 already had them |
| Both names for one thing fail "in a query string" only | JSON request bodies reject the pair too, with their own conflict error |
| Named fleets, fleet labels and label targeting described as generally available | **Named fleets are Premium**, fleet-scoped labels have their own gate, label targeting is gated separately again for policies, reports and profiles, and software deployment is Premium outright. 1.4 had said fleets were Premium all along |

### Unsourced claims removed

"Almost always a fleet doing a label's job", "routinely surprise people", duplicate hosts "usually" merging, "many organizations" running an Unassigned baseline. "One case is genuinely destructive" became "one consequence is irreversible", since a transfer discards several things and the ranking was not established. "A locked disk has no recovery path" became "Fleet no longer holds a recovery key for that disk", which is what the source shows; whether anything else holds one is not Fleet's to know.

The time-based tiebreaker survived as a heuristic with its exception stated: **agent options are fleet-scoped and labels take no part in selecting them**, so an update-channel pilot needs a fleet however short-lived, which is what 3.7 says. The summary's "a group that needs its own profiles or software wants a fleet" was wrong for the same reason in reverse, since both can be label-targeted inside an existing fleet.

### Added

The transfer section now records that Fleet authorizes the move against **both** the source and destination fleets, so a partially scoped administrator is refused.

## Third round, 2026-08-27

NOT READY, seven items. Same shift as 1.2: mostly refinements and propagation rather than fabrication, but three were substantive.

| The claim | Why it was wrong |
|---|---|
| "A fleet with no options of its own falls back to the global ones" | True for the **osquery** half of agent options and false for the **Orbit** half. `update_channels`, `command_line_flags` and extensions are read from the fleet's own document, with only the script execution timeout falling back, which is why 3.7's update-channel guidance disagreed with this row. Split by consumer |
| "Labels play no part in selecting agent options" | Too broad. Extensions are agent options and **can** be filtered by label, with that filter independently Premium. Narrowed to update channels specifically |
| The freshness guard "delivers to the hosts that have reported" | It makes them **eligible to be judged**, not entitled to the item: the include labels still have to match and an exclusion still excludes. Same mistake was in 8.6 |
| The guard described as applying to any exclusion label | **Dynamic labels only.** The query tests `label_membership_type = 0`, so manual membership is trusted immediately and a fresh manual exclusion takes effect at once. That makes a manual exclusion the safe way to stage one |
| "No two item types share the same set of modes" | Contradicted the table two lines below it. Profiles and software share the same three modes and differ only in whether an include and an exclude may be combined |
| "Two devices sharing a hardware identifier merge" | Path-dependent. Serial matching is limited to Apple MDM enrollment on supported Apple platforms and skipped elsewhere; UUID matching depends on the enrollment identifier |
| Transfer losses "recoverable through another report" | The host rebuilds state in the **destination** scope. Old-fleet policy results, report results and label memberships are deleted and never rebuilt, because the host is never evaluated against a scope it has left |

8.6 took the matching corrections: a differing `team_id` is decisive for profiles and software and irrelevant for a globally scoped policy, report or label, and the exclusion-guard rows now separate dynamic from manual labels.
