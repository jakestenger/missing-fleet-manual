## The team -> fleet rename mechanism (VERIFIED, this is the good stuff)

Fleet implements the rename as a **struct tag alias layer**, not a hard rename.

- Struct tag: `renameto:"fleet_id"` alongside `json:"team_id"` and `db:"team_id"`.
  Example `server/fleet/labels.go:214` (`Label.TeamID`), `:225` (`LabelWithTeamName.TeamName
  renameto:"fleet_name"`), `:233` (`LabelSummary.TeamID`), `:296` (`LabelSpec.TeamID`).
- Tag consumers:
  - `server/platform/endpointer/endpoint_utils.go:157` `extractAliasRulesRecursive` builds
    `[]AliasRule{OldKey, NewKey, Inline}` by walking the struct recursively.
  - `server/platform/endpointer/endpoint_utils.go:295-320`: **query-string params** accept the
    OLD name (from the `query` tag) or the NEW name (from `renameto`). If BOTH are supplied the
    request fails 400 with `Specify only one of "<old>" or "<new>"`. Using the old name logs a
    deprecation warning when logging topic `DeprecatedFieldTopic` is enabled.
  - `server/platform/endpointer/json_key_duplicator.go:17-47` `DuplicateJSONKeys`:
    API **responses carry BOTH names**. "if a rule maps OldKey:"team_id" -> NewKey:"fleet_id",
    and the JSON contains "team_id": 42, the output will contain both "team_id": 42 and
    "fleet_id": 42." Renamed containers split into old-subtree/new-subtree; renamed leaves are
    duplicated in place as siblings. `Inline` opts a container into merged duplication (docstring
    example: `abm_tokens` carrying both `macos_team` and `macos_fleet`).
    If the new key already exists in the same object scope, duplication is skipped.
  - `pkg/spec/gitops_validate.go:114-117`: GitOps registers the `renameto` alias as an accepted
    key, so GitOps YAML accepts both spellings.
  - `cmd/fleetctl/fleetctl/generate_gitops.go:113` uses it when generating GitOps YAML.
  - `tools/ci/apiparamcheck/apiparamcheck.go:58` is a CI check over the tag.
- 65 Go files carry a `renameto` tag at this tag.

## Label scoping: parameter names and semantics

API/GitOps key names (all snake_case JSON):
`labels_include_any`, `labels_include_all`, `labels_exclude_any`, `labels_exclude_all`.
- policies carry all four: `server/fleet/api_policies.go:15-17` (+ `LabelsExcludeAll`, see
  `server/fleet/policies.go:199-234`).
- software/VPP carry three: `server/fleet/vpp.go:39,43,47` (payload) and `:129,131,133`
  (response, with `db:` tags of the same names).
- queries carry only two, include_any / include_all: `server/fleet/queries.go:313-319`
  `verifyQueryLabelScopeMutualExclusion`. Error `ErrQueryConflictingLabels` =
  "report can include at most one of labels_include_any or labels_include_all"
  (`server/fleet/queries.go:310`). Confirmed by schema: `query_labels` (schema.sql:2687) has
  `require_all` but NO `exclude` column.
- `premium:"true"` tag on the policy label fields, so label targeting is Premium.

`LabelScope` string enum (`server/fleet/labels.go:397-411`): `"exclude_any"`, `"include_any"`,
`"include_all"`. Three only. (Policy `labels_exclude_all` is validated in policies.go but is not
in this enum.)
NOTE the source doc comment for `LabelScopeIncludeAny` is WRONG: it reads "should be applied to a
host that if the host is a member of all of the associated labels" (copy/paste of include_all).
The SQL is any-of. See SQL below.

### Validation rules
- Policies (`server/fleet/policies.go:199-234` `verifyPolicyLabelScopes`): at most ONE include
  scope and at most ONE exclude scope may carry values. An include and an exclude scope MAY be
  combined. No label may appear in both an include and an exclude list, error
  `label %q cannot appear in both an include and an exclude list`. Empty slice `[]` counts as
  "no value", so `{labels_include_any: [], labels_include_all: [A]}` is valid.
  Errors: `ErrPolicyConflictingIncludeLabels`, `ErrPolicyConflictingExcludeLabels`.
- `LabelOverlap(include, exclude)` (`server/fleet/labels.go:385-395`) returns the first name
  present in both unions.

### On-disk encoding: two booleans, not an enum
Join tables encode the scope as `exclude` + `require_all` tinyints, not a scope string:
- `mdm_configuration_profile_labels` (schema.sql:1979): `apple_profile_uuid`,
  `windows_profile_uuid`, `android_profile_uuid` (CHECK constraint
  `ck_mdm_configuration_profile_labels_profile_uuid` requires EXACTLY ONE of the three non-null),
  `label_name` varchar(255) NOT NULL, `label_id` int NULL, `exclude` tinyint default 0,
  `require_all` tinyint default 0. FK `label_id` -> `labels(id)` ON DELETE RESTRICT.
  `label_name` is denormalised alongside `label_id`.
- `mdm_declaration_labels` (same shape, `apple_declaration_uuid`; see
  `server/datastore/mysql/apple_mdm.go:5302-5312`).
- `software_installer_labels` (schema.sql:3072): `software_installer_id`, `label_id` NOT NULL,
  `exclude`, `require_all`.
- `vpp_app_team_labels` (schema.sql:3394): `vpp_app_team_id`, `label_id` NOT NULL, `exclude`,
  `require_all`.
- `policy_labels` (schema.sql:2608): `policy_id`, `label_id`, `exclude`, `require_all`.
- `query_labels` (schema.sql:2687): `query_id`, `label_id`, `require_all`. No `exclude`.

Mapping: `exclude=0,require_all=0` -> include_any; `exclude=0,require_all=1` -> include_all;
`exclude=1,require_all=0` -> exclude_any; `exclude=1,require_all=1` -> exclude_all (policies only).

### The actual evaluation SQL (server/datastore/mysql/vpp.go:2855-2935, Android VPP branch;
### the same three-branch UNION shape recurs for installers and profiles)
Per branch, counts and HAVING:
- include_any: `WHERE exclude = 0 AND require_all = 0`,
  `HAVING count_installer_labels > 0 AND count_host_labels > 0`.
  So: host is in AT LEAST ONE of the labels.
- include_all: `WHERE exclude = 0 AND require_all = 1`,
  `HAVING count_installer_labels > 0 AND count_host_labels = count_installer_labels`.
  So: host is in EVERY label.
- exclude_any: `WHERE exclude = 1 AND require_all = 0`,
  `HAVING count_installer_labels > 0 AND count_installer_labels = count_host_updated_after_labels
   AND count_host_labels = 0`.
  So: host is in NONE of the labels, AND every one of those labels is "trustworthy" for this host.

**The trust term is the heart of the exclude-any timing hazard.** Verbatim source comment
(vpp.go:2881-2884): "exclude any, ignore software that depends on labels created _after_ the
label_updated_at timestamp of the host (because we don't have results for that label yet, the
host may or may not be a member)."
`count_host_updated_after_labels` sums 1 per label when EITHER
  (a) `lbl.label_membership_type = 0` (dynamic) AND `hosts.label_updated_at >= lbl.created_at`, OR
  (b) `lbl.label_membership_type = 1` (manual), unconditionally.
Manual labels are trusted immediately. Dynamic labels are trusted only once the host has reported
label results at or after the label's creation time. Until then the whole exclude-any scope is
withheld (nothing is delivered) rather than delivered-by-default.

### Null-safe fleet match
The scoping join uses MySQL's null-safe equality: `hosts.team_id <=> vpp_apps_teams.team_id`
(vpp.go:2873, 2907, 2928). `<=>` returns true for NULL <=> NULL, which is how the no-fleet bucket
matches its own scoped content. A plain `=` would never match an unassigned host.

### 4.90.1 fix, in the source
`server/datastore/mysql/apple_mdm.go:7931-7941`: on Apple MDM reset the code calls
`upsertMDMAppleHostLabelMembershipDB` to "restore builtin label memberships for mdm reset", then

## Built-in label membership at Apple enrollment
`server/datastore/mysql/apple_mdm.go:2081-2141` `upsertMDMAppleHostLabelMembershipDB`.
Verbatim comment: "Builtin label memberships are usually inserted when the first distributed query
results are received; however, we want to insert pending MDM hosts now because it may still be some
time before osquery is running on these devices. Because these are Apple devices, we're adding them
to the "All Hosts" and one of "macOS", "iOS", "iPadOS" labels."
- Lookup: `SELECT id, name FROM labels WHERE label_type = 1 AND (name = 'All Hosts' OR name =
  'macOS' OR name = 'iOS' OR name = 'iPadOS')`. Looked up BY NAME, not by ID:
  "We cannot assume IDs on labels, thus we look by name."
- If the result is not exactly 4 rows it logs `expected 4 builtin labels but got %d` and
  **returns nil (silently does nothing)**. Comment: "Builtin labels can get deleted so it is
  important that we check that they still exist before we continue."
  EDGE CASE: delete or rename any one of those four built-ins and Apple hosts stop getting
  pre-osquery built-in memberships, with only a server-log error to show for it.
- Platform mapping: `ios` -> iOS, `ipados` -> iPadOS, default (assume `darwin`) -> macOS.
- Insert is `INSERT INTO label_membership (host_id, label_id) VALUES ... ON DUPLICATE KEY UPDATE
  host_id = host_id`, i.e. idempotent no-op on conflict.

### Precedence when a host matches more than one package of a title
`server/datastore/mysql/software.go:3833-4001` `resolveFirstAddedInstallersForHost`.
Verbatim: "resolves, for each of the given titles, the package to display for this host: the
first-added (smallest installer_id) active package the host is in label scope for."
Ranking (software.go:3995-4001): candidate packages are ranked in tiers,
1. platform-compatible AND in-scope, 2. in-scope, 3. platform-compatible, 4. any active package.
"Rows are ordered installer_id ASC, so within each tier the first-added package wins."
So the tie-break is **lowest `software_installers.id`**, i.e. the package added first.
Platform compatibility outranks add-order: an in-scope package for the wrong platform loses to a
compatible in-scope one. Compat test at software.go:3853-3854: `r.Platform == hostPlatform ||
((r.Extension == "sh" || r.Extension == "py") && r.Platform == "linux" &&
fleet.IsUnixLike(host.Platform))`.
Tier 4 is display-only. Verbatim: "The fallback is display-only: availability and install decisions
use inScope (below) and never the fallback, so a host is never offered or sent a package it isn't
scoped for."
- Same first-added rule in setup experience: `server/datastore/mysql/setup_experience.go:336-337`
  "the first-added (smallest installer_id) package per title so setup doesn't double-queue; labels
  don't apply during setup. VPP apps are single-package per title, so they pass through untouched."
  NOTE: **labels do not apply during setup experience.**
- `SoftwareScopeLabel.RequireAll` json tag is `"-"` (not rendered)
  (`server/fleet/software_installer.go:1275`).

## Host identity: how Fleet decides "is this the same host?"

`server/datastore/mysql/hosts.go:2294-2368` `matchHostDuringEnrollment(ctx, q, enrollType,
isAppleMDMEnabled, osqueryID, uuid, serial, platform)`.
It builds a UNION of up to three lookups, each stamped with a numeric `priority`, then sorts by
priority ascending and takes row 0. Lowest priority number wins.

| Priority | Match on | Condition |
|---|---|---|
| 1 | `hosts.osquery_host_id = ?` | whenever `osqueryID != "" \|\| uuid != ""`. If `osqueryID` is empty the `uuid` is substituted ("special-case, if there's no osquery identifier, use the uuid") |
| 2 | `hosts.hardware_serial = ?` AND `platform IN ('darwin','ios','ipados')`, `ORDER BY id LIMIT 1` | only when serial non-empty AND Apple MDM enabled AND NOT (orbit enroll with an explicit osquery identifier) AND platform != android. Comment: "Apple DEP pre-creates host records with hardware_serial set, so orbit-enroll can find them this way." |
| 3 | `hosts.uuid = ?` AND `platform = 'android'`, `ORDER BY id LIMIT 1` | android only, same orbit guard |

`nodeKeyColumn` is `orbit_node_key` for orbit enrolls, `node_key` for osquery enrolls; the query
selects `<col> IS NOT NULL AS node_key_set`. For `mdmEnroll` the column does not matter.
Guard var: `orbitEnrollingWithOsqueryIdentifier := enrollType == orbitEnroll && osqueryID != ""`,
with comment "We want to prevent orbit enrolling with an osquery identifier to be matched with the
serial number."
No match -> `sql.ErrNoRows` -> a brand-new `hosts` row.

### EnrollOrbit (`server/datastore/mysql/hosts.go:2370-...`)
- Requires non-empty `orbit_node_key` and non-empty `HardwareUUID`. Serial may be empty:
  "NOTE: allow an empty serial, currently it is empty for Windows." (hosts.go:2387)
- Windows never matches by serial: `serialToMatch = ""` when `platform == "windows"`,
  "For Windows, don't match by serial number to retain legacy functionality." (hosts.go:2399-2402)
- Match branch UPDATE (hosts.go:2433-2444) sets `orbit_node_key = ?` and fills only EMPTY fields:
  `uuid = COALESCE(NULLIF(uuid,''), ?)`, `osquery_host_id = COALESCE(NULLIF(osquery_host_id,''), ?)`,
  `hardware_serial = COALESCE(NULLIF(...))`, `computer_name`, `hardware_model`,
  `refetch_requested`. **`team_id` is absent from the UPDATE**: re-enrollment does NOT move the host
  between fleets, even with an enroll secret belonging to a different fleet.
- Also on re-enroll: `DELETE FROM host_mdm_actions WHERE host_id = ?`, and if the previous platform
  was `windows` and the new one is not, `DELETE FROM host_mdm WHERE host_id = ?`
  ("so that hosts that get re-imaged with other OS don't show erroneous MDM status").
- If `node_key_set` was already true it logs WARN "orbit host with duplicate identifier has enrolled
  in Fleet and will overwrite existing host data" with `identifier` and `host_id`. Comment: "This can
  happen if two devices have duplicate hardware identifiers or if orbit's node key file was deleted
  from the device (e.g. uninstall+install)."
- TPM host identity certs do NOT tolerate duplicates: mismatch returns "orbit host identity cert host
  id does not match enrolled host id. This is likely due to a duplicate UUID/identity identifier used
  by multiple hosts: %s" (hosts.go:2424-2429).
- New-host INSERT (hosts.go:2488-2507) sets `team_id` from the enroll secret, `refetch_requested = 1`,
  and `node_key = orbit_node_key` initially: "We are also initially setting node_key to be the same
  as orbit_node_key because node_key has a unique constraint."
  `last_enrolled_at`, `detail_updated_at`, `label_updated_at`, `policy_updated_at` all set to
  `common_mysql.GetDefaultNonZeroTime()` (2000-01-01 UTC), described as "the canonical "never"
  sentinel ... so CleanupExpiredHosts does not immediately delete it."
- Comment at hosts.go:2551-2558 explains the returned uuid can diverge from the submitted hardware
  UUID because the match can be by `osquery_host_id` or `hardware_serial` while the UPDATE preserves
  the existing uuid.

## The no-fleet bucket: NULL in the DB, 0 in the API

- DB: `hosts.team_id` is NULLABLE. No fleet == `team_id IS NULL` (schema.sql:1414).
  FK `hosts_ibfk_1 ... ON DELETE SET NULL`, so **deleting a fleet moves its hosts to no fleet**
  rather than deleting them.
- API/service layer: 0 is the no-fleet id. `server/fleet/policies.go:150-151`
  `// PolicyNoTeamID is the team ID of "No team" policies.` `const PolicyNoTeamID = uint(0)`.
- Name constants (`server/fleet/teams.go:15-35`):
  `TeamNameNoTeam = "No team"`, `TeamNameAllTeams = "All teams"`,
  `ReservedNameNoTeam = "No team"`, `ReservedNameAllTeams = "All teams"`,
  and the newer display names `DisplayNameNoTeam = "Unassigned"`,
  `DisplayNameAllTeams = "All fleets"` ("Display names used in user-facing error messages").
  `IsReservedTeamName` (teams.go:38-47) reserves all four, case-insensitively, NFC-normalised:
  "no team", "all teams", "unassigned", "all fleets". You cannot name a fleet any of them.
- **THE precedence quote** (`server/fleet/apple_mdm.go:458-462`, `EffectiveTeamID`):
  "returns 0 for hosts not in a team. team_id=0 is its own team (the "no team" / global scope),
  NOT a fallback for teamed hosts: a host with team_id=5 matches profiles with team_id=5 only, it
  does not also inherit team_id=0 profiles. Equality between EffectiveTeamID and a profile's team_id
  is the correct match check."
  Same wording in `server/fleet/windows_mdm.go:639`, `server/fleet/datastore.go:2457,2501`.
  So there is NO inheritance from no-fleet down into fleets. Scopes are disjoint, not nested.
- `server/fleet/datastore.go:1809`: "A nil (or 0) teamID scopes to "No team" (team_id IS NULL)".
- `server/fleet/software_installer.go:152,206,218`: "A value of nil means it is scoped to hosts that
  are assigned to "No team"."
- Some features are no-fleet-only: `server/fleet/mdm.go:1244` "VPP token is available only for
  "No team" team." (verify scope of that claim before citing broadly)

## API surface: /fleets is canonical, /teams is a registered alias

`server/service/handler.go:321-331,370-375,556-559`: canonical routes are
`/api/_version_/fleet/fleets`, `/fleets/{id}`, `/fleets/{id}/secrets`, `/fleets/{id}/agent_options`,
`/fleets/{id}/users`, `/fleets/{fleet_id}/policies`, `/fleets/{fleet_id}/schedule`,
`POST /api/_version_/fleet/spec/fleets`.
Path variable names are a mix: `{fleet_id}` in newer routes, `{id}` in the CRUD routes.

`server/service/handler_deprecated_paths.go` holds a declarative table
`deprecatedPathAliases []eu.DeprecatedPathAlias` with **47 entries** at this tag, registered by
`endpointer.RegisterDeprecatedPathAliases(r, apiVersions, registry, deprecatedPathAliases)`
(`server/service/handler.go:1258-1259`). Each entry maps `Method` + `PrimaryPath` to one or more
`DeprecatedPaths`, and the alias is wired to **the same handler**, so both paths behave identically.
Categories, verbatim from the file header comment:
  "teams -> fleets: team CRUD, secrets, agent_options, users, spec /
   team/teams -> fleets: policies, schedule (both singular and plural deprecated) /
   queries -> reports: query CRUD, spec, report data /
   host queries -> reports /
   live queries -> reports: run, run_by_identifiers, run_by_names /
   ABM/VPP token teams -> fleets"
Registration panics at startup if the primary handler is missing
(endpoint_utils.go:882-883), so the table cannot silently rot.
Hitting a deprecated path logs at WARN with extras `deprecated_path` and `deprecation_warning`
= "API `<old>` is deprecated, use `<new>` instead" (endpoint_utils.go:858-872), gated on the
`DeprecatedFieldTopic` logging topic.

**So the vocabulary split, precisely:**
| Surface | Word | Note |
|---|---|---|
| UI | fleet | |
| DB tables/columns | `teams`, `team_id` | no `fleets` table exists |
| API path | `/fleets` canonical, `/teams` alias | 47 alias entries, WARN logged |
| API path var | `{fleet_id}` (new routes), `{id}` | mixed |
| API JSON body/response | BOTH `team_id` and `fleet_id` | responses duplicate the key |

## Host transfer between fleets: exactly what happens

Datastore: `server/datastore/mysql/hosts.go:3609-3671` `AddHostsToTeam`.
Batched at `BatchSize: 10_000` by default (`server/fleet/hosts.go:1883-1889`
`NewAddHostsToTeamParams`; comment "A large number of hosts could be changing teams at once, so we
need to batch this operation to prevent excessive locks"). Each batch is one `withRetryTxx`
transaction. Order inside the transaction:

1. `cleanupPolicyMembershipOnTeamChange` (`server/datastore/mysql/policies.go:2076-2093`):
   `DELETE FROM policy_membership WHERE policy_id IN (SELECT id FROM policies WHERE team_id IS NOT
   NULL) AND host_id IN (?)`. Fleet-scoped policy results are dropped; **global policy results
   survive**. Then `updateHostIssuesFailingPolicies`.
2. `cleanupQueryResultsOnTeamChange` (policies.go:2110-2124):
   `DELETE FROM query_results WHERE query_id IN (SELECT id FROM queries WHERE team_id IS NOT NULL)
   AND host_id IN (?)`. Fleet-scoped saved query results dropped, global ones survive.
3. `cleanupLabelMembershipOnTeamChange` (policies.go:2095-2108):
   `DELETE FROM label_membership WHERE label_id IN (SELECT id FROM labels WHERE team_id IS NOT NULL)
   AND host_id IN (?)`. **Only FLEET-SCOPED label memberships are dropped. Global label memberships
   (team_id IS NULL), which is most labels including all built-ins, survive the transfer.**
4. `cleanupConditionalAccessOnTeamChange` (policies.go:2126-2136):
   `DELETE FROM microsoft_compliance_partner_host_statuses WHERE host_id IN (?)`. Unconditional.
5. `UPDATE hosts SET team_id = ? WHERE id IN (?)`.
6. `cleanupDiskEncryptionKeysOnTeamChangeDB` (`server/datastore/mysql/disk_encryption.go:358-373`):
   looks up the destination fleet's Apple FileVault profile by
   `mobileconfig.FleetFileVaultPayloadIdentifier`. If the destination has NO FileVault profile it
   runs `DELETE FROM host_disk_encryption_keys WHERE host_id IN (?)`.
   **DESTRUCTIVE: transferring a host into a fleet with no FileVault profile deletes its escrowed
   recovery key.** Comment: "We are using Apple's encryption profile to determine if any hosts,
   including Windows and Linux, are encrypted. This is a safe assumption since encryption is enabled
   for the whole team." So a Windows or Linux host's escrowed key is deleted based on the presence of
   an *Apple* profile in the destination.
7. `reconcileHostDeviceNamesForTeamDB` (hosts.go:3659): host-name template enforcement.
   Comment: "eligible hosts moving into a template team get queued rows, and hosts moving to a
   template-less team or "No team" have their rows deleted."

Service layer: `server/service/hosts.go:1249-1325` `(*Service).AddHostsToTeam`.
- Authorizes `fleet.ActionTransferHost` against the DESTINATION (`&fleet.Host{TeamID: teamID}`),
  then separately authorizes the SOURCE fleets of every host via `authorizeHostSourceTeams`.
  You need write access to both ends.
- Android: `CreatePendingCertificateTemplatesForNewHost(hostUUID, destTeamID)` per host,
  `UpdateTeamIDOnAndroidDevices` to sync `android_devices.team_id`, and
  `QueueBulkSetAndroidAppsAvailableForHosts`.
- `BulkSetPendingMDMHostProfiles(ctx, hostIDs, nil, nil, nil)` unless `skipBulkPending`.
  This is what recomputes profile deltas: profiles only in the old fleet get queued for removal,
  profiles only in the new one get queued for install, **profiles present in both are left alone**.
  (The 4.90.1 Windows fix in CHANGELOG is about the display side of exactly this: "a Windows
  configuration profile staying listed on Host details > OS settings when it stopped applying to a
  host but another profile on that host still enforced all of the same settings. This affected
  deleting or renaming a profile, and transferring a host between fleets with matching profiles.")
- Apple ADE hosts: `ListMDMAppleDEPSerialsInHostIDs` then
  `worker.QueueMacosSetupAssistantJob(..., worker.MacosSetupAssistantHostsTransferred, teamID,
  serials...)`, i.e. the DEP profile is re-assigned to match the new fleet's setup assistant.
- Ends with `createTransferredHostsActivity`.
- `ee/server/service/mdm.go:1284` calls it with `skipBulkPending = true`.

NOT touched by a transfer (verified by absence in the above):
- `hosts.id`, `uuid`, `hardware_serial`, `osquery_host_id`, `node_key`, `orbit_node_key`.
- global label memberships, global policy results, global query results.
- software inventory (`host_software`), host vitals, activity history.
- `hosts.label_updated_at` is NOT reset, so a transferred host's exclude-any trust state carries
  over for global labels.

## Dynamic label membership: the pipeline and its timing

1. Host posts to the osquery distributed/read endpoint (channel 2 in 1.2).
2. `svc.labelQueriesForHost` (`server/service/osquery.go:867-877`): gate on
   `shouldUpdate(labelReportedAt, svc.config.Osquery.LabelUpdateInterval, host.ID)`.
   Bypassed when `host.RefetchRequested` is true.
   - `LabelUpdateInterval` config key `osquery.label_update_interval`, YAML
     `label_update_interval`, **default 1 hour** (`server/config/config.go:267,1460`).
     Siblings: `osquery.policy_update_interval` 1h, `osquery.detail_update_interval` 1h.
   - `shouldUpdate` (osquery.go:846-866) adds **per-host jitter** from a jitter hash table sized
     `MaxJitterPercent * interval.Minutes() / 100`; config `osquery.max_jitter_percent`,
     **default 10** (config.go:281,1472). Cutoff is `now - (interval + jitter)`.
     So a host's label refresh lands somewhere in a window, not on the hour.
3. `ds.LabelQueriesForHost` (`server/datastore/mysql/labels.go:928-955`):
   `SELECT id, query FROM labels WHERE (platform = ? OR platform = '') AND
    label_membership_type = ? AND (team_id IS NULL OR team_id = ?)`
   with `fleet.LabelMembershipTypeDynamic` and `host.TeamID`.
   Three filters worth stating: **only dynamic labels are ever sent to osquery** (manual and
   host_vitals labels are never distributed), the label's `platform` must match the host's or be
   empty, and a fleet-scoped label goes only to hosts in that fleet (global labels go to everyone).
4. Queries go out named `fleet_label_query_<label_id>` (`server/service/osquery.go:642,1126`
   `hostLabelQueryPrefix = "fleet_label_query_"`; detail queries use
   `hostDetailQueryPrefix = "fleet_detail_query_"`).
5. Results come back on the distributed/write endpoint and land via
   `ds.RecordLabelQueryExecutions` (`server/datastore/mysql/labels.go:957-1054`).
   Results are `map[uint]*bool`. Three cases, per label:
   - `nil` -> **membership left untouched**. Comment: "The query errored (e.g. extension socket
     unavailable), rather than returning a definitive 0 rows. Leave existing membership untouched."
   - `true` -> `INSERT INTO label_membership (updated_at, label_id, host_id) ... ON DUPLICATE KEY
     UPDATE updated_at = VALUES(updated_at)`.
   - `false` -> `DELETE FROM label_membership WHERE host_id = ? AND label_id IN (?)`.
   Label IDs are sorted ascending before building the SQL "to have generated SQL queries ordered to
   minimize deadlocks. See https://github.com/fleetdm/fleet/issues/1146."
6. Then `UPDATE hosts SET label_updated_at = ? WHERE id = ?` (labels.go:1027), unless
   `deferredSaveHost`, in which case it goes through `ds.writeCh` as a `hostXUpdatedAt` item with
   `what: "label_updated_at"` (labels.go:1037-1053). Async path equivalents:
   `AsyncBatchInsertLabelMembership`, `AsyncBatchDeleteLabelMembership`,
   `AsyncBatchUpdateLabelTimestamp` (labels.go:1679-1697). Comment at labels.go:988-994 says the two
   paths must stay semantically equivalent.

**So `hosts.label_updated_at` is "when this host last reported a complete label result set", and it
is the trust watermark the exclude-any guard reads.** Timing consequence: a dynamic label created at
time T is not trusted for any host until that host's next label report after T, which is up to
`label_update_interval + jitter` (default up to about 66 minutes) away, and longer for an offline
host.

## GitOps surface

Directory layout (verified against the repo's own dogfood config, `it-and-security/`):
`default.yml`, `fleets/<fleet-name>.yml`, `fleets/unassigned.yml`, `lib/`.
`it-and-security/fleets/` at this tag contains: company-owned-mobile-devices.yml,
personal-mobile-devices.yml, servers.yml, testing-and-qa.yml, unassigned.yml, workstations.yml.
`it-and-security/fleets/unassigned.yml` starts with `name: Unassigned`.
`pkg/spec/gitops.go:683-684`: `noTeam = "No team"`, `unassignedTeamName = "Unassigned"`.
`IsNoTeam()` / `IsUnassignedTeam()` (gitops.go:667-673) match either spelling, case-insensitively.
Fleet name is free text and may contain emoji (dogfood uses `name: "💻 Workstations"`).

Top-level keys accepted in a fleet/global file (`pkg/spec/gitops.go:522`):
`name`, `settings`, `org_settings`, `agent_options`, `controls`, `policies`, `reports`, `software`,
`labels`, `custom_host_vitals`.
Omitting a top key defaults it to `null`, "This will clear the settings as if the key was provided
with an empty value" (gitops.go:602-606), EXCEPT `name`, `labels`, `software`, `custom_host_vitals`,
`settings`, `org_settings`, which are skipped from that defaulting (gitops.go:590).
So omitting `labels` preserves labels; omitting `policies` deletes them.

`labels` is rejected in the unassigned file: `if result.IsNoTeam() { logFn("[!] 'labels' is not
supported in %s. This key will be ignored.\n", ...) }` (gitops.go:610-616). Docs agree
(`docs/Configuration/yaml-files.md:11`): "Labels cannot be specified in `fleets/unassigned.yml`."

Label keys (`docs/Configuration/yaml-files.md:15-27`, backed by `fleet.LabelSpec`):
`name`, `description`, `platform`, `label_membership_type` (default `dynamic`), `query`, `hosts`,
`criteria`. Plus `path:` / `paths:` file references (yaml-files.md:1374 lists `scripts`,
`configuration_profiles`, `labels`, `policies`, `reports` as supporting both).
- Docs: "Must be unique across all global and fleet labels." Matches the DB
  `UNIQUE KEY idx_label_unique_name (name)`.
- Docs: "Changing a label's `name` in GitOps will delete and re-create the label, temporarily
  clearing its membership. To avoid this, update the label name in the UI before making the change
  in YAML." NAME IS THE IDENTITY IN GITOPS. Big edge case.
- Docs: `hosts` accepts `id`, `hardware_serial`, or `uuid`; "The `hostname` host identifier is
  deprecated." Omitted -> membership preserved; present but empty -> all hosts removed. Matches the
  `Label.UnmarshalJSON` special case in `pkg/spec/gitops.go:260-280` which distinguishes an omitted
  `hosts` key from an explicit null.
- Docs: "Only one of `query`, `hosts`, or `criteria` can be specified. If none are specified, a
  manual label with no hosts will be created."
- Docs: "Any labels referenced in other sections (like policies, reports or software) _must_ be
  specified in the `labels` section."
- Docs (yaml-files.md:453,461,604): "Only one of `labels_include_all`, `labels_include_any`, or
  `labels_exclude_any` can be specified. If none are specified, all hosts are targeted."
  **No labels at all = every host in the fleet.**
- Docs (yaml-files.md:218): "If using `labels_include_any`/`labels_exclude_any` for targeting, these
  keys are specified on the individual policies. Specifying at the top level of `policies` will
  _not_ apply the labels to each policy." Silent no-op trap.
- Docs (yaml-files.md:28): including `labels` in `default.yml` deletes unlisted GLOBAL labels;
  including it in `fleets/<name>.yml` deletes that fleet's unlisted labels; omitting it changes
  nothing. Consequence noted in the docs: GitOps mode does NOT lock label editing in the UI.

## RBAC (server/authz/policy.rego)

Actions (policy.rego:13-22): `read`, `list`, `write`, `create` ("only for labels right now"),
`write_host_label`, `cancel_host_activity`, `transfer_host`, `resend`, `read_secrets`,
`write_members`. `ActionTransferHost = "transfer_host"` (`server/fleet/authz.go:16-19`, comment
"refers to transferring a host between fleets (teams)").

Transfer:
- Global `admin`, `maintainer`, `technician`, `gitops` may transfer any host (policy.rego:343-348).
- Fleet-scoped `admin`, `maintainer`, `technician`, `gitops` may transfer hosts **of their own
  fleet** (policy.rego:387-395). Verbatim: "This is needed both for write access to the source team
  (where the host currently is) and the destination team (where the host is being transferred to);
  the service layer authorizes both sides separately."
  So a fleet-scoped admin can only move hosts between fleets they administer.

Labels:
- Read: global admin/maintainer/technician/observer_plus/observer/gitops (policy.rego:426-431).
- Fleet users can read GLOBAL labels, with `any([is_null(object.team_id), object.team_id == 0])`
  and the comment "allow specifying team ID 0 for listing exclusively global labels"
  (policy.rego:433-440). Another place where 0 stands in for NULL.
- Create: global admin/maintainer/technician/gitops; fleet-scoped roles of the same names may
  create GLOBAL labels (`is_null(object.team_id)`, policy.rego:456-462).
- Write: global roles as above. A fleet-scoped role may write a global label **only if they
  authored it** (`not is_null(object.author_id)` and `object.author_id = subject.id`,
  policy.rego:464-472). That is what `labels.author_id` is for.
- Fleet-scoped labels: read by any role on that fleet (policy.rego:474-480), write by
  admin/maintainer/technician/gitops on that fleet (policy.rego:482+).
