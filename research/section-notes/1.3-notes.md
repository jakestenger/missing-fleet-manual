# 1.3 Hosts, fleets, labels: citation ledger

## 2026-08-25 review pass

Independent review on `gpt-5.6-sol`.

### Corrected: duplicate identifiers do not always merge

As published: "**Two devices sharing a hardware identifier merge rather than fail** ... Fleet
records this rather than rejecting it, so the symptom is one host record whose details keep
changing, rather than an error anyone notices."

True on the default path and false on another. `server/datastore/mysql/hosts.go:2675-2690` logs a
warning and lets the newer enrollment overwrite, but immediately below, an enrollment carrying a
TPM-backed host identity certificate whose host ID does not match is **rejected** with an error.
The comment is explicit: "We do not support duplicate host identifiers when using TPM-backed host
identity certificates."

So the same underlying problem presents as a silent merge in one deployment and a loud enrollment
failure in another, and the published text told a reader on the second path to look for a symptom
they will never see. Both behaviours are now described, along with what decides which one applies.

Another instance of the recurring pattern: a correct reading of one code path stated as a
universal rule. `build/check-absolutes.py` did not flag "merge rather than fail"; the phrasing is
outside its pattern set.

### Corrected: transfer described as close to a no-op

As published: "a transfer between two similarly configured fleets is close to a no-op on the
device itself."

Profile reconciliation for Apple and Windows is deferred to a periodic job rather than performed
during the transfer (`server/fleet/datastore.go:1657-1666`), so the host settles over the
following minutes. Little is asked of the device, but it is not immediate, and an administrator
verifying a transfer straight afterwards will see an incomplete state that is not a fault.

encryption removes the escrowed recovery key, that it applies across platforms rather than only
macOS, and that the destination should be confirmed first. Verified against
`server/datastore/mysql/disk_encryption.go:358-386`, where the absence of a FileVault profile on
the destination triggers `bulkDeleteHostDiskEncryptionKeysDB`, and the comment confirms the Apple
profile governs Windows and Linux hosts too. **No change made.**

Recorded because reviewer findings are not automatically right, and this one bundled a correct
observation about the deletion section with an incorrect one about the transfer section.

### Fixed in passing

"Lables" at line 231. Swept the manual for that and five other common misspellings; none remain.

## Part I re-review, 2026-08-27

NOT READY, and the heaviest of the Part I reviews: nine factual defects, five unsourced claims and five cross-chapter contradictions. Two of the nine were load-bearing enough that the chapter's central advice changed.

### The two that mattered most

**Targeting modes are per item, and no two items agree.** The chapter offered one three-mode table as though targeting were a single control. It is four modes, and each item type supports a different subset with different combination rules: policies alone have `exclude_all` and alone permit one include *and* one exclude together; profiles permit one include mode plus exclude-any; software permits exactly one mode and rejects any combination; reports have no exclusion at all. A reader following the old table would write payloads Fleet refuses. Replaced with a per-item matrix, and the screenshot brief rewritten to capture two controls side by side, since no single capture can stand for all four.

**A fleet does not duplicate everything, and the asymmetry runs both ways.** The chapter said a fleet is a complete configuration set and a host receives its fleet's configuration "and no other". Profiles and software are exact-scope, so that half is right. Policies, scheduled reports and labels are not: the selection accepts a null scope alongside the host's own, so a global one applies inside every fleet. The chapter's advice therefore had readers copying global policies into each fleet, running every check twice, which is the exact drift it warned against.

### The rest

| Claim as written | Why it was wrong |
|---|---|
| The exclusion freshness guard applies to "the item" | It is implemented for profiles and software. **Policy selection has no equivalent**, so a fresh exclusion on a policy is not fail-closed |
| "An installed profile does not un-install itself when the truth arrives" | It does. Fleet queues installed profiles for removal when label membership takes a host out of scope. The reason to withhold delivery is the slow visible round trip, not permanence |
| "Devices being evaluated or newly enrolled land" in Unassigned | Placement happens at enrollment and follows the path: the secret carries a fleet, an Apple Business token has per-platform defaults, Android and ChromeOS differ again. Unassigned is where a host lands when nothing said otherwise, not a staging area |
| Four mutually exclusive label "kinds" | Two independent fields. Three membership types (dynamic, manual, host vitals) and a separate owner field (regular, built-in). Built-ins have membership types like anything else, and Fleet ships more than one kind |
| Stale membership means "anything targeting it still delivers" | An include over-delivers and an **exclude under-delivers**, and the second is invisible because there is no failure to see. The membership timestamps are the signal, and 8.6 already had them |
| Both names for one thing fail "in a query string" only | JSON request bodies reject the pair too, with their own conflict error |
| Named fleets, fleet labels and label targeting described as generally available | **Named fleets are Premium**, fleet-scoped labels have their own gate, label targeting is gated separately again for policies, reports and profiles, and software deployment is Premium outright. 1.4 had said fleets were Premium all along |

### Unsourced claims removed

"Almost always a fleet doing a label's job", "routinely surprise people", duplicate hosts "usually" merging, "many organizations" running an Unassigned baseline. "One case is genuinely destructive" became "one consequence is irreversible", since a transfer discards several things and the ranking was not established. "A locked disk has no recovery path" became "Fleet no longer holds a recovery key for that disk", which is what the source shows; whether anything else holds one is not Fleet's to know.

The time-based tiebreaker survived as a heuristic with its exception stated: **agent options are fleet-scoped and labels take no part in selecting them**, so an update-channel pilot needs a fleet however short-lived, which is what 3.8 says. The summary's "a group that needs its own profiles or software wants a fleet" was wrong for the same reason in reverse, since both can be label-targeted inside an existing fleet.

### Added

The transfer section now records that Fleet authorizes the move against **both** the source and destination fleets, so a partially scoped administrator is refused.

## Third round, 2026-08-27

NOT READY, seven items. Same shift as 1.2: mostly refinements and propagation rather than fabrication, but three were substantive.

| The claim | Why it was wrong |
|---|---|
| "A fleet with no options of its own falls back to the global ones" | True for the **osquery** half of agent options and false for the **Orbit** half. `update_channels`, `command_line_flags` and extensions are read from the fleet's own document, with only the script execution timeout falling back, which is why 3.8's update-channel guidance disagreed with this row. Split by consumer |
| "Labels play no part in selecting agent options" | Too broad. Extensions are agent options and **can** be filtered by label, with that filter independently Premium. Narrowed to update channels specifically |
| The freshness guard "delivers to the hosts that have reported" | It makes them **eligible to be judged**, not entitled to the item: the include labels still have to match and an exclusion still excludes. Same mistake was in 8.6 |
| The guard described as applying to any exclusion label | **Dynamic labels only.** The query tests `label_membership_type = 0`, so manual membership is trusted immediately and a fresh manual exclusion takes effect at once. That makes a manual exclusion the safe way to stage one |
| "No two item types share the same set of modes" | Contradicted the table two lines below it. Profiles and software share the same three modes and differ only in whether an include and an exclude may be combined |
| "Two devices sharing a hardware identifier merge" | Path-dependent. Serial matching is limited to Apple MDM enrollment on supported Apple platforms and skipped elsewhere; UUID matching depends on the enrollment identifier |
| Transfer losses "recoverable through another report" | The host rebuilds state in the **destination** scope. Old-fleet policy results, report results and label memberships are deleted and never rebuilt, because the host is never evaluated against a scope it has left |

## Fourth round, 2026-08-27

NOT READY, four items, and one of them corrects something I had been confident about twice.

**Fleet keeps an archive of superseded disk-encryption keys.** I had written that a transfer to a fleet without encryption enforcement deletes "the only copy Fleet had", and the reviewer withdrew its own earlier acceptance of that wording. Fleet writes a host's previous key to `host_disk_encryption_keys_archive` whenever a differing key is reported, so a host whose key has been rotated at least once has something archived; a host on its first and only key does not. The chapter now says the **active** key is deleted, names the archive as a possible mitigation to ask about, and stops calling the loss irreversible.

The global-scope model was correct in the opening and the matrices and **reintroduced three sections later**, where the targeting explanation still called every global item organization-wide. That is the propagation shape again, in a chapter whose own table two screens up says otherwise.

Three unsupported claims survived: "not the behaviour most people expect", "most investigations end at a fleet mismatch", and "the single most-copied wrong assumption".

## Capped at the review limit, 2026-08-27

Five rounds, every finding from every round applied, last verdict NOT READY. Under the owner's rule the chapter now stays at `drafting` and waits for the whole-part review once Parts IV to VII are drafted.

**What five rounds actually bought.** Round one found fabricated claims. Rounds two and three found the corrections to those claims. Rounds four and five found propagation failures, corrections applied in one passage while the same claim survived in a table, an alt text, an image prompt or a neighbouring chapter. The defect count did not fall to zero and there is no sign it was going to; what changed was the *kind* of defect, from wrong to inconsistent, and inconsistency is cheaper to attack with `claims.py` and a grep than with another review.

**Round five's own finding is the one worth remembering.** The disk-encryption archive paragraph was wrong in a way neither of us caught for two rounds, because the function's **comment** says it archives the existing key and its **code** inserts the incoming one. An absent active key counts as different, so a host's very first key is archived too, and the read path falls back to the newest decryptable archived copy. An integration test confirms it. I had written the opposite twice: first that the key was the only copy, then that only rotated keys are archived. Read the statement, not the comment.

## Addendum, Fleet 4.91.0: the `linux` label platform option (IA15)

Drafted 2026-09-08 against `fleet-v4.91.0` (35fc1c024490). New
`#### A dynamic label can be restricted to a platform` subsection under `### Labels group hosts`,
placed before "Labels can themselves be fleet-scoped". Changelog line: "Added `linux` as a label
platform option, which targets hosts on any Linux distribution."

### Stated: verified at the tag

| Claim | Basis |
|---|---|
| The valid platform values are unset, `darwin`, `windows`, `linux`, `ubuntu`, `centos` | `ValidLabelPlatformVariants` in `server/fleet/labels.go:145-152`, with the inline comment on `linux`: "matches hosts on any Linux distribution" |
| Only a dynamic label may carry a platform | `ValidateLabelMembershipFields` in `server/fleet/labels.go:156-198`: the manual branch appends "label %q is declared as manual but contains a platform", the host-vitals branch the equivalent, and only the dynamic branch checks the value against the allow-list |
| The platform decides which hosts are asked the query at all | `LabelQueriesForHost` in `server/datastore/mysql/labels.go:953-965`: `WHERE (platform IN (?) OR platform = '') AND label_membership_type = ?`, with the host's platform set supplied by `platformsForHost` |
| A Linux host matches both its specific platform and the generic `linux` | `platformsForHost` at `server/datastore/mysql/labels.go:938-951`: `if fleet.IsLinux(specific) && specific != "linux" { return []string{specific, "linux"} }`, and the function comment "Linux hosts additionally match the generic 'linux' platform regardless of distribution" |
| CentOS is matched by inspecting the OS version of an `rhel` host | Same function: `if host.Platform == "rhel" && strings.Contains(strings.ToLower(host.OSVersion), "centos") { specific = "centos" }` |
| The interface offers exactly those six choices, labelled "All platforms", "macOS", "Windows", "Linux", "Ubuntu (Linux)", "CentOS (Linux)" | `platformOptions` in `frontend/pages/labels/components/PlatformField/PlatformField.tsx:25-32` |
| The platform is fixed at creation and not editable afterwards | The `PLATFORM_STRINGS` comment in the same file: "Used to display the platform of an existing label on the edit label page (platform is not editable after creation)", and the `isEditing` branch rendering plain text rather than the dropdown |
| `IsLinux` is a membership test against Fleet's list of Linux platform strings | `server/fleet/hosts.go:1350-1352`, `slices.Contains(HostLinuxOSs, hostPlatform)` |

### Derived (reasoning, not just citation)

| Conclusion | Reasoning |
|---|---|
| "Before 4.91 the only Linux choices were those two distributions" | `linux` is the only addition to the allow-list, and the UI option list matches it one for one. Recorded as a version boundary claim from the changelog plus the current allow-list, not re-verified at the 4.90 tag |
| "A label meant to cover the whole Linux estate had to be left unrestricted and carry the distribution test inside its own query, on every host including the Macs and Windows machines" | Follows from the query gate: an unset platform matches every host, so the query runs everywhere. This is the cost the new option removes, and it is the reason the feature is worth a reader's attention rather than a line in a changelog |
| "Not a third kind of label" | Written deliberately to avoid contradicting the section's existing organising claim that two independent properties describe a label (membership source and ownership). The platform is a constraint on how one membership type is computed, not a classification axis, and the prose says so rather than leaving the reader to reconcile them (§27, read against the chapter) |
| "A platform chosen too narrowly means building a new label rather than editing this one" | Operational consequence of the stated immutability. Label names are globally unique (this chapter already says so), so the rebuild also means renaming, which is not spelled out here because the naming constraint is two paragraphs away |
