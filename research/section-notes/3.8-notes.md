## 2026-08-25 review pass

Independent review on `gpt-5.6-sol`, run after the chapter was written and committed.

### Corrected: the chapter described one clock and there are two

As published: "Three timings decide how quickly a channel change reaches an estate", followed by
the update interval, the jitter and the retry cooldown.

Those three describe Orbit polling the **update repository** for new content on its current
channel. A **channel change made in Fleet** travels by a different route entirely: Orbit polls
Fleet for configuration on a roughly thirty-second interval
(`client/orbit_client.go:193`, `defaultOrbitConfigReceiverInterval = 30 * time.Second`), records
the new `update_channels` value, and restarts, with the restart followed by its own update check
(`orbit/cmd/orbit/orbit.go:1368-1379`, whose comment names `update_channels` as a trigger).

So the chapter told an administrator to wait on the wrong clock, by roughly fifteen minutes
against under a minute.

### Corrected: the cooldown is per artifact, not per agent

As published: "A host that cannot reach the update server, or that fails on a broken package,
goes quiet for a day rather than retrying continuously."

`pkg/retry/limited_with_cooldown.go:33-38` keys both the retry count and the cooldown by hash:
`retries map[string]int // retries tracks the number of retries for each hash key`. The doc
comment states the requirement as "retry n consecutive times **per hash**, then wait for a defined
cooldown."

So a host failing on one artifact is not silenced for everything else, and a corrected build is a
new target that the old cooldown does not hold back. The published version would have led someone
to wait out a day that was never going to apply.

**This is the ledger's own failure, not just the chapter's.** The row asserting the cooldown was
filed under **stated**, citing `retry.NewLimitedWithCooldown(3, 24*time.Hour)`. That line does say
three and 24 hours. What it does not say is *per what*, and the answer was one file away. Citing a
line correctly is not the same as establishing its scope, and a "stated" row can carry an
inference inside it.

  (`articles/fleet-4.43.0.md:39-47`). The chapter presents agent options as available without

- Fleet-level agent options replace organization-level options rather than merging with them

## Corrected 2026-08-27, before any review, from Part III's organising-claim rule

Four of Part III's five first reviews came back NOT READY on the sentence the chapter is built around, so 3.8's timing claims were checked against `orbit/pkg/update/runner.go` rather than against what the chapter already said. One of them was wrong, and it was the one that shapes what an operator expects.

**Retracted the same day. The original chapter was right and this "correction" was wrong.**

I checked `orbit/pkg/update/runner.go`, saw that `NewRunner` only computes hashes and that `Execute` creates a ticker and waits, and concluded Orbit performs no startup update check. It does. `orbitAction` calls `updateRunner.UpdateAction()` **before starting any subsystem**, with a source comment saying the early check exists so that a bug elsewhere cannot interfere with fetching updates, and Orbit exits if that check updates Orbit itself. I had read the runner and not its caller, which is the same partial-reading mistake this project keeps recording, committed while applying a rule written to prevent it.

So the chapter's original claims hold: Orbit checks at startup and then on its interval, a restart is followed by a check, and a channel change therefore takes effect in about a minute. The text is restored to that, with the mechanism named rather than asserted, and the verification bullet put back.

**What survives from the wrong pass, because it is independently true:** the periodic loop's first tick really is one interval plus jitter with no immediate run, and the jitter is capped at the smaller of the interval and ten minutes rather than a flat ten. Both are now stated as properties of the loop that follows the startup check, which is where they belong.

**And one thing the mistake turned up:** an agent packaged with updates disabled performs no startup check and runs no update loop, so neither clock applies and a channel change reaches it and does nothing. The chapter said updates-disabled is a packaging decision agent options cannot undo; it now also says what that means for the timings in this section.

**The jitter cap is the smaller of the interval and ten minutes**, not a flat ten. At the default fifteen-minute interval it is up to ten, which is what the chapter said; a deployment that shortened the interval gets proportionally less. Stated precisely now, because the whole point of the paragraph is estate-wide spread.

**Added:** on a host without Fleet Desktop, Orbit drops the desktop channel from the comparison entirely, so setting it neither applies nor triggers a restart. A `desktop` value that appears to work on some hosts and not others is that, rather than a failed rollout.

**Re-verified and held:** `update_channels` is Fleet Premium, rejected with `ErrMissingLicense` in agent-options validation; an omitted component is treated as `stable` on both sides of the comparison, which is why a block naming only `orbit` moves the other two; and the override lands in `server-overrides.json`, which is the file 8.2 inventories.

### Chrome extension naming reconciled across four chapters, 2026-08-27

3.6's review pointed out that this manual calls the ChromeOS extension "fleetd" in some places and "not fleetd" in others, and that the extension's actual name is *Fleetd for Chrome*. Checking the four places found a real error underneath the naming problem.

**1.1 and 3.8 both listed the extension as a component of the fleetd bundle.** It is not. The bundle is Orbit and osquery, with Fleet Desktop as a packaging option, and it is installed on macOS, Windows and Linux. ChromeOS gets a browser extension instead, carrying none of those components. Describing it as bundle content implies a Mac's fleetd contains a Chrome extension, which it does not, and implies the extension is subject to this chapter, which it is not either.

Standardised on: the bundle is Orbit and osquery; *Fleetd for Chrome* is a separate artifact that does fleetd's job on the one platform where the bundle does not exist. 1.1, 1.2, 3.1 and 3.8 now agree.

**And it removed 3.8 from a claim it should never have made.** The extension's manifest carries its own `update_url` at a Fleet-published address, and **Chrome** performs the update; Orbit and the TUF repository are not involved. So none of this chapter's subject matter, channels, update intervals, retry cooldowns, agent options, reaches it, and the chapter now says so rather than listing the extension among the things it governs.

## First independent review, 2026-08-27: NOT READY. Applied.

3.8 had never been reviewed. Eight required corrections, and the largest are the two absolutes the chapter opens with.

**"Changing a channel without rebuilding installers requires Fleet Premium" is wrong about what Premium buys.** Orbit accepts `--orbit-channel`, `--osqueryd-channel` and `--desktop-channel` and their `ORBIT_*_CHANNEL` environment variables, so any deployment can change a channel by editing a host's service configuration and restarting. What Premium gates is doing it **centrally**, through `update_channels` in agent options. The chapter said as much in two other places and contradicted itself in the sentence a reader acts on.

**"Once fleetd is installed it keeps itself current" contradicted the chapter's own updates-disabled material**, and that material was itself too narrow: `--disable-updates` and `ORBIT_DISABLE_UPDATES` exist at runtime, so it is not only a packaging decision. What is true and worth keeping is that **Fleet cannot undo it**.

**The pinning rule was wrong.** A prefix moves: `4` follows every `4.x.x`, `4.6` follows every `4.6.x`. Only the full three-part version pins. The chapter said a prefix "does not move", three lines after correctly explaining that prefixes track.

**Two `update_channels` state transitions were missing, and one of them is how you would try to undo a pin.** Removing the block entirely is a **no-op**: Orbit treats an absent block as the server not using the feature and leaves each host on its last recorded channel. So removing it stops managing channels centrally and does not reset anything, which is the opposite of the natural expectation. And a channel name that does not exist freezes that component with host-side errors rather than failing visibly in Fleet.

**Two version facts the chapter needed.** Remote channel configuration requires **fleetd 1.20.0**; older agents ignore the block, which looks exactly like a change that did not apply. And Fleet documents a restart loop when a packaged channel and a server channel disagree across that boundary downwards, which is a hazard in precisely the old-agent estates the 1.38.1 stepping-stone section is about.

**Fleet Desktop is a component of the bundle, optional, not something alongside it.** Fleet's own architecture documentation lists it as an optional fleetd component and `--fleet-desktop` puts it in the package. The component table now has all three rows.

**The rollout-ring advice deferred a prerequisite to a.3, which is a stub.** Two things now stated here: a host in a fleet gets **that fleet's** agent options *instead of* the global ones rather than merged with them, so a pilot fleet's block has to carry everything else those hosts need; and writing agent options is an administrator or GitOps operation.

**And the under-a-minute promise had survived my own backoff correction**, in the concluding sentence of the paragraph that introduced the backoff, in the verification bullet, and in the image brief. All three now say one configuration poll, thirty seconds healthy and up to five minutes after sustained failures, plus download and restart.

## Third round, 2026-08-27

NOT READY, three defects and two contradictions, one of which was worth the round on its own.

**8.4 and 3.8 disagreed on the Orbit bridge version**, 1.38.0 against 1.38.1. Fleet's configuration reference says 1.38.1, and it matters exactly here: a host stranded below the update-server migration has to be pointed at 1.38.1 specifically, and aiming it one patch lower leaves it stranded while looking like an ordinary upgrade. 8.4 corrected.

**8.4 also concluded that Free hosts must keep their packaged channels.** The Premium gate covers the *central* route, agent options; a Free deployment can still change a host's channels on the host, through Orbit's flags and environment variables. That is a per-host operation rather than a fleet-wide one, and it is a real answer for a small estate.

The three chapter defects: the channel taxonomy was presented as closed when Fleet accepts an arbitrary channel name and an organisation running its own repository can publish any tag it likes; "cannot upgrade directly to anything newer" included 1.38.1 in "anything newer" and so contradicted the bridge instruction six lines below; and the configuration backoff is exponential with jitter rather than a doubling, triggered by any error from the cycle including a failure applying the configuration, not only server or network errors.
