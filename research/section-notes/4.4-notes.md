## Derived

**"A finding is a conclusion from two inputs."** The chapter's organising claim. Each input is source-checked; framing the finding as their product, and observing that incompleteness in either shortens the list rather than erroring, is the manual's argument and the reason the chapter opens with the inventory switch rather than with vulnerabilities.

**The prioritisation order**, known-exploited then probability then reach then remediability, is editorial. The fields are source-checked; the ordering is judgement and is presented as such rather than as Fleet behaviour.

**"Version matching is the source of most false positives, and Linux distributions are where it bites."** The backporting problem is real and is why Fleet carries OVAL and goval data at all, but the word "most" is a frequency claim I have hedged into. **Flag for review**: either establish it or state the mechanism without the ranking.

## Deliberately not stated

**No claim about which feed covers which platform in detail.** The directory listing establishes that several sources exist; mapping each to its coverage needs a check per source that I have not done, and a wrong map here would be worse than the general statement that coverage differs.

**No claim about vulnerability history retention.** The agreed structure assigns exposure history to this chapter, and I have not verified the CVE dataset's retention or resolution. **Flag for review**: this is a named gap rather than an omission I am unaware of.

**No count of vulnerability sources.** The directory has entries that are not all feeds, so a count would be wrong in the way 4.1's detail-query count would have been.

## Boundaries held

Installing and updating software is Part V's, and the chapter hands over at the version rather than describing delivery. Patch policies are named and their trap repeated from 4.3, without re-explaining them. Single-host software absence goes to 8.4. Self-hosting concerns about feed reachability go to 2.2.

## Review round, 2026-08-27

NOT READY, fifteen required changes, all applied. Rewritten. Two findings corrected claims I had also written into other chapters.

### The thesis was one-directional and the failure is two-directional

I wrote that incomplete inputs make the conclusion "wrong in the direction that looks like good news". Stale inventory also **over-reports**: software uninstalled a week ago that Fleet still believes is present produces findings for risk that no longer exists. The chapter and the image brief now carry both directions.

### `software_updated_at` does not mean what I said, in two chapters

I described it as advancing when Fleet finishes reconciling a host's software. It advances when Fleet **changes** the stored software, inside the block that runs after an insert or delete. A host reporting the same software every hour leaves the field untouched, so three weeks old is consistent with perfect reporting and nothing installed. **Fleet exposes no host-level timestamp proving a successful unchanged refresh.** Corrected here and in 4.1's producer table.

### The rest

**Inventory disabled is not a silent clean page.** Fleet shows an explicit disabled state. And disabling collection is not deleting data: previously stored software stays.

**The setting is two-level.** Global, with a per-fleet features override, so "is inventory on" is a per-scope question. Added a procedure with that precedence and the dependency on the global vulnerability job.

**`disable_data_sync` is not "sync broken".** Five states look alike: downloading normally, externally provisioned deliberately, sync failing, local data failing to load, and matching failing. Only the first two are intended, and the second is indistinguishable from the third if the external process stops.

**Software and OS vulnerabilities are separate pipelines** with separate data and switches, including one that disables Windows OS vulnerability processing. They remediate differently, which is the reason the distinction belongs in a reading chapter.

**Mobile inventory was overgeneralised.** A personally owned iOS or iPadOS device reports only the apps Fleet manages, not its own; **iOS and iPadOS application vulnerabilities are not supported at this release**, so an empty mobile list is expected rather than clean.

**Six enriched fields, not three.** Publication date, description and resolved version join the three prioritisation signals. Only the three signals are Premium. **Free is not without ranking**: identifier, host count and detection date remain, which the draft told readers to ignore.

**A Premium null is not necessarily a sync fault**; it means no value is available, which may be an upstream gap. And **EPSS is a thirty-day prediction**, so a low score is not evidence that nobody is exploiting it, which is the reading my draft invited.

### Added on the completeness question

Vulnerability exposure history, which the agreed structure assigned here and my ledger flagged as a known gap: critical severity only, over a curated software set, about a month retained, seven days shown by default, and **the interface gates it on Premium** although the chart route itself has no separate licence check. A prioritisation and drill-down workflow ending at a version and a population. And the platform coverage map.

### Propagated

The patch-policy boundary went back into **4.3**: it is built from a Fleet-maintained app and is **Premium**, so it is not available for an arbitrary title you package yourself. My 4.3 draft said only that it must be fleet-scoped.

## Addendum, Fleet 4.91.0: Adobe plugins in software inventory (IA7)

Drafted 2026-09-08 against `fleet-v4.91.0` (35fc1c024490). New `### Adobe Creative Cloud plugins`
subsection under `## Where software inventory comes from`. Changelog line: "Added Adobe plugins to
software inventory: Fleet now detects Adobe Creative Cloud plugins (CEP and UXP extensions) on macOS
and Windows hosts and lists them on the Software page and host details with the software type
'Plugin (Adobe)', including version and host count."

### Stated: verified at the tag

| Claim | Basis |
|---|---|
| Collection is a detail query named `software_adobe_plugins`, selecting from an `adobe_plugins` table, platforms `darwin` and `windows` | `softwareAdobePlugins` in `server/service/osquery_utils/queries.go:1221-1237`, registered as `generatedMap["software_adobe_plugins"]` at `:3666` and appended to the software results at `server/service/osquery.go:1583-1584` |
| The results join the other software queries rather than being ingested separately | The comment on `softwareAdobePlugins`: "Has no IngestFunc, DirectIngestFunc or DirectTaskIngestFunc because the results of this query are appended to the results of the other software queries" |
| The query runs only where the table is registered | `Discovery: discoveryTable("adobe_plugins")`, which is `SELECT 1 FROM osquery_registry WHERE active = true AND registry = 'table' AND name = 'adobe_plugins'` (`queries.go:964-966`) |
| The table is a fleetd (orbit) extension table, not stock osquery, on macOS and Windows only | `orbit/pkg/table/adobe_plugins/`, registered in `orbit/pkg/table/extension_darwin.go:58` and `extension_windows.go:23`; `adobe_plugins_stub.go` for everything else |
| Two scan levels; standard is the default and covers CEP and UXP only, deep adds native plug-ins | Package doc and `generate` in `orbit/pkg/table/adobe_plugins/adobe_plugins.go:1-13,115-125` (`WithDefaults("standard")`, `WithAllowedValues{standard, deep}`) |
| Fleet's inventory query does not request the deep level | `softwareAdobePlugins.Query` is a bare `FROM adobe_plugins` with no `scan_level` constraint; the query comment states "The default (standard) scan level is used, which covers CEP and UXP extensions" |
| Scanned directories: system-wide and per local user CEP and UXP extension directories | `getScanPaths` in `adobe_plugins_darwin.go` (`/Library/Application Support/Adobe/{CEP,UXP}/extensions` plus each `/Users/<u>/Library/Application Support/Adobe/...`) and `adobe_plugins_windows.go` (`C:\Program Files\Common Files\Adobe\...`, the x86 CEP path, and each `C:\Users\<u>\AppData\Roaming\Adobe\...`) |
| Deep-level native plug-in directories are per application (Photoshop, Premiere Pro, After Effects, and Illustrator on macOS) | The `level == "deep"` branch of both `getScanPaths` implementations |
| Per-user installs carry the user name on the row | `colUser: sp.user` set in `parseCEPPlugin` / `parseUXPPlugin`; the query comment notes the table "emits one row per plugin, including a user column for per-user installs, so there's no need to join with cached_users" |
| Name, version and vendor come from the manifest; when it cannot be read the row still returns with the directory name and no version or vendor | `parseCEPPlugin` reads `CSXS/manifest.xml`, `parseUXPPlugin` reads `manifest.json`; both return the partially populated `row` on a read or parse error, having set only path, name (`filepath.Base`), extension type, user and platform |
| Manifest reads are capped at 1 MB | `maxManifestSize = 1 << 20` and `readFileCapped` |
| Native plug-ins have no manifest and therefore no version | Package doc ("The deep scan level additionally reports native plug-ins, which have no manifest and thus no version"); `parseNativePlugin` sets no version column |
| The displayed software type is the flat string "Plugin (Adobe)" | `frontend/interfaces/software.ts:321`, `adobe_plugins: "Plugin (Adobe)"` |
| The host application is read but not stored against the title, so the type label never names it | `softwareAdobePlugins.Query` selects `'' AS extension_for` and `'' AS bundle_identifier`; the query comment explains the keying collisions that motivated it and states "the Type column shows a flat 'Plugin (Adobe)' and never displays the host application"; the frontend comment at `software.ts:321` says the same |
| The plugin's bundle id is carried as `extension_id`, which is not part of a title's identity | `bundle_id AS extension_id` in the query, with the comment "the plugin's bundle id goes in extension_id instead, which is not part of a software title's identity" |
| No `last_opened_at` is reported | `'' AS last_opened_at` in the query |
| The source is not installable through Fleet | `INSTALLABLE_SOURCE_PLATFORM_CONVERSION.adobe_plugins = null` (`frontend/interfaces/software.ts:356`) |
| Adobe plugins are excluded from vulnerability scanning | `ExcludedSources: append(oval.SupportedSoftwareSources, "ios_apps", "ipados_apps", "adobe_plugins")` in `server/vulnerabilities/nvd/cpe.go:868-871` (covered in full by SE5) |

### Derived (reasoning, not just citation)

| Conclusion | Reasoning |
|---|---|
| A host on an older fleetd reports no plugins and no error | The discovery query gates the whole detail query on the table being registered in `osquery_registry`. An agent without the extension does not register it, so the query is not issued at all; nothing on that path produces a host-visible failure. Stated as a silent absence rather than as a version number, because the changelog states no minimum fleetd version for this feature and none was found in the code |
| "Plugin counts climb as hosts update" during an agent rollout | Follows from the previous row: collection is per host and gated per host, so the population reporting plugins is the population running an agent that has the table |
| "A blank version means the manifest was not readable" | The only path that leaves version blank for a CEP or UXP extension is a manifest read or parse failure (both parsers return the partial row); native plug-ins, the other version-less case, are not collected at the standard level Fleet uses |
| Symlinked entries are skipped, so a plugin reachable only through a symlink is not reported | Stated in `generate` (`entry.Type()&fs.ModeSymlink != 0 { continue }`). Not written into the chapter: too fine a detail for the reader's decisions, recorded here so a future editor does not treat it as an omission |

### Not edited / deferred
- The vulnerability exclusion is named in one sentence with a link forward, and is covered properly by
  SE5 in "Five states that all look like 'no vulnerabilities'". Deliberately not explained twice.
- The 4.91 bug-fix renaming the "Program (Windows)" software type to "Application (Windows)" is a fix,
  not a feature, and is out of scope for chapter edits this campaign. Grepped `manual/` for "Program
  (Windows)": no occurrence, so nothing in the manual is stale because of it.
- `enable_software_inventory` per fleet over the API is IA17 and lands in "Turning software inventory
  on, and what 'off' looks like", not here.

## Addendum, Fleet 4.91.0: per-fleet software inventory over the API (IA17)

Drafted 2026-09-08 against `fleet-v4.91.0` (35fc1c024490). Four paragraphs added to
`## Turning software inventory on, and what "off" looks like`, before "Turning it off is not the same
as deleting what Fleet already has". Changelog line: "Added support for enabling/disabling software
inventory per-fleet via `PATCH /api/v1/fleet/fleets/{id}` with
`{"features": {"enable_software_inventory": <bool>}}`. The key follows PATCH-merge semantics: when
omitted, the stored value is unchanged."

### Stated: verified at the tag

| Claim | Basis |
|---|---|
| The key is writable through the fleet PATCH endpoint's `features` block | `TeamPayloadFeatures` in `server/fleet/teams.go:69-81`, reached from `TeamPayload.Features` (`teams.go:65`), applied in `ee/server/service/teams.go:520-522` |
| Omitting the key leaves the stored value unchanged | The field is `optjson.Bool` and is only applied when `.Valid` is true; the struct comment states it outright: "uses optjson.Bool so a key omitted from a PATCH body retains its current stored value (PATCH-merge semantics)" |
| Only software inventory and the historical-data sub-keys are writable through this endpoint's `features` block | `TeamPayloadFeatures` has exactly those two fields, and its doc comment says "Only the sub-fields defined here take effect; the broader Features fields (enable_host_users, additional_queries, detail_query_overrides) remain settable per-fleet only via the `/spec/fleets` GitOps path" |
| It is Fleet Premium | `ModifyTeam` lives in `ee/server/service/teams.go`; the fleet (team) endpoints are the EE service throughout |
| No activity is emitted when the value flips | `ModifyTeam` emits activities for OS-update settings, disk encryption, recovery-lock passwords, conditional access and, through `OnHistoricalDataChanged`, the historical-data sub-keys. The `EnableSoftwareInventory` branch (`ee/server/service/teams.go:520-522`) writes the value and emits nothing; grepped the surrounding function for `NewActivity` and confirmed no call is reachable from that branch |
| Historical-data sub-keys behave the same way per sub-key | `HistoricalDataPayload` at `server/fleet/teams.go:88-95`, each field `optjson.Bool` with the same merge comment |

### Derived (reasoning, not just citation)

| Conclusion | Reasoning |
|---|---|
| "Which previously meant a GitOps run" | The changelog frames the API as the addition; the payload comment says the broader feature fields remain GitOps-only, implying this one did not used to be here. Recorded as a version boundary from the changelog rather than re-verified at 4.90 |
| "A request that changes something else about the fleet cannot silently switch collection back on" | The operational point of the merge semantics, and the reason the changelog bothers to state them. Follows from the `.Valid` guard |
| "A PATCH carrying them changes nothing" (for host users and query customisations) | The payload struct has no fields for them, so they are dropped during unmarshalling rather than rejected. Stated as "changes nothing" rather than "is rejected", which is the weaker and correct claim; not verified whether an unknown key produces a 4xx on this endpoint |
| "It matters more here than usual, because turning collection off is exactly the kind of change somebody will later want to date" | Editorial, resting on this chapter's existing point that a fleet with inventory off shows old data rather than no data, so the question "when did this stop" is a real one with no answer in the audit log |

  the delay before hosts pick up a change. Not rewritten; the new material sits after it.
- 1.5's audited-by-exception rule needed no edit. It states the general principle and this is an

- a.8 does not list the fleet PATCH endpoint's feature keys; the endpoint itself predates 4.91. Same
