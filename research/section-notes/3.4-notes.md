## Corrected before review, 2026-08-27: the escrow prerequisites were wrong

Found by re-reading `orbit/pkg/luks/luks_linux.go` in the pattern 3.2's and 3.3's reviews had established: check the chapter's organising claim against Fleet's source rather than against what the manual already believed.

**Escrow is Orbit's work, not Fleet Desktop's.** The runner is registered directly on the Orbit client, so `--fleet-desktop` is not a prerequisite. What the interactive path needs is a **desktop dialog tool on the host**, `zenity` or `kdialog`, and `cryptsetup`. The first draft said a package built without `--fleet-desktop` could never escrow, which is the obvious guess and is wrong.

**And there are two escrow paths, not one.** A host using snapd-managed TPM-backed full-disk encryption, as on recent Ubuntu, takes a **silent recovery-key path** over the snapd socket with no dialog and no person involved. Orbit detects that first and only falls through to the passphrase path otherwise, with a source comment explaining why the detection error is fatal: a metadata read failure could mean the host is snapd-managed but unconfirmable, and prompting for a passphrase the user does not have would be worse than failing.

So the first draft's "a headless server can never escrow a key, no matter how it was packaged" was wrong in both directions. On the snapd path a headless host escrows silently; on the passphrase path Orbit fails with "No supported dialog tool found" rather than hanging, which is at least legible.

**1.2 carried the same error and is corrected with it.** It attributed the Linux passphrase prompt to Fleet Desktop and said escrow "cannot happen at all" without it. Both halves are wrong, and 1.2 is a Part I chapter that has already been reviewed once, which is a reminder that a reviewed chapter is not a verified one.

Also tightened: `--enable-scripts` is genuinely permanent on Linux, unlike macOS where Fleet's own MDM profile turns scripts on regardless ([3.2](3.2-enroll-macos-devices.md)). Worth stating as a contrast now that the macOS behaviour is documented.

## First independent review, 2026-08-27: NOT READY. Applied, plus a Fleet code defect found while applying.

Seven factual defects. Two of them had already been caught by re-reading the source before the review arrived; the review found five more, and one of its findings led to a defect in Fleet itself.

**Fleet can lock and wipe Linux hosts, and the chapter said it could not.** Fleet Premium runs both as **scripts** rather than as MDM commands, and the source says so in a comment: Windows and macOS require MDM enrollment for a wipe, Linux uses scripts. The chapter had listed lock and wipe among the things Linux does not get, which is the natural inference from "no MDM" and is wrong. It also makes `--enable-scripts` matter far more than the chapter implied, since a host with scripts disabled cannot be locked or wiped. **1.2 carried the same error twice**, in its capability table and in its Orbit-against-MDM split, and both are corrected: the split is about mechanism, not capability.

**`--enable-scripts` is not permanent on Linux.** Orbit reads `ORBIT_ENABLE_SCRIPTS`, which the Linux packager writes into `/etc/default/orbit`, so the setting can be changed with an edit and a restart using exactly the mechanism the chapter recommends for everything else. The first draft said a package built without it produced hosts you could never run a script against, **and then added a contrast with macOS asserting it**, which is the same error made twice in one paragraph.

**Escrow is not an enrollment-time decision, and the chapter listed two of its gates.** Being encrypted at provisioning time is genuinely an image decision; everything else is configuration that can be changed afterwards and any of it can leave you with no key: Premium, a configured server private key without which Fleet refuses to enable disk encryption at all, enablement for the host's scope, fleetd **1.36.0** or later, and Fleet having observed the disk as encrypted. The section is now split into what the image decides and what the configuration decides, because building the right image and still receiving nothing is the confusing outcome.

**What Fleet escrows is a key of its own.** On the passphrase path it validates the user's existing passphrase, **generates a fresh random one**, and adds that in a new key slot; the snapd path obtains a dedicated recovery key. The chapter said Fleet "takes a copy of the key", which misdescribes both what is stored and what revoking it involves.

**Encryption status and escrow are separate.** Fleet learns whether the root disk is encrypted from an ordinary osquery detail query, with no escrow, no dialog tool and no Premium licence. The chapter had told a reader who wanted *reporting* to arrange the whole escrow apparatus.

**"One channel" was the wrong model.** Linux has no MDM channel, but it still has the osquery distributed channel, the osquery logging channel and Orbit's separately authenticated API, which is what 1.2 says and what the routes show. The verification section had followed the framing into checking one thing: `systemctl status orbit` proves a supervisor is alive and nothing about live reports, ingestion, scripts or software. Now three checks, one per channel.

**Also added, from the review's omissions list:** `--fleet-certificate` for private-CA deployments, concrete install commands per package type, and a removal procedure, which 3.1 explicitly delegates here.

### A Fleet code defect, found while writing the removal procedure

Verifying the uninstall behaviour rather than citing 8.4 turned up an inverted branch in the Linux pre-removal script:

```sh
case "${1:-}" in
  1|remove|deconfigure)  systemctl disable --now orbit.service || true ;;
  0|upgrade)             ;;
esac
```

The comment directly above it states RPM's convention correctly: preun is called with `0` on uninstall and `1` on upgrade. The branches are the wrong way round for that convention. Debian is unaffected, because its prerm receives words (`remove`, `upgrade`, `deconfigure`) and never numerals, and Arch is unaffected because its script disables unconditionally.

So on an RPM host, an **uninstall** leaves `orbit.service` enabled and running while the post-removal script deletes `/opt/orbit` out from under it, and an **upgrade** stops the service and relies on the post-install script to bring it back. The chapter documents the observable behaviour and tells the reader to check `systemctl is-enabled orbit` after removing, rather than describing the intent. **Not filed**, per the standing instruction; recorded in `PROJECT_STATUS.md` as C5.
