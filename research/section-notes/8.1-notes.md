## Corrections made in this pass

### 1. Channel 2's cadence was wrong by a factor of six, and the book already had it right

**Stated.** The channel table gave the osquery config TLS cadence as "~10s". fleetd starts osqueryd with `--config_refresh=60`, in `orbit/pkg/osquery/flags.go`, with a source comment saying osquery's own default of 0 "is probably not ideal for a client connected to Fleet". The real cadence on any fleetd-managed host is 60 seconds.

Fleet's default agent options (`server/fleet/app.go`) set `distributed_interval: 10` and `logger_tls_period: 10` and set no config refresh value at all, so the "~10s" figure had no source on either path.

**This is the dominant defect class again.** 1.2 already stated the correct value, in its own five-channels table: "`config_refresh`; Fleet sets this to 60 seconds". Two chapters disagreed and each was internally consistent. `claims.py config_refresh` surfaced it in one run.

Corrected, and the chapter now points at 1.2 for where each cadence is set rather than restating them, per §18.

### 2. `fleetctl debug connection` was given an enrollment URL

**Stated.** The example read `fleetctl debug connection --fleet-certificate <ca-cert.pem> <enroll-url>`. The argument is the Fleet server address. `cmd/fleetctl/fleetctl/debug.go` assigns the positional argument straight to the client config's `Address`, and Fleet's own error text for the empty case suggests `fleetctl debug connection localhost:8080`. An enrollment profile URL pasted there checks whatever host that URL names, which on the ADE path is not Fleet.

This is the copyable-and-confident class. The command runs, prints successes, and answers a question the operator did not ask.

The section now also says what the command actually checks, in order, since the failing line is the diagnostic: hostname resolution, TCP dial, TLS validation against the supplied root, then a POST to `/api/osquery/enroll` with a deliberately invalid secret. All four are **stated**, from the same file. The command returns at the first failure, so the last line printed names the stage. Also stated: with an explicit address and no `--fleet-certificate`, the root CA falls back to the embedded osquery certificate bundle used to build fleetd packages, and the command says so in its output.

### 3. The Orbit channel is not a steady 30 seconds when it is failing

**Stated.** `client/orbit_client.go`: `defaultOrbitConfigReceiverInterval = 30 * time.Second` drives the ticker, and a failed run calls `configBackoff.RecordFailure()` and resets the ticker to the backed-off interval, with `maxConfigBackoff = 5 * time.Minute`. A success resets it to 30 seconds. Each extension logs `running config receivers, backing off` with a `next_retry` field.

The chapter gave only the 30 seconds. Mid-incident that is a trap in both directions: a channel you have just fixed can take five minutes to show it, and a channel that looks dead may be backed off. Added to the channel table and to the prose beneath it, with the log string, since the string is the cheap way to tell the two apart.

**Carries to 8.11.** 8.11 states the same 30 seconds as a flat interval and calls it a compiled-in constant with no configuration surface. The constant part is right. The flat part has the same gap this chapter had. 8.11 is out of scope for this sweep and is flagged rather than edited.

### 4. "Roughly thirty named schedules", and "all thirty"

**Stated.** There are **34** at this tag, counted from `CronScheduleName` constants in `server/fleet/cron_schedules.go`. "Roughly thirty" was defensible; "all thirty schedules" in the callout asserted a count the reader cannot reconcile, which is §26.

Now given as 34 at 4.90.1, with the more durable instruction alongside it: an unrecognised name makes the server return the supported list, so the reader can get the current set from their own deployment rather than trusting a number in a book. That is `triggerNotFoundError{... msg: cs.formatSupportedTriggerNames()}`.

Every schedule name printed in the chapter was checked against the source list and all eleven exist: `mdm_apple_profile_manager`, `mdm_windows_profile_manager`, `apple_mdm_dep_profile_assigner`, `apple_mdm_apns_pusher`, `maintained_apps`, `vulnerabilities`, `automations`, `integrations`, `refresh_vpp_app_versions`, `upcoming_activities_maintenance`, `host_vitals_label_membership`.

### 5. A garbled sentence and three code identifiers in reader-facing prose

The trigger callout contained "`CronSchedules.TriggerCronSchedule` discards the `didTrigger` return value the scheduler discards it", which is two half-sentences spliced together. It also named `Trigger()`, `CronSchedules.TriggerCronSchedule` and `didTrigger`, all of which §8 forbids in prose and none of which an administrator can act on.

Rewritten as behaviour. The behaviour itself was re-verified and is correct:

**Stated**, `server/service/schedule/schedule.go:484`. `Trigger` returns without triggering in exactly three cases: the schedule's own run is already `pending`; a prior trigger is `pending` or `queued`; or the send to the internal trigger channel hits its `default` branch and logs "trigger channel not available" at debug level.

**Stated**, `server/fleet/cron_schedules.go`. The caller is `stats, _, err := sched.Trigger(ctx)`. The second return value is the flag saying whether the trigger actually went out, and it is discarded. The first two cases return non-nil stats and become a conflict error, which `fleetctl` prints as `[!] Conflict`. The third returns nil stats and nil error, so `fleetctl` prints its success line for a run that did not happen.

### 6. A code fence collapsed into one unrunnable line, and the bug that did it

`build/unwrap.py` joined the `cron_stats` query in the trigger callout into a single line, `` ```sql SELECT ... LIMIT 5; ``` ``, which renders as a broken fence and cannot be copied.

**Root cause.** `FENCE` is anchored with `^\s*(```|~~~)`, so it does not match a fence inside a blockquote, where the line begins with `>`. The fence and its contents fell through to the blockquote branch and were joined as prose. The safety net did not catch it because `sig()` strips leading `>` markers and collapses whitespace before comparing, so the wreckage compared equal to the original.

Both fixed. `unwrap.py` now recognises a quoted fence and copies it verbatim to its quoted closing fence, and the fix is idempotent. A grep for `` ```[a-z]* .*``` `` across `manual/` finds no other instance, so this was the only casualty.

Per `CONTRIBUTING.md`, the class is checkable and the fix went in before the instance.

### 7. The half-enrolled state's failure rate was presented as a rate

**Stated, with its scope corrected.** `fleetdm/fleet#47793` is real and open as of today. Its body reads: "Fleet uses the v1 MDM protocol `InstallEnterpriseApplication` command. `antonella` saw ~20-30 machines out 1000 not get fleetd." So the number is sourced and quoted correctly.

What the citation did not establish is scope, which is the §27 trap. One person's observation of one estate was written as "Reported at roughly 2 to 3 percent of ADE enrollments", which reads as a population rate the reader can plan against. Rewritten to attribute it to one deployment and to say so.

Two smaller things fixed with it: the issue is a proposal to move the install to the declarative protocol rather than a bug report, which is worth knowing before following the link; and "open as of 4.89.2" is now "open as of 4.90.1", confirmed rather than carried forward.

`InstallEnterpriseApplication` is confirmed as a command Fleet sends, in `server/mdm/apple/commander.go`.

### 8. "Fleet does not buffer query results" was broader than the source

**Was derived, presented as stated.** The two-clocks check rested on a universal negative about Fleet's whole result path, which the source does not establish; the log destination clients are not all synchronous pass-throughs.

What is stated, in `server/service/osquery.go`, is narrower and does the same work: Fleet writes results to the configured destination inside the request that delivered them, and deliberately returns an error when the destination write fails "so that the logs are not lost and osquery retries on its next log interval". The chapter now says that, and the conclusion the check needs, that old record timestamps mean device-side buffering, follows from it.

### 9. An unsourced superlative about Fleet's online indicator

The chapter claimed "the most misleading single field in Fleet is a healthy MDM status on a host whose agent is gone". Unverifiable, and `check-absolutes.py` exists because of this shape.

Replaced with the mechanism, which is stronger. **Stated**, `server/fleet/hosts.go`: `Host.Status` compares `SeenTime` against `min(ConfigTLSRefresh, DistributedInterval) + OnlineIntervalBuffer`, where `OnlineIntervalBuffer = 60`. Both inputs are osquery intervals. **Derived** from that: the online field reports on channels 1 and 2 and carries no information about 3, 4 or 5. The chapter defers the window itself to 1.2, per §18.

### 10. The thirteen questions, and where they are

**Stated.** `docs/Contributing/product-groups/mdm/mdm-bug-checklist.md` contains exactly thirteen numbered questions. The count was right.

The chapter's own table has eleven rows, because it regroups Fleet's list and adds "what changed", which Fleet's checklist does not ask. A reader who counted would have found eleven under a sentence promising thirteen. The prose now says it is a regrouping and names the addition, which satisfies §26 without padding the table to match.
