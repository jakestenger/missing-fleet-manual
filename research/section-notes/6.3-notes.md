## Derived

**The default the chapter gives.** Use the documented method and path for each resource, prefix
included, and contract-test it against every release you target. Mixed prefixes across one client are
an ordinary consequence rather than a mistake. **Added at review**: the chapter offered three
approaches and no recommendation, and the reviewer's point was that the three overlap, so a reader
was owed a default.

**The minimum client contract**, restored at review after compression removed it: the URL prefix,
connection and whole-request deadlines, a response bound, the status classes worth distinguishing,
and recording Fleet's error identifier.

## Rejected, and why

**"Everything Fleet does, it does through this API."** Broader than the user-authenticated API the
chapter teaches; Fleet also serves agent, device and protocol route classes.

**"Strict JSON parsers object to duplicate keys."** Wrong. These are two differently named keys.

**"Nothing anywhere adds an identifier as a secondary key."** Some endpoints do.

**Three "only" claims** that lost their scope in compression, which was the failure mode this
review named and which recurred in 6.4 and 6.5.

## Cross-chapter corrections this chapter forced

**a.8**, twice: it said each endpoint is registered under every version Fleet declares, which is true
of the core module and not of the API; and it promised its upstream reference stays correct across
releases. A third followed at review: it rendered the Android callback route with a wildcard prefix
when that route is fixed to one. **6.1** said the API can do nothing declarative; it has declarative
endpoints, so it now says no reconciliation loop. **6.4** claimed every `fleetctl` capability belongs
to 6.3, which oversteps.
