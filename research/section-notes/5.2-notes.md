# 5.2 Manage configuration profiles and declarative settings, citation ledger

Drafted 2026-08-27 against `fleet-v4.90.1` (dd0200f062).

## Stated

| Claim | Source at the tag |
|---|---|
| Profile delivery status is one of pending, verifying, verified, failed, or unset | `server/fleet/mdm.go`, the `MDMDeliveryStatus` constants and `IsValid` |
| Verifying means the command applied but Fleet has not independently verified it | Same file, the doc comment block above those constants, quoted almost directly |

## Derived

**The three-step choice** (Fleet's own settings, then a declaration, then a custom profile) is
editorial. The supporting fact is the OS updates guard, which shows Fleet actively defending one
such boundary; the general ordering is my recommendation.

**"Removal is automatic."** Follows necessarily from scope being a continuously evaluated
membership test, and from the presence of a remove operation type. Stated as a consequence.

**"Uploading is not validating."** Editorial framing of the boundary between what Fleet checks and
what it cannot.

**The Apple identifier collision point** is general Apple platform behaviour rather than Fleet
behaviour, and is stated as a property of the device.

**The diagnostic order** at the end is editorial method.

## Deliberately not stated

**No profile format tutorial.** Writing a property list payload or a Windows configuration path is
the platform vendor's documentation, not Fleet's, and it would date. The chapter covers what Fleet
does with the document.

**No claim about how Fleet performs its independent verification, or on which platforms.** The
existence of the verifying-versus-verified distinction is established for all three platforms by
the shared status table. 8.6 describes the verification pass as an Apple mechanism. Whether Windows
and Android reach `verified` by the same route was not established. The chapter states what the
states mean and does not describe the mechanism. **Flag for a later round.**

**No retry timing.** The retry counts are established; how long Fleet waits between attempts was
not checked.

**No enumeration of which settings have built-in Fleet controls.** That list belongs with each
subject: encryption in 5.8, OS updates in 5.6.

## Extended 2026-09-02 (round4 RM8) — declaration user-channel section

New "Declarations: the user channel, and where it can't reach" section, verified against
`fleet-v4.90.1` (same tag as the rest of the chapter).

| Claim | Source at the tag |
|---|---|
| `PayloadScope` is a top-level declaration key, `"System"` (default) or `"User"`; System targets the device channel, User the user channel (macOS only) | `server/fleet/apple_mdm.go`: the `PayloadScope`/`PayloadScopeSystem`/`PayloadScopeUser` constants, the `Scope` field doc comment on `MDMAppleDeclaration`, `MDMAppleRawDeclaration.ScopeOrDefault` and `ValidateScope`; corroborated by `docs/Contributing/architecture/mdm/apple-declarative-device-management.md`'s DDM section, which states the same default and macOS-only restriction |
| The key is stripped from the declaration only when served to the device, so the delivered JSON stays valid Apple DDM | Same doc comment on `MDMAppleRawDeclaration.PayloadScope`; confirmed behaviorally by `TestAppleUserScopedDDMEndToEnd` in `server/service/integration_mdm_ddm_test.go`, which asserts `PayloadScope` is absent from the served content |
| iOS/iPadOS refuse a user-scoped install outright and immediately (status failed, no hold) | `resolveUserChannelDeliveries` in `server/service/apple_mdm_declarations_batched.go`, the `IsAppleMobilePlatform` branch, with `fleet.IsAppleMobilePlatform` defined as `ios`/`ipados` in `server/fleet/mdm.go` |
| A macOS host only has a user channel if it automatically enrolled; a manually enrolled Mac never gets one | Same function's `default` branch and its failure detail string, "Currently, Fleet creates the user channel for hosts that automatically enroll" |
| Grace period before failing a held user-scoped install is 2 hours from device enrollment | `HoursToWaitForUserEnrollmentAfterDeviceEnrollment = 2` in `server/mdm/apple/reconcile.go`, referenced by the same function's grace-window branch |
| Within the grace window, a pending user-scoped install is held (nil status, retried next tick) rather than failed | Same function, the grace-window `case`, setting `row.Status = nil` |
| A user-scoped REMOVE row for a host with no channel is hard-deleted rather than left pending | Same function's doc comment and its `toDelete` handling, which the comment says "mirrors how the profile reconciler cleans up undeliverable user-scoped profiles" |
| The two channels are independent connections with independent commands and status | `TestAppleUserScopedDDMEndToEnd`, which drives both channels through the simulated client and asserts each transitions independently |

**JSON example in the section** uses a placeholder `com.apple.configuration.<setting>` Type
rather than a specific Apple declaration type, since Fleet's own validation only requires the
`com.apple.configuration.` prefix (8.8 already documents the full validation order) and no
specific type name was verified as authoritative for this illustration; the point being
demonstrated is the `PayloadScope` key, not the type.

**Deliberately not stated:** what triggers Setup Assistant's user-channel enrollment step
mechanically (out of scope; 3.2 owns ADE enrollment sequencing), and Windows/Android
equivalents (neither platform has a user channel in Fleet's DDM implementation).
