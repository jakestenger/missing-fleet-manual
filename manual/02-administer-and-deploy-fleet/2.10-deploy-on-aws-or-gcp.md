# Deploy on AWS or GCP

Fleet deploys against ordinary MySQL, Redis and S3-compatible object storage rather than through any cloud's control plane. What differs between the clouds is mostly what sits behind those three clients, though authentication and endpoint behaviour still have provider-specific corners.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers the two clouds Fleet publishes reference architectures for, what each one actually builds, and where the two differ enough to change your decision. How large to make any of it is [2.9](2.9-self-hosting-architecture-and-capacity.md). Running Fleet in containers or on plain virtual machines, on any cloud or none, is [2.11](2.11-deploy-with-containers-or-virtual-machines.md). Choosing where osquery results are delivered is [2.5](2.5-activity-audit-logs-and-log-delivery.md), which this chapter assumes you have already read.

Fleet talks to managed services through the same generic clients it uses everywhere. That is why a single setting can carry opposite advice on the two clouds without anything being inconsistent, and why a store neither cloud sells can serve Fleet perfectly well.

## AWS and GCP are not two equivalent options

![Explanation](../_assets/icons/explanation.svg) Both are supported and both are documented, but they are at very different stages, and choosing between them on preference alone will surprise you later.

**AWS is where Fleet runs Fleet.** The reference architecture is published as a reusable Terraform module, sized configurations run from five thousand hosts to three hundred thousand, and there are optional add-ons for monitoring and installer delivery. Fleet's own production deployment is built from that same module.

**GCP is a smaller, working reference.** Three sized configurations, from one thousand hosts to one hundred and fifty thousand. The Terraform provisions a complete deployment and it is genuinely usable. It is thinner in coverage rather than in quality: fewer breakpoints, no published add-ons, and one dependency whose availability posture you have to establish yourself, covered below.

**Azure has no published architecture at this release.** Fleet points at community support. Nothing prevents running Fleet on Azure, since the dependencies are ordinary managed MySQL and Redis, but you will be assembling it yourself against [2.9](2.9-self-hosting-architecture-and-capacity.md) rather than following a reference.

## What the AWS architecture builds

![Reference](../_assets/icons/reference.svg) The Terraform stands up a VPC with public and private subnets and the usual access controls, then places Fleet inside it.

Fleet itself runs as containers on ECS with Fargate providing the compute, which is what makes the many identical instances from [2.9](2.9-self-hosting-architecture-and-capacity.md) straightforward: permissions come from task roles rather than from credentials in the container. The database is RDS Aurora MySQL 8, the cache is ElastiCache Redis, and there are S3 buckets for file carves and software installers. Osquery results go to Firehose, which syncs to an S3 bucket for whatever processes them next.

Two add-ons are published separately and both are worth knowing about before you decide you do not need them. One provides CloudWatch alarms, which matters because [2.9](2.9-self-hosting-architecture-and-capacity.md) leaves you needing somewhere to send the metrics Fleet exposes. The other puts CloudFront in front of software installers, which changes where the bandwidth for large package downloads is served from.

## Two Terraform locations, and which one you want

![How-to](../_assets/icons/howto.svg) Fleet's documentation links two different Terraform locations for AWS, and the relationship between them is not stated anywhere obvious.

**The reusable module is its own repository**, `fleetdm/fleet-terraform`. That is the thing you consume.

**The copy inside the Fleet repository is Fleet's own deployment**, and it consumes that module rather than replacing it, pinned to a specific released version. It is a worked example of the module in use, complete with Fleet's own domain and Fleet's own choices, which makes it excellent for reading and a poor thing to copy wholesale.

Pinning the module to a version reference, as Fleet's own deployment does, is the pattern to copy. It is also the reason the two can drift: the example is pinned to whichever module version Fleet last moved to, not to the module's newest release.

## The S3 settings that behave differently than you expect

![Troubleshooting](../_assets/icons/troubleshooting.svg) Two settings cause most of the object storage problems on AWS, and both are consequences of the generic S3 client rather than bugs.

**Do not set an endpoint URL when you are using task roles or IRSA.** It reads as an S3 setting and it is not. Setting it overrides the endpoint for every AWS API call Fleet makes, not just the ones to S3, and that breaks the token-based authentication those roles depend on. If you are on ECS task roles or EKS with IAM Roles for Service Accounts, leave it unset and set the region instead.

**Set the region explicitly even when it feels redundant.** With no region configured, Fleet falls back to `us-east-1` purely as a starting point and asks the bucket where it actually lives. That works, until something about the deployment makes that first call fail, at which point the failure points at a region you never configured and do not use.

## Cost on AWS follows report frequency

![Explanation](../_assets/icons/explanation.svg) Firehose is billed per use. Since it is the destination the reference architecture wires up for osquery results, the volume of data flowing through it is set by how often your scheduled reports run and how much each one returns.

This makes report frequency an infrastructure cost decision as well as a data freshness decision, which is not how most people first think about it. Doubling the frequency of a broad report across a large estate doubles a line on the cloud bill, quietly, with no signal from Fleet.

Which destination to use at all is [2.5](2.5-activity-audit-logs-and-log-delivery.md). What is specific here is that the cloud you are on determines whether that choice has a metered price attached.

## The Terraform role is broadly privileged

![Reference](../_assets/icons/reference.svg) The permission set Fleet documents as the minimum for applying its AWS Terraform is wide: full access to roughly twenty-five services, including identity, key management and secrets, with no resource restriction.

This is normal for infrastructure-as-code that provisions a whole environment. The consequence is worth stating precisely: the policy grants wildcard actions across identity, key management and secrets with no resource restriction, so whatever runs it can grant itself anything else in the account. If that is a continuous integration system, your CI credentials carry that reach. A dedicated account or an equivalent credential boundary for the Fleet deployment is a far easier conversation than scoping those permissions down.

## What the GCP architecture builds

![Reference](../_assets/icons/reference.svg) Fleet runs as Cloud Run containers, which is the closest GCP analogue to Fargate and gives the same disposable-instance model.

The database is Cloud SQL for MySQL 8, reachable only over private networking rather than from the internet, which Cloud Run reaches through a serverless VPC connector. Redis is Memorystore, and the reference runs it in standalone rather than cluster mode. TLS terminates at a Google-managed certificate on the load balancer, which means the deployment expects you to delegate your domain's nameservers to the DNS zone the Terraform creates. Cloud Run also restricts which container images it will run, so the Terraform copies Fleet's public image into Artifact Registry rather than pulling it directly.

## Object storage on GCP works, despite what the architecture page says

![Explanation](../_assets/icons/explanation.svg) Fleet's reference architecture page states that software installation and file carve support on GCP are coming soon. At this release that is out of date, and it is worth being precise about what is and is not true, because the claim would reasonably steer somebody off GCP altogether.

**Both features work.** Fleet reaches Google Cloud Storage through the same S3 client it uses for AWS, pointed at Google's S3-compatible endpoint with path-style addressing turned on. Software installers and file carves each have their own complete set of settings for this, and both are documented.

**There are two ways to authenticate, and the better one is not the one the reference Terraform uses.** The published GCP Terraform authenticates with an HMAC key, which is a long-lived credential sitting in the environment. Fleet also supports Google Application Default Credentials, which on Cloud Run resolves to the workload's own identity and means no stored secret at all. That option is mutually exclusive with the access key settings, so it is a choice rather than an addition, and it requires the endpoint URL to be Google's.

**What is genuinely missing is narrower than the page suggests.** The published GCP Terraform provisions a bucket for software installers and does not provision one for carves. So carves fall back to MySQL on that architecture, as [1.6](../01-foundations/1.6-the-fleet-server.md) describes, until you add the bucket yourself. That is a gap in the Terraform, not in Fleet.

**If you use file carves on GCP, that is a separate setup.** Carves have their own complete set of settings, including their own choice between an HMAC key and workload identity, so configuring installers does nothing for them. Create and authorize a second bucket, point the carve settings at it, pick the same credential style you chose for installers, and run one carve to confirm where the blocks actually land. Skipping that leaves carves quietly falling back into MySQL, which works and grows the database.

Prefer workload identity over HMAC keys where you have the choice. The reason is credential lifecycle rather than capability: an HMAC key is a long-lived secret somebody has to store, rotate and eventually find again, and workload identity removes it from the deployment entirely.

Because object storage is reached through an S3 client, any store speaking the S3 API can serve as Fleet's object storage, on any cloud or none.

## The two architectures differ on failure, not just on size

![Explanation](../_assets/icons/explanation.svg) The sized configurations for the two clouds are not directly comparable, and the difference that matters is not the instance classes.

The AWS configurations specify three Redis nodes and two or three database nodes at every size, so the intent is legible from the sizing tables alone.

On GCP you have to read the Terraform, and the two dependencies land differently. **Redis is provisioned on Memorystore's high-availability tier**, which is a replicated instance with automatic failover, so the single node count in Fleet's published table is one highly available instance rather than a lone server. **Cloud SQL is the one to check yourself.** The Terraform pins a zone and hands the rest to an external community module without setting an availability type, so whether you get a zonal instance or a regional pair depends on that module's defaults rather than on anything Fleet states. That is not determinable from Fleet's published files, and it is the single most important thing to confirm before you treat the GCP reference as production-ready.

[2.9](2.9-self-hosting-architecture-and-capacity.md) covers what availability actually requires, and the single-writer constraint described there applies identically on both clouds.

The per-instance allocation differs too, at one CPU and two gigabytes on GCP against one CPU and four gigabytes on AWS. Both hold their allocation constant as host count grows, which is the pattern from [2.9](2.9-self-hosting-architecture-and-capacity.md) reappearing on a second cloud and worth treating as confirmation rather than coincidence.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) The verification that matters after a cloud deployment is not that Terraform applied cleanly. It is that the pieces Terraform cannot check are actually connected.

Confirm the health endpoint from [2.9](2.9-self-hosting-architecture-and-capacity.md) is what your load balancer targets, and confirm it individually for MySQL and for Redis. Then check the thing that endpoint does not cover: upload a software installer and download it from a host. That single test exercises object storage, the credentials reaching it, and, on AWS with the CloudFront add-on, the delivery path in front of it, none of which any health check touches. If carves are in scope, run one as well, because it uses a different bucket and different credentials and a successful installer download proves nothing about it.

Confirm results are arriving at your log destination, and check the volume rather than only the presence, since on AWS that volume is the cost.

Ownership divides along a line that is easy to leave undrawn. The Terraform, the account it applies into, and the privileged credentials that run it belong to whoever owns cloud infrastructure. The Fleet settings inside it, particularly the object storage and database connection settings, belong to whoever owns Fleet. The failure mode this prevents is the common one where a cloud team changes a managed database version or a region default and nobody connects it to Fleet until hosts stop checking in.

## Precedence and edge cases

![Reference](../_assets/icons/reference.svg) Fleet's Terraform is one opinionated arrangement, not a requirement, and a few of its edges are worth knowing.

The published sizing figures assume on-demand pricing and exclude network egress and gateway charges, so they understate the real bill by an amount that depends entirely on your topology.

Running several Fleet deployments against one managed database instance needs it provisioned for all of them together, which is the same warning as [2.9](2.9-self-hosting-architecture-and-capacity.md) and is easier to trip over on a cloud where creating another database looks expensive.

On GCP, the managed certificate will not issue until the nameserver delegation is complete, so a deployment that otherwise applied successfully can sit unreachable while DNS propagates, with nothing in Fleet indicating why.

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.1. Cloud service names, instance classes and the contents of Fleet's Terraform all move independently of Fleet releases, so treat the shape as durable and the specifics as a starting point.

The statement on Fleet's reference architecture page that GCP support for software installation and file carves is coming soon does not match the product at this release. Both features have complete, documented configuration for Google Cloud Storage, including a workload identity option. Only the carves bucket is absent from the published GCP Terraform.

Azure has no published reference architecture at this release.
