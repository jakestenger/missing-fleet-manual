# Connect certificate authorities

A configuration profile that carries a certificate variable cannot resolve it until the authority the variable names is connected here on the server first, which is why this chapter comes before the profiles that appear to do the work. Connecting an authority is a one-time, server-side act by an administrator. Ordinary profiles that carry no certificate variable install without any of this, so the prerequisite is specific to certificate delivery. [5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md) covers the profile; this chapter covers its prerequisite.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers connecting Fleet to an external issuing certificate authority: the six types Fleet speaks to, what you supply for each, what creation checks before it accepts the connection, where Fleet keeps the credentials, and how a connected authority turns a profile variable into a certificate on a host. Authoring the profiles that consume these authorities is [5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md); this chapter is the setup that has to exist before that profile can resolve.

A device presenting a client certificate to satisfy an Okta conditional-access check is a different feature that happens to share the word "certificate". Its trust boundary lives with the identity material in [2.5](2.5-identity-providers-sso-scim-and-role-sync.md), not here. At this release conditional access uses its own locally generated certificate authority and its own certificate records, not a certificate issued through any authority connected here; nothing in the product couples the two, and treating them as one feature is the quickest route to confusion.

## Prerequisites: a server private key, and Premium

![How-to](../_assets/icons/howto.svg) Two things must be true before a single authority will connect.

**The Fleet server private key must be configured.** Creating any authority is refused without it, with a message telling you to configure the private key first. This is the same key that encrypts the stored credentials (below), gates the delivery proxy, and gates the conditional-access identity provider in [2.5](2.5-identity-providers-sso-scim-and-role-sync.md). Set it once, as part of standing the server up, and everything that depends on it becomes available together. It is a server startup property, so setting it means a configuration change and a restart, not a toggle in the interface.

**The whole surface is Fleet Premium.** Connecting, reading a full record, updating, deleting, and test-issuing a certificate are all rejected on Free with a missing-licence error, and the SCEP (Simple Certificate Enrollment Protocol) proxy that hosts fetch their certificates through is mounted only when the server starts with a Premium licence. Two behaviours depart from that clean rule, and both can mislead:

- **The GitOps read-back is not licence-gated.** A `GET` of the GitOps certificate-authorities spec runs on Free, so a read of current state succeeds where a write would be refused.
- **A Free GitOps apply that names only a custom EST or a Smallstep authority reports success and creates nothing.** The emptiness test that is meant to reject the write on Free was written before those two types existed and does not count them, so a request carrying only EST or Smallstep authorities, or no authorities at all, is accepted, applies nothing, and returns green. A Free apply that adds an NDES, DigiCert, custom SCEP, or Hydrant authority is rejected as expected. Read a green Free GitOps run that mentions only EST or Smallstep as having done nothing, not as having succeeded.

## The six certificate authority types

![Reference](../_assets/icons/reference.svg) Fleet speaks to six kinds of authority, and they fall into three families by protocol. Microsoft's **Network Device Enrollment Service (NDES)**, custom **Simple Certificate Enrollment Protocol (SCEP)**, and Smallstep are SCEP proxies: Fleet stands between the host and your SCEP endpoint. Hydrant and custom **Enrollment over Secure Transport (EST)** are EST-based. DigiCert is its own REST API. The family decides how a certificate is later delivered, so it is worth holding onto.

Each type is identified in configuration by a fixed value, and each takes its own set of fields. The name you give an authority is validated strictly: letters, digits, and underscores only, non-empty, up to 255 characters, with spaces and hyphens rejected by design. For DigiCert, custom SCEP, and Smallstep that name becomes part of a profile variable later, parsed back out at delivery, which is what makes the character rules load-bearing rather than cosmetic; Hydrant and custom EST are held to the same rule even though their names never appear in a variable.

| Type (config value) | What you supply | Secret | Family |
|---|---|---|---|
| **DigiCert** (`digicert`) | `name`, `url`, `api_token`, `profile_id`, `certificate_common_name`, `certificate_user_principal_names`, `certificate_seat_id` | `api_token` | REST API |
| **NDES SCEP** (`ndes_scep_proxy`) | `url`, `admin_url`, `username`, `password` | `password` | SCEP proxy |
| **Custom SCEP** (`custom_scep_proxy`) | `name`, `url`, `challenge` | `challenge` | SCEP proxy |
| **Smallstep** (`smallstep`) | `name`, `url`, `challenge_url`, `username`, `password` | `password` | SCEP proxy |
| **Hydrant** (`hydrant`) | `name`, `url`, `client_id`, `client_secret` | `client_secret` | EST |
| **Custom EST** (`custom_est_proxy`) | `name`, `url`, `username`, `password` | `password` | EST |

**NDES is a singleton, and its name is fixed.** You may connect one NDES authority; a second is refused with a message saying only a single NDES authority can be added. It takes no `name` field of its own, because Fleet forces the name to `NDES`, and `NDES` is reserved so that no other authority can claim it. Every other type may have several, each under its own name.

The REST endpoints that create, list, read, update, delete, and test-issue authorities are catalogued in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md); the `certificate_authority` permission that governs them is in [a.4](../09-appendices/a.4-roles-and-permissions-matrix.md).

## What creation validates, and what it does not

![Explanation](../_assets/icons/explanation.svg) Creation is not a shape check. Fleet makes a live outbound call to the authority at the moment you connect it, so an authority that is unreachable, firewalled off from the Fleet server, or speaking the wrong protocol fails to connect rather than failing quietly at first use. This live reachability and protocol check is the single most useful thing about the create step, and it is worth reading its limits precisely, because they differ by type.

For three types the live check also exercises the credentials you supplied:

- **DigiCert** performs an authenticated profile lookup, so a bad API token or an unknown profile ID is caught at connect time.
- **NDES** exercises both the SCEP URL and the admin URL, distinguishing a full password cache, insufficient permissions, and bad credentials.
- **Smallstep** exercises the SCEP URL and its separate challenge URL.

For the other three, connection can succeed while a credential you got wrong stays untested until something actually requests a certificate from the authority:

- **Hydrant** and **custom EST** fetch the authority's certificate over an unauthenticated call. That call does not use the username, password, client ID, or client secret you supplied, so those are validated for shape but not for correctness.
- **Custom SCEP** fetches the authority's certificate but does not test the issuance challenge you configured.

So promise yourself live reachability and protocol validation, not proof of issuance. A successful connection means Fleet reached the authority and it answered in the expected protocol. For DigiCert, NDES, and Smallstep it means a little more; for Hydrant, custom EST, and custom SCEP it means only that. Where a bad secret for those three surfaces depends on the type: custom SCEP fails the first time a host requests a certificate through the proxy, while Hydrant and custom EST, which never deliver to a host at this release, only exercise their credentials when a caller invokes the test-issue endpoint.

## Where Fleet keeps the credentials

![Explanation](../_assets/icons/explanation.svg) Fleet stores each authority's configuration in its database. The secret column for each type, the API token, the password, the challenge, or the client secret, is encrypted at rest with the server private key, which is why that key is a hard prerequisite rather than a nicety. The non-secret fields, the URLs, the profile ID, the common name, the seat ID, the client ID, and the username, are stored in the clear so they can be listed and compared.

Reading a secret back out through the API is a separate, higher permission than reading the record, so an operator who can see that an authority exists cannot necessarily retrieve the token behind it. That matters when you decide who administers this surface.

## From a connected authority to a certificate on a host

![Explanation](../_assets/icons/explanation.svg) A connected authority does nothing by itself. A certificate lands on a host only when a configuration profile scoped to that host carries a Fleet variable naming the authority, and Fleet resolves that variable as it sends the profile to the device. There are two delivery mechanisms, and which one applies is decided by the family in the type table above.

Both lanes end at the certificate installed on the host.](assets/2.13-ca-delivery-loop.webp)

**The variable carries the authority's name.** The profile variables are `$FLEET_VAR_NDES_SCEP_CHALLENGE` and `$FLEET_VAR_NDES_SCEP_PROXY_URL` for NDES; `$FLEET_VAR_CUSTOM_SCEP_CHALLENGE_<CAName>` and `$FLEET_VAR_CUSTOM_SCEP_PROXY_URL_<CAName>` for custom SCEP; `$FLEET_VAR_SMALLSTEP_SCEP_CHALLENGE_<CAName>` and `$FLEET_VAR_SMALLSTEP_SCEP_PROXY_URL_<CAName>` for Smallstep; and `$FLEET_VAR_DIGICERT_DATA_<CAName>` and `$FLEET_VAR_DIGICERT_PASSWORD_<CAName>` for DigiCert. The `<CAName>` suffix is the name from the type table, parsed back out at delivery, which is why that name is held to letters, digits, and underscores. A renewal identifier variable and a Windows-specific SCEP certificate identifier variable complete the set.

**SCEP family: the host fetches through Fleet's proxy, and the challenge handling is not uniform.** For NDES, custom SCEP, and Smallstep the host does not enrol against your SCEP endpoint directly. It enrols against Fleet's own SCEP proxy, and Fleet relays the request to the upstream authority and returns the signed certificate. What differs between the three is the challenge:

- **Custom SCEP** puts the static upstream challenge you configured into the profile, and encodes a separate, Fleet-generated one-time challenge into the proxy URL. Fleet consumes that URL challenge once.
- **NDES** and **Smallstep** fetch the upstream challenge live and insert it into the profile, and their proxy URL carries no Fleet one-time challenge. Instead the proxy checks the age of the recorded challenge and may ask for the profile to be resent.

**DigiCert issues server-side and ships the certificate inside the profile.** Fleet requests the certificate from DigiCert itself, embeds the returned PKCS12 blob into `$FLEET_VAR_DIGICERT_DATA_<CAName>`, and puts a random password into `$FLEET_VAR_DIGICERT_PASSWORD_<CAName>`. The host never contacts DigiCert; the certificate arrives inside the profile it already receives.

**Which platforms each path serves.** The Apple configuration-profile path resolves all four delivery-capable types: NDES, custom SCEP, Smallstep, and DigiCert. Windows delivers NDES and custom SCEP through its own resolver, addressed by the Windows SCEP certificate identifier variable. Android delivers custom SCEP, referenced from its policy rather than from an uploaded profile ([2.12](2.12-bind-android-enterprise.md), [3.6](../03-connect-devices/3.6-enroll-android-devices.md)). Smallstep and DigiCert are established end-to-end on the Apple path at this release; do not assume they behave identically on Windows or Android without checking, because those platform resolvers were not built to the same shape.

**Hydrant and custom EST do not deliver through profiles at this release.** The EST family has no profile variable. The only way to obtain a certificate from a connected Hydrant or custom EST authority is the synchronous test-issue endpoint, which takes a certificate signing request and returns a certificate as PEM or PKCS7. It rejects every other type with a message saying it currently supports Hydrant and EST only. Treat it as a validation and testing path, not as fleet delivery: it hands one certificate back to the caller, it does not put one on a managed host. Connecting an EST-family authority today is mostly about proving reachability and exercising that endpoint.

## The GitOps representation

![How-to](../_assets/icons/howto.svg) In GitOps, authorities live under `org_settings.certificate_authorities`, grouped by type. NDES is a single object because there is only ever one; every other type is a list. The field names are the ones from the type table.

```yaml
org_settings:
  certificate_authorities:
    ndes_scep_proxy:            # a single object, not a list
      url: https://ndes.example.com/certsrv/mscep/mscep.dll
      admin_url: https://ndes.example.com/certsrv/mscep_admin/
      username: fleet-ndes
      password: $NDES_PASSWORD          # secret
    digicert:
      - name: MyDigiCert
        url: https://one.digicert.com
        api_token: $DIGICERT_API_TOKEN  # secret
        profile_id: abc123
        certificate_common_name: $FLEET_VAR_HOST_HARDWARE_SERIAL
        certificate_user_principal_names:
          - $FLEET_VAR_HOST_END_USER_EMAIL_IDP
        certificate_seat_id: $FLEET_VAR_HOST_END_USER_EMAIL_IDP
    custom_scep_proxy:
      - { name: MyCustomSCEP, url: https://scep.example.com/scep, challenge: $SCEP_CHALLENGE }
    smallstep:
      - { name: MySmallstep, url: https://ca.example.com, challenge_url: https://ca.example.com/challenge, username: fleet, password: $SMALLSTEP_PASSWORD }
    hydrant:
      - { name: MyHydrant, url: https://hydrant.example.com/est, client_id: fleet, client_secret: $HYDRANT_SECRET }
    custom_est_proxy:
      - { name: MyEST, url: https://est.example.com/.well-known/est, username: fleet, password: $EST_PASSWORD }
```

Keep the secret values out of the file. `fleetctl generate-gitops` emits this block for an existing deployment with each secret replaced by a placeholder, which is the sound way to capture what you have without committing a credential.

**The old keys are now a hard error.** Earlier Fleet configured some of these authorities under `org_settings.integrations` (`ndes_scep_proxy`, `digicert`, `custom_scep_proxy`). Those keys now fail the apply outright and tell you to move to `certificate_authorities`. If you are upgrading a GitOps repository from an older Fleet, expect that error and rename the block; there is no silent migration. [6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md) covers how the certificate-authorities block is applied and reconciled on its own path, separately from the rest of org settings.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) Because creation makes a live call, a successful connection is itself a real signal for reachability and protocol. Confirm it, then confirm the part creation cannot: that a certificate actually issues.

1. **Connect the authority and read the record back.** A clean create means Fleet reached it. Every successful connection also writes an activity record, so the connection is auditable ([1.5](../01-foundations/1.5-audit-and-activity.md), [8.12](../08-troubleshooting/8.12-audit-logs.md)).
2. **Issue one certificate end to end.** For a delivery-capable type, scope a test profile carrying the authority's variable to one host and watch the certificate install ([5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md)). For Hydrant or custom EST, use the test-issue endpoint with a sample signing request. This is the step that catches the credentials creation did not test.
3. **Record who owns the credential and when it expires.** An authority's token, password, or challenge has real reach and no human attached to notice when it lapses. Give it a named owner and a rotation date in the ownership register from [2.1](2.1-administration-model-and-deployment-choices.md).

Ongoing, this belongs to the global administrator group alongside the other integration credentials in this part. The credential behind each authority needs a rotation cycle, and a rotation is not finished until a certificate has issued through the renewed value.

## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting.svg) A connection can fail to create for two quite different reasons, and the returned error tells you which. Local validation rejects the request before any outbound call: a missing server private key, a malformed or empty URL or name, a disallowed character in the name, a missing required field, or more than one authority in a single request. Reachability or protocol failures come from the live call itself: the Fleet server cannot reach the authority's URL, a firewall sits between them, or the endpoint is not speaking the protocol Fleet expects for that type. Read the error to tell a local rejection from a live one; either way creation will not have stored anything.

A connection that creates cleanly and then fails to issue is the credential creation did not test, for Hydrant, custom EST, and custom SCEP, or a delivery problem in the profile itself. Certificate delivery through profiles, including how profile status reads during issuance, is [5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md). Apple MDM delivery diagnostics are [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md); Windows MDM diagnostics are [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md).

The endpoints and the publicly reachable proxy path are catalogued in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md).

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.1. The whole surface is Fleet Premium.

Custom EST and Smallstep are the two newest types at this release, added well after NDES, DigiCert, custom SCEP, and Hydrant. Their behaviour, error messages, and the vendor-side setup around them are the least settled, and the Free GitOps no-op described above is a direct consequence of one having been added without the emptiness check being updated to count it. Treat any Smallstep or EST specifics as version-fragile and re-check them against the exact release you run.
