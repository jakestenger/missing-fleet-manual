# Deploy on AWS or GCP

![Explanation](../_assets/icons/explanation-light.svg) Fleet’s cloud reference architectures give you a practical starting point for running the service in infrastructure your organization already knows. They connect Fleet to managed MySQL, Redis, and object storage, with cloud services handling the underlying compute and availability. This chapter helps you choose a reference, understand what it provisions, and adapt the provider-specific settings.

## Purpose and scope

![Explanation](../_assets/icons/explanation-light.svg) This chapter covers the two clouds Fleet publishes reference architectures for, what each one actually builds, and where the two differ enough to change your decision. How large to make any of it is [2.2](2.2-self-hosting-architecture-and-capacity.md). Running Fleet in containers or on plain virtual machines, on any cloud or none, is [2.4](2.4-deploy-with-containers-or-virtual-machines.md). Choosing where osquery results are delivered, and how that differs from the activity audit stream, is [2.8](2.8-activity-audit-logs-and-log-delivery.md), later in this part.

Fleet uses the same generic clients for these managed services as it does elsewhere. The cloud provider determines the endpoints and authentication they need, so settings that are appropriate on AWS may need different values on GCP.

The AWS section explains how to consume the reusable `fleetdm/fleet-terraform` module. Its example is a module block to incorporate into your Terraform configuration, with certificate, DNS, and migration resources supplied alongside it. Fleet’s deployment documentation and the module repository in the further reading provide the apply instructions for the pinned module.

The GCP section uses a complete reference tree from the Fleet repository. Clone the pinned tag, make the documented one-line syntax correction, and adapt it to your project before applying. For Azure, where Fleet provides community support but no reference architecture at this release, or a custom deployment, use the requirements in [2.2](2.2-self-hosting-architecture-and-capacity.md).

<a id="aws-and-gcp-are-not-two-equivalent-options"></a>

## Choose the AWS or GCP deployment path

![Explanation](../_assets/icons/explanation-light.svg) Both AWS and GCP have supported, documented reference architectures. Compare their deployment tooling, sizing coverage, and availability settings alongside your organization’s cloud preference.

**AWS is where Fleet runs Fleet.** The reference architecture is published as a reusable Terraform module, sized configurations run from five thousand hosts to three hundred thousand, and there are optional add-ons for monitoring and installer delivery. Fleet's own production deployment is built from that same module.

**GCP provides a complete reference deployment** with three sized configurations, from one thousand to one hundred and fifty thousand hosts. It has fewer sizing breakpoints and no published add-ons. Confirm the database availability setting in its external Terraform module as described below.

**Azure has no published architecture at this release.** Fleet points at community support. Nothing prevents running Fleet on Azure, since the dependencies are ordinary managed MySQL and Redis, but you will be assembling it yourself against [2.2](2.2-self-hosting-architecture-and-capacity.md) rather than following a reference.

## What the AWS architecture builds

![Reference](../_assets/icons/reference-light.svg) The Terraform stands up a VPC with public and private subnets and the usual access controls, then places Fleet inside it.

Fleet itself runs as containers on ECS with Fargate providing the compute, which is what makes the many identical instances from [2.2](2.2-self-hosting-architecture-and-capacity.md) straightforward: permissions come from task roles rather than from credentials in the container. The database is RDS Aurora MySQL 8, the cache is ElastiCache Redis, and there are S3 buckets for file carves and software installers. Osquery results go to Firehose, which syncs to an S3 bucket for whatever processes them next.

Two optional add-ons extend the AWS deployment. One provides CloudWatch alarms for operational monitoring. The other puts CloudFront in front of software installers so large package downloads can be served through the CDN. Consider both when planning monitoring and software distribution.

<a id="two-terraform-locations-and-which-one-you-want"></a>

## Choose a Terraform starting point

![How-to](../_assets/icons/howto-light.svg) Use the reusable AWS module as your deployment dependency, and the configuration in Fleet’s main repository as an example of how to consume it.

**The reusable module is its own repository**, `fleetdm/fleet-terraform`. That is the thing you consume.

The configuration inside the Fleet repository is Fleet’s own deployment. It consumes a pinned release of `fleetdm/fleet-terraform` and includes Fleet’s domains and infrastructure choices. Read it for the module wiring, then supply values appropriate to your own environment.

Pinning the module to a version reference, as Fleet's own deployment does, is the pattern to copy. It is also the reason the two can drift: the example is pinned to whichever module version Fleet last moved to, not to the module's newest release.

## Understand and consume Fleet's AWS module

![How-to](../_assets/icons/howto-light.svg) Start with Fleet’s Terraform root module to build the ECS-on-Fargate architecture described above. The example uses the module’s defaults and shows the inputs you will connect to your surrounding Terraform configuration.

You need an AWS account and credentials, Terraform 1.12 or newer with the AWS provider 5.68 or newer (the version Fleet's own deployment tests against at this release), a registered domain, and somewhere to keep Terraform state. For anything past a single operator applying by hand, keep that state in S3 with a DynamoDB lock rather than on a laptop.

The deployment is one `module "fleet"` block, pinned to a released module version, plus a certificate for the load balancer to terminate TLS with. Fleet's own example wires an ACM certificate and a Route 53 zone alongside it. What follows is that `module "fleet"` block on its own. It is an excerpt, not a file you can apply as printed, since it references a certificate the block itself doesn't create:

```hcl
terraform {
  required_version = ">= 1.12.0"
  required_providers {
    aws = { source = "hashicorp/aws", version = ">= 5.68.0" }
  }
}

provider "aws" {
  region = "us-east-2"
}

locals {
  domain_name = "fleet.example.com"
  vpc_name    = "fleet-vpc"
  zone_name   = "fleet.example.com"
  fleet_environment_variables = {
    FLEET_LOGGING_JSON = "true"
    # FLEET_LICENSE_KEY = "<key>"   # unlock Premium features
  }
}

module "fleet" {
  source          = "github.com/fleetdm/fleet-terraform?depth=1&ref=tf-mod-root-v1.30.0"
  certificate_arn = module.acm.acm_certificate_arn

  vpc = { name = local.vpc_name }

  fleet_config = {
    image       = "fleetdm/fleet:v4.90.0"          # this line chooses the Fleet version
    autoscaling = { min_capacity = 2, max_capacity = 5 }
    mem         = 4096                              # 4 GB; vulnerability scanning needs it
    cpu         = 512
    extra_environment_variables = local.fleet_environment_variables
  }
}
```

Two version pins matter here and they move independently. **`ref=tf-mod-root-v1.30.0` pins the Terraform module**, which releases on its own cadence from `fleetdm/fleet-terraform`, not on Fleet's. **`image = "fleetdm/fleet:v4.90.0"` pins the Fleet server**, and it is the line you change to run a particular release. Fleet's example pins its migration and MDM add-ons to their own tags for the same reason.

Three more pieces turn that excerpt into a configuration you can actually apply, and none of them are shown above because their exact wiring (input and output names) belongs to whatever `fleet-terraform` release you pinned, not to this manual:

- An `acm` module supplying `certificate_arn`
- An `aws_route53_zone` for that certificate to validate against
- The **migrations add-on**, `fleetdm/fleet-terraform/addons/migrations`, which runs Fleet's database migration as its own ECS task so the schema is prepared before the service comes up; wire it in rather than expecting the service to migrate itself

Add the MDM add-on as well if you will manage Apple devices, since it provisions the SCEP material [2.10](2.10-apple-mdm-configuration.md) depends on. The module's own repository documents the current inputs and outputs for each; match them to the module version you pinned above, since they can move between releases.

Once those pieces are wired into the same file as the `module "fleet"` block above, apply the complete configuration:

```bash
terraform init
terraform apply
```

If Terraform creates the Route 53 zone, add the nameservers from its `route53_name_servers` output to your parent domain. ACM validates the certificate through DNS, so delegation must resolve before the load balancer can serve the site over HTTPS.

That complete configuration (`module "fleet"` plus the acm, Route 53, and migrations pieces) is what provisions the VPC, the Aurora database, the ElastiCache Redis, the ECS service and the load balancer, and runs the schema migration. When the service is healthy behind the load balancer, open your domain and create the first administrator through the setup screen: the module stands up the infrastructure and the running server, and the first account is yours to create, the same first-run step [2.2](2.2-self-hosting-architecture-and-capacity.md#complete-first-run-setup) covers.

Sizing the autoscaling, database and cache for your host count is [2.2](2.2-self-hosting-architecture-and-capacity.md), which points at the reference architectures Fleet publishes with tested numbers from five thousand to three hundred thousand hosts. The module carries options this simple form leaves at their defaults, among them customer-managed KMS keys, Aurora blue-green cutovers, GovCloud partitions and CloudFront installer delivery; reach for one when a requirement asks for it, not before.

<a id="the-s3-settings-that-behave-differently-than-you-expect"></a>

## Configure S3 storage behavior

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Review the endpoint and region settings when connecting Fleet to S3. Both affect how Fleet’s generic AWS client discovers services and authenticates.

With ECS task roles or EKS IRSA (IAM Roles for Service Accounts), leave the endpoint URL unset and configure the region. An endpoint override affects every AWS API call Fleet makes, including the token-based authentication calls those roles require. It is broader than the S3 bucket endpoint alone.

Set the region explicitly. Otherwise, Fleet starts with `us-east-1` and asks the bucket for its actual region. If that discovery request fails, the resulting error refers to the fallback region and can obscure the intended destination.

## Cost on AWS follows report frequency

![Explanation](../_assets/icons/explanation-light.svg) Firehose is billed per use. Since it is the destination the reference architecture wires up for osquery results, the volume of data flowing through it is set by how often your scheduled reports run and how much each one returns.

Plan report frequency together with data freshness and cloud cost. Running a broad report twice as often produces roughly twice the result traffic when each run returns the same volume, and that traffic contributes to Firehose usage charges.

Which destination to use at all is [2.8](2.8-activity-audit-logs-and-log-delivery.md). What is specific here is that the cloud you are on determines whether that choice has a metered price attached.

## The Terraform role is broadly privileged

![Reference](../_assets/icons/reference-light.svg) The permission set Fleet documents as the minimum for applying its AWS Terraform is wide: full access to roughly twenty-five services, including identity, key management and secrets, with no resource restriction.

The deployment policy grants wildcard actions across identity, key management, and secrets without resource restrictions. The identity running it can therefore grant itself further access in the account, including when that identity belongs to CI. A dedicated deployment account or equivalent credential boundary provides a practical way to contain that reach; narrowing the individual permissions takes additional design and validation.

## What the GCP architecture builds

![Reference](../_assets/icons/reference-light.svg) Fleet runs as Cloud Run containers, which is the closest GCP analogue to Fargate and gives the same disposable-instance model.

The database is Cloud SQL for MySQL 8, reachable only over private networking rather than from the internet, which Cloud Run reaches through a serverless VPC connector. Redis is Memorystore, and the reference runs it in standalone rather than cluster mode. TLS terminates at a Google-managed certificate on the load balancer, which means the deployment expects you to delegate your domain's nameservers to the DNS zone the Terraform creates. The Cloud Run service references the public `fleetdm/fleet` image directly from Docker Hub rather than staging it through Artifact Registry first.

## Stand up a reference Fleet deployment on GCP

![How-to](../_assets/icons/howto-light.svg) Unlike AWS, there is no separately versioned, reusable module here. Fleet publishes only the raw Terraform behind its own GCP reference, `infrastructure/dogfood/terraform/gcp` in the `fleetdm/fleet` repository itself, pinned in what follows to the `fleet-v4.90.0` tag. Read it the way [the section above](#choose-a-terraform-starting-point) reads Fleet's AWS copy: a worked example built from plain resources and community modules, meant to be copied and adapted rather than consumed as a dependency. As pinned it does not pass `terraform validate` untouched; one file needs a one-line fix first, covered below, so treat it as a tree to correct and adapt rather than one that applies as cloned.

You need a GCP project with billing enabled, a registered domain to delegate, and Terraform with the `google` and `google-beta` providers (the configuration pins `google` to `4.51.0`). The configuration itself enables only two project APIs through `google_project_service` resources, `vpcaccess.googleapis.com` and `secretmanager.googleapis.com`; Cloud Run, Cloud SQL Admin, Memorystore, Compute Engine and Cloud DNS all need to already be enabled on the project before you apply. No backend block is defined anywhere in the configuration, so state defaults to local; add a GCS backend before letting this run from anywhere but one operator's machine.

Clone the pinned tag and go to that directory:

```bash
git clone --branch fleet-v4.90.0 --depth 1 https://github.com/fleetdm/fleet.git
cd fleet/infrastructure/dogfood/terraform/gcp
```

Only `project_id` has no default in `variables.tf` and must be supplied. `dns_zone` and
`dns_name` default to empty strings, which apply cleanly but leave the Cloud DNS zone and
managed certificate with nothing to bind, so they're operationally required even though
Terraform won't stop you from omitting them. The software-installers bucket name defaults to
`fleet-software-installers`, and Cloud Storage bucket names are unique across all of Google
Cloud, so a literal apply collides with whoever already holds that name; override it with one
of your own. `prefix` and `image` already default to the values below; set them explicitly if
you want a different resource prefix or a different Fleet version. Save the required and
operationally-required values as `terraform.tfvars` in that same directory, so `terraform
apply` picks it up automatically without a `-var-file` flag:

```hcl
project_id                      = "<your project id>"
prefix                          = "fleet"
dns_zone                        = "example.com."
dns_name                        = "fleet.example.com."
software_installers_bucket_name = "<your-globally-unique-bucket-name>"
image                           = "fleetdm/fleet:v4.90.0"   # this line chooses the Fleet version
```

Fix the one thing that stops the pinned tree from parsing first. Its `loadbalancer.tf` sets `custom_request_headers` twice inside the single `backends.default` object, and Terraform rejects the second as a redefined argument, so the configuration fails `terraform validate` as published. Delete the duplicate, then initialize the working directory before you validate: `terraform validate` inspects the installed modules, and this tree pulls community modules from the registry, so it errors with "Module not installed" until `terraform init` has fetched them.

```bash
sed -i.bak '/^      custom_request_headers = null$/d' loadbalancer.tf
terraform init
terraform validate
```

With the modules installed and the configuration parsing, apply it from inside `infrastructure/dogfood/terraform/gcp`:

```bash
terraform apply
```

That single apply provisions everything:

- A VPC with a serverless VPC Access connector and private service access peering
- A Cloud SQL for MySQL 8 instance sized by `db_tier` and pinned to `db_zone`, provisioned through the community `GoogleCloudPlatform/sql-db/google//modules/mysql` module, which is the module whose availability-type default you have to confirm yourself, as [above](#compare-failure-handling-across-the-architectures)
- A Memorystore Redis instance on the `STANDARD_HA` tier
- A Cloud Storage bucket for software installers with an HMAC service-account key wired into `FLEET_S3_SOFTWARE_INSTALLERS_*`, the long-lived-credential path this chapter recommends against where workload identity is available, so adapt `cloud_run.tf` yourself if you want the latter
- A Cloud Run service running Fleet, whose container command is `fleet prepare --no-prompt=true db; exec fleet serve`, meaning the schema migration runs as part of the service's own startup rather than as the separate task AWS's migrations add-on provides
- An HTTPS load balancer with a Google-managed certificate bound to a Cloud DNS zone the same apply creates

Unlike the AWS module, this tree declares no Terraform outputs, so the zone's nameservers are not printed when the apply finishes. Read them off the created Cloud DNS zone yourself, from the Google Cloud console or with `gcloud dns managed-zones describe`, and delegate those at your registrar. The same caution from the AWS procedure applies here too: do that before waiting on anything else, since the managed certificate will not issue until the delegation resolves, and until it does the load balancer has no certificate to serve. Once the domain resolves and the load balancer is healthy, open it and create the first administrator through the setup screen, the same first-run step [2.2](2.2-self-hosting-architecture-and-capacity.md#complete-first-run-setup) covers.

## Object storage on GCP works, despite what the architecture page says

![Explanation](../_assets/icons/explanation-light.svg) Fleet supports software installation and file carves using Google Cloud Storage at this release. The reference architecture page’s “coming soon” description is stale. The configuration below explains the supported storage paths and the extra bucket you need to add for carves.

Fleet reaches Google Cloud Storage through its S3 client, using Google’s S3-compatible endpoint with path-style addressing enabled. Software installers and file carves each have a documented, independent set of storage settings.

Choose between an HMAC key and Google Application Default Credentials. The published Terraform uses a long-lived HMAC key in the environment. Application Default Credentials can use the Cloud Run workload’s identity, removing the need to store that key. This option requires Google’s endpoint URL and cannot be combined with the access key settings.

The published Terraform creates a software-installers bucket. Add a separate bucket for file carves if you use them; until then, carve data falls back to MySQL as described in [1.6](../01-foundations/1.6-the-fleet-server.md).

Configure and authorize the carves bucket separately, including its own HMAC or workload identity credentials. Installer configuration does not configure the carve store. Run a test carve and confirm the blocks arrive in the intended bucket; the MySQL fallback continues to work but adds to database growth.

Prefer workload identity over HMAC keys where you have the choice. The reason is credential lifecycle rather than capability: an HMAC key is a long-lived secret somebody has to store, rotate and eventually find again, and workload identity removes it from the deployment entirely.

Fleet 4.91 can send clients directly to Google Cloud Storage for software installers, in-house apps, and bootstrap packages. Enable `s3.software_installers_signed_url` (`FLEET_S3_SOFTWARE_INSTALLERS_SIGNED_URL` in the environment or `--s3_software_installers_signed_url` on the command line) to return a presigned URL instead of streaming the file through Fleet. This reduces download traffic through the server, much as CloudFront signing does on AWS.

Fleet validates the following requirements at startup. If any check fails, it stops with a message naming the setting:

| Requirement | Why |
|---|---|
| The endpoint URL is `https` | The client is being sent straight at the object store |
| The endpoint URL is a `storage.googleapis.com` host | Presigned downloads are supported against Google Cloud Storage only, not against AWS or another S3-compatible store |
| An access key and secret are configured | Presigning uses those credentials, and without them every download would quietly fall back to being proxied |

Direct downloads require HMAC credentials, which creates a trade-off with workload identity. Fleet rejects presigning when Application Default Credentials or an STS assume-role is also configured. Choose between direct delivery with an HMAC key you will rotate and workload identity with proxied downloads.

If CloudFront is also configured, Fleet selects it first and does not use the presigned GCS path.

Software installer and bootstrap package links remain valid for six hours; in-house app links remain valid for five minutes. Account for these lifetimes when investigating a download, especially if you copy a link from a log.

Because object storage is reached through an S3 client, any store speaking the S3 API can serve as Fleet's object storage, on any cloud or none.

## Compare failure handling across the architectures

![Explanation](../_assets/icons/explanation-light.svg) Compare how each reference handles a failed database or cache instance before comparing instance sizes. Similar-looking node counts can represent different availability arrangements.

The AWS configurations specify three Redis nodes and two or three database nodes at every size, so the intent is legible from the sizing tables alone.

On GCP you have to read the Terraform, and the two dependencies land differently. **Redis is provisioned on Memorystore's high-availability tier**, which is a replicated instance with automatic failover, so the single node count in Fleet's published table is one highly available instance rather than a lone server.

**Cloud SQL depends on a value Fleet's own Terraform never sets.** `mysql.tf` hands the instance to the external `GoogleCloudPlatform/sql-db/google//modules/mysql` community module (pinned to `9.0.0`) without an `availability_type` argument, so whichever way that module defaults is what you get. At `9.0.0`, the module's own `variables.tf` defaults `availability_type` to `"REGIONAL"` (a replicated instance, not a lone zonal one), so as pinned here, the reference deployment gets Cloud SQL high availability by default. That default lives in the module, not in anything Fleet publishes or tests, so a future module bump could change it silently; confirm it against whichever module version you're actually applying, and set `availability_type = "REGIONAL"` explicitly in `mysql.tf` if you want that guaranteed regardless of what the module ships next.

[2.2](2.2-self-hosting-architecture-and-capacity.md) covers what availability actually requires, and the single-writer constraint described there applies identically on both clouds.

The per-instance allocation differs too, at one CPU and one gibibyte on GCP against one CPU and four gigabytes on AWS. Both hold their allocation constant as host count grows, which is the pattern from [2.2](2.2-self-hosting-architecture-and-capacity.md) reappearing on a second cloud and worth treating as confirmation rather than coincidence.

## Verification and ownership

![How-to](../_assets/icons/howto-light.svg) After Terraform succeeds, test the service from an administrator’s and a device’s perspective. These checks confirm the credentials, storage, DNS, and delivery paths work together.

Confirm the health endpoint from [2.2](2.2-self-hosting-architecture-and-capacity.md) is what your load balancer targets, and confirm it individually for MySQL and for Redis. Then check the thing that endpoint does not cover: upload a software installer and download it from a host. That single test exercises object storage, the credentials reaching it, and, on AWS with the CloudFront add-on, the delivery path in front of it, none of which any health check touches. If carves are in scope, run one as well, because it uses a different bucket and different credentials and a successful installer download proves nothing about it.

Confirm results are arriving at your log destination, and check the volume rather than only the presence, since on AWS that volume is the cost.

Ownership divides along a line that is easy to leave undrawn. The Terraform, the account it applies into, and the privileged credentials that run it belong to whoever owns cloud infrastructure. The Fleet settings inside it, particularly the object storage and database connection settings, belong to whoever owns Fleet. The failure mode this prevents is the common one where a cloud team changes a managed database version or a region default and nobody connects it to Fleet until hosts stop checking in.

## Precedence and edge cases

![Reference](../_assets/icons/reference-light.svg) Fleet's Terraform is one opinionated arrangement, not a requirement, and a few of its edges are worth knowing.

The published sizing figures assume on-demand pricing and exclude network egress and gateway charges, so they understate the real bill by an amount that depends entirely on your topology.

Running several Fleet deployments against one managed database instance needs it provisioned for all of them together, which is the same warning as [2.2](2.2-self-hosting-architecture-and-capacity.md) and is easier to trip over on a cloud where creating another database looks expensive.

On GCP, the managed certificate will not issue until the nameserver delegation is complete, so a deployment that otherwise applied successfully can sit unreachable while DNS propagates, with nothing in Fleet indicating why.

## Version notes

![Reference](../_assets/icons/reference-light.svg) Verified against Fleet 4.90.0. Cloud service names, instance classes and the contents of Fleet's Terraform all move independently of Fleet releases, so treat the shape as durable and the specifics as a starting point.

The statement on Fleet's reference architecture page that GCP support for software installation and file carves is coming soon does not match the product at this release. Both features have complete, documented configuration for Google Cloud Storage, including a workload identity option. Only the carves bucket is absent from the published GCP Terraform.

Azure has no published reference architecture at this release.
