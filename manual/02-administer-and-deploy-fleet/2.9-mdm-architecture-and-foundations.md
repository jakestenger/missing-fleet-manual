# MDM architecture and foundations

![Explanation](../_assets/icons/explanation-light.svg) Fleet brings Apple, Windows, and Android management into the same administration workflow. It uses each platform’s management capabilities to deliver settings and device actions, alongside the inventory and automation channels covered in Part I. Understanding those connections helps you plan a rollout that works for employees wherever their devices are used.

## Purpose and scope

![Explanation](../_assets/icons/explanation-light.svg) Before enrolling devices, prepare the network access and platform credentials that make MDM possible. This chapter explains what each connection requires and how to keep it working through certificate renewals and infrastructure changes.

Continue with [2.10](2.10-apple-mdm-configuration.md) for Apple configuration, [2.11](2.11-configure-windows-management.md) for Windows, and [2.12](2.12-bind-android-enterprise.md) for Android. Part III then guides enrollment once the platform connection is ready.

## Fleet is the server, the operating system is the client

![Explanation](../_assets/icons/explanation-light.svg) Apple and Windows devices have management clients built into the operating system. Fleet implements the server side of their vendor-defined protocols. For Android, Fleet uses Google’s management API, with Google handling communication to the device.

Setting up MDM establishes the platform’s trust in your deployment and gives enrolled devices a management connection. The certificates and enterprise bindings below provide that trust.

It also explains a distinction that runs through the whole manual. Fleet composes an instruction; the operating system carries it out. When a profile does not apply, the question is which of those two stages it reached, and [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) covers why that channel fails independently of the agent.

## What each platform gives you, and what Linux does not

![Reference](../_assets/icons/reference-light.svg) Plan around the capabilities each platform supplies. Fleet presents them together, while the underlying delivery and enrollment paths remain platform-specific.

| Platform | Management path |
|---|---|
| macOS, iOS, iPadOS | Apple MDM |
| Windows | Windows OMA-DM |
| Android | Android Management API |
| Linux | **None.** No platform MDM protocol exists |
| ChromeOS | Extension management, not MDM |

Fleet manages Linux through its agent channels. Linux disk encryption support is escrow-only, and configuration management generally remains with the tool that already owns it. Include those agent and external-tool workflows in a mixed-platform plan.

## The credentials you are taking on

<!-- SCREENSHOT-REUSE: SS-2.10-01. Reuse the Apple MDM credential/status capture to make ownership and renewal dates concrete; retain the platform diagram for the overall trust model. -->

![Reference](../_assets/icons/reference-light.svg) Give each platform credential an owner and record how it is renewed or replaced. The platform’s trust model determines the ongoing work.

**Apple's push certificate renews every year, and it is issued by Apple.** You generate a signing request in Fleet, take it to Apple's push certificate portal, and upload what comes back. That cycle repeats annually for as long as you manage Apple devices.

**Windows uses a certificate and key pair that you generate yourself.** Fleet is configured with them, and because you issue them you also choose the lifetime; the documented example is long-lived. There is no external party to renew with.

Android’s enterprise binding includes a Pub/Sub subscription tied to the Fleet server URL. Google must be able to reach that URL to deliver device events. Fleet accepts later changes to its URL setting, but the subscription continues using the original address and Android management stops receiving events. Choose the stable address before connecting Android ([2.12](2.12-bind-android-enterprise.md)).

**Apple Business Manager tokens expire too**, separately from the push certificate. Fleet warns in the interface when one is within thirty days of expiring, and shows expired ones distinctly.

### What happens if the Apple push certificate lapses

![Reference](../_assets/icons/reference-light.svg) Renew the existing Apple push certificate with the same Apple ID each year. Keeping that identity and certificate continuity preserves trust with enrolled devices.

**If the certificate expires, pushes stop and queued MDM work waits.** Configuration profile changes and other MDM commands sit in Pending until you renew the same certificate and upload it; delivery then resumes, without a server restart and with nothing to do on the devices, which stay enrolled throughout ([2.10](2.10-apple-mdm-configuration.md)).

Using a different Apple ID creates a new certificate instead of renewing the existing one. That breaks trust with enrolled devices and requires MDM to be turned off and back on for each Apple host, with action by the person using the device.

Use an organization-controlled Apple ID and keep its recovery details available to the people responsible for renewal. This lets ownership change without losing the account tied to your enrolled devices.

## What has to be reachable from the internet

![Explanation](../_assets/icons/explanation-light.svg) Devices need to reach Fleet while working away from your network, and Google needs to deliver Android events. Prepare public access to the required management paths through your ingress or reverse proxy.

The required paths depend on the platforms and enrollment features you enable.

**The set of paths grows with the features you use.** A basic Apple connection needs fewer than one using automatic enrollment, identity-provider authentication during setup, an end-user license agreement, and a bootstrap package. Each of those adds its own path.

**Two of Apple's paths sit outside Fleet's `/api` prefix**, because they are not REST endpoints and are not meant for API clients or browsers. A proxy rule written on the assumption that everything lives under `/api` will miss them.

**Windows uses four distinct Microsoft protocols**, for management, discovery, policy and enrolment token issuance, plus a terms-of-service path required for automatic enrollment. They are separate endpoints, and exposing some but not all produces enrollment that fails partway rather than cleanly.

The exact paths per platform and per feature belong in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md); what matters here is that this is a network design question to settle with whoever owns your ingress, before you promise a date.

## Connecting one platform at a time

![How-to](../_assets/icons/howto-light.svg) Take the platforms in sequence rather than together, and prove each one end to end before starting the next.

For each platform: establish the connection, enroll a small pilot group, and confirm three separate things reached the device. Inventory arriving proves the device is talking. A profile applying proves the delivery path works. A low-risk command completing proves the round trip, including the result coming back.

Check each result separately: inventory confirms communication, a profile confirms settings delivery, and a completed command confirms the response path. Recording all three gives you useful evidence when expanding the pilot.

Add the next platform after those checks succeed. This keeps the pilot easy to diagnose because each new connection has a known working baseline beside it.

## Verification and ownership

![How-to](../_assets/icons/howto-light.svg) Before you consider a platform connected, confirm all three of the checks above on a real device rather than in the interface alone.

Then assign owners, because MDM's ongoing cost is almost entirely renewal:

- **Each platform credential**, with its expiry date on a calendar that someone reads. Apple's is annual and external, so it needs the most warning.
- **The Apple ID or organizational account** each vendor credential was created under, recorded somewhere that survives the person who created it.
- **The ingress rules**, since the set of required paths changes when you turn on a new MDM feature rather than staying fixed at setup.
- **The Fleet server URL**, which several of these bind to and none of them tolerate changing quietly.

## Edge cases and precedence

![Reference](../_assets/icons/reference-light.svg) An expired credential can stop MDM while the agent continues reporting inventory. Check management delivery as well as host visibility when reviewing platform health; [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) explains the independent channels.

**Turning MDM off can be an administrative action; turning it back on usually is not.** Fleet admins and maintainers can turn MDM off for a single Apple or BYOD-Android host from the server ([5.7](../05-manage-devices/5.7-control-devices-and-send-mdm-commands.md)); what has no server-side shortcut is turning it back on, which depends on how the host enrolled and, on Apple hosts, often needs action on the device itself. Any event that forces a full off-and-on cycle therefore still has a cost proportional to your device count.

**Android's URL binding is one-way.** Changing the Fleet server URL after enrollment starts is not a reconfiguration, because the event subscription was created against the original address.

Linux hosts continue using their agent channels and are unaffected by MDM credential expiry. Their management plan still needs the agent-based actions supported on Linux.
