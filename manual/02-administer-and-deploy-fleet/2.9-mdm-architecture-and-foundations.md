# MDM architecture and foundations

Fleet ships no management agent of its own for MDM. Apple and Windows devices already carry a management client built into the operating system, and Fleet implements the server side those clients talk to. Android is the exception that proves the shape: there Fleet drives Google's management API rather than speaking to the device.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers what MDM requires of your deployment regardless of platform: what has to be reachable, which credentials you take on, and how long each one lasts.

Configuring a specific platform is [2.10](2.10-apple-mdm-configuration.md) for Apple, [2.11](2.11-configure-windows-management.md) for Windows and [2.12](2.12-bind-android-enterprise.md) for Android. Getting devices enrolled once the connection exists is Part III. What you want from this chapter is the shape of the commitment before you make it.

## Fleet is the server, the operating system is the client

![Explanation](../_assets/icons/explanation.svg) The management client on a Mac, a Windows PC or an Android device is part of the operating system. It was written by Apple, Microsoft or Google, it runs whether or not Fleet exists, and it speaks a protocol those vendors defined.

Turning on MDM means giving that client a server to talk to, and proving to the vendor that your server is entitled to manage their devices. Everything else in this chapter follows from that second part.

It also explains a distinction that runs through the whole manual. Fleet composes an instruction; the operating system carries it out. When a profile does not apply, the question is which of those two stages it reached, and [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) covers why that channel fails independently of the agent.

## What each platform gives you, and what Linux does not

![Reference](../_assets/icons/reference.svg) The management paths differ enough that "we use MDM" is not a single statement about an estate.

| Platform | Management path |
|---|---|
| macOS, iOS, iPadOS | Apple MDM |
| Windows | Windows OMA-DM |
| Android | Android Management API |
| Linux | **None.** No platform MDM protocol exists |
| ChromeOS | Extension management, not MDM |

**Linux has no MDM path at all.** Everything Fleet does on a Linux host arrives over the agent channels instead, which is why disk encryption there is escrow-only and why configuration management usually stays with whatever tool already owns it. Planning MDM coverage for a mixed estate means planning a different approach for the Linux part of it, not a smaller one.

## The credentials you are taking on

![Reference](../_assets/icons/reference.svg) This is the part that is easy to underestimate. Connecting a platform means holding a credential that platform issues or accepts, and the burden differs in kind rather than degree.

**Apple's push certificate renews every year, and it is issued by Apple.** You generate a signing request in Fleet, take it to Apple's push certificate portal, and upload what comes back. That cycle repeats annually for as long as you manage Apple devices.

**Windows uses a certificate and key pair that you generate yourself.** Fleet is configured with them, and because you issue them you also choose the lifetime; the documented example is long-lived. There is no external party to renew with.

**Android binds to an enterprise, and the binding is tied to your server URL.** Google has to be able to reach that URL for device events to arrive. **Fleet will let you change it afterwards and Google will not follow**: the push subscription was created against the old address, so the setting is accepted and the events stop. Treat the URL as fixed from the moment Android is connected, and settle it before the first device rather than after ([2.12](2.12-bind-android-enterprise.md)).

**Apple Business Manager tokens expire too**, separately from the push certificate. Fleet warns in the interface when one is within thirty days of expiring, and shows expired ones distinctly.

### What happens if the Apple push certificate lapses

![Reference](../_assets/icons/reference.svg) Worth stating plainly, because the expensive failure here is not the expiry itself.

**If the certificate expires, pushes stop and queued MDM work waits.** Configuration profile changes and other MDM commands sit in Pending until you renew the same certificate and upload it; delivery then resumes, without a server restart and with nothing to do on the devices, which stay enrolled throughout ([2.10](2.10-apple-mdm-configuration.md)).

**Renewing with a different Apple ID is the failure that costs the estate.** Fleet's guidance is explicit that you must use the same Apple ID year over year; renewing under a different one is treated as a new certificate, not a renewal, and it breaks trust with every enrolled device: MDM has to be turned off and back on for every Apple host, by hand, by the person using each device.

The practical implication is that this credential belongs to the organization rather than to a person. An Apple ID tied to an individual's account is one departure away from an estate-wide outage that no amount of server access can fix.

## What has to be reachable from the internet

![Explanation](../_assets/icons/explanation.svg) MDM is not something a device does from inside your network on a schedule you control. The device reaches your Fleet server directly, wherever it is, which means specific paths have to be publicly reachable.

Three things follow that surprise people planning the network side.

**The set of paths grows with the features you use.** A basic Apple connection needs fewer than one using automatic enrollment, identity-provider authentication during setup, an end-user license agreement, and a bootstrap package. Each of those adds its own path.

**Two of Apple's paths sit outside Fleet's `/api` prefix**, because they are not REST endpoints and are not meant for API clients or browsers. A proxy rule written on the assumption that everything lives under `/api` will miss them.

**Windows uses four distinct Microsoft protocols**, for management, discovery, policy and enrolment token issuance, plus a terms-of-service path required for automatic enrollment. They are separate endpoints, and exposing some but not all produces enrollment that fails partway rather than cleanly.

The exact paths per platform and per feature belong in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md); what matters here is that this is a network design question to settle with whoever owns your ingress, before you promise a date.

## Connecting one platform at a time

![How-to](../_assets/icons/howto.svg) Take the platforms in sequence rather than together, and prove each one end to end before starting the next.

For each platform: establish the connection, enroll a small pilot group, and confirm three separate things reached the device. Inventory arriving proves the device is talking. A profile applying proves the delivery path works. A low-risk command completing proves the round trip, including the result coming back.

Those three prove different links, which is why the third one matters even when the first two look healthy. A profile that shows as pending and a command that never returns are the same symptom from a reader's point of view, and separating them later is harder than checking now.

Only then add the next platform. Debugging two half-configured platform connections at once is materially harder than debugging one, because the failure modes look alike from the Fleet side while having nothing in common underneath.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) Before you consider a platform connected, confirm all three of the checks above on a real device rather than in the interface alone.

Then assign owners, because MDM's ongoing cost is almost entirely renewal:

- **Each platform credential**, with its expiry date on a calendar that someone reads. Apple's is annual and external, so it needs the most warning.
- **The Apple ID or organizational account** each vendor credential was created under, recorded somewhere that survives the person who created it.
- **The ingress rules**, since the set of required paths changes when you turn on a new MDM feature rather than staying fixed at setup.
- **The Fleet server URL**, which several of these bind to and none of them tolerate changing quietly.

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) **A lapsed credential does not degrade gracefully.** The device does not fall back to a reduced mode; the management channel simply stops, while the agent channels carry on reporting normally. A fleet that looks healthy in every inventory view can have a completely dead MDM path, which is the single most misleading state in Fleet and the reason [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) insists on asking which channel.

**Turning MDM off and on again is an end-user action on Apple hosts.** There is no administrative equivalent, so any event that forces it has a cost proportional to your device count and no shortcut.

**Android's URL binding is one-way.** Changing the Fleet server URL after enrollment starts is not a reconfiguration, because the event subscription was created against the original address.

**Linux hosts are unaffected by any of this**, having no MDM path to lose. That cuts both ways: they will not be caught by an expired certificate, and they will not receive anything MDM delivers either.
