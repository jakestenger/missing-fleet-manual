# Organization and server settings

Organization settings describe how Fleet should serve people and devices. Server settings describe how the Fleet service runs. They are different things, owned by different people, changed through different mechanisms, and worth keeping distinct in your head.

## Purpose and scope

This chapter covers what each kind of setting is for, which decisions are expensive to reverse, and how to change one safely.

It does not enumerate every setting. That belongs in [a.3 Configuration model and precedence](../09-appendices/a.3-configuration-model-and-precedence.md), along with the rules for what wins when two levels disagree, and **a.3 is not written yet**; Fleet's own configuration reference is the enumeration until it is, read with the caveat in [8.14](../08-troubleshooting/8.14-degradation.md) that its defaults have disagreed with the server's three times. What you want here is the map and the handful of settings that behave differently from the rest.

## Two kinds of configuration

![Explanation](../_assets/icons/explanation.svg) **Organization settings** are the ones your organization decides: what Fleet is called, who to contact, how long to keep things, which features are on, which integrations are connected. They live in Fleet's own configuration, they are readable and writable through the UI and the API, and they are the natural home for anything you would want reviewed as code.

**Server settings** are the ones the process needs in order to run: database and Redis connections, TLS, logging, proxying, process behaviour. They are supplied to the Fleet server as environment variables or a config file, they are owned by whoever owns the infrastructure, and they change when the deployment changes rather than when policy does.

The practical test for which is which: **if changing it requires restarting Fleet, it is a server setting.** If Fleet can apply it while running, it is an organization setting.

Manage organization settings through GitOps wherever you can, so that changes are reviewed, attributable, and reversible. Keep secrets out of source control. Details are in [6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md).

## The server URL is the one to get right first

![Explanation](../_assets/icons/explanation.svg) Of every setting in Fleet, this is the one that is cheapest to choose now and most expensive to change later.

`server_url` is the base address that people, automation, and devices all use to reach Fleet. It is baked into what fleetd receives, what fleetctl talks to, what your identity provider redirects to, and what platform management services call back on.

**If the server URL changes after Apple devices have MDM turned on, end users have to turn MDM off and back on to restore MDM features.** That is a per-device, human-performed action across every Mac, iPhone, and iPad you manage. There is no administrative shortcut for it.

**On Android the URL cannot change at all.** The Pub/Sub subscription that carries device events is created against one address and Fleet has no way to move it, so a URL change breaks Android management rather than degrading it. [2.8](2.8-windows-and-android-management-configuration.md) covers what that commits you to.

So plan the DNS name, the TLS certificate, the reverse proxy, and any URL path before enrolling a single device, and choose a name you will still be happy with after a reorganization or an acquisition. A vendor-neutral hostname you control outlasts one named after a team or a project.

Two related settings exist for the cases where one URL is not enough:

- **`sso_server_url`** covers the case where administrators sign in at a different address from the one devices use. When it is set, SSO works only from that URL.
- **`server_url_prefix`** serves Fleet under a path such as `/apps/fleet`, with no trailing slash. Note the naming here: this one is organization configuration, while the process-level `server.url_prefix` is a different setting in a different plane, and the two are easy to confuse when searching. Changing it also changes the URLs given to osquery through its flagfile, the configuration Fleet serves to agents, the prefix fleetctl uses, and the redirect URL registered with your identity provider. It is a coordinated change across four places rather than one setting.

## Organization name, logo, and contact URL

![Reference](../_assets/icons/reference.svg) `org_info` holds your organization's name and logo. Fleet accepts a light-mode and a dark-mode logo, each as either a path or a URL, and you set one or the other for each rather than both. Square logos work best at 256 by 256 pixels; a wordmark at 516 by 256.

The field worth pausing on is **`contact_url`**, because it is the only setting in this chapter your end users read. It appears in error messages shown to them, and it defaults to Fleet's own contact page. Left alone, a user who hits an error is invited to contact Fleet rather than your help desk. Set it to your internal support destination early, and it quietly does useful work every day thereafter.

These settings apply organization-wide only; there is no per-fleet version.

## Retention: how long Fleet keeps hosts and history

![Reference](../_assets/icons/reference.svg) Two settings decide what Fleet forgets, and both are off by default.

**Host expiry** removes a host record when it has not communicated with Fleet for a set number of days. `host_expiry_enabled` turns it on, `host_expiry_window` sets the number of days, and the window must be greater than zero once enabled. It can be set organization-wide or per fleet, which is useful when a lab of loaner machines should age out faster than a fleet of assigned laptops.

**Activity expiry** cleans up activity records, and the live report data associated with them, older than a set window. `activity_expiry_enabled` and `activity_expiry_window` control it. **It only ever removes activities with no host link left**, so it trims the general history and cannot orphan a device's story however short the window.

A third setting sits alongside it: **`preserve_host_activities_on_reenrollment`**, plural, keeps a host's activities across a wipe and re-enrollment, which is what you want when a machine is redeployed and you still care what happened on it. It is currently supported for company-owned Apple devices enrolled through Automated Device Enrollment.

**Its default depends on your deployment's history rather than on the setting itself.** The migration that introduced it decides once, on a single test: **on if any user account already existed when it ran, off if none did**. That is on for a deployment that upgraded into it and off for a fresh install, so two servers of the same version can differ. Read the value rather than assuming it. When it is off, a re-enrollment unlinks that host's activities, and any of those rows with no other host attached then fall within reach of the expiry window above ([1.5](../01-foundations/1.5-audit-and-activity.md)).

Decide these deliberately rather than leaving the defaults. Keeping everything forever is a choice with a storage cost; keeping nothing is a choice with an investigative cost.

### One exception to how GitOps works

Nearly every setting managed through GitOps follows the same rule: if it is absent from your YAML, it is reset to its default. That is what makes the configuration declarative, and it is usually exactly what you want.

**`host_expiry_settings` does not behave that way.** If it is not defined in your YAML files it keeps its current value rather than resetting.

This is the kind of exception that is harmless once you know it and confusing when you do not, because it means host expiry can be enabled in a deployment whose configuration repository says nothing about it. If you manage Fleet as code and want host expiry off, set it off explicitly rather than relying on its absence.

## GitOps mode: making the interface read-only

![How-to](../_assets/icons/howto.svg) Once configuration lives in a repository, the interface becomes a way to accidentally diverge from it. Someone changes a setting to fix something urgently, the change is never committed, and the next GitOps run silently reverts it.

Fleet has a setting for that. **GitOps mode marks the managed sections of the interface read-only**, with a tooltip pointing at the repository that owns them. It is enabled with `gitops_mode_enabled`, requires `repository_url` as a valid `http://` or `https://` address, and **requires Fleet Premium**.

Both are organization-wide only; there is no per-fleet version.

**It is a user interface setting and not an authorization boundary.** Fleet's own description is that GitOps mode is UI-only and that API permissions continue to follow the user's role. Anyone who can write through the API still can, unchanged. Treat it as a guardrail that stops accidental divergence, not as a control that makes the repository the only possible writer. If you need the second thing, that is a role and scope question, and it is [2.3](2.3-user-accounts-roles-and-service-identities.md).

**Labels are deliberately excluded.** GitOps mode does not restrict creating or editing labels in the interface, because omitting the `labels` key from YAML deletes labels not listed. Making labels read-only in the UI while that is true would leave people no safe place to manage them.

**A second exception to the reset rule lives here.** As with host expiry above, **omitting the `gitops` section from your YAML preserves whatever is already configured** rather than resetting it. So GitOps mode cannot be switched off by deleting the key; it has to be set to false explicitly.


## Verification and ownership

![How-to](../_assets/icons/howto.svg) Changing a setting is a small act with occasionally large reach, so give it the same handling as any other change: record the previous value, the intended outcome, who it affects, and how to put it back. Apply it in a non-production environment first where you have one.

Then verify along two paths, because a setting can look correct in the UI and still not have reached devices:

- **The administrator path.** Confirm the value is what you set, and that the change appears in the activity record with the right actor.
- **The device path.** Confirm a representative host behaves as intended. This matters most for anything that changes what agents receive.

Ownership splits along the same line as the settings themselves. The global administrator group owns organization settings and the review cycle for them. Whoever owns the infrastructure owns server settings, TLS, and the restart that a server-setting change implies.
