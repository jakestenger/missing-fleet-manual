# Self-hosting architecture and capacity

Sizing a Fleet deployment is mostly sizing MySQL. The application tier grows by adding identical instances rather than larger ones, and the constraint most likely to stop you sits between the two.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter is about how large to make a self-hosted deployment, how to make it survive a failure, and how to confirm it is healthy. [1.6](../01-foundations/1.6-the-fleet-server.md) explains why Fleet's state is split the way it is, and that model is assumed here rather than repeated. Running it on a specific cloud is [2.10](2.10-deploy-on-aws-or-gcp.md), containers and virtual machines are [2.11](2.11-deploy-with-containers-or-virtual-machines.md), and handing the result to whoever operates it is [2.12](2.12-production-readiness-and-handoff.md).

None of this applies to managed cloud hosting, where these are Fleet's decisions rather than yours. [2.1](2.1-administration-model-and-deployment-choices.md) covers which path you are on.

## What a deployment requires

![Reference](../_assets/icons/reference.svg) Fleet needs MySQL, Redis, and a TLS certificate. Object storage is a fourth requirement, though not from the first day, for reasons covered below.

**MySQL 8.0.44 is the floor.** Fleet is tested against 8.0.44, 8.4.8 and 9.5.0, and **9.6.0 is currently incompatible**. On Fleet a newer MySQL is not automatically a safer one, so an automatic minor-version upgrade on a managed database service can take a working deployment down. Check the version in both directions before you let anything upgrade itself. MariaDB and other drop-in replacements are unsupported.

**Redis has no minimum version stated**, and Fleet's own reference architectures specify Redis 7.x at every size.

**The TLS certificate has a requirement that catches people**, because it is enforced by the agent rather than by Fleet. The CNAME or a subject alternate name on the certificate must match the hostname that osquery uses to connect. A wildcard SAN covers a subdomain, so `*.example.com` serves `fleet.example.com`. If you use a self-signed certificate, the full chain has to reach the agent, which on the host side is the `--tls_server_certs` flag rather than anything Fleet controls.

**If Fleet terminates TLS itself, prefer an ECDSA certificate over RSA.** This is not a general security preference. RSA certificates have been associated with a specific performance problem in Fleet, arising from Go's standard library TLS implementation, and the cost lands on the Fleet process rather than on the proxy. If a load balancer terminates TLS instead, the question does not arise.

## What grows with your estate, and what does not

![Explanation](../_assets/icons/explanation.svg) Fleet publishes sized configurations for **its AWS reference architecture**, from five thousand hosts up to three hundred thousand. These are starting points to measure from, not capacity guarantees, and they describe one deployment on one cloud. Pick the row matching your enrolled host count, then revise it against your own reporting volume, API traffic and availability target.

Three of the eight published breakpoints, with the per-instance connection limit included because the next section turns on it:

| Up to | Fleet instances | Per instance | `max_open_conns` | Redis | MySQL |
|---|---|---|---|---|---|
| 5,000 hosts | 6 | 1 CPU, 4GB | 10 | 3 nodes, `cache.t4g.small` | 2 nodes, `db.t4g.medium` |
| 50,000 hosts | 15 | 1 CPU, 4GB | 20 | 3 nodes, `cache.r6g.large` | 3 nodes, `db.r6g.xlarge` |
| 300,000 hosts | 70 | 1 CPU, 4GB | 20 | 3 nodes, `cache.r6g.xlarge` | 3 nodes, `db.r6g.8xlarge` |

Read across the range rather than picking a row out of it, because the shape of the change carries more than any single row. Three things hold steady across a sixtyfold increase in hosts, and each is a design decision showing through.

**The per-instance allocation does not change.** Across every AWS row it stays at one CPU and four gigabytes, from the smallest deployment to the largest, and the count rises from six to seventy instead. The GCP rows hold their allocation constant too, at one CPU and two gigabytes, so the pattern is not an artefact of one cloud. This is the disposable server from [1.6](../01-foundations/1.6-the-fleet-server.md) expressed as a purchase order: because no instance holds state the others need, capacity in the application tier comes from adding instances rather than enlarging them.

**Redis stays at three nodes throughout** and climbs only two instance classes across the whole range. Redis holds work in progress, and work in progress does not accumulate the way records do. Sizing Redis by host count overshoots badly. The thing that actually stresses Redis is result volume from a single wide report, which is [1.6](../01-foundations/1.6-the-fleet-server.md)'s output buffer limit and is not a capacity question at all.

**MySQL absorbs nearly all of the growth.** It is the only component moving substantially in both node count and instance size. When a deployment is slow for capacity reasons rather than configuration ones, MySQL is where to look first.

The practical consequence is that the sizing conversation you need to have with whoever owns databases is a much longer conversation than the one you need to have with whoever owns compute.

## Database connections are a shared budget

![Explanation](../_assets/icons/explanation.svg) One number does not appear in the sizing tables as a resource, and it is the one most likely to stop a deployment that was scaling comfortably.

Each Fleet instance opens its own pool of connections to MySQL. **The default limit is fifty per instance.** Every one of Fleet's own sized configurations sets it to ten or twenty instead, at every scale including the largest.

The number the database sees is instances multiplied by the per-instance limit, so scaling the application tier out scales connection demand with it. Twenty-five instances left on the default would ask for as many as twelve hundred and fifty connections. The same twenty-five at Fleet's recommended twenty ask for five hundred. Treat that product as a worst-case ceiling rather than a count of connections actually held open. The symptom when you exceed it is connections being refused, which presents as a database fault and is arithmetic.

Fleet's own documented rule is to divide: take the connections your database will accept, divide by the maximum number of Fleet instances you will ever run at once, and leave a margin. Include the margin deliberately, because autoscaling and rolling deployments both mean the real instance count briefly exceeds the steady-state one.

The settings are `mysql.max_open_conns`, `mysql.max_idle_conns`, which defaults to the same fifty and should not exceed the open limit, and `mysql.conn_max_lifetime`, which defaults to unlimited so Fleet reuses a connection indefinitely unless something else closes it.

**A read replica has its own pool.** `mysql_read_replica.max_open_conns` is configured separately and inherits nothing from the primary, so a deployment with replicas has a second budget to calculate rather than a shared one.

**Connections are not the only ceiling.** Fleet uses prepared statements, and MySQL's `max_prepared_stmt_count` has to be at least `max_open_conns` multiplied by the maximum number of Fleet servers, multiplied by four. On a default MySQL this is reached well before anyone thinks to look at it, and the same scaling-out decision drives both numbers.

## Where Fleet sits in the network

![How-to](../_assets/icons/howto.svg) Fleet listens on all interfaces on port 8080 by default and serves TLS itself unless you tell it otherwise. In most production deployments a load balancer terminates TLS and Fleet sits behind it, which is also what lets you run the many identical instances the sizing tables assume.

**Outbound traffic matters more than people expect.** Vulnerability processing and device management both need Fleet to reach the internet. Fleet honours the conventional `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` environment variables, and there is one thing to be clear about: `NO_PROXY` is an exclusion list, not a fallback. Hosts named there connect directly. Nothing named there gets a second attempt through the proxy if the direct connection fails.

Putting Fleet behind a proxy also changes what it can see about your devices. Fleet works out a device's public IP from request headers, checking `True-Client-IP` first, then `X-Real-IP`, then the first value in `X-Forwarded-For`, and falling back to the connection's remote address. **Behind an ingress proxy that sets none of those headers, that fallback is the proxy's own address**, so every host appears to share one public IP. If public IP is something you rely on, confirm your proxy sets one of the three headers rather than assuming it does.

## Shared object storage is required before you scale software distribution

![Explanation](../_assets/icons/explanation.svg) Fleet starts without a bucket configured and does not refuse to run. That is what makes this a capacity decision rather than a prerequisite, and it is why it tends to be discovered late.

What breaks at the second instance depends on where each artifact falls back to, and the two destinations behave very differently.

| Artifact | Without object storage | What that means with several instances |
|---|---|---|
| File carves | MySQL | Stays shared and keeps working. Grows the database |
| Apple bootstrap packages | MySQL | Stays shared and keeps working. Grows the database |
| Software installers | Local filesystem | Breaks. Not shared, and the default location is a temporary directory |
| Software title icons | Local filesystem | Breaks. Same reason |

The database-backed fallbacks survive horizontal scaling because every instance reaches the same database. The filesystem-backed ones do not: an installer uploaded through one instance is invisible to every other instance, and to whichever instance the load balancer hands the download to. Fleet logs that it is using a local store and that this is not suitable for production, once for installers and once for icons.

So the rule is conditional rather than universal. If you deploy software or use Apple setup experience assets, configure object storage before the second instance. If you use neither, the fallbacks stay shared and the decision becomes one about database growth instead. Since every sized configuration above the smallest specifies at least six instances, most deployments built to those figures need it. A single-instance deployment is a different case and can be a legitimate small production one, as [2.11](2.11-deploy-with-containers-or-virtual-machines.md) covers.

## Availability, and the constraint that shapes it

![Explanation](../_assets/icons/explanation.svg) Fleet supports exactly one writable database. Read replicas are supported and help some access patterns, particularly API and command-line traffic. Multi-writer and group replication setups are not supported.

**The Fleet instances must reach a writer in the same datacenter.** Cross-region replication is available for failover, but writes have to be local. This one constraint decides the shape of most availability designs: you are building a single-region deployment with a failover story, not an active-active one across regions, and no amount of load balancer configuration changes that.

The rest is conventional. Put a load balancer in front of the Fleet instances, which also lets it terminate TLS and hand the Fleet process back that compute. Run Redis with the three nodes the reference configurations specify. Use a database service that supports automated backups and managed failover, and turn both on.

**The agents absorb more than most people expect.** When Fleet is unreachable, osquery keeps running its existing configuration and buffers results locally until the server comes back, bounded by the agent's own buffer setting. A Fleet outage is not a data-loss event within that buffer. Fleet's guidance treats short planned downtime as ordinary for this reason, which is the argument to make to whoever approves maintenance windows.

## Upgrades take the service down on purpose

![How-to](../_assets/icons/howto.svg) Database migrations are meant to run with the server offline. The sequence is to stop Fleet, run `fleet prepare db`, then start the new version.

Fleet's own guidance puts the window at seconds to minutes, even on large installations. Back the database up first, every time. Agents buffer through it, so the cost is a gap in freshness rather than a hole in your history.

Leaving old instances serving traffic against a partly migrated schema is not a supported configuration. Fleet's instruction is that all instances are shut down for the migration, so a rolling upgrade is not a supported alternative to the outage.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) Fleet exposes a health check at `/healthz`, and it is the right target for a load balancer. It returns 200 when the server is running and its connections to MySQL and Redis are healthy, and 500 when they are not. Individual dependencies can be checked with `/healthz?check=mysql` or `/healthz?check=redis`, which is how you tell the two apart quickly during an incident.

**Know what that check does not cover.** It tests exactly two dependencies. Object storage is not among them, so a deployment returning 200 can still be failing to deliver software installers. The response body carries no detail either; the reason a check failed is written to the server logs, not returned to the caller.

**Metrics are switched off until you configure them.** Fleet serves Prometheus-compatible metrics at `/metrics`, but that endpoint does not exist unless you set a basic auth username and password for it, or explicitly disable the auth requirement. With neither set, Fleet logs that the metrics endpoint is disabled at startup and serves nothing there. Anyone who points Prometheus at a fresh deployment and gets nothing back should read the startup log before debugging the scrape configuration.

Worth alerting on, from Fleet's own recommendations: host enrollment departing from its expected level, latency rising on HTTP endpoints, and error rates rising on them. Enrollment count is the one that catches problems the other two miss, because a deployment can be healthy by every infrastructure measure while hosts quietly stop checking in.

Ownership here divides along existing team lines, with one exception that falls between them.

| What | Owner | What they verify |
|---|---|---|
| The database, its version pinning, backups and failover | Whoever runs databases | That the version is inside Fleet's tested set, and that a restore has been performed |
| The TLS certificate and its renewal | Whoever runs TLS | That the name still matches what agents connect to |
| Connection limit arithmetic | Assign this deliberately | Instances multiplied by the per-instance limit, against what the database accepts |

The third row has no natural owner, which is why it needs an assigned one. It is the only number in the deployment that changes meaning whenever either of the other two teams acts alone.

## Shared database capacity and credential handling

![Reference](../_assets/icons/reference.svg) A few behaviours here are easy to get wrong in ways that are hard to attribute afterwards.

Running several Fleet deployments against one database server needs the server resourced for all of them together. Fleet's guidance is explicit that this requires more provisioning and offers no formula for it.

Pass credentials to Fleet through environment variables or a configuration file rather than command line arguments. Anything on the command line is visible to process listing, and it is also captured in the debug archive that Fleet asks for when you report a performance problem, which means it has to be scrubbed by hand before the archive leaves your organization.

A single virtual private server can carry hundreds and possibly thousands of hosts. The sized configurations start at five thousand for a reason, and reaching for the smallest of them at a few hundred hosts buys availability rather than capacity.

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.1. The MySQL version window is the most perishable fact in this chapter: 8.0.44 as the floor, 8.0.44, 8.4.8 and 9.5.0 tested, 9.6.0 incompatible. Confirm it against the release you are deploying rather than trusting this list, because it moves independently of everything else here.

The sized configurations are Fleet's published reference architectures and describe one opinionated deployment on one cloud. Treat the pattern across them as durable and the specific instance classes as a starting point to measure from.

The connection limit default of fifty has been stable for a long time, but it is a default rather than a recommendation, and the gap between it and Fleet's own sized configurations is deliberate rather than an inconsistency to resolve.
