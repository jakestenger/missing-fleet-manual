# Configure Windows management

Apple asks you to keep renewing things. Windows asks you to decide things once: you issue the certificate that runs its management yourself, no vendor renews it, and you live with the decision.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers connecting Fleet to Windows management: the certificate it needs, what the connection commits you to afterwards, and how to turn it off. Enrolling individual devices is [3.3](../03-connect-devices/3.3-enroll-windows-devices.md). What MDM asks of your deployment in general is [2.9](2.9-mdm-architecture-and-foundations.md).

Anyone arriving from Apple's model should set it aside here. Windows uses no vendor-issued certificate on an annual clock, and it does not fail the way Apple fails.

## What the Windows connection commits you to

![Explanation](../_assets/icons/explanation.svg) What you supply is a certificate and key pair you generate yourself. There is no external issuer and no vendor renewal: you choose the lifetime, Fleet's own example runs ten years, and nothing prompts you or expires on someone else's schedule. The pair also carries a consequence covered below that makes replacing or renewing it far harder than issuing it, because escrowed disk encryption data opens only under the exact certificate it was escrowed to.

The basic connection is Fleet Free. Zero-touch enrollment through Microsoft Entra ID is Fleet Premium, and Fleet rejects the Entra tenant and client IDs on Free; migrating Windows hosts from another MDM is Premium too. Migration, where you have it, is automatic, with no end user interaction.

Android's commitments are the inverse shape: no credential at all, nothing to renew, and a Fleet server URL that is fixed in practice even though Fleet will let you edit it ([2.12](2.12-bind-android-enterprise.md)).

## Windows: the certificate you issue yourself

![How-to](../_assets/icons/howto.svg) Fleet authenticates and manages its conversation with a Windows host using a certificate and key pair that you create. No certificate authority is involved and no vendor signs anything, which is why nothing about Windows appears on a renewal calendar.

Generate the key first, then a self-signed certificate over it:

```
openssl genrsa --traditional -out fleet-mdm-win-wstep.key 4096
openssl req -x509 -new -nodes -key fleet-mdm-win-wstep.key -sha256 -days 3652 \
  -out fleet-mdm-win-wstep.crt -subj '/CN=Fleet Root CA/C=US/O=Fleet.'
```

**On macOS the `openssl` command is usually LibreSSL, which does not support `--traditional`.** Run `openssl version` first. If it names LibreSSL, install and use real OpenSSL, or the first command fails and the failure will not obviously be about the wrong binary.

The `3652` is ten years, and it comes from Fleet's own documented example rather than from any requirement. Nothing forces that number, but before shortening it out of habit, read the next section: a short lifetime here is a genuine nuisance rather than good hygiene.

Give the contents to the server as `FLEET_MDM_WINDOWS_WSTEP_IDENTITY_CERT_BYTES` and `FLEET_MDM_WINDOWS_WSTEP_IDENTITY_KEY_BYTES`, then restart Fleet. The `_BYTES` suffix is a general convention across Fleet's configuration and not specific to these two: a variable ending in `_BYTES` wants the file's contents, and dropping the suffix gives you the variable that wants a path instead.

**The restart is not optional.** Fleet parses and caches this pair once, when `fleet serve` starts. This is one of the settings from [2.7](2.7-organization-and-server-settings.md) that cannot be changed from the UI or the API, because it is not stored in the database at all.

## The Windows key pair is also Fleet's escrow key

![Explanation](../_assets/icons/explanation.svg) The name says WSTEP, which is a Microsoft enrollment protocol, so the pair reads like a Windows-only detail. It is not. Fleet also uses this certificate to encrypt escrowed disk encryption keys, and only this certificate together with its private key can decrypt them again.

When a Windows host reports its disk encryption key, Fleet encrypts that key to the WSTEP certificate before storing it. When an administrator later views the key on the host details page, Fleet decrypts it with the WSTEP private key. Neither operation has a fallback.

**Replacing the pair makes every key escrowed under the old one unreadable, and a renewal alone does it too.** Retrieval matches the stored ciphertext against the current certificate by issuer and serial, so even a renewed certificate carrying the same key pair stops opening old escrow, and Fleet goes on reporting those keys as available. There is no supported operation that re-escrows an existing population on demand. Before any change, preserve and verify the old certificate and key; afterwards, cause genuinely new escrow by a method you have tested in your own deployment, and prove recovery by retrieving one credential ([7.6](../07-operate-fleet/7.6-maintain-credentials-certificates-and-access.md)). That is the reason a ten-year certificate is a defensible default here and a one-year certificate would not be.

Fleet chooses the decryption path by platform, and only Windows uses this one. Linux hosts with LUKS encrypt escrowed data with the server private key. Apple hosts use Fleet's Apple MDM certificate authority assets, and that path deliberately keeps previously rolled over authority certificates around so that keys escrowed against an earlier one still open. Windows has no such accommodation.

> Fleet's published configuration reference states that changing this pair affects **macOS** hosts. Reading the code at this release, the WSTEP path is selected for Windows hosts and Apple hosts take the certificate authority path instead. Treat the platform in that sentence as Windows.

## Turning Windows MDM on

![How-to](../_assets/icons/howto.svg) With the pair in place and the server restarted, go to **Settings > Integrations > Mobile device management (MDM)**, select **Turn on** next to Windows, and set the toggle.

You are also choosing an end user experience here. **Automatic** is the recommended setting and means enrollment happens without anyone being asked. **Manual** requires the end user to take an action to turn management on.

Fleet's guidance is that turning Windows MDM on **disables Windows tamper protection** on the host, as a consequence of how Windows hands management to an MDM rather than as a Fleet decision. **Nothing in Fleet's source at this release establishes it**, so confirm it on a test machine before quoting it in a compliance answer. Either way it is worth raising early, because the answer changes a security posture.

## Windows enrollment waits for a sign-in

![Explanation](../_assets/icons/explanation.svg) **Fleet's guidance is that Windows completes MDM enrollment in the context of a signed-in user**, not at boot and not when the agent first checks in.

Note the boundary, because it decides what you can conclude. Fleet's source establishes only that the agent's check-in **starts** registration: Orbit runs as a system service and calls Windows' registration API without inspecting who is logged in ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)). When Windows **completes** enrollment is Windows' behaviour, and nothing in the checkout establishes it.

Taking the guidance at face value: a host with no interactive session has not finished enrolling. A freshly imaged machine sitting at the lock screen, a kiosk, a shared device waiting for its first user would all report MDM as **Off**, and any commands, configuration profiles and disk encryption settings aimed at them stay queued. Nothing is lost and nothing needs re-sending, because Fleet keeps offering the enrollment. Fleet puts the completion at about thirty seconds after the next sign-in; that figure is Fleet's, not this manual's, and it is worth confirming on a test machine before planning a rollout window around it.

The practical consequence is worth carrying whether or not the timing holds exactly: an estate of unattended Windows machines reporting MDM `Off` is a state to rule out before treating the rollout as broken.

## Automatic enrollment through Microsoft Entra ID

![How-to](../_assets/icons/howto.svg) Automatic enrollment on Windows is a Fleet Premium capability and it runs through Microsoft Entra ID, which puts the sign-in during device setup in Microsoft's hands rather than Fleet's.

**Check what Entra already does before you start.** Some Intune deployments have automatic enrollment into Intune switched on, and if it is on your devices will never appear in Fleet. In Intune, under **Devices > Device onboarding > Enrollment > Automatic Enrollment**, both **MDM user scope** and **WIP user scope** need to be **None**.

Licensing is Microsoft's and it is per-person. You, as the administrator, need a Microsoft Enterprise Mobility + Security E3 license. Every end user who enrolls automatically or turns MDM on by hand needs at least Entra ID P1, which they already have if they hold an E3 or E5. Fleet's own Autopilot notes describe that end-user requirement as their **current understanding** rather than something verified end to end, so price a rollout against Microsoft's terms rather than against this summary ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)).

**Two of these paths need Fleet Premium as well.** The Settings-app and automatic enrollment routes both depend on Entra tenant and client IDs, which Fleet Free rejects, and **migrating Windows hosts from another MDM is Premium** too. A Free deployment has the agent-driven path and no migration.

The connection itself is three values that have to agree, held in two consoles:

- **The Entra tenant ID**, copied from Entra and added in Fleet under **Settings > Integrations > MDM > Windows Enrollment**.
- **The MDM URLs**, copied from Fleet and pasted into a custom application you create in Entra under **Mobility (MDM and WIP)**. The same application's **Application ID URI** must be set to your Fleet URL.
- **The application client ID**, copied back from that Entra application into Fleet. Entra issues v2 access tokens whose audience is the client ID, so Fleet cannot validate a token without it.

**Two different omissions produce exactly the same error.** If either the tenant ID or the client ID is missing, the end user sees "Device management could not be enabled" and cannot enroll. The message does not distinguish them, so check both.

Your Fleet URL also has to be registered in Entra as a verified custom domain, which means a TXT or MX record at your registrar. On managed cloud hosting you do not control that DNS, so ask Fleet to create the record.

The application then needs Microsoft Graph permissions, and both kinds. Delegated: `Group.Read.All` and `Group.ReadWrite.All`. Application: `Device.Read.All`, `Device.ReadWrite.All`, `Directory.Read.All`, `Group.Read.All`, `User.Read.All`. Grant admin consent afterwards, or the permissions are requested but not usable.

Connecting Entra also gives end users the **Settings > Access work or school** route for turning management on themselves, and Fleet collects the email address from that sign-in and stores it as the host's IdP username. During setup, users are prompted to configure Windows Hello and a PIN.

Windows Autopilot sits on top of this once it is working, and does for Windows roughly what Automated Device Enrollment does for Apple: branding and a shaped out-of-box experience. It does not replace anything above.

## Migrating Windows hosts from another MDM

![How-to](../_assets/icons/howto.svg) Fleet can move Windows hosts off another MDM with no end user interaction at all. Turn Windows MDM on, install fleetd on the hosts and wait for them to appear, then return to **Manage Windows MDM** and select **Automatically migrate hosts connected to another MDM solution**. Fleet notifies each host and the move usually takes minutes.

That silence is the difference from Apple, where migration requires the person holding the device to accept it. On Windows nobody is asked, which makes the rollout easier and makes a bad migration harder to notice.

![Troubleshooting](../_assets/icons/troubleshooting.svg) When hosts stay stuck at MDM "Off" after a migration, look at the host before the Fleet configuration. **Residue from the previous manager is the case Fleet has written a script for**, `fix-windows-mdm-migration.ps1`, which is the strongest indication available that it is worth ruling out first; nothing establishes how it ranks against other causes. Its signature is an enrollment error in the fleetd logs, typically a `400` or `0x8018000a`, sometimes with local accounts locked as well. Run the script, reboot, then refetch the host in Fleet.

Third-party RMM agents left behind by the old deployment cause the same symptoms independently. Agents such as N-able, ConnectWise or Kaseya can block enrollment and, in some cases, stop Windows Update working. Remove the ones nobody needs any more.

Re-using a device that was previously enrolled through Autopilot needs its stale records cleared first, in a specific order: delete the host in Fleet, delete the device object in **Entra ID > Devices**, then confirm in Intune that the hardware hash is still registered and the right profile assigned. **Do not delete the Autopilot registration itself.** Sync, then reset the device. If the first boot skips Autopilot, restart and try again, since the sync can lag by a few minutes.

## Turning Windows MDM off

![How-to](../_assets/icons/howto.svg) **This is destructive to more than MDM.** `uninstall-fleetd-windows.ps1` first unregisters the device from MDM, then stops and removes fleetd itself — Orbit, osqueryd, and Fleet Desktop are all torn down, along with their service, program files, and registry entries. Once it has run, the host stops reporting inventory, sending osquery results, and executing scripts or software installs through Fleet, not just losing MDM management, until fleetd is reinstalled. Confirm that is the outcome you want before running it at scale.

Turning Windows MDM off is per host and then global. Run Fleet's `uninstall-fleetd-windows.ps1` script across the Windows hosts, which turns MDM off and removes fleetd with it, then switch Windows MDM off under **Settings > Integrations > MDM**.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) For Windows, the test is a real device rather than a settings page: a freshly wiped machine, a test Entra user, **Set up for an organization** at the setup screen, and then the Fleet icon in the taskbar leading to a **My device** page showing **Online**. Because enrollment depends on a sign-in, a status check that does not involve signing in tells you very little.

Ownership is worth naming explicitly, because automatic enrollment puts a piece of your Fleet deployment inside somebody else's administrative boundary. The Windows key pair is yours alone and belongs wherever you keep server secrets. The Entra tenant, the application registration and its Graph permissions belong to whoever administers Microsoft identity, who may not be the person running Fleet.

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) A few behaviours here surprise people, and all of them come from the boundary between Fleet and the platform vendor.

Intune's automatic enrollment silently wins over Fleet. It is not reported as a conflict; the devices simply never arrive.

Enrolling against an identity provider that is not federated with Entra is not supported. A third-party IdP works only through that federation.

A Windows host that has never had an interactive sign-in is not failed, it is waiting, and it will report **Off** for as long as nobody logs in.
