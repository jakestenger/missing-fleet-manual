# Windows and Android management configuration

Apple asks you to keep renewing things. Windows and Android ask you to decide things, once, and then live with the decision.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers connecting Fleet to Windows management and to Android Enterprise: the credentials each one needs, what the connection commits you to afterwards, and how to turn either one off. Enrolling individual devices is [3.3](../03-connect-devices/3.3-enroll-windows-devices.md) and [3.6](../03-connect-devices/3.6-enroll-android-and-chromeos-devices.md). What MDM asks of your deployment in general is [2.9](2.9-mdm-architecture-and-foundations.md).

Anyone arriving from Apple's model should set it aside here. Neither platform uses a vendor-issued certificate on an annual clock, and neither fails the way Apple fails.

## Two platforms, two kinds of commitment

![Reference](../_assets/icons/reference.svg) The credential story is the fastest way to see how differently these two behave.

| | Windows | Android |
|---|---|---|
| **What you supply** | A certificate and key pair you generate yourself | Nothing. You bind a Google enterprise |
| **Who issues it** | You. There is no external issuer | Google, through a signup flow |
| **Renewal** | No vendor renewal. You choose the lifetime, and Fleet's example runs ten years | None. The binding does not expire |
| **What is hard to change afterwards** | The certificate and key pair, because escrowed data opens only under the exact certificate it was escrowed to | The Fleet server URL. Fleet accepts a new one; Google keeps pushing to the old one |
| **Basic connection** | Fleet Free | Fleet Free, for work profiles on personal devices |
| **Zero-touch or company-owned** | Fleet Premium, through Microsoft Entra ID. Fleet rejects the Entra tenant and client IDs on Free | **Not licence-gated in Fleet's server at this release.** Nothing in the Android module checks a licence, and a company-owned QR enrollment is one query parameter on the same token endpoint the personal path uses ([3.6](../03-connect-devices/3.6-enroll-android-and-chromeos-devices.md)). Confirm against Fleet's own pricing rather than against behaviour |
| **Migrating from another MDM** | Automatic, with no end user interaction | Manual at both ends |

Windows gives you a credential with no vendor behind it and no renewal date, which means nothing prompts you and nothing expires on someone else's schedule. Android gives you no credential at all, and a server URL that is fixed in practice even though Fleet will let you edit it. Neither costs anything on the day you set it up, and the Windows certificate carries a consequence covered below that makes replacing or renewing it far harder than issuing it.

## Windows: the certificate you issue yourself

![How-to](../_assets/icons/howto.svg) Fleet authenticates and manages its conversation with a Windows host using a certificate and key pair that you create. No certificate authority is involved and no vendor signs anything, which is why nothing about Windows appears on a renewal calendar.

Generate the key first, then a self-signed certificate over it:

```
openssl genrsa --traditional -out fleet-mdm-win-wstep.key 4096
openssl req -x509 -new -nodes -key fleet-mdm-win-wstep.key -sha256 -days 3652 \
  -out fleet-mdm-win-wstep.crt -subj '/CN=Fleet Root CA/C=US/O=Fleet.'
```

**On macOS the `openssl` command is usually LibreSSL, which does not support `--traditional`.** Run `openssl version` first. If it names LibreSSL, install and use real OpenSSL, or the first command fails and the failure will not obviously be about the wrong binary.

The `3652` is ten years, and it comes from Fleet's own documented example rather than from any requirement. Nothing forces that number, but before shortening it out of habit, read the next section: a short lifetime here is a genuine nuisance rather than good hygiene.

Give the contents to the server as `FLEET_MDM_WINDOWS_WSTEP_IDENTITY_CERT_BYTES` and `FLEET_MDM_WINDOWS_WSTEP_IDENTITY_KEY_BYTES`, then restart Fleet. The `_BYTES` suffix is a general convention across Fleet's configuration and not specific to these two: a variable ending in `_BYTES` wants the file's contents, and dropping the suffix gives you the variable that wants a path instead.

**The restart is not optional.** Fleet parses and caches this pair once, when `fleet serve` starts. This is one of the settings from [2.7](2.7-organization-and-server-settings.md) that cannot be changed from the UI or the API, because it is not stored in the database at all.

## The Windows key pair is also Fleet's escrow key

![Explanation](../_assets/icons/explanation.svg) The name says WSTEP, which is a Microsoft enrollment protocol, so the pair reads like a Windows-only detail. It is not. Fleet also uses this certificate to encrypt escrowed disk encryption keys, and only this certificate together with its private key can decrypt them again.

When a Windows host reports its disk encryption key, Fleet encrypts that key to the WSTEP certificate before storing it. When an administrator later views the key on the host details page, Fleet decrypts it with the WSTEP private key. Neither operation has a fallback.

**Replacing the pair makes every key escrowed under the old one unreadable, and a renewal alone does it too.** Retrieval matches the stored ciphertext against the current certificate by issuer and serial, so even a renewed certificate carrying the same key pair stops opening old escrow, and Fleet goes on reporting those keys as available. There is no supported operation that re-escrows an existing population on demand. Before any change, preserve and verify the old certificate and key; afterwards, cause genuinely new escrow by a method you have tested in your own deployment, and prove recovery by retrieving one credential ([7.6](../07-operate-fleet/7.6-maintain-credentials-certificates-and-access.md)). That is the reason a ten-year certificate is a defensible default here and a one-year certificate would not be.

Fleet chooses the decryption path by platform, and only Windows uses this one. Linux hosts with LUKS encrypt escrowed data with the server private key. Apple hosts use Fleet's Apple MDM certificate authority assets, and that path deliberately keeps previously rolled over authority certificates around so that keys escrowed against an earlier one still open. Windows has no such accommodation.

> Fleet's published configuration reference states that changing this pair affects **macOS** hosts. Reading the code at this release, the WSTEP path is selected for Windows hosts and Apple hosts take the certificate authority path instead. Treat the platform in that sentence as Windows.

## Turning Windows MDM on

![How-to](../_assets/icons/howto.svg) With the pair in place and the server restarted, go to **Settings > Integrations > Mobile device management (MDM)**, select **Turn on** next to Windows, and set the toggle.

You are also choosing an end user experience here. **Automatic** is the recommended setting and means enrollment happens without anyone being asked. **Manual** requires the end user to take an action to turn management on.

Fleet's guidance is that turning Windows MDM on **disables Windows tamper protection** on the host, as a consequence of how Windows hands management to an MDM rather than as a Fleet decision. **Nothing in Fleet's source at this release establishes it**, so confirm it on a test machine before quoting it in a compliance answer. Either way it is worth raising early, because the answer changes a security posture.

## Windows enrollment waits for a sign-in

![Explanation](../_assets/icons/explanation.svg) **Fleet's guidance is that Windows completes MDM enrollment in the context of a signed-in user**, not at boot and not when the agent first checks in.

Note the boundary, because it decides what you can conclude. Fleet's source establishes only that the agent's check-in **starts** registration: Orbit runs as a system service and calls Windows' registration API without inspecting who is logged in ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)). When Windows **completes** enrollment is Windows' behaviour, and nothing in the checkout establishes it.

Taking the guidance at face value: a host with no interactive session has not finished enrolling. A freshly imaged machine sitting at the lock screen, a kiosk, a shared device waiting for its first user would all report MDM as **Off**, and any commands, configuration profiles and disk encryption settings aimed at them stay queued. Nothing is lost and nothing needs re-sending, because Fleet keeps offering the enrollment. Fleet puts the completion at about thirty seconds after the next sign-in; that figure is Fleet's, not this manual's, and it is worth confirming on a test machine before planning a rollout window around it.

The practical consequence is worth carrying whether or not the timing holds exactly: an estate of unattended Windows machines reporting MDM `Off` is a state to rule out before treating the rollout as broken.

## Automatic enrollment through Microsoft Entra ID

![How-to](../_assets/icons/howto.svg) Automatic enrollment on Windows is a Fleet Premium capability and it runs through Microsoft Entra ID, which puts the sign-in during device setup in Microsoft's hands rather than Fleet's.

**Check what Entra already does before you start.** Some Intune deployments have automatic enrollment into Intune switched on, and if it is on your devices will never appear in Fleet. In Intune, under **Devices > Device onboarding > Enrollment > Automatic Enrollment**, both **MDM user scope** and **WIP user scope** need to be **None**.

Licensing is Microsoft's and it is per-person. You, as the administrator, need a Microsoft Enterprise Mobility + Security E3 license. Every end user who enrolls automatically or turns MDM on by hand needs at least Entra ID P1, which they already have if they hold an E3 or E5. Fleet's own Autopilot notes describe that end-user requirement as their **current understanding** rather than something verified end to end, so price a rollout against Microsoft's terms rather than against this summary ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)).

**Two of these paths need Fleet Premium as well.** The Settings-app and automatic enrollment routes both depend on Entra tenant and client IDs, which Fleet Free rejects, and **migrating Windows hosts from another MDM is Premium** too. A Free deployment has the agent-driven path and no migration.

The connection itself is three values that have to agree, held in two consoles:

- **The Entra tenant ID**, copied from Entra and added in Fleet under **Settings > Integrations > MDM > Windows Enrollment**.
- **The MDM URLs**, copied from Fleet and pasted into a custom application you create in Entra under **Mobility (MDM and WIP)**. The same application's **Application ID URI** must be set to your Fleet URL.
- **The application client ID**, copied back from that Entra application into Fleet. Entra issues v2 access tokens whose audience is the client ID, so Fleet cannot validate a token without it.

**Two different omissions produce exactly the same error.** If either the tenant ID or the client ID is missing, the end user sees "Device management could not be enabled" and cannot enroll. The message does not distinguish them, so check both.

Your Fleet URL also has to be registered in Entra as a verified custom domain, which means a TXT or MX record at your registrar. On managed cloud hosting you do not control that DNS, so ask Fleet to create the record.

The application then needs Microsoft Graph permissions, and both kinds. Delegated: `Group.Read.All` and `Group.ReadWrite.All`. Application: `Device.Read.All`, `Device.ReadWrite.All`, `Directory.Read.All`, `Group.Read.All`, `User.Read.All`. Grant admin consent afterwards, or the permissions are requested but not usable.

Connecting Entra also gives end users the **Settings > Access work or school** route for turning management on themselves, and Fleet collects the email address from that sign-in and stores it as the host's IdP username. During setup, users are prompted to configure Windows Hello and a PIN.

Windows Autopilot sits on top of this once it is working, and does for Windows roughly what Automated Device Enrollment does for Apple: branding and a shaped out-of-box experience. It does not replace anything above.

## Migrating Windows hosts from another MDM

![How-to](../_assets/icons/howto.svg) Fleet can move Windows hosts off another MDM with no end user interaction at all. Turn Windows MDM on, install fleetd on the hosts and wait for them to appear, then return to **Manage Windows MDM** and select **Automatically migrate hosts connected to another MDM solution**. Fleet notifies each host and the move usually takes minutes.

That silence is the difference from Apple, where migration requires the person holding the device to accept it. On Windows nobody is asked, which makes the rollout easier and makes a bad migration harder to notice.

![Troubleshooting](../_assets/icons/troubleshooting.svg) When hosts stay stuck at MDM "Off" after a migration, look at the host before the Fleet configuration. **Residue from the previous manager is the case Fleet has written a script for**, `fix-windows-mdm-migration.ps1`, which is the strongest indication available that it is worth ruling out first; nothing establishes how it ranks against other causes. Its signature is an enrollment error in the fleetd logs, typically a `400` or `0x8018000a`, sometimes with local accounts locked as well. Run the script, reboot, then refetch the host in Fleet.

Third-party RMM agents left behind by the old deployment cause the same symptoms independently. Agents such as N-able, ConnectWise or Kaseya can block enrollment and, in some cases, stop Windows Update working. Remove the ones nobody needs any more.

Re-using a device that was previously enrolled through Autopilot needs its stale records cleared first, in a specific order: delete the host in Fleet, delete the device object in **Entra ID > Devices**, then confirm in Intune that the hardware hash is still registered and the right profile assigned. **Do not delete the Autopilot registration itself.** Sync, then reset the device. If the first boot skips Autopilot, restart and try again, since the sync can lag by a few minutes.

## Android: binding an enterprise

![How-to](../_assets/icons/howto.svg) There is no certificate to generate for Android. You bind Fleet to an Android Enterprise, and everything afterwards flows through Google.

Fleet supports devices that are Play Protect certified, previously known as GMS. Start at **Settings > Integrations > Mobile device management (MDM)** and select **Connect**, which opens Google's signup. Which flow you get depends on what your organization already uses, and the difference is mostly about proving you own your domain.

With **Google Workspace**, sign up with an existing admin account and a free Android Enterprise subscription is added to your Workspace. With **Microsoft 365**, enter your Microsoft email and choose **Sign in with Microsoft**. With **neither**, sign up with a work email rather than a personal `@gmail.com` address, and verify your domain in the Google Admin console afterwards.

**Whether Microsoft 365 organizations need to verify the domain is unclear at this release.** Fleet's guide states in one place that Google Workspace and Microsoft organizations do not need to verify domain ownership, and then instructs Microsoft 365 administrators to do exactly that as the last two steps of their procedure. The two readings cannot both be right and the source does not resolve it. Verifying the domain is harmless and satisfies either reading, so do it unless you already know your domain is verified.

**The Workspace account needs super administrator privileges, but only for a moment.** It is used for the initial enterprise binding and nothing else. Once the binding exists it survives, so the privileges can be reduced immediately afterwards and the connection keeps working.

## What the Android connection commits you to

![Explanation](../_assets/icons/explanation.svg) Fleet does not talk to Google's Android Management API directly by default. It talks to a proxy running on fleetdm.com, which talks to Google. The enterprise creation, the policy, the Pub/Sub subscription and the per-device enrollment tokens all pass through that proxy.

Three consequences follow, and each one is easier to accept before enrollment than after.

**Your Fleet server URL must be publicly reachable.** Google delivers device events by Pub/Sub push, which means Google originating a connection to your server. A URL that only resolves inside your network cannot receive them.

**That URL is then fixed.** The Pub/Sub subscription is created against one URL and Fleet has no way to move it. Changing your Fleet server URL after Android is turned on breaks Android management, and there is an open Fleet issue tracking the gap. If a hostname change is anywhere in your plans, make it before you connect Android.

**One Fleet server URL supports one Android enterprise, on the default path.** This is enforced by the proxy Fleet operates, which is what a default deployment uses; a deployment configured to talk to Google directly is not subject to the proxy's rule. It is most visible to people running non-production instances, where the same URL cannot simply be rebound after the database is reset.

There is also a half-finished state worth knowing about. The binding takes several round trips, and a network failure partway through can leave the proxy having created an enterprise that your Fleet server never received the secret key for. The symptom is a connection that looks established on Google's side and absent on Fleet's.

## Android is managed without an agent, and then with a very small one

![Explanation](../_assets/icons/explanation.svg) There is no fleetd on Android and no osquery, and the traffic is mainly Google telling Fleet what happened: `ENROLLMENT` when a device enrolls, `STATUS_REPORT` when its state changes.

**Two things stop that being the whole picture**, and both matter when something goes wrong. Fleet **polls Google hourly** to reconcile which devices still exist, so a disappearance can be noticed without anyone being told. And on Fleet Premium, a host with a pending certificate template gets a **narrow Fleet app** added to its policy, which enrols with Fleet and reports certificate results back ([3.6](../03-connect-devices/3.6-enroll-android-and-chromeos-devices.md)). So there is a small amount of Fleet-initiated traffic and a small device-side component.

Which means Android hosts sit outside most of what the rest of this book describes. No live queries, no scheduled reports, no scripts. Policies and inventory on Android come from what the Android Management API chooses to report, and the surface is Google's, not Fleet's.

The single exception is certificates, and the reason is a gap in Google's API rather than a Fleet design choice. The Android Management API has no REST call for installing a client certificate. What it does allow is delegating the `CERT_INSTALL` scope to a companion app, so Fleet ships one, and that app exists to do that one thing.

Fleet adds it to the device policy as `FORCE_INSTALLED`, so the user cannot decline it, with its permissions pre-granted, the `COMPANION_APP` role, and high-priority auto-updates. The policy also pins the app's signing certificate fingerprint, so a package that merely shares the name cannot take its place. Its package name and expected fingerprint are server settings, `mdm.android_agent.package` and `mdm.android_agent.signing_sha256`, which have working defaults, are hidden from the configuration reference, and must be set together or not at all. They exist for Fleet's own development, and there is no ordinary reason to touch them.

Android API operations are also batched, at `mdm.android_batch_size` hosts per call, defaulting to 100 with 0 meaning no limit. That one is likewise hidden, and it matters only if you are reasoning about API pressure on a large Android estate.

## Personally enrolled Android hosts report an enterprise-specific ID

![Explanation](../_assets/icons/explanation.svg) On a personally owned Android device enrolled with a work profile, the `hardware_serial` and `uuid` that Fleet reports are not hardware identifiers. They are what Google calls an enterprise-specific ID: unique to this work profile in your organization, stable across factory resets, and meaningless to anyone else.

This is deliberate on Google's part and Fleet inherits it.

**Apple's personal enrollments are not all alike here, and the console does not distinguish them.** Both show "On (manual - personal)", and only one hides the hardware: **account-driven user enrollment** gives Fleet an enrollment identifier rather than a serial or UDID, while **personal enrollment by link** supplies the real serial and UDID during the over-the-air exchange ([3.5](../03-connect-devices/3.5-enroll-ios-and-ipados-devices.md)). So the status alone does not tell you whether a given Apple host's identifiers are real.

Any process that assumes a serial number identifies a physical device, hardware asset reconciliation especially, will not work on the Android hosts above or on account-driven Apple enrollments.

Wiping behaves differently too. Fleet sends the Android Management API's wipe command rather than its delete device command, specifically because the delete command expires after thirty days. A device that is off, lost or abroad for longer than that would otherwise quietly stop being wiped. The wipe command does not expire, so the work profile is removed whenever the device next appears.

## Turning either one off

![How-to](../_assets/icons/howto.svg) The two are not comparably reversible, and the Android side deserves care.

Turning Windows MDM off is per host and then global. Run Fleet's `uninstall-fleetd-windows.ps1` script across the Windows hosts, which turns MDM off and removes fleetd with it, then switch Windows MDM off under **Settings > Integrations > MDM**.

**Turning Android MDM off deletes your Android Enterprise.** Fleet deletes the enterprise at Google, drops its own record of it, and marks every Android host unenrolled, so management stops for all of them. What happens on the devices afterwards is Google's side of the contract rather than something Fleet commands: on personally owned devices Google's behaviour is that the work profile goes too, and a fully managed company-owned device has no work profile to lose, it simply stops being managed. This is the intended behaviour, not an edge case, and it is not undone by turning Android MDM back on: that is a fresh binding.

The same thing happens if somebody deletes the Android Enterprise from the **Google Admin console**, without going near Fleet. Android MDM turns off in Fleet and the same device-side consequences follow. Whoever holds administrative access to that Google organization can end Android management for your whole estate from a console that has nothing to do with Fleet, and there is no confirmation step in Fleet to catch it.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) For Windows, the test is a real device rather than a settings page: a freshly wiped machine, a test Entra user, **Set up for an organization** at the setup screen, and then the Fleet icon in the taskbar leading to a **My device** page showing **Online**. Because enrollment depends on a sign-in, a status check that does not involve signing in tells you very little.

For Android, the settings page is genuinely the confirmation. **Settings > Integrations > MDM** shows Android MDM on once the binding is complete, and on the Google side the free Android Enterprise subscription appears in the Workspace subscriptions list.

Ownership divides along console lines and is worth naming explicitly, because both platforms put a piece of your Fleet deployment inside somebody else's administrative boundary. The Windows key pair is yours alone and belongs wherever you keep server secrets. The Entra tenant, the application registration and its Graph permissions belong to whoever administers Microsoft identity, who may not be the person running Fleet. The Android enterprise belongs to whoever administers your Google organization, with the consequences described above.

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) A few behaviours here surprise people, and all of them come from the boundary between Fleet and the platform vendor.

Intune's automatic enrollment silently wins over Fleet. It is not reported as a conflict; the devices simply never arrive.

Enrolling against an identity provider that is not federated with Entra is not supported. A third-party IdP works only through that federation.

A Windows host that has never had an interactive sign-in is not failed, it is waiting, and it will report **Off** for as long as nobody logs in.

Android software installs must be marked self-service. Apps reach the user through the Play Store inside the work profile, so there is no silent push equivalent for Android.

Android operating system updates have no built-in form in Fleet at this release, unlike macOS, iOS, iPadOS and Windows. They can still be enforced: the control is a `systemUpdate` block inside an Android configuration profile, Premium-gated independently of everything else, and [5.6](../05-manage-devices/5.6-control-operating-system-updates.md) owns it.

## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting.svg) Windows MDM diagnostics, including reading enrollment failures out of the fleetd logs, are in [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md). Android diagnostics, which are largely a matter of interpreting what Google has and has not pushed, are in [8.10](../08-troubleshooting/8.10-android-diagnostics.md).

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.1. The Microsoft licensing requirements, the Entra console layout and Google's signup flow are all vendor-owned and change on their schedules, not Fleet's.

Certificate delivery to Android hosts arrived in 4.84.0, with automatic retry of failed installations and per-host resending; 4.85.0 added ordering so that a Wi-Fi profile referencing a certificate is delivered only after the certificate itself. An instance running an earlier release will not behave as described.

The Fleet server URL restriction on Android is a known limitation with an open issue against it, so it may not hold indefinitely. Everything else in this chapter reflects deliberate design.
