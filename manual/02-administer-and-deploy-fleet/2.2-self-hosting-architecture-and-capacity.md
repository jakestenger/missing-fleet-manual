# Self-hosting architecture and capacity

Self-hosting lets you fit Fleet into your organization’s infrastructure, availability requirements, and operating practices. You can start with a small deployment and add application instances as your device population grows. MySQL capacity and the connections each instance uses deserve particular attention: they often determine how comfortably that growth proceeds.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) Use this chapter to size a self-hosted deployment, plan for failures, and confirm the service is healthy. The storage model in [1.6](../01-foundations/1.6-the-fleet-server.md) explains the reasoning behind these choices. When you are ready to deploy, follow [2.3](2.3-deploy-on-aws-or-gcp.md) for cloud infrastructure or [2.4](2.4-deploy-with-containers-or-virtual-machines.md) for containers and virtual machines. [7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md) covers the handover to ongoing operations.

All of those paths finish with [first-run setup](#complete-first-run-setup), which creates the first administrator and gives you a working sign-in. The shared instructions are included below.

The examples follow Fleet’s reference architectures and link to them for topology-specific details. You can adapt the design to your environment while keeping the requirements in this chapter in place.

With managed cloud hosting, Fleet handles these infrastructure decisions. You can continue with identity and platform configuration after choosing your operating model in [2.1](2.1-administration-model-and-deployment-choices.md).

## What a deployment requires

![Reference](../_assets/icons/reference.svg) Provision MySQL, Redis, and a TLS certificate before starting Fleet. Plan shared object storage around the features and number of instances you will use, as described below. Check the supported dependency versions for the Fleet release you are deploying when you provision or upgrade them.

Fleet requires **MySQL 8.0.44 or later within its supported version window**. It is tested against 8.0.44, 8.4.8, and 9.5.0; **9.6.0 is incompatible** with the release covered here. Check managed database upgrade policies against that window before enabling automatic upgrades. MariaDB and other drop-in replacements are unsupported.

Fleet requires **Redis 6.2 or later**. The 4.86 release line introduced a Redis-backed cache for host lookups during osquery and Orbit authentication, so older Redis versions do not meet the requirement for this agent-facing path. Fleet is actively tested against Redis 6.2 and 7, and its reference architectures use Redis 7.x at every size.

The TLS certificate must match the hostname osquery uses to connect, through its CNAME or a subject alternate name. A wildcard SAN such as `*.example.com` covers `fleet.example.com`. For a self-signed certificate, provide the full chain to the agent through its `--tls_server_certs` setting. Certificate verification happens on the agent.

When Fleet terminates TLS itself, prefer an ECDSA certificate. RSA certificates have been associated with a performance problem in Go’s standard library TLS implementation that adds load to the Fleet process. This recommendation concerns that performance cost; it does not apply when a load balancer terminates TLS.

![How-to](../_assets/icons/howto.svg) First-run setup turns a freshly migrated server into a service you can sign in to. It creates the organization and first administrator. Once that administrator exists, the server removes the setup route, so this step runs once on every deployment path.

Loading the server's URL in a browser shows the setup screen, which asks for a name, email, password and organization name, then signs you in directly. The command-line equivalent is the only `fleetctl` command that runs before you have credentials, which is why it takes those same values as flags rather than reading them from a saved context:

```
fleetctl config set --address https://fleet.example.com
fleetctl setup --email admin@example.com --name "Admin" --org-name "Example Org"
```

`config set --address` points the client's active context at the server. Leave `--password` off and `setup` prompts for it twice, interactively, so it never lands in shell history or a process listing; pass it as a flag only in a throwaway environment.

**`setup` creates the administrator and writes their API token into the context you just pointed at the server, in the same call.** `fleetctl get config` immediately afterward is enough to confirm both worked, since a missing or stale token makes that call fail.

Running `setup` again returns `Fleet has already been setup`. The server has removed the route that creates the first administrator, so the same restriction applies to both the command line and the browser setup screen.

Continue with organization, identity, and platform configuration once setup succeeds. The deployment procedures in [2.3](2.3-deploy-on-aws-or-gcp.md) and [2.4](2.4-deploy-with-containers-or-virtual-machines.md) both return to this step.

## What grows with your estate, and what does not

![Explanation](../_assets/icons/explanation.svg) Fleet publishes sized configurations for **its AWS reference architecture**, from five thousand hosts up to three hundred thousand. These are starting points to measure from, not capacity guarantees, and they describe one deployment on one cloud. Pick the row matching your enrolled host count, then revise it against your own reporting volume, API traffic and availability target.

Three of the eight published breakpoints, with the per-instance connection limit included because the next section turns on it:

| Up to | Fleet instances | Per instance | `max_open_conns` | Redis | MySQL |
|---|---|---|---|---|---|
| 5,000 hosts | 6 | 1 CPU, 4GB | 10 | 3 nodes, `cache.t4g.small` | 2 nodes, `db.t4g.medium` |
| 50,000 hosts | 15 | 1 CPU, 4GB | 20 | 3 nodes, `cache.r6g.large` | 3 nodes, `db.r6g.xlarge` |
| 300,000 hosts | 70 | 1 CPU, 4GB | 20 | 3 nodes, `cache.r6g.xlarge` | 3 nodes, `db.r6g.8xlarge` |

The pattern across these sizes is useful when planning growth: application instances multiply, Redis grows modestly, and MySQL takes on most of the additional capacity.

The AWS configurations keep each Fleet instance at one CPU and four gigabytes while increasing the count from six to seventy. GCP follows the same pattern with one CPU and one gibibyte per instance. Because Fleet instances share state through the stores described in [1.6](../01-foundations/1.6-the-fleet-server.md), you can add application capacity by adding instances.

Redis stays at three nodes and moves up two instance classes across the AWS range. Its load depends on work in progress, including the volume of results from a wide report, so host count alone is a poor sizing guide. Review the output buffer limit in [1.6](../01-foundations/1.6-the-fleet-server.md) alongside memory capacity.

**MySQL absorbs nearly all of the growth.** It is the only component moving substantially in both node count and instance size. When a deployment is slow for capacity reasons rather than configuration ones, MySQL is where to look first.

Include the database owner early in capacity planning. Application scaling is relatively straightforward, while MySQL sizing, connection limits, and failover require coordination.

## Database connections are a shared budget

![Explanation](../_assets/icons/explanation.svg) Adding Fleet instances also adds demand for database connections. Set a connection budget alongside the CPU and memory plan so autoscaling can add capacity without exhausting MySQL.

Each Fleet instance opens its own pool of connections to MySQL. **The default limit is fifty per instance.** Every one of Fleet's own sized configurations sets it to ten or twenty instead, at every scale including the largest.

Multiply the maximum instance count by the per-instance connection limit to calculate the worst-case demand. Twenty-five instances at the default limit can request 1,250 connections; at Fleet’s recommended limit of twenty, they can request 500. Actual usage may be lower, but exceeding the database’s available connections causes refusals that can look like a database fault.

Fleet's own documented rule is to divide: take the connections your database will accept, divide by the maximum number of Fleet instances you will ever run at once, and leave a margin. Include the margin deliberately, because autoscaling and rolling deployments both mean the real instance count briefly exceeds the steady-state one.

The settings are `mysql.max_open_conns`, `mysql.max_idle_conns`, which defaults to the same fifty and should not exceed the open limit, and `mysql.conn_max_lifetime`, which defaults to unlimited so Fleet reuses a connection indefinitely unless something else closes it.

**A read replica has its own pool.** `mysql_read_replica.max_open_conns` is configured separately and inherits nothing from the primary, so a deployment with replicas has a second budget to calculate rather than a shared one.

Include prepared statements in the same budget. MySQL’s `max_prepared_stmt_count` must be at least `max_open_conns` × the maximum number of Fleet servers × four. Scaling out raises both limits, and MySQL’s default prepared-statement allowance can become a constraint before the connection limit does.

## Async host processing moves check-in writes off the writer

![Explanation](../_assets/icons/explanation.svg) The connection budget above is one way to protect the single writer. Async host processing is another, and it works by taking a class of writes off the synchronous check-in path altogether. It is off by default, and it is a configuration choice rather than a licensed feature, so it is available and identical on Fleet Free and Premium.

Four kinds of per-host update normally happen inline, as part of each host's check-in: label membership, policy membership, the host's last-seen timestamp, and scheduled query statistics. Under a check-in storm, when many hosts enrol or report at once, every one of those writes lands on the MySQL writer at the same moment. Turning async processing on changes the path. Fleet buffers these updates in Redis, and a collector drains them to MySQL in batches on an interval. The writer sees fewer, larger writes in place of many small synchronous ones, and that is what relieves it under load.

The cost is Redis memory to hold the buffer, and a lag before an update reaches MySQL, normally about one collection interval plus jitter, so membership and last-seen are briefly stale. A skipped collection lock, a failed or timed-out collection, or a backlog can stretch that lag beyond a single interval.

Enable the collector with `osquery_enable_async_host_processing`, which defaults to `false`. Its nominal interval is thirty seconds, with up to ten percent jitter to spread collection across processes, and it holds the collection lock for up to a minute. Batch sizes differ by operation: inserts and deletes flush two thousand rows, updates one thousand, and the Redis side pops one thousand entries and scans one thousand keys per pass. Use those values when estimating collector load.

**Test this against a non-production deployment before you enable it**, for two reasons. Fleet publishes no figures for how much it helps or costs, so the only way to know whether it earns its place on your estate is to measure the writer and Redis before and after ([7.4](../07-operate-fleet/7.4-observe-progress-and-service-health.md), [7.5](../07-operate-fleet/7.5-maintain-capacity-and-availability.md)). And it interacts with automations that watch the same state it now updates late: with the failing-policies webhook also enabled, some transitions between passing and failing can be missed. [8.14](../08-troubleshooting/8.14-degradation.md) covers that interaction from the degradation side.

## Where Fleet sits in the network

![How-to](../_assets/icons/howto.svg) Fleet listens on all interfaces on port 8080 by default and serves TLS itself unless you tell it otherwise. In most production deployments a load balancer terminates TLS and Fleet sits behind it, which is also what lets you run the many identical instances the sizing tables assume.

Vulnerability processing and device management require outbound access. Fleet honors `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY`. Hosts listed in `NO_PROXY` connect directly, with no retry through the proxy if that direct connection fails.

Putting Fleet behind a proxy also changes what it can see about your devices. Fleet works out a device's public IP from request headers, checking `True-Client-IP` first, then `X-Real-IP`, then the first value in `X-Forwarded-For`, and falling back to the connection's remote address. **Behind an ingress proxy that sets none of those headers, that fallback is the proxy's own address**, so every host appears to share one public IP. If public IP is something you rely on, confirm your proxy sets one of the three headers rather than assuming it does.

**GitHub downloads can be redirected.** A GitHub asset download may follow a redirect that Fleet does not control, so the host that finally serves a downloaded file is not always one of the fixed names above. Treat the GitHub rows as the addresses Fleet starts from rather than a guarantee of where every byte arrives from.

**What the usage payload contains.** Each hourly send carries an anonymous identifier and the Fleet version, the licence tier, and the organization (the licensed organization name on Premium, and the literal value `unknown` on Free); scale counts (enrolled hosts, users, teams, policies, queries, and software and CVE totals); feature flags (including whether AI features and telemetry are enabled); per-version host breakdowns by operating system and agent version; and the server's stored errors, serialized, which include an `error_message` and `error_additional_info` whose contents depend on what failed. It does not carry hostnames, host identifiers, IP addresses, or query results. Why a Premium deployment cannot simply switch this off is [a.3](../09-appendices/a.3-configuration-model-and-precedence.md)'s subject.

**A few senders are not the Fleet server.** The ChromeOS agent contacts `ipapi.co` when a live query reads its geolocation table, and that request tells `ipapi.co` the device's public IP; the agent's own update server is covered with the agent ([3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md)); and `fleet-mcp` is a separate binary rather than part of the server. They sit here so the boundary of the map is clear: it covers the Fleet server and the destinations you configure on it, not every component in the wider Fleet system.

## Shared object storage is required before you scale software distribution

![Explanation](../_assets/icons/explanation.svg) Shared object storage lets every Fleet instance serve the same software artifacts. Fleet can start without a bucket, which is convenient for an initial deployment, but review the fallback stores before adding instances or distributing software.

What breaks at the second instance depends on where each artifact falls back to, and the two destinations behave very differently.

| Artifact | Without object storage | What that means with several instances |
|---|---|---|
| File carves | MySQL | Stays shared and keeps working. Grows the database |
| Apple bootstrap packages | MySQL | Stays shared and keeps working. Grows the database |
| Software installers | Local filesystem | Breaks. Not shared, and the default location is a temporary directory |
| Software title icons | Local filesystem | Breaks. Same reason |

The database-backed fallbacks survive horizontal scaling because every instance reaches the same database. The filesystem-backed ones do not: an installer uploaded through one instance is invisible to every other instance, and to whichever instance the load balancer hands the download to. Fleet logs that it is using a local store and that this is not suitable for production, once for installers and once for icons.

Configure object storage before adding a second instance if you distribute software installers or software title icons: their local filesystem fallbacks are not shared. Apple bootstrap packages remain shared in MySQL and contribute to database growth. If you use neither installers nor icons, the decision is primarily about that database growth. The published configurations use at least six instances, so deployments following them will generally need shared object storage. [2.4](2.4-deploy-with-containers-or-virtual-machines.md) also covers small production deployments on a single instance.

## Availability, and the constraint that shapes it

![Explanation](../_assets/icons/explanation.svg) Fleet supports exactly one writable database. Read replicas are supported and help some access patterns, particularly API and command-line traffic. Multi-writer and group replication setups are not supported.

Keep Fleet instances and the writable database in the same datacenter. Cross-region replication can support failover, but writes must remain local to the active deployment. Plan a single-region service with a regional failover procedure; an active-active design across regions is unsupported.

The rest is conventional. Put a load balancer in front of the Fleet instances, which also lets it terminate TLS and hand the Fleet process back that compute. Run Redis with the three nodes the reference configurations specify. Use a database service that supports automated backups and managed failover, and turn both on.

Agents help devices continue working during a short service interruption. osquery keeps its existing configuration and buffers results locally until Fleet returns, subject to its buffer limit. That behavior supports planned maintenance windows while preserving buffered results.

## Upgrades take the service down on purpose

![How-to](../_assets/icons/howto.svg) Database migrations are meant to run with the server offline. The sequence is to stop Fleet, run `fleet prepare db`, then start the new version.

Fleet's own guidance puts the window at seconds to minutes, even on large installations. Back the database up first, every time. Agents buffer through it, so the cost is a gap in freshness rather than a hole in your history.

Leaving old instances serving traffic against a partly migrated schema is not a supported configuration. Fleet's instruction is that all instances are shut down for the migration, so a rolling upgrade is not a supported alternative to the outage.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) Fleet exposes a health check at `/healthz`, and it is the right target for a load balancer. It returns 200 when the server is running and its connections to MySQL and Redis are healthy, and 500 when they are not. Individual dependencies can be checked with `/healthz?check=mysql` or `/healthz?check=redis`, which is how you tell the two apart quickly during an incident.

The health check covers MySQL and Redis. Check software delivery separately, because object storage failures can occur while `/healthz` returns 200. When a health check fails, the server logs contain the reason; the response body contains no diagnostic detail.

Enable metrics explicitly before configuring your monitoring system. Fleet serves Prometheus-compatible metrics at `/metrics` once you set a basic auth username and password or explicitly disable the authentication requirement. Until then, Fleet logs that the endpoint is disabled at startup. If a scrape receives no metrics, check that startup message first.

Worth alerting on, from Fleet's own recommendations: host enrollment departing from its expected level, latency rising on HTTP endpoints, and error rates rising on them. Enrollment count is the one that catches problems the other two miss, because a deployment can be healthy by every infrastructure measure while hosts quietly stop checking in.

Ownership here divides along existing team lines, with one exception that falls between them.

| What | Owner | What they verify |
|---|---|---|
| The database, its version pinning, backups and failover | Whoever runs databases | That the version is inside Fleet's tested set, and that a restore has been performed |
| The TLS certificate and its renewal | Whoever runs TLS | That the name still matches what agents connect to |
| Connection limit arithmetic | Assign this deliberately | Instances multiplied by the per-instance limit, against what the database accepts |

Assign an owner to the connection budget as well as the individual services. Changes to either the database limit or the maximum Fleet instance count affect that shared calculation.

## Shared database capacity and credential handling

![Reference](../_assets/icons/reference.svg) When adapting the reference architecture, account for shared database load and choose a credential delivery method that keeps secrets out of process listings and diagnostic archives.

Running several Fleet deployments against one database server needs the server resourced for all of them together. Fleet's guidance is explicit that this requires more provisioning and offers no formula for it.

Pass credentials to Fleet through environment variables or a configuration file rather than command line arguments. Anything on the command line is visible to process listing, and it is also captured in the debug archive that Fleet asks for when you report a performance problem, which means it has to be scrubbed by hand before the archive leaves your organization.

A single virtual private server can carry hundreds and possibly thousands of hosts. The sized configurations start at five thousand for a reason, and reaching for the smallest of them at a few hundred hosts buys availability rather than capacity.

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.0. The MySQL version window is the most perishable fact in this chapter: 8.0.44 as the floor, 8.0.44, 8.4.8 and 9.5.0 tested, 9.6.0 incompatible. Confirm it against the release you are deploying rather than trusting this list, because it moves independently of everything else here.

The sized configurations are Fleet's published reference architectures and describe one opinionated deployment on one cloud. Treat the pattern across them as durable and the specific instance classes as a starting point to measure from.

The connection limit default of fifty has been stable for a long time, but it is a default rather than a recommendation, and the gap between it and Fleet's own sized configurations is deliberate rather than an inconsistency to resolve.
