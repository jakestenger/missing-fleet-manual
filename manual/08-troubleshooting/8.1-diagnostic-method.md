# The diagnostic method

The rest of this chapter tells you how to read one particular surface. This section tells you which one to open.

Almost every Fleet problem reduces to one sentence: **an intent was expressed in one place and did not manifest in another.** A profile assigned but absent from the Mac. Software targeted but not installed. A report scheduled with no results arriving. A policy that passes on the laptop and reads failing in the console.

> **A note on "report" and "query".** Fleet 4.90.1 calls the thing you save and run a **report**, and an ad-hoc run a **live report**. It renamed these from "query" and "live query" in 4.82.0, in the UI, API, CLI, and GitOps.
>
> osquery did not rename anything, and neither did Fleet's storage. So this chapter says **report** when it means the Fleet object you created, and **query** when it means osquery's own mechanism: the distributed query channel, a scheduled query in `osquery_schedule`, the watchdog denylisting one, the `queries` table in MySQL, or a `livequery:` key in Redis. Both words are correct; they name different layers, and Part VIII spends its time at all of them.

A second, smaller family has no failed delivery at all. Everything arrives, and the system is slow, expensive, or fighting something else on the host. Those need a different procedure. §8.1.3 is the fork.

## 8.1.1 The order of operations

| Step | Do | Section |
|---|---|---|
| 1 | Establish the facts. Do not theorise yet | §8.1.2 |
| 2 | Decide: delivery failure, or degradation? | §8.1.3 |
| 3 | Identify which of the five channels carries the failing feature | §8.1.4 |
| 4 | Classify the failure into one of seven classes | §8.1.5 |
| 5 | Bisect. Do not walk the pipeline | §8.1.6 |
| 6 | Force the stage you suspect, and verify it actually ran | §8.1.7 |
| 7 | Read logs | §8.1.8 |

Logs are step seven. Opening them first is how afternoons disappear.

## 8.1.2 Establish the facts before you form a theory

Fleet runs different code paths depending on facts you cannot infer from the symptom. Enrollment type changes which items get enqueued at setup. Agent version changes whether a Windows host can be woken at all. A proxy changes whether the host can reach Apple. Skip this and you are debugging a system other than the one in front of you.

Fleet's own MDM engineers ask thirteen context questions before mentioning a log (`docs/Contributing/product-groups/mdm/mdm-bug-checklist.md`).

| Axis | What to pin down |
|---|---|
| **Blast radius** | One host, one class of hosts (a fleet, a platform, a region, an OS build), or everything? Does it survive a reboot? |
| **Platform** | OS **and build number**. `macOS 26.2`, `Windows 11 Pro 25H2 (10.0.26200.7462)`, `Android 16` |
| **Hardware** | Model identifier. Recent Apple silicon and recent Windows builds have their own failure modes |
| **Agent** | fleetd version. Fleet Desktop enabled? Any customisation to the installer package? |
| **Enrollment type** | ⭐ macOS: ADE/ABM, manual profile, or account-driven. Windows: agent-driven, Autopilot, or Settings-app. Android: work profile, QR, or account. **Different code paths.** |
| **History** | Previously managed by another MDM? How was it migrated? Is the old agent still installed? Was it told to stop managing? |
| **Interference** | Application allow or deny listing? Conflicting configuration profiles? Other management software? |
| **Network** | Proxy, VPN, or TLS inspection? Are Fleet's server **and update** URLs allowlisted? Are **Apple's** services (APNs, ABM) allowlisted? |
| **Fleet-side** | Are detail queries disabled for this fleet? Is IdP authentication enabled? Was fleetd installed before MDM enrollment? |
| **External credentials** | APNs certificate valid? ABM and VPP tokens current? Any renewed recently? |
| **What changed** | Fleet version, agent version, OS update, a GitOps commit, a certificate or token expiry, near the onset |

Host identifiers (serial numbers, UUIDs) are needed but belong on a private channel, never in a public issue tracker. Full intake lists, including one for self-hosted infrastructure, are in [8.13](8.13-escalation.md).

**Pin down both endpoints precisely.** For *intended*, prefer the GitOps YAML or the API response over the console, because the console shows what someone set rather than what the host received. For *observed*, check on the host. Checking in Fleet conflates a real failure with a stale read, and that distinction is class 6 below.

## 8.1.3 The fork: delivery failure or degradation?

Did something fail to arrive, or did everything arrive too slowly?

| | Delivery failure | Degradation |
|---|---|---|
| Symptom | "X didn't happen" | "X is slow, heavy, or erratic" |
| Method | §8.1.4 to §8.1.8 | [8.14](8.14-degradation.md) |
| Tools | Queue tables, command results, host state | `fleetctl debug profile`, `heap`, `goroutine`, `trace` |

A degradation problem investigated as a delivery problem sends you hunting a queue that is working fine. If nothing is stuck and everything eventually arrives, stop here and go to [8.14](8.14-degradation.md).

## 8.1.4 Identify the channel first

A host talks to Fleet over five independent channels. They fail separately.

| # | Channel | Carries | Cadence |
|---|---|---|---|
| 1 | osquery **distributed** | live reports, detail and vitals queries | `distributed_interval`, commonly 10s to 30s |
| 2 | osquery **config TLS** | scheduled query config, agent options | ~10s |
| 3 | osquery **logger TLS** | query results outbound | `logger_tls_period` |
| 4 | **Orbit API** | software installs, scripts, setup experience, disk-encryption keys, MDM migration | 30s config receivers |
| 5 | **MDM protocol** | profiles, MDM commands, VPP installs, lock and wipe | APNs push (Apple), SyncML poll or fleetd wake (Windows), AMAPI (Android) |

**"Is the host online?" is not a well-formed question.** A host can answer live queries while its MDM channel is dead, or report vitals while Orbit is wedged. The most misleading single field in Fleet is a healthy MDM status on a host whose agent is gone.

Channel 4 can break channel 5. A Windows host on the relaxed 480 minute MDM poll is woken through Orbit, so a broken Orbit channel delays MDM commands by up to eight hours with nothing wrong in the MDM subsystem. See [8.9](8.9-windows-mdm-diagnostics.md).

### The channel isolation sweep

Two minutes, before any feature-specific work. Whatever fails localises the problem to a subsystem before you read a log.

| Test | Proves | If it fails |
|---|---|---|
| Run a live report against the host | 1, distributed | osquery is not reaching Fleet |
| Check when host vitals last updated | 1 and 2, detail queries | Agent quiet, or you are reading stale data |
| `fleetctl run-script` with something trivial | 4, Orbit | Orbit wedged or not running |
| Load the **My Device** page from the host | Desktop and My Device | Desktop broken, Orbit may be fine |
| `fleetctl mdm run-command` with a benign command | 5, MDM | MDM channel dead independent of osquery |

For reachability and TLS specifically:

```sh
fleetctl debug connection --fleet-certificate <ca-cert.pem> <enroll-url>
```

This validates connectivity and the certificate chain. It covers the HTTPS and enrollment path only. It will not tell you that Orbit is running but stuck.

### The half-enrolled state

Worth recognising by name because it presents as a healthy host. On ADE enrollment Fleet installs the agent with the MDM `InstallEnterpriseApplication` command, and that command sometimes fails while enrollment succeeds. The result is a host **MDM-enrolled with no agent**: MDM status reads `On (company-owned)`, nothing checks in, and MDM commands accumulate unacknowledged.

Reported at roughly 2 to 3 percent of ADE enrollments (20 to 30 per 1,000) in `fleetdm/fleet#47793`, open as of 4.89.2. Detection and recovery are in [8.4](8.4-host-side-investigation.md).

## 8.1.5 Classify the failure

Almost everything Fleet does is asynchronous, through a queue. A delivery failure sits in exactly one of seven classes, and **you can determine the class before you know anything about the feature**, because the tells are structural.

| # | Class | Meaning | Generic tell | Go to |
|---|---|---|---|---|
| 0 | **Not intended** | The config does not say what you think | Desired state absent at the source | Read the config, not logs |
| 1 | **Not targeted** | Intent exists, does not resolve to this host | Host not in the resolved fleet or label set | [8.6.13](8.6-server-state.md#8613-scoping-which-fleet-which-labels-was-this-host-targeted) |
| 2 | **Not queued** | Targeted, but no work item created | No row for this host and item | The cron that creates it, §8.1.7 |
| 3 | **Queued, not delivered** | Row exists, device never took it | Row present, `activated_at` or sent timestamp NULL | The channel, §8.1.4 |
| 4 | **Delivered, not executed** | Device got it, did not act or did not report | Command sent, no result row | [8.4](8.4-host-side-investigation.md) |
| 5 | **Executed, failed** | It ran and errored | Result row with error or non-zero status | [8.4](8.4-host-side-investigation.md) |
| 6 | **Succeeded, not reflected** | It worked, Fleet's view is stale | Host reality differs from Fleet UI | Nothing is broken. Refetch. |

**Class 6 is the most common misdiagnosis.** Profiles listed as Enforcing on the host while Fleet shows something else, or vitals lagging a change, send people hunting a delivery pipeline that worked fine. Check the host before you check the queue.

The nastier inverse is **executed, reported success, did not work**. A Linux package manager that exits zero on a no-op is recorded as a successful install. If Fleet says success and the host disagrees, suspect the exit code rather than the pipeline.

### Where the queues live

| Queue | Table |
|---|---|
| Scripts, software installs and uninstalls, VPP and in-house app installs | `upcoming_activities`. `activated_at IS NULL` means queued but not started |
| Apple MDM commands | `nano_commands` holds the command once; `nano_enrollment_queue` ties it to each recipient; results land in `nano_command_results`. Enrollment in `nano_enrollments`, `nano_devices` |
| Windows MDM commands | `windows_mdm_command_queue` then `windows_mdm_command_results`. `windows_mdm_responses` holds only the gzipped session envelope |
| Per-host profile desired vs actual | `host_mdm_apple_profiles`, `host_mdm_windows_profiles`, `host_mdm_apple_declarations`, `host_mdm_android_profiles` |
| Setup experience | `setup_experience_status_results` |
| Async worker jobs | `jobs` |

Reading these directly is normal practice, not an escalation. Full schema in [8.6](8.6-server-state.md).

**Depth matters more than presence.** One queued item tells you little. A queue that is growing tells you the drain is broken. A queue that is shrinking tells you to wait. A host showing ten pending activities and twenty-four an hour later is the diagnosis, not a detail.

## 8.1.6 Bisect, do not walk

Walking a pipeline stage by stage costs one observation per stage. Halving it costs far fewer. Choose a cut where **one observation has two opposite-pointing interpretations.**

| Cut | Left means | Right means |
|---|---|---|
| Is there a queue row for this host and item? | Server-side, classes 0 to 2 | Delivery or execution, classes 3 to 5 |
| Does the host's own state match Fleet's view? | Genuine failure, 3 to 5 | Staleness, class 6 |
| Does it fail on one platform but not another? | Platform, agent, or protocol path | Server-side config or targeting |
| One host, or every host in the fleet? | Host-specific | Targeting or server-side |
| Did the responsible cron run recently and cleanly? | The scheduler | The work the job does |
| **Is the record's own timestamp old, or only its arrival time?** | Produced long ago, arriving late. Look left | Nothing new is being produced. Look right |

### The two-clocks check

The last cut resolves an entire family of stale-data reports in one observation. When something arrives carrying an old timestamp, ask which timestamp is old: the one inside the record, or the one stamped on arrival.

**Record old, arrival recent.** The data was produced long ago and is only now arriving. Look left, at the host. Fleet does not buffer query results, it forwards them as osquery sends them, so the buffering happened on the device: osquery stored results locally while it could not reach Fleet and is now draining that store, replaying with original timestamps. Confirm by checking whether the affected hosts share a recent return to connectivity.

**Both old.** Nothing new is being produced or forwarded. Look right, at the destination. It may be re-reading an existing bucket or stream rather than receiving anything new.

This check needs **individual record timestamps**. An aggregated latency metric cannot answer it. If your pipeline exposes only an average, instrument it to sample raw records before you need this.

## 8.1.7 Force the stage, then verify it ran

Many Fleet stages can be forced rather than waited on. Force the stage you believe is stuck and see whether it advances. If it advances, the stage was fine and its trigger was not. If it does not, you have localised to the stage.

```sh
fleetctl trigger --name=<schedule>
```

Fleet runs roughly thirty named schedules. Common targets: `mdm_apple_profile_manager`, `mdm_windows_profile_manager`, `apple_mdm_dep_profile_assigner`, `apple_mdm_apns_pusher`, `maintained_apps`, `vulnerabilities`, `automations`, `integrations`, `refresh_vpp_app_versions`, `upcoming_activities_maintenance`, `host_vitals_label_membership`.

> ### ⚠️ `fleetctl trigger` reports success for runs that never happen
>
> `Trigger()` returns without triggering in three cases: a scheduled run is already pending, a previous trigger is still pending or queued, or the internal trigger channel is busy (logged at debug level only).
>
> The first two return stats and surface as `[!] Conflict`. The third does not. `CronSchedules.TriggerCronSchedule` discards the `didTrigger` return value the scheduler discards it, so the channel-busy path returns a nil error and `fleetctl` prints `[+] Sent request to trigger <name> schedule` for a run that did not occur.
>
> **Never interpret a trigger without checking whether the run happened.**
>
> ```sql SELECT name, instance, stats_type, status, created_at, updated_at, errors FROM   cron_stats WHERE  name = '<schedule>' ORDER  BY created_at DESC LIMIT  5; ```
>
> `status` moves `queued` to `pending` to `completed`, with `expired` and `canceled` as terminal alternatives. `errors` is JSON. `instance` identifies which server node ran it, which matters on multi-node deployments where one node can fail while the others are healthy. There is no API for this; it needs database access.
>
> Checking that all thirty schedules are current, not only the one you suspect, is the fastest way to tell one broken job from a wedged scheduler. See [8.6](8.6-server-state.md).

Other forceable stages, and whether they are safe on a production host, are in [8.11](8.11-reproducing-and-isolating.md).

## 8.1.8 Read logs last

By now you know the channel, the class, and the stage, so you know which log to open and what you are looking for.

| Want | Go to |
|---|---|
| The full map of every log surface and its path | [8.2](8.2-log-surfaces.md) |
| Fleet server operational logs and error strings | [8.3](8.3-server-logs.md) |
| Host-side agent logs and on-disk state | [8.4](8.4-host-side-investigation.md) |
| `fleetctl debug` and the debug archive | [8.5](8.5-fleetctl-debug.md) |
| Who changed what, and when | [8.12](8.12-audit-logs.md) |

Two traps worth knowing before you start. `fleetctl debug errors` reads Fleet's recorded errors out of Redis rather than a file, and records **server faults only**: client 4xx errors are never stored, so chasing one there returns nothing. And per-request log lines are emitted at debug level unless the error is a non-client error, so some failures produce no line at all at default verbosity. Raise verbosity before reproducing, not after. Both are covered in [8.3](8.3-server-logs.md).

## 8.1.9 When to stop

Stop when you can name the class and the stage, or when you have proven you cannot observe the stage you need. Then collect and escalate.

At minimum: the §8.1.2 intake, the channel sweep result, the relevant queue rows, `fleetctl debug archive`, and host-side agent logs for the window. Full list in [8.13](8.13-escalation.md).

**Say what you ruled out, not only what you saw.** "Live reports respond, MDM command unacknowledged, an active `nano_enrollment_queue` row for this host with no matching result, `cron_stats` clean" is a diagnosis. "It's not working" is a ticket.
