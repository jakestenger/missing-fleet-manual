# The diagnostic method

The rest of Part VIII tells you how to read one particular surface each. This chapter tells you which one to open.

Almost every Fleet problem reduces to one sentence: **an intent was expressed in one place and did not manifest in another.** A profile assigned but absent from the Mac. Software targeted but not installed. A report scheduled with no results arriving. A policy that passes on the laptop and reads failing in the console.

> **A note on "report" and "query".** Fleet 4.90.0 calls the thing you save and run a **report**, and an ad-hoc run a **live report**. It renamed these from "query" and "live query" in 4.82.0, in the UI, API, CLI, and GitOps.
>
> osquery did not rename anything, and neither did Fleet's storage. So this chapter says **report** when it means the Fleet object you created, and **query** when it means osquery's own mechanism: the distributed query channel, a scheduled query in `osquery_schedule`, the watchdog denylisting one, the `queries` table in MySQL, or a `livequery:` key in Redis. Both words are correct; they name different layers, and Part VIII spends its time at all of them.

A second, smaller family has no failed delivery at all. Everything arrives, and the system is slow, expensive, or fighting something else on the host. Those need a different procedure. §8.1.3 is the fork.

A third surface is not a host at all. When an AI assistant reaches Fleet through the MCP server ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)), its failures run along an operator-side path that none of the host channels below describe. If the symptom is that the assistant stopped answering, or answers with the wrong hosts, take the assistant-surface fork before §8.1.4 rather than working the channel method.

## 8.1.1 The order of operations

| Step | Do | Section |
|---|---|---|
| 1 | Establish the facts. Do not theorise yet | §8.1.2 |
| 2 | Decide: delivery failure, or degradation? | §8.1.3 |

| 4 | Classify the failure into one of seven classes | §8.1.5 |

| 6 | Force the stage you suspect, and verify it actually ran | §8.1.7 |

Logs are step seven. Opening them first is how afternoons disappear.

## 8.1.2 Establish the facts before you form a theory

Fleet runs different code paths depending on facts you cannot infer from the symptom. Enrollment type changes which items get enqueued at setup. Agent version changes whether a Windows host can be woken at all. A proxy changes whether the host can reach Apple. Skip this and you are debugging a system other than the one in front of you.

Fleet's own MDM engineers ask thirteen context questions before mentioning a log, in a public checklist they keep in Fleet's contributor documentation under `docs/Contributing/product-groups/mdm/`. What follows regroups those onto the axes you actually pin down, and adds the one they leave out, which is what changed.

| Axis | What to pin down |
|---|---|
| **Blast radius** | One host, one class of hosts (a fleet, a platform, a region, an OS build), or everything? Does it survive a reboot? |
| **Platform** | OS **and build number**. `macOS 26.2`, `Windows 11 Pro 25H2 (10.0.26200.7462)`, `Android 16` |
| **Hardware** | Model identifier. Recent Apple silicon and recent Windows builds have their own failure modes |
| **Agent** | fleetd version. Fleet Desktop enabled? Any customisation to the installer package? |
| **Enrollment type** | ⭐ macOS: ADE/ABM, or a manual profile as company-owned or personal. iOS/iPadOS: ADE/ABM, an enrollment URL either way, or account-driven, which is **iOS and iPadOS only**. Windows: agent-driven, Autopilot, or Settings-app. Android: work profile, QR, or account, the last **unestablished**, appearing only in Fleet's triage notes rather than as a described path ([3.6](../03-connect-devices/3.6-enroll-android-devices.md)). **Different code paths.** |
| **History** | Previously managed by another MDM? How was it migrated? Is the old agent still installed? Was it told to stop managing? |
| **Interference** | Application allow or deny listing? Conflicting configuration profiles? Other management software? |
| **Network** | Proxy, VPN, or TLS inspection? Are Fleet's server **and update** URLs allowlisted? Are **Apple's** services (APNs, ABM) allowlisted? |
| **Fleet-side** | Are detail queries disabled for this fleet? Is IdP authentication enabled? Was fleetd installed before MDM enrollment? |
| **External credentials** | APNs certificate valid? ABM and VPP tokens current? Any renewed recently? |
| **What changed** | Fleet version, agent version, OS update, a GitOps commit, a certificate or token expiry, near the onset |

Host identifiers (serial numbers, UUIDs) are needed but belong on a private channel, never in a public issue tracker. Full intake lists, including one for self-hosted infrastructure, are in [8.13](8.13-escalation.md).

**There are three states here, not two, and collapsing them is how classes 0 and 1 get skipped.** What was *declared*, in GitOps YAML or whatever you configure from. What Fleet *resolved and stored*, which you read from the API. And what the host *has*, which you read on the host. YAML proves someone wrote it down, not that Fleet accepted it; the API proves Fleet accepted it, not that the host received it. Compare all three, in that order, and the first gap you find is the class.

For the third, check on the host rather than in Fleet. Checking in Fleet conflates a real failure with a stale read, and that distinction is class 6 below.

## 8.1.3 The fork: delivery failure or degradation?

Did something fail to arrive, or did everything arrive too slowly?

| | Delivery failure | Degradation |
|---|---|---|
| Symptom | "X didn't happen" | "X is slow, heavy, or erratic" |
| Method | §8.1.4 to §8.1.8 | [8.14](8.14-degradation.md) |
| Tools | Queue tables, command results, host state | `fleetctl debug profile`, `heap`, `goroutine`, `trace` |

A degradation problem investigated as a delivery problem sends you hunting a queue that is working fine. If nothing is stuck and everything eventually arrives, stop here and go to [8.14](8.14-degradation.md).

### The assistant surface, not a host

The channels in §8.1.4 are how a managed *host* talks to Fleet. The MCP server that connects an AI assistant to Fleet ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)) is none of them: it is a separate proxy process an operator runs, and its failures live on a path the host method never visits. Take this fork when the symptom is that the assistant stopped answering, or is answering with the wrong hosts.

Fault-find it in the order the request travels, from the client inward, and stop at the first stage that fails:

| Stage | A failure here looks like | Read |
|---|---|---|
| **Client to server** | The assistant lists no Fleet tools at all. The client config, the absolute binary path, or on Apple Silicon the binary signature | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Transport** | Over SSE, the client cannot reach the server or a `/healthz` probe fails. Under stdio, the client cannot launch the process | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Bearer and TLS**, SSE only | Every SSE request is refused with 401, or the client rejects the server certificate. Under stdio there is no bearer to test | [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **MCP process** | Tools are present but every call errors, and the server's own log shows it never started cleanly or is mid-restart | [8.3](8.3-server-logs.md), the MCP subsection |
| **Fleet token** | The server refuses to start, its log naming the reachability or API-only check on `FLEET_API_KEY` that it failed | [8.3](8.3-server-logs.md), [6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) |
| **Fleet API** | Tools work but a read returns something surprising. A direct-proxy tool derives its answer from one Fleet route without fanning out, projected into the tool's own documented shape; a composed tool may have dropped or capped a component | [6.3](../06-automate-fleet/6.3-use-the-fleet-rest-api.md), [a.11](../09-appendices/a.11-mcp-tool-reference.md) |

The last stage is the common one. When a direct-proxy read tool returns fewer hosts or different data than expected, the server derived that answer from a single Fleet route without fanning out. Even so it does not hand back Fleet's raw response: it selects a documented subset of fields, and some of these tools disambiguate or re-bucket before they answer, so reproduce the underlying REST call ([6.3](../06-automate-fleet/6.3-use-the-fleet-rest-api.md)) and compare it against the tool's documented projection and targeting rules ([a.11](../09-appendices/a.11-mcp-tool-reference.md)) before suspecting the server. A composed tool is different: it builds its answer from several Fleet calls, intersecting filters or fanning out across fleets, and drops any component that failed or hit a cap into the server's own log, so replay every component route from [a.11](../09-appendices/a.11-mcp-tool-reference.md) and read those warnings before concluding Fleet was wrong. A live query that reaches fewer hosts than expected is [8.7](8.7-live-query-introspection.md)'s territory whether or not the assistant asked for it. Nothing else in this chapter's method applies to this surface.

## 8.1.4 Identify the channel first

A fully enrolled Mac or Windows computer talks to Fleet over five management channels, and they are separately diagnosable: each leaves its own evidence, and one can be broken while the others are healthy. That independence has a limit worth holding onto here. Three of the five are endpoints of one osquery process sharing a single node key, so a network fault can isolate one of them, but a wedged or dead process takes all three together ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). **Five is the count for that host and not for every host**: Linux has four, an MDM-only or agent-only host has fewer again, and iOS, iPadOS, Android and ChromeOS have one apiece. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) carries the per-platform matrix, and "which channel" below always means the channels this platform actually has.

A **device-authenticated API** sits outside this count deliberately. It is reached at `device/...` with a per-host token rather than a node key, Fleet Desktop is its main consumer, and Orbit maintains that token whether or not Desktop is installed ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). Nothing in this chapter's method depends on it.

| # | Channel | Carries | Cadence |
|---|---|---|---|
| 1 | osquery **distributed** | live reports, detail and vitals queries | `distributed_interval`, 10s on a new install |
| 2 | osquery **config TLS** | scheduled report config and the `agent_options.config` block; Orbit's own settings travel on channel 4 | 60s. fleetd starts osquery with `--config_refresh=60` |
| 3 | osquery **logger TLS** | query results outbound | `logger_tls_period`, 10s on a new install |
| 4 | **Orbit API** | software installs, scripts, setup experience, disk-encryption keys, MDM migration | 30s, stretching toward 5 minutes while the fetch keeps failing |
| 5 | **MDM protocol** | profiles, MDM commands, VPP installs, and most lock and wipe operations, though **Windows lock and both Linux operations are scripts** and belong to channel 4 ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)) | APNs push (Apple), SyncML poll or fleetd wake (Windows), AMAPI (Android) |

Channel 2 is the slowest of the three osquery channels and the one people misjudge. An agent options change is not late at forty seconds; it has not been fetched yet. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) sets out where each cadence comes from and which of them you can change.

Channel 4 does not hold a steady 30 seconds when it is unhealthy. Each failed config fetch backs the interval off exponentially to a ceiling of five minutes, and it returns to 30 seconds on the first success. So a host you are watching recover can sit silent for five minutes with nothing further wrong, and a host you have just fixed takes up to five minutes to show it. fleetd logs `running config receivers, backing off` with the next retry interval each time it extends, which is the cheapest way to tell a backed-off channel from a dead one.

**"Is the host online?" is not a well-formed question.** A host can answer live queries while its MDM channel is dead, or report vitals while Orbit is wedged. Once a host has recorded an osquery check-in, Fleet stamps the host's last-seen time in the shared authentication step every osquery request passes through, so **any** of channels 1, 2 and 3 keeps a host online: a device that has stopped answering distributed reads but is still shipping logs still reads as online. What online never speaks for is channel 4 or channel 5. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) gives the window it uses. A host MDM-enrolled with no agent is the case that catches people, and it is covered below.

Channel 4 can break channel 5. A Windows host on the relaxed 480 minute MDM poll is woken through Orbit, so a broken Orbit channel delays MDM commands by up to eight hours with nothing wrong in the MDM subsystem. See [8.9](8.9-windows-mdm-diagnostics.md).

### The quick evidence sweep

Run this before any feature-specific work. It is a **sweep, not an isolation**: the tests share prerequisites, and the table below says what each one actually establishes rather than which channel it cleanly proves. Read the "proves" column strictly, because most of the wrong turns in Apple and Windows MDM start with a test that was believed to prove more than it did.

| Test | A pass proves | What it does not prove, and its prerequisites |
|---|---|---|
| Run a live report against the host | The whole distributed round trip worked: server, MySQL, Redis, the websocket or CLI path, and the host answering on channel 1 | A failure implicates any one of those, not "osquery is not reaching Fleet". Narrow it with the control test in [8.14](8.14-degradation.md#8142-establish-a-control-first) |
| Check when host vitals last updated | The host returned detail-query results **and Fleet ingested them**. They come back on **channel 1**, not channel 2 | Staleness can mean a quiet agent, detail queries disabled for the fleet, a cached view, or results that arrived and failed to ingest. Fleet logs an ingestion error and carries on, so that last one leaves the host looking quiet while it is talking normally |
| `fleetctl run-script` with something trivial | Channel 4 accepted and ran the script | **The command refuses unless Fleet already considers the host online**, so it cannot test Orbit on a host whose osquery is silent. macOS, Windows and Linux only, and scripts must be enabled |
| Load the **My Device** page from the host | The device-authenticated web path works, so Fleet Desktop's token is valid | Nothing about whether the Desktop process is running. It proves the path, not the process |
| `fleetctl mdm run-command` with a benign command | Channel 5 accepted the command for delivery | Acceptance is not delivery: an Apple command sits queued until the device connects back. **macOS and Windows only**, needs a raw payload file, and Android has no equivalent |

There is no cheap test that isolates channel 2 on its own, and the tempting one does not work: **do not compare `osquery_info.config_hash` between hosts**, because Fleet builds the served configuration per host, including label-scoped content, so two correct hosts on one fleet can hold different hashes ([8.7.1](8.7-live-query-introspection.md#871-the-query-library)). What channel 2 will tell you is whether *this* host picked up a change: alter something in agent options, then watch that host's own `osquery_flags` and `osquery_info.config_hash` move. `config_valid = 0` is the other channel 2 signal worth having, since it means the host fetched a config and rejected it ([8.4.6](8.4-host-side-investigation.md#846-osquery-introspection-tables)).

How long the sweep takes depends on the deployment: a script can wait on the host's Orbit poll and its own execution, and an MDM acknowledgement depends on the platform and on whether the device is awake. Start it early rather than budgeting a fixed number of minutes for it.

For reachability and TLS specifically:

```sh
fleetctl debug connection --fleet-certificate "<ca-cert.pem>" "<fleet-server-address>"
```

The argument is the Fleet server address, in the form `fleet.example.com` or `fleet.example.com:8080`, and the scheme is added for you if you leave it off. It is not an enrollment profile URL, and passing one gets you a check against whatever host that URL happens to name.

Four checks run in order, and the command stops at the first failure, so the last line you see is the stage to work on: the hostname resolves, a TCP connection opens, the TLS certificate validates against the supplied root, and an enrollment request with a deliberately invalid secret gets the response Fleet should give. That last one is what distinguishes a reachable server from a reachable load balancer.

The certificate flag only applies when an address is given. Without one the command reads the address and root CA from your `fleetctl` context instead, and with no root CA in either place it falls back to the same embedded certificate bundle that fleetd packages ship with, which it tells you it is doing.

None of this observes the agent. A host that passes every check can still have an Orbit that is running and stuck.

### The half-enrolled state

Worth recognising by name because it presents as a healthy host. **On macOS MDM enrollments, manual as well as ADE**, Fleet installs the agent with the MDM `InstallEnterpriseApplication` command, and that command sometimes fails while enrollment succeeds. The one exception is an ADE enrollment where `setup_experience.macos_manual_agent_install` is set, which suppresses the command deliberately and needs a bootstrap package to deliver the agent instead ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)); on such a fleet a missing agent may be the configured behaviour rather than a failure.

The result is a host **MDM-enrolled with no agent**: the console shows MDM status `On (company-owned)` or `On (manual)` depending on the path, and nothing that depends on the agent ever happens. No osquery check-ins, no vitals, no scripts, no agent-delivered software. The MDM channel itself is healthy and keeps acknowledging commands, which is what makes the host look fine. If MDM commands *are* also piling up unacknowledged, that is a separate channel 5 failure and the missing agent does not explain it.

One deployment reported 20 to 30 machines in 1,000 not getting fleetd this way, in `fleetdm/fleet#47793`, which proposes moving the install to the declarative protocol. Neither the issue nor its state appears in the 4.90.0 source, so check it rather than relying on this sentence. Treat that as one estate's observation rather than a rate you can expect. Detection and recovery are in [8.4](8.4-host-side-investigation.md).

## 8.1.5 Classify the failure

Almost everything Fleet does is asynchronous, through a queue. Start by placing the failure in one of seven classes, which you can usually do **before you know anything about the feature**, because the tells are structural.

| # | Class | Meaning | Generic tell | Go to |
|---|---|---|---|---|
| 0 | **Not intended** | The config does not say what you think | Desired state absent at the source | Read the config, not logs |
| 1 | **Not targeted** | Intent exists, does not resolve to this host | Host not in the resolved fleet or label set | [8.6.13](8.6-server-state.md#8613-scoping-which-fleet-which-labels-was-this-host-targeted) |
| 2 | **Not queued** | Targeted, but no work item created | No row for this host and item | The cron that creates it, §8.1.7 |
| 3 | **Queued, not delivered** | Row exists, device never took it | Row present, `activated_at` or sent timestamp NULL | The channel, §8.1.4 |
| 4 | **Delivered, not executed** | Device got it, did not act or did not report | Command sent, no result row | [8.4](8.4-host-side-investigation.md) |
| 5 | **Executed, failed** | It ran and errored | Result row with error or non-zero status | [8.4](8.4-host-side-investigation.md) |
| 6 | **Succeeded, not reflected** | It worked, Fleet's view is stale | Host reality differs from Fleet UI | Refetch. If it is still stale afterwards, the detail results are not being ingested, which is a real failure |

**Class 6 is the one this manual most wants you to rule out early**, and that is a judgement about cost rather than a claim about frequency: profiles listed as Enforcing on the host while Fleet shows something else, or vitals lagging a change, send people hunting a delivery pipeline that worked fine, and the check that avoids it takes a minute. Check the host before you check the queue.

One case sits outside all seven, and it is the nastiest: **executed, reported success, did not work**. A Linux package manager that exits zero on a no-op is recorded as a successful install. Nothing in the pipeline is wrong and no class describes it. If Fleet says success and the host disagrees, suspect the exit code rather than the pipeline.

### Where the queues live

| Queue | Table |
|---|---|
| Scripts, software installs and uninstalls, VPP and in-house app installs | `upcoming_activities`. `activated_at IS NULL` means queued but not started |
| Apple MDM commands | `nano_commands` holds the command once; `nano_enrollment_queue` ties it to each recipient; results land in `nano_command_results`. Enrollment in `nano_enrollments`, `nano_devices` |
| Windows MDM commands | `windows_mdm_command_queue` then `windows_mdm_command_results`. `windows_mdm_responses` holds only the gzipped session envelope |
| Per-host profile desired vs actual | `host_mdm_apple_profiles`, `host_mdm_windows_profiles`, `host_mdm_apple_declarations`, `host_mdm_android_profiles` |
| Setup experience | `setup_experience_status_results` |
| Async worker jobs | `jobs` |

Reading these directly is normal practice rather than an escalation, where you have a read-only database credential. On a managed deployment you may not, and then the equivalent is to collect what [8.13](8.13-escalation.md) asks for and hand it over. Full schema in [8.6](8.6-server-state.md).

**Depth matters more than presence.** One queued item tells you little. A queue that is growing tells you the drain is broken. A queue that is shrinking tells you to wait. A host showing ten pending activities and twenty-four an hour later is the diagnosis, not a detail.

## 8.1.6 Bisect, do not walk

Walking a pipeline stage by stage costs one observation per stage. Halving it costs far fewer. Choose a cut where **one observation has two opposite-pointing interpretations.**

| Cut | Left means | Right means |
|---|---|---|
| Is there a queue row for this host and item? | Server-side, classes 0 to 2 | Delivery or execution, classes 3 to 5 |
| Does the host's own state match Fleet's view? | Genuine failure, 3 to 5 | Staleness, class 6 |
| Does it fail on one platform but not another? | Platform, agent, or protocol path | Server-side config or targeting |
| One host, or every host in the fleet? | Host-specific | Targeting or server-side |
| Did the responsible cron run recently and cleanly? | The scheduler | The work the job does |
| **Is the record's own timestamp old, or only its arrival time?** | Produced long ago, arriving late. Look left | Nothing new is being produced. Look right |

### The two-clocks check

The last cut resolves an entire family of stale-data reports in one observation. When something arrives carrying an old timestamp, ask which timestamp is old: the one inside the record, or the one stamped on arrival.

**Record old, arrival recent.** The data was produced long ago and is only now arriving. Look left, at the host. Fleet writes results to the configured destination in the same request that delivered them, and returns an error to osquery when that write fails so the agent retries on its next log period. Both halves point at the device: osquery holds results in its local store while it cannot get them accepted, and drains that store when it can, replaying with the timestamps they were recorded under. Confirm by checking whether the affected hosts share a recent return to connectivity.

**Both old.** Nothing new is being produced or forwarded. Look right, at the destination. It may be re-reading an existing bucket or stream rather than receiving anything new.

This check needs **individual record timestamps**. An aggregated latency metric cannot answer it. If your pipeline exposes only an average, instrument it to sample raw records before you need this.

## 8.1.7 Force the stage, then verify it ran

Many Fleet stages can be forced rather than waited on. Force the stage you believe is stuck and see whether it advances. If it advances, the stage was fine and its trigger was not. If it does not, you have localised to the stage.

```sh
fleetctl trigger --name="<schedule>"
```

Fleet 4.90.0 can register 35 schedules, the 34 names in its own list plus `mdm_service_discovery` ([8.6.3](8.6-server-state.md#863-the-named-schedules) lists them all), and a given server registers a subset depending on licence and configuration. Passing a name it does not recognise makes it print the list that server actually registered, which is the quickest way to get the real set rather than a number from a book. Common targets: `mdm_apple_profile_manager`, `mdm_windows_profile_manager`, `apple_mdm_dep_profile_assigner`, `apple_mdm_apns_pusher`, `maintained_apps`, `vulnerabilities`, `automations`, `integrations`, `refresh_vpp_app_versions`, `upcoming_activities_maintenance`, `host_vitals_label_membership`.

> ### ⚠️ `fleetctl trigger` reports success for runs that never happen
>
> A trigger returns without triggering in three cases: a scheduled run of that schedule is already pending, a previous trigger is still pending or queued, or the internal channel the request goes down is momentarily full.
>
> The first two are reported. They come back with the offending run's statistics and `fleetctl` prints `[!] Conflict`, so you know the trigger did not take. The third is not reported at any level you will see. The server notes it at debug level, discards the flag saying whether the trigger actually went out, and returns no error, so `fleetctl` prints `[+] Sent request to trigger <name> schedule` for a run that never happened.
>
> **Never interpret a trigger without checking whether the run happened.**
>
> ```sql
> SELECT name, instance, stats_type, status, created_at, updated_at, errors
> FROM   cron_stats
> WHERE  name = '<schedule>'
> ORDER  BY created_at DESC
> LIMIT  5;
> ```
>
> A local run starts at `pending` and moves to `completed`. `queued` is not a universal first state: it is what a trigger gets when the schedule runs on a different node, and it becomes `pending` when that node claims it. `expired` and `canceled` are terminal alternatives. `errors` is JSON. `instance` identifies which server node ran it, which matters on multi-node deployments where one node can fail while the others are healthy. There is no API for this; it needs database access.
>
> Checking that every schedule is current, not only the one you suspect, is the fastest way to tell one broken job from a wedged scheduler. See [8.6](8.6-server-state.md).

Other forceable stages, and whether they are safe on a production host, are in [8.11](8.11-reproducing-and-isolating.md).

## 8.1.8 Read logs last

By now you know the channel, the class, and the stage, so you know which log to open and what you are looking for.

| Want | Go to |
|---|---|
| The full map of every log surface and its path | [8.2](8.2-log-surfaces.md) |
| Fleet server operational logs and error strings | [8.3](8.3-server-logs.md) |
| Host-side agent logs and on-disk state | [8.4](8.4-host-side-investigation.md) |
| `fleetctl debug` and the debug archive | [8.5](8.5-fleetctl-debug.md) |

Two traps worth knowing before you start. `fleetctl debug errors` reads Fleet's recorded errors out of Redis rather than a file, and records **server faults only**: client 4xx errors are never stored, so chasing one there returns nothing. And per-request log lines are emitted at debug level unless the error is a non-client error, so some failures produce no line at all at default verbosity. Raise verbosity before reproducing, not after. Both are covered in [8.3](8.3-server-logs.md).

## 8.1.9 When to stop

Stop when you can name the class and the stage, or when you have proven you cannot observe the stage you need. Then collect and escalate.

At minimum: the §8.1.2 intake, the channel sweep result, the relevant queue rows, `fleetctl debug archive`, and host-side agent logs for the window. Full list in [8.13](8.13-escalation.md).

**Say what you ruled out, not only what you saw.** "Live reports respond, MDM command unacknowledged, an active `nano_enrollment_queue` row for this host with no matching result, `cron_stats` clean" is a diagnosis. "It's not working" is a ticket.
