# Diagnosing degradation

[8.1](8.1-diagnostic-method.md) covers problems where something failed to arrive. This section covers the other family: everything arrives, and the system is slow, heavy, or fighting something else. Nothing is stuck, so the seven-class taxonomy has nothing to classify.

The tooling for this family is good and almost nobody uses it. Fleet ships full [pprof]() profiling of the server through `fleetctl debug`. Its `profile`, `heap`, `goroutine`, and `trace` subcommands appear zero times across 5,112 real support conversations and zero times in Fleet's own documentation, while server performance is the most recurring issue category in that same corpus. `fleetctl debug archive` collects all of them in one file, and it is the right first move (§8.14.3).

## 8.14.1 The four causes

| Cause | The question | Distinguishing observation |
|---|---|---|
| **Resource contention** (§8.14.6) | Is Fleet competing with something else for CPU, memory, or I/O? | Onset correlates with another product's version or policy change, not with Fleet's. Cost is on the **host**, or on the server node, not in Fleet's own profile. |
| **Scale ceiling** (§8.14.7) | Does it work small and fail large? | The same operation succeeds against a small target set and fails against a large one. Failure moves with **cardinality**, not with content. |
| **Limits and quotas** (§8.14.4) | Is something silently truncating or refusing? | Partial results with **no error**, or a hard cliff at a round number. Reducing size makes it work. |
| **Query cost** (§8.14.5) | Is the work itself expensive? | The control test passes and the real query does not. Cost visible per query in `osquery_schedule`, or per endpoint in a CPU profile. |

Two of these imitate each other. A limit trips at volume, so it presents as a scale ceiling. A scale ceiling has a cliff, so it presents as a limit. The separator is whether raising the limit fixes it, so go looking for the limit first: that is one lookup, and a scale investigation is a day.

## 8.14.2 Establish a control first

Before profiling anything, prove the path works with a query that cannot be expensive.

```sql
SELECT 1 WHERE 1 = 0;
```

Run it as a live report against the affected hosts. `(100% responded)` means the whole path is healthy: device to Fleet, Fleet to Redis, Fleet to MySQL, websocket to browser. Fleet's own live report troubleshooting guide opens with the same test.

**What each outcome tells you:**

| Control result | Real query result | Conclusion |
|---|---|---|
| 100% responded | 100% responded | Not infrastructure, not the query. Look at result volume and the destination. |
| 100% responded | partial or hangs | The **query**. Go to §8.14.5. |
| partial or hangs | (irrelevant) | The **infrastructure**. Bypass layers below. |

### Bypass one layer at a time

| Test | Removes from the path | If it now works |
|---|---|---|
| Same query through `fleetctl report --query '…' --hosts '…' --exit` | Browser rendering | Browser or rendering problem, not server |
| A different browser | That browser's state | Same |
| The synchronous live report API (below) | **Websockets** | Your infrastructure is blocking or dropping websocket upgrades |
| `/healthz?check=mysql` and `/healthz?check=redis` | Everything but one dependency | That dependency is down or unreachable from this node |

Synchronous live report, over plain HTTP:

```sh
curl -X POST \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  https://fleet.example.com/api/v1/fleet/reports/<report_id>/run \
  -d '{"host_ids": [375]}'
```

`POST /api/v1/fleet/reports/:id/run` replaced `GET /api/v1/fleet/queries/run` in Fleet 4.43.0, and the old endpoint still answers. It is a simplified implementation, sized for a handful of hosts rather than thousands (fleetdm.com/docs/rest-api/rest-api).

`/healthz` returns HTTP 200 when the server is up **and** holds healthy MySQL and Redis connections, and 500 otherwise, with detail in the server log. The `check` URL parameter narrows it to one dependency (fleetdm.com/docs/deploy/reference-architectures).

### How long the synchronous API waits

`FLEET_LIVE_QUERY_REST_PERIOD` is an environment variable, absent from the server configuration reference, and it sets **two different things with two different defaults**:

| Use | Default when unset |
|---|---|
| Deadline for collecting live report results | **25s** |
| Floor for the HTTP server's write timeout, plus 10s | **90s** (so 100s) |

Setting the variable moves both: the deadline becomes your value, and the write timeout floor becomes your value plus 10 seconds.

> Fleet's live report troubleshooting guide says the synchronous API "will wait for ~100 seconds by default". That figure is the write timeout. The result deadline is 25 seconds. Fleet treats the mismatch as known and has left it alone, so that a short deadline cannot shorten the write timeout and break long-running uploads.

A live report also times out when `distributed_interval` is larger than `FLEET_LIVE_QUERY_REST_PERIOD`, because hosts have not checked in yet. Fix that by raising the period or lowering the interval. Fleet recommends `distributed_interval` between **10 and 30 seconds**.

## 8.14.3 Server profiling with `fleetctl debug`

| Command | Produces | Answers |
|---|---|---|
| `fleetctl debug profile` | 30-second CPU profile | Where is the server burning CPU |
| `fleetctl debug heap` | Heap-allocated memory | What is holding memory, and is it growing |
| `fleetctl debug goroutine` | Stack traces of every goroutine, meaning each concurrent task the server has in flight | Deadlocks, stuck workers, runaway concurrency, goroutine leaks |
| `fleetctl debug trace` | 1-second execution trace | Scheduling, blocking, and latency detail |
| `fleetctl debug cmdline` | The server's argv | Effective config, as opposed to intended config |
| `fleetctl debug errors` | Recorded server errors, from Redis | Recent error classes, non-destructive unless `--flush` |
| `fleetctl debug migrations` | Missing or unknown migrations | Schema drift after an upgrade |
| `fleetctl debug db-locks` | Waiting and blocking transactions | Lock contention in MySQL |
| `fleetctl debug db-innodb-status` | `SHOW ENGINE INNODB STATUS` | InnoDB internals, deadlock history, buffer pool |
| `fleetctl debug db-process-list` | `SHOW PROCESSLIST` | Long-running or piled-up queries, right now |
| `fleetctl debug archive` | All of the above in one `.tar.gz` | **The right first move.** |

Flags on all of them: `--outfile` (`OUTFILE`), `--config`, `--context`, `--debug`. `errors` adds `--stdout` and `--flush`. `connection` adds `--fleet-certificate`. Through `fleetctl` the durations are fixed: `profile` samples for 30 seconds and `trace` for 1 second. For a longer sample, call the endpoint directly (below).

### What `archive` contains

Thirteen files, in this order:

`allocs` · `block` · `cmdline` · `errors` · `goroutine` · `heap` · `mutex` · `profile` · `threadcreate` · `trace` · `db-locks` · `db-innodb-status` · `db-process-list`

Four of those come only from `archive`, with no subcommand of their own:

| Profile | Answers |
|---|---|
| `allocs` | All allocations since start, including freed ones. Heap shows what is live; allocs shows what churned. |
| `block` | Time spent blocked on synchronisation primitives |
| `mutex` | Contended mutexes and who holds them |
| `threadcreate` | What is creating OS threads |

A `Failed <profile>` line on stderr is normal rather than an error. The command continues on purpose, so a struggling server still yields whatever it can, and a run from outside the server's own environment still gets you most of the archive. The common pair is `Failed db-innodb-status` and `Failed db-locks`, which means the database user lacks the privileges described below.

### Consuming the output

Profiles are in Go's standard pprof format, so `go tool pprof` and `go tool trace` read them directly. Since Fleet 4.86.0 the released binaries ship without debug symbols, so supplying the `fleet` binary alongside a profile adds nothing. The profiles stand on their own: Go's runtime writes function names into them as it collects. See [8.5](8.5-fleetctl-debug.md).

```sh
tar xzf fleet-profiles-archive-20260819T120000Z.tar.gz

# Interactive: 'top', 'list <func>', 'web' (needs graphviz)
go tool pprof fleet-profiles-archive-.../profile.prof

# Browser UI with flame graph, no binary needed
go tool pprof -http=:8081 fleet-profiles-archive-.../profile.prof

# Goroutine dump as plain text, which is usually what you want
go tool pprof -text -nodecount=100 fleet-profiles-archive-.../goroutine.prof

# Execution trace
go tool trace fleet-profiles-archive-.../trace.prof

# Memory growth: capture twice, minutes apart, then diff
go tool pprof -http=:8081 -base heap-t0.prof heap-t1.prof
```

`db-locks`, `db-innodb-status`, `db-process-list`, and `errors` are JSON, so `jq` reads them.

**Reading `goroutine.prof` without pprof:** the raw file is a text stack dump. A count in the thousands for one stack is the finding. Look for large counts parked in database or Redis wait, which means the pool is the bottleneck, not the code.

### Requirements and hazards

**Database privileges:** `db-innodb-status` and `db-locks` read InnoDB tables, which needs global `PROCESS` and `SELECT`. The error message names the grant:

```sql
GRANT PROCESS, SELECT ON *.* TO 'fleet'@'%';
```

All three database profiles query the **writer** by design. Lock and process state on a read replica describes the replica, not the deployment.

**Authorisation:** the `/debug/` endpoints require a bearer token belonging to a user whose **global role is admin**. Team admins get a 403. This requirement is undocumented.

**Sensitive content:** `cmdline` contains the server's command line. If credentials are passed as CLI arguments rather than environment variables or a config file, they are in the archive. Scrub before sharing. `fleetctl` prints a warning to this effect.

### Pin profiling to a named node

`fleetctl` normally talks to a load balancer, so profiles land on whichever node answered. On a multi-node deployment, that makes results unrepeatable. Create a context pinned to one node:

```sh
fleetctl config set --context server-a --address https://server-a:8080
fleetctl login --context server-a
fleetctl debug archive --context server-a
```

Pair this with the `instance` column in `cron_stats` ([8.6](8.6-server-state.md)): one bad node in an otherwise healthy set of nodes is a real and easily missed shape.

### Raw pprof, for a longer sample

`fleetctl` calls `/debug/pprof/<name>` with no query parameters, which is why the sample duration is fixed there. The endpoints behind it are Go's standard `net/http/pprof` handlers, and those accept `seconds`:

```sh
curl -H "Authorization: Bearer $API_TOKEN" \
  "https://fleet.example.com/debug/pprof/profile?seconds=120" -o profile-120s.prof
```

Not documented; inferred from Fleet mounting the standard profile and trace handlers unmodified.

### Traces, for request-level detail

Fleet exports OpenTelemetry traces with `FLEET_LOGGING_TRACING_ENABLED=true` and `OTEL_EXPORTER_OTLP_ENDPOINT`. Sampling is route-aware and built in, so `OTEL_TRACES_SAMPLER` has no effect on it:

| Tier | Rate | Routes |
|---|---|---|
| Never | 0% | `/healthz`, `/version`, `/metrics` |
| High volume | 0.1% | osquery distributed read/write, config, log upload, orbit config and ping, device ping and desktop |
| Standard | 2% | Admin and UI read endpoints |
| Always | 100% | Enrollment, MDM command flows, SCEP, GitOps applies, cron jobs |

For a short high-resolution window during a reproduction:

```sh
curl -X PATCH "https://fleet.example.com/debug/trace_sampler" \
  -H "Authorization: Bearer $API_TOKEN" \
  -d '{"force_full": true}'
```

Each node polls for the change about once a minute. Revert it when you are done: at 100% on a large fleet the span volume is enormous.

## 8.14.4 Limits that fail silently

Each of these produces missing data or a refused write with no obvious error. Every row is a single lookup, which is why §8.14.1 says to clear them before opening a scale investigation.

| Limit | Default | Set where | At the boundary | Confirm with |
|---|---|---|---|---|
| Redis publish/subscribe (pubsub) output buffer | `client-output-buffer-limit pubsub 32mb 8mb 60` | Redis config | Redis **disconnects the subscriber**. Live report results vanish with no error. | Redis client-output-buffer metrics during a large run |
| Same, on AWS ElastiCache | different parameter names | Parameter group | Same | `client-output-buffer-limit-pubsub-hard-limit`, `-soft-limit`, `-soft-seconds` |
| MySQL `max_allowed_packet` vs `carver_block_size` ([file carving]()) | MySQL 8 default 64MB (`67108864`) | MySQL, and agent options | MySQL **rejects the write**. The carve fails or stalls. | `SHOW VARIABLES LIKE 'max_allowed_packet'` |
| `mysql_max_open_conns` | `50` per Fleet server | `FLEET_MYSQL_MAX_OPEN_CONNS` | Requests queue waiting for a connection. Latency, not errors. | `db-process-list`, connection count on the DB |
| MySQL `max_prepared_stmt_count` | MySQL default | MySQL | Prepared statement errors under load | Must be ≥ `FLEET_MYSQL_MAX_OPEN_CONNS × (number of Fleet servers) × 4` |
| `redis_max_open_conns` | `0` (no limit) | `FLEET_REDIS_MAX_OPEN_CONNS` | With a non-zero value, waits up to `redis_conn_wait_timeout` (default `0`, meaning no wait) then fails | Redis connection metrics |
| `redis_read_timeout` / `redis_write_timeout` | `10s` each | `FLEET_REDIS_READ_TIMEOUT`, `..._WRITE_TIMEOUT` | Operation fails, request errors | Server error log |
| `server_default_max_request_body_size` | `1MiB` | `FLEET_SERVER_DEFAULT_MAX_REQUEST_BODY_SIZE` | HTTP request rejected. Per-endpoint overrides exist via `server_endpoint_request_size_overrides`. | Server access log status codes |
| `osquery_max_log_write_body_size` | built-in `10MiB` | `FLEET_OSQUERY_MAX_LOG_WRITE_BODY_SIZE` | `/api/osquery/log` rejects the batch. **Only applies when `osquery_allow_body_auth_fallback` is `true` (the default).** | Orbit and osquery status logs on the host |
| `osquery_max_distributed_write_body_size` | built-in `5MiB` | `FLEET_OSQUERY_MAX_DISTRIBUTED_WRITE_BODY_SIZE` | `/api/osquery/distributed/write` rejects the results. Same body-auth condition. | Same |
| `FLEET_LIVE_QUERY_REST_PERIOD` | `25s` deadline | environment only | Synchronous live report returns partial results | §8.14.2 |
| osquery `--events_max` | `50000` rows per evented table | agent options | **Oldest events expire.** Silent data loss. | `SELECT name, events FROM osquery_events;` |
| osquery `--events_expiry` | `86000` seconds | agent options | Rows expire once the table has been queried after generation | Same |
| Login rate limit | 10/min, burst 9 | built in | HTTP 429 | 429s on `/api/v1/fleet/login` in the access log |
| Forgot-password rate limit | 10/hour, burst 9 | built in | HTTP 429 | Access log |
| Org-logo endpoint | 60/min, burst 20 | built in | HTTP 429 | Access log |
| SSO and MDM SSO | `auth_sso_rate_limit_per_minute`, `mdm.sso_rate_limit_per_minute` | config | HTTP 429 | Config reference |
| Fleet Desktop device endpoints | 1,000 consecutive **failing** requests per minute, then the source IP is banned for 1 minute | built in | Desktop stops working for everything behind that IP | Access log, 429s clustered by source IP |
| S3 carve parts | 10,000 parts, `carver_block_size` ≥ 5MiB | agent options | Upload rejected | fleetdm.com/guides/file-carving |
| Individual carve file size | under 8GB | n/a | The carve fails | Same |

**Fleet rate-limits the endpoints above and no others.** So a 429 on a plain read endpoint comes from something between you and Fleet: a load balancer, a WAF, or an API gateway.

The Desktop IP ban deserves attention on any deployment behind a NAT or corporate egress. The threshold counts **failing** requests, so a fleet with a population of hosts holding stale device tokens can ban the whole office.

## 8.14.5 Query cost, on the host

osquery keeps its own accounting. These tables are readable through a live report and are the fastest way to turn "Fleet is heavy on my laptop" into a named query.

### `osquery_schedule`

Columns: `name`, `query`, `interval`, `executions`, `last_executed`, `denylisted`, `output_size`, `wall_time`, `wall_time_ms`, `last_wall_time_ms`, `user_time`, `last_user_time`, `system_time`, `last_system_time`, `average_memory`, `last_memory`.

Cost ranking, per host:

```sql
SELECT name, interval, executions, output_size, average_memory, last_memory,
       wall_time_ms, last_wall_time_ms, last_executed, denylisted
FROM osquery_schedule
ORDER BY average_memory DESC;
```

Per-execution CPU, which is the number that matters when a query runs often:

```sql
SELECT name, interval, executions, output_size,
       (user_time / executions)   AS avg_user_time,
       (system_time / executions) AS avg_system_time,
       average_memory, last_executed
FROM osquery_schedule;
```

That second form is the one Fleet itself uses to populate host vitals.

### The denylist

```sql
SELECT name, query FROM osquery_schedule WHERE denylisted = '1';
```

osquery's watchdog denylists a scheduled query that repeatedly exceeds its resource budget. **A denylisted query stays out of the schedule until osquery restarts.**

This is the mechanism behind a specific and confusing presentation: a query that "times out" or completes at 40 to 70 percent across a fleet, with a healthy server. Nothing failed to deliver. The hosts declined to run it. Directory traversal and wildcard paths are the usual trigger.

Fleet 4.74.0 downgraded the server-side `distributed query is denylisted` message from error to warning, because it reports a host problem rather than a server one, so look for it at warning level. Release notes are at github.com/fleetdm/fleet/releases.

### The watchdog

osquery's watcher process enforces a memory limit and a CPU limit against the worker process, and against each managed extension:

| Flag | Controls |
|---|---|
| `--watchdog_memory_limit` | Maximum memory, in MB |
| `--watchdog_utilization_limit` | Maximum CPU, as `processes.user_time` + `system_time` |
| `--watchdog_latency_limit` | How long CPU may stay over the limit |
| `--watchdog_delay` | Grace period before limits are enforced. Default 60 seconds. |
| `--watchdog_forced_shutdown_delay` | Wait between `SIGTERM` and `SIGKILL` |
| `--watchdog_level` | Preset limit profile |
| `--disable_watchdog` | Turns it off entirely |

Fleet states the default budget as **200 MB of memory and 10% CPU**.

Kill sequence for the worker: `SIGUSR1`, then `SIGTERM`, then `SIGKILL` after `--watchdog_forced_shutdown_delay`. If the worker cannot be respawned within the respawn limit, **osquery shuts down entirely**, which presents as a host that has gone silent rather than a host that is slow (fleetdm.com/guides/osquery-watchdog).

Every watchdog flag is a command-line flag, so it goes under `command_line_flags` in agent options and **takes effect on the next fleetd restart**. `distributed_interval`, `logger_tls_period`, `events_max`, `events_expiry`, and `schedule_splay_percent` are accepted in both places, so setting them under `options` applies without a restart.

### Evented tables

```sql
SELECT name, publisher, type, subscriptions, events, active FROM osquery_events;
```

`events` is the buffered row count. A large number on a table nobody queries is pure cost. `subscriptions = 0` means the publisher is generating events that nothing reads.

Cost controls, in order of bluntness: stop the underlying OS utility generating the events, narrow the `SELECT`, lower `--events_max` and `--events_expiry`, or set `disable_events`. Both osquery and the underlying utility drop events under load. osquery logs its own drops; drops inside the utility are invisible to it (fleetdm.com/guides/osquery-evented-tables-overview).

### The two agent intervals

| Setting | Fleet's guidance | Lowering it | Raising it |
|---|---|---|---|
| `distributed_interval` | **10 to 30 seconds** | Live reports return faster; more check-in load on the server, multiplied by host count | Live reports time out before hosts check in, per §8.14.2 |
| `logger_tls_period` | not stated as a range | Results arrive sooner; more, smaller uploads | Fewer, larger uploads. Larger batches can hit `osquery_max_log_write_body_size`. |

The Fleet-side counterpart, `buffered_log_max`, sets how much osquery holds locally while Fleet is unreachable. Fleet's availability model depends on it: agents keep running and keep buffering through server downtime.

### Fleet's own cost signal

Fleet computes a per-query **performance impact** of minimal, considerable, or excessive from the stats above, shown on the reports pages. `app_enable_report_stats` (default `true`, `FLEET_APP_ENABLE_REPORT_STATS`) controls collection for scheduled reports. Stats are still collected for live reports when it is `false`.

## 8.14.6 Interference

Another product on the host or the server contends with Fleet's components, or blocks them outright. Endpoint detection and response (EDR) tooling is the usual counterparty. This is a real and recurring root cause, and it is invisible from Fleet's own telemetry because nothing Fleet does fails.

| Shape | Presentation |
|---|---|
| **Resource contention** | Both agents alive and healthy. Host is slow. Watchdog restarts in Orbit logs. Cost is real but attributed to whichever agent the user notices. |
| **Inspection and scanning** | An endpoint security product scans or intercepts files or syscalls that osquery touches, multiplying the cost of ordinary osquery work. Onset tracks the **other** product's version, or a change in what osquery does. |
| **Blocking** | Application allow-listing or deny-listing prevents a Fleet binary from running, or TLS inspection breaks the certificate chain. This one usually presents as a delivery failure, so treat it under [8.1](8.1-diagnostic-method.md) if nothing is arriving at all. |

### The diagnostic

1. **Get the onset date precisely.** Not "last month". The day.
2. **List every version that changed near it**, on both sides: Fleet server, fleetd, osquery inside fleetd, the OS, and the other product plus its policy or signature version. A degradation whose onset matches the other product's rollout and not Fleet's is not a Fleet regression, whatever the symptom looks like.
3. **Test on one host with the other product disabled**, or with Fleet's paths excluded from it. One host. This is the whole test, and it is decisive in either direction.
4. **Check the host's own accounting** (§8.14.5) while the other product is running and while it is not. If `average_memory` and `wall_time_ms` for the same queries change materially, the interference is real and measurable.
5. **Check the other product's logs**, not Fleet's. Fleet's logs will look fine, because from Fleet's side nothing failed.

### Remediating

Endpoint security products generally support exclusion by **code-signing publisher** or by **path**. Publisher-based exclusion is the more durable of the two: it survives path changes across agent versions. Fleet's binaries and working directories are the exclusion targets. Confirm the exact paths for your platform and installer against [8.4](8.4-host-side-investigation.md) rather than assuming, since they differ by OS and by whether fleetd was installed with a custom prefix.

Where the other product is blocking rather than merely competing, the fix is an allow-list entry, and the intake question is item 7 of Fleet's MDM bug checklist: "is any sort of application level allowlisting or denylisting installed?" Fleet's own checklist names Santa and Jamf Pro there as examples.

> [!internal] The single most recurring issue cluster in Fleet's support history (roughly 25 tickets merged into four entries) is exactly this shape: an EDR product began flagging osquery as malicious after osquery v5.23.0 changed to make a temporary copy of keychain files, and the resulting contention presented to customers as "Fleet server performance". Resolution was publisher-level exclusion of Fleet's signing identity plus the agent binary paths, then a Fleet patch release. Note the misattribution: the reported symptom was *server* performance, and the cause was entirely host-side. The mapping of that fix to a specific Fleet patch version is recorded in the corpus but is not identifiable in Fleet's public release notes; treat the version number as unverified.

## 8.14.7 Scale

### What Fleet publishes

Fleet's reference architecture gives sizing breakpoints. Reproduced from fleetdm.com/docs/deploy/reference-architectures, for AWS with Fargate, Aurora MySQL 8 and ElastiCache Redis 7.x. These are Fleet's own numbers rather than a benchmark:

| Hosts | Fleet tasks | Per task | `FLEET_MYSQL_MAX_OPEN_CONNS` | Redis | MySQL |
|---|---|---|---|---|---|
| 5,000 | 6 | 1024 CPU units, 4GB | 10 | `cache.t4g.small` ×3 | `db.t4g.medium` ×2 |
| 10,000 | 8 | 1024 / 4GB | 10 | `cache.t4g.medium` ×3 | `db.t4g.large` ×2 |
| 25,000 | 10 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.large` ×2 |
| 50,000 | 15 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.xlarge` ×3 |
| 80,000 | 20 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.2xlarge` ×3 |
| 100,000 | 25 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.2xlarge` ×3 |
| 150,000 | 40 | 1024 / 4GB | 20 | `cache.r6g.large` ×3 | `db.r6g.4xlarge` ×3 |
| 300,000 | 70 | 1024 / 4GB | 20 | `cache.r6g.xlarge` ×3 | `db.r6g.8xlarge` ×3 |

Read the shape, not the rows. Fleet nodes stay at a fixed size and multiply. Redis barely moves. **MySQL is what grows**, and it grows faster than host count. A degradation investigation that starts anywhere other than the database is usually starting in the wrong place.

### Constraints on the topology

- Fleet scales **horizontally**: more processes against the same MySQL and Redis, behind a load balancer. All APIs work in that arrangement.
- MySQL must be **single-writer**, one primary with read replicas. Multi-writer and group replication are not supported.
- Fleet servers need a writer **in the same datacenter**. Cross-region replication is for failover; writes stay local.
- Read replica config is set with the `mysql_read_replica_` prefix and inherits **nothing** from the primary. Every required value must be set again. There is no default for `mysql_read_replica_address`, so a partial configuration silently runs everything against the primary.
- With a read replica, set a non-zero `mysql_read_replica_conn_max_lifetime`. Some environments repoint the replica address during auto-scaling, and Fleet notices the new address when idle connections are recycled.
- Minimum MySQL is **8.0.44**. Tested against 8.0.44, 8.4.8, and 9.5.0. **9.6.0 is incompatible.**
- Multiple Fleet deployments sharing one database server need proportionally more database resources.

### What to watch as the fleet grows

| Signal | Where | Meaning |
|---|---|---|
| Fleet node CPU and memory **during** a live report | Container metrics | Vertical or horizontal headroom |
| Redis CPU and memory during a live report | Redis metrics | Redis as the bottleneck; check the pubsub buffer before resizing |
| MySQL writer CPU | DB metrics | The usual first ceiling |
| Replica lag | DB metrics | Reads returning stale data, which presents as class 6 in [8.1](8.1-diagnostic-method.md) |
| `db-process-list` during the slowdown | `fleetctl debug` | Which statements are piling up |
| `db-locks` | `fleetctl debug` | Whether it is contention rather than volume |
| Host enrollment count changes | Prometheus | Enrollment storms and duplicate identifiers |
| HTTP latency and error rate per endpoint | Prometheus | Which surface degraded |

Fleet exposes Prometheus-format metrics and suggests alerting on enrollment level changes, endpoint latency, and endpoint error rates. Traces are sampled at the moment a request arrives, at the rates in §8.14.3, so read total request counts and error rates from metrics.

### Server-side knobs that trade freshness for load

| Setting | Default | Effect |
|---|---|---|
| `osquery_label_update_interval` | `1h` | Raising it cuts baseline load. **Lowering it can cause outages**, in Fleet's own words. |
| `osquery_policy_update_interval` | `1h` | Same |
| `osquery_detail_update_interval` | `1h` | Same |
| `osquery_max_jitter_percent` | `10` | Spreads check-ins so hosts do not arrive together |
| `osquery_min_software_last_opened_at_diff` | `1h` | Suppresses redundant software timestamp writes |
| `redis_host_cache_enabled` | `true` | Fronts host lookups on osquery and orbit auth paths, cutting MySQL load on the highest-volume endpoints |
| `redis_host_cache_ttl` | see note | Longer TTL, less DB reader load, staler host records. Jittered ±10%. |
| `osquery.enroll_cooldown` | `0` (off) | Rejects re-enrollment within the window. Explicitly a **load control for deployments where many hosts share an identifier**. |
| `osquery_host_identifier` | `provided` | `uuid` or `instance` prevents identifier collisions outright |
| `query_reports_disabled` (server settings, via API or GitOps) | `false` | Query report storage is a documented database load source. Turning it off is a real remediation for writer saturation. |
| `osquery_enable_async_host_processing` | `false` | **Experimental.** Moves label membership, policy membership, host last-seen, and scheduled query stats through Redis. Less Fleet and MySQL load, more Redis load. |
| `server_gzip_responses` | see config reference | Trades server CPU for bandwidth |

> **Two different defaults are published for `redis_host_cache_ttl`.** The configuration reference says `60s`. The server's own default is `180s`, and Fleet's 4.89.0 release notes record the raise from 60s to 180s. Treat 180s as the live value.

Turning off query reports:

```sh
fleetctl api -X PATCH \
  -F server_settings='{"query_reports_disabled":true}' \
  /api/v1/fleet/config
```

The async host processing option has a stated correctness caveat: with the failing policies webhook **and** async processing both enabled, some webhook fires can be missed on transitions between passing and failing.

### Duplicate enrollment as a scale problem

Hosts sharing an identifier overwrite each other's records on enrollment. The downstream effect is Redis backlog and live reports that return late and all at once rather than trickling in. Fleet documents the two fixes as `osquery_host_identifier: uuid` (or `instance`) and `osquery.enroll_cooldown`, recommending the identifier change as the better of the two.

### Row counts, before hardware

Some tables accumulate rows in proportion to activity rather than to fleet size, and a slow query against a bloated table looks exactly like insufficient hardware. Fleet has shipped both indexes and cleanup jobs for these: `distributed_query_campaign_targets` gained an index and a 24-hour cleanup of completed campaigns, and live query campaign activity is cleaned up on a cron. Before resizing anything, check row counts on the tables involved in the slow statements you found in `db-process-list`.

> [!internal] A customer's `distributed_query_campaign_targets` reached roughly 110 million rows and truncating it resolved the slowdown outright. Check row counts before recommending hardware.

### Upgrading is a legitimate remediation

Fleet's release notes carry a steady stream of performance fixes, several of them order-of-magnitude, and a handful of performance **regressions** later reverted. Recent examples: Windows MDM profile changes at scale (4.89.0), orbit check-in dropping a three-table join per check-in per host (4.89.0), the Apple profile and declarative device management reconciler, label listing with host counts, and per-vendor caching in CVE matching. Fleet 4.73.x had a documented MySQL read regression fixed in a later patch.

So "which Fleet version did this start on" is a first-class question, and the answer sometimes settles the investigation on its own. Read the release notes between the last good version and the current one before you profile (github.com/fleetdm/fleet/releases).

## 8.14.8 What is not documented

Where this section rests on inference rather than on Fleet's own docs.

| Item | Status |
|---|---|
| `fleetctl debug profile / heap / goroutine / trace` | All four work. No usage documentation anywhere in Fleet's docs: `archive` is documented, the individual profiles are not. |
| `db-locks`, `db-innodb-status`, `db-process-list` subcommands | All three work. Absent from Fleet's documentation. |
| `allocs`, `block`, `mutex`, `threadcreate` | Produced by `archive` alone. No subcommand, no documentation. |
| Global-admin requirement on `/debug/` | Confirmed behaviour, undocumented. |
| `?seconds=` on the pprof endpoints | Inferred from Fleet mounting Go's standard profile handlers unmodified. Undocumented, and `fleetctl` does not expose it. |
| `FLEET_LIVE_QUERY_REST_PERIOD` | Environment variable, absent from the server configuration reference. Both defaults, the 25s result deadline and the 90s write-timeout floor, come from the server rather than from documentation. |
| `redis_host_cache_ttl` default | Two published values. Treat the live default as 180s. |
| An infrastructure intake questionnaire for self-hosted deployments | Does not exist. The MDM bug checklist has no server-side counterpart, and "what are the common details of self-hosted customer infrastructure" recurs in Fleet's support history. Ask for topology, MySQL and Redis sizing and version, replica configuration, load balancer and TLS termination, node count, and log destination, up front. |
| Threshold values for "too slow" | Fleet publishes no latency or resource thresholds. Anything of that kind in this section would be invented. Compare against your own baseline. |

## 8.14.9 What to collect

Beyond [8.13](8.13-escalation.md)'s general list, degradation needs:

- `fleetctl debug archive`, taken **during** the degradation, from a named node (`--context`). Two heap profiles minutes apart if memory is the suspicion.
- The control result: did `SELECT 1 WHERE 1 = 0;` report `(100% responded)`.
- Topology: node count, instance sizes, MySQL and Redis versions and sizes, whether a read replica is configured, where TLS terminates.
- The onset date, and every version that changed near it on both sides.
- `osquery_schedule` and `osquery_events` output from an affected host, plus the same from an unaffected one.
- Fleet node, Redis, and MySQL CPU and memory graphs covering the window.
- Row counts for any table appearing in `db-process-list`.

## Version notes

- **4.89.0:** default `FLEET_REDIS_HOST_CACHE_TTL` raised 60s to 180s, and the host-update invalidation path stopped doing reverse-index GETs. Both reduce DB reader load and Redis CPU. Windows MDM profile changes at scale made faster and much lighter on the database. Orbit check-in no longer runs a three-table join per check-in per host.
- **4.84.3:** reduced database load from Fleet Desktop endpoints when invalid or expired device tokens are presented, by resolving the token with a single indexed lookup before the multi-join host-details query.
- **4.74.0:** `distributed query is denylisted` downgraded from error to warning on the server, because it indicates a host problem.
- **4.43.0:** `POST /api/v1/fleet/reports/:id/run` replaced `GET /queries/run` for the synchronous live report. The old endpoint remains for compatibility.

Release notes for each of these are at github.com/fleetdm/fleet/releases.
