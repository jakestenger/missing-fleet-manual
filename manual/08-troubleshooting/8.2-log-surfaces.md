# The log surfaces

Every place Fleet writes something a diagnostician can read: what it is, where it lives, how long it survives, and how to turn the volume up.

## 8.2.1 Which log answers which question

Start here. Find the row, open that file.

| Question | Surface | Location |
|---|---|---|
| Did fleetd start? Did it enroll? Is it failing to reach the server? | Orbit stdout/stderr | [8.2.2](#822-fleetd-orbit-stdout-and-stderr) |
| Did an update, script, or software install run on the host? | Orbit stdout/stderr | [8.2.2](#822-fleetd-orbit-stdout-and-stderr) |
| Same, but I have no shell access to the host | `fleetd_logs` osquery table, via live report | [8.2.6](#826-reading-fleetds-own-logs-without-shell-access) |
| Is osquery itself healthy? Did a flag take? Did a scheduled query blow its watchdog? | osquery **status** log | [8.2.4](#824-osquery-result-and-status-logs) |
| What data did a scheduled query actually produce? | osquery **result** log | [8.2.4](#824-osquery-result-and-status-logs) |
| Why is the Fleet Desktop menu bar item wrong, missing, or not authenticating? | `fleet-desktop.log` | [8.2.5](#825-fleet-desktop) |
| Is this host enrolled, and under which identity? | Orbit root directory artifacts | [8.2.7](#827-the-rest-of-the-orbit-root-directory) |
| Why did a macOS profile or MDM command fail on the device side? | `unified_log`, `process = 'mdmclient'` | [8.2.8](#828-macos-mdm-client-logs-by-live-report) |
| Same, on iPhone or iPad | sysdiagnose archive | [8.2.9](#829-iosipados-sysdiagnose) |
| Did the Fleet server itself throw? | Server stderr, plus recorded errors in Redis | [8.3](8.3-server-logs.md), [8.5](8.5-fleetctl-debug.md) |
| Where did my scheduled query results go after Fleet received them? | Configured result log destination | [8.2.11](#8211-server-side-log-destinations) |
| Who changed what in Fleet, and when? | Audit log stream | [8.2.11](#8211-server-side-log-destinations), [8.12](8.12-audit-logs.md) |
| Which surface is even worth opening for this symptom? | The narrowing procedure | [8.1](8.1-diagnostic-method.md) |

Two distinctions in that table are commonly confused. **Result and status logs are separate streams answering separate questions** ([8.2.4](#824-osquery-result-and-status-logs)). And **Orbit's log and osquery's status log are separate files**: Orbit is the supervising agent, osquery is the process it supervises. An enrollment failure is Orbit's. A table that returns nothing is osquery's.

## 8.2.2 fleetd (Orbit) stdout and stderr

fleetd writes Orbit's and osqueryd's combined stdout/stderr per platform:

| Platform | Path | Rotated? |
|---|---|---|
| macOS | `/var/log/orbit/orbit.stdout.log` and `/var/log/orbit/orbit.stderr.log` | No |
| Windows | `C:\Windows\system32\config\systemprofile\AppData\Local\FleetDM\Orbit\Logs\orbit-osquery.log` | Yes |
| Linux | syslog: `/var/log/syslog` (Debian/Ubuntu), `/var/log/messages` (RHEL/CentOS), or journald, systemd's own log store, read with `journalctl -u orbit` | By the OS log system |

Fleet documents these paths at fleetdm.com/guides/fleet-troubleshooting-for-it-admins. The two macOS files are the standard-output and standard-error redirects written into Orbit's LaunchDaemon plist at package time, so every macOS host uses them.

**Reading them:**

```sh
# macOS: most failures land in stderr, not stdout
sudo tail -f /var/log/orbit/orbit.stderr.log

# Linux, systemd
sudo journalctl -u orbit -f
sudo journalctl -u orbit --since "30 min ago" --no-pager

# Linux, syslog file
sudo grep -i orbit /var/log/syslog | tail -n 200
```

```powershell
# Windows
Get-Content -Wait -Tail 200 'C:\Windows\system32\config\systemprofile\AppData\Local\FleetDM\Orbit\Logs\orbit-osquery.log'
```

**Rotation is Windows-only.** Windows is the one platform whose installer hands Orbit a `--log-file`, aimed at the path in the table above. Given a `--log-file`, Orbit rotates that file at 25 MB, keeping 3 backups for 28 days. The macOS files are launchd redirects with no Fleet-managed rotation and no size cap, so on a long-lived host with debug enabled they can consume substantial disk. Truncate rather than delete when you need the space back, because Orbit keeps writing to the unlinked inode until it restarts.

**Collecting them from a macOS host without shell access.** Fleet ships a library script named "Collect fleetd logs" that copies the two most useful files to a shared folder the end user can reach:

```sh
cp /var/log/orbit/orbit.stderr.log ~/Library/Logs/Fleet/fleet-desktop.log /Users/Shared
```

Run it as a Fleet script, then have the user retrieve the files from `/Users/Shared`. **Expect the Desktop log to be missing.** Fleet scripts run as root, and `~` in a root context is not the logged-in user's home directory, so the second path resolves somewhere that has no Desktop log in it. The Orbit stderr log is absolute and does arrive. To get the Desktop log, name the user's home directory explicitly or have the user fetch it themselves.

## 8.2.3 Windows: the osquery event log channel

The Windows installer also registers an Event Tracing for Windows (ETW) provider named `FleetDM` publishing to an Event Log channel named `osquery`, with severity-mapped events (debug, info, warning, error, fatal).

```powershell
Get-WinEvent -LogName 'osquery' -MaxEvents 100 | Format-List TimeCreated, LevelDisplayName, Message
```

osqueryd writes to that channel when its own `--logger_plugin` list includes `windows_event_log`. fleetd's default list is `tls,filesystem` ([8.2.4](#824-osquery-result-and-status-logs)), so on a stock install the channel is registered and empty. Undocumented.

## 8.2.4 osquery result and status logs

**They answer different questions.**

| Stream | Contains | Open it when |
|---|---|---|
| **Result** | Rows produced by scheduled queries. Differential by default (added/removed rows), or snapshot if the query is configured that way. | You want to know *what the query found*, or whether it produced anything at all. |
| **Status** | osquery's own diagnostics: INFO/WARNING/ERROR lines, flag parsing, table errors, watchdog kills, scheduled query performance. | You want to know *whether osquery is healthy* and why a query returned nothing. |

"Scheduled query returns no rows" is a status-log question first, result-log question second. A watchdog kill or a denied table shows up in status, never in result.

**On the host.** fleetd starts osqueryd with `--logger_plugin=tls,filesystem` and `--logger_path=<root-dir>/osquery_log`. Both destinations are active on a default install: logs go to Fleet over TLS **and** a copy lands on disk.

| Platform | Directory |
|---|---|
| macOS | `/opt/orbit/osquery_log` |
| Linux | `/opt/orbit/osquery_log` |
| Windows | `C:\Program Files\Orbit\osquery_log` |

Inside that directory osquery writes `osqueryd.results.log` and `osqueryd.INFO` / `osqueryd.WARNING` / `osqueryd.ERROR` per osquery's own filesystem logger conventions. Fleet's docs name the directory rather than the filenames, so `ls` it rather than assuming a name.

> Fleet's troubleshooting guide (fleetdm.com/guides/fleet-troubleshooting-for-it-admins) phrases this as "if the `logger_path` agent configuration is set to `filesystem`". Read that as `logger_plugin`. `logger_path` is the directory, `logger_plugin` is the list of destinations, and fleetd sets both out of the box. **The on-disk copy is there before you change any setting.**

**Changing it.** `logger_plugin` and `logger_path` are osquery command-line flags, so they go in `command_line_flags` in agent options and take effect on the next fleetd restart:

```yaml
command_line_flags:
  logger_path: /var/log/osquery
```

`command_line_flags` set to `{}` or `null` behaves differently from omitting the key. Omitting it leaves each host's existing flags alone. `{}` empties every host's `osquery.flags` file and restarts osquery without them (fleetdm.com/docs/configuration/agent-configuration).

**On the server.** Everything osquery ships over TLS lands in whichever plugin `osquery_result_log_plugin` and `osquery_status_log_plugin` name. See [8.2.11](#8211-server-side-log-destinations).

## 8.2.5 Fleet Desktop

One file per user, in the user's log directory, named `fleet-desktop.log`:

| Platform | Directory |
|---|---|
| macOS | `$HOME/Library/Logs/Fleet` |
| Windows | `%LocalAppData%/Fleet` |
| Linux | `$XDG_STATE_HOME/Fleet`, falling back to `$HOME/.local/state/Fleet` |

Fleet documents these directories at fleetdm.com/guides/fleet-troubleshooting-for-it-admins.

Rotation is at 25 MB, 3 backups, 28 days. A sibling file `fleet-desktop.err` in the same directory catches raw stderr, including Go panics, and it is **truncated on every Desktop start**. When you are chasing a Desktop crash, copy `fleet-desktop.err` off the host before restarting anything. The `.err` file is undocumented.

Fleet Desktop runs in the logged-in user's session, so the file is per user. On a shared or multi-user Mac, check every home directory on the machine.

## 8.2.6 Reading fleetd's own logs without shell access

fleetd exposes its own log ring buffer as an osquery table, so you can read Orbit's logs over a live report.

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error', 'warn')
ORDER BY time DESC
LIMIT 100;
```

Columns: `time`, `level`, `payload`, `message`, `error`. Orbit registers the table through its own osquery extension ([8.2.7](#827-the-rest-of-the-orbit-root-directory)). Undocumented.

Constraints that matter:

| Property | Value |
|---|---|
| Storage | In memory, in the Orbit process |
| Capacity | 10,000 most recent entries, oldest evicted |
| Survives Orbit restart | **No.** The buffer is empty after a restart |
| Time format | UTC, `YYYY-MM-DD HH:MM:SS.fffffffff`, parseable by SQLite date functions |

Reach for this when the host is remote, the user is not technical, and you need Orbit's view right now. A crash loop is the one case it cannot cover, because every restart empties the buffer. Get the file instead ([8.2.2](#822-fleetd-orbit-stdout-and-stderr)).

## 8.2.7 The rest of the Orbit root directory

Orbit's root directory is `/opt/orbit` on macOS and Linux, `C:\Program Files\Orbit` on Windows. `/var/lib/orbit` appears as a symlink to it only on packages that bundled an Orbit older than `0.0.11`, so on anything recent the two paths are not interchangeable and looking in `/var/lib/orbit` on a modern host finds nothing. Orbit separately keeps working when its own executable genuinely lives below `/var/lib/orbit`, which is how the hosts installed before the default moved carry on. The files below answer identity and state questions faster than any log does.

| Path (relative to the Orbit root) | What it is | What its absence or contents tell you |
|---|---|---|
| `identifier` | Fleet Desktop auth token | Present means Desktop has a token. Rotated by Orbit even when Desktop is disabled. |
| `secret.txt` | An enroll secret on disk. Usually the one fleetd was packaged with, though a `--use-system-configuration` host writes the same file at runtime from its configuration profile, so presence does not identify the package type. **macOS and Windows only**; the Linux packages put the secret in `/etc/default/orbit` as `ORBIT_ENROLL_SECRET` and write no such file | **Read its absence carefully, because on its own it is not a finding.** macOS has two cases and they point opposite ways. With an ordinary package, Orbit moves the packaged secret into the Keychain on first launch and deletes the file, so a healthy Mac has none. A `--use-system-configuration` package ships without one and then **writes** `secret.txt` and `fleet_url.txt` once the configuration profile arrives, so absence there means the profile has not landed yet rather than that the package is wrong. On Linux its absence means nothing at all. |
| `secret-orbit-node-key.txt` | Orbit's node key, issued at orbit-enroll | Its absence is **consistent with** the host never having completed orbit enrollment, and with Orbit having cleared it deliberately: on macOS, Orbit deletes this file, the Desktop identifier, the osquery database and `hardware-uuid.txt` when it finds the agent directory on different hardware ([8.4](8.4-host-side-investigation.md), [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). Read it as evidence rather than as proof. |
| `osquery.db` | osquery's local store, an embedded RocksDB database: differential state, event buffers, query results pending upload | Deleting it forces a full re-baseline and makes every differential query re-report everything once. |
| `osquery.pid` | PID of the running osqueryd | Stale file with no matching process means osqueryd died without cleanup. |
| `certs.pem` | The curl-derived public CA bundle embedded in `fleetctl` and written at package time. Passed to osquery as `--tls_server_certs`. | `orbit shell` hard-fails without it. Fleet documents the bundle at fleetdm.com/guides/certificates-in-fleetd. |
| `fleet.pem` | Root CA for the connection to the Fleet server, when packaged with `--fleet-certificate` | Referenced by `ORBIT_FLEET_CERTIFICATE`, which lives in the launchd plist on macOS and in `/etc/default/orbit` on Linux. Same variable, different file, so check the right one for the platform. |
| `update.pem` | Root CA for Fleet's update server, a signed repository built on The Update Framework (TUF) | Referenced by `ORBIT_UPDATE_TLS_CERTIFICATE`. |
| `fleet_client.crt` / `fleet_client.key` | mTLS client cert and key for the Fleet server | Present only on mTLS deployments. |
| `update_client.crt` / `update_client.key` | mTLS client cert and key for the update server | Same. |
| `hardware-uuid.txt` | Last-seen hardware UUID | **macOS only.** Writing this file, reading it back and comparing it against the live UUID all sit inside a `darwin` branch, so it does not exist on Windows or Linux and its absence there is not a finding. Where it does exist, a mismatch is what triggers Orbit to clear its enrollment state and restart ([8.4](8.4-host-side-investigation.md), [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). |
| `fleet_url.txt` | Fleet URL read from an Apple config profile | Only on `--use-system-configuration` packages. |
| `server-overrides.json` | Update-channel overrides the server pushed down, plus the last-known-good osquery and Desktop paths | Narrower than it sounds. It is not a dump of the host's configuration; it answers which channels this host was told to use. |
| `mdm_migration.txt` | Marker that the host is partway through an MDM migration | Present means a migration started and did not finish. |
| `setup_experience.json` | Setup experience completion marker. The web setup experience path runs on Linux **and** Windows at this release | |
| `host_identity.crt` / `host_identity_tpm.pem` | HTTP message signature cert and TPM-backed key | Only when host identity signing is in use. |
| `bin/orbit/<os>/<channel>/orbit` | The Orbit binary for the configured channel | `bin/orbit/orbit` is a symlink to the active one; `/usr/local/bin/orbit` symlinks to that. |
| `bin/osqueryd/<platform>/<channel>/<file>` | The osqueryd download for the configured channel. **Both the platform token and the filename vary**, and the generic form exists on no host: Linux `linux` or `linux-arm64` with `osqueryd`, Windows `windows` or `windows-arm64` with `osqueryd.exe`, macOS `macos-app` with `osqueryd.app.tar.gz` and the extracted executable at `osquery.app/Contents/MacOS/osqueryd` beside it | Confirms which channel and which architecture actually got installed, versus what agent options say. |
| `bin/desktop/…` | The Fleet Desktop binary | Absent means the package was built without Desktop. |
| `osquery_log/` | osquery result and status logs | [8.2.4](#824-osquery-result-and-status-logs) |
| `.inband_upgrade` | Transient marker during an in-band package upgrade, **macOS only**. The Linux packages detect the same case from the `INSTALLER_PATH` environment variable and write no marker file | Removed by the postinstall script. Lingering means a macOS upgrade was interrupted; its absence on Linux means nothing. |
| `osquery.flags` | The flag file Orbit reconciles from `command_line_flags` in agent options | Packages create it empty, and setting `command_line_flags` to `{}` or `null` empties it again, so **an empty file is the normal state and proves nothing**. Read the flags actually in effect instead ([8.4.6](8.4-host-side-investigation.md#846-osquery-introspection-tables)). |
| `extensions.load` | osquery's `--extensions_autoload` list | Orbit passes the flag only when this file exists and is non-empty. |
| `orbit-osquery.em` | Unix socket for Orbit's osquery extension. On Windows it is the named pipe `\\.\pipe\orbit-osquery-extension` instead. | Missing or unconnectable means `orbit_info`, `fleetd_logs`, and the other Fleet-added tables return nothing. |
| `staging/` | Download staging area for the TUF updater | Contents left behind point at an update that did not finish extracting. |
| `shell/` | A second, separate osquery data directory used only by `orbit shell` | Why the shell never contends with the service for the RocksDB lock ([8.4.7](8.4-host-side-investigation.md#847-orbit-shell-the-local-osquery-shell)). |

Two of those `.pem` names get swapped for each other, and for a third that does not exist. `certs.pem` is the public CA bundle osquery uses for TLS. `fleet.pem` is the custom Fleet-server CA, written by packages built with `--fleet-certificate`. **There is no `cert.pem`.**

Useful one-liners:

```sh
# What identity does this host have?
sudo ls -la /opt/orbit
sudo test -s /opt/orbit/secret-orbit-node-key.txt && echo "orbit-enrolled"

# Which osqueryd is actually installed? The binary is nested per platform and
# channel, so discover the path rather than assuming it.
sudo find /opt/orbit/bin/osqueryd -type f -name osqueryd -perm -u+x
# macOS lands at bin/osqueryd/macos-app/<channel>/osquery.app/Contents/MacOS/osqueryd

ps -ef | grep -E 'orbit|osqueryd' | grep -v grep
```

On Windows the equivalents live under `C:\Program Files\Orbit\bin\` and end in `.exe`.

## 8.2.8 macOS MDM client logs, by live report

macOS writes MDM client activity to the unified log, the system-wide log store behind Console and `log show`, under the `mdmclient` process. A live report against the `unified_log` table pulls it remotely, with no shell access on the device. Bound the time window. Unbounded, the query is slow and the result is enormous.

```sql
SELECT
  timestamp,
  datetime(timestamp, 'unixepoch') AS event_time,
  process,
  subsystem,
  category,
  level,
  message
FROM unified_log
WHERE timestamp > (SELECT unix_time - 3600 FROM time)
  AND process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
```

Fleet publishes this query at fleetdm.com/guides/fleet-troubleshooting-for-it-admins.

`(SELECT unix_time - 3600 FROM time)` is the last hour. Change the constant to move the window: `1800` for 30 minutes, `86400` for a day. Widen carefully. The unified log on a busy Mac produces a lot of rows, and a live report result has to fit through the live report path.

Run it from the CLI when you want the whole result in a file rather than in a browser:

```sh
fleetctl report --hosts "<hostname>" --exit --timeout 2m --query "
SELECT datetime(timestamp,'unixepoch') AS event_time, level, category, message
FROM unified_log
WHERE timestamp > (SELECT unix_time - 3600 FROM time)
  AND process = 'mdmclient' AND subsystem = 'com.apple.ManagedClient'
" > mdmclient.json
```

Interpreting what comes back is [8.8](8.8-apple-mdm-diagnostics.md). Getting the bytes is this section's job.

Locally on the Mac, the same data without osquery:

```sh
sudo log show --predicate 'process == "mdmclient"' --last 1h --info --debug
sudo log stream --predicate 'subsystem == "com.apple.ManagedClient"' --level debug
```

## 8.2.9 iOS/iPadOS sysdiagnose

iOS and iPadOS run no agent, so every log pull goes through the device owner. They generate a sysdiagnose, Apple's on-demand diagnostic archive, and send it to you. End to end:

1. Hold **Power** plus **Volume Up** and **Volume Down** together for about one second. An iPhone vibrates once and takes a screenshot. An iPad takes a screenshot.
2. Wait a few minutes. The archive is generated in the background and is not available immediately.
3. On the device: **Settings > Privacy & Security > Analytics & Improvements > Analytics Data**.
4. Search for `sysdiag`. Tap the matching entry.
5. Share the `.tar.gz` file (AirDrop, Files, mail, whatever your policy allows).
6. On a Mac, expand the archive and find `system_logs.logarchive`.
7. Open `system_logs.logarchive` in **Console**.
8. Filter for `mdmclient`.

Fleet documents this procedure at fleetdm.com/guides/fleet-troubleshooting-for-it-admins.

From the command line instead of Console, once you have the archive:

```sh
tar -xzf sysdiagnose_*.tar.gz
log show --archive ./sysdiagnose_*/system_logs.logarchive \
  --predicate 'process == "mdmclient"' --info --debug
```

Ask for the sysdiagnose **immediately after** reproducing the failure. The archive covers a bounded recent window, and on a busy device the interesting part may already have aged out.

## 8.2.10 Raising verbosity, and putting it back

Five levers. Each one has an off switch, and leaving them on costs disk.

| Lever | Scope | Takes effect | Turn it off by |
|---|---|---|---|
| `fleetctl package --debug` | Every host installed from that package | At install | Rebuild the package without `--debug` and reinstall, or use one of the runtime toggles below |
| `toggle-fleetd-debug.sh` (macOS) | One host | ~15 s later, after Orbit restarts | Run the script again, or `./toggle-fleetd-debug.sh disable` |
| `toggle-fleetd-debug.ps1` (Windows) | One host | Immediately, service restarts | Run the script again |
| `ORBIT_DEBUG=true` in `/etc/default/orbit` (Linux) | One host | On `systemctl restart orbit` | Remove the line, restart |
| `command_line_flags: {verbose: true}` in agent options | Team, or global | Next fleetd restart | Set it back to `false` |

### `fleetctl package --debug`

```sh
fleetctl package --type=pkg --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" --debug
```

Bakes debug on into the installer. On macOS that becomes `ORBIT_DEBUG` in the launchd plist, on Windows a `--debug` argument in the service `ImagePath`, and on Linux `ORBIT_DEBUG=true` in `/etc/default/orbit`. Fleet documents the flag at fleetdm.com/guides/fleet-troubleshooting-for-it-admins.

### macOS: `toggle-fleetd-debug.sh`

Fleet publishes it in its repository at `docs/solutions/macos/scripts/toggle-fleetd-debug.sh` (github.com/fleetdm/fleet/blob/fleet-v4.90.1/docs/solutions/macos/scripts/toggle-fleetd-debug.sh). It accepts `enable`, `disable`, or nothing, which toggles.

> ### ⚠️ At 4.90.0 this script cannot turn debug on for a stock package
>
> The LaunchDaemon plist only carries an `ORBIT_DEBUG` key when the package was built with `--debug`. The script reads that key and writes it back with `PlistBuddy set`, which fails when the key is not there to set. So on an ordinary package, which is exactly the case where you need a runtime toggle, the script has nothing to flip.
>
> Add the key when it is missing, and set it when it is present:
>
> ```sh
> plist=/Library/LaunchDaemons/com.fleetdm.orbit.plist
> sudo /usr/libexec/PlistBuddy -c 'add EnvironmentVariables:ORBIT_DEBUG string true' "$plist" \
>   || sudo /usr/libexec/PlistBuddy -c 'set EnvironmentVariables:ORBIT_DEBUG true' "$plist"
> sudo launchctl bootout system/com.fleetdm.orbit
> sudo launchctl bootstrap system "$plist"
> ```
>
> To turn it off, set the value to `false` rather than deleting the key, so the published script has something to read next time.

What it does, in order:

1. Reads `EnvironmentVariables:ORBIT_DEBUG` out of `/Library/LaunchDaemons/com.fleetdm.orbit.plist` with `PlistBuddy`.
2. If the current state already matches the target, prints and exits.
3. Otherwise forks a detached background job and returns immediately, so the parent script exits cleanly.
4. The background job **sleeps 15 seconds first**, and that delay is load-bearing. It lets the script response reach Fleet, so Fleet records the run as complete before Orbit, the process running the script, is killed.
5. Sets `ORBIT_DEBUG` in the plist.
6. `launchctl bootout system/com.fleetdm.orbit`, waits in a `pgrep orbit` loop until the process is gone, then `launchctl bootstrap system <plist>`.

The background job's own output goes to `/tmp/orbit_debug_script_logs.txt`. When the toggle looks like it did nothing, read that file first.

The manual equivalent, if you have shell:

```sh
plist=/Library/LaunchDaemons/com.fleetdm.orbit.plist

# Read it. On a stock package this prints an error, because the key is absent.
sudo /usr/libexec/PlistBuddy -c 'print EnvironmentVariables:ORBIT_DEBUG' "$plist"

# Add or set, in that order, so it works whether or not the key exists.
sudo /usr/libexec/PlistBuddy -c 'add EnvironmentVariables:ORBIT_DEBUG string true' "$plist" \
  || sudo /usr/libexec/PlistBuddy -c 'set EnvironmentVariables:ORBIT_DEBUG true' "$plist"

sudo launchctl bootout system/com.fleetdm.orbit
sudo launchctl bootstrap system "$plist"
```

`set` alone is what the published script does, and it is why that script cannot turn debug on for a package built without `--debug`.

### Windows: `toggle-fleetd-debug.ps1`

`docs/solutions/windows/scripts/toggle-fleetd-debug.ps1`, in the same repository directory. It edits the service's `ImagePath` rather than an environment variable:

1. Reads `ImagePath` from `HKLM:\SYSTEM\CurrentControlSet\Services\Fleet osquery`.
2. Adds ` --debug` if absent, strips it if present.
3. Writes it back as `ExpandString`.
4. `Restart-Service -Name "Fleet osquery" -Force`.
5. Prints the log path.

The service name is `Fleet osquery`. Where the macOS script waits, this one restarts the service inline with no delay, so run it as a script from Fleet only if you can tolerate losing the script result when Orbit dies mid-run.

Check the current state without changing it:

```powershell
(Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Services\Fleet osquery' -Name ImagePath).ImagePath
```

### Linux

Linux has no supplied script. Orbit's systemd unit carries `EnvironmentFile=/etc/default/orbit`, which makes the equivalent two commands and their reverse. **A package built with `--debug` already bakes `ORBIT_DEBUG=true` into that file**, the same way the macOS launchd plist can carry the key from build time (above), so deleting every `ORBIT_DEBUG=` line on the way back down silently discards that baked-in value instead of restoring it. Capture whatever line was already there first, then restore exactly that on the way off:

```sh
prior=$(grep '^ORBIT_DEBUG=' /etc/default/orbit || true)
echo 'ORBIT_DEBUG=true' | sudo tee -a /etc/default/orbit
sudo systemctl restart orbit.service
# off again: restore the prior line instead of assuming there wasn't one
sudo sed -i '/^ORBIT_DEBUG=/d' /etc/default/orbit
[ -n "$prior" ] && echo "$prior" | sudo tee -a /etc/default/orbit
sudo systemctl restart orbit.service
```

Undocumented.

### osquery `--verbose`

Separate lever, separate stream. `--verbose` turns up osqueryd's status log, not Orbit's. Set it fleet-wide or per team through agent options:

```yaml
command_line_flags:
  verbose: true
```

`command_line_flags` apply after fleetd restarts (fleetdm.com/docs/configuration/agent-configuration). To test on one host without touching agent options, use the bundled shell:

```sh
sudo orbit shell -- --verbose
```

That loads a standalone osquery with a default config rather than the config Fleet serves. What it proves is osquery behavior. Fleet's configuration of osquery stays a separate question.

### Turning debug on for hosts as they enroll

Fleet's agent configuration reference describes an `orbit` block with several debug controls. **At Fleet 4.90.0 only one of them exists**, and the distinction matters because the others appear in the documentation as though they were available.

What works is `debug_logging_on_enroll_duration`, which stamps every host enrolling under that scope with a debug window measured in seconds, up to a maximum of `86400`, which is 24 hours. It is the whole of the `orbit` options schema at this release.

```yaml
agent_options:
  orbit:
    debug_logging_on_enroll_duration: 3600
```

**What does not work at this release**, checked against the server rather than the documentation: a standing `orbit.debug_logging` field, which is not part of the schema and will not be accepted, and a per-host override endpoint at `POST /api/v1/fleet/hosts/:id/debug-logging`, which is not a registered route. Fleet's reference marks this area "Coming soon". Use the per-platform toggles above for a host that is already enrolled.

That option is the only server-controlled window here, and its boundary is precise: Fleet stamps the deadline **after** Orbit enrollment has succeeded, immediately before handing back the node key. So it cannot capture a failing enrollment, which is the thing people reach for it to do. Use it for what happens *after* a host is in: setup experience, the first configuration fetches, early software and script work. When the enrollment request itself is failing, install a package built with `--debug` instead.

The two levers also differ in what they turn on. The enrollment window raises Orbit's own logging and merges `verbose=true` into the osquery flags. A package built with `--debug` additionally passes `--tls_dump`, which is what you want when the question is what is on the wire.

The window is not fire and forget: enrolling under that scope stamps the host with a deadline, in `hosts.orbit_debug_until`, and the field comes back on the host object as `orbit_debug_until`. That is the one debug lever on this page you can confirm from the server rather than by going to the device, and it is worth checking before you conclude a host never took the setting.

### Turning it back off matters

Debug on macOS writes to an unrotated file. A host left in debug for a month with `--tls_dump` on can consume substantial disk. Make the "off" run part of the same change ticket as the "on" run.

## 8.2.11 Server-side log destinations

### Three plugin-routed streams

Fleet routes three unrelated streams through destination plugins. Each has its own plugin setting, and each can land somewhere different from the other two. Fleet's own operational log is a fourth surface with no plugin setting, covered in [8.3](8.3-server-logs.md).

| Stream | Setting | Env var | Default |
|---|---|---|---|
| Scheduled query **results** | `osquery_result_log_plugin` | `FLEET_OSQUERY_RESULT_LOG_PLUGIN` | `filesystem` |
| osquery **status** logs | `osquery_status_log_plugin` | `FLEET_OSQUERY_STATUS_LOG_PLUGIN` | `filesystem` |
| Fleet **audit** logs (Premium) | `activity_audit_log_plugin`, gated by `activity_enable_audit_log` | `FLEET_ACTIVITY_AUDIT_LOG_PLUGIN`, `FLEET_ACTIVITY_ENABLE_AUDIT_LOG` | `filesystem`, audit disabled |

All three settings are in Fleet's server configuration reference (fleetdm.com/docs/configuration/fleet-server-configuration). The audit stream is the only one of the three a cron carries: results and status logs are written in the request that delivered them, while audit records are drained to their destination by the `activities_streaming` schedule every five minutes. So an audit event missing from the destination is not late until five minutes have passed, and you can force the drain rather than wait, with `fleetctl trigger --name=activities_streaming` and the caveat in [8.1](8.1-diagnostic-method.md#817-force-the-stage-then-verify-it-ran) about trigger reporting. Audit content and schema are [8.12](8.12-audit-logs.md).

The audit logger is also built only on a Premium licence. On a Free licence, `activity_enable_audit_log` is accepted and nothing is written, with no error at startup.

### Supported destinations

Ten destinations, and the plugin dispatch accepts any of them for any of the three streams: `filesystem`, `webhook`, `firehose`, `kinesis`, `lambda`, `pubsub`, `stdout`, `kafkarest`, `nats`, `splunk`. **Accepted by the dispatch is not the same as usable**, and `webhook` for the audit stream is the case where those come apart, below. An unrecognised value is a startup failure naming the stream, not a silent fallback to `filesystem`. An **empty** value is a fallback to `filesystem`, and Fleet says so in a startup line.

| Plugin | Destination | Flag namespace | Size behavior at the boundary |
|---|---|---|---|
| `filesystem` | Local disk on the Fleet server | `filesystem` | Rotation off by default. See below. |
| `webhook` | HTTP POST of a batch to a configured URL | `webhook` | Per-stream URLs, and only two of them exist. See the trap below |
| `firehose` | Amazon Kinesis Data Firehose | `firehose` | Records over **1 MB** are **dropped**, with a notice in the Fleet server log |
| `kinesis` | Amazon Kinesis Data Streams | `kinesis` | Records over **1 MB** are **dropped**, with a notice in the Fleet server log |
| `lambda` | AWS Lambda | `lambda` | Over **6 MB** **dropped** with a notice. Invoked **once per log line**, synchronously |
| `pubsub` | Google Cloud Pub/Sub | `pubsub` | Messages over **10 MB** are skipped with a notice, and the skip is not graceful. See below |
| `kafkarest` | Apache Kafka via the Confluent REST proxy | `kafka` | Requires the REST proxy in front of Kafka |
| `nats` | NATS | `nats` | Absent from Fleet's log destinations guide, listed as a valid option in the server configuration reference |
| `splunk` | Splunk HTTP Event Collector (HEC) | `splunk` | Events over **1 MB** **dropped** with a notice, and batches flushed at 1 MB. Retries HTTP 503 and 429, up to 8 times, doubling from 200 ms |
| `stdout` | Fleet server stdout | `stdout` | For debugging or a log-forwarding sidecar |

Destination behavior is documented at fleetdm.com/guides/log-destinations and fleetdm.com/docs/configuration/fleet-server-configuration.

### Two traps in how the three streams are wired

**`webhook` has a URL for results and a URL for status, and none for audit.** The settings are `webhook_result_url` and `webhook_status_url`. Point `activity_audit_log_plugin` at `webhook` and one of two things happens, neither of them what you asked for. With no result URL configured, Fleet refuses to start, and the error names audit while the missing setting is a webhook URL that has no audit spelling: there is no `webhook_audit_url` to add. With a result URL configured, Fleet starts and sends your audit stream to the **result** webhook, because the audit configuration never sets a URL of its own and inherits the one left behind by the result stream. Whether that means audit records arrive mixed in with query results depends on whether results are themselves routed to `webhook`; if they are not, the audit stream arrives alone at a URL you configured for something else. Use a different plugin for audit.

**An oversized Pub/Sub message does not drop cleanly.** The writer allocates one result slot per log record, skips the oversized one leaving its slot empty, and then waits on **every** slot including the empty one. So a single record over the limit takes the whole batch's write down with it rather than costing you that one record. Treat `dropping log over 10MB PubSub limit` in the server log as a batch-level event, not a record-level one, and if you are routing results to Pub/Sub keep an eye on the largest rows a scheduled report can produce.

**Splunk is configured once for the whole server.** `splunk_url`, `splunk_token`, `splunk_index`, `splunk_source` and `splunk_source_type` have no per-stream variants, so results, status and audit routed to Splunk all arrive at the same index under the same source and sourcetype. Seven destinations do take a per-stream target: a stream name for Firehose and Kinesis, a function for Lambda, a topic for Pub/Sub and Kafka, a subject for NATS, a file for `filesystem`. The exceptions are Splunk, `webhook`, whose two URLs cover results and status but not audit, and `stdout`, which has no target configuration at all. If you need the three streams separable in Splunk, separate them before Fleet, or send two of them somewhere else.

Snowflake is not a plugin. Sending to Snowflake means configuring `firehose` and then wiring Firehose into Snowpipe on the AWS side.

**The multi-node trap.** With `filesystem` or `stdout` on a load-balanced Fleet deployment, logs are **load-balanced across the nodes, not duplicated**. Any single node has a fraction of the stream. If your grep on one server comes back sparse, that is why, and it is the same trap that hits `fleetctl debug` on multi-node deployments ([8.5](8.5-fleetctl-debug.md)).

Splunk configured directly, as an example of the shape:

```yaml
osquery:
  status_log_plugin: splunk
  result_log_plugin: splunk
splunk:
  url: https://splunk.example.com:8088
  token: your-hec-token
  index: main
  source: fleet
  source_type: fleet:json
```

> **Log destination config is a self-hosted lever.** On managed cloud the change goes through Fleet.

### The `filesystem` plugin's own settings

| Setting | Env var | Default | Meaning |
|---|---|---|---|
| `filesystem_result_log_file` | `FLEET_FILESYSTEM_RESULT_LOG_FILE` | `/tmp/osquery_result` | Path for result logs |
| `filesystem_status_log_file` | `FLEET_FILESYSTEM_STATUS_LOG_FILE` | `/tmp/osquery_status` | Path for status logs |
| `filesystem_audit_log_file` | `FLEET_FILESYSTEM_AUDIT_LOG_FILE` | `/tmp/audit` | Path for audit logs |
| `filesystem_enable_log_rotation` | `FLEET_FILESYSTEM_ENABLE_LOG_ROTATION` | `false` | Master switch for rotation |
| `filesystem_enable_log_compression` | `FLEET_FILESYSTEM_ENABLE_LOG_COMPRESSION` | `false` | gzip the rotated files |
| `filesystem_max_size` | `FLEET_FILESYSTEM_MAX_SIZE` | `500` | Megabytes before rotating |
| `filesystem_max_age` | `FLEET_FILESYSTEM_MAX_AGE` | `28` | Days retained. `0` retains forever |
| `filesystem_max_backups` | `FLEET_FILESYSTEM_MAX_BACKUPS` | `3` | Old files retained. `0` retains all, though `max_age` may still delete them |

The rotation settings take effect when `filesystem_enable_log_rotation` is `true`, and it is `false` by default. The three default paths are built from the operating system's temporary directory, which on a Linux Fleet server means `/tmp`, and many distributions clear it on boot. A production deployment sets explicit paths:

```yaml
osquery:
  result_log_plugin: filesystem
  status_log_plugin: filesystem
filesystem:
  result_log_file: /var/log/osquery/result.log
  status_log_file: /var/log/osquery/status.log
  audit_log_file: /var/log/fleet/audit.log
  enable_log_rotation: true
  enable_log_compression: true
  max_size: 500
  max_age: 28
  max_backups: 3
```

### The Fleet server's own logs

A fourth stream, separate from the three above: the Fleet server's own operation, written to stderr.

| Setting | Env var | Default | Meaning |
|---|---|---|---|
| `logging_debug` | `FLEET_LOGGING_DEBUG` | `false` | Debug-level server logging |
| `logging_json` | `FLEET_LOGGING_JSON` | `false` | Emit JSON instead of logfmt |
| `logging_disable_banner` | `FLEET_LOGGING_DISABLE_BANNER` | `false` | Suppress the startup banner |
| `logging_error_retention_period` | `FLEET_LOGGING_ERROR_RETENTION_PERIOD` | `24h` | How long recorded errors live in Redis. `0` never expires, negative disables error storage |
| `logging_enable_topics` | `FLEET_LOGGING_ENABLE_TOPICS` | none | Comma-delimited topics to re-enable. Topics are on by default, so this changes nothing at this release. See [8.3](8.3-server-logs.md#832-the-settings) |
| `logging_disable_topics` | `FLEET_LOGGING_DISABLE_TOPICS` | none | Comma-delimited topics to suppress, for example `deprecated-field-names`. A topic in both lists is **disabled** |
| `logging_tracing_enabled` | `FLEET_LOGGING_TRACING_ENABLED` | `false` | Export traces to an OpenTelemetry collector over OTLP |
| `logging_otel_logs_enabled` | `FLEET_LOGGING_OTEL_LOGS_ENABLED` | `false` | Also export logs over OTLP. Requires `logging_tracing_enabled` |

OTLP destination and service name come from the standard OpenTelemetry SDK environment variables, most often `OTEL_EXPORTER_OTLP_ENDPOINT` and `OTEL_SERVICE_NAME` (defaults to `fleet`).

Reading the server's stderr is [8.3](8.3-server-logs.md).

**Fleet's recorded server errors live in Redis rather than in a file.** They carry a `logging_error_retention_period` TTL and are read with `fleetctl debug errors` ([8.5](8.5-fleetctl-debug.md)).

## 8.2.12 What survives, and for how long

| Surface | Persistence | Lifetime |
|---|---|---|
| macOS `orbit.stdout.log` / `orbit.stderr.log` | File | Until removed by hand, by an uninstall, or by something else you run. No Fleet-managed rotation, no cap |
| Windows `orbit-osquery.log` | File | 25 MB, 3 backups, 28 days |
| Linux Orbit output | syslog/journald | Whatever the OS log config says |
| osquery result/status logs on the host | Files in `osquery_log/` | osquery's own filesystem-logger rotation |
| `fleet-desktop.log` | File | 25 MB, 3 backups, 28 days |
| `fleet-desktop.err` | File | **Truncated on every Desktop start** |
| `fleetd_logs` table | Memory | 10,000 entries, lost on Orbit restart |
| `/opt/orbit/osquery.db` | RocksDB | Until deleted. Holds pending results across reboots |
| macOS `unified_log` | Ring buffer on the device | Hours to days, depending on volume |
| iOS/iPadOS sysdiagnose | Generated on demand | Bounded recent window |
| Server `filesystem` logs | Files | No rotation unless `filesystem_enable_log_rotation` is on |
| Server recorded errors | Redis | `logging_error_retention_period`, default 24h |
| External destinations | Whatever the destination retains | Depends on the stream. Fleet keeps no second server-side copy of results or status, but the host's own `osquery_log` copy is unaffected, and **audit activities stay in Fleet's activity store**: streaming marks the row streamed rather than removing it ([8.12](8.12-audit-logs.md)) |

Two consequences worth acting on. **The host holds pending osquery results in `osquery.db` across reboots**, so a host returning from a long offline period replays old results with their original timestamps ([8.1](8.1-diagnostic-method.md) uses this as the worked example). And **the ephemeral surfaces are gone after a restart**, so collect `fleetd_logs`, `fleet-desktop.err`, and the unified log *before* you restart anything to "see if that fixes it."
