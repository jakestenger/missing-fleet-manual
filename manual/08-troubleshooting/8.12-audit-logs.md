# Audit logs: who did what, when

Fleet's record of server-side actions. One row per action, in MySQL, readable in the UI and over the API, optionally streamed to an external destination. Fleet calls the rows **activities**; "audit log" is the name for the same rows once they leave Fleet.

## 8.12.1 The short answers

| Question | Answer |
|---|---|
| Where do the rows live | `activity_past` in MySQL, with a host join table `activity_host_past` |
| Is it on by default | The rows are always written. **Streaming** them out is off by default (`activity_enable_audit_log` defaults to `false`) |
| Is it Premium | Reading is free. External streaming is Fleet Premium |
| Retention | Unlimited until you enable `activity_expiry_settings.activity_expiry_enabled` |
| Does it cover host-side events | Server-side action only. Host-side history lives elsewhere: [8.12.6](#8126-the-limit-server-side-action-only) |

## 8.12.2 The table

`activity_past` holds the rows themselves:

| Column | Type | Meaning |
|---|---|---|
| `id` | `int unsigned` auto-inc | Row ID. Monotonic, and the pagination cursor the API uses |
| `created_at` | `timestamp(6)` | When the action happened. Microsecond precision. Default `CURRENT_TIMESTAMP(6)` |
| `user_id` | `int unsigned` nullable | FK to `users.id`, `ON DELETE SET NULL` |
| `user_name` | `varchar(255)` nullable | Actor name **snapshotted at write time** |
| `user_email` | `varchar(255)` NOT NULL, default `''` | Actor email, also snapshotted |
| `activity_type` | `varchar(255)` NOT NULL | The type string, e.g. `edited_policy` |
| `details` | `json` nullable | Type-specific payload. Shape differs per type |
| `streamed` | `tinyint(1)` NOT NULL default `0` | Whether the audit streamer has shipped this row |
| `fleet_initiated` | `tinyint(1)` NOT NULL default `0` | `1` when Fleet itself did it, not a user |
| `host_only` | `tinyint(1)` NOT NULL default `0` | `1` hides the row from the global feed |

`activity_host_past` is `(host_id, activity_id)`, primary key on both, with `ON DELETE CASCADE` from `activity_past`. That is the many-to-many link that makes a host's own activity list possible.

**The rename matters if you have saved SQL.** These two tables were `activities` and `host_activities` until a schema migration renamed them. The index names still carry the old spelling (`activities_created_at_idx`, `idx_activities_type_created`), and Fleet's REST API reference still offers to sort by "any column in the `activities` table" (fleetdm.com/docs/rest-api/rest-api). That reference text is stale. The table is `activity_past`.

### Two columns that will surprise you

**`user_name` and `user_email` are copies, not lookups.** Deleting a Fleet user nulls `user_id` but leaves the name and email text in place. The audit trail survives user deletion, which is the point. It also means the row shows the name the user had at the time, not the name they have now.

**`host_only = 1` rows are excluded from the global activity feed.** The query behind the global feed filters on `host_only = false`, and the flag is set at write time by the activity type itself, so certain types are written to the table, shown on the host's own page, and withheld from the global page by design. An empty result from the global endpoint is therefore not proof that nothing happened. Query the host endpoint, or the table with the host join, before you conclude the event was never recorded.

## 8.12.3 Entry shape

The API response and the streamed record are the same object:

| JSON field | Source | Notes |
|---|---|---|
| `id` | `activity_past.id` | Omitted when zero |
| `uuid` | `upcoming_activities.execution_id` | Populated for **upcoming** activities only, not past rows |
| `created_at` | `created_at` | |
| `type` | `activity_type` | |
| `actor_id` | `user_id` | Null for `fleet_initiated` rows |
| `actor_full_name` | joined `users.name` | |
| `actor_email` | joined `users.user_email` | |
| `actor_gravatar` | joined `users.gravatar_url` | |
| `actor_api_only` | joined `users.api_only` | Whether the actor is an API-only user |
| `fleet_initiated` | `fleet_initiated` | |
| `details` | `details` | Raw JSON, shape per type |

The `streamed` bookkeeping column stays inside Fleet and never appears in the output.

A real record:

```json
{
  "created_at": "2023-07-27T14:35:08Z",
  "id": 25,
  "actor_full_name": "Anna Chao",
  "actor_id": 3,
  "actor_gravatar": "",
  "actor_email": "",
  "type": "installed_software",
  "fleet_initiated": false,
  "details": {
    "status": "installed",
    "host_id": 1272,
    "host_display_name": "MacBook Pro",
    "policy_id": null,
    "policy_name": null,
    "install_uuid": "23c18ea1-8cd7-4af4-a1d8-f2666993a66b",
    "self_service": false,
    "software_title": "zoom.us.app",
    "software_package": "ZoomInstallerIT.pkg"
  }
}
```

The `details` object carries the useful content, and its shape is per-type. Fleet enumerates every field of every type in its audit-log reference, fleetdm.com/docs/contributing/audit-logs, which runs to some 80 KB of tables. That page is the authoritative payload reference. Do not guess a field name from a type name.

## 8.12.4 Activity types: the categories

Roughly 200 types exist, and Fleet's audit-log reference lists every one with its payload. For the shorter list of types your own deployment actually writes:

```sql
SELECT DISTINCT activity_type FROM activity_past ORDER BY activity_type;
```

### `fleet_initiated` separates people from automation

One `activity_type` covers both. An `installed_software` row with `fleet_initiated: false` and an `actor_id` is a person who clicked install. The same type with `fleet_initiated: true` and no actor is a policy automation, and its `details` object names the policy that fired. When the question is "who did this", read `fleet_initiated` before you name a person.

## 8.12.5 Reading it

### API

| Endpoint | Returns |
|---|---|
| `GET /api/v1/fleet/activities` | Global feed. `host_only = 1` rows are withheld |
| `GET /api/v1/fleet/hosts/:id/activities` | That host's past activities |
| `GET /api/v1/fleet/hosts/:id/activities/upcoming` | Queued activities for that host, still waiting to run |
| `DELETE /api/v1/fleet/hosts/:id/activities/upcoming/:activity_id` | Cancels a queued activity |
| `GET /api/v1/fleet/policies/:id/automation_activities` | Activities generated by one policy's automation |

All five are in Fleet's REST API reference at fleetdm.com/docs/rest-api/rest-api.

Query parameters on the global endpoint:

| Parameter | Use |
|---|---|
| `page`, `per_page` | Max `per_page` is 10,000, and **10,000 is also what you get when you send no pagination parameters at all.** Ask for a page size |
| `order_key`, `order_direction` | `asc` is the default direction. You almost always want `order_key=created_at&order_direction=desc` |
| `after` | Cursor. Requires `order_key`, uses that column |
| `query` | Free text over `actor_full_name` and `actor_email`. The `details` payload is out of its reach |
| `activity_type` | Exact type string |
| `start_created_at`, `end_created_at` | Time-window bounds. This is the parameter pair that makes incident correlation practical |

The window query, which is the one worth memorising:

```bash
fleetctl get api \
  '/api/v1/fleet/activities?order_key=created_at&order_direction=desc&start_created_at=2026-08-19T13:00:00Z&end_created_at=2026-08-19T15:00:00Z&per_page=500'
```

Or with plain `curl`:

```bash
curl -sH "Authorization: Bearer $FLEET_TOKEN" \
  "$FLEET_URL/api/v1/fleet/activities?order_key=created_at&order_direction=desc&start_created_at=2026-08-19T13:00:00Z&end_created_at=2026-08-19T15:00:00Z&per_page=500" \
  | jq -r '.activities[] | [.created_at, .type, (.actor_email // "fleet"), (.fleet_initiated|tostring)] | @tsv'
```

`fleetctl` reaches activities through `fleetctl get api`, as above. Through 4.90.0 it has no dedicated activities subcommand, so the API is the route.

### UI

Fleet's home page has an **Activity** section, and each host's page has its own activity feed. Both are volatile surfaces, and both render `details` as prose rather than raw JSON, so a field you came for may be summarised away. Read the payload over the API.

### MySQL

The global feed, last two hours, actor resolved:

```sql
SELECT ap.id,
       ap.created_at,
       ap.activity_type,
       ap.fleet_initiated,
       COALESCE(ap.user_email, '(none)') AS actor,
       ap.details
FROM   activity_past ap
WHERE  ap.host_only = 0
  AND  ap.created_at >= NOW() - INTERVAL 2 HOUR
ORDER  BY ap.created_at DESC;
```

Everything touching one host, including `host_only` rows the global feed hides:

```sql
SELECT ap.created_at, ap.activity_type, ap.user_email, ap.fleet_initiated, ap.details
FROM   activity_past ap
JOIN   activity_host_past ahp ON ahp.activity_id = ap.id
WHERE  ahp.host_id = 1272
ORDER  BY ap.created_at DESC
LIMIT  200;
```

What kinds of change happened in a window, ranked. Run this first when you do not yet know what you are looking for:

```sql
SELECT activity_type, COUNT(*) AS n, MIN(created_at) AS first, MAX(created_at) AS last
FROM   activity_past
WHERE  created_at BETWEEN '2026-08-19 13:00:00' AND '2026-08-19 15:00:00'
GROUP  BY activity_type
ORDER  BY n DESC;
```

Pull one field out of `details`, here the team on transfers:

```sql
SELECT created_at, user_email,
       details->>'$.team_name' AS team_name,
       JSON_LENGTH(details->'$.host_ids') AS host_count
FROM   activity_past
WHERE  activity_type = 'transferred_hosts'
  AND  created_at >= NOW() - INTERVAL 7 DAY
ORDER  BY created_at DESC;
```

Confirm `details` field names against Fleet's audit-log reference before you rely on a JSON path. The shapes are per-type, and MySQL enforces nothing beyond valid JSON.

Backlog check on streaming, which is also a rough health signal for the streamer:

```sql
SELECT streamed, COUNT(*), MIN(created_at), MAX(created_at)
FROM   activity_past
GROUP  BY streamed;
```

Other MySQL tables worth reading during an investigation are [8.6](8.6-server-state.md).

## 8.12.6 The limit: server-side action only

**The audit log has no host-side event history.** It records actions taken through Fleet's server. An event on the device itself, taken outside Fleet, leaves no row.

Every row in `activity_past` is written by the Fleet server at the moment it performs an action. The host writes nothing into the table, and no reconciliation pass records host state drifting away from what Fleet expects.

That boundary decides several common questions:

| You want to know | What the audit log holds | Where the answer is |
|---|---|---|
| How fleetd was removed from a device | An uninstall Fleet performed. A local `sudo` uninstall, an MDM removal outside Fleet, an imaging event, or another management tool taking the package off are all invisible to it | [8.4](8.4-host-side-investigation.md) for on-host state, [8.2](8.2-log-surfaces.md) for agent logs |
| Whether a user deleted a configuration profile locally | Fleet's own profile delivery and removal | [8.4](8.4-host-side-investigation.md), [8.8](8.8-apple-mdm-diagnostics.md) |
| Whether someone disabled FileVault on the machine | The Fleet setting change | [8.4](8.4-host-side-investigation.md) |
| Who ran a command on the host outside Fleet | `ran_script` rows for scripts Fleet dispatched | Host-side OS audit facilities, not Fleet |
| Whether the agent stopped running, and when | Nothing. There is no `agent_stopped` type | [8.4](8.4-host-side-investigation.md); host `seen_time` in [8.6](8.6-server-state.md) |

> [!internal] This is the shape of a real support case: a customer asked how the agent had been removed from a device, expecting the audit trail to name a person. There were no rows for that host at all, which is the correct behavior and not a finding. The answer had to come from the device: package receipts, launchd state, and the local installer/removal history. Set the expectation before running the query, because "the audit log is empty for this host" reads as suspicious to a customer when it is the tool's scope.

`mdm_unenrolled` comes closest to a host-initiated row. It records Fleet **observing** an unenrollment, so it carries the fact and the timing without naming who acted.

## 8.12.7 Diagnostic use: "what changed"

[8.1](8.1-diagnostic-method.md)'s intake asks what changed near the onset. The audit log answers exactly one slice of that: server-side configuration and action changes. It is the fastest slice to check, so check it first.

### Procedure

1. **Fix the onset time.** From the first bad result, the first failed check-in, the first alert. Get it to the minute if you can.
2. **Widen deliberately.** Query `onset - 2h` to `onset`. Two hours, not two days. Fleet's own cron and automation traffic will bury a single human change in a wide window.
3. **Aggregate before you read.** Run the `GROUP BY activity_type` query from [8.12.5](#8125-reading-it). You are looking for a type that is unusual for this deployment, not for a type with a high count.
4. **Split human from Fleet.** Filter `fleet_initiated = 0` for changes a person made, `fleet_initiated = 1` for changes automation made. The second set is the one people forget to check, and it is often the answer.
5. **Cross the boundary.** If the window shows nothing, the change was not made through Fleet's server. Go to [8.12.9](#8129-other-what-changed-sources).

### High-value types when correlating

| Symptom onset | Types to look for | Why |
|---|---|---|
| Broad, many hosts, all at once | `applied_spec_team`, `applied_spec_policy`, `applied_spec_saved_query`, `edited_agent_options`, `edited_enroll_secrets` | These are the GitOps apply footprint. A burst of `applied_spec_*` at one timestamp is a GitOps run |
| One team's hosts only | `applied_spec_team`, `transferred_hosts`, `edited_agent_options` | Team-scoped config, or hosts moved into a team whose config differs |
| Specific hosts, no pattern | `transferred_hosts` | Check whether the affected host IDs appear in a transfer's `details.host_ids` |
| Policy results flipped | `edited_policy`, `created_policy`, `deleted_policy`, `reset_policy` | An edited query changes pass/fail without anything on the host changing |
| Profiles reinstalling or churning | `edited_macos_profile`, `created_macos_profile`, `deleted_macos_profile`, `resent_configuration_profile_batch`, and the Windows/Android/declaration equivalents | A profile edit triggers redelivery to every matching host |
| Enrollment newly failing | `edited_enroll_secrets`, `disabled_windows_mdm`, `disabled_android_mdm`, `enabled_gitops_mode` | Rotated secrets and disabled MDM both present as enrollment failure |
| Encryption or key access questions | `enabled_macos_disk_encryption`, `disabled_macos_disk_encryption`, `read_host_disk_encryption_key` | The read type also answers the access question |
| Query load spike on hosts | `created_saved_query`, `edited_saved_query`, `live_query` | A newly scheduled expensive report, or someone running live reports at scale |
| Config changes stopped landing | `enabled_gitops_mode` | GitOps mode makes the UI and API read-only for the managed surface |

### Two traps

**Timezone.** `created_at` is stored as a MySQL `timestamp`, so what you read back depends on the session time zone. Pin it before comparing against anything:

```sql
SET time_zone = '+00:00';
```

The API returns RFC3339 with an explicit offset, which is one reason to prefer the API when you are correlating across tools.

**The audit log is not a state record.** An `edited_policy` row proves someone saved a change. It does not prove the change reached any host, and it does not carry the before/after values unless the type's `details` payload happens to include them. For whether it landed, go to the state tables in [8.6](8.6-server-state.md) or the host itself in [8.4](8.4-host-side-investigation.md).

## 8.12.8 Streaming it out

The audit log is one of Fleet's log streams, with its own destination plugin, separate from the osquery result and status streams and from the server's own output. Which stream is which is [8.3](8.3-server-logs.md); the full destination list is [8.2](8.2-log-surfaces.md).

### Config

From Fleet's server configuration reference, fleetdm.com/docs/configuration/fleet-server-configuration:

| Setting | Env var | Default | Effect |
|---|---|---|---|
| `activity_enable_audit_log` | `FLEET_ACTIVITY_ENABLE_AUDIT_LOG` | `false` | Master switch. Nothing streams until this is `true` |
| `activity_audit_log_plugin` | `FLEET_ACTIVITY_AUDIT_LOG_PLUGIN` | `filesystem` | Destination. No effect unless the switch above is on |
| `filesystem_audit_log_file` | `FLEET_FILESYSTEM_AUDIT_LOG_FILE` | `/tmp/audit` | Path, `filesystem` plugin only |
| `filesystem_enable_log_rotation` | `FLEET_FILESYSTEM_ENABLE_LOG_ROTATION` | `false` | Rotates at 500 MB or 28 days. Shared with the osquery result and status files |

YAML form:

```yaml
activity:
  enable_audit_log: true
  audit_log_plugin: firehose
```

**The default path is a trap.** `filesystem` is the default plugin and `/tmp/audit` is the default file. Turn on `activity_enable_audit_log` without setting a plugin and Fleet writes your audit trail to `/tmp` on each node, unrotated, where the OS or a container restart will eventually remove it. Set `filesystem_audit_log_file` explicitly or pick a real destination.

### Destinations that carry it

`filesystem`, `firehose`, `kinesis`, `lambda`, `pubsub`, `kafkarest`, `nats`, `splunk`, `stdout`. `stdout` needs no further configuration. Each of the others has its own flag namespace, and the configuration reference gates every one of those flags on `activity_audit_log_plugin` being set to that plugin **and** `activity_enable_audit_log` being `true`.

`webhook` appears as a destination in Fleet's log destinations guide (fleetdm.com/guides/log-destinations) and is absent from the `activity_audit_log_plugin` option list. Treat audit-over-webhook as unsupported.

### Mechanism

| Property | Value |
|---|---|
| Trigger | Cron schedule `activities_streaming`, interval **5 minutes** |
| Selection | Rows with `streamed = 0`, ordered by `id` ascending, cursor-paginated on `id` |
| Batch | 500 rows per fetch, looping until a fetch comes back short |
| Write granularity | **One row per write to the destination**, deliberately, so Fleet can tell which rows landed |
| Payload | The same JSON object the API returns, one object per row |
| Bookkeeping | `streamed` flips to `1` on the rows the destination accepted |
| On error | Stops at the first failed row, marks the ones before it, retries the rest on the next 5-minute tick |
| Licensing | Fleet Premium. Fleet builds the audit logger under a Premium license and skips it otherwise |

Consequences:

- **Up to 5 minutes of lag**, which the configuration reference states directly. Alerting built on the audit stream inherits that delay, so treat five minutes as the floor.
- **Backlog is visible in one column.** A growing count of `streamed = 0` rows means the destination is rejecting writes or the schedule is not running. Check the `cron_stats` row for `activities_streaming` in [8.6](8.6-server-state.md), and the server log for the `streamed events` message with its `count` attribute.
- **Enabling streaming backfills the whole table.** Every pre-existing row carries `streamed = 0`, so the first run after you flip the switch walks the entire history in 500-row batches. On a deployment with years behind it, that is a large one-time burst arriving at a destination sized for steady state. Size for the burst, or set an expiry window first and let it shrink the table.
- **One node streams per tick.** The schedule takes the usual Redis lock, so the work stays unduplicated across nodes. It also means a stuck node holds the schedule, the same failure mode as any other Fleet cron.

## 8.12.9 Other "what changed" sources

The audit log covers action taken through Fleet's server. Four other change surfaces sit outside `activity_past` entirely.

| Source | What it covers that the audit log does not | How to read it |
|---|---|---|
| GitOps repository history | The **content** of the change. The audit log records that `applied_spec_team` happened; the repo records what the YAML said before and after, who authored it, and which PR it came from | `git log`, `git diff` on the config repo. Correlate the CI run timestamp against the `applied_spec_*` timestamps |
| Fleet server version | Fleet ships roughly every three weeks. An upgrade changes behavior without producing any activity row | `GET /api/v1/fleet/version`; the startup banner in the server log ([8.3](8.3-server-logs.md)); `migration_status_tables` in MySQL for the migration floor. Compare the version you find against its release notes at github.com/fleetdm/fleet/releases |
| Agent version | fleetd and osquery version changes are per-host and are not activities | `hosts.osquery_version` and the fleetd version in host details ([8.6](8.6-server-state.md)) |
| Host OS updates | An OS minor version bump changes query results, profile behavior, and MDM behavior. Not an activity | `hosts.os_version` and `operating_systems` ([8.6](8.6-server-state.md)) |

`fleetctl debug errors` belongs to a different question. It records server faults rather than changes, and it stays silent on client 4xx errors ([8.3](8.3-server-logs.md), [8.5](8.5-fleetctl-debug.md)).

When the audit log window comes back empty, check the Fleet version and the agent version next. Those two account for most "nothing changed, but it broke" cases. The general method is [8.1](8.1-diagnostic-method.md).

## 8.12.10 Retention and volume

| Property | Value |
|---|---|
| Default retention | **Unlimited.** Rows accumulate for the life of the deployment until expiry is enabled |
| Expiry switch | `activity_expiry_settings.activity_expiry_enabled` |
| Expiry window | `activity_expiry_settings.activity_expiry_window`, in **days** |
| Cleanup job | `cleanup_activities`, inside the `cleanups_then_aggregation` schedule |
| Per-run delete cap | **5,000 rows**, a cap Fleet sizes as adequate for deployments generating about 120,000 activities per day |

Both expiry settings are in Fleet's YAML reference, fleetdm.com/docs/configuration/yaml-files. GitOps form:

```yaml
org_settings:
  activity_expiry_settings:
    activity_expiry_enabled: true
    activity_expiry_window: 30
```

Enabling expiry also enables live report cleanup against the same window. One switch, two effects.

**The delete cap is the operational catch.** The job removes at most 5,000 expired rows per run. Enable a 30-day window on a table holding millions of rows and it will drain at 5,000 per run rather than in one pass. Watch the count fall over days, not minutes:

```sql
SELECT COUNT(*) FROM activity_past WHERE created_at < NOW() - INTERVAL 30 DAY;
```

If that number is not decreasing, the `cleanups_then_aggregation` schedule is not running. `cron_stats` is [8.6](8.6-server-state.md).

**Expiry and streaming interact badly if you get the order wrong.** Deleting a row that still has `streamed = 0` loses it permanently. If you are enabling both, enable streaming and let the backlog drain before you enable expiry.

### Volume drivers

`fleet_initiated` rows dominate on most deployments: policy-triggered software installs, automation runs, and MDM lifecycle events all write rows without a human involved. Human activity is a small fraction. That matters for two things: sizing the destination, and reading a count. A spike in row volume is usually automation, not people.

`activity_past` carries seven secondary indexes, among them `idx_activities_type_created` on `(activity_type, created_at)`. Filter on those two columns and the query is indexed. Filter on `details` and MySQL scans the whole JSON column.

### `preserve_host_activities_on_reenrollment`

`activity_expiry_settings.preserve_host_activities_on_reenrollment` controls whether a managed host keeps its existing activities and MDM commands when it re-enrolls. The default depends on how the deployment came to exist: **`true` on installs upgraded from an earlier version**, preserving the older behavior, and **`false` on fresh installs**. Two Fleet deployments running the same version can differ here purely by age. Read the value before you conclude that a re-enrolled host has no history. Fleet's published configuration reference does not cover this setting; treat the documentation coverage as absent.

## 8.12.11 Compliance use

`activity_past` is the surface an auditor asks for when they want a record of privileged action in the device-management platform. The rows that usually matter are `read_host_disk_encryption_key`, `viewed_host_recovery_lock_password`, `read_managed_local_account`, `changed_user_global_role`, `changed_user_team_role`, `user_logged_in`, `user_failed_login`, and `wiped_host`.

Streaming to an external destination is the part that makes it hold up, because a row in Fleet's own MySQL is deletable by anyone with database access, and expiry will remove it on schedule. Fleet does not sign, hash-chain, or otherwise tamper-proof the rows.
