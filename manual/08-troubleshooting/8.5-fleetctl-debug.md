# `fleetctl debug` and the debug archive

Use `fleetctl debug` to collect server diagnostics through Fleet's `/debug/` HTTP endpoints. Authenticated commands require a global admin token and network access to the API. You can call the endpoints with `curl` when the CLI lacks an option you need. [6.4](../06-automate-fleet/6.4-use-fleetctl.md) covers fleetctl installation, contexts, and login.

The `connection` subcommand performs local network checks. With an explicit address, it needs neither credentials nor a configuration context. It does not call `/debug/`; the other commands below do.

## 8.5.0 Start here

Select a capture for the question you need to answer:

| What you are trying to establish | Command | Section |
|---|---|---|
| Anything can reach this Fleet at all | `fleetctl debug connection <address>` | [8.5.7](#857-fleetctl-debug-connection) |
| Whether a default fleetd package's CA bundle would trust the server | `fleetctl debug connection <address>`, no `--fleet-certificate` | [8.5.7](#857-fleetctl-debug-connection) |
| Which errors the server is actually recording, and which one most | `fleetctl debug errors --stdout`, sorted by `count` | [8.5.6](#856-fleetctl-debug-errors) |
| Whether the schema matches this binary, per node | `fleetctl debug migrations` | [8.5.10](#8510-fleetctl-debug-migrations) |
| Which argv this process started with, per node | `fleetctl debug cmdline` | [8.5.9](#859-fleetctl-debug-cmdline) |
| Why CPU is pinned | `fleetctl debug profile`, then `go tool pprof -http` | [8.5.8](#858-the-pprof-set) |
| Why memory keeps growing | Two `heap` captures, then `pprof -base` | [8.5.8](#858-the-pprof-set) |
| Why everything is hung with no CPU use | `fleetctl debug goroutine`, then `?debug=2` | [8.5.8](#858-the-pprof-set) |
| Whether the database is blocking itself | `fleetctl debug db-locks`, then `db-process-list` | [8.5.11](#8511-the-three-database-subcommands) |
| Handing the whole picture to someone else | `fleetctl debug archive`, plus `migrations` separately | [8.5.5](#855-fleetctl-debug-archive) |

Before collecting, confirm [global-admin access](#852-access-requirements) and which node will answer. A load balancer selects the serving node for authenticated calls; use a direct context when profiling one particular process ([8.5.5](#targeting-one-node)).

## 8.5.1 The complete subcommand list

The twelve subcommands are:

| Subcommand | Produces | Endpoint | Default output file | Read with |
|---|---|---|---|---|
| `profile` | 30-second CPU profile | `GET /debug/pprof/profile` | `fleet-profile-<ts>.prof` | `go tool pprof` |
| `heap` | Heap-allocated memory snapshot | `GET /debug/pprof/heap` | `fleet-heap-<ts>.prof` | `go tool pprof` |
| `goroutine` | Stack traces of every goroutine, Go's unit of concurrent work | `GET /debug/pprof/goroutine` | `fleet-goroutine-<ts>.prof` | `go tool pprof` |
| `trace` | 1-second execution trace | `GET /debug/pprof/trace` | `fleet-trace-<ts>.prof` | `go tool trace` |
| `cmdline` | The server process's argv | `GET /debug/pprof/cmdline` | stdout, or `--outfile` | Read as text |
| `errors` | Recorded server errors from Redis | `GET /debug/errors` | `fleet-errors-<ts>.json` | `jq` |
| `archive` | All of the above in one tarball | many (see 8.5.5) | `fleet-profiles-archive-<ts>.tar.gz` | `tar -xzf` |
| `connection [<address>]` | Connectivity and TLS chain check | `POST /api/osquery/enroll` | stdout | Read as text |
| `migrations` | Schema migration status | `GET /debug/migrations` | stdout | Read as text |
| `db-locks` | Blocking and waiting transactions | `GET /debug/db/locks` | `fleet-db-locks-<ts>` | `jq` |
| `db-innodb-status` | `SHOW ENGINE INNODB STATUS` output | `GET /debug/db/innodb-status` | `fleet-db-innodb-status-<ts>` | Read as text |
| `db-process-list` | `SHOW PROCESSLIST` output | `GET /debug/db/process-list` | `fleet-db-process-list-<ts>` | `jq` |

Fleet's documentation covers `errors` and `archive`. The pprof set, `cmdline`, `migrations` and the three `db-*` subcommands all work, and fleetdm.com/docs documents none of them as CLI commands.

## 8.5.2 Access requirements

| Subcommand | Auth | Also needs |
|---|---|---|
| `connection` | **None** when you pass an address: no login, no token, no config context | Network path to the server |
| `errors` | Global admin | Redis reachable from the server; error storage not disabled |
| `db-locks`, `db-innodb-status` | Global admin | DB user with global `PROCESS` and `SELECT`. Without them these two return the privilege error |
| `db-process-list` | Global admin | Runs without `PROCESS`, and returns only the Fleet user's own connections. The privilege is what makes it server-wide |
| `archive` | Global admin | Completes regardless. The same DB privileges decide whether its three database members are complete |
| everything else | Global admin | |

Every `/debug/` route requires an account permitted to perform actions and a global admin role. An admin scoped to a fleet or a global maintainer receives HTTP 403 with `Unauthorized`. A global-admin API-only identity can perform these calls for scripted collection.

A forced password reset also blocks actions, even for a global admin. It produces the same 403 response as a role failure. If a previously working token is rejected while its role is unchanged, check the account's reset status.

Authenticated calls follow the address in the fleetctl context. When that is a load balancer, record or control which node handles the capture using §8.5.5.

### Database privileges

`db-innodb-status` runs `SHOW ENGINE INNODB STATUS` and `db-process-list` runs `SHOW PROCESSLIST`, both against the writer connection. Without global `PROCESS` the first returns exactly this, which names the fix:

```
getting innodb status: DB user must have global PROCESS and SELECT privilege
```

The grant:

```sql
GRANT PROCESS, SELECT ON *.* TO 'fleet'@'%';
```

Check database privileges before treating the archive's database members as complete. Without `PROCESS`, `db-locks` and `db-innodb-status` return a privilege error. `db-process-list` still returns data, but only for connections owned by Fleet's database user. A populated process list can therefore omit other database clients.

## 8.5.3 Flags

| Flag | Env var | Applies to | Meaning |
|---|---|---|---|
| `--outfile` | `OUTFILE` | all except `connection`, `migrations` | Path to write to, overriding the generated name |
| `--stdout` | `STDOUT` | `errors` only | Print to stdout instead of a file. Mutually exclusive with `--outfile` |
| `--flush` | `FLUSH` | `errors` only | Delete the errors from Redis after reading them |
| `--fleet-certificate` | `FLEET_CERTIFICATE` | `connection` only | PEM file to use as the root CA for the TLS check |
| `--config` | `CONFIG` | every `fleetctl debug` subcommand | fleetctl config file, default `~/.fleet/config`. **Not universal across the client**: `package` and `new` do not declare it, and the `mdm` and `generate` subcommands declare only `--context` |
| `--context` | `CONTEXT` | all | Named context within that file, default `default` |
| `--debug` | `DEBUG` | all except `connection`, `migrations` | Log the HTTP request and response to stderr |

The client-side `--debug` flag logs fleetctl's own HTTP requests and responses. Configure Fleet server verbosity separately.

## 8.5.4 Where output lands

Output goes to the current working directory of whoever ran `fleetctl`. A newly created file gets mode `0600`; what happens when the path already exists differs by subcommand, and [8.5.13](#8513-what-is-safe-to-share) has the detail. Generated names follow one pattern, `fleet-<subcommand>-<timestamp>`, so a heap capture lands as `fleet-heap-20260819143002Z.prof`.

Generated filenames use the client's local time in `YYYYMMDDhhmmss` format. The trailing `Z` is literal and does not indicate UTC. Record timezone information when comparing files from different operators.

`profile`, `heap`, `goroutine` and `trace` get `.prof`. `errors` gets `.json`. The three `db-*` files get no extension at all. `archive` gets `.tar.gz`.

## 8.5.5 `fleetctl debug archive`

```sh
fleetctl debug archive
```

The archive attempts a fixed set of thirteen members. It keeps successful captures and skips failed members without retrying, so inspect the contents before relying on its coverage.

Collection proceeds sequentially in the order below. The CPU profile holds its connection for thirty seconds, placing the later database samples roughly half a minute after the earlier goroutine capture. Record start and finish times so transient symptoms can be compared with the correct collection interval.

| Item in archive | Filename | Notes |
|---|---|---|
| `allocs` | `allocs.prof` | Cumulative allocation profile |
| `block` | `block.prof` | **Empty in practice.** See below |
| `cmdline` | `cmdline.prof` | Server argv, despite the `.prof` extension |
| `errors` | `errors.json` | Non-flushing read of the Redis error store |
| `goroutine` | `goroutine.prof` | |
| `heap` | `heap.prof` | |
| `mutex` | `mutex.prof` | **Empty in practice.** See below |
| `profile` | `profile.prof` | The 30-second CPU profile |
| `threadcreate` | `threadcreate.prof` | OS thread creation sites |
| `trace` | `trace.prof` | The 1-second execution trace |
| `db-locks` | `db-locks.json` | |
| `db-innodb-status` | `db-innodb-status.json` | |
| `db-process-list` | `db-process-list.json` | |

Run `migrations` separately; the archive does not include it.

Fleet does not enable Go's blocking or mutex profiling rates, so `block.prof` and `mutex.prof` are empty. They provide no measurement of contention in this release.

<a id="failures-inside-the-archive-are-expected"></a>

### Check for failed archive members

A failed member is reported on stderr and skipped while collection continues. Retain those messages with the archive so the next investigator knows which evidence is missing:

```
Ran heap
Failed profile: Get "https://fleet.example.com/debug/pprof/profile": context deadline exceeded
Ran goroutine
```

`Failed profile` names the CPU capture. The remaining archive can still be useful when that capture fails, including from a client outside the server's environment.

The CPU capture waits thirty seconds, compared with the one-second trace and immediate snapshots. Fleet's HTTP write timeout defaults to one hundred seconds, derived from its live-query rest period. A failure at thirty seconds therefore suggests an intervening ingress, proxy, or load-balancer timeout. This is an inference from the timing; check the actual configuration before assigning the cause.

List the archive members before sharing it:

```sh
tar -tzf fleet-profiles-archive-20260819143002Z.tar.gz
```

Archive members have a directory prefix matching the archive filename. Extraction therefore creates a directory such as `fleet-profiles-archive-<ts>.tar.gz`. Include that prefix when identifying a file for another investigator.

### Targeting one node

Create a context for each node when you need process-specific evidence. A context pointing to the load balancer can capture a healthy node while the affected process remains unobserved:

```sh
fleetctl config set --context server-a --address https://server-a:8080
fleetctl login --context server-a
fleetctl debug archive --context server-a
```

Documented at fleetdm.com/docs/deploy/reference-architectures. The same `--context` approach applies to every authenticated subcommand here, and it is the normal `fleetctl` method for comparing nodes.

## 8.5.6 `fleetctl debug errors`

```sh
fleetctl debug errors --stdout | jq .
fleetctl debug errors --outfile server-errors.json
fleetctl debug errors --flush --outfile server-errors.json
```

The command reads Redis entries stored under `error:{<hash>}:json` and `error:{<hash>}:count`. Retention controls their lifetime; Fleet keeps no equivalent error file on disk.

| Property | Value |
|---|---|
| Storage | Redis, keys `error:{hash}:json` and `error:{hash}:count` |
| Retention | `logging_error_retention_period`, default **24h**. `0` means never expire, negative disables error storage entirely |
| Deduplication | By SHA-256 over, principally, the cause type, the cause message, and the root error's stack. Errors reported by fleetd add their own source fields. Repeats increment `count` rather than adding a row |
| Reading | Non-destructive. The entries stay in Redis and keep counting |
| `--flush` | Deletes the matching keys once the read has succeeded |

Read each entry's `count` as well as the number of distinct entries. Counts of 4, 6, and 91,000 identify a very different recurrence pattern from counts of 4, 6, and 7.

Response shape, one object per distinct error:

```json
[
  {
    "count": "3",
    "chain": [
      { "message": "Authorization header required" },
      {
        "message": "missing FleetError in chain",
        "data": { "timestamp": "2022-06-03T14:16:01-03:00" },
        "stack": [
          "<go package path>.<function> (<file>:<line>)",
          "<go package path>.<function> (<file>:<line>)"
        ]
      }
    ]
  }
]
```

Shape documented under "Get errors" at fleetdm.com/docs/rest-api/rest-api. Note `count` arrives as a string, which is why the `jq` below casts it.

Sort by count to identify frequently recorded faults:

```sh
fleetctl debug errors --stdout | jq -r 'sort_by(.count|tonumber) | reverse | .[] | "\(.count)\t\(.chain[0].message)"'
```

### Flush discipline

Save the existing evidence before flushing. `--flush` deletes the keys it reads without retaining a copy. After capture, you can flush, reproduce, and read again to collect newly recorded faults:

```sh
fleetctl debug errors --outfile errors-before.json      # keep
fleetctl debug errors --flush --outfile errors-baseline.json
# ... reproduce ...
fleetctl debug errors --stdout | jq .
```

The Redis store is shared across Fleet nodes. Reads therefore return cluster-wide errors, and a flush removes evidence for every operator using that store. Coordinate before clearing it.

An empty list can reflect disabled retention or errors outside the store's scope. A negative `logging_error_retention_period` disables storage. Client errors such as 401 and 422 responses are never recorded here. Check server configuration, or startup arguments where applicable, then use the [request logs](8.3-server-logs.md) for client-error investigation.

## 8.5.7 `fleetctl debug connection`

```sh
fleetctl debug connection https://fleet.example.com
fleetctl debug connection --fleet-certificate /path/to/ca.pem https://fleet.example.com
fleetctl debug connection                     # uses the current context's address
```

Four checks, in order, ten-second timeout each.

| # | Check | Success line | Failure prefix |
|---|---|---|---|
| 1 | DNS resolves the hostname to at least one IP | `Success: can resolve host <host>.` | `Fail: resolve host:` |
| 2 | Raw TCP dial to host:port (assumes 443 if no port, and says so) | `Success: can dial server at <host:port>.` | `Fail: dial server:` |
| 3 | TLS chain validates against the chosen root CA (HTTPS only) | `Success: TLS certificate seems valid.` | `Fail: certificate:` |
| 4 | `POST /api/osquery/enroll` with `{"enroll_secret": "--invalid--"}` returns HTTP 401 with `node_invalid: true` | `Success: agent API endpoints are available.` | `Fail: agent API endpoint:` |

It prints a header line first naming the host, the config context, the root CA in use, and whether TLS verification is on.

For deployments under a URL prefix, check the fourth probe's path. The command replaces it with `/api/osquery/enroll`, so `https://host/apps/fleet` is tested at `https://host/api/osquery/enroll`. DNS, TCP, and TLS checks remain useful, but verify the actual prefixed enrolment path before interpreting `Fail: agent API endpoint:`.

These checks make no authenticated request. The deliberately invalid enrol secret tests whether Fleet returns the expected agent-API response. Success establishes reachability, without granting or verifying access.

<a id="the-flag-rules-are-strict-and-the-errors-are-terse"></a>

### Address and certificate flag rules

- `--fleet-certificate` requires an explicit `<address>` alongside it. On its own it gives `the --fleet-certificate flag can only be set when an <address> is provided`.
- Passing an `<address>` rules out `--config` and `--context`, and the context's `rootca` and `tls-skip-verify` stop applying. An address means a check from scratch.
- A second positional argument gives `too many arguments`.

### Which CA it validates against

Three cases, in priority order:

1. `--fleet-certificate <path>` given: that PEM is the root CA.
2. Not given, but the fleetctl context has `rootca` set: that is the root CA.
3. Neither: **the certificate bundle embedded in fleetd packages** is the root CA, written to a temp file for the duration of the check.

With no certificate flag or context CA, the check uses the bundle embedded in a default fleetd package. To reproduce trust for a custom-certificate installation, supply that agent's actual CA through `--fleet-certificate`.

### What a pass proves

A pass covers DNS, TCP, TLS termination, and the expected response from the osquery enrol endpoint. Use the [channel sweep in 8.1](8.1-diagnostic-method.md) to check agent operation, Orbit, MDM push, and APNs separately.

For `Fail: certificate:` when a browser connects successfully, inspect the served intermediates and trusted roots. A browser may fetch a missing intermediate or trust a private root absent from the embedded bundle. For `Fail: agent API endpoint: invalid JSON`, inspect the responding service; a captive portal, TLS-inspecting proxy, or WAF may have returned an HTML page.

## 8.5.8 The pprof set

Use `profile`, `heap`, `goroutine`, and `trace` to collect CPU, memory, concurrency, and runtime-scheduling evidence. Fleet does not document these as CLI commands, but they are available for the investigations below.

| Command | Answers | Reach for it when |
|---|---|---|
| `profile` | What is the server spending CPU on? | CPU is pinned, or request latency rises with load |
| `heap` | What is holding memory right now? | Resident memory climbs and stays there; OOM kills |
| `goroutine` | What is every worker blocked on, and how many are there? | Requests hang, throughput drops with no CPU use, a cron never completes |
| `trace` | What did the scheduler do over one second? | Latency spikes with no obvious hot function; GC pauses suspected |

Read the captures with the Go toolchain's `go tool pprof` and `go tool trace`. If Go is unavailable locally, transfer the capture to a suitable machine or include it in the [escalation packet](8.13-escalation.md).

### Reading them

```sh
# Interactive flame graph / call tree in a browser. Start here.
go tool pprof -http=:8080 fleet-profile-20260819143002Z.prof

# Text, top 30 by cumulative cost, no browser needed.
go tool pprof -top -cum -nodecount=30 fleet-heap-20260819143002Z.prof

# Goroutine stacks, aggregated with counts.
go tool pprof -traces fleet-goroutine-20260819143002Z.prof

# Execution trace. Opens its own web UI with the scheduler and GC timelines.
go tool trace fleet-trace-20260819143002Z.prof
```

Fleet's released binaries are built without debug symbols as of Fleet 4.86.0 (github.com/fleetdm/fleet/releases), so passing the `fleet` binary alongside a profile adds nothing. The files above stand on their own: Go's runtime writes function names into the profile as it collects it.

<a id="two-captures-beat-one"></a>

### Compare captures to measure growth

Take two heap captures across the affected interval to measure memory growth. A single capture shows allocations at one point; subtracting the earlier capture identifies what accumulated:

```sh
fleetctl debug heap --context server-a --outfile heap-t0.prof
sleep 1800
fleetctl debug heap --context server-a --outfile heap-t1.prof
go tool pprof -http=:8080 -base heap-t0.prof heap-t1.prof
```

`-base` subtracts the earlier capture and displays the difference. Use the same approach for goroutine captures to identify stacks whose counts keep increasing without returning, a sign to investigate for a leak.

### Full goroutine stacks as text

The CLI fetches `/debug/pprof/goroutine` in compressed binary form. Add `?debug=2` to the HTTP endpoint for a text dump of full goroutine stacks. fleetctl has no flag for that format, so call it directly with the context's bearer token:

```sh
TOKEN=$(fleetctl config get token | awk '{print $NF}')
curl -sS -H "Authorization: Bearer $TOKEN" \
  'https://fleet.example.com/debug/pprof/goroutine?debug=2' > goroutines.txt
```

`fleetctl config get token` prints `  <context>.token => <value>`, which is why the `awk` is there. The token lives in `~/.fleet/config`, a YAML file of named contexts, mode `0600`.

`?debug=1` aggregates matching stacks with counts. Fleet uses Go's `net/http/pprof` handlers unchanged; these parameters come from Go. [8.14](8.14-degradation.md) also covers `?seconds=`.

Use [8.14](8.14-degradation.md) to interpret the captures and narrow a performance problem.

## 8.5.9 `fleetctl debug cmdline`

```sh
fleetctl debug cmdline
```

Prints the argv the Fleet server process was started with, one quoted token per element:

```
['/usr/bin/fleet', 'serve', '--config', '/etc/fleet/fleet.yml']
```

Compare the reported arguments with the intended startup flags. Node-specific differences can help explain inconsistent behavior and identify the process that answered.

The result contains argv only. Inspect environment variables and configuration files separately; a short argument list is expected when those sources hold the settings.

## 8.5.10 `fleetctl debug migrations`

```sh
fleetctl debug migrations
```

Exactly four possible outputs:

| Output | Meaning | Action |
|---|---|---|
| `Migrations up-to-date.` | Schema matches the running binary | None |
| `Missing migrations detected: tables=[…], data=[…].` | The binary knows migrations the database has not run | Run `fleet prepare db`, then restart `fleet serve` |
| `Unknown migrations detected: tables=[…], data=[…].` | The database has migrations this binary does not know about | You are running an **older** binary than the one that migrated the database. Practical reading, inferred; Fleet reports the condition without naming the cause |
| `Your Fleet database is not initialized. Fleet cannot start up.` | No migrations at all | `fleet prepare db`. Reaching this line takes some doing, since the command authenticates first and authentication needs the `sessions` table that migrations create |

Check migration status on each node after an upgrade problem or inconsistent node behavior. An incomplete rollout can return `Unknown migrations` from older binaries and `Migrations up-to-date.` from newer ones. Direct contexts make that comparison possible.

## 8.5.11 The three database subcommands

```sh
fleetctl debug db-process-list --outfile procs.json
fleetctl debug db-locks --outfile locks.json
fleetctl debug db-innodb-status --outfile innodb.txt
```

All three database commands query the writer connection, including when read replicas are configured.

| Subcommand | Underlying SQL | Fields |
|---|---|---|
| `db-process-list` | `SHOW PROCESSLIST` | `id`, `user`, `host`, `db`, `command`, `time`, `state`, `info` |
| `db-locks` | `information_schema.innodb_lock_waits` joined to `innodb_trx`, falling back to `performance_schema.data_lock_waits` on MySQL 8 where the older view is gone | `waiting_trx_id`, `waiting_thread`, `waiting_query`, `blocking_trx_id`, `blocking_thread`, `blocking_query` |
| `db-innodb-status` | `SHOW ENGINE INNODB STATUS` | One raw text blob as a JSON string |

Use `db-locks` to inspect blocking and waiting queries during a slowdown. An empty sample establishes that no lock wait was observed at that instant. Collect several samples across an intermittent symptom before ruling out contention.

`db-process-list` sorted by `time` descending finds the long-running query:

```sh
jq -r 'sort_by(.time) | reverse | .[] | "\(.time)s\t\(.state)\t\(.info)"' procs.json | head -20
```

Compare samples a few seconds apart. A persistent query needs investigation, but it may still be progressing. Evaluate its `state`, `time`, expected duration, and related lock waits before classifying it as stalled.

## 8.5.12 Trace sampling, endpoints only

The following two admin-only endpoints use `/debug/` authentication. Call them directly because fleetctl has no wrapper:

Full sampling of osquery, Orbit, and device traffic can create substantial collector volume. Keep the reproduction window short and restore the captured settings in step 4. PATCH updates only supplied fields, so restoration requires another explicit write.

```sh
TOKEN=$(fleetctl config get token | awk '{print $NF}')
FLEET=https://fleet.example.com          # add your URL prefix here if you serve one

# 1. Capture the current setting. This is your rollback value.
ORIGINAL=$(curl -sS --fail-with-body -H "Authorization: Bearer $TOKEN" "$FLEET/debug/trace_sampler" | jq -r '.force_full')

# 2. Open the window
curl -sS --fail-with-body -X PATCH -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"force_full": true}' "$FLEET/debug/trace_sampler"

# 3. Wait about a minute for every node to pick it up, then reproduce.

# 4. Restore the captured value, not a hardcoded false.
curl -sS --fail-with-body -X PATCH -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d "$(jq -n --argjson v "$ORIGINAL" '{force_full: $v}')" "$FLEET/debug/trace_sampler"

# 5. GET again and confirm it went back.
curl -sS --fail-with-body -H "Authorization: Bearer $TOKEN" "$FLEET/debug/trace_sampler"
```

If step 1 returns `force_full: true`, coordinate with the operator using that window before changing it. Allow the sixty-second polling interval in step 3 so every node can read the setting before reproduction. At the end, restore the captured value rather than assuming the earlier value was `false`.

Use `--fail-with-body` so a rejected HTTP request produces a failing exit status as well as its response. Plain `curl -sS` can exit zero after a 403. Supply any URL prefix, custom CA, or TLS verification setting explicitly; these direct calls do not inherit the fleetctl context.

`GET` returns `high_volume_ratio`, `standard_ratio`, `force_full` and `updated_at`. `PATCH` accepts any subset of the first three; ratios must be within `[0, 1]`. Settings live in the `trace_sampler_settings` row and each Fleet node polls it every 60 seconds, so a change takes effect without a restart. Documented at fleetdm.com/docs/rest-api/rest-api, shipped in Fleet 4.87.0.

Default sampling follows route tiers. High-volume agent routes, including osquery distributed reads and writes, Orbit ping and config, and device desktop and ping, are sampled at 0.1%. Administrative reads use 2%. Other work, including enrolment, SCEP, MDM check-in, cron jobs, and GitOps batches, uses 100%. Liveness probes are dropped.

Account for the route's sampling rate when a trace is missing. An agent check-in can be omitted by the 0.1% tier. An enrolment request has a 100% route default, so also inspect arrival at Fleet, export success, and incoming trace context. Fleet honors an upstream context marked unsampled regardless of the route tier.

These controls require `logging_tracing_enabled` and a receiving OpenTelemetry backend. A short `force_full` window captures all of the normally sampled agent traffic, so monitor the resulting volume.

## 8.5.13 What is safe to share

Archive and error commands print a sensitivity warning when writing files. `fleetctl debug errors --stdout` omits that banner but returns the same potentially sensitive data.

```
################################################################################
# WARNING:
#   The files in the generated archive may contain sensitive data.
#   Please review them before sharing.
```

Review the contents of each member before sharing:

| Item | Contains | Risk |
|---|---|---|
| `cmdline.prof` | Server argv | **Highest.** Any credential passed as a CLI argument is in plaintext here. Fleet's docs call this out explicitly and say to scrub it |
| `db-process-list.json` | Running SQL text, plus each client's `host:port` | Query text can carry host identifiers, serials, emails, and your internal network layout |
| `db-innodb-status.json` | Recent deadlock detail, including the SQL involved | Same as above |
| `errors.json` | Error messages and Go stack traces | Error chains can carry request context. Socket addresses are normalized to `<addr>` for request-timeout errors; every other error keeps whatever its message held, addresses included |
| `profile.prof`, `heap.prof`, `goroutine.prof`, `allocs.prof`, `trace.prof` | Function names, line numbers, allocation sites | Lower, and not zero. These are mostly Fleet's own code paths, and goroutine stacks can carry argument values |

Extract the archive and review `cmdline.prof` and the three database files, then assess the remaining members for sensitive content. Profiling captures can also include information that needs restricted handling.

New output files use mode `0600` on Unix. For an existing archive target, Fleet's file opener resets the mode to `0600`; other subcommands preserve an existing target's permissions. Windows has no equivalent effect from these Unix mode bits. Check actual access controls before sharing or retaining a capture.

> Use a private support channel for debug archives, as Fleet's reference architecture guidance allows. Include the node identity and topology so the recipient can place the capture in the deployment.

## 8.5.14 Choosing between the archive and a single capture

After choosing a diagnostic surface in [8.5.0](#850-start-here), decide whether the investigation needs the complete archive or a focused capture.

Take the archive for a broad initial view, for another investigator, or to collect database and runtime evidence within one interval. It attempts all thirteen listed members; retain the messages identifying any that failed.

Take a single capture for a specific question, repeated measurements of growth, or a time-sensitive snapshot that should not wait for the archive's thirty-second CPU profile.

In either case, record the answering node and collect `migrations` separately when migration status is needed.
