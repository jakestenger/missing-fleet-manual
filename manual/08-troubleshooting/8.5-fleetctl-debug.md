# `fleetctl debug` and the debug archive

`fleetctl debug` is a thin client over a set of HTTP endpoints the Fleet server mounts under `/debug/`. Any machine that can reach Fleet's API and holds a global admin token can run every command here, and `curl` will do the same work when `fleetctl` is missing a flag you want.

## 8.5.1 The complete subcommand list

Twelve subcommands.

| Subcommand | Produces | Endpoint | Default output file | Read with |
|---|---|---|---|---|
| `profile` | 30-second CPU profile | `GET /debug/pprof/profile` | `fleet-profile-<ts>.prof` | `go tool pprof` |
| `heap` | Heap-allocated memory snapshot | `GET /debug/pprof/heap` | `fleet-heap-<ts>.prof` | `go tool pprof` |
| `goroutine` | Stack traces of every goroutine, Go's unit of concurrent work | `GET /debug/pprof/goroutine` | `fleet-goroutine-<ts>.prof` | `go tool pprof` |
| `trace` | 1-second execution trace | `GET /debug/pprof/trace` | `fleet-trace-<ts>.prof` | `go tool trace` |
| `cmdline` | The server process's argv | `GET /debug/pprof/cmdline` | stdout, or `--outfile` | eyes |
| `errors` | Recorded server errors from Redis | `GET /debug/errors` | `fleet-errors-<ts>.json` | `jq` |
| `archive` | All of the above in one tarball | many (see 8.5.5) | `fleet-profiles-archive-<ts>.tar.gz` | `tar -xzf` |
| `connection [<address>]` | Connectivity and TLS chain check | `POST /api/osquery/enroll` | stdout | eyes |
| `migrations` | Schema migration status | `GET /debug/migrations` | stdout | eyes |
| `db-locks` | Blocking and waiting transactions | `GET /debug/db/locks` | `fleet-db-locks-<ts>` | `jq` |
| `db-innodb-status` | `SHOW ENGINE INNODB STATUS` output | `GET /debug/db/innodb-status` | `fleet-db-innodb-status-<ts>` | eyes |
| `db-process-list` | `SHOW PROCESSLIST` output | `GET /debug/db/process-list` | `fleet-db-process-list-<ts>` | `jq` |

Fleet's documentation covers `errors` and `archive`. The pprof set, `cmdline`, `migrations` and the three `db-*` subcommands all work, and fleetdm.com/docs documents none of them as CLI commands.

## 8.5.2 Access requirements

| Subcommand | Auth | Also needs |
|---|---|---|
| `connection` | **None** when you pass an address: no login, no token, no config context | Network path to the server |
| `errors` | Global admin | Redis reachable from the server; error storage not disabled |
| `db-locks`, `db-innodb-status`, `db-process-list` | Global admin | DB user with global `PROCESS` and `SELECT` |
| `archive` | Global admin | Same DB privileges as the `db-*` set |
| everything else | Global admin | |

Every `/debug/` route sits behind one gate, and it asks two things: that the caller is able to act at all, and that their **global** role is admin. A team admin gets HTTP 403 with the body `Unauthorized`, and so does a global maintainer. An API-only user carrying the global admin role passes, which is the right way to script this.

The first half of that gate catches a case the role check does not. A global admin who has been flagged for a forced password reset cannot perform actions, so every `/debug/` route returns the same 403 with the same one-word body as a role failure. If a token that used to work starts returning `Unauthorized` and the account's role has not changed, check whether an administrator reset that account's password before you go looking at the token.

These are ordinary authenticated HTTP calls, and they travel through whatever load balancer `fleetctl` already points at. That has a consequence, covered in 8.5.5: on a multi-node deployment you get whichever node the load balancer picked, which for a CPU profile is close to a coin toss.

### Database privileges

`db-innodb-status` runs `SHOW ENGINE INNODB STATUS` and `db-process-list` runs `SHOW PROCESSLIST`, both against the writer connection. Without global `PROCESS` the first returns exactly this, which names the fix:

```
getting innodb status: DB user must have global PROCESS and SELECT privilege
```

The grant:

```sql
GRANT PROCESS, SELECT ON *.* TO 'fleet'@'%';
```

`fleetctl debug archive` includes those three items, so an archive taken against a Fleet whose DB user lacks `PROCESS` arrives with the pprof data intact and the database sections missing. Worth checking before you go looking for a bug in the archive.

## 8.5.3 Flags

| Flag | Env var | Applies to | Meaning |
|---|---|---|---|
| `--outfile` | `OUTFILE` | all except `connection`, `migrations` | Path to write to, overriding the generated name |
| `--stdout` | `STDOUT` | `errors` only | Print to stdout instead of a file. Mutually exclusive with `--outfile` |
| `--flush` | `FLUSH` | `errors` only | Delete the errors from Redis after reading them |
| `--fleet-certificate` | `FLEET_CERTIFICATE` | `connection` only | PEM file to use as the root CA for the TLS check |
| `--config` | `CONFIG` | all | fleetctl config file, default `~/.fleet/config` |
| `--context` | `CONTEXT` | all | Named context within that file, default `default` |
| `--debug` | `DEBUG` | all except `connection`, `migrations` | Log the HTTP request and response to stderr |

`--debug` here means "log fleetctl's own HTTP traffic". It has nothing to do with `fleet serve --debug` on the server side.

## 8.5.4 Where output lands

Output goes to the current working directory of whoever ran `fleetctl`, with mode `0600`. Generated names follow one pattern, `fleet-<subcommand>-<timestamp>`, so a heap capture lands as `fleet-heap-20260819143002Z.prof`.

The timestamp is the client machine's **local** time in `YYYYMMDDhhmmss` form. The trailing `Z` is a literal character in the name pattern rather than a claim about UTC, so filename order equals capture order within one operator's machine and not across two.

`profile`, `heap`, `goroutine` and `trace` get `.prof`. `errors` gets `.json`. The three `db-*` files get no extension at all. `archive` gets `.tar.gz`.

## 8.5.5 `fleetctl debug archive`

```sh
fleetctl debug archive
```

One tarball, thirteen items, best-effort. The list is fixed and there is no flag to change it:

| Item in archive | Filename | Notes |
|---|---|---|
| `allocs` | `allocs.prof` | Cumulative allocation profile |
| `block` | `block.prof` | **Empty in practice.** See below |
| `cmdline` | `cmdline.prof` | Server argv, despite the `.prof` extension |
| `errors` | `errors.json` | Non-flushing read of the Redis error store |
| `goroutine` | `goroutine.prof` | |
| `heap` | `heap.prof` | |
| `mutex` | `mutex.prof` | **Empty in practice.** See below |
| `profile` | `profile.prof` | The 30-second CPU profile |
| `threadcreate` | `threadcreate.prof` | OS thread creation sites |
| `trace` | `trace.prof` | The 1-second execution trace |
| `db-locks` | `db-locks.json` | |
| `db-innodb-status` | `db-innodb-status.json` | |
| `db-process-list` | `db-process-list.json` | |

`migrations` is **not** in the archive. Run it separately.

`block.prof` and `mutex.prof` come back empty. Go collects blocking and mutex profiles once a program asks it to, at a sampling rate the program sets, and Fleet never asks. An empty block profile is the expected result, so treat it as no data rather than as a finding about contention.

### Failures inside the archive are expected

Each item is fetched on its own. A failure is printed to stderr and skipped rather than ending the run, on the reasoning that a server in a bad state will refuse some requests and the rest of the capture is still worth having. So a run interleaves lines like these:

```
Ran heap
Failed profile: Post "https://fleet.example.com/debug/pprof/profile": context deadline exceeded
Ran goroutine
```

**`Failed profile` means the CPU profile item failed, and has nothing to do with a configuration profile.** The word collision has cost people time. Taking the archive from a client outside the server's own environment produces this routinely, and the archive is still usable.

The CPU profile is the item most likely to fail from a remote client, because it holds the connection open for 30 seconds while everything else returns immediately. Fleet's own HTTP server allows at least 100 seconds of write time, so the timeout that fires belongs to something in between: an ingress, a proxy, or the load balancer's idle setting. Inferred from the timeout arithmetic, not documented.

Check the file list before you send an archive anywhere:

```sh
tar -tzf fleet-profiles-archive-20260819143002Z.tar.gz
```

Tar member paths are prefixed with the archive's own filename, so extraction creates a directory literally named `fleet-profiles-archive-<ts>.tar.gz` with the files inside it. Paths in a bug report need that prefix to make sense to the person reading them.

### Targeting one node

`fleetctl` talks to whatever address its context holds, which on a real deployment is the load balancer. A CPU profile from a random node is close to useless when one node is the sick one. Give each node its own context:

```sh
fleetctl config set --context server-a --address https://server-a:8080
fleetctl login --context server-a
fleetctl debug archive --context server-a
```

Documented at fleetdm.com/docs/deploy/reference-architectures. The same `--context` trick applies to every subcommand in this section, and it is the only way to compare nodes.

## 8.5.6 `fleetctl debug errors`

```sh
fleetctl debug errors --stdout | jq .
fleetctl debug errors --outfile server-errors.json
fleetctl debug errors --flush --outfile server-errors.json
```

This reads out of **Redis**. Each distinct error lives under the keys `error:{<hash>}:json` and `error:{<hash>}:count` and expires on a TTL, so the store is in memory and this command is the way into it. There is no file on disk holding the same data.

| Property | Value |
|---|---|
| Storage | Redis, keys `error:{hash}:json` and `error:{hash}:count` |
| Retention | `logging_error_retention_period`, default **24h**. `0` means never expire, negative disables error storage entirely |
| Deduplication | By SHA-256 of the cause type, cause message, and the root error's stack. Repeats increment `count` rather than adding a row |
| Reading | Non-destructive. The entries stay in Redis and keep counting |
| `--flush` | Deletes the matching keys once the read has succeeded |

Because the store is deduplicated, **`count` is the interesting field**, not the number of entries. Three distinct errors with counts of 4, 6 and 91,000 is a very different server from three with counts of 4, 6 and 7.

Response shape, one object per distinct error:

```json
[
  {
    "count": "3",
    "chain": [
      { "message": "Authorization header required" },
      {
        "message": "missing FleetError in chain",
        "data": { "timestamp": "2022-06-03T14:16:01-03:00" },
        "stack": [
          "<go package path>.<function> (<file>:<line>)",
          "<go package path>.<function> (<file>:<line>)"
        ]
      }
    ]
  }
]
```

Shape documented under "Get errors" at fleetdm.com/docs/rest-api/rest-api. Note `count` arrives as a string, which is why the `jq` below casts it.

Sort by count before reading anything:

```sh
fleetctl debug errors --stdout | jq -r 'sort_by(.count|tonumber) | reverse | .[] | "\(.count)\t\(.chain[0].message)"'
```

### Flush discipline

`--flush` is how you get a clean window. Flush, reproduce the problem, read again, and everything you see belongs to the reproduction. It also destroys whatever was there before, and nothing else has a copy. Capture first:

```sh
fleetctl debug errors --outfile errors-before.json      # keep
fleetctl debug errors --flush --outfile errors-baseline.json
# ... reproduce ...
fleetctl debug errors --stdout | jq .
```

On a multi-node deployment every node writes to the same Redis, so the store is shared. That makes `errors` the one subcommand where the load balancer picking a node at random costs you nothing, and the one where your flush lands on every operator at once.

Two ways this command returns an empty list from a server that is throwing errors hard. A negative `logging_error_retention_period` switches the store off entirely. And the store holds server faults: a request that Fleet answers with a 4xx is a client error and is never recorded, so a hunt for a `401` or a `422` here comes back with nothing. Confirm the retention setting with `fleetctl debug cmdline` or the server config, then take 4xx questions to the request logs in [8.3](8.3-server-logs.md).

## 8.5.7 `fleetctl debug connection`

```sh
fleetctl debug connection https://fleet.example.com
fleetctl debug connection --fleet-certificate /path/to/ca.pem https://fleet.example.com
fleetctl debug connection                     # uses the current context's address
```

Four checks, in order, ten-second timeout each.

| # | Check | Success line | Failure prefix |
|---|---|---|---|
| 1 | DNS resolves the hostname to at least one IP | `Success: can resolve host <host>.` | `Fail: resolve host:` |
| 2 | Raw TCP dial to host:port (assumes 443 if no port, and says so) | `Success: can dial server at <host:port>.` | `Fail: dial server:` |
| 3 | TLS chain validates against the chosen root CA (HTTPS only) | `Success: TLS certificate seems valid.` | `Fail: certificate:` |
| 4 | `POST /api/osquery/enroll` with `{"enroll_secret": "--invalid--"}` returns HTTP 401 with `node_invalid: true` | `Success: agent API endpoints are available.` | `Fail: agent API endpoint:` |

It prints a header line first naming the host, the config context, the root CA in use, and whether TLS verification is on.

**Check 4 reports a false failure on a deployment served under a URL prefix.** It builds its request by replacing the path outright with `/api/osquery/enroll`, so a Fleet served at `https://host/apps/fleet` is probed at `https://host/api/osquery/enroll`, which is not where it lives. The first three checks still tell you the truth, and a `Fail: agent API endpoint:` on a prefixed deployment means nothing until you have tested the real path yourself.

**None of the four authenticates.** The command is a local sequence of network checks, not a `/debug/` API client like the rest of this chapter, and check 4 deliberately uses an invalid secret to see whether the server answers in the shape an agent would recognise. So it works without credentials, and a success proves the path is reachable rather than that anything would be authorised.

### The flag rules are strict and the errors are terse

- `--fleet-certificate` requires an explicit `<address>` alongside it. On its own it gives `the --fleet-certificate flag can only be set when an <address> is provided`.
- Passing an `<address>` rules out `--config` and `--context`, and the context's `rootca` and `tls-skip-verify` stop applying. An address means a check from scratch.
- A second positional argument gives `too many arguments`.

### Which CA it validates against

Three cases, in priority order:

1. `--fleet-certificate <path>` given: that PEM is the root CA.
2. Not given, but the fleetctl context has `rootca` set: that is the root CA.
3. Neither: **the certificate bundle embedded in fleetd packages** is the root CA, written to a temp file for the duration of the check.

Case 3 is the default and the interesting one. With no flag and no context CA, the question being answered is whether *an enrolled agent* would trust this server, using the same bundle `fleetctl package` ships, rather than whether your laptop would. That is usually the question worth asking, and it is why a pass here can coexist with a browser warning on the same URL.

### What a pass proves

Check 4 hits the osquery enroll endpoint, so a pass covers one path end to end: DNS, TCP, TLS termination, and Fleet answering on the agent API. That is the enrollment path and nothing further. Agent health on a given host, a wedged Orbit, MDM push, and APNs reachability each need their own check, and the five-channel sweep in [8.1](8.1-diagnostic-method.md) walks them.

Two failure shapes worth recognising. `Fail: certificate:` on a server that browsers accept usually means the served chain is missing an intermediate: this check validates the chain exactly as served, where a browser will go and fetch the missing link. `Fail: agent API endpoint: invalid JSON` means something answered that is not Fleet, which is the signature of a captive portal, a TLS-inspecting proxy, or a WAF returning an HTML error page.

## 8.5.8 The pprof set

**This is the part of `fleetctl debug` that nobody uses.** `profile`, `heap`, `goroutine` and `trace` produce pprof files, Go's standard profiling format, and they appear zero times across 5,112 published and draft entries in Fleet's support corpus. Server performance is the single most recurring issue in that same corpus. The gap between those two numbers is what the rest of this section is for.

| Command | Answers | Reach for it when |
|---|---|---|
| `profile` | What is the server spending CPU on? | CPU is pinned, or request latency rises with load |
| `heap` | What is holding memory right now? | Resident memory climbs and stays there; OOM kills |
| `goroutine` | What is every worker blocked on, and how many are there? | Requests hang, throughput drops with no CPU use, a cron never completes |
| `trace` | What did the scheduler do over one second? | Latency spikes with no obvious hot function; GC pauses suspected |

Reading all four takes the Go toolchain, `go tool pprof` and `go tool trace`, and nothing else consumes these files. Without Go installed locally, move the archive to a machine that has it or hand it on through [8.13](8.13-escalation.md).

### Reading them

```sh
# Interactive flame graph / call tree in a browser. Start here.
go tool pprof -http=:8080 fleet-profile-20260819143002Z.prof

# Text, top 30 by cumulative cost, no browser needed.
go tool pprof -top -cum -nodecount=30 fleet-heap-20260819143002Z.prof

# Goroutine stacks, aggregated with counts.
go tool pprof -traces fleet-goroutine-20260819143002Z.prof

# Execution trace. Opens its own web UI with the scheduler and GC timelines.
go tool trace fleet-trace-20260819143002Z.prof
```

Fleet's released binaries are built without debug symbols as of Fleet 4.86.0 (github.com/fleetdm/fleet/releases), so passing the `fleet` binary alongside a profile adds nothing. The files above stand on their own: Go's runtime writes function names into the profile as it collects it.

### Two captures beat one

A single heap profile tells you what is allocated. **Growth** is the actual question in nearly every memory complaint, and growth takes two captures spaced across the problem, then a diff:

```sh
fleetctl debug heap --context server-a --outfile heap-t0.prof
sleep 1800
fleetctl debug heap --context server-a --outfile heap-t1.prof
go tool pprof -http=:8080 -base heap-t0.prof heap-t1.prof
```

The `-base` flag subtracts, so the browser now shows only the delta. The same technique works on `goroutine`: a goroutine count that climbs monotonically and never returns is a leak, and the diff names the stack that is leaking.

### Full goroutine stacks as text

`fleetctl debug goroutine` fetches `/debug/pprof/goroutine` with no query string, which returns the compressed binary form that pprof reads. The same endpoint serves a plain text dump of every goroutine's full stack at `?debug=2`, which during an incident is usually faster to skim than opening pprof. `fleetctl` exposes no flag for it, so call the endpoint directly with the bearer token `fleetctl` already holds:

```sh
TOKEN=$(fleetctl config get token | awk '{print $NF}')
curl -sS -H "Authorization: Bearer $TOKEN" \
  'https://fleet.example.com/debug/pprof/goroutine?debug=2' > goroutines.txt
```

`fleetctl config get token` prints `  <context>.token => <value>`, which is why the `awk` is there. The token lives in `~/.fleet/config`, a YAML file of named contexts, mode `0600`.

`?debug=1` gives the same data aggregated with counts per unique stack. Fleet mounts Go's `net/http/pprof` handlers unmodified, so the `debug` parameter is Go's rather than Fleet's, which is why Fleet's API docs say nothing about it. The same is true of `?seconds=`, covered in [8.14](8.14-degradation.md).

Full narrowing procedure for performance problems: [8.14](8.14-degradation.md). This section covers capture; 8.14 covers what to do with what you captured.

## 8.5.9 `fleetctl debug cmdline`

```sh
fleetctl debug cmdline
```

Prints the argv the Fleet server process was started with, one quoted token per element:

```
['/usr/bin/fleet', 'serve', '--config', '/etc/fleet/fleet.yml']
```

This is the **effective** invocation. When someone describes how the server is configured and its behaviour disagrees, this is the cheapest disproof available, and on a deployment whose nodes start with different flags it identifies which node answered.

Its reach stops at argv. Fleet takes most of its configuration from environment variables and a config file, and neither shows up here, so a short argv is the normal result and points you at those two places.

## 8.5.10 `fleetctl debug migrations`

```sh
fleetctl debug migrations
```

Exactly four possible outputs:

| Output | Meaning | Action |
|---|---|---|
| `Migrations up-to-date.` | Schema matches the running binary | None |
| `Missing migrations detected: tables=[…], data=[…].` | The binary knows migrations the database has not run | Run `fleet prepare db`, then restart `fleet serve` |
| `Unknown migrations detected: tables=[…], data=[…].` | The database has migrations this binary does not know about | You are running an **older** binary than the one that migrated the database. Practical reading, inferred; Fleet reports the condition without naming the cause |
| `Your Fleet database is not initialized. Fleet cannot start up.` | No migrations at all | `fleet prepare db`. Reaching this line takes some doing, since the command authenticates first and authentication needs the `sessions` table that migrations create |

Run this first on any post-upgrade problem, and on any deployment where nodes disagree with each other. A partially-rolled-out upgrade produces `Unknown migrations` from the old nodes and `Migrations up-to-date.` from the new ones, and `--context` per node is how you see that.

## 8.5.11 The three database subcommands

```sh
fleetctl debug db-process-list --outfile procs.json
fleetctl debug db-locks --outfile locks.json
fleetctl debug db-innodb-status --outfile innodb.txt
```

All three read through the **writer** connection by design, so on a deployment with read replicas they report the primary rather than whichever replica a read would otherwise land on.

| Subcommand | Underlying SQL | Fields |
|---|---|---|
| `db-process-list` | `SHOW PROCESSLIST` | `id`, `user`, `host`, `db`, `command`, `time`, `state`, `info` |
| `db-locks` | `information_schema.innodb_lock_waits` joined to `innodb_trx`, falling back to `performance_schema.data_lock_waits` on MySQL 8 where the older view is gone | `waiting_trx_id`, `waiting_thread`, `waiting_query`, `blocking_trx_id`, `blocking_thread`, `blocking_query` |
| `db-innodb-status` | `SHOW ENGINE INNODB STATUS` | One raw text blob as a JSON string |

`db-locks` is the direct answer to "everything is slow and nothing is erroring". An empty result rules out lock contention in one call. A non-empty result names both the blocking query and the blocked one, which is usually the whole diagnosis.

`db-process-list` sorted by `time` descending finds the long-running query:

```sh
jq -r 'sort_by(.time) | reverse | .[] | "\(.time)s\t\(.state)\t\(.info)"' procs.json | head -20
```

These are point-in-time samples of a moving system, so take several a few seconds apart. A query present in all of them is stuck. A query present in one is working.

## 8.5.12 Trace sampling, endpoints only

Two endpoints, admin-only, behind the same `/debug/` auth. `fleetctl` has no wrapper for either, so `curl` is the interface:

```sh
curl -sS -H "Authorization: Bearer $TOKEN" https://fleet.example.com/debug/trace_sampler

curl -sS -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"force_full": true}' https://fleet.example.com/debug/trace_sampler
```

`GET` returns `high_volume_ratio`, `standard_ratio`, `force_full` and `updated_at`. `PATCH` accepts any subset of the first three; ratios must be within `[0, 1]`. Settings live in the `trace_sampler_settings` row and each Fleet node polls it every 60 seconds, so a change takes effect without a restart. Documented at fleetdm.com/docs/rest-api/rest-api, shipped in Fleet 4.87.0.

The two ratios are named for route tiers rather than for endpoints, and knowing which tier a route sits in is what makes a trace worth chasing. Sampling is route-aware by default: the agent firehose, meaning osquery distributed read and write, Orbit ping and config, and the device desktop and ping endpoints, is sampled at **0.1%**; admin reads at **2%**; and everything else, including enrollment, SCEP, MDM check-in, cron jobs and GitOps batch operations, at **100%**. Liveness probes are dropped outright.

That tiering is why a missing trace is usually not a missing request. An agent check-in you cannot find was almost certainly one of the 999 in 1,000 that were never sampled, and an enrollment you cannot find was genuinely not traced.

This all takes effect when tracing is on (`logging_tracing_enabled`) and an OpenTelemetry backend is receiving. Given both, `force_full` for a short window during a reproduction lifts the 0.1% tier to everything. Turn it back off afterwards: those are the highest-volume endpoints Fleet serves, and full sampling on them will bury the backend.

## 8.5.13 What is safe to share

`archive` and `errors` both print a warning banner to stderr on completion:

```
################################################################################
# WARNING:
#   The files in the generated archive may contain sensitive data.
#   Please review them before sharing.
```

Concretely, per item:

| Item | Contains | Risk |
|---|---|---|
| `cmdline.prof` | Server argv | **Highest.** Any credential passed as a CLI argument is in plaintext here. Fleet's docs call this out explicitly and say to scrub it |
| `db-process-list.json` | Running SQL text, plus each client's `host:port` | Query text can carry host identifiers, serials, emails, and your internal network layout |
| `db-innodb-status.json` | Recent deadlock detail, including the SQL involved | Same as above |
| `errors.json` | Error messages and Go stack traces | Error chains can carry request context. Socket addresses are normalized to `<addr>` for request-timeout errors; every other error keeps whatever its message held, addresses included |
| `profile.prof`, `heap.prof`, `goroutine.prof`, `allocs.prof`, `trace.prof` | Function names, line numbers, allocation sites | Low. These reveal Fleet's own code paths, not your data |

Review before you send. `tar -xzf` the archive and read `cmdline.prof` and the three `db-*` files; they are small and human-readable, which is more than can be said for the rest of it.

Output files are written `0600`, so they stay private to the user who ran the command until a copy leaves that directory.

> [!internal] Debug archives can be sent through the private support channel rather than a public issue. Fleet's reference-architecture doc says this in as many words: "Debug archives can also be submitted confidentially through other support channels." Ask for the archive plus the node topology; an archive with no statement of which node it came from is much less useful than it looks.

## 8.5.14 Which subcommand for which question

| Question | Command |
|---|---|
| Can anything reach this Fleet server at all? | `connection` (needs no credentials) |
| Would an *agent* trust this server's certificate? | `connection <address>` with no `--fleet-certificate` |
| Is Fleet throwing errors, and which one most? | `errors --stdout`, sorted by `count` |
| Is the schema behind, or ahead, of this binary? | `migrations`, per node |
| Is the server actually running the config I think? | `cmdline`, per node |
| Why is CPU pinned? | `profile`, then `go tool pprof -http` |
| Why does memory keep growing? | Two `heap` captures, then `pprof -base` |
| Why is everything hung with no CPU use? | `goroutine`, then `?debug=2` for full stacks |
| Is the database blocking itself? | `db-locks`, then `db-process-list` |
| I need to hand this to someone else | `archive`, plus `migrations` separately |

For anything on the bottom half of that table, the archive gets you all of it in one call and is the right opening move. Reach for individual subcommands when you already have a hypothesis, or when you need two captures spaced in time.
