# 8.10 Android and AMAPI diagnostics

Android management is declarative **for profiles and applications**. Fleet writes one policy per device into Google's Android Management API (AMAPI), Google delivers that policy to the device, and the device reports back what it applied. For those, "the command is stuck in the queue" describes nothing that exists, and everything downstream of the policy write belongs to Google.

Lock, wipe and clear passcode are the exception: those really are AMAPI commands, tracked in `mdm_android_commands` as `pending`, `acknowledged` or `error`. They are the one part of Android management that behaves like the other two platforms, and the one part `fleetctl get mdm-commands` cannot show you.

That changes the first question. On Apple you ask whether the command left the queue. On Windows you ask whether the device opened a session. On Android you ask **which policy version Fleet last wrote, and which policy version the device says it applied**. Those two integers are the whole diagnosis most of the time.

§8.10.1 is an inventory of the instruments that do not carry over from the other two platforms, and is worth reading if you arrived here from one of them.

## 8.10.0 Start here

| Symptom | Start at | First thing to check |
|---|---|---|
| A profile is not reaching one Android host | [8.10.11](#81011-narrowing-the-search) | Compare two integers: the policy version Fleet wrote against the version the device says it applied |
| **Every** Android host is frozen at the same moment | [8.10.6](#8106-the-pubsub-return-path) | Pub/Sub. Run the fleet-wide `MAX(last_policy_sync_time)` query before anything else |
| Google rejected the policy write | [8.10.5](#8105-android-tables) | `android_policy_requests.error_details` and `payload`. This is the best-instrumented failure on Android |
| All of a host's profiles failed at once | [8.10.5](#retry-and-idempotency) | They share one PATCH. One malformed profile burns the retry budget for the rest |
| A device enrolled and never appeared in Fleet | [8.10.8](#8108-enrollment-paths) | Start at Pub/Sub. The notification not arriving is one cause; a notification that arrived and was rejected is another |
| An app is not installing | [8.10.9](#8109-app-installation-through-managed-google-play) | `AVAILABLE` means offered, not installed |
| A Wi-Fi profile is stuck pending with no policy request | [8.10.10](#81010-certificates-and-the-fleet-android-agent) | It is withheld pending a certificate, not failing to deliver |
| Lock, wipe or clear passcode is stuck | [8.10.5](#8105-android-tables) | `mdm_android_commands.status` and `error_message`. Correlate a `COMMAND` notification through `operation_name` |
| You are reaching for a tool from the Apple or Windows chapters | [8.10.1](#8101-the-instruments-android-does-not-have) | Most of them do not exist here |

For Android profiles and apps, stop looking for a command queue: there is none. Compare the policy version Fleet wrote with the version the device applied. Then check Pub/Sub, because it is Fleet's return path for status.

## 8.10.1 The instruments Android does not have

Anyone arriving from [8.8](8.8-apple-mdm-diagnostics.md) or [8.9](8.9-windows-mdm-diagnostics.md) reaches for these first. None of them are here.

| Instrument you would reach for | On Android | Use instead |
|---|---|---|
| Live report (`fleetctl report`) | Does not exist. No osquery on Android | The AMAPI status report, which arrives over Pub/Sub. §8.10.6 |
| osquery tables, scheduled queries, query reports | Do not exist | Nothing equivalent. Host facts come only from what AMAPI reports |
| `fleetctl run-script` / script activities | No path. Scripts are delivered by Orbit, and Android hosts have no fleetd. Nothing documents an Android script path | Nothing equivalent. Configuration changes go through the policy |
| Orbit / osqueryd logs on the host | Do not exist | Fleet server log plus `android_policy_requests`. §8.10.5 |
| `sudo profiles status` (macOS) or the `Enrollments` registry key (Windows) | Nothing comparable is exposed to an admin | The device's own **Device policy** app screens, and the AMAPI device resource as Google holds it |
| `fleetctl debug connection` from the device | No device-side Fleet CLI | Confirm the Fleet server URL is publicly reachable, since Pub/Sub push requires it. §8.10.6 |
| `fleetctl get mdm-commands` as the source of truth | **Returns nothing for Android.** The command list unions Apple and Windows only at this release, so an Android lock or wipe never appears in it | `mdm_android_commands` directly, §8.10.5. `host_mdm_android_profiles` for profiles |
| A per-command retry you can force | Policy writes are idempotent PATCHes, not queued commands. Re-triggering the profile cron retries **profile reconciliation only**; a pending lock, wipe or clear-passcode is not a profile and the cron will not touch it | Re-trigger the profile cron for profiles. §8.10.7. For a stuck command, §8.10.5 |
| Host refetch producing new host detail | Not documented; unverified. Nothing describes an Android refetch path | Wait for the next AMAPI status report |
| APNs-style push credential to check | There is no push certificate. Google owns delivery to the device | Pub/Sub subscription health. §8.10.6 |

Two things **do** exist on the host, and they confuse people because they look like an agent:

- **Android Device Policy**, Google's own controller app. It is Google's, not Fleet's. It applies the policy and reports state.
- **The Fleet Android agent**, an app Fleet installs through the policy with a managed configuration. Its documented scope is certificate installation over [SCEP](../09-appendices/a.6-glossary-and-release-compatibility.md#scep) plus reporting install status back to Fleet. It is a different program from fleetd, with no osquery, no scripts, and no live report. §8.10.10.

## 8.10.2 Vocabulary

| Term | Meaning |
|---|---|
| AMAPI | Google's Android Management API. The only management transport Fleet uses for Android |
| Enterprise | The AMAPI tenant object binding a Fleet server to Google. One per Fleet server URL. `android_enterprises` |
| Policy | The declarative document AMAPI applies to a device. Fleet keeps one policy per host (`android_devices.applied_policy_id`) |
| Policy version | An integer Google increments on each accepted policy write. The device reports the version it has applied |
| Work profile | A separate, managed user on a personally owned device. Personal side stays untouched |
| COBO | Company-owned, business only. Fully managed device, `PERSONAL_USAGE_DISALLOWED` |
| BYO / personally owned | Work profile enrollment, `PERSONAL_USAGE_ALLOWED` |
| Enterprise-specific ID | Google's stable per-enterprise device identifier for a work profile. Fleet stores it in `android_devices.enterprise_specific_id` and surfaces it where `hardware_serial` and `uuid` would otherwise go (fleetdm.com/docs/rest-api/rest-api) |
| Pub/Sub push | Google Cloud Pub/Sub delivering device notifications to a Fleet HTTPS endpoint |
| Managed configuration | Key/value config Fleet sets on an installed app through the policy |

## 8.10.3 The delivery path

| # | Hop | Transport | Where state lands | How to observe |
|---|---|---|---|---|
| 1 | Fleet decides the host's desired profile set changed | `mdm_android_profile_manager`, default every 30s | `host_mdm_android_profiles.status` NULL or `pending` | SQL, §8.10.5 |
| 2 | Fleet merges the profiles into one policy body, ordered by profile name ascending | in-process | nothing yet | nothing until hop 3 |
| 3 | Fleet PATCHes the policy | HTTPS to AMAPI, direct or via the fleetdm.com proxy | one row in `android_policy_requests` with `payload`, `status_code`, `error_details`, `policy_version` | §8.10.5 |
| 4 | Fleet records which policy version carried each profile | MySQL write | `host_mdm_android_profiles.included_in_policy_version`, `policy_request_uuid` | SQL |
| 5 | Google pushes the policy to the device | Google's own channel. Fleet has no visibility and no control | nothing in Fleet | nothing. This is the blind hop |
| 6 | Device applies the policy and reports | AMAPI status report | Google's device resource: `appliedPolicyVersion`, `lastPolicySyncTime`, `nonComplianceDetails` | §8.10.6 |
| 7 | Google publishes a `STATUS_REPORT` notification | Pub/Sub push, `POST /api/v1/fleet/android_enterprise/pubsub?token=…` | `android_devices.applied_policy_version`, `last_policy_sync_time` | server log `Received PubSub message` at DEBUG |
| 8 | Fleet verifies profiles against the applied version | in-process | `host_mdm_android_profiles.status` moves to `verified` or `failed` with `detail` | server log `Verifying Android device policy` at DEBUG |

Hop 5 has no instrumentation on either side. When hops 1 through 4 are clean and hop 7 never arrives, you cannot tell from Fleet whether Google failed to deliver or the device failed to check in. That is the structural limit of Android diagnosis.

### Verification is version-gated

Fleet verifies a profile once its `included_in_policy_version` is less than or equal to the device's reported `appliedPolicyVersion`, and not before. A profile written into version 12 stays `pending` until a status report says the device applied 12 or later, no matter how many status reports arrive in between. A profile stuck at `pending` with `included_in_policy_version` well above `android_devices.applied_policy_version` is a device that has not caught up, not a Fleet-side failure.

With no `nonComplianceDetails` in the report, everything pending at or below the applied version flips to `verified`. With non-compliance details present, Fleet maps them back to the profiles that set the offending fields and marks those `failed`, writing Google's reason into `detail`.

## 8.10.4 The seven failure classes on Android

Mapping onto [8.1](8.1-diagnostic-method.md) §8.1.5:

| Class | Applies on Android? | Where it shows |
|---|---|---|
| 1, not targeted | Yes | No row in `host_mdm_android_profiles` for that host and profile. Team assignment on `android_devices.team_id` |
| 2, not queued | Yes, in a modified form. There is no queue, but there is a policy write that may never have happened | No `android_policy_requests` row referenced from the profile row, and `cron_stats` shows the cron did not run |
| 3, queued not delivered | **Collapsed.** Fleet cannot distinguish "Google has not delivered" from "device has not applied" | `android_policy_requests.status_code = 200` but `applied_policy_version` behind `included_in_policy_version` |
| 4, delivered not executed | **Not separable from class 3.** No device-side acknowledgement exists short of a status report | Same signal as class 3 |
| 5, executed and failed | Yes, and this is the well-instrumented one | `nonComplianceDetails` in the status report, landing as `host_mdm_android_profiles.status = 'failed'` with `detail` |
| 6, succeeded not reflected | Yes, and Android generates it more than the other platforms | Pub/Sub delivery broken. §8.10.6 |
| Inverse (reported success, did not work) | Not documented; unverified. Google reports compliance, and Fleet trusts it | Compare against the device's Device policy screens |

Classes 3 and 4 collapsing into one is the practical consequence of the declarative model. Do not spend time trying to separate them. Spend it on deciding whether the problem is left of hop 4 (Fleet and Google's API, fully observable) or right of it (opaque).

## 8.10.5 Android tables

Cross-reference [8.6](8.6-server-state.md).

| Table | Key columns |
|---|---|
| `android_devices` | `id`, `host_id`, `device_id`, `enterprise_specific_id`, `last_policy_sync_time`, `applied_policy_id`, `applied_policy_version`, `team_id`, `created_at`, `updated_at` |
| `android_enterprises` | `id`, `signup_name`, `enterprise_id`, `signup_token`, `pubsub_topic_id`, `user_id`, `created_at`, `updated_at` |
| `android_policy_requests` | `request_uuid`, `request_name`, `policy_id`, `payload` (JSON), `status_code`, `error_details`, `applied_policy_version`, `policy_version`, `created_at`, `updated_at` |
| `host_mdm_android_profiles` | `host_uuid`, `profile_uuid`, `profile_name`, `status`, `operation_type`, `detail`, `policy_request_uuid`, `device_request_uuid`, `request_fail_count`, `included_in_policy_version`, `can_reverify`, `checksum`, `created_at`, `updated_at` |
| `mdm_android_configuration_profiles` | `profile_uuid`, `team_id`, `name`, `raw_json`, `auto_increment`, `checksum` (generated from `raw_json`), `created_at`, `uploaded_at` |
| `mdm_android_commands` | `command_uuid`, `host_uuid`, `operation_name`, `command_type`, `status` (`pending`/`acknowledged`/`error`), `error_code`, `error_message`, `created_at`, `updated_at` |
| `android_app_configurations` | `id`, `application_id`, `team_id`, `global_or_team_id`, `configuration` (JSON), `created_at`, `updated_at` |

`host_mdm_android_profiles.status` is a foreign key onto `mdm_delivery_status`, the same status vocabulary Apple and Windows profiles use, so cross-platform profile queries work unchanged.

### The one query to run first

```sql
SELECT h.uuid,
       ad.device_id,
       ad.applied_policy_id,
       ad.applied_policy_version,
       ad.last_policy_sync_time,
       p.profile_name,
       p.status,
       p.included_in_policy_version,
       p.request_fail_count,
       LEFT(p.detail, 200) AS detail
FROM   hosts h
JOIN   android_devices ad ON ad.host_id = h.id
LEFT   JOIN host_mdm_android_profiles p ON p.host_uuid = h.uuid
WHERE  h.uuid = '<host-uuid>';
```

Then the write side, which is where Google's own error text lives:

```sql
SELECT pr.request_uuid, pr.request_name, pr.policy_id, pr.status_code,
       pr.policy_version, pr.applied_policy_version,
       LEFT(pr.error_details, 500) AS error_details, pr.created_at
FROM   android_policy_requests pr
JOIN   host_mdm_android_profiles p ON p.policy_request_uuid = pr.request_uuid
WHERE  p.host_uuid = '<host-uuid>'
ORDER  BY pr.created_at DESC
LIMIT  20;
```

`android_policy_requests.payload` holds the exact JSON Fleet sent. That is the single most useful artifact for an AMAPI problem, because you can hand it to Google's API reference field by field, and it is the only place the merged policy body is preserved.

### Reading the state combination

| `status_code` | `status` | `included_in_policy_version` vs `applied_policy_version` | Where to look |
|---|---|---|---|
| no request row | NULL | n/a | Hop 1. Check `cron_stats` for `mdm_android_profile_manager`, then whether the host is in the profile's team scope |
| `200` | `pending` | included > applied | Hop 5 or 6. Google accepted the write; the device has not caught up. Check `last_policy_sync_time` |
| `200` | `pending` | included <= applied | Hop 7 or 8. The device applied that version but Fleet never verified. Suspect Pub/Sub. §8.10.6 |
| `200` | `verified` | included <= applied | Working |
| `200` | `failed` | included <= applied | Class 5. Read `detail`; it carries Google's non-compliance reason |
| `4xx` / `5xx` | NULL, `request_fail_count` climbing | n/a | Google rejected the write. Read `error_details`. Almost always the policy body or a permissions problem |
| `4xx` / `5xx` | `failed` after 3 attempts | n/a | Fleet gave up. Three attempts per policy write is the ceiling |

### Retry and idempotency

- A failed policy PATCH increments `request_fail_count` on every profile in that policy and leaves `status` NULL so the next cron tick retries.
- At `request_fail_count >= 3`, Fleet marks the whole set `failed` and writes Google's last error into `detail`.
- The retry budget is **three attempts per policy write, not three per profile**. One malformed profile burns the budget for every other profile in the same host's policy, because they all ride the same PATCH. That is one mechanism by which "all my Android profiles failed at once" happens, and the one to test first because a single malformed profile explains the whole set.
- Profiles whose `openNetworkConfiguration` references a certificate that is not yet verified are **withheld** from the policy and kept `pending` with a zero checksum, so they re-send once the certificate lands. A profile pending with no `policy_request_uuid` and a Wi-Fi payload is usually this rather than a delivery failure.
- `mdm_android_configuration_profiles.checksum` is generated from `raw_json`, and `host_mdm_android_profiles.checksum` records what was actually sent. Equal checksums mean no re-send. Unrelated policy edits therefore do not re-deliver every profile.

## 8.10.6 The Pub/Sub return path


**Check which path your deployment uses before reaching for the Google Cloud console.** By default Fleet reaches the Android Management API through a proxy on fleetdm.com, and on that path Fleet never receives a topic name, so `android_enterprises.pubsub_topic_id` is empty and there is no topic or subscription in a project you control. Everything below about backlogs and push errors applies to a deployment configured to talk to Google directly. On the proxy path, the observable end of Pub/Sub is Fleet's own receiving endpoint and its logs, and the topic is Fleet's to see rather than yours.

Policy, application and command status all arrive here, and nothing else carries them. Two narrow exceptions exist and are worth knowing precisely because they keep working when this path does not: the Fleet Android agent posts certificate results directly to Fleet ([8.10.10](#81010-certificates-and-the-fleet-android-agent)), and `mdm_android_device_reconciler` polls AMAPI hourly for device existence ([8.10.7](#8107-the-two-crons)).

| Fact | Value |
|---|---|
| Endpoint | `POST /api/v1/fleet/android_enterprise/pubsub?token=<token>` |
| Auth | A single `token` query parameter, generated by Fleet, stored as MDM asset `android_pubsub_token` |
| Body size limit | 10 MiB |
| Topic | Created at enterprise signup. `android_enterprises.pubsub_topic_id` holds it only when Fleet talks to Google directly; on the default proxy path that column is empty, see below |
| Notification types subscribed | `ENROLLMENT`, `STATUS_REPORT`, `COMMAND`, `USAGE_LOGS` |
| Types Fleet acts on | `ENROLLMENT`, `STATUS_REPORT`, `COMMAND`. `test` and anything else are logged and dropped |
| Payload encoding | `message.data` is base64, `message.attributes.notificationType` selects the handler |
| Server URL requirement | Publicly reachable, and fixed for the life of the enterprise. Pub/Sub is configured with one URL at signup |

### Why this is a single point of failure

If Pub/Sub push stops reaching Fleet, nothing errors on the device and nothing errors in the policy write path. Devices keep receiving policies from Google and keep applying them. Fleet stops learning about it. Profiles sit at `pending` forever, `android_devices.applied_policy_version` and `last_policy_sync_time` freeze, and host detail goes stale. That is class 6, succeeded but not reflected, generated at scale and across every Android host simultaneously.

### The signature

**Every** Android host frozen at the same wall-clock time is Pub/Sub. One host frozen is the device. Check it directly:

```sql
SELECT MAX(last_policy_sync_time) AS newest_sync,
       COUNT(*)                   AS android_hosts
FROM   android_devices;
```

A `newest_sync` that is hours old across the whole fleet means no status report has been processed since then. Nothing in Fleet will tell you why, because a push that never arrives leaves no log line.

### What is observable, and where

| Question | Where |
|---|---|
| Is Fleet receiving pushes at all? | Server log at DEBUG, `Received PubSub message` with the `notification` field ([8.3](8.3-server-logs.md)). Absence of this line over a window covering many devices is the finding |
| Is Google failing to deliver? | Google Cloud console, the subscription attached to `android_enterprises.pubsub_topic_id`. Look at unacked message count and push error rate. Fleet has no view of this |
| Is Fleet rejecting the pushes? | The token check runs per notification. A rotated or mismatched token means Fleet returns an error and Google retries, so this shows as a growing backlog on Google's side and no state movement in Fleet |
| Did the server URL change? | `android_enterprises` plus app config `server_settings.server_url`. Pub/Sub holds the URL it was given at signup and keeps using it |
| Is a proxy or WAF blocking it? | Access logs in front of Fleet, filtered to the pubsub path. The request is unauthenticated apart from the query token, so a WAF rule on unauthenticated POSTs will eat it |

The current implementation has no straightforward way to rotate that token. Treat a token mismatch as an escalation rather than something to fix in place. See [8.13](8.13-escalation.md).

> **On a server that moved behind a new load balancer or changed its external URL, check the Pub/Sub push URL before diagnosing anything else about Android.** The URL is fixed at enterprise signup, and the symptom is silent staleness rather than an error.

## 8.10.7 The two crons

Both write to `cron_stats`, which is the only record that they ran. See [8.6](8.6-server-state.md).

| Schedule name | Default interval | Job | What it does |
|---|---|---|---|
| `mdm_android_profile_manager` | 30 seconds | `manage_android_profiles` | Computes each Android host's desired profile set, merges it into one policy body, PATCHes the policy through AMAPI, records the request in `android_policy_requests`, and stamps `included_in_policy_version` on the profiles it carried |
| `mdm_android_device_reconciler` | 1 hour | `reconcile_android_devices` | Pages every device AMAPI reports for the enterprise, compares against hosts Fleet thinks are enrolled, and flips the missing ones to unenrolled with an `mdm_unenrolled` activity |

### When to suspect the profile manager

Profiles stuck with `status` NULL and no `policy_request_uuid`. Confirm with `cron_stats`, then force a run:

```sh
fleetctl trigger --name=mdm_android_profile_manager
```

`fleetctl trigger` can report success for a run that never happened, so always pair it with a `cron_stats` check. See [8.11](8.11-reproducing-and-isolating.md).

A trigger only helps where there is still an eligible attempt to make. A profile set whose `request_fail_count` has reached three is already `failed`, and the cron will not call AMAPI for it again however many times you trigger it.

Batch size is capped by `mdm.android_batch_size`, default `100` hosts per batch, configurable to spread AMAPI load. `0` means no limit. On a large Android fleet, a backlog that drains steadily rather than stalling is the batch limit working, not a fault.

### When to suspect the reconciler

Hosts that Fleet shows as enrolled but that no longer exist in Google, or the opposite: an unenrollment that Fleet never noticed. The reconciler complements Pub/Sub `DELETED` handling rather than replacing it, so with Pub/Sub broken it is the one thing that eventually notices a wiped device, and it does so up to an hour late.

It logs `android reconcile complete` at DEBUG with `checked` and `unenrolled` counts, and `android device missing in Google; marked unenrolled` per device. Pagination is bounded at 10,000 pages; hitting the bound returns an error rather than a partial device set, deliberately, because a partial set would flip present devices to unenrolled.

### Two one-time migration schedules

`enable_android_app_reports_on_default_policy` and `migrate_to_per_host_policy` run once after upgrade (to 4.76.0 and 4.77.0 respectively) and then stop. If you are diagnosing a Fleet upgraded from before 4.77.0 and hosts appear to share a policy, check `cron_stats` for `migrate_to_per_host_policy`.

## 8.10.8 Enrollment paths

| Path | How it starts | Token settings | Signature when it breaks |
|---|---|---|---|
| Work profile, personally owned (BYOD) | End user opens the Fleet enrollment page, Fleet fetches an AMAPI enrollment token, the user is redirected to `https://enterprise.google.com/android/enroll?et=<token>` | `AllowPersonalUsage: PERSONAL_USAGE_ALLOWED`, `OneTimeOnly: true`, default 1 hour lifetime | No `android_devices` row and no `ENROLLMENT` notification. Google-side failure, or an expired or reused token |
| QR code at initial setup (company-owned, COBO) | Device is factory reset and sitting at the initial setup screen. Tap the welcome screen to reach the QR scanner, scan the code from the enrollment token response | `fully_managed=true` sets `PERSONAL_USAGE_DISALLOWED`. Only enrollable at the initial setup screen | Enrollment refused outright on a device that has already completed setup. This is the constraint, not a bug |
| Google account based | Named as a supported path in Fleet's own MDM bug checklist. **Not documented beyond that; unverified.** | n/a | Check `android_devices.enterprise_specific_id` presence and the `ENROLLMENT` notification in the server log, same as work profile |

Fleet creates the enrollment token itself, and puts the Fleet enroll secret and an optional identity provider (IdP) UUID into AMAPI's `additionalData` field. That is how Fleet ties the resulting device back to a fleet and, when the UUID is present, to an end user; a bad enroll secret fails at token creation time, before the device is involved at all.

**Neither association is unconditional.** The identity association only happens when the enrollment carried an IdP UUID, so a device enrolled without one has no end user and that is not a fault. And the secret's fleet is only the answer for a device Fleet has never seen: **on a re-enrollment Fleet restores the device's last known fleet in preference to the secret's**, even when the host row was deleted in between ([3.6](../03-connect-devices/3.6-enroll-android-devices.md)).

| Enrollment fact | Value |
|---|---|
| Token endpoint | `GET /api/v1/fleet/android_enterprise/enrollment_token?enroll_secret=<secret>&fully_managed=<bool>` |
| Response fields | `android_enrollment_token`, `android_enrollment_url`, `android_enrollment_qrcode` |
| Token reuse | `OneTimeOnly: true`. One device per token |
| Default lifetime | 1 hour (AMAPI default; Fleet does not override it) |
| Policy assigned at enrollment | The enterprise's default policy, then moved to a per-host policy |
| Identity Fleet stores | `enterprise_specific_id`, which survives factory reset within the same enterprise for work profile enrollments |

### Enrollment failures worth recognising

- `DPM_PRECONDITION_CHECK_FAILED_FOR_PROFILE_OWNER`: a leftover work profile from a previous attempt. On a **test device you are willing to wipe**, list users over the Android Debug Bridge with `adb shell pm list users` and remove the stale work profile with `adb shell pm remove-user <id>`. That deletes the profile and everything in it, so on a device belonging to someone it is a conversation before it is a command.
- `This enterprise is already enrolled with another EMM`: the Google account already has an enterprise bound somewhere else.

**Do not answer this by deleting the organization unless you know it is disposable.** Fleet's guidance to remove the organization under Admin settings at `play.google.com/work` is written for a development signup made with a personal account, where the organization exists only from a previous test. Applied to a real Android Enterprise it is destructive on a scale that has nothing to do with the error you were chasing: as [2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md) records, deleting the enterprise turns Android management off in Fleet, unenrolls **every enrolled Android device**, and on personally owned devices takes the work profile with it.

In an established deployment the useful question is which account and which enterprise, not how to clear the conflict. A Google account can bind one enterprise, and Fleet's proxy allows one enterprise per server URL, so the reading to test first is that you are signing in with an account already committed elsewhere, rather than that anything needs deleting.
- Enrollment succeeded on the device but the host never appears in Fleet. **Go to §8.10.6, and do not stop at "the notification did not arrive".** Fleet validates the payload after receipt, requiring hardware, software and memory data, re-verifies the enroll secret carried in the token, and then does database work. A notification that arrived perfectly can fail at any of those, and a revoked or rotated secret fails at the second. A `STATUS_REPORT` for a device Fleet does not know can also create the host, so `ENROLLMENT` is not the only way in.
- A device that enrolls but lands in the wrong team. **Check whether Fleet has seen it before, because on re-enrollment the last known team wins over the token's.** Fleet looks up the device's prior team by its host key and uses that in preference to the enroll secret's, and does so even when the host row was deleted in between. So a device returning to where it used to be is the designed behaviour, not a wrong secret; the secret decides placement only for a device Fleet has genuinely never seen. Where the device *is* new, check `android_devices.team_id` and which team's secret went into the token. Separately, a recent release fixed a case where device check-ins could revert an admin team transfer (github.com/fleetdm/fleet/releases), so if the team flips back on its own, check the version.

One enterprise per Fleet server URL when using the fleetdm.com proxy, and that server URL is fixed once the enterprise is bound. Both constraints bite in staging and migration work.

## 8.10.9 App installation through Managed Google Play

There is no installer, no download, and no install script. Fleet adds the app to the host's policy and Google Play does the rest.

| `InstallType` | Effect | Used for |
|---|---|---|
| `AVAILABLE` | App becomes installable from the work-profile Play Store. The user installs it | Normal software installs |
| `PREINSTALLED` | Google installs it automatically | Setup experience, which adds all relevant apps to the host's policy at enrollment |

The API call is [`enterprises.policies.modifyPolicyApplications`](https://developers.google.com/android/management/reference/rest/v1/enterprises.policies/modifyPolicyApplications), issued per host, with the result recorded in the database.

Diagnostic consequences:

- **`AVAILABLE` means "offered", not "installed".** An install that sits pending while the user never opens Play is working as designed. Check whether the app is visible in the work profile Play Store before treating it as a failure.
- Android app installs never produce `nano_command_results` rows, because they never touch the Apple MDM path. Look for Android installs in the Android tables, not in the Apple MDM command tables.
- Install jobs are batched and staggered across worker ticks to spread AMAPI load, so a slow rollout across many hosts is expected.
- `self_service` is **required** when adding an Android app, and it controls whether the app appears in the work profile Play Store (fleetdm.com/docs/rest-api/rest-api).
- Managed app configuration lives in `android_app_configurations`, keyed by `global_or_team_id` and `application_id`. A misconfigured managed config presents as an app that installs and then misbehaves, with nothing wrong anywhere in the profile tables.
- If the app is not approved in Managed Google Play for the enterprise, the policy write can fail. Check `android_policy_requests.error_details`, then `play.google.com/work`.

## 8.10.10 Certificates and the Fleet Android agent

The chain is longer than on the other platforms because the certificate is installed by an app, not by the MDM policy:

1. Host enrolls. The default policy does **not** contain the Fleet Android agent.
2. The software worker runs and installs the agent with its managed configuration.
3. The agent starts (on install, on `BOOT_COMPLETED`, or on its own worker every 15 minutes) and reads the managed configuration.
4. If it has no `orbit_node_key`, it calls the Fleet enroll endpoint with the enroll secret to get one, and stores it encrypted.
5. For each pending certificate, it calls `GET /api/fleetd/certificates/:id`, generates a key and CSR, retrieves the certificate over SCEP, and stores it in the keychain.
6. It reports the outcome with `PUT /api/fleetd/certificates/:id/status`.

| Retry layer | Budget | Behaviour |
|---|---|---|
| Client side, in the agent | 3 SCEP attempts | Retries locally before reporting failure to Fleet |
| Server side | 3 redeliveries | On a reported failure Fleet resets the certificate to `pending` for redelivery on the next cron cycle, logging an `installed_certificate` activity with `status: "failed_install"` each time |
| Manual resend | 1 attempt | Resend sets `pending` with `retry_count` already at the maximum, so exactly one delivery attempt with no automatic retry |
| Renewal | Resets to 0 | Automatic renewal restores a full retry budget |

**The two automatic layers compose.** The agent exhausts its local attempts before it reports failure, so each server redelivery starts a fresh client budget. A failing certificate therefore produces substantially more than three SCEP requests against the certificate authority before Fleet gives up. Read the two budgets as multiplying, not as a shared total of three.

Two diagnostic points that follow from this shape:

- **A Wi-Fi profile can be blocked by a certificate.** Profiles referencing an unverified certificate alias are withheld from the policy entirely (§8.10.5). Fix the certificate first; the profile will re-send on its own.
- **A certificate failure is an app problem, not an MDM problem.** If the agent never installed, no certificate will ever be attempted, and the profile tables will show nothing wrong. Check that the agent app is present in the work profile before reading certificate state. The `installed_certificate` activities in `activity_past` are the server-side trail ([8.12](8.12-audit-logs.md)).

## 8.10.11 Narrowing the search

The first cut is **compare two integers**, not "is the host online".

```sql
SELECT ad.applied_policy_version,
       ad.last_policy_sync_time,
       MAX(p.included_in_policy_version) AS newest_written_version,
       MAX(pr.status_code)               AS newest_request_status
FROM   android_devices ad
JOIN   hosts h ON h.id = ad.host_id
LEFT   JOIN host_mdm_android_profiles p ON p.host_uuid = h.uuid
LEFT   JOIN android_policy_requests pr ON pr.request_uuid = p.policy_request_uuid
WHERE  h.uuid = '<host-uuid>'
GROUP  BY ad.id;
```

- **`newest_written_version` is NULL:** Fleet never wrote the profile into a policy. Look **left**. Check `cron_stats` for `mdm_android_profile_manager` (§8.10.7), then team scope, then whether the profile is being withheld by a pending certificate (§8.10.10).
- **`newest_request_status` is not `200`:** Google rejected the write. Look at `android_policy_requests.error_details` and `payload`. Everything device-side is irrelevant. This is the best-instrumented failure on Android; use it.
- **`newest_written_version` > `applied_policy_version`, `last_policy_sync_time` recent:** the device is talking to Google and has not applied the newest policy yet. Wait a cycle. If it never advances, the policy body is being partially rejected on the device, and the evidence will arrive as `nonComplianceDetails` in a later status report.
- **`newest_written_version` <= `applied_policy_version` but profiles still `pending`:** the device applied it and Fleet did not notice. **Go to Pub/Sub** (§8.10.6), not to the device. This is the Android-specific failure that has no equivalent on Apple or Windows.
- **`last_policy_sync_time` stale and fleet-wide:** Pub/Sub. Run the fleet-wide `MAX(last_policy_sync_time)` query in §8.10.6 before touching anything else.
- **No `android_devices` row:** the device never enrolled, or the `ENROLLMENT` notification never arrived, or it enrolled and has since been reconciled away. Fleet polls Google hourly to check which devices still exist, so a device removed at Google's end loses its row without any notification having failed. §8.10.8.

Second cut: **one host or all Android hosts.** All Android hosts stale at the same moment is Pub/Sub or the server URL. All Android hosts failing policy writes is the enterprise binding, the service account, or the fleetdm.com proxy. One host is the device, or that host's policy body.

Third cut, only if the write side is failing: **one profile or the whole set.** Because every profile for a host shares one policy PATCH, a single malformed profile fails all of them (§8.10.5).

**Do not bisect by removing profiles from a production team.** Two reasons. Removing a profile changes configuration for every host on that team, not just the one you are debugging. And once the shared failure count has reached three the set is already marked `failed`, so re-triggering the cron makes no further AMAPI request and proves nothing.

Bisect on a dedicated team with one test host and fresh copies of the profiles instead. To recover the production set once it has gone terminal, re-add the offending profile so it gets fresh state rather than waiting for a retry that will not come.

### Reproducing it

```sh
fleetctl trigger --name=mdm_android_profile_manager
```

Then watch, in order: a new `android_policy_requests` row (Fleet tried), its `status_code` (Google's answer), and a `Received PubSub message` line at DEBUG with `notification=STATUS_REPORT` for that device (the return path). Whichever of those three does not appear is the hop that is broken.

To shrink the case, put one Android host on a team with exactly one profile whose payload you control. A single-key policy that sets something visible on the device (camera disabled, for which Fleet publishes a ready-made example profile) gives you a change you can confirm by hand on the device in seconds. That is the one form of host-side verification Android offers. General technique: [8.11](8.11-reproducing-and-isolating.md).

### Before escalating

Collect: the Fleet version, the `android_devices` row, the last several `android_policy_requests` rows including `payload` and `error_details` verbatim, the `host_mdm_android_profiles` rows with `included_in_policy_version` and `request_fail_count`, whether Fleet uses the fleetdm.com proxy or a direct Google service account, whether the Fleet server URL has ever changed since Android was enabled, the Pub/Sub subscription's unacked count from the Google Cloud console, and the fleet-wide `MAX(last_policy_sync_time)`. See [8.13](8.13-escalation.md).

## Version notes

Android is the newest of the three MDM platforms in Fleet and moves fastest, so check the release notes at github.com/fleetdm/fleet/releases for anything in this section that does not match what you see.

| Change | Release |
|---|---|
| One-time job enabling application reports on the default policy | 4.76.0 |
| One-time migration moving Android hosts from a shared default policy to one policy per host | 4.77.0 |
| Profiles use content checksums to decide when to re-sync, so unrelated policy edits stop re-delivering everything | 4.87.0 |
| Lock, Wipe, and Clear passcode for Android. Lock and Clear passcode on both BYO and COBO, Wipe COBO-only. All Android commands issued with `duration=315360000s` (10 years) | 4.87.0 |
| BYO Unenroll issues an AMAPI `WIPE` that removes only the work profile. The `mdm_unenrolled` activity is emitted later, when the resulting notification arrives | 4.87.0 |
| Configurable `FLEET_MDM_ANDROID_BATCH_SIZE`, plus batching and staggered scheduling for Android software installs | 4.89.0 |
| `$FLEET_VAR_HOST_*` variables in Android configuration profiles and managed app configurations, with automatic resend when IdP values change | 4.89.0 |

**One caution about that batch-size row.** Fleet's release notes for 4.89.0 give the default as 1,000 hosts. The server registers **100**, and says so in the setting's own help text. The value in §8.10.7 is the one the server uses. If a future reader "corrects" this manual against the release notes, they will be introducing the error rather than fixing one.

The Android enterprise and enrollment token endpoints are marked **experimental** in Fleet's contributor API reference, meaning breaking changes to the API surface are expected. Do not build automation on them without pinning a version.

## Coverage gaps

Open questions, named plainly so nobody goes hunting:

- **Google account based enrollment** is named in Fleet's own MDM bug checklist but not described anywhere. Not documented; unverified.
- **What Google does between hops 4 and 6** has no observable surface from Fleet. Only the Google Cloud console and Google's admin surfaces see it.
- **Host refetch on Android** is not described anywhere in Fleet's documentation. Whether the UI's refetch control does anything for an Android host is unverified.
- **AMAPI non-compliance reason codes** are Google's vocabulary, and Fleet's documentation does not enumerate them. `host_mdm_android_profiles.detail` carries Google's text through; read it literally and check it against Google's API reference.
- **Whether an Android host can report success on a setting that did not actually apply** is not documented. Fleet trusts Google's compliance report.
