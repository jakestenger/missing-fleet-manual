# Inspecting server state

Fleet's server state is two stores. **MySQL** holds every queue, every per-host desired-vs-actual record, and the run history of every background schedule. **Redis** holds live query campaigns and their results, recorded server errors, IP banning and rate limiting, failing-policy sets, and a handful of caches. Both are external to the Fleet process, so restarting Fleet loses neither; what Redis survives beyond that is a question about your Redis, its persistence settings and its eviction policy, not about Fleet.

Some of what follows has no API at all. `cron_stats` is readable from the database alone, and it is the only way to interpret `fleetctl trigger`. Get a read-only MySQL user before you need one.

## 8.6.1 Safety

**Every query in this section is read-only.** Nothing here mutates state except the one documented exception below. Read-only is not the same as free, though: several of these group or filter fleet-wide without an index that supports them, and the disk-key candidate query can walk the whole host population. Read from the replica if you have one (`mysql_read_replica_address`), bound a time window where you can, and `EXPLAIN` anything fleet-wide before running it against a large deployment during an incident.

**Treat everything as read-only, with exactly one documented exception.**

| Mutation | Safe? | Effect |
|---|---|---|
| `UPDATE nano_dep_names SET syncer_cursor = NULL, syncer_cursor_at = NULL` | **Yes, at any scale.** Documented by Fleet | Next [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep) sync falls back to a full `fetch-devices`. Does not re-enroll devices, change ABM assignments, or re-push DEP profiles. See §8.6.9 |
| Anything else | **No** | Fleet's queues carry foreign keys, activation ordering, and checksums that the server maintains transactionally. Deleting a "stuck" row usually strands its siblings |

Deleting rows from `upcoming_activities`, `nano_enrollment_queue`, or `host_mdm_apple_profiles` to clear a jam is the tempting mistake this section exists to head off. The supported way to clear a host's queue is the API (cancel activity) or removing the profile from the fleet, both of which run the compensating writes.

## 8.6.2 `cron_stats`: did the job run?

**This is the table that answers "did the background job run, when, on which node, and with what errors."** There is no read API for it and no entry for it in Fleet's documentation. Without it, a `fleetctl trigger` result is uninterpretable (§8.6.2.4).

### 8.6.2.1 Schema

| Column | Type | Meaning |
|---|---|---|
| `id` | `int unsigned` | Autoincrement |
| `name` | `varchar(255)` | Schedule name. The same string `fleetctl trigger --name=` takes. §8.6.3 lists them |
| `instance` | `varchar(255)` | The Fleet instance that ran it. See §8.6.2.3 |
| `stats_type` | `varchar(255)` | `scheduled` or `triggered` |
| `status` | `varchar(255)` | `pending`, `completed`, `expired`, `canceled`, `queued` |
| `created_at` | `timestamp` | Start of the run |
| `updated_at` | `timestamp` | For a `completed` row, the end of the run |
| `errors` | `json`, nullable | JSON object keyed by **job ID**, value the error string. `NULL` when the run had no job errors |

Index: `(name, created_at)`.

`stats_type` and `status` are separate axes, and conflating them is common. No run ever carries a status of `triggered` or `scheduled`.

### 8.6.2.2 The query

Did this schedule run, when, where, with what errors:

```sql
SELECT name, instance, stats_type, status,
       created_at, updated_at,
       TIMESTAMPDIFF(SECOND, created_at, updated_at) AS duration_s,
       errors
FROM   cron_stats
WHERE  name = 'mdm_apple_profile_manager'
ORDER  BY created_at DESC
LIMIT  10;
```

Every schedule's most recent run, in one shot. This is the fastest way to tell one broken job from a wedged scheduler:

```sql
SELECT cs.name, cs.instance, cs.stats_type, cs.status,
       cs.created_at, cs.updated_at, cs.errors
FROM   cron_stats cs
JOIN  (SELECT name, MAX(created_at) AS created_at
       FROM   cron_stats
       GROUP  BY name) latest
  ON   latest.name = cs.name AND latest.created_at = cs.created_at
ORDER  BY cs.created_at ASC;
```

Read that output top-down. The oldest `created_at` is the schedule that has gone quiet, and a schedule whose newest row is much older than its interval (§8.6.3) has stopped running.

Only the runs that errored:

```sql
SELECT name, instance, status, created_at, JSON_KEYS(errors) AS failed_jobs, errors
FROM   cron_stats
WHERE  errors IS NOT NULL
ORDER  BY created_at DESC;
```

`JSON_KEYS(errors)` gives the job IDs that failed inside the schedule. A schedule is a set of jobs: one failing job leaves the others running, and the run still lands on `completed`. **A `completed` row with a non-`NULL` `errors` column is a partial failure, and it is easy to miss.**

Runs still in flight, plus anything wedged:

```sql
SELECT name, instance, stats_type, status, created_at,
       TIMESTAMPDIFF(MINUTE, created_at, NOW()) AS age_min
FROM   cron_stats
WHERE  status IN ('pending', 'queued')
ORDER  BY created_at ASC;
```

### 8.6.2.3 What `instance` tells you

`instance` is a random 64-byte identifier generated once per server process at startup and written to the server log as an `instance info` line carrying an `instanceID` field. The value maps to nothing in your infrastructure: not a hostname, not a pod name, not a task ARN. Two consequences:

- **On multi-node deployments, `instance` is the only field that says which node ran the job.** A single node that has lost its Redis or Apple connectivity will fail jobs while the others succeed, and every symptom will look intermittent until you group by `instance`.
- **A changed `instance` value across consecutive runs means a different Fleet process ran the schedule.** On a multi-node deployment that is the normal case, because every process competes for the lock, so it is not by itself evidence of a restart. It becomes one only when your logs or orchestrator show both values belonging to successive processes on the same node.

To map an `instance` back to a pod, grep your server logs for the value. That log line is emitted at startup only.

```sql
SELECT instance, COUNT(*) AS runs,
       SUM(errors IS NOT NULL) AS runs_with_errors,
       MIN(created_at) AS first_seen, MAX(created_at) AS last_seen
FROM   cron_stats
WHERE  created_at > NOW() - INTERVAL 6 HOUR
GROUP  BY instance;
```

One instance with a high `runs_with_errors` and the others clean localises the problem to a node before you read a single log.

The literal string `trigger-api` in `instance` is a sentinel rather than a node. Fleet writes it when a trigger is queued for a schedule that runs on a different server (§8.6.3). When the owning node picks the trigger up, it overwrites `instance` with its own ID.

### 8.6.2.4 Status transitions, and why a trigger can lie

| Status | Written when |
|---|---|
| `queued` | A trigger was requested for a schedule this node does not run. Waiting for the owning node's poll |
| `pending` | The run has started. Row inserted at start of run |
| `completed` | The run finished. `updated_at` is the end time. `errors` may still be non-`NULL` |
| `canceled` | The run was interrupted by shutdown, or the process was stopped with a run in flight. On graceful shutdown Fleet flips all of that instance's `pending` rows to `canceled` |
| `expired` | Reaped. `pending` or `queued` for more than 2 hours with no live lock in the `locks` table, or more than 12 hours regardless of lock state |

`canceled` and `expired` differ by who wrote the row. A cancelled run gets its terminal status from the instance that was running it, seconds after the cancellation, so it never sits around long enough to be reaped. `expired` belongs to the cleanup pass, and its usual meaning is that nobody ever closed the row out, because the process that owned it went away without writing anything.

> ### ⚠️ Five schedules can be marked `expired` while they are still running
>
> The two-hour rule spares a run whose schedule still holds a live lock, and it finds that lock by matching the lock's name against the schedule's name. Five schedules take their lock under a different name, so that match never succeeds for them:
>
> | Schedule | Lock name it actually takes |
> |---|---|
> | `cleanups_then_aggregation` | leader |
> | `frequent_cleanups` | leader_frequent_cleanups |
> | `integrations` | worker |
> | `apple_mdm_worker` | apple_mdm |
> | `calendar` | calendar, registered separately from the schedule |
>
> For those five the lock lookup finds nothing, so the reaper falls through to the two-hour timeout and stamps `expired` on a run that is alive and working. The twelve-hour hard cap behaves the same way for everything else.
>
> This matters most where it is most misleading. `cleanups_then_aggregation` runs roughly forty jobs on an hourly schedule, and on a large estate a pass taking more than two hours is not remarkable. Its `cron_stats` row will say `expired` anyway.
>
> **So `expired` on one of those five is not evidence that anything died.** Confirm with the instance's own log before treating it as a fault, and use the `pending` and `queued` age query above rather than the status, since the row's `created_at` is still the truth about when the run started.

`fleetctl trigger --name=<schedule>` returns without triggering in three cases:

1. A `scheduled` run is already `pending`.
2. A `triggered` run is already `pending` or `queued`.
3. The internal trigger channel is busy. Logged as `trigger channel not available`, at debug level.

Cases 1 and 2 surface as an HTTP 409 with a message like `conflicts with current status of <name> schedule: scheduled run started 12.5s ago`. Case 3 looks exactly like success, and at the default log level it leaves no trace.

**Never interpret a trigger without reading `cron_stats` afterward.** The confirmation you want is a new row with `stats_type = 'triggered'`:

```sql
SELECT id, instance, status, created_at, updated_at, errors
FROM   cron_stats
WHERE  name = 'apple_mdm_dep_profile_assigner'
  AND  stats_type = 'triggered'
ORDER  BY created_at DESC
LIMIT  3;
```

If the newest `triggered` row predates your command, nothing ran.

### 8.6.2.5 Retention

Rows are **deleted after 2 days**. That cleanup runs hourly and sits outside the schedule system on purpose, because the schedule system reads `cron_stats` to decide whether to run.

Two days is short. If you are investigating something that happened last week the cron history is gone, so capture `cron_stats` early in an incident, before it ages out.

When Fleet asks itself for the latest state of a schedule it reads at most two rows: the newest `scheduled` row with status `pending` or `completed`, and the newest `triggered` row with status `pending`, `completed`, or `queued`. `expired` and `canceled` rows fall outside that window, so read those yourself.

## 8.6.3 The named schedules

Thirty-five schedules can be registered: the thirty-four Fleet names in its own list, plus `mdm_service_discovery`, which is registered with a literal name that never made it into that list. Which of them actually start depends on the deployment. Premium-only schedules are skipped without a licence, several are gated on config, and the two software migrations register only when a software installer store is configured. Column three is what the schedule owns, so you can map a symptom to the job that would have produced it. These names and intervals come from the server itself; Fleet does not document them.

Trigger any of them:

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

An invalid name returns a 404 whose body lists every schedule the server actually registered. That is the authoritative list for a given deployment, and it is shorter than the table above when the license is Free or a schedule is disabled.

**`vulnerabilities` is special.** When processing is disabled on a node (`vulnerabilities.disable_schedule`, or `current_instance_checks` set to `no`), Fleet registers a proxy in its place. Triggering it inserts a `cron_stats` row with `status = 'queued'` and `instance = 'trigger-api'`; the node that actually runs vulnerabilities polls for that row **every 60 seconds** and claims it. So a queued trigger takes up to a minute to start, and if it stays `queued` past that, the processing node is down.

## 8.6.4 `upcoming_activities`: the unified per-host queue

One table holds the queue for scripts, software installs, software uninstalls, [VPP](../09-appendices/a.6-glossary-and-release-compatibility.md#vpp) installs, and in-house app installs. Type-specific arguments live in sibling tables (`script_upcoming_activities`, `software_install_upcoming_activities`, `vpp_app_upcoming_activities`, `in_house_app_upcoming_activities`), keyed by `upcoming_activities.id`.

| Column | Type | Meaning |
|---|---|---|
| `id` | `bigint unsigned` | Autoincrement |
| `host_id` | `int unsigned` | Joins `hosts.id` |
| `priority` | `int`, default 0 | Higher runs first. Setup-experience items use a raised priority |
| `user_id` | `int unsigned`, nullable | Who requested it. `NULL` for Fleet-initiated work |
| `fleet_initiated` | `tinyint(1)` | 1 when Fleet queued it, not a user |
| `activity_type` | `enum` | `script`, `software_install`, `software_uninstall`, `vpp_app_install`, `in_house_app_install` |
| `execution_id` | `varchar(255)`, unique | The ID you see in the API, in activity records, and in `host_script_results` / `host_software_installs` |
| `payload` | `json` | Type-dependent. Keys seen in Fleet's own queries include `$.user.name`, `$.user.email`, `$.software_title_name`, `$.installer_filename`, `$.source` |
| `activated_at` | `datetime(6)`, **nullable** | **`NULL` = queued, not started. Non-`NULL` = started** |
| `created_at` / `updated_at` | `datetime(6)` | Enqueue time and last change |

### 8.6.4.1 Activation semantics

Fleet activates **one activity at a time per host**. When an activity reaches a final state, Fleet deletes its row and activates the next one, ordered by:

```
ORDER BY (activated_at IS NOT NULL) DESC, priority DESC, created_at ASC
```

Activation means inserting into the executing table (`host_script_results` for scripts, `host_software_installs` for installs, `host_vpp_software_installs` plus a nano queue entry for VPP) and stamping `activated_at`. Consecutive `vpp_app_install` rows are batch-activated up to **5** at a time to cut push count.

So `activated_at IS NULL` on the top row of a host's queue while nothing is running means the queue is **blocked**, not merely waiting. The `upcoming_activities_maintenance` cron unblocks up to 500 hosts every 10 minutes.

### 8.6.4.2 Queries

Everything queued for one host, in execution order:

```sql
SELECT ua.id, ua.activity_type, ua.execution_id, ua.priority,
       ua.fleet_initiated,
       ua.activated_at,
       ua.created_at,
       TIMESTAMPDIFF(MINUTE, ua.created_at, NOW()) AS age_min,
       ua.payload
FROM   upcoming_activities ua
JOIN   hosts h ON h.id = ua.host_id
WHERE  h.uuid = '<host-uuid>'
ORDER  BY (ua.activated_at IS NOT NULL) DESC, ua.priority DESC, ua.created_at ASC;
```

Queue depth by type, fleet-wide:

```sql
SELECT activity_type,
       COUNT(*)                                AS total,
       SUM(activated_at IS NULL)               AS not_started,
       SUM(activated_at IS NOT NULL)           AS in_flight,
       MIN(created_at)                         AS oldest
FROM   upcoming_activities
GROUP  BY activity_type;
```

Hosts whose queue is not draining, worst first. This is the query that turns "ten pending" into a diagnosis:

```sql
SELECT h.id, h.hostname, h.uuid,
       COUNT(*) AS queued,
       MIN(ua.created_at) AS oldest,
       TIMESTAMPDIFF(HOUR, MIN(ua.created_at), NOW()) AS oldest_age_h,
       SUM(ua.activated_at IS NOT NULL) AS activated
FROM   upcoming_activities ua
JOIN   hosts h ON h.id = ua.host_id
GROUP  BY h.id, h.hostname, h.uuid
HAVING oldest_age_h > 2
ORDER  BY queued DESC
LIMIT  50;
```

`activated = 0` with a large `queued` is a blocked queue. `activated = 1` with a large `queued` and an old `oldest` is one stuck activity holding the line, and the `execution_id` of the activated row is what you take to `host_script_results` or `host_software_installs`.

**Depth over time is the signal, not depth.** Run the fleet-wide query twice, twenty minutes apart. Growing means the drain is broken. Shrinking means wait.

Find one execution ID anywhere:

```sql
SELECT 'upcoming' AS src, host_id, activity_type, activated_at, created_at
FROM   upcoming_activities WHERE execution_id = '<execution-id>'
UNION ALL
SELECT 'script', host_id, 'script', NULL, created_at
FROM   host_script_results WHERE execution_id = '<execution-id>';
```

## 8.6.5 Apple MDM tables

The Apple MDM stack is NanoMDM. Its tables are prefixed `nano_` and are joined to Fleet's by **`hosts.uuid = nano_enrollments.id`** for the device channel.

| Table | Holds |
|---|---|
| `nano_devices` | One row per device that ever completed `Authenticate`. `id` (UDID), `serial_number`, `identity_cert`, `authenticate` / `authenticate_at`, `token_update` / `token_update_at`, `bootstrap_token_b64` / `bootstrap_token_at`, `unlock_token` / `unlock_token_at`, `platform`, `enroll_team_id` |
| `nano_enrollments` | One row per channel. `id`, `device_id`, `user_id`, `type`, `topic`, `push_magic`, `token_hex`, `enabled`, `token_update_tally`, `last_seen_at`, `enrolled_from_migration`, `hardware_attested` |
| `nano_commands` | The command itself, once, shared across recipients. `command_uuid`, `request_type`, `command` (the raw plist), `subtype` (`None` or `ProfileWithSecrets`), `name` |
| `nano_enrollment_queue` | The per-enrollment queue. `id`, `command_uuid`, `active`, `priority`, `created_at` |
| `nano_command_results` | Device replies. `id`, `command_uuid`, `status`, `result` (raw XML), `not_now_at`, `not_now_tally` |
| `nano_view_queue` | **A view** joining the three above. Use this instead of writing the join |
| `nano_dep_names` | Per-ABM-token DEP state. `name`, OAuth credentials, `access_token_expiry`, `syncer_cursor`, `syncer_cursor_at`, `assigner_profile_uuid`, `assigner_profile_uuid_at` |
| `nano_cert_auth_associations` | Device identity cert binding. `id`, `sha256`, `cert_not_valid_after`, `renew_command_uuid` |
| `nano_push_certs` | APNs push certificate per `topic`. `cert_pem`, `key_pem`, `stale_token` |

`nano_enrollments.type` carries the NanoMDM enrollment type: `Device`, `User`, `User Enrollment (Device)`, `User Enrollment`, `Shared iPad`. Fleet's own queries filter to `type IN ('Device', 'User Enrollment (Device)')` when they want the device channel.

`nano_command_results.status` carries Apple's value: `Acknowledged`, `Error`, `CommandFormatError`, `NotNow`. `Idle` is never stored. A `NotNow` reply leaves the queue row `active` and bumps `not_now_tally`; `not_now_at` records only the **first** `NotNow`.

### 8.6.5.1 Queries

The command queue for a host, with results, using the view:

```sql
SELECT q.command_uuid, q.request_type, q.name,
       q.active, q.priority, q.created_at,
       q.status, q.result_updated_at
FROM   nano_view_queue q
WHERE  q.id = '<host-uuid>'
ORDER  BY q.priority DESC, q.created_at;
```

Commands sent but never answered, oldest first. This is class 3/4 in the §8.1.5 taxonomy:

```sql
SELECT ne.id AS host_uuid, h.hostname,
       nc.request_type, nc.command_uuid,
       neq.created_at,
       TIMESTAMPDIFF(HOUR, neq.created_at, NOW()) AS age_h
FROM   nano_enrollment_queue neq
JOIN   nano_commands nc     ON nc.command_uuid = neq.command_uuid
JOIN   nano_enrollments ne  ON ne.id = neq.id
LEFT  JOIN nano_command_results ncr
       ON ncr.command_uuid = neq.command_uuid AND ncr.id = neq.id
LEFT  JOIN hosts h ON h.uuid = ne.device_id
WHERE  neq.active = 1
  AND  ncr.status IS NULL
ORDER  BY neq.created_at ASC
LIMIT  100;
```

Hosts whose MDM channel has gone quiet. `last_seen_at` moves on any MDM check-in, including `Idle`, so a stale value with `enabled = 1` is a dead push path, not a busy device:

Devices assigned to Fleet in Apple Business that have not enrolled. ## 8.6.7 Desired vs actual, per host

These are the tables that say what Fleet **wants** on a host and what it **believes** is there. All four profile tables share `status`, `operation_type`, and `detail`.

| Table | Key | Extra columns |
|---|---|---|
| `host_mdm_apple_profiles` | `host_uuid`, `profile_uuid` | `profile_identifier`, `profile_name`, `command_uuid`, `checksum`, `retries`, `scope` (`System`/`User`), `secrets_updated_at`, `variables_updated_at`, `ignore_error`, `has_acme_payload` |
| `host_mdm_windows_profiles` | `host_uuid`, `profile_uuid` | `profile_name`, `command_uuid`, `checksum`, `retries`, `secrets_updated_at` |
| `host_mdm_apple_declarations` | `host_uuid`, `declaration_uuid` | `declaration_identifier`, `declaration_name`, `token`, `resync`, `scope`, `secrets_updated_at`, `variables_updated_at`, `assets_updated_at`, `activation_updated_at` |
| `host_mdm_android_profiles` | `host_uuid`, `profile_uuid` | `profile_name`, `policy_request_uuid`, `device_request_uuid`, `request_fail_count`, `included_in_policy_version`, `can_reverify`, `checksum` |

`status` is one of `pending`, `verifying`, `verified`, `failed`, or `NULL`. `operation_type` is `install` or `remove`.

**`verifying` and `verified` are different claims, on Apple.** `verifying` means Fleet sent the command and got an acknowledgement but has not yet confirmed the profile is present via its own verification pass. `verified` means it confirmed. A host sitting at `verifying` indefinitely is a §8.1.5 class 6 shape, so look on the host before you look in the queue: delivery already succeeded by the time this state is reached.

**On Windows, `verified` is a weaker claim and does not mean that**, for ordinary profiles: Fleet maps any successful SyncML response straight to `verified`, a `202 Accepted` included, with no read-back at all. The exception is a profile using a Fleet-proxied SCEP certificate, which does get independent confirmation. Do not read a Windows `verified` as evidence the setting is in force ([8.9](8.9-windows-mdm-diagnostics.md)).

Everything Fleet thinks it owes one host:

```sql
SELECT 'apple'  AS kind, profile_name AS name, status, operation_type, retries,
       command_uuid, detail
FROM   host_mdm_apple_profiles       WHERE host_uuid = '<host-uuid>'
UNION ALL
SELECT 'declaration', declaration_name, status, operation_type, 0, '', detail
FROM   host_mdm_apple_declarations   WHERE host_uuid = '<host-uuid>'
UNION ALL
SELECT 'windows', profile_name, status, operation_type, retries, command_uuid, detail
FROM   host_mdm_windows_profiles     WHERE host_uuid = '<host-uuid>'
UNION ALL
SELECT 'android', profile_name, status, operation_type, request_fail_count, '', detail
FROM   host_mdm_android_profiles     WHERE host_uuid = '<host-uuid>';
```

Fleet-wide profile failure summary, which tells you whether it is one profile or one fleet:

```sql
SELECT profile_name, status, operation_type, COUNT(*) AS hosts,
       SUBSTRING(MAX(detail), 1, 200) AS sample_detail
FROM   host_mdm_apple_profiles
WHERE  status = 'failed'
GROUP  BY profile_name, status, operation_type
ORDER  BY hosts DESC;
```

`retries` above 0 with `status = 'pending'` means Fleet has already resent and is waiting again. A `retries` value that is climbing across observations is a profile the device keeps rejecting.

| `host_mdm_managed_certificates` | `host_uuid`, `profile_uuid` | `type` (`digicert`, `custom_scep_proxy`, `ndes`, `smallstep`), `ca_name`, `serial`, `not_valid_before`, `not_valid_after`, `challenge_retrieved_at` |

`host_mdm.enrollment_status` is `GENERATED ALWAYS AS` a `CASE` over `enrolled`, `installed_from_dep`, `is_server`, and `is_personal_enrollment`. Values: `On (manual)`, `On (automatic)`, `On (manual - personal)`, `Pending`, `Off`, or `NULL` when `is_server = 1`. You cannot write it. It is the exact field that reads healthy in the half-enrolled state described in [8.1](8.1-diagnostic-method.md), because MDM enrollment and agent presence are independent.

#### One status, three vocabularies

The value in the database is not the string on the screen, and neither is the string you filter by. Fleet renames one of them for display and keeps the old name in the API for compatibility, so a query written from what the console shows returns nothing.

| Database and API | What the console displays | What the host filter takes |
|---|---|---|
| `On (automatic)` | **On (company-owned)** | `automatic` |
| `On (manual)` | On (manual) | `manual` |
| `On (manual - personal)` | On (manual - personal) | `personal` |
| `Pending` | Pending | `pending` |
| `Off` | Off | `unenrolled` |

Two consequences worth carrying. **`On (company-owned)` never appears in the database or in an API response**, so `WHERE enrollment_status = 'On (company-owned)'` matches zero rows however many company-owned hosts you have; the stored value is `On (automatic)`. And **there is no status called `On (personal)`**: the personal-device value is `On (manual - personal)` in every layer. Elsewhere in Part VIII this manual uses the console vocabulary when it is describing what an administrator sees, which is the right register there and the wrong string to put in SQL.

```sql
SELECT h.hostname, h.uuid, hm.enrolled, hm.enrollment_status,

FROM   host_mdm hm
JOIN   hosts h ON h.id = hm.host_id
WHERE  h.uuid = '<host-uuid>';
```

### 8.6.7.2 Half-enrolled hosts: MDM live, agent stale

8.6.7.1 noted that `host_mdm.enrollment_status` reads healthy in the half-enrolled state, because MDM enrollment and agent presence are independent. This query finds those hosts, and neither host-list filter does. The online/offline axis is time since the agent was last seen, so a half-enrolled host reads offline, the same label a sleeping laptop gets. Missing/MIA is worse for it: that filter takes the greater of the agent and MDM timestamps, so a fresh Apple MDM check-in keeps the host out of the bucket even when the agent has never checked in. The two channels have to be compared separately, which the schema allows because it keeps the timestamps apart: `host_seen_times.seen_time` is the agent channel, and `nano_enrollments.last_seen_at` is the Apple MDM channel, which advances on any MDM message including `Idle`.

```sql
-- Example thresholds only; choose them for your estate.
SELECT h.hostname,
       h.uuid,
       h.platform,
       hm.enrollment_status,
       hst.seen_time   AS agent_last_seen,
       ne.last_seen_at AS mdm_last_seen
FROM hosts h
JOIN host_mdm hm
  ON hm.host_id = h.id
JOIN nano_enrollments ne
  ON ne.id = h.uuid
 AND ne.type IN ('Device', 'User Enrollment (Device)')
 AND ne.enabled = 1
LEFT JOIN host_seen_times hst
  ON hst.host_id = h.id
WHERE h.platform = 'darwin'
  AND hm.enrolled = 1
  AND ne.last_seen_at >= NOW() - INTERVAL 7 DAY
  AND (
        hst.seen_time IS NULL
        OR hst.seen_time < NOW() - INTERVAL 7 DAY
      )
ORDER BY ne.last_seen_at DESC;
```

Join on `ne.id = h.uuid`, the enrollment channel's own key, rather than `ne.device_id`, the parent-device key. For the two device-channel types in the filter they coincide today, but `id` is the correct key and stays correct if that filter ever widens to user channels. The seven-day windows are operational choices and not Fleet guarantees: set the agent threshold to a few multiples of your osquery interval, and the MDM threshold to how recently you require the MDM channel to have spoken.

This detector is macOS-only, by the `h.platform = 'darwin'` filter, and the other platforms stay out of it on purpose.

- **iOS and iPadOS** run no agent, so an absent `seen_time` is normal rather than a fault. The `darwin` filter keeps them out.
- **Linux** runs an agent but has no `host_mdm` row, so it never enters an MDM-anchored query.
- **ChromeOS** is the inverse case. It has an agent, the Fleetd for Chrome extension, which writes `host_seen_times`, but it has no `host_mdm` row and no `nano_enrollments` row, because Fleet does not MDM-manage the device ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)). Chrome hosts never enter this query, and it neither flags nor helps them.
- **Windows** populates `host_mdm` but not `nano_enrollments`, which is Apple-only, so there is no MDM last-seen timestamp to compare against. A Windows half-enrolled host needs a separate detector, and `mdm_windows_enrollments` carries no `last_seen_at` column to build one from ([8.6.6](#866-windows-mdm-tables)).

This is the mirror of the gone-quiet query in [8.6.5.1](#8651-queries): that one finds a live agent behind a silent MDM channel, and this one finds a live MDM channel in front of a silent agent. They belong side by side, and [8.4](8.4-host-side-investigation.md) sends you here for exactly this detection.

### `jobs`

The async worker queue. Three schedules drain it, each taking a different subset of the `name` column: `integrations` and `apple_mdm_worker` between them handle most of it, while `scheduled_batch_activities` takes the batch-script rows.

Job names and schedule names look alike and are different things. A value in `jobs.name` is a unit of work; a schedule name is what `fleetctl trigger` accepts. The pair to keep straight is `apple_mdm_worker`, which is the schedule and the thing `fleetctl trigger` accepts, and `apple_mdm`, which is the `jobs.name` value that schedule drains and also its alternate lock name. A trigger for `apple_mdm` gets you nothing.

| Column | Meaning |
|---|---|
| `name` | `apple_mdm`, `macos_setup_assistant`, `apple_software`, `software_worker`, `jira`, `zendesk`, `db_migration`, `batch_scripts`, `chart_scrub_dataset_global`, `chart_scrub_dataset_fleet` |
| `args` | `json` |
| `state` | `queued`, `success`, `failure` |
| `retries` | Attempt count |
| `error` | `text`. The full error, unlike `setup_experience_status_results.error` |
| `not_before` | Do not run until this time. **A future `not_before` is backoff, not a stall** |

```sql
SELECT name, state, retries, not_before, created_at, updated_at,
       SUBSTRING(error, 1, 300) AS error
FROM   jobs
WHERE  state != 'success'
ORDER  BY created_at DESC
LIMIT  50;
```

Backlog by name, and whether it is moving:

```sql
SELECT name, state, COUNT(*) AS n,
       MIN(created_at) AS oldest, MAX(not_before) AS latest_not_before
FROM   jobs
GROUP  BY name, state
ORDER  BY n DESC;
```

Successful rows are removed by `cleanup_worker_jobs` inside `cleanups_then_aggregation`, so a large `success` count means that cron has not run recently. Check `cron_stats`.

### `host_disk_encryption_keys`

| Column | Meaning |
|---|---|
| `host_id` | The host |
| `base64_encrypted` | The escrowed key, **encrypted**. Not readable from SQL |
| `base64_encrypted_salt`, `key_slot` | Linux LUKS specifics |
| `decryptable` | `NULL` = not yet checked, `1` = Fleet can decrypt it, `0` = it cannot |
| `reset_requested` | A key rotation was asked for |
| `client_error` | What the host reported when escrow failed. **This is the useful column** |

```sql
SELECT h.hostname, h.platform, hdek.decryptable, hdek.reset_requested,
       hdek.key_slot, hdek.client_error, hdek.updated_at
FROM   host_disk_encryption_keys hdek
JOIN   hosts h ON h.id = hdek.host_id
WHERE  hdek.decryptable IS NOT TRUE

```

`decryptable = 0` means the key on file cannot be decrypted with the current credentials, so the escrowed value is useless and the host needs to re-escrow. `decryptable IS NULL` means the `verify_disk_encryption_keys` job inside `cleanups_then_aggregation` has not evaluated it yet. If a lot of rows are `NULL`, check that schedule in `cron_stats` before assuming a key problem.

Apple and Windows hosts with no escrowed key row at all. Read this as a **candidate list, not a violation list**: it tests platform and the absence of a key, and nothing here knows whether disk encryption is actually enforced for that host's fleet, or whether the host is MDM-enrolled. SELECT h.id, h.hostname, h.platform
```sql
FROM   hosts h
LEFT  JOIN host_disk_encryption_keys hdek ON hdek.host_id = h.id
WHERE  hdek.host_id IS NULL
  AND  h.platform IN ('darwin', 'windows');
```

### `mdm_config_assets`

Fleet's encrypted asset store, soft-deleted rather than removed. It holds most MDM credentials, though not all of them: ABM tokens carry their own OAuth material in `nano_dep_names`, and VPP tokens have their own tables.

| Column | Meaning |
|---|---|
| `name` | Asset name. See below |
| `value` | `longblob`, **encrypted with `server_private_key`**. Unreadable in SQL |
| `md5_checksum` | Checksum of the encrypted value |
| `deleted_at` / `deletion_uuid` | Soft delete. Live rows have `deletion_uuid = ''` |

Known names: `ca_cert`, `ca_key`, `apns_cert`, `apns_key`, `abm_cert`, `abm_key`, `scep_challenge`, `ndes_password`, `android_pubsub_token`, `android_fleet_server_secret`, `host_identity_ca_cert`, `host_identity_ca_key`, `conditional_access_ca_cert`, `conditional_access_ca_key`, `conditional_access_idp_cert`, `conditional_access_idp_key`, `psso_signing_key`, `psso_ca_cert`, `psso_encryption_key`, `vpp_proxy_bearer_token`, `apple_account_provisioning_idp_client_secret`. The legacy `abm_token` and `vpp_token` names are deprecated.

The diagnostic use is presence and count, not content:

```sql
SELECT name, COUNT(*) AS live_rows, MAX(created_at) AS newest
FROM   mdm_config_assets
WHERE  deleted_at IS NULL AND deletion_uuid = ''
GROUP  BY name
ORDER  BY name;
```

A missing `apns_cert` or `abm_cert` row explains an entire subsystem being dark. There is never more than one live row per name: a unique index on the name and the deletion marker allows only one row with an empty `deletion_uuid`.

**If `server_private_key` changes or is lost, every row here becomes unreadable** and Fleet cannot decrypt its own APNs key. The symptom is total MDM failure with valid Apple credentials. Check whether the key changed before checking Apple.

## 8.6.9 DEP sync, and the one safe mutation

Fleet syncs ABM-assigned devices through NanoDEP, driven by a cursor stored per ABM token in `nano_dep_names`.

| Cursor state | Apple API Fleet calls |
|---|---|
| `syncer_cursor IS NULL` | `fetch-devices` (full list) |
| `syncer_cursor` set | `sync-devices` (deltas only) |

Mechanics:

- **200 devices per request**, looping until Apple reports no more pages.
- Cadence is `mdm.apple_dep_sync_periodicity`, **default 1 minute**.
- **Apple expires cursors after 7 days.** Fleet recovers on its own by falling back to a full fetch.
- Devices that hit Apple's throttling threshold stop being returned on cursor requests until the cooldown ends.

```sql
SELECT name,
       syncer_cursor IS NOT NULL AS has_cursor,
       syncer_cursor_at,
       TIMESTAMPDIFF(HOUR, syncer_cursor_at, NOW()) AS cursor_age_h,
       access_token_expiry,
       DATEDIFF(access_token_expiry, NOW())          AS token_days_left,
       assigner_profile_uuid_at
FROM   nano_dep_names;
```

`cursor_age_h` above 168 means the cursor is past Apple's expiry and the next sync will full-fetch anyway. `token_days_left` going negative is an expired ABM token, and that presents as "new devices stopped appearing" with no error anywhere in the UI.

### Resetting the cursor

```sql
UPDATE nano_dep_names
SET    syncer_cursor    = NULL,
       syncer_cursor_at = NULL;
```

Then force the sync and confirm it ran:

```sh
fleetctl trigger --name=apple_mdm_dep_profile_assigner
```

```sql
SELECT instance, stats_type, status, created_at, updated_at, errors
FROM   cron_stats
WHERE  name = 'apple_mdm_dep_profile_assigner'
ORDER  BY created_at DESC LIMIT 3;
```

**This is fine on large deployments.** It does not re-enroll devices, change ABM assignments, or re-push DEP profiles. It re-baselines Fleet's assignment list, nothing more. Add a `WHERE name = '<token-name>'` clause if you have multiple ABM tokens and only want to reset one.

## 8.6.10 Redis

Redis holds live query campaigns and their results, recorded server errors, IP banning and rate limit counters, failing-policy sets, and a small key-value cache. **Treat everything in it as ephemeral.** Losing Redis data resets in-flight live reports, the recorded error buffer, IP-ban and rate-limit counters, and the failing-policy sets awaiting delivery. Those sets feed Jira and Zendesk tickets as well as webhooks, so all three are lost together ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)). None of that is the system of record, which is the design ([1.6](../01-foundations/1.6-the-fleet-server.md)), but a notification that was owed and never sent does not come back.

| Key pattern | Holds |
|---|---|
| `livequery:{<campaignID>}` | Bitfield of target host IDs. The braces are literal, and are the cluster hash tag |
| `sql:livequery:{<campaignID>}` | The campaign's SQL |
| `livequery:active` | Set of active campaign IDs |
| `livequery:active:reverse`, `livequery:host:<hostID>` | Reverse targeting model: campaign IDs per host |
| `results_<campaignID>` | A **pub/sub channel** rather than a key. Results stream over it |
| `error:{<hash>}:json` | A recorded server error, JSON |
| `error:{<hash>}:count` | Occurrence count for that error |
| `policies:failing:<policyID>`, `policies:failing_sets` | Hosts failing each policy, awaiting webhook |

### Reading the recorded errors

```sh
fleetctl debug errors                 # non-destructive
fleetctl debug errors --flush         # reads, then clears
```

They live in Redis under `error:{…}:json` rather than in any log file, with a TTL set by `logging.error_retention_period`, **default 24 hours**. Capture before you flush, and remember they age out. Detail in [8.5](8.5-fleetctl-debug.md).

### The pub/sub buffer limit

Live report results reach the browser as: device → Fleet → Redis pub/sub → the Fleet node holding the websocket → browser. Redis drops a pub/sub subscriber that falls behind its output buffer, and Fleet is that subscriber.

Default:

```
client-output-buffer-limit pubsub 32mb 8mb 60
```

Hard limit 32 MB, soft limit 8 MB sustained for 60 seconds. On a large fleet with a wide result set, a live report can cross 8 MB of buffered output and get its subscriber killed. The symptom is a live report that returns partial results and then stops, with no error in Fleet's logs.

To remove the limits:

```
client-output-buffer-limit pubsub 0 0 0
```

**AWS ElastiCache does not accept that syntax.** Set three separate parameter-group values instead:

| Redis config | ElastiCache parameter |
|---|---|
| hard limit (first value) | `client-output-buffer-limit-pubsub-hard-limit` |
| soft limit (second value) | `client-output-buffer-limit-pubsub-soft-limit` |
| soft seconds (third value) | `client-output-buffer-limit-pubsub-soft-seconds` |

Confirm what is actually in effect rather than what the parameter group says:

```sh
redis-cli CONFIG GET 'client-output-buffer-limit'
```

More on this failure mode, and the rest of the degradation procedure, in [8.14](8.14-degradation.md).

### Redis health at a glance

```sh
redis-cli INFO clients      # connected_clients, blocked_clients, client_output_buffer figures
redis-cli INFO stats        # pubsub_channels, expired_keys, evicted_keys
redis-cli INFO memory       # used_memory, maxmemory, maxmemory_policy
redis-cli INFO replication
```

`evicted_keys` climbing on a Redis with a `maxmemory_policy` other than `noeviction` means Fleet's keys are being thrown away under pressure, and live reports will fail non-deterministically. Fleet expects Redis to keep every key it writes.

Count live query campaign keys without blocking the server. Never run `KEYS` on production:

```sh
redis-cli --scan --pattern 'livequery:*' | head -50
redis-cli SCARD livequery:active
```

A large and growing `livequery:active` means campaigns are not being cleaned up. That cleanup is the `cleanup_live_queries` and `distributed_query_campaigns` jobs inside `cleanups_then_aggregation`, so check that schedule in `cron_stats`.

If Fleet is deployed against a Redis **cluster**, the braces in key names (`error:{<hash>}:json`, `livequery:{<id>}`) are hash tags that keep related keys on one slot. Do not rewrite them.

## 8.6.11 Getting access

`fleetctl debug archive` needs a MySQL user with global **PROCESS** and **SELECT** privileges. A `Failed profile` message means the CPU profile member genuinely failed to collect, which is expected when you run the command from outside the server's own environment and is not a reason to stop. It is still a member you did not get, so say so when you hand the archive on ([8.5](8.5-fleetctl-debug.md)).

For the queries in this section, `SELECT` on the Fleet schema is enough:

```sql
CREATE USER 'fleet_ro'@'%' IDENTIFIED BY '<password>';
GRANT SELECT ON fleet.* TO 'fleet_ro'@'%';
```

Point it at the read replica if one is configured. Read replica settings are fully independent from the primary, so `mysql_read_replica_address` and its siblings must all be set explicitly.

> **Set this up before an escalation call, not during one.** In hosted deployments there is often no DB access path at all, and opening a change request to create the user is a multi-day lead time on something that takes thirty seconds to use. `cron_stats` is the item most likely to be needed and least likely to be reachable.

## 8.6.12 Triggering is writable, reading the result is not

There is **no read API for `cron_stats`**. `POST /api/v1/fleet/trigger` exists and takes an authenticated user with write permission on Fleet's schedules, so a user can force a schedule and then has no supported way to find out whether it ran. Every observation in §8.6.2 needs database access, which makes that access a prerequisite for diagnosing anything scheduled.

## 8.6.13 Scoping: which fleet, which labels, was this host targeted

Class 1 in §8.1.5, and the cheapest class to rule out. A host that was never targeted produces no delivery row and no delivery log, so the silence is a targeting answer rather than a delivery failure. Everything here is `SELECT` only.

| Question | Table |
|---|---|
| Which fleet does Fleet think this host is in | `hosts.team_id`. `NULL` is the no-fleet scope, which is a **sibling** of the named fleets and not their parent |
| Is the host's label state trusted, and how fresh is it | `hosts.label_updated_at`, stamped on every full label report |
| Is the host in this label | `label_membership (host_id, label_id)`, `created_at`, `updated_at`. **No status column**: a stale row and a correct row look identical |
| What kind of label is this | `labels.label_membership_type`: 0 dynamic, 1 manual, 2 host vitals. `labels.label_type = 1` marks a built-in. `labels.team_id` non-NULL confines it to one fleet |
| What scope did the item actually store | `mdm_configuration_profile_labels`, `mdm_declaration_labels`, `software_installer_labels`, `vpp_app_team_labels`, `in_house_app_labels`, `policy_labels`. The pair `exclude` / `require_all` is the scope: `0/0` include-any, `0/1` include-all, `1/0` exclude-any, `1/1` exclude-all (policies only). **`query_labels` is the exception**: it carries `require_all` and no `exclude` column, so a report can be scoped include-any or include-all and never excluded |
| Are host vitals labels being maintained at all | `cron_stats` for `host_vitals_label_membership`, §8.6.2. It runs every 5 minutes and **aborts the whole pass** on the first label that errors |

The host's side of the question, in one query:

```sql
SELECT h.id, h.hostname, h.team_id, h.label_updated_at,
       l.id AS label_id, l.name, l.label_membership_type, l.team_id AS label_team_id,
       l.created_at AS label_created_at, lm.updated_at AS membership_updated_at
FROM   hosts h
LEFT   JOIN label_membership lm ON lm.host_id = h.id
LEFT   JOIN labels l           ON l.id = lm.label_id
WHERE  h.id = <host-id>
ORDER  BY l.name;
```

Use `<=>` whenever you compare a `team_id` yourself. `NULL = NULL` is never true, so a plain `=` silently drops every no-fleet host, which is the single most common way a hand-written scoping query lies to you.

### The narrowing, in three cuts

**First cut: fleet or label?** Compare the item's `team_id` with the host's under `<=>`. If they differ, that is decisive **for a configuration profile or a software title**, which match the scope exactly; stop there, because the label state is irrelevant. For a **policy, a scheduled report or a label**, a differing `team_id` is not a reason to stop at all when the item's scope is global, since those accept a null scope alongside the host's own. Three things produce that, and none of them is ranked above the others: a transfer nobody mentioned, a re-enroll that left the host where it was despite a different enroll secret (a re-enroll never writes `team_id`), or, for a profile or a software title only, an item created in the no-fleet scope in the belief that it reaches every fleet. It does not; those match the scope exactly, so a globally scoped one reaches unassigned hosts and nobody else. A global **policy, report or label** does apply inside every fleet ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)), so the same observation means opposite things depending on the item in your hand.

**Second cut: is the host outside the label, or merely recorded that way?** Those two point in opposite directions.

| Observation | Reads as |
|---|---|
| Member, scope is an include | Targeting is correct. This is a delivery problem now, class 2 or later |
| Not a member, `label_updated_at` recent | The query genuinely returned zero rows. Re-run the label's SQL as a live query ([8.7](8.7-live-query-introspection.md)) and see |
| Not a member, `label_updated_at` stale | The host has not reported since the label became relevant. Nothing is wrong yet |
| Scope is an exclude on a **profile or software title** using a **dynamic** label, and the host got the item anyway | Compare that host's `label_updated_at` against `labels.created_at` for every dynamic label in the exclude list. A label newer than this host's watermark should have withheld delivery from this host; if it did not, something cleared memberships without winding the watermark back |
| Scope is an exclude using a **manual** label, and the host got the item anyway | Not the guard, which does not apply to manual labels at all: the query tests `label_membership_type = 0`, the dynamic type, so manual membership is trusted immediately. Check the membership itself |
| Scope is an exclude on a profile or software title, and only some hosts got it | Expected, transiently. **The guard is evaluated per host**, so a host that has reported since the label was created becomes eligible to be judged normally, and the rest are withheld until they report |
| Scope is an exclude on a **policy**, and the host got the item anyway | Not the guard. **Policies have no freshness guard at all**, so a policy with a fresh exclusion runs on hosts that have not yet been evaluated for it. This is working as implemented rather than a fault to find |

The exclude guard is the mechanism behind the first two of those rows, it covers profiles and software only, and it is described in [1.3](../01-foundations/1.3-hosts-fleets-labels.md).

**Third cut, for a population rather than one host.** A label whose host count is zero or implausible fails in a different place depending on its type.

| Type | Where it fails |
|---|---|
| dynamic | Host-side. `labels.platform` takes one of five values only, and the mismatch it causes is worse than it looks. See below. A fleet-scoped label is never distributed outside its fleet. A query that **errors** now leaves membership frozen rather than clearing it, so the rows can be a week stale and look fine |
| manual | No host-side path at all. Check whether an apply sent `hosts: []`, which removes every member, and whether the identifiers used are ones Fleet accepts (`id`, `hardware_serial`, `uuid`) |
| host vitals | Neither. Check the cron in `cron_stats`. One failing criteria expression stalls every host vitals label |

#### A dynamic label's `platform` reaches fewer hosts than its name suggests

A label's `platform` accepts exactly five values: the empty string, `darwin`, `windows`, `ubuntu`, and `centos`. Fleet distributes a dynamic label's query to a host when the label's platform is empty, or when it equals **the platform string the host reported for itself**.

Those two facts together are the trap, because hosts report far more than five platform strings. Fleet recognises roughly twenty Linux platforms, among them `debian`, `rhel`, `sles`, `kali`, `gentoo`, `amzn`, `pop`, `arch`, `linuxmint`, `void`, `flatcar`, `coreos`, `zorin` and `cachyos`. A label set to `ubuntu` reaches none of them. It reaches hosts reporting exactly `ubuntu`, and nothing else. `linux` is not an accepted value at all, so the label cannot be created that way either.

**So there is no dynamic label platform that means "Linux".** To cover a mixed Linux estate, leave `platform` empty and do the filtering in the label's own SQL, which every host then runs.

One exception is worth knowing because it looks like an inconsistency. A host reporting `rhel` is treated as `centos` for label distribution when its OS version string contains "centos", so a `centos` label does reach CentOS hosts that enrol as `rhel`.

Two more traps sit next to this one. Zorin hosts, new at 4.90.0, report `platform=zorin`, and Fleet's release notes say they "can be targeted by label platform filters". That is true of the **host list's** platform filter, which does include Zorin, and not of a label's `platform` field, which cannot be set to `zorin`. The two filters share a name and are unrelated. And a manual label rejects `platform` outright rather than ignoring it, so a spec that carries both is an error, not a silent narrowing.

Staleness has one usable signal. Compare `label_membership.updated_at` for the suspect label against `hosts.label_updated_at` for the same hosts: a large gap on one label and not on the others points at that label's query rather than at the host.

### Forcing and shrinking

To force a label refresh on one host, set `refetch_requested`. It bypasses the interval gate entirely, so the refresh lands on the host's next distributed read rather than an hour later. The UI's Refetch button and the host refetch API endpoint are what set it, a mapping inferred from the column and the gate it skips rather than from documentation.

To shrink a fleet-versus-label question to a minimal case, put one host in a fleet of its own and give the item an include-any scope on a **manual** label containing exactly that host. Manual labels are trusted immediately and have no host-side dependency, so a failure with that setup is not a labels problem. General technique: [8.11](8.11-reproducing-and-isolating.md).
