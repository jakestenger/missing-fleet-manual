# Live report as an introspection tool

A live report is a diagnostic instrument that happens to be shaped like a reporting feature. It reads agent state, OS state, and the agent's own logs from one host or ten thousand without a shell session, a ticket, or a user interrupting their day.

Two things bound it. It rides the osquery distributed channel and nothing else, so what it proves is narrow ([8.7.3](#873-what-a-live-report-cannot-tell-you)). And it runs on real endpoints, so cost is real ([8.7.7](#877-cost-and-etiquette)).

Every table and column below is verified against `schema/osquery_fleet_schema.json` in the Fleet repo. Platform availability comes from the same file.

## 8.7.0 Start here

| What you are trying to do | Go to |
|---|---|
| Ask one host a question you would otherwise need a shell for | [8.7.1](#871-the-query-library), then run it against that host |
| Find out how many hosts are affected, or whether it is only one | [8.7.2](#872-ask-the-population-not-the-host) |
| Work out what a live report result does **not** prove | [8.7.3](#873-what-a-live-report-cannot-tell-you) |
| Understand why a report is slow, times out, or returns partial results | [8.7.4](#874-how-it-works-briefly), then [8.14](8.14-degradation.md) |
| Pull a macOS host's system log without touching the host | [8.7.5](#875-collecting-macos-host-logs-remotely) |
| Script it, or take the browser out of the path | [8.7.6](#876-the-cli-form) |
| Get the actual contents of a file off a host, not facts about it | [8.7.8](#878-running-and-retrieving-a-file-carve) |

**Two limits to carry into everything below.** A live report rides the osquery distributed channel and nothing else, so a result proves that one channel works and says nothing about the other four ([8.7.3](#873-what-a-live-report-cannot-tell-you)). And a result set is a **sample, not a census**: hosts that were offline are silently absent, which is the single easiest way to quote a wrong number from this chapter ([8.7.2](#872-ask-the-population-not-the-host)).

## 8.7.1 The query library

| Question | Table | Platforms |
|---|---|---|
| Which osquery is this, and is its config valid? | `osquery_info` | darwin, windows, linux, chrome |
| Which OS build exactly? | `os_version` | darwin, linux, windows, chrome |
| Which hardware, and what is its serial? | `system_info` | windows, darwin, linux, chrome |
| Did that flag actually take effect? | `osquery_flags` | darwin, linux, windows |
| What is a scheduled query costing this host? | `osquery_schedule` | darwin, linux, windows |
| Are evented tables actually receiving events? | `osquery_events` | darwin, linux, windows |
| What has fleetd logged since it started? | `fleetd_logs` | darwin, windows, linux |
| Is the host's clock right, and what window am I in? | `time` | darwin, linux, windows |
| Is the disk encrypted? | `disk_encryption`, `filevault_status`, `bitlocker_info` | darwin+linux / darwin / windows |
| Is this software installed? | `apps`, `programs`, `deb_packages`, `rpm_packages` | darwin / windows / linux |
| Is this certificate present, and when does it expire? | `certificates` | darwin, linux, windows |
| Did the file carve finish? | `carves` | darwin, linux, windows |
| Is a conflicting product running right now? | `processes` | darwin, linux, windows |

### Agent and OS identity

```sql
SELECT version, config_hash, config_valid, build_platform, build_distro,
       start_time, watcher, pid, uuid, instance_id, extensions
FROM osquery_info;
```

`config_valid = 0` is a strong signal when a host is ignoring agent options: osquery rejected the config it was served. `watcher` is the watchdog process PID.

**`config_hash` is not a convergence test.** Fleet builds the served config per host, including label-scoped scheduled queries, so two hosts on the same team can legitimately hold different hashes without either being stale. Use it to confirm that one host's config *changed* after you changed something, not to compare hosts against each other.

```sql
SELECT name, version, major, minor, patch, build, platform, platform_like, arch
FROM os_version;
```

`build` is the field that matters for OS-specific bugs. `version` alone hides the build that a vendor advisory names.

```sql
SELECT hostname, computer_name, hardware_vendor, hardware_model,
       hardware_serial, uuid, cpu_brand, cpu_logical_cores, physical_memory
FROM system_info;
```

`hardware_serial` is the field to correlate against ABM, an asset system, or a Fleet host record. `uuid` is the hardware UUID.

### Whether a flag took effect

```sql
SELECT name, type, default_value, value, shell_only
FROM osquery_flags
WHERE name IN ('distributed_interval', 'distributed_tls_max_attempts',
               'logger_tls_period', 'disable_events', 'events_expiry',
               'watchdog_memory_limit', 'watchdog_utilization_limit');
```

Everything that has drifted from stock, in one row set:

```sql
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

This is the direct answer to "is this flag live on this host." Agent options in Fleet are the intent. `osquery_flags` is the effect. Fleet does not document osquery's own default for `distributed_interval`; the agent configuration reference carries example values (`3` and `10` in different examples) and a recommended range of 10 to 30 seconds, not a default (`docs/Configuration/agent-configuration.md`, `docs/Contributing/guides/troubleshooting-live-queries.md`). Read the effective value here rather than assuming one.

### Scheduled query cost

```sql
SELECT name, interval, executions, denylisted, output_size,
       average_memory, last_memory, wall_time_ms, last_wall_time_ms,
       user_time, system_time, last_executed
FROM osquery_schedule
ORDER BY average_memory DESC;
```

`denylisted` is a text column; compare against `'1'`:

```sql
SELECT name, query FROM osquery_schedule WHERE denylisted = '1';
```

A denylisted query is not run again until osquery restarts. The performance treatment of this, including watchdog flags and the fleet-wide presentation, is [8.14](8.14-degradation.md).

### Evented table state

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

`events = 0` on an active subscriber means the publisher is alive and nothing has been emitted. `active = 0` means it is not running at all, and the flag that disables events is what to check first.

### The agent-side log ring

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error', 'warn')
ORDER BY time DESC
LIMIT 100;
```

`fleetd_logs` returns fleetd's current session only. It is an in-memory ring that keeps the most recent 10,000 entries and is erased when fleetd restarts. The erase-on-restart behavior is documented in `schema/osquery_fleet_schema.json`; the 10,000-entry cap is a constant in the table's implementation, not documented anywhere else. Read this table before you restart anything. It comes from Fleet's `fleetd_tables` extension, so if `osquery_extensions` shows no extension loaded, it returns nothing.

### Clock and time window

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Clock skew breaks certificate validation, MDM SCEP, and any log correlation you try to do across hosts. It also makes every bounded-window query below wrong. Check it before you trust a timestamp comparison.

### Disk encryption

macOS and Linux:

```sql
SELECT name, uuid, encrypted, type, encryption_status, filevault_status, uid
FROM disk_encryption;
```

`encryption_status` is one of `encrypted`, `not encrypted`, `undefined`. `filevault_status` is one of `on`, `off`, `unknown`.

macOS, the short form:

```sql
SELECT status FROM filevault_status;
```

Windows:

```sql
SELECT device_id, drive_letter, protection_status, conversion_status,
       encryption_method, percentage_encrypted, lock_status
FROM bitlocker_info;
```

### Installed software presence

One table per platform. Filter, never enumerate.

```sql
-- macOS
SELECT name, bundle_identifier, bundle_short_version, bundle_version, path
FROM apps
WHERE bundle_identifier LIKE 'com.example.%';

-- Windows
SELECT name, version, publisher, install_location, install_date
FROM programs
WHERE name LIKE '%Example%';

-- Linux (Debian family)
SELECT name, version, arch, status FROM deb_packages WHERE name LIKE '%example%';

-- Linux (RPM family)
SELECT name, version, release, arch, vendor FROM rpm_packages WHERE name LIKE '%example%';
```

### Certificate presence and expiry

```sql
SELECT common_name, subject, issuer, ca, self_signed, path,
       datetime(not_valid_after, 'unixepoch') AS expires_utc,
       key_strength, sha1
FROM certificates
WHERE common_name LIKE '%example%';
```

On Windows, `certificates` also carries `store`, `store_location`, `store_id`, `sid`, and `username`. Unfiltered, this table walks the whole keychain or certificate store. That is expensive enough to risk a watchdog kill on a busy host, and expensive enough to be worth avoiding regardless. Constrain it.

### File carve status

```sql
SELECT time, carve_guid, request_id, path, size, sha256, status
FROM carves
ORDER BY time DESC;
```

`status` is `STARTING`, `PENDING`, `SUCCESS`, or `FAILED`. This is the host's own view of a carve, which is the half of the picture Fleet's server-side carve record does not give you. The `carve` column is a write trigger, not a status: setting it to `'1'` in a query starts a carve rather than reporting one. Starting one and reading it back from the server is [8.7.8](#878-running-and-retrieving-a-file-carve).

### Is something else running

```sql
SELECT pid, name, path, cmdline, uid, start_time, resident_size
FROM processes
WHERE name LIKE '%example%';
```

Useful when the question is whether a second management agent, a security product, or a second osqueryd is live on the host right now.

## 8.7.2 Ask the population, not the host

The single-host use of these queries is covered in [8.4](8.4-host-side-investigation.md), where you already know which host is broken. The case for a live report is the other one: you do not know which hosts are broken, or how many, and logging into one machine cannot tell you.

| Population question | Query | What the spread tells you |
|---|---|---|
| osquery version spread | `SELECT version FROM osquery_info;` | Whether the osqueryd channel is stalled on a subset. This is the osquery toolkit version, **not** the fleetd or Orbit version; for that use `orbit_info` in the next row |
| Orbit and osqueryd channel spread | `SELECT version, orbit_channel, osqueryd_channel, desktop_version FROM orbit_info;` | Which hosts are pinned to a channel that no longer matches policy |
| OS build spread | `SELECT name, version, build, arch FROM os_version;` | Whether a symptom tracks one OS build. This is the fastest test of "is it the OS update." |
| Config validity | `SELECT config_hash, config_valid FROM osquery_info;` | How many hosts rejected the config they were served. Count `config_valid = 0`; do not read multiple hashes as partial convergence, since Fleet serves a per-host config |
| Flag convergence | `SELECT value FROM osquery_flags WHERE name = 'distributed_interval';` | Whether an agent options change reached the whole team or a fraction of it |
| Conflicting product | `SELECT name, path FROM processes WHERE name LIKE '%example%';` | Blast radius of an interference theory, before you spend a day on it |
| Clock skew | `SELECT unix_time, timezone FROM time;` | Whether skew is one broken host or a broken NTP source |

**Fleet does not aggregate live report results for you.** Each responding host returns its own rows, and the count is yours to do. Two ways to do it:

- In the UI, the results table exports to CSV. Count there. (Volatile surface.)
- Via `fleetctl`, results are emitted as one JSON object per host on stdout, shaped `{"host": "<hostname>", "rows": [ {...} ], "error": "..."}`, so pipe them. The JSON writer is the default; `--pretty` switches to a rendered table instead.

```sh
fleetctl report --labels "macOS" \
  --query "SELECT version FROM os_version;" \
  --exit --timeout 2m | jq -r '.rows[].version' | sort | uniq -c | sort -rn
```

**Those are result rows, not responding hosts.** One host can return many rows or none, so piping `.rows[]` counts rows and a host that answered with zero rows disappears entirely. Count hosts by counting JSON objects, and read the status line for the coverage. **Then read the result as a sample, not a census, and the flags are the reason.** `--exit` returns once every host Fleet currently considers online has answered, so hosts that were offline are simply not in it. `--timeout` is what stops the command waiting indefinitely for an online host that never replies; without it there is nothing to end the wait. And `jq '.rows[]'` takes only result rows, discarding hosts that returned an error and hosts that returned nothing at all.

`--quiet` suppresses the status information, which is exactly the line telling you what fraction of the target answered. It is useful when you already know the shape of the answer and unhelpful the first time you ask, so the example above leaves it off deliberately.

Before quoting a number from this to anyone, compare the **responding-host count**, taken from the status line or by counting the host objects rather than the rows, against the population you targeted. A version distribution that omits every non-responder looks the same as one that covers the estate.

**Targeting.** `--hosts` accepts hostname, UUID, or serial number, comma separated. `--labels` accepts label names, comma separated, and matches hosts carrying any of them. Passing both targets the union. Label targeting is the practical way to ask a population question, because it is the same targeting surface your policies and profiles already use.

For a trait that no osquery table exposes, or when the population question is about hosts that are not responding at all, the answer is in Fleet's own MySQL rather than in a live report. See [8.6](8.6-server-state.md).

## 8.7.3 What a live report cannot tell you

A live report travels the osquery distributed channel: `distributed/read` to fetch, `distributed/write` to return results. That is one of the channels a host uses to talk to Fleet, and on a fully enrolled Mac or Windows computer it is one of five ([8.1](8.1-diagnostic-method.md)). A live report result proves that one channel works and says nothing about the others, however many this platform has. On ChromeOS it proves less than it looks: the extension answers the same endpoints with no osqueryd anywhere on the device ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)).

| Situation | What a live report shows | What is actually true |
|---|---|---|
| MDM enrollment broken, osquery fine | 100% responded | Profiles and commands are failing. A live report never touches the MDM channel. |
| osquery dead, Orbit fine | No response | Orbit is still checking in, still taking scripts and software installs. The host is not offline. |
| Host asleep or off network | No response | Nothing is wrong with it. There is no such thing as a queued live query for a host that never checks in during the campaign. |
| Android host | Not targetable | No osquery and no fleetd on Android. Live reports do not apply. |
| Windows or Linux host, `unified_log` query | Table does not exist | `unified_log` is macOS only. |

Two more limits worth stating plainly:

- **A live report is not durable.** Results are collected for the life of the campaign and are not stored as host data. If you need the answer over time, that is a scheduled report or a host vital, not a live report.
- **A non-responding host is not a diagnosis.** It is one bit. Separating "osquery is not running", "the host is not on the network", and "the query is being denylisted or killed" needs the control test in [8.14](8.14-degradation.md#8142-establish-a-control-first).

## 8.7.4 How it works, briefly

The mechanism bounds the claims. Source: `docs/Contributing/guides/troubleshooting-live-queries.md`.

| # | Step | Where state lands |
|---|---|---|
| 1 | `POST /api/latest/fleet/reports/run` with query and targets | Fleet creates a live query campaign row in **MySQL** and gets a campaign ID |
| 2 | Fleet stores the campaign and its targets | **Redis** |
| 3 | Browser or `fleetctl` opens a connection under `GET /api/latest/fleet/results/` and upgrades to a **websocket**; that Fleet instance subscribes to the campaign in Redis | Redis pubsub subscription, held by one Fleet instance |
| 4 | Each device hits `distributed/read` on **its next check-in**, at its own `distributed_interval`. Fleet reads the campaign from Redis and hands the SQL back | Nothing new; this is a read |
| 5 | The device runs the query locally and returns rows on `distributed/write` | Fleet writes results to **Redis** for that device and campaign |
| 6 | Redis delivers results to the subscribed instance, which streams them over the websocket | Rendered in the browser or written to stdout by `fleetctl` |

Three consequences of that shape:

- **Latency is the check-in interval, not the network.** A host with a 60 second `distributed_interval` responds up to 60 seconds after you press run. A live query that "times out" against a slow-checking fleet is a settings problem.
- **Any Fleet instance can collect, one instance streams.** Multiple instances write results to Redis; the browser or `fleetctl` is connected to exactly one instance, which reads them back out of Redis. Redis is the coupling point, which is why Redis is the first thing to check when live reports are the symptom.
- **Websockets are load bearing** for the browser path. Infrastructure that drops or does not upgrade websocket connections breaks live reports while leaving the rest of Fleet working.

Paths to put in an ingress rule or grep for in an access log. The campaign is created at `POST /api/latest/fleet/reports/run`, or at `POST /api/latest/fleet/reports/run_by_identifiers` when the caller targets by hostname, UUID or serial, which is what `fleetctl` uses. Results stream from a handler mounted on the **prefix** `/api/latest/fleet/results/`, so an ingress rule should match that prefix rather than any one path under it; `fleetctl` requests `/results/websocket`, and matching only that exact path is how a rule ends up letting the CLI through and dropping the browser. There is also a `GET` on the same `reports/run` path, a separate synchronous endpoint rather than part of this flow; [8.14](8.14-degradation.md) covers it as the way to take the websocket out of the picture entirely.

When the path itself is the problem rather than the query, go to [8.14](8.14-degradation.md): it owns the `SELECT 1 WHERE 1 = 0;` control test, the layer-bypass procedure, the synchronous no-websocket API, and the Redis pubsub output buffer limit that makes results vanish without an error.

## 8.7.5 Collecting macOS host logs remotely

`unified_log` reads the OSLog framework over the distributed channel, so you get a host's system log without touching the host. macOS only.

mdmclient activity in the last hour:

```sql
SELECT timestamp, process, subsystem, category, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 3600 FROM time)
ORDER BY timestamp DESC;
```

**Always bound the window.** `unified_log` returns 100 rows by default (`max_rows`), and the schema explicitly asks for a `timestamp >` or `timestamp >=` constraint for performance (`schema/osquery_fleet_schema.json`). Unbounded, this is one of the most expensive queries you can send to a fleet of Macs. Raise the cap deliberately when you need more:

```sql
SELECT timestamp, process, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 900 FROM time)
  AND max_rows = 500
ORDER BY timestamp DESC;
```

The `predicate` column takes an OSLog predicate string, merged into the predicate osquery builds from your other constraints. Reading and interpreting the log surfaces themselves, including which subsystems matter for which pipeline, is [8.2](8.2-log-surfaces.md).

## 8.7.6 The CLI form

```sh
fleetctl report \
  --query "SELECT version FROM osquery_info;" \
  --hosts "host-a,host-b" \
  --exit \
  --timeout 2m
```

`fleetctl query` is a deprecated alias for `fleetctl report` and still works, logging a deprecation notice when used. **The notice is suppressible**, because every deprecation warning in the client is gated on one log topic that a single flag turns off, so its absence is not evidence that a name is current.

| Flag | Env var | What it does |
|---|---|---|
| `--query` | `QUERY` | The SQL to run. Mutually exclusive with `--report-name`. |
| `--report-name` (alias `--query-name`) | `REPORT_NAME`, `QUERYNAME` | Run a saved query by name instead of ad hoc SQL |
| `--hosts` | `HOSTS` | Comma-separated targets, by hostname, UUID, or serial number |
| `--labels` | `LABELS` | Comma-separated label names; matches hosts with any of them |
| `--exit` | `EXIT` | Exit once 100% of **online** hosts have returned results |
| `--timeout` | `TIMEOUT` | Give up after a duration (`10s`, `1h`) |
| `--quiet` | `QUIET` | Results only, no status line. Use this when piping. |
| `--pretty` | `PRETTY` | Human-readable output instead of JSON |
| `--fleet` (alias `--team`) | | Team ID that owns the named saved report; `0` means global |

Either `--hosts` or `--labels` is required, otherwise the command errors with `No hosts or labels targeted. Please provide either --hosts or --labels.`

The status line, written to stderr, reads:

```
 42% responded (91% online) | 210/500 targeted hosts (210/230 online)
```

**The same count appears three times.** Both fractions carry responders on top: 210 of 500 targeted, and 210 of the 230 Fleet currently believes are online. The two denominators are the whole point. `--exit` waits for the second fraction to reach 1, so a run can finish at 42 percent of what you targeted and report success, because the other 290 hosts were never online to be waited for. That is the same sampling caveat as §8.7.2, in the one place you are most likely to read past it.

Two reasons to reach for the CLI over the UI:

- **It removes the browser from the path.** If the CLI returns results and the UI does not, the remaining difference is the browser, its network path, and the websocket upgrade between them, which is a much smaller search space than "live reports are broken". This is one row of the layer-bypass table in [8.14](8.14-degradation.md).
- **It scripts.** JSON on stdout, one object per host, so a population question becomes a pipeline rather than a CSV export.

## 8.7.7 Cost and etiquette

These queries run on laptops that people are using.

| Rule | Why |
|---|---|
| `LIMIT` anything that could return many rows | Large result sets can overwhelm network throughput and the results never arrive (`docs/Contributing/guides/troubleshooting-live-queries.md`) |
| Constrain wide tables (`certificates`, `processes`, `unified_log`, file globs) | The osquery watchdog kills expensive queries, and a repeatedly expensive scheduled query gets denylisted |
| Bound every time window against `time` | An unbounded log query is the most expensive thing you can send |
| Target narrowly, then widen | One host, then a label, then a team. A query that kills osquery on one host will kill it on ten thousand. |
| Avoid recursive directory traversal and wildcard paths | The usual trigger for watchdog kills |

The performance treatment, including watchdog flags, denylisting, and what a 40 to 70 percent response rate against a healthy server actually means, is [8.14](8.14-degradation.md).

## 8.7.8 Running and retrieving a file carve

The query library above reads facts about a host. A carve reads the file itself. When osquery can tell you a file exists, its size and its hash, but you need the bytes, a log too large to page through `unified_log`, a corrupt configuration, a sample for analysis, a carve is osquery's purpose-built path for lifting the whole file off the host and reassembling it in Fleet. It is a Free capability, and retrieving a carve is global-admin only (`carve · read`, [a.4](../09-appendices/a.4-roles-and-permissions-matrix.md)). There is no team-scoped equivalent.

The host-side view of a carve, its `STARTING`, `PENDING`, `SUCCESS` and `FAILED` states, is the [File carve status](#file-carve-status) query above. This section is the server-side other half: how you start one, how it arrives, and how you get the file back out.

### Initiate a carve

There is no "start a carve" button and no carve-specific API endpoint. You start one through the same live-report surface as any other query; the difference is that the query writes rather than reads. A query against the `carves` table with the `carve` column set to `1` (or a call to osquery's `carve()` function) is a request to carve the matching path:

```sql
SELECT * FROM carves WHERE carve = 1 AND path LIKE '/var/log/example.log';
```

Run that through the UI live query, the live-report REST endpoint, or `fleetctl report --query "..."` ([8.7.6](#876-the-cli-form)), targeting the host holding the file. The file's bytes do not come back in the live-report result; osquery uploads them on the separate carve channel described below, and you retrieve the file afterwards through the carve interfaces.

The `carve` write trigger, the `carve()` function, and those host-side state transitions are osquery's own behaviour, not Fleet's, so they are not settled by Fleet's source. Confirm the host actually started carving with the `carves`-table query above rather than assuming the trigger fired.

### How blocks reach Fleet

osquery splits the file into fixed-size blocks, 8 MB by default (`--carver_block_size`), and opens an upload session with Fleet. It first sends a begin request declaring the carve's total size, block size and block count, and receives a session id; it then posts each block in turn. Fleet checks that blocks arrive strictly in order and within the declared size, reassembles them, and stores them.

These uploads never involve an operator login, so they happen with no administrator signed in. Authentication then changes after the first request:

- **Begin request:** the host's node key authenticates it, the same credential osquery presents on its other server requests, and Fleet identifies the host and creates the carve session before it validates anything.
- **Block request, default mode:** with `osquery.allow_body_auth_fallback` left on, a matching `session_id` and `request_id` authenticate the block on their own. No node key travels with it, and Fleet does not check that the posting host owns the session.
- **Block request with `osquery.allow_body_auth_fallback` off:** the block route additionally demands the host's node key in an `Authorization` header and rejects any block whose authenticated host does not own the carve.

That setting strengthens block authentication only; it does not change how the begin request works.

The begin request is refused if the declared carve size is zero, if it exceeds the 8 GiB carve ceiling, if the block size exceeds the 256 MiB block ceiling, or if the size and block count are inconsistent ([8.14](8.14-degradation.md) carries the ceilings). That check runs before Fleet records the session, so a refused begin leaves no carve session on the server, though osquery on the host had already begun the attempt. A block that breaks the in-order or size rule fails the carve after the session exists, and Fleet records it as errored where it can, so it surfaces on retrieval rather than failing silently.

### Retrieve a completed carve

There is no carves page anywhere in the Fleet web UI. Retrieval is `fleetctl` or the REST API, and global-admin only.

| Step | Command |
|---|---|
| List carves, with a completion percentage and an errored column | `fleetctl get carves` (add `--expired` to include expired ones) |
| Read one carve's metadata | `fleetctl get carve <id>` |
| Download the reassembled file | `fleetctl get carve <id> --outfile <path>` (or `--stdout`) |

The REST equivalents are `GET /api/v1/fleet/carves` (list), `GET /api/v1/fleet/carves/{id}` (metadata) and `GET /api/v1/fleet/carves/{id}/block/{block_id}` (one block); the `fleetctl` download walks the blocks in order. A carve is ready to pull when `get carves` shows its completion at `100%` and `errored` at `no`. The command surface is in [a.7](../09-appendices/a.7-fleetctl-command-reference.md).

### Where carves are stored

A carve's metadata always lives in MySQL. The block bytes go to one of two places:

- **MySQL, by default.** No object storage is required, but carve blocks are the fastest way to grow the Fleet database ([1.6](../01-foundations/1.6-the-fleet-server.md), [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md)).
- **S3 or GCS, when a carves bucket is configured.** The bytes move to object storage and only the metadata stays in MySQL ([2.3](../02-administer-and-deploy-fleet/2.3-deploy-on-aws-or-gcp.md) for buckets, [8.13](8.13-escalation.md) for the `s3_carves_*` keys).

### Retention: carve evidence is perishable

A carve captures bytes that came off a host at one moment, and nothing re-uploads them. The two stores treat that evidence very differently: MySQL deletes the blocks on its own clock, while object storage keeps them until its lifecycle policy or an operator removes them.

**MySQL-backed carves are collect-and-retrieve-within-a-day.** An hourly cleanup job deletes the stored block data of carves older than 24 hours, up to 50,000 per run, then marks them expired. The deletion is the job's work, so it follows crossing 24 hours by up to the cron interval rather than landing exactly on the hour, and it depends on the job running. There is no carve-specific setting on the MySQL side to keep those blocks longer. Treat a MySQL-backed carve as something to pull the same day.

**S3-backed carves live as long as the bucket keeps them.** Fleet never deletes a carve object. Their lifetime is whatever your bucket lifecycle policy, a manual deletion, or any object-store loss decides, which is infrastructure you own rather than Fleet. The hourly job only reconciles the S3 side: it probes each completed carve older than 24 hours and, if the object is definitively missing, marks the carve expired to match; a transient error such as throttling or a network failure is not read as a missing object. That reconcile can be disabled and tuned (`s3_carves_cleanup_disabled`, `s3_carves_cleanup_max_per_run`, `s3_carves_cleanup_concurrency`); the MySQL side has no equivalent switch.

**Expiry is one-way, and the metadata outlives the bytes.** A carve reaches expired either when the reconcile probe finds its object gone or when a download finds it gone. After that, any block download or `--outfile` fails with `cannot get block for expired carve`, but the record does not vanish: `get carves` still lists it and `get carve <id>` still prints its metadata. A carve appearing in the listing is not proof the file is still retrievable. Fleet has no operation to re-request the file, un-expire the record, or otherwise recover a carve once its blocks are gone; recovery means restoring your MySQL or object-store backup, which is the data-protection concern in [7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md).

### Failures and gotchas

| Symptom | Cause and fix |
|---|---|
| No carves anywhere in the web UI | There is no UI for carves. Use `fleetctl` or the REST API, as a global admin. |
| A team admin or maintainer cannot see a carve | Retrieval is global-admin only (`carve · read`). There is no team-scoped read. |
| `cannot get block for expired carve` | The blocks are gone: past the MySQL 24-hour cleanup, or the S3 object was deleted or lost. Not recoverable from Fleet; restore from backup ([7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md)). |
| `get carves` lists it, but the download fails | The record is expired, not deleted. The metadata survives cleanup; the bytes do not. |
| `--outfile` leaves a wrong tail on the file | `--outfile` opens the file without truncating, so writing a shorter carve over a longer file leaves the old tail attached. Write to a fresh path ([a.7](../09-appendices/a.7-fleetctl-command-reference.md)). |
| Carve shows `errored` | A block arrived out of order or over its declared size, or a block failed to store. Begin-time failures never land here (see the next row). |
| A carve never appears at all | The begin request was rejected on its size or consistency checks, so Fleet created no carve session. osquery had started the attempt on the host, but there is no server-side record to list or retrieve. |
| S3 upload fails after lowering the block size | Fleet passes each block straight to the configured object store without checking its size, so any minimum-part-size rule is the backend's, not Fleet's. On AWS S3 that minimum is 5 MiB for every part but the last, and a hand-lowered block below it fails the upload; other S3-compatible or GCS backends may draw the line elsewhere, so validate it against the store you actually run. Fleet's default is 8,000,000 bytes, which clears AWS S3's 5 MiB floor, but Fleet validates no backend's minimum, only its own 256 MiB block ceiling. |
