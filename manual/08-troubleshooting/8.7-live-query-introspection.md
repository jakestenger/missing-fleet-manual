# Live report as an introspection tool

A live report is a diagnostic instrument that happens to be shaped like a reporting feature. It reads agent state, OS state, and the agent's own logs from one host or ten thousand without a shell session, a ticket, or a user interrupting their day.

Two things bound it. It rides the osquery distributed channel and nothing else, so what it proves is narrow ([8.7.3](#873-what-a-live-report-cannot-tell-you)). And it runs on real endpoints, so cost is real ([8.7.7](#877-cost-and-etiquette)).

Every table and column below is verified against `schema/osquery_fleet_schema.json` in the Fleet repo. Platform availability comes from the same file.

## 8.7.1 The query library

| Question | Table | Platforms |
|---|---|---|
| Which agent is this, and is its config valid? | `osquery_info` | darwin, windows, linux, chrome |
| Which OS build exactly? | `os_version` | darwin, linux, windows, chrome |
| Which hardware, and what is its serial? | `system_info` | windows, darwin, linux, chrome |
| Did that flag actually take effect? | `osquery_flags` | darwin, linux, windows |
| What is a scheduled query costing this host? | `osquery_schedule` | darwin, linux, windows |
| Are evented tables actually receiving events? | `osquery_events` | darwin, linux, windows |
| What has fleetd logged since it started? | `fleetd_logs` | darwin, windows, linux |
| Is the host's clock right, and what window am I in? | `time` | darwin, linux, windows |
| Is the disk encrypted? | `disk_encryption`, `filevault_status`, `bitlocker_info` | darwin+linux / darwin / windows |
| Is this software installed? | `apps`, `programs`, `deb_packages`, `rpm_packages` | darwin / windows / linux |
| Is this certificate present, and when does it expire? | `certificates` | darwin, linux, windows |
| Did the file carve finish? | `carves` | darwin, linux, windows |
| Is a conflicting product running right now? | `processes` | darwin, linux, windows |

### Agent and OS identity

```sql
SELECT version, config_hash, config_valid, build_platform, build_distro,
       start_time, watcher, pid, uuid, instance_id, extensions
FROM osquery_info;
```

`config_valid = 0` is the whole answer when a host is ignoring agent options. `config_hash` differing across hosts on the same team means one of them has not taken the current config. `watcher` is the watchdog process PID.

```sql
SELECT name, version, major, minor, patch, build, platform, platform_like, arch
FROM os_version;
```

`build` is the field that matters for OS-specific bugs. `version` alone hides the build that a vendor advisory names.

```sql
SELECT hostname, computer_name, hardware_vendor, hardware_model,
       hardware_serial, uuid, cpu_brand, cpu_logical_cores, physical_memory
FROM system_info;
```

`hardware_serial` is the field to correlate against ABM, an asset system, or a Fleet host record. `uuid` is the hardware UUID.

### Whether a flag took effect

```sql
SELECT name, type, default_value, value, shell_only
FROM osquery_flags
WHERE name IN ('distributed_interval', 'distributed_tls_max_attempts',
               'logger_tls_period', 'disable_events', 'events_expiry',
               'watchdog_memory_limit', 'watchdog_utilization_limit');
```

Everything that has drifted from stock, in one row set:

```sql
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

This is the only reliable answer to "is this flag live on this host." Agent options in Fleet are the intent. `osquery_flags` is the effect. Fleet does not document osquery's own default for `distributed_interval`; the agent configuration reference carries example values (`3` and `10` in different examples) and a recommended range of 10 to 30 seconds, not a default (`docs/Configuration/agent-configuration.md`, `docs/Contributing/guides/troubleshooting-live-queries.md`). Read the effective value here rather than assuming one.

### Scheduled query cost

```sql
SELECT name, interval, executions, denylisted, output_size,
       average_memory, last_memory, wall_time_ms, last_wall_time_ms,
       user_time, system_time, last_executed
FROM osquery_schedule
ORDER BY average_memory DESC;
```

`denylisted` is a text column; compare against `'1'`:

```sql
SELECT name, query FROM osquery_schedule WHERE denylisted = '1';
```

A denylisted query is not run again until osquery restarts. The performance treatment of this, including watchdog flags and the fleet-wide presentation, is [8.14](8.14-degradation.md).

### Evented table state

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

`events = 0` on an active subscriber means the publisher is alive and nothing has been emitted. `active = 0` means it is not running at all, usually because events are disabled by flag.

### The agent-side log ring

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error', 'warn')
ORDER BY time DESC
LIMIT 100;
```

`fleetd_logs` returns fleetd's current session only. It is an in-memory ring that keeps the most recent 10,000 entries and is erased when fleetd restarts. The erase-on-restart behavior is documented in `schema/osquery_fleet_schema.json`; the 10,000-entry cap is `maxEntries` in `orbit/pkg/table/fleetd_logs/fleetd_logs.go`, not documented anywhere else. Read this table before you restart anything. It comes from Fleet's `fleetd_tables` extension, so if `osquery_extensions` shows no extension loaded, it returns nothing.

### Clock and time window

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Clock skew breaks certificate validation, MDM SCEP, and any log correlation you try to do across hosts. It also makes every bounded-window query below wrong. Check it before you trust a timestamp comparison.

### Disk encryption

macOS and Linux:

```sql
SELECT name, uuid, encrypted, type, encryption_status, filevault_status, uid
FROM disk_encryption;
```

`encryption_status` is one of `encrypted`, `not encrypted`, `undefined`. `filevault_status` is one of `on`, `off`, `unknown`.

macOS, the short form:

```sql
SELECT status FROM filevault_status;
```

Windows:

```sql
SELECT device_id, drive_letter, protection_status, conversion_status,
       encryption_method, percentage_encrypted, lock_status
FROM bitlocker_info;
```

### Installed software presence

One table per platform. Filter, never enumerate.

```sql
-- macOS
SELECT name, bundle_identifier, bundle_short_version, bundle_version, path
FROM apps
WHERE bundle_identifier LIKE 'com.example.%';

-- Windows
SELECT name, version, publisher, install_location, install_date
FROM programs
WHERE name LIKE '%Example%';

-- Linux (Debian family)
SELECT name, version, arch, status FROM deb_packages WHERE name LIKE '%example%';

-- Linux (RPM family)
SELECT name, version, release, arch, vendor FROM rpm_packages WHERE name LIKE '%example%';
```

### Certificate presence and expiry

```sql
SELECT common_name, subject, issuer, ca, self_signed, path,
       datetime(not_valid_after, 'unixepoch') AS expires_utc,
       key_strength, sha1
FROM certificates
WHERE common_name LIKE '%example%';
```

On Windows, `certificates` also carries `store`, `store_location`, `store_id`, `sid`, and `username`. Unfiltered, this table walks the whole keychain or certificate store, which is exactly the kind of query the watchdog kills. Constrain it.

### File carve status

```sql
SELECT time, carve_guid, request_id, path, size, sha256, status
FROM carves
ORDER BY time DESC;
```

`status` is `STARTING`, `PENDING`, `SUCCESS`, or `FAILED`. This is the host's own view of a carve, which is the half of the picture Fleet's server-side carve record does not give you. The `carve` column is a write trigger, not a status: setting it to `'1'` in a query starts a carve rather than reporting one.

### Is something else running

```sql
SELECT pid, name, path, cmdline, uid, start_time, resident_size
FROM processes
WHERE name LIKE '%example%';
```

Useful when the question is whether a second management agent, a security product, or a second osqueryd is live on the host right now.

## 8.7.2 Ask the population, not the host

The single-host use of these queries is covered in [8.4](8.4-host-side-investigation.md), where you already know which host is broken. The case for a live report is the other one: you do not know which hosts are broken, or how many, and logging into one machine cannot tell you.

| Population question | Query | What the spread tells you |
|---|---|---|
| Agent version spread | `SELECT version FROM osquery_info;` | Whether an update channel is stalled on a subset. One outlier version is a rollout problem, not a host problem. |
| Orbit and osqueryd channel spread | `SELECT version, orbit_channel, osqueryd_channel, desktop_version FROM orbit_info;` | Which hosts are pinned to a channel that no longer matches policy |
| OS build spread | `SELECT name, version, build, arch FROM os_version;` | Whether a symptom tracks one OS build. This is the fastest test of "is it the OS update." |
| Config convergence | `SELECT config_hash, config_valid FROM osquery_info;` | How many hosts have taken the current agent options. Multiple hashes on one team means partial convergence. |
| Flag convergence | `SELECT value FROM osquery_flags WHERE name = 'distributed_interval';` | Whether an agent options change reached the whole team or a fraction of it |
| Conflicting product | `SELECT name, path FROM processes WHERE name LIKE '%example%';` | Blast radius of an interference theory, before you spend a day on it |
| Clock skew | `SELECT unix_time, timezone FROM time;` | Whether skew is one broken host or a broken NTP source |

**Fleet does not aggregate live report results for you.** Each responding host returns its own rows, and the count is yours to do. Two ways to do it:

- In the UI, the results table exports to CSV. Count there. (Volatile surface.)
- Via `fleetctl`, results are emitted as one JSON object per host on stdout, shaped `{"host": "<hostname>", "rows": [ {...} ], "error": "..."}`, so pipe them. Source: `cmd/fleetctl/fleetctl/query_output.go`. The JSON writer is the default; `--pretty` switches to a rendered table instead.

```sh
fleetctl report --labels "macOS" \
  --query "SELECT version FROM os_version;" \
  --exit --quiet | jq -r '.rows[].version' | sort | uniq -c | sort -rn
```

**Targeting.** `--hosts` accepts hostname, UUID, or serial number, comma separated. `--labels` accepts label names, comma separated, and matches hosts carrying any of them. Passing both targets the union (`cmd/fleetctl/fleetctl/query.go`). Label targeting is the practical way to ask a population question, because it is the same targeting surface your policies and profiles already use.

For a trait that no osquery table exposes, or when the population question is about hosts that are not responding at all, the answer is in Fleet's own MySQL rather than in a live report. See [8.6](8.6-server-state.md).

## 8.7.3 What a live report cannot tell you

A live report travels the osquery distributed channel: `distributed/read` to fetch, `distributed/write` to return results. That is one of the five channels a host uses to talk to Fleet ([8.1](8.1-diagnostic-method.md)). A live report result proves that one channel works, and says nothing about the other four.

| Situation | What a live report shows | What is actually true |
|---|---|---|
| MDM enrollment broken, osquery fine | 100% responded | Profiles and commands are failing. A live report never touches the MDM channel. |
| osquery dead, Orbit fine | No response | Orbit is still checking in, still taking scripts and software installs. The host is not offline. |
| Host asleep or off network | No response | Nothing is wrong with it. There is no such thing as a queued live query for a host that never checks in during the campaign. |
| Android host | Not targetable | No osquery and no fleetd on Android. Live reports do not apply. |
| Windows or Linux host, `unified_log` query | Table does not exist | `unified_log` is macOS only. |

Two more limits worth stating plainly:

- **A live report is not durable.** Results are collected for the life of the campaign and are not stored as host data. If you need the answer over time, that is a scheduled report or a host vital, not a live report.
- **A non-responding host is not a diagnosis.** It is one bit. Separating "osquery is not running", "the host is not on the network", and "the query is being denylisted or killed" needs the control test in [8.14](8.14-degradation.md#8142-establish-a-control-first).

## 8.7.4 How it works, briefly

The mechanism bounds the claims. Source: `docs/Contributing/guides/troubleshooting-live-queries.md`.

| # | Step | Where state lands |
|---|---|---|
| 1 | `POST /api/latest/fleet/reports/run` with query and targets | Fleet creates a live query campaign row in **MySQL** and gets a campaign ID |
| 2 | Fleet stores the campaign and its targets | **Redis** |
| 3 | Browser or `fleetctl` opens `GET /api/latest/fleet/results` and upgrades to a **websocket**; that Fleet instance subscribes to the campaign in Redis | Redis pubsub subscription, held by one Fleet instance |
| 4 | Each device hits `distributed/read` on **its next check-in**, at its own `distributed_interval`. Fleet reads the campaign from Redis and hands the SQL back | Nothing new; this is a read |
| 5 | The device runs the query locally and returns rows on `distributed/write` | Fleet writes results to **Redis** for that device and campaign |
| 6 | Redis delivers results to the subscribed instance, which streams them over the websocket | Rendered in the browser or written to stdout by `fleetctl` |

Three consequences of that shape:

- **Latency is the check-in interval, not the network.** A host with a 60 second `distributed_interval` responds up to 60 seconds after you press run. A live query that "times out" against a slow-checking fleet is a settings problem.
- **Any Fleet instance can collect, one instance streams.** Multiple instances write results to Redis; the browser or `fleetctl` is connected to exactly one instance, which reads them back out of Redis. Redis is the coupling point, which is why Redis is the first thing to check when live reports are the symptom.
- **Websockets are load bearing** for the browser path. Infrastructure that drops or does not upgrade websocket connections breaks live reports while leaving the rest of Fleet working.

When the path itself is the problem rather than the query, go to [8.14](8.14-degradation.md): it owns the `SELECT 1 WHERE 1 = 0;` control test, the layer-bypass procedure, the synchronous no-websocket API, and the Redis pubsub output buffer limit that makes results vanish without an error.

## 8.7.5 Collecting macOS host logs remotely

`unified_log` reads the OSLog framework over the distributed channel, so you get a host's system log without touching the host. macOS only.

mdmclient activity in the last hour:

```sql
SELECT timestamp, process, subsystem, category, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 3600 FROM time)
ORDER BY timestamp DESC;
```

**Always bound the window.** `unified_log` returns 100 rows by default (`max_rows`), and the schema explicitly asks for a `timestamp >` or `timestamp >=` constraint for performance (`schema/osquery_fleet_schema.json`). Unbounded, this is one of the most expensive queries you can send to a fleet of Macs. Raise the cap deliberately when you need more:

```sql
SELECT timestamp, process, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 900 FROM time)
  AND max_rows = 500
ORDER BY timestamp DESC;
```

The `predicate` column takes an OSLog predicate string, merged into the predicate osquery builds from your other constraints. Reading and interpreting the log surfaces themselves, including which subsystems matter for which pipeline, is [8.2](8.2-log-surfaces.md).

## 8.7.6 The CLI form

```sh
fleetctl report \
  --query "SELECT version FROM osquery_info;" \
  --hosts "host-a,host-b" \
  --exit
```

`fleetctl query` is a deprecated alias for `fleetctl report` and still works; it logs a deprecation notice (`cmd/fleetctl/fleetctl/query.go`).

| Flag | Env var | What it does |
|---|---|---|
| `--query` | `QUERY` | The SQL to run. Mutually exclusive with `--report-name`. |
| `--report-name` (alias `--query-name`) | `REPORT_NAME`, `QUERYNAME` | Run a saved query by name instead of ad hoc SQL |
| `--hosts` | `HOSTS` | Comma-separated targets, by hostname, UUID, or serial number |
| `--labels` | `LABELS` | Comma-separated label names; matches hosts with any of them |
| `--exit` | `EXIT` | Exit once 100% of **online** hosts have returned results |
| `--timeout` | `TIMEOUT` | Give up after a duration (`10s`, `1h`) |
| `--quiet` | `QUIET` | Results only, no status line. Use this when piping. |
| `--pretty` | `PRETTY` | Human-readable output instead of JSON |
| `--fleet` (alias `--team`) | | Team ID that owns the named saved report; `0` means global |

Either `--hosts` or `--labels` is required, otherwise the command errors with `No hosts or labels targeted`.

The status line, written to stderr, reads `N% responded (N% online) | responded/targeted targeted hosts (online/online online)`. Both denominators matter: the percentage of targeted hosts and the percentage of hosts Fleet believes are online are different numbers, and `--exit` waits on the second one. Source: `cmd/fleetctl/fleetctl/query.go`.

Two reasons to reach for the CLI over the UI:

- **It removes the browser from the path.** If the CLI returns results and the UI does not, the fault is browser or rendering, not server. This is one row of the layer-bypass table in [8.14](8.14-degradation.md).
- **It scripts.** JSON on stdout, one object per host, so a population question becomes a pipeline rather than a CSV export.

## 8.7.7 Cost and etiquette

These queries run on laptops that people are using.

| Rule | Why |
|---|---|
| `LIMIT` anything that could return many rows | Large result sets can overwhelm network throughput and the results never arrive (`docs/Contributing/guides/troubleshooting-live-queries.md`) |
| Constrain wide tables (`certificates`, `processes`, `unified_log`, file globs) | The osquery watchdog kills expensive queries, and a repeatedly expensive scheduled query gets denylisted |
| Bound every time window against `time` | An unbounded log query is the most expensive thing you can send |
| Target narrowly, then widen | One host, then a label, then a team. A query that kills osquery on one host will kill it on ten thousand. |
| Avoid recursive directory traversal and wildcard paths | The usual trigger for watchdog kills |

The performance treatment, including watchdog flags, denylisting, and what a 40 to 70 percent response rate against a healthy server actually means, is [8.14](8.14-degradation.md).
