# Live report as an introspection tool

A live report can help you investigate a device without opening a shell session or asking its user to collect information. You can read agent state, OS details, and recent agent logs from one host, then run the same query across a wider group to see who else is affected.

This chapter provides queries for that work, explains how to interpret coverage, and shows how to collect logs and files remotely. Live reports use the osquery distributed channel and run on the endpoints themselves, so both channel health and query cost matter.

Every table and column below is verified against `schema/osquery_fleet_schema.json` in the Fleet repo. Platform availability comes from the same file.

| What you are trying to do | Go to |

| Find out how many hosts are affected, or whether it is only one | [8.7.2](#872-investigate-a-group-of-hosts) |

## 8.7.1 The query library

| Question | Table | Platforms |
|---|---|---|
| Which osquery is this, and is its config valid? | `osquery_info` | darwin, windows, linux, chrome |
| Which OS build exactly? | `os_version` | darwin, linux, windows, chrome |
| Which hardware, and what is its serial? | `system_info` | windows, darwin, linux, chrome |
| Did that flag actually take effect? | `osquery_flags` | darwin, linux, windows |
| What is a scheduled query costing this host? | `osquery_schedule` | darwin, linux, windows |
| Are evented tables actually receiving events? | `osquery_events` | darwin, linux, windows |
| What has fleetd logged since it started? | `fleetd_logs` | darwin, windows, linux |
| Is the host's clock right, and what window am I in? | `time` | darwin, linux, windows |
| Is the disk encrypted? | `disk_encryption`, `filevault_status`, `bitlocker_info` | darwin+linux / darwin / windows |
| Is this software installed? | `apps`, `programs`, `deb_packages`, `rpm_packages` | darwin / windows / linux |
| Is this certificate present, and when does it expire? | `certificates` | darwin, linux, windows |
| Did the file carve finish? | `carves` | darwin, linux, windows |
| Is a conflicting product running right now? | `processes` | darwin, linux, windows |

### Agent and OS identity

```sql
SELECT version, config_hash, config_valid, build_platform, build_distro,
       start_time, watcher, pid, uuid, instance_id, extensions
FROM osquery_info;
```

If a host is ignoring agent options, check `config_valid`: a value of `0` means osquery rejected the configuration it received. `watcher` is the watchdog process PID.

Use `config_hash` to check whether a host's configuration changed after an update. Fleet builds configuration per host, including label-scoped scheduled queries, so two hosts in the same fleet can have different hashes and both be current.

```sql
SELECT name, version, major, minor, patch, build, platform, platform_like, arch
FROM os_version;
```

Include `build` when investigating an OS-specific bug. A vendor advisory may identify a build that the broader `version` field does not distinguish.

```sql
SELECT hostname, computer_name, hardware_vendor, hardware_model,
       hardware_serial, uuid, cpu_brand, cpu_logical_cores, physical_memory
FROM system_info;
```

Use `hardware_serial` to match the device to ABM, an asset system, or its Fleet host record. `uuid` contains the hardware UUID.

### Whether a flag took effect

```sql
SELECT name, type, default_value, value, shell_only
FROM osquery_flags
WHERE name IN ('distributed_interval', 'distributed_tls_max_attempts',
               'logger_tls_period', 'disable_events', 'events_expiry',
               'watchdog_memory_limit', 'watchdog_utilization_limit');
```

To see flags whose effective values differ from their defaults:

```sql
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

`osquery_flags` shows the values currently in use on the host, which lets you check whether an agent-options change took effect. Read `distributed_interval` here before assuming a value: Fleet's agent configuration reference includes examples of `3` and `10` and recommends 10 to 30 seconds, but does not document osquery's default (`docs/Configuration/agent-configuration.md`, `docs/Contributing/guides/troubleshooting-live-queries.md`).

### Scheduled query cost

```sql
SELECT name, interval, executions, denylisted, output_size,
       average_memory, last_memory, wall_time_ms, last_wall_time_ms,
       user_time, system_time, last_executed
FROM osquery_schedule
ORDER BY average_memory DESC;
```

`denylisted` is a text column; compare against `'1'`:

```sql
SELECT name, query FROM osquery_schedule WHERE denylisted = '1';
```

A denylisted query stays disabled until osquery restarts. [8.14](8.14-degradation.md) covers watchdog flags, query cost, and how denylisting appears across a fleet.

### Evented table state

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

An active subscriber with `events = 0` has received no events from its publisher. If `active = 0`, the subscriber is not running; start by checking the flag that disables events.

### The agent-side log ring

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error', 'warn')
ORDER BY time DESC
LIMIT 100;
```

Read `fleetd_logs` before restarting fleetd. It holds the current session's most recent 10,000 entries in memory, and a restart clears them. The schema documents the reset behavior; the table implementation defines the entry limit.

The table comes from Fleet's `fleetd_tables` extension. If `osquery_extensions` shows no extension loaded, `fleetd_logs` returns nothing.

### Clock and time window

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Check the host's clock before comparing timestamps across systems. Clock skew can cause certificate validation and MDM SCEP failures, and can put the events you need outside a query's time window.

### Disk encryption

macOS and Linux:

```sql
SELECT name, uuid, encrypted, type, encryption_status, filevault_status, uid
FROM disk_encryption;
```

`encryption_status` is one of `encrypted`, `not encrypted`, `undefined`. `filevault_status` is one of `on`, `off`, `unknown`.

macOS, the short form:

```sql
SELECT status FROM filevault_status;
```

Windows:

```sql
SELECT device_id, drive_letter, protection_status, conversion_status,
       encryption_method, percentage_encrypted, lock_status
FROM bitlocker_info;
```

### Installed software presence

Choose the table for the host's platform and filter for the software you are investigating.

```sql
-- macOS
SELECT name, bundle_identifier, bundle_short_version, bundle_version, path
FROM apps
WHERE bundle_identifier LIKE 'com.example.%';

-- Windows
SELECT name, version, publisher, install_location, install_date
FROM programs
WHERE name LIKE '%Example%';

-- Linux (Debian family)
SELECT name, version, arch, status FROM deb_packages WHERE name LIKE '%example%';

-- Linux (RPM family)
SELECT name, version, release, arch, vendor FROM rpm_packages WHERE name LIKE '%example%';
```

### Certificate presence and expiry

```sql
SELECT common_name, subject, issuer, ca, self_signed, path,
       datetime(not_valid_after, 'unixepoch') AS expires_utc,
       key_strength, sha1
FROM certificates
WHERE common_name LIKE '%example%';
```

On Windows, `certificates` also includes `store`, `store_location`, `store_id`, `sid`, and `username`. Add a filter to keep the lookup focused: an unfiltered query walks the whole keychain or certificate store and can exceed the watchdog's resource limits on a busy host.

### File carve status

```sql
SELECT time, carve_guid, request_id, path, size, sha256, status
FROM carves
ORDER BY time DESC;
```

The host reports carve progress as `STARTING`, `PENDING`, `SUCCESS`, or `FAILED`. This complements the server-side record by showing what happened on the device.

Take care with the `carve` column: setting it to `'1'` starts a carve. To inspect an existing attempt, read its `status`. [8.7.8](#878-running-and-retrieving-a-file-carve) explains how to start a carve and retrieve the file.

<a id="is-something-else-running"></a>

### Running processes

```sql
SELECT pid, name, path, cmdline, uid, start_time, resident_size
FROM processes
WHERE name LIKE '%example%';
```

Use this query to check for another management agent, a security product, or a second osqueryd process on the host.

## 8.7.2 Investigate a group of hosts

Once you have a useful query, a live report can show how widely the condition occurs. Run it across the relevant group to compare versions, configuration, or symptoms. For a closer investigation of one affected host, follow [8.4](8.4-host-side-investigation.md).

| Population question | Query | What the spread tells you |
|---|---|---|
| osquery version spread | `SELECT version FROM osquery_info;` | Whether the osqueryd channel is stalled on a subset. This is the osquery toolkit version, **not** the fleetd or Orbit version; for that use `orbit_info` in the next row |
| Orbit and osqueryd channel spread | `SELECT version, orbit_channel, osqueryd_channel, desktop_version FROM orbit_info;` | Which hosts are pinned to a channel that no longer matches policy |
| OS build spread | `SELECT name, version, build, arch FROM os_version;` | Whether a symptom tracks one OS build. Use it to check whether an OS update is associated with the issue. |
| Config validity | `SELECT config_hash, config_valid FROM osquery_info;` | How many hosts rejected the config they were served. Count `config_valid = 0`; do not read multiple hashes as partial convergence, since Fleet serves a per-host config |
| Flag convergence | `SELECT value FROM osquery_flags WHERE name = 'distributed_interval';` | Whether an agent options change reached the whole fleet or a fraction of it |
| Conflicting product | `SELECT name, path FROM processes WHERE name LIKE '%example%';` | How widely a suspected conflicting product is running |
| Clock skew | `SELECT unix_time, timezone FROM time;` | Whether skew is limited to one host or shared by hosts using an NTP source |

Fleet returns each host's rows separately. To summarize the results across hosts, export them or process the CLI output:

- In the UI, export the results table to CSV and count the values you need. The UI is a volatile surface.
- With `fleetctl`, process the JSON objects written to stdout. Each host returns an object shaped `{"host": "<hostname>", "rows": [ {...} ], "error": "..."}`. JSON is the default output; `--pretty` displays a table.

```sh
fleetctl report --labels "macOS" \
  --query "SELECT version FROM os_version;" \
  --exit --timeout 2m | jq -r '.rows[].version' | sort | uniq -c | sort -rn
```

Count the per-host JSON objects when you need the number of responding hosts. A host can return several rows, no rows, or an error; piping through `jq '.rows[]'` keeps only rows and loses the empty and error responses.

The command's completion flags also affect coverage. `--exit` waits for hosts Fleet currently considers online, so it can finish while offline targets remain absent. Set `--timeout` to bound the wait for an online host that never replies; without a timeout, that wait can continue indefinitely.

Keep the status line visible while checking coverage. `--quiet` suppresses it, which can be useful in a script once you have another way to account for responding and missing hosts. The example above leaves it enabled.

When sharing a count or distribution, include the responding-host count and the number targeted. This makes it clear how much of the group the result represents, especially if the missing hosts may be affected by the issue.

`--hosts` accepts comma-separated hostnames, UUIDs, or serial numbers. `--labels` accepts comma-separated label names and targets hosts with any of those labels. Passing both selects their union. Labels let you investigate the same groups you already use for policies and profiles.

For information that osquery does not expose, or a question about hosts that cannot respond, use Fleet's stored server state. [8.6](8.6-server-state.md) covers the relevant MySQL queries.

## 8.7.3 What a live report cannot tell you

A live report uses `distributed/read` to fetch the query and `distributed/write` to return results. A successful response confirms that path. On a fully enrolled Mac or Windows computer, it is one of five channels described in [8.1](8.1-diagnostic-method.md); check the others separately when investigating MDM, scripts, or software installs.

On ChromeOS, the extension answers these endpoints without running osqueryd ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)).

| Situation | What a live report shows | What is actually true |
|---|---|---|
| MDM enrollment broken, osquery fine | 100% responded | Profiles and commands are failing. A live report never touches the MDM channel. |
| osquery dead, Orbit fine | No response | Orbit is still checking in, still taking scripts and software installs. Fleet's online status tracks the osquery last-seen time, though ([4.5](../04-know-your-devices/4.5-monitor-fleet-wide-state.md)), so once that ages past the host's interval Fleet reports the host offline even while Orbit keeps working. |
| Host asleep or off network | No response | The host may be healthy but unavailable. It receives no live query if it never checks in during the campaign. |
| Android host | Not targetable | No osquery and no fleetd on Android. Live reports do not apply. |
| Windows or Linux host, `unified_log` query | Table does not exist | `unified_log` is macOS only. |

Also account for result lifetime and missing responses:

- Results last for the campaign and are not stored as host data. Use a scheduled report or host vital when you need a record over time.
- A missing response needs further investigation. The [control test in 8.14](8.14-degradation.md#8142-establish-a-control-first) helps distinguish an unavailable host or osquery process from a query that the watchdog killed or denylisted.

## 8.7.4 How it works, briefly

The following sequence shows where a report can wait or fail. It follows `docs/Contributing/guides/troubleshooting-live-queries.md`.

| # | Step | Where state lands |
|---|---|---|
| 1 | `POST /api/latest/fleet/reports/run` with query and targets | Fleet creates a live query campaign row in **MySQL** and gets a campaign ID |
| 2 | Fleet stores the campaign and its targets | **Redis** |
| 3 | Browser or `fleetctl` opens a connection under `GET /api/latest/fleet/results/` and upgrades to a **websocket**; that Fleet instance subscribes to the campaign in Redis | Redis pubsub subscription, held by one Fleet instance |
| 4 | Each device hits `distributed/read` on **its next check-in**, at its own `distributed_interval`. Fleet reads the campaign from Redis and hands the SQL back | Nothing new; this is a read |
| 5 | The device runs the query locally and returns rows on `distributed/write` | Fleet writes results to **Redis** for that device and campaign |
| 6 | Redis delivers results to the subscribed instance, which streams them over the websocket | Rendered in the browser or written to stdout by `fleetctl` |

Use that sequence to guide your checks:

- Allow for the host's check-in interval as well as execution and network time. With a 60-second `distributed_interval`, a host may wait up to 60 seconds before receiving the query. Check that interval when choosing a timeout.
- Check Redis when results are missing across Fleet instances. Any instance can receive host results, but one instance holds the client's connection and reads those results from Redis.
- Check websocket upgrades and connection lifetime at the load balancer or proxy. A broken websocket path can interrupt reports while other Fleet features continue to work.

For ingress rules and access-log searches, look for campaign creation at `POST /api/latest/fleet/reports/run` or `POST /api/latest/fleet/reports/run_by_identifiers`. The latter accepts hostname, UUID, or serial targets and is used by `fleetctl`.

Results use the `/api/latest/fleet/results/` prefix. Match the prefix in ingress rules: `fleetctl` uses `/results/websocket`, but a rule allowing only that exact path may exclude the browser.

`GET` on the same `reports/run` path is a separate synchronous endpoint. [8.14](8.14-degradation.md) uses it to test reporting without a websocket connection.

If the report path appears to be failing, continue with [8.14](8.14-degradation.md). It provides the `SELECT 1 WHERE 1 = 0;` control test, tests that bypass individual layers, and the synchronous API. It also explains how Redis pubsub output-buffer limits can end a report early: Fleet logs and reports the pub/sub error, but does not retry the lost delivery.

## 8.7.5 Collecting macOS host logs remotely

On macOS, `unified_log` reads the OSLog framework through a live report. This lets you collect relevant system-log entries remotely.

To read mdmclient activity from the last hour:

```sql
SELECT timestamp, process, subsystem, category, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 3600 FROM time)
ORDER BY timestamp DESC;
```

Keep the time window narrow. The schema asks for a `timestamp >` or `timestamp >=` constraint for performance (`schema/osquery_fleet_schema.json`), and `max_rows` defaults to 100. If you need more entries, raise the cap while retaining the time constraint:

```sql
SELECT timestamp, process, level, message
FROM unified_log
WHERE process = 'mdmclient'
  AND subsystem = 'com.apple.ManagedClient'
  AND timestamp > (SELECT unix_time - 900 FROM time)
  AND max_rows = 500
ORDER BY timestamp DESC;
```

`predicate` accepts an OSLog predicate string and combines it with the constraints osquery builds from the other columns. [8.2](8.2-log-surfaces.md) explains which log subsystems to inspect for each pipeline.

## 8.7.6 The CLI form

```sh
fleetctl report \
  --query "SELECT version FROM osquery_info;" \
  --hosts "host-a,host-b" \
  --exit \
  --timeout 2m
```

Use `fleetctl report` for new commands and scripts. `fleetctl query` remains a deprecated alias and logs a notice when used. That notice shares the client's deprecation log topic, which can be suppressed with one flag, so an absent warning does not establish that an alias is current.

| Flag | Env var | What it does |
|---|---|---|
| `--query` | `QUERY` | The SQL to run. Mutually exclusive with `--report-name`. |
| `--report-name` (alias `--query-name`) | `REPORT_NAME`, `QUERYNAME` | Run a saved query by name instead of ad hoc SQL |
| `--hosts` | `HOSTS` | Comma-separated targets, by hostname, UUID, or serial number |
| `--labels` | `LABELS` | Comma-separated label names; matches hosts with any of them |
| `--exit` | `EXIT` | Exit once 100% of **online** hosts have returned results |
| `--timeout` | `TIMEOUT` | Give up after a duration (`10s`, `1h`) |
| `--quiet` | `QUIET` | Results only, no status line. Use this when piping. |
| `--pretty` | `PRETTY` | Human-readable output instead of JSON |
| `--fleet` (alias `--team`) | | Fleet ID that owns the named saved report; `0` means global |

Provide `--hosts` or `--labels`. Without either, the command returns `No hosts or labels targeted. Please provide either --hosts or --labels.`

The status line, written to stderr, reads:

```
 42% responded (91% online) | 210/500 targeted hosts (210/230 online)
```

Here, 210 hosts have responded out of 500 targets, of which Fleet considers 230 online. `--exit` waits for the online fraction to reach 100%; it does not wait for all 500 targets. Read both fractions when deciding whether the results cover the group you intended to investigate.

The CLI is useful for both diagnosis and automation:

- If the CLI returns results while the UI does not, focus on the browser and its network and websocket path. The CLI still uses a websocket, but removes the browser from the test. See the layer-bypass table in [8.14](8.14-degradation.md).
- JSON output gives scripts one object per responding host, ready to summarize or compare with another data source.

## 8.7.7 Keep queries considerate of device resources

Live reports run on devices people may be using for work. Start with a focused query and a small target group, then expand once you understand its cost.

| Rule | Why |
|---|---|
| `LIMIT` anything that could return many rows | Large result sets can overwhelm network throughput and the results never arrive (`docs/Contributing/guides/troubleshooting-live-queries.md`) |
| Constrain wide tables (`certificates`, `processes`, `unified_log`, file globs) | The osquery watchdog kills expensive queries, and a repeatedly expensive scheduled query gets denylisted |
| Bound every time window against `time` | A bounded window limits log scanning and keeps the returned events relevant |
| Target narrowly, then widen | Test on one host, then a label, then a fleet. Resolve excessive resource use before expanding the targets. |
| Avoid recursive directory traversal and wildcard paths | These can require enough work to trigger the watchdog |

[8.14](8.14-degradation.md) covers watchdog flags, denylisting, and investigations where a healthy server receives responses from only 40 to 70 percent of the targets.

## 8.7.8 Running and retrieving a file carve

A file carve retrieves the contents of a file from a host. Use it when you need a configuration file, a sample for analysis, or a log that is too large to inspect through `unified_log`. osquery uploads the file in blocks for Fleet to reassemble.

Carving is available in Free. Retrieval requires a global admin with `carve · read`; there is no fleet-scoped equivalent ([a.4](../09-appendices/a.4-roles-and-permissions-matrix.md)).

The [File carve status](#file-carve-status) query above shows the host's progress through `STARTING`, `PENDING`, `SUCCESS`, and `FAILED`. The steps below cover starting the attempt, receiving it in Fleet, and downloading the completed file.

### Initiate a carve

Start a carve through a live report. There is no dedicated start button or carve-specific start endpoint. Setting the `carves` table's `carve` column to `1`, or calling osquery's `carve()` function, requests an upload of the matching file:

```sql
SELECT * FROM carves WHERE carve = 1 AND path LIKE '/var/log/example.log';
```

Run the query through the UI, live-report REST endpoint, or `fleetctl report --query "..."`, targeting the host with the file ([8.7.6](#876-the-cli-form)). osquery uploads the bytes through the separate carve channel; download them afterward through the interfaces below.

Check the host's `carves` table to confirm the attempt started. The write trigger, `carve()` function, and host-side state transitions belong to osquery, so Fleet's source alone does not establish their behavior.

### How blocks reach Fleet

osquery splits the file into blocks, 8 MB by default (`--carver_block_size`). A begin request declares the total size, block size, and block count, and Fleet returns a session ID. osquery then posts the blocks in order. Fleet checks their sequence and declared sizes as it reassembles and stores the file.

Uploads use host and session credentials, so they can proceed without an administrator signed in. The begin and block requests authenticate differently:

- The begin request uses the host's node key, as other osquery requests do. Fleet identifies the host and validates the declared sizes before recording the session.
- With `osquery.allow_body_auth_fallback` enabled, block requests authenticate with matching `session_id` and `request_id` values. They carry no node key, and Fleet does not check host ownership of the session.
- With that setting disabled, block requests also require the host's node key in an `Authorization` header. Fleet rejects a block if that host does not own the carve.

That setting strengthens block authentication only; it does not change how the begin request works.

Fleet rejects a begin request if the declared carve size is zero or exceeds 8 GiB, the block size exceeds 256 MiB, or the sizes and block count are inconsistent. These checks happen before the session is recorded, so a rejected begin leaves no server-side carve record even though the host attempted it. [8.14](8.14-degradation.md) lists the limits.

An out-of-order or oversized block fails after the session exists. Fleet marks the carve errored where it can, making that failure visible during retrieval.

### Retrieve a completed carve

Retrieve carves through `fleetctl` or the REST API as a global admin. The Fleet web UI has no carves page.

| Step | Command |
|---|---|
| List carves, with a completion percentage and an errored column | `fleetctl get carves` (add `--expired` to include expired ones) |
| Read one carve's metadata | `fleetctl get carve <id>` |
| Download the reassembled file | `fleetctl get carve <id> --outfile <path>` (or `--stdout`) |

The REST endpoints are `GET /api/v1/fleet/carves` for the list, `GET /api/v1/fleet/carves/{id}` for metadata, and `GET /api/v1/fleet/carves/{id}/block/{block_id}` for one block. `fleetctl` downloads the blocks in order.

Wait until `get carves` reports `100%` completion and `errored` is `no`, then download the file. [a.7](../09-appendices/a.7-fleetctl-command-reference.md) documents the commands.

### Where carves are stored

A carve's metadata always lives in MySQL. The block bytes go to one of two places:

- MySQL stores the blocks by default, with no object storage required. Large carves can add substantial database storage ([1.6](../01-foundations/1.6-the-fleet-server.md), [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md)).
- A configured S3 or GCS carves bucket stores the bytes while metadata remains in MySQL. See [2.3](../02-administer-and-deploy-fleet/2.3-deploy-on-aws-or-gcp.md) for bucket setup and [8.13](8.13-escalation.md) for `s3_carves_*` settings.

<a id="retention-carve-evidence-is-perishable"></a>

### Carve retention and expiry

Retrieve a carve while its blocks are still available. It captures a file at one moment, and Fleet does not automatically request another upload. MySQL removes blocks through scheduled cleanup; object storage retains them according to its lifecycle policy and operator actions.

For MySQL-backed carves, plan to download the file the same day. An hourly job deletes blocks from carves older than 24 hours, up to 50,000 carves per run, and marks them expired. Actual deletion depends on the job running and reaching the carve; it does not happen exactly at the 24-hour mark. There is no carve-specific setting to extend MySQL retention.

For S3-backed carves, retention follows the bucket's lifecycle policy. Fleet does not delete the objects. Its hourly job checks completed carves older than 24 hours and marks them expired when an object is definitively missing. Throttling and transient network failures do not count as proof of deletion.

You can tune or disable that reconciliation with `s3_carves_cleanup_disabled`, `s3_carves_cleanup_max_per_run`, and `s3_carves_cleanup_concurrency`. These settings do not disable MySQL cleanup.

Carve metadata remains after the blocks expire. Reconciliation or a download can discover that an object is gone; subsequent block downloads and `--outfile` attempts return `cannot get block for expired carve`. You can still inspect metadata with `get carve <id>`, but its presence does not mean the file is available.

Fleet cannot un-expire a carve or recover its missing blocks. Recovery requires a MySQL or object-store backup, as covered in [7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md).

<a id="failures-and-gotchas"></a>

### Carve troubleshooting

| Symptom | Cause and fix |
|---|---|
| Cannot find carves in the web UI | There is no UI for carves. Use `fleetctl` or the REST API, as a global admin. |
| A fleet admin or maintainer cannot see a carve | Retrieval is global-admin only (`carve · read`). There is no fleet-scoped read. |
| `cannot get block for expired carve` | The blocks are gone: past the MySQL 24-hour cleanup, or the S3 object was deleted or lost. Not recoverable from Fleet; restore from backup ([7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md)). |
| `get carves` lists it, but the download fails | Check whether the record is expired. Metadata can remain after the blocks are removed. |
| `--outfile` leaves a wrong tail on the file | `--outfile` opens the file without truncating, so writing a shorter carve over a longer file leaves the old tail attached. Write to a fresh path ([a.7](../09-appendices/a.7-fleetctl-command-reference.md)). |
| Carve shows `errored` | A block arrived out of order or over its declared size, or a block failed to store. Begin-time failures never land here (see the next row). |
| A carve never appears at all | The begin request was rejected on its size or consistency checks, so Fleet created no carve session. osquery had started the attempt on the host, but there is no server-side record to list or retrieve. |
| S3 upload fails after lowering the block size | Fleet passes each block straight to the configured object store without checking its size, so any minimum-part-size rule is the backend's, not Fleet's. On AWS S3 that minimum is 5 MiB for every part but the last, and a hand-lowered block below it fails the upload; other S3-compatible or GCS backends may draw the line elsewhere, so validate it against the store you actually run. Fleet's default is 8,000,000 bytes, which clears AWS S3's 5 MiB floor, but Fleet validates no backend's minimum, only its own 256 MiB block ceiling. |
