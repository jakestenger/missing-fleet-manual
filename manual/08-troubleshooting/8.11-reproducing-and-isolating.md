# Reproducing and isolating

Turning "it happens sometimes" into something observable on demand. Everything here is technique that applies across features. Feature sections point at this one rather than restating it.

Come here once you have classified the failure in [8.1](8.1-diagnostic-method.md) and know which channel and which stage you mean to test. A reproduction is only worth building against a specific hypothesis.

Raise server verbosity before anything else. That is not the same as reading logs, which [8.1](8.1-diagnostic-method.md) puts at step seven and means it. Raising verbosity turns the recorder on so that step seven has something to read: per-request log lines are DEBUG unless the error is a non-client error, so at default verbosity a failure can leave no trace, and you cannot go back and re-log a request that already happened. The change carries a restart and a log-volume cost, and [8.3](8.3-server-logs.md) owns both.

Then read the timing table below, because a sizeable share of "stuck" is a wait you did not know you were inside.

## 8.11.1 Timings that make something look stuck

Read this before deciding anything is broken. These are the intervals Fleet and fleetd actually wait. Being inside one means the wait is normal so far. It does not mean the stage is healthy, and a failure can already have happened inside any of them. Use the table to decide whether you have waited long enough to have evidence, not to decide that nothing is wrong.

| Stage | Value | Where it is set |
|---|---|---|
| osquery check-in for distributed queries | **10 seconds** on a new Fleet install, which ships `distributed_interval: 10` in the global agent options. Fleet recommends 10 to 30 seconds. | `config.options.distributed_interval` in agent options |
| osquery result log upload period | **10 seconds** on a new Fleet install, from the same shipped agent options. No recommended range is published. | `config.options.logger_tls_period` |
| Orbit config receiver poll | **30 seconds** between polls, on every platform including Linux. A poll that fails enters exponential backoff up to a **5 minute** ceiling, and returns to 30 seconds on the next success. | Fixed |
| Ad-hoc script (**Scripts** tab, `fleetctl run-script`) | **5 minutes** | `script_execution_timeout` in agent options, in seconds. Maximum 18000, which is 5 hours. A team with no value of its own inherits the global one. |
| Install, post-install, and uninstall scripts for software | **1 hour**, and one value covers every step: install, post-install, the implicit uninstall after a failed post-install, and an explicit uninstall. Download time is not counted. | Fixed. The agent option above does not apply to this path. |
| Software installer result upload to Fleet | **5 attempts**, 30 seconds apart, so roughly 2 minutes | Fixed. Script results, unlike installer results, are not retried at all. |
| VPP app install verification | **10 minutes** | `server.vpp_verify_timeout`, `FLEET_SERVER_VPP_VERIFY_TIMEOUT` |
| VPP verification poll gap | **5 seconds** between verification requests | `server.vpp_verify_request_delay` |
| Windows MDM relaxed poll | **480 minutes (8 hours)** | Set on the device by the poll schedule Fleet sends at enrollment ([8.9](8.9-windows-mdm-diagnostics.md)) |
| Windows MDM fast poll | **1 minute** | Same mechanism, used for hosts whose fleetd cannot be woken on demand |
| DEP profile assignment sync | **1 minute** | `mdm.apple_dep_sync_periodicity` |
| First run of any cron after server start | **10 seconds**, or the schedule interval if that is shorter | Fixed |
| Cron interval config reload | **1 hour** | Fixed |

The two script timeouts are the pair that gets confused, because the same word covers both. A trivial control script run from the **Scripts** tab is on the 5 minute clock; an install script inside a software package is on the 1 hour clock. Fleet names the number in the failure itself, as "Timeout. Fleet stopped the script after N seconds to protect host performance", so read N rather than assuming which limit you hit.

The Windows number is the one that catches people. An 8 hour poll means a queued command can sit for most of a working day if fleetd cannot wake the host, and that is correct behavior, not a stuck queue. Fleet's design intent is that commands other than the poll ride an on-demand session opened through fleetd's config check-in. So the real question on a slow Windows command is whether that host is wakeable.

### Read the interval the host is using

Agent options are what you asked for. The host record carries what osquery has: `distributed_interval`, `config_tls_refresh`, and `logger_tls_period` are columns on the host object returned by `GET /api/v1/fleet/hosts/:id` (fleetdm.com/docs/rest-api/rest-api). To read them from the host itself:

```sql
SELECT name, value FROM osquery_flags
WHERE name IN ('distributed_interval', 'config_tls_refresh', 'config_refresh', 'logger_tls_period');
```

That is Fleet's own query for it. A gap between the configured value and the effective one means the host has yet to pick up the config, or the value came from a flagfile rather than from Fleet.

## 8.11.2 Establish a control before changing anything

Find the simplest version of the operation that should work. Confirm it does. Then add variables back one at a time. Without a passing control you cannot tell a broken feature from a broken path.

| Control | What a pass tells you | What a failure points at |
|---|---|---|
| **Trivial script:** run a script whose body is `echo hi` on the affected host | Script queue, Orbit script receiver, and result upload were all working for that one run | The script pipeline, not your script |
| **Benign MDM command:** send a read-only command (for macOS, a `DeviceInformation` query) to the affected host | APNs push, host check-in, command queue, and result parsing were all working for that one command | The MDM transport, not the profile or command content |
| **Minimal profile on one host:** a profile with a single trivial payload, scoped to a one-host label | Profile delivery worked end to end for that payload | Delivery, not the payload |
| **Live report** | Whole path from device to browser | See [8.14](8.14-degradation.md) §8.14.2, which owns the live report control test and the layer-bypass sequence |

Run the control against the **same host** and the **same team** as the failure. A control that passes on a different host has told you less than it looks like.

A control narrows the investigation; it does not close a branch. A passing trivial script says the pipeline carried one small payload once, which is a different claim from "the script pipeline is healthy", and the difference matters for anything intermittent or size-dependent.

## 8.11.3 Forcing timing instead of waiting

Most Fleet background work runs on a named cron schedule. Trigger it rather than waiting out the interval.

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

Schedule names as of 4.90.0. Not all are registered on every deployment, and the error message on an unknown name lists the ones that are:

`apple_mdm_dep_profile_assigner` · `cleanups_then_aggregation` · `frequent_cleanups` · `usage_statistics` · `vulnerabilities` · `automations` · `integrations` · `activities_streaming` · `mdm_apple_profile_manager` · `mdm_windows_profile_manager` · `mdm_android_profile_manager` · `mdm_android_device_reconciler` · `apple_mdm_iphone_ipad_refetcher` · `apple_mdm_apns_pusher` · `calendar` · `google_workspace_sync` · `uninstall_software_migration` · `upgrade_code_software_migration` · `maintained_apps` · `maintained_apps_auto_update` · `refresh_vpp_app_versions` · `apple_mdm_iphone_ipad_reviver` · `upcoming_activities_maintenance` · `host_vitals_label_membership` · `batch_activity_completion_checker` · `scheduled_batch_activities` · `enable_android_app_reports_on_default_policy` · `migrate_to_per_host_policy` · `query_results_cleanup` · `send_recovery_lock_commands` · `send_managed_local_account_rotation_commands` · `apple_mdm_worker` · `chart_data_collection` · `cleanup_expired_adue_challenges`

### A trigger can report success for a run that never happened

This is the trap. A trigger returns **without triggering** in three cases:

| Case | What the caller gets | What `fleetctl` prints |
|---|---|---|
| A scheduled run is already `pending` | The pending run's stats | `[!] Conflict…` |
| A triggered run is `pending` or `queued` | The pending run's stats | `[!] Conflict…` |
| Fleet's internal trigger channel is busy | **No stats, no error, and no run** | `[+] Sent request to trigger <name> schedule` |

The third row is a silent no-op. Nothing on the path from the trigger to the API to the CLI checks whether the run actually started, so the CLI prints its normal success line for a run that did not occur. The busy-channel case is logged at **debug level only**, as `trigger channel not available`.

**So pair every trigger with a `cron_stats` check.** A new row with `stats_type = 'triggered'` and a `created_at` matching your trigger tells you the request was accepted. Read its status before concluding the work ran:

| Status | What it means |
|---|---|
| No matching row | The request never became a run. Suspect the silent no-op above. |
| `queued` | Accepted for a node that runs this schedule remotely. Not started. |
| `pending` | Running now. |
| `completed` | The run ended. Not a success signal on its own: read the `errors` column, which carries the errors from the individual jobs inside the schedule. |
| `canceled` | The run was interrupted with errors already recorded. |
| `expired` | The row sat `pending` or `queued` and was reaped by cleanup: after 2 hours with no live lock for that schedule, or after 12 hours regardless. The run's real outcome was never written. |

Triggering needs a **global administrator**. No team role can do it, at any level. There is no read API for `cron_stats` either; it needs database access. See [8.6](8.6-server-state.md), which owns that table.

Two further wrinkles, before you trust a trigger:

- **Multi-node.** The trigger lands on whichever node the load balancer picked. For a schedule that is disabled on that node, Fleet records a remote trigger: a `queued` row for the node that does run the schedule to pick up on its own trigger poll. On a node where neither applies, the name comes back as not found. Pin a context to one node as in [8.14](8.14-degradation.md) §8.14.3.
- **Concurrent triggers can double-run.** The remote-trigger read-then-insert is not atomic. Fleet accepts that, because the worst case is the schedule running twice.

## 8.11.4 Shrink the target set

Fleet, then a label, then one host. Do this before shrinking anything else, because a one-host repro makes every other step cheap.

A one-host label, applied with GitOps:

```yaml
labels:
  - name: repro-host
    description: Single host under investigation. Delete when done.
    label_membership_type: manual
    hosts:
      - <hardware-serial-or-uuid>
```

Or through the API:

```sh
fleetctl api -X POST -F name='repro-host' -F hosts='["<hardware-serial-or-uuid>"]' \
  /api/v1/fleet/labels
```

Use the host's **hardware serial** or **UUID**, or its Fleet host ID through GitOps or the `host_ids` field of the API. Fleet deprecated `hostname` as a label host identifier, and a hostname that does not resolve to a host produces a label with no members rather than an error, which is a repro that silently tests nothing.

Confirm membership before you trust the scope. The label should show exactly one host, and it should be the right one. Then scope the profile, script, or installer to `repro-host`, and delete the label once you have your answer, so a stale one-host label does not quietly narrow someone else's change later.

**Why the setup cost is worth paying.** A one-host repro removes host count from the variable list, which is what separates a scale ceiling from a limit and both from a content problem ([8.14](8.14-degradation.md) §8.14.1). It also makes host-side evidence tractable: one Orbit log, one `profiles status`, one set of osquery counters ([8.4](8.4-host-side-investigation.md)). And it makes the blast radius of destructive steps like re-enrollment acceptable.

Use a **spare host**, not a user's laptop, if any step in the repro is disruptive.

## 8.11.5 Shrink the payload

Strip the thing being delivered until it cannot fail, then add back. Whatever still fails is the cause.

| Real thing | Minimal substitute | What a still-failing minimum means |
|---|---|---|
| Configuration profile | One trivial payload, one key. Same identifier scheme, same signing state. | Delivery, not content |
| Software installer | A script package whose install script is `echo hi` and whose uninstall script is `echo hi` | The install pipeline, not the installer |
| Install script that hangs | Replace with `echo hi`; if the timeout still trips, it is not your script | See the 1 hour software-install timeout in §8.11.1, and check the number in the timeout message to confirm which clock ran out |
| Scheduled query or live report | `SELECT 1;` | The query path, not the SQL |
| Policy | A policy whose query is `SELECT 1;` (always passes) | Policy evaluation or reporting, not the check |
| MDM command | `DeviceInformation` with a single requested key | Command transport, not the command |

Change **one dimension at a time**. Shrinking payload and target set in the same step means a pass tells you nothing about which change mattered.

## 8.11.6 Other ways to force a stage

| Action | Forces | Production safe |
|---|---|---|
| Host refetch (`POST /api/v1/fleet/hosts/:id/refetch`, or **Refetch** in the UI) | Host detail queries on the host's next check-in | Yes |
| Resend a profile (**Resend** on the host's profile, or `POST /api/v1/fleet/hosts/:id/configuration_profiles/:uuid/resend`) | Re-delivery of that one profile | Yes |
| Retry a software install | A fresh install attempt through the full pipeline | Yes, but the install itself runs on the user's machine |
| `fleetctl trigger --name=<schedule>` | Server-side background work | Yes. Check `cron_stats`, per §8.11.3. |
| Restart fleetd on the host | Config re-fetch, and re-read of anything under `command_line_flags` | Yes, with a short gap in reporting. Watchdog denylist state resets too ([8.14](8.14-degradation.md) §8.14.5). |
| `sudo profiles renew -type enrollment` (macOS) | A fresh run of automated device enrollment (ADE, formerly DEP) against the enrollment profile currently assigned to the host | **No.** Use it on a host you are willing to disturb. It re-runs enrollment, so it can change MDM state. Confirm the before and after with `sudo profiles status -type enrollment` ([8.4](8.4-host-side-investigation.md)). |
| Unenroll and re-enroll a host | Everything, from scratch | **No.** Last resort. Destroys the evidence for whatever you were investigating. |

Pick the least destructive action that touches the stage you suspect. Re-enrollment answers "does it work from clean" and nothing else, and you cannot ask a follow-up question afterwards.

## 8.11.7 Differential isolation

Often cheaper than reproduction, and sometimes the answer. Vary exactly one axis and compare.

State what you held constant, and stay aware of what you did not control. Each row below is evidence, not a verdict.

| Vary this | Same result on both makes unlikely | A different result implicates |
|---|---|---|
| **Host**, same team, same payload | Anything host-specific: local state, another agent, disk, the logged-in user | That host. Go host-side, [8.4](8.4-host-side-investigation.md). |
| **Platform**, same feature | The Fleet-side logic and the payload | The platform's MDM channel or agent path |
| **Team**, same payload | Team-scoped config: agent options overrides, team profiles, team software | Team configuration or scoping |
| **Fleet instance** (a throwaway, §8.11.9) | Anything specific to your deployment: infrastructure, network path, data, scale | Your production deployment. What remains in play on a clean instance is Fleet's behavior at that version, the payload, the test host, or a shared dependency. |
| **Fleet version** on the same data | Nothing on its own; it is a regression test | A regression. Read the release notes between the two versions (github.com/fleetdm/fleet/releases). |
| **Network position** (host on VPN versus off, or a different egress) | The host and the payload | Proxy, TLS inspection, or egress filtering |

Read the instance row in that direction and not the other. The same failure on a clean instance does not clear Fleet; it clears your deployment. §8.11.9 says the same thing in prose, and the two need to agree.

The platform comparison is the highest-value one for MDM problems, because the Apple, Windows, and Android delivery paths share almost no code below the queue. A failure on one platform only makes a platform-path failure much more likely than a Fleet-logic failure, whatever the symptom looks like from the UI. It does not establish one on its own, because the payload can be platform-specific too, and so can what the OS does with it.

## 8.11.8 Preparing for the next occurrence

When the failure will not come back on demand, set up so the **next** occurrence is diagnosable. Do this before the window closes.

| Prepare | Why |
|---|---|
| Raise server log verbosity now | Per-request log lines are DEBUG unless the error is a non-client error. At default verbosity some failures leave no trace at all, and you cannot go back and re-log a past request. |
| Capture `cron_stats` on a schedule | `cron_stats` has no read API and is trimmed by cleanup jobs. Snapshot name, instance, stats_type, status, errors, created_at, updated_at on a timer. [8.6](8.6-server-state.md) |
| Capture queue depth on the same timer | A backlog that has drained by the time you look is invisible. A time series of it is not. |
| Sample **raw record timestamps**, not aggregate metrics | See below. This is the one that fails most often. |
| Capture `fleetctl debug errors` before anything flushes | Errors live in Redis and age out per `logging_error_retention_period`. `--flush` deletes them. Capture, then flush if you must. |
| Note the exact onset time and every version that changed near it | Both sides: Fleet server, fleetd, osquery, the OS, and any other agent. |

### The two-clocks question needs per-record timestamps

Keep per-record timestamps alongside your percentiles. The core narrowing question in [8.1](8.1-diagnostic-method.md) compares the timestamp **inside** a record against the timestamp the destination stamped **on arrival**. An aggregated latency metric has already collapsed both into one number, so no sample rate recovers the comparison.

> [!internal] A real support case stalled exactly here. The customer's monitoring exposed only an aggregated latency figure for their log destination, so the two-clocks check could not be run at all, and the investigation could not distinguish a draining host-side osquery buffer from a destination re-reading its own bucket. The fix was a monitoring change, not a Fleet change.

### Long reproduction windows lose their own evidence

`logging_error_retention_period` governs how long recorded server errors survive in Redis. A reproduction window measured in days can age out the errors from the start of it. Snapshot `fleetctl debug errors` periodically across a long window rather than once at the end.

## 8.11.9 A throwaway Fleet instance

When the repro is destructive, needs a version change, or needs config you will not apply to production, stand up a disposable Fleet.

Docker Compose, per Fleet's own guide (fleetdm.com/guides/deploy-fleet-on-docker-compose):

```sh
mkdir fleet-repro && cd fleet-repro
curl -O https://raw.githubusercontent.com/fleetdm/fleet/fleet-v4.90.1/docs/solutions/docker-compose/docker-compose.yml
curl -O https://raw.githubusercontent.com/fleetdm/fleet/fleet-v4.90.1/docs/solutions/docker-compose/env.example
cp env.example .env
openssl rand -base64 32   # use as FLEET_SERVER_PRIVATE_KEY
```

Fetch from the release tag rather than `main`, so the file you get is the one that shipped with the version you are testing.

Two edits before you bring it up.

**Pin the image.** The published file uses `image: fleetdm/fleet` with no tag. An unpinned image cannot establish behavior at a version, which is the only reason to stand this up at all. Set it to the version under test, in the form Fleet's own Helm chart uses:

```yaml
    image: fleetdm/fleet:v4.90.1
```

[2.11](../02-administer-and-deploy-fleet/2.11-deploy-with-containers-or-virtual-machines.md) asks for the same pin in production, for a different reason.

**Decide about TLS.** `env.example` ships `FLEET_SERVER_TLS=true` and points `FLEET_SERVER_CERT` and `FLEET_SERVER_KEY` at `/fleet/fleet.crt` and `/fleet/fleet.key`. Those paths are inside the `data` named volume, and nothing in the recipe puts anything there. Left as shipped, Fleet has no certificate to serve. For a throwaway you drive from your own browser, set `FLEET_SERVER_TLS=false`. Keep it on only if you are pointing a real host at the instance, because fleetd requires TLS, and then you own placing a certificate and key at those paths in the volume.

Then set `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`, and `FLEET_SERVER_PRIVATE_KEY` in `.env` and bring the stack up. Fleet, MySQL, and Redis in one Compose file.

Confirm the version you actually got before you trust anything it tells you:

```sh
docker compose exec fleet /usr/bin/fleet version
```

**What it costs.** Fleet's own guide says about 15 minutes, and needs ports 1337, 3306, and 6379 free. That gets you Fleet, MySQL, and Redis, which is enough for anything server-side and anything agent-side you can point a test host at.

**What it does not get you.** Apple MDM needs an APNs certificate, ADE needs an Apple Business Manager (ABM) token, VPP needs a VPP token, and Android needs Android Enterprise. Each has to be issued to that instance. Windows MDM needs a publicly resolvable hostname with a trusted certificate, because the device does the connecting. So a throwaway is cheap for orchestration, software, scripts, and queries, and it is real work for MDM enrollment paths. Budget accordingly before you promise one.

**What it can prove.** Which side of the line the cause is on. A repro on a clean instance shows the production deployment is not a necessary condition, which leaves Fleet at that version, the payload, the test host, or a shared dependency such as the network path to Apple. A failure to reproduce on a clean instance points back at production: data, scale, infrastructure, network path, or config drift. Neither outcome names a single cause, and the first one is not by itself a Fleet bug report.

## 8.11.10 What is not documented

| Item | Status |
|---|---|
| A trigger that reports success without running | Verified behaviour. Undocumented, and `fleetctl` prints its normal success line for it. |
| Effective `distributed_interval` and `logger_tls_period` on an existing server | A new Fleet install ships both at 10 seconds in the global agent options, and Fleet's REST API reference states the 10 second `distributed_interval` default. Neither is a claim about a server that has been running for a while: agent options persist across upgrades, teams override globals, and flagfiles override Fleet. Read the effective value from `osquery_flags` per §8.11.1. |
| Env var names for `mdm.apple_dep_sync_periodicity` and `server.vpp_verify_request_delay` | Inferred from Fleet's config-key to env-var convention (`FLEET_MDM_APPLE_DEP_SYNC_PERIODICITY`, `FLEET_SERVER_VPP_VERIFY_REQUEST_DELAY`). The config keys and their defaults are verified in the server; the env var spellings are not individually verified. |
| Configurability of the 1 hour software-install timeout and the 30 second config receiver poll | No configuration surface found for either, and both are compiled-in constants at 4.90.1. The 5 minute ad-hoc script timeout is a different matter: it is configurable, and §8.11.1 gives the option. |
