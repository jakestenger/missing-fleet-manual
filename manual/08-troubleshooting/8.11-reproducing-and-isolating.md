# Reproducing and isolating

A useful reproduction turns an intermittent symptom into a test you can observe and repeat. This chapter provides techniques for choosing a control, reducing the target set and payload, and collecting evidence while the failure happens.

Start with the channel and failure stage identified in [8.1](8.1-diagnostic-method.md). Use them to state a hypothesis, such as "the host receives the script but cannot upload its result," and choose a test that can distinguish it from the alternatives.

Arrange the logging you need before running the test. Per-request DEBUG lines may be absent at normal verbosity, and raising verbosity afterward cannot recover them. [8.3](8.3-server-logs.md) covers the restart and log-volume implications of changing server logging.

Check the timing table as well so your test allows the relevant polling, execution, and reporting steps to finish.

## 8.11.1 Timings that make something look stuck

Use these intervals to choose an observation window. A stage can fail before its interval expires, so continue checking errors during the wait. Conversely, a waiting operation may still be within its normal delivery or execution window.

| Stage | Value | Where it is set |
|---|---|---|
| osquery check-in for distributed queries | **10 seconds** on a new Fleet install, which ships `distributed_interval: 10` in the global agent options. Fleet recommends 10 to 30 seconds. | `config.options.distributed_interval` in agent options |
| osquery result log upload period | **10 seconds** on a new Fleet install, from the same shipped agent options. No recommended range is published. | `config.options.logger_tls_period` |
| Orbit config receiver poll | **30 seconds** between polls, on every platform including Linux. A poll that fails enters exponential backoff up to a **5 minute** ceiling, and returns to 30 seconds on the next success. | Fixed |
| Ad-hoc script (**Scripts** tab, `fleetctl run-script`) | **5 minutes** | `script_execution_timeout` in agent options, in seconds. Maximum 18000, which is 5 hours. A fleet with no value of its own inherits the global one. |
| Install and post-install scripts for software, and the rollback Fleet runs after a failed post-install | **1 hour** per step. Download time is not counted. | Fixed. The agent option above does not apply to this path. |
| Explicit uninstall of software | **5 minutes**. An uninstall you request is dispatched as an ordinary script rather than through the installer, so it is on the same clock as the **Scripts** tab, and on a different clock from the rollback above, which Fleet runs itself. | `script_execution_timeout`, exactly as for an ad-hoc script |
| Software installer result upload to Fleet | **5 attempts**, 30 seconds apart, so roughly 2 minutes | Fixed. Script results, unlike installer results, are not retried at all. |
| VPP app install verification | **10 minutes** | `server.vpp_verify_timeout`, `FLEET_SERVER_VPP_VERIFY_TIMEOUT` |
| VPP verification poll gap | **5 seconds** between verification requests | `server.vpp_verify_request_delay` |
| Windows MDM relaxed poll | **480 minutes (8 hours)** | Set on the device by the poll schedule Fleet sends at enrollment ([8.9](8.9-windows-mdm-diagnostics.md)) |
| Windows MDM fast poll | **1 minute** | Same mechanism, used for hosts whose fleetd cannot be woken on demand |
| DEP profile assignment sync | **1 minute** | `mdm.apple_dep_sync_periodicity` |
| First run of any cron after server start | **10 seconds**, or the schedule interval if that is shorter | Fixed |
| Cron interval config reload | **1 hour** | Fixed |

The timeout depends on which runner executes the work. Ad-hoc scripts and requested uninstalls use the configurable 5-minute script timeout. Install scripts, post-install scripts, and automatic rollback after a failed post-install use the installer's fixed 1-hour limit for each step.

The same uninstall script can therefore have a 5-minute limit when requested directly and a 1-hour limit when run as rollback. Check the value in "Timeout. Fleet stopped the script after N seconds to protect host performance" to identify the limit that applied.

A Windows host on the 8-hour poll relies on fleetd for prompt delivery between polls. If that wake path fails, commands can wait until the fallback session. Check the host's wake capability and Orbit connectivity using [8.9](8.9-windows-mdm-diagnostics.md).

### Read the interval the host is using

Compare configured agent options with the values reported by the host. `GET /api/v1/fleet/hosts/:id` exposes `distributed_interval`, `config_tls_refresh`, and `logger_tls_period`. You can also read the effective values directly from osquery:

```sql
SELECT name, value FROM osquery_flags
WHERE name IN ('distributed_interval', 'config_tls_refresh', 'config_refresh', 'logger_tls_period');
```

If those values differ from Fleet's configuration, check whether the host has refreshed its configuration and whether a flagfile overrides the option.

## 8.11.2 Establish a control before changing anything

Choose the smallest operation expected to succeed on the affected path. Run it, record the result, then add complexity one change at a time. A passing control gives you a comparison for the failing workload.

| Control | What a pass tells you | What a failure points at |
|---|---|---|
| **Trivial script:** run a script whose body is `echo hi` on the affected host | Script queue, Orbit script receiver, and result upload were all working for that one run | The script pipeline rather than your script's content |
| **Benign MDM command:** send a read-only command (for macOS, a `DeviceInformation` query) to the affected host | Host check-in, command delivery, and result parsing worked for this command; check APNs separately if the device may have connected without a push | The MDM transport rather than the profile or command content |
| **Minimal profile on one host:** a profile with a single trivial payload, scoped to a one-host label | Profile delivery worked end to end for that payload | Delivery rather than the payload |
| **Live report** | Whole path from device to browser | See [8.14](8.14-degradation.md) §8.14.2, which owns the live report control test and the layer-bypass sequence |

Run the control against the same host and in the same fleet as the failure where possible. If you use another host, record that difference as part of the test.

Keep the conclusion proportional to the control. A successful short script confirms one successful trip through the pipeline; it does not rule out intermittent failures or problems with larger output.

## 8.11.3 Trigger background work for a test

You can request a named cron run to test background work without waiting for its next scheduled interval.

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

The following names are registered as of 4.90.0, depending on deployment configuration. An unknown-name error lists the schedules available on the responding instance.

`apple_mdm_dep_profile_assigner` · `cleanups_then_aggregation` · `frequent_cleanups` · `usage_statistics` · `vulnerabilities` · `automations` · `integrations` · `activities_streaming` · `mdm_apple_profile_manager` · `mdm_windows_profile_manager` · `mdm_android_profile_manager` · `mdm_android_device_reconciler` · `apple_mdm_iphone_ipad_refetcher` · `apple_mdm_apns_pusher` · `calendar` · `google_workspace_sync` · `uninstall_software_migration` · `upgrade_code_software_migration` · `maintained_apps` · `maintained_apps_auto_update` · `refresh_vpp_app_versions` · `apple_mdm_iphone_ipad_reviver` · `upcoming_activities_maintenance` · `host_vitals_label_membership` · `batch_activity_completion_checker` · `scheduled_batch_activities` · `enable_android_app_reports_on_default_policy` · `migrate_to_per_host_policy` · `query_results_cleanup` · `send_recovery_lock_commands` · `send_managed_local_account_rotation_commands` · `apple_mdm_worker` · `chart_data_collection` · `cleanup_expired_adue_challenges` · `mdm_service_discovery`

<a id="a-trigger-can-report-success-for-a-run-that-never-happened"></a>

### Confirm that the triggered run started

A trigger can return without starting a new run in these cases:

| Case | What the caller gets | What `fleetctl` prints |
|---|---|---|
| A scheduled run is already `pending` | The pending run's stats | `[!] Conflict…` |
| A triggered run is `pending` or `queued` | The pending run's stats | `[!] Conflict…` |
| Fleet's internal trigger channel is busy | **No stats, no error, and no run** | `[+] Sent request to trigger <name> schedule` |

When the internal trigger channel is busy, Fleet logs `trigger channel not available` at DEBUG but returns no error to the CLI. The normal `[+]` message therefore confirms only that the request was sent. Check `cron_stats` to establish whether it became a run.

Look for a new row with `stats_type = 'triggered'` and a `created_at` matching your request, then read its status:

| Status | What it means |
|---|---|
| No matching row | The request never became a run. Suspect the silent no-op above. |
| `queued` | Accepted for a node that runs this schedule remotely. Not started. |
| `pending` | Running now. |
| `completed` | The run ended. Not a success signal on its own: read the `errors` column, which carries the errors from the individual jobs inside the schedule. |
| `canceled` | The run was interrupted with errors already recorded. |
| `expired` | The row sat `pending` or `queued` and was reaped by cleanup: after 2 hours with no live lock for that schedule, or after 12 hours regardless. The run's real outcome was never written. |

Triggering requires a global administrator; fleet-scoped roles cannot do it. Reading `cron_stats` requires database access because it has no read API. [8.6](8.6-server-state.md) documents the table.

For multi-node deployments, also account for routing and concurrent requests:

- The load balancer chooses the node receiving the trigger. If the schedule is disabled there but registered for remote execution, Fleet creates a `queued` row for a node that runs it. That node picks it up on its trigger poll. If neither applies, the name is reported as not found. You can pin a context to a node using [8.14](8.14-degradation.md) §8.14.3.
- Concurrent remote triggers can schedule duplicate runs because the read and insert are not atomic. Check the resulting rows before issuing another request.

## 8.11.4 Shrink the target set

Reduce a widespread case to a label or one host before simplifying its payload. A smaller target set makes device-side evidence easier to collect and compare.

A one-host label, applied with GitOps:

```yaml
labels:
  - name: repro-host
    description: Single host under investigation. Delete when done.
    label_membership_type: manual
    hosts:
      - <hardware-serial-or-uuid>
```

Or through the API:

```sh
fleetctl api -X POST -F name='repro-host' -F hosts='["<hardware-serial-or-uuid>"]' \
  /api/v1/fleet/labels
```

Identify the host by hardware serial, UUID, or Fleet host ID through GitOps or the API's `host_ids` field. `hostname` is deprecated for label membership. An unresolved hostname can create an empty label without an error, so verify membership after creating it.

Confirm that the label contains exactly the intended host, then scope the test to `repro-host`. Remove the temporary label when the investigation is complete so its purpose does not become unclear later.

Check the test instance's license before choosing this approach. Label-scoped configuration profiles and software installers require Premium. Scripts are available on Free. A missing license can prevent the reproduction from reaching the stage you intended to test.

A one-host test helps determine whether the failure needs a larger population. It also gives you one set of Orbit logs, profile state, and osquery counters to examine ([8.4](8.4-host-side-investigation.md)). If the issue appears only at scale, [8.14](8.14-degradation.md) §8.14.1 explains how to distinguish capacity problems from configured limits.

Use a spare host for disruptive steps, including re-enrollment.

## 8.11.5 Shrink the payload

Simplify the payload to a known small example, then restore one part at a time. If the minimal case still fails, continue investigating the shared delivery or execution path. The result narrows the search without identifying a cause by itself.

| Real thing | Minimal substitute | What a still-failing minimum means |
|---|---|---|
| Configuration profile | One trivial payload, one key. Same identifier scheme, same signing state. | The delivery path, rather than what you were sending |
| Software installer | A script package whose install script is `echo hi` and whose uninstall script is `echo hi` | The install pipeline, rather than the installer you were shipping |
| Install script that hangs | Replace with `echo hi`. If the timeout remains, investigate the runner and delivery path before returning to the original script | See the 1 hour software-install timeout in §8.11.1, and check the number in the timeout message to confirm which clock ran out |
| Scheduled query or live report | `SELECT 1;` | The query path, rather than your SQL |
| Policy | A policy whose query is `SELECT 1;` (always passes) | Policy evaluation or reporting, rather than the check itself |
| MDM command | `DeviceInformation` with a single requested key | Command transport, rather than the command you were sending |

Change one dimension at a time. Keep the payload constant while reducing hosts, then keep that host set constant while reducing the payload.

## 8.11.6 Other ways to force a stage

| Action | Forces | Production safe |
|---|---|---|
| Host refetch (`POST /api/v1/fleet/hosts/:id/refetch`, or **Refetch** in the UI) | Host detail queries on the host's next check-in | Yes |
| Resend a profile (**Resend** on the host's profile, or `POST /api/v1/fleet/hosts/:id/configuration_profiles/:uuid/resend`) | Re-delivery of that one profile | Yes |
| Retry a software install or uninstall (**Retry** on a failed install, or **Retry uninstall** on a failed uninstall; from the host's software library an operator retry re-sends the host action `POST /api/v1/fleet/hosts/:id/software/:software_title_id/install` or `.../uninstall`, while in self-service the user's retry re-sends the device-authenticated action `POST /api/v1/fleet/device/{token}/software/install/:software_title_id` or `.../uninstall/:software_title_id`; Premium) | A fresh install or uninstall attempt through the full pipeline | Yes, but the work itself runs on the user's machine |
| `fleetctl trigger --name=<schedule>` | Server-side background work | Yes. Check `cron_stats`, per §8.11.3. |
| Restart fleetd on the host | Config re-fetch, and re-read of anything under `command_line_flags` | Yes, with a short gap in reporting. Watchdog denylist state resets too ([8.14](8.14-degradation.md) §8.14.5). |
| `sudo profiles renew -type enrollment` (macOS) | A fresh run of automated device enrollment (ADE, formerly DEP) against the enrollment profile currently assigned to the host | **No.** Use it on a host you are willing to disturb. It re-runs enrollment, so it can change MDM state. Confirm the before and after with `sudo profiles status -type enrollment` ([8.4](8.4-host-side-investigation.md)). |
| Unenroll and re-enroll a host | Everything, from scratch | **No.** Last resort. Destroys the evidence for whatever you were investigating. |

Choose the least disruptive action that exercises the suspected stage. Capture current state before re-enrollment, since rebuilding enrollment can remove evidence of the original failure.

## 8.11.7 Differential isolation

A comparison can help when the failure is difficult to reproduce on demand. Vary one condition and compare the results.

Record what stayed constant and what could not be controlled. Use the table to decide what each comparison makes more or less likely.

| Vary this | Same result on both makes unlikely | A different result implicates |
|---|---|---|
| **Host**, same fleet, same payload | Anything host-specific: local state, another agent, disk, the logged-in user | That host. Go host-side, [8.4](8.4-host-side-investigation.md). |
| **Platform**, same feature | A platform-specific delivery path. What stays in play is Fleet-side logic and the payload, since both platforms share those | The platform's MDM channel or agent path |
| **fleet**, same payload | Configuration scoped to the fleet: agent options, profiles, and software | Configuration or scoping |
| **Fleet instance** (a throwaway, §8.11.9) | Anything specific to your deployment: infrastructure, network path, data, scale | Your production deployment. What remains in play on a clean instance is Fleet's behavior at that version, the payload, the test host, or a shared dependency. |
| **Fleet version**, on a disposable copy of the same data (§8.11.9) | A regression introduced between the two versions tested. What stays in play is the shared environment, the payload and the host | A regression between those versions. Read the release notes (github.com/fleetdm/fleet/releases) |
| **Network position** (host on VPN versus off, or a different egress) | The network position, and the proxy, TLS inspection and egress filtering that come with it | Proxy, TLS inspection, or egress filtering on the path you varied |

A matching result weakens explanations specific to the condition you changed. For example, the same failure on a clean instance shows that production-specific data or configuration is not required to reproduce it. Fleet's behavior, the payload, the host, and shared dependencies still need investigation.

Platform comparisons can help with MDM because Apple, Windows, and Android use distinct delivery paths. A failure limited to one platform directs attention to that path, its payload, and the OS behavior. Keep those payload differences in mind when comparing results.

## 8.11.8 Preparing for the next occurrence

If the failure will not repeat on demand, prepare to capture its next occurrence. Choose collection intervals and retention that cover the expected investigation window.

| Prepare | Why |
|---|---|
| Raise server log verbosity now | Per-request log lines are DEBUG unless the error is a non-client error. At default verbosity some failures leave no trace at all, and you cannot go back and re-log a past request. |
| Capture `cron_stats` on a schedule | `cron_stats` has no read API and is trimmed by cleanup jobs. Snapshot name, instance, stats_type, status, errors, created_at, updated_at on a timer. [8.6](8.6-server-state.md) |
| Capture queue depth on the same timer | Periodic snapshots preserve a backlog that may drain before investigation begins. |
| Sample **raw record timestamps**, not aggregate metrics | Keep both event and arrival times for the comparison below. |
| Capture `fleetctl debug errors` before anything flushes | Errors live in Redis and age out per `logging_error_retention_period`. `--flush` deletes them. Capture, then flush if you must. |
| Note the exact onset time and every version that changed near it | Both sides: Fleet server, fleetd, osquery, the OS, and any other agent. |

<a id="the-two-clocks-question-needs-per-record-timestamps"></a>

### Keep both event and arrival timestamps

Save per-record timestamps alongside aggregate latency metrics. The check in [8.1](8.1-diagnostic-method.md) compares the event time inside each record with the destination's arrival time. A percentile alone cannot reconstruct that comparison.

Those two timestamps help distinguish delayed delivery from a destination re-reading old data. If monitoring currently retains only aggregate latency, add record-level collection before the next test.

<a id="long-reproduction-windows-lose-their-own-evidence"></a>

### Preserve errors throughout a long test

Errors in Redis expire according to `logging_error_retention_period`. During a reproduction that spans days, capture `fleetctl debug errors` periodically so early failures are still available at the end.

## 8.11.9 A disposable Fleet instance

Use a separate Fleet instance for tests that need disruptive changes, another server version, or configuration unsuitable for production.

Docker Compose, per Fleet's own guide (fleetdm.com/guides/deploy-fleet-on-docker-compose):

```sh
mkdir fleet-repro && cd fleet-repro
curl -O https://raw.githubusercontent.com/fleetdm/fleet/fleet-v4.90.0/docs/solutions/docker-compose/docker-compose.yml
curl -O https://raw.githubusercontent.com/fleetdm/fleet/fleet-v4.90.0/docs/solutions/docker-compose/env.example
cp env.example .env
openssl rand -base64 32   # use as FLEET_SERVER_PRIVATE_KEY
```

Fetch from the release tag rather than `main`, so the file you get is the one that shipped with the version you are testing.

Before starting it, pin the images and prepare the TLS files.

The published Compose file uses `image: fleetdm/fleet` without a tag. Replace it with the release under test, using the format from Fleet's Helm chart:

```yaml
    image: fleetdm/fleet:v4.90.0
```

[2.4](../02-administer-and-deploy-fleet/2.4-deploy-with-containers-or-virtual-machines.md) asks for the same pin in production, for a different reason.

The file also uses `mysql:8`, `redis:6`, and `alpine:latest` for the permission-init container. Pin these to exact versions or record their resolved images after the first start. That lets you recreate the same environment even when tags change.

`env.example` enables TLS and sets `FLEET_SERVER_CERT` and `FLEET_SERVER_KEY` to `/fleet/fleet.crt` and `/fleet/fleet.key`. The Compose file mounts them read-only from `./certs/fleet.crt` and `./certs/fleet.key`. Create the `certs` directory beside the Compose file and supply those files before startup.

The mounts apply even when TLS is disabled. If their source paths are missing, Docker creates directories named `certs/fleet.crt` and `certs/fleet.key`.

The stack can start with those directories while `FLEET_SERVER_TLS=false`. If TLS is later enabled, Fleet terminates with:

```
{"level":"info","msg":"listening","transport":"https","address":"0.0.0.0:1337"}
{"level":"info","msg":"terminated","err":"read /fleet/fleet.crt: is a directory"}
```

The container then appears as `Restarting` in `docker compose ps`; read its logs for the error. Create the files before the first start. If Docker already created directories at those paths, remove the empty directories before placing the certificate and key files there.

For an isolated local browser test, you can set `FLEET_SERVER_TLS=false`. Orbit also permits plain HTTP to `localhost` or `127.0.0.1`, or elsewhere when an agent is built to skip verification. Keep these exceptions confined to the disposable test environment.

Set `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`, and `FLEET_SERVER_PRIVATE_KEY` in `.env`, then run `docker compose up -d` from the Compose directory to start Fleet, MySQL, and Redis.

Once the containers exist, record the exact images and digests:

```sh
docker compose images   # lists the image and digest each running service resolved to
```

To obtain a digest you can use directly in the Compose file:

```sh
docker image inspect fleetdm/fleet:v4.90.0 --format '{{index .RepoDigests 0}}'
```

Save the output with the reproduction notes.

Confirm the Fleet version inside the running container:

```sh
docker compose exec fleet /usr/bin/fleet version
```

With the example pin, this prints `fleet version 4.90.0`. An unpinned image can run a later release; during the manual's 2026-08-27 test it resolved to 4.90.1. Record the actual version before using the result to assess a version-specific failure.

Check the startup schedule list when reproducing cron behavior. The unlicensed test instance started 21 schedules; Premium-only schedules were absent. If the schedule you need is missing, confirm the license and deployment configuration.

`FLEET_LICENSE_KEY` is blank in `env.example`, so the instance starts as Free. Supply a Premium key for reproductions involving software installers, label-scoped profiles, ADE/ABM, or VPP. Queries, scripts, and policies can be tested on Free.

The recipe needs ports 1337, 3306, and 6379 available. In the manual's laptop test with images already downloaded, `/healthz` responded about a minute after startup. Initial image downloads add time. The resulting stack supports server-side tests and agent-side work on hosts pointed to it, within the configured license tier.

MDM tests need additional setup. Apple MDM requires an APNs certificate, ADE an ABM token, VPP a VPP token, and Android an enterprise binding for the test instance.

For Windows MDM, the device must resolve the server hostname and trust its certificate. Fleet's source does not establish that the hostname must be publicly resolvable: it validates an HTTP or HTTPS server URL with a host and derives the enrollment endpoints from it. Plan connectivity from the test device's network and verify it before enrollment.

If the failure repeats on a clean instance, production-specific state is not required to cause it. Investigate Fleet at that version, the payload, the test host, and any shared dependencies. If it does not repeat, compare production data, scale, infrastructure, network access, and configuration. Either result helps choose the next test.

## 8.11.10 What is not documented

| Item | Status |
|---|---|
| A trigger that reports success without running | Verified behaviour. Undocumented, and `fleetctl` prints its normal success line for it. |
| Effective `distributed_interval` and `logger_tls_period` on an existing server | A new Fleet install ships both at 10 seconds in the global agent options, and Fleet's REST API reference states the 10 second `distributed_interval` default.
