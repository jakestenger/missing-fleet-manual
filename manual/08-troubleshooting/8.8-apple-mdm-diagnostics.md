# 8.8 Apple MDM diagnostics

Apple MDM puts more hops between Fleet's decision and the device's action than any other channel Fleet manages, and Fleet's own Apple MDM architecture pages are stubs. What follows is the delivery path, the table each hop writes to, and the failures that leave no error message behind. Where a behaviour is undocumented, it says so.

## 8.8.1 The delivery path

Every Apple MDM symptom is "which hop stopped". Enumerate the hops first.

| # | Hop | Transport | Where state lands | How to observe |
|---|---|---|---|---|
| 1 | Fleet decides a command is needed | in-process, or a cron | `host_mdm_apple_profiles` / `host_mdm_apple_declarations` status set to `pending`, or a row in `upcoming_activities` | SQL, or Host details → Activity → Upcoming |
| 2 | Command is enqueued | MySQL write | `nano_commands` (one row per command) + `nano_enrollment_queue` (one row per recipient, `active = 1`) | `nano_view_queue`, §8.8.3 |
| 3 | Fleet pushes to APNs | HTTP/2 mTLS, outbound to Apple on 443 or 2197 | nothing persisted per push; the push cert is in `nano_push_certs`, the device token in `nano_enrollments.token_hex` / `push_magic` | `apple_mdm_apns_pusher` cron in `cron_stats`; `fleetctl debug errors` |
| 4 | APNs wakes the device | Apple's network, device on TCP 5223 (443 fallback) | none on Fleet's side | device-side only, `mdmclient` log ([8.2](8.2-log-surfaces.md)) |
| 5 | Device checks in | `PUT /mdm/apple/mdm`, client cert auth | `nano_enrollments.last_seen_at` advances | SQL on `nano_enrollments` |
| 6 | Fleet hands over the next command | same connection | queue row stays `active = 1` until answered | `nano_view_queue` |
| 7 | Device acknowledges | `PUT /mdm/apple/mdm`, `Status: Acknowledged` / `Error` / `NotNow` | `nano_command_results` row; queue row deactivated | §8.8.3 |
| 8 | Fleet interprets the result | in-process | profile row moves `pending` → `verifying` → `verified`, or `failed` | `host_mdm_apple_profiles.status` |

**The push is not the delivery.** APNs, the Apple Push Notification service, carries no payload. The push is a wake-up signal, and commands wait in Fleet's queue until the device connects back. A broken APNs path therefore produces a growing queue and no error message anywhere, which makes it the most misleading failure mode in the Apple stack.

## 8.8.2 Inspecting commands

### `fleetctl`

```sh
fleetctl get mdm-commands --host <hostname|uuid|serial>
fleetctl get mdm-commands --host <ident> --type InstallProfile
fleetctl get mdm-commands --host <ident> --command_status pending,failed
fleetctl get mdm-command-results --id <command-uuid>
fleetctl mdm run-command --hosts <ident>[,<ident>] --payload ./apple-restart-device.xml
```

| Flag | Notes |
|---|---|
| `--host` | **Required** on `get mdm-commands` since 4.89.2. Fleet's MDM commands guide still shows an unfiltered `fleetctl get mdm-commands`; that form is stale |
| `--type` | Filters by request type, for example `InstallProfile`, `DeviceInformation`, `InstallApplication` |
| `--command_status` | Comma-separated. Valid values are `pending`, `ran`, `failed` |
| `--id` on `mdm-command-results` | The command UUID. `--host` is accepted as an extra filter |
| `--hosts` / `--payload` on `run-command` | Both required. All targets must be the same platform. Any host with MDM off aborts the whole call |

Output columns are `UUID`, `TIME`, `TYPE`, `STATUS`, `HOSTNAME`, printed under "The list of N most recent commands". A blank request type is displayed as `InstallProfile`. Fleet's guide describes the list as the 1,000 most recent commands. **Treat that as an upper bound rather than a promise**: the page size the command actually requests is not documented, and an external review of this chapter put it far lower. Before concluding a command is absent from the history, confirm the window by paging the API directly rather than trusting the tail of this list.

`mdm-command-results` pretty-prints both the payload plist and the raw device reply, so use it in preference to reading `nano_command_results.result` by hand.

### API

| Call | Endpoint |
|---|---|
| List commands | `GET /api/v1/fleet/commands` |
| Get command results | `GET /api/v1/fleet/commands/results?command_uuid=<uuid>` |
| Run a command | `POST /api/v1/fleet/commands/run` |

`GET /api/_version_/fleet/mdm/commandresults` and `POST /api/_version_/fleet/mdm/commands/run` are the deprecated aliases, and still work.

The request payload is base64 of the raw plist, and the `result` field comes back base64 too. Decode it before reading it.

```sh
curl -sS -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/api/v1/fleet/commands/results?command_uuid=$COMMAND_UUID" \
| jq -r '.results[].result' | base64 -d
```

To send one:

```sh
curl -sS -X POST -H "Authorization: Bearer $FLEET_API_TOKEN" \
  -H 'Content-Type: application/json' \
  --data "{\"command\":\"$(base64 < apple-restart-device.xml)\",\"host_uuids\":[\"<host-uuid>\"]}" \
  "$FLEET_URL/api/v1/fleet/commands/run"
```

Supplying your own `CommandUUID` key in the plist makes the result lookup trivial later.

### UI (volatile)

Host details → **Activity** card → **Past** or **Upcoming** tab → the **Show MDM commands** toggle swaps the activity feed for a raw command feed. The info button on a row opens the payload and result. The Upcoming tab covers macOS, Windows, Linux, iOS, and iPadOS.

**`RemoveProfile` sent this way targets the device channel only.** User-scoped profiles are out of reach for both `fleetctl mdm run-command` and the run endpoint.

## 8.8.3 Is this command queued, delivered, or answered

One query. Run it against the host UUID, not the host ID.

```sql
SELECT nc.command_uuid,
       nc.request_type,
       neq.active                        AS still_queued,
       neq.created_at                    AS queued_at,
       ncr.status                        AS device_status,
       ncr.not_now_tally,
       ncr.updated_at                    AS answered_at,
       ne.last_seen_at                   AS host_last_checkin
FROM   nano_enrollment_queue neq
JOIN   nano_commands   nc  ON nc.command_uuid = neq.command_uuid
JOIN   nano_enrollments ne ON ne.id = neq.id
LEFT  JOIN nano_command_results ncr
       ON ncr.command_uuid = neq.command_uuid AND ncr.id = neq.id
WHERE  neq.id = '<host-uuid>'
ORDER  BY neq.created_at DESC
LIMIT  50;
```

Read it like this:

| `still_queued` | `device_status` | State | Look at |
|---|---|---|---|
| `1` | `NULL` | Queued, never answered | Hop 3 or 4. APNs or the device is not coming back. Compare `host_last_checkin` to now |
| `1` | `NotNow` | Delivered, device deferred it (usually locked or at the login window) | Nothing. It retries. Watch `not_now_tally` climb |
| `0` | `Acknowledged` | Delivered and accepted | Hop 8. If the profile still reads wrong, the problem is verification, not delivery |
| `0` | `Error` | Device rejected it | Decode `nano_command_results.result`, the `ErrorChain` has Apple's reason |
| no row at all | | Never enqueued | Hop 1. The cron did not run, or Fleet did not think this host needed it |

`nano_view_queue` is a view over the same three tables, and the shorter way in when `last_seen_at` is not part of the question. The full column reference for all of these is in [8.6](8.6-server-state.md) §8.6.5.

Companion tables worth knowing, all detailed in [8.6](8.6-server-state.md): `nano_devices` (one row per device that ever completed `Authenticate`), `nano_enrollments` (one row per channel, device and user), `nano_push_certs` (APNs cert per topic), `nano_cert_auth_associations` (device identity cert binding), `host_mdm_commands` (`host_id` + `command_type`, a coarse per-host marker), `host_mdm` (enrollment status, `installed_from_dep`, `server_url`).

## 8.8.4 APNs

**Check certificate expiry first when every Apple device stops responding at once.** An expired APNs certificate stops every push and produces no device-side error, because the devices never learn there is anything to fetch. Certificates are valid for 12 months.

The certificate is in `nano_push_certs.cert_pem`. See [8.6](8.6-server-state.md) §8.6.5 for the one-liner that pipes it through `openssl x509 -noout -enddate`.

**Renewal must use the same Apple Account that created the certificate.** Losing access to that account means creating a new certificate, which breaks the trust relationship with every enrolled device and forces a full re-enrollment. Treat that account credential as the highest-blast-radius secret in the Apple stack.

### Network

| Direction | Ports | Destination |
|---|---|---|
| Managed device → APNs | TCP 5223 primary, TCP 443 fallback | Apple |
| Fleet server → APNs | TCP 443 or TCP 2197 | Apple |

Apple's guidance is to permit the whole `17.0.0.0/8` block, which Apple owns outright (Apple support articles 103229 and 101555).

**TLS inspection breaks APNs.** Apple detects interception on the APNs connection and treats it as compromised, so the device refuses it. If you run outbound TLS inspection, add an explicit bypass for APNs. On iOS 13.4+, iPadOS 13.4+, macOS 10.15.4+, and tvOS 13.4+, APNs can traverse a PAC-specified web proxy that passes the traffic through without decrypting it.

TLS inspection intercepting Fleet's own traffic is a separate and equally common root cause; see the certificate-chain notes in [8.4](8.4-host-side-investigation.md).

### The pusher cron

`apple_mdm_apns_pusher`, 1 minute period (see the cron table in [8.6](8.6-server-state.md) §8.6.2). It sends pushes for hosts with pending commands in the nano queue. Commands piling up while the cron stops advancing in `cron_stats` is a Fleet-side scheduling problem, not an Apple one.

```sh
fleetctl trigger --name=apple_mdm_apns_pusher
```

### One device failing while the rest work

This pattern points at that device's push token, not at the certificate. Erasing a device breaks the trust relationship between it and APNs, and Fleet's stored `token_hex` and `push_magic` then match nothing. Re-enrolling that one device is the fix. Check `nano_enrollments.last_seen_at` and `token_update_tally` for the device before anything more elaborate.

Also confirm `nano_enrollments.topic` matches `nano_push_certs.topic`. A mismatch after an APNs certificate swap stops pushes for the affected enrollments without logging anything; the query is in [8.6](8.6-server-state.md) §8.6.5.

## 8.8.5 ADE/DEP sync and the cursor

Fleet syncs ABM-assigned devices through its DEP client, driven by a cursor stored per ABM token in `nano_dep_names`. Apple's current name for this is [ADE](); the API, the crons, and the tables all still say [DEP]().

| Cursor state | Apple API Fleet calls | Result |
|---|---|---|
| `syncer_cursor` NULL | `fetch-devices` | Full device list |
| `syncer_cursor` set | `sync-devices` | Deltas only |

| Fact | Value |
|---|---|
| Page size | 200 devices per request |
| Cadence | `mdm.apple_dep_sync_periodicity`, default 1 minute |
| Cursor lifetime at Apple | 7 days |
| Cron | `apple_mdm_dep_profile_assigner` |

Fleet loops pages until Apple reports no more. When Apple expires a cursor, Fleet recovers on its own by falling back to a full fetch.

### Resetting the cursor

```sql
UPDATE nano_dep_names
SET    syncer_cursor = NULL,
       syncer_cursor_at = NULL;
```

**Safe at any scale**, and documented by Fleet as such. It re-baselines Fleet's assignment list and stops there: no device is re-enrolled, ABM assignments are untouched, and no DEP profile is re-pushed. Force the next sync with:

```sh
fleetctl trigger --name=apple_mdm_dep_profile_assigner
```

### When Apple stops returning the device

Apple throttles. Fleet's own troubleshooting documentation records cases where devices hit the threshold for a cooldown state and Apple stops returning them on cursor requests at all. Resetting the cursor has no effect on that, and the device stays invisible to Fleet until Apple releases it. Fleet's `integrations` cron drains `dep_cooldowns` ([8.6](8.6-server-state.md) §8.6.2).

Ingested ADE devices are recorded in `host_dep_assignments`, and a delete there is a soft delete. Deleting a host in the UI while a live `host_dep_assignments` row exists causes Fleet to recreate the host immediately, as if freshly ingested. That is the usual explanation for "the host I deleted keeps coming back".

Fleet's own documentation calls the sync job `dep_syncer` in places. The registered cron name is `apple_mdm_dep_profile_assigner`, and that is the one to use with `fleetctl trigger` and to look for in `cron_stats`.

## 8.8.6 Assignment time but no push time

Host details → MDM status shows an assignment timestamp and a push timestamp for ADE hosts. **Assignment time present, push time absent means the push to the device never happened.** The device is assigned to Fleet in ABM but was never told to renew its enrollment, so it will sit at the old MDM or at no MDM indefinitely.

Remediate from the device:

```sh
sudo profiles renew -type enrollment
```

A restart of the host does the same thing on the next Setup Assistant pass.

The Apple Business issue vital on the dashboard filters the affected hosts. Size the problem there first, then work the list.

> [!internal] At migration scale this shows up as a stubborn tail of a few percent that never move, long after the bulk of the fleet has flipped.

## 8.8.7 Profile status values

Four values, plus NULL. Windows profiles share this vocabulary ([8.9](8.9-windows-mdm-diagnostics.md)).

| Status | Meaning | Real failure? |
|---|---|---|
| NULL | Needs to be applied, the reconcile cron has not picked it up yet. Counted as Pending by the summary endpoints and the host filter | No |
| `pending` | The cron is processing this host; the MDM command may already be enqueued | No, transitional |
| `verifying` | The command was applied successfully, but Fleet has not independently confirmed the resulting state on the device | No, transitional. Can still move to `failed`, `pending`, or NULL |
| `verified` | Applied and independently verified by Fleet. Terminal | No |
| `failed` | Terminal. Will not retry further | **Yes** |

Retry behaviour splits by where the failure happened. A failure the device reports in its MDM response is retried a fixed number of times, and the status becomes `failed` permanently once those are used up. A failure to *enqueue* the command in the first place resets the status to NULL instead, so the next cron run picks the host up again.

**`verifying` that never becomes `verified` is the interesting case.** Delivery worked, verification did not. That points at the detail-query path (osquery reporting installed profiles) rather than at MDM.

The reconcile cron is `mdm_apple_profile_manager`, 30 second period ([8.6](8.6-server-state.md) §8.6.2). It writes `host_mdm_apple_profiles` and enqueues `InstallProfile` / `RemoveProfile` into `nano_enrollment_queue`.

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

Desired vs actual for one host, with the full column list in [8.6](8.6-server-state.md) §8.6.7:

```sql
SELECT profile_name, status, operation_type, retries, detail
FROM   host_mdm_apple_profiles
WHERE  host_uuid = '<host-uuid>'
ORDER  BY status, profile_name;
```

## 8.8.8 DDM declarations

Declarative device management (DDM) is Apple's newer delivery model, and a declaration is its unit of policy: a JSON object the device fetches, applies, and then reports back on. Declarations live in `mdm_apple_declarations`, separately from `mdm_apple_configuration_profiles`, and their per-host state is in `host_mdm_apple_declarations`. The profile UUID prefix tells you which table to look in: `d` for a declaration, `a` for an Apple `.mobileconfig`, `w` for Windows.

### How delivery differs

Fleet's declaration reconcile enqueues one command per host, not one per declaration. It marks the changed declarations `pending` and sends a single `DeclarativeManagement` MDM command. From there the device drives the exchange: it requests `tokens`, then `declaration-items`, then the individual `declaration/activation/...` and `declaration/configuration/...` payloads, then posts a `status` report. Fleet stores every DDM message it receives in `mdm_apple_declarative_requests`.

Status transitions have two sources:

- The `DeclarativeManagement` command result moves the host's declarations from `pending` to `verifying` or `failed` in one batch.
- The DDM `status` endpoint marks each declaration `verified` if active and valid, `failed` if invalid.

Removal is inferred. The device reports the declarations it holds, and Fleet reads a declaration's absence from that report as removal.

So the entry point for a stuck declaration is `mdm_apple_declarative_requests` plus `host_mdm_apple_declarations`, rather than the command queue. `nano_view_queue` shows the single `DeclarativeManagement` command and nothing more, however many declarations moved.

### `Error.UnknownDeclarationType`

The OS is too old for that declaration type. Fleet treats this status reason code the same way it treats an invalid declaration. Real example: VPN declarations need macOS 27+, and earlier versions reject them with exactly this code. Check the host's OS version before rewriting the declaration.

### DDM limits

A declaration Fleet will deliver has to be a configuration type: it cannot carry OS update settings (use Controls → OS updates for those), cannot be a type that requires assets, and cannot be a status subscription type. **Neither resend endpoint accepts a declaration.** The batch path and the single-host path both reject one with the same message: declarations cannot be resent because a host checks in to collect the current set by itself. Attempting either during an incident returns a 400 and advances nothing.

That is a design consequence rather than a gap. Configuration profiles are pushed and therefore need a way to be pushed again; declarations are pulled, so the equivalent action is making the host check in.

## 8.8.9 The half-enrolled state

ADE enrollment succeeds, `InstallEnterpriseApplication` fails, and the device ends up MDM-enrolled with no `fleetd` agent. It answers MDM commands and never appears as an osquery host.

Reported rate is roughly 2 to 3 percent, 20 to 30 hosts per 1,000, **as reported in `fleetdm/fleet#47793`**, not as a published Fleet figure. The issue is open as of 4.90.x. The planned fix is a DDM-based agent install.

Detection and recovery are in [8.4](8.4-host-side-investigation.md), and that is where the diagnosis has to happen: a half-enrolled host looks healthy in every Apple MDM table on the server.

## 8.8.10 VPP install verification is a second phase

A [VPP]() install is two phases, and the second one can fail on its own.

1. Fleet sends `InstallApplication`.
2. On acknowledgement, Fleet loops `InstalledApplicationList` commands until either the app appears as installed, or the verification timeout expires.

| Setting | Default | Env var |
|---|---|---|
| `server.vpp_verify_timeout` | 10 minutes | `FLEET_SERVER_VPP_VERIFY_TIMEOUT` |
| `server.vpp_verify_request_delay` | 5 seconds | `FLEET_SERVER_VPP_VERIFY_REQUEST_DELAY` |

**A reported VPP failure is often a verification timeout with the app actually installed.** Slow networks, large apps, and devices that go to sleep mid-install all produce it. Check the device before treating it as an install failure. The signature in the host's command feed is an acknowledged `InstallApplication` followed by a run of `InstalledApplicationList` commands that never reaches a terminal success.

In-house `.ipa` installs use the same verification path. The difference is that their `InstallApplication` command carries a `ManifestURL` instead of an `iTunesStoreID`.

## 8.8.11 Error strings worth recognising

Every string below is emitted by the Fleet server verbatim, so grep for it. The DEP client formats Apple's rejections as `DEP auth error: <status>: <body>` and `DEP HTTP error: <status>: <body>`, which puts Apple's own code at the end of the message.

| Apple code | Typical rendering | Meaning | Fix |
|---|---|---|---|
| `T_C_NOT_SIGNED` | `DEP auth error: 403 Forbidden: "T_C_NOT_SIGNED"` | Apple's terms and conditions have not been accepted in ABM | Sign in to Apple Business as an administrator and accept the terms. Nothing in Fleet changes |
| `signature_invalid` | `DEP auth error: 403 Forbidden: "signature_invalid"` | The ABM server token was revoked or replaced in ABM without the new token being uploaded to Fleet | Download a fresh server token from ABM and upload it |
| `token_rejected` | same shape, 401 or 403 | Same root cause as `signature_invalid` per Apple's own error-code doc | Re-upload the ABM token |

All three can arrive as 403, so match on the body of the message rather than on the HTTP status.

`Error.UnknownDeclarationType` is covered in §8.8.8.

## 8.8.13 Narrowing the search

The bisection question is **did the device come back at all**.

```sql
SELECT id, last_seen_at, TIMESTAMPDIFF(MINUTE, last_seen_at, NOW()) AS mins_ago
FROM   nano_enrollments
WHERE  id = '<host-uuid>' AND enabled = 1;
```

- **`last_seen_at` is recent, command still queued:** the push worked and the device connected, so hops 1 to 5 are healthy. The failure is at 6 or later: the command was handed over and either errored or is being deferred with `NotNow`. Decode the result.
- **`last_seen_at` is stale:** the device is not checking in, so the failure is at hop 4 or earlier. Now ask the second question, **is it one device or all of them.**
  - **All Apple devices stale:** APNs certificate expiry, topic mismatch after a
    cert swap, or a network path change (TLS inspection, firewall). §8.8.4.
  - **One device stale:** invalid device token, or the device is genuinely
    offline. Re-enroll. §8.8.4.
- **No queue row at all:** nothing was ever enqueued. Look at the crons in `cron_stats` ([8.6](8.6-server-state.md) §8.6.2) and at whether Fleet thinks the host needs the profile at all.

For ADE-specific symptoms the equivalent first cut is **does Fleet know about the serial**: check `host_dep_assignments` and `nano_dep_names.syncer_cursor_at` before touching anything else. A cursor older than 168 hours is past Apple's expiry.

Before escalating, collect what Fleet's MDM bug checklist asks for: exact OS version including minor, hardware model, fleetd version, enrollment method, prior MDM and whether it was told to stop managing, proxy/TLS-inspection posture, whether Apple's services are allowlisted, and whether the issue survives a reboot. Serial numbers go in a private channel, never in a public issue. See [8.13](8.13-escalation.md).
