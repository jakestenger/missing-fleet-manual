# 8.8 Apple MDM diagnostics

Apple MDM delivery involves Fleet, Apple's services, and the device. When a profile or command does not arrive, checking the state at each step can show where progress stopped, even when there is no explicit error. This chapter maps those steps to the tables and logs you can inspect. For the architecture behind them, see [2.9](../02-administer-and-deploy-fleet/2.9-mdm-architecture-and-foundations.md).

## 8.8.0 Start here

Start with the symptom below, then follow the relevant part of the [delivery path](#881-the-delivery-path). Later sections cover profile verification, declarations, ADE sync, and VPP installs, each of which has additional checks.

| Symptom | Start at | First thing to check |
|---|---|---|
| A profile or command is not arriving on one Mac | [8.8.13](#8813-narrowing-the-search) | Has the device checked in at all? `nano_enrollments.last_seen_at` |
| **Every** Apple device went quiet at once | [8.8.4](#884-apns) | APNs certificate expiry, then topic mismatch after a cert swap |
| A profile says `verifying` and never becomes `verified` | [8.8.7](#887-profile-status-values) | Check the osquery detail-reporting path that verifies delivery |
| A declaration is stuck | [8.8.8](#888-ddm-declarations) | The `DeclarativeManagement` command first, then `mdm_apple_declarative_requests` and the applied version |
| ADE devices are not appearing, or the wrong ones are | [8.8.5](#885-adedep-sync-and-the-cursor) | ABM token expiry, then the sync cursor |
| A device is assigned in ABM but still on the old MDM | [8.8.6](#886-assignment-time-but-no-push-time) | Assignment time present with no push time |
| MDM reads healthy and the host never reports | [8.8.9](#889-the-half-enrolled-state) | Check whether fleetd was installed after MDM enrollment |
| A VPP install reports failure | [8.8.10](#8810-vpp-install-verification) | Read `software_installed` in the API command result |

APNs sends a wake-up signal. The command itself stays in Fleet's queue until the device connects back to retrieve it. If pushes stop reaching devices, the queue can grow without a device error, so check queue age and check-in time as well as reported failures.

## 8.8.1 The delivery path

Each step leaves different evidence:

| # | Hop | Transport | Where state lands | How to observe |
|---|---|---|---|---|
| 1 | Fleet decides a command is needed | in-process, or a cron | `host_mdm_apple_profiles` / `host_mdm_apple_declarations` status set to `pending`, or a row in `upcoming_activities` | SQL, or Host details → Activity → Upcoming |
| 2 | Command is enqueued | MySQL write | `nano_commands` (one row per command) + `nano_enrollment_queue` (one row per recipient, `active = 1`) | `nano_view_queue`, §8.8.3 |
| 3 | Fleet pushes to APNs | HTTP/2 mTLS, outbound to Apple on 443 or 2197 | nothing persisted per push; the push cert is in `nano_push_certs`, the device token in `nano_enrollments.token_hex` / `push_magic` | `apple_mdm_apns_pusher` cron in `cron_stats`; `fleetctl debug errors` |
| 4 | APNs wakes the device | Apple's network, device on TCP 5223 (443 fallback) | none on Fleet's side | device-side only, `mdmclient` log ([8.2](8.2-log-surfaces.md)) |
| 5 | Device checks in | `PUT /mdm/apple/mdm`, client cert auth | `nano_enrollments.last_seen_at` advances | SQL on `nano_enrollments` |
| 6 | Fleet hands over the next command | same connection | the queue row is unchanged. `active = 1` is what makes it eligible, and answering does not clear it | `nano_view_queue` |
| 7 | Device responds | `PUT /mdm/apple/mdm`, `Status: Acknowledged` / `Error` / `NotNow` | `nano_command_results` row. The queue row is **not** deactivated. **Any status except `NotNow` is terminal** and stops it being selected; a `NotNow` does not, and the command stays eligible | §8.8.3 |
| 8 | Fleet interprets the result | in-process | profile row moves `pending` → `verifying` → `verified`, or `failed` | `host_mdm_apple_profiles.status` |

Fleet does not persist a record for each APNs push or device wake-up. For those steps, combine the pusher cron and server-error logs with the device's check-in time and `mdmclient` log. The absence of a recorded error alone does not establish that the push reached the device.

## 8.8.2 Inspecting commands

### `fleetctl`

```sh
fleetctl get mdm-commands --host "<hostname|uuid|serial>"
fleetctl get mdm-commands --host "<ident>" --type InstallProfile
fleetctl get mdm-commands --host "<ident>" --command_status pending,failed
fleetctl get mdm-command-results --id "<command-uuid>"
fleetctl mdm run-command --hosts "<ident>[,<ident>]" --payload ./apple-restart-device.xml
```

| Flag | Notes |
|---|---|
| `--host` | **Required** on `get mdm-commands` since 4.89.2. Fleet's MDM commands guide still shows an unfiltered `fleetctl get mdm-commands`; that form is stale |
| `--type` | Filters by request type, for example `InstallProfile`, `DeviceInformation`, `InstallApplication` |
| `--command_status` | Comma-separated. Valid values are `pending`, `ran`, `failed` |
| `--id` on `mdm-command-results` | The command UUID. `--host` is accepted as an extra filter |
| `--hosts` / `--payload` on `run-command` | Both required. All targets must be the same platform. Any host with MDM off aborts the whole call |

The CLI prints `UUID`, `TIME`, `TYPE`, `STATUS`, and `HOSTNAME` under "The list of N most recent commands". An empty result prints `No MDM commands have been run on this host.`; a blank request type displays as `InstallProfile`.

`TIME` is the row's last update. To measure how long a command has been queued, use `nano_enrollment_queue.created_at`. A command queued yesterday and answered today will show today's time in the CLI.

`fleetctl` fetches a fixed page of 20 commands and does not request further pages. The header counts that page, not the full history, despite the guide describing 1,000 commands. If the command you need is older, page through the API results.

Use `mdm-command-results` to read the payload plist and raw device reply in a formatted view. This saves decoding `nano_command_results.result` by hand.

### API

| Call | Endpoint |
|---|---|
| List commands | `GET /api/v1/fleet/commands` |
| Get command results | `GET /api/v1/fleet/commands/results?command_uuid=<uuid>` |
| Run a command | `POST /api/v1/fleet/commands/run` |

`GET /api/_version_/fleet/mdm/commandresults` and `POST /api/_version_/fleet/mdm/commands/run` are the deprecated aliases, and still work.

Both the request plist and response `result` are base64 encoded. The examples below decode the result and assume `FLEET_URL` and `FLEET_API_TOKEN` are set:

```sh
export FLEET_URL=https://fleet.example.com          # add your URL prefix here if you serve one
export FLEET_API_TOKEN=$(fleetctl config get token | awk '{print $NF}')
```

```sh
curl -sS -H "Authorization: Bearer $FLEET_API_TOKEN" \
  "$FLEET_URL/api/v1/fleet/commands/results?command_uuid=<command-uuid>" \
| jq -r '.results[].result' | base64 -d
```

To send a command:

```sh
jq -n --arg cmd "$(base64 < apple-restart-device.xml | tr -d '\r\n')" \
      --arg uuid "<host-uuid>" \
      '{command: $cmd, host_uuids: [$uuid]}' \
| curl -sS -X POST -H "Authorization: Bearer $FLEET_API_TOKEN" \
    -H 'Content-Type: application/json' \
    --data-binary @- \
    "$FLEET_URL/api/v1/fleet/commands/run"
```

Use `jq` to construct the JSON and `tr` to remove line breaks from the base64 output. Tools such as GNU `base64` wrap long output by default; literal newlines inside a manually constructed JSON string cause Fleet to reject the body before decoding the command.

Include a `CommandUUID` in the plist if you want a known identifier for the later result lookup.

### UI (volatile)

Host details → **Activity** card → **Past** or **Upcoming** tab → the **Show MDM commands** toggle swaps the activity feed for a raw command feed. The info button on a row opens the payload and result. The Upcoming tab covers macOS, Windows, Linux, iOS, and iPadOS.

These interfaces send `RemoveProfile` on the device channel only. Neither `fleetctl mdm run-command` nor the run endpoint can remove user-scoped profiles.

## 8.8.3 Is this command queued, delivered, or answered

Run this query with the host UUID. It does not accept the numeric host ID.

```sql
SELECT nc.command_uuid,
       nc.request_type,
       neq.active                        AS queue_active,
       neq.created_at                    AS queued_at,
       ncr.status                        AS device_status,
       ncr.not_now_tally,
       ncr.updated_at                    AS answered_at,
       ne.last_seen_at                   AS host_last_checkin
FROM   nano_enrollment_queue neq
JOIN   nano_commands   nc  ON nc.command_uuid = neq.command_uuid
JOIN   nano_enrollments ne ON ne.id = neq.id
LEFT  JOIN nano_command_results ncr
       ON ncr.command_uuid = neq.command_uuid AND ncr.id = neq.id
WHERE  neq.id = '<host-uuid>'
ORDER  BY neq.created_at DESC
LIMIT  50;
```

Interpret the result by checking device status, then queue eligibility:

Start with `device_status`. Fleet selects a command when its queue row is active and it has no terminal result. Every status except `NotNow` is terminal, so `Acknowledged`, `Error`, and `CommandFormatError` stop further selection even though `active` normally remains `1`.

`active = 0` means the row was deactivated, for example by clearing the queue. It does not record whether the device answered.

`NotNow` means the device received the command and deferred it. Fleet keeps the command eligible for a later session, records the first deferral in `not_now_at`, and increments `not_now_tally`. A rising tally confirms repeated delivery and deferral.

During the exchange in which the device sends `NotNow`, Fleet excludes deferred commands from that response so it does not immediately return the same command. On a later `Idle` check-in, the command is eligible again. This behavior never changes `active`.

| `device_status` | `queue_active` | State | Look at |
|---|---|---|---|
| `NULL` | `1` | Eligible and unanswered | Hop 3 or 4, but this is not proof that the push failed. Compare `host_last_checkin` to now |
| `NotNow` | `1` | Delivered, device deferred it, which happens when it is locked or at the login window | Watch `not_now_tally` and check why the device is deferring the command; it remains eligible for a later session |
| `NotNow` | `0` | Deferred, and then the row was deactivated by something else | Investigate queue clearing or another deactivation. `NotNow` does not change `active`; this row will no longer be selected |
| `Acknowledged` | either | Completed and accepted. **Terminal**, so it will not be offered again | Hop 8. If the profile still reads wrong, check the verification path |
| `Error` | either | Device rejected it. **Terminal**, so it will not be retried by the queue | Decode `nano_command_results.result`, the `ErrorChain` has Apple's reason |
| `NULL` | `0` | No longer deliverable. The queue was cleared or the row was deactivated | Check why the row was deactivated; it will no longer be selected |
| no row at all | | Never enqueued | Hop 1. The cron did not run, or Fleet did not think this host needed it |

A recent `host_last_checkin` confirms the enrollment connected, but the device may have received an earlier or higher-priority command. Look for a result for the command you are investigating; a `NULL` result contains no device reply to decode.

Use `nano_view_queue` for a shorter query when you do not need `last_seen_at`. It joins the same three tables. [8.6](8.6-server-state.md) §8.6.5 lists their columns.

For related state, [8.6](8.6-server-state.md) also covers `nano_devices` (devices that completed `Authenticate`), `nano_enrollments` (device and user channels), `nano_push_certs` (APNs certificates by topic), and `nano_cert_auth_associations` (device identity certificate bindings). `host_mdm_commands` holds coarse per-host command markers; `host_mdm` records enrollment status, `installed_from_dep`, and `server_url`.

## 8.8.4 APNs

When all Apple devices stop responding, start with APNs certificate expiry. An expired certificate prevents pushes, so devices receive no notification and produce no error for the waiting commands. Certificates are valid for 12 months.

The certificate is in `nano_push_certs.cert_pem`. See [8.6](8.6-server-state.md) §8.6.5 for the one-liner that pipes it through `openssl x509 -noout -enddate`.

Renew the existing certificate using the Apple Account that created it, and keep access to that account available to the administrators responsible for renewal. Replacing the certificate instead of renewing it changes the trust relationship and requires enrolled devices to enroll again.

### Network

| Direction | Ports | Destination |
|---|---|---|
| Managed device → APNs | TCP 5223 primary, TCP 443 fallback | Apple |
| Fleet server → APNs | TCP 443 or TCP 2197 | Apple |

Apple's guidance is to permit the whole `17.0.0.0/8` block, which Apple owns outright (Apple support articles 103229 and 101555).

Exclude APNs from outbound TLS inspection. Apple treats an intercepted connection as compromised, and the device refuses it. A proxy can pass the traffic through without decrypting it: PAC-specified web proxies are supported from iOS 13.4, iPadOS 13.4, macOS 10.15.4, and tvOS 13.4.

TLS inspection intercepting Fleet's own traffic is a separate root cause with the same presentation; see the certificate-chain notes in [8.4](8.4-host-side-investigation.md).

### The pusher cron

`apple_mdm_apns_pusher` runs every minute and sends pushes for hosts with pending nano queue commands. If the queue is growing and this cron's entries in `cron_stats` stop advancing, investigate Fleet scheduling. See [8.6](8.6-server-state.md) §8.6.2.

```sh
fleetctl trigger --name=apple_mdm_apns_pusher
```

### One device failing while the rest work

If other devices still receive pushes, check the affected device's `last_seen_at` and `token_update_tally` in `nano_enrollments`. An erased device can leave Fleet with obsolete `token_hex` and `push_magic` values; re-enrollment establishes a new relationship. First confirm the device is available and that this is the condition you are seeing.

Also compare `nano_enrollments.topic` with `nano_push_certs.topic`. A certificate swap can leave a mismatch that prevents pushes for those enrollments without a logged error. [8.6](8.6-server-state.md) §8.6.5 provides the query.

## 8.8.5 ADE/DEP sync and the cursor

Fleet syncs ABM-assigned devices through its DEP client, driven by a cursor stored per ABM token in `nano_dep_names`. Apple's current name for this is [ADE](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep); the API, the crons, and the tables all still say [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep).

| Cursor state | Apple API Fleet calls | Result |
|---|---|---|
| `syncer_cursor` NULL | `fetch-devices` | Full device list |
| `syncer_cursor` set | `sync-devices` | Deltas only |

| Fact | Value |
|---|---|
| Page size | 200 devices per request |
| Cadence | `mdm.apple_dep_sync_periodicity`, default 1 minute |
| Cursor lifetime at Apple | 7 days |
| Cron | `apple_mdm_dep_profile_assigner` |

Fleet loops pages until Apple reports no more. When Apple expires a cursor, Fleet recovers on its own by falling back to a full fetch.

### Resetting the cursor

Resetting the cursor makes Fleet fetch a full assignment list. Fleet documents this as safe at any scale: it leaves ABM assignments, device enrollment, and pushed DEP profiles unchanged. Scope the reset to the affected token using `nano_dep_names.name`, the token name and primary key:

```sql
UPDATE nano_dep_names
SET    syncer_cursor = NULL,
       syncer_cursor_at = NULL
WHERE  name = '<token-name>';
```

To reset all ABM tokens, remove the `WHERE` clause:

```sql
UPDATE nano_dep_names
SET    syncer_cursor = NULL,
       syncer_cursor_at = NULL;
```

Force the next sync with:

```sh
fleetctl trigger --name=apple_mdm_dep_profile_assigner
```

### When Apple stops returning the device

Fleet's troubleshooting documentation describes Apple placing devices in a cooldown state after throttling. Apple then omits them from cursor responses until it releases them; resetting the cursor does not resolve that condition. Fleet's `integrations` cron drains `dep_cooldowns` ([8.6](8.6-server-state.md) §8.6.2).

Check `host_dep_assignments` when a deleted ADE host reappears. Fleet records ingested assignments there using soft deletion. If a live assignment remains when you delete the host in the UI, Fleet recreates it as a newly ingested host.

Use `apple_mdm_dep_profile_assigner` with `fleetctl trigger` and in `cron_stats`. Some documentation calls the job `dep_syncer`, but that is not its registered name.

### Apple lookup errors in Fleet 4.91

Fleet 4.91 adds token and host-lookup fields that help distinguish an invalid token, a device-assignment problem, and a failed request to Apple.

The ABM token's `token_invalid` flag records whether Apple rejected the token or its signature. Fleet clears the flag when Apple successfully authenticates it, including when the request then fails because updated terms have not been accepted. Apple checks the terms after token authentication.

Timeouts and server errors leave the flag unchanged. Read `false` as "not known to be rejected"; it does not establish that a recent health check succeeded. Check `terms_expired` alongside it.

`GET /hosts/:id/dep_assignment` returns a readable `dep_device_error` explaining a failed lookup. It is null on success and distinguishes these five causes:

| Cause | What it means |
|---|---|
| Token rejected or its signature invalid | Fleet cannot connect to Apple Business at all. Renew the token |
| Terms not signed | The Apple Business terms changed and an administrator has to accept them |
| Serial not in Apple's response | This host is not, or is no longer, assigned to this token. It may have been removed or pointed at a different MDM server |
| Apple returned a server error | Apple's side. Try again later |
| Anything else | A network failure or a timeout reaching Apple. Also try again later |

If Apple omits a serial, inspect that device's assignment. It may have been reassigned or [released from Apple Business](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md#releasing-a-device-from-apple-business).

Token rejection and unsigned terms affect hosts assigned through that token. Server errors and timeouts can affect a subset of requests or be transient, so use the error's scope to guide the next check.

## 8.8.6 Assignment time but no push time

Host details → MDM status shows assignment and **profile pushed** timestamps for ADE hosts. The latter records the last time Apple reported that the device retrieved its assigned profile.

If assignment time is present but profile pushed time is absent, investigate retrieval from Apple. The device can remain with its old MDM, or with none, until it collects the assigned profile.

Remediate from the device:

```sh
sudo profiles renew -type enrollment
```

A restart of the host does the same thing on the next Setup Assistant pass.

Use the dashboard's Apple Business issue vital to find affected hosts and track the remaining work.

During a migration, track devices still awaiting profile retrieval separately from those already enrolled. Their count gives you a follow-up list specific to your deployment.

## 8.8.7 Profile status values

Four values, plus NULL. Windows profiles share this vocabulary ([8.9](8.9-windows-mdm-diagnostics.md)).

| Status | Meaning | Real failure? |
|---|---|---|
| NULL | Needs to be applied, the reconcile cron has not picked it up yet. Counted as Pending by the summary endpoints and the host filter | No |
| `pending` | The cron is processing this host; the MDM command may already be enqueued | No, transitional |
| `verifying` | The command was applied successfully, but Fleet has not independently confirmed the resulting state on the device | No, transitional. Can still move to `failed`, `pending`, or NULL |
| `verified` | Applied, and confirmed present by Fleet's own verification pass. **Not terminal**: a later osquery detail report that finds the profile missing or changed moves it back into retry or to `failed` | No |
| `failed` | The automatic retry budget is spent: three retries after the initial attempt. No further automatic attempt happens. A resend permits one more delivery, and does **not** replenish the budget | **Yes** |

Fleet retries an MDM failure reported by the device up to three times after the initial attempt, then marks the profile `failed`. An enqueue failure follows a different path: Fleet resets status to NULL so the next cron run can pick it up.

A resend resets status to NULL but retains the retry counter. For a profile that has exhausted its retries, this permits one additional delivery attempt.

If a profile remains `verifying`, delivery succeeded but independent confirmation has not. Check the osquery detail-query path that reports installed profiles before investigating command delivery again.

The reconcile cron is `mdm_apple_profile_manager`, 30 second period ([8.6](8.6-server-state.md) §8.6.2). It writes `host_mdm_apple_profiles` and enqueues `InstallProfile` / `RemoveProfile` into `nano_enrollment_queue`.

> ### ⚠️ Apple MDM pagination issue in Fleet 4.90.0
>
> In 4.90.0, deployments with more than 5,000 Apple MDM hosts and at least one duplicate host UUID could repeatedly skip the same hosts during reconciliation. The reconciler paged by UUID, then counted the rows after deduplication to decide whether more pages remained. A duplicate could make a full page appear short and cause the cursor to wrap early.
>
> Hosts after that point received no queued command, their profile status stayed NULL, and no failure was logged. Declarations used the same pagination and were also affected.
>
> Fleet 4.90.1 fixes the count by checking whether the page was full before deduplication. If this pattern matches a deployment on 4.90.0, check the server version first. Chapter 1.3 explains how duplicate hardware identifiers arise.

```sh
fleetctl trigger --name=mdm_apple_profile_manager
```

To compare desired and actual state for one host, use the following query. [8.6](8.6-server-state.md) §8.6.7 lists all columns.

```sql
SELECT profile_name, status, operation_type, retries, detail
FROM   host_mdm_apple_profiles
WHERE  host_uuid = '<host-uuid>'
ORDER  BY status, profile_name;
```

## 8.8.8 DDM declarations

A declarative device management (DDM) declaration is a JSON policy object that an Apple device fetches, applies, and reports on. Fleet stores declarations in `mdm_apple_declarations` and per-host state in `host_mdm_apple_declarations`, separately from configuration profiles.

The profile UUID prefix identifies the type: `d` for a declaration, `a` for an Apple `.mobileconfig`, `w` for Windows, and `g` for Android.

### How delivery differs

Fleet marks changed declarations `pending` and queues a `DeclarativeManagement` command for each affected enrollment channel. Device-scoped changes use the device channel; user-scoped changes use the corresponding user enrollment. A host with changes on both can have two commands, each acknowledging only its own channel's declarations.

The device then requests `tokens`, `declaration-items`, and the individual `declaration/activation/...` and `declaration/configuration/...` payloads before posting a `status` report. Fleet records received DDM messages in `mdm_apple_declarative_requests`.

Status transitions have two sources:

- The `DeclarativeManagement` command result moves the host's declarations from `pending` to `verifying` or `failed` in one batch.
- The DDM `status` endpoint marks each declaration `verified` if active and valid, `failed` if invalid.

Removal is inferred. The device reports the declarations it holds, and Fleet reads a declaration's absence from that report as removal.

Start with the `DeclarativeManagement` command for the declaration's channel. If it remains unacknowledged, investigate delivery using the queue checks above. Then inspect `mdm_apple_declarative_requests` and `host_mdm_apple_declarations` for the individual declaration's progress. `nano_view_queue` shows the channel's command, which can cover several declarations.

### `Error.UnknownDeclarationType`

This code means the device does not recognize or support the declaration type. Fleet handles it as an invalid declaration. Check the OS version and whether the type is supported on that platform before changing the declaration.

### DDM limits

With default settings, uploaded declarations must be configuration types. Fleet rejects these in order: `com.apple.configuration.watch.enrollment` and `com.apple.configuration.account.google`; the status-subscription type; `com.apple.configuration.app.managed` and `com.apple.configuration.package`; and types outside the `com.apple.configuration.` prefix.

`mdm.allow_all_declarations`, disabled by default, bypasses those checks. Check this setting if Fleet accepts a type that the default validation would reject.

At 4.90.0, Premium accepts a custom software-update declaration when Fleet's own OS update settings are not already configured for that scope. Declarations can also reference Fleet-managed assets, served through `declaration/asset/...` requests.

[5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md#declaration-assets) covers asset authoring and upload. If an asset does not resolve on a device, confirm it was uploaded: a GitOps run on Free skips asset uploads without reporting that omission.

The batch and single-host resend endpoints reject declarations with a 400 response. Devices collect the current declaration set during check-in, so these endpoints cannot trigger a declaration resend.

For a declaration that has not arrived, investigate the host's check-in and DDM exchange using the steps above.

## 8.8.9 The half-enrolled state

MDM enrollment succeeds, `InstallEnterpriseApplication` fails, and the device ends up MDM-enrolled with no `fleetd` agent. It answers MDM commands and never appears as an osquery host.

Both ADE and manual macOS enrollment queue a post-enrollment task with a one-shot agent-install command. A failed install can therefore leave either path without fleetd. A manually enrolled Mac in this state shows `On (manual)`; an ADE-enrolled Mac shows `On (company-owned)`.

There is an ADE exception: the Premium setting `setup_experience.macos_manual_agent_install` suppresses the command when a bootstrap package is configured to deliver the agent separately. If that setting is enabled, investigate your own installation path. Manual enrollment always sends the command.

Audit agent presence after a bulk enrollment. The report in `fleetdm/fleet#47793` describes 20 to 30 missing agents among 1,000 machines in one deployment; use it as an example of the failure, not a forecast for your environment. The issue proposes a DDM-based installation path, but the 4.90.0 source does not establish that proposal as available behavior.

Follow [8.4](8.4-host-side-investigation.md) to confirm agent presence and recover the host. Apple MDM tables can look healthy while the agent is missing.

## 8.8.10 VPP install verification

A [VPP](../09-appendices/a.6-glossary-and-release-compatibility.md#vpp) install includes command delivery and a separate verification phase:

1. Fleet sends `InstallApplication`.
2. On acknowledgement, Fleet loops `InstalledApplicationList` commands until either the app appears as installed, or the verification timeout expires.

| Setting | Default | Env var |
|---|---|---|
| `server.vpp_verify_timeout` | 10 minutes | `FLEET_SERVER_VPP_VERIFY_TIMEOUT` |
| `server.vpp_verify_request_delay` | 5 seconds | `FLEET_SERVER_VPP_VERIFY_REQUEST_DELAY` |

A VPP failure can reflect a verification timeout even if the app ultimately installs. A slow network, large download, or device going to sleep can outlast the configured window. Check the command-result metadata before deciding to retry the installation.

Fetch `InstallApplication` results through the API to read `software_installed` and `vpp_verify_timeout_seconds`. They record installation state and the verification window. `fleetctl` does not print these fields, so its failure output alone cannot distinguish an installation failure from a verification timeout.

In the host's command feed, look for an acknowledged `InstallApplication` followed by repeated `InstalledApplicationList` commands without a successful verification result.

In-house `.ipa` installs use the same verification path. The difference is that their `InstallApplication` command carries a `ManifestURL` instead of an `iTunesStoreID`.

## 8.8.11 Error strings worth recognising

Search server logs for the strings below. The DEP client formats Apple responses as `DEP auth error: <status>: <body>` or `DEP HTTP error: <status>: <body>`, with Apple's error code in the body.

| Apple code | Typical rendering | Meaning | Fix |
|---|---|---|---|
| `T_C_NOT_SIGNED` | `DEP auth error: 403 Forbidden: "T_C_NOT_SIGNED"` | Apple's terms and conditions have not been accepted in ABM | Sign in to Apple Business as an administrator and accept the terms. Nothing in Fleet changes |
| `signature_invalid` | `DEP auth error: 403 Forbidden: "signature_invalid"` | The ABM server token was revoked or replaced in ABM without the new token being uploaded to Fleet | Download a fresh server token from ABM and upload it |
| `token_rejected` | same shape, 401 or 403 | Same root cause as `signature_invalid` per Apple's own error-code doc | Re-upload the ABM token |

All three can arrive as 403, so match on the body of the message rather than on the HTTP status.

`Error.UnknownDeclarationType` is covered in §8.8.8.

## 8.8.13 Narrowing the search

Begin with the device's last check-in and the command's result:

```sql
SELECT id, last_seen_at, TIMESTAMPDIFF(MINUTE, last_seen_at, NOW()) AS mins_ago
FROM   nano_enrollments
WHERE  id = '<host-uuid>' AND enabled = 1;
```

- A recent `last_seen_at` shows the device connected. Check for a result for this command: decode a terminal response, follow a `NotNow` deferral, or inspect selection order if no result exists. The device may have taken an earlier or higher-priority command.
- A stale `last_seen_at` calls for availability and push-path checks. If all Apple devices are affected, inspect APNs certificate expiry, topic changes, TLS inspection, and firewall changes. If one is affected, confirm it is online and inspect its push token before deciding whether it needs re-enrollment. See §8.8.4.
- No queue row means the command was not enqueued. Check the relevant cron in `cron_stats` and whether Fleet's desired state requires that profile ([8.6](8.6-server-state.md) §8.6.2).

For ADE symptoms, first check whether Fleet has the serial in `host_dep_assignments`. Inspect `nano_dep_names.syncer_cursor_at` as well: a cursor older than 168 hours has passed Apple's expiry.

Before escalating, gather the details in Fleet's MDM bug checklist: exact OS version, hardware model, fleetd version, enrollment method, prior MDM and whether it stopped managing the device, proxy and TLS-inspection configuration, Apple-service allowlisting, and whether a reboot changes the result. Share serial numbers through a private channel. [8.13](8.13-escalation.md) explains how to assemble the evidence.
