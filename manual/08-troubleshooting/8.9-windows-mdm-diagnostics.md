# 8.9 Windows MDM diagnostics

Every Windows MDM session is opened by the device. Wake comes through fleetd, over the Orbit channel, because Fleet does not use WNS, and that one fact makes an Orbit problem present as an MDM problem. Read §8.9.2 before anything else.

## 8.9.0 Start here

| Symptom | Start at | First thing to check |
|---|---|---|
| A Windows host is not getting its profile | [8.9.2](#892-the-relaxed-poll-and-the-fleetd-wake) | **Read that section before anything else.** On the relaxed poll a broken Orbit channel delays commands up to 8 hours with nothing wrong in MDM |
| Commands queue and are never acknowledged | [8.9.11](#8911-narrowing-the-search) | Has the device opened an OMA-DM session? That is a different question from "is the host online" |
| A profile was rejected by the device | [8.9.5](#895-syncml-status-and-alert-codes) | `404`, `405` and `415` are authoring errors; `500` is a device-side apply failure |
| A profile upload was refused by Fleet | [8.9.6](#reserved-locuris) | Only two subtrees are actually gated, and both conditionally |
| Enrollment fails | [8.9.7](#897-the-three-enrollment-paths) | Which of the three paths. Orbit, Entra licensing and scope, or the URL |
| Every Windows host fails management while enrollment works | [8.9.8](#898-wstep-device-identity-certificates) | Client certificates are used at `/management` and nowhere else, so a proxy stripping them affects only this endpoint. It is not automatically fatal, since the credential path may still authenticate |
| Host-side state: is it even enrolled, and to whom | [8.9.10](#8910-host-side-checks) | `dsregcmd /status`, then the `Enrollments` registry key |

**What follows from the fact at the top of this chapter:** because wake travels over the Orbit channel, Fleet cannot reach a device whose agent is not talking to it, and there is no single credential whose expiry takes the whole estate quiet at once. Both halves of that shape which failures are plausible, and §8.9.11 uses them to narrow a search.

## 8.9.1 Endpoints

Five HTTP paths, all under `/api/mdm/microsoft`.

| Path | Role |
|---|---|
| `/api/mdm/microsoft/discovery` | Discovery, in Microsoft's MS-MDE2 enrollment protocol. Returns the enrollment service and policy service URLs |
| `/api/mdm/microsoft/policy` | Certificate policy and requirements (key length, validity) |
| `/api/mdm/microsoft/enroll` | WSTEP, Microsoft's certificate enrollment protocol (§8.9.8). Takes the CSR, returns the signed device identity cert and the management endpoint |
| `/api/mdm/microsoft/management` | The OMA-DM session endpoint. OMA-DM is the device-management protocol Windows speaks, and SyncML is its XML wire format. `application/vnd.syncml.dm+xml`. Authenticates by client certificate **or** by SyncML credentials, see below |
| `/api/mdm/microsoft/tos` | Terms-of-use page rendered during Entra/Autopilot enrollment |

**Discovery is unauthenticated.** Only `policy` and `enroll` carry a bearer token in the SOAP `BinarySecurityToken` element: either Fleet's own enroll secret path (`DeviceEnrollmentUserToken`) or an Entra-issued JWT (`urn:ietf:params:oauth:token-type:jwt`).

The management endpoint has **two** ways to authenticate a session, and this is the fact that decides how you read a silent device. Fleet accepts the device identity certificate when one is presented, and it can also challenge the device and authenticate it with SyncML MD5 credentials carried in the message header, tracked per enrollment in `credentials_hash` and `credentials_acknowledged`. So a device without a usable certificate is not automatically shut out.

## 8.9.2 The relaxed poll and the fleetd wake

**Read this first for any "Windows host is not getting its profile" report.**

Fleet has two poll schedules and picks one per enrollment based on what fleetd says it can do.

| Schedule | Interval | Applies to |
|---|---|---|
| Fast (default) | `1` minute | Hosts whose fleetd does not advertise on-demand Windows MDM sync |
| Relaxed | `480` minutes (8 hours) | Hosts whose fleetd does advertise it |

The mechanism, in order:

1. **fleetd advertises the capability.** Windows fleetd sends `windows_mdm_sync` in the `X-Fleet-Capabilities` header on its config check-in.
2. **Fleet persists it per enrollment.** `POST /api/fleet/orbit/config` writes `mdm_windows_enrollments.fleetd_sync_capable` when the value changes. The header rides on the Orbit request, so the OMA-DM session reads the stored column instead.
3. **Fleet enqueues a poll change.** When `fleetd_sync_capable` and `poll_schedule_relaxed` disagree, Fleet builds a SyncML `Replace` on `./Device/Vendor/MSFT/DMClient/Provider/Fleet/Poll/IntervalForFirstSetOfRetries` with the new interval, enqueues it like any other command, and records the new intent in `poll_schedule_relaxed`. The column records *intent*, not confirmation, so the command is enqueued once per change rather than once per session.
4. **The device applies it** in the response to its next OMA-DM session, which is an ordinary command delivery.
5. **Wake on demand, when the host qualifies.** When a non-poll command is queued, Fleet sets `mdm_windows_enrollments.has_pending_commands`. The host's next fleetd config check-in returns `windows_mdm_sync_request: true` **only if two things hold**: the host's fleetd advertises the on-demand sync capability, and the host is not part-way through the setup experience, which takes precedence while `awaiting_configuration` is pending or active. When both hold, fleetd starts an immediate OMA-DM session. Older fleetd never advertises the capability, which is why those hosts keep the fast poll and never get a wake.

Fleet's own poll `Replace` is excluded from the pending-command signal, so tuning the poll never itself requests a wake.

### The diagnostic consequence

**A host on the relaxed poll with a broken Orbit channel will not receive MDM commands for up to 8 hours, and nothing in the MDM subsystem is wrong.** Everything in the MDM tables looks correct: the command is queued, the enrollment row is healthy, the device certificate is valid. The device has not been told to connect, and its own fallback poll is 8 hours away. The failure is in Orbit.

So **fleetd version is a diagnostic input for a Windows MDM problem**, and there is one version you particularly do not want to be on.

| fleetd | Behaviour |
|---|---|
| Before 1.57.0 | Does not advertise on-demand sync, so the host stays on the 1 minute poll. A multi-minute delay is real and worth chasing |
| **1.57.0** | Advertises the capability, so Fleet moves the host to the 8 hour poll, and then **cannot reliably start the session on some hosts**. That combination is the worst of both: the relaxed poll penalty with none of the wake benefit, and commands sitting for up to 8 hours on a host with nothing else wrong |
| 1.58.0 and later | The wake defect is fixed. fleetd now recognises the Fleet enrollment by any non-zero `EnrollmentState` |

Before opening the command queue, check that fleetd is running and reaching `POST /api/fleet/orbit/config` ([8.4](8.4-host-side-investigation.md)), and check its version against that table. **A fleet sitting on 1.57.0 is the single cheapest thing to rule out here**, because it presents exactly like a broken Orbit channel and is fixed by an agent upgrade rather than by anything in the MDM subsystem.

### Right after boot or resume

fleetd-initiated sessions can take a few minutes to begin connecting after a boot or a resume from sleep. Fleet keeps returning the sync request on every config check-in until the command is acknowledged, so the wake is retried rather than lost. Give a delay of a few minutes after a reboot time to clear before treating it as a fault, and confirm it cleared rather than assuming it did.

### Wake without a push service

Fleet wakes devices through fleetd instead of WNS (Windows Push Notification Service). WNS needs extra setup and credential management, is sometimes unreliable, and is a larger engineering lift, so Fleet uses the fleetd channel it already has. Fleet's architecture documentation lists WNS-based wake as a possible future addition. So there is no WNS credential to check and no push certificate to expire, and the poll schedule in this section is what actually determines how quickly a command arrives.

## 8.9.3 The delivery path

| # | Hop | Transport | Where state lands | How to observe |
|---|---|---|---|---|
| 1 | Fleet decides a command is needed | in-process, or `mdm_windows_profile_manager` | `host_mdm_windows_profiles.status` set to `pending`, or NULL awaiting the cron | SQL, §8.9.9 |
| 2 | Command is enqueued | MySQL write | one row in `windows_mdm_commands` (the SyncML body) plus one row per recipient in `windows_mdm_command_queue` with `acked_at` NULL | §8.9.4 |
| 3 | Fleet flags the enrollment | MySQL write | `mdm_windows_enrollments.has_pending_commands = 1` | SQL |
| 4 | fleetd is told to sync, **if it is capable and not in setup experience** (§8.9.2) | `POST /api/fleet/orbit/config` response | nothing persisted | `windows_mdm_sync_request` in the response body; server log at DEBUG ([8.2](8.2-log-surfaces.md)). Absent is the expected reading on a host that does not qualify |
| 5 | Device opens an OMA-DM session | `POST /api/mdm/microsoft/management`, SyncML, authenticated by certificate or credentials | `windows_mdm_responses` row per received envelope, `raw_response_gz` | §8.9.4 |
| 6 | Fleet delivers commands in the session response | same HTTP response | queue row still unacked | §8.9.4 |
| 7 | Device applies and reports status | next SyncML message in the same session, or the next session | `windows_mdm_command_results` row with `status_code`; queue row's `acked_at` set | §8.9.4 |
| 8 | Fleet interprets the result | in-process | `host_mdm_windows_profiles.status` moves to `verifying` / `verified` / `failed` | §8.9.9 |

**The session is device-initiated, always.** Hop 4 is a request, not a delivery. When hop 5 never happens, hop 4 and Orbit are where the problem is.

## 8.9.4 Command state in the database

Full column reference in [8.6](8.6-server-state.md). This is the working set.

| Table | Key columns |
|---|---|
| `windows_mdm_commands` | `command_uuid`, `raw_command`, `target_loc_uri`, `created_at`, `updated_at` |
| `windows_mdm_command_queue` | `enrollment_id`, `command_uuid`, `acked_at`, `created_at`, `updated_at` |
| `windows_mdm_command_results` | `enrollment_id`, `command_uuid`, `raw_result`, `response_id`, `status_code`, `created_at`, `updated_at` |
| `windows_mdm_responses` | `id`, `enrollment_id`, `raw_response_gz`, `created_at`, `updated_at` |
| `mdm_windows_enrollments` | `id`, `mdm_device_id`, `mdm_hardware_id`, `device_state`, `device_type`, `device_name`, `enroll_type`, `enroll_user_id`, `enroll_proto_version`, `enroll_client_version`, `not_in_oobe`, `host_uuid`, `hardware_serial`, `credentials_hash`, `credentials_acknowledged`, `awaiting_configuration`, `awaiting_configuration_at`, `poll_schedule_relaxed`, `has_pending_commands`, `fleetd_sync_capable`, `managed_local_account_escrowed` |

Three facts that catch people out:

- **The join key is `enrollment_id`, an integer, not the host UUID.** Go through `mdm_windows_enrollments.host_uuid` to get there.
- **`windows_mdm_responses.raw_response_gz` is a gzipped blob**, not text. Fleet compresses stored response envelopes to cut write pressure on the check-in path. Decompress before reading.
- **There is no `windows_mdm_responses.status`.** Per-command status lives in `windows_mdm_command_results.status_code`, which points back at the envelope through `response_id`.

### Queued vs delivered vs responded

```sql
SELECT c.command_uuid,
       c.target_loc_uri,
       q.created_at                  AS queued_at,
       q.acked_at,
       r.status_code,
       r.created_at                  AS responded_at,
       e.has_pending_commands,
       e.poll_schedule_relaxed,
       e.fleetd_sync_capable
FROM   mdm_windows_enrollments e
JOIN   windows_mdm_command_queue q  ON q.enrollment_id = e.id
JOIN   windows_mdm_commands      c  ON c.command_uuid  = q.command_uuid
LEFT   JOIN windows_mdm_command_results r
       ON r.enrollment_id = q.enrollment_id
      AND r.command_uuid  = q.command_uuid
WHERE  e.host_uuid = '<host-uuid>'
ORDER  BY q.created_at DESC
LIMIT  50;
```

| `acked_at` | `status_code` | State | Look at |
|---|---|---|---|
| NULL | NULL | Queued, never delivered | Hops 4 and 5. Is the device opening sessions at all? Check `fleetd_sync_capable` and `poll_schedule_relaxed` together, then check Orbit. §8.9.2 |
| NULL | set | **Should not occur on the normal path.** Fleet writes the result and stamps `acked_at` in one transaction, so seeing this pair is worth investigating rather than waiting out |
| set | `200` | Delivered, and the device said it applied it | Fleet takes the device's word for it: an ordinary Windows profile has **no read-back** (§8.9.9). If the setting still reads wrong on the device, the device and Fleet disagree, and the host is the only place that can settle it |
| set | `4xx` / `5xx` | The device rejected the command | Decode `raw_result`. §8.9.6, then §8.9.8 |
| no row at all | | Never enqueued | Hop 1. Check `cron_stats` for `mdm_windows_profile_manager`, and check whether Fleet thinks the host is in scope |

A queue with rows older than the relaxed poll and `has_pending_commands = 1` means Fleet believes there is work to deliver. It does **not** by itself mean wake requests are reaching the host: the sync request is only returned when the host's fleetd advertises the capability, and the setup-experience path gates it too. Confirm `fleetd_sync_capable` and check the config-check-in response before calling it an Orbit or network finding.

Acknowledged rows do not stay forever. `cleanup_windows_mdm_command_queue` runs as a job inside the `cleanups_then_aggregation` schedule ([8.6](8.6-server-state.md#863-the-named-schedules)) and retains one hour. So a missing old queue row is weak evidence on its own: an acknowledged command more than an hour old is expected to be gone.

## 8.9.5 SyncML status and alert codes

These are the values that land in `windows_mdm_command_results.status_code`.

| Code | Meaning |
|---|---|
| `200` | Applied |
| `202` | Accepted, result to follow later |
| `212` | Authentication accepted |
| `214` | Operation cancelled |
| `215` | Not executed |
| `216` | Atomic operation rolled back |
| `400` | Malformed command. Usually a bad `LocURI` or `Format` |
| `401` | Invalid credentials |
| `403` | Forbidden |
| `404` | The `LocURI` does not exist on this device. Wrong CSP path (§8.9.6), or the CSP is not present on this SKU or build |
| `405` | The verb is not allowed on that node, for example `Replace` against a read-only node |
| `406` | Optional feature not supported |
| `407` | Authentication required |
| `415` | The `Format` does not match what the node expects |
| `418` | The node already exists |
| `425` | Permission denied |
| `500` | Device-side failure applying the setting |
| `507` | An item inside `<Atomic>` failed |
| `516` | Atomic failed *and* the rollback failed. The device is in a partial state |

**`404`, `405`, and `415` are the profile-authoring codes.** All three say delivery worked and the payload is wrong. `500` says delivery worked and the device could not apply the setting. They sit at opposite ends of the pipeline.

Session alert codes, useful when reading a raw envelope:

| Code | Meaning |
|---|---|
| `1200` | Server-initiated management session |
| `1201` | Client-initiated management session |
| `1222` | More data follows in the next message |
| `1223` | Session abort |
| `1224` | Client event |
| `1225` | No end of data |
| `1226` | Generic alert |

A fleetd-woken session is still a *client*-initiated session, so `1201` is the code you will see even on a session Fleet asked for. Fleet has no push channel and sends no `1200`.

## 8.9.6 CSPs, LocURI, and Format

A **Configuration Service Provider (CSP)** is the device-side component that owns a settings area and exposes it as a tree of nodes. Every SyncML command targets one node by path.

```xml
<Replace>
  <Item>
    <Meta>
      <Format xmlns="syncml:metinf">chr</Format>
    </Meta>
    <Target>
      <LocURI>./Device/Vendor/MSFT/Policy/Config/RemoteDesktopServices/AllowUsersToConnectRemotely</LocURI>
    </Target>
    <Data>&lt;enabled/&gt;&lt;data id="SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" value="1"/&gt;</Data>
  </Item>
</Replace>
```

That is one of the worked Windows profile examples Fleet publishes (linked under further reading). Read them before authoring anything new.

| Element | What it is | Failure it causes when wrong |
|---|---|---|
| `<LocURI>` | The CSP node path. `./Device/...` for the device scope, `./User/...` for the user scope | `404` if the node does not exist on that build or SKU. Scope mistakes are the common form: a device-scope path used where the setting is user-scope only |
| `<Format>` | The data type declaration, in the `syncml:metinf` namespace | `415` when it disagrees with the node's type. `chr` is what Fleet's own example profiles use for ADMX-backed and string nodes. The full `Format` vocabulary is Microsoft's, and this manual does not restate it |
| `<Data>` | The value | `400` or `500` depending on how wrong |
| Top-level verb | `<Replace>`, `<Add>` or `<Atomic>` for ordinary profiles; `<Exec>` is accepted but its LocURIs are validated against the SCEP set, so it is not a general-purpose verb | Fleet rejects a profile with any other top-level element at upload rather than letting it fail on devices |

### Validation Fleet does at upload

Two checks catch a class of authoring mistake before it reaches a device:

- The payload must contain at least one supported SyncML top-level element (`<Replace>`, `<Add>`, `<Exec>`, `<Atomic>`). Non-XML and empty payloads are rejected.
- `<LocURI>` must not be empty, must not start with `/`, and must not contain `..` path traversal segments.

A successful upload means the shape is plausible. Path correctness is discovered on the device, as a `404`.

### Reserved LocURIs

Two subtrees are gated, both conditionally, and a third that this manual previously listed is not gated at all.

| LocURI prefix | What actually happens |
|---|---|
| `/Vendor/MSFT/BitLocker` | Rejected with "Couldn't add. The configuration profile can't include BitLocker settings." **unless** custom disk encryption is enabled for the deployment, in which case it is allowed through |
| `/Vendor/MSFT/Policy/Config/Update` | Not a blanket refusal. A profile targeting it needs **Fleet Premium**, and is rejected if OS updates are already configured for that fleet through Controls. Configure it in one place or the other, not both |
| `/Vendor/MSFT/RemoteWipe` | **No reserved-subtree check exists.** Fleet issues wipe as a command, and a custom profile touching this subtree is not refused at upload on that basis |

If a Windows profile upload is rejected and the payload looks fine, the BitLocker and OS-update conditions above are the first things to check, and the message names which one you hit.

### ADMX-backed policy

Third-party and legacy Group Policy settings arrive as ADMX-backed policies, ADMX being the XML format Windows uses for Group Policy templates. The `LocURI` names a Policy CSP node, and the `<Data>` carries an XML fragment of `<enabled/>` or `<disabled/>` plus `<data id="..." value="..."/>` elements. Fleet's worked examples include a full ADMX profile for Google Chrome.

**Whether Fleet compares those fragments semantically or as strings is not established at this release.** An equality helper for ADMX fragments exists in the source and a search found no production call sites, so this manual claims neither. Two consequences follow while it stays unestablished: do not rely on equivalent fragments in different orders being treated as equal, and treat a profile that keeps re-delivering as a delivery question first.

## 8.9.7 The three enrollment paths

Same protocol, three different ways the device is told to start, and three distinct failure signatures.

| Path | How the device learns Fleet's URL | Auth token at `/enroll` | Where it breaks |
|---|---|---|---|
| Agent-driven (programmatic) | Orbit receives `needs_programmatic_windows_mdm_enrollment` and `windows_mdm_discovery_endpoint` on its config check-in, then calls into Windows' `mdmregistration.dll` to register the device for management | Fleet's Orbit [node key](../09-appendices/a.6-glossary-and-release-compatibility.md#node-key), as `DeviceEnrollmentUserToken` | Orbit. Enrollment starts when Orbit is running and can reach Fleet; nothing on the device triggers it independently |
| Autopilot / Entra (OOBE) | Entra hands the device an MDM URL during the out-of-box experience (OOBE), the first-boot setup flow. Autopilot redirects to Fleet | An Entra-issued JWT (`urn:ietf:params:oauth:token-type:jwt`) | Licensing and Entra scope, almost always. See below |
| Settings app (BYOD) | The user types or is given the enrollment URL under Settings, Access work or school, Connect | Depends on the configured flow | The `host_uuid` link, historically. Fleet links the enrollment to the host record at the first management session, reading OMA-DM `DevDetail/SMBIOSSerialNumber` rather than waiting for osquery |

The enrollment SOAP exchange is identical in all three cases: discovery, then policy, then enroll, then the management session loop.

### Autopilot

Autopilot is Microsoft's zero-touch provisioning flow for new Windows devices. **Fleet never talks to it.** Autopilot and Intune assign a deployment profile to the device; that profile makes Entra hand the device Fleet's MDM URL during OOBE; the device then runs the ordinary MS-MDE2 flow against Fleet. There is no Fleet-to-Autopilot API call and no Autopilot state on the Fleet side to inspect. Confirm assignment in the Intune admin center.

Licensing:

| Who | License | For |
|---|---|---|
| The end user who signs in during enrollment | Microsoft Entra ID P1 | Automatic MDM enrollment. Without it, `MdmUrl` is empty in `dsregcmd /status` and enrollment fails silently |
| The admin | Microsoft Intune (for example Intune Plan 1) | Registering Autopilot devices, managing deployment profiles, connecting Entra to Fleet |

Fleet's Autopilot documentation marks the end-user requirement (Entra ID P1, no Intune license) as its current understanding rather than something verified end to end. When enrollment fails with `binarySecurityToken is empty` for a user who already has Entra ID P1, an Intune license is the next thing to try.

Entra scope is the other half. Under Mobility (MDM and WIP) in Entra, the Fleet app's MDM user scope must be **All**, or **Some** covering the enrolling user, and the Microsoft Intune app's MDM user scope should be **None**. Fleet scoped to None means Entra issues no MDM URL to anyone. Both apps scoped means devices may enroll into Intune instead of Fleet.

### The JWT and JWKS

Entra issues a JWT, the device presents it in the SOAP `BinarySecurityToken`, and Fleet verifies it by fetching Entra's public keys from `https://login.microsoftonline.com/common/discovery/v2.0/keys`. So **Fleet needs outbound HTTPS to `login.microsoftonline.com` for Entra-based enrollment to work at all.** An egress-restricted Fleet server fails every Autopilot enrollment while agent-driven enrollment keeps working, which is a useful bisection.

Token audience depends on how the Entra app was created:

| Token version | `aud` claim | Notes |
|---|---|---|
| v1 | The Fleet server URL | Existing applications |
| v2 | The application's client ID | New on-premises MDM applications created through the Entra portal flow from July 1, 2026. The client ID must be configured in Fleet |

A v2 token against a Fleet that only knows the server-URL audience fails verification. That is an audience mismatch, not a licensing problem.

### Enrollment error codes

The codes below are the ones Fleet's own documentation and release notes name.

| Code / string | Where it appears | Meaning | Fix |
|---|---|---|---|
| `80180006` | Device-side enrollment failure | The device's discovery `RequestVersion` was rejected. Fresh Windows 11 25H2 and other recent builds send a `RequestVersion` such as `"9.0"`, which an exact-match allow-list rejected. Fleet now accepts any MS-MDE2 discovery `RequestVersion` at or above the minimum `"4.0"` | Upgrade to 4.89.1 or later |
| `0x80180024` | Device-side, during Autopilot enrollment | Authentication failure, often stale state from earlier failed attempts | Start from clean state and retry |
| `binarySecurityToken is empty` | Fleet server log | The enrolling user has no Entra ID P1 license, or Fleet's MDM user scope is None in Entra | Assign the license to the enrolling user; set the Fleet app's MDM user scope to All |
| `ZtdDeviceIsNotRegistered` | Windows OOBE diagnostics (Ctrl+Shift+D during OOBE) | The device hash is not registered in any Autopilot tenant | Upload the hash to Intune and wait for Profile status: Assigned |
| `The string contains a non-printable character` | Windows certificate enrollment | A custom SCEP proxy CA challenge contains a character outside the printable set, for example an underscore. **4.90.1 removed** the upload-time validation 4.89.0 had added, because Apple devices enrol fine with such challenges. The Windows-side failure is unfixed at this release and Fleet's own notes say a fix ships separately | Use a challenge without such characters for Windows, rather than expecting Fleet to reject it at upload |

Fleet logs client errors on the Windows MDM endpoints at `info`, so an empty binary security token shows up at info level and an error-level filter misses it. See [8.2](8.2-log-surfaces.md) for verbosity behavior. `fleetctl debug errors` stores server faults, which puts a client-side enrollment rejection out of its scope as well.

## 8.9.8 WSTEP device identity certificates

Windows MDM can authenticate the management session with a certificate Fleet issues during enrollment, and that is one of two paths rather than the only one (§8.9.1). WSTEP is Microsoft's certificate request protocol, roughly the counterpart of [SCEP](../09-appendices/a.6-glossary-and-release-compatibility.md#scep) on Apple.

**Advertised policy values**, which is what Fleet tells the device during enrollment:

| Fact | Value |
|---|---|
| Signing | Fleet signs the device CSR with the WSTEP identity key |
| Minimum key length | `2048` |
| Certificate validity | `31536000` seconds (365 days) |
| Renewal period offered in the certificate policy | `15552000` seconds (180 days) |
| Renewal period written into the provisioning document | `365` days |
| Renewal retry interval | `4` (the unit is not documented) |
| ROBO (request on behalf of) support | `true` |
| Provider ID written to the device | `Fleet` |
| Binding table | `wstep_cert_auth_associations` (`id`, `sha256`, `created_at`, `updated_at`) |

**The dates on the certificate Fleet actually issues are not those.** When Fleet signs the CSR it backdates `NotBefore` by the renewal period, 180 days, and sets `NotAfter` to 365 days after that. So a certificate issued today is stamped valid from six months ago and **expires about 185 days from now**, not in a year.

That gap matters more than it looks. It means a Windows MDM deployment reaches its first certificate expiries at roughly six months, not twelve, and it means enrollment age is useless as a proxy for remaining life. **Read `NotAfter` off the certificate itself** rather than counting from the enrollment date.

Where certificate problems surface:

- **The management session, not enrollment.** A bad or missing device certificate is a problem at `/api/mdm/microsoft/management` and not at the enrollment endpoints. It does not automatically end the session, because the SyncML credential path above can still authenticate it. Where it does end the session there is no `windows_mdm_responses` row and no status code to read, and the symptom is commands queuing forever with `acked_at` NULL, exactly like a wake failure.
- **Telling those apart takes the host side plus a session check.** `DMPCertThumbPrint` and `RootCertThumbPrint` under the enrollment registry key (§8.9.10) say whether the device still has a certificate and which root it trusts. Read that alongside `MAX(windows_mdm_responses.created_at)` for the enrollment: a device that is opening sessions is authenticating somehow, whatever its certificate state, and the problem is downstream.
- **Renewal failure** is recorded client-side in `RenewErrorCode`, `RenewStatus`, and `RenewTimestamp` under the same key.
- `wstep_cert_auth_associations` is the server's record of which certificate hash is bound to which device. Fleet writes it, and at this release **nothing reads it back to reject an unassociated certificate**: association verification is marked as work not yet done, alongside renewal and revocation. Do not treat a row here as an access-control boundary.
- A TLS-terminating proxy that does not pass the client certificate through removes one of the two authentication paths at `/management`, and leaves enrollment untouched because the enrollment endpoints do not use it. Whether that stops a given device depends on whether it can fall back to the credential path. It is still worth checking early, because it explains a fleet-wide management failure with healthy enrollments better than anything on the device does.

### Renewal is advertised and is not implemented

Fleet's provisioning document tells the device the server supports request-on-behalf-of automatic certificate renewal, offers a 365 day renewal period, and gives a retry interval. Fleet's WSTEP implementation lists certificate lifecycle management, renewal and revocation, as work not yet done.

Those two facts sit a few lines apart in Fleet's own source and this manual is not going to guess how they resolve. What a device does as its certificate approaches expiry, and whether Fleet's enrollment endpoint happens to serve a renewal request as a fresh enrollment, is **not established at this release**.

What follows is a monitoring instruction rather than a prediction. Given the 185 day effective life above, a Windows MDM deployment reaches this question in its first six months. Watch `RenewStatus`, `RenewErrorCode` and `RenewTimestamp` under the enrollment registry key (§8.9.10) on a sample of the oldest enrollments, and read `NotAfter` from the certificates themselves rather than inferring it from enrollment dates.

## 8.9.9 Profiles and the `mdm_windows_profile_manager` cron

`mdm_windows_profile_manager` reconciles desired against actual Windows profile state and enqueues the SyncML commands. For its period, see the cron table in [8.6](8.6-server-state.md).

```sh
fleetctl trigger --name=mdm_windows_profile_manager
```

Per-host state:

```sql
SELECT profile_name, status, operation_type, retries, command_uuid, detail
FROM   host_mdm_windows_profiles
WHERE  host_uuid = '<host-uuid>'
ORDER  BY status, profile_name;
```

`host_mdm_windows_profiles` carries `host_uuid`, `profile_uuid`, `profile_name`, `status`, `operation_type`, `detail`, `command_uuid`, `retries`, `checksum`, `secrets_updated_at`, `created_at`, `updated_at`. `status` and `operation_type` are foreign keys into `mdm_delivery_status` and `mdm_operation_types`, the same two lookup tables Apple profiles use, so the vocabulary matches [8.8](8.8-apple-mdm-diagnostics.md) §8.8.7.

**`verified` means less on Windows than it does on Apple, for ordinary profiles.** Fleet maps a successful SyncML response straight to `verified`, including a `202 Accepted`, which means the device took the command rather than that it finished applying it. There is no independent read-back. So a Windows profile reading `verified` next to a setting that is plainly wrong on the device is not the contradiction it looks like: delivery succeeded and nothing has checked the result.

**The exception, new at 4.90.1**, is a profile using a Fleet-proxied SCEP certificate, from a custom SCEP proxy, NDES or Smallstep. Those now report `verified` only once Fleet has observed the issued certificate on the host, and `failed` when the proxy request returns an upstream error or the certificate is still missing an hour after delivery. For those profiles `verified` really does mean confirmed.

`host_mdm_windows_profiles_status` (`host_uuid`, `status`, `updated_at`) is a per-host rollup, one row per host. Use it to size a problem across the fleet; use `host_mdm_windows_profiles` to diagnose one host.

**`command_uuid` on the profile row is the join into the command queue.** That is the link that turns "profile stuck pending" into "which SyncML command, and did the device answer it":

```sql
SELECT p.profile_name, p.status, p.retries,
       q.acked_at, r.status_code, LEFT(p.detail, 200) AS detail
FROM   host_mdm_windows_profiles p
JOIN   mdm_windows_enrollments e ON e.host_uuid = p.host_uuid
LEFT   JOIN windows_mdm_command_queue q
       ON q.command_uuid = p.command_uuid AND q.enrollment_id = e.id
LEFT   JOIN windows_mdm_command_results r
       ON r.command_uuid = p.command_uuid AND r.enrollment_id = e.id
WHERE  p.host_uuid = '<host-uuid>';
```

Windows profiles are queued the moment a host enrolls in Windows MDM rather than at the next reconcile pass, so a newly enrolled host with no queue rows at all is a real finding rather than a timing artifact.

## 8.9.10 Host-side checks

### Entra join and MDM URL

```powershell
dsregcmd /status
```

Fields that matter: `AzureAdJoined`, `MdmUrl`, `TenantName`. **An empty `MdmUrl` on a device that should be Autopilot-enrolled means Entra never issued one**, which points at the missing Entra ID P1 license or an MDM user scope of None rather than at Fleet. To force a refresh of the primary refresh token after fixing licensing:

```powershell
dsregcmd /refreshprt
```

Allow 15 to 30 minutes for license propagation before retrying.

### Registry

`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Enrollments\` holds one subkey per enrollment, named with a GUID. The values worth reading:

| Value | What it tells you |
|---|---|
| `DiscoveryServiceFullURL` | Which MDM the device is actually talking to. Compare against your Fleet URL |
| `ProviderID` | `Fleet` for a Fleet enrollment |
| `EnrollmentState` | A non-zero value means enrolled, and that is the reading fleetd itself uses. The specific numeric meanings are published only in a Microsoft Graph beta reference that describes a different surface, so treat individual values beyond zero-versus-non-zero as unverified |
| `EnrollmentType` | `Device`, `Full`, or `AppManaged`. Fleet reports observing `6` on Entra-joined devices and `1` on manual enrollment, and marks those two values as observed rather than specified |
| `DMPCertThumbPrint` | Thumbprint of the MDM device certificate |
| `RootCertThumbPrint` | Thumbprint of the WSTEP root certificate |
| `RenewalPeriod`, `RenewStatus`, `RenewErrorCode`, `RenewTimestamp`, `RenewROBOSupport` | Certificate renewal state |
| `CurCryptoProvider`, `CurKeyContainer` | Key storage provider and container. Often `Microsoft Software Key Storage Provider` |
| `isFederated` | Endpoints came from discovery rather than manual install |
| `UPN`, `SID` | The enrolling user |
| `AADResourceID`, `AADTenantID` | Present on Entra-enrolled devices. Absence on a device you expected to be Entra-joined is diagnostic |
| `EnrollmentFlags` | MS-XCEP certificate template flags |

`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Provisioning\Diagnostics\AutoPilot` holds Autopilot provisioning diagnostic data.

**Two enrollment subkeys with different `DiscoveryServiceFullURL` values mean the device is carrying a stale enrollment.** Worth checking before any migration troubleshooting.

### OOBE diagnostics

During OOBE, Ctrl+Shift+D opens Autopilot diagnostics. That is where `ZtdDeviceIsNotRegistered` appears. Shift+F10 opens a command prompt at the OOBE screen, which is how you run `dsregcmd` before the device finishes provisioning.

### The Windows MDM event log channel

Fleet's own documentation names no event log channel, but Windows has one and it is the device's own record of enrollment and CSP failures, which no registry value can substitute for. Microsoft documents `Applications and Services Logs > Microsoft > Windows > DeviceManagement-Enterprise-Diagnostics-Provider > Admin` as the first log to read for an enrollment failure, with a Debug channel available when the Admin log is not enough, and an MDM diagnostics report for collecting the lot.

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin' -MaxEvents 100 |
  Format-List TimeCreated, Id, LevelDisplayName, Message
```

For a fuller capture than the Admin channel gives, Windows can collect an MDM diagnostics report, which bundles the relevant registry state, the enrollment record and the provider logs into one archive:

```powershell
mdmdiagnosticstool.exe -area "DeviceEnrollment;DeviceProvisioning;Autopilot" -zip C:\Temp\mdmdiag.zip
```

That is the artifact to ask an end user for when you have no other access to the device, and it is the Windows counterpart to the sysdiagnose in [8.2](8.2-log-surfaces.md#829-iosipados-sysdiagnose). The channel and the tool are Microsoft's, not Fleet's, so their contents are documented at learn.microsoft.com rather than here. Use them alongside the registry values above and the SyncML status codes in §8.9.5.

Host-side surfaces, in one place:

| Check | Command or path |
|---|---|
| Device's own record of enrollment and CSP failures | `Get-WinEvent -LogName 'Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin'` |
| Everything in one archive, for an end user to send | `mdmdiagnosticstool.exe -area "DeviceEnrollment;DeviceProvisioning;Autopilot" -zip <path>` |
| Entra join, MDM URL, tenant | `dsregcmd /status` |
| Force PRT refresh | `dsregcmd /refreshprt` |
| Hardware identity as Autopilot sees it | `Get-CimInstance Win32_ComputerSystemProduct \| Select Vendor, Name, UUID, IdentifyingNumber` |
| Enrollment record, certs, state | `HKLM\SOFTWARE\Microsoft\Enrollments\<GUID>` |
| Autopilot provisioning diagnostics | `HKLM\SOFTWARE\Microsoft\Provisioning\Diagnostics\AutoPilot` |
| BitLocker state before sysprep | `manage-bde -status C:` |

fleetd and Orbit log locations are in [8.4](8.4-host-side-investigation.md).

## 8.9.11 Narrowing the search

The first cut is **has the device opened an OMA-DM session recently**, a different question from "is the host online".

```sql
SELECT e.id, e.host_uuid, e.fleetd_sync_capable, e.poll_schedule_relaxed,
       e.has_pending_commands,
       MAX(rs.created_at) AS last_session
FROM   mdm_windows_enrollments e
LEFT   JOIN windows_mdm_responses rs ON rs.enrollment_id = e.id
WHERE  e.host_uuid = '<host-uuid>'
GROUP  BY e.id;
```

- **`last_session` recent, commands still unacked:** the device is connecting. Everything left of hop 5 is healthy. Look right. Decode `windows_mdm_command_results.status_code`; a `404`, `405`, or `415` is a payload problem (§8.9.6), a `500` is a device-side apply failure.
- **`last_session` stale and `poll_schedule_relaxed = 1`:** the device is on the 8 hour poll and depends on the fleetd wake. **Go look at Orbit** (§8.9.2). Confirm fleetd is checking in before touching anything MDM.
- **`last_session` stale and `poll_schedule_relaxed = 0`:** the device should be polling every minute and is not. That is a network path, a device certificate, or an unenrollment. Check `DMPCertThumbPrint` on the host (§8.9.10) and check whether a TLS-terminating proxy is dropping the client certificate (§8.9.8), remembering that on its own that removes one of two authentication paths rather than all of them.
- **`last_session` NULL and no enrollment row:** the device never completed enrollment. Go to §8.9.7 and pick the path. Which of the three it is decides where to look: Orbit for agent-driven, Entra licensing and scope for Autopilot, the URL and the `host_uuid` link for Settings-app.
- **Enrollment row present but `host_uuid` empty:** the enrollment exists and is not linked to a Fleet host record. Fleet links it at the first management session via `DevDetail/SMBIOSSerialNumber`, so an empty `host_uuid` alongside a populated `last_session` is a real defect worth escalating.

Second cut, once you know it is one side or the other: **is it one host or all Windows hosts.** All Windows hosts failing enrollment while existing enrollments keep working points at the enrollment endpoints, the Entra JWKS fetch, or a `RequestVersion` mismatch (§8.9.7). All Windows hosts failing *management* while enrollment works points at the proxy layer, since the client certificate is used at `/management` and nowhere else (§8.9.8). One host failing is a device-state problem: registry, certificate, or fleetd.

The blast-radius failures here are the enrollment endpoints and the client-certificate path at `/management`. Note what is **not** on that list: there is no single expiring credential that takes the whole estate quiet at once, which is the Apple shape and not this one.

### Reproducing it

```sh
fleetctl trigger --name=mdm_windows_profile_manager
```

Then watch `windows_mdm_command_queue` for a new row, and watch the config check-in response for `windows_mdm_sync_request`. If the row appears and the sync request is returned but no `windows_mdm_responses` row follows within a few minutes, you have reproduced a wake failure and the rest of the investigation is on the host.

A host on the fast poll (`poll_schedule_relaxed = 0`) reaches Fleet within a minute regardless of Orbit. Comparing a relaxed-poll host against a fast-poll one confirms a wake problem without instrumenting either device.

Before escalating, collect: exact Windows build including the feature update (25H2 and similar recent builds have their own enrollment history), fleetd version, which of the three enrollment paths was used, the `EnrollmentState` and `DiscoveryServiceFullURL` registry values, `dsregcmd /status` output, the `status_code` on the failing command, and whether a TLS-terminating proxy sits in front of Fleet. See [8.13](8.13-escalation.md).

> [!internal] On migrations from another Windows MDM, the stale-enrollment case in §8.9.10 (two subkeys under `Enrollments\`, different `DiscoveryServiceFullURL`) is worth checking on a sample of hosts before anyone starts diagnosing individual machines. It presents as intermittent, per-host weirdness rather than as a clean failure.

**That 4.90.1 entry is a §8.9.9 symptom with no §8.9.9 cause.** When every one of a removed profile's settings is still enforced by another profile, there is no `<Delete>` to send, so no command is enqueued and no acknowledgement will ever arrive to clear the host's row. Before 4.90.1 the row simply stayed. Diagnosing it through the command queue finds nothing, because nothing was ever queued, and the reader following §8.9.4's "no row at all" line would go looking at the reconcile cron and at scoping. On 4.90.0 and earlier the answer is that the profile is genuinely gone and only its row is left.
