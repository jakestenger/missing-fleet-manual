# 8.9 Windows MDM diagnostics

Windows devices open their own MDM sessions. Fleet can request an immediate session through fleetd's Orbit channel, so a problem with that channel can delay MDM commands even when enrollment is healthy. This chapter helps you distinguish that delay from enrollment, authentication, and profile errors. Start with the [poll and wake behavior](#892-the-relaxed-poll-and-the-fleetd-wake) when profiles are slow to arrive.

## 8.9.0 Start here

| Symptom | Start at | First thing to check |
|---|---|---|
| A Windows host is not getting its profile | [8.9.2](#892-the-relaxed-poll-and-the-fleetd-wake) | Check the poll schedule and Orbit connectivity; missing wake requests can delay delivery up to 8 hours |
| Commands queue and are never acknowledged | [8.9.11](#8911-narrowing-the-search) | Has the device opened an OMA-DM session? That is a different question from "is the host online" |
| A profile was rejected by the device | [8.9.5](#895-syncml-status-and-alert-codes) | `404`, `405` and `415` are authoring errors; `500` is a device-side apply failure |
| A profile upload was refused by Fleet | [8.9.6](#reserved-locuris) | Check the conditional BitLocker and OS-update restrictions |
| Enrollment fails | [8.9.7](#897-the-three-enrollment-paths) | Which of the three paths. Orbit, Entra licensing and scope, or the URL |
| Every Windows host fails management while enrollment works | [8.9.8](#898-wstep-device-identity-certificates) | Client certificates are used at `/management` and nowhere else, so a proxy stripping them affects only this endpoint. It is not automatically fatal, since the credential path may still authenticate |
| Host-side state: is it even enrolled, and to whom | [8.9.10](#8910-host-side-checks) | `dsregcmd /status`, then the `Enrollments` registry key |

Fleet uses fleetd for on-demand wake requests and device polling as a fallback. It has no WNS credential or shared push certificate to renew. The checks below follow those paths separately, then examine the session and command results.

## 8.9.1 Endpoints

Five HTTP paths, all under `/api/mdm/microsoft`.

| Path | Role |
|---|---|
| `/api/mdm/microsoft/discovery` | Discovery, in Microsoft's MS-MDE2 enrollment protocol. Returns the enrollment service and policy service URLs |
| `/api/mdm/microsoft/policy` | Certificate policy and requirements (key length, validity) |
| `/api/mdm/microsoft/enroll` | WSTEP, Microsoft's certificate enrollment protocol (§8.9.8). Takes the CSR, returns the signed device identity cert and the management endpoint |
| `/api/mdm/microsoft/management` | The OMA-DM session endpoint. OMA-DM is the device-management protocol Windows speaks, and SyncML is its XML wire format. `application/vnd.syncml.dm+xml`. Authenticates by client certificate **or** by SyncML credentials, see below |
| `/api/mdm/microsoft/tos` | Terms-of-use page rendered during Entra/Autopilot enrollment |

Discovery is unauthenticated. The `policy` and `enroll` requests carry a bearer token in the SOAP `BinarySecurityToken` element: Fleet's `DeviceEnrollmentUserToken` path or an Entra-issued JWT (`urn:ietf:params:oauth:token-type:jwt`).

The management endpoint accepts a device identity certificate or SyncML MD5 credentials in the message header. Fleet tracks the latter per enrollment in `credentials_hash` and `credentials_acknowledged`. When investigating a missing or unusable certificate, check whether the device is still authenticating through the credential path.

## 8.9.2 The relaxed poll and the fleetd wake

Check the host's poll schedule and fleetd version when a Windows profile is waiting for delivery.

Fleet chooses a poll schedule for each enrollment based on the capability fleetd advertises.

| Schedule | Interval | Applies to |
|---|---|---|
| Fast (default) | `1` minute | Hosts whose fleetd does not advertise on-demand Windows MDM sync |
| Relaxed | `480` minutes (8 hours) | Hosts whose fleetd does advertise it |

The mechanism, in order:

1. Windows fleetd advertises `windows_mdm_sync` in the `X-Fleet-Capabilities` header on its config check-in.
2. `POST /api/fleet/orbit/config` updates `mdm_windows_enrollments.fleetd_sync_capable` when that capability changes. The OMA-DM session reads the stored value.
3. If `fleetd_sync_capable` and `poll_schedule_relaxed` disagree, Fleet queues a SyncML `Replace` for `./Device/Vendor/MSFT/DMClient/Provider/Fleet/Poll/IntervalForFirstSetOfRetries`. It records the new intent in `poll_schedule_relaxed`, so the change is queued once per capability change. This value does not confirm device application.
4. The device receives and applies the poll change in its next OMA-DM session.
5. For other queued commands, Fleet sets `mdm_windows_enrollments.has_pending_commands`. A capable host's next config response includes `windows_mdm_sync_request: true`, and fleetd starts an immediate session. This request is withheld while setup experience takes precedence with `awaiting_configuration` pending or active. Older fleetd versions that do not advertise the capability retain the fast poll.

Fleet's own poll `Replace` is excluded from the pending-command signal, so tuning the poll never itself requests a wake.

<a id="the-diagnostic-consequence"></a>

### Check Orbit when delivery is delayed

On the relaxed poll, a host that cannot receive an Orbit wake request may wait up to 8 hours for its next MDM session. Its command queue, enrollment, and certificate can all look healthy during that wait. Check Orbit connectivity as well as MDM state.

The fleetd version also matters. Version 1.57.0 has a wake defect on some hosts:

| fleetd | Behaviour |
|---|---|
| Before 1.57.0 | Does not advertise on-demand sync, so the host stays on the 1 minute poll. Investigate delays that exceed the normal polling interval |
| **1.57.0** | Advertises the capability, so Fleet moves the host to the 8 hour poll, and then **cannot reliably start the session on some hosts**. Commands can wait up to 8 hours for the fallback poll |
| 1.58.0 and later | The wake defect is fixed. fleetd now recognises the Fleet enrollment by any non-zero `EnrollmentState` |

Confirm that fleetd is running and reaching `POST /api/fleet/orbit/config`, then compare its version with the table ([8.4](8.4-host-side-investigation.md)). If it is 1.57.0, upgrade the agent to resolve the known wake defect.

### Right after boot or resume

After boot or resume, fleetd-initiated sessions can take a few minutes to connect. Fleet repeats the sync request on each config check-in until the command is acknowledged. Allow for that delay, then verify that the session starts and the command progresses.

### Wake without a push service

Fleet uses its existing fleetd channel for wake requests. WNS (Windows Push Notification Service) is listed in the architecture documentation as a possible future addition and is not used at this release. For current delivery delays, inspect fleetd and the poll schedule above.

## 8.9.3 The delivery path

| # | Hop | Transport | Where state lands | How to observe |
|---|---|---|---|---|
| 1 | Fleet decides a command is needed | in-process, or `mdm_windows_profile_manager` | `host_mdm_windows_profiles.status` set to `pending`, or NULL awaiting the cron | SQL, §8.9.9 |
| 2 | Command is enqueued | MySQL write | one row in `windows_mdm_commands` (the SyncML body) plus one row per recipient in `windows_mdm_command_queue` with `acked_at` NULL | §8.9.4 |
| 3 | Fleet flags the enrollment | MySQL write | `mdm_windows_enrollments.has_pending_commands = 1` | SQL |
| 4 | fleetd is told to sync, **if it is capable and not in setup experience** (§8.9.2) | `POST /api/fleet/orbit/config` response | nothing persisted | `windows_mdm_sync_request` in the response body; server log at DEBUG ([8.2](8.2-log-surfaces.md)). Absent is the expected reading on a host that does not qualify |
| 5 | Device opens an OMA-DM session | `POST /api/mdm/microsoft/management`, SyncML, authenticated by certificate or credentials | `windows_mdm_responses` row per received envelope, `raw_response_gz` | §8.9.4 |
| 6 | Fleet delivers commands in the session response | same HTTP response | queue row still unacked | §8.9.4 |
| 7 | Device applies and reports status | next SyncML message in the same session, or the next session | `windows_mdm_command_results` row with `status_code`; queue row's `acked_at` set | §8.9.4 |
| 8 | Fleet interprets the result | in-process | `host_mdm_windows_profiles.status` moves to `verifying` / `verified` / `failed` | §8.9.9 |

Hop 4 asks the device to start a session; delivery happens when the device connects. If no session follows, check the configured schedule. A capable host on the 8-hour poll depends on fleetd for prompt delivery, while a host on the fast poll should connect independently every minute.

For missing sessions, inspect Orbit where wake requests apply, then enrollment, network and proxy behavior, and authentication. [8.9.11](#8911-narrowing-the-search) provides the sequence.

## 8.9.4 Command state in the database

These tables provide the working set for command diagnosis. [8.6](8.6-server-state.md) contains the full column reference.

| Table | Key columns |
|---|---|
| `windows_mdm_commands` | `command_uuid`, `raw_command`, `target_loc_uri`, `created_at`, `updated_at` |
| `windows_mdm_command_queue` | `enrollment_id`, `command_uuid`, `acked_at`, `created_at`, `updated_at` |
| `windows_mdm_command_results` | `enrollment_id`, `command_uuid`, `raw_result`, `response_id`, `status_code`, `created_at`, `updated_at` |
| `windows_mdm_responses` | `id`, `enrollment_id`, `raw_response_gz`, `created_at`, `updated_at` |
| `mdm_windows_enrollments` | `id`, `mdm_device_id`, `mdm_hardware_id`, `device_state`, `device_type`, `device_name`, `enroll_type`, `enroll_user_id`, `enroll_proto_version`, `enroll_client_version`, `not_in_oobe`, `host_uuid`, `hardware_serial`, `credentials_hash`, `credentials_acknowledged`, `awaiting_configuration`, `awaiting_configuration_at`, `poll_schedule_relaxed`, `has_pending_commands`, `fleetd_sync_capable`, `managed_local_account_escrowed` |

Use these keys and formats when querying the tables:

- Join on the integer `enrollment_id`. Find it through `mdm_windows_enrollments.host_uuid` when starting from a host UUID.
- Decompress `windows_mdm_responses.raw_response_gz` before reading it. Fleet stores response envelopes as gzip blobs to reduce writes on the check-in path.
- Read per-command status from `windows_mdm_command_results.status_code`, then follow `response_id` to the envelope. `windows_mdm_responses` has no `status` column.

### Queued vs delivered vs responded

```sql
SELECT c.command_uuid,
       c.target_loc_uri,
       q.created_at                  AS queued_at,
       q.acked_at,
       r.status_code,
       r.created_at                  AS responded_at,
       e.has_pending_commands,
       e.poll_schedule_relaxed,
       e.fleetd_sync_capable
FROM   mdm_windows_enrollments e
JOIN   windows_mdm_command_queue q  ON q.enrollment_id = e.id
JOIN   windows_mdm_commands      c  ON c.command_uuid  = q.command_uuid
LEFT   JOIN windows_mdm_command_results r
       ON r.enrollment_id = q.enrollment_id
      AND r.command_uuid  = q.command_uuid
WHERE  e.host_uuid = '<host-uuid>'
ORDER  BY q.created_at DESC
LIMIT  50;
```

| `acked_at` | `status_code` | State | Look at |
|---|---|---|---|
| NULL | NULL | Queued, no recorded answer | Hops 4 and 5. Is the device opening sessions at all? Check `fleetd_sync_capable` and `poll_schedule_relaxed` together, then check Orbit. §8.9.2 |
| NULL | set | Investigate this inconsistent state: Fleet normally records the result and `acked_at` in one transaction |
| set | `200` | Delivered, and the device said it applied it | For ordinary profiles, Fleet relies on the response without reading the setting back (§8.9.9). Inspect the host if the setting differs |
| set | `4xx` / `5xx` | The device rejected the command | Decode `raw_result`. §8.9.6, then §8.9.8 |
| no row at all | | Never enqueued | Hop 1. Check `cron_stats` for `mdm_windows_profile_manager`, and check whether Fleet thinks the host is in scope |

Old queue rows with `has_pending_commands = 1` confirm that Fleet has work waiting. To establish whether it requested a wake, also check `fleetd_sync_capable`, the setup-experience state, and the config response. Those conditions determine whether the response includes a sync request.

Acknowledged queue rows become eligible for cleanup after one hour. `cleanup_windows_mdm_command_queue` runs within the hourly `cleanups_then_aggregation` schedule, so removal normally happens on the following pass and can take close to two hours. An absent older row may have been cleaned up; a row still present at 90 minutes can be within that window. See [8.6](8.6-server-state.md#863-the-named-schedules).

## 8.9.5 SyncML status and alert codes

These are the values that land in `windows_mdm_command_results.status_code`.

| Code | Meaning |
|---|---|
| `200` | Applied |
| `202` | Accepted, result to follow later |
| `212` | Authentication accepted |
| `214` | Operation cancelled |
| `215` | Not executed |
| `216` | Atomic operation rolled back |
| `400` | Malformed command. Usually a bad `LocURI` or `Format` |
| `401` | Invalid credentials |
| `403` | Forbidden |
| `404` | The `LocURI` does not exist on this device. Wrong CSP path (§8.9.6), or the CSP is not present on this SKU or build |
| `405` | The verb is not allowed on that node, for example `Replace` against a read-only node |
| `406` | Optional feature not supported |
| `407` | Authentication required |
| `415` | The `Format` does not match what the node expects |
| `418` | The node already exists |
| `425` | Permission denied |
| `500` | Device-side failure applying the setting |
| `507` | An item inside `<Atomic>` failed |
| `516` | Atomic failed *and* the rollback failed. The device is in a partial state |

For `404`, check the CSP path and device support; for `405`, check the verb; for `415`, check the format. These responses confirm delivery and direct you to the payload's compatibility with the device. `500` means the device received the command but could not apply the setting.

Session alert codes, useful when reading a raw envelope:

| Code | Meaning |
|---|---|
| `1200` | Server-initiated management session |
| `1201` | Client-initiated management session |
| `1222` | More data follows in the next message |
| `1223` | Session abort |
| `1224` | Client event |
| `1225` | No end of data |
| `1226` | Generic alert |

A fleetd-requested session still uses the client-initiated code `1201`. Fleet does not use a push channel that sends `1200`.

## 8.9.6 CSPs, LocURI, and Format

A **Configuration Service Provider (CSP)** is the device-side component that owns a settings area and exposes it as a tree of nodes. Every SyncML command targets one node by path.

```xml
<Replace>
  <Item>
    <Meta>
      <Format xmlns="syncml:metinf">chr</Format>
    </Meta>
    <Target>
      <LocURI>./Device/Vendor/MSFT/Policy/Config/RemoteDesktopServices/AllowUsersToConnectRemotely</LocURI>
    </Target>
    <Data>&lt;enabled/&gt;&lt;data id="SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" value="1"/&gt;</Data>
  </Item>
</Replace>
```

The example comes from Fleet's published Windows profiles, linked under further reading. They provide useful starting points for authoring your own.

| Element | What it is | Failure it causes when wrong |
|---|---|---|
| `<LocURI>` | The CSP node path. `./Device/...` for the device scope, `./User/...` for the user scope | `404` if the node does not exist on that build or SKU. Check whether the path matches the setting's supported device or user scope |
| `<Format>` | The data type declaration, in the `syncml:metinf` namespace | `415` when it disagrees with the node's type. `chr` is what Fleet's own example profiles use for ADMX-backed and string nodes. The full `Format` vocabulary is Microsoft's, and this manual does not restate it |
| `<Data>` | The value | `400` or `500`, depending on the validation or apply failure |
| Top-level verb | `<Replace>`, `<Add>` or `<Atomic>` for ordinary profiles; `<Exec>` is accepted but its LocURIs are validated against the SCEP set, so it is not a general-purpose verb | Fleet rejects a profile with any other top-level element at upload rather than letting it fail on devices |

### Validation Fleet does at upload

Fleet checks the payload before accepting it:

- The payload must contain at least one supported SyncML top-level element (`<Replace>`, `<Add>`, `<Exec>`, `<Atomic>`). Non-XML and empty payloads are rejected.
- `<LocURI>` must not be empty, must not start with `/`, and must not contain `..` path traversal segments.

Upload validation checks structure. The device determines whether the target path exists and returns `404` if it does not.

### Reserved LocURIs

BitLocker and OS-update paths have conditional restrictions. The table also includes RemoteWipe to distinguish it from those checks.

| LocURI prefix | What actually happens |
|---|---|
| `/Vendor/MSFT/BitLocker` | Rejected with "Couldn't add. The configuration profile can't include BitLocker settings." **unless** custom disk encryption is enabled for the deployment, in which case it is allowed through. Enabling it needs **Fleet Premium**: Fleet turns `enable_custom_disk_encryption` off at startup when the licence is absent, so on Free this row has no exception |
| `/Vendor/MSFT/Policy/Config/Update` | A profile targeting it requires **Fleet Premium**, and is rejected if OS updates are already configured for that fleet through Controls. Choose either a custom profile or Controls for this scope |
| `/Vendor/MSFT/RemoteWipe` | There is no reserved-subtree check for this path. Fleet issues wipe as a command, and a custom profile touching this subtree is not refused at upload on that basis |

If Fleet rejects an otherwise valid upload, compare the error with the BitLocker and OS-update conditions above.

### ADMX-backed policy

Third-party and legacy Group Policy settings arrive as ADMX-backed policies, ADMX being the XML format Windows uses for Group Policy templates. The `LocURI` names a Policy CSP node, and the `<Data>` carries an XML fragment of `<enabled/>` or `<disabled/>` plus `<data id="..." value="..."/>` elements. Fleet's worked examples include a full ADMX profile for Google Chrome.

This release's source review did not establish whether Fleet compares ADMX fragments semantically or as strings. An equality helper exists, but no production call sites were found. Keep fragment ordering consistent rather than relying on equivalent orderings being treated as equal. If a profile repeatedly delivers, begin with its delivery history.

## 8.9.7 The three enrollment paths

Each enrollment path uses the same protocol, but a different component starts the process. Identify the path before choosing your checks.

| Path | How the device learns Fleet's URL | Auth token at `/enroll` | Where it breaks |
|---|---|---|---|
| Agent-driven (programmatic) | Orbit receives `needs_programmatic_windows_mdm_enrollment` and `windows_mdm_discovery_endpoint` on its config check-in, then calls into Windows' `mdmregistration.dll` to register the device for management | Fleet's Orbit [node key](../09-appendices/a.6-glossary-and-release-compatibility.md#node-key), as `DeviceEnrollmentUserToken` | Orbit. Enrollment starts when Orbit is running and can reach Fleet; nothing on the device triggers it independently |
| Autopilot / Entra (OOBE) | Entra hands the device an MDM URL during the out-of-box experience (OOBE), the first-boot setup flow. Autopilot redirects to Fleet | An Entra-issued JWT (`urn:ietf:params:oauth:token-type:jwt`) | Check licensing and Entra scope as described below |
| Settings app | The user types or is given the enrollment URL under Settings, Access work or school, Connect. Often used for personally owned machines, though **Fleet records no personal-enrollment status on Windows**, so that is a description of your intent rather than anything the console will tell you ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)) | Depends on the configured flow | Check the `host_uuid` link. Fleet links the enrollment to the host record at the first management session, reading OMA-DM `DevDetail/SMBIOSSerialNumber` rather than waiting for osquery |

The enrollment SOAP exchange is identical in all three cases: discovery, then policy, then enroll, then the management session loop.

### Autopilot

Autopilot provisions new Windows devices by using an assigned deployment profile to direct them through Entra during OOBE. Entra provides Fleet's MDM URL, and the device starts the MS-MDE2 enrollment flow against Fleet.

Check profile assignment in the Intune admin center. Fleet makes no Autopilot API call and stores no Autopilot assignment state.

Licensing:

| Who | License | For |
|---|---|---|
| The end user who signs in during enrollment | Microsoft Entra ID P1 | Automatic MDM enrollment. Without it, `MdmUrl` is empty in `dsregcmd /status` and enrollment fails silently. An empty `MdmUrl` does not prove the licence is missing, though: propagation delay and an MDM user scope of `None` produce the same symptom (§8.9.10) |
| The admin | Microsoft Intune (for example Intune Plan 1) | Registering Autopilot devices, managing deployment profiles, connecting Entra to Fleet |

Fleet's Autopilot documentation marks the end-user requirement (Entra ID P1, no Intune license) as its current understanding rather than something verified end to end. When enrollment fails with `binarySecurityToken is empty` for a user who already has Entra ID P1, an Intune license is the next thing to try.

In Entra's Mobility (MDM and WIP) settings, set the Fleet application's MDM user scope to **All**, or **Some** that includes the enrolling user. Set the Microsoft Intune application's scope to **None**. Fleet scoped to None receives no MDM enrollment URL from Entra; overlapping scopes can send devices to Intune instead.

### The JWT and JWKS

Fleet verifies the Entra JWT presented in `BinarySecurityToken` using public keys from `https://login.microsoftonline.com/common/discovery/v2.0/keys`. Allow outbound HTTPS to `login.microsoftonline.com`. If Entra-based enrollment fails while agent-driven enrollment works, check whether Fleet can fetch those keys.

Token audience depends on how the Entra app was created:

| Token version | `aud` claim | Notes |
|---|---|---|
| v1 | The Fleet server URL | Existing applications |
| v2 | The application's client ID | New on-premises MDM applications created through the Entra portal flow from July 1, 2026. The client ID must be configured in Fleet |

If Fleet is configured only for the server-URL audience, a v2 token fails audience validation. Check the application's client ID configuration before investigating licensing for that error.

### Enrollment error codes

The codes below are the ones Fleet's own documentation and release notes name.

| Code / string | Where it appears | Meaning | Fix |
|---|---|---|---|
| `80180006` | Device-side enrollment failure | The device's discovery `RequestVersion` was rejected. Fresh Windows 11 25H2 and other recent builds send a `RequestVersion` such as `"9.0"`, which an exact-match allow-list rejected. Fleet now accepts any MS-MDE2 discovery `RequestVersion` at or above the minimum `"4.0"` | Upgrade to 4.89.1 or later |
| `0x80180024` | Device-side, during Autopilot enrollment | Authentication failure, often stale state from earlier failed attempts | Start from clean state and retry |
| `binarySecurityToken is empty` | Fleet server log | The enrolling user has no Entra ID P1 license, or Fleet's MDM user scope is None in Entra | Assign the license to the enrolling user; set the Fleet app's MDM user scope to All |
| `ZtdDeviceIsNotRegistered` | Windows OOBE diagnostics (Ctrl+Shift+D during OOBE) | The device hash is not registered in any Autopilot tenant | Upload the hash to Intune and wait for Profile status: Assigned |
| `The string contains a non-printable character` | Windows certificate enrollment | A custom SCEP proxy CA challenge contains a character outside the printable set, for example an underscore. **4.90.0 removed** the upload-time validation 4.89.0 had added, because Apple devices enrol fine with such challenges. The Windows-side failure is unfixed at this release and Fleet's own notes say a fix ships separately | Use a challenge without such characters for Windows, rather than expecting Fleet to reject it at upload |

Include `info` messages when collecting Windows enrollment logs. Fleet logs client errors, including an empty binary security token, at that level. Error-only filters and `fleetctl debug errors`, which stores server faults, can miss these rejections. [8.2](8.2-log-surfaces.md) covers verbosity.

## 8.9.8 WSTEP device identity certificates

Fleet issues a device identity certificate during WSTEP enrollment. Windows can use it to authenticate management sessions, alongside the SyncML credential path in §8.9.1. WSTEP is Microsoft's certificate request protocol, serving a role similar to [SCEP](../09-appendices/a.6-glossary-and-release-compatibility.md#scep) on Apple.

Fleet advertises the following policy values during enrollment:

| Fact | Value |
|---|---|
| Signing | Fleet signs the device CSR with the WSTEP identity key |
| Minimum key length | `2048` |
| Certificate validity | `31536000` seconds (365 days) |
| Renewal period offered in the certificate policy | `15552000` seconds (180 days) |
| Renewal period written into the provisioning document | `365` days |
| Renewal retry interval | `4` (the unit is not documented) |
| ROBO (request on behalf of) support | `true` |
| Provider ID written to the device | `Fleet` |
| Binding table | `wstep_cert_auth_associations` (`id`, `sha256`, `created_at`, `updated_at`) |

Check the issued certificate's dates separately from those advertised values. Fleet backdates `NotBefore` by 180 days and sets `NotAfter` to 365 days after that date. A newly issued certificate therefore has about 185 days remaining.

Read `NotAfter` from the certificate when assessing expiry. The enrollment date can help identify older devices to inspect, but a later certificate renewal may make that date an inaccurate guide.

Where certificate problems surface:

- Certificate authentication applies at `/api/mdm/microsoft/management`. An unusable certificate can still be followed by successful SyncML credential authentication. If authentication fails entirely, no `windows_mdm_responses` row or command status is available, and queued commands retain NULL `acked_at`.
- Compare the host's `DMPCertThumbPrint` and `RootCertThumbPrint` with the latest session time in `windows_mdm_responses`. A recent session confirms that authentication succeeded through an available path.
- Inspect `RenewErrorCode`, `RenewStatus`, and `RenewTimestamp` under the enrollment registry key for client-side renewal failures (§8.9.10).
- `wstep_cert_auth_associations` records certificate-to-device bindings. At this release, Fleet does not read it back to reject unassociated certificates; association verification, renewal, and revocation are listed as unfinished work. Its presence is not evidence of an enforced access-control check.
- At a TLS-terminating proxy, confirm that client certificates reach Fleet. Stripping them removes one authentication path for management while leaving enrollment endpoints unaffected. Whether a device can continue depends on its credential path.

<a id="renewal-is-advertised-and-is-not-implemented"></a>

### Certificate renewal status at this release

The provisioning document advertises request-on-behalf-of renewal, a 365-day renewal period, and a retry interval. The WSTEP implementation also lists lifecycle management, renewal, and revocation as unfinished.

The source review for this release did not establish how devices behave at expiry or whether a renewal request can be handled as a fresh enrollment. Treat renewal behavior as unverified.

Monitor a sample of older enrollments before their certificates reach the roughly 185-day effective lifetime. Check `NotAfter` directly, together with `RenewStatus`, `RenewErrorCode`, and `RenewTimestamp` under the registry key in §8.9.10.

## 8.9.9 Profiles and the `mdm_windows_profile_manager` cron

`mdm_windows_profile_manager` reconciles desired against actual Windows profile state and enqueues the SyncML commands. For its period, see the cron table in [8.6](8.6-server-state.md).

```sh
fleetctl trigger --name=mdm_windows_profile_manager
```

Per-host state:

```sql
SELECT profile_name, status, operation_type, retries, command_uuid, detail
FROM   host_mdm_windows_profiles
WHERE  host_uuid = '<host-uuid>'
ORDER  BY status, profile_name;
```

`host_mdm_windows_profiles` carries `host_uuid`, `profile_uuid`, `profile_name`, `status`, `operation_type`, `detail`, `command_uuid`, `retries`, `checksum`, `secrets_updated_at`, `created_at`, `updated_at`. `status` and `operation_type` are foreign keys into `mdm_delivery_status` and `mdm_operation_types`, the same two lookup tables Apple profiles use, so the vocabulary matches [8.8](8.8-apple-mdm-diagnostics.md) §8.8.7.

For ordinary Windows profiles, Fleet sets `verified` from a successful SyncML response without independently reading the setting back. This includes `202 Accepted`, which can precede application. If the device's setting differs from the intended value, inspect the device even when Fleet shows `verified`.

Profiles using a Fleet-proxied SCEP certificate, through a custom proxy, NDES, or Smallstep, have an additional check. Fleet marks them `verified` after observing the issued certificate on the host.

An upstream SCEP proxy error fails the profile immediately. A missing certificate is handled during certificate-report ingestion, and only when Fleet has evidence that the relevant store was readable. User-scoped profiles require evidence from a user store.

An offline host, or an agent unable to enumerate certificates, can remain `verifying` beyond an hour. In that case, investigate certificate reporting; elapsed time alone does not trigger the missing-certificate failure.

`host_mdm_windows_profiles_status` (`host_uuid`, `status`, `updated_at`) is a per-host rollup, one row per host. Use it to size a problem across the fleet; use `host_mdm_windows_profiles` to diagnose one host.

Join the profile's `command_uuid` to the command queue to find the SyncML command and its device response:

```sql
SELECT p.profile_name, p.status, p.retries,
       q.acked_at, r.status_code, LEFT(p.detail, 200) AS detail
FROM   host_mdm_windows_profiles p
JOIN   mdm_windows_enrollments e ON e.host_uuid = p.host_uuid
LEFT   JOIN windows_mdm_command_queue q
       ON q.command_uuid = p.command_uuid AND q.enrollment_id = e.id
LEFT   JOIN windows_mdm_command_results r
       ON r.command_uuid = p.command_uuid AND r.enrollment_id = e.id
WHERE  p.host_uuid = '<host-uuid>';
```

Fleet queues Windows profiles during enrollment. If a newly enrolled host has no queue rows, investigate that step rather than waiting for the next reconciliation pass.

## 8.9.10 Host-side checks

### Entra join and MDM URL

```powershell
dsregcmd /status
```

Read `AzureAdJoined`, `MdmUrl`, and `TenantName`. An empty `MdmUrl` on an expected Autopilot enrollment means Entra has not supplied an MDM URL. Check the enrolling user's Entra ID P1 license, whether the assignment has propagated, and whether the Fleet application's MDM user scope is `None` ([3.3](../03-connect-devices/3.3-enroll-windows-devices.md)).

After correcting licensing, you can refresh the primary refresh token with:

```powershell
dsregcmd /refreshprt
```

Allow 15 to 30 minutes for license propagation before retrying.

### Registry

`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Enrollments\` holds one subkey per enrollment, named with a GUID. The values worth reading:

| Value | What it tells you |
|---|---|
| `DiscoveryServiceFullURL` | Which MDM the device is actually talking to. Compare against your Fleet URL |
| `ProviderID` | `Fleet` for a Fleet enrollment |
| `EnrollmentState` | A non-zero value means enrolled, and that is the reading fleetd itself uses. The specific numeric meanings are published only in a Microsoft Graph beta reference that describes a different surface, so treat individual values beyond zero-versus-non-zero as unverified |
| `EnrollmentType` | `Device`, `Full`, or `AppManaged`. Fleet reports observing `6` on Entra-joined devices and `1` on manual enrollment, and marks those two values as observed rather than specified |
| `DMPCertThumbPrint` | Thumbprint of the MDM device certificate |
| `RootCertThumbPrint` | Thumbprint of the WSTEP root certificate |
| `RenewalPeriod`, `RenewStatus`, `RenewErrorCode`, `RenewTimestamp`, `RenewROBOSupport` | Certificate renewal state |
| `CurCryptoProvider`, `CurKeyContainer` | Key storage provider and container. Often `Microsoft Software Key Storage Provider` |
| `isFederated` | Endpoints came from discovery rather than manual install |
| `UPN`, `SID` | The enrolling user |
| `AADResourceID`, `AADTenantID` | Present on Entra-enrolled devices. Absence on a device you expected to be Entra-joined is diagnostic |
| `EnrollmentFlags` | MS-XCEP certificate template flags |

`HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Provisioning\Diagnostics\AutoPilot` holds Autopilot provisioning diagnostic data.

When investigating a migration, check for enrollment subkeys with different `DiscoveryServiceFullURL` values. A record pointing to the previous MDM can reveal stale enrollment state.

### OOBE diagnostics

During OOBE, Ctrl+Shift+D opens Autopilot diagnostics. That is where `ZtdDeviceIsNotRegistered` appears. Shift+F10 opens a command prompt at the OOBE screen, which is how you run `dsregcmd` before the device finishes provisioning.

### The Windows MDM event log channel

For enrollment and CSP failures, read the device's `Applications and Services Logs > Microsoft > Windows > DeviceManagement-Enterprise-Diagnostics-Provider > Admin` log. Microsoft documents it as the initial enrollment log, with a Debug channel for further detail. It complements the registry and server-side command state.

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin' -MaxEvents 100 |
  Format-List TimeCreated, Id, LevelDisplayName, Message
```

To collect the related registry state, enrollment record, and provider logs together, create an MDM diagnostics report:

```powershell
mdmdiagnosticstool.exe -area "DeviceEnrollment;DeviceProvisioning;Autopilot" -zip C:\Temp\mdmdiag.zip
```

Ask for this archive when you need an end user to collect evidence from an otherwise inaccessible device. It serves a similar purpose to the iOS/iPadOS [sysdiagnose](8.2-log-surfaces.md#829-iosipados-sysdiagnose). Microsoft documents its contents at learn.microsoft.com. Compare it with the registry values above and the SyncML codes in §8.9.5.

Host-side surfaces, in one place:

| Check | Command or path |
|---|---|
| Device's own record of enrollment and CSP failures | `Get-WinEvent -LogName 'Microsoft-Windows-DeviceManagement-Enterprise-Diagnostics-Provider/Admin'` |
| Everything in one archive, for an end user to send | `mdmdiagnosticstool.exe -area "DeviceEnrollment;DeviceProvisioning;Autopilot" -zip <path>` |
| Entra join, MDM URL, tenant | `dsregcmd /status` |
| Force PRT refresh | `dsregcmd /refreshprt` |
| Hardware identity as Autopilot sees it | `Get-CimInstance Win32_ComputerSystemProduct \| Select Vendor, Name, UUID, IdentifyingNumber` |
| Enrollment record, certs, state | `HKLM\SOFTWARE\Microsoft\Enrollments\<GUID>` |
| Autopilot provisioning diagnostics | `HKLM\SOFTWARE\Microsoft\Provisioning\Diagnostics\AutoPilot` |
| BitLocker state before sysprep | `manage-bde -status C:` |

fleetd and Orbit log locations are in [8.4](8.4-host-side-investigation.md).

## 8.9.11 Narrowing the search

First check whether the device has opened a recent OMA-DM session. Fleet's online status alone does not answer that question.

```sql
SELECT e.id, e.host_uuid, e.fleetd_sync_capable, e.poll_schedule_relaxed,
       e.has_pending_commands,
       MAX(rs.created_at) AS last_session
FROM   mdm_windows_enrollments e
LEFT   JOIN windows_mdm_responses rs ON rs.enrollment_id = e.id
WHERE  e.host_uuid = '<host-uuid>'
GROUP  BY e.id;
```

- If `last_session` is recent, inspect the command result and selection state. Check payload compatibility for `404`, `405`, or `415`, and the device's apply failure for `500` (§8.9.6).
- If `last_session` is stale and `poll_schedule_relaxed = 1`, confirm fleetd is checking in and receiving a wake request (§8.9.2).
- If `last_session` is stale and `poll_schedule_relaxed = 0`, investigate the device's minute-by-minute polling: enrollment state, network and proxy access, and authentication. Check `DMPCertThumbPrint` and certificate forwarding, remembering that SyncML credentials provide another authentication path (§8.9.8).
- If `last_session` is NULL and there is no enrollment row, follow the appropriate enrollment path in §8.9.7: Orbit for agent-driven enrollment, Entra configuration for Autopilot, or the URL and host link for Settings-app enrollment.
- If an enrollment row has an empty `host_uuid` despite a recorded session, investigate the missing host association. Fleet normally creates that link during the first management session using `DevDetail/SMBIOSSerialNumber`. Include this evidence when escalating.

Next compare the affected hosts. Widespread enrollment failures with working existing enrollments point toward enrollment endpoints, Entra key retrieval, or discovery-version handling. Widespread management failures with working enrollment call for a proxy and authentication check. For one affected host, inspect its registry state, certificate, and fleetd.

For a widespread incident, focus on shared endpoints and infrastructure. Windows MDM has no equivalent of the shared APNs certificate whose expiry interrupts Apple pushes.

### Reproducing it

```sh
fleetctl trigger --name=mdm_windows_profile_manager
```

After triggering reconciliation, look for a new queue row and `windows_mdm_sync_request` in the config response. If both appear but no `windows_mdm_responses` row follows after a few minutes, continue on the host to determine why the requested session did not reach Fleet.

Compare an affected relaxed-poll host with a fast-poll host. The latter should connect within a minute independently of Orbit. A difference in their behavior helps narrow the investigation to wake requests, though the hosts' other conditions still need to be comparable.

Before escalating, collect: exact Windows build including the feature update (25H2 and similar recent builds have their own enrollment history), fleetd version, which of the three enrollment paths was used, the `EnrollmentState` and `DiscoveryServiceFullURL` registry values, `dsregcmd /status` output, the `status_code` on the failing command, and whether a TLS-terminating proxy sits in front of Fleet. See [8.13](8.13-escalation.md).

> During a Windows MDM migration, inspect a sample of hosts for stale enrollment records before troubleshooting each device. Different `DiscoveryServiceFullURL` values under `Enrollments\` can help explain inconsistent per-host behavior (§8.9.10).

**That 4.90.1 entry is a §8.9.9 symptom with no §8.9.9 cause.** When every one of a removed profile's settings is still enforced by another profile, there is no `<Delete>` to send, so no command is enqueued and no acknowledgement will ever arrive to clear the host's row. Before 4.90.1 the row simply stayed. Diagnosing it through the command queue finds nothing, because nothing was ever queued, and the reader following §8.9.4's "no row at all" line would go looking at the reconcile cron and at scoping. On 4.90.0 and earlier the answer is that the profile is genuinely gone and only its row is left.
