# Fleet server logs and what they actually tell you

The Fleet server's own operational log: how it is emitted, where it lands, what a line contains, and which questions belong to another surface.

## 8.3.0 Start here

Most visits to this chapter are one of five questions. Take the row.

| What you are trying to do | Go to | The thing that catches people |
|---|---|---|
| Find the log at all, on this deployment | [8.3.8](#838-where-the-logs-land) | Startup database errors bypass the logger and go to stdout as plain text, so a JSON collector misses them ([8.3.7](#837-startup-messages-that-bypass-the-logger)) |
| Understand why a failing request left no line | [8.3.4](#834-the-per-request-line-and-the-level-it-needs) | A lone 4xx logs at `debug` and is dropped at the default level. Silence is not evidence |
| Tie a customer-visible error to the node that produced it | [8.3.4](#the-uuid-correlation-trick) | Behind a load balancer, one request touches one node ([8.3.9](#839-multi-instance-the-log-you-are-reading-may-be-the-healthy-node)) |
| Recognise a specific error string | [8.3.6](#836-error-strings-worth-recognising) | Several are informational. A string is evidence, not a root cause |
| Turn verbosity up for a reproduction | [8.3.11](#8311-turning-verbosity-up-for-a-reproduction-and-back-down) | The level is fixed at process start, so both directions cost a restart, on every node |

Two facts decide how you read anything below. **The level is fixed when the process starts**, so you cannot raise verbosity on a running server. And **recorded errors are a different surface from the log**: they live in Redis, hold server faults only, and are read with `fleetctl debug errors` ([8.5](8.5-fleetctl-debug.md)).

## 8.3.1 Four streams, and which one this is

| Stream | What it carries | Destination setting | Section |
|---|---|---|---|
| Fleet server's own operational log | Startup, cron runs, health checks, per-request lines, internal errors | None. Always stderr. OTLP export optional | This section |
| osquery scheduled query **results** | Rows that scheduled queries produced on hosts | `osquery_result_log_plugin` | [8.2](8.2-log-surfaces.md) |
| osquery **status** logs | osquery's own health messages, forwarded through Fleet | `osquery_status_log_plugin` | [8.2](8.2-log-surfaces.md) |
| Fleet **audit** log | Who did what in Fleet, as activity records | `activity_audit_log_plugin`, gated by `activity_enable_audit_log` | [8.12](8.12-audit-logs.md) |

Rows two and three are pass-through: Fleet receives them from agents and writes them somewhere else. Fleet does not read them back. Row four is generated by Fleet but is a product record, not a diagnostic one.

The distinguishing fact: **the first stream has no plugin setting.** There is no `logging_plugin`. The server writes to stderr, and additionally to an OpenTelemetry collector over OTLP when you turn that export on. If you want it in a file, in Splunk, or in CloudWatch, that is your process supervisor's job, not Fleet's.

## 8.3.2 The settings

| Setting | Env var | CLI flag | Default | Effect |
|---|---|---|---|---|
| `logging_debug` | `FLEET_LOGGING_DEBUG` | `--logging_debug` | `false` | Debug level instead of info, **on stderr**. It does not govern OTLP export, see below |
| `logging_json` | `FLEET_LOGGING_JSON` | `--logging_json` | `false` | JSON records instead of `key=value` text |
| `logging_disable_banner` | `FLEET_LOGGING_DISABLE_BANNER` | `--logging_disable_banner` | `false` | Documented as suppressing the welcome banner |
| `logging_error_retention_period` | `FLEET_LOGGING_ERROR_RETENTION_PERIOD` | `--logging_error_retention_period` | `24h` | TTL on recorded errors in Redis. `0` never expires. Negative disables recording entirely |
| `logging_enable_topics` | `FLEET_LOGGING_ENABLE_TOPICS` | `--logging_enable_topics` | none | Comma-delimited topics to re-enable. See below, because this does less than it looks |
| `logging_disable_topics` | `FLEET_LOGGING_DISABLE_TOPICS` | `--logging_disable_topics` | none | Comma-delimited topics to suppress. A topic in both lists is **disabled** |
| `logging_tracing_enabled` | `FLEET_LOGGING_TRACING_ENABLED` | `--logging_tracing_enabled` | `false` | Export traces over OTLP, and inject `trace_id`/`span_id` into log records |
| `logging_otel_logs_enabled` | `FLEET_LOGGING_OTEL_LOGS_ENABLED` | `--logging_otel_logs_enabled` | `false` | Also ship log records to the OTLP collector, **at every severity regardless of `logging_debug`**. Stderr still gets whatever its own floor admits. Silently inert when `logging_tracing_type` is `elasticapm`, see below |
| `logging_tracing_type` | `FLEET_LOGGING_TRACING_TYPE` | `--logging_tracing_type` | empty | `elasticapm` sends traces to Elastic APM. Any other value means OTEL |

Every key except `logging_tracing_type` is in the configuration reference at fleetdm.com/docs/configuration/fleet-server-configuration. `logging_tracing_type` is accepted as a configuration key and has no entry there.

Three behaviours the table leaves out.

**There are exactly two levels on stderr.** Info normally, debug when `logging_debug` is on. There is no warn-only or error-only threshold, and no setting raises the floor above info.

**That floor is stderr's alone, and this is the part that surprises people.** When OTLP log export is on, Fleet wraps the two destinations in a handler that asks each one separately whether it wants the record. Stderr answers by its floor. The OTLP side answers yes to everything, because the exporter is built with a plain batch processor and no severity filter. So a server with `logging_debug` off and OTLP export on is still shipping **debug records to the collector**, and the only place they are missing is the terminal you are watching. Two consequences worth planning around: the collector's volume is a debug-level volume whatever `logging_debug` says, and turning debug off does not stop debug records from leaving the process.

**The level is fixed at process start.** Fleet reads it once, when the process starts. No SIGHUP handler and no level-setting endpoint exists (not documented; established by its absence). Changing verbosity means restarting the process.

**`logging_otel_logs_enabled` without `logging_tracing_enabled` is fatal at startup**, with this message:

```
logging.otel_logs_enabled requires logging.tracing_enabled to be true
```

**And there is a second combination that is not fatal and does nothing.** Fleet only builds its OpenTelemetry providers when tracing is enabled **and** `logging_tracing_type` is not `elasticapm`. So `logging_tracing_type: elasticapm` with `logging_otel_logs_enabled: true` passes the startup check, starts cleanly, and exports no logs at all: traces go to Elastic APM and the OTLP log exporter is never created. Nothing warns you. If you are on Elastic APM, OTLP log export is not available to you at this release.

`logging_disable_banner` is read from configuration and has no consumer elsewhere in the server as of 4.90.1. Treat its effect as unverified.

**Log topics are on unless something turns them off.** A topic Fleet has never heard of is treated as enabled, and at this release Fleet disables none of them by default. So `logging_enable_topics` has nothing to switch on: it removes a topic from the disabled set, and the disabled set starts empty. Setting it and seeing no change is the expected outcome, not a broken setting. `logging_disable_topics` is the half that does something. The two lists are applied in that order at startup, enables then disables, so naming a topic in both leaves it off.

## 8.3.3 Line shape

Text by default, JSON when `logging_json` is set. Both go through the same field rewriting:

| Field | Value |
|---|---|
| `ts` | RFC3339, always UTC. Renamed from the default field name `time` |
| `level` | Lowercased: `debug`, `info`, `warn`, `error` |
| `msg` | The message. **Omitted entirely when empty**, which is the normal case for request lines |
| `trace_id`, `span_id` | Present when `logging_tracing_enabled` is on and a span is active |
| everything else | Whatever the call site attached, as key/value pairs |

Shape of a text line, reconstructed from the logging configuration rather than copied from a running server:

```
ts=2026-08-19T14:03:11Z level=info msg="instance info" instanceID=Zm9vYmFy...
```

The `ts` rename and the lowercase level exist for compatibility with Fleet's older log format. Parsers built against Fleet output key on `ts`, not `time`.

## 8.3.4 The per-request line, and the level it needs

Every API request produces one log record. Attributes:

| Attribute | Meaning |
|---|---|
| `user` | Authenticated user's email, or the literal `unauthenticated`. Omitted on endpoints that skip caller logging |
| `method` | HTTP method |
| `uri` | Request URI |
| `took` | Handler duration |
| `err` | Text of every error on the request that carries no internal detail. Multiple joined with ` \|\| ` |
| `internal` | Text of every error that does carry internal detail, which is the part withheld from the client |
| `uuid` | Error UUIDs, comma-separated, matching the `uuid` field in the JSON error response body |
| (extras) | Per-endpoint key/value pairs the handler attached |

These records carry no `msg`. Grep for `uri=` or `"uri":`, not for a message.

`err` and `internal` split the request's errors between them rather than showing you the same error twice. An error that carries internal detail appears **only** in `internal`. So a line with `internal` and no `err` is normal, and it is the line you want: it means the caller was told something bland and the cause is right there.

**The level rule has three branches, and only one of them is the one people remember.**

| Condition | Level |
|---|---|
| The request produced **more than one** error, or a single error that is not a client error | `error` |
| The handler explicitly set a level for this request | Whatever it set, in practice `info` or `warn` |
| Everything else, including every success and every lone 4xx | `debug` |

The middle branch is the one the short version drops, and it is why this chapter's error-string table contains a `warn`-level request attribute. Login, logout and SSO initiation force `info`; deprecated API paths and deprecated field names force `warn`. All of those are request records and all of them survive at the default level.

The first branch has a sharp edge worth knowing. A request is demoted to `debug` for being a client error **only when it produced exactly one error**. A request that accumulates two client errors is logged at `error`, because the check that recognises a 4xx only looks at a single-error list. An `error`-level line is therefore not proof of a server fault.

Consequences:

- A host failing to check in with a stale [node key]() produces `authentication error: invalid node key`, one client error, so at default verbosity **nothing appears in the server log at all.** The host looks offline and the server looks quiet. Both are true and neither is the finding.
- Silence at the default level is close to no information about ordinary traffic, but it is not total silence: a deployment with automation on pre-rename API paths emits a `warn` request line per call, and every login and logout emits an `info` one.
- `logging_debug=true` turns on one line per request per node. On a deployment with agent check-ins that is the dominant volume. See [8.3.11](#8311-turning-verbosity-up-for-a-reproduction-and-back-down).

### The `uuid` correlation trick

Fleet's JSON error responses carry a `uuid` field. The server log line for that same request carries the same value in its `uuid` attribute. Given a failed API call, grab the uuid from the response body and grep every node's log for it. Behind a load balancer that is the reliable way to tie a customer-visible error to the node that produced it.

Caveat: Fleet reads the uuid from the unwrapped cause without walking the error chain, so an error whose top-of-chain type carries no uuid produces no uuid in the response body or the log line. This behaviour is not documented.

### `internal` is where the real cause hides

Fleet deliberately splits client-facing error text from internal detail. A request that returns a bland message to the caller can still log the actual database or upstream error in `internal`. If the API told you nothing useful, `internal` on that request's log line is the next place to look, at the verbosity where that line survives.

## 8.3.5 Recorded errors, and what the entries mean

`fleetctl debug errors` reads a dedup-and-count store of server errors that lives in **Redis**, not on disk and not in MySQL. Command flags are [8.5](8.5-fleetctl-debug.md). What follows is how to read the output.

### Mechanism

| Property | Value |
|---|---|
| Storage | Redis keys `error:{<hash>}:json` and `error:{<hash>}:count` |
| TTL | `logging_error_retention_period`, default `24h`. `0` means no expiry. Negative means the handler never runs and nothing is recorded |
| Dedup key | SHA-256 of the root cause's type, its message, and the stack trace captured where the error originated |
| Write path | Asynchronous, with a 2 second give-up timer. Errors can be dropped under load |
| Read path | `GET /debug/errors`. Non-destructive unless `flush=true` |
| Scope | **Cluster-wide.** All Fleet nodes write to the same Redis |

### Server faults only

Fleet's error handler stores an error in Redis when the error is a **server fault**. Client errors increment a metric and return to the caller without reaching the store. 4xx-shaped problems, including bad enroll secrets, invalid node keys, validation failures, and permission denials, will not be in `fleetctl debug errors`. This behaviour is not documented.

So an empty `fleetctl debug errors` output narrows things without settling them: no server-side fault was **recorded** in the retention window. Recording is asynchronous with a short give-up, so a burst can be dropped under load, and the store is off entirely when the retention period is negative. It says nothing at all about whether hosts are being rejected, since those are client errors.

### Entry shape

Each entry deserialises to `{"count": N, "chain": [...]}`. Each chain element has `message`, optional `data`, and optional `stack`. The chain is **reversed before storage into chronological order**, so element zero is the root cause and the last element is the outermost annotation.

Read it as: first element is what actually broke, later elements are the call path that wrapped it. The root error carries a full stack trace, and each wrapper carries one frame.

`data` is JSON attached at error creation. It always has `timestamp` in RFC3339, plus whatever diagnostic context the request contributed.

### Reading `count`

`count` is per unique hash, and the hash includes the stack trace. So:

| Pattern | Reading |
|---|---|
| One entry, very high count | One code path failing repeatedly. Usually an integration or a dependency, not a data problem |
| Many entries, count 1 each | Broad, varied failure. Look at what they share: a table, a team, a time window |
| Count that stops growing between two reads | The fault ended, or the writer gave up. Compare against the request-line volume |

One nuance: for errors carrying HTTP 408, socket addresses in the message are normalised to `<addr>` before hashing, so per-connection variants collapse into one entry. Request-timeout entries therefore aggregate; most others do not.

### Capture before you flush

Reading is non-destructive by default. `--flush` issues a Redis `DEL` on the keys it read. There is no undo and no copy anywhere else. Take a plain read first, keep the file, then flush if you want a clean window for a reproduction.

Without `--stdout`, `fleetctl debug errors` writes to a generated filename of the form `fleet-errors-20260819140311Z.json` in the working directory and prints a warning that the file may contain sensitive data. Review before attaching it to anything. Collection for escalation is [8.13](8.13-escalation.md).

## 8.3.6 Error strings worth recognising

Most of the strings below are emitted verbatim and can be grepped for directly. Several are patterns with a placeholder in angle brackets, so grep the fixed part of those.

| String | What it means |
|---|---|
| `DEP auth error: 403 Forbidden: T_C_NOT_SIGNED` | Fleet's [DEP]() client could not authenticate to Apple Business Manager: the terms and conditions have not been accepted. An admin must sign in to ABM and accept. Nothing on the Fleet side is broken |
| `DEP auth error: 403 Forbidden: signature_invalid` | The ABM server token is invalid or expired. Renew and re-upload the token. Fleet also matches this body on 401, so the status code alone does not identify the cause |
| `authentication error: missing node key` | An osquery request arrived with no node key. Usually an agent that has not enrolled yet |
| `authentication error: invalid node key` | The node key does not match any host row. The host was deleted from Fleet, or the database was restored from a point before that host enrolled. Client error, so debug level only, and not in `fleetctl debug errors` |
| `authentication error: missing orbit node key` | An Orbit endpoint was called without a key |
| `authentication error: invalid orbit node key` | Orbit's key does not match. Same causes as the osquery case, different agent component |
| `authentication error: invalid authorization header` | Header-based osquery auth failed. Check what sits between the agent and Fleet |
| `authentication error: missing HTTP signature` | Host identity certificates are in play and the request was not signed |
| `authentication error: certificate serial number mismatch` | The signing certificate is not the one Fleet has recorded for that host |
| `authentication error: certificate matching HTTP message signature not found` | No stored host identity certificate matched the signature |
| `health check failed` with `component=healthz`, `health-checker=<name>`, `err=<cause>` | Warn level. This is what `/healthz` returning 500 looks like from inside. `health-checker` names the dependency, usually MySQL or Redis |
| `total runtime (<d>) exceeded schedule interval (<d>)` | Info level. A cron job took longer than its own interval. The scheduler is now behind. Cross-check `cron_stats` in [8.6](8.6-server-state.md) |
| `pending job might still be running, wait <d>` | Info level. A previous run of this schedule has not reported completion, so this node is deferring |
| `lock failed` | Error level. The node could not take the schedule's lock, which lives in **MySQL**, in the `locks` table, not in Redis. Losing a race for the lock is ordinary on a multi-node deployment and is not logged as a failure; this line means the lock attempt itself errored, which usually means the database did. Treat it as a database signal rather than as contention |
| `unlock failed` | Error level, and the more alarming twin. A node finished a run and could not release the lock, so the schedule stays locked until the lock row's own expiry. Same reading: the write failed, so look at MySQL. Read it alongside `cron_stats` rows that never leave `pending` |
| `Request exceeds the max size limit of <size>` | The request body exceeded `server_default_max_request_body_size`. The client-facing text includes the configuration documentation link; the `internal` text adds the observed size |
| `logging.otel_logs_enabled requires logging.tracing_enabled to be true` | Startup refused. Fix the config pair |
| `orbit host with duplicate identifier has enrolled in Fleet and will overwrite existing host data`, with `identifier=` and `host_id=` | Warn level. Two machines are sharing one host record, or one machine lost its node key file and re-enrolled. Repeating on a schedule means two live hosts are stealing the record from each other. The osquery-channel twin of this message names `osquery.db`. Confirmed at 4.90.1 |
| `orbit host identity cert host id does not match enrolled host id. This is likely due to a duplicate UUID/identity identifier used by multiple hosts` | The same collision, but on a host with a TPM-backed identity certificate, where Fleet **refuses** the enroll instead of merging. Confirmed at 4.90.1 |
| `host identified by <osquery host id> enrolling too often` | The `osquery.enroll_cooldown` setting rejected a re-enroll. Default is 0, meaning disabled, so seeing this at all means someone set it. osquery channel only, never Orbit. Confirmed at 4.90.1 |
| `expected 4 builtin labels but got N` | One of the built-in labels `All Hosts`, `macOS`, `iOS`, `iPadOS` was deleted or renamed, so Apple hosts get **no** pre-osquery built-in label memberships. Fails open and silent apart from this line, one per enrollment. Anything scoped `macOS` include-any misses newly enrolled Macs. Confirmed at 4.90.1 |

**Missing built-in memberships have a second cause on 4.90.0, and no log line at all.** Re-enrolling an Apple host cleared its built-in label memberships and did not restore them, so label-scoped profiles, software and OS updates stopped being delivered to hosts that had done nothing wrong. 4.90.1 restores the memberships as part of the re-enrollment reset, marks the host's labels as not-yet-reported so the exclude-any guard does not trust the cleared set, and ships a migration that backfills hosts already affected. If you are diagnosing missing label-scoped delivery on Apple hosts, check the server version before you check anything else: on 4.90.0 the symptom needs no misconfiguration to appear, and on 4.90.1 upgrading is the fix.
| ``deprecated_path=<old path>`` with ``deprecation_warning=API `<old>` is deprecated, use `<new>` instead`` | Warn level, on the `deprecated-field-names` topic, which is on by default. Automation is still calling a pre-rename path (`/teams` rather than `/fleets`). Nothing is broken; the alias table routes it to the same handler. Note the backticks around the paths in Fleet's own text, which matter if you grep for the string. See [1.3](../01-foundations/1.3-hosts-fleets-labels.md) |
| `deprecation_warning='<old>' is deprecated, use '<new>' instead`, with no `deprecated_path` | The same topic and level, for a deprecated **field or query parameter** rather than a path. This variant quotes with apostrophes where the path variant uses backticks |

## 8.3.7 Startup messages that bypass the logger

Three database-state messages are written straight to **stdout**, not through the logger:

| Message opening | Meaning |
|---|---|
| `Your Fleet database is not initialized. Fleet cannot start up.` | No migrations have run. Run `fleet prepare db`. The process exits |
| `Your Fleet database is missing required migrations.` | Partial migration state. Exits unless the override below is set. **Fleet's own message names the config key wrongly**, see the note under this table |
| `Your Fleet database has unrecognized migrations.` | An older Fleet binary against a database migrated by a newer one. Unlike the other two, this one does **not** stop a production server: Fleet prints the banner and carries on, and only refuses to start in dev mode. That is how a partially rolled-back deployment keeps serving from a schema its binary does not fully know |

All three are framed in `#` banner lines. Because they bypass the logger, they are plain text even when `logging_json` is on, and a collector configured for structured stderr misses them. When a container restarts in a loop and your log search shows nothing, read the raw container output.


**One correction to Fleet's own output.** The message printed on a failed startup offers three ways to run without migrating, and the middle one names the wrong config path:

```
- Set environment variable FLEET_UPGRADES_ALLOW_MISSING_MIGRATIONS=1, or,
- Set config updates.allow_missing_migrations to true, or,
- Use command line argument --upgrades_allow_missing_migrations=true
```

The setting is under **`upgrades`**, not `updates`. The environment variable and the command line argument in that message are both correct; only the config path is wrong. Following it verbatim during a failed startup produces a second failure while appearing to do exactly what the server asked.

This is an override rather than a fix. It starts a server against a database that is missing migrations Fleet expects, which is a deliberate, temporary choice and not a way to skip `fleet prepare db`.

## 8.3.8 Where the logs land

| Deployment | Where server stderr goes | How to read it |
|---|---|---|
| systemd | journald, per the unit | `journalctl -u fleet.service -f` |
| Docker | Container stdout/stderr, per the configured logging driver | `docker logs -f <container>` |
| Kubernetes | Node container runtime, then whatever DaemonSet collector you run | `kubectl logs -f deploy/fleet` , add `--previous` after a crash loop, `-l app=fleet --max-log-requests=N` across replicas |
| ECS / Fargate | The task definition's log driver, normally `awslogs` to CloudWatch Logs | CloudWatch Logs Insights against the log group |
| Managed cloud | Not customer-accessible | Ask Fleet. `fleetctl debug errors` still works if you have an admin API token |

The systemd unit and `journalctl` invocation are from Fleet's reference architectures (fleetdm.com/docs/deploy/reference-architectures), which also sets `--logging_json` in the sample unit. The Docker, Kubernetes, and ECS rows are the standard behaviour of those platforms for a process that writes to stderr; Fleet does not document them.

> [!internal] On managed cloud, changing `logging_debug` is a Fleet-side operation with a restart attached. Plan the reproduction window before asking, because the window is what costs, not the flag.

## 8.3.9 Multi-instance: the log you are reading may be the healthy node

Each Fleet process logs its own work to its own stderr. Nothing aggregates them. On a multi-node deployment a fault can be confined to one node while every other node's log is clean.

### Identifying the node

At startup each process logs:

```
level=info msg="instance info" instanceID=<base64>
```

The instance ID is 64 random bytes, base64-encoded, generated in memory at every process start. A restart produces a new one, and the value is unrelated to the hostname or the pod name. Grab it once per node and keep the mapping for the length of the investigation.

### Where else that ID appears

| Surface | Field |
|---|---|
| Cron schedule log lines | `instanceID` attribute, alongside `schedule=<name>` |
| `cron_stats` table | `instance` column ([8.6](8.6-server-state.md)) |

Those are the same value. That is the join. A `cron_stats` row stuck in `pending` names the instance that started the job; grep that instance's log for the matching `instanceID` and you have the node that stalled. If no running process reports that instance ID at startup, the node that owned the row is gone and the row is orphaned.

### The load balancer trap

An API call reaches exactly one node. So does an MDM check-in, a script result upload, and an osquery distributed write. A single failing request leaves a trace on one node only. Three ways this bites:

1. **You reproduce a 500 and grep the wrong node's log.** Use the response body's `uuid` and search all nodes ([8.3.4](#834-the-per-request-line-and-the-level-it-needs)).
2. **You enable `logging_debug` on one node** and the reproduction lands on another. Enable it fleet-wide for the window, or pin your client to a single node.
3. **`filesystem` and `stdout` log destinations split the forwarded osquery streams across nodes** rather than duplicating them, so any one node holds a fraction of the stream. That is [8.2](8.2-log-surfaces.md)'s territory, same root cause.

Recorded errors are the exception. They go to shared Redis, so `fleetctl debug errors` returns a cluster-wide view regardless of which node answers the call. When you need "did this happen anywhere", reach for recorded errors before grepping stderr.

## 8.3.10 Questions that belong to another surface

| You want to know | Where it lives | Go to |
|---|---|---|
| Whether fleetd started, enrolled, or ran an install script on the host | Host-side agent logs. The host never reports them to the server | [8.4](8.4-host-side-investigation.md) |
| Why a macOS profile failed on the device | Device-side `mdmclient` behaviour | [8.4](8.4-host-side-investigation.md), [8.8](8.8-apple-mdm-diagnostics.md) |
| What rows a scheduled query returned | Forwarded result stream | [8.2](8.2-log-surfaces.md) |
| Whether osquery is healthy on a host | Forwarded status stream | [8.2](8.2-log-surfaces.md) |
| Who changed a team, policy, or configuration, and when | Audit log | [8.12](8.12-audit-logs.md) |
| Whether an operation succeeded | Fleet's state tables. Successful requests log at debug and carry no outcome semantics | [8.6](8.6-server-state.md) for the resulting state |

The general shape: the server log records what **this process** did and what broke inside it. Host behaviour and user intent live on other surfaces. A `uri=/api/v1/fleet/hosts/123` line at debug level proves that a request arrived, not that the host changed.

## 8.3.11 Turning verbosity up for a reproduction, and back down

Restarting is required in both directions. Budget for it.

**Up:**

1. Set `FLEET_LOGGING_DEBUG=true` on **every** node, not one ([8.3.9](#839-multi-instance-the-log-you-are-reading-may-be-the-healthy-node)).
2. Optionally set `FLEET_LOGGING_ERROR_RETENTION_PERIOD=0` so recorded errors do not expire out from under a long reproduction. Remember to put it back; `0` means never.
3. Restart. Note the new `instance info` line and the new instance IDs.
4. Run `fleetctl debug errors` and keep the output. That is your before-baseline.
5. Reproduce. Note the wall-clock time, and the `uuid` from any error response.
6. Capture: the log window from every node, plus a fresh `fleetctl debug errors`.

**Down:**

1. Remove `FLEET_LOGGING_DEBUG` and any retention override.
2. Restart.
3. Confirm the per-request debug lines stopped **on stderr**. Some request lines legitimately remain there, because handlers force `info` and `warn` levels for logins, logouts and deprecation warnings, so look for the disappearance of ordinary agent check-in lines rather than of all `uri=` lines. If they are still there, one node did not get the change. **In the OTLP collector they will not disappear at all**, for the reason in [8.3.2](#832-the-settings); do not read their continued presence there as a node that missed the restart.

What you gain at debug: the per-request line for every request, including successes and every 4xx, plus debug-level messages from Fleet's internals. The per-request line is most of the gain and all of the volume.

A single-node reproduction is cheaper than a fleet-wide one. If you can pin your client past the load balancer to one node, do that and enable debug there only. General technique for shrinking a repro is [8.11](8.11-reproducing-and-isolating.md).

## 8.3.12 Volume and retention at scale

Three facts to size against:

| Setting | Volume behaviour |
|---|---|
| `logging_debug=false` | Low and unpredictable. Not purely error-driven: logins, logouts, SSO initiation and every deprecated API call also emit a request line at this level |
| `logging_debug=true` | One record per API request per node. Agent check-in traffic dominates, so this scales with host count and check-in interval, not with user activity |
| `logging_otel_logs_enabled=true` | **The collector gets debug volume whatever `logging_debug` says.** Records at info and above go to both destinations, so those are emitted twice; debug records go to OTLP only, and are emitted once, in the place you are not looking. Unless `logging_tracing_type` is `elasticapm`, in which case OTLP export never starts |

Retention belongs to your platform. Journald, the Docker log driver, and CloudWatch each have their own limits, and Fleet writes to stderr regardless of whether anything is listening. The one retention control Fleet owns is `logging_error_retention_period`, and it applies to recorded errors in Redis, not to stderr.

Debug logging left on permanently is a cost and ingest problem before it is a performance problem. The performance side, including what to watch when the server is degraded, is [8.14](8.14-degradation.md).
