# Fleet server logs and how to read them

Use server operational logs to inspect startup, request handling, and background work. This reference explains where to collect them, how to interpret a record, and when another surface provides the evidence you need.

## 8.3.0 Start here

Choose the task that matches your investigation:

| What you are trying to do | Go to | Evidence or limit to check |
|---|---|---|
| Find the log at all, on this deployment | [8.3.8](#838-where-the-logs-land) | Startup database errors bypass the logger and go to stdout as plain text, so a JSON collector misses them ([8.3.7](#837-startup-messages-that-bypass-the-logger)) |
| Understand why a failing request left no line | [8.3.4](#834-the-per-request-line-and-the-level-it-needs) | A lone 4xx logs at `debug` and is dropped at the default level. Check whether debug was enabled |
| Tie a customer-visible error to the node that produced it | [8.3.4](#correlate-a-response-with-its-uuid) | Behind a load balancer, one request touches one node ([8.3.9](#839-collect-logs-from-every-serving-instance)) |
| Recognise a specific error string | [8.3.6](#836-error-strings-worth-recognising) | Several are informational. Interpret the string with its request context |
| Turn verbosity up for a reproduction | [8.3.11](#8311-turning-verbosity-up-for-a-reproduction-and-back-down) | The level is fixed at process start, so both directions cost a restart, on every node |

Plan for a restart when changing verbosity: Fleet reads the level at process startup. Also distinguish operational logs from recorded errors. The latter are server faults retained in Redis and read through [fleetctl debug errors](8.5-fleetctl-debug.md).

## 8.3.1 Four streams, and which one this is

| Stream | What it carries | Destination setting | Section |
|---|---|---|---|
| Fleet server's own operational log | Startup, cron runs, health checks, per-request lines, internal errors | None. Always stderr. OTLP export optional | This section |
| osquery scheduled query **results** | Rows that scheduled queries produced on hosts | `osquery_result_log_plugin` | [8.2](8.2-log-surfaces.md) |
| osquery **status** logs | osquery's own health messages, forwarded through Fleet | `osquery_status_log_plugin` | [8.2](8.2-log-surfaces.md) |
| Fleet **audit** log | Who did what in Fleet, as activity records | `activity_audit_log_plugin`, gated by `activity_enable_audit_log` | [8.12](8.12-audit-logs.md) |

Fleet forwards the result and status streams from agents to their configured destinations without reading them back. The audit stream records product activity, including administrative changes. Use the operational stream for the server process's diagnostic evidence.

Operational output goes to stderr, with optional OpenTelemetry export over OTLP. There is no `logging_plugin` setting. Configure the process supervisor or collector to retain stderr in a file, Splunk, CloudWatch, or another destination.

The optional [MCP server](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) runs as a separate binary with its own log. See §8.3.13 for that output.

## 8.3.2 The settings

| Setting | Env var | CLI flag | Default | Effect |
|---|---|---|---|---|
| `logging_debug` | `FLEET_LOGGING_DEBUG` | `--logging_debug` | `false` | Debug level instead of info, **on stderr**. It does not govern OTLP export, see below |
| `logging_json` | `FLEET_LOGGING_JSON` | `--logging_json` | `false` | JSON records instead of `key=value` text |
| `logging_disable_banner` | `FLEET_LOGGING_DISABLE_BANNER` | `--logging_disable_banner` | `false` | Documented as suppressing the welcome banner |
| `logging_error_retention_period` | `FLEET_LOGGING_ERROR_RETENTION_PERIOD` | `--logging_error_retention_period` | `24h` | TTL on recorded errors in Redis. `0` never expires. Negative disables recording entirely |
| `logging_enable_topics` | `FLEET_LOGGING_ENABLE_TOPICS` | `--logging_enable_topics` | none | Comma-delimited topics to re-enable. Topics start enabled; see the details below |
| `logging_disable_topics` | `FLEET_LOGGING_DISABLE_TOPICS` | `--logging_disable_topics` | none | Comma-delimited topics to suppress. A topic in both lists is **disabled** |
| `logging_tracing_enabled` | `FLEET_LOGGING_TRACING_ENABLED` | `--logging_tracing_enabled` | `false` | Export traces over OTLP, and inject `trace_id`/`span_id` into log records |
| `logging_otel_logs_enabled` | `FLEET_LOGGING_OTEL_LOGS_ENABLED` | `--logging_otel_logs_enabled` | `false` | Also ship log records to the OTLP collector, **at every severity regardless of `logging_debug`**. Stderr still gets whatever its own floor admits. Silently inert when `logging_tracing_type` is `elasticapm`, see below |
| `logging_tracing_type` | `FLEET_LOGGING_TRACING_TYPE` | `--logging_tracing_type` | empty | `elasticapm` sends traces to Elastic APM. Any other value means OTEL |

Every key except `logging_tracing_type` is in the configuration reference at fleetdm.com/docs/configuration/fleet-server-configuration. `logging_tracing_type` is accepted as a configuration key and has no entry there.

Account for these configuration details when choosing a destination and verbosity:

Stderr has two available thresholds: info by default, or debug with `logging_debug`. There is no setting for a warn-only or error-only threshold.

OTLP export accepts every severity independently of the stderr threshold. With export enabled and `logging_debug` off, debug records still leave the process for the collector while remaining absent from stderr. Size collector ingestion for that volume; changing `logging_debug` controls stderr only.

The level is fixed at process startup. Fleet has no SIGHUP reload or level-setting endpoint, so apply a verbosity change by restarting the process.

Enabling `logging_otel_logs_enabled` without `logging_tracing_enabled` prevents startup with this message:

```
logging.otel_logs_enabled requires logging.tracing_enabled to be true
```

With `logging_tracing_type: elasticapm`, traces go to Elastic APM and Fleet never creates the OTLP log exporter. `logging_otel_logs_enabled: true` still passes startup validation in that combination, without a warning or log export. Use the OpenTelemetry tracing path when OTLP logs are required.

`logging_disable_banner` is read from configuration and has no consumer elsewhere in the server as of 4.90.0, so it has no operational effect at this release.

Topics are enabled by default, including names Fleet has not previously seen. At this release, the initial disabled set is empty, so `logging_enable_topics` usually has nothing to restore. At startup Fleet applies the enable list, then the disable list. A topic present in both ends up disabled.

## 8.3.3 Line shape

Text by default, JSON when `logging_json` is set. Both go through the same field rewriting:

| Field | Value |
|---|---|
| `ts` | RFC3339, always UTC. Renamed from the default field name `time` |
| `level` | Lowercased: `debug`, `info`, `warn`, `error` |
| `msg` | The message. **Omitted entirely when empty**, which is the normal case for request lines |
| `trace_id`, `span_id` | Present when `logging_tracing_enabled` is on and a span is active |
| everything else | Whatever the call site attached, as key/value pairs |

Shape of a text line, reconstructed from the logging configuration rather than copied from a running server:

```
ts=2026-08-19T14:03:11Z level=info msg="instance info" instanceID=Zm9vYmFy...
```

The `ts` rename and the lowercase level exist for compatibility with Fleet's older log format. Parsers built against Fleet output key on `ts`, not `time`.

## 8.3.4 The per-request line, and the level it needs

Every API request produces one log record. Attributes:

| Attribute | Meaning |
|---|---|
| `user` | Authenticated user's email, or the literal `unauthenticated`. Omitted on endpoints that skip caller logging |
| `method` | HTTP method |
| `uri` | Request URI |
| `took` | Handler duration |
| `err` | Text of every error on the request that carries no internal detail. Multiple joined with ` \|\| ` |
| `internal` | Text of every error that does carry internal detail, which is the part withheld from the client |
| `uuid` | Error UUIDs, comma-separated, matching the `uuid` field in the JSON error response body |
| (extras) | Per-endpoint key/value pairs the handler attached |

Request records omit `msg`. Search for `uri=` in text output or `"uri":` in JSON.

Read both error attributes. An error with internal detail appears in `internal`; an error without that detail appears in `err`. They contain different errors rather than duplicate copies. A record with `internal` alone can therefore contain the underlying cause withheld from the client.

The request level follows these rules, in order:

| Condition | Level |
|---|---|
| The request produced **more than one** error, or a single error that is not a client error | `error` |
| The handler explicitly set a level for this request | Whatever it set, in practice `info` or `warn` |
| Everything else, including every success and every lone 4xx | `debug` |

Handlers can raise the request level explicitly. Login, logout, and SSO initiation use `info`; deprecated paths and field names use `warn`. These records remain visible on stderr at its default threshold.

The client-error exception applies only to a single-error list. A request with two client errors is logged at `error`, so inspect the errors themselves before classifying that line as a server fault.

Use those rules when interpreting missing or high-volume request output:

- A stale [node key](../09-appendices/a.6-glossary-and-release-compatibility.md#node-key) produces the single client error `authentication error: invalid node key`. Its request line is debug-level and absent from default stderr output.
- Default verbosity still includes login and logout records, along with warning-level requests using deprecated API paths or fields.
- `logging_debug=true` includes ordinary requests on every node, increasing volume with agent check-ins. Plan the collection window using [8.3.11](#8311-turning-verbosity-up-for-a-reproduction-and-back-down).

<a id="the-uuid-correlation-trick"></a>

### Correlate a response with its `uuid`

Take the `uuid` from a JSON error response and search every Fleet node's log for the same request attribute. This identifies the node that handled the failing call behind a load balancer.

Some errors have no UUID in either location. Fleet reads the unwrapped cause without walking the error chain, so a top-level cause that carries no UUID provides none to correlate. This behavior is not documented in the guide.

<a id="internal-is-where-the-real-cause-hides"></a>

### Read `internal` for additional error detail

Inspect `internal` when the client-facing message lacks enough detail. Fleet can retain the database or upstream error there while returning a more general message to the caller. Ensure the request's log level was collected during reproduction.

## 8.3.5 Recorded errors, and what the entries mean

`fleetctl debug errors` reads deduplicated server faults and counts from Redis. [8.5](8.5-fleetctl-debug.md) lists the command flags; the following sections explain its output.

### Mechanism

| Property | Value |
|---|---|
| Storage | Redis keys `error:{<hash>}:json` and `error:{<hash>}:count` |
| TTL | `logging_error_retention_period`, default `24h`. `0` means no expiry. Negative means the handler never runs and nothing is recorded |
| Dedup key | SHA-256 of the root cause's type, its message, and the stack trace captured where the error originated |
| Write path | Asynchronous, with a 2 second give-up timer. Errors can be dropped under load |
| Read path | `GET /debug/errors`. Non-destructive unless `flush=true` |
| Scope | **Cluster-wide.** All Fleet nodes write to the same Redis |

### Server faults only

The error handler records server faults in Redis. Client errors, including invalid enrol secrets, node keys, validation failures, and permission denials, increment a metric and return to the caller without entering this store. Use request logs to investigate those failures. This filtering is not documented in the guide.

An empty result means no fault was retained in the window. Asynchronous writes can time out under load, and a negative retention period disables recording entirely. It also provides no evidence about rejected host requests, which are client errors.

### Entry shape

Each entry deserialises to `{"count": N, "chain": [...]}`. Each chain element has `message`, optional `data`, and optional `stack`. The chain is **reversed before storage into chronological order**, so element zero is the root cause and the last element is the outermost annotation.

Read from the root cause at element zero through the later wrappers. The root includes a full stack trace; each wrapper contributes one frame showing how the error moved through the call path.

`data` is JSON attached at error creation. It always has `timestamp` in RFC3339, plus whatever diagnostic context the request contributed.

### Reading `count`

Counts group errors by hash, including their stack trace. Interpret the count alongside the error context:

| Pattern | Reading |
|---|---|
| One entry, very high count | One code path failing repeatedly. Inspect the repeated operation and its integration or dependency context |
| Many entries, count 1 each | Broad, varied failure. Look at what they share: a table, a fleet, a time window |
| Count that stops growing between two reads | The fault ended, or the writer gave up. Compare against the request-line volume |

For HTTP 408 errors, Fleet normalizes socket addresses to `<addr>` before hashing. This groups request timeouts that differ only by connection address into one entry.

### Capture before you flush

Save a normal read before using `--flush`. Flushing deletes the Redis keys returned by that read, without an undo or retained copy. After preserving the evidence, a flush can establish a fresh window for reproduction.

Without `--stdout`, `fleetctl debug errors` writes to a generated filename of the form `fleet-errors-20260819140311Z.json` in the working directory and prints a warning that the file may contain sensitive data. Review before attaching it to anything. Collection for escalation is [8.13](8.13-escalation.md).

## 8.3.6 Error strings worth recognising

Most of the strings below are emitted verbatim and can be grepped for directly. Several are patterns with a placeholder in angle brackets, so grep the fixed part of those.

| String | What it means |
|---|---|
| `DEP auth error: 403 Forbidden: T_C_NOT_SIGNED` | Fleet's [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep) client could not authenticate to Apple Business Manager: the terms and conditions have not been accepted. An admin must sign in to ABM and accept. The required action is in Apple Business Manager |
| `DEP auth error: 403 Forbidden: signature_invalid` | The ABM server token is invalid or expired. Renew and re-upload the token. Fleet also matches this body on 401, so the status code alone does not identify the cause |
| `authentication error: missing node key` | An osquery request arrived with no node key. Check whether the agent has completed enrolment |
| `authentication error: invalid node key` | The node key does not match any host row. The host was deleted from Fleet, or the database was restored from a point before that host enrolled. Client error, so debug level only, and not in `fleetctl debug errors` |
| `authentication error: missing orbit node key` | An Orbit endpoint was called without a key |
| `authentication error: invalid orbit node key` | Orbit's key does not match. Same causes as the osquery case, different agent component |
| `authentication error: invalid authorization header` | Header-based osquery auth failed. Check what sits between the agent and Fleet |
| `authentication error: missing HTTP signature` | Host identity certificates are in play and the request was not signed |
| `authentication error: certificate serial number mismatch` | The signing certificate is not the one Fleet has recorded for that host |
| `authentication error: certificate matching HTTP message signature not found` | No stored host identity certificate matched the signature |
| `health check failed` with `component=healthz`, `health-checker=<name>`, `err=<cause>` | Warn level. This is what `/healthz` returning 500 looks like from inside. `health-checker` names the dependency, usually MySQL or Redis |
| `total runtime (<d>) exceeded schedule interval (<d>)` | Info level. A cron job took longer than its own interval. The scheduler is now behind. Cross-check `cron_stats` in [8.6](8.6-server-state.md) |
| `pending job might still be running, wait <d>` | Info level. A previous run of this schedule has not reported completion, so this node is deferring |
| `lock failed` | Error level. The node could not take the schedule's lock, which lives in **MySQL**, in the `locks` table, not in Redis. Losing a race for the lock is ordinary on a multi-node deployment and is not logged as a failure; this line means the lock attempt itself errored, which is a database-side failure rather than a lost race. Investigate the MySQL error attached to the attempt |
| `unlock failed` | Error level. A node finished a run and could not release the lock, so the schedule stays locked until the lock row's own expiry. Same reading: the write failed, so look at MySQL. Read it alongside `cron_stats` rows that never leave `pending` |
| `Request exceeds the max size limit of <size>` | The request body exceeded `server_default_max_request_body_size`. The client-facing text includes the configuration documentation link; the `internal` text adds the observed size |
| `logging.otel_logs_enabled requires logging.tracing_enabled to be true` | Startup refused. Fix the config pair |
| `orbit host with duplicate identifier has enrolled in Fleet and will overwrite existing host data`, with `identifier=` and `host_id=` | Warn level. Two machines are sharing one host record, or one machine lost its node key file and re-enrolled. Repeating on a schedule means two live hosts are stealing the record from each other. The osquery-channel twin of this message names `osquery.db`. Confirmed at 4.90.0 |
| `orbit host identity cert host id does not match enrolled host id. This is likely due to a duplicate UUID/identity identifier used by multiple hosts` | The same collision, but on a host with a TPM-backed identity certificate, where Fleet **refuses** the enroll instead of merging. Confirmed at 4.90.0 |
| `host identified by <osquery host id> enrolling too often` | The `osquery.enroll_cooldown` setting rejected a re-enroll. Default is 0, meaning disabled, so seeing this at all means someone set it. osquery channel only, never Orbit. Confirmed at 4.90.0 |
| `expected 4 builtin labels but got N` | One of the built-in labels `All Hosts`, `macOS`, `iOS`, `iPadOS` was deleted or renamed, so Apple hosts get **no** pre-osquery built-in label memberships. Fails open and silent apart from this line, one per enrollment. Anything scoped `macOS` include-any misses newly enrolled Macs. Confirmed at 4.90.0 |

Apple re-enrolment has a separate built-in-label failure in 4.90.0 that produces no log line: it clears memberships without restoring them. Label-scoped profiles, software, and OS updates can then stop reaching the host. Version 4.90.1 restores memberships during reset, marks labels as not yet reported for the exclude-any guard, and backfills affected hosts through a migration. Include the server version when investigating this symptom.

| Deprecation record | Interpretation |
|---|---|
| ``deprecated_path=<old path>`` with ``deprecation_warning=API `<old>` is deprecated, use `<new>` instead`` | Warn level on the default-enabled `deprecated-field-names` topic. A pre-rename path such as `/teams` is still routed to the same handler as `/fleets`. Preserve the backticks when searching for the literal message ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)) |
| `deprecation_warning='<old>' is deprecated, use '<new>' instead`, with no `deprecated_path` | A deprecated field or query parameter uses the same topic and level, with apostrophes around the names |

## 8.3.7 Startup messages that bypass the logger

These three database-state messages go directly to stdout:

| Message opening | Meaning |
|---|---|
| `Your Fleet database is not initialized. Fleet cannot start up.` | No migrations have run. Run `fleet prepare db`. The process exits |
| `Your Fleet database is missing required migrations.` | Partial migration state. Exits unless the override below is set. **Fleet's own message names the config key wrongly**, see the note under this table |
| `Your Fleet database has unrecognized migrations.` | An older Fleet binary against a database migrated by a newer one. Unlike the other two, this one does **not** stop a production server: Fleet prints the banner and carries on, and only refuses to start in dev mode. That is how a partially rolled-back deployment keeps serving from a schema its binary does not fully know |

Each message appears inside `#` banner lines as plain text, even with `logging_json` enabled. A structured-stderr collector may miss it. For an unexplained startup loop, read the raw container output as well.


The failed-startup message lists three migration overrides. Its configuration-file example contains a path typo:

```
- Set environment variable FLEET_UPGRADES_ALLOW_MISSING_MIGRATIONS=1, or,
- Set config updates.allow_missing_migrations to true, or,
- Use command line argument --upgrades_allow_missing_migrations=true
```

Use `upgrades` as the configuration section. The printed `updates` section is incorrect; the message's environment variable and command-line argument are correct.

Use that override only as a deliberate temporary decision. It allows startup with missing migrations and leaves the database unprepared; it does not replace `fleet prepare db`.

## 8.3.8 Where the logs land

| Deployment | Where server stderr goes | How to read it |
|---|---|---|
| systemd | journald, per the unit | `journalctl -u fleet.service -f` |
| Docker | Container stdout/stderr, per the configured logging driver | `docker logs -f <container>` |
| Kubernetes | Node container runtime, then whatever DaemonSet collector you run | `kubectl logs -f deploy/fleet` , add `--previous` after a crash loop, `-l app=fleet --max-log-requests=N` across replicas |
| ECS / Fargate | The task definition's log driver, normally `awslogs` to CloudWatch Logs | CloudWatch Logs Insights against the log group |
| Managed cloud | Not customer-accessible | Ask Fleet. `fleetctl debug errors` still works if you have an admin API token |

The systemd unit and `journalctl` invocation are from Fleet's reference architectures (fleetdm.com/docs/deploy/reference-architectures), which also sets `--logging_json` in the sample unit. The Docker, Kubernetes, and ECS rows are the standard behaviour of those platforms for a process that writes to stderr; Fleet does not document them.

> On managed cloud, arrange the verbosity change and restart with Fleet. Agree on a reproduction window so the extra logging is active when the failure occurs.

<a id="839-multi-instance-the-log-you-are-reading-may-be-the-healthy-node"></a>

## 8.3.9 Collect logs from every serving instance

Each Fleet process writes its own work to stderr. Fleet does not aggregate that output, so collect every relevant node when a fault may be isolated to one instance.

### Identifying the node

At startup each process logs:

```
level=info msg="instance info" instanceID=<base64>
```

The instance ID is generated from 64 random bytes and base64-encoded at each process start. It changes on restart and does not encode the hostname or pod name. Record the mapping for each node during the investigation.

### Where else that ID appears

| Surface | Field |
|---|---|
| Cron schedule log lines | `instanceID` attribute, alongside `schedule=<name>` |
| `cron_stats` table | `instance` column ([8.6](8.6-server-state.md)) |

Match `cron_stats.instance` with the log's `instanceID`. A pending row identifies the process that started the job. If no running process has that startup ID, the owning process is gone and the row is orphaned.

<a id="the-load-balancer-trap"></a>

### Follow requests through the load balancer

Each API call, MDM check-in, script-result upload, or distributed write reaches one node. Collect and configure logs with that routing in mind:

1. Search every node for the error response's `uuid` ([8.3.4](#834-the-per-request-line-and-the-level-it-needs)).
2. Enable debug on all possible serving nodes for the window, or pin the reproducing client to one node with debug enabled.
3. Collect forwarded filesystem or stdout logs from every node; the osquery streams are distributed across them ([8.2](8.2-log-surfaces.md)).

Recorded errors use shared Redis, so `fleetctl debug errors` provides a cluster-wide view regardless of the node answering the request. Use it to look for retained server faults across the deployment.

## 8.3.10 Questions that belong to another surface

| You want to know | Where it lives | Go to |
|---|---|---|
| Whether fleetd started, enrolled, or ran an install script on the host | Host-side agent logs. The host never reports them to the server | [8.4](8.4-host-side-investigation.md) |
| Why a macOS profile failed on the device | Device-side `mdmclient` behaviour | [8.4](8.4-host-side-investigation.md), [8.8](8.8-apple-mdm-diagnostics.md) |
| What rows a scheduled query returned | Forwarded result stream | [8.2](8.2-log-surfaces.md) |
| Whether osquery is healthy on a host | Forwarded status stream | [8.2](8.2-log-surfaces.md) |
| Who changed a fleet, policy, or configuration, and when | Audit log | [8.12](8.12-audit-logs.md) |
| Whether an operation succeeded | Fleet's state tables. Successful requests log at debug and carry no outcome semantics | [8.6](8.6-server-state.md) for the resulting state |

The operational log describes this server process's work. Use host logs for device behavior, audit records for administrative changes, and state tables for outcomes. A `uri=/api/v1/fleet/hosts/123` request line establishes that the request arrived.

## 8.3.11 Turning verbosity up for a reproduction, and back down

Allow for a restart when enabling debug and another when restoring the previous configuration.

**Enable collection:**

1. Set `FLEET_LOGGING_DEBUG=true` on **every** node, not one ([8.3.9](#839-collect-logs-from-every-serving-instance)).
2. Optionally set `FLEET_LOGGING_ERROR_RETENTION_PERIOD=0` so recorded errors do not expire out from under a long reproduction. Remember to put it back; `0` means never.
3. Restart. Note the new `instance info` line and the new instance IDs.
4. Run `fleetctl debug errors` and keep the output. That is your before-baseline.
5. Reproduce. Note the wall-clock time, and the `uuid` from any error response.
6. Capture: the log window from every node, plus a fresh `fleetctl debug errors`.

**Restore normal collection:**

1. Remove `FLEET_LOGGING_DEBUG` and the temporary retention override.
2. Restart the affected processes.
3. Confirm that ordinary agent request lines stop appearing on stderr. Login, logout, and deprecation records can remain at `info` or `warn`. Continued ordinary debug lines indicate that a node still has debug enabled. OTLP continues exporting those records independently of this setting ([8.3.2](#832-the-settings)).

Debug adds request records for successes and client errors, along with internal diagnostic messages. Agent request volume can make this a substantial increase.

If the reproduction can be pinned directly to one node, enable debug there to reduce collection volume. [8.11](8.11-reproducing-and-isolating.md) describes ways to narrow a reproduction.

## 8.3.12 Volume and retention at scale

Size collection for the selected output:

| Setting | Volume behaviour |
|---|---|
| `logging_debug=false` | Low and unpredictable. Not purely error-driven: logins, logouts, SSO initiation and every deprecated API call also emit a request line at this level |
| `logging_debug=true` | One record per API request per node. Agent check-in traffic dominates, so this scales with host count and check-in interval, not with user activity |
| `logging_otel_logs_enabled=true` | The collector receives every severity. Stderr independently applies its info or debug threshold, so records admitted by both are emitted to both. With `logging_tracing_type=elasticapm`, the OTLP exporter is never created |

Set stderr retention in journald, the Docker logging driver, CloudWatch, or your collector. Fleet continues writing independently of those systems' retention settings. Its own `logging_error_retention_period` applies to the Redis error store.

Monitor storage and ingestion costs during extended debug collection. If logging coincides with service degradation, use [8.14](8.14-degradation.md) to measure the performance effect.

## 8.3.13 The Fleet MCP server keeps its own log

The [Fleet MCP server](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) writes its own stderr log, at info by default or debug with `LOG_LEVEL=debug`. Fleet server logging settings do not control it. Under stdio transport, stdout is reserved for JSON-RPC, so collect diagnostics from the process's stderr using the same deployment approach as §8.3.8.

Start with MCP startup messages to establish its transport and authenticated Fleet identity. For an unexpected direct-proxy answer, repeat the [REST call](../06-automate-fleet/6.3-use-the-fleet-rest-api.md) and compare the result with the tool's field projection in [A.11](../09-appendices/a.11-mcp-tool-reference.md).

For a composed tool, inspect MCP warnings for dropped or capped components before replaying the requests. These tools may intersect filters, expand a CVE lookup, or gather reports and policies across fleets.

The CVE-impact tool's estate-count failure is silent: it substitutes zero for the total-systems denominator. Use A.11's count check for that result even when no warning appears.

| Log line, or its absence | Reading |
|---|---|
| `starting Fleet MCP server`, then a line naming the API-only Fleet user it verified | Normal start. `FLEET_API_KEY` was accepted and belongs to an API-only user |
| Refuses to start, its line naming a failed check on `FLEET_API_KEY` | Fleet was unreachable, or the token was rejected, or the token belongs to a UI user rather than an API-only one. It fails closed by design, so a server that is up has already passed this |
| Refuses to start over a missing or too-short `MCP_AUTH_TOKEN` | The token is required at startup on every transport and must be at least 32 bytes, even though stdio never checks it against a request ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)) |
| `transport: SSE` with a listening port, or `transport: stdio` | Which transport this process selected. A client configured for the other one will not connect, and any value but the literal `stdio` starts the SSE listener |
| Over SSE, a short plain-text 404 on any path but the MCP routes | A route guard, not a fault. Only the MCP protocol paths and the unauthenticated `/healthz` probe are served, so crawler and probe traffic never reaches the bearer layer |

The MCP `/healthz` probe checks process liveness. Pair it with an authenticated read to test Fleet reachability and current token validity ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)). The assistant path in [8.1](8.1-diagnostic-method.md) helps select the next stage to inspect.
