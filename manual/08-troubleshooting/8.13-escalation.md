# What to collect before escalating

One list, two directions.

| You are | Read this as |
|---|---|
| Opening a ticket or issue | Gather every row that applies, then file. The exceptions in 8.13.1 override this: file with what you have |
| Receiving a ticket | The intake questionnaire. Ask for the rows that are blank |

The device and MDM list (8.13.3) is adapted from Fleet's own `docs/Contributing/product-groups/mdm/mdm-bug-checklist.md`. The infrastructure list (8.13.4) has no equivalent in Fleet and is assembled here from the config reference and the deploy docs.

## 8.13.1 The gate: are you ready to escalate?

The standard to aim for is that you can name the failure class and the stage, from classes 0 through 6 in [8.1](8.1-diagnostic-method.md) §8.1.5, or that you have established you cannot observe the stage you need. The second is a complete answer, not a failure: "the queue row exists, the class is 3 or 4, and I have neither database nor host access" is a well-formed escalation.

It is a standard, not a gate. Escalate before you reach it when any of these hold, and say in the ticket what you had not yet inspected:

- Production is down or a security incident is suspected. Impact outranks tidiness.
- The evidence is perishable. Redis-backed errors age out, `cron_stats` gets trimmed, and log buffers roll. Getting help started in parallel with collection is cheaper than a complete ticket filed after the evidence has gone.
- You do not hold the access the next step needs, and obtaining it is a change request rather than a command.

Otherwise, the rows below are the ones to work through first, because each has an answer you can get faster than a support round trip can:

| Not yet | Do this first |
|---|---|
| "It isn't working" | Identify the channel. [8.1](8.1-diagnostic-method.md) §8.1.4 |
| One host, never reproduced | Try a second host in the same fleet. [8.11](8.11-reproducing-and-isolating.md) |
| Fleet's UI disagrees with the host | Check the host first. It is class 6 until a refetch fails to clear it, and then it is a real ingestion failure. [8.1](8.1-diagnostic-method.md) §8.1.5 |
| Slow, expensive, or self-interfering | Different procedure entirely. [8.14](8.14-degradation.md) |
| Cron output missing | Read `cron_stats` for the schedule. [8.6](8.6-server-state.md) §8.6.2 |

## 8.13.2 The header block, every ticket

Put these at the top regardless of what the problem turns out to be.

| Field | Example value |
|---|---|
| Fleet **server** version now reproducing it | 4.89.2 |
| Server version where first observed, and last known good | Observed 4.88.0; last good 4.87.1 |
| fleetd version on the affected hosts | 1.52 |
| Channel | MDM protocol (Apple) |
| Failure class and stage | Class 3, queued not delivered |
| Blast radius | One fleet, macOS 26.x only, 41 of 44 hosts |
| Operational impact | Rollout blocked; no production outage |
| Onset, and what changed near it | 2026-08-14, same day fleetd went 1.51 to 1.52 |
| Actual behaviour | Profile stays at Pending indefinitely; no error surfaces anywhere in the UI |
| Expected behaviour | Profile reaches Verified within a normal check-in interval |
| Steps to reproduce | Numbered, from a clean install |
| Reproduction status | Confirmed on multiple Fleet instances, **or** describes the workflow but not yet reproduced elsewhere |
| Ruled out | Live reports respond; `cron_stats` clean for `mdm_apple_profile_manager` |

**Actual and expected behaviour are separate fields for a reason, and the second is the one people skip.** Fleet's bug template asks for both, and where the two look identical to you the gap between them is exactly what the recipient cannot infer: a profile that never leaves Pending is a bug if you expected Verified and a support question if you expected it to wait for a device that is switched off. The reproduction status is a two-way checkbox in the template rather than a yes or no, and answering "describes the workflow but I have not reproduced it on a second instance" is a complete answer that changes who picks the ticket up. Source: `.github/ISSUE_TEMPLATE/bug-report.md`.

Blast radius and impact are different questions. Forty-one hosts is a number; whether those forty-one are a blocked pilot or a production outage is what decides how the ticket gets handled, and only you can supply it.

Add the `fleetctl` client version only when CLI behaviour is part of the problem. It is a separate thing from the server version, and putting it in the version field is a live source of confusion during exactly the upgrades where version matters most.

The two-version split (observed, reproduced) is what Fleet's own bug template asks for. Source: `.github/ISSUE_TEMPLATE/bug-report.md`.

| Android | Google account based | **No expected status established.** See below |

**The iOS and iPadOS rows are this manual's, not the checklist's.** Fleet's checklist discusses Apple hosts generally and even gives an iPad example, but its **enrollment-method item** covers macOS, Windows and Android and stops there, while the tagged console offers iOS and iPadOS a company-owned or personal choice on an enrollment URL, and the DEP sync assigns iPhones and iPads to their own fleets. So the rows are derived from the code and the console rather than quoted, and a recipient who cites the checklist will not find them.

**Google-account-based Android enrollment has no expected status in this manual.** Fleet's checklist names the method and supplies no status for it, and nothing at this tag establishes one. Record what Fleet actually shows for such a host and say that you did; do not reason from the two Android rows above, because those differ from each other and there is no basis for picking one.

**Account-driven user enrollment is iOS and iPadOS only** at this release. Fleet rejects a macOS attempt with "only iOS and iPadOS devices are supported for account driven user enrollment", so a macOS host described as account-driven was enrolled some other way, and establishing which is part of the intake.

A mismatch between the method the customer describes and the status Fleet shows is itself the finding. Record both.

## 8.13.4 Infrastructure intake list, self-hosted

**Assembled here, not official.** Fleet publishes no infrastructure intake checklist. Every setting name below is from `docs/Configuration/fleet-server-configuration.md`; the topology questions come from `docs/Deploy/Reference-Architectures.md`. Anything not traceable to those two is marked.

### Topology

| Ask | Why it changes the answer |
|---|---|

### MySQL

| Ask | Notes and setting names |
|---|---|
| Version and flavour | Minimum 8.0.44. Tested on 8.0.44, 8.4.8, 9.5.0. **9.6.0 is incompatible.** Drop-in replacements are not officially supported |
| Managed or self-run, and instance size | RDS Aurora MySQL is the AWS recommendation |
| Single writer? | Fleet supports one writable primary plus read replicas. **Multi-writer and group replication are not supported** |

| Replica connection lifetime | A non-zero `mysql_read_replica_conn_max_lifetime` is recommended where the replica address can change |
| Connection pool, per instance | `mysql_max_open_conns` (default 50), `mysql_max_idle_conns` (default 50), `mysql_conn_max_lifetime` (default 0, unlimited) |
| Database-side connection ceiling | `mysql_max_open_conns` must be below it, with headroom. AWS breakpoint table sets `FLEET_MYSQL_MAX_OPEN_CONNS` to 10 across 6 Fargate tasks at 5000 hosts |
| `max_prepared_stmt_count` on the server | Needs to be at least `FLEET_MYSQL_MAX_OPEN_CONNS * (number of Fleet servers) * 4` |

### Version and change history

| Ask | Notes |
|---|---|
| Exact Fleet **server** version now | `GET /api/v1/fleet/version` with any authenticated user, or the UI. **Not `fleetctl --version`**, which reports the version of the `fleetctl` binary on your own machine and never asks the server. ### How configuration reaches the server

| Ask | Notes |
|---|---|
| YAML file, environment variables, or command-line flags? | All three are supported. Flags can be piped in on stdin |
| Are app-level settings managed by GitOps? | `fleetctl gitops`. If yes, the next apply governs the fields GitOps actually sends. Fields it does not send or default are not reverted, so check which of the two you have ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)) |
| Who can change server config, and how fast? | Server config changes require a Fleet restart |
| Is the license key set? | `license_key`, and **three states are worth telling apart, because two of them look nothing like each other**. **No key at all** starts the server as Fleet Free. **An invalid key stops the server starting**, so a deployment that will not come up is a candidate. **An expired Premium key still loads as Premium**: the parser ignores expiry as the sole validation error and marks the licence expired rather than refusing it, so an expired key is not why a Premium feature is missing. Where a feature genuinely is unlicensed, Free behaves inconsistently: some paths refuse with an explicit licence error, as `fleetctl` does for Premium MDM operations, and others are silently ignored or forced off, which the source says in those words for the low-disk-space host filter and for software vulnerability detail. | Is `server_private_key` set, and how is it supplied? | Direct value, or `server_private_key_arn` plus region and STS settings. It encrypts material at rest, so a deployment that has lost or changed it will fail on the things that material feeds. **The precise failure surface was not verified**; treat a changed or missing key as a lead, not a diagnosis |

## 8.13.5 Artefacts to attach

Five items. Each links to the section that says how to get it.

| Artefact | Take it | Reference |
|---|---|---|
| `fleetctl debug archive` | Per node where the deployment has more than one, using a named `--context`. Check the member list before sending | [8.5](8.5-fleetctl-debug.md) §8.5.5 |
| `fleetctl debug errors` | **Before any `--flush`.** These live in Redis and expire; a flush destroys them. The archive already collects an `errors.json`, so a separate file is worth attaching when it captures an earlier window than the archive, or when the archive's copy failed | [8.5](8.5-fleetctl-debug.md) §8.5.6 |
| Host-side agent logs for the incident window | Orbit stdout/stderr, osquery logs, Fleet Desktop log, per platform | [8.2](8.2-log-surfaces.md) §8.2.2 to §8.2.5 |
| The relevant queue rows | `upcoming_activities`, or the `nano_*` and `host_mdm_*` tables for the item in question | [8.6](8.6-server-state.md) §8.6.4 to §8.6.6 |
| `cron_stats` rows for the schedule involved | Name, instance, `stats_type`, status, errors JSON, timestamps. The only record that a background job ran. No read API; database access required | [8.6](8.6-server-state.md) §8.6.2 |

Three notes that save a round trip:

- **`Failed <item>` means the archive is incomplete, and the archive is still written.** The collector takes thirteen items and continues past any that error, so a partial archive looks like a whole one. `Failed profile` is the common case and refers to the CPU profile item, not to a configuration profile. Read the `Failed` lines as you collect them and say in the ticket which members are absent and why, because the recipient cannot tell an item that failed from one that was never attempted.
- **The debug endpoints require a global administrator.** A team-scoped token is refused outright, so this is a prerequisite to arrange before the incident rather than during it.
- **Two of the three database members need a DB user with global `PROCESS` and `SELECT`.** Without them `db-locks` and `db-innodb-status` return a message saying so. `db-process-list` is the one to watch: it runs `SHOW PROCESSLIST`, which succeeds without the privilege and returns only your own connection's threads. It arrives looking like a healthy idle server rather than like an error. Say which case you are in.

## 8.13.6 Sensitive data

### Never in a public issue tracker

Serial numbers, UUIDs, and host IDs go on a private channel and are referenced from the public issue, not pasted into it. Fleet's own checklist says the same, naming a `fleetdm/confidential` issue or a private chat as the destination. Customer names go in code names, and private data is scrubbed. Source: `mdm-bug-checklist.md` item 3 and `.github/ISSUE_TEMPLATE/csa-task.md`.

### What can hide in an artefact

| Artefact | Can contain |
|---|---|
| `fleetctl debug archive` | `cmdline.prof` (server argv, highest risk), `db-process-list.json` and `db-innodb-status.json` (in-flight and recent SQL text), `errors.json`. Per-item breakdown: [8.5](8.5-fleetctl-debug.md) §8.5.13 |
| `fleetctl debug errors` | Internal hostnames, URLs, user identifiers, occasionally tokens embedded in a failing request |
| Orbit and osquery logs | Enroll secret paths and values in verbose modes, node keys, internal hostnames, usernames, installed software inventory |
| Queue and MDM table dumps | Serials, UUIDs, user emails, IdP identifiers, enrollment tokens |
| Fleet Desktop log | End-user identity and the device token |
| GitOps YAML or `fleetctl get config` | Enroll secrets, SMTP credentials, integration API tokens, SSO metadata |

### Redaction pass before anything leaves

1. `tar -tzf` the archive. Read the member list before sending it.
2. Read `cmdline.prof` in full, and render it first. The archive stores the server's command line raw, as the kernel holds it, with a NUL byte between each argument rather than a space. Many viewers stop at the first NUL and show you only the binary path, which reads as "nothing sensitive here" while the arguments that carry the risk sit unread behind it. Translate the separators before you review:

   ```sh
   tr '\0' '\n' < cmdline.prof
   ```
3. Search every attachment for the enroll secret string, any `Bearer` token, any `_KEY`, `_SECRET`, `_TOKEN`, `_PASSWORD` environment variable name, and the organisation's internal domain suffix.
4. Replace serials, UUIDs, and host IDs with stable placeholders (`HOST-A`, `HOST-B`) and keep the mapping on the private channel. Placeholders that stay consistent across attachments preserve the correlation you need.
5. If an enroll secret was in anything shared externally, rotate it. It is a credential.

> **Do not put customer-identifying information in the manual or a public issue; use your private support channel.**

## 8.13.7 Writing it up so it is useful

Say what you **ruled out**, not only what you saw, and say which channel each observation actually covers. A live report answers for the osquery distributed path and nothing else; it says nothing about the Orbit API or the MDM channel, and claiming otherwise ([8.7](8.7-live-query-introspection.md) §8.7.3) turns a narrow result into a wrong conclusion in the reader's mind and then in the ticket.

**Useful:**

> macOS configuration profile stuck at Pending on 41 of 44 hosts in one fleet, all macOS 26.2, since 2026-08-14. Rollout blocked; no production outage. Server 4.89.2, last good 4.87.1, fleetd 1.52. Channel is MDM protocol; classes 0 and 1 ruled out, the profile resolves to these hosts and Fleet shows the intent. Class 3: a `nano_enrollment_queue` row exists for each host with no result row in `nano_command_results` and no acknowledgement. `cron_stats` for `mdm_apple_profile_manager` shows completed runs with no errors through 2026-08-19, so the profiles were enqueued rather than never generated. The same hosts answer live reports within seconds, which shows the osquery distributed channel is healthy; the Orbit channel was not separately tested. The three unaffected hosts are the three on macOS 26.1. Attached: debug archive (all thirteen members present), `debug errors` (pre-flush), the queue rows, `cron_stats` rows. Not yet tried: a fresh test host on 26.2, and `apple_mdm_apns_pusher` stats to confirm the schedule is running at all.

Channel, class, stage, and the observation that supports each. Plus the bisection that separated 41 hosts from 3.

Note what the last sentence claims and what it does not. `cron_stats` for `apple_mdm_apns_pusher` establishes that the schedule ran, and **nothing about whether these particular hosts were woken**. When Apple rejects the push for some of the devices in a batch, Fleet logs the failure at info level and the job returns success, so the row you would read is green either way. Per-host delivery is a server-log question ([8.3](8.3-server-logs.md)), not a `cron_stats` question, and a ticket that says "the pusher ran, so the hosts were pushed" has drawn a conclusion the evidence does not carry.

**Useless:**

> Profiles aren't installing for a customer. They say it started last week. Can someone look?

No channel, no class, no scope, no artefacts, no ruled-out list. Every question in 8.13.3 still open.

Three habits that carry most of the value:

- Give timestamps with a timezone, and give a window rather than a moment.
- Give the counts. "41 of 44" is a lead; "some hosts" is not.
- Name the last thing that changed on both sides, Fleet version and fleetd version, even where you believe it is unrelated.

## 8.13.8 Where to file

**Pick the destination before you pick the template**, because the largest group of templates on the repository is not for you.

| You are | Go here first |
|---|---|
| Anything urgent, suspected-security, or customer-identifying | Your organisation's own incident or support path, whatever that is. Nothing in this table sends an outage or a security question to a public tracker |
| A Fleet customer with a support agreement | Your support channel rather than the public tracker. It can take the identifiers a public issue cannot; §8.13.6 covers the other private routes and what may travel on them |
| Self-hosting, or on Fleet Free, and you believe it is a **scrubbed, reproducible** defect | 🦟 Bug report on `fleetdm/fleet`. Public, permanent, and indexed: everything in §8.13.6 applies before you press submit |
| Self-hosting and it is a scaling or performance problem | 🔧 Reliability, which is a different intake, not a politer bug report |
| Not sure it is a bug | fleetdm.com/support or the documentation, both linked from the repository's own issue chooser. A question filed as a bug is slower than a question asked as a question |
| Asked to open something by a Fleet employee | Whatever they named. The ownership column below says which of the rest are yours to open unprompted |

The full inventory below **mixes templates that are yours to open with Fleet's internal product-work vocabulary**, which is why it carries an ownership column rather than a warning. The internal ones are listed so you can recognise what you are looking at when a maintainer converts your issue into one, or links you to one; opening a Story or a Sub-task yourself is not the path in.

| Template | For | Yours to open? |
|---|---|---|
| 🦟 Bug report | A bug. Asks for the discovered and reproduced Fleet versions, browser and OS, actual vs expected behaviour, and reproduction steps with a checkbox for whether they reproduce across multiple Fleet instances | Yes |
| 🔧 Reliability | Scaling, performance, and reliability issues, including post-mortem action items. This is the right home for [8.14](8.14-degradation.md) degradation cases | Yes |
| 💡 Feature request | A missing capability or a Fleet-maintained app request | Yes |
| ⚔️ CSA task | Asking a Customer Solutions Architect for research or solutioning help. Explicitly requires private data scrubbed and customer code names used | Only if you have a CSA |
| 🎟 Story | An iterative product change, written as a user story | Fleet's |
| 🧩 Sub-task | A technical piece of exactly one story | Fleet's |
| ✨ Quick win | Too small for a bug, worth doing anyway | Fleet's |
| ⏳ Timebox | Effort capped by a fixed amount of time | Fleet's |
| 🎸 Air guitar | Requesting wireframes | Fleet's |
| 🍽️ Dogfood | A dogfooding issue | Fleet's |
| 🕸️ Website request | fleetdm.com changes | Yes |
| 📝 Article | Proposing an article | Yes |
| Release QA / Release QA - fleetd | Pre-release test checklists, not for reporting problems | Fleet's |

Blank issues are disabled (`config.yml`, `blank_issues_enabled: false`), so there is no way to open an issue without choosing from that list. The same file is where the two non-issue destinations in the routing table come from.

Anything customer-identifying goes to the private channel, referenced from the public issue by number.
