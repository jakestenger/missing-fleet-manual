# Host-side investigation: agent state, Orbit, osquery

What you run on the machine, or hand to someone who has it. Fleet's UI shows what the server last heard. The host shows what is true now. When the two disagree the host settles it, and this section is how you get its answer.

## 8.4.1 Which question, which command

| Question | Run this | Section |
|---|---|---|
| Is the agent process alive? | `launchctl print system/com.fleetdm.orbit`, `Get-Service "Fleet osquery"`, `systemctl status orbit.service` | [8.4.2](#842-is-the-agent-running) |
| Did the agent ever enroll? | `ls -la /opt/orbit` and look for `secret-orbit-node-key.txt` | [8.4.3](#843-the-orbit-root-directory) |

## 8.4.2 Is the agent running?

fleetd is two processes under one supervisor. `orbit` is the supervisor and does enrollment, updates, scripts, and software installs. `osqueryd` is the child it launches. Orbit does not restart it in place: if osqueryd exits, Orbit exits too and the service manager brings the pair back ([8.4.2](#three-restarts-that-are-normal)). `fleet-desktop` is a third process, running in the logged-in user's session; the other two run with or without it.

| Platform | Managed by | Name |
|---|---|---|
| macOS | launchd system domain | `com.fleetdm.orbit`, plist at `/Library/LaunchDaemons/com.fleetdm.orbit.plist` |
| Windows | Service Control Manager | `Fleet osquery` |
| Linux | systemd | `orbit.service`, unit at `/usr/lib/systemd/system/orbit.service` |

Those names come from fleetd's own packaging templates, so every package `fleetctl` builds with a service uses them. **A package built with `--service=false` registers nothing with the service manager**, so everything in this section that looks for a daemon, a service or a unit finds nothing on such a host and finds nothing correctly. Establish which kind of package the host has before reading an absence as a fault.

### macOS

Orbit runs as a LaunchDaemon on an ordinary package, meaning a system-wide background service that launchd starts at boot, with no user logged in.

```sh
# Loaded? What's its PID and last exit status?
sudo launchctl print system/com.fleetdm.orbit

# Just the processes
ps -ef | grep -E 'orbit|osqueryd|fleet-desktop' | grep -v grep

# Stop, start, restart
sudo launchctl bootout system/com.fleetdm.orbit
sudo launchctl bootstrap system /Library/LaunchDaemons/com.fleetdm.orbit.plist
sudo launchctl kickstart -k system/com.fleetdm.orbit
```

Read three fields out of `launchctl print`. **`state`** should be `running`. **`last exit code`** non-zero on a daemon with `KeepAlive` true means a crash loop. **`pid`** changing every few seconds means the same thing. The plist throttles respawns to one every ten seconds, so a crash-looping Orbit comes back on that cadence rather than instantly.

`launchctl bootout` returning `Boot-out failed: 36: Operation now in progress` means the boot-out has been accepted and has not finished, so it is not a failure to retry. Whether it is *routine* is not something this manual can establish; what Fleet's own script does is wait for the process to go rather than treat the message as an error. Wait for `pgrep orbit` to come back empty before bootstrapping, which is exactly what Fleet's own toggle script does with `while pgrep orbit > /dev/null; do sleep 1 ; done`.

A missing plist is **consistent with** the agent having been uninstalled, and is not proof of it: `fleetctl package --service=false` builds a package that never writes the plist at all, and an incomplete or damaged install produces the same absence. Where it was an uninstall, Fleet's published script attempts to remove `/Library/LaunchDaemons/com.fleetdm.orbit.plist` along with `/opt/orbit`, `/var/lib/orbit`, `/usr/local/bin/orbit`, and `/var/log/orbit`. It does not check that each removal succeeded, so **a host with some of those paths still standing does not tell you who cleaned it up**: the script may simply have failed part way. Partial remnants date the host to after some cleanup attempt and say nothing about whose.

### Windows

```powershell
Get-Service -Name "Fleet osquery"
Get-CimInstance Win32_Service -Filter "Name='Fleet osquery'" | Format-List Name, State, StartMode, PathName

Stop-Service  -Name "Fleet osquery" -Force
Start-Service -Name "Fleet osquery"
Restart-Service -Name "Fleet osquery" -Force
```

`PathName` is the same `ImagePath` the debug toggle edits, so it also tells you which flags this install is running with, including whether `--debug` is on and which `--fleet-url` it was packaged against. The MSI writes those arguments at install time.

The service name and the registry path come from Fleet. The cmdlets are stock Windows.

### Linux

```sh
systemctl status orbit.service
systemctl is-enabled orbit.service
sudo systemctl restart orbit.service
sudo journalctl -u orbit -n 200 --no-pager
```

The unit sets `Restart=always`, `RestartSec=1`, and `CPUQuota=20%`. A restart count climbing in `systemctl status` is the Linux equivalent of a launchd crash loop. Check the CPU quota before you conclude that osquery is "slow" on a busy Linux box: the whole control group is capped at 20 percent of one core.

### Three restarts that are normal

Before treating a restart as a fault, rule these out. Orbit runs every subsystem as one group, and **the first subsystem to stop tears down all the others**, which makes three restarts expected rather than suspicious.

**osquery exited, for any reason.** The group unwinds, Orbit exits, and the service manager restarts the bundle. A restart in Orbit's log is routinely osquery's doing rather than Orbit's, so read the osquery status log for the same timestamp before investigating Orbit.

**An update succeeded.** Orbit returns deliberately so the bundle comes back on the new binaries. Correlate with §8.4.12 to confirm which target moved.

**An agent option changed the osquery flags or a channel.** The same deliberate exit, so the change takes effect. If a restart lands shortly after a configuration apply, this is the likely cause and nothing is wrong.

What is left after those three is a genuine crash loop, and the useful next step is the log files in §8.4.10 rather than the service state you are already looking at.

**Fleet Desktop is supervised differently and its restarts mean something else.** Orbit supervises it rather than the operating system, because it runs as the logged-in user. Orbit retries while no desktop session exists and restarts it if it disappears once running, so repeated Desktop starts on a host with no one logged in are the wait loop working, not a fault.

## 8.4.3 The Orbit root directory

| Platform | Orbit root |
|---|---|
| macOS | `/opt/orbit` |
| Linux | `/opt/orbit`. `/var/lib/orbit` is a symlink to it only on packages that bundled an Orbit older than `0.0.11`, so do not expect it on a recent host ([8.2](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory)) |
| Windows | `C:\Program Files\Orbit`, or `%ProgramFiles%\Orbit` if that variable is set |

Windows reads that path from the `ProgramFiles` environment variable at startup, so on a non-standard install drive the Orbit root moves with it.

The full inventory of the directory is [8.2.7](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory). These are the entries that answer a diagnostic question on their own.

| Entry | Present means | Absent is consistent with |
|---|---|---|
| `secret-orbit-node-key.txt` | Orbit completed orbit-enroll and holds a [node key](../09-appendices/a.6-glossary-and-release-compatibility.md#node-key) | Enrollment never completed **or** the key was cleared. Orbit clears it deliberately, along with the Desktop identifier, the osquery database and its stored hardware UUID, when it detects the agent directory has moved to different hardware, though **that detection is macOS-only in this release** ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)), so on Windows and Linux a migrated directory keeps its key rather than losing it. Absence is strong evidence, not proof |
| `secret.txt` | An enroll secret on disk, **on macOS and Windows only**. Usually the one the package was built with, though a `--use-system-configuration` host writes the same file at runtime once it reads its profile, so presence identifies neither the package type nor the host's health. The Linux packages set `ORBIT_ENROLL_SECRET` in `/etc/default/orbit` instead and never create this file | Absence alone means very little. On macOS Orbit moves a packaged secret into the Keychain on first launch and deletes the file. A `--use-system-configuration` package starts without one and **writes both `secret.txt` and `fleet_url.txt` once its configuration profile arrives**, so absence there dates the host to before the profile rather than condemning the package. On Linux, look in `/etc/default/orbit` |
| `identifier` | Fleet Desktop's auth token, rotated by Orbit even when Desktop is off | Orbit has not reached the point of provisioning a token |
| `osquery.db/` | osquery's local store, an embedded RocksDB database: differential state, event buffers, results pending upload | osqueryd has never started here, **or** the database path was relocated with `--osquery-db` at package time |
| `osquery.flags` | The flag file Orbit reconciles from `command_line_flags` in agent options | Little on its own. Packages create it empty and clearing `command_line_flags` empties it again, so both an absent and an empty file are ordinary. Read the flags in effect instead ([8.4.6](#846-osquery-introspection-tables)) |
| `certs.pem` | The CA root bundle fleetd hands osquery via `--tls_server_certs`, embedded in `fleetctl` at package time | `orbit shell` will refuse to start. See [8.4.7](#847-orbit-shell-the-local-osquery-shell) |
| `fleet.pem` | The custom Fleet server CA, present only on packages built with `--fleet-certificate` | Nothing, on a deployment using a publicly trusted certificate |
| `server-overrides.json` | Update-channel overrides the server pushed down, and last-known-good binary paths | Nothing is being overridden. Fleet writes it when the server's channels differ from the package's, so a host taking config normally can still have no file |
| `bin/orbit/<os>/<channel>/orbit` | The Orbit binary for the configured channel | |
| `bin/osqueryd/<platform>/<channel>/<file>` | The osqueryd binary actually installed, versus what agent options claim. **The generic form above exists on no host**: both the platform token and the filename vary by platform and architecture, and [8.2.7](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory) enumerates them | |
| `bin/desktop/…` | Fleet Desktop was included in the package | Package was built without `--fleet-desktop` |

Fleet documents `certs.pem` at fleetdm.com/guides/certificates-in-fleetd: the bundle is generated from curl's `cacert.pem`, embedded in the `fleetctl` binary, and written into the Orbit root by `fleetctl package`.

There is no `cert.pem`. `certs.pem` (the CA root store) and `fleet.pem` (your server's CA, on custom-certificate deployments) are different files with different jobs, and mixing up the names costs an afternoon.

```sh
# macOS / Linux
sudo ls -la /opt/orbit /opt/orbit/bin/orbit /opt/orbit/bin/osqueryd
sudo cat /opt/orbit/server-overrides.json
sudo orbit version
```

```powershell
Get-ChildItem 'C:\Program Files\Orbit' -Force
Get-ChildItem 'C:\Program Files\Orbit\bin' -Recurse -Depth 3
```

`orbit version` is a real subcommand. Prefer the `orbit_info` table for the same answer remotely ([8.4.6](#846-osquery-introspection-tables)).

**An Orbit root that exists but holds only `certs.pem` and `bin/`** is consistent with a package that installed and then failed to enroll, and it is not proof of that. Every platform's package builder writes `osquery.flags` regardless of whether enrollment ever happened, so a root missing it is as likely to be an incomplete install, a damaged directory, or something having removed files afterwards. Take the shape as a reason to read the log, not as the answer. Read `/var/log/orbit/orbit.stderr.log` next ([8.2.2](8.2-log-surfaces.md#822-fleetd-orbit-stdout-and-stderr)). **No Orbit root at all** on a host Fleet shows as MDM-enrolled is [8.4.5](#845-the-half-enrolled-state-mdm-without-an-agent).

## 8.4.4 macOS MDM truth from the host

```sh
sudo profiles status -type enrollment
```

The output is short, and these are the fields worth reading. The exact shape varies with macOS version, so treat the table as what to look for rather than as a line count:

| Line | Values you care about |
|---|---|
| `Enrolled via DEP:` | `Yes` means the device came through Automated Device Enrollment ([ADE](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep)), which Apple's older API and this command still call [DEP](../09-appendices/a.6-glossary-and-release-compatibility.md#ade-and-dep). `No` means manual or user enrollment, whatever Fleet's UI says about it. |
| `MDM enrollment:` | `Yes (User Approved)` is a fully functional enrollment. `Yes` without `(User Approved)` cannot install certain payload types. `No` means not enrolled at all. |
| `MDM server:` | The check-in URL. Confirms *which* MDM owns this device, which is the whole question during a migration. |

Fleet's own uninstall script branches on this output, grepping for `MDM enrollment: Yes` and `MDM enrollment: No`. fleetd uses the sibling command `profiles show -type enrollment` to read the assigned enrollment profile during an MDM migration, and it runs that one as the console user:

```sh
launchctl asuser $(id -u $(stat -f "%u" /dev/console)) profiles show -type enrollment
```

`profiles show` behaves differently outside a user session, which is the reason to prefer `profiles status` here. Whether `profiles status` is genuinely session-independent on every macOS version is **not established** by anything in Fleet's source; it is what this manual has seen and it matches how Fleet's own notes use it. No Fleet-facing documentation mentions the command.

**The rest of the `profiles` family:**

```sh
# Which enrollment profile is this device assigned in ABM, and from which server
sudo profiles show -type enrollment

# Every installed configuration payload, with identifiers
sudo profiles show -type configuration

# Terse listing
sudo profiles list -all

# Force the device to re-fetch its assigned enrollment profile from Apple
sudo profiles renew -type enrollment

# Remove Fleet's enrollment profile (this un-enrolls the device)
sudo profiles remove -identifier com.fleetdm.fleet.mdm.apple
```

Fleet's internal MDM troubleshooting notes use `profiles show -type configuration` and `profiles renew -type enrollment`, and the `com.fleetdm.fleet.mdm.apple` identifier comes from its uninstall script. `profiles list -all` is stock macOS, with no Fleet documentation behind the flag.

**UI equivalent, and it moves between macOS versions:** System Settings > General > Device Management shows the enrollment profile and every installed payload with its source. Use it when you are on a call with an end user who should not be asked to open Terminal. It carries most of the same facts, and it is not a substitute for the command: the DEP and user-approved distinctions are not presented there, and what else the pane shows moves between macOS versions.

**Remotely, without shell.** The `mdm` osquery table carries most of the same fields and can be pulled with a live report:

```sql
SELECT enrolled, server_url, installed_from_dep, user_approved, dep_capable,
       payload_identifier, install_date, has_scep_payload, topic
FROM mdm;
```

macOS only. Interpreting what the MDM channel then does with that enrollment is [8.8](8.8-apple-mdm-diagnostics.md).

## 8.4.5 The half-enrolled state: MDM without an agent

**Presentation:** Fleet shows **MDM status: On**, often `(company-owned)`. The host never reports. No Fleet Desktop menu bar icon.

**MDM commands should still complete.** The MDM channel is the operating system's and owes nothing to fleetd, so a host in this state acknowledges commands normally, and that healthy acknowledgement is exactly what makes it look fine. If commands *are* piling up unacknowledged, you are looking at two faults rather than one: a missing agent, and a separate channel 5 failure that the missing agent does not explain ([8.8](8.8-apple-mdm-diagnostics.md)).

**What is actually true:** the device is MDM-enrolled and fleetd was never installed, or was installed and removed. Fleet's MDM status reflects *enrollment*, not current channel health, so it reads green regardless of whether the MDM channel is still working.

**That last distinction decides the remedy, so establish it before acting.** A half-enrolled host with a working MDM channel acknowledges commands normally and only agent-dependent work is missing. A host whose MDM commands are also piling up unacknowledged has a second problem, and on that one an MDM-delivered reinstall will not arrive either. Check `nano_enrollments.last_seen_at` and whether recent commands are getting results ([8.8.3](8.8-apple-mdm-diagnostics.md#883-is-this-command-queued-delivered-or-answered)) before choosing between the two.

**Confirm it on the host.** The first command says enrolled, the other two say the agent is not there:

```sh
sudo profiles status -type enrollment    # MDM enrollment: Yes, MDM server: your Fleet
sudo ls -la /opt/orbit                   # missing, or present with no node key
sudo launchctl print system/com.fleetdm.orbit   # "Could not find service"
```

Enrolled plus no Orbit root equals half-enrolled. Enrolled plus an Orbit root plus an unloaded LaunchDaemon is the same failure caught slightly later.

**One cause, on any macOS MDM path:** the `InstallEnterpriseApplication` MDM command that delivers the fleetd package fails, and nothing retries it. Fleet sends that command after **manual** enrollment as well as after ADE, so a link-enrolled Mac reaches this state the same way; only ADE has an opt-out, `setup_experience.macos_manual_agent_install`, which is Fleet Premium and requires a bootstrap package to be configured before Fleet will accept it ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)). Nothing at this release establishes how this ranks against the other causes, so do not go looking for it first on the strength of this section. A host that enrolled and later had its agent removed, by an uninstall, an imaging step or another management tool, presents identically, and this section covers both. Tracked as [`fleetdm/fleet#47793`](https://github.com/fleetdm/fleet/issues/47793). The issue number and its state are not recorded anywhere in the 4.90.1 source, so check it rather than relying on this sentence. The proposed fix is delivering the agent over declarative device management instead of a one-shot MDM command.

**How often:** that issue records one deployment seeing 20 to 30 machines in 1,000 miss fleetd this way. It is a single estate's observation in a public issue rather than a measured rate across deployments, so treat it as evidence that the failure is common enough to plan for and not as a number to forecast against. The practical consequence holds either way: audit for it after a bulk enrollment rather than meeting each instance as a novel incident. [8.1](8.1-diagnostic-method.md#the-half-enrolled-state) carries the same figure with the same caveat.

**Recovery: reinstall the agent.** Where the MDM channel is healthy the enrollment is fine and needs no attention, and wiping the device fixes the symptom by accident at the cost of a day of someone's time. Where the MDM channel is also stalled, fix that first, because the reinstall has to travel over it unless you have another delivery path.

```sh
fleetctl package --type=pkg \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --fleet-desktop \
  --enable-scripts
```

Then install the resulting `.pkg` on the device by whatever channel you have: hand-delivery, an MDM command over the enrollment that is working, or another management tool. **Not Fleet's own software installer**, which is executed by a runner inside Orbit and needs its osquery connection: on a host with no agent there is nothing to run it.

**Detecting it fleet-wide.** Query Fleet's server for hosts that are MDM-enrolled and have no osquery check-in, rather than walking hosts one at a time. That is a server-side question: [8.6](8.6-server-state.md#8672-half-enrolled-hosts-mdm-live-agent-stale) carries the query.

> **Queue depth that only grows is the tell**, and "MDM status is shown as On" is the misleading signal: the status says nothing about whether commands are moving. It is easy to lose days here before separating the channels; one such investigation was resolved by re-enrollment, which was more than the problem needed.

## 8.4.6 osquery introspection tables

Run these **against the running agent**, as a live report or from the host details page. `orbit shell` is not a substitute here: it starts a separate osquery with a default configuration and its own database, so its `osquery_flags`, `osquery_schedule`, `osquery_info.start_time` and logs describe the shell, not the service you are diagnosing. In interactive mode it registers a stand-in `orbit_info` row that tells you to connect to the running extension instead, and a single-query invocation does not start the extension runner at all ([8.4.7](#847-orbit-shell-the-local-osquery-shell)).

Every table below is in Fleet's published table schema (fleetdm.com/tables) and available on macOS, Windows, and Linux unless noted.

### Which agent is this, and is its config valid

```sql
SELECT i.pid, i.version, i.uuid, i.instance_id, i.config_hash, i.config_valid,
       i.build_platform, i.start_time, i.watcher,
       o.version    AS orbit_version,
       o.enrolled   AS orbit_enrolled,
       o.orbit_channel, o.osqueryd_channel, o.desktop_channel,
       o.scripts_enabled, o.update_url, o.last_recorded_error
FROM osquery_info i, orbit_info o;
```

`config_valid = 0` means osquery rejected the config Fleet served it and is running on whatever it had before. That single column explains a large share of "my agent options did nothing". `orbit_info.last_recorded_error` is Orbit's most recent error string, which is often enough to skip the log file entirely.

`osquery_info.start_time` is a Unix timestamp. Compare it against `time` to get uptime without arithmetic in your head:

```sql
SELECT (SELECT unix_time FROM time) - start_time AS osquery_uptime_seconds
FROM osquery_info;
```

An uptime that resets every few minutes is worth investigating, after ruling out the three normal restarts in §8.4.2, since an agent options change or a successful update restarts the bundle deliberately. What is left is usually a watchdog kill or a crash loop. The reason lands in the osquery status log ([8.2.4](8.2-log-surfaces.md#824-osquery-result-and-status-logs)), never in the result log.

`orbit_info` carries its own `uptime` column, in seconds, and reading both at once separates the two processes:

```sql
SELECT o.uptime AS orbit_uptime_seconds,
       (SELECT unix_time FROM time) - i.start_time AS osquery_uptime_seconds
FROM orbit_info o, osquery_info i;
```

**Orbit cannot restart osqueryd without restarting itself.** There is one osquery runner, its `Execute` returns when the process exits, the source says in as many words that it may not be restarted afterwards, and everything that would restart osqueryd, an agent options change included, triggers an Orbit restart instead. So the pair goes down and comes back together, which is §8.4.2's territory and usually the service manager doing it.

**A gap between the two is therefore not evidence that the supervisor restarted its child**, because it has no way to. What a gap does measure is how long Orbit spent before it got to starting osqueryd, and that can be substantial: `orbit_info.uptime` runs from early in Orbit's startup, and Orbit performs an update check and can retry resolving update targets for minutes before the osquery runner is created. So a difference on a freshly started host is ordinary, and it has no useful upper bound: resolving update targets retries **without a maximum attempt count**, once every five minutes, until it succeeds. A host that could not reach its update repository for an hour after boot spent that hour with Orbit up and osquery not yet started, and the gap is an hour.

That makes the size of the gap a poor diagnostic on its own. **Read Orbit's own log first**, where the update runner records what it was retrying; a large gap with retry entries behind it is explained, and a large gap with a quiet log is not. The remaining candidates for an unexplained one are another osqueryd started outside Orbit, or a clock the host does not agree with.

### Did the flag actually take

```sql
SELECT name, value, default_value, type
FROM osquery_flags
WHERE name IN ('disable_events','verbose','logger_plugin','logger_path',
               'config_refresh','distributed_interval','watchdog_memory_limit',
               'disable_watchdog','enable_file_events','enable_process_etw_events');
```

```sql
-- Everything you changed from stock, in one screen
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

This is the answer to "I set it in agent options and nothing happened." `command_line_flags` apply after fleetd restarts, and Orbit reconciles them into `<orbit root>/osquery.flags` first (fleetdm.com/docs/configuration/agent-configuration). **Compare the value, not the presence of the row:** the table lists osquery's registered flags with their current and default values, so a flag that has not taken yet is present with its old value rather than absent. A flag genuinely missing from the table is more likely a name osquery does not register at this version than a pending restart.

A revoked enroll secret can also stop flag updates, and the route is less direct than it sounds, which is worth knowing because it changes when the symptom appears. Orbit's ordinary config fetches, the ones that carry `command_line_flags`, authenticate with the **Orbit node key**, not the secret. The secret is used only to enrol and re-enrol. So flags keep flowing on a valid node key long after a secret is revoked, and stop at the point the host is forced to re-enrol and cannot, which is when authenticated requests have been failing with 401 for longer than Orbit's grace period. The gap between revoking and noticing can be long.

### Why a scheduled query produces nothing

```sql
SELECT name, interval, executions, last_executed,
       datetime(last_executed,'unixepoch') AS last_executed_utc,
       denylisted, output_size, average_memory, last_memory,
       wall_time_ms, last_wall_time_ms, system_time, user_time
FROM osquery_schedule
ORDER BY last_executed DESC;
```

| Column | Reads as |
|---|---|
| `denylisted = 1` | osquery's watchdog killed this query for resource use and stopped running it. Fleet's published schema says it stays denylisted until osquery restarts, so treat a restart as the reset rather than waiting for an expiry. |
| `executions = 0` | The query is in the config but has never run. Check `interval` against `osquery_info.start_time`. |
| `last_executed` far in the past | It ran once and stopped, or the schedule was replaced. |
| `average_memory` / `last_memory` high | The candidate for the next watchdog kill. |
| `output_size` large | The reason a result log destination is dropping records ([8.2.11](8.2-log-surfaces.md#8211-server-side-log-destinations)). |

A query missing from this table entirely has not reached this host's running config. Three things produce that, and nothing here establishes which is more common: the query never reached the host, the host is out of the query's scope, or the host has not fetched its configuration since the query changed (channel 2, [8.1](8.1-diagnostic-method.md#814-identify-the-channel-first)). All three are answered server-side ([8.6](8.6-server-state.md)).

### Evented tables

An evented table is filled by a background publisher as events occur, rather than by inspecting the system at the moment a query runs.

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

`active = 0` on everything means eventing is off, which is osquery's default. Fleet documents turning it on through agent options (fleetdm.com/guides/osquery-evented-tables-overview):

```yaml
command_line_flags:
  disable_events: false
```

`active = 1` with `events = 0` means the publisher is running and has emitted nothing **since osquery started**, which is what the counter measures. On a recently restarted host that is expected. Where it persists, the first thing it is consistent with is nothing having happened that the publisher matches, which is not a fault. Permissions and platform support are the other candidates and nothing at this release ranks them against each other. On macOS, `es_process_events` additionally needs `--disable_endpointsecurity=false`; on Windows, `process_etw_events` needs `--enable_process_etw_events=true`; YARA's `yara_events` needs `--enable_file_events=true`. All three are in that guide.

### fleetd's own logs, without a shell

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error','warn')
ORDER BY time DESC
LIMIT 100;
```

In-memory ring of 10,000 entries inside the Orbit process, emptied on every Orbit restart. Useless for a crash loop, excellent for a remote host you cannot shell into. Details and columns in [8.2.6](8.2-log-surfaces.md#826-reading-fleetds-own-logs-without-shell-access).

### Clock skew

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Run this before you spend an hour on "results arriving hours late." A host whose clock is wrong stamps its results wrong, and the timestamps in your SIEM will be exactly as wrong. The two-clocks comparison that uses this is in [8.1](8.1-diagnostic-method.md).

### Also useful

| Table | Answers |
|---|---|
| `osquery_extensions` | Whether Fleet's `fleetd_tables` extension is loaded. Missing extension means `orbit_info`, `fleetd_logs`, and the Fleet-added tables all return nothing. |
| `osquery_packs` | Which packs are active, and their discovery-query cache behavior |
| `osquery_registry` | Which tables, plugins, and loggers are registered and active in this instance |
| `managed_policies` | macOS: managed preference values as the OS reports them. Useful for confirming a setting landed, though it reports preferences rather than an inventory of installed profiles; `profiles show -type configuration` is the profile list |

## 8.4.7 `orbit shell`: the local osquery shell

```sh
sudo orbit shell
```

Opens `osqueryi` using the osqueryd binary this host already has, in an interactive shell. Aliased as `orbit osqueryi`.

**Fleet's own tables are not usable here the way you would expect.** In interactive mode the shell registers a placeholder `orbit_info` row whose contents tell you to connect to the running extension instead; it does not read the live agent's state. Reaching the real extension from the shell is undocumented at this release. Treat `orbit shell` as a way to test **osquery behaviour**, and read Fleet's tables through a live report against the running agent ([8.4.6](#846-osquery-introspection-tables)).

**The shell is a separate osquery, not the running agent.** It loads a standalone instance with a default config rather than the config Fleet serves, and it uses its own data path (`<orbit root>/shell`, with its own `osquery.db`), so it never contends with the daemon for the RocksDB lock. What it proves is osquery behaviour. Fleet's configuration of osquery stays a separate question, and Fleet's agent configuration reference draws the same line (fleetdm.com/docs/configuration/agent-configuration).

```sh
# Extra osquery flags go after a bare --
sudo orbit shell -- --verbose
sudo orbit shell -- --disable-events false

# A single query and exit: the last argument, with no leading --, is treated as SQL
sudo orbit shell -- "SELECT version FROM osquery_info;"

# Pin the osqueryd channel
sudo orbit shell --osqueryd-channel stable
```

The `--disable-events false` form is Fleet's documented way to test evented tables locally (fleetdm.com/guides/osquery-evented-tables-overview). **The shell is ephemeral, so you only see events gathered while it is open.** Open it, do the thing you want to catch, then query. An `osquery_events` row showing `events = 0` in a shell you opened five seconds ago proves nothing.

On argument handling: a trailing argument that does not start with `--` puts osquery in single-query mode. The extension runner starts in interactive mode alone, so a single-query invocation has no Fleet extension at all. Interactive mode starts one, but it serves the shell's own placeholder rather than the running agent's state, per the note above. Undocumented either way.

If `orbit shell` exits with `cert not found at <root>/certs.pem`, the CA bundle is missing from the Orbit root. Pass a path explicitly with `--fleet-certificate`, or treat it as a damaged install ([8.4.3](#843-the-orbit-root-directory)).

## 8.4.8 Raising verbosity on an installed host

The full lever table is [8.2.10](8.2-log-surfaces.md#8210-raising-verbosity-and-putting-it-back). On a host that is already installed, these three are what you reach for.

| Platform | Turn on | Turn off | Restart delay |
|---|---|---|---|
| macOS | `sudo ./toggle-fleetd-debug.sh enable` | `sudo ./toggle-fleetd-debug.sh disable` | 15 s, then bootout/bootstrap |
| Windows | `.\toggle-fleetd-debug.ps1` (toggles) | run it again | none, service restarts inline |
| Linux | `echo 'ORBIT_DEBUG=true' \| sudo tee -a /etc/default/orbit` then `sudo systemctl restart orbit.service` | `sudo sed -i '/^ORBIT_DEBUG=/d' /etc/default/orbit`, restart | none |

Fleet publishes both scripts in its repository, at `docs/solutions/macos/scripts/toggle-fleetd-debug.sh` and `docs/solutions/windows/scripts/toggle-fleetd-debug.ps1` (github.com/fleetdm/fleet/tree/fleet-v4.90.1/docs/solutions). Linux has no supplied script. Its systemd unit carries `EnvironmentFile=/etc/default/orbit`, and a package built with `--debug` writes `ORBIT_DEBUG=true` into that file, which is what the table above does by hand.

**Fleet's macOS script does nothing at all on an ordinary package**, which is worth knowing before you conclude the toggle failed. The LaunchDaemon plist carries an `ORBIT_DEBUG` key only when the package was built with `--debug`, and the script uses `PlistBuddy set`, which fails when there is no key to set. So the case where you most need a runtime toggle is the case the script cannot serve. Add the key rather than setting it, falling back to a set when it is already there:

```sh
plist=/Library/LaunchDaemons/com.fleetdm.orbit.plist
sudo /usr/libexec/PlistBuddy -c 'add EnvironmentVariables:ORBIT_DEBUG string true' "$plist" \
  || sudo /usr/libexec/PlistBuddy -c 'set EnvironmentVariables:ORBIT_DEBUG true' "$plist"
```

Then bootout and bootstrap the daemon as the script would. [8.2.10](8.2-log-surfaces.md#8210-raising-verbosity-and-putting-it-back) has the full discussion.

**The 15-second sleep in the macOS script is load-bearing.** The script forks a detached background job that sleeps 15 seconds before touching anything, because Orbit is the process running the script and is about to be killed. The delay lets the script's result reach Fleet first, so Fleet records the run as complete. The Windows script restarts the service inline with no such delay, so running it as a Fleet script means accepting that the result may be lost.

The background job on macOS writes to `/tmp/orbit_debug_script_logs.txt`. When a toggle appears not to have worked, read that file before anything else.

Confirm the current state without changing it:

```sh
# macOS
sudo /usr/libexec/PlistBuddy -c 'print EnvironmentVariables:ORBIT_DEBUG' \
  /Library/LaunchDaemons/com.fleetdm.orbit.plist
```

```powershell
# Windows: --debug present in ImagePath means debug is on
(Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Services\Fleet osquery' -Name ImagePath).ImagePath
```

```sh
# Linux
grep ORBIT_DEBUG /etc/default/orbit
```

macOS debug output goes to an unrotated file. Put the "off" step in the same ticket as the "on" step.

## 8.4.9 Diffing against a known-good host

The fastest way to shorten a host-side investigation is to run the same commands on a host that works, same platform, same team, same Fleet server. Diff these:

| Compare | Broken host | Known-good host | A difference means |
|---|---|---|---|
| `orbit_info.version` and `orbit_channel` | | | The broken host is pinned to, or stuck on, a different channel. Updates are failing. |
| `osquery_info.version` | | | Different osquery versions mean the two hosts are on different `osqueryd` channels, or one has not taken an update. Table behaviour and available columns can differ between versions, so a version gap can explain a query that works on one and not the other |
| `osquery_info.config_valid` | | | `0` on one side is the answer: that host rejected the config it was served. **Do not diff `config_hash`**: Fleet serves a per-host config, so two correct hosts on one fleet can differ legitimately ([8.7.1](8.7-live-query-introspection.md#871-the-query-library)) |
| `osquery_flags` where `value != default_value` | | | The broken host never got, or never restarted into, the current `command_line_flags` |
| `sudo profiles status -type enrollment` | | | Different `MDM server`, or DEP vs manual, or approved vs not |
| `sudo profiles show -type configuration` | | | A payload present on one and missing on the other localizes the failure to a specific profile |
| `ls -la /opt/orbit` | | | A missing **node key** on one side. Do **not** read anything into `secret.txt`, which is routinely absent on a healthy host for the reasons in §8.4.3 |
| `server-overrides.json` | | | The server is telling the two hosts different things |

Do it as one live report across both hosts rather than two shells, and the diff is in one result set:

```sh
fleetctl report --hosts "<broken-host>,<known-good-host>" --exit --query "
SELECT i.version AS osquery_version, i.config_valid,
       o.version AS orbit_version, o.orbit_channel, o.osqueryd_channel, o.enrolled
FROM osquery_info i, orbit_info o;
"
```

`config_hash` is deliberately not in that list. Fleet builds each host's configuration from its fleet, its platform and the packs its labels select, so two correct hosts can legitimately hash differently and a diff on it produces findings that mean nothing. Two hosts with identical selections do hash the same, which is why the mismatch tells you nothing either way.

Same platform matters. macOS and Windows differ in enough of these fields that a cross-platform diff generates noise instead of signal. Same team matters because agent options and profiles are assigned per team.

If both hosts look identical and one still fails, agent state is not the variable. The next candidates are the network path between host and server, and the server itself ([8.1](8.1-diagnostic-method.md)).

## 8.4.10 The log files you open first

Full inventory, per platform, with rotation and lifetimes: [8.2](8.2-log-surfaces.md). In practice you open these:

```sh
# macOS: enrollment failures, script runs, update failures. Almost always stderr.
sudo tail -n 500 /var/log/orbit/orbit.stderr.log

# Linux
sudo journalctl -u orbit -n 500 --no-pager

# macOS and Linux: osquery's own health, watchdog kills, flag parsing
sudo ls -la /opt/orbit/osquery_log/
sudo tail -n 200 /opt/orbit/osquery_log/osqueryd.INFO
```

```powershell
# Windows: Orbit's combined output
Get-Content -Tail 500 'C:\Windows\system32\config\systemprofile\AppData\Local\FleetDM\Orbit\Logs\orbit-osquery.log'

# Windows: osquery's own status logs live separately
Get-ChildItem 'C:\Program Files\Orbit\osquery_log'
Get-Content -Tail 200 'C:\Program Files\Orbit\osquery_log\osqueryd.INFO'
```

Collect the ephemeral surfaces **before** you restart anything. `fleetd_logs` is wiped by an Orbit restart and `fleet-desktop.err` is truncated on every Desktop start ([8.2.12](8.2-log-surfaces.md#8212-what-survives-and-for-how-long)).

## 8.4.11 What the host cannot tell you

| Question | Why the host cannot answer it | Where to go |
|---|---|---|
| Why did the server stop accepting this host's check-ins? | The rejection happens server-side. The host sees a failure, not a reason. | [8.6](8.6-server-state.md) |
| Which MDM commands are queued for this device, and how long have they been queued? | The queue lives in Fleet's database. The device only sees commands it has been handed. | [8.6](8.6-server-state.md) |
| What did Fleet intend this host's profiles or software to be? | Desired state is server-side. The host holds actual state only. | [8.6](8.6-server-state.md) |
| Is this problem specific to this host, or fleet-wide? | One host is a sample of one | [8.6](8.6-server-state.md), [8.7](8.7-live-query-introspection.md) |
| How did the agent get removed, and by whom? | **There is no host-side event history.** Fleet's audit log records server-side actions only, so an agent removed by a local admin, another management tool, or a user leaves no trace Fleet can show you. | [8.12](8.12-audit-logs.md) for what the audit log does cover |
| Did the query results Fleet received match what the host produced? | Requires both ends | [8.1](8.1-diagnostic-method.md), two-clocks comparison |

The agent-removal gap is a real limit and customers hit it. Say so plainly rather than searching the audit log for an event that was never written. Host-side attribution has to come from the platform's own audit facility: the macOS unified log, the Windows Event Log, or Linux auditd.

## 8.4.12 Agent updates: which channel landed, and why it did not

Orbit updates the whole bundle from a signed update repository of its own, built on The Update Framework (TUF), rather than through the Fleet server. So an update problem leaves no server-side trace beyond a version that will not move, and the narrowing question is **what is on disk versus what was asked for.**

Ask for it first. Channel names come from Orbit's own extension table, so this works as a live report against a host you cannot reach ([8.4.6](#846-osquery-introspection-tables)):

```sql
SELECT version, orbit_channel, osqueryd_channel, desktop_channel,
       update_url, last_recorded_error
FROM orbit_info;
```

Then look at what landed. Binaries live at `<orbit root>/bin/<target>/<platform>/<channel>/<file>`, so a channel change is visible as a new directory:

| Target | Platform string | File on disk | Executable inside |
|---|---|---|---|
| `orbit` | `macos`, `linux`, `linux-arm64`, `windows`, `windows-arm64` | `orbit`, `orbit.exe` | n/a |
| `osqueryd` | `macos-app` | `osqueryd.app.tar.gz` | `osquery.app/Contents/MacOS/osqueryd` |
| `osqueryd` | `linux`, `linux-arm64` | `osqueryd` | n/a |
| `osqueryd` | `windows`, `windows-arm64` | `osqueryd.exe` | n/a |
| `desktop` | `macos` | `desktop.app.tar.gz` | `Fleet Desktop.app/Contents/MacOS/fleet-desktop` |
| `desktop` | `windows`, `windows-arm64` | `fleet-desktop.exe` | n/a |
| `desktop` | `linux`, `linux-arm64` | `desktop.tar.gz` | `fleet-desktop/fleet-desktop` |

```sh
sudo ls -la /opt/orbit/bin/orbit/*/ /opt/orbit/bin/osqueryd/*/
sudo /opt/orbit/bin/osqueryd/macos-app/stable/osquery.app/Contents/MacOS/osqueryd --version
```

Three states, each pointing somewhere different:

| On disk | Reads as | Next look |
|---|---|---|
| Requested channel directory **absent** | The channel does not exist in the repository, or the download has not succeeded yet | Grep the Orbit log for `tuf: file not found` (nonexistent channel) or `max retries exceeded, retrying again in` (in cooldown, below) |
| Directory **present**, old version still running | The update landed and the restart did not happen, or is failing | Look for `exiting due to successful update` followed by a start. Absent, the restart never fired |
| Both present, version **flapping** | Downgrade loop. Orbit below 1.20.0 packaged on one channel, with `update_channels` pointing at a channel holding a different side of that boundary | Move one of the two channels across 1.20.0 in the same direction |

**The cooldown is the reason a retry does nothing.** A failed target download gets 3 attempts, then a **24 hour cooldown for that target**. The retry key is the target's content hash, so publishing a new version resets it immediately.

**Restarting Orbit also clears it.** The retry counts and cooldown timestamps live in maps held by the updater in memory, and a new Orbit process builds a new updater with empty ones. Nothing about the cooldown is written to disk. So restarting the agent is a legitimate way to force a stuck update to try again, and it is worth trying before waiting out a day.

The startup fetch loop retries every 5 minutes, but that interval exists to keep the logs readable rather than to bypass anything: each attempt still goes through the updater, so the per-target cooldown continues to apply within a single process.

**A corrupt download self-heals.** Orbit health-checks an installed binary by running it (`<binary> --help`, or a target-specific check). On failure it deletes the extracted directory, the archive, and the cached `.sha512`, logs `removed corrupt target for re-download`, and fetches it again. When this happens during the startup pass the refetch and recheck happen immediately, in the same pass, so a truncated download does not necessarily cost an update interval.

**Two version floors that look like a broken update server.** Orbit below **1.38.1** cannot upgrade past the move from `tuf.fleetctl.com` to `updates.fleetdm.com` and logs `update failed error="lookup failed: lookup orbit: tuf: file not found`. Fleet's own configuration reference names 1.38.1 as the bridge, so get a host **to 1.38.1 specifically**, wait for it to land, then upgrade to the version you actually want. Pointing a stranded host straight at a current release leaves it stranded rather than failing loudly ([3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md)). The other floor is 1.20.0, which is where per-target update channels became configurable from agent options at all: a host on an older Orbit ignores `update_channels`, so a channel you set and a channel it runs can differ with nothing logged.

**Expired TUF signatures block startup by role.** Expired `root`, `targets`, or `snapshot` roles stop targets loading; Orbit then rechecks expiry each interval and exits once they are valid so the next start initialises normally. An expired `timestamp` role does not block startup.

### Forcing an update check

The check runs at startup, before any other subsystem, so restarting the service is the fastest trigger ([8.4.2](#842-is-the-agent-running)). To shrink an update problem to a minimal case on one host, shorten `--update-interval` and turn on `--debug` ([8.4.8](#848-raising-verbosity-on-an-installed-host)), then watch the `hash(<target>)=` lines against what the TUF metadata advertises. The first periodic check after startup adds a random offset of up to `min(interval, 10 minutes)`, so an idle-looking first window is expected rather than a stall.

Channel and update behaviour as designed, including the `update_channels` precedence rules, is in [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md). Note that **setting `update_channels` in agent options at all is Fleet Premium**: its own validation rejects the key without a licence. That gates the *central* route only. On Free a host's channels can still be changed on the host itself, through Orbit's flags and environment variables, which is a per-host operation rather than a fleet-wide one ([3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md)).
