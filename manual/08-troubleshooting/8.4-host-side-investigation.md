# Host-side investigation: agent state, Orbit, osquery

What you run on the machine, or hand to someone who has it. Fleet's UI shows what the server last heard. The host shows what is true now. When the two disagree the host settles it, and this section is how you get its answer.

## 8.4.2 Is the agent running?

fleetd is two processes under one supervisor. `orbit` is the supervisor and does enrollment, updates, scripts, and software installs. `osqueryd` is the child it launches and restarts. `fleet-desktop` is a third process, running in the logged-in user's session; the other two run with or without it.

| Platform | Managed by | Name |
|---|---|---|
| macOS | launchd system domain | `com.fleetdm.orbit`, plist at `/Library/LaunchDaemons/com.fleetdm.orbit.plist` |
| Windows | Service Control Manager | `Fleet osquery` |
| Linux | systemd | `orbit.service`, unit at `/usr/lib/systemd/system/orbit.service` |

Those names come from fleetd's own packaging templates, so every package `fleetctl` builds uses them.

### macOS

Orbit runs as a LaunchDaemon, meaning a system-wide background service that launchd starts at boot, with no user logged in.

```sh
# Loaded? What's its PID and last exit status?
sudo launchctl print system/com.fleetdm.orbit

# Just the processes
ps -ef | grep -E 'orbit|osqueryd|fleet-desktop' | grep -v grep

# Stop, start, restart
sudo launchctl bootout system/com.fleetdm.orbit
sudo launchctl bootstrap system /Library/LaunchDaemons/com.fleetdm.orbit.plist
sudo launchctl kickstart -k system/com.fleetdm.orbit
```

Read three fields out of `launchctl print`. **`state`** should be `running`. **`last exit code`** non-zero on a daemon with `KeepAlive` true means a crash loop. **`pid`** changing every few seconds means the same thing. The plist throttles respawns to one every ten seconds, so a crash-looping Orbit comes back on that cadence rather than instantly.

`launchctl bootout` returning `Boot-out failed: 36: Operation now in progress` is normal on a busy daemon. Wait for `pgrep orbit` to come back empty before bootstrapping, which is exactly what Fleet's own toggle script does with `while pgrep orbit > /dev/null; do sleep 1 ; done`.

A missing plist means the agent was uninstalled. Fleet's published uninstall script removes `/Library/LaunchDaemons/com.fleetdm.orbit.plist` along with `/opt/orbit`, `/var/lib/orbit`, `/usr/local/bin/orbit`, and `/var/log/orbit`. A host with some of those paths still standing was cleaned up by something other than that script.

### Windows

```powershell
Get-Service -Name "Fleet osquery"
Get-CimInstance Win32_Service -Filter "Name='Fleet osquery'" | Format-List Name, State, StartMode, PathName

Stop-Service  -Name "Fleet osquery" -Force
Start-Service -Name "Fleet osquery"
Restart-Service -Name "Fleet osquery" -Force
```

`PathName` is the same `ImagePath` the debug toggle edits, so it also tells you which flags this install is running with, including whether `--debug` is on and which `--fleet-url` it was packaged against. The MSI writes those arguments at install time.

The service name and the registry path come from Fleet. The cmdlets are stock Windows.

### Linux

```sh
systemctl status orbit.service
systemctl is-enabled orbit.service
sudo systemctl restart orbit.service
sudo journalctl -u orbit -n 200 --no-pager
```

The unit sets `Restart=always`, `RestartSec=1`, and `CPUQuota=20%`. A restart count climbing in `systemctl status` is the Linux equivalent of a launchd crash loop. Check the CPU quota before you conclude that osquery is "slow" on a busy Linux box: the whole control group is capped at 20 percent of one core.

### Three restarts that are normal

Before treating a restart as a fault, rule these out. Orbit runs every subsystem as one group, and **the first subsystem to stop tears down all the others**, which makes three restarts expected rather than suspicious.

**osquery exited, for any reason.** The group unwinds, Orbit exits, and the service manager restarts the bundle. A restart in Orbit's log is routinely osquery's doing rather than Orbit's, so read the osquery status log for the same timestamp before investigating Orbit.

**An update succeeded.** Orbit returns deliberately so the bundle comes back on the new binaries. Correlate with §8.4.12 to confirm which target moved.

**An agent option changed the osquery flags or a channel.** The same deliberate exit, so the change takes effect. If a restart lands shortly after a configuration apply, this is the likely cause and nothing is wrong.

What is left after those three is a genuine crash loop, and the useful next step is the log files in §8.4.10 rather than the service state you are already looking at.

**Fleet Desktop is supervised differently and its restarts mean something else.** Orbit supervises it rather than the operating system, because it runs as the logged-in user. Orbit retries while no desktop session exists and restarts it if it disappears once running, so repeated Desktop starts on a host with no one logged in are the wait loop working, not a fault.

## 8.4.3 The Orbit root directory

| Platform | Orbit root |
|---|---|
| macOS | `/opt/orbit` |
| Linux | `/opt/orbit`, with `/var/lib/orbit` a compatibility symlink to it |
| Windows | `C:\Program Files\Orbit`, or `%ProgramFiles%\Orbit` if that variable is set |

Windows reads that path from the `ProgramFiles` environment variable at startup, so on a non-standard install drive the Orbit root moves with it.

The full inventory of the directory is [8.2.7](8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory). These are the entries that answer a diagnostic question on their own.

| Entry | Present means | Absent means |
|---|---|---|
| `secret-orbit-node-key.txt` | Orbit completed orbit-enroll and holds a [node key]() | The host never finished enrolling with the Fleet server. Everything downstream is explained by this. |
| `secret.txt` | The enroll secret the package was built with | Missing on a package built normally is a broken install. Empty is expected on `--use-system-configuration` packages, which read the secret from a config profile instead. |
| `identifier` | Fleet Desktop's auth token, rotated by Orbit even when Desktop is off | Orbit has not reached the point of provisioning a token |
| `osquery.db/` | osquery's local store, an embedded RocksDB database: differential state, event buffers, results pending upload | osqueryd has never started here |
| `osquery.flags` | The flag file Orbit reconciles from `command_line_flags` in agent options | The host has never received agent options, or they were cleared |
| `certs.pem` | The CA root bundle fleetd hands osquery via `--tls_server_certs`, embedded in `fleetctl` at package time | `orbit shell` will refuse to start. See [8.4.7](#847-orbit-shell-the-local-osquery-shell) |
| `fleet.pem` | The custom Fleet server CA, present only on packages built with `--fleet-certificate` | Nothing, on a deployment using a publicly trusted certificate |
| `server-overrides.json` | Config the server pushed down to this host | The host has not taken a config from the server yet |
| `bin/orbit/<os>/<channel>/orbit` | The Orbit binary for the configured channel | |
| `bin/osqueryd/<os>/<channel>/osqueryd` | The osqueryd binary actually installed, versus what agent options claim | |
| `bin/desktop/…` | Fleet Desktop was included in the package | Package was built without `--fleet-desktop` |

Fleet documents `certs.pem` at fleetdm.com/guides/certificates-in-fleetd: the bundle is generated from curl's `cacert.pem`, embedded in the `fleetctl` binary, and written into the Orbit root by `fleetctl package`.

There is no `cert.pem`. `certs.pem` (the CA root store) and `fleet.pem` (your server's CA, on custom-certificate deployments) are different files with different jobs, and mixing up the names costs an afternoon.

```sh
# macOS / Linux
sudo ls -la /opt/orbit /opt/orbit/bin/orbit /opt/orbit/bin/osqueryd
sudo cat /opt/orbit/server-overrides.json
sudo orbit version
```

```powershell
Get-ChildItem 'C:\Program Files\Orbit' -Force
Get-ChildItem 'C:\Program Files\Orbit\bin' -Recurse -Depth 3
```

`orbit version` is a real subcommand. Prefer the `orbit_info` table for the same answer remotely ([8.4.6](#846-osquery-introspection-tables)).

**An Orbit root that exists but holds only `certs.pem` and `bin/`** is a package that installed and then failed to enroll. Read `/var/log/orbit/orbit.stderr.log` next ([8.2.2](8.2-log-surfaces.md#822-fleetd-orbit-stdout-and-stderr)). **No Orbit root at all** on a host Fleet shows as MDM-enrolled is [8.4.5](#845-the-half-enrolled-state-mdm-without-an-agent).

## 8.4.4 macOS MDM truth from the host

```sh
sudo profiles status -type enrollment
```

Output is three lines:

| Line | Values you care about |
|---|---|
| `Enrolled via DEP:` | `Yes` means the device came through Automated Device Enrollment ([ADE]()), which Apple's older API and this command still call [DEP](). `No` means manual or user enrollment, whatever Fleet's UI says about it. |
| `MDM enrollment:` | `Yes (User Approved)` is a fully functional enrollment. `Yes` without `(User Approved)` cannot install certain payload types. `No` means not enrolled at all. |
| `MDM server:` | The check-in URL. Confirms *which* MDM owns this device, which is the whole question during a migration. |

Fleet's own uninstall script branches on this output, grepping for `MDM enrollment: Yes` and `MDM enrollment: No`. fleetd uses the sibling command `profiles show -type enrollment` to read the assigned enrollment profile during an MDM migration, and it runs that one as the console user:

```sh
launchctl asuser $(id -u $(stat -f "%u" /dev/console)) profiles show -type enrollment
```

`profiles show` behaves differently outside a user session. `profiles status` reads the same either way. No Fleet-facing documentation mentions it, and it is the best host-side MDM check macOS offers.

**The rest of the `profiles` family:**

```sh
# Which enrollment profile is this device assigned in ABM, and from which server
sudo profiles show -type enrollment

# Every installed configuration payload, with identifiers
sudo profiles show -type configuration

# Terse listing
sudo profiles list -all

# Force the device to re-fetch its assigned enrollment profile from Apple
sudo profiles renew -type enrollment

# Remove Fleet's enrollment profile (this un-enrolls the device)
sudo profiles remove -identifier com.fleetdm.fleet.mdm.apple
```

Fleet's internal MDM troubleshooting notes use `profiles show -type configuration` and `profiles renew -type enrollment`, and the `com.fleetdm.fleet.mdm.apple` identifier comes from its uninstall script. `profiles list -all` is stock macOS, with no Fleet documentation behind the flag.

**UI equivalent, and it moves between macOS versions:** System Settings > General > Device Management shows the enrollment profile and every installed payload with its source. Use it when you are on a call with an end user who should not be asked to open Terminal. It carries the same facts, apart from the DEP and user-approved distinctions.

**Remotely, without shell.** The `mdm` osquery table carries most of the same fields and can be pulled with a live report:

```sql
SELECT enrolled, server_url, installed_from_dep, user_approved, dep_capable,
       payload_identifier, install_date, has_scep_payload, topic
FROM mdm;
```

macOS only. Interpreting what the MDM channel then does with that enrollment is [8.8](8.8-apple-mdm-diagnostics.md).

## 8.4.5 The half-enrolled state: MDM without an agent

**Presentation:** Fleet shows **MDM status: On**, often `(company-owned)`. The host never reports. No Fleet Desktop menu bar icon. MDM commands accumulate in the host's pending activity and none complete.

**What is actually true:** the device is MDM-enrolled and the MDM channel is healthy. fleetd was never installed, or was installed and removed. Fleet's MDM status reflects the MDM channel only, so it reads green while the channel that carries osquery data, scripts, and software is absent.

**Confirm it on the host.** The first command says enrolled, the other two say the agent is not there:

```sh
sudo profiles status -type enrollment    # MDM enrollment: Yes, MDM server: your Fleet
sudo ls -la /opt/orbit                   # missing, or present with no node key
sudo launchctl print system/com.fleetdm.orbit   # "Could not find service"
```

Enrolled plus no Orbit root equals half-enrolled. Enrolled plus an Orbit root plus an unloaded LaunchDaemon is the same failure caught slightly later.

**Cause:** the `InstallEnterpriseApplication` MDM command that delivers the fleetd package during ADE fails, and nothing retries it. Tracked as [`fleetdm/fleet#47793`](https://github.com/fleetdm/fleet/issues/47793), still open as of 4.90.x. The planned fix is delivering the agent over declarative device management instead of a one-shot MDM command.

**Rate:** roughly 2 to 3 percent of ADE enrollments, meaning 20 to 30 hosts per 1,000. Not documented: this is an observed rate from support practice rather than a published figure. Plan a post-enrollment audit at that scale rather than treating each one as a novel incident.

**Recovery: reinstall the agent. Do not re-enroll.** The MDM enrollment is fine. Wiping and re-enrolling the device fixes the symptom by accident and costs the user a day.

```sh
fleetctl package --type=pkg \
  --fleet-url=https://fleet.example.com \
  --enroll-secret=<secret> \
  --fleet-desktop \
  --enable-scripts
```

Then install the resulting `.pkg` on the device by whatever channel you have: hand-delivery, another management tool, or Fleet's own software installer if a second MDM path exists.

**Detecting it fleet-wide.** Query Fleet's server for hosts that are MDM-enrolled and have no osquery check-in, rather than walking hosts one at a time. That is a server-side question: [8.6](8.6-server-state.md).

> [!internal] A customer thread ran two days on this before anyone separated the channels. The customer's opening line was "MDM status is shown as On", which is the misleading signal, and the strongest available evidence (24 MDM commands pending and climbing) was volunteered by the customer and never picked up. Resolution was re-enrollment, which was more than the problem needed. Queue depth that only grows is the tell.

## 8.4.6 osquery introspection tables

Runnable in `orbit shell`, or as a live report against a host you cannot reach. Every table below is in Fleet's published table schema (fleetdm.com/tables) and available on macOS, Windows, and Linux unless noted.

### Which agent is this, and is its config valid

```sql
SELECT i.pid, i.version, i.uuid, i.instance_id, i.config_hash, i.config_valid,
       i.build_platform, i.start_time, i.watcher,
       o.version    AS orbit_version,
       o.enrolled   AS orbit_enrolled,
       o.orbit_channel, o.osqueryd_channel, o.desktop_channel,
       o.scripts_enabled, o.update_url, o.last_recorded_error
FROM osquery_info i, orbit_info o;
```

`config_valid = 0` means osquery rejected the config Fleet served it and is running on whatever it had before. That single column explains a large share of "my agent options did nothing". `orbit_info.last_recorded_error` is Orbit's most recent error string, which is often enough to skip the log file entirely.

`osquery_info.start_time` is a Unix timestamp. Compare it against `time` to get uptime without arithmetic in your head:

```sql
SELECT (SELECT unix_time FROM time) - start_time AS osquery_uptime_seconds
FROM osquery_info;
```

An uptime that resets every few minutes is a watchdog kill or a crash loop. The reason lands in the osquery status log ([8.2.4](8.2-log-surfaces.md#824-osquery-result-and-status-logs)), never in the result log.

### Did the flag actually take

```sql
SELECT name, value, default_value, type
FROM osquery_flags
WHERE name IN ('disable_events','verbose','logger_plugin','logger_path',
               'config_refresh','distributed_interval','watchdog_memory_limit',
               'disable_watchdog','enable_file_events','enable_process_etw_events');
```

```sql
-- Everything you changed from stock, in one screen
SELECT name, default_value, value FROM osquery_flags WHERE value != default_value;
```

This is the answer to "I set it in agent options and nothing happened." `command_line_flags` apply after fleetd restarts, and Orbit reconciles them into `<orbit root>/osquery.flags` first (fleetdm.com/docs/configuration/agent-configuration). A flag missing from this table means the restart has not happened, or the host is enrolled with a revoked enroll secret, which stops flag updates while everything else keeps working.

### Why a scheduled query produces nothing

```sql
SELECT name, interval, executions, last_executed,
       datetime(last_executed,'unixepoch') AS last_executed_utc,
       denylisted, output_size, average_memory, last_memory,
       wall_time_ms, last_wall_time_ms, system_time, user_time
FROM osquery_schedule
ORDER BY last_executed DESC;
```

| Column | Reads as |
|---|---|
| `denylisted = 1` | osquery's watchdog killed this query for resource use and stopped running it. Nothing downstream will ever see results until it is fixed or the denylist expires. |
| `executions = 0` | The query is in the config but has never run. Check `interval` against `osquery_info.start_time`. |
| `last_executed` far in the past | It ran once and stopped, or the schedule was replaced. |
| `average_memory` / `last_memory` high | The candidate for the next watchdog kill. |
| `output_size` large | The reason a result log destination is dropping records ([8.2.11](8.2-log-surfaces.md#8211-server-side-log-destinations)). |

A query missing from this table entirely was never delivered. That is a config problem, not a query problem, and the next look is server-side ([8.6](8.6-server-state.md)).

### Evented tables

An evented table is filled by a background publisher as events occur, rather than by inspecting the system at the moment a query runs.

```sql
SELECT name, publisher, type, subscriptions, events, refreshes, active
FROM osquery_events
ORDER BY events DESC;
```

`active = 0` on everything means eventing is off, which is osquery's default. Fleet documents turning it on through agent options (fleetdm.com/guides/osquery-evented-tables-overview):

```yaml
command_line_flags:
  disable_events: false
```

`active = 1` with `events = 0` means the publisher is running and receiving nothing, which is a permissions or platform problem rather than a Fleet one. On macOS, `es_process_events` additionally needs `--disable_endpointsecurity=false`; on Windows, `process_etw_events` needs `--enable_process_etw_events=true`; YARA's `yara_events` needs `--enable_file_events=true`. All three are in that guide.

### fleetd's own logs, without a shell

```sql
SELECT time, level, message, error, payload
FROM fleetd_logs
WHERE level IN ('error','warn')
ORDER BY time DESC
LIMIT 100;
```

In-memory ring of 10,000 entries inside the Orbit process, emptied on every Orbit restart. Useless for a crash loop, excellent for a remote host you cannot shell into. Details and columns in [8.2.6](8.2-log-surfaces.md#826-reading-fleetds-own-logs-without-shell-access).

### Clock skew

```sql
SELECT unix_time, iso_8601, timezone, local_timezone FROM time;
```

Run this before you spend an hour on "results arriving hours late." A host whose clock is wrong stamps its results wrong, and the timestamps in your SIEM will be exactly as wrong. The two-clocks comparison that uses this is in [8.1](8.1-diagnostic-method.md).

### Also useful

| Table | Answers |
|---|---|
| `osquery_extensions` | Whether Fleet's `fleetd_tables` extension is loaded. Missing extension means `orbit_info`, `fleetd_logs`, and the Fleet-added tables all return nothing. |
| `osquery_packs` | Which packs are active, and their discovery-query cache behavior |
| `osquery_registry` | Which tables, plugins, and loggers are registered and active in this instance |
| `managed_policies` | macOS: what configuration profiles actually applied, as the OS sees them, rather than as Fleet believes |

## 8.4.7 `orbit shell`: the local osquery shell

```sh
sudo orbit shell
```

Opens `osqueryi` using the osqueryd binary this host already has, in an interactive shell. Aliased as `orbit osqueryi`.

**The shell is a separate osquery, not the running agent.** It loads a standalone instance with a default config rather than the config Fleet serves, and it uses its own data path (`<orbit root>/shell`, with its own `osquery.db`), so it never contends with the daemon for the RocksDB lock. What it proves is osquery behaviour. Fleet's configuration of osquery stays a separate question, and Fleet's agent configuration reference draws the same line (fleetdm.com/docs/configuration/agent-configuration).

```sh
# Extra osquery flags go after a bare --
sudo orbit shell -- --verbose
sudo orbit shell -- --disable-events false

# A single query and exit: the last argument, with no leading --, is treated as SQL
sudo orbit shell -- "SELECT version FROM osquery_info;"

# Pin the osqueryd channel
sudo orbit shell --osqueryd-channel stable
```

The `--disable-events false` form is Fleet's documented way to test evented tables locally (fleetdm.com/guides/osquery-evented-tables-overview). **The shell is ephemeral, so you only see events gathered while it is open.** Open it, do the thing you want to catch, then query. An `osquery_events` row showing `events = 0` in a shell you opened five seconds ago proves nothing.

On argument handling: a trailing argument that does not start with `--` puts osquery in single-query mode. The extension runner that provides `orbit_info` and `fleetd_logs` starts in interactive mode alone, so **Fleet's own tables are available only in the interactive shell**. Undocumented.

If `orbit shell` exits with `cert not found at <root>/certs.pem`, the CA bundle is missing from the Orbit root. Pass a path explicitly with `--fleet-certificate`, or treat it as a damaged install ([8.4.3](#843-the-orbit-root-directory)).

## 8.4.8 Raising verbosity on an installed host

The full lever table is [8.2.10](8.2-log-surfaces.md#8210-raising-verbosity-and-putting-it-back). On a host that is already installed, these three are what you reach for.

| Platform | Turn on | Turn off | Restart delay |
|---|---|---|---|
| macOS | `sudo ./toggle-fleetd-debug.sh enable` | `sudo ./toggle-fleetd-debug.sh disable` | 15 s, then bootout/bootstrap |
| Windows | `.\toggle-fleetd-debug.ps1` (toggles) | run it again | none, service restarts inline |
| Linux | `echo 'ORBIT_DEBUG=true' \| sudo tee -a /etc/default/orbit` then `sudo systemctl restart orbit.service` | `sudo sed -i '/^ORBIT_DEBUG=/d' /etc/default/orbit`, restart | none |

Fleet publishes both scripts in its repository, at `docs/solutions/macos/scripts/toggle-fleetd-debug.sh` and `docs/solutions/windows/scripts/toggle-fleetd-debug.ps1` (github.com/fleetdm/fleet/tree/main/docs/solutions). Linux has no supplied script. Its systemd unit carries `EnvironmentFile=/etc/default/orbit`, and a package built with `--debug` writes `ORBIT_DEBUG=true` into that file, which is what the table above does by hand.

**The 15-second sleep in the macOS script is load-bearing.** The script forks a detached background job that sleeps 15 seconds before touching anything, because Orbit is the process running the script and is about to be killed. The delay lets the script's result reach Fleet first, so Fleet records the run as complete. The Windows script restarts the service inline with no such delay, so running it as a Fleet script means accepting that the result may be lost.

The background job on macOS writes to `/tmp/orbit_debug_script_logs.txt`. When a toggle appears not to have worked, read that file before anything else.

Confirm the current state without changing it:

```sh
# macOS
sudo /usr/libexec/PlistBuddy -c 'print EnvironmentVariables:ORBIT_DEBUG' \
  /Library/LaunchDaemons/com.fleetdm.orbit.plist
```

```powershell
# Windows: --debug present in ImagePath means debug is on
(Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Services\Fleet osquery' -Name ImagePath).ImagePath
```

```sh
# Linux
grep ORBIT_DEBUG /etc/default/orbit
```

macOS debug output goes to an unrotated file. Put the "off" step in the same ticket as the "on" step.

## 8.4.9 Diffing against a known-good host

The fastest way to shorten a host-side investigation is to run the same commands on a host that works, same platform, same team, same Fleet server. Diff these:

| Compare | Broken host | Known-good host | A difference means |
|---|---|---|---|
| `orbit_info.version` and `orbit_channel` | | | The broken host is pinned to, or stuck on, a different channel. Updates are failing. |
| `osquery_info.version` and `config_hash` | | | Different `config_hash` on the same team means one host has not taken the current config |
| `osquery_info.config_valid` | | | `0` on one side is the whole answer |
| `osquery_flags` where `value != default_value` | | | The broken host never got, or never restarted into, the current `command_line_flags` |
| `sudo profiles status -type enrollment` | | | Different `MDM server`, or DEP vs manual, or approved vs not |
| `sudo profiles show -type configuration` | | | A payload present on one and missing on the other localizes the failure to a specific profile |
| `ls -la /opt/orbit` | | | A missing node key or secret file on one side |
| `server-overrides.json` | | | The server is telling the two hosts different things |

Do it as one live report across both hosts rather than two shells, and the diff is in one result set:

```sh
fleetctl report --hosts <broken-host>,<known-good-host> --exit --query "
SELECT i.version AS osquery_version, i.config_hash, i.config_valid,
       o.version AS orbit_version, o.orbit_channel, o.osqueryd_channel, o.enrolled
FROM osquery_info i, orbit_info o;
"
```

Same platform matters. macOS and Windows differ in enough of these fields that a cross-platform diff generates noise instead of signal. Same team matters because agent options and profiles are assigned per team.

If both hosts look identical and one still fails, agent state is not the variable. The next candidates are the network path between host and server, and the server itself ([8.1](8.1-diagnostic-method.md)).

## 8.4.10 The log files you open first

Full inventory, per platform, with rotation and lifetimes: [8.2](8.2-log-surfaces.md). In practice you open these:

```sh
# macOS: enrollment failures, script runs, update failures. Almost always stderr.
sudo tail -n 500 /var/log/orbit/orbit.stderr.log

# Linux
sudo journalctl -u orbit -n 500 --no-pager

# Any platform: osquery's own health, watchdog kills, flag parsing
sudo ls -la /opt/orbit/osquery_log/
sudo tail -n 200 /opt/orbit/osquery_log/osqueryd.INFO
```

```powershell
Get-Content -Tail 500 'C:\Windows\system32\config\systemprofile\AppData\Local\FleetDM\Orbit\Logs\orbit-osquery.log'
```

Collect the ephemeral surfaces **before** you restart anything. `fleetd_logs` is wiped by an Orbit restart and `fleet-desktop.err` is truncated on every Desktop start ([8.2.12](8.2-log-surfaces.md#8212-what-survives-and-for-how-long)).

## 8.4.11 What the host cannot tell you

| Question | Why the host cannot answer it | Where to go |
|---|---|---|
| Why did the server stop accepting this host's check-ins? | The rejection happens server-side. The host sees a failure, not a reason. | [8.6](8.6-server-state.md) |
| Which MDM commands are queued for this device, and how long have they been queued? | The queue lives in Fleet's database. The device only sees commands it has been handed. | [8.6](8.6-server-state.md) |
| What did Fleet intend this host's profiles or software to be? | Desired state is server-side. The host holds actual state only. | [8.6](8.6-server-state.md) |
| Is this problem specific to this host, or fleet-wide? | One host is a sample of one | [8.6](8.6-server-state.md), [8.7](8.7-live-query-introspection.md) |
| How did the agent get removed, and by whom? | **There is no host-side event history.** Fleet's audit log records server-side actions only, so an agent removed by a local admin, another management tool, or a user leaves no trace Fleet can show you. | [8.12](8.12-audit-logs.md) for what the audit log does cover |
| Did the query results Fleet received match what the host produced? | Requires both ends | [8.1](8.1-diagnostic-method.md), two-clocks comparison |

The agent-removal gap is a real limit and customers hit it. Say so plainly rather than searching the audit log for an event that was never written. Host-side attribution has to come from the platform's own audit facility: the macOS unified log, the Windows Event Log, or Linux auditd.

## 8.4.12 Agent updates: which channel landed, and why it did not

Orbit updates the whole bundle from a signed update repository of its own, built on The Update Framework (TUF), rather than through the Fleet server. So an update problem leaves no server-side trace beyond a version that will not move, and the narrowing question is **what is on disk versus what was asked for.**

Ask for it first. Channel names come from Orbit's own extension table, so this works as a live report against a host you cannot reach ([8.4.6](#846-osquery-introspection-tables)):

```sql
SELECT version, orbit_channel, osqueryd_channel, desktop_channel,
       update_url, last_recorded_error
FROM orbit_info;
```

Then look at what landed. Binaries live at `<orbit root>/bin/<target>/<platform>/<channel>/<file>`, so a channel change is visible as a new directory:

| Target | Platform string | File on disk | Executable inside |
|---|---|---|---|
| `orbit` | `macos`, `linux`, `linux-arm64`, `windows`, `windows-arm64` | `orbit`, `orbit.exe` | n/a |
| `osqueryd` | `macos-app` | `osqueryd.app.tar.gz` | `osquery.app/Contents/MacOS/osqueryd` |
| `osqueryd` | `linux`, `linux-arm64` | `osqueryd` | n/a |
| `osqueryd` | `windows`, `windows-arm64` | `osqueryd.exe` | n/a |
| `desktop` | `macos` | `desktop.app.tar.gz` | `Fleet Desktop.app/Contents/MacOS/fleet-desktop` |
| `desktop` | `windows`, `windows-arm64` | `fleet-desktop.exe` | n/a |

```sh
sudo ls -la /opt/orbit/bin/orbit/*/ /opt/orbit/bin/osqueryd/*/
sudo /opt/orbit/bin/osqueryd/macos-app/stable/osquery.app/Contents/MacOS/osqueryd --version
```

Three states, each pointing somewhere different:

| On disk | Reads as | Next look |
|---|---|---|
| Requested channel directory **absent** | The channel does not exist in the repository, or the download has not succeeded yet | Grep the Orbit log for `tuf: file not found` (nonexistent channel) or `max retries exceeded, retrying again in` (in cooldown, below) |
| Directory **present**, old version still running | The update landed and the restart did not happen, or is failing | Look for `exiting due to successful update` followed by a start. Absent, the restart never fired |
| Both present, version **flapping** | Downgrade loop. Orbit below 1.20.0 packaged on one channel, with `update_channels` pointing at a channel holding a different side of that boundary | Move one of the two channels across 1.20.0 in the same direction |

**The cooldown is the reason a retry does nothing.** A failed target download gets 3 attempts, then a **24 hour cooldown for that target**. The retry key is the target's content hash, so publishing a new version resets it immediately. Restarting Orbit does not. Fetching targets **at startup** is the exception: it retries forever at 5 minute intervals rather than entering cooldown.

**A corrupt download self-heals, slowly.** Orbit health-checks an installed binary by running it (`<binary> --help`, or a target-specific check). On failure it deletes the extracted directory, the archive, and the cached `.sha512`, logs `removed corrupt target for re-download`, and refetches on the next pass. So a truncated download costs at least one update interval and needs no intervention.

**Two version floors that look like a broken update server.** Orbit below 1.38.1 cannot upgrade past the move from `tuf.fleetctl.com` to `updates.fleetdm.com` and logs `update failed error="lookup failed: lookup orbit: tuf: file not found`. Get to 1.38.1 first, let it land, then continue. Orbit 1.38.0 and later rewrite a configured `tuf.fleetctl.com` URL to `updates.fleetdm.com` on their own.

**Expired TUF signatures block startup by role.** Expired `root`, `targets`, or `snapshot` roles stop targets loading; Orbit then rechecks expiry each interval and exits once they are valid so the next start initialises normally. An expired `timestamp` role does not block startup.

### Forcing an update check

The check runs at startup, before any other subsystem, so restarting the service is the fastest trigger ([8.4.2](#842-is-the-agent-running)). To shrink an update problem to a minimal case on one host, shorten `--update-interval` and turn on `--debug` ([8.4.8](#848-raising-verbosity-on-an-installed-host)), then watch the `hash(<target>)=` lines against what the TUF metadata advertises. The first periodic check after startup adds a random offset of up to `min(interval, 10 minutes)`, so an idle-looking first window is expected rather than a stall.

Channel and update behaviour as designed, including the `update_channels` precedence rules, is in [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md).
