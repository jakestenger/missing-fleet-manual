# Operate Fleet with fleetctl

For operations against a Fleet server, `fleetctl` is an API client. It also does a good deal of client-side work: configuration, packaging, scaffolding, conversion and update-repository management. The authorization and resource semantics of anything it sends come from [6.3](6.3-use-the-fleet-rest-api.md); this chapter covers what the client adds or changes.

What it adds includes how it decides which server it is talking to, what it does when the versions disagree, and **what its exit status does and does not tell you**. That last one is the reason a chapter is needed at all.

> **The one thing to take away.** `fleetctl` returns zero or one, and that status tells you whether the **client action** returned an error. What the operation actually achieved may be in the output, may be absent entirely, or may only be readable from Fleet afterwards.

## Install and match fleetctl to the server

![How-to](../_assets/icons/howto.svg) Version matching is your job, not the client's.

**Verify the client version you actually got**, before anything else. Installation forms vary, and one of them matters for automation: **the npm launcher downloads the binary on first invocation and writes installation messages to standard output**, which will contaminate an output stream a pipeline is trying to parse. Run it once before you depend on its output.

**A version mismatch produces a warning and nothing else.** There is no gate, no refusal, and no difference in that behaviour for GitOps: the same string comparison and the same warning, on any authenticated command.

So the client will happily talk to a server it was not built for. What breaks is unpredictable, a field the client does not know how to send or a route that has moved, and the failure surfaces as an ordinary error rather than as a version problem.

**Pin the client version in automation, to the server's release**, and treat an upgrade of one as requiring an upgrade of the other ([7.2](../07-operate-fleet/7.2-upgrade-fleet-and-fleetd.md) owns that coordination).

## Configure connections and contexts safely

![Reference](../_assets/icons/reference.svg) A named context holds a server address and a credential. [6.1](6.1-automation-design-and-change-control.md) covers the credential; this is about the file.

A context can carry the server address, a custom certificate authority, a URL prefix and the token. Switching context switches all of it at once, which is exactly what you want when you have more than one Fleet and exactly the risk if you have more than one shell.

> ### Concurrent writes to the configuration file lose each other
>
> **The file is rewritten whole, with no locking, no atomic replacement and no conflict detection.**
>
> Two processes changing configuration at the same time can therefore lose one of the two changes, silently, with both exiting successfully. It is not a rare race.
>
> **In automation, give each job its own configuration file** rather than sharing the default one. It removes the whole class of problem and costs nothing.

## Choose the appropriate command surface

![Explanation](../_assets/icons/explanation.svg) Four surfaces, and the differences between them are not cosmetic.

| Surface | Use it for | Watch out for |
|---|---|---|
| **Native commands** | Everyday work: hosts, queries, scripts, software | Some report results in text rather than in the exit status |
| **Client-side utilities** | Configuration and contexts, packaging, scaffolding, conversion, preview, update repositories | Not API operations at all. [3.7](../03-connect-devices/3.7-manage-fleetd-orbit-and-updates.md) owns the packaging and update-repository semantics |
| **`apply` and `delete`** | One-off spec files | **The dry run does not check five of the eight kinds it accepts, and `delete` ignores five of them** |
| **`gitops`** | Declared state, reconciled | All of [6.2](6.2-manage-fleet-with-gitops.md) |
| **`api`** | Reaching a route the client has no command for | **Defaults to the numbered version and discards error bodies** |

### The raw API passthrough has two sharp edges

**It defaults to the numbered version prefix**, and recognises only that one and `latest`. It cannot straightforwardly address the dated prefix at all. Since route availability is declared per endpoint ([6.3](6.3-use-the-fleet-rest-api.md)), a route that does not exist on the numbered version returns not-found through this command even though it exists on the server.

**And it discards the response body on a non-success status.** You get the status and lose Fleet's explanation of it, which is usually the part you needed.

**Note the asymmetry with the native commands**, which select their own routes internally rather than defaulting to the numbered prefix. Two `fleetctl` invocations can therefore reach different versions of the same resource.

Use it for reads and for routes with no native command. For anything you will run repeatedly, an ordinary HTTP client gives you the error body.

## Use commands without duplicating feature chapters

![How-to](../_assets/icons/howto.svg) Discovery, not a command reference.

Command help is the reference. [a.7](../09-appendices/a.7-fleetctl-command-reference.md) **will be** the index and is not written yet, so what follows is enough to work from on its own:

- **Getting things** and **applying things** are separate verbs over the same specs.
- **Host actions** reach the same server operations the interface does. **The owning feature chapter defines queueing, completion and verification**, and the client does not always default to the same shape: `run-script` is synchronous by default, where [5.3](../05-manage-devices/5.3-run-and-manage-scripts.md)'s normal administrative model is not.
- **Diagnostics** talk to the server about itself, and hand off to [Part VIII](../08-troubleshooting/8.1-diagnostic-method.md) when the answer is not immediate.

**Two commands do less than their names suggest**, and both do it quietly:

> **`delete` accepts eight kinds of thing and deletes three.** Reports, packs and labels are removed. The other five are parsed, accepted, and **silently ignored**: nothing is deleted, nothing is printed, and the command exits successfully.
>
> **`apply --dry-run` skips five of the eight kinds it accepts.** Reports, labels, packs, policies and user roles are noted on standard output and not validated against the server. Configuration, fleet and enroll-secret specs do get dry-run processing. Accepted kinds are parsed into their local spec types with whatever parse-time checks that involves, which is not the same as local semantic validation.
>
> So a pull-request gate built on `apply --dry-run` validates the file's syntax and rather less of its content than it appears to.

### Two exit codes, and what they cannot express

**`fleetctl` itself returns zero or one.** That status tells you whether the client action returned an error. Command-specific outcome detail may be in the output, **absent entirely**, or available only from later Fleet state. A wrapper timeout, a signal, or a failure to start the process can of course produce other statuses that `fleetctl` never chose.

The case that matters most:

> **`run-script` exits zero when the script ran, whatever the script's own exit code was.**
>
> Fleet delivered the script, the host executed it, the result came back: from the client's point of view that is success. The script's actual exit code is in the printed output. **And `--quiet` removes the line that carries it.**
>
> **A pipeline that runs a script through `fleetctl` and checks the exit status is not checking whether the script worked.** Parse the output, or read the execution result through the API afterwards ([6.3](6.3-use-the-fleet-rest-api.md)).

Not every zero exit is a hidden failure, and it is worth being precise: many are ordinary informational output, and asynchronous commands correctly report that work was *queued* rather than finished ([6.1](6.1-automation-design-and-change-control.md)). The rule is not "distrust every success", it is **"know what each command's exit status represents, and where its outcome is exposed"**. Sometimes that is the output. For the ignored `delete` kinds it is nowhere at all.

### Errors are split by kind, not by severity

| What failed | Where it is written |
|---|---|
| **The action** you asked for | Standard error |
| **Your flags**, your environment, or a missing required flag | **Standard output**, with the help text |

That second row is the trap. A pipeline capturing only standard error sees nothing when a flag is wrong, and a renamed or removed flag is exactly what a version upgrade introduces.

**Capture both streams.** Keep them separate if you can, so you can tell an action failure from a usage failure, but do not discard either.

### Timeouts

There is **no overall deadline on an ordinary authenticated call**. Transport-level and handshake timeouts exist and will catch a network that is genuinely broken, but a server that accepts your connection and then takes a very long time will be waited for indefinitely.

**Impose your own deadline in automation.** Your job runner's timeout is the backstop, and it should be set deliberately rather than left at whatever the default is.

## Run fleetctl in CI and troubleshoot the client boundary

![Troubleshooting](../_assets/icons/troubleshooting.svg) The scaffold is a starting point, and it needs three corrections before you use it.

Fleet generates a workflow that gets the shape right: a dry run on proposed changes, a scheduled apply, and a concurrency block so two runs cannot interleave. It is a good starting point and **three of its shipped defaults need changing before you point it at an existing Fleet**.

**Two of them are state hazards, and they combine.**

> 1. **It defaults the destructive fleet-deletion flag to on.** [6.2](6.2-manage-fleet-with-gitops.md) explains why that flag belongs only on a canonical complete invocation. On a scaffold pointed at an existing deployment it is aimed at your fleets.
> 2. **It generates no Unassigned file.** That is the empty-Unassigned trap from [6.2](6.2-manage-fleet-with-gitops.md) shipped as a default: a global file with no `unassigned.yml` synthesises an empty one and applies it, clearing the GitOps-managed fields 6.2 lists and affecting software according to the effective software exception.
>
> An unmodified run against an existing Fleet therefore has a far larger state-changing scope than it looks like it has.

**The third and fourth are separate problems.** The scaffold places the credential in command arguments, twice: anything that can list processes on the runner can read it, and Fleet's own documentation warns against exactly this. Supply it through the environment or a file instead. And **both generated pipelines can fall back to the newest client** rather than failing when the matching version is unavailable, which is the opposite of the pinning this chapter asks for.

Only the generated GitHub workflow has the concurrency block; the generated GitLab pipeline does not.

### A preflight worth running

Before any automated invocation, in order: **its own configuration file**, a **confirmed address and context**, a **client version matching the server**, the **output form you intend to parse**, an **external deadline**, and a **verification step** for whatever the command was supposed to achieve.

That is the ordinary safe path. Everything else in this chapter is what happens when one of those six is missing.

### Working in CI

**Give the job its own configuration file**, for the locking reason above and because a shared one is shared state you did not intend.

**Pin the client version** rather than fetching the newest.

**Set a job timeout**, since the client will not impose one.

**Capture both output streams**, since usage errors are on the one you would not think to keep.

### Telling a client problem from a server problem

Before escalating, establish which side you are on. **The client owns**: the configuration file and its contexts, the address and certificate trust, the version it is, flag parsing, and how output is rendered. Everything else is the server's, and belongs to [Part VIII](../08-troubleshooting/8.1-diagnostic-method.md).

The useful signal is *how far the request got*. A failure before any request left the machine is yours: bad flags, no context, an address that does not resolve, a certificate the client will not trust. A response that arrived and said something unwelcome is the server's, and the status code and body are the beginning of that conversation rather than this chapter's business.
