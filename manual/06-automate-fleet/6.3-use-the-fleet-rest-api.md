# Use the Fleet REST API

Almost everything you do as an administrator, you do through this API. The interface is a client of it, `fleetctl` is a client of it, and GitOps is a client of `fleetctl`. **The exceptions are the settings that are not application state at all**, the ones the server reads at startup from its own configuration, which no API can change ([a.3](../09-appendices/a.3-configuration-model-and-precedence.md)). Fleet serves other route classes too, for agents, devices and protocol callbacks, and this chapter is about the one you write clients against: the most capable path, and the one with the fewest guard rails.

This chapter is about the API's *mechanics*: how to address it, how to page through it, what its errors mean, and how to write a client that survives a Fleet upgrade. **What each resource means belongs to the chapter that owns it**, and this chapter deliberately does not repeat any of it.

The Fleet MCP server is another client of this API: it wraps a read-mostly subset of these routes as tools for an AI assistant, so most of its behaviour and its failures are this API's, seen through one more layer ([6.6](6.6-connect-fleet-to-an-ai-assistant.md), [a.11](../09-appendices/a.11-mcp-tool-reference.md)).

[6.1](6.1-automation-design-and-change-control.md) owns credentials and the design rules. Read it first if you have not.

## Start from the documented resource and scope

![How-to](../_assets/icons/howto.svg) Four questions before you write a line of client code.

1. **Which resource, and which chapter owns it?** The owning chapter tells you what the fields mean and which states are terminal. This one will not.
2. **Which role does the call need**, and does your automation's identity have it? ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md))
3. **Global or fleet-scoped?** Many resources exist at both, on different routes, with different permissions.
4. **What does the response actually contain?** Frequently not what the write returned, and frequently not enough to confirm the write worked.

> **The reference is a map, not an inventory.** Fleet's published API reference is hand-maintained, so it is the best available account rather than a promise of completeness. Fleet also embeds a machine-readable catalogue of routes, and **that is not an inventory either**: it is the allowlist consulted for API-only accounts carrying a non-empty endpoint restriction list, it is validated only in the direction of catalogue to route, and Fleet separately registers backward-compatible aliases it does not contain ([a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md)).

## Build and authenticate a request

![Reference](../_assets/icons/reference.svg) The credential is 6.1's. The *address* is where the surprises are.

Authentication is one session key carried after `Bearer`, and [6.1](6.1-automation-design-and-change-control.md) explains why there is no second kind of token. This section is about everything before the header.

### There is no single version prefix for the whole API

This is the finding most likely to break an assumption you did not know you had made.

It works in two stages. **Each route-registering module declares an ordered base set of version names.** Then **an individual route can narrow that set further**, with its own start and end boundaries. A `latest` registration is added to eligible current routes, as a literal path rather than a redirect, so a historical or deliberately fixed route may not have one at all.

> **So there is no dated prefix on which the entire API exists.** The core module's set is not every module's set, at least one route family is fixed to a single prefix, and a client touching two modules can find that none serves both.

> **Default to the exact documented method and path for each resource, including its prefix, and contract-test that path against every Fleet release you target.** Mixed prefixes across one client are an ordinary consequence of per-route contracts rather than a mistake. Use `latest` only as a deliberate convenience for routes that expose it, and understand that it increases your dependence on those tests rather than removing the need for them.

**What a prefix does not do is freeze the response schema.** Choosing an older prefix selects which routes are available. It does not give you an older shape of the data.

### The renamed fields, which will bite you on a write

Fleet renamed its team and query concepts to fleets and reports. The old names still work, and that compatibility has a sharp edge:

- **A response governed by these aliases can contain both names** for the same value.
- **A request containing an alias pair is rejected** with a client error.

So the obvious integration pattern **can fail**: if you take an object that came back carrying an alias pair and reuse it as the request body for an endpoint that accepts that pair, Fleet refuses it.

> **Build the request from its own request schema and keep only the canonical name.** Do not echo a response body back to Fleet. This is worth saying to anyone maintaining an older integration, because the field renames were announced and the route spellings and aliases were not.

### The minimum a client has to get right

Beyond the credential and the prefix:

- **Include the configured URL prefix** if your deployment has one. It sits in front of everything.
- **Set a connection deadline and a whole-request deadline.** Fleet imposes neither on your behalf.
- **Bound the response size** as well as the page size, so an unexpectedly large page cannot exhaust the client.
- **Send JSON content type on writes**, and read the body on every response, not only on failures.
- **Record Fleet's error identifier when one is present.** It is the handle that ties your failure to the server's own record of it ([8.3](../08-troubleshooting/8.3-server-logs.md#the-uuid-correlation-trick)).

| Status | Ordinarily means | Reasonable response |
|---|---|---|
| **401** | The credential is not valid, or a password reset is required | Stop. Do not retry with the same one |
| **402** | Authenticated and permitted by role, but your license tier does not include this | A licensing gate, not a role problem. Check the licence, not the role ([a.4](../09-appendices/a.4-roles-and-permissions-matrix.md)) |
| **403** | Authenticated, but the action is refused | Stop. Usually a role or team-scope limit ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)); it can instead be an endpoint restriction or an account-state gate that answers before your role decides the request ([1.4](../01-foundations/1.4-identity-and-roles.md), [8.5](../08-troubleshooting/8.5-fleetctl-debug.md)) |
| **409** | A semantic conflict, such as a duplicate name | Read the current state and decide |
| **413** | The request was too large | Reduce it; do not retry unchanged |
| **429** | A limiter refused you | Wait for the hint it carries |
| **5xx** or a connection failure | Unknown outcome | **Verify by reading before repeating a write** |

## Page, filter, and order complete result sets

![Troubleshooting](../_assets/icons/troubleshooting.svg) The section where a client that works on a small deployment stops working on a large one.

### Two defaults that are nothing like each other

On endpoints using Fleet's shared list machinery:

| What you send | What you get |
|---|---|
| **No pagination parameters at all** | Up to **one million rows** |
| **Any page number, including zero, and no page size** | **Twenty rows** |

Both are surprising, and the second is worse, because adding what looks like a harmless parameter silently shrinks your result set by a factor of fifty thousand. **Always set the page size explicitly.** Defaults and maximums are per endpoint, so check the one you are calling.

### Ordering is not stable unless you make it so

**The host list applies no ordering at all when you do not ask for one.** The common list machinery adds no identifier tiebreaker, and the host list adds none itself, so two identical requests can return rows in different orders and offset paging can show you a row twice and never show you another. Some individual endpoints do add their own secondary ordering; do not assume yours is one of them.

> **Traverse the host list by cursor**: order by identifier, ascending, with an explicit page size, passing the last identifier you saw as the start of the next page. **Cursor support is endpoint-specific**, and the host response carries no pagination metadata, so you stop when a page comes back empty or short.
>
> **Reject the whole page if the response carries a top-level error**, for the reason in the next section.
>
> And know what a clean traversal still does not buy you: **the result is not a transactional snapshot.** Rows created or deleted while you page will appear or vanish. If exactness matters, reconcile afterwards.

### Filters fail quietly

**An unknown query parameter is ordinarily ignored.** A misspelled filter therefore does not error; it silently widens your result to everything.

Filter support is per endpoint and does not follow from the resource. A filter honoured by one endpoint can be ignored by its closest sibling, including by a counting endpoint and the listing endpoint it counts. Licence tier can change behaviour too, and not always by refusing: a filter can be accepted, validated, and then not applied, so a valid request returns an unfiltered list and a success status.

**Verify the exact endpoint.** Test that your filter actually narrows something, rather than assuming the absence of an error means it worked.

## Handle errors, limits, and ambiguous writes

![Reference](../_assets/icons/reference.svg) The status code carries less information than you would like, in both directions.

### What the codes mean here

| Code | Ordinarily means |
|---|---|
| **422** | Fleet's validation rejected the content |
| **400** | The request framing was malformed, or it carried a deprecated and canonical name together |
| **404 / 405** | May come from the router rather than from Fleet, in which case the body is **plain text rather than Fleet's JSON error shape** |

A client that assumes every error body parses as Fleet's error object will fail to parse exactly the errors that mean it addressed the wrong path.

> ### The host list can return an error inside a 200
>
> At least one read shares Part VI's broader lesson that a status code alone is not sufficient.
>
> **The host list commits its success status before it has finished assembling the response.** It fetches its base rows first, then commits the 200, and a failure during the per-host work that follows is reported as a top-level error **inside that successful body**.
>
> **Parse the complete body and reject a host-list response carrying a top-level error key, whatever its status.** This is a streaming implementation particular to that endpoint rather than a general contract, and it is enough to stop you trusting a status code by itself.

### Rate limits

**Ordinary authenticated routes have no Fleet rate limiter.** There is no request budget to plan around on the routes your integration spends its time in.

Limiters do exist elsewhere. Some are **deployment-wide fixed buckets**, including the sign-in family, so an automation that re-authenticates frequently spends an allowance shared with every human trying to sign in. Others are keyed by address. **Only the limiter responses carry a retry hint**; nothing else Fleet returns tells you when to come back.

**Consequences for your client, both directions.** Fleet will not throttle you, so you must pace yourself: a client with unbounded concurrency can overwhelm a deployment that is serving devices at the same time. And sign in once, keep the session, and do not re-authenticate per request.

### After an ambiguous write

**Read, then decide.** [6.1](6.1-automation-design-and-change-control.md) has the general rule; here is the specific one for this API.

**Retry safety is a property of the endpoint, not of the verb and not of a route family.** Fleet's declarative endpoints are POST, batch routes vary, and no naming convention tells you which are safe. There is no idempotency key.

So for any write whose outcome you did not observe: **make a verification read against the resource's documented state, and decide from that.** Repeating a write because it timed out is a guess, and on this API it is an unnecessary one.

## Design idempotent and observable clients

![How-to](../_assets/icons/howto.svg) What a durable client keeps hold of.

**Keep the handles Fleet gives you**: resource identifiers, profile identifiers, script execution identifiers, command identifiers, batch execution identifiers. These are how you ask later what happened.

**Note where Fleet gives you nothing.** A per-host software install returns an accepted status and an **empty body with no install identifier**, even though Fleet has one internally. Your correlation for that call has to come from your own side, plus a later read.

**Keep your own correlation record.** Fleet stores no request identifier and no client identity beyond the account ([6.1](6.1-automation-design-and-change-control.md)), so the link between your change ticket and Fleet's activity exists only if you write it down.

**Log the request, the response status, the body's error key if present, and your own identifier.** The body's error key matters because of the read behaviour above.

## Version and test the integration contract

![How-to](../_assets/icons/howto.svg) The section that decides whether your integration survives the next upgrade.

**Pin your tests to a Fleet release**, and run them against the target release before [7.3](../07-operate-fleet/7.3-upgrade-fleet-and-fleetd.md) upgrades production. That is the whole discipline, and the rest is detail about what to test.

What deserves a test, because these are the things that change:

- **Every route you call, at the prefix you call it.** Route availability is per module.
- **The shape you send on writes**, especially anything touching a renamed field.
- **Your pagination assumptions**, including that your page size is still accepted.
- **Your filters**, asserted to actually narrow rather than to merely succeed.
- **Your error handling**, including a deliberately malformed path to check you cope with a non-JSON error body.

> **Do not treat `latest` as a stable external contract.** `fleetctl` uses it internally, which is not the same as Fleet promising it to you. If you use it, your compatibility tests are the only thing standing between an upgrade and a broken integration.

**And watch for deprecations you were not told about.** Fleet announced the field renames. It did not document the old route spellings as deprecated, and its own catalogue's deprecation flags do not cover the name aliases. **Inventory the routes and fields you depend on before an upgrade rather than after**, because the release notes are not guaranteed to mention the one that affects you.
