# Connect integrations, webhooks, and external workflows

![Explanation](../_assets/icons/explanation-light.svg) Fleet's integrations connect device information to the work happening in your other systems. A policy failure can prompt follow-up, an activity can reach an external workflow, and agent logs can feed an existing logging platform. These connections let administrators build on the tools and processes they already use.

Choose the delivery mechanism around the event and the result you need. Fleet's seven configurable senders differ in triggers, timing, batching, retries, and scope, so a receiver needs to understand the contract of each one it consumes. [5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md) explains what triggers policy automations; this chapter follows the delivery to the receiving system.

## Choose event delivery, polling, or a native integration

![Explanation](../_assets/icons/explanation-light.svg) You can receive a notification, read Fleet state on a schedule, or let a native integration perform supported work at the destination. Each approach gives you a different balance of timing, control, and recovery:

- **Webhooks push notifications.** The receiver must be available when delivery occurs or within any supported retry window. Several senders make only one attempt.
- **API polling reads state.** It adds requests and may detect a condition later, but can recover current state after the receiver resumes ([6.3](6.3-use-the-fleet-rest-api.md)).
- **Native integrations create supported tickets or calendar events.** Fleet handles the destination operation, with less scope for custom receiver behavior.

For a custom workflow, use a webhook to trigger an API read where possible. Reading the current state helps the workflow respond consistently when notifications are repeated or arrive out of order.

Recovery still depends on what remains in Fleet. A policy that is still failing, a vulnerability that is still present, or a host that is still quiet can be read later. A condition that clears between polls may be missed. Migration-button presses, log batches, and calendar callbacks have no supported replay; protect those deliveries in the receiver if you need to retain them.

## Configure destinations and ownership

![Reference](../_assets/icons/reference-light.svg) Check the supported scope before choosing which workflow owns a destination. Some settings belong to the whole deployment, while others can follow a particular fleet:

| Mechanism | Global | Per fleet |
|---|---|---|
| **Activity** | Yes | Yes (Premium) |
| **Failing policies** | Yes | Yes |
| **Host status** | Yes | Yes |
| **Vulnerabilities** | Yes | No |
| **Calendar callback** | No | Yes, named fleets only |
| **macOS MDM migration** | Yes | No |
| **Log destination** | Yes | No |

Vulnerability, migration, and log destinations are global only. Calendar callback destinations belong to named fleets, even though the Google Calendar credentials are global.

Fleet 4.91 adds per-fleet activity webhooks on Premium. They operate alongside the global webhook and receive a different event set, as described under [The activity webhook, global or per fleet](#the-activity-webhook-global-or-per-fleet).

<a id="the-eighth-sender-which-is-not-yours"></a>

### Fleet usage analytics and outbound access

Fleet also sends usage analytics to a fixed address outside these seven configurable destinations. Include that traffic in your outbound-access review. [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md#built-in-and-commonly-configured-egress-destinations) lists the address, the analytics payload, and the server's other egress destinations.

<a id="the-one-an-end-user-can-set-off"></a>

### End-user initiation of macOS MDM migration

The macOS MDM migration webhook is invoked by a device-authenticated request when a person presses **Start** on their machine. After a successful delivery, Fleet suppresses another delivery for that host for three minutes. Design the receiver around individual user actions and the bursts those actions can produce.

This is the dedicated webhook endpoint directly invoked by an end user. Other user actions can still cause webhook traffic indirectly: self-service actions create activities, which can reach an activity webhook.

## Understand each webhook contract

![Reference](../_assets/icons/reference-light.svg) Use the trigger, cadence, and retry behavior together when deciding what the receiver must retain and how it should recover:

| Mechanism | What triggers it | Cadence | Delivery unit | Retries |
|---|---|---|---|---|
| **Activity** | An activity is written | Immediate | One activity | 429 only, up to 30 minutes |
| **Failing policies** | A host transitions to failing | Shared interval, 24 hours by default | Configurable host batches | No immediate retry; hosts remain pending for the next cycle |
| **Host status** | A threshold is met on the current evaluation | Same shared interval | One unbounded identifier list | No; evaluated again next cycle |
| **Vulnerabilities** | A newly detected vulnerability | Separate interval, one hour by default | Configurable host batches | No |
| **Calendar callback** | A calendar-enabled policy remains failing during the active window | Five-minute job arms delivery; the host's result initiates it | Per host | 429 only, up to 30 minutes |
| **macOS MDM migration** | An end user presses Start | Immediate, then suppressed for three minutes per host | Per host | No |
| **Log destination** | An agent submits logs | Streaming | The agent's submitted batch | No |

All seven senders accept any 2xx response as success and use a thirty-second timeout.

The log-destination row applies only to the `webhook` plugin, which sends each agent batch as a JSON POST to the configured URL. Other log plugins, including `filesystem`, `stdout`, and cloud streams, have different contracts. Their setup and diagnostics are in [2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md) and [8.2](../08-troubleshooting/8.2-log-surfaces.md).

<a id="three-settings-not-one"></a>

### Delivery intervals and their scope

The shared interval directly schedules failing-policy and host-status delivery. The same automation schedule also drives Jira and Zendesk collection and the scan that re-fires reset automations ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)). Changing its frequency affects that work too.

Vulnerabilities and calendar processing use separate intervals. Activity, migration, and log delivery respond to events rather than a schedule.

The vulnerability interval is a server startup setting. You can read it through the configuration API, but changing it requires deployment configuration and a server restart. It cannot be changed through the API or GitOps.

### The activity webhook, global or per fleet

The global activity webhook sends every activity on both Free and Premium. The per-fleet form, added in Fleet 4.91, requires Premium and sends only activities linked to hosts in that fleet. An activity with no host, such as a policy edit or a user sign-in, reaches the global webhook only.

Configure a per-fleet destination from the Hosts page or through the fleet's GitOps `webhook_settings.host_activities_webhook` setting. The **No fleet** host set accepts the same setting.

Both scopes use the activity sender's delivery contract: immediate POST, any 2xx as success, a thirty-second timeout, and retries only for `429`, for up to thirty minutes. Requests are unsigned, the destination is masked in error logs, and the dial-time private-address protection applies.

When an activity spans multiple fleets, each enabled per-fleet webhook receives a separate POST containing only that fleet's host IDs. Two fleets using the same destination URL still produce separate requests. If the global webhook is enabled, it receives the activity as well.

The payload includes `timestamp`, `actor_full_name`, `actor_id`, `actor_email`, `type`, and `details`. For batch activities whose stored details omit the host list, such as a bulk script run or software install, the per-fleet copy adds a `host_ids` array for that fleet. The global copy keeps its stored details unchanged. The added array has no size limit, so receivers must accommodate large batches.

If looking up the relevant fleet webhooks fails, Fleet logs the failure and drops the complete delivery set for that activity. Recording the activity proceeds regardless. Changes to a per-fleet webhook also omit the `enabled_activity_automations`, `edited_activity_automations`, and `disabled_activity_automations` records used for global-webhook changes. Those activity types therefore do not provide a history of per-fleet webhook configuration changes.

<a id="host-status-is-the-one-that-will-surprise-your-receiver"></a>

### Repeated host-status notifications

Fleet evaluates the host-status threshold on every pass and sends whenever it is met. It keeps no alert history, suppression state, or hysteresis, the buffer that would prevent repeated notifications as a value crosses back and forth over a threshold. A persistent condition produces a delivery every cycle.

Each payload contains every matching host identifier, without batching or a size limit, and has no timestamp. Global and per-fleet settings are evaluated separately, so overlapping populations produce overlapping notifications.

Record a receipt timestamp and make the receiver handle repeated, potentially large payloads. [4.5](../04-know-your-devices/4.5-monitor-fleet-wide-state.md) explains the same behavior when designing monitoring.

<a id="two-ways-delivery-is-lost"></a>

### Vulnerability and log delivery failures

A failed vulnerability POST ends that run. The subset delivered before the failure is nondeterministic, and the remaining newly detected vulnerabilities will not be delivered later. There is no delivery queue or replay.

The log webhook records a delivery error in the Fleet server log but does not report it to the agent or other log submitter. Monitor that server-side failure path alongside receipt at the destination.

<a id="one-filtering-surprise"></a>

### Vulnerability filtering by licence tier

Premium vulnerability automations retain findings only when the vulnerability has recent metadata. Free applies no such filter. Findings from other sources can still pass when their vulnerabilities meet that condition. Account for this difference when comparing event counts between tiers: Premium can deliver fewer events.

## Secure the receiver

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Put source authentication in front of a custom receiver. Fleet's seven senders issue plain JSON POSTs without a signature or configurable authentication header, so the payload itself cannot prove that Fleet sent it.

Use a gateway, proxy, or receiving service that authenticates the source before starting the workflow. Prefer API polling when you cannot establish that boundary. Avoid credentials in destination URLs: two senders include the unmasked address when wrapping delivery errors, which can expose the value in logs and diagnostics.

Validate payload fields before using them in downstream actions. Host names, serial numbers, and query results can originate on devices; their presence in a Fleet payload does not make them safe inputs to a command or another service.

<a id="the-private-address-change"></a>

### Private-address protection

Fleet 4.90.0 blocks private, loopback, link-local, and metadata-service destination addresses by default. The check occurs when establishing the connection, so an internal URL can pass configuration validation and save successfully while every delivery fails.

Choose the narrowest applicable exception if the design requires an internal receiver. A dedicated setting permits ordinary private ranges. Reaching loopback, link-local, or metadata addresses requires the broader bypass, which disables the protection generally. Review the destination design before using that broader setting.

## Build idempotent external workflows

![How-to](../_assets/icons/howto-light.svg) Design the receiving workflow so repeated delivery cannot cause an unintended repeated action. Fleet supplies no delivery identifier that distinguishes one send from another send of the same event.

Payloads contain entity and event fields, such as policy IDs, host IDs, vulnerability IDs, serial numbers, and timestamps. These can contribute to a key your receiver constructs, but they provide no universal deduplication contract. A repeated host-status notification may represent a new evaluation, and each calendar retry carries a fresh timestamp.

Build the receiver around three behaviors:

1. **Separate receipt from processing.** Acknowledge promptly, then perform the downstream work so a slow operation does not cause delivery to time out.
2. **Handle repetition deliberately.** Make the side effect safe to repeat or use an event-specific deduplication rule.
3. **Allow out-of-order events.** Fleet provides no delivery-order guarantee.

Pace any calls back into Fleet. A large host-status payload followed by one concurrent API call per host can create a burst against authenticated routes that have no Fleet rate limiter ([6.3](6.3-use-the-fleet-rest-api.md)).

## Observe, test, and recover delivery

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Track receipt and processing at the destination so you can tell whether a notification completed the intended workflow. Fleet-side records can help explain a gap, but each covers only part of the delivery path.

The scheduler's run record has no API or command-line read interface; inspecting it requires direct database access. Other observation points include:

| Source | What it shows |
|---|---|
| **Fleet activities** | Some automation executions, for types that record activities |
| **Fleet error diagnostics** | Recent failures, including some that contain destination addresses |
| **Server logs** | Delivery failures, including log-webhook errors reported nowhere else |
| **Receiver telemetry** | Which deliveries arrived and whether downstream processing completed |

Compare these records when delivery stops. [8.14](../08-troubleshooting/8.14-degradation.md) covers Fleet-side causes, including the failing-policies webhook's interaction with asynchronous host processing.

### Testing

Record and replay real payloads for every mechanism the receiver consumes. Testing one sender's shape does not establish compatibility with the others.

Exercise four cases: duplicate delivery, an out-of-order pair, a larger-than-expected payload, and receiver failure. Include a large host-status payload and confirm the retry behavior of each sender; most do not retry a failed POST.

### Recovering a missed delivery

Read current state through the API where Fleet retains it. You can recover an outstanding policy failure, vulnerability, or quiet-host condition while it remains present.

Migration-button presses, log batches, and calendar deliveries have no supported reconstruction or replay path. Their recovery depends on durable receipt in your own system.

### Rotating a destination

A destination change takes effect on the next send. In-flight requests continue to their original destination, and there is no queue to drain or record identifying which deliveries crossed the change boundary. Confirm receipt at the affected destinations when delivery continuity matters.

The log destination is a startup setting. Change it through server deployment configuration and restart the server; it cannot be edited as a runtime interface setting.
