# Design safe automation and control change

Five ways to drive Fleet from outside the console: three that change it, being a declarative repository, direct API calls and the supported command-line client; one that carries events out of it; and one that lets an AI assistant read Fleet and run live queries through Fleet's MCP server. This chapter owns what the first four share, so the chapters after it can stop repeating themselves; the assistant path has its own chapter, [6.6](6.6-connect-fleet-to-an-ai-assistant.md).

**Fleet exposes one control plane through several paths.** Reliable automation gives every field and action one owner, uses the path that suits the job, and **verifies the resulting state rather than trusting a successful invocation**. That last clause is the part's through-line, and Part V spent nine chapters on why it matters.

## Choose the automation path and declare ownership

![Explanation](../_assets/icons/explanation.svg) Three inbound paths and one outbound make up the control-plane model this chapter owns. They are not interchangeable, and Fleet will not stop you using two of the inbound three on the same field. The table below also lists the AI assistant/MCP path for completeness, but it is a read-mostly handoff covered on its own in [6.6](6.6-connect-fleet-to-an-ai-assistant.md), not part of this chapter's four-path model or diagram.

| Path | What it is for | What it cannot do |
|---|---|---|
| **GitOps** ([6.2](6.2-manage-fleet-with-gitops.md)) | Declared state, reviewed and reapplied | Anything not representable in its schema; anything needing a response |
| **REST API** ([6.3](6.3-use-the-fleet-rest-api.md)) | Requests and reads, custom clients | No reconciliation loop; you own convergence |
| **`fleetctl`** ([6.4](6.4-use-fleetctl.md)) | Supported shell work and pipelines | It is a client of the API, so it inherits the API's limits |
| **Webhooks** ([6.5](6.5-integrations-webhooks-and-external-workflows.md)) | Reacting to something Fleet noticed | Changing anything; delivery is one-way |
| **AI assistant, MCP** ([6.6](6.6-connect-fleet-to-an-ai-assistant.md)) | Letting a person drive Fleet in natural language, for reads and live queries | Changing configuration; it is a read-mostly client of the API with one destructive tool, bounded by its token's role |

### There is no owner field

This is the section's load-bearing negative.

**Fleet has no field-level ownership mechanism.** No annotation marking a resource as managed, no conditional-write token, no generation or version number, and no stale-write rejection. Two writers changing the same field do not collide; the second one wins, and neither is told.

Ordinary semantic conflicts still return a conflict status, a duplicate name being the obvious case. **What does not exist is optimistic concurrency**: nothing lets you say "write this only if it has not changed since I read it."

**And the activity record identifies the account, not the path.** A GitOps run, a `fleetctl` command and a custom client sharing one credential are indistinguishable afterwards.

Those are three separate problems and they need three separate answers. Conflating them is how people end up believing a naming convention has bought them safety.

> **Keep the ownership map outside Fleet**, because Fleet has nowhere to put it.
>
> **Serialise every ownership boundary through one workflow**, because nothing rejects an interleaved write.
>
> **Give each automated workflow its own API-only identity** ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)), because that is what makes activities attributable. One per *workflow*, not one per tool: a single workflow may reasonably use GitOps and direct calls together.
>
> The map prevents overlap, serialisation prevents interleaving, and the identity gives you the record. **A distinct identity on its own does none of the first two.**

Two features look like ownership controls and are not. **GitOps mode** makes supported interface controls read-only but authorizes nothing, so the API is unaffected. **The change-management exceptions** are enforced by the GitOps client rather than by the endpoints, so another writer is unaffected by them too. Both are useful governance. **Neither is a boundary**, and the difference matters when you are deciding what you can rely on.

### Verifying with a writer that cannot read

A deliberately narrow GitOps identity is good practice and creates a problem this chapter has to name: **it may not be able to read the evidence that its own change worked.** Host details, activities and software-install results are all separately authorized, and an identity scoped tightly enough to be a safe writer can be denied all three.

**The answer is a second, read-only identity for verification, not a wider writer.** Widening the writer to make verification convenient defeats the reason it was narrow.

### Detecting drift

There is no drift report. The nearest thing is exporting your configuration and comparing it against your repository, and the export is a hidden command that omits sensitive values, declares some state unsupported, and does not diff anything. **It is a lossy structural export from which you can build a check, not a detector.** Plan to verify the state it cannot see some other way.

### A note on Terraform

Four things, because a reader who goes looking will find all four and they are not the same:

1. **Terraform modules for deploying the Fleet service** are real and belong to [Part II](../02-administer-and-deploy-fleet/2.3-deploy-on-aws-or-gcp.md).
2. **Managing Fleet's contents** is GitOps or the API. That is this part.
3. **There is an unpublished provider in Fleet's own tree**, with a single resource and a note saying publishing it is future work. It is development work, not a supported option.
4. **Community providers** exist outside what this manual verifies.

## Authenticate automation clients

![Reference](../_assets/icons/reference.svg) One credential type, and four others that are not it.

**There is no separate "automation token."** Signing in returns a session key. The API expects that same value after the word `Bearer`, which is the HTTP transport scheme rather than a second kind of token. An API token *is* a session key belonging to an API-only user.

That has three consequences worth knowing before you build against it:

| | Regular user | API-only user |
|---|---|---|
| **Session lifetime** | An **inactivity** timeout, five days by default, measured from last use | **Unlimited** |
| **What renews it** | Using it | Nothing needs to |
| **Reported expiry** | Meaningful | **Reported from the global setting, and wrong** |

**Do not trust the reported expiry on an API-only session.** It is computed from the general duration and does not reflect the exception that makes the session unlimited.

**Where the credential lives.** `fleetctl` stores it in a named context in a plain-text configuration file, created at owner-only permissions on macOS and Linux. **Windows does not enforce those permission bits**, so there the file's protection is whatever the filesystem gives it.

**What restrictions exist.** Premium can restrict an API-only user to a list of endpoints. It intersects with the role: it can narrow what a role permits and can never grant anything the role denies, and an empty list restricts nothing. **Treat it as defence in depth over the real boundary**, which remains role and scope ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)), rather than as the boundary itself.

### Four credentials that are not API credentials

Confusing any of these with an API token leads somewhere unhelpful:

- **An enroll secret** authorizes a device to enroll. It manages nothing.
- **A device token** reaches that one device's own pages, and has a freshness requirement measured in an hour.
- **An MDM identity certificate** authenticates a device to device endpoints.
- **Host and agent node keys** are the agent's credentials, not an administrator's.

### Revocation is not cancellation

**Revoking a credential stops the next request. It does not stop work already queued.** A script, an install or an MDM command ordered by a credential you have just revoked still runs, because queued work has no link back to the session that created it.

If a credential is compromised, revoke it *and* deal with what it started. Section six has the sequence.

## Manage automation secrets

![How-to](../_assets/icons/howto.svg) Where Fleet protects a value, and where it does not.

**Fleet secret variables** are the mechanism designed for this. Values are stored encrypted with the server private key, list responses omit them, and what your script or profile retains is a placeholder substituted at delivery. A stored variable nothing references is not removed automatically. Using them needs the server private key configured.

**Ordinary environment substitution in GitOps is different**: it happens on the client, and Fleet stores the result. The variable is a build convenience, not a secret store.

Three boundaries worth knowing precisely, because assuming the wrong one is how secrets escape:

> **Masking on read is not encryption at rest.** Selected third-party credentials in your configuration are masked when the API returns them. That is not the same as being encrypted in the database, and only specific stores get real application encryption. **Treat a database backup as credential material** ([7.2](../07-operate-fleet/7.2-back-up-and-restore-service-state.md)).
>
> **Fleet does not redact output.** Stored inputs keep their placeholders, but results do not: script output, install and post-install output, uninstall results and setup-experience errors are stored as they came back. A secret echoed by a failing command is stored as text. [5.3](../05-manage-devices/5.3-run-and-manage-scripts.md) and [5.4](../05-manage-devices/5.4-manage-software-and-applications.md) own the authoring rules; the boundary to remember here is that **there is no general redaction anywhere on the output path.**
>
> **Do not put credentials in a webhook destination.** A destination is not masked the way other integration values are.

## Design for repetition and ambiguous outcomes

![Explanation](../_assets/icons/explanation.svg) The section that decides whether your automation can safely run twice.

**Fleet has no general idempotency contract.** No idempotency key, no request identifier you supply, and no conditional write. If a request times out, nothing in the protocol tells you whether it landed.

> **The usual heuristic is backwards here.** In most APIs a PUT is safe to repeat and a POST is not. **Fleet's declarative endpoints are POST**, so the method tells you nothing. Retry safety is a property of the specific endpoint and the current state, not of the verb.

### What to key on instead

Since the protocol will not make a write idempotent for you, make the result *findable*.

**Handles Fleet gives you** and you should keep: numeric resource identifiers, profile identifiers, script execution identifiers, command identifiers, batch execution identifiers.

**Scoped business keys** you can reconcile against: a fleet's name, and a label or secret-variable name globally. Beyond those, use the identity contract the endpoint documents rather than assuming a name is unique within its fleet.

**Never key on** an enroll secret, a node key, a session key, or Fleet's internal deduplication values. Those are credentials or implementation details.

### After an ambiguous write

**Read, then decide.** Do not retry blindly.

Some duplicate protection exists and is easy to over-read. A second install request for the same installer is refused while one is pending, but that refusal **does not prove your request created the pending work**, and once the pending state clears another request creates new work. "Already exists" is evidence to investigate, not an acknowledgement of your original call.

### A successful call is not a converged state

Three examples worth internalising, because they are the shapes everything else follows:

| You call | You get | What it means | Convergence evidence |
|---|---|---|---|
| **Apply profiles** | Success, no content | Fleet accepted the desired state | The per-host profile operation and status, **interpreted per platform** ([5.2](../05-manage-devices/5.2-manage-configuration-profiles-and-declarative-settings.md)) |
| **Run a script asynchronously** | Accepted, plus an execution identifier | It is queued | The execution's result. **An offline host can leave it pending indefinitely; there is no server-side deadline** |
| **Install software** | Accepted, and an empty body | It is queued. Fleet has an execution identifier for it; **the response does not give it to you**, though the host's upcoming activities show it while it is pending | Two different reads answering two different questions: the host's execution record for whether the install *ran*, and inventory for whether the software is *present*. They are not equivalent |

The middle row is the one to design around. **If your automation needs a script to have finished, your automation needs its own deadline and its own stop condition**, because Fleet will not impose one.

## Test before production

![How-to](../_assets/icons/howto.svg) A ladder, and an honest account of what each rung cannot do.

1. **Check your YAML parses.** A generic syntax check, and nothing more: it is not Fleet validation and knows nothing about Fleet's schema.
2. **Validate against a reachable Fleet instance.** **There is no offline Fleet validation.** GitOps validation authenticates, checks the server version, and reads configuration, labels and fleets before it even looks at your files, so the first rung that tells you anything about Fleet needs a Fleet to talk to.
3. **A separate Fleet instance**, where you own everything and can break anything.
4. **A test fleet on the real instance**, with the limits below.
5. **A bounded production target**, chosen deliberately.
6. **Promotion**, with the verification from section six.

### What a test fleet cannot isolate

This is worth being exact about.

**Global settings, users and secret variables are instance-wide.** A test fleet does not isolate them, because they do not belong to a fleet.

> **And your test fleet's hosts still run applicable global policies and enabled global scheduled reports.** Fleet-level isolation cannot opt them out. Platform and label targeting still decide whether a particular item applies, but *the fleet boundary is not what decides it.*
>
> If what you are testing is global, a test fleet is not a test environment. Use a separate instance.

**Labels need care.** Label definitions can be fleet-scoped, but **label names are instance-global**. Reusing a production label name in a test fleet fails, or, if the same GitOps run removes it from production and adds it to test, *moves* the label. Use test-specific names and the question never arises.

**There is no "run this policy once."** Test the query as a live query against a bounded set of hosts, then apply it as a policy in an isolated fleet and wait for a real scheduled result before promoting it. [5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md) explains why the difference between a live result and a scheduled one matters.

**If you use Fleet's preview environment, pin it.** It defaults to the latest server image and to preview assets from the development branch, neither of which is the version you are testing against.

## Review, verify, and recover

![Troubleshooting](../_assets/icons/troubleshooting.svg) Evidence, and a sequence for when something is wrong.

### What the audit trail does and does not give you

**Activities are not a general access log.** They record who changed what. Most reads and all authorization denials are absent, so a failed attempt to do something leaves no trace you can query. **Selected sensitive reads are the exception and do produce activities**, including reading a disk-encryption key or viewing a Recovery Lock credential ([5.8](../05-manage-devices/5.8-enforce-disk-encryption-and-manage-recovery-credentials.md), [8.12](../08-troubleshooting/8.12-audit-logs.md)).

What is recorded: the account, its name and email, and the change. **An API-only identity is distinguishable from a human while that account still exists**, though the marker is resolved at read time from the live user, so it disappears once the account is deleted. Policy-driven work is attributed to Fleet rather than to a person ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)), but token-driven work is not flattened that way.

What is not recorded: which path made the change, the session or token used, the client, the user agent, or the source address for anything but sign-in. **A pipeline and a person sharing one account cannot be told apart**, which is what the separate-identity convention above is for.

### Recovering from an automation that did the wrong thing

In order, because the order matters:

1. **Stop new requests.** Pause the pipeline or the schedule. **Revoking the credential is not this step**: it prevents new calls but does not stop what is already queued.
2. **Cancel what is still cancellable.** Two routes exist: cancelling an item on a host's upcoming list, and cancelling a batch script run. Cancelling removes the queued item even after it has been activated, but **after activation it is a race against the device fetching the work**. Activated lock and wipe are refused outright.
3. **Establish what already crossed into device execution.** That work cannot be recalled. Custom MDM commands have no cancellation route at all.
4. **Apply the corrective state.** For GitOps that means applying a known-good complete commit, which is a forward apply rather than a rollback. **For the API there is no general undo**: a read response is not usually a valid restore payload, so recovery means keeping your pre-change request, or constructing the documented request that sets the resource back.
5. **Verify.** Not that your call succeeded, which is where this chapter started, but that the state and the devices agree.

### The pre-change contract

Change control is the point of this chapter, and it comes down to what you can state **before** the change rather than what you can explain afterwards. Six things, and if any of them is missing the automation is not ready:

| | |
|---|---|
| **Owner and identity** | The logical owner of the boundary, and the API-only identity that will execute |
| **Target and intent** | Exactly what is being changed, and to what |
| **Evidence** | What you will read in Fleet, and what you will check on a device |
| **Stop condition** | What observation halts it, the deadline, and **who is allowed to decide** |
| **Correction** | The corrective request, or the known-good commit to reapply |
| **Correlation** | Your change reference, the commit, and the preserved output of the run |

The last row exists because **Fleet records no run or request correlation marker of its own** ([6.2](6.2-manage-fleet-with-gitops.md)). If your pipeline does not keep that link, nothing does. It is also where the separate read-only verification identity naturally appears.

If nobody except the author can halt it, the automation is not ready for production.
