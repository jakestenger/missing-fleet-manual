# Connect an AI assistant to Fleet

![Explanation](../_assets/icons/explanation.svg) Fleet includes an MCP server in its source: a small program that gives a compatible AI assistant named tools for reading Fleet, and, if you allow it, running live osquery against your devices. This chapter helps you decide what data and authority an assistant may receive, choose how it connects, build the server for the release you run, and tell a working connection from a safe and complete one.

It does not teach the Fleet REST API itself; [6.3](6.3-use-the-fleet-rest-api.md) owns that, and this server is a client of it. It does not teach how to write osquery, which is [4.2](../04-know-your-devices/4.2-run-queries-and-reports.md) and [4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md).

MCP is the Model Context Protocol, an open standard for how an assistant discovers and calls external tools; it is defined in [a.6](../09-appendices/a.6-glossary-and-release-compatibility.md) and its specification is linked as further reading. Fleet distributes the server as source inside its repository rather than as a prebuilt download, so running it starts with a build.

## What sits between the assistant and Fleet

![Explanation](../_assets/icons/explanation.svg) The MCP server is a thin proxy. It holds one Fleet API token, advertises a set of tools to an assistant, and turns most tool calls into ordinary Fleet REST API calls using that token. It stores no fleet data of its own and grants no access the token does not already carry, so Fleet authorizes every Fleet-backed call exactly as it would if you had made it with `fleetctl` or `curl`. Three tools sit outside that boundary and never reach Fleet at all: `get_vetted_queries` reads a query library bundled into the server binary; `get_osquery_schema` reads the server's current in-memory osquery schema, which begins as a bundled snapshot but is replaced whenever a background refresh from `raw.githubusercontent.com` succeeds; and `refresh_osquery_schema` forces that same fetch on demand. See [A.11](../09-appendices/a.11-mcp-tool-reference.md) for which rows these are.

Fleet data crosses four systems on its way to an answer: Fleet, the MCP server, the model service, and the assistant application. A fault or a data-exposure decision can live at any of them. The transport wires the near end; it does not decide where the data ends up. So before you connect anything, settle whether the assistant's model service is approved to receive what these tools return: hostnames, serials, IP addresses, local usernames, software inventory, policy detail, and live-query output.

The MCP client reaches the server one of two ways, and the difference decides where the connection's trust boundary sits.

Over **stdio**, the client launches the server as a local subprocess and speaks to it on standard input and output, so there is no network hop. **`MCP_AUTH_TOKEN` performs no authentication under this transport at all**: the server checks once at startup that it is set and long enough, then never asks for it again. The token is a configuration guard rather than an access control, and the boundary is whoever can launch and talk to that local process.

Over **SSE** (Server-Sent Events), the client connects across HTTP and the server checks the bearer on every MCP request, the unauthenticated `/healthz` probe aside, so the boundary is the token and the TLS in front of it. The tools behave identically on both.

Reads resolve synchronously, though not always in a single request. A simple read makes one or a few Fleet API calls. Other tools make many calls and merge the answers: listing saved reports (`get_queries`) or policies calls Fleet once per fleet, and a vulnerability or affected-software question issues a request per matching item; and a few, such as the vetted-query library, come from data bundled into the server rather than from Fleet at all.

Running a live query is the exception. Fleet dispatches it to devices and collects results over Redis, so it is asynchronous, and the server waits a bounded period for online hosts to report before returning what it has. A single-host live query uses Fleet's synchronous ad-hoc query for that host; a multi-host run opens an ad-hoc campaign whose query is not saved, and streams results as hosts answer.

## The tools the assistant sees

![Reference](../_assets/icons/reference.svg) The assistant sees a catalogue of typed tools across four areas (hosts, queries, policies and vulnerabilities, and inventory) each with named arguments it fills in, rather than Fleet's endpoints. An assistant handles "list the failing Linux hosts for policy 42" far more reliably against a named tool with a `platform` argument than against a REST path it has to construct and paginate.

| Area | Tools | What the assistant can do |
|---|---|---|
| **Hosts** | `get_endpoints`, `get_host`, `get_host_policies`, `get_total_system_count`, `get_aggregate_platforms`, `get_fleets`, `get_labels` | List and filter enrolled hosts, read a selected projection of one host (not Fleet's full host detail), read a host's per-policy pass/fail, and read fleet-wide counts by platform |
| **Queries** | `get_queries`, `prepare_live_query`, `run_live_query`, `get_osquery_schema`, `refresh_osquery_schema`, `get_vetted_queries` | List saved reports, fetch the osquery schema, validate targets, and run live osquery against devices |
| **Policies and vulnerabilities** | `get_policies`, `get_policy_compliance`, `get_policy_hosts`, `get_vulnerability_impact`, `get_vulnerability_hosts` | Read policy pass/fail counts, list the hosts on either side of a policy, and find the hosts a CVE affects |
| **Inventory** | `get_software`, `get_host_users` | Read stored software and local user accounts from Fleet's cached inventory, without touching the device |

**A host list is a page, not a census.** The host-listing tools cap a page at 200 and do not paginate the whole fleet for you. The ones that answer "which hosts" (failing a policy, affected by a CVE) return that capped page with no running total, so above the cap a returned list is a partial first page, not the full set.

Read a count question, like how many hosts fail policy 42, from the counting tools rather than from the length of a list. Even a count can be a floor: the 10,000-host ceiling applies per underlying fetch, not to the merged total, so an aggregate that fans out across several fetches (a CVE affecting multiple software versions, for example) can undercount each fetch past its own cap while still reporting a combined figure above 10,000.

A filtered live query resolves up to 500 matching hosts as its targets and previews at most 100 of them. When the preview is truncated, narrow the filter rather than trusting it to cover everything; matches beyond 500 are not queried. One filter pair does not narrow the way it reads: setting both `label` and `platform` does not intersect them, the label wins and `platform` is silently dropped, so SQL authored for one operating system can run against labeled hosts on another. Scope by `label` or by `platform`, not both, and confirm the previewed targets are the machines you meant before firing.

The tools also resolve hosts by identity, run a best-effort schema check on live queries before running them, and work around Fleet's weaker filters.

A numeric host ID goes straight through, and a name matching several hosts returns a candidate list for the assistant to choose from rather than a silent pick, because Fleet allows hosts to share a hostname.

A live query is checked before it runs, and it helps to know which half is enforced: the server rejects the common mistake of comparing a text column against a bare integer (except a literal `0` or `1`, let through as a boolean-style flag), a mistake Fleet would otherwise answer with zero rows. But fetching the schema and previewing the targets first are steps the assistant is advised to take rather than gates the server requires; it resolves the query's targets itself when the query runs.

A CVE or platform question is composed from several Fleet calls, because Fleet's own single filter for those is unreliable at this release. That composition is imprecise in the other direction: for a CVE the server finds the affected software titles, then fetches hosts for every version of each title, including versions the CVE does not affect. So the CVE tools can over-report, listing and counting hosts that run an unaffected version of an affected title. Read their output as a set to confirm against a host's own software inventory, not an authoritative remediation list or exposure count.

The inventory tools read Fleet's stored inventory, so they answer for a host that is currently offline, where a live query reaches only hosts online during its wait. Their answers are only as current as the last successful collection of the relevant detail, which runs on Fleet's inventory interval and only for the platforms and features that gather it; an ordinary check-in does not by itself refresh software or user records, so read freshness against [4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md) and [4.4](../04-know-your-devices/4.4-understand-software-and-vulnerabilities.md). Prefer the inventory tool when either would answer: it is cached and spends no device CPU. The tools' exact arguments are in [a.11](../09-appendices/a.11-mcp-tool-reference.md); the REST routes underneath them are in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md).

## Read-only is not the same as harmless

![Explanation](../_assets/icons/explanation.svg) Every tool carries a hint telling a cooperating client whether it only reads. All but one are read-only; `run_live_query` is marked destructive, and a well-behaved client such as Claude Desktop prompts before it fires.

It counts as destructive even for a `SELECT` because a live query runs arbitrary osquery on every targeted device: it consumes device CPU and may appear in endpoint detection and response (EDR) alerts and logs, and osquery's schema documents tables whose job is reading local files or reaching cloud-metadata endpoints over the network, so a query is not confined to the passive read a `SELECT` usually implies. That is an osquery capability, the same one Fleet's console and `fleetctl` expose, drawn from the schema rather than from running such a query end-to-end; the server does not special-case it.

What is enforced and what is merely advised are different things, and an administrator has to tell them apart:

- **The API-only identity** is checked by the server at startup, once.
- **Role and fleet scope** are enforced by Fleet on every call, so an observer token gets a permission error the moment it attempts a live query, and a token scoped to two fleets cannot read a third.
- **An endpoint allowlist** narrows an API-only user beyond its role. On Premium, Fleet permits a request only when its route appears in both Fleet's route catalog and that user's own list. This is maintenance work, not a one-time checkbox: the list must cover the full route set the tools use (the startup identity check, each tool's own routes, and the secondary calls its fan-out paths make), and it has to be re-derived when the tools change. [A.11](../09-appendices/a.11-mcp-tool-reference.md) gives that route set per tool, and two starting profiles are below; build and test the result against your own deployment rather than treating it as a quick lock-down. One route the allowlist cannot cover at all: the live-query results stream authenticates its own bearer token when the connection opens instead of going through the allowlist check, so a partial list still lets a token that can start a multi-host run read that run's results back.
- **Schema-first preparation, target preview, and the confirmation prompt** are advice to a cooperating assistant, not gates the server keeps. A prompt-injected client can skip them, and `run_live_query` resolves its own targets when it runs, so a preview is a look and not a locked transaction.

So the token is the security decision, and your Fleet edition shapes it. A read-only deployment gives the server an **observer** token on either edition. Running live queries needs a role permitted to run them. On Fleet Premium the least-privilege choice is **Observer+**; **Technician**, **maintainer**, and **admin** also qualify, though Technician carries broader device-change power than the query work needs. Fleet Free has neither Observer+ nor Technician, so it uses a **maintainer** or **admin** identity. Give the server the lowest such role.

The server adds one requirement of its own on both editions: it refuses to start unless its token belongs to an **API-only** Fleet user (no console session, its own audit identity), and the check fails closed, so an unreachable Fleet or an invalid token stops startup. Two ways to narrow that user further are Premium only: scoping it to specific fleets, and restricting it to an endpoint allowlist. On Free the API-only user is global. Creating that user is covered under service identities in [2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md), and the roles are [1.4](../01-foundations/1.4-identity-and-roles.md).

After configuring it, confirm the boundary from both sides: run one operation the role allows and one it should deny, and check Fleet returns the permission error for the second.

### Two starting allowlist profiles

![Reference](../_assets/icons/reference.svg) Both are read from [A.11](../09-appendices/a.11-mcp-tool-reference.md)'s per-tool route lists, de-duplicated, plus `GET /me`. The server's startup identity check calls `GET /me` once regardless of role, and Fleet applies the same catalog-membership and user-allowlist check to it as to any other route for a restricted API-only user, with no exemption. Leave it off the list and the server fails closed at startup for that user, before any tool ever runs. Confirm the full set against your own deployment before relying on it, and re-derive both lists whenever the tools change or a new one is added. These routes use A.11's shorthand: each drops the common `/api/v1/fleet` prefix that an allowlist entry cannot. Fleet matches the literal submitted path, so restore the prefix on every route and submit each as a full `{"method", "path"}` pair, exactly as A.11 shows: its `GET /hosts` row becomes `{"method": "GET", "path": "/api/v1/fleet/hosts"}`. Copy the profile that matches your case and adjust it, prefix restored; there's no need to retain the individual routes.

- **Read-only** (every tool except `run_live_query`): `GET /me`, `GET /hosts`, `GET /hosts/count`, `GET /hosts/{id}`, `GET /hosts/identifier/{identifier}`, `GET /hosts/{id}/software`, `GET /host_summary`, `GET /labels`, `GET /labels/{id}/hosts`, `GET /fleets`, `GET /fleets/{id}/policies`, `GET /fleets/{id}/policies/{policy_id}`, `GET /global/policies`, `GET /global/policies/{id}`, `GET /software/titles`, `GET /software/titles/{id}`, `GET /reports`.
- **Read plus live query**: the read-only list above, plus `POST /hosts/{id}/query` and `POST /reports/run` for running queries. It cannot add the results stream, since that route sits outside the allowlist mechanism entirely (above): anyone who can reach `POST /reports/run` can already read what it returns.

A profile is inert until it is attached to the API-only user, and this is the step that turns a list of pairs into a restriction. An API-only user created with no allowlist is unrestricted, reachable on every route its role allows, so attach the profile when you create the identity rather than in a second step. The allowlist is Premium, like the fleet-scoping above. Pass the pairs as `api_endpoints`, each with its `/api/v1/fleet` prefix restored:

```bash
export FLEET="https://fleet.example.com"
export TOKEN="your-admin-api-token"

curl -sS --fail-with-body -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "MCP server",
    "global_role": "observer",
    "api_endpoints": [
      {"method": "GET", "path": "/api/v1/fleet/me"},
      {"method": "GET", "path": "/api/v1/fleet/hosts"}
    ]
  }' \
  "$FLEET/api/v1/fleet/users/api_only"
```

Put every route from the profile you chose in that array. Fleet generates the user's email and password itself and returns the API token in the response; capture that token, because it is the identity the server authenticates with. To narrow an API-only user that already exists, send the same `api_endpoints` in a `PATCH` to `/api/v1/fleet/users/api_only/{id}`; sending `"api_endpoints": null` there clears the list and returns the user to unrestricted, which is the state to avoid. Read the user back afterward and confirm the stored entries match the profile you intended.

The server also guards its own front door. The client's bearer token must be at least 32 characters, and the server refuses a weaker one; `openssl rand -hex 32` satisfies it. Over SSE the server speaks plain HTTP, so a non-loopback SSE deployment belongs behind a TLS-terminating proxy, which a managed platform's edge already provides. The stdio transport has no network hop and sidesteps this.

## Choose a transport and scope the token

![How-to](../_assets/icons/howto.svg) Before the build, settle how the assistant connects and what its token may do. Both are easier to get right at the start than to change once an assistant is wired up.

Transport follows topology. Use **stdio** when the assistant runs on the same machine as an operator, as Claude Desktop does: the client launches the server as a subprocess, with no port to expose and no TLS to terminate. Use **SSE** when the assistant is a separate or remote client, such as Claude Code or Cursor, where a network endpoint is unavoidable and you own the TLS in front of it. Client capability decides which a given assistant can use; the brand does not fix the transport. Set it with `-transport`, and note that only the literal value `stdio` selects the local transport: any other value, a typo included, starts the network-facing SSE listener rather than refusing to run. Confirm the server's first startup log line names the transport you intended (`transport: stdio` or `transport: SSE`).

Token role follows the assistant's job. Give it an **observer** token when its work is reading posture, inventory and compliance, and the destructive tool cannot fire. Give it **Observer+** when it needs to answer live questions the stored inventory cannot, and accept that the assistant can then run osquery against devices, bounded by the token's fleet scope, with the client's confirmation prompt as an advisory check rather than an enforced one. Pick the lowest role the real work needs.

Prerequisites, once those are settled: a reachable Fleet instance, an API-only Fleet user at the role you chose ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)) and its API token, an MCP-capable assistant, and Go 1.26.5 or newer to build the server.

## Build and connect the assistant

![How-to](../_assets/icons/howto.svg) Build the server from Fleet's source at the release you run, so the tool matches the server it talks to.

```bash
git clone https://github.com/fleetdm/fleet
cd fleet/cmd/fleet-mcp
git checkout fleet-v4.90.0
go build -o fleet-mcp .
```

The built binary carries an embedded copy of the osquery schema and serves it immediately. About two seconds after startup it attempts a background refresh from the schema file on Fleet's `main` branch, and repeats that every 24 hours by default. A successful refresh replaces the in-memory copy, and a failed one leaves the previous copy untouched. That keeps column types current. It also means the schema it validates against tracks `main` rather than your release, and fetching it needs outbound access.

Change the interval with `FLEET_MCP_SCHEMA_REFRESH_INTERVAL`, a Go duration string such as `12h` or `6h30m`; an unset or unparseable value falls back to the 24-hour default rather than failing startup. The variable is read once at startup, so changing it needs a restart to take effect.

In a strictly release-pinned deployment, stop the startup/periodic fetch by setting `FLEET_MCP_SCHEMA_REFRESH_DISABLE` to any non-empty value (for example, `export FLEET_MCP_SCHEMA_REFRESH_DISABLE=1`), and the binary serves only its embedded snapshot until restarted. This does not disable `refresh_osquery_schema`: that tool calls the same GitHub fetch unconditionally, on the assistant's request, regardless of the variable. For a genuinely air-gapped deployment, also block outbound access to `raw.githubusercontent.com` at the network layer, or maintain a custom build that drops the tool's registration.

Generate the value for `MCP_AUTH_TOKEN` next. The server requires it at startup on every transport, including stdio, and will not start without it (Fleet MCP rejects anything under 32 characters; `openssl rand -hex 32` produces 64). Under SSE this same value is the client bearer the caller sends on every request; under stdio it authenticates nothing and stays a startup guard, as the transport section above explains.

```bash
export MCP_AUTH_TOKEN="$(openssl rand -hex 32)"
```

Reuse `$MCP_AUTH_TOKEN` in every step below rather than retyping the value; a shell variable does not survive into a JSON config file, so for the config-file clients further down, run `echo "$MCP_AUTH_TOKEN"` once and paste that literal value in. These commands assume the same shell session as the export above; in a new session, re-export the same value first.

The rest of this section splits by the path you are on: a local desktop client over stdio, an SSE client, a direct smoke test of the server, and a supervised production deployment. Read the one you need.

### Connect Claude Desktop over stdio

For **Claude Desktop over stdio**, the assistant launches the binary directly and reads its environment from its own JSON config rather than any `.env` file. Point it at an absolute path, because a leading `~` is not expanded.

Edit `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS:

```json
{
  "mcpServers": {
    "fleet-mcp": {
      "command": "/absolute/path/to/fleet-mcp",
      "args": ["-transport", "stdio"],
      "env": {
        "FLEET_BASE_URL": "https://your-fleet.example.com",
        "FLEET_API_KEY": "the API-only user's token",
        "MCP_AUTH_TOKEN": "the value printed by echo $MCP_AUTH_TOKEN above (JSON can't read a shell variable)",
        "LOG_LEVEL": "info"
      }
    }
  }
}
```

On Apple Silicon, ad-hoc sign the binary after building it, and again after each rebuild, before Claude Desktop will launch it. Gatekeeper caches the signature against the file's identity, so replacing the binary at the same path invalidates the earlier approval and the launch fails silently.

```bash
codesign --force --sign - ./fleet-mcp
```

Fully quit and relaunch the assistant, not just its window, and the tools appear in its context. The Claude Desktop specifics here (the confirmation prompt on the destructive tool, reading environment from the JSON config, the ad-hoc signing step, and the full relaunch) describe that client and macOS at the time of writing, not behaviour Fleet enforces, so confirm them against your client and OS version if they differ.

### Connect an SSE client

For **Claude Code, Cursor, or another SSE client**, run the built binary so it listens for SSE connections. Supply `FLEET_BASE_URL`, `FLEET_API_KEY` and `MCP_AUTH_TOKEN` through the process environment, or through a `.env` file that the binary reads from its working directory. Run it from the directory that holds the file. It listens on `PORT`, default 8080.

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
# MCP_AUTH_TOKEN is already exported from above; re-export it here if this is a new shell
./fleet-mcp            # transport: SSE, listening on :8080
```

### Smoke-test the server directly

Confirm the binary works on its own before wiring a client to it, by driving it directly over stdio JSON-RPC. This isolates a server or token fault from a client-configuration fault:

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
# MCP_AUTH_TOKEN is already exported from above; re-export it here if this is a new shell

cat <<'EOF' | ./fleet-mcp -transport stdio
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"1.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_total_system_count","arguments":{}}}
EOF
```

Only a successful `tools/call` result, one that returns the enrolled-system count rather than an error result (a bad token or a missing permission still returns a valid response, just an error one), confirms that the server, its Fleet token, and stdio all work. Swap the `tools/call` line for any other tool, e.g. `get_host_policies` with a `host_id` argument, to exercise it directly. Then point the client at the `/sse` path with the bearer token as an `Authorization: Bearer` header, and terminate TLS in front of any endpoint that is not localhost, because the server speaks plain HTTP.

### Deploy a supervised SSE server

For a real SSE deployment, run the binary as a supervised service rather than a foreground process: put it under a process manager that restarts it, behind the TLS-terminating proxy, and give it the deployment-level settings that matter: `PORT`, `LOG_LEVEL` kept off `debug` where logs are centralized, `FLEET_CA_FILE` if Fleet presents a private CA, `FLEET_LIVE_QUERY_REST_PERIOD` at or above the Fleet server's own, and the schema-refresh controls if you need to pin or disable the outbound schema fetch. A managed platform supplies the supervisor and the TLS edge; a self-hosted deployment owns both.

### A worked example: systemd behind Caddy

One pairing that satisfies all of that on a self-hosted box: a systemd unit that restarts the binary, behind Caddy terminating TLS in front of it. The commands below assume a Debian or Ubuntu host with systemd, UFW as the firewall, OpenSSH and Caddy already installed, a DNS name that resolves to the box, and port 443 reachable from your clients. On another distribution the package manager, firewall tool, and service account command differ, but the shape of the deployment does not.

Create the service account and install the binary first:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin fleet-mcp
sudo cp ./fleet-mcp /usr/local/bin/fleet-mcp
sudo chown root:root /usr/local/bin/fleet-mcp
sudo chmod 755 /usr/local/bin/fleet-mcp
```

Then write the environment file, owned by that account and readable only by it:

```bash
sudo mkdir -p /etc/fleet-mcp
sudo tee /etc/fleet-mcp/env > /dev/null <<EOF
FLEET_BASE_URL=https://your-fleet.example.com
FLEET_API_KEY=the API-only user's token
MCP_AUTH_TOKEN=$MCP_AUTH_TOKEN
EOF
sudo chown fleet-mcp:fleet-mcp /etc/fleet-mcp/env
sudo chmod 600 /etc/fleet-mcp/env
```

`/etc/systemd/system/fleet-mcp.service`:

```ini
[Unit]
Description=Fleet MCP server
After=network.target

[Service]
Type=simple
User=fleet-mcp
EnvironmentFile=/etc/fleet-mcp/env
ExecStart=/usr/local/bin/fleet-mcp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`/etc/fleet-mcp/env` (written above) holds `FLEET_BASE_URL`, `FLEET_API_KEY`, and `MCP_AUTH_TOKEN`, world-unreadable and owned by the `fleet-mcp` user; `PORT` only needs setting if something else on the host already holds 8080. The binary already shuts down cleanly on SIGTERM, so `systemctl restart fleet-mcp` and a crash both leave `Restart=on-failure` to bring it back.

Install the unit file, but do not start the service yet; close the cleartext port first:

```bash
sudo tee /etc/systemd/system/fleet-mcp.service > /dev/null <<'EOF'
[Unit]
Description=Fleet MCP server
After=network.target

[Service]
Type=simple
User=fleet-mcp
EnvironmentFile=/etc/fleet-mcp/env
ExecStart=/usr/local/bin/fleet-mcp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
```

The binary binds its plain-HTTP port on every interface, and at this release it has no option to bind loopback only, so starting the service would expose `8080` to the whole network, not just to the proxy in front of it. Terminating TLS at Caddy does not change that: the cleartext port stays open beside the encrypted one. Put an active firewall rule in place before the listener ever starts, so the port is never reachable from off the box, not even in the window between starting the unit and adding the rule:

```bash
# Allow what must stay reachable BEFORE the firewall is active, or enabling it
# drops your own SSH session:
sudo ufw allow OpenSSH
sudo ufw allow 443/tcp
# ufw already exempts loopback, so Caddy's localhost:8080 hop keeps working:
sudo ufw deny 8080/tcp
# Enable the firewall (harmless if already active), then confirm it:
sudo ufw --force enable
sudo ufw status verbose
```

`ufw deny` protects the port only once the firewall is actually active: on a host where ufw is installed but inactive the rule sits dormant and `8080` stays open, so the `ufw status verbose` line is the one that matters. It should report `Status: active` with a deny rule for `8080`. On a cloud host the equivalent is a security-group rule that leaves `8080` off the ingress list entirely, applied before the instance starts the service; only `443` needs to be reachable. Either way the assistant reaches Fleet MCP through Caddy on `443`, and nothing external should reach `8080` directly.

With the cleartext port closed and the firewall verified active, start the service:

```bash
sudo systemctl enable --now fleet-mcp
```

Caddy needs one line, because it forwards headers unchanged and does not buffer a streamed response. Add it to `/etc/caddy/Caddyfile` and reload:

```
your-mcp-host.example.com {
    reverse_proxy localhost:8080
}
```

```bash
sudo systemctl reload caddy
```

Confirm the negative case along with the positive one. Only the header differs between the last two:

```bash
curl -i https://your-mcp-host.example.com/healthz
# → 200, unauthenticated by design

curl -i https://your-mcp-host.example.com/sse
# → 401, no Authorization header reached the server

curl -N --max-time 2 -i -H "Authorization: Bearer $MCP_AUTH_TOKEN" https://your-mcp-host.example.com/sse
# → 200 and the stream opens; --max-time caps an otherwise endless read
```

Then prove the cleartext port is actually closed, from a different machine on the network rather than from the host itself:

```bash
curl -i --max-time 2 http://your-mcp-host.example.com:8080/healthz
# → connection refused or a timeout; a 200 here means 8080 is still exposed, so fix the firewall
```

nginx or another reverse proxy works the same way in principle: forward `/sse` and `/message` unmodified, including the `Authorization` header, turn off response buffering so the stream isn't held, and leave the accept/reject decision to the binary's own bearer check rather than the proxy.

For **Claude Code**, add this block to the project's `.mcp.json` or to your global MCP config; other SSE clients (Cursor and the rest) have their own MCP config file, but take the same `type`/`url`/`headers` shape:

```json
{
  "mcpServers": {
    "fleet": {
      "type": "sse",
      "url": "https://your-mcp-host.example.com/sse",
      "headers": {
        "Authorization": "Bearer the value printed by echo $MCP_AUTH_TOKEN above"
      }
    }
  }
}
```

### One-shot seed mode

The binary also has a `-seed` flag, unrelated to serving MCP traffic: `./fleet-mcp -seed` creates four standard global saved reports (macOS admin users, Windows update failures, Linux running containers, universal OS version) against the Fleet in `FLEET_BASE_URL`, then exits without starting a server. It still requires `FLEET_API_KEY` to belong to an API-only user and still requires `MCP_AUTH_TOKEN` to be set at startup, even though seeding never uses the bearer token.

Seeding writes global saved reports, which Fleet authorizes as a write on a query with no team: only a global admin, maintainer, or gitops identity can do it. This chapter's recommended low-privilege runtime roles, observer and Observer+, are both read-only for queries and are rejected outright. If `FLEET_API_KEY` is also allowlist-restricted, neither of the two starting profiles above includes `POST /reports`, so seeding fails closed even for a correctly-roled token. Use a temporary, elevated identity (and, if allowlisted, a temporary `POST /reports` entry) to run `-seed` once, then switch `FLEET_API_KEY` back to the token this server actually runs with.

It is not idempotent: it does not check for an existing report with the same name first, so running it again against an already-seeded Fleet fails per-report on Fleet's own name-uniqueness constraint rather than creating duplicates or overwriting what is there; the log line at the end reports how many of the four succeeded.

## Confirm it works and decide who owns it

![How-to](../_assets/icons/howto.svg) The server logs the API-only user it verified against Fleet and refuses to start if that check fails, so a running server has already confirmed its token. An SSE deployment answers an unauthenticated liveness probe at `/healthz`, which reports only that the process is up (it does not check Fleet), so pair it with a periodic authenticated read as the end-to-end signal.

From the assistant, the tools appear after a restart. A single read confirms the whole path: ask it something like "how many hosts does Fleet know about?" and check the total against the Fleet console. That one question exercises tool discovery, the Fleet token, and a read, without running anything on a device. Ask instead for the breakdown by platform and the total still confirms the link, but the per-platform figures need not match the console: the server counts only the most common Linux distributions as Linux and folds the rest into an "Other" bucket, so a fleet running less common distributions reads low on Linux and high on Other even when everything is working. Over SSE it also exercises the bearer; under stdio there is no bearer to test, as this chapter's transport section explains.

Missing tools point at the client-to-server link: the config path, the absolute binary path, or on Apple Silicon the signature. Tools present but every call failing points at the server-to-Fleet link: the base URL, the token, or the API-only requirement.

Ownership follows the tokens, and there are two: the Fleet API key and the client bearer. One server process carries one of each, so over SSE the bearer is a single shared secret rather than per-user login: every client that holds it has the same Fleet scope, every Fleet activity the server generates is attributed to the same API-only user, and the server cannot tell two clients apart, revoke one, or throttle it. Where separate revocation or attribution matters, run a server and API-only identity per trust group, or front it with an identity-aware gateway.

Rotate the API key on the Fleet user and scope that user to the fewest fleets the assistant needs; rotate the bearer whenever a client that held it should lose access. To rotate either, update the server's configuration, update the SSE client's `Authorization` header if the bearer changed, restart the server, and re-run the allowed-and-denied check from the previous section.

Know what the record does and does not hold. Fleet attributes activity-producing operations, live queries among them, to the API-only user in its activity feed ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)). The server's own logs record which tools were invoked, and at debug level the request method and route, but not tool arguments, returned data, or the assistant's prompts. Together they tell you which tools ran and who ran the writes; they are not a transcript of the conversation. If you need a complete record of what an assistant did, capture it at an MCP client or gateway that logs tool calls, and hold those logs to the same retention policy as the data they contain.

Once an assistant relies on this server it is a production service with the same operating needs as Fleet itself, and Part VII is where those live. Give it an operating model and a named owner ([7.1](../07-operate-fleet/7.1-define-the-service-operating-model.md)); fold the `/healthz` probe and the authenticated read above into service-health monitoring ([7.4](../07-operate-fleet/7.4-observe-progress-and-service-health.md)); put the client bearer, the Fleet API key, and the proxy's TLS certificate on the credential and certificate rotation schedule ([7.6](../07-operate-fleet/7.6-maintain-credentials-certificates-and-access.md)) rather than rotating them only when something breaks; and carry the server onto the readiness checklist and into any handoff ([7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md)).

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) Where the answers have limits, and what happens at them.

**A shared hostname returns candidates, not a guess.** When a name matches more than one host the tools return the candidates, and the assistant re-asks by numeric host ID. A host whose only distinguishing name is its display name is best fetched by ID from the start, because the substring search does not index the display name.

**A live query is bounded by a wait and reaches only online hosts.** The server waits a fixed period, 25 seconds by default, and returns early once every online host has answered. In a multi-host campaign an offline host contributes no result rows and is not queued for later; in a single-host query the one host comes back marked offline with no rows, rather than being dropped. Keep this wait at or above the Fleet server's own live-query period, so the server does not give up before Fleet finishes the campaign. For a host that may be offline, an inventory tool answers from cache where a live query returns nothing. Inventory data is only as fresh as the last successful collection of that detail, which is not the same as the last check-in and is not live.

**Malformed inputs are rejected before Fleet sees them.** A CVE identifier must match the standard `CVE-YYYY-NNNN` shape, a policy identifier must be a positive integer, a policy-result filter requires the policy it applies to, and a page size is capped at 200. Each gets a usable error at the server.

**Unsafe TLS and token configurations refuse to start rather than run quietly.** Skipping TLS verification is allowed only when Fleet is at localhost; paired with any remote URL the server refuses to start, so a development shortcut cannot follow a copied config into a remote deployment. A bearer token shorter than 32 characters is refused the same way, and TLS skip-verify and a custom CA file are mutually exclusive.

**Over SSE, an oversized request body is capped.** Incoming bodies are limited to one mebibyte and header and read timeouts are bounded, which limits what a single oversized or slow request can do. These are not rate limiting; the server runs none, so throttling a flood of requests belongs at the proxy or platform edge. The stdio transport has no such surface.

## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting.svg) Most read tools are a direct proxy, so diagnosis is almost always diagnosis of the Fleet API path behind them. When such a tool returns something unexpected, the same call against the REST API tells you whether the server or Fleet produced it; [6.3](6.3-use-the-fleet-rest-api.md) is that surface and [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) is the endpoint reference. Composed tools are the exception: the ones that intersect filters, fan a CVE lookup out per title and version, or gather queries and policies across every team synthesize their result from several Fleet calls and quietly drop any component that failed or was capped into the server's own log, so there may be no single equivalent REST call. For those, replay each component route from [a.11](../09-appendices/a.11-mcp-tool-reference.md) and read the MCP warnings before blaming Fleet. When a live query returns fewer hosts than expected, [8.7](../08-troubleshooting/8.7-live-query-introspection.md) explains how Fleet runs a campaign and why online hosts drop out of one. When the server itself misbehaves, read its logs together with Fleet's server logs, which is [8.3](../08-troubleshooting/8.3-server-logs.md).

## Version notes

![Reference](../_assets/icons/reference.svg) The Fleet MCP server lives in the Fleet repository under `cmd/fleet-mcp` and is present at the 4.90.0 release. It is built from source rather than shipped as a binary, needs Go 1.26.5 or newer, and carries no release tag of its own, so it tracks the repository; build it from the same tag you run. Its osquery schema is a partial exception: it refreshes from Fleet's `main` branch at runtime unless that refresh is disabled, so the validation schema can move ahead of your release.

The role and scoping options depend on edition: Observer+, fleet-scoped API users, and endpoint allowlists are Fleet Premium, while Fleet Free uses a global identity and a maintainer or admin role to run live queries.
