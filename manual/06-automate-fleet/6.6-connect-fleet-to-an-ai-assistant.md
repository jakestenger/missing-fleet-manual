# Connect an AI assistant to Fleet

![Explanation](../_assets/icons/explanation.svg) Fleet includes an MCP server in its source: a small program that gives a compatible AI assistant named tools for reading Fleet, and, if you allow it, running live osquery against your devices. This chapter helps you decide what data and authority an assistant may receive, choose how it connects, build the server for the release you run, and tell a working connection from a safe and complete one.

It does not teach the Fleet REST API itself; [6.3](6.3-use-the-fleet-rest-api.md) owns that, and this server is a client of it. It does not teach how to write osquery, which is [4.2](../04-know-your-devices/4.2-run-queries-and-reports.md) and [4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md).

MCP is the Model Context Protocol, an open standard for how an assistant discovers and calls external tools; it is defined in [a.6](../09-appendices/a.6-glossary-and-release-compatibility.md) and its specification is linked as further reading. Fleet distributes the server as source inside its repository rather than as a prebuilt download, so running it starts with a build.

## What sits between the assistant and Fleet

![Explanation](../_assets/icons/explanation.svg) The MCP server is a thin proxy. It holds one Fleet API token, advertises a set of tools to an assistant, and turns each tool call into ordinary Fleet REST API calls using that token. It stores no fleet data of its own and grants no access the token does not already carry, so Fleet authorizes every call exactly as it would if you had made it with `fleetctl` or `curl`.

A tool result passes back through four places — the assistant application, the model service behind it, the MCP server, and Fleet — and a fault or a data-exposure decision can live at any of them. The transport wires the near end; it does not decide where the data ends up. So before you connect anything, settle whether the assistant's model service is approved to receive what these tools return: hostnames, serials, IP addresses, local usernames, software inventory, policy detail, and live-query output.

The MCP client reaches the server one of two ways, and the difference decides where the connection's trust boundary sits. Over **stdio**, the client launches the server as a local subprocess and speaks to it on standard input and output; there is no network hop, and **`MCP_AUTH_TOKEN` performs no authentication under this transport at all** — the server checks once at startup that it is set and long enough, then never asks for it again, so the token is a configuration guard rather than an access control and the entire boundary is whoever can launch and talk to that local process. Over **SSE** — Server-Sent Events — the client connects across HTTP and the server checks the bearer on every MCP request, the unauthenticated `/healthz` probe aside, so the boundary is the token and the TLS in front of it. The tools behave identically on both.

Reads resolve synchronously, though not always in a single request. A simple read is one or a few HTTP calls against Fleet's stored state; others fan out — listing saved reports (`get_queries`) or policies calls Fleet once per fleet, and a vulnerability or affected-software question issues a request per matching item — and a few, such as the vetted-query library, come from data bundled into the server rather than from Fleet at all. Running a live query is the exception. Fleet dispatches it to devices and collects results over Redis, so it is asynchronous, and the server waits a bounded period for online hosts to report before returning what it has. A single-host live query uses Fleet's synchronous ad-hoc query for that host; a multi-host run opens an ad-hoc campaign whose query is not saved, and streams results as hosts answer.

## The tools the assistant sees

![Reference](../_assets/icons/reference.svg) The assistant sees a catalogue of typed tools across four areas — hosts, queries, policies and vulnerabilities, and inventory — each with named arguments it fills in, rather than Fleet's endpoints. An assistant handles "list the failing Linux hosts for policy 42" far more reliably against a named tool with a `platform` argument than against a REST path it has to construct and paginate.

| Area | Tools | What the assistant can do |
|---|---|---|
| **Hosts** | `get_endpoints`, `get_host`, `get_host_policies`, `get_total_system_count`, `get_aggregate_platforms`, `get_fleets`, `get_labels` | List and filter enrolled hosts, read one host's full detail, read a host's per-policy pass/fail, and read fleet-wide counts by platform |
| **Queries** | `get_queries`, `prepare_live_query`, `run_live_query`, `get_osquery_schema`, `refresh_osquery_schema`, `get_vetted_queries` | List saved reports, fetch the osquery schema, validate targets, and run live osquery against devices |
| **Policies and vulnerabilities** | `get_policies`, `get_policy_compliance`, `get_policy_hosts`, `get_vulnerability_impact`, `get_vulnerability_hosts` | Read policy pass/fail counts, list the hosts on either side of a policy, and find the hosts a CVE affects |
| **Inventory** | `get_software`, `get_host_users` | Read stored software and local user accounts from Fleet's cached inventory, without touching the device |

**A host list is a page, not a census.** The host-listing tools cap a page at 200 and do not paginate the whole fleet for you. The ones that answer "which hosts" — failing a policy, affected by a CVE — return that capped page with no running total, so above the cap a returned list is a partial first page, not the full set.

Read a count question, like how many hosts fail policy 42, from the counting tools rather than from the length of a list. Even a count can be a floor: the 10,000-host ceiling applies per underlying fetch, not to the merged total, so an aggregate that fans out across several fetches — a CVE affecting multiple software versions, for example — can undercount each fetch past its own cap while still reporting a combined figure above 10,000.

A filtered live query resolves up to 500 matching hosts as its targets and previews at most 100 of them. When the preview is truncated, narrow the filter rather than trusting it to cover everything; matches beyond 500 are not queried.

The tools also resolve hosts by identity, validate live queries before running them, and work around Fleet's weaker filters. A numeric host ID goes straight through, and a name matching several hosts returns a candidate list for the assistant to choose from rather than a silent pick, because Fleet allows hosts to share a hostname. A live query is checked before it runs, and it helps to know which half is enforced: the server rejects the common mistake of comparing a text column against a bare integer — except a literal `0` or `1`, let through as a boolean-style flag — a mistake Fleet would otherwise answer with zero rows, but fetching the schema and previewing the targets first are steps the assistant is advised to take rather than gates the server requires — it resolves the query's targets itself when the query runs. A CVE or platform question is composed from several Fleet calls, because Fleet's own single filter for those is unreliable at this release; the assistant sees the correct hosts.

The inventory tools read Fleet's stored inventory, so they answer for a host that is currently offline, where a live query reaches only hosts online during its wait. Their answers are only as current as the last successful collection of the relevant detail, which runs on Fleet's inventory interval and only for the platforms and features that gather it; an ordinary check-in does not by itself refresh software or user records, so read freshness against [4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md) and [4.4](../04-know-your-devices/4.4-understand-software-and-vulnerabilities.md). Prefer the inventory tool when either would answer: it is cached and spends no device CPU. The tools' exact arguments are in [a.11](../09-appendices/a.11-mcp-tool-reference.md); the REST routes underneath them are in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md).

## Read-only is not the same as harmless

![Explanation](../_assets/icons/explanation.svg) Every tool carries a hint telling a cooperating client whether it only reads. All but one are read-only; `run_live_query` is marked destructive, and a well-behaved client such as Claude Desktop prompts before it fires. It counts as destructive even for a `SELECT` because a live query runs arbitrary osquery on every targeted device — it consumes device CPU, shows up in EDR telemetry, and osquery's schema documents tables whose job is reading local files or reaching cloud-metadata endpoints over the network, so a query is not confined to the passive read a `SELECT` usually implies. That is an osquery capability, the same one Fleet's console and `fleetctl` expose, drawn from the schema rather than from running such a query end-to-end; the server does not special-case it.

What is enforced and what is merely advised are different things, and an administrator has to tell them apart:

- **The API-only identity** is checked by the server at startup, once.
- **Role and fleet scope** are enforced by Fleet on every call, so an observer token gets a permission error the moment it attempts a live query, and a token scoped to two fleets cannot read a third.
- **An endpoint allowlist** is a separate, optional restriction you can place on an API-only Fleet user, narrowing it further than its role. It is a Fleet Premium feature: Fleet checks the request's route against a fixed catalog of known routes, then against the user's own allowed list, and denies anything that isn't an exact match on both. It is only safe once it covers the full route set the tools use (the startup identity check, each tool's own routes, and the secondary calls its fan-out paths make), and it has to be re-derived when the tools change. [A.11](../09-appendices/a.11-mcp-tool-reference.md) gives that route set per tool, and two starting profiles are below; build and test the result against your own deployment rather than treating it as a quick lock-down. One route the allowlist cannot cover at all: the live-query results stream authenticates its own bearer token when the connection opens instead of going through the allowlist check, so a partial list still lets a token that can start a multi-host run read that run's results back.
- **Schema-first preparation, target preview, and the confirmation prompt** are advice to a cooperating assistant, not gates the server keeps. A prompt-injected client can skip them, and `run_live_query` resolves its own targets when it runs, so a preview is a look and not a locked transaction.

So the token is the security decision, and your Fleet edition shapes it. A read-only deployment gives the server an **observer** token on either edition. Running live queries needs a role permitted to run them: **observer-plus** on Fleet Premium, or a **maintainer** or **admin** identity on Fleet Free, which has no observer-plus. Give the server the lowest such role. The server adds one requirement of its own on both editions: it refuses to start unless its token belongs to an **API-only** Fleet user — no console session, its own audit identity — and the check fails closed, so an unreachable Fleet or an invalid token stops startup. Two ways to narrow that user further are Premium only: scoping it to specific fleets, and restricting it to an endpoint allowlist. On Free the API-only user is global. Creating that user is covered under service identities in [2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md), and the roles are [1.4](../01-foundations/1.4-identity-and-roles.md). After configuring it, confirm the boundary from both sides: run one operation the role allows and one it should deny, and check Fleet returns the permission error for the second.

### Two starting allowlist profiles

![Reference](../_assets/icons/reference.svg) Both are read from [A.11](../09-appendices/a.11-mcp-tool-reference.md)'s per-tool route lists, de-duplicated, plus `GET /me`: the server's startup identity check calls it once regardless of role, and Fleet applies the same catalog-membership and user-allowlist check to it as to any other route for a restricted API-only user — there is no exemption. Leave it off the list and the server fails closed at startup for that user, before any tool ever runs. Confirm the full set against your own deployment before relying on it, and re-derive both lists whenever the tools change or a new one is added.

- **Read-only** (every tool except `run_live_query`): `GET /me`, `GET /hosts`, `GET /hosts/count`, `GET /hosts/{id}`, `GET /hosts/identifier/{identifier}`, `GET /hosts/{id}/software`, `GET /host_summary`, `GET /labels`, `GET /labels/{id}/hosts`, `GET /fleets`, `GET /fleets/{id}/policies`, `GET /fleets/{id}/policies/{policy_id}`, `GET /global/policies`, `GET /global/policies/{id}`, `GET /software/titles`, `GET /software/titles/{id}`, `GET /reports`.
- **Read plus live query**: the read-only list above, plus `POST /hosts/{id}/query` and `POST /reports/run` for running queries. It cannot add the results stream, since that route sits outside the allowlist mechanism entirely (above): anyone who can reach `POST /reports/run` can already read what it returns.

The server also guards its own front door. The client's bearer token must be at least 32 characters, and the server refuses a weaker one; `openssl rand -hex 32` satisfies it. Over SSE the server speaks plain HTTP, so a non-loopback SSE deployment belongs behind a TLS-terminating proxy, which a managed platform's edge already provides. The stdio transport has no network hop and sidesteps this.

## Choose a transport and scope the token

![How-to](../_assets/icons/howto.svg) Before the build, settle how the assistant connects and what its token may do. Both are easier to get right at the start than to change once an assistant is wired up.

Transport follows topology. Use **stdio** when the assistant runs on the same machine as an operator, as Claude Desktop does: the client launches the server as a subprocess, with no port to expose and no TLS to terminate. Use **SSE** when the assistant is a separate or remote client, such as Claude Code or Cursor, where a network endpoint is unavoidable and you own the TLS in front of it. Client capability decides which a given assistant can use; the brand does not fix the transport.

Token role follows the assistant's job. Give it an **observer** token when its work is reading posture, inventory and compliance, and the destructive tool cannot fire. Give it **observer-plus** when it needs to answer live questions the stored inventory cannot, and accept that the assistant can then run osquery against devices, bounded by the token's fleet scope, with the client's confirmation prompt as an advisory check rather than an enforced one. Pick the lowest role the real work needs.

Prerequisites, once those are settled: a reachable Fleet instance, an API-only Fleet user at the role you chose ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)) and its API token, an MCP-capable assistant, and Go 1.26.5 or newer to build the server.

## Build and connect the assistant

![How-to](../_assets/icons/howto.svg) Build the server from Fleet's source at the release you run, so the tool matches the server it talks to.

```bash
git clone https://github.com/fleetdm/fleet
cd fleet/cmd/fleet-mcp
git checkout fleet-v4.90.1
go build -o fleet-mcp .
```

The built binary carries an embedded copy of the osquery schema, then replaces it at startup, and every 24 hours after by default, with the schema file from Fleet's `main` branch. That keeps column types current but means the schema it validates against tracks `main` rather than your release, and it needs outbound access to fetch it. Change the interval with `FLEET_MCP_SCHEMA_REFRESH_INTERVAL`, a Go duration string such as `12h` or `6h30m`; an unset or unparseable value falls back to the 24-hour default rather than failing startup. The variable is read once at startup, so changing it needs a restart to take effect. In an air-gapped or strictly release-pinned deployment, disable the refresh entirely by setting `FLEET_MCP_SCHEMA_REFRESH_DISABLE` to any non-empty value (for example, `export FLEET_MCP_SCHEMA_REFRESH_DISABLE=1`), and the binary uses only its embedded snapshot.

Generate the client bearer token next. It is required on every transport, including stdio, and the server will not start without it.

```bash
openssl rand -hex 32
```

For **Claude Desktop over stdio**, the assistant launches the binary directly and reads its environment from its own JSON config rather than any `.env` file. Point it at an absolute path, because a leading `~` is not expanded.

Edit `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS:

```json
{
  "mcpServers": {
    "fleet-mcp": {
      "command": "/absolute/path/to/fleet-mcp",
      "args": ["-transport", "stdio"],
      "env": {
        "FLEET_BASE_URL": "https://your-fleet.example.com",
        "FLEET_API_KEY": "the API-only user's token",
        "MCP_AUTH_TOKEN": "the openssl output from above",
        "LOG_LEVEL": "info"
      }
    }
  }
}
```

On Apple Silicon, ad-hoc sign the binary after building it, and again after each rebuild, before Claude Desktop will launch it. Gatekeeper caches the signature against the file's identity, so replacing the binary at the same path invalidates the earlier approval and the launch fails silently.

```bash
codesign --force --sign - ./fleet-mcp
```

Fully quit and relaunch the assistant, not just its window, and the tools appear in its context. The Claude Desktop specifics here — the confirmation prompt on the destructive tool, reading environment from the JSON config, the ad-hoc signing step, and the full relaunch — describe that client and macOS at the time of writing, not behaviour Fleet enforces, so confirm them against your client and OS version if they differ.

For **Claude Code, Cursor, or another SSE client**, run the built binary so it listens for SSE connections. Supply `FLEET_BASE_URL`, `FLEET_API_KEY` and `MCP_AUTH_TOKEN` through the process environment, or through a `.env` file that the binary reads from its working directory — so run it from the directory that holds the file. It listens on `PORT`, default 8080.

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
export MCP_AUTH_TOKEN="the openssl output from above"
./fleet-mcp            # transport: SSE — listening on :8080
```

Confirm the binary works on its own before wiring a client to it, by driving it directly over stdio JSON-RPC — this isolates a server or token fault from a client-configuration fault:

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
export MCP_AUTH_TOKEN="the openssl output from above"

cat <<'EOF' | ./fleet-mcp -transport stdio
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"1.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_total_system_count","arguments":{}}}
EOF
```

A response to the `tools/call` message confirms the server, its Fleet token, and stdio all work. Swap the `tools/call` line for any other tool, e.g. `get_host_policies` with a `host_id` argument, to exercise it directly. Then point the client at the `/sse` path with the bearer token as an `Authorization: Bearer` header, and terminate TLS in front of any endpoint that is not localhost, because the server speaks plain HTTP.

For a real SSE deployment, run the binary as a supervised service rather than a foreground process: put it under a process manager that restarts it, behind the TLS-terminating proxy, and give it the deployment-level settings that matter — `PORT`, `LOG_LEVEL` kept off `debug` where logs are centralized, `FLEET_CA_FILE` if Fleet presents a private CA, `FLEET_LIVE_QUERY_REST_PERIOD` at or above the Fleet server's own, and the schema-refresh controls if you need to pin or disable the outbound schema fetch. A managed platform supplies the supervisor and the TLS edge; a self-hosted deployment owns both.

### A worked example: systemd behind Caddy

One pairing that satisfies all of that on a self-hosted box: a systemd unit that restarts the binary, behind Caddy terminating TLS in front of it.

`/etc/systemd/system/fleet-mcp.service`:

```ini
[Unit]
Description=Fleet MCP server
After=network.target

[Service]
Type=simple
User=fleet-mcp
EnvironmentFile=/etc/fleet-mcp/env
ExecStart=/usr/local/bin/fleet-mcp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

`/etc/fleet-mcp/env` holds `FLEET_BASE_URL`, `FLEET_API_KEY`, and `MCP_AUTH_TOKEN`, world-unreadable and owned by the `fleet-mcp` user; `PORT` only needs setting if something else on the host already holds 8080. The binary already shuts down cleanly on SIGTERM, so `systemctl restart fleet-mcp` and a crash both leave `Restart=on-failure` to bring it back. `systemctl daemon-reload && systemctl enable --now fleet-mcp` starts it and survives a reboot.

Caddy needs one line, because it forwards headers unchanged and does not buffer a streamed response:

```
your-mcp-host.example.com {
    reverse_proxy localhost:8080
}
```

Confirm the negative case along with the positive one — only the header differs between the last two:

```bash
curl -i https://your-mcp-host.example.com/healthz
# → 200, unauthenticated by design

curl -i https://your-mcp-host.example.com/sse
# → 401, no Authorization header reached the server

curl -i -H "Authorization: Bearer the-same-openssl-output" https://your-mcp-host.example.com/sse
# → 200, the connection opens
```

nginx or another supervisor work the same way in principle: forward `/sse` and `/message` unmodified, including the `Authorization` header, turn off response buffering so the stream isn't held, and leave the accept/reject decision to the binary's own bearer check rather than the proxy.

For **Claude Code**, add this block to the project's `.mcp.json` or to your global MCP config; other SSE clients (Cursor and the rest) have their own MCP config file, but take the same `type`/`url`/`headers` shape:

```json
{
  "mcpServers": {
    "fleet": {
      "type": "sse",
      "url": "https://your-mcp-host.example.com/sse",
      "headers": {
        "Authorization": "Bearer the-same-openssl-output"
      }
    }
  }
}
```

### One-shot seed mode

The binary also has a `-seed` flag, unrelated to serving MCP traffic: `./fleet-mcp -seed` creates four standard global saved reports (macOS admin users, Windows update failures, Linux running containers, universal OS version) against the Fleet in `FLEET_BASE_URL`, then exits without starting a server. It still requires `FLEET_API_KEY` to belong to an API-only user and still requires `MCP_AUTH_TOKEN` to be set at startup, even though seeding never uses the bearer token. It is not idempotent: it does not check for an existing report with the same name first, so running it again against an already-seeded Fleet fails per-report on Fleet's own name-uniqueness constraint rather than creating duplicates or overwriting what is there; the log line at the end reports how many of the four succeeded.

## Confirm it works and decide who owns it

![How-to](../_assets/icons/howto.svg) The server logs the API-only user it verified against Fleet and refuses to start if that check fails, so a running server has already confirmed its token. An SSE deployment answers an unauthenticated liveness probe at `/healthz`, which reports only that the process is up — it does not check Fleet — so pair it with a periodic authenticated read as the end-to-end signal. From the assistant, the tools appear after a restart. A single read confirms the whole path: ask it something like "how many hosts does Fleet know about, grouped by platform?" and check the answer against the Fleet console. That one question exercises tool discovery, the bearer, the Fleet token, and a read, without running anything on a device. Missing tools point at the client-to-server link: the config path, the absolute binary path, or on Apple Silicon the signature. Tools present but every call failing points at the server-to-Fleet link: the base URL, the token, or the API-only requirement.

Ownership follows the tokens, and there are two: the Fleet API key and the client bearer. One server process carries one of each, so over SSE the bearer is a single shared secret rather than per-user login: every client that holds it has the same Fleet scope, every Fleet activity the server generates is attributed to the same API-only user, and the server cannot tell two clients apart, revoke one, or throttle it. Where separate revocation or attribution matters, run a server and API-only identity per trust group, or front it with an identity-aware gateway. Rotate the API key on the Fleet user and scope that user to the fewest fleets the assistant needs; rotate the bearer whenever a client that held it should lose access. To rotate either, update the server's configuration, update the SSE client's `Authorization` header if the bearer changed, restart the server, and re-run the allowed-and-denied check from the previous section.

Know what the record does and does not hold. Fleet attributes activity-producing operations, live queries among them, to the API-only user in its activity feed ([2.8](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md)). The server's own logs record which tools were invoked, and at debug level the request method and route, but not tool arguments, returned data, or the assistant's prompts. Together they tell you which tools ran and who ran the writes; they are not a transcript of the conversation. If you need a complete record of what an assistant did, capture it at an MCP client or gateway that logs tool calls, and hold those logs to the same retention policy as the data they contain.

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) Where the answers have limits, and what happens at them.

**A shared hostname returns candidates, not a guess.** When a name matches more than one host the tools return the candidates, and the assistant re-asks by numeric host ID. A host whose only distinguishing name is its display name is best fetched by ID from the start, because the substring search does not index the display name.

**A live query is bounded by a wait and reaches only online hosts.** The server waits a fixed period, 25 seconds by default, and returns early once every online host has answered. In a multi-host campaign an offline host contributes no result rows and is not queued for later; in a single-host query the one host comes back marked offline with no rows, rather than being dropped. Keep this wait at or above the Fleet server's own live-query period, so the server does not give up before Fleet finishes the campaign. For a host that may be offline, an inventory tool answers from cache where a live query returns nothing. Inventory data is only as fresh as the last successful collection of that detail, which is not the same as the last check-in and is not live.

**Malformed inputs are rejected before Fleet sees them.** A CVE identifier must match the standard `CVE-YYYY-NNNN` shape, a policy identifier must be a positive integer, a policy-result filter requires the policy it applies to, and a page size is capped at 200. Each gets a usable error at the server.

**Unsafe configurations refuse to start rather than run quietly.** Skipping TLS verification is allowed only when Fleet is at localhost; paired with any remote URL the server refuses to start, so a development shortcut cannot follow a copied config into a remote deployment. A bearer token shorter than 32 characters is refused the same way, and TLS skip-verify and a custom CA file are mutually exclusive.

**Over SSE, an oversized request body is capped.** Incoming bodies are limited to one mebibyte and header and read timeouts are bounded, which limits what a single oversized or slow request can do. These are not rate limiting; the server runs none, so throttling a flood of requests belongs at the proxy or platform edge. The stdio transport has no such surface.

## Platform differences

## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting.svg) The server is a proxy, so diagnosis is almost always diagnosis of the Fleet API path behind it. When a read tool returns something unexpected, the same call against the REST API tells you whether the server or Fleet produced it; [6.3](6.3-use-the-fleet-rest-api.md) is that surface and [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) is the endpoint reference. When a live query returns fewer hosts than expected, [8.7](../08-troubleshooting/8.7-live-query-introspection.md) explains how Fleet runs a campaign and why online hosts drop out of one. When the server itself misbehaves, read its logs together with Fleet's server logs, which is [8.3](../08-troubleshooting/8.3-server-logs.md).

## Version notes

![Reference](../_assets/icons/reference.svg) The Fleet MCP server lives in the Fleet repository under `cmd/fleet-mcp` and is present at the 4.90.1 release. It is built from source rather than shipped as a binary, needs Go 1.26.5 or newer, and carries no release tag of its own, so it tracks the repository; build it from the same tag you run. Its osquery schema is a partial exception: it refreshes from Fleet's `main` branch at runtime unless that refresh is disabled, so the validation schema can move ahead of your release. The role and scoping options depend on edition: observer-plus, fleet-scoped API users, and endpoint allowlists are Fleet Premium, while Fleet Free uses a global identity and a maintainer or admin role to run live queries.
