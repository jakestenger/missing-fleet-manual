# Connect an AI assistant to Fleet

![Explanation](../_assets/icons/explanation-light.svg) Fleet's MCP server lets a compatible AI assistant read device information and, with the appropriate permissions, run live osquery queries. An administrator can use it to explore inventory, investigate a policy result, or ask a device question that the stored inventory cannot answer. You choose the data and authority available to the assistant through the Fleet identity the server uses.

MCP, the Model Context Protocol, defines how an assistant discovers and calls external tools ([a.6](../09-appendices/a.6-glossary-and-release-compatibility.md)). Fleet supplies its MCP server as source in the repository, so setup begins with a build for your Fleet release.

The server calls the REST API described in [6.3](6.3-use-the-fleet-rest-api.md). For help writing the queries it can run, use [4.2](../04-know-your-devices/4.2-run-queries-and-reports.md) and [4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md). Here, start with the connection and access model, then follow the setup path for your assistant.

## What sits between the assistant and Fleet

![Explanation](../_assets/icons/explanation-light.svg) The MCP server holds one Fleet API token and advertises named tools to the assistant. Most tool calls become ordinary API requests made with that token. The server stores no Fleet data of its own, and Fleet authorizes each request against the same role and scope it would use for fleetctl or curl.

Three tools obtain their data without calling Fleet:

- **`get_vetted_queries`** reads the query library bundled into the binary.
- **`get_osquery_schema`** reads the current in-memory schema. It starts from a bundled snapshot and is replaced after successful refreshes from `raw.githubusercontent.com`.
- **`refresh_osquery_schema`** requests that GitHub fetch immediately.

[A.11](../09-appendices/a.11-mcp-tool-reference.md) identifies these tools and the API routes used by the others.

An answer can carry data through four systems: Fleet, the MCP server, the model service, and the assistant application. Before connecting them, confirm that the model service is approved to receive the returned information. Depending on the tools used, that can include hostnames, serials, IP addresses, local usernames, software inventory, policy details, and live-query output. The transport secures the connection to the MCP server; it does not determine how the model service or application handles the data afterward.

### Local and network connections

With **stdio**, the assistant launches a local server subprocess and communicates through standard input and output. There is no network hop. `MCP_AUTH_TOKEN` must be present and meet the length requirement at startup, but it is never checked again under this transport. Access depends on who can launch and communicate with the process.

With **SSE**, or Server-Sent Events, the assistant connects over HTTP. The server checks a bearer token on MCP requests; the `/healthz` liveness probe is unauthenticated. Put TLS in front of the plain-HTTP server when clients connect over a network. Both transports expose the same tools.

### Reads and live queries

Read tools return synchronously, although some gather data through several API calls. Listing saved reports (`get_queries`) or policies makes a call for each fleet. Vulnerability and affected-software tools can issue a request for each matching item, then merge the results. The bundled query library and schema tools use their local data sources instead.

Live queries involve the devices. Fleet dispatches the query, gathers responses through Redis, and returns results from hosts that answer within a bounded wait. A single-host query uses Fleet's synchronous ad-hoc request. A multi-host query starts an ad-hoc campaign and streams arriving results; it does not create a saved report.

## The tools the assistant sees

![Reference](../_assets/icons/reference-light.svg) The assistant receives a catalogue of tools with named arguments. For example, it can request hosts failing a specified policy through a tool with policy and platform arguments, without constructing the REST request itself. The tools cover four areas:

| Area | Tools | What the assistant can do |
|---|---|---|
| **Hosts** | `get_endpoints`, `get_host`, `get_host_policies`, `get_total_system_count`, `get_aggregate_platforms`, `get_fleets`, `get_labels` | List and filter hosts, read selected host details and per-policy results, and retrieve deployment-wide counts by platform |
| **Queries** | `get_queries`, `prepare_live_query`, `run_live_query`, `get_osquery_schema`, `refresh_osquery_schema`, `get_vetted_queries` | List saved reports, inspect schema, validate targets, and run live osquery |
| **Policies and vulnerabilities** | `get_policies`, `get_policy_compliance`, `get_policy_hosts`, `get_vulnerability_impact`, `get_vulnerability_hosts` | Read pass/fail counts, find hosts by policy result, and identify hosts associated with a CVE |
| **Inventory** | `get_software`, `get_host_users` | Read stored software and local-account inventory without contacting the device |

### Result limits and counts

Host-listing tools return pages capped at 200 hosts; they do not traverse the entire population for you. The policy- and CVE-host tools provide that capped page without a running total. A full page may therefore represent only the first portion of the matching hosts. `get_host` also returns a selected projection of host details rather than Fleet's complete host record.

Use counting tools for questions such as how many hosts fail a policy. Even those counts can be lower bounds. A 10,000-host ceiling applies to each underlying fetch, not the merged total. An aggregate spanning several software versions can exceed 10,000 overall while still undercounting individual fetches that reached their caps.

### Live-query targets and filters

A filtered live query resolves at most 500 matching hosts and previews at most 100. Narrow a truncated preview until you can confirm the intended targets; matches beyond 500 will not be queried.

For a plain live query, supplying both `label` and `platform` uses the label and silently drops the platform filter. SQL written for one operating system could then reach labeled hosts on another. Use one of those filters and inspect the preview before running the query.

CVE-filtered live queries combine the filters differently: `label` and `platform` both narrow the affected-host set. Check which query path you are using before applying that intersection rule.

### Host identity and schema checks

Use a numeric host ID when a precise target is important. IDs pass directly to Fleet; names first go through a search. A successful name search that matches several hosts returns up to 50 candidates for selection. The reported count covers only those returned candidates, with no indication that further matches were trimmed.

If the preliminary search fails, the server falls back to a single-record identifier lookup. That lookup returns one match with no defined ordering, so it can select a host from a shared hostname without surfacing the collision. Numeric IDs avoid that fallback path.

The server checks live queries for a common type mistake: comparing a text column with a bare integer. It rejects those comparisons except for literal `0` and `1`, which are accepted as boolean-style flags. Otherwise this mistake can produce zero rows from Fleet.

Fetching the schema and previewing targets are recommended preparation steps for the assistant, not required server gates. The server resolves targets again when it runs the query.

### Interpreting composed and cached results

The MCP server combines several API calls for CVE and platform questions because Fleet's corresponding single filters are unreliable at this release. CVE composition can also include too much: it finds affected software titles, then fetches hosts across all versions of those titles, including unaffected versions. Confirm candidate hosts against their software inventory before using the result as a remediation population or exposure count.

Inventory tools can answer for an offline host because they read stored records. Their freshness depends on the last successful collection of the relevant detail and the platforms and features that collect it. A routine check-in does not itself refresh software or local-account inventory ([4.1](../04-know-your-devices/4.1-understand-hosts-vitals-and-inventory.md), [4.4](../04-know-your-devices/4.4-understand-software-and-vulnerabilities.md)).

Prefer an inventory read when it provides the answer you need; it uses no device CPU. Choose a live query when you need a new observation from an online device. Exact tool arguments are in [a.11](../09-appendices/a.11-mcp-tool-reference.md), with underlying routes in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md).

## Read-only is not the same as harmless

![Explanation](../_assets/icons/explanation-light.svg) Each tool includes a hint describing whether it only reads. All tools except `run_live_query` carry the read-only hint. `run_live_query` is marked destructive, which prompts cooperating clients such as Claude Desktop to request confirmation.

A live query runs arbitrary osquery on the targeted devices, even when the SQL is a `SELECT`. It consumes CPU and may appear in endpoint-detection alerts or logs. The osquery schema also describes tables that read local files or contact cloud-metadata endpoints. These are documented osquery capabilities shared with Fleet's interface and fleetctl; this manual has not verified those queries end to end, and the MCP server does not special-case them.

### Enforced access controls and advisory preparation

Choose the token's role and scope as the primary access decision. The server and assistant apply different checks:

- **API-only account check:** the MCP server verifies the identity once at startup. An invalid token or unreachable Fleet stops startup.
- **Role and fleet scope:** Fleet enforces them on each call. An observer cannot run a live query, and a token scoped to two fleets cannot read a third.
- **Endpoint allowlist:** on Premium, a restricted API-only user's request must match both Fleet's route catalogue and the user's list. Include startup checks, tool routes, and secondary calls made while assembling results. [A.11](../09-appendices/a.11-mcp-tool-reference.md) supplies route lists and starting profiles; test them against the deployment and revise them when tools change.
- **Preparation and confirmation:** schema inspection, target preview, and confirmation prompts are advice to the assistant. A compromised or prompt-injected client can skip them. A preview also does not lock the target set; the server resolves it again at execution.

The multi-host live-query result stream uses its own bearer authentication when the connection opens and bypasses the endpoint-allowlist check. A token that can start the campaign can therefore read its results even when the stream is absent from its endpoint list.

For stored-data reads, use an **observer** API-only identity on either edition. For live queries on Premium, **Observer+** is the least-privileged suitable role. **Technician**, **maintainer**, and **admin** can also run queries, but Technician includes device-change privileges beyond this task. Free has neither Observer+ nor Technician, so live-query access requires **maintainer** or **admin**.

The API-only requirement applies on both editions. Premium can narrow the user to specific fleets and endpoints; Free uses a global API-only identity. [2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md) covers creation, and [1.4](../01-foundations/1.4-identity-and-roles.md) explains the roles. Verify the configured boundary with one allowed operation and one that Fleet should deny.

### Two starting allowlist profiles

![Reference](../_assets/icons/reference-light.svg) [A.11](../09-appendices/a.11-mcp-tool-reference.md#starting-allowlist-profiles) provides a read-only profile and a profile that also permits live queries. They combine the per-tool route lists and the startup `GET /me` request.

Include `GET /me` even for a read-only deployment. A restricted API-only user receives the same catalogue and allowlist checks on that route as on other routes; omitting it stops the server at startup.

Restore the `/api/v1/fleet` prefix omitted from the appendix's shorthand. For example, `GET /hosts` becomes `{"method": "GET", "path": "/api/v1/fleet/hosts"}`. Submit every route as a full method/path pair and test the complete set against your deployment. Revisit it when the tools change or a new tool is added.

Attach the profile when creating the API-only user. A user with no list can reach every endpoint its role permits, so a profile kept only in a file applies no restriction. The allowlist requires Premium. Supply the selected pairs in `api_endpoints`:

```bash
export FLEET="https://fleet.example.com"
export TOKEN="your-admin-api-token"

curl -sS --fail-with-body -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data '{
    "name": "MCP server",
    "global_role": "observer",
    "api_endpoints": [
      {"method": "GET", "path": "/api/v1/fleet/me"},
      {"method": "GET", "path": "/api/v1/fleet/hosts"},
      {"method": "GET", "path": "/api/v1/fleet/hosts/count"}
    ]
  }' \
  "$FLEET/api/v1/fleet/users/api_only"
```

Populate that array with every route in the chosen profile. Fleet generates the user's email and password and returns its API token in the response. Capture the token for the MCP server's `FLEET_API_KEY`.

For an existing user, send `api_endpoints` in a `PATCH` to `/api/v1/fleet/users/api_only/{id}`. Sending `"api_endpoints": null` clears the restriction. Read the user back and confirm that the stored list matches the intended profile.

The MCP server also requires its own client token, `MCP_AUTH_TOKEN`, with a minimum raw length of 32 bytes. `openssl rand -hex 32` produces 64 hex characters and meets that requirement. SSE clients send this token to the MCP server; stdio uses it only as a startup check. Network SSE deployments also need a TLS-terminating proxy or a managed platform's TLS edge.

## Choose a transport and scope the token

![How-to](../_assets/icons/howto-light.svg) Match the transport to where the assistant runs, then give the Fleet identity the permissions that its work requires.

Use **stdio** when the assistant can launch the server as a local subprocess, as in the Claude Desktop example below. Use **SSE** for a separate or remote client that connects to a network endpoint. Claude Code, Cursor, and other clients may support that path; check client capability rather than choosing solely by product name.

Set the transport with `-transport`. Only the exact value `stdio` selects the local transport. Any other value, including a typo, starts the SSE listener. Confirm the later transport log line reads `transport: stdio` or `transport: SSE` as intended; the opening startup line does not identify it.

Use an observer identity for posture, inventory, and compliance reads. Choose Observer+ on Premium when live queries are needed, or the suitable Free role described above. Live-query permission allows osquery execution on devices within the token's scope; the assistant's confirmation prompt remains advisory.

Before building, prepare a reachable Fleet instance, the API-only user and token, an MCP-capable assistant, and Go 1.26.5 or newer.

## Build and connect the assistant

![How-to](../_assets/icons/howto-light.svg) Build the MCP server from the Fleet release tag you run. This keeps the tool implementation aligned with your Fleet server.

```bash
git clone https://github.com/fleetdm/fleet
cd fleet/cmd/fleet-mcp
git checkout fleet-v4.90.0
go build -o fleet-mcp .
```

### Choose how the osquery schema stays current

The binary includes an osquery schema and can serve it immediately. About two seconds after startup, it attempts to refresh that schema from Fleet's `main` branch. It repeats the fetch every 24 hours by default. A successful fetch replaces the in-memory copy; a failed fetch leaves the previous copy available.

This refresh needs outbound access and can move the validation schema ahead of your Fleet release. To change its frequency, set `FLEET_MCP_SCHEMA_REFRESH_INTERVAL` to a Go duration such as `12h` or `6h30m`. An unset or unparseable value uses the 24-hour default. Restart the process after changing the variable.

For a deployment that must use the release's embedded schema, set `FLEET_MCP_SCHEMA_REFRESH_DISABLE` to any non-empty value, such as `1`. This stops the startup and periodic fetches. The assistant can still invoke `refresh_osquery_schema`, which fetches from GitHub regardless of that setting. An air-gapped deployment also needs to block outbound access to `raw.githubusercontent.com`, or use a custom build that removes that tool.

### Prepare the client token

Generate `MCP_AUTH_TOKEN` before starting the server. It is required on both transports and must be at least 32 bytes long. This command produces 64 hex characters:

```bash
export MCP_AUTH_TOKEN="$(openssl rand -hex 32)"
```

Reuse the exported value in the commands below. For a JSON client configuration, run `echo "$MCP_AUTH_TOKEN"` once and paste the literal value into the file; JSON does not expand shell variables. These examples assume the same shell session. If you open another session, re-export the same value first.

Choose the connection instructions for your assistant below. The direct smoke test can help you check the server before adding a client.

### Connect Claude Desktop over stdio

Claude Desktop launches the binary as a subprocess and supplies its environment through a JSON configuration. Put the variables there rather than relying on a `.env` file. Use an absolute binary path; a leading `~` is not expanded.

On macOS, edit `~/Library/Application Support/Claude/claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "fleet-mcp": {
      "command": "/absolute/path/to/fleet-mcp",
      "args": ["-transport", "stdio"],
      "env": {
        "FLEET_BASE_URL": "https://your-fleet.example.com",
        "FLEET_API_KEY": "the API-only user's token",
        "MCP_AUTH_TOKEN": "the value printed by echo $MCP_AUTH_TOKEN above (JSON can't read a shell variable)",
        "LOG_LEVEL": "info"
      }
    }
  }
}
```

On Apple Silicon, ad-hoc sign the binary after building it and after every rebuild. Gatekeeper caches the signature against the file's identity, so replacing the binary invalidates the earlier approval and can make the launch fail silently.

```bash
codesign --force --sign - ./fleet-mcp
```

Fully quit and relaunch Claude Desktop so it starts the server and discovers the tools. Closing its window alone does not restart the process.

These client details, including confirmation prompts, JSON environment settings, signing, and relaunch behavior, describe Claude Desktop and macOS at the time of writing. Check them against your client and OS version if setup behaves differently; Fleet does not enforce those client behaviors.

### Connect an SSE client

For a client that supports SSE, such as Claude Code or Cursor, start the binary as a network service. Supply `FLEET_BASE_URL`, `FLEET_API_KEY`, and `MCP_AUTH_TOKEN` through the process environment or a `.env` file in its working directory. The listener uses `PORT`, with a default of 8080.

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
# MCP_AUTH_TOKEN is already exported from above; re-export it here if this is a new shell
./fleet-mcp            # transport: SSE, listening on :8080
```

### Smoke-test the server directly

You can test the server over stdio before configuring an assistant. The following JSON-RPC requests exercise MCP's named-method protocol and help separate server or token problems from client configuration problems:

```bash
export FLEET_BASE_URL="https://your-fleet.example.com"
export FLEET_API_KEY="the API-only user's token"
# MCP_AUTH_TOKEN is already exported from above; re-export it here if this is a new shell

cat <<'EOF' | ./fleet-mcp -transport stdio
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"1.0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"get_total_system_count","arguments":{}}}
EOF
```

Check that `tools/call` returns the enrolled-system count. A valid JSON response can still contain an error, so receiving a response alone does not confirm the connection. A successful count confirms the server, its Fleet token, and stdio communication. To check another tool, replace the `tools/call` line, for example with `get_host_policies` and a `host_id` argument.

For an SSE connection, point the client at `/sse` and send the token in an `Authorization: Bearer` header. The MCP server serves plain HTTP, so place TLS termination in front of any endpoint beyond localhost.

### Deploy a supervised SSE server

Run a shared SSE server under a process manager that can restart it, with a TLS-terminating proxy in front. A managed platform may provide both; for a self-hosted deployment, configure and operate them yourself.

Set `PORT` for the listener and keep `LOG_LEVEL` off `debug` when logs are centralized. Use `FLEET_CA_FILE` if Fleet presents a certificate from a private CA. For multi-host queries, set `FLEET_LIVE_QUERY_REST_PERIOD` at or above the Fleet server's own live-query period. Single-host queries have a separate fixed timeout, described under [Edge cases and precedence](#edge-cases-and-precedence).

Also choose the schema-refresh settings described above if you need a release-pinned schema or must control outbound access.

### A worked example: systemd behind Caddy

This example uses systemd to supervise the process and Caddy to provide TLS. It assumes a Debian or Ubuntu host with systemd, UFW, OpenSSH, and Caddy installed, a DNS name that resolves to the host, and port 443 reachable from your clients. On another distribution, adapt the package, firewall, and service-account commands.

Create the service account and install the binary:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin fleet-mcp
sudo cp ./fleet-mcp /usr/local/bin/fleet-mcp
sudo chown root:root /usr/local/bin/fleet-mcp
sudo chmod 755 /usr/local/bin/fleet-mcp
```

Write the environment file with access limited to the service account:

```bash
sudo mkdir -p /etc/fleet-mcp
sudo tee /etc/fleet-mcp/env > /dev/null <<EOF
FLEET_BASE_URL=https://your-fleet.example.com
FLEET_API_KEY=the API-only user's token
MCP_AUTH_TOKEN=$MCP_AUTH_TOKEN
EOF
sudo chown fleet-mcp:fleet-mcp /etc/fleet-mcp/env
sudo chmod 600 /etc/fleet-mcp/env
```

The resulting `/etc/fleet-mcp/env` contains `FLEET_BASE_URL`, `FLEET_API_KEY`, and `MCP_AUTH_TOKEN`. It is owned by `fleet-mcp` and is not world-readable. Set `PORT` as well if another service already uses 8080.

Install the systemd unit, but leave the service stopped until the firewall is ready:

```bash
sudo tee /etc/systemd/system/fleet-mcp.service > /dev/null <<'EOF'
[Unit]
Description=Fleet MCP server
After=network.target

[Service]
Type=simple
User=fleet-mcp
EnvironmentFile=/etc/fleet-mcp/env
ExecStart=/usr/local/bin/fleet-mcp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
```

The binary binds its plain-HTTP port on every interface. This release has no loopback-only bind option, so starting it would expose port 8080 to the network. Caddy's TLS listener does not close that separate port. Configure the firewall before starting the service:

```bash
# Allow what must stay reachable BEFORE the firewall is active, or enabling it
# drops your own SSH session:
sudo ufw allow OpenSSH
sudo ufw allow 443/tcp
# ufw already exempts loopback, so Caddy's localhost:8080 hop keeps working:
sudo ufw deny 8080/tcp
# Enable the firewall (harmless if already active), then confirm it:
sudo ufw --force enable
sudo ufw status verbose
```

Check that `ufw status verbose` reports `Status: active` and a deny rule for 8080. A rule in an inactive firewall provides no protection. On a cloud host, a security group can provide the equivalent restriction: allow ingress to 443, omit 8080, and apply the rules before the service starts. Clients should reach the MCP server through Caddy on 443.

Once you have verified the firewall, start the service:

```bash
sudo systemctl enable --now fleet-mcp
```

The binary supports a clean shutdown on SIGTERM, so use `systemctl restart fleet-mcp` when changing its configuration. The unit's `Restart=on-failure` setting brings it back after a crash.

Add the following to `/etc/caddy/Caddyfile`. Caddy forwards the headers and streams the response without buffering:

```
your-mcp-host.example.com {
    reverse_proxy localhost:8080
}
```

Reload Caddy:

```bash
sudo systemctl reload caddy
```

Test both accepted and rejected authentication. The last two requests differ only in their header:

```bash
curl -i https://your-mcp-host.example.com/healthz
# → 200, unauthenticated by design

curl -i https://your-mcp-host.example.com/sse
# → 401, no Authorization header reached the server

curl -N --max-time 2 -i -H "Authorization: Bearer $MCP_AUTH_TOKEN" https://your-mcp-host.example.com/sse
# → 200 and the stream opens; --max-time caps an otherwise endless read
```

From another machine, confirm that the plain-HTTP port cannot be reached directly:

```bash
curl -i --max-time 2 http://your-mcp-host.example.com:8080/healthz
# → connection refused or a timeout; a 200 here means 8080 is still exposed, so fix the firewall
```

If you use nginx or another reverse proxy, forward `/sse`, `/message`, and the `Authorization` header unchanged. Disable response buffering so the client receives the stream promptly. Let the binary perform its bearer-token check.

For Claude Code, add the following to the project's `.mcp.json` or your global MCP configuration. Other SSE clients need the same `/sse` URL and bearer token; use the syntax documented by that client.

```json
{
  "mcpServers": {
    "fleet": {
      "type": "sse",
      "url": "https://your-mcp-host.example.com/sse",
      "headers": {
        "Authorization": "Bearer the value printed by echo $MCP_AUTH_TOKEN above"
      }
    }
  }
}
```

### One-shot seed mode

You can also run `./fleet-mcp -seed` to create four global saved reports: macOS admin users, Windows update failures, Linux running containers, and universal OS version. It uses the Fleet instance in `FLEET_BASE_URL` and exits without starting an MCP server.

Seed mode still requires an API-only user's `FLEET_API_KEY` and a valid `MCP_AUTH_TOKEN` at startup, although it does not use the bearer token. Creating global reports requires a global admin, maintainer, or gitops identity. The observer and Observer+ roles recommended for runtime reads cannot perform this write.

If the API user has an endpoint allowlist, it also needs `POST /reports`. Neither [starting profile in A.11](../09-appendices/a.11-mcp-tool-reference.md#starting-allowlist-profiles) includes that route. Use a temporary elevated identity, with a temporary route entry if needed, to seed the reports. Then restore `FLEET_API_KEY` to the runtime identity.

Seed mode does not check for existing report names. Running it again causes each existing name to fail Fleet's uniqueness check; it neither duplicates nor overwrites those reports. The final log line reports how many of the four were created successfully.

## Confirm it works and decide who owns it

![How-to](../_assets/icons/howto-light.svg) Start with an end-to-end read from the assistant, then establish how you will monitor the service and manage its credentials.

### Verify the connection

At startup, the server logs the API-only user it verified against Fleet. It refuses to start if that check fails. An SSE server also provides an unauthenticated `/healthz` endpoint, but that probe checks only that the process is running. Pair it with a periodic authenticated read to check the connection to Fleet.

After restarting the assistant, ask “How many hosts does Fleet know about?” and compare the result with the console. This exercises tool discovery, the Fleet token, and an inventory read without running a query on a device. Over SSE, it also checks the client bearer token.

Use the total for this initial comparison. A platform breakdown can differ from the console because the MCP server recognizes only a fixed subset of Linux platform strings. It counts other distributions under “Other”, which can make Linux appear low and Other appear high even when the connection works.

If the tools are missing, check the client configuration path, the absolute binary path, and the signature on Apple Silicon. If tools appear but every call fails, check the server's Fleet base URL, token, and API-only identity.

### Own the credentials and access

One server process uses one Fleet API key and one MCP client token. Every SSE client with that bearer token receives the same Fleet scope, and activity is attributed to the same API-only user. The server cannot distinguish clients, revoke one client's access, or throttle clients individually. For separate revocation or attribution, use a server and API-only identity per trust group, or an identity-aware gateway.

Scope the Fleet user to the fewest fleets the assistant needs, where your edition supports that scope. Rotate its API key on your normal credential schedule. Rotate the MCP bearer token when a client that held it should lose access.

For either rotation, update the server configuration and restart the process. If you changed the bearer token, update the SSE client's `Authorization` header as well. Repeat the accepted-and-rejected authentication checks to confirm the change.

### Understand the audit record

Fleet attributes activity-producing operations, including live queries, to the API-only user in its [activity feed](../02-administer-and-deploy-fleet/2.8-activity-audit-logs-and-log-delivery.md). The MCP server does not log complete tool arguments, returned data, or assistant prompts. Its debug request log records the method and route with the query string removed.

Some warnings still contain targeting data. A software-fetch cap warning can include a host identifier; a warning about collapsing multiple targets can include the first fleet, platform, or label value. Apply access and retention controls suitable for the records those values identify.

Fleet and MCP logs provide operational evidence, but they do not form a complete conversation transcript. If you need a full record of assistant tool calls, capture it in an MCP client or gateway that supports that logging, with retention appropriate to the data it records.

### Include MCP in service operations

Once people rely on the assistant, give its MCP server a named owner and an [operating model](../07-operate-fleet/7.1-define-the-service-operating-model.md). Add the liveness probe and authenticated read to [service-health monitoring](../07-operate-fleet/7.4-observe-progress-and-service-health.md). Include the API key, bearer token, and proxy TLS certificate in your [rotation schedule](../07-operate-fleet/7.6-maintain-credentials-certificates-and-access.md), and include the service in the [readiness checklist and handoff](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md).

## Edge cases and precedence

![Reference](../_assets/icons/reference-light.svg) These limits help explain an unexpected answer or a connection that fails before reaching Fleet.

### Hostnames and display names

When a hostname matches several hosts and the preliminary search succeeds, the server returns candidates so the assistant can ask again by numeric host ID. If that search fails, the fallback lookup can select one matching host without a defined order. Use numeric host IDs for safety-critical reads. Also use an ID when the distinguishing value is a display name, because the substring search does not index display names.

### Live-query waits and offline hosts

Multi-host queries wait 25 seconds by default and return early once every online host has answered. Offline hosts contribute no rows and are not queued for later. A single-host query reports the host as offline with no rows.

`FLEET_LIVE_QUERY_REST_PERIOD` controls the multi-host wait. Keep it at or above Fleet's own server-side live-query period so the MCP server can wait for the campaign to finish.

Single-host queries use a synchronous request with a fixed 30-second client timeout compiled into the binary. Changing the multi-host wait does not affect it. Fleet's server-side live-query period must stay below 30 seconds for this path to complete with the stock client. A period at or above 30 seconds requires rebuilding the client with a longer timeout.

For an offline host, an inventory tool may still provide useful cached data. Its freshness depends on the last successful collection of that detail, which can be older than the host's last check-in.

### Input validation

The MCP server rejects malformed inputs before sending them to Fleet. CVEs must use the `CVE-YYYY-NNNN` shape, policy IDs must be positive integers, and a policy-result filter must include its policy. Page sizes are capped at 200. The tool returns an error when an input fails these checks.

### TLS and token validation

`FLEET_TLS_SKIP_VERIFY` enables skipped certificate verification only when set to the literal value `true`, and only for a Fleet URL at localhost. The server refuses to start if that setting accompanies a remote URL. It also rejects a token shorter than 32 bytes and rejects using `FLEET_TLS_SKIP_VERIFY` together with `FLEET_CA_FILE`.

### SSE request limits

SSE request bodies are capped at one mebibyte, with bounded header and read timeouts. These limit individual oversized or slow requests. The server has no rate limiter; configure throttling at the proxy or platform edge if needed. Stdio has no HTTP request surface.

The osquery data available on macOS, Windows, and Linux depends on the platform support of each table, covered in [4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md). ## Reference and troubleshooting

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) For a direct read tool, repeat its request against the Fleet REST API. Comparing the responses helps locate the problem in Fleet or in the MCP layer. [6.3](6.3-use-the-fleet-rest-api.md) explains API use, and [A.8](../09-appendices/a.8-api-action-and-endpoint-reference.md) lists the endpoints.

A composed tool may need several requests to reproduce its result. Filter intersections, CVE lookups across titles and versions, and reports or policies gathered across fleets all combine multiple Fleet responses. A failed or capped component can leave an incomplete result, with a warning in the MCP server log. Replay the component routes listed in [A.11](../09-appendices/a.11-mcp-tool-reference.md) and check those warnings.

The CVE-impact tool's estate count needs a separate check. If that count request fails, the tool silently uses zero as its total-systems denominator. Before treating a zero total as an empty estate, run A.11's estate-count check; there may be no warning to explain it.

For a live query that returns fewer hosts than expected, use [8.7](../08-troubleshooting/8.7-live-query-introspection.md) to examine the campaign and participation. For server problems, compare the MCP logs with Fleet's [server logs](../08-troubleshooting/8.3-server-logs.md).
