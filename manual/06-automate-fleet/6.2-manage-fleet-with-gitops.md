# Manage Fleet with GitOps

![Explanation](../_assets/icons/explanation-light.svg) GitOps lets you keep supported Fleet configuration in a repository, review changes before applying them, and use the same workflow to maintain that configuration over time. It gives administrators a shared record of intended settings and a practical way to coordinate changes across fleets.

The work happens in `fleetctl gitops`. The client reads your YAML and Fleet's current state, then applies a sequence of ordinary API calls. Each operation commits separately. Fleet has no server-side GitOps engine, repository watcher, or transaction covering the whole run, so your pipeline controls when runs happen and how they recover from an interruption.

Before the first production apply, prepare the complete file set, including an explicit `unassigned.yml` whenever you supply the global file. Check the deployment's effective exception settings too: they determine what omission can delete. Use dry runs for validation, then test a real apply in a non-production environment; a dry run has side effects and does not produce a change plan.

## Understand Fleet's GitOps execution model

![Explanation](../_assets/icons/explanation-light.svg) File order and deferred operations determine how a run progresses. Knowing that order helps you interpret its output and find the state left behind if it stops:

1. **Preflight.** Parse every supplied file, resolve environment variables and referenced files, and read existing Fleet state.
2. **Apply the global file first.** This includes organization settings, integrations, and controls.
3. **Apply the remaining files in the order supplied.** An explicit `unassigned.yml` runs at its place in the invocation; the client does not move it to the end.
4. **Complete conditional work.** Restore token assignments cleared earlier in the run and reapply App Store apps that were deferred.
5. **Delete absent fleets**, if the invocation requests it.
6. **Apply an empty Unassigned configuration** when a global file was supplied without an explicit Unassigned file. The clearing behavior is detailed below.
7. **Complete deferred label and certificate-authority deletions.**

A failure stops the sequence without undoing completed operations. If the fourth of six fleet files fails, the first three remain applied, the remaining files are untouched, and steps four through seven do not run. The resulting configuration may match neither the old commit nor the new one.

Keep the complete invocation, commit, output, and outcome in your pipeline history. Individual operations may produce activities ([8.12](../08-troubleshooting/8.12-audit-logs.md)), but Fleet records no run-level marker connecting them to a commit or confirming that the invocation finished.

Serialize applies in the pipeline as well. Fleet provides no lock to prevent two administrators, or an administrator and a scheduled job, from interleaving their runs.

### What Fleet knows about GitOps

The server handles GitOps requests through its ordinary API. It accepts a flag requesting replacement rather than merging, records which file a fleet came from, and can validate supported requests without persisting them. The client on your build runner handles the rest of the orchestration.

## Design the repository and configuration boundaries

![How-to](../_assets/icons/howto-light.svg) Organize the repository around a global file, a file for each named fleet, and a file for Unassigned. Fleet's generated workflow adds a pull-request dry run, a scheduled apply, and a concurrency block. Adapt that layout around four safeguards:

1. **Include an explicit `unassigned.yml` with every global apply.** Supply it even when the desired Unassigned configuration is empty.
2. **Maintain a complete production file manifest.** Check and record exactly which files the invocation supplies. An unchecked glob can omit a file and leave its resources eligible for deletion.
3. **Bind each environment to its destination.** Record the repository ref, file manifest, Fleet address, context, and credential together. A separate branch controls the content but cannot prevent it being sent to the wrong server.
4. **Restrict absent-fleet deletion to the complete production workflow.** Leave it disabled for staged migrations and ad hoc runs.

> ### The empty-Unassigned trap
>
> When a global file is supplied without `unassigned.yml`, the client creates an empty Unassigned configuration and applies it.
>
> On Premium, this clears the Unassigned setup-experience script, policies, self-service categories, and failing-policies webhook configuration. The software exception determines what happens to packages, Fleet-maintained apps, and App Store associations: they survive when the exception is on and are removed when it is off.
>
> Reports and labels remain unaffected. Unassigned does not support reports, and labels declared in an Unassigned file are ignored.
>
> The client emits no special warning about creating the empty configuration. Read any would-delete entries in the dry-run output before applying; the exit status alone will not draw attention to this change.

Absent-fleet deletion also uses the files in the invocation as its reference. It does not inspect the rest of your repository. Enabling the deletion flag with a partial file set requests deletion of fleets outside that set.

## Know what GitOps owns and can represent

![Reference](../_assets/icons/reference-light.svg) Removing a setting from YAML can clear it, reset it to a default, or leave its stored value unchanged. The result depends on the setting's GitOps contract. Four organization-setting blocks are replaced in full when a run applies:

- Features
- SSO settings
- MDM end-user authentication
- Apple account provisioning

For other supported settings, the client supplies defaults for individual fields. This includes integrations, the four webhook enable flags, Apple Business Manager and App Store assignment lists, most MDM controls, YARA rules, and the end-user licence agreement. These fields behave declaratively without making their entire containing blocks declarative.

Enroll secrets and certificate authorities have their own reconciliation paths, including exceptions and deferred deletion. They do not use the field-defaulting mechanism.

Other values survive omission: SMTP settings, server settings, host expiry, activity expiry, Fleet Desktop, vulnerability settings, conditional access, unspecified organization-information fields, and the change-management block itself. Removing one of those values from YAML leaves the stored setting in place.

For webhooks, omission affects the enable flag and destination differently. Omitting a webhook block turns off its defaulted enable flag, while retaining its destination and other configuration. Someone can later re-enable that stored configuration even though the repository no longer shows it.

### What can be expressed where

| Surface | Global | Named fleet | Unassigned | On omission |
|---|---|---|---|---|
| **Organization settings** | Yes | No | No | Four blocks replaced; most others survive |
| **Labels** | Yes | Yes | Ignored | Governed by the labels exception |
| **Reports** | Yes | Yes | Not supported | Cleared |
| **Policies** | Yes | Yes | Yes | Cleared |
| **Agent options** | Yes | Yes | Accepted but ignored, with a warning | `agent_options` is required in a global or named-fleet file; omission fails the run |
| **Profiles, scripts** | Yes | Yes | Yes | Cleared |
| **Controls** | Yes | Yes | Yes | Omission resets named-fleet controls. Exactly one of the global and Unassigned files must define controls; both or neither is an error. Controls defined only in Unassigned apply to global scope |
| **Software** | No | Yes | Yes | Governed by the software exception |
| **Enroll secrets** | Yes | Yes | Yes | Governed by the secrets exception |

The client recognizes `unassigned.yml` by its basename and rejects unknown keys by default. Keep that validation enabled in production. Use the absent-fleet deletion flag only with the complete, canonical invocation described above.

### The exceptions, which you must read rather than assume

Change-management exceptions determine whether omission deletes the corresponding resources. Their initial values can depend on deployment history:

| Exception | Fresh 4.90.0 | Upgraded to 4.90.0 |
|---|---|---|
| **Labels** | `false` | `true` |
| **Secrets** | `true` | `true` |
| **Software** | `false` | `false` |

With those defaults, omitting `labels:` deletes custom labels on a fresh installation and preserves them on an upgraded one. Check the current values under **Settings > Integrations > Change management** or in the returned configuration before deciding what an apply will do. Administrators can change these settings after deployment.

On a stock Premium deployment, the enabled secrets exception preserves enroll secrets when `secrets:` is omitted and rejects the key when it is included. Turning that exception off makes omission delete the secrets. Build the invocation around the effective setting, rather than assuming one omission rule for every resource.

## Migrate from click-ops

![How-to](../_assets/icons/howto-light.svg) Exporting your existing configuration gives you a starting point for a GitOps repository. Plan time to compare and repair the output before applying it: the hidden export command omits sensitive values and can produce YAML that will not apply.

Fleet's checked-in example output includes a structural type error and an internal placeholder token. Ordinary Premium configurations can produce these problems too, although not every export contains both. Review the export through a complete migration sequence:

1. **Export** the existing configuration.
2. **Compare** it with live state and record omissions.
3. **Repair** placeholders, structural errors, and missing configuration.
4. **Validate and test** a real apply in a non-production environment.
5. **Promote** one ownership boundary at a time.

### A worked migration

Start in a clean directory so you can compare the generated files with your repository:

```
mkdir migration && cd migration
fleetctl generate-gitops --dir .
```

`generate-gitops` writes `default.yml` at the root and `fleets/unassigned.yml` for Unassigned. It names other fleet files after the fleets in your deployment. The examples below use fleets named “Workstations” and “Servers”; replace their filenames with those actually generated for your deployment:

```
find fleets -maxdepth 1 -name '*.yml'
```

Compare each generated file with the settings visible in Fleet. Leave `--insecure` off so Fleet secret variables and other sensitive values are exported as placeholders instead of clear text. Fill those values through your chosen secret-handling process as you repair the files.

After repairing placeholders, structural errors, and omissions, validate the file set. Supply one `-f` for each file listed by `find`:

```
fleetctl gitops \
  -f default.yml \
  -f fleets/workstations.yml \
  -f fleets/servers.yml \
  -f fleets/unassigned.yml \
  --dry-run
```

The `-f` flag is required and repeatable. It accepts one file per flag, not a comma-separated list. GitOps rejects positional arguments, so a filename supplied without `-f` fails the command.

For a real test, use the same complete file set with an explicit non-production context and remove `--dry-run`:

```
fleetctl gitops \
  -f default.yml \
  -f fleets/workstations.yml \
  -f fleets/servers.yml \
  -f fleets/unassigned.yml \
  --context non-production
```

Always name the test context explicitly. Omitting `--context` uses the `default` context, which may point to a production deployment. Confirm the destination before running the command.

This complete invocation includes every fleet file and an explicit `unassigned.yml`. Once you intend it to be authoritative, you can add `--delete-other-fleets` to remove fleets outside the manifest. Keep that flag out of all partial invocations.

During a staged migration, use a separate invocation for the subset being adopted. Leave absent-fleet deletion disabled, and include `unassigned.yml` in any stage that contains the global file. Keep staged and complete workflows separate in the pipeline so the deletion flag cannot be combined with a partial manifest.

As each boundary moves into GitOps, agree who owns it and which interface changes should stop. GitOps mode can help communicate that ownership, with the enforcement limits below.

After a stage creates a fleet, check its failing-policies webhook. A webhook declared in the creation spec is not retained on that first apply; a second apply sets it through the edit path. Reapply the same complete state and confirm the webhook is configured ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)).

### GitOps mode is a guardrail, not a boundary

Turn on GitOps mode to make supported interface controls read-only and direct administrators to the repository. This helps reduce accidental interface changes to configuration managed in Git.

Authorization still comes from roles and credentials. API writes and non-GitOps fleetctl commands remain available, as do supported interface actions such as user administration, live queries, and host actions. Combine GitOps mode with the ownership agreement and access controls that govern those other paths.

## Supply secrets without committing them

![How-to](../_assets/icons/howto-light.svg) Choose the substitution mechanism around where you need the secret to remain protected. Ordinary environment substitution replaces a variable on the client before sending the request. Fleet receives and stores the resulting value, with no record of the environment variable that supplied it.

Fleet secret variables keep the value in Fleet, encrypted with the server private key. The stored script or profile retains a placeholder, which Fleet substitutes when delivering it to a device. List responses omit the value. Configure the server private key before using secret variables, and remove unused variables yourself; they are not deleted automatically.

Keep debug logging disabled in GitOps pipelines. It writes request and response bodies to standard error without redaction, and those bodies can contain enroll secrets, referenced secret values, substituted credentials, and integration tokens.

Check the runner's environment as well as its command line. A bare `DEBUG` environment variable enables the same behavior when its value resolves to true, even if another tool set it for an unrelated purpose. Treat logs from such a run as a secret exposure. Authorization headers and binary bodies are excluded, but the request and response bodies still require protection.

## Validate, review, and apply

![How-to](../_assets/icons/howto-light.svg) Use validation to catch problems early, then test the actual apply before promoting it. Each stage answers a different question about the files and the resulting Fleet state.

### What a dry run actually does

A dry run checks parsing and much of the supplied configuration, with several gaps:

- **Policies and reports** are read and compared but never sent to Fleet for validation.
- **Labels** are not sent for validation.
- **Profiles containing a Fleet secret variable** receive client-side file and structure checks but are excluded from the server-side profile validation batch.
- **A fleet that does not yet exist** causes validation to return before checking that fleet's Android certificates, policies, icons, and reports.

Dry runs also have network and server side effects. They transmit referenced secret values to Fleet for validation, after which Fleet discards the values without storing them. They can download software or fetch an app manifest when no usable cached copy exists, and they write transient server state.

Read the output for the checks performed and any would-delete entries. A clean dry run does not guarantee a successful apply or provide a plan of the changes the real run would make.

### The ladder

1. **Match client and server releases exactly.**
2. **Supply the complete file set** for the production workflow.
3. **Run validation and review its output.** The exit code alone is insufficient.
4. **Apply in a non-production environment.** Inspect the resulting state and test the workflow's recovery behavior.
5. **Serialize production applies** through the pipeline.
6. **Allow the run to finish.** Cancellation mid-sequence leaves completed operations in place and later work unapplied.
7. **Verify live state**, including device-side results where the change affects devices.

## Resolve drift, partial applies, and disagreement

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Use the failed run's output together with live Fleet state to decide how to recover. A repository shows the intended configuration; after a partial apply, you also need to establish which operations completed.

### When a run fails part way

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Stop other applies, identify the first failed operation, and correct its cause. Then rerun the same complete commit and full file set so the deferred operations can finish.

Applying an older commit sets its desired state through another forward apply. It cannot recall changes already delivered to devices or restore deleted resources that the older commit does not describe. Assess those effects separately when choosing a correction.

### The assignment-loss window

On Premium, a multi-file run may need to assign an Apple Business Manager or App Store token to a fleet it has not created yet. When the global configuration requests that assignment, the client first clears the assignment lists, creates the fleets, and restores the assignments near the end of the run.

A failure between those steps leaves the assignments cleared and can disrupt enrollment. Recover in this order:

1. **Stop subsequent and concurrent applies.**
2. **Inspect live assignments** to establish which mappings are missing.
3. **Preserve the failed output** and identify the first failed operation.
4. **Correct the cause and rerun the complete commit and file set** so the assignment-restoration phase executes.
5. **Restore the assignment map directly** under your incident procedure if a complete rerun cannot succeed promptly, then reconcile the repository and live state.
6. **Verify enrollment routing, token assignments, and affected App Store associations.**

### Living with the gaps

Your pipeline sets the reconciliation schedule and serializes the runs. Fleet has no built-in cadence or concurrency lock for GitOps, so configuration changes only when a client runs.

Retain each run's output and outcome in pipeline history. Individual activities can help investigate a change, but Fleet has no run-level “last apply succeeded” result to query. Check deferred deletions explicitly: labels, certificate authorities, and fleets removed by omission are deleted near the end of a successful run.

Also account for changes outside the GitOps workflow. Another API writer can change a field between runs, and GitOps mode leaves some interface actions available. The next apply governs the state represented by the requests it sends; it leaves settings outside that coverage untouched.
