# Design setup and self-service experiences

Two features share this chapter because administrators keep confusing them. **Setup** prepares a device during or immediately after a qualifying enrollment. **Self-service** stays available for the rest of the device's working life. Setup can hold a person at a progress screen; self-service never holds anyone anywhere.

The setup experience is the more demanding of the two, and it is not one feature with per-platform footnotes. **Platform decides the trigger, the available components, whether work blocks first use, what releases the device, and what anyone can see about it.** A macOS setup and a Windows setup share a name and a settings page, and almost nothing else.

Everything here is Fleet Premium.

## Choose setup-time enforcement or ongoing self-service

![Explanation](../_assets/icons/explanation.svg) The decision is about consequences. **On the platforms that block, an item in setup is an item that can fail somebody's first login.** Software that would merely be nice to have belongs in self-service, where a failure is a shrug rather than a support call from someone holding a new laptop.

**The blocking paths, macOS and Windows in OOBE, share one shape:**

1. An enrollment event triggers setup.
2. Fleet decides which configuration applies, by fleet and platform.
3. The end-user experience initialises, where the platform has one.
4. **Two lanes run at once**: the configuration lane (profiles, bootstrap package, account settings) and the setup-item lane (software, and on macOS a script).
5. The platform's coordinator joins the terminal states it cares about.
6. The device continues, blocks, offers an override, or is released.

Setup is not a serial checklist. Configuration work and setup-item work progress independently, and the release decision joins them later. Within the setup-item lane software is serialised, but that lane runs alongside profile delivery rather than after it.

**Two platforms are outside this model entirely.** Linux has only the agent-driven setup-item lane and holds no release at all. Android does not use the step-by-step machinery: it applies apps as a policy batch. iOS and iPadOS block on ADE but have no Fleet-driven progress flow. Read the lifecycle above as describing macOS and Windows-in-OOBE, and each platform section below for what actually happens.

### What each platform can actually do

![Reference](../_assets/icons/reference.svg)

| | macOS | Windows | Linux | iOS and iPadOS | Android |
|---|---|---|---|---|---|
| **Trigger** | **ADE, except MDM migration** | Enrollment | Agent enrollment | Enrollment, chiefly ADE | Enrollment |
| **Blocks first use** | Yes | **Only in OOBE** | No | Yes, on ADE | No |
| **End-user surface** | Fleet's setup dialog | Windows' own status page | A browser page | Setup Assistant only | None |
| **Profiles** | Yes | Yes | No | Yes | Policy |
| **Software** | Packages, store apps | Packages | Packages | Store apps only | Play apps |
| **Setup script** | **Yes** | No | No | No | No |
| **Overall timeout** | Depends, see below | **3 hours** | None | Worker-bounded | None |

**Only macOS has a setup script.** On Windows and Linux, a script-only package is ordinary setup software instead. The blocking row decides how much risk you are taking: a failure on macOS or an ADE iPhone happens in front of a waiting person, while a failure on Linux is a background inconvenience.

## Compose and govern the setup contract

![How-to](../_assets/icons/howto.svg)

### Prerequisites

Setup needs the platform's management channel already working: Apple Business and Apple MDM, Windows MDM, or Android Enterprise ([2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md), [2.11](../02-administer-and-deploy-fleet/2.11-windows-and-android-management-configuration.md)). Agent-delivered software additionally needs fleetd with scripts enabled. **Desktop self-service** needs Fleet Desktop; iOS and iPadOS reach it through an administrator-deployed web clip, and Android through managed Google Play.

### Targeting, and the label rule that surprises everyone

Setup software is selected **per fleet and per platform**. That is the whole of the targeting model, and it is narrower than the one you use everywhere else.

> **Labels do not filter setup software.** A package's label scope governs ordinary installation. It does **not** narrow what setup installs, on any platform, and the same is true of App Store and Play apps. An item you select for setup goes to **every** otherwise-eligible device enrolling into that fleet.

The practical consequence: **you cannot use labels to give one group of new machines a different setup payload.** If you need that, use separate fleets.

Two related points, so the rule does not get over-applied:

- **Linux distribution compatibility still filters.** A `.deb` does not go to an RPM host.
- **Policy labels are honoured.** The Windows and Linux policy gate described below resolves each policy's platform and label scope properly. Two label mechanisms sit inside this one feature and they behave oppositely, which is the trap.

When a title has several packages selected for setup, Fleet ignores the variants and takes the **first-added** one ([5.4](5.4-manage-software-and-applications.md)).

### End-user authentication

Setup can require the user to authenticate with your identity provider before the device continues. This is a **different configuration from administrator SSO**, with its own callback, and Fleet keeps them separately ([2.5](../02-administer-and-deploy-fleet/2.5-identity-providers-sso-scim-and-role-sync.md)). Use a separate application in your IdP: Fleet does not require it, but sharing one invites a change made for administrators to alter what happens to end users.

Enable it per fleet. What comes back is an identity Fleet attaches to the host, which is what makes a device's owner known from the moment it is set up rather than from whenever someone gets round to recording it.

> **On Windows and Linux, authentication fails open in three situations**: the agent's capability header cannot be read, the agent is older than 1.50.0, or the host is re-enrolling and Fleet still has a record of it. Each is permitted, and enrollment proceeds without any failure appearing in the interface: only the server logs distinguish a bypass from an authentication. **Do not treat setup authentication as a guarantee that every enrolled device has an authenticated owner.** An estate with older agents has holes in it you will not find by looking at Fleet's screens.

The end-user licence agreement has two constraints worth knowing. **It is shown only during macOS ADE**, and only when end-user authentication is on, so it is not a general consent mechanism across your estate. And **Fleet does not record acceptance**: the button advances the page and nothing else, with no acceptance event and no server-side record. Present it if you want people to read something. Do not present it to a compliance team as an auditable control.

### Failure and escape, decided before rollout

Decide three things before any device enrolls, because deciding them afterwards means deciding them while somebody waits.

**Which items are genuinely mandatory.** Keep that list short. A dependency you cannot test outside Fleet does not belong in it.

**What happens when software fails.** Where the platform offers it, you can stop setup on a failed install. Note what that covers: it cancels **all** remaining setup work including the macOS setup script, and it cancels Fleet's record of that work rather than reversing anything or stopping a script already running on the device.

**How you get a stuck device out.** The answer differs per platform and is covered in each section below. Have it written down before you need it.

## Build the macOS setup experience

![Explanation](../_assets/icons/explanation.svg) The richest setup experience, and the only desktop path with no overall timeout when a capable agent is coordinating it.

Once an ADE device enrolls, Fleet queues the work: the enrollment profile and configuration profiles, fleetd, the bootstrap package, and account configuration. These are delivered asynchronously rather than in a fixed order. Alongside them the setup-item lane works through software, one at a time, in **alphabetical order by display name, fixed when the work is queued**, and then runs the setup script.

**Only macOS orders software this way**, and only macOS has that script. Note the trigger too: setup runs on ADE enrollment, and MDM migration does not start it.

### Release, which has two paths

![Reference](../_assets/icons/reference.svg) A Mac is released by a `DeviceConfigured` command, and which machinery sends it depends on the machine:

| Situation | Release path | Timeout |
|---|---|---|
| No setup items at all | The worker | **15 minutes**, 10 to 30 attempts |
| Setup items, current capable agent | The agent's status poll | **None** |
| Setup items, older or incapable agent | The worker | 15 minutes |

**A Mac with setup software has no automatic timeout**, and that is the row you create by using the feature. If something it is waiting on never reaches a terminal state, it waits indefinitely, and there is no ordinary administrator control to force release. An identical Mac with no setup items would have given up after fifteen minutes.

Setting release to manual disables both automatic paths, which is a deliberate choice to take release into your own hands rather than a way to avoid the above.

### Release-ready is not successful

The setup release check does not ask whether things worked. It asks whether it should stop waiting.

A failed bootstrap package, an errored account configuration and a **Failed** profile all count as ready to release. So does a profile in **Verifying**, which Fleet has acknowledged but not independently confirmed, and which can still move backwards later ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md)). Release-ready is a weaker condition than success, and it is the condition that governs.

**So a Mac can be released to its user with a failed profile on it, and the setup screen the user watched will not have said so.** What Fleet does record is the profile's own status, visible under the host's OS settings. That is the place to look, and it is not the same place as the setup progress the user saw.

**Platform SSO is where this bites hardest.** Platform SSO is not a setup item and has no setup status of its own. It arrives as a configuration profile, sometimes with its extension app installed as setup software, and Fleet's part is timing rather than orchestration: it waits for those to become release-ready, releases the Mac, and Apple then presents the sign-on pane. Because a failed profile counts as release-ready, **Fleet can release a Mac whose Platform SSO prerequisites failed.** In Simplified Platform SSO deployments a failed supporting certificate profile or a failed extension app can leave the user sitting at Apple's sign-on pane. Check the ordinary profile and software-delivery results before wiping anything and starting again.

The Setup Assistant sign-on pane needs macOS 26 or later. The inspected upload and assignment paths contain no Fleet-side version check, so an older fleet receives the profile without ever seeing the pane.

### Accounts

Fleet can create the user's local account and set its full name and username. The account type has **three** choices, not two:

| Choice | Meaning |
|---|---|
| `admin` | The user's account is a local administrator |
| `standard` | The user's account is not an administrator |
| `none` | **No end-user account is created at all** |

**Both `standard` and `none` require the managed local administrator account**, because otherwise the Mac would have no administrator on it. Fleet enforces that.

> **Turning on end-user authentication also locks the name fields**, unless you explicitly say otherwise. The setting that locks them follows the authentication setting by default. People notice this as "why can't I type my own name", and it is easier to explain in advance.

Note also that installing fleetd manually conflicts with using macOS setup software or a setup script. Choose one.

## Hold and release Windows at the Enrollment Status Page

![Explanation](../_assets/icons/explanation.svg) Windows has two setup experiences and the difference between them is invisible from the settings page.

**The Enrollment Status Page runs only when two things are true**: enrollment is automatic, and the device is in the out-of-box experience. Automatic enrollment includes a user enrolling through Settings later, so **it is being in OOBE that decides**, not the enrollment type.

**When those conditions are not both met, Windows takes the same path Linux does**: a background, non-blocking browser experience with no status page and no hold.

> **The stop-on-failure setting for Windows only applies to the blocking path.** A device enrolled outside OOBE, which includes the ordinary BYOD case, ignores it entirely. Nothing warns you, and the setting looks active in the interface.

Check your own estate against that before assuming setup enforces anything on machines people enrolled themselves.

### The three-hour timeout is Fleet's

Fleet holds the status page for **three hours**, then gives up and cancels the remaining work. It sends that value to Windows as well, so both clocks agree, but the choice is Fleet's: Windows accepts anything from one hour to twenty-four. **It is not configurable**, and the two clocks start from slightly different moments, so treat three hours as approximate rather than exact.

To bring up the failure page promptly when something fails, Fleet briefly asks Windows for a timeout below Microsoft's documented minimum. It works on the Windows builds Fleet has tested. A future build could ignore it and delay the failure page by about an hour, which is worth knowing if you ever see that delay and wonder whether Fleet has hung.

### What holds the page, and what decides the outcome

Two different questions, and conflating them is easy.

**What holds the page:** work that has not finished. Pending profiles and in-flight software both keep the status page waiting.

**What decides how it ends:** a software failure, or the timeout. Profile *failure* does not produce the failure screen, because a failed profile is release-ready in the same way it is on macOS: Windows waits until a profile is verified or failed, then stops caring about it.

The failure outcome then depends on your stop-on-failure setting:

| Setting | What the user gets |
|---|---|
| **Enabled** | Remaining setup work is cancelled, and the failure page offers **reset only** |
| **Disabled** | Fleet waits for the other work to finish, then shows a **continuable** failure page offering reset or **Continue anyway** |

Collect logs is available either way. Neither reset nor log collection is a Fleet operation, and a reset means the device enrolls again from the beginning.

There is **no setup script on Windows.** A script-only package is setup software like any other.

## Run the Linux setup flow

![Explanation](../_assets/icons/explanation.svg) Linux has no MDM channel, so setup here is entirely the agent's doing, and it holds nothing.

The user gets a browser page showing progress. **It is not a gate.** Closing the browser does not stop the work, and nothing prevents the person using the machine while installs continue behind them. There is no overall timeout because there is nothing being held.

Setup software must be compatible with the distribution: `.deb` to Debian-based hosts, `.rpm` to RHEL-based hosts, and `.tar.gz`, `.sh` and `.py` anywhere. **This filtering does apply even though label scoping does not.**

### The policy gate

![Reference](../_assets/icons/reference.svg) Windows and Linux share one capability macOS does not have: a setup software item can be gated on policies, so Fleet installs it only if the device needs it.

Fleet waits until it has fresh label membership for this enrollment, works out which of the item's policies actually apply to this host by platform and label, and then decides:

| State of the applicable policies | What Fleet does |
|---|---|
| None applies to this host | **Install** |
| Any one of them is failing | **Install**, immediately, without waiting for the others |
| All of them are passing | **Skip**, and record the item as successful |
| None failing, but some results missing | **Wait**, then install anyway |

On that last row, Fleet waits up to **30 minutes**, measured from when the host enrolled rather than from when Fleet first looked at the item, and then **fails open and installs**. A result counts as missing if Fleet has no definitive answer recorded since this enrollment.

Two boundaries on that timer. A database error is not a missing result and does not fail open. And the timer only starts once label membership is fresh, so if freshness never arrives the gated item has no separate timeout releasing it. Fleet expects the first check-in after enrollment to provide it.

**A skipped item is recorded as successful.** There is no separate skipped state, which matters when you read the results.

## Finish iOS and iPadOS setup

![Explanation](../_assets/icons/explanation.svg) Much smaller in scope than the desktop experiences, and correspondingly less to go wrong.

Setup here can deliver configuration profiles and **App Store apps only**. No packages, no scripts, no Fleet dialog, and no agent, so there is nothing polling on the device's behalf. The user sees Apple's Setup Assistant and nothing of Fleet's.

The distinction that matters is the enrollment path. **On ADE, setup blocks**: the device waits before the user reaches the home screen, and release is bounded by the worker's fifteen-minute cutoff, **unless you have turned manual Apple release on**, which suppresses the automatic release entirely. **On manual or account-driven enrollment the same work happens in the background** afterwards, holding nothing.

App installs consume App and Book licences and are verified by asking the device what it holds ([5.4](5.4-manage-software-and-applications.md)). A licence shortage during setup fails the item rather than blocking indefinitely.

## Provision Android during enrollment

![Explanation](../_assets/icons/explanation.svg) Android setup is a policy operation, not a sequence of steps, and it is the exception to something [5.4](5.4-manage-software-and-applications.md) establishes.

Ordinarily Fleet does not install an Android app: it makes the app available in managed Google Play for the user to install. **Setup is the one path that pushes.** An app selected for setup is marked for installation in the device's policy, and the device installs it as it applies that policy.

There is no Fleet setup interface on Android, no progress list, and **no ordering guarantee**. Work is expressed as policy and applied as a batch. Fleet learns the outcome when the device reports the application's state, and this is the only Android path where an install is recorded and verified at all.

Both company-owned and personal work-profile enrollments can carry setup apps. Nothing here blocks the user.

## Publish and operate self-service

![How-to](../_assets/icons/howto.svg) Self-service is the opposite bargain from setup: nothing is enforced, nothing blocks, and the user chooses.

### Entitlement, and what does not provide it

An item appears in self-service when it is marked self-service **and** the host is in its label scope. Those two together are the entitlement model, and it is the model setup does not use ([5.4](5.4-manage-software-and-applications.md) owns the flag itself).

**Categories are navigation.** They group items in the interface so a long catalog is browsable. They are not security, they are not targeting, and moving an item between categories changes nothing about who can install it. Fleet ships seven, and they are per fleet, so two fleets can organise the same software differently.

**Android apps are always self-service** and cannot be made otherwise.

> Publishing and label scope govern self-service installation entitlement. They should not be treated as a general authorization boundary for every device-authenticated management action.

Who can do what splits the way it does elsewhere: administrators, maintainers and GitOps can publish and shape the catalog; administrators, maintainers and technicians can act on a host. GitOps can define the catalog and cannot use the device actions ([5.7](5.7-control-devices-and-send-mdm-commands.md)); a technician is the reverse ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)).

### Where people find it

| Platform | Surface |
|---|---|
| macOS, Windows, Linux | Fleet Desktop, the My device page |
| iOS and iPadOS | A web clip pointing at the device's self-service page |
| Android | Managed Google Play |

**Fleet does not create the iOS web clip for you.** The address is predictable, but deploying the profile that puts the icon on the home screen is your job. Documentation describes the workflow; nothing happens automatically, and a self-service catalog nobody can reach is a common and quiet failure.

### What a user can do, and what you will see

Install is the main action. **Install all** is worth understanding before someone presses it: it is not a transaction. Fleet queues each title independently in name order, and partial success is normal. It reports acceptance whether or not anything queued, and **when nothing queues at all it writes no activity**, so there is no record in the interface and only the server logs show the attempt. A user saying "I clicked Install all and nothing happened" may be describing exactly that.

**Uninstall availability differs by source.** Installer-backed titles can be uninstalled. App Store and in-house apps have no per-host uninstall action.

The install status and output a user sees is the same output an administrator sees, unredacted. That is the reason for the warning in [5.4](5.4-manage-software-and-applications.md) about what install scripts print.

## Read status, verify outcomes, and recover

![Troubleshooting](../_assets/icons/troubleshooting.svg)

### Two audiences, two different pictures

The setup progress a user sees is **not** an administrator results table, and reading one as the other causes real mistakes.

| The user sees | What it can actually mean |
|---|---|
| **Installed** | The requirement reached terminal success. **It does not prove Fleet ran an installer**: a policy-gated item that was skipped shows as installed |
| **Failed** | The step failed, **or** it was cancelled without ever running |

To tell those apart, use the activity record. A skipped item has no install activity at all. A cancelled item produces a cancellation activity, and when a failure stopped setup there is a separate activity saying so.

Fleet exposes **no administrator route or host-details checklist mirroring the user's setup screen.** What you have instead is partial and spread out: the host's OS settings for profile state, bootstrap package status on macOS, upcoming activities for queued work, and past activities recording what completed. Profile status is the most important of these and the least obvious, because it is where a failure that did not block release shows up.

### Verify before you roll out

**Test each enrollment path, not each operating system.** Windows in OOBE and Windows enrolled from Settings are different code paths with different blocking behaviour; ADE and manual enrollment differ the same way on Apple platforms. An estate that works when tested one way can behave completely differently when a real person enrolls another way.

For each path, confirm: the user was asked to authenticate if you required it, the account was created as intended, profiles are in the state you expect rather than merely done with delivery, the software you selected actually arrived, the script ran on macOS, and the device released.

Then deliberately break one thing and watch what happens. A setup you have never seen fail is a setup whose failure behaviour you are guessing at.

For self-service, test with an entitled device and an excluded one, and confirm the excluded device cannot see the item.

### Recovery

Removing or repairing a blocking item is the first move; asking users to re-enroll is the second, and it is worth knowing what re-enrollment actually does.

- **A fresh setup enqueue deletes the previous results and rebuilds the contract.** Re-enrolling does **not** preserve steps that already succeeded. Only the explicit retry-failed-steps operation does that.
- **On Windows and Linux, a host Fleet already knows about can re-enroll without end-user authentication.** If you are wiping a device specifically to enforce authentication again, delete it from Fleet first, or it will skip the step you wiped it for.
- **Apple re-enrollment cancels queued work and clears Fleet's Platform SSO registration** so fresh device keys are issued. Whether past activities stay attached to the host depends on your settings. For **Okta** Simplified Platform SSO specifically, Fleet's guidance is to revoke both the host's and the user's Okta Verify registrations before re-enrolling. Other identity providers will have their own equivalent, and it is worth finding out what it is before you need it.
