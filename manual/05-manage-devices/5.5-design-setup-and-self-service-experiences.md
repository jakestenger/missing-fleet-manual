# Design setup and self-service experiences

Two features share this chapter because administrators keep confusing them. **Setup** prepares a device during or immediately after a qualifying enrollment. **Self-service** stays available for the rest of the device's working life. Setup can hold a person at a progress screen; self-service never holds anyone anywhere.

The setup experience is the more demanding of the two, and it is not one feature with per-platform footnotes. **Platform decides the trigger, the available components, whether work blocks first use, what releases the device, and what anyone can see about it.** A macOS setup and a Windows setup share a name and a settings page, and almost nothing else.

Setup and self-service are Fleet Premium. The Fleet Desktop and My Device surface that self-service runs on ships on every edition, with individual features on the page gated separately; the section on that surface sets out which need Premium.

## Choose setup-time enforcement or ongoing self-service

![Explanation](../_assets/icons/explanation.svg) The decision is about consequences. **On the platforms that block, an item in setup is an item that can fail somebody's first login.** Software that would merely be nice to have belongs in self-service, where a failure is a shrug rather than a support call from someone holding a new laptop.

**The blocking paths, macOS and Windows in OOBE, share one shape:**

1. An enrollment event triggers setup.
2. Fleet decides which configuration applies, by fleet and platform.
3. The end-user experience initialises, where the platform has one.
4. **Two lanes run at once**: the configuration lane (profiles, bootstrap package, account settings) and the setup-item lane (software, and on macOS a script).
5. The platform's coordinator joins the terminal states it cares about.
6. The device continues, blocks, offers an override, or is released.

Setup is not a serial checklist. Configuration work and setup-item work progress independently, and the release decision joins them later. Within the setup-item lane software is serialised, but that lane runs alongside profile delivery rather than after it.

**Two platforms are outside this model entirely.** Linux has only the agent-driven setup-item lane and holds no release at all. Android does not use the step-by-step machinery: it applies apps as a policy batch. iOS and iPadOS block on ADE but have no Fleet-driven progress flow. Read the lifecycle above as describing macOS and Windows-in-OOBE, and each platform section below for what actually happens.

### What each platform can actually do

![Reference](../_assets/icons/reference.svg)

| | macOS | Windows | Linux | iOS and iPadOS | Android |
|---|---|---|---|---|---|
| **Trigger** | **ADE, except MDM migration** | Enrollment | Agent enrollment | Enrollment, chiefly ADE | Enrollment |
| **Blocks first use** | Yes | **Only in OOBE** | No | Yes, on ADE | No |
| **End-user surface** | Fleet's setup dialog | Windows' own status page | A browser page | Setup Assistant only | None |
| **Profiles** | Yes | Yes | No | Yes | Policy |
| **Software** | Packages, store apps | Packages | Packages | Store apps only | Play apps |
| **Setup script** | **Yes** | No | No | No | No |
| **Overall timeout** | Depends, see below | **3 hours** | None | Worker-bounded | None |

**Only macOS has a setup script.** On Windows and Linux, a script-only package is ordinary setup software instead. The blocking row decides how much risk you are taking: a failure on macOS or an ADE iPhone happens in front of a waiting person, while a failure on Linux is a background inconvenience.

## Compose and govern the setup contract

![How-to](../_assets/icons/howto.svg)

### Prerequisites

Setup needs the platform's management channel already working: Apple Business and Apple MDM, Windows MDM, or Android Enterprise ([2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md), [2.11](../02-administer-and-deploy-fleet/2.11-configure-windows-management.md), [2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md)). Agent-delivered software additionally needs fleetd with scripts enabled. **Desktop self-service** needs Fleet Desktop; iOS and iPadOS reach it through an administrator-deployed web clip, and Android through managed Google Play.

### Targeting, and the label rule that surprises everyone

Setup software is selected **per fleet and per platform**. That is the whole of the targeting model, and it is narrower than the one you use everywhere else.

> **Labels do not filter setup software.** A package's label scope governs ordinary installation. It does **not** narrow what setup installs, on any platform, and the same is true of App Store and Play apps. An item you select for setup goes to **every** otherwise-eligible device enrolling into that fleet.

The practical consequence: **you cannot use labels to give one group of new machines a different setup payload.** If you need that, use separate fleets.

Two related points, so the rule does not get over-applied:

- **Linux distribution compatibility still filters.** A `.deb` does not go to an RPM host.
- **Policy labels are honoured.** The Windows and Linux policy gate described below resolves each policy's platform and label scope properly. Two label mechanisms sit inside this one feature and they behave oppositely, which is the trap.

When a title has several packages selected for setup, Fleet ignores the variants and takes the **first-added** one ([5.4](5.4-manage-software-and-applications.md)).

### End-user authentication

Setup can require the user to authenticate with your identity provider before the device continues. This is a **different configuration from administrator SSO**, with its own callback, and Fleet keeps them separately ([2.5](../02-administer-and-deploy-fleet/2.5-identity-providers-sso-scim-and-role-sync.md)). Use a separate application in your IdP: Fleet does not require it, but sharing one invites a change made for administrators to alter what happens to end users.

Enable it per fleet. What comes back is an identity Fleet attaches to the host, which is what makes a device's owner known from the moment it is set up rather than from whenever someone gets round to recording it.

**Fleet 4.91 adds a deliberate way out, for installers you build yourself.** `fleetctl package --bypass-end-user-auth` produces an installer whose agent does not ask for end-user authentication during enrollment. It applies to **Linux and Windows only**: a Mac handles end-user authentication during MDM enrollment rather than during the agent's, so the flag changes nothing there. It needs fleetd v1.60.0 or later, since the behaviour lives in the agent the package installs.

The case it is for is a device whose user has already authenticated somewhere else, typically through an MDM enrollment that ran first, where asking again is noise rather than assurance. **On Windows, Fleet handles that case for you and the flag defers to it:** when the MSI installer carries a token proving the user authenticated during MDM enrollment, Fleet processes the token and links the identity, and the bypass does not apply. So the flag does not cost you the identity in the situation it was most likely built for.

**Whether the server accepts a bypassing agent is the server's decision, not the installer's.** The flag makes the agent stop asking; a server setting decides whether an agent that does not ask may enroll into a fleet that requires authentication. That setting is the subject of the note below.

> ### Fleet 4.91 changed who decides whether an unauthenticated host may enroll
>
> **Before 4.91, an agent that did not advertise the end-user authentication capability was let through**, and there was nothing you could do about it. The header the agent sent effectively made the decision, so an agent older than 1.50.0, the first fleetd whose capability list carries end-user authentication, or one whose header could not be read, enrolled without authenticating.
>
> **At 4.91 the server decides and the header is only a hint.** The setting is `mdm.allow_orbit_end_user_auth_bypass` in server configuration, and it **defaults to true**, which reproduces the old behaviour deliberately: an agent that does not ask for authentication is still allowed into a fleet that requires it, so upgrading the server does not lock out an estate of older agents overnight. Set it to `false` and those hosts are refused instead. It also governs the installers built with `--bypass-end-user-auth` above, which is the same case seen from the other end.
>
> **Turning it off does not close every hole, and the remaining one is worth knowing.** A host that Fleet can match to an existing record which has previously completed an agent enrollment is allowed to re-enroll without authenticating, whatever the setting says. The reasoning is sound, since a device rebuilding its agent state after a service restart or a database loss should not stop and demand a login from whoever happens to be at the keyboard, but the consequence is that **`false` means "every new Linux and Windows host authenticates", not "every enrollment authenticates"**. A record with no prior agent enrollment, such as one Fleet pre-created from Apple Business, does not qualify for the exemption.
>
> **A bypass still looks exactly like an authentication in the interface.** Enrollment proceeds, no failure appears anywhere, and only the server log distinguishes the two: it records the reason it allowed the host through. **So do not treat setup authentication as a guarantee that every enrolled device has an authenticated owner** unless you have turned the setting off, and even then read the sentence above about re-enrollment.

The end-user licence agreement has two constraints worth knowing. **It is shown only during macOS ADE**, and only when end-user authentication is on, so it is not a general consent mechanism across your estate. And **Fleet does not record acceptance**: the button advances the page and nothing else, with no acceptance event and no server-side record. Present it if you want people to read something. Do not present it to a compliance team as an auditable control.

### Failure and escape, decided before rollout

Decide three things before any device enrolls, because deciding them afterwards means deciding them while somebody waits.

**Which items are genuinely mandatory.** Keep that list short. A dependency you cannot test outside Fleet does not belong in it.

**What happens when software fails.** Where the platform offers it, you can stop setup on a failed install. Note what that covers: it cancels **all** remaining setup work including the macOS setup script, and it cancels Fleet's record of that work rather than reversing anything or stopping a script already running on the device.

**How you get a stuck device out.** The answer differs per platform and is covered in each section below. Have it written down before you need it.

## Build the macOS setup experience

![Explanation](../_assets/icons/explanation.svg) The richest setup experience, and the only desktop path with no overall timeout when a capable agent is coordinating it.

Once an ADE device enrolls, Fleet queues the work: the enrollment profile and configuration profiles, fleetd, the bootstrap package, and account configuration. These are delivered asynchronously rather than in a fixed order. Alongside them the setup-item lane works through software, one at a time, in **alphabetical order by display name, fixed when the work is queued**, and then runs the setup script.

**Only macOS orders software this way**, and only macOS has that script. Note the trigger too: setup runs on ADE enrollment, and MDM migration does not start it.

### Release, which has two paths

![Reference](../_assets/icons/reference.svg) A Mac is released by a `DeviceConfigured` command, and which machinery sends it depends on the machine:

| Situation | Release path | Timeout |
|---|---|---|
| No setup items at all | The worker | **15 minutes**, 10 to 30 attempts |
| Setup items, current capable agent | The agent's status poll | **None** |
| Setup items, older or incapable agent | The worker | 15 minutes |

**A Mac with setup software has no automatic timeout**, and that is the row you create by using the feature. If something it is waiting on never reaches a terminal state, it waits indefinitely, and there is no ordinary administrator control to force release. An identical Mac with no setup items would have given up after fifteen minutes.

Setting release to manual disables both automatic paths, which is a deliberate choice to take release into your own hands rather than a way to avoid the above.

### Release-ready is not successful

The setup release check does not ask whether things worked. It asks whether it should stop waiting.

A failed bootstrap package, an errored account configuration and a **Failed** profile all count as ready to release. So does a profile in **Verifying**, which Fleet has acknowledged but not independently confirmed, and which can still move backwards later ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md)). Release-ready is a weaker condition than success, and it is the condition that governs.

**So a Mac can be released to its user with a failed profile on it, and the setup screen the user watched will not have said so.** What Fleet does record is the profile's own status, visible under the host's OS settings. That is the place to look, and it is not the same place as the setup progress the user saw.

**Platform SSO is where this bites hardest.** Platform SSO is not a setup item and has no setup status of its own. It arrives as a configuration profile, sometimes with its extension app installed as setup software, and Fleet's part is timing rather than orchestration: it waits for those to become release-ready, releases the Mac, and Apple then presents the sign-on pane. Because a failed profile counts as release-ready, **Fleet can release a Mac whose Platform SSO prerequisites failed.** In Simplified Platform SSO deployments a failed supporting certificate profile or a failed extension app can leave the user sitting at Apple's sign-on pane. Check the ordinary profile and software-delivery results before wiping anything and starting again ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md#887-profile-status-values) is where Apple profile status values are read).

The Setup Assistant sign-on pane needs macOS 26 or later. The inspected upload and assignment paths contain no Fleet-side version check, so an older fleet receives the profile without ever seeing the pane.

### Accounts

Fleet can create the user's local account and set its full name and username. The account type has **three** choices, not two:

| Choice | Meaning |
|---|---|
| `admin` | The user's account is a local administrator |
| `standard` | The user's account is not an administrator |
| `none` | **No end-user account is created at all** |

**Both `standard` and `none` require the managed local administrator account**, because otherwise the Mac would have no administrator on it. Fleet enforces that: if the account type needs the managed account and it is not enabled, the configuration is rejected.

The managed local administrator account is Fleet's answer to Windows LAPS: a local admin account, username `_fleetadmin`, whose password Fleet holds, rotates and audits, so a Mac keeps an administrator even when the end user has none. Enable it with the setup-experience setting `enable_managed_local_account` (renamed to `enable_create_local_admin_account`, with the old key still accepted), which is off by default. Creating, enabling and disabling the account are Premium, and Fleet records each as an activity. The account described here is the macOS one, created through the setup experience. From Fleet 4.91.0 a Windows host can carry a managed local admin account too, built a different way and covered under [The Windows managed local admin account](#the-windows-managed-local-admin-account); Linux still has none, so do not plan on one there.

> **Turning on end-user authentication also locks the name fields**, unless you explicitly say otherwise. The setting that locks them follows the authentication setting by default. People notice this as "why can't I type my own name", and it is easier to explain in advance.

Note also that installing fleetd manually conflicts with using macOS setup software or a setup script. Choose one.

### Provision and sync the local account with Platform SSO

Fleet can provision the **local macOS account** a person logs into and unlocks their screen with, and keep that account's password in sync with the password they use against your identity provider, using Apple's Platform SSO framework in its Password mode. This is a different account from the one [2.5](../02-administer-and-deploy-fleet/2.5-identity-providers-sso-scim-and-role-sync.md) covers: 2.5's JIT provisioning creates a **Fleet console** account, for someone signing in to administer or observe Fleet itself. This feature creates and updates a **local user account on the Mac** instead, has no bearing on who can sign in to Fleet, and lives on its own settings page, **Account provisioning** under **Settings > Integrations**, next to and separate from **Single sign-on (SSO) for Fleet users**. `fpsso` is the search term Fleet's own settings search uses for that page, which is where this section, not 2.5, is the answer.

This is Fleet Premium, and it only ever acts on macOS. Apple's Platform SSO framework itself is older than this: the floor is Fleet's own, because Fleet's password-sync implementation targets macOS 26 or later, the same floor already noted above for the Setup Assistant sign-on pane, while the PSSO extension's older code paths need only macOS 14. The licence gate covers the feature as a whole: setting any one of its fields without a Premium licence is rejected outright, not silently accepted and then ignored.

**Three fields describe the upstream OAuth application:**

| Field | What it holds |
|---|---|
| Token URL | The identity provider's OAuth token endpoint, one that supports the Resource Owner Password Grant (ROPG), for example `https://your-okta-domain.okta.com/oauth2/v1/token` |
| Client ID | The application's client ID, registered with the identity provider |
| Client secret | The application's client secret |

They are **all-or-nothing**: Fleet accepts the three set together or all three empty, never a partial state that looks configured but cannot actually complete a sign-in. Setting them for the first time needs [Fleet's server private key](../01-foundations/1.6-the-fleet-server.md) already configured, the same prerequisite disk encryption has, because the client secret is encrypted with that key before Fleet stores it. The token URL and client ID are stored openly, and every read of the configuration back returns the secret masked rather than in the clear. **Changing the token URL requires supplying the secret again, even when the secret itself is not changing.** Carrying a stored secret across a change of endpoint without asking would hand your identity provider credential to whatever the new URL turns out to be, so Fleet refuses to do that silently.

Configure it through the **Account provisioning** UI page, the REST API's `mdm.apple_account_provisioning` configuration keys, or GitOps's `apple_account_provisioning` key. In GitOps, that key lives in your default, all-fleets file: it cannot be scoped to one fleet, matching the fact that it is macOS-only rather than fleet-specific. **GitOps applies your file as the whole configuration on every run, not as a diff**, so the secret has to be present in the section on every apply; a secret already stored from a previous run does not satisfy that requirement, and leaving the section out of the file entirely clears the configuration and deletes the stored secret rather than leaving it untouched.

Register a device by delivering one configuration profile: the same `com.apple.extensiblesso` profile and registration token [5.2](5.2-manage-configuration-profiles-and-declarative-settings.md#variables-and-secrets) introduces as the value designed never to be stored. The profile has to be Fleet's own. Its `ExtensionIdentifier` starts `com.fleetdm`, naming the Platform SSO extension bundled inside Fleet Desktop rather than a third-party IdP extension such as Okta Verify or Company Portal, and its `PlatformSSO` dictionary sets `UseSharedDeviceKeys` to `true`. Fleet rejects the registration-token variable anywhere else in a profile, so it cannot leak into a payload that isn't this one. The profile's `ExtensionData.BaseURL` has to be an HTTPS URL for your Fleet server, and every endpoint that URL implies needs a publicly trusted TLS certificate, including the `apple-app-site-association` document Apple fetches to associate the extension with that domain. Apple silently rejects a self-signed certificate, so check that first when a registration never happens.

Deliver the profile the way you deliver any other. Once it lands, the Mac's Platform SSO extension generates a signing and an encryption key pair in the Secure Enclave and registers the public halves with Fleet, authenticated by that registration token rather than by anything the device merely claims about itself. Registering again after a key rotation adds new keys without invalidating the old ones. During the same setup, Fleet also issues and certifies a key pair for the device to hold, so the two sides can derive a shared secret the Mac keeps locally. That shared secret is Apple's mechanism for letting the account unlock without Fleet or the identity provider needing to be reachable at that exact moment.

Whether the Mac is released to its user before or after these prerequisites finish is a setup-timing question, and it is covered where setup release is covered: [Release-ready is not successful](#release-ready-is-not-successful) above.

**macOS does not check in with Fleet at every sign-in or unlock.** It validates the local password against the identity provider only when its existing token is missing, expired, or more than four hours old, at whichever login or unlock comes next. Logging out and back in inside that window does not force a check. So a password changed at the identity provider can lag on the Mac by up to that four-hour window plus however long the screen stays locked, and what catches it up is someone entering the new password, not the passage of time.

When the check does run, the extension encrypts the password to Fleet's own published encryption key before it leaves the device, so the network path never carries it in the clear. Fleet decrypts it and relays the plaintext to your identity provider using the OAuth ROPG grant, with username and password posted as form fields. That grant is a lower bar than an interactive sign-in, and your identity provider may restrict or refuse it. Okta requires Resource Owner Password to be explicitly enabled on the application. Entra rejects it outright for users subject to MFA or federated through AD FS, and for those users the feature cannot authenticate them at all.

Your users' local-account passwords pass through Fleet on their way to the identity provider, and Fleet does not keep them. Each password is used once, for that one validation request, and then discarded.

If the identity provider accepts the password, it returns an OIDC `id_token`, and Fleet reads its claims without verifying any of it: not the signature, and not the issuer, audience, expiry or any other registered claim either, only that a `sub` is present at all. The reasoning that justifies skipping the signature, that Fleet received the token directly from the identity provider's own endpoint over TLS rather than by way of an untrusted party, does not extend to the rest of what goes unchecked. Treat this plainly as **Fleet trusting whatever your configured token endpoint sends back**, wholesale, not as a narrower claim about one skipped check. Only the subject is guaranteed present; the email address, name and preferred username Fleet forwards are exactly what the identity provider chose to send and can come back empty even after a password it accepted.

**Fleet does not decide which claim fills in the account's short name or full name.** That mapping is written once, by you, in the `com.apple.extensiblesso` profile's own `TokenToUserMapping`, for example mapping Apple's `AccountName` key to whatever claim your identity provider sends as the person's username. Fleet's part is narrower: it forwards the identity provider's standard claims through unchanged, plus anything the identity provider sends back under a claim name starting `account`, so a custom claim like `accountName` reaches that mapping. **What Fleet does set itself, on top of what it forwards, is the token's issuer, audience, nonce, timestamps and expiry**, the fields the device actually checks the signed token against, regardless of what the identity provider's response contained; that stops a rogue claim from colliding with Fleet's own protocol bookkeeping. It is not a guarantee about the user's identity: the subject and the other identity claims are the identity provider's values, passed through as sent, so a compromised or malicious token endpoint can still choose who a device believes it's provisioning for.

**A rejected password is the identity provider's decision, not Fleet's, and Fleet adds nothing of its own on top of it.** There is no separate lockout, retry limit, or cooldown on this path: Fleet relays whatever the identity provider said and stops there, so account lockout after repeated failures is a policy your identity provider enforces rather than a feature of this one. Nothing here changes the recovery picture already covered under [Recovery](#recovery): a device whose Platform SSO registration is broken is a candidate for the same re-enrollment path as any other setup failure, and the Okta-specific guidance there, to revoke both registrations before re-enrolling, applies here too.

### Retrieve and rotate the managed local administrator password

![How-to](../_assets/icons/howto.svg) The password is a privileged credential with its own reveal-and-rotate lifecycle, closer to Recovery Lock and the disk-encryption key in [5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md) than to anything else in setup.

**Who can read it:** anyone who can read the host, the same permission that reveals a disk-encryption key. Reading is per host and, from Fleet 4.91.0, works on a Windows managed account as well as a macOS one, once the account exists and its password is available, which is not immediate on a freshly enrolled host. **Fleet records each read as an activity**, so a reveal leaves a trace with a name on it. **Everything below about rotation is macOS-only**: a Windows account is revealed the same way but never rotates ([The Windows managed local admin account](#the-windows-managed-local-admin-account)).

**A reveal schedules a rotation, and only the first one does.** The first eligible view sets the password to auto-rotate about 65 minutes later and marks the rotation as Fleet's own. A repeat view inside that window reads back the same pending deadline rather than extending it. This is the opposite of Recovery Lock, where every reveal resets the clock and pushes rotation further out. A background job checks for due rotations every few minutes and, when one is due, sends the Mac a command to set a new password, so completion is device-dependent in the same way any MDM command is.

**Forcing a rotation is a separate, more restricted action.** Anyone who can read the host can reveal the password, but forcing a rotation needs the narrower permission to send MDM commands, which administrators and maintainers hold and observers do not. A forced rotation is refused while another rotation is already in flight for that host. Fleet records both a rotation and any failure to rotate as activities, attributing an automatic rotation to itself.

Enabling and disabling the account both log an activity, and disabling uses the same setup-experience setting that turned it on. Because the reveal-and-rotate mechanics mirror the disk-encryption key, the handle-it-as-a-secret guidance and the reveal path in [5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md#reveal-validate-and-repair-disk-recovery-credentials-safely) apply to this credential too.

## Hold and release Windows at the Enrollment Status Page

![Explanation](../_assets/icons/explanation.svg) Windows has two setup experiences and the difference between them is invisible from the settings page.

**The Enrollment Status Page runs only when two things are true**: enrollment is automatic, and the device is in the out-of-box experience. Automatic enrollment includes a user enrolling through Settings later, so **it is being in OOBE that decides**, not the enrollment type.

**When those conditions are not both met, Windows takes the same path Linux does**: a background, non-blocking browser experience with no status page and no hold.

> **The stop-on-failure setting for Windows only applies to the blocking path.** A device enrolled outside OOBE, which includes the ordinary BYOD case, ignores it entirely. Nothing warns you, and the setting looks active in the interface.

Check your own estate against that before assuming setup enforces anything on machines people enrolled themselves.

### The three-hour timeout is Fleet's

Fleet holds the status page for **three hours**, then gives up and cancels the remaining work. It sends that value to Windows as well, so both clocks agree, but the choice is Fleet's: Windows accepts anything from one hour to twenty-four. **It is not configurable**, and the two clocks start from slightly different moments, so treat three hours as approximate rather than exact.

To bring up the failure page promptly when something fails, Fleet briefly asks Windows for a timeout below Microsoft's documented minimum. It works on the Windows builds Fleet has tested. A future build could ignore it and delay the failure page by about an hour, which is worth knowing if you ever see that delay and wonder whether Fleet has hung.

### What holds the page, and what decides the outcome

Two different questions, and conflating them is easy.

**What holds the page:** work that has not finished. Pending profiles and in-flight software both keep the status page waiting.

**What decides how it ends:** a software failure, or the timeout. Profile *failure* does not produce the failure screen, because a failed profile is release-ready in the same way it is on macOS: Windows waits until a profile is verified or failed, then stops caring about it.

The failure outcome then depends on your stop-on-failure setting:

| Setting | What the user gets |
|---|---|
| **Enabled** | Remaining setup work is cancelled, and the failure page offers **reset only** |
| **Disabled** | Fleet waits for the other work to finish, then shows a **continuable** failure page offering reset or **Continue anyway** |

Collect logs is available either way. Neither reset nor log collection is a Fleet operation, and a reset means the device enrolls again from the beginning.

There is **no setup script on Windows.** A script-only package is setup software like any other.

### The Windows managed local admin account

![Explanation](../_assets/icons/explanation.svg) macOS is no longer the only platform with a Fleet-managed local administrator. From Fleet 4.91.0 a Windows host can carry the same `_fleetadmin` account, so a Windows machine keeps an administrator Fleet controls even when the person using it has none. It is the Windows counterpart to the macOS account under [Accounts](#accounts), and Fleet's answer to Windows LAPS on Windows itself rather than by analogy.

**It is built a different way.** On macOS Fleet creates the account with an MDM command as part of the setup experience. Windows has no such command in this path: fleetd creates the account directly on the device, hides it from the sign-in screen, generates its password locally, and sends that password back to Fleet to hold. Because the work happens in the agent, Fleet gives **fleetd 1.60.0 or later** as the requirement; the mechanism underneath is a capability the agent advertises, so an older agent never advertises it and Fleet never asks. The feature is **Fleet Premium**, gated on the licence the same way the macOS account is.

Turn it on with a setting of its own, separate from the macOS one:

| | macOS | Windows |
|---|---|---|
| Setting | `enable_managed_local_account` under `macos_setup` (older name `enable_create_local_admin_account`) | `enable_managed_local_account` under `windows_settings` |
| Who creates the account | Fleet, by MDM command | fleetd, on the device |
| Default | Off | Off |

Set the Windows key per fleet or across all fleets: the REST API takes it at `mdm.windows_settings.enable_managed_local_account`, and GitOps at `controls.windows_settings.enable_managed_local_account`. Enabling and disabling it are each recorded as an activity, as on macOS.

Once the setting is on, Fleet asks a host's fleetd to create the account on that host's next configuration check-in. Any Windows host connected to Fleet's MDM qualifies, whether it enrolled a minute ago or a year ago: enrollment is not the trigger and the Enrollment Status Page is not a prerequisite, so turning the setting on across an estate that is already enrolled reaches those hosts as they poll. fleetd generates a password formatted in hyphen-separated groups meant to be read off a screen and typed at a login prompt, leaving out characters that get confused when transcribed by hand, creates or resets the account, and escrows the password. Fleet stores it encrypted with [the Fleet server private key](../01-foundations/1.6-the-fleet-server.md), the same key disk-encryption keys need, so that key has to be configured or the escrow has nowhere to land. Fleet keeps asking until the host escrows a password for its current enrollment, then stops. **Re-enrolling or re-imaging the device clears that record, so Fleet asks again and fleetd resets the account to a fresh escrowed password.** If fleetd cannot create the account it reports why, and Fleet records the failure on the host the way it records a BitLocker or LUKS escrow failure, rather than leaving it in the logs alone.

> **The Windows account can be revealed but not rotated.** Reading its password uses the same host-read permission and reveal path as the macOS account and the disk-encryption key ([Retrieve and rotate the managed local administrator password](#retrieve-and-rotate-the-managed-local-administrator-password)), and each read is an activity. None of the rotation machinery in that section reaches Windows: revealing a Windows password does not arm an auto-rotation, and there is no force-rotate action for it, which Fleet refuses outright. The only thing that changes a Windows managed account's password is fleetd re-provisioning it on the next enrollment. Plan rotation as a re-enrollment, not a button.

## Run the Linux setup flow

![Explanation](../_assets/icons/explanation.svg) Linux has no MDM channel, so setup here is entirely the agent's doing, and it holds nothing.

The user gets a browser page showing progress. **It is not a gate.** Closing the browser does not stop the work, and nothing prevents the person using the machine while installs continue behind them. There is no overall timeout because there is nothing being held.

Setup software must be compatible with the distribution: `.deb` to Debian-based hosts, `.rpm` to RHEL-based hosts, and `.tar.gz`, `.sh` and `.py` anywhere. **This filtering does apply even though label scoping does not.**

### The policy gate

![Reference](../_assets/icons/reference.svg) Windows and Linux share one capability macOS does not have: a setup software item can be gated on policies, so Fleet installs it only if the device needs it.

Fleet waits until it has fresh label membership for this enrollment, works out which of the item's policies actually apply to this host by platform and label, and then decides:

| State of the applicable policies | What Fleet does |
|---|---|
| None applies to this host | **Install** |
| Any one of them is failing | **Install**, immediately, without waiting for the others |
| All of them are passing | **Skip**, and record the item as successful |
| None failing, but some results missing | **Wait**, then install anyway |

On that last row, Fleet waits up to **30 minutes**, measured from when the host enrolled rather than from when Fleet first looked at the item, and then **fails open and installs**. A result counts as missing if Fleet has no definitive answer recorded since this enrollment.

Two boundaries on that timer. A database error is not a missing result and does not fail open. And the timer only starts once label membership is fresh, so if freshness never arrives the gated item has no separate timeout releasing it. Fleet expects the first check-in after enrollment to provide it.

**A skipped item is recorded as successful.** There is no separate skipped state, which matters when you read the results.

## Finish iOS and iPadOS setup

![Explanation](../_assets/icons/explanation.svg) Much smaller in scope than the desktop experiences, and correspondingly less to go wrong.

Setup here can deliver configuration profiles and **App Store apps only**. No packages, no scripts, no Fleet dialog, and no agent, so there is nothing polling on the device's behalf. The user sees Apple's Setup Assistant and nothing of Fleet's.

The distinction that matters is the enrollment path. **On ADE, setup blocks**: the device waits before the user reaches the home screen, and release is bounded by the worker's fifteen-minute cutoff, **unless you have turned manual Apple release on**, which suppresses the automatic release entirely. **On manual or account-driven enrollment the same work happens in the background** afterwards, holding nothing.

App installs consume App and Book licences and are verified by asking the device what it holds ([5.4](5.4-manage-software-and-applications.md)). A licence shortage during setup fails the item rather than blocking indefinitely.

## Provision Android during enrollment

![Explanation](../_assets/icons/explanation.svg) Android setup is a policy operation, not a sequence of steps, and it is the exception to something [5.4](5.4-manage-software-and-applications.md) establishes.

Ordinarily Fleet does not install an Android app: it makes the app available in managed Google Play for the user to install. **Setup is the one path that pushes.** An app selected for setup is marked for installation in the device's policy, and the device installs it as it applies that policy.

There is no Fleet setup interface on Android, no progress list, and **no ordering guarantee**. Work is expressed as policy and applied as a batch. Fleet learns the outcome when the device reports the application's state, and this is the only Android path where an install is recorded and verified at all.

Both company-owned and personal work-profile enrollments can carry setup apps. Nothing here blocks the user.

## Publish and operate self-service

![How-to](../_assets/icons/howto.svg) Self-service is the opposite bargain from setup: nothing is enforced, nothing blocks, and the user chooses.

### Entitlement, and what does not provide it

An item appears in self-service when it is marked self-service **and** the host is in its label scope. Those two together are the entitlement model, and it is the model setup does not use ([5.4](5.4-manage-software-and-applications.md) owns the flag itself).

**Categories are navigation.** They group items in the interface so a long catalog is browsable. They are not security, they are not targeting, and moving an item between categories changes nothing about who can install it. Fleet ships seven, and they are per fleet, so two fleets can organise the same software differently.

**Outside the setup experience, ordinary Android catalog apps are always offered** through managed Google Play for the user to install, rather than pushed. Setup is the one exception, and it pushes.

> Publishing and label scope govern self-service installation entitlement. They should not be treated as a general authorization boundary for every device-authenticated management action.

Who can do what splits the way it does elsewhere: administrators, maintainers and GitOps can publish and shape the catalog; administrators, maintainers and technicians can act on a host. GitOps can define the catalog and cannot use the device actions ([5.7](5.7-control-devices-and-send-mdm-commands.md)); a technician is the reverse ([2.6](../02-administer-and-deploy-fleet/2.6-user-accounts-roles-and-service-identities.md)).

### Where people find it

| Platform | Surface |
|---|---|
| macOS, Windows, Linux | Fleet Desktop, the My device page |
| iOS and iPadOS | A web clip pointing at the device's self-service page |
| Android | Managed Google Play |

**Fleet does not create the iOS web clip for you, but the address is predictable, so the profile is short.** An Apple mobile device reaches its catalog at `https://{YOUR_SERVER_URL}/device/$FLEET_VAR_HOST_UUID/self-service`, where `$FLEET_VAR_HOST_UUID` is the per-host variable Fleet substitutes when it sends the profile ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md)). The host identifier in that address is how Fleet locates the device on that path: iOS and iPadOS carry no desktop device token, so the UUID-bearing URL is the supported route and an ordinary device-token address is refused for them (how the request actually authenticates is covered under the My Device surface below). Deliver it as a managed web-clip configuration profile scoped to those hosts, the same way any Apple profile is delivered; Fleet's iOS and iPadOS solution documentation publishes a ready-made self-service web-clip profile you can adapt rather than authoring one from scratch. Then confirm the icon lands on the home screen and opens the catalog, because nothing happens automatically, and a self-service catalog nobody can reach is a common and quiet failure.

### What a user can do, and what you will see

Install is the main action. **Install all** is worth understanding before someone presses it: it is not a transaction. Fleet queues each title independently in name order, and partial success is normal. It reports acceptance whether or not anything queued, and **when nothing queues at all it writes no activity**, so there is no record in the interface and only the server logs show the attempt. A user saying "I clicked Install all and nothing happened" may be describing exactly that.

**Uninstall availability differs by source.** Installer-backed titles can be uninstalled. App Store and in-house apps have no per-host uninstall action.

The install status and output a user sees is the same output an administrator sees, unredacted. That is the reason for the warning in [5.4](5.4-manage-software-and-applications.md) about what install scripts print.

### How a person reaches it without a Fleet account

The My Device page authenticates with a per-host device token carried in the URL, not a Fleet login. The token identifies one host, and it is what lets someone open their own device page while holding no Fleet account and no role. This is the device-authenticated surface [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md#the-five-channels) sets apart from Fleet's management channels, and [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md#who-calls-fleet-and-what-they-present) catalogues its endpoints as the Device auth class.

**The token has a one-hour freshness window, measured from the last time it changed.** Fleet accepts the current token, or the one immediately before it, only while the stored token was written within the last hour. A genuine token change resets that window; an agent check-in does not, and re-submitting the same token does not either, because presenting the existing value again does not refresh its timestamp. Keeping the one previous token valid makes rotation graceful, so a link does not break the instant the token turns over. If a host goes quiet long enough that no fresh token is written, its My Device link stops authenticating until a new token is written, whether by the agent's next rotation or by one of the server-side paths below.

**Three things can write that token.**

- **Orbit** normally provisions and rotates it on the host, whether or not Fleet Desktop was included in the package. This is the ordinary path.
- **A global administrator requesting the host's My Device URL** makes Fleet reuse a still-fresh token or mint a new one and store it the way Orbit does, which is what hands the administrator a working link. That request is restricted to global administrators, more tightly than the host-read permission that reveals most host detail, and Fleet audits it as a distinct my-device-URL retrieval activity.
- **Conditional-access remediation** mints and stores a token when a host with failing policies is sent through remediation and its existing token is missing or expired, so the remediation redirect resolves to a working device page.

Treat a My Device URL as a credential for that host, because for its freshness window it is one.

iOS and iPadOS do not use the device token, because those platforms carry no fleetd to hold one. When the device presents a client certificate Fleet authenticates on that, and the certificate takes precedence; where none is presented, Fleet falls back to the UUID-bearing self-service URL, so the host identifier in that address identifies the device rather than standing in as a second, separate credential.

### The transparency link, and what the page will not reveal

**The menu bar's About Fleet link points at a transparency page, chosen by a fixed precedence.** By default it is Fleet's own transparency page. A deployment with Fleet's Secureframe partnership configured gets that partner destination instead. On Premium, a custom transparency URL you set takes precedence over both, so you can point users at your own account of what device management can and cannot see. The custom URL is the Premium step; the default and the partner destination are not something you choose.

**The end user sees summaries and banners, never key values.** Disk encryption is the sharp example: My Device can tell a user that a recovery key is available for their device, as a banner, but the decrypted key is never returned to the device-authenticated page. Reading the actual value is an operator action on the user-authenticated host endpoint, covered in [5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md#reveal-validate-and-repair-disk-recovery-credentials-safely). The same shape holds across the page: the user gets enough to see state and to act, not the underlying secrets.

### The feature family is gated member by member

![Reference](../_assets/icons/reference.svg) "Is Fleet Desktop Premium?" has no single answer, because the surface is a family of separately licensed features. Packaging the component and opening the basic My Device page are available on every edition; several of the things the page can do are not.

| Feature | Edition |
|---|---|
| Fleet Desktop packaging (`--fleet-desktop`) and the menu-bar item | Every edition |
| Opening the My Device page | Every edition |
| The Fleet Desktop summary the menu-bar item reads | Premium |
| Self-service install and uninstall | Premium |
| Custom transparency URL | Premium |
| Conditional-access bypass from My Device | Premium |
| User-initiated Linux LUKS escrow from My Device | Premium |

Fleet's own Fleet Desktop client is not part of this manual's source, so this describes the server's contract rather than the client's behaviour: the server designates one endpoint, `/desktop`, as the summary the menu-bar item is meant to read. Whether that summary returns, and what it carries, is where the Premium line falls for the menu-bar item. Self-service composition and entitlement are covered above in this chapter; the Linux LUKS escrow the page can trigger is a device-initiated action covered with disk encryption in [5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md).

## Read status, verify outcomes, and recover

![Troubleshooting](../_assets/icons/troubleshooting.svg)

### Two audiences, two different pictures

The setup progress a user sees is **not** an administrator results table, and reading one as the other causes real mistakes.

| The user sees | What it can actually mean |
|---|---|
| **Installed** | The requirement reached terminal success. **It does not prove Fleet ran an installer**: a policy-gated item that was skipped shows as installed |
| **Failed** | The step failed, **or** it was cancelled without ever running |

To tell those apart, use the activity record. A skipped item has no install activity at all. A cancelled item produces a cancellation activity, and when a failure stopped setup there is a separate activity saying so.

Fleet exposes **no administrator route or host-details checklist mirroring the user's setup screen.** What you have instead is partial and spread out: the host's OS settings for profile state, bootstrap package status on macOS, upcoming activities for queued work, and past activities recording what completed. Profile status is the most important of these and the least obvious, because it is where a failure that did not block release shows up.

### Verify before you roll out

**Test each enrollment path, not each operating system.** Windows in OOBE and Windows enrolled from Settings are different code paths with different blocking behaviour; ADE and manual enrollment differ the same way on Apple platforms. An estate that works when tested one way can behave completely differently when a real person enrolls another way.

For each path, confirm: the user was asked to authenticate if you required it, the account was created as intended, profiles are in the state you expect rather than merely done with delivery, the software you selected actually arrived, the script ran on macOS, and the device released.

Then deliberately break one thing and watch what happens. A setup you have never seen fail is a setup whose failure behaviour you are guessing at.

For self-service, test with an entitled device and an excluded one, and confirm the excluded device cannot see the item.

### Recovery

Removing or repairing a blocking item is the first move; asking users to re-enroll is the second, and it is worth knowing what re-enrollment actually does.

- **A fresh setup enqueue deletes the previous results and rebuilds the contract.** Re-enrolling does **not** preserve steps that already succeeded. Only the explicit retry-failed-steps operation does that.
- **On Windows and Linux, a host Fleet already knows about can re-enroll without end-user authentication.** If you are wiping a device specifically to enforce authentication again, delete it from Fleet first, or it will skip the step you wiped it for.
- **Apple re-enrollment cancels queued work and clears Fleet's Platform SSO registration** so fresh device keys are issued. Whether past activities stay attached to the host depends on your settings. For **Okta** Simplified Platform SSO specifically, Fleet's guidance is to revoke both the host's and the user's Okta Verify registrations before re-enrolling. Other identity providers will have their own equivalent, and it is worth finding out what it is before you need it.
