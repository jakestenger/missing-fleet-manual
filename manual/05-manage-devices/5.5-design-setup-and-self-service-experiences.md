THE ORGANISING ARGUMENT, and the reason the stub's original six headings were rejected: the setup
experience is NOT one portable feature with per-platform footnotes. Platform determines the trigger,
the available components, whether work blocks first use, what releases the device, and what status
anyone sees. The reviewer's words: the stub was "a sound topic inventory, but not a safe drafting
spine". So the five platforms get five sections, and the common lifecycle is the spine that carries

THE SHAPE OF SETUP IS PARALLEL LANES WITH A JOIN, not a serial list. Configuration work and
setup-item work progress asynchronously; the device's continuation decision joins their terminal
states later. Within the setup-item lane, software is serialised and the macOS setup script follows
software. Write the lifecycle as that, because a serial list is the misconception the chapter exists
to correct.

FOUR CLAIMS PINNED IN REVIEW. Write these exactly; each was corrected from my first understanding.

1. LABELS DO NOT FILTER SETUP SOFTWARE, ON ANY PLATFORM. Not macOS-only, as I first thought. The
   enqueue query filters by fleet, setup selection, platform and Linux distribution, and never joins
   the label tables. Its own comment says "labels don't apply during setup", so it is deliberate at
   this release. The same holds for VPP and Android store apps. CONSEQUENCE TO WARN ABOUT: a label
   controls ordinary availability but does NOT narrow setup installation, so an item selected for
   setup reaches every otherwise-eligible enrolling device in that fleet and platform. Linux
   distribution compatibility still filters .deb and .rpm. And when a title has several active
   packages selected for setup, Fleet ignores the label variants and queues the FIRST-ADDED package.
   Do NOT confuse this with policy labels: Windows/Linux policy gating DOES resolve each associated
   policy's platform and label scope.

2. SKIPPED AND CANCELED NORMALISE, BUT THE AUDIENCE MATTERS. A Windows/Linux item whose gating
   policies all pass is written terminal `success` with no install request, and the END-USER setup
   UI renders that as "Installed". Unfinished rows are written `cancelled` and rewritten to `failure`
   when Orbit or the My device endpoint next consumes them, rendering as "Failed". CORRECTION FROM
   MY FRAMING: these are end-user progress labels, not an administrator results table. The
   administrator sees no install activity for a skipped item, a "canceled ... install ... during
   setup experience" activity for canceled software, and a separate "canceled setup experience ...
   because ... failed to install" activity when a failure stopped setup. So teach: Installed means
   the requirement reached terminal success and does NOT prove Fleet ran an installer; Failed can
   mean the step failed OR that it was canceled without running; use the activity record to tell
   them apart.

3. THE THREE-HOUR WINDOWS ESP TIMEOUT IS FLEET'S, NOT MICROSOFT'S. `ESPTimeoutSeconds = 3 * 60 * 60`.
   Fleet sends 180 minutes to Microsoft's CSP and independently treats the ESP as timed out past that
   age. Microsoft's accepted range is 60 to 1440 minutes; Fleet picks 180 within it, and it is not
   administrator-configurable at this release. Call it "Fleet's three-hour Windows ESP timeout", never
   "the Windows ESP three-hour maximum": do not attribute a Fleet choice to Microsoft.

4. POLICY-GATE PRECEDENCE, Windows and Linux only, for setup packages with install-software
   automation pointing at them. Fleet waits for fresh label membership, resolves which policies apply
   by platform and policy label scope, then:
     no applicable policy                  -> install
     any applicable policy failing         -> install immediately, even if another result is missing
     every applicable policy passing       -> skip, store success
     none failing but results missing      -> wait, then fail open and install
   "Missing" means no definitive passes value at or after the host's current LastEnrolledAt.
   "Eventually" is a 30 MINUTE timeout anchored to LastEnrolledAt, not to when Fleet first looked,
   and Fleet installs when elapsed time is strictly greater. A datastore error is NOT treated as a
   missing result and does not fail open.

## Choose setup-time enforcement or ongoing self-service

<!--
- The two different promises: setup prepares a device during or immediately after enrollment;
  self-service stays available for the device's whole working life.

  must be ready before release; compose the setup items; select fleet and platform; let the
  platform coordinator run them; interpret completion and recover.
- THE PLATFORM CAPABILITY MATRIX LIVES HERE, not in its own section. Columns: triggering enrollment

  steps, blocking or background behaviour, completion owner, failure and timeout exit.

  self-service. Every item in setup is an item that can block or fail a first login.
