# Plan, target, and govern device changes

Fleet connects the device information in Part IV to the actions administrators take every day: applying settings, delivering software, running scripts, and helping employees recover access. Those capabilities are most useful when a change has a clear target, a small pilot, and a result you know how to verify. Part V follows that path from planning through delivery.

Start with three questions that will help you choose and follow any device change in this part:

1. **What kind of change is this?** Desired state, a discrete activity, or a device action.
2. **What carries it?** Fleet's agent, Apple's MDM channel, Windows management, or Android's policy API.
3. **How do you know it worked?** Each of those has its own status model, and they do not mean the same things by the same words.

## Three kinds of change

![Explanation](../_assets/icons/explanation.svg) Identify whether you are maintaining a setting, requesting a unit of work, or taking a device action. That choice determines how the change is repeated and verified.

**Desired state** is a description of how a device should be, which Fleet keeps true. A configuration profile is the clearest example. You do not run a profile; you declare that hosts in a scope have it, and Fleet reconciles reality against that declaration continuously. Remove a host from the scope and the profile is removed from the host. There is no single moment when it "ran".

**A discrete activity** is a unit of work that happens once, has an identity, and ends in a terminal state. Running a script and installing software are discrete activities. They queue, they execute, they succeed or fail, and the record persists whether or not you ask again.

**A device action** is an instruction to the device itself: lock it, wipe it, find it. These have the character of activities, but their consequences are not confined to Fleet's model of the world, and some are irreversible.

A desired-state change is followed until the device matches its configuration. A discrete activity has a completion result to review. A device action may have lasting consequences outside Fleet, so verification includes confirming that you selected the intended device and outcome.

A familiar action can use a different model on each platform. An App Store installation is a Fleet activity delivered through Apple MDM. An Android application is delivered by changing managed policy and does not enter Fleet’s activity queue. Follow the platform-specific delivery model when interpreting progress.

## The four channels

![Reference](../_assets/icons/reference.svg) Under the three kinds sit four transports. Which one carries a change decides how quickly it arrives, what happens when the device is asleep, and where you look when it does not.

| Channel | Carries | Reaches |
|---|---|---|
| **Fleet's agent** | Scripts, installer-based software | Hosts running fleetd ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)) |
| **Apple MDM and declarative management** | Apple profiles, App Store and in-house app installs, Apple device actions | Enrolled Apple devices ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)) |
| **Windows management** | Windows profiles and commands, delivered inside a management session | Enrolled Windows devices |
| **Android policy** | Android configuration and application delivery, by changing the device's policy | Enrolled Android devices |

The delivery channel helps explain a wait. Agent scripts need a host check-in; Apple commands need a push and device response; Windows profiles need a management session; and Android devices need to fetch the updated policy. Check the relevant channel’s progress when a change takes longer than expected ([8.1](../08-troubleshooting/8.1-diagnostic-method.md)).

## The queue every discrete activity passes through

![Explanation](../_assets/icons/explanation.svg) Fleet organizes scripts and software installations in a per-host queue. Reviewing that queue shows which work is active and what must wait for it to finish.

**Five kinds of work go through it:** running a script, installing software, uninstalling software, installing an App Store app, and installing an in-house app.

**It is one queue per host, and it is ordered.** Work already activated comes first, then higher priority, then earliest requested. Nothing new activates while something is still activated, so **an activity blocks everything behind it on that host until it reaches a terminal state**. A script that takes twenty minutes is twenty minutes during which that host's other queued work does not start.

Ordinary work has priority zero; setup-experience scripts and software have priority one hundred so enrollment work can finish promptly. Fleet sets these priorities internally and exposes no control for assigning arbitrary values.

**One exception to strict serialisation.** Fleet activates up to five App Store installs at once when they are consecutive, the same type, and the same priority. This batches Apple MDM commands to cut latency and push traffic, and the same-priority condition exists because ordering cannot be guaranteed across priorities once commands reach Apple's queue. It is the only case where a host runs queued work concurrently.

Activation hands an item to its delivery channel. Confirm the channel’s returned result before treating the activity as completed.

## Cancelling, and what cancelling does not mean

![Troubleshooting](../_assets/icons/troubleshooting.svg) You can cancel upcoming work on a host. The limits are worth knowing before you rely on it.

**Lock and wipe cannot be cancelled once activated.** Fleet refuses, and says so: they cannot be cancelled if they are about to run, to prevent you losing access to the host. The moment to change your mind about a wipe is before it activates.

Cancellation reliably removes queued work. Once a channel has received an activated request, the device may still carry it out even after Fleet stops tracking it. Check the device outcome for work that was already in flight.

**Cancelling an App Store install releases a reserved licence seat.** Enqueuing one reserves a seat, so a queue of cancelled installs would otherwise hold licences nothing is using.

**Turning MDM off for a host clears only the MDM-dependent queue items**, the App Store and in-house app installs. Scripts and installer-based software survive, because they do not need MDM to run. So on re-enrollment the queue is not wiped clean, it is filtered.

**Deleting a host deletes its queued work**, along with the rest of its records.

## Targeting: who gets the change

![How-to](../_assets/icons/howto.svg) Choose the fleet scope first, then check the targeting options supported by the particular change. Label support varies across profiles, software, scripts, and OS-update settings.

**fleets provide the durable scope.** Each host has one fleet assignment, and most management configuration belongs to that scope. Named fleets require Premium ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Labels narrow within and across fleets for most mechanisms**, and are the tool for a population defined by a condition rather than by ownership: a hardware generation, an OS version, a rollout ring. The exception is built-in OS-update enforcement ([5.6](5.6-control-operating-system-updates.md#targeting-is-the-other-half-of-the-choice)): its generated payloads are fleet-scoped only and do not accept labels, so a rollout ring for OS updates has to be a custom update profile instead.

Dynamic labels follow query results as host state changes. Manual labels retain the devices an administrator chose, and host-vitals labels follow an attribute. Choose the label type that reflects how you want the rollout population to evolve.

## Rollout rings

![How-to](../_assets/icons/howto.svg) Expand a change through progressively broader groups so you can learn from real devices before applying it widely.

1. **A ring of one.** Your own device, or a spare. Enough to catch the change being outright wrong.
2. **A ring of the willing.** People who will tell you rather than file a ticket in three weeks.
3. **A representative ring.** Deliberately including the awkward cases: the oldest hardware, the locked-down build, the department with different software.
4. **The rest**, in stages if the estate is large enough that a bad change would be expensive to unwind.

For mechanisms that support label targeting, use labels to represent rollout rings. You can then expand membership while keeping the deployed artifact stable. Built-in OS-update settings are fleet-scoped, so use their supported scope or the custom-profile approach described in [5.6](5.6-control-operating-system-updates.md#targeting-is-the-other-half-of-the-choice).

**Wait for a full check-in cycle at each ring.** The failures worth catching are the ones that only appear on a device that was asleep, or offline, or in the middle of something else.

## Designing for the second time it runs

![Explanation](../_assets/icons/explanation.svg) Plan for retries and repeated requests. A change may be run again after a partial result, an operator action, or an automation reset.

**Desired state is naturally repeatable.** Reconciliation is the mechanism, so applying a profile twice is not a meaningful event.

**Discrete activities are not.** A script runs every time it is asked. If it appends a line to a file, it appends a line every time. If it creates a user, it must decide what to do when the user exists. Fleet will not deduplicate this for you, and the queue guarantees ordering rather than exactly-once execution.

Write scripts to check the current state before changing it and to reach the same end state when repeated. [5.3](5.3-run-and-manage-scripts.md) shows how this makes retries easier to manage.

**Design the way back before you need it.** For a profile, removal is the way back and it is usually clean. For a script, the way back is another script, which you should write before you run the first one. For a device action, there may be no way back at all.

## Ownership

![How-to](../_assets/icons/howto.svg) Give each profile, script, and deployment a purpose and owner so another administrator can maintain it.

Record, alongside the thing itself: **what it is for**, **who owns it**, **what it assumes about a host**, and **how you would undo it**. Managing these as code makes that a review artefact rather than folklore ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

Use the activity record to trace recorded actions and actors ([1.5](../01-foundations/1.5-audit-and-activity.md)). Keep the reason for the change with its configuration or approval record so the next operator can understand the intent as well.
