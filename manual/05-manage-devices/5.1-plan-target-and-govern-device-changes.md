# Plan, target, and govern device changes

Part IV was about reading. This part is about writing. A change written to a device can fail halfway, arrive in an order you did not choose, collide with something else you asked for, or turn out to be something you cannot take back.

This chapter is the vocabulary for the rest of Part V: three questions every later chapter assumes you can already answer.

1. **What kind of change is this?** Desired state, a discrete activity, or a device action.
2. **What carries it?** Fleet's agent, Apple's MDM channel, Windows management, or Android's policy API.
3. **How do you know it worked?** Each of those has its own status model, and they do not mean the same things by the same words.

## Three kinds of change

![Explanation](../_assets/icons/explanation.svg) The first question decides everything downstream, and the interface does not ask it.

**Desired state** is a description of how a device should be, which Fleet keeps true. A configuration profile is the clearest example. You do not run a profile; you declare that hosts in a scope have it, and Fleet reconciles reality against that declaration continuously. Remove a host from the scope and the profile is removed from the host. There is no single moment when it "ran".

**A discrete activity** is a unit of work that happens once, has an identity, and ends in a terminal state. Running a script and installing software are discrete activities. They queue, they execute, they succeed or fail, and the record persists whether or not you ask again.

**A device action** is an instruction to the device itself: lock it, wipe it, find it. These have the character of activities, but their consequences are not confined to Fleet's model of the world, and some are irreversible.

The distinction predicts the failure mode. Desired state drifts and gets reconciled, so its failure is "still not converged". A discrete activity fails once, visibly, with a reason. A device action can succeed completely and still be the wrong thing to have done.

One administrator gesture can be more than one of these. Installing an App Store app is a discrete activity in Fleet's queue *and* a command on Apple's MDM channel. Installing an app on Android is managed software that never enters Fleet's queue at all, because delivery happens by changing the device's policy, which is desired state. So "install this app" is a different kind of change depending on the platform, because Fleet inherits how each platform delivers.

## The four channels

![Reference](../_assets/icons/reference.svg) Under the three kinds sit four transports. Which one carries a change decides how quickly it arrives, what happens when the device is asleep, and where you look when it does not.

| Channel | Carries | Reaches |
|---|---|---|
| **Fleet's agent** | Scripts, installer-based software | Hosts running fleetd ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)) |
| **Apple MDM and declarative management** | Apple profiles, App Store and in-house app installs, Apple device actions | Enrolled Apple devices ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)) |
| **Windows management** | Windows profiles and commands, delivered inside a management session | Enrolled Windows devices |
| **Android policy** | Android configuration and application delivery, by changing the device's policy | Enrolled Android devices |

**A change is slow because of what its channel does when the device is not currently talking.** An agent-delivered script waits for the host's next check-in. An Apple command waits for a push and the device's response. A Windows profile waits for the next management session. An Android policy change waits for the device to fetch policy. These are different waits with different characteristic lengths, and diagnosing "why has this not happened yet" starts with knowing which one you are in ([8.1](../08-troubleshooting/8.1-diagnostic-method.md)).

## The queue every discrete activity passes through

![Explanation](../_assets/icons/explanation.svg) Scripts and software installs do not go straight to a device. They enter a **per-host queue**.

**Five kinds of work go through it:** running a script, installing software, uninstalling software, installing an App Store app, and installing an in-house app.

**It is one queue per host, and it is ordered.** Work already activated comes first, then higher priority, then earliest requested. Nothing new activates while something is still activated, so **an activity blocks everything behind it on that host until it reaches a terminal state**. A script that runs for twenty minutes holds that host's other queued work for twenty minutes.

**Priority is not yours to set.** Ordinary work is priority zero. Setup experience work, scripts and software alike, is priority one hundred, so it jumps the queue during enrollment. No administrator-facing control assigns arbitrary priority, so priority is not a rollout lever. The mechanism exists so that a device being set up finishes being set up.

**One exception to strict serialisation.** Fleet activates up to five App Store installs at once when they are consecutive, the same type, and the same priority. This batches Apple MDM commands to cut latency and push traffic, and the same-priority condition exists because ordering cannot be guaranteed across priorities once commands reach Apple's queue. It is the only case where a host runs queued work concurrently.

**Queued is not delivered.** An item that has activated has been handed to its channel. After that the channel owns it, and the queue's view is only as good as what the channel reports back.

## Cancelling, and what cancelling does not mean

![Troubleshooting](../_assets/icons/troubleshooting.svg) You can cancel upcoming work on a host. What cancelling does depends on how far the work has already got.

**Lock and wipe cannot be cancelled once activated.** Fleet refuses, and says so: they cannot be cancelled if they are about to run, to prevent you losing access to the host.

**Cancellation removes the request. It does not recall work already in flight.** For anything already handed to a channel, cancelling tells you Fleet has stopped tracking it, not that the device will not do it. Treat cancellation as reliable for queued work and as a request for activated work.

**Cancelling an App Store install releases a reserved licence seat.** Enqueuing one reserves a seat, so a queue of cancelled installs would otherwise hold licences nothing is using.

**Turning MDM off for a host clears only the MDM-dependent queue items**, the App Store and in-house app installs. Scripts and installer-based software survive, because they do not need MDM to run. So re-enrollment filters the queue instead of emptying it.

**Deleting a host deletes its queued work**, along with the rest of its records.

## Targeting: who gets the change

![How-to](../_assets/icons/howto.svg) Fleets are the boundary every mechanism in Part V respects. Label support on top of that varies by mechanism, so check the chapter that owns the one you are targeting before assuming a label will narrow it.

**Fleets are the durable boundary.** A host is in exactly one, and most management configuration is a property of the fleet. Named fleets are Fleet Premium ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Labels narrow within and across fleets for most mechanisms**, and are the tool for a population defined by a condition rather than by ownership: a hardware generation, an OS version, a rollout ring. The exception is built-in OS-update enforcement ([5.6](5.6-control-operating-system-updates.md#targeting-is-the-other-half-of-the-choice)): its generated payloads are fleet-scoped only and do not accept labels, so a rollout ring for OS updates has to be a custom update profile instead.

**The three label kinds behave differently under change**, which matters more when writing than when reading. A dynamic label recomputes membership from a query, so a host can leave the scope of a change by changing its own state. A manual label holds the hosts you named. A host vitals label is built from an attribute. Scoping a change to a dynamic label means the scope is a moving target.

## Rollout rings

![How-to](../_assets/icons/howto.svg) Stage every change through progressively wider populations.

1. **A ring of one.** Your own device, or a spare. Enough to catch the change being outright wrong.
2. **A ring of the willing.** People who will tell you rather than file a ticket in three weeks.
3. **A representative ring.** Deliberately including the awkward cases: the oldest hardware, the locked-down build, the department with different software.
4. **The rest**, in stages if the estate is large enough that a bad change would be expensive to unwind.

**Make the rings labels, and make the change target the label.** Promoting a rollout is then a change to label membership rather than a change to the thing being rolled out, which keeps the artefact stable while its audience grows.

**Wait for a full check-in cycle at each ring.** Some failures only appear on a device that was asleep, or offline, or in the middle of something else.

## Designing for the second time it runs

![Explanation](../_assets/icons/explanation.svg) Anything you can ask for once, you can ask for again.

**Desired state is naturally repeatable.** Reconciliation is the mechanism, so applying a profile twice is not a meaningful event.

**Discrete activities are not.** A script runs every time it is asked. If it appends a line to a file, it appends a line every time. If it creates a user, it must decide what to do when the user exists. Fleet will not deduplicate this for you, and the queue guarantees ordering rather than exactly-once execution.

**So write for repetition.** Check before acting, make the end state the goal rather than the action, and prefer work that can be repeated with no additional effect. [5.3](5.3-run-and-manage-scripts.md) makes this concrete.

**Design the way back before you need it.** For a profile, removal is the way back and it is usually clean. For a script, the way back is another script, which you should write before you run the first one. For a device action, there may be no way back at all.

## Ownership

![How-to](../_assets/icons/howto.svg) Every artefact in this part outlives the person who made it.

Record, alongside the thing itself: **what it is for**, **who owns it**, **what it assumes about a host**, and **how you would undo it**. Managing these as code makes that a review artefact rather than folklore ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

The activity record shows what was done and by whom ([1.5](../01-foundations/1.5-audit-and-activity.md)). It does not show why.
