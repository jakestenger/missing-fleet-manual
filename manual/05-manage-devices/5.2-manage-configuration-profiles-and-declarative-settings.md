# Manage configuration profiles and declarative settings

Profiles are the clearest case of the desired state model in [5.1](5.1-plan-target-and-govern-device-changes.md). You do not run a profile. You declare that hosts in a scope have it, and Fleet works continuously to make that true.

That single fact explains almost everything in this chapter: why there is no "it ran" moment, why removing a host from a scope removes the profile from the device, why a status can go backwards, and why the most useful status word in the product means something narrower than it sounds.

## Choosing where a setting lives

![How-to](../_assets/icons/howto.svg) The same setting can often be delivered three ways, and the right choice is usually the highest one on this list that can express what you need.

**Fleet's own settings first.** Where Fleet has a built-in control for something, use it. Disk encryption is the clearest example ([5.8](5.8-enforce-disk-encryption-and-manage-recovery-credentials.md)), as are operating system updates ([5.6](5.6-control-operating-system-updates.md)). These carry status models Fleet understands, and they are visible as the thing they are rather than as an opaque payload.

**Then a declaration, on Apple platforms.** Apple's declarative device management lets the device hold the desired state and report its own status, rather than waiting to be told. Fleet supports Apple declarations alongside classic profiles.

**Then a classic profile.** The general-purpose mechanism, and the only one for many settings.

**Why the order matters:** each step down loses Fleet's understanding of what you did. A custom profile that enforces something Fleet has a built-in control for is a setting Fleet cannot report on, cannot verify, and may conflict with. Fleet actively guards one of these cases: it refuses to apply built-in OS update settings when a custom declaration already covers them, and tells you to remove the custom one first.

## Authoring, by platform

![Reference](../_assets/icons/reference.svg) The three platforms take different formats, and the differences are not cosmetic.

**Apple** takes property list profiles, and declarations as JSON. A profile carries an identifier that must be unique on the device; two profiles claiming the same identifier are one profile as far as the device is concerned, and the second replaces the first.

**Windows** takes configuration in the syntax its management protocol uses, addressing settings by path. There is no equivalent of the Apple profile identifier, so replacement is not implicit.

**Android** works through the device's policy rather than through documents you upload. Configuration is a property of the policy Fleet maintains for the device, which is why Android behaves like desired state even more completely than the other two.

**Uploading is not validating.** Fleet checks that what you supply is well formed and that it does not collide with something it manages itself. It cannot tell you that a setting is correct for your fleet, that a key is spelled the way the vendor expects, or that the payload will do what you intended on a version of the OS you have not tested. The first ring in your rollout is where that gets caught ([5.1](5.1-plan-target-and-govern-device-changes.md)).

## Scoping, and what happens at the edges

![Explanation](../_assets/icons/explanation.svg) A profile is attached to a fleet, and optionally narrowed by labels.

**The scope is a membership test, evaluated continuously.** This is the part worth internalising, because it means **removal is automatic**. A host that leaves the scope has the profile removed from it, without anyone asking for a removal. That is the desired state model working correctly, and it surprises people the first time a host moves between fleets and quietly loses configuration.

**Moving a host between fleets is therefore a configuration change**, not just a reporting change. The host loses what the old fleet declared and gains what the new one declares, and both halves happen as MDM work on the device.

**Label scoping inherits the label's behaviour.** Scope to a dynamic label and membership recomputes as hosts change, so a host can install or remove a profile because its own state changed and nobody touched Fleet ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Nothing is instant.** Fleet reconciles on a schedule, not on the keystroke. A change to scope or content becomes work to be done, and that work then waits for the device's channel.

## Variables and secrets

![How-to](../_assets/icons/howto.svg) A profile is a static document, which is a problem when the value differs per host or must not be stored in plain text. Fleet has two distinct answers, and confusing them is a security mistake.

**Fleet variables are per-host substitutions**, written `$FLEET_VAR_NAME` or `${FLEET_VAR_NAME}`, resolved when the profile is sent to a particular device. They fall into two families.

*Host and identity variables* fill in something Fleet already knows about the host or its user: the hardware serial, the host UUID, the platform, and a set of values sourced from your identity provider including the username, the local part of the username, the full name, the department and group membership. These are how one profile serves an estate.

*Certificate authority variables* are the more consequential family. They carry challenges, proxy URLs and renewal identifiers for certificate issuance, including NDES, DigiCert, Smallstep and custom certificate authorities. A profile using them is not merely templated, it is participating in certificate enrollment, and it should be treated as infrastructure.

**Secrets are different.** A secret variable is a named value you store in Fleet and reference from a profile, so the profile's content in Fleet does not contain the sensitive value. Names are uppercase letters, digits and underscores.

**The distinction that matters:** a Fleet variable is a substitution Fleet performs; a secret is a value Fleet deliberately keeps out of the document. Putting a credential in a Fleet variable rather than a secret defeats the point, because the profile then contains it.

**One variable is designed never to be stored at all.** The Platform SSO device registration token resolves to a per-host signed token at the moment the device fetches the command, specifically so that it is not stored and does not appear when commands are listed. That design is worth knowing about as the pattern to expect from anything genuinely sensitive.

**A profile that uses secrets has its own change signal.** Fleet's fingerprint for such a profile includes when its secrets were last updated, so rotating a secret is a change to the profile as far as reconciliation is concerned, and the device gets the new value without you editing the document.

## Reading status honestly

![Reference](../_assets/icons/reference.svg) Fleet reports a per-host, per-profile status. There are four named states and a fifth unnamed one, and the differences are not decorative.

**The same five states are used for all three platforms.** Apple, Windows and Android profile records all draw their status from one shared set, so the vocabulary below is worth learning once and applies everywhere. What differs between platforms is how Fleet reaches a given state, not what the state is called.

| Status | What it means |
|---|---|
| **Pending** | Fleet is processing this host and the command may be enqueued |
| **Verifying** | The command was applied successfully, and Fleet has **not** independently confirmed it |
| **Verified** | Applied, and Fleet has independently confirmed it. Terminal |
| **Failed** | It will not be retried further. Terminal |
| *No status yet* | The profile needs to be applied or removed and reconciliation has not reached it |

**"Verifying" is the state people over-read.** It means the device accepted the command. It does not mean Fleet has checked the setting is actually in force. Only **Verified** means that, and the gap between them is where a profile that was accepted and then overridden, reverted or ignored will sit.

**The unnamed state is counted as Pending.** A profile with no status yet is reported as pending in summaries and filters, so the pending count is really "pending plus not yet looked at". This matters when you are watching a rollout and expecting the pending count to fall monotonically.

**Status can move backwards, and that is not a bug.** Verifying can go back to pending, or to no status at all, when circumstances change. A number that goes the wrong way during a rollout is usually reconciliation reacting to something, not a failure.

**Failed is terminal, but not immediate.** Fleet retries a failed Apple profile install up to three times and a Windows one once before marking it permanently failed. So a profile reading failed has already been through its retries; resending it is a deliberate act, not a first attempt.

**Each profile also carries an operation type**, install or remove, and it is the piece people forget when reading status. A profile sitting in pending with a **remove** operation is not failing to install. It is waiting to be taken off.

## Changing, resending and removing

![How-to](../_assets/icons/howto.svg) Four operations, with different consequences.

**Editing the content** makes it a new desired state and reconciliation delivers it. You do not need to remove the old version first.

**Resending is narrower than it looks.** You can resend a profile that is **failed** or **verified**. You cannot resend one that is pending or verifying, and Fleet refuses with an explicit message rather than quietly doing nothing. This is a sensible restriction that catches people out: the profile you most want to poke is usually the one stuck in verifying, and that is precisely the one you cannot resend. Wait for it to reach a terminal state.

**Removing the profile from the fleet removes it from the devices.** This is not the same as deleting a file; it enqueues removal work per host, with its own status.

**Narrowing the scope has the same effect for the hosts that fall outside it**, which is the more common accidental removal. Edit a label used by a profile and you have changed configuration on every host whose membership changed.

**Resending is per host and is recorded.** It appears in the activity record with the profile name and the host, so it is auditable, and it is worth using deliberately rather than as a reflex ([1.5](../01-foundations/1.5-audit-and-activity.md)).

## When a profile is not on a device

![Troubleshooting](../_assets/icons/troubleshooting.svg) The order to check things, before escalating to Part VIII.

1. **Is the host actually in scope?** Fleet membership and every label the profile uses. This is the most common answer.
2. **Is the host MDM-enrolled**, and on the platform the profile targets ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md))?
3. **What is the status, and what is the operation type?** A remove in progress looks like a failure to install if you do not read the second column.
4. **Has reconciliation run, and has the device checked in since?** Desired state is not instant, and the wait is the channel's rather than Fleet's ([5.1](5.1-plan-target-and-govern-device-changes.md)).
5. **If the status is verifying and staying there**, the device accepted it and Fleet cannot confirm it. Ask what on the device might be overriding it, including another profile claiming the same identifier.
6. **If failed**, it has exhausted its retries. The reason is the useful part, and resending without a hypothesis just consumes another attempt.

Beyond that, profile delivery problems are MDM channel problems ([8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md), [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md)).
