# Enforce disk encryption and manage recovery credentials

![Explanation](../_assets/icons/explanation-light.svg) Disk encryption protects data when a device is lost or removed from service. Recovery credentials help you restore access when a user cannot unlock it. Fleet brings enforcement, reported encryption status, and credential escrow into a shared administrative view, helping IT and security staff manage both protection and recovery.

The controls are scoped by fleet, with shared licensing, permissions, storage, and audit logging across three platform mechanisms. macOS uses FileVault, Windows uses BitLocker, and Linux uses LUKS. Fleet can enable encryption on supported Macs and Windows hosts; Linux disks must already be encrypted before Fleet can escrow recovery material.

Fleet's enforcement, escrow, status interpretation, and Recovery Lock controls described here require Premium. Revealing a key Fleet already holds is Premium in practice too, because escrow is, though the retrieval itself carries no licence check.

This chapter follows those platform flows and explains which credentials Fleet holds, what they unlock, who can reveal them, and what happens during re-enrollment or certificate changes. It also separates reported protection from a tested recovery procedure, so you can assess both with confidence.

## Separate desired enforcement, observed encryption, escrow, and recovery proof

![Explanation](../_assets/icons/explanation-light.svg) A useful encryption review answers four questions. Fleet provides signals for the first three; the fourth requires a recovery test:

1. **Is enforcement desired?** You have told Fleet you want this fleet encrypted.
2. **Is the disk observed encrypted?** The device reports that it is.
3. **Does Fleet hold a recovery credential?** Separate from the above, and not implied by it.
4. **Would the credential unlock the disk?** Fleet does not test recovery with the credential, so its status cannot establish this.

An encrypted disk may have no usable credential in Fleet, and Fleet can escrow a credential for a disk encrypted before enrollment. Although enforcement and escrow share a control, check the reported encryption state and the availability of recovery material separately.

> Read the status as a platform-specific summary. macOS has six values, Windows five, and Linux three. The summary combines encryption and escrow signals, does not identify an archived credential when one is returned, and does not establish that recovery will work.

## Check licensing, prerequisites, compatibility, and competing configuration

![Reference](../_assets/icons/reference-light.svg)

| | macOS | Windows | Linux |
|---|---|---|---|
| **Can Fleet turn encryption on?** | Yes | Yes | **No** |
| **What the setting does there** | Enforces and escrows | Enforces and escrows | **Escrow only** |
| **Already-encrypted disk** | Existing credential invalidated | Existing credential invalidated **and removed from the device** | Left alone |
| **Who starts escrow** | Fleet | Fleet | **The end user, from their own device page** |

**On Linux the switch is escrow-only.** Fleet cannot enable LUKS, and refuses escrow until the disk is already encrypted. If your Linux estate is not encrypted, this feature will not encrypt it.

Check the prerequisites before enabling the control. Every platform needs fleetd. macOS also needs Fleet's Apple MDM; Windows needs Fleet's Windows MDM, a non-server edition, and a working TPM. Linux needs a supported distribution, LUKS2, local encryption utilities, and a sufficiently recent fleetd. Recovery Lock additionally requires Apple silicon and MDM enrollment. The complete platform matrices are in [3.2](../03-connect-devices/3.2-enroll-macos-devices.md), [3.3](../03-connect-devices/3.3-enroll-windows-devices.md), and [3.4](../03-connect-devices/3.4-enroll-linux-devices.md).

Fleet rejects a custom FileVault profile while built-in enforcement is enabled unless you turn on the Premium deployment-wide override. Review that override across platforms before using it: it also disables the equivalent BitLocker conflict check and applies to every fleet.

On Windows, encryption and the startup PIN are locked together as one decision rather than two.

## Enforce FileVault and escrow a personal recovery key

![How-to](../_assets/icons/howto-light.svg) Fleet delivers the FileVault configuration, macOS asks the user to enable it, and the resulting personal recovery key is escrowed to Fleet. Include the user prompt in your rollout communications so people know what is expected.

The observable sequence:

1. Enforcement is turned on for the fleet and the profile reaches the Mac.
2. **The user is prompted**, and must act. FileVault enablement is not silent on macOS.
3. macOS generates a **personal recovery key**.
4. That key is escrowed to Fleet.
5. Fleet reports the host as encrypted with a credential held.

For an already-encrypted Mac, Fleet arranges a new recovery credential it can escrow. Review any keys retained before enrollment as part of that transition; you should not assume they remain valid.

## Enforce BitLocker and escrow a numerical-password protector

![How-to](../_assets/icons/howto-light.svg) On Windows, fleetd performs the BitLocker work after the management prerequisites are satisfied. The agent enables protection and sends the recovery material to Fleet.

Fleet escrows a BitLocker **numerical password protector**, the recovery credential used to regain access to the encrypted volume. Using that term helps distinguish it from other BitLocker protectors when reviewing the device's configuration.

This flow runs silently from Fleet's side. Windows may display its own prompts or messages, so provide any organizational instructions through your normal employee communications.

On an already-encrypted Windows disk, Fleet invalidates and removes the existing recovery credential from the device. Include the owners of any previous recovery-key store in your rollout plan so they know which credentials remain usable.

Guide the user to **Create PIN** on My Device. The dialog explains how to open Windows' Manage BitLocker tool, choose Change how the drive is unlocked at startup, and enter a PIN there. It then asks the user to close the instructions and refetch My Device so Fleet receives the new state. The PIN is entered only in Windows and never sent to Fleet.

The PIN requirement contributes to BitLocker's reported status. A host can show Verified or Verifying only when the required PIN is present. A host that otherwise qualifies as Verified shows Action required without the PIN, but remains usable. The status updates after the next host detail refresh; a My Device refetch brings that check forward.

**Fleet knows whether the PIN is set by asking the host.** Its osquery query reads the `bitlocker_key_protectors` table for protector types 4 or 6, the TPM-plus-PIN protectors, on the `C:` volume, and records the result as a `tpm_pin_set` boolean. That boolean is what the status logic reads, and it is why the Create PIN flow ends with a refetch rather than an immediate change in the console.

## Escrow recovery material from an already-encrypted LUKS host

<!-- SCREENSHOT-REUSE: SS-3.4-01. Reuse the Linux My Device escrow entry and empty passphrase dialog here to guide the required user step. -->

![How-to](../_assets/icons/howto-light.svg) Linux escrow adds a recovery credential to Fleet for an existing LUKS-encrypted disk. Plan the user step as part of enrollment so recovery material is available when support staff need it.

**Fleet cannot encrypt a Linux disk.** The setting only arranges escrow, and escrow is refused until LUKS is already in place.

The end user starts escrow from My Device and supplies their passphrase. It is a one-shot operation: Fleet does not retry it in a later background cycle, and administrators cannot initiate it remotely.

> Include My Device escrow instructions in your Linux onboarding process and follow up with users whose hosts have no credential. Waiting for an administrator action or an automatic retry will not complete that step.

TPM-backed Ubuntu is a distinct case. The observable difference is that escrow happens without the user being prompted for a passphrase, and what Fleet ends up holding is its own recovery credential rather than the one the platform uses day to day.

## Read compound status without overclaiming recovery

![Reference](../_assets/icons/reference-light.svg) Use encryption status to identify hosts that need attention, then examine the underlying signal before choosing a repair.

Fleet's credential verification establishes, at most, that the server can decrypt a stored value. It does not attempt to unlock the disk with that value.

> Windows and Linux mark a credential usable when it is escrowed and do not run a scheduled decryption check afterward. A successful reveal confirms that Fleet can still decrypt the stored value, which provides more evidence than the unchanged indicator.

On Windows one displayed status covers two unrelated causes, and the explanatory tooltip names only one of them. If you see that status and the stated cause does not fit the host, consider the other.

Validate your recovery procedure on a device set aside for testing. Retrieve its credential through the approved process and use it to recover access. Record the result separately from Fleet's status so your team has evidence that the procedure and credential worked together.

## Reveal, validate, and repair disk-recovery credentials safely

![How-to](../_assets/icons/howto-light.svg)

**The operator path is the host details page, the Actions menu, then Show disk encryption key.** The option is present only when Fleet holds a credential for the host, current or archived, and it is disabled while the encryption profile is still pending or has failed. Selecting it reads the host's `encryption_key` endpoint, which decrypts the stored value and returns it to a modal on screen.

**Who can reveal a credential:** anyone who can read the host, which is a wider group than those who can change anything. Retrieval is per host. **Fleet records a successful read as an activity**, so revealing a credential leaves a trace with your name on it, by design. That record is written only after the decrypt succeeds. A retrieval that cannot decrypt returns an error and writes no read activity, so a failed attempt leaves nothing in the activity feed.

When the current credential is missing or cannot be decrypted, Fleet tries the newest archived entry. The interface returns that value without marking it as archived. If a retrieved credential does not unlock the disk, investigate whether this fallback supplied an older value.

The archive is a one-deep fallback, not a history you can page through. A different, non-empty key is copied into it when the host's stored key changes, and **only the newest archived entry is ever retrievable**: earlier keys are not reachable through Fleet.

**When nothing Fleet holds can be decrypted, the reveal returns one generic message**: that the decryption certificate and key are invalid because MDM has been turned off. **That text is the same on every platform**, Windows and Linux included, where Apple MDM plays no part. Read it as "Fleet could not decrypt what it holds", then diagnose the platform's own decrypt dependency rather than the Apple wording ([8.6](../08-troubleshooting/8.6-server-state.md#host_disk_encryption_keys) reads the escrow record, including the column that says why a key is not decryptable).

Revealing a FileVault, BitLocker, or LUKS recovery credential leaves its value unchanged. Fleet decrypts it, records the successful read, and returns it. Recovery Lock and the macOS managed local administrator password have different reveal behavior: their reads schedule a rotation.

**Each platform decrypts with different server-side material.** Linux uses the Fleet server private key directly, Windows the current Windows enrolment certificate and key, and macOS the Apple MDM certificate authority assets. The macOS path keeps rolled-over authority certificates, so a key escrowed under a previous certificate authority still decrypts; the Windows path uses only the current enrolment identity, which is why a routine enrolment-certificate renewal can quietly break BitLocker retrieval. The rollover asymmetry and the safe renewal order are covered under [certificate and key material](#certificate-and-key-material) below, and the material itself is inventoried in [7.6](../07-operate-fleet/7.6-maintain-credentials-certificates-and-access.md#inventory-operational-trust-material).

**Revealing a key is Premium in practice, not by a check on the read.** The escrow that fills the store is Premium, so a Free deployment has no ordinary way to put a key there to read back. The retrieval itself applies no separate licence test, so a deployment that already holds escrowed data, for instance one downgraded to Free, can still reach it.

**Handle the value like the credential it is.** Move it through whatever channel your organisation uses for secrets, not through a ticket or a chat message. Rotate or re-escrow after a disclosure that went somewhere it should not have.

Choose the repair procedure for the platform and the failure. Fleet has no universal credential-rotation action, and the available recovery paths differ.

### The one credential Fleet repairs on its own

A scheduled job re-tries decrypting every macOS key it has not already verified, using the current Apple certificate authority material ([above](#read-compound-status-without-overclaiming-recovery) is what that verification does and does not prove). When a key comes back undecryptable and the host's own agent has told Fleet it supports Escrow Buddy, Fleet sets a rotation instruction in that host's configuration. **The agent does not act silently:** at the person's next login, it prompts them for their account password, generates a new personal recovery key, and escrows the replacement. If the agent has not declared the Escrow Buddy capability, none of that happens: Fleet sends no instruction, and nothing in the interface tells you a repair was skipped.

Fleet requests that macOS rotation only when an existing credential is marked undecryptable. There is no action to invoke it for a key Fleet can still read, including through [credential reveal](#reveal-validate-and-repair-disk-recovery-credentials-safely).

**Windows and Linux have no equivalent.** BitLocker enforcement reacts to a different signal, whether the host itself reports encryption disabled, not whether Fleet can decrypt what it is holding, so an undecryptable Windows credential stays undecryptable until whatever broke the enrolment certificate is fixed ([above](#certificate-and-key-material)). Linux repair is the one this chapter already covers: [only the end user can start it](#escrow-recovery-material-from-an-already-encrypted-luks-host), and Fleet does not retry that either.

## Survive re-enrollment, scope changes, disablement, certificate rollover, and archives

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Include escrow in the change plan for enrollment, fleet moves, and certificate maintenance. These operations can affect recovery even when the disk remains encrypted.

### Turning enforcement off

Disabling disk-encryption enforcement stops new escrow. It does not decrypt disks or delete credentials already held, and those credentials remain available for retrieval.

Disabling Recovery Lock follows a separate removal lifecycle, described below: Fleet clears that lock and its credential after the device acknowledges the command.

### Moving a host between fleets

During a fleet move, Fleet preserves the live credential when its destination-enforcement check succeeds and deletes it when that check fails. The check's implementation creates an important cross-platform limitation:

The part to know is *how Fleet decides*. It looks for exactly one thing, Fleet's own FileVault configuration profile on the destination fleet, and uses its presence as the answer for **all three platforms**. In a deployment with Windows MDM and no Apple MDM, that profile does not exist on any fleet, so the destination always looks like one that does not enforce encryption, and **every fleet move deletes escrowed BitLocker credentials.** If you run Windows without Apple MDM, treat a fleet move as a de-escrow and confirm the behaviour on one host before doing it in bulk.

### Re-enrollment

macOS and Windows re-escrow automatically after re-enrollment. Linux needs the user to start escrow again from My Device. Include that step and its follow-up in any Linux re-enrollment campaign.

### Certificate and key material

Each platform depends on different server-side material, and **the three are independent**:

| Platform | What must survive for held credentials to stay readable |
|---|---|
| **macOS** | The Apple MDM CA private key, **and** the Fleet server private key that protects it |
| **Windows** | **The Windows enrolment identity certificate and key.** The server private key is not involved |
| **Linux** | The Fleet server private key, directly |

Two consequences require a pre-change recovery plan.

> **Renewing or replacing the Windows enrolment certificate can make every escrowed BitLocker credential unreadable through Fleet**, even when the key pair is reused. Fleet decrypts using the current certificate identity, and unlike macOS it keeps no fallback to a historical certificate. A routine, scheduled renewal is enough.
>
> Windows may continue to show those credentials as available because it marks them usable on arrival and does not recheck them later. Verify retrieval after a certificate change; the existing status can remain positive while decryption fails.
>
> Removing Apple MDM deactivates its certificate authority material along with the push certificate, immediately stopping FileVault retrieval. Reconfiguring it creates a new certificate authority key, so credentials escrowed under the previous one remain outside Fleet's active decryption path. Fleet provides no warning for either transition.
>
> **So never remove Apple MDM as part of renewing the push certificate.** Upload the renewed certificate over the existing configuration. If it has already been removed, **stop before reconfiguring**: preserve the database, the backups and the server private key, and treat it as an incident rather than a next step.

Preserve the current certificate and key material, database, and suitable backups before making these changes. Restoring the original material or a compatible backup may be the only recovery path if retrieval breaks. Test that path before a user needs it.

## Manage Recovery Lock as a separate Apple credential

![Explanation](../_assets/icons/explanation-light.svg) Recovery Lock protects access to a Mac's recovery environment. Manage it separately from the FileVault recovery key, with its own control, status, and rotation process.

The distinction matters during support: the FileVault key unlocks an encrypted volume, while Recovery Lock controls access to the recovery environment itself.

> **Viewing it schedules its rotation.** Revealing the password marks it as viewed and sets a rotation due about an hour later. The hour is a floor on when Fleet starts, not a guarantee of when the old value stops working: the replacement is delivered as a command like any other, so completion depends on the device.
>
> **Each reveal resets that clock**, so repeated viewing pushes rotation further out rather than triggering it sooner.

Account for the scheduled rotation when deciding who should retrieve this credential and when:

**Anyone who can read the host can reveal it**, which is a wider group than the administrators and maintainers who can explicitly rotate it. So a read by someone with no authority to change the credential nonetheless causes it to change.

Use status for routine checks. Reveal the Recovery Lock password when you need its value and are prepared for the resulting rotation.

**Disabling Recovery Lock removes the credential, but not at the moment you disable it.** Fleet schedules a clear, sends it to the Mac as a command, and deletes what it holds once the Mac acknowledges. Until then the password remains readable. So disablement is a request with a device-dependent completion, like most things in [5.7](5.7-control-devices-and-send-mdm-commands.md). If the Mac never checks in, Fleet still holds a credential for a lock that is supposed to be gone.

Disk-encryption enforcement preserves stored credentials when disabled. Recovery Lock removes its stored credential after the device acknowledges the clear, so account for the specific control when planning a change.
