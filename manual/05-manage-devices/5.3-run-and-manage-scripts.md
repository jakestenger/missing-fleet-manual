# Run and manage scripts

Scripts give administrators a flexible way to repair a device, gather a targeted diagnostic, or automate a task beyond Fleet’s built-in controls. You can run the same reviewed script on one host or a larger population and inspect the result from Fleet. Because scripts run with full administrative privilege, define their intended effect and test their assumptions before broad use.

A script is a discrete activity: Fleet queues it per host, runs it once, and records its result ([5.1](5.1-plan-target-and-govern-device-changes.md)). Design it to handle repeated requests and partial execution, since Fleet does not continuously reconcile the state it leaves behind.

This chapter covers the execution environment, practical limits, reusable script design, and the results you will use to verify a run.

<a id="what-a-script-runs-as-and-when-it-will-not-run-at-all"></a>

## Script privileges and execution prerequisites

![Explanation](../_assets/icons/explanation.svg) Confirm the service account and script-support settings before writing or distributing a script. They determine its access to the device and whether it can run.

**Scripts run with full administrative privilege.** Fleet's agent is installed as a system service: a launch daemon on macOS, a system service unit on Linux, and a service on Windows. Scripts run as that service, which means root on macOS and Linux. There is no lower-privilege mode and no per-script privilege setting.

Scripts need no interactive elevation. They run in the agent’s service context, so user-specific paths and permissions can differ from a command tested in someone’s terminal. Check those assumptions explicitly when working with user files.

Script execution must be enabled both globally and in the host’s effective agent configuration:

- **Globally**, in organization settings. Fleet refuses the run and says scripts are disabled in organization settings.
- **Per host**, through the agent’s script-support setting. Packaging supplies an initial value, with platform-specific ways to enable it later described in [3.2](../03-connect-devices/3.2-enroll-macos-devices.md), [3.3](../03-connect-devices/3.3-enroll-windows-devices.md), and [3.4](../03-connect-devices/3.4-enroll-linux-devices.md). A host with scripts disabled returns **exit code -2** and “Scripts are disabled.”

Hosts can have different effective script settings even within the same fleet. Agent-delivered software installation also uses scripts, so disabling them prevents that installation path too ([5.4](5.4-manage-software-and-applications.md)). Check the host configuration when only part of a population rejects the work.

If a script fails instantly on a subset of hosts with no meaningful output, check this before anything else.

## The limits, and what each one implies

![Reference](../_assets/icons/reference.svg) Use these limits to choose how much work the script should perform and how it should report the result.

| Limit | Value | What it implies |
|---|---|---|
| Saved script length | 500,000 characters | Effectively no constraint on a reasonable script |
| Ad-hoc script length | 10,000 characters | Roughly 250 lines. Meant for one-off work |
| Runtime on the host | **5 minutes**, then terminated | The single most important number here |
| Server wait for a synchronous run | 6 minutes | The host limit plus a minute for delivery |
| Output kept | 10,000 characters | And it keeps the **end**, not the beginning |
| Configurable execution timeout | Up to 18,000 seconds | Raises the host limit, through agent options |

**Five minutes is the number to design around.** A script exceeding it is terminated, not paused, and a terminated script has done whatever it did up to that point. There is no rollback and no completion. If your work might take longer, either it belongs in a package with an installer that owns its own lifetime ([5.4](5.4-manage-software-and-applications.md)), or the script should start something and exit rather than wait for it.

**The timeout is raisable, and raising it is a real decision.** Agent options accept a script execution timeout up to eighteen thousand seconds, which is five hours. That applies to every script for hosts under those options, not to the one you are worried about. A five-hour ceiling means a runaway script blocks that host's queue for five hours ([5.1](5.1-plan-target-and-govern-device-changes.md)).

Fleet retains the last ten thousand characters of output and discards earlier text beyond that limit. Put a concise result and useful diagnostics at the end so they survive truncation. Keep routine progress output brief.

## Platforms and interpreters

![Reference](../_assets/icons/reference.svg) Fleet accepts three file types and is specific about what may run them.

**`.sh`, `.ps1` and `.py`.** Anything else is refused at upload.

**Shell scripts must declare a supported interpreter**: `/bin/sh`, `/bin/bash` or `/bin/zsh`, with or without a `/usr` prefix. A shell script with a different shebang is refused, and the error names the supported set.

**Python is supported** through `/usr/bin/env python3` or an absolute path to `python` or `python3`. That is a real dependency on the host having Python, which Fleet does not install for you.

**PowerShell is the Windows path**, by file extension rather than by shebang.

**The interpreter is a targeting decision as much as a technical one.** A `.ps1` script has no meaning on macOS, and Fleet's platform scoping is what keeps you from finding that out at scale.

## Writing a script that can run twice

![How-to](../_assets/icons/howto.svg) The habit [5.1](5.1-plan-target-and-govern-device-changes.md) named, made concrete. Scripts get re-run: by a retry, by a policy automation firing again, by a colleague who did not know you had already done it.

Check whether the desired state already exists and exit successfully when no change is needed. For example, add a configuration line only when it is absent so repeated runs do not create duplicates.

**Make the end state the goal, not the action.** "Ensure this setting is X" survives repetition. "Toggle this setting" does not.

**Exit codes are your interface.** Zero means success. Anything else means failure, and Fleet records it. Use a non-zero exit deliberately for "I could not do this", and do not exit non-zero for "there was nothing to do", which is a success.

Print a short result describing the state found and any change made. This gives a later reviewer useful context beside the exit code.

**Fail early and loudly on assumptions.** If the script needs a directory, a binary or a privilege level, check for it at the top and exit non-zero with a clear message rather than failing obscurely halfway.

## Secrets and per-host values

![How-to](../_assets/icons/howto.svg) The same mechanisms as profiles, with the same distinctions and higher stakes ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md)).

**Secret variables** keep a credential out of the script's stored content. The script references the name; Fleet supplies the value when the script is sent.

**Built-in variables fill in what Fleet already knows about the host.** Written `$FLEET_VAR_NAME` or `${FLEET_VAR_NAME}`, they are resolved for one host at the moment that host's agent fetches the script, which means one stored script can carry per-host values without a templating step of your own. They work in a saved script, in a script you run once without saving, in a setup experience script, and in a software title's install, post-install and uninstall scripts. **They require Fleet Premium** (Fleet 4.91 and later; before 4.91 a script referencing one received the literal text).

Scripts support the eight variables listed below. Certificate-authority variables are reserved for profile-based certificate enrollment and are unavailable in scripts.

| Variable | Resolves to |
|---|---|
| `$FLEET_VAR_HOST_UUID` | The host's UUID |
| `$FLEET_VAR_HOST_HARDWARE_SERIAL` | The host's hardware serial |
| `$FLEET_VAR_HOST_PLATFORM` | `macos` on a Mac, and otherwise the platform string Fleet records, so `windows` on Windows and the distribution name on Linux |
| `$FLEET_VAR_HOST_END_USER_IDP_USERNAME` | The end user's identity-provider username |
| `$FLEET_VAR_HOST_END_USER_IDP_USERNAME_LOCAL_PART` | The part of that username before the `@` |
| `$FLEET_VAR_HOST_END_USER_IDP_FULL_NAME` | The end user's full name |
| `$FLEET_VAR_HOST_END_USER_IDP_DEPARTMENT` | The end user's department |
| `$FLEET_VAR_HOST_END_USER_IDP_GROUPS` | The end user's groups, joined with commas and no spaces |

**`$FLEET_VAR_HOST_PLATFORM` is not spelled the same way here as in a host name template.** A name template resolves it to `macOS`, `iOS` or `iPadOS` ([5.2](5.2-manage-configuration-profiles-and-declarative-settings.md#naming-hosts-from-a-template)); a script gets `macos`, lower case, and gets the raw platform string for everything else. Compare it case-insensitively, or match on something else.

**Anything outside the eight is refused when you save.** Fleet validates the content on upload, on an ad-hoc run, on a GitOps run, and on a software title's scripts, and the error names both the offending variable and, for a title, which of its three scripts holds it. Script content that predates the validation is left alone rather than rejected, so an old script referencing an unsupported name still runs and still receives the literal text.

**A variable that cannot be resolved for a host stops that host's execution before the script runs.** The IdP variables are the ones this happens to: a host with no identity-provider user, or one whose user has no department, no full name or no groups, has nothing to substitute. Fleet records the run as finished with exit code -5 and puts the reason in the output, one line per failing variable, so a script referencing three variables that all fail tells you about all three in one pass rather than one per attempt. The same failure on a software title's scripts fails the install with "Fleet couldn't resolve variables in this software's scripts" and the same per-variable reasons.

**Resolution order is deliberate, and it is the reason an IdP value cannot smuggle a secret out.** Fleet expands secrets and custom host vitals first, and built-in variables last. A department or full name that happens to contain the text `$FLEET_SECRET_SOMETHING` therefore lands in the script as that literal text, because the secrets pass has already run by the time the value arrives. Values are still substituted as plain text with no shell escaping, so quote every expansion: [5.4](5.4-manage-software-and-applications.md#secrets-and-output) makes the same point about lifecycle scripts, and it applies identically here.

Protect secret values in output as well as stored script content. A script can print a substituted credential, and Fleet retains that output for people authorized to read the host’s activity. Avoid echoing secret-bearing command lines or allowing tools to include credentials in their output.

Keep shell tracing off around secrets and control output from tools that might print their arguments. Use an output format that is safe for everyone who can read the result.

**Command line arguments are visible on the host** while the process runs, to anything that can list processes, which includes osquery ([4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md)). A credential passed as an argument can therefore end up in your own telemetry. Pass secrets through the environment or standard input where the tool allows it.

## Running one, and reading what came back

![How-to](../_assets/icons/howto.svg) Two ways to run, and they differ in more than convenience.

**Asynchronously** is the normal path. The script joins the host's queue and you read the result when it arrives. This is the only sensible option for more than a handful of hosts.

**Synchronously** waits for the result, up to six minutes, and is for the case where you are watching. The extra minute over the host's own limit exists to cover delivery, so a synchronous run that times out at the server has not necessarily failed on the device.

Read the exit code, output, and runtime together. A zero exit code confirms that the process reported success; use its output and a follow-up check to establish that it made the intended change. If the output is empty and the runtime is zero seconds, inspect the script and its conditions before relying on that result.

**A negative exit code is not your script's exit code.** It is Fleet's, and it means the script did not run as written. -2 means scripts are disabled on that host. -5 means Fleet could not resolve a built-in variable the script uses, and the output holds the reason. Any negative code is worth reading as Fleet telling you something rather than as your script's own result.

A Pending script is waiting for the host or for earlier work in its queue. Review upcoming activities to see whether a software installation or another script is ahead of it ([5.1](5.1-plan-target-and-govern-device-changes.md)). If queues stop draining across hosts, investigate server state ([8.6](../08-troubleshooting/8.6-server-state.md#864-upcoming_activities-the-unified-per-host-queue)).

**Results are per execution, not per script.** Each run is its own record with its own identity, which is what makes the history readable when a script has run on a host many times.

![How-to](../_assets/icons/howto.svg) A batch run sends one saved script to many hosts in a single request. It is the same discrete activity as a single run, multiplied: each host queues its own copy, runs once, and ends in its own terminal state. What changes is how you target, what can turn a host away before the script ever queues, and where you read the outcome back.

A batch runs a saved library script, never ad-hoc content: you pick one saved script and a set of hosts. It is exposed through the REST API and the UI, with no `fleetctl` batch command and no GitOps path, because a batch is imperative work rather than declared state ([a.5](../09-appendices/a.5-interface-index.md) carries the interface grid). Fleet hands back a batch execution ID, and that identifier is how you read status and results afterwards.

You target either by an explicit list of host IDs or by a filter, and exactly one of the two: sending both is refused.

A filter has to name a fleet, so batch targeting will not sweep every fleet at once, and every target has to sit on the same fleet as the script anyway. A saved script belongs to one fleet, or to Unassigned, and a batch only touches hosts in that fleet; an explicit list that reaches across fleets is refused as a whole rather than run in part, which is the ownership boundary a single run respects too.

Host health plays no part either way: failing policies are not a targeting criterion, so a host is never selected or dropped for being unhealthy, though the all-hosts branch does skip loading each host's issue counts as a minor query-cost optimisation.

**Two conditions refuse the whole run before it starts.** Scripts disabled globally turn it away with the same organization-settings message a single run gives ([What a script runs as](#script-privileges-and-execution-prerequisites)). And a batch targets at most **5,000 hosts**; a larger selection is rejected outright, not trimmed to the first five thousand.

**A targeted host can still be turned away as incompatible, for one of four reasons**, and all four surface under the single status `incompatible`:

- **`invalid-host`**: the host ID does not resolve to a host Fleet can target.
- **`incompatible-team`**: the host is on a different fleet from the script.
- **`incompatible-fleetd`**: the host’s agent reports scripts disabled, the same condition that produces exit code -2 on a single run.
- **`incompatible-platform`**: the script's interpreter has no meaning on the host's operating system, a PowerShell script aimed at macOS being the usual case.

An incompatible host never queues the script, so it shows in the counts but produces no run.

**Cancellation stops only what has not run yet.** A cancel request reaches the pending work: on a started batch it pulls each host's not-yet-activated copy from the queue, and on a batch scheduled for later it marks the whole thing cancelled before it begins. A script that has already run on a host cannot be recalled, so cancellation after activation is a race against the device fetching the work ([6.1](../06-automate-fleet/6.1-automation-design-and-change-control.md)). Cancel always records a `canceled_script_batch` activity with the targeted and cancelled counts, and it records that activity even when the batch had already finished and there was nothing left to stop.

**Read status and per-host outcomes from the batch's own endpoints, not from the log stream.** `GET /api/v1/fleet/scripts/batch/{batch_execution_id}` returns the batch's status, scheduled, started, or finished, with counts of how many hosts ran, are pending, errored, were cancelled, or were incompatible. `GET /api/v1/fleet/scripts/batch/{batch_execution_id}/host_results` returns one row per host with that host's own status. These are the surface that tells you what happened, because the per-host `ran_script` records a batch produces are host-only: they land on each host's own timeline but stay out of the global activity feed and the external log stream ([1.5](../01-foundations/1.5-audit-and-activity.md)). The batch's request, schedule, and cancellation are ordinary activities and do reach those surfaces; the per-host results do not, so the status and host-results endpoints are where you confirm each machine's outcome.

**Only an admin or a maintainer can start a batch.** Starting one needs both `script · write` and `host_script_result · write`, and their intersection is the global and fleet admin and maintainer roles. A technician can run and read an individual script but cannot start a batch this way. Reading a batch's status or host results needs only `script · read`, which an observer has ([a.4](../09-appendices/a.4-roles-and-permissions-matrix.md)).

**The batch run performs no licence check.** Premium is what creates and manages the fleets a fleet-scoped batch targets, not what runs the batch across one. On Free, where the only fleet is Unassigned, a batch runs across those hosts without a licence.

<a id="building-a-library-worth-having"></a>

## Build a reusable script library

![How-to](../_assets/icons/howto.svg) Keep the script library focused on tasks your administrators still perform, with enough context for someone else to use each entry confidently.

Name scripts for their outcome, such as “Reset printing subsystem.” Keep revision history in source control so the library name stays useful to operators.

**Put the contract in a comment at the top**: what it assumes about the host, what it changes, what it does not handle, and how to undo it. This is the same discipline as a query description ([4.6](../04-know-your-devices/4.6-advanced-osquery-queries-and-tables.md)) and it matters more here, because a script changes things.

**One script, one job.** A script that does three loosely related things fails partway through and leaves the host in a state you cannot name.

Manage scripts as code so changes can be reviewed before distribution and recovered when necessary ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

Retire unused scripts after confirming no setup experience or automation depends on them. This keeps outdated repair steps from being mistaken for current procedures.

<a id="before-you-run-it-on-everything"></a>

## Test before expanding script scope

![Troubleshooting](../_assets/icons/troubleshooting.svg) Complete these checks on representative test devices before expanding the rollout:

1. **Confirm scripts are enabled** on the hosts you are targeting, globally and in their agent packaging.
2. **Read it as though somebody else wrote it**, and ask what it does on a host in a state you did not anticipate: no network, disk full, the file already present, a user logged in.
3. **Run it on your own device**, then on the awkward hosts rather than the clean ones.
4. **Run it twice on the same host** and confirm the second run is uneventful.
5. **Check the output is legible**, and that the part you need survives truncation.
6. **Confirm it finishes well inside five minutes**, on the slowest hardware you support.
7. **Know how you would undo it**, and write that script before you need it.
8. **Then a ring**, and only then the estate ([5.1](5.1-plan-target-and-govern-device-changes.md)).
