# Use policies for compliance

A policy is a report with a yes-or-no answer. It runs the same way a scheduled report does, on the same channel and the same kind of schedule, and everything [4.2](4.2-run-queries-and-reports.md) says about scope and cost applies here too. What it adds is a verdict: for each host, Fleet records whether the policy passed.

That verdict is the whole value and also the whole risk. A pass is a statement about what a host reported at a particular moment, and it is easy to read as a statement about the host now, or about hosts the policy never reached. The chapter's job is to keep those apart.

## A policy has three states, not two

![Explanation](../_assets/icons/explanation.svg) Fleet records a policy's result per host as passing, failing, **or nothing at all**. The third is not a display quirk; it is a stored state with no value in it, and it means Fleet has no result for this host and this policy.

| State | What it means |
|---|---|
| **Pass** | The host ran the policy and its query returned at least one row |
| **Fail** | The host ran the policy and its query returned no rows |
| **No result** | Fleet has not recorded an answer from this host |

**A policy passes when its query returns rows and fails when it returns none.** That is worth stating explicitly because it inverts the intuition of anyone used to writing checks that find problems. In Fleet you write the query that describes the *good* state, and a host that matches it passes.

**The third state is the one that misleads.** A host with no result is neither compliant nor non-compliant, and it is invisible in a count of failures. A newly enrolled host, a host that has not run the policy pass yet, and a host whose query fails on that platform all sit here. If you report compliance as "failing hosts", every one of these counts as a success, which is the wrong way round for a control.

**So read passing plus failing against your total, not failing against zero.** The gap is the population you know nothing about, and it is usually the population worth asking about.

## When a policy actually runs

![Reference](../_assets/icons/reference.svg) Policies run on their own pass, on `policy_update_interval`, which defaults to one hour with a per-host jitter of up to ten percent so an estate does not evaluate in lockstep ([4.1](4.1-understand-hosts-vitals-and-inventory.md)).

The host record carries `policy_updated_at`, dating that host's last policy evaluation. It is a different clock from `detail_updated_at` and from `seen_time`, so **a host can be comfortably online with policy results an hour old**, and that is ordinary.

Policy **counts** carry a clock of their own. Fleet stores the passing and failing host counts for each policy alongside a timestamp saying when they were computed, so the numbers on a policy list are a cached aggregate rather than a live count. When a policy's counts disagree with the host list beneath it, that timestamp is the explanation.

## Scoping a policy

![How-to](../_assets/icons/howto.svg) Four things decide which hosts a policy reaches, and getting any of them wrong produces a silent gap rather than an error.

**Platform** uses the generic selectors, `darwin`, `windows`, `linux` and `chrome`, not the specific platform value stored on a host. A Fedora host is selected by `linux` even though its inventory field reads `rhel` ([4.1](4.1-understand-hosts-vitals-and-inventory.md)). An unscoped policy is sent to hosts whose tables do not exist, and those hosts fail it for the wrong reason.

**Fleet scope** decides the base population, and the asymmetry here catches people: **a policy in the global scope applies to hosts in every fleet**, not only to unassigned ones. That is the opposite of how configuration profiles and software behave ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Labels** narrow it further, and **policies are the only item in Fleet that supports all four targeting modes**: include-any, include-all, exclude-any and exclude-all, with one include mode and one exclude mode allowed together. Everything else supports a subset.

**Label targeting on policies is Fleet Premium.** So is a named fleet. On Fleet Free a policy is global and unlabelled, which means the platform selector is the only scoping you have.

**One warning that applies to policies specifically.** The freshness guard that protects configuration profiles and software from acting on stale label membership **does not exist for policies** ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)). A policy with a newly created exclusion label will run on hosts that have not yet been evaluated for it. If exclusion matters, let the label populate before you attach it.

## Writing a policy that is worth having

![How-to](../_assets/icons/howto.svg) The query is the easy part. These are the fields that decide whether anyone can act on the result.

**Write the query for the good state.** A policy that returns a row when the disk is encrypted passes on encrypted hosts. Written the other way round it reports the exact inverse of what you meant, and it will look plausible on a small test set.

**The resolution is not decoration.** Fleet stores a resolution alongside each policy, and it is what somebody reads at the moment they have to fix a failing host. Write it as an instruction rather than a restatement of the problem: "Turn on FileVault in System Settings, Privacy and Security" is useful; "This host does not have FileVault enabled" is the failure repeated back.

**Mark a policy critical only if you mean it.** Fleet carries a critical flag on policies, and it is worth reserving for the ones whose failure changes what somebody does today. A list where everything is critical sorts no better than a list where nothing is.

**Test it live before you save it.** A policy is a report, so run its query as a live report first and read the responded, no-results and error counts ([4.2](4.2-run-queries-and-reports.md)). A query that errors on a platform is a policy that fails there for reasons unrelated to compliance.

## Turning a failure into an action

![Explanation](../_assets/icons/explanation.svg) A failing policy can trigger work rather than only sitting on a page. Fleet supports attaching an automation to a policy: installing a software title, or running a script, when a host fails it.

**These are Part V's subject**, because they change the device rather than read it ([5.7](../05-manage-devices/5.7-automate-remediation-with-policies.md)). Three things belong here, because they change how you read the policy:

**Automations are attached to fleet policies.** A policy in the global scope does not carry a software or script automation.

**Continuous automations are Fleet Premium.** By default an automation fires on the transition into failure. The setting that keeps it acting on a host that stays failing is Premium, and the distinction matters: without it, a host that fails, is remediated by hand, and fails again gets a second trigger, while a host that simply stays broken does not.

**A remediated host does not update until its next policy pass.** The automation runs, the device changes, and the policy page keeps saying failing until the next evaluation on that host's hourly clock. That interval is the difference between "the automation did not work" and "the automation worked and nothing has re-checked yet", and the host's `policy_updated_at` is what tells you which.

## Reading a compliance number honestly

![Troubleshooting](../_assets/icons/troubleshooting.svg) The questions to ask before quoting a policy result to anybody.

| Question | Why it matters |
|---|---|
| How many hosts have **no result**? | They are in neither count, and a compliance figure that ignores them overstates coverage |
| When were the **counts** computed? | They are a cached aggregate with their own timestamp, not a live count |
| When did each host last **evaluate**? | `policy_updated_at` per host; an hour is ordinary, a week is not |
| Does the **platform scope** match the hosts you care about? | An unscoped policy fails on platforms it was never meant for |
| Is this policy **global or fleet-scoped**? | A global policy is running in every fleet, which may be more than you intended |
| Did the query **error** anywhere? | An erroring policy produces no result rather than a failure, so it vanishes from both counts |

**A policy result is evidence about a report at a moment, not a certificate.** It says a host answered a particular question a particular way, within the last evaluation interval. For anything that has to hold up as an assertion about the estate, quote the three numbers together: passing, failing, and the remainder.
