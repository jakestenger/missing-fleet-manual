# Run queries and read reports

[4.1](4.1-understand-hosts-vitals-and-inventory.md) covers what Fleet asks every host without being told to. This chapter is about asking your own questions, and it opens with storage rather than syntax because **where a result goes is decided before it is produced**, by settings on the query itself, and getting that wrong is the most expensive mistake available here.

The short version: a query can execute and leave nothing behind. It can execute and store a result you can read on the report page. It can execute and forward a result to a log destination. Those are three separate outcomes governed by three separate settings, and none of them implies another.

## Execution, storage, and forwarding are three decisions

![Explanation](../_assets/icons/explanation.svg) Every scheduled query in Fleet resolves three questions independently.

**Does it run?** A query runs on a host when it is scheduled, the host's platform matches the query's platform selector, and the host's osquery is at or above any minimum version the query sets. A live report is different again and runs on demand ([below](#live-reports-and-scheduled-reports-answer-different-questions)).

**Is the result stored in Fleet?** Fleet keeps the **newest result per host per query**, overwriting that host's previous rows rather than accumulating them, so the report page shows the current answer and never a trend. Four things stop that happening:

| What stops storage | Where it is set |
|---|---|
| `query_reports_disabled` | Server-wide, in organization settings. Turning it on also **deletes** the rows already stored, rather than only preventing new ones |
| `discard_data` | On the individual query |
| A logging type other than **snapshot** | On the individual query. Differential logging is not stored as a report |
| The report row cap | Server-wide, defaulting to **1000 rows per query** |

**Is the result forwarded to a log destination?** Only when that query's **automations are enabled**, which is off when a query is created. This is the single most common reason a correctly configured log destination sits empty: the destination is a server setting, and forwarding is a per-query decision on top of it ([2.5](../02-administer-and-deploy-fleet/2.5-activity-audit-logs-and-log-delivery.md)).

**None of the three implies another.** A query with automations on and `discard_data` set forwards results and stores nothing. A query with automations off and storage on gives you a report page and an empty destination. Decide both deliberately.

## The report cap does not behave like a limit

![Reference](../_assets/icons/reference.svg) The row cap is worth its own section because "capped at 1000" suggests something tidier than what happens.

Fleet marks a query's report **clipped** once it reaches the cap, and the reader-facing consequence is not that the report holds a neat thousand rows. A host whose single result set is larger than the cap **stores nothing at all**, rather than storing the first thousand of its rows. And a cleanup job trims across hosts, keeping the most recently inserted rows, so an older host's answer can disappear from a report that is otherwise working.

**So a clipped report has unknown coverage and unknown freshness.** Once you see that marker, stop reading the page as an estate-wide answer. Either narrow the query so it returns fewer rows per host, or forward the results to a log destination and read them there, where no cap applies.

## Live reports and scheduled reports answer different questions

![Explanation](../_assets/icons/explanation.svg) The two look similar in the interface and are not interchangeable.

**A live report** goes out now, over the osquery distributed channel, to the hosts that are online and answering. It returns what they say, and it stores nothing. It is the right tool for "what is true right now" and for testing a query before scheduling it. It is the wrong tool for coverage, because a host that is asleep simply does not appear, and the report cannot tell you the difference between a host that answered "no rows" and a host that never answered.

Two things bound live reports beyond the obvious. Fleet has a server setting that **disables live reporting entirely**, which is worth knowing before diagnosing an unresponsive button. And a query's `observer_can_run` flag decides whether observer-role users may run it at all, which is how a deployment lets a support team run a chosen set of reports without granting broader access ([1.4](../01-foundations/1.4-identity-and-roles.md)).

**A scheduled report** runs on the host's own schedule and produces the stored result and the forwarded result described above. It is the right tool for coverage and for anything you want to look at later. It is the wrong tool for "right now", because you are reading whatever each host last reported, on its own clock.

**On ChromeOS there are no scheduled reports at all.** The extension answers the distributed endpoints, so live reports work, and it never posts to the logging endpoint, so nothing is ever scheduled or forwarded ([3.6](../03-connect-devices/3.6-enroll-android-and-chromeos-devices.md)). On iOS, iPadOS and Android there is no osquery at all, so neither kind applies.

## Designing a report that answers what you asked

![How-to](../_assets/icons/howto.svg) The mechanics above decide whether you get an answer. These decide whether it is the right one.

**Scope the platform deliberately.** A query's platform selector takes the generic values `darwin`, `windows`, `linux` and `chrome`, not the specific platform value stored on a host, so a Fedora host is selected as `linux` even though its inventory field reads `rhel` ([4.1](4.1-understand-hosts-vitals-and-inventory.md)). A query left unscoped is sent to hosts whose tables do not exist, which produces errors rather than empty results.

**Set a minimum osquery version when a query needs one.** A table or column added in a later osquery release fails on hosts below it, and that failure is per host and quiet. Naming the version keeps those hosts out of the result rather than in the error log.

**Decide the logging type before you schedule.** Snapshot logging reports the current rows each time. Differential logging reports what changed, which is much smaller on a stable estate and is **not stored as a report**, so a differential query gives you a log stream and an empty report page by design.

**Return fewer rows than you think you need.** The cap above is per query across the estate, so a query returning fifty rows per host reaches it at twenty hosts. Aggregate in SQL rather than in your head: count, filter and limit on the host, where it costs one row, instead of shipping everything and filtering later.

## Reading a result honestly

![Reference](../_assets/icons/reference.svg) A results table has more failure modes than it shows, and separating them is most of the skill.

| What you see | What it can mean |
|---|---|
| Rows from some hosts | Those hosts answered. It says nothing about the others |
| No rows from a host | The query ran and matched nothing, **or** it failed on that host. The results table does not distinguish these |
| A host absent entirely from a live report | Offline, or not answering the distributed channel, or filtered out by the query's platform or version scope |
| A stored report with old rows | That host has not reported since; each row carries its own fetch time, which is the timestamp to read |
| The report marked clipped | Coverage and freshness are both unknown, per the section above |

**"No rows" and "could not run" are different states and the results table shows them the same way.** That distinction lives in the osquery status log rather than in the report ([8.2](../08-troubleshooting/8.2-log-surfaces.md)), which is why a query that is quietly failing on a fifth of the estate looks like a query with a smaller answer than expected.

**Read the per-row fetch time rather than the page.** A stored report is an accumulation of per-host answers taken at different moments, not a snapshot of the estate at one instant.

## Getting results out of Fleet

![How-to](../_assets/icons/howto.svg) Three routes, with different guarantees.

**The report page** is the fastest and is bounded by the cap and the storage settings above.

**The API** returns the stored report rows and is the route to use when you want them somewhere else on a schedule. Note that `fleetctl` is not this route: its query command runs a fresh live report, and its get command lists definitions, so neither retrieves what is already stored ([1.1](../01-foundations/1.1-what-fleet-is.md)).

**A log destination** receives forwarded results, for queries whose automations are on, and is the only one of the three with no cap. If you need history rather than current state, this is the route, because Fleet's own storage keeps the newest result and nothing before it ([2.5](../02-administer-and-deploy-fleet/2.5-activity-audit-logs-and-log-delivery.md)).

## Verifying what a report costs

![Troubleshooting](../_assets/icons/troubleshooting.svg) A query that answers correctly can still be a problem, and Fleet gives you the evidence before your users do.

Fleet records per-query execution statistics from the hosts that ran it, which is the first place to look when a scheduled report is suspected of causing load. A query whose average execution time is climbing, or whose memory use stands out against its neighbours, is the candidate.

**Test on a representative host before scheduling on the estate.** Run it as a live report against a small label first: a busy server and a laptop with a full disk will tell you more than a clean test machine. The mechanics of reading query statistics, the osquery watchdog, and what happens when a query is denylisted are [4.6](4.6-advanced-osquery-queries-and-tables.md)'s subject.
