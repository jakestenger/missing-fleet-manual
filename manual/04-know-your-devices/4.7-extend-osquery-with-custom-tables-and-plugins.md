# Extend Fleet telemetry

Everything so far in this part reads what Fleet already collects. This chapter is about the question you reach after that: **osquery does not have a table for the thing I need to know.**

There are five answers, and they differ enormously in cost, risk and how much of your life they consume. The mistake this chapter exists to prevent is reaching for the heaviest one first. Writing an osquery extension is a real engineering project with a maintenance tail, and most questions that feel like they need one do not.

## The hierarchy, lightest first

![Explanation](../_assets/icons/explanation.svg) Work down this list and stop at the first thing that answers your question.

| | Mechanism | Use when |
|---|---|---|
| 1 | **A saved or scheduled query** | The data exists in a table and you want to see it ([4.2](4.2-run-queries-and-reports.md)) |
| 2 | **A policy or a label** | The answer is a yes-or-no you want to act on or target by ([4.3](4.3-use-policies-for-compliance.md), [1.3](../01-foundations/1.3-hosts-fleets-labels.md)) |
| 3 | **`features.additional_queries`** | The data exists in a table and you want it **on the host record**, refreshed with the host's other details |
| 4 | **`features.detail_query_overrides`** | A built-in detail query is wrong or harmful for your estate. An escape hatch, not an option |
| 5 | **An osquery extension** | The data genuinely is not in any table on the platform |

The first two are covered elsewhere. This chapter is about three, four and five.

**The question that separates two from three** is whether you want an answer *about* a host or a field *on* a host. A scheduled report gives you rows you go and read. `additional_queries` puts the result on the host record itself, where it refreshes with everything else and travels with the host.

## `additional_queries`: adding fields to the host record

![Reference](../_assets/icons/reference.svg) The mechanism most administrators should reach for, and the one that is hardest to discover.

**What it is.** A JSON object of name-to-SQL pairs in the server's feature settings. Fleet appends each one to the set of detail queries a host is asked, prefixed internally as `fleet_additional_query_<name>`, and stores the returned rows on the host as `additional` data under the name you gave.

**When it runs.** With the host's other detail queries, on the detail update interval, not on a schedule you set. That is the point of the mechanism: the field ages with the rest of the host record rather than on its own clock ([4.1](4.1-understand-hosts-vitals-and-inventory.md)).

Four properties that will surprise you.

**It is not platform-gated.** Built-in detail queries carry platform conditions. An additional query is registered with a discovery condition that is **always true**, so it is asked of every host regardless of platform. Where the table does not exist it simply fails, nothing warns you, and the failure is per host. If your query is platform-specific, guard it inside the SQL rather than expecting Fleet to scope it.

**It is skipped when Fleet is in a hurry.** When Fleet is refetching only critical detail queries for a host, additional queries are not included, so the field is not refreshed in that window.

**It is global.** These are server feature settings, not per-fleet configuration.

**The name is the contract.** It becomes the key on the host record, so anything reading that key breaks if you rename it.

**Use it for** a licence key, an asset tag, a locally meaningful registry value or configuration file field, a site or building identifier that lives on the machine. Things you want to see next to a host, rather than things you want to count across the estate.

**Do not use it for anything expensive.** It now runs on every host on the detail interval, indefinitely. The design discipline in [4.6](4.6-advanced-osquery-queries-and-tables.md) applies with more force here than to a scheduled query you could simply delete.

## `detail_query_overrides`: an escape hatch with sharp edges

![Troubleshooting](../_assets/icons/troubleshooting.svg) This one replaces or removes Fleet's **own** detail queries. Fleet's contributor documentation describes it as a debugging tool and warns that it can break host data ingestion. That warning is accurate, and the mechanism behind it is worth understanding before you use it.

**How it behaves,** for each name-to-SQL pair you supply:

- Give it SQL, and Fleet **replaces the query text** for that built-in detail query.
- Give it null or an empty string, and Fleet **deletes that detail query entirely**. The host stops being asked, and whatever it populated stops being updated.
- Name something that is not a real detail query, and Fleet logs an error and **carries on applying the rest**. There is no rejection, so a typo silently does nothing while its neighbours take effect.

**Why it breaks ingestion.** Replacing the SQL does not replace the code that reads the result. Fleet keeps the original ingestion function, which expects specific column names. An override returning a perfectly sensible result set with different columns will be collected and then fail to ingest, and the host field it feeds goes stale while the configuration looks correct.

**So the rule is:** an override must return exactly the columns the original returned. Read the built-in query first and match its shape, not its intent.

**Legitimate uses are narrow:** suppressing a detail query that is pathological on your hardware, or working around a known defect on a specific platform. If you are reaching for it to *add* something, you wanted `additional_queries`.

**Record why.** An override is invisible in the interface and changes what every host reports. Six months on, an unexplained override is indistinguishable from a mistake, so it belongs in GitOps with a comment ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

## Extensions: when the data really is not there

![Explanation](../_assets/icons/explanation.svg) An osquery extension is a separate program that registers new tables with osquery. Fleet has a managed path for distributing them and a raw path for when you are on your own.

**The managed path** is the `extensions` key in agent options: a map of extension name to a small object naming a **platform**, a **TUF update channel**, and optionally **labels**. Fleet's updater delivers the binary on that channel and orbit loads it.

Three things to know before planning around it:

- **Label scoping is Fleet Premium.** Naming labels without a licence fails the request outright. That is a genuine refusal, unlike the silent parameter dropping described in [4.5](4.5-monitor-device-and-management-status.md).
- **A named label must already exist** on that fleet, or the request is rejected. Create the label first.
- **The platform tokens are not the query platform tokens.** An extension's platform is `macos`, where a query's platform is `darwin`. The same concept, two spellings, and the wrong one is a configuration that quietly matches nothing.

**The raw path** is osquery's own autoload. Orbit adds the `--extensions_autoload` flag when an `extensions.load` file exists in its root directory and is not empty; an empty file is ignored. This is the route for an extension you are not distributing through Fleet's updater, and it means the extension's presence is a property of the host's disk rather than of your Fleet configuration. Nothing in Fleet will tell you which hosts have it.

**What you are taking on.** An extension is code running alongside osquery on every machine you deploy it to. It needs building per platform, signing where the platform requires it, distributing, versioning, and updating when osquery's extension interface changes. It is subject to the same watchdog and denylisting as anything else ([4.6](4.6-advanced-osquery-queries-and-tables.md)), and a table that blocks takes the worker down with it.

**Before you write one,** confirm three things: that no existing table answers the question on that platform, that the question is worth per-host code in your estate for years, and that somebody will own it when its author leaves. The third is the one that gets skipped.

## Other collection you can turn on without writing code

![Reference](../_assets/icons/reference.svg) Two osquery subsystems sit in agent options and produce telemetry without a new table.

**File integrity monitoring** takes sets of paths to watch, path sets defined by query, and exclusions. It produces events rather than snapshot rows, so it belongs in a log destination rather than in a report ([2.5](../02-administer-and-deploy-fleet/2.5-activity-audit-logs-and-log-delivery.md)).

**YARA** takes named signature sets and the paths to scan with them, with the same event-shaped output.

Both are worth knowing about specifically because they answer a class of question, "tell me when this file changes", that people otherwise try to answer by scheduling an expensive filesystem query every fifteen minutes.

## Choosing, in practice

![How-to](../_assets/icons/howto.svg) A sequence for a question you cannot currently answer.

1. **Search the table schema for the platform**, not for the concept. The table may exist under a name you would not have guessed.
2. **Ask whether a nearby table answers a slightly different question well enough.** An approximate answer that costs nothing often beats an exact one that costs a watchdog restart ([4.6](4.6-advanced-osquery-queries-and-tables.md)).
3. **Decide whether you want a row or a field.** Rows are a report. Fields on the host record are `additional_queries`.
4. **If a built-in is actively wrong for you**, that is the only case for an override, and match the original's columns exactly.
5. **If nothing has the data**, check whether an existing open-source extension already provides it before writing one.
6. **If you write one**, treat it as software: version it, scope it with labels, roll it out to a small population first, and watch the query statistics on the hosts that have it.

**Whatever you choose, write down why.** Every mechanism in this chapter except the first two is invisible from the interface. Whoever inherits your deployment will find an unexplained additional query, an override, or an extension on a channel, with no way to reconstruct the reasoning.
