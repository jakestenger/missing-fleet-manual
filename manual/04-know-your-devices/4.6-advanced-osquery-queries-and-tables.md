# Advanced osquery: query design, tables, and performance

[4.2](4.2-run-queries-and-reports.md) covers getting a result out of Fleet. This chapter is about the query itself: why osquery's tables are not database tables, what a query costs on somebody's laptop, what Fleet lets you do about it, and how to find out before the estate finds out for you.

The governing idea is that **cost is a design decision, not an optimisation you apply later**. A query that reads a whole filesystem costs that on every host that runs it, every interval, forever, and no amount of tuning afterwards recovers the time already spent.

## Why osquery tables are not database tables

![Explanation](../_assets/icons/explanation.svg) An osquery table looks like SQL and behaves differently in ways that decide what your query costs.

**Most tables are generated on demand.** There is no stored table being scanned. When you select from a table describing processes, osquery goes and enumerates processes at that moment. The cost of a query is the cost of the work the tables do, not the cost of reading rows.

**Some tables do nothing until you constrain them.** A table describing files or directory contents needs a path to work from, and without one it either returns nothing or attempts something enormous. These are the tables where a `WHERE` clause is not a filter applied to results; it is the input that makes the table work at all.

**A join can multiply that work.** Joining two generated tables can mean generating one of them repeatedly, so a join that looks cheap in SQL terms can be the most expensive thing in your query. Where a join is against a small, cheap table, this does not matter; where it is against a table that enumerates a filesystem, it matters enormously.

**Tables differ by platform and by osquery version.** A table available on macOS may not exist on Windows, and a column added in a later osquery release does not exist on hosts below it. Neither produces a partial answer: the query fails on that host, and a failed query is not a result ([4.2](4.2-run-queries-and-reports.md)).

## The four knobs Fleet puts on a scheduled query

![Reference](../_assets/icons/reference.svg) Beyond the SQL, a scheduled query carries four fields that exist specifically to control blast radius. Three of them are widely missed.

| Field | What it does |
|---|---|
| `platform` | Restricts the query to `darwin`, `linux` or `windows`. Empty or unset means every platform |
| `version` | Runs only on osquery versions greater than or equal to this string |
| `shard` | Runs on a **percentage of target hosts**, 1 to 100 |
| `denylist` | Whether this query **may be denylisted** when the watchdog stops it. Defaults to true |

**`shard` is the canary mechanism, and it needs no licence and no label.** Set a query to 10 and it runs on roughly a tenth of its targets, which is the cheapest possible way to learn what a new query costs before it reaches everything. This is the field to reach for when you want a staged rollout in Fleet Free, where named fleets are not available ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**`denylist: false` is a loaded weapon.** It means "keep running this even though the watchdog keeps stopping it". There are legitimate uses, and all of them involve knowing exactly why the query trips the watchdog. Setting it to silence a denylisting you did not understand converts a query Fleet stopped for you into a query that keeps damaging the host.

## What osquery does to a query that misbehaves

![Explanation](../_assets/icons/explanation.svg) osquery protects the host from your query, and how that presents in Fleet is the single most useful thing in this chapter.

**The watchdog watches the worker process** and restarts it when it exceeds its limits. From Fleet's side this looks like a host that stopped answering and then came back, which is easy to read as a network problem.

**The watchdog's limits are Fleet agent options, not just osquery defaults.** `watchdog_memory_limit`, `watchdog_utilization_limit`, `watchdog_delay`, `watchdog_latency_limit` and `watchdog_level` are all settable through Fleet's agent options, as is `disable_watchdog`. That last one deserves the same suspicion as `denylist: false`: it disables the thing protecting your fleet's laptops from your own SQL.

**A query the watchdog repeatedly stops gets denylisted on that host**, unless the query set `denylist: false`. osquery stops running it there and the host carries on running everything else. For distributed queries, `distributed_denylist_duration` in agent options controls how long that lasts.

**Denylisting is per host.** A query that is too expensive for your oldest laptops and fine on everything else produces a result set silently biased toward newer hardware, which is a quietly serious problem for a compliance report. The report is not wrong about the hosts in it; it is wrong about which hosts are in it.

**Where Fleet tells you.** Three places, and they are not equally findable:

- **The query's performance impact** reads **Denylisted** when the flag is set. This is the surface most people will actually see.
- **The per-host scheduled query statistics** carry a `denylisted` boolean, over the API.
- **The server log** records `distributed query is denylisted` at **warn** level, for distributed queries. Fleet's own source comments that exposing this in the interface is an open request, so the log is where it lives today ([8.6](../08-troubleshooting/8.6-server-state.md)).

## The statistics Fleet keeps, and how to read them

![Reference](../_assets/icons/reference.svg) Fleet collects per-host execution statistics for scheduled queries and aggregates them per query.

**First, a prerequisite that will otherwise waste your afternoon.** Collection is governed by the server setting `enable_scheduled_query_stats`, which defaults to **true**. If a deployment has turned it off, every number below is empty and nothing in the interface explains why. Check it before concluding a query has never run ([2.7](../02-administer-and-deploy-fleet/2.7-organization-and-server-settings.md)).

Per host, the statistics carry executions, average memory, system time, user time, wall time, output size, last executed, the interval, and the denylisted flag, alongside whether data is discarded and whether automations are enabled.

**These are current values, not a series.** Per-host statistics are written with a replace, so a new report overwrites the old one. There is no history to read and no trend to plot. The method is comparison: this query against other queries on the same hosts.

**The percentiles are per-host averages, not per-execution.** Fleet computes the fiftieth and ninety-fifth percentiles by first working out each host's total time divided by its total executions, then taking the percentile **across hosts**. So the ninety-fifth percentile means "the host at the ninety-fifth percentile of average cost per execution", not "the slowest five percent of runs". Hosts that have never executed the query are excluded from the calculation entirely.

**Wall time exists in two units and one of them is derived.** `wall_time` is in seconds; `wall_time_ms` is in milliseconds. Where Fleet holds only the seconds value it fills the millisecond one in by multiplying by a thousand, so a `wall_time_ms` that is suspiciously round may be a conversion rather than a measurement.

**Output size is bytes, not rows.** It tells you what the query costs to ship and store. It does **not** tell you whether the query is near the row threshold below, because row count and byte size vary independently: a thousand narrow rows and ten enormous ones are different problems.

## The performance impact indicator, and what it cannot see

![Reference](../_assets/icons/reference.svg) Fleet shows a query's performance impact as one of five words, and the calculation behind it matters.

| Indicator | When |
|---|---|
| **Undetermined** | The query has no executions yet |
| **Minimal** | The two fiftieth-percentile CPU figures sum to under 2,000 |
| **Considerable** | They sum to under 4,000 |
| **Excessive** | Anything above that |
| **Denylisted** | The query has been stopped for resource consumption |

**Read the row that is not there.** The indicator is computed from the **fiftieth** percentile only. A query that is cheap on the median host and brutal on the oldest tenth of your estate reads as **Minimal** while it is being denylisted on real machines. The ninety-fifth percentile figures are in the API and are not in this calculation.

That is the case for going to the statistics rather than trusting the word: the indicator answers "is this query expensive in general", and the question you usually care about is "is this query expensive somewhere".

## Design for cost first

![How-to](../_assets/icons/howto.svg) Six habits, in rough order of how much they save.

**Constrain the expensive table, not the result.** `WHERE path LIKE '/Applications/%'` on a file table is a different query from selecting everything and filtering afterwards, even though they return the same rows. The first tells the table what to generate; the second generates everything and throws most of it away.

**Aggregate on the host.** Count, group and limit in SQL, where the work happens once, rather than in whatever reads the results. This also keeps you clear of the row threshold: **a host that returns more than 1,000 rows has its entire result set rejected**, and nothing is stored for that host. That limit is fixed and is not `report_cap`; `report_cap` governs how much of a report Fleet keeps across hosts, and raising it does nothing for a host tripping the per-host limit ([4.2](4.2-run-queries-and-reports.md)).

**Select the columns you need.** Some columns are cheap to produce and some are computed per row. Selecting everything asks for all of them.

**Prefer a cheap table that answers the question over an expensive table that answers it precisely.** A great many "is this present" questions can be answered from a package or application inventory rather than by walking a filesystem.

**Scope by platform, always.** An unscoped query reaches hosts whose tables do not exist, where it errors. Those hosts then have no answer, and a missing answer is quieter than an exclusion.

**Set a minimum version when the query needs one.** It keeps the query away from hosts that would fail it, which turns a silent failure into a deliberate omission you chose.

## A worked example

![How-to](../_assets/icons/howto.svg) The same question, designed badly and then designed well.

**The question:** which hosts have a browser extension installed from outside the official stores?

**The bad version** selects every file under every user's home directory and filters for extension manifests in the `WHERE` clause. On a developer's laptop with a large home directory this walks hundreds of thousands of files every interval. It returns one row per extension, which on a heavily-extended browser is dozens of rows per host, each carrying a long path. It is unscoped, so it also fails outright on Windows hosts whose paths differ.

Its symptoms, in order of appearance: the performance impact reads **Excessive**; output size climbs; a handful of hosts stop appearing in results; those hosts show `denylisted` over the API while the interface still reads Excessive rather than Denylisted, because the aggregate is computed across every host and most of them are fine.

**The better version** starts from a browser extensions table rather than a filesystem walk, so the table does the enumeration natively. It constrains on the specific columns that identify provenance rather than filtering afterwards. It aggregates to **one row per host**, a count and a boolean, so the row threshold is unreachable and the output size is a few dozen bytes. It is platform-scoped, and it declares a minimum osquery version because the provenance column is not in every release. It ships at `shard: 10` for a week.

**Then it is measured, not assumed.** After a few intervals: executions climbing on the sharded population, the two fiftieth-percentile CPU figures well under 2,000, the ninety-fifth percentile checked separately over the API, no denylisted hosts. Only then does the shard come off.

The second version answers a slightly narrower question than the first. That is usually the trade, and it is usually worth it.

## Testing a query before the estate tests it

![How-to](../_assets/icons/howto.svg) A sequence that catches the failures above before they are distributed.

1. **Run it as a live report against one host of each target platform.** Read the error column, not only the rows. A missing table or column shows here.
2. **Run it against something old and something busy.** A clean test machine is the least informative host you own. A laptop with a full disk, a server with thousands of processes, and your oldest supported hardware will tell you what the estate will.
3. **Check what it returns per host.** More than 1,000 rows from any single host means that host stores nothing.
4. **Schedule it with a shard**, and read the statistics after a few intervals: executions, average memory, both percentiles, output size and the denylist flag.
5. **Widen the shard** only once those numbers are boring.
6. **Re-read the statistics a week later.** A query's cost changes as the estate changes, and the moment it starts being denylisted is the moment it stops being trustworthy as evidence.

## Time, platform and version

![Reference](../_assets/icons/reference.svg) Three sources of difference that produce wrong answers rather than errors.

**Time.** osquery reports times in a mixture of units and epochs depending on the table, and a query that assumes seconds where a table gives milliseconds produces a plausible number wrong by a factor of a thousand. Fleet's own statistics demonstrate the hazard, carrying wall time in both seconds and milliseconds under names a line apart. Check the units on the columns you compute with.

**Platform.** The same conceptual question maps to different tables per platform, and the honest way to handle that is usually several platform-scoped queries rather than one query with branching logic. Separate queries fail visibly on the wrong platform; a clever universal query fails quietly.

**Version.** A column added in a later osquery release does not exist below it, and the difference between "no rows" and "no such column" is the difference between an answer and a failure. Where a query needs a recent table or column, say so with the minimum version rather than discovering it as missing hosts.

## Building a library rather than a pile

![How-to](../_assets/icons/howto.svg) The queries that survive are the ones somebody else can pick up.

**Name for the question, not the mechanism.** "Hosts without disk encryption" is findable; "FileVault check v2" is not.

**Write the description as though the reader is not you.** What it answers, what a row means, and what it does not cover. The last of those is the part people leave out and the part that matters when a query is reused in a context it was not written for.

**Keep the scope on the query rather than in your head.** Platform, minimum version and shard are the things a person reusing the query has no way to reconstruct.

**Collect only what you need.** A query returning full command lines, environment variables or file paths from user directories is collecting personal data, and the fact that it is technically cheap does not make it appropriate. Aggregate to a count where a count answers the question.

**Manage them as code.** A query library in GitOps is reviewable, diffable and recoverable, and it stops the collection becoming a pile of near-duplicates nobody dares delete ([6.2](../06-automate-fleet/6.2-manage-fleet-with-gitops.md)).

**Prune deliberately.** A scheduled query nobody reads still costs every host that runs it, every interval. The cheapest performance work available in most deployments is deleting queries whose answers nobody has looked at in a year.

## When a query stops behaving

![Troubleshooting](../_assets/icons/troubleshooting.svg) The symptoms this chapter's mechanisms produce, and where each one goes.

| Symptom | Look at |
|---|---|
| Results arriving from fewer hosts than before | The `denylisted` flag per host, over the API. The interface aggregate will not show it while most hosts are fine |
| A host stores nothing while others store rows | The 1,000-row per-host threshold. Aggregate in SQL rather than raising `report_cap` |
| Every statistic is empty | `enable_scheduled_query_stats` on the server, before anything about the query |
| Performance impact reads Minimal while people complain | The ninety-fifth percentile over the API. The indicator only reads the fiftieth |
| A whole platform returns nothing | Platform scope, or a table that does not exist there ([4.2](4.2-run-queries-and-reports.md)) |
| One host answers nothing at all, for any query | Not a query design problem ([8.4](../08-troubleshooting/8.4-host-side-investigation.md), [8.7](../08-troubleshooting/8.7-live-query-introspection.md)) |
| Everything slowed down at once | The server rather than the query ([8.14](../08-troubleshooting/8.14-degradation.md)) |
