# Understand host data, vitals, and inventory

A host record is Fleet's answer to "what is this machine". Almost everything else in this manual either reads one or changes something it reports, so it is worth knowing not just what a host record contains but **which producer supplied each part of it, and when**.

That second question is what this chapter is really about. A host page presents identity, hardware, software, users, certificates, policies and labels on one screen, as though they were one observation taken at one moment. They are not. They come from at least six different producers on different clocks, and an empty field can mean the host answered "nothing", or that the question was never asked of this host, or that it was asked and failed and Fleet kept the previous answer.

There is no single rule that resolves those cases. What this chapter gives you instead is a method: for any field on the page, ask what produced it, whether this host is even capable of producing it, which timestamp dates that producer, and what Fleet does with that field when collection fails.

## Which questions Fleet asks a given host

![Explanation](../_assets/icons/explanation.svg) On a host running fleetd, Fleet does not ask open-ended questions to build the record. It sends a set of **detail queries** it defines itself, and ingests each result into a specific part of the host record. Their names describe the shape of the set: `system_info`, `os_version`, `network_interface_unix`, `uptime`, `disk_space_windows`, `battery`, `orbit_info`, `disk_encryption_darwin`, `certificates_windows`.

**That set is assembled per host rather than fixed.** It is worth understanding why, because it explains most "why does this host not have that field" questions:

- Some queries are added only when a feature is on. Software, host users, scheduled-query statistics, MDM and encryption queries all come and go with configuration.
- Every query carries platform restrictions, so a Linux host is not asked the macOS keychain question and never was.
- Some carry a **discovery query**, a cheap test that decides whether the real question is worth asking on this host at all.
- Some are generated dynamically from the deployment's own state rather than written out in advance.
- Administrator-defined **additional queries** are appended to the set ([4.7](4.7-extend-osquery-with-custom-tables-and-plugins.md)).
- `detail_query_overrides` can replace or remove Fleet's own queries entirely, which Fleet's contributor documentation describes as a debugging tool that can break host-data ingestion.

So "Fleet collects this" is always shorthand for "Fleet collects this on hosts where the query applies, is enabled, and passes discovery". A field that is empty across a whole platform is usually that, and not a fault.

**Not everything in the Vitals card came from a query.** Fleet 4.90.0 has **custom host vitals**: definitions an administrator creates, with a value set per host through the API. They appear alongside collected values in the same card, they are available on Fleet Free, and host-vitals labels can select on them ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)). A custom vital's payload carries a name and a value and **no timestamp of its own**, so nothing on the page tells you when it was last true. If a Vitals field looks like nothing osquery would report, this is usually why.

**Those definitions are managed, not just read.** The `custom_host_vitals` endpoints create a definition, list and search them, rename one, and delete it, and a separate per-host call sets or clears a host's value for a definition; a GitOps spec can declare the whole set at once through `spec/custom_host_vitals`. Every create, rename, value change and delete writes an activity, so the audit log carries the history a vital has no timestamp of its own for. Setting a value to the empty string is accepted and read back as empty, which is how you blank a vital without removing its definition. Deleting a definition cascades: its per-host values go with it, and a host that had one simply stops surfacing it.

## Six producers, and the timestamps that date them

![Reference](../_assets/icons/reference.svg) This is the table to work from. Fleet does not have one freshness clock, and the four that look like a set do not cover everything on the page.

| Producer | What it supplies | What dates it |
|---|---|---|
| **osquery detail queries** | Most of the host row: identity, OS, hardware, uptime, disk space, battery | `detail_updated_at` |
| **Directly ingested child inventories** | Certificates, host users, and similar lists stored in their own tables | Nothing host-wide. Direct ingestion does not by itself advance `detail_updated_at` |
| **Software inventory** | Installed software and its versions | `software_updated_at`, which dates the last time Fleet **changed** this host's stored software, not its last successful collection ([4.4](4.4-understand-software-and-vulnerabilities.md)) |
| **The server's own observation** | `public_ip`, taken from the address Fleet saw the request arrive from | The request that carried it; not a host report at all |
| **MDM and management APIs** | iOS, iPadOS and Android inventory, and Apple MDM certificates | Apple host details expose a separate last-MDM-check-in time |
| **Administrators** | Custom host vitals | Nothing. There is no per-value timestamp |

Alongside those, three further timestamps date *passes* rather than producers, and each runs on its own hourly interval:

| Field | What it dates |
|---|---|
| `seen_time` | The last time this host made any authenticated osquery request, on any of the three osquery channels ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)) |
| `label_updated_at` | The last time this host's label membership was evaluated |
| `policy_updated_at` | The last time this host's policy results were recorded |

**The intervals are approximate by design.** `detail_update_interval`, `label_update_interval` and `policy_update_interval` all default to one hour, and Fleet applies a per-host jitter of up to ten percent by default so an estate does not refresh in lockstep. "Within about the last hour" is the right expectation; an exact hour is not.

**A host can be online and stale at the same time**, which is not a contradiction. Online is a judgement about `seen_time`, which can be a minute old while `detail_updated_at` is an hour old and `software_updated_at` older still.

**On agentless hosts, read the management timestamp instead.** Online status is computed from the osquery check-in calculation, so for an iPhone, an iPad or an Android device it is not the signal you want. Their evidence of life is the management channel's own record of when it last heard from the device.

## What `detail_updated_at` does and does not prove

![Reference](../_assets/icons/reference.svg) This field is the one most often over-read, so it is worth stating precisely.

`detail_updated_at` advances when **at least one** ordinary detail result from the host's batch reaches Fleet's ingestion. It is a statement that the host answered *something*, not that every query ran, not that every field is current, and not that any particular field succeeded.

**A failed detail query is skipped rather than ingested**, so it does not clear the value it failed to refresh. That produces the case worth naming: a host whose `detail_updated_at` is two minutes old, showing a field whose real value changed a week ago, because the one query responsible has been failing since.

Certificate ingestion is explicit about this. When the certificate query returns no rows, or returns nothing parseable, Fleet **keeps the certificates it already had** rather than emptying the list.

So there is no universal empty-field rule in Fleet, and any method that assumes one will mislead you. Some failures preserve the previous value, some empty results genuinely overwrite, and one successful query is enough to move the host-wide timestamp.

## Reading one host record: a worked method

![How-to](../_assets/icons/howto.svg) Take any field that looks wrong and ask these four questions in order. They resolve most host-record puzzles without opening a log.

**1. What produced it?** Find the field in the producer table above. A `public_ip` that looks wrong is not a host problem at all, because the host never reported it.

**2. Can this host produce it?** Check the platform and enrollment path below. An iPhone has no local users because it has no osquery, not because collection failed.

**3. Which clock dates that producer?** `detail_updated_at` for most of the host row, `software_updated_at` for software, nothing at all for a custom vital or a directly ingested list.

**4. What happens to this field when collection fails?** If failure preserves the old value, a plausible-looking field can be arbitrarily old while the host looks healthy. Certificates behave this way.

Only if all four are satisfied and the field still looks wrong is it a fault, and then it is [8.4](../08-troubleshooting/8.4-host-side-investigation.md)'s territory rather than this chapter's.

## Identity, operating system, and network

![Explanation](../_assets/icons/explanation.svg) **How Fleet recognises a returning device depends on the path it returns by.** It is not a single rule about serial numbers. Fleet matches on the osquery host identifier first; serial matching applies to qualifying Apple MDM hosts; Android matches on UUID separately; and Windows deliberately does not use serial matching. Where identifiers do collide, the consequence differs again: an ordinary duplicate can overwrite the existing record, while a host using TPM-backed identity rejects the mismatch instead ([3.1](../03-connect-devices/3.1-enrollment-design-and-host-lifecycle.md)).

**Fleet enforces uniqueness only on the osquery host identifier**, and its own source is explicit that serial numbers are not unique. Before joining Fleet's data to another system on a serial, satisfy yourself that your estate has no duplicates rather than assuming the identifier guarantees it.

**The operating system arrives as three things that are easy to conflate**, and using the wrong one produces a validation error rather than a wrong answer, which is at least a fast failure:

| Where you are | What Fleet expects |
|---|---|
| The stored inventory field on the host | The specific value, so a Fedora host reads `rhel` |
| Scoping a policy or a report to a platform | The generic selector: `darwin`, `windows`, `linux` or `chrome`. Fleet maps Linux-family hosts to `linux` for this |
| SQL inspecting `os_version.platform` inside a query | Whatever osquery reports on that host, which can be `rhel` |

**The network fields are three separate things, and only two came from the host.** `primary_ip` and `primary_mac` are the address and MAC of the interface the system uses to reach its default route, selected by a query that returns exactly one row; they are not an inventory of every interface. `public_ip` is different in kind: **Fleet takes it from the address the request arrived from**, so it is the server's observation of the host rather than the host's report of itself.

## Users and device mappings answer different questions

![Explanation](../_assets/icons/explanation.svg) Two parts of the record look like "who uses this machine" and are not the same thing.

**Host users are local accounts on the device**, collected by a platform-specific query that filters its own results: accounts of type `special`, accounts whose shell is `false`, `nologin`, `shutdown` or `halt`, Windows machine accounts ending in `$`, and macOS accounts beginning with an underscore are excluded. Read that as a named set of exclusions rather than as a guarantee: service accounts can survive the filter, and a filtered-out account is not necessarily unusable by a person.

Collecting them at all is `enable_host_users`, on by default. A deployment that turned it off shows an empty list on every host, which reads exactly like a collection failure.

**Device mappings are email addresses associated with the host.** Fleet stores more sources internally than it returns, so work from the values the API actually gives you:

| Source you will see | What it means |
|---|---|
| `google_chrome_profiles` | Chrome profiles observed on the device |
| `mdm_idp_accounts` | An identity associated at enrollment. On Windows this can come from the enrollment user's name when Fleet links the enrollment, so it is not exclusively evidence of an identity-provider sign-in |
| `custom` | Any administrator-supplied or installer-supplied mapping. Fleet normalises its internal `custom_*` sources to this one value |

Two rules govern how they combine. **An administrator's override replaces the installer-supplied mapping only**; it does not override a Chrome profile or an identity-provider mapping. And Fleet promotes an identity-provider mapping into the host's primary end-user identity, putting the rest into other emails, rather than treating every source as equal.

**Setting an identity-provider mapping through the API is Fleet Premium**, while setting a custom mapping is not, so the two entries in that table are not equally available.

## Certificates

![Explanation](../_assets/icons/explanation.svg) Fleet keeps a per-host certificate list, and it answers questions nothing else in the record can: which hosts hold a certificate expiring inside the month, whether a certificate you deployed actually arrived. It has four limits worth knowing before you rely on it.

**The coverage is narrower than "the machine's certificates".** On macOS Fleet reads the system keychain and users' login keychains. On Windows it reads the **Personal** store, not the trusted-root store.

**So it does not tell you what a host trusts.** Certificate presence, including a flag marking a certificate as a certificate authority, is not the same as the platform's trust decision. You cannot certify from this list alone that a retiring authority is no longer trusted.

**On Windows, a user's certificates are visible only while that user's registry hive is loaded**, which in practice means while they are logged in. Fleet handles this deliberately by preserving the scopes it could not observe rather than deleting them, so the list can contain entries that are no longer there.

**Certificates can arrive from Apple MDM as well as from osquery**, and the certificate payload does not tell you which. Two entries that look alike can have different provenance and different freshness.

Read the list against those limits rather than against a timestamp: directly ingested inventories do not advance `detail_updated_at`, so there is no host-wide clock that dates it.

## What each platform and enrollment path populates

![Reference](../_assets/icons/reference.svg) Platform alone does not tell you what a host record can contain, because a Mac with MDM and no agent is a different reading surface from a Mac with both.

| Host | Where its data comes from | What not to expect |
|---|---|---|
| macOS or Windows, fleetd enrolled | osquery detail queries, plus MDM where enrolled | Individual queries are still platform-restricted; this is not a uniform surface |
| macOS or Windows, **MDM only** | The management channel alone | No osquery at all, so no detail queries, no users, no reports. The host record is thin and that is the configuration, not a fault ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)) |
| Linux, fleetd enrolled | osquery detail queries | No MDM, and a smaller detail set: the certificate queries are macOS and Windows only |
| iOS, iPadOS | The enrollment exchange, then device information fetched over MDM | No osquery. The scheduled refetch is **Fleet Premium**; on Free that schedule is never registered, so inventory does not refresh on its own ([3.5](../03-connect-devices/3.5-enroll-ios-and-ipados-devices.md)) |
| Android | Status reports from Google's management API | No osquery, no live or scheduled reports |
| ChromeOS | The *Fleetd for Chrome* extension's own virtual tables, over the ordinary distributed endpoints | No osqueryd, a much smaller table set, and no scheduled reports at all ([3.7](../03-connect-devices/3.7-enroll-chromeos-devices.md)) |

**The host page looks much the same for all of these.** When a reading is empty for a set of hosts, establish what those hosts are and how they enrolled before treating it as a fault.

## Where labels and freshness meet

![Explanation](../_assets/icons/explanation.svg) One consequence of `label_updated_at` is worth stating here because it changes what a stale host means operationally rather than cosmetically.

For **configuration profiles and software titles** scoped with a **dynamic** exclusion label, Fleet compares the host's `label_updated_at` against the label's creation time, and withholds the item from a host that has not been evaluated since the label existed. A host that looks fine can therefore be deliberately skipped ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**This applies to dynamic labels only.** Manual membership is administrator-maintained and needs nothing from the host, so a manual exclusion takes effect immediately.

Both of those capabilities carry licence gates that the freshness rule does not: **label scoping on configuration profiles is Fleet Premium**, and **software deployment and its label targeting are Fleet Premium**. On Free the situation this rule describes does not arise.
