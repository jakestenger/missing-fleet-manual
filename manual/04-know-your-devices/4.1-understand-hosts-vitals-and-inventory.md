# Understand host data, vitals, and inventory

A host record is Fleet's answer to "what is this machine". Almost everything else in this manual either reads one or changes something it reports, so it is worth knowing not just what a host record contains but **where each part of it came from and when**.

That second question is what this chapter is really about. A host page presents identity, hardware, software, users, policies and labels on one screen, as though they were a single observation. They are not. They arrive by different routes, on different clocks, and a field being empty can mean the host said "nothing", or "I cannot answer that", or "nobody has asked me yet". Reading a host record well is mostly the discipline of not treating those three as the same.

## How Fleet builds and refreshes a host record

![Explanation](../_assets/icons/explanation.svg) On a host running fleetd, Fleet does not ask open-ended questions to build the record. It asks a **fixed set of detail queries**, defined in Fleet's own source rather than by you, and ingests each result into a specific part of the host record.

Their names describe the shape of the set: `system_info`, `os_version`, `network_interface_unix`, `uptime`, `disk_space_windows`, `battery`, `orbit_info`, `disk_encryption_darwin`, `certificates_windows`, and so on. Several are per-platform variants of the same question, so counting the entries is not the same as counting the questions Fleet asks.

**That fixed set is what "vitals" means.** It is not a summary of everything osquery could tell you; it is the specific list Fleet decided every host should be asked. Anything outside it is a report you write ([4.2](4.2-run-queries-and-reports.md)), a policy ([4.3](4.3-use-policies-for-compliance.md)), or an extension of the set itself ([4.7](4.7-extend-osquery-with-custom-tables-and-plugins.md)).

**The refresh is not continuous.** Fleet sends the detail queries on an interval, `osquery.detail_update_interval`, which defaults to **one hour**. A host answers when it next collects its distributed work, so the practical freshness of a vital is "within about the last hour, plus however long since that host last checked in".

Two consequences catch people out. A change on the device is not visible in Fleet the moment it happens; it is visible after the next detail pass. And a host that is checking in perfectly well can be showing you hour-old hardware and software data, which is ordinary rather than a fault.

## Four clocks, not one

![Reference](../_assets/icons/reference.svg) Fleet stores **four separate timestamps** on the host record and they mean different things. Reading the wrong one will misjudge whether data is stale.

| Field | What it dates | Advanced by |
|---|---|---|
| `seen_time` | The last time this host made **any** authenticated osquery request | Any osquery check-in: config, distributed, or logger |
| `detail_updated_at` | The last time the **detail queries** were ingested | The detail pass, on `detail_update_interval`, one hour by default |
| `label_updated_at` | The last time this host's **label membership** was evaluated | The label pass, on `label_update_interval`, one hour by default |
| `policy_updated_at` | The last time this host's **policy results** were recorded | The policy pass, on `policy_update_interval`, one hour by default |

**A host can be online and stale at the same time**, and that is not a contradiction. Online is a judgement about `seen_time` ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)), which can be a minute old while `detail_updated_at` is an hour old and `policy_updated_at` older still. If you are asking "is this current", name which data first, then read that clock.

The reverse is worth knowing too. **A stale `label_updated_at` is not cosmetic.** Fleet compares it against a label's creation time to decide whether it can trust a host's absence from an exclusion label, so a host that has not been evaluated recently is deliberately withheld from some profiles and software rather than being sent them ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

## Identity, hardware, operating system, and network

![Explanation](../_assets/icons/explanation.svg) The identity fields are the ones other systems will try to join on, so they deserve more care than their size on the page suggests.

**Hardware serial and UUID** are what Fleet uses to recognise a returning device, and they are what an asset system will match against. They are reported by the device, which means they are exactly as trustworthy as the device is: virtual machines, cloned images and replaced mainboards can all produce duplicates, and what Fleet does when they collide depends on the enrollment path ([3.1](../03-connect-devices/3.1-enrollment-design-and-host-lifecycle.md)).

**The display name** is assembled for readability and is the wrong thing to automate against. Use the host ID for Fleet's own API and the serial or UUID for anything crossing a system boundary.

**Operating system** arrives as a name, a version and a platform token, and the token is the one that matters, because it is what policies and reports are scoped against. Fleet's platform vocabulary does not always match the marketing name: a Fedora host reports its platform as `rhel`, which is why a rule written against the platform behaves differently from one written against the OS name ([3.4](../03-connect-devices/3.4-enroll-linux-devices.md)).

**Network interfaces** come from a per-platform query and give you the addresses the host itself can see. A host behind NAT reports its private address, so an address in Fleet is evidence about the host's own view of the network rather than about how you would reach it.

## Users and device mappings answer different questions

![Explanation](../_assets/icons/explanation.svg) Two parts of the host record look like "who uses this machine" and are not the same thing.

**Host users are local accounts on the device.** Fleet collects them with a platform-specific query and filters the result deliberately: accounts of type `special`, accounts whose shell is `false`, `nologin`, `shutdown` or `halt`, Windows machine accounts ending in `$`, and macOS system accounts beginning with an underscore are all excluded. So the list is closer to "accounts a person could log in with" than to "every row in the users table", and a service account you were looking for may be absent by design.

Collecting them at all is a feature flag, `enable_host_users`, which is on by default. A deployment that turned it off shows an empty list on every host, which reads exactly like a collection failure.

**Device mappings are email addresses associated with the host**, and Fleet records which source each came from:

| Source | What it means |
|---|---|
| `google_chrome_profiles` | Chrome profiles observed on the device |
| `mdm_idp_accounts` | The identity that authenticated during MDM enrollment |
| `idp` | Set deliberately through the API |
| `custom_installer` | Set by fleetd through the device-authenticated API |
| `custom_override` | Set deliberately by an administrator, taking precedence over the rest |

The distinction matters when you are answering "whose laptop is this". A Chrome profile is evidence that somebody signed into a browser. An `mdm_idp_accounts` entry is evidence that somebody authenticated at enrollment. They can disagree, and Fleet shows you both rather than choosing.

## Certificates

![Explanation](../_assets/icons/explanation.svg) Fleet collects the certificates present on macOS and Windows hosts, through detail queries of their own, and stores them as a per-host list you can read like any other inventory.

This is a part of the host record that is easy to leave out of planning, and it answers questions nothing else in the record can: which hosts still trust a certificate authority you are retiring, which have a certificate expiring inside the month, whether a certificate you deployed actually arrived.

It also goes out of date more quietly than most, because a certificate's presence changes without anything else on the host changing. Read it against `detail_updated_at` rather than against the host's online state.

## What each platform actually populates

![Reference](../_assets/icons/reference.svg) This is the table to carry into every later chapter in this part, because a reading that is sound on a Mac can be meaningless on an iPhone.

| Platform | Where host data comes from | What not to expect |
|---|---|---|
| macOS, Windows, Linux | osquery, through Fleet's detail queries | Nothing structural; this is the full reading surface |
| iOS, iPadOS | The enrollment exchange, then device information fetched over MDM on a schedule | No osquery, so no arbitrary queries, no local users, no scheduled reports |
| Android | Status reports from Google's management API, populating hardware, OS, storage and timing fields | No osquery, no live reports, no scheduled reports |
| ChromeOS | The *Fleetd for Chrome* extension's own virtual tables, answered over the ordinary distributed endpoints | No osqueryd, a much smaller table set, and **no scheduled reports at all**, because the extension never posts to the logging endpoint |

**The trap is that the host page looks much the same for all four.** An iPhone and a Mac both show identity, OS and software; only one of them can be asked a question you thought of yourself. When a report "returns nothing" for a set of hosts, check what those hosts are before checking anything else ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)).

## Reading absence correctly

![Troubleshooting](../_assets/icons/troubleshooting.svg) An empty field is the least informative thing on the page, and it is easy to read more into it than it carries. These are the readings worth separating.

| What you see | What it is consistent with |
|---|---|
| A field is empty and `detail_updated_at` is recent | The host answered and had nothing to report. This is a real observation |
| A field is empty and `detail_updated_at` is old | Nobody has asked recently. This is not an observation at all |
| A whole category is empty on every host | A feature flag, most likely `enable_host_users` or `enable_software_inventory`, rather than a collection failure ([4.4](4.4-understand-software-and-vulnerabilities.md)) |
| A whole category is empty on one platform | Usually correct, and usually the table above rather than a fault |
| A field is empty on one host and populated on its neighbours | The interesting case, and the only one here worth investigating as a fault ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)) |

**The host record does not distinguish "returned no rows" from "could not run".** Both leave the field empty. That distinction lives in the logs, which is why a host quietly failing one detail query looks identical to one that legitimately has nothing to report ([8.2](../08-troubleshooting/8.2-log-surfaces.md)).
