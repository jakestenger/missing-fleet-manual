# Monitor fleet-wide state

Everything so far in this part reads one host, or one question across hosts. This chapter is about the estate: the counts Fleet computes, what each one actually measures, how to cut them into populations you can act on, how to get data out at scale, and how to be told about a problem rather than finding it.

The counts are not as simple as they look. Two of them are the same number under different names, one of them measures something other than what it is called, and they are computed from **different definitions of when a host was last seen**. This chapter is mostly about not over-reading them.

Single-host diagnosis stays in Part VIII.

## The counts, and what each one measures

![Reference](../_assets/icons/reference.svg) Fleet computes a host summary for a scope you choose. Here is what each count is, precisely.

| Count | Definition |
|---|---|
| **Total** | Every host record in scope |
| **Online** | Last seen within `LEAST(distributed_interval, config_tls_refresh)` plus a **60 second** buffer |
| **Offline** | Everything that is not online, by the same expression |
| **New** | Host record **created** within the last 24 hours |
| **Missing** | Effective last seen more than **30 days** ago, excluding hosts pending MDM enrollment |
| **MIA** | Identical to Missing. Deprecated since Fleet 4.15 |
| **Low disk space** | Hosts with available disk below a threshold you supply, **in gigabytes**, 1 to 100 |
| **Per platform** | Total per platform token. Not a status breakdown |
| **Automated enrollment errors** | Apple Business assignments whose response was **failed or throttled** |

Five of those need more than a row.

**Online and Offline do not partition the estate against the other counts.** They partition it against each other, and nothing else. A new host is also online or offline. A missing host is also offline. Adding the counts up produces a number larger than the total, and a dashboard that appears to be showing you slices of a pie is showing you overlapping populations.

**"New" counts record creation, not enrollment.** The count is hosts whose record was created in the last 24 hours. Fleet's own source comment describes this status as hosts that *enrolled* in that window, and the SQL disagrees with the comment. For most hosts these coincide. They come apart when a record is recreated, so a re-enrolling host that was deleted and came back reads as new.

**"Missing" and "MIA" are the same number.** They are byte-identical expressions in the same query, returned under two names. MIA has been deprecated since Fleet 4.15 and is slated for removal in Fleet 5.0. If you are building anything durable, read `missing_30_days_count`.

**Missing excludes hosts pending MDM enrollment.** A host awaiting automated enrollment is never counted missing however long it has been silent, which is correct behaviour and surprising if you are trying to reconcile the number by hand.

**Low disk space is Fleet Premium, and Free does not refuse it.** Ask for it without a licence and Fleet silently drops the parameter, returning a summary with no such count rather than an error. That pattern is worth recognising generally: a Premium capability presenting as an absence rather than a refusal. The threshold is gigabytes of available space, and hosts reporting a negative figure are excluded from the count.

**The automated enrollment error count includes throttling.** It counts Apple Business assignments whose response was failed **or throttled**, over assignments that have not been deleted. Throttling is a rate-limit response and is not the same problem as a rejected assignment, so the count answers "how many assignments are not in a good state" rather than naming a cause ([2.7](../02-administer-and-deploy-fleet/2.7-apple-mdm-configuration.md)).

## The last-seen problem, and what it does to mobile

![Explanation](../_assets/icons/explanation.svg) The single most useful thing in this chapter: **the counts do not agree on when a host was last seen.**

**Online and offline** use the osquery seen time, falling back to the record's creation time if the host has never been seen.

**Missing** uses a wider expression: the greatest of the osquery seen time and the **MDM check-in time**, falling back to the last detail update and then to record creation.

For a host running fleetd these usually agree. For a device that has MDM and no osquery, they cannot. An iPhone, an iPad or an Android device checking in over MDM every day is **permanently offline and never missing**, at the same time, and both numbers are behaving as designed ([4.1](4.1-understand-hosts-vitals-and-inventory.md)).

The practical consequence is that an estate-wide online percentage that mixes agent-managed computers with MDM-only mobile devices is not a health metric. Segment by platform before reading it, or count mobile separately.

## Cutting the estate into populations

![How-to](../_assets/icons/howto.svg) A number for the whole estate is rarely actionable. Three tools narrow it, and they compose.

**Fleets** are the durable scope, and asking for a summary per fleet is the cheapest useful segmentation. Named fleets are Fleet Premium ([1.3](../01-foundations/1.3-hosts-fleets-labels.md)).

**Labels** are the flexible tool, and the right one for a population that crosses fleets or that you expect to dissolve. They come in three kinds, and the difference decides whether a population maintains itself:

- **Dynamic labels** run a query and recompute membership. A host joins and leaves as its answer changes.
- **Manual labels** hold a list of hosts you nominated. Membership changes only when you change it.
- **Host vitals labels** are built from a host attribute rather than a query.

**Filters** on the host list narrow by status, platform, software title, policy result and the presence of an issue.

**Turning an observation into a population is a choice between those three.** If a filter finds a set that matters and the criterion is expressible as a query, a dynamic label keeps it current. If the set is "these specific machines", a manual label is honest about that and a dynamic one would be a fiction. The mistake is building a dynamic label whose query approximates a judgement you actually made by hand.

## Reading agent, enrollment, and management posture

![Explanation](../_assets/icons/explanation.svg) Four fleet-wide questions come up repeatedly, and each is a shape rather than a single number.

**Is the agent healthy everywhere?** The useful figure is not "online" but the gap between online and total, **per platform**, for platforms that run osquery at all. A platform whose offline share diverges from its neighbours' is telling you something structural.

**Is everything that should be MDM-enrolled actually enrolled?** This is a reconciliation, and it is worth doing properly:

1. List hosts filtered to a platform, with no MDM filter. That is the denominator.
2. List the same platform filtered to MDM-enrolled. That is one numerator.
3. The difference is hosts with an agent and no MDM.
4. Now invert it: MDM-enrolled hosts whose osquery seen time is absent or stale are hosts with MDM and no working agent.

The second direction is the quieter of the two, because those hosts still appear in MDM reporting and still receive configuration ([3.2](../03-connect-devices/3.2-enroll-macos-devices.md)).

**Are agent versions converging?** Look for a tail rather than an average. Group hosts by fleetd version and read the oldest few groups by count. [3.7](../03-connect-devices/3.7-manage-fleetd-orbit-and-updates.md) enumerates the causes; what this chapter wants is the count and whether it is shrinking.

**Is anything failing to enroll automatically?** The automated enrollment error count, read as failed-or-throttled rather than as a diagnosis.

## Two kinds of history, and what they cost to turn off

![Reference](../_assets/icons/reference.svg) Fleet keeps historical rollups for two datasets. Both carry traps.

**Uptime history does not record how long hosts have been up.** It records **which hosts were online**, per bucket. The host record does have a boot-duration `uptime` field, and this is not a history of that field. Read it as a presence chart.

**Vulnerability history collects at every severity, over tracked software and OS vulnerabilities.** The critical-only view you see is display-time narrowing, not what was collected ([4.4](4.4-understand-software-and-vulnerabilities.md)).

**Collection is hourly; display is coarser.** Uptime buckets are collected on the hour. The default display resolution for both datasets is **three hours**, so the chart is an aggregate of collection buckets rather than the buckets themselves.

**An empty bucket is not recorded.** When no host is online in a bucket, uptime collection writes nothing at all. A total outage and a period where collection did not run are therefore indistinguishable in the data. This is the one failure mode worth knowing about before you rely on the chart as evidence.

**Turning a dataset off deletes its history.** Disabling collection does not merely stop collecting: it enqueues a scrub job that **removes every collected row** for that dataset, globally if you flipped it globally and for that fleet if you flipped it per fleet. Re-enabling starts from nothing. Treat the toggle as destructive, because it is.

So this is a trend indicator rather than an audit record. It answers "is this getting better or worse". It does not answer "what was true on the fourteenth", and it will not be there to answer it later if somebody toggles the setting ([2.4](../02-administer-and-deploy-fleet/2.4-organization-and-server-settings.md)).

## Reading at scale

![How-to](../_assets/icons/howto.svg) Three routes out, with different strengths and different limits.

**The API** is the route for anything repeated.

- The host summary endpoint returns the counts above for a scope, which is cheaper than listing hosts and counting them.
- Host lists are **paginated**. A script that reads one page and stops is a script that silently reports on your first page of hosts.
- The interface's filters are available as parameters, so a saved investigation becomes a scripted one.
- **Premium-only parameters are dropped rather than refused** on Free, as with low disk space. A script that relies on one will return successfully and be wrong.

**CSV export** hands a population to somebody who does not use Fleet. It exports everything matching the filter rather than the current page, so the filter is the whole of the work.

**`fleetctl`** is the route for a person at a terminal. Note what it is not: it does not retrieve stored report results ([4.2](4.2-run-queries-and-reports.md)), so a script that needs those wants the API.

**All three are bounded by the viewer's scope.** A summary is over the hosts the authenticated identity can see, so the same request run by two people can legitimately return two different totals ([2.3](../02-administer-and-deploy-fleet/2.3-user-accounts-roles-and-service-identities.md)).

**Ask for the narrowest thing that answers the question.** Requesting every host and filtering locally works until the estate outgrows it, and the point where it stops working tends to be an incident rather than a slow script ([8.14](../08-troubleshooting/8.14-degradation.md)).

## Being told, rather than looking

![How-to](../_assets/icons/howto.svg) Fleet can send a webhook when too much of the estate goes quiet. This is the one fleet-wide alert worth configuring first, and it has four properties that decide whether it is useful.

It takes four settings: whether it is enabled, a destination URL, a **percentage of hosts**, and a **number of days**. It fires when the unseen share is **at or above** that percentage, for hosts unseen at least that many days.

**It exists globally and per fleet.** Both are evaluated on each run, so a global webhook and a fleet webhook can both fire for overlapping populations. A failure sending one fleet's webhook does not stop the others.

**Its cadence is shared with the failing policies webhook.** One interval setting drives both. You cannot make host status alerts more frequent without also making policy alerts more frequent ([4.3](4.3-use-policies-for-compliance.md)).

**It re-fires while the condition holds.** There is no state and no de-duplication: every interval where the threshold is met sends another request. Whatever receives it needs to tolerate repeats.

**It uses the osquery seen time only.** Not the wider expression that "missing" uses. An estate with a meaningful share of MDM-only mobile devices will cross the threshold permanently, and the alert will be useless from the day it is enabled. Set the percentage against the population that actually runs an agent.

**The payload contains the full list of unseen host IDs**, alongside the unseen count, the total, the day count, and a message. On a large estate in a bad state that is a large request. Confirm the receiving endpoint tolerates it before relying on the alert.

**It answers exactly one question: has a large share of the estate stopped talking to Fleet.** That is the failure most worth catching automatically, because it makes every other number quietly wrong. It will not tell you about a single important host, and it is not a substitute for policy automation.

## A recurring review

![How-to](../_assets/icons/howto.svg) A sequence that surfaces estate-level problems, written to be repeatable by somebody other than its author.

**Fix the scope before you start.** Global or a named fleet, and the same one every time. A review that silently changes scope produces changes that are not changes.

1. **Total against the last run.** Record the number and the date. Movement has a small set of causes: enrollment, deletion, hosts transferred between fleets, a change in your own access scope, and host expiry if it is enabled.
2. **Online share per platform**, for agent-running platforms only. Compare platforms against each other rather than against an absolute target.
3. **The missing population.** Thirty days of silence is a decision point: recover the host, or retire the record. Check whether host expiry is enabled first, because if it is, records are being retired on a timer and the missing count is bounded by that window rather than by reality ([2.4](../02-administer-and-deploy-fleet/2.4-organization-and-server-settings.md)).
4. **Agent and MDM enrollment gaps**, in both directions, per platform, by the reconciliation above.
5. **Agent version spread**, reading the oldest groups by count.
6. **Policy compliance**, counting the no-answer group rather than only the failures ([4.3](4.3-use-policies-for-compliance.md)).
7. **Known-exploited and critical vulnerabilities**, ordered by host count ([4.4](4.4-understand-software-and-vulnerabilities.md)).
8. **Anything that changed shape** rather than value. A count stable for a month that moved this week is more interesting than one that has always looked wrong.

**Record the decision and the owner, not only the observation.** A review that produces no decision leaves no evidence next month that anything was looked at, and the number it recorded is not reconstructable once the underlying data has rolled over.

## When a number does not make sense

![Troubleshooting](../_assets/icons/troubleshooting.svg) Before treating a surprising count as a fault, rule out the reasons it can be both surprising and correct: the scope you asked about, the viewer's own access, a Premium field silently dropped, a platform whose data does not come from osquery, the fact that missing and offline use different last-seen definitions, and the overlaps between counts described at the top of this chapter.

Aggregates that are cached rather than computed on request, notably policy counts, can also disagree with the host list beneath them for their own refresh interval ([4.3](4.3-use-policies-for-compliance.md)).

Once those are ruled out, an estate-wide problem is a server-state question ([8.6](../08-troubleshooting/8.6-server-state.md)), or a degradation question if it correlates with load ([8.14](../08-troubleshooting/8.14-degradation.md)). A single host behaving oddly was never this chapter's problem ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)).
