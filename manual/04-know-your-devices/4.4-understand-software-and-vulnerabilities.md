# Understand software and vulnerabilities

A vulnerability finding is not an observation. Fleet does not scan your hosts for weaknesses; it matches what it believes is installed against vulnerability data it has downloaded, and every finding is a conclusion drawn from those two inputs.

**When either input is wrong, the conclusion is wrong in both directions.** Incomplete inventory or stale feed data under-reports, and a page with nothing on it reads like good news. Stale inventory over-reports too: software uninstalled a week ago that Fleet still believes is present produces findings for a risk that no longer exists, and time spent on them is time not spent elsewhere. Neither failure announces itself.

So this chapter starts with the inputs.

## Turning software inventory on, and what "off" looks like

![How-to](../_assets/icons/howto.svg) **Whether inventory collection is on by default depends on when your deployment was created.** Fleet enables `enable_software_inventory` for **new installations**. A deployment that existed before that behaviour and upgraded into it does not get it switched on, because Fleet deliberately avoided enabling collection under running fleets during an upgrade. Two servers on the same version can therefore differ, and the difference is their history.

The setting exists at two levels. There is a global value in organization settings, and a fleet can carry its own features block that overrides it for its hosts. So "is inventory on" has to be answered for the scope you are looking at, not once for the server.

To check and change it:

1. Read the global value in organization settings, or through the API's application configuration.
2. Read the features block on each fleet you care about; a fleet that sets its own value wins for its hosts.
3. If you enable it, expect nothing immediately. Hosts pick up the changed query set on their next configuration refresh, and then report software on their next detail pass.

**Turning it off is not the same as deleting what Fleet already has.** Disabling collection stops future gathering and processing; previously stored software rows do not vanish because the switch moved. So an estate that has just had inventory disabled shows old data rather than no data, which is its own kind of misleading.

> ### The setting only reaches the platforms that run osquery
>
> `enable_software_inventory` decides whether Fleet issues the software detail queries. **It is read in one place, on that path, and nowhere else.**
>
> **iOS, iPadOS and Android do not consult it.** Their application inventory arrives over the management channel rather than from a query, and the code that ingests it checks only whether device management is configured. So **an administrator who turns software inventory off still gets iPhone, iPad and Android application inventory**, and will go on getting it.
>
> That matters most where the setting is being used as a privacy control rather than a performance one. If the reason for turning it off is that you should not be holding a list of what is installed on people's devices, **the switch does not achieve that on mobile**, and the only lever that does is turning off the management channel itself.

**Fleet does tell you when inventory is off.** The software surfaces show an explicit disabled state rather than an empty list, so this is not the silent failure it might be. Read that state as "not collecting" rather than as "nothing installed".

**Vulnerability processing depends on the global scheduled job**, so a deployment where that job is not running produces no findings regardless of what inventory says.

## Where software inventory comes from

![Explanation](../_assets/icons/explanation.svg) On hosts running fleetd, Fleet collects software with per-platform queries generated as part of the detail set: separate queries for macOS, Windows, Linux and Chrome, with additional variants for particular Linux package managers.

Coverage is therefore not uniform, and absence in the list is evidence about Fleet's collection rather than proof about the machine. A package manager Fleet has no query for is one whose contents do not appear.

**`software_updated_at` is not a "last successfully collected" timestamp.** Fleet advances it when it **changes** a host's stored software, after an insert or a delete. A host that reports the same software it reported last time leaves the field where it was. So a `software_updated_at` of three weeks ago is consistent with a host that has reported faithfully every hour and simply not installed or removed anything.

**Fleet exposes no host-level timestamp that proves a successful unchanged software refresh.** When you need to know that a host is still reporting, read its check-in and detail clocks instead ([4.1](4.1-understand-hosts-vitals-and-inventory.md)), and treat `software_updated_at` as "when this host's software last changed".

### What the platforms without osquery report

| Platform | Software source | Boundary |
|---|---|---|
| macOS, Windows, Linux | Per-platform osquery queries | The full inventory surface |
| iOS, iPadOS, **company-owned** | Applications reported over MDM | No osquery-derived detail |
| iOS, iPadOS, **personally owned** | Only the apps Fleet manages, not the device's own | A BYOD device does not hand over its personal application list, so absence says nothing |
| Android | Applications from the management API's status reports | Timing follows Google's reporting rather than a Fleet interval |
| ChromeOS | The extension's own virtual tables, which report extensions rather than desktop applications | A Chromebook's "software" is a different category of thing |

**iOS and iPadOS application findings are not supported at this release.** Fleet excludes both from vulnerability matching outright, and says so in its own source, so an empty list for iPhones and iPads is the expected state rather than a clean bill of health.

**Android is different, and the difference is easy to miss.** Fleet does match **Android operating-system vulnerabilities**, through a separate scheduled check that uses a different vulnerability source from the desktop path. It is on by default and governed by its own server setting.

> **Turning that setting off does not remove the Android findings you already have.** It stops the check running, and the cleanup that runs when the setting is disabled removes only the Ubuntu findings from that same source. **Android rows stay where they are**, unrefreshed and unmarked, so the estate goes on showing Android vulnerability data that has stopped being maintained. There is nothing in the interface to distinguish a current Android finding from one frozen at the moment the setting changed.

Android *application* findings are a separate question from OS findings and are not produced.

## Fleet-maintained apps are a catalogue, not an inventory

![Explanation](../_assets/icons/explanation.svg) Two things in Fleet are called software and point in opposite directions.

**Software inventory** is what your hosts report having. **Fleet-maintained apps** are a curated catalogue Fleet ships, describing applications it knows how to install. It is a list of what you *could* deploy and exists whether or not any host has the application.

Reading the catalogue as coverage is the mistake to avoid: a title being in Fleet's maintained list says nothing about how many of your hosts have it. Installing from it is [5.4](../05-manage-devices/5.4-manage-software-and-applications.md)'s subject.

## Two matching pipelines, not one

![Explanation](../_assets/icons/explanation.svg) Fleet produces two kinds of finding and they behave differently.

**Software vulnerabilities** attach to an installed title and version. **Operating system vulnerabilities** attach to the host's OS build, and Fleet tracks them separately, with their own data and their own switches, including one that disables Windows OS vulnerability processing specifically.

The distinction matters at remediation. A software finding is usually fixed by updating a package; an OS finding is fixed by an operating system update, which is a different mechanism, a different approval path and usually a different team.

Fleet draws on several sources rather than one, which is why coverage differs by platform: the National Vulnerability Database, OVAL definitions for Linux distributions, Microsoft's security update data for Windows, a dedicated source for Microsoft Office on macOS, and open-source vulnerability data.

**Matching runs on a schedule**, `vulnerabilities.periodicity`, one hour by default. Neither new software nor a newly published vulnerability is evaluated the instant it appears.

## Five states that all look like "no vulnerabilities"

![Troubleshooting](../_assets/icons/troubleshooting.svg) The vulnerability data has to arrive before it can be matched, and there is more than one way for that not to happen.

| State | What it is |
|---|---|
| **Downloading normally** | Fleet fetches vulnerability data itself. The intended state |
| **Externally provisioned** | Fleet's own download is switched off deliberately, because something else places the data where Fleet reads it. Correct in an air-gapped deployment, and indistinguishable from the next row if the external process stops |
| **Sync failing** | Fleet is trying to download and cannot. Matching continues against whatever it last had |
| **Local data failing to load** | The data is present and Fleet cannot read or parse it |
| **Matching failing** | Data and inventory are both fine and the analysis is not completing |

All five produce a shorter list rather than an error on the page. Confirming which one you are in is a server-state and log question rather than a reading question ([8.6](../08-troubleshooting/8.6-server-state.md), [8.13](../08-troubleshooting/8.13-escalation.md)).

## Supplying vulnerability data to an air-gapped deployment

![How-to](../_assets/icons/howto.svg) The "Externally provisioned" state above is a deliberate configuration: Fleet stops fetching feeds itself and matches against data that something else has placed where it reads. Two settings put it there, and both live in server configuration rather than the interface ([a.3](../09-appendices/a.3-configuration-model-and-precedence.md) holds their defaults and precedence).

`vulnerabilities.databases_path` is the single directory Fleet reads feed data from and writes downloads to, default `/tmp/vulndbs`. `vulnerabilities.disable_data_sync`, set true, stops Fleet reaching out for feeds and has it expect the data to be present in that directory already. The pair is what an air-gapped server needs: no outbound feed traffic, and matching against local files.

To fill the directory, `fleetctl vulnerability-data-stream --dir <path>` performs nine download operations on an internet-connected host: the CPE database and its translations, the NVD CVE feed, the EPSS scores, the CISA known-exploited catalogue, the OVAL definitions, the Microsoft security bulletins, the macOS Office release notes, and the OSV data. Run it where there is internet, copy `<path>` to the server's `databases_path`, and set `disable_data_sync=true`.

**The two settings eliminate direct feed egress, provided `databases_path` has also been populated with every artifact the enabled scanners need.** `disable_data_sync=true` reliably stops the server's own downloads, but the analysers that run afterwards are not gated, so one meeting an empty directory finds nothing to match against. The pre-download command does not mirror everything the server itself fetches: the server's vulnerability job also pulls goval-dictionary databases and the Windows Office bulletin artifacts, and `vulnerability-data-stream` fetches neither. A `databases_path` filled only from that command leaves those two scanners without data, so supply every artifact the scanners you have enabled require, not just the command's nine.

Data supply is one half of advanced operation; the other is who runs the job. Fleet can hand vulnerability processing to an external scheduler instead of its own internal timer, and that is a separate switch from data supply: `disable_data_sync` decides where the data comes from, while disabling the schedule decides who triggers the work. The mechanics of running processing on a dedicated node, and what a stalled trigger looks like, are [8.6](../08-troubleshooting/8.6-server-state.md)'s.

### The vulnerability dashboard is a separate application

![Explanation](../_assets/icons/explanation.svg) Fleet's public repository also carries a vulnerability dashboard. It is a standalone companion web application that reads from a Fleet instance over the public API, configured with a Fleet base URL and an API-only user's token. It is a separate deployable, not part of the Fleet server, and this manual's server chapters neither describe nor depend on it. Its bundled administrator login is created only by a development bootstrap and is absent from a production deployment, and this manual makes no claim about its licensing. Treat it as an external API client that happens to ship in the same repository.

## The enriched fields, and what each edition gets

![Reference](../_assets/icons/reference.svg) Fleet enriches a vulnerability with six things: a **CVSS base score**, an **EPSS probability**, a **CISA known-exploited** flag, the **publication date**, a **description**, and where Fleet has one, a **resolved version**.

**Three of those are prioritisation signals and are Fleet Premium**: CVSS, EPSS and CISA known-exploited. On Free the API **omits those fields entirely** rather than returning them empty.

**A present-but-empty field on Premium is not automatically a fault.** It means no value is available, which may be a synchronisation problem and may simply be a vulnerability for which the upstream source has no score. Check before treating it as an outage.

**Free is not without ranking.** You still have the identifier, the host count, and the detection date, so reach and age remain available as axes. What you lose is severity, exploitation probability and known-exploited status. Filtering and sorting *by* those Premium fields, and the resolved-version display, are Premium too.

**EPSS is a prediction with a horizon.** It estimates the probability that a vulnerability will be exploited in the next thirty days. A low EPSS means the model does not expect exploitation soon; **it is not evidence that nobody is exploiting it**, and it is certainly not evidence about your environment. Keep it distinct from the CISA catalogue, which is a record of observed exploitation, and from anything your own detection tooling is telling you.

## Prioritising a list you can act on

![How-to](../_assets/icons/howto.svg) A workable order, given the signals above.

1. **Known exploited.** Filter to the CISA flag first. It is observation rather than prediction and the shortest list you will get.
2. **Then reach.** Sort by affected host count. This works on both editions and is the axis most often left out of a severity conversation.
3. **Then likelihood and severity together.** EPSS for what is likely to be attacked, CVSS for what would hurt if it were. A moderate score with a high probability can outrank a high score nobody is expected to touch.
4. **Then remediability.** Where Fleet supplies a resolved version, the work is defined. Where it does not, the finding needs research before it needs scheduling.
5. **Drill down before acting.** From a vulnerability, get to the affected titles and versions and then to the hosts, so that what you hand to remediation is a version and a population rather than an identifier.

## Exposure over time

![Explanation](../_assets/icons/explanation.svg) Fleet keeps a limited vulnerability history, alongside the uptime history covered in [4.5](4.5-monitor-fleet-wide-state.md).

**Collection and display are not the same thing, and the difference matters.** Fleet collects vulnerabilities at **every severity**, over a curated set of tracked software **and OS vulnerabilities**. The critical-only chart is narrowed at display time. The data behind the view is therefore broader than the view, and the narrowing is a presentation choice rather than a limit on what was gathered.

Collection runs hourly. The default display resolution is three hours, so a point on the chart aggregates several collection buckets.

**The administrator-facing view of it is Fleet Premium.** The chart endpoint behind it has authorization but no separate licence check at this release, so the accurate statement is that the interface gates it rather than that the route rejects Free.

**Turning the dataset off deletes what it has already collected.** Disabling vulnerability history enqueues a scrub that removes every stored row for the dataset, rather than simply stopping collection. Re-enabling starts from nothing. [4.5](4.5-monitor-fleet-wide-state.md) covers this for both datasets.

Read it as a trend indicator rather than as an audit record. It answers "is our critical exposure on this software going up or down" and does not answer "what were we exposed to on a given date".

## Handing a finding to remediation

![Explanation](../_assets/icons/explanation.svg) Part IV ends where the fix begins, and what belongs here is a clean handover.

**For a software finding**, the handover is a title, a version and a population. Where Fleet supplies a resolved version, that is the target; where it does not, somebody has to establish one before the work can be scheduled. Delivery is [5.4](../05-manage-devices/5.4-manage-software-and-applications.md)'s.

**For an OS finding**, the handover is an operating system version, and the mechanism is OS updates rather than software installation ([5.6](../05-manage-devices/5.6-control-operating-system-updates.md)).

**A patch policy turns a one-off check into a standing one** ([4.3](4.3-use-policies-for-compliance.md)). Note its boundary: it is built from a Fleet-maintained app and is Premium, so it is not available for arbitrary titles or on Free.

**Expect a lag, and expect it to differ by platform.** After a fix, the host's software has to change and be reported, then the hourly vulnerability match has to run again. On desktop platforms the reporting interval is configurable, so your own deployment's settings decide the first half of that. On mobile, timing follows the management channel rather than any Fleet interval. A finding that persists for an hour after a successful fix is ordinary; one that persists for a day is worth asking about.
