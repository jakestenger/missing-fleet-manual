# Understand software and vulnerabilities

Vulnerability data is the most consequential thing Fleet shows you and the most conditional. Every finding on the page is a conclusion drawn from two inputs: what Fleet believes is installed, and what Fleet's vulnerability feeds say about it. If either is incomplete, the conclusion is wrong in the direction that looks like good news.

So this chapter starts with a question that is not about vulnerabilities at all.

## First, verify that software inventory is on

![Troubleshooting](../_assets/icons/troubleshooting.svg) **Software inventory can be switched off, and whether it is on by default depends on when your deployment was created.**

Fleet turns `enable_software_inventory` on for **new installations**. A deployment that predates that behaviour and upgraded into it does not get it switched on, because Fleet deliberately did not enable inventory collection under existing fleets during an upgrade. So two servers running the same version can differ, and the difference is their history.

**An estate with software inventory off produces an empty software list and no vulnerabilities at all.** Not an error, not a warning: a clean page that reads exactly like an estate with nothing installed and nothing wrong. It is the single most dangerous default in this part of Fleet, and checking it takes a moment.

Check the setting before you interpret anything else in this chapter. If a host shows no software and its neighbours do, that is a different question ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)); if the whole estate shows none, look here first.

## Where software inventory comes from

![Explanation](../_assets/icons/explanation.svg) On hosts running fleetd, Fleet collects software with per-platform queries, generated as part of the detail set: separate queries for macOS, Windows, Linux and Chrome, with additional variants for particular Linux package managers.

That per-platform construction is worth knowing because coverage is not uniform. What counts as "installed software" differs by platform, and a package manager Fleet does not have a query for is a package manager whose contents do not appear. Absence in the list is evidence about Fleet's collection, not proof about the machine.

**Software carries its own clock.** The host record has `software_updated_at`, separate from `detail_updated_at` and from `seen_time` ([4.1](4.1-understand-hosts-vitals-and-inventory.md)). It advances when Fleet finishes reconciling that host's software, so a host can be online, have recent host details, and have a software list from some hours ago. When judging whether a vulnerability finding is current, this is the timestamp to read.

**On platforms without osquery, software comes from the management channel instead.** iOS, iPadOS and Android report installed applications through MDM and the Android management API respectively, which is a different inventory with different fields and different timing ([4.1](4.1-understand-hosts-vitals-and-inventory.md)).

## Fleet-maintained apps are a catalogue, not an inventory

![Explanation](../_assets/icons/explanation.svg) Two things in Fleet are called software and mean opposite directions.

**Software inventory** is what your hosts report having.

**Fleet-maintained apps** are a curated catalogue Fleet ships, describing applications it knows how to install, with the metadata needed to deliver and update them. It is a list of what you *could* deploy, and it exists whether or not any host has the application.

Confusing the two produces a specific mistake: reading the catalogue as coverage. A title being in Fleet's maintained list says nothing about how many of your hosts have it. Installing from the catalogue is Part V's subject ([5.4](../05-manage-devices/5.4-install-software-with-fmas-and-custom-packages.md)).

## How a vulnerability finding is produced

![Explanation](../_assets/icons/explanation.svg) Fleet does not scan hosts for vulnerabilities. It matches the software it believes is installed against vulnerability data it has downloaded, and the finding is the product of that match.

Fleet draws on several feeds rather than one, which is why coverage differs by platform and why a title can be well covered on one operating system and thinly covered on another. Among them are the National Vulnerability Database, OVAL definitions for Linux distributions, Microsoft's security update data for Windows, a dedicated source for Microsoft Office on macOS, and open-source vulnerability data.

**The matching runs on a schedule**, `vulnerabilities.periodicity`, one hour by default. A newly reported piece of software is not evaluated the instant it appears, and a newly published vulnerability is not applied to your estate the instant it is published.

**The feeds have to be downloadable.** Fleet syncs this data, and a deployment that has disabled that sync, or cannot reach the sources, keeps matching against whatever it last had. That produces the same clean page as having no vulnerabilities, so an air-gapped or egress-restricted deployment should confirm the sync is working rather than inferring health from an empty list ([2.9](../02-administer-and-deploy-fleet/2.9-self-hosting-architecture-and-capacity.md)).

## What the severity fields are, and who gets them

![Reference](../_assets/icons/reference.svg) Fleet attaches three pieces of metadata to a vulnerability, and they answer different questions.

| Field | What it tells you |
|---|---|
| **CVSS base score** | How severe the vulnerability is in the abstract, from 0 to 10 |
| **EPSS probability** | How likely it is to be exploited, as a probability, which is a different question from how bad it would be |
| **CISA known exploited** | Whether it is on the catalogue of vulnerabilities known to have been exploited in the wild |

**All three are Fleet Premium.** They are not merely hidden on Free: the API **omits the fields entirely** rather than returning them empty, and Fleet distinguishes that omission from a Premium deployment where the field is present but has no value because the score data has not synced. So on Free you get the vulnerability identifiers and not the means to rank them.

**That distinction matters when reading the API.** A missing field means Free. A present-but-null field means Premium with no score available, which is a sync problem rather than a vulnerability with no severity.

## Prioritising without drowning

![How-to](../_assets/icons/howto.svg) A vulnerability list of any size is unusable as a list. These are the axes Fleet gives you to turn it into work.

**Known exploited first.** The CISA catalogue is the strongest signal Fleet carries, because it is evidence rather than prediction: somebody has actually been attacked through it.

**Then probability, not just severity.** A high CVSS score with a very low EPSS probability describes something dangerous that nobody is exploiting; a moderate score with a high probability may be the more urgent piece of work. Reading only CVSS sorts by how bad it *would* be and ignores how likely it is.

**Then reach.** A vulnerability on three hosts and a vulnerability on three thousand are different pieces of work regardless of score, and host counts are the axis most often left out of a severity conversation.

**Then remediability.** Some findings are fixed by an update you can deploy today; others need a version that does not exist yet. Sorting a list you cannot act on wastes the attention you have.

## Reading a finding honestly

![Troubleshooting](../_assets/icons/troubleshooting.svg) Before treating a vulnerability figure as a statement about the estate.

| Question | Why it matters |
|---|---|
| Is software inventory **on**? | If not, the whole page is empty for a reason unconnected to your security posture |
| When did this host's software **last update**? | `software_updated_at`, not `seen_time`. A stale inventory produces stale findings in both directions |
| Are the vulnerability feeds **syncing**? | Matching against stale data looks identical to matching against clean software |
| Does this platform have **good coverage**? | Feeds differ by operating system, so a quiet platform may be under-covered rather than healthy |
| Is this a **false positive**? | Version-based matching produces them, particularly where a distribution backports a fix without changing the version string |
| Am I on **Free**? | Then there are no severity, probability or exploitation fields to prioritise with |

**Version matching produces false positives**, and Linux distributions are where the mechanism is clearest: a distribution that patches a package while keeping its version number looks vulnerable to a matcher that reads versions. Fleet's Linux definitions reduce this, and they do not eliminate it. Treat a finding on a backporting distribution as a question rather than a conclusion.

**And absence is never proof.** No vulnerabilities can mean a clean estate, inventory switched off, a feed that has not synced, a platform Fleet covers thinly, or a title Fleet's data does not describe. The list tells you what Fleet matched, not what is safe.

## Handing a finding to remediation

![Explanation](../_assets/icons/explanation.svg) Part IV ends where the fix begins. What belongs here is the handover, and the handover is the version.

A vulnerability finding names a title and a version on a set of hosts. The remediation is a version bump, delivered by the mechanisms in Part V ([5.4](../05-manage-devices/5.4-install-software-with-fmas-and-custom-packages.md)), and the check that it worked comes back here: the same hosts, reporting a new version, on their own software clock.

**A patch policy is the durable form of that check** ([4.3](4.3-use-policies-for-compliance.md)). Rather than confirming a fix once, it asserts the required version continuously, and it carries the trap that chapter names: a host without the software at all is not failing to be patched.

**Expect a lag in both directions.** After remediation, the host's software inventory has to refresh before Fleet knows, and then the vulnerability match has to run again before the finding clears. Two hourly clocks, plus whatever the host's own check-in interval adds. A finding that persists for an hour after a successful fix is ordinary, not evidence that the fix failed.
