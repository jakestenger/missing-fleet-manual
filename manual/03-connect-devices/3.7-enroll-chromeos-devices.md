# Enroll ChromeOS devices

![Explanation](../_assets/icons/explanation.svg) The ChromeOS agent is **Fleetd for Chrome**, a browser extension sharing fleetd's name and nothing else: no Orbit, no osqueryd, no Fleet Desktop. It reports against eleven tables it implements itself, and it is deployed and configured the way any managed extension is, through extension policy in the Google Admin console. The prerequisite is a managed Chrome estate; management of the device itself stays in Google's console, not Fleet.

## ChromeOS: an extension, and only on ChromeOS

![Explanation](../_assets/icons/explanation.svg) Fleet does not manage ChromeOS. Google's console does. What Fleet gets is a reporting agent, and that agent is a Chrome extension deployed the way you deploy any managed extension.

No MDM, no enrollment profile, no package. Two things have to be true:

1. **The extension is force-installed** on the ChromeOS devices you want, from Fleet's published update URL.
2. **Its policy carries `fleet_url` and `enroll_secret`.** The extension reads both out of Chrome's managed storage, which is to say out of the extension policy set in the Google Admin console. That is the entire configuration. The enroll secret places the host exactly as it does on the fleetd path, **which means it places a genuinely new host and does not move one Fleet already knows** ([3.1](3.1-enrollment-design-and-host-lifecycle.md)). Repointing the policy at another fleet's secret does not by itself move anything, and does not by itself re-enrol anything: the extension enrols when it has no node key, and re-enrols when a request is refused. A host that already holds a node key carries on where it is.

### Doing it

![How-to](../_assets/icons/howto.svg) Open **Add hosts**, choose **ChromeOS**, and Fleet gives you three things to paste into the Google Admin console: the **extension ID**, the **installation URL** of Fleet's update manifest, and a small **policy JSON** carrying `fleet_url` and `enroll_secret` already filled in for your server and the fleet you selected.

In Google Admin, scope those to the organisational unit you want and set the extension to **force install**. That is the whole of the deployment: there is nothing to run on the device and nothing to build.

**The policy JSON contains an enroll secret**, so treat the paste like the credential it is, and remember that it then lives in Google's console rather than in Fleet.

**The Fleet URL has to present a certificate the device already trusts.** There is no equivalent of packaging your own certificate authority into the agent here.

**It refuses to run anywhere but ChromeOS.** The extension checks the platform at startup, logs an error saying it will not run on a non-ChromeOS device under a managed install, and stops. So pushing it to your users' desktop Chrome browsers produces no Fleet host and leaves a message in the service-worker console. Whether anything is visible to the person at the machine is Chrome's business rather than the extension's, since a force-installed extension appears in the browser either way. A development install is the only exception.

### What ChromeOS can actually answer

This is worth being exact about, because the platform table's row of **no**s reads as though nothing can be asked.

**Live reports work.** The extension enrols at the ordinary osquery enrollment endpoint with the enroll secret and the device's serial number, then polls the same distributed read and write endpoints a real osquery agent uses. **It does this without running osqueryd**, which is the distinction to hold: Fleet's distributed channel is in use, osquery is not ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)).

**Against a virtual database, not osquery.** There is no osqueryd here. The extension runs as a Manifest V3 service worker, and its database is SQLite compiled to WebAssembly and held in memory, with **eleven tables of its own**, and this is all of them: `chrome_extensions`, `disk_info`, `geolocation`, `network_interfaces`, `os_version`, `osquery_info`, `privacy_preferences`, `screenlock`, `system_info`, `system_state`, `users`.

Most are backed by Chrome's own APIs, and not all of those are enterprise ones: `disk_info` reads Chrome's storage API and **`geolocation` calls an external web service**, which is worth knowing before you run it across an estate.

**A query naming a table that is not there fails; it does not come back empty.** The extension catches the SQLite error and returns a status of 1 with the message, so Fleet shows the host as failing that report rather than as having nothing to say. That distinction matters because an empty result and an error mean opposite things about the host ([8.7](../08-troubleshooting/8.7-live-query-introspection.md)).

**It polls on its own clock, every ten seconds.** The main loop reschedules itself on a ten-second timer; the one-minute alarm people notice in the manifest exists to stop Chrome suspending the service worker, not to drive the cycle. Fleet's own host page reports the ChromeOS distributed interval as ten seconds and it is not configurable, so `distributed_interval` and the rest of osquery's agent options do not reach these hosts.

**Scheduled reports do not work**, because the extension never posts to the logging endpoint. There is no result or status stream from a Chromebook.

**Fleet's server queries these hosts too, not only you.** The same distributed channel carries the server's own detail queries. Fleet asks a ChromeOS host for its operating-system version and system information, its network interface, its installed Chrome extensions (which is what software inventory means on this platform), the signed-in Google account, and the host's users, and it fills the host's vitals and software inventory from the answers. It also evaluates the built-in **`chrome` label**, whose membership is the query `SELECT 1 FROM os_version WHERE platform = 'chrome'`, which gives you a ready-made filter for scoping the estate to Chromebooks. The account comes from the `chromeos_profile_user_info` query reading the `users` table, whose single row carries the Chrome profile ID as `uid` and the account email as both `username` and `email`.

**Policies run, but remediation is Google's.** Fleet sends compliance policies over the same distributed read, the extension answers them from the eleven tables, and Fleet ingests the results, so a policy tells you whether a Chromebook is compliant. Acting on that answer is where the platform stops. Fleet does not manage a ChromeOS device, so alongside the missing log stream there are no scripts, no software installation, no MDM commands, and no agent-side remediation. What Fleet has here is read-only reporting over the live channel, and every change to the device is made in Google's console.

### Keeping the extension current

![How-to](../_assets/icons/howto.svg) The extension updates the way any managed Chrome extension does. **Chrome manages the update, and Fleet hosts the update manifest and the package**, which is the split to hold onto: this is not the agent updater built on The Update Framework (TUF) that services fleetd on the other platforms, so there is nothing to schedule in Fleet and nothing to run on the device.

Fleet's extension documentation describes the cadence as roughly once a day, with two manual levers when you need a version sooner: the **Update** button on `chrome://extensions`, or toggling the extension policy from Block back to Force install to force a fresh pull. Those are documented behaviours rather than something this manual verified against the release, so treat the timing as guidance, not a guarantee.

The version on the host, reported as `fleetd-chrome-<version>` by the `osquery_info` table, is the extension's version, and it moves independently of your Fleet server version. A Chromebook sitting on an old extension version is one that has not taken an update, and the two levers above are how you push it.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) A ChromeOS enrollment is verified from Fleet first, because the extension gives you no shell.

The clearest confirmation is a live report the host answers now. `SELECT * FROM os_version` is a small confirmation query, and a result coming back proves the whole distributed path is working. Host vitals on their own are weaker evidence, because a host's first `os_version` and `system_info` arrive with the enrollment itself, so their presence does not prove a later check-in. Recently refreshed software or host details do, and so does a live query that returns. A Chromebook that keeps answering also keeps its agent last-seen time current, because every authenticated request on the distributed channel records it.

## Diagnosing a ChromeOS enrollment

![Troubleshooting](../_assets/icons/troubleshooting.svg) When a device has the extension installed and no host appears in Fleet, the one diagnostic instrument on the device is the extension's **service-worker console**. Reach it from `chrome://extensions` with developer mode on, through the extension's service-worker link, the path Fleet's own extension documentation describes. There is no shell, no log file, and no fleetctl route to the device: the console, and the extension policy in Google Admin that feeds it, are what you have.

A missing host has not necessarily failed at the network. Before it makes a request the extension can refuse the platform, fail to initialise its database, or hit warnings building the details it enrols with. On the wire it can then fail to reach the URL, fail to verify the certificate, or be refused the secret. Some of those separate cleanly at the console and some collapse into one generic request failure. Check the policy value in Google Admin and the certificate on the Fleet URL before you reach for the firewall, because a value that never arrived at the extension can look, at the console, much like one the extension could not use.

| What you observe | What it means, and what to check next |
|---|---|
| A platform refusal is logged and no host appears | The extension was force-installed to desktop Chrome rather than ChromeOS, and it stops at startup. Move the policy to a ChromeOS organisational unit. |
| Per-column warnings from `system_info` for the hardware model or vendor | The policy-gated hardware platform API was unavailable, usually because `EnterpriseHardwarePlatformAPIEnabled` is not set. Vendor and model are read only through that API; the host still enrols without them. |
| Per-column warnings from `system_info` for the serial or hostname | A device attribute read through the enterprise device-attributes API was unavailable. That API is separate from the hardware-platform policy above, so `EnterpriseHardwarePlatformAPIEnabled` is not the cause here. The host usually still enrols, under its UUID when the serial is missing, so the warning is not by itself an enrollment failure. |
| A request or fetch failure, and no host | The Fleet URL is unreachable, its certificate is not trusted, or the configured URL is invalid or empty. These do not fully separate at the console. Confirm the URL and its certificate, and the policy value in Google Admin. |
| Enrollment rejected with a server message such as `no matching secret found` | The `enroll_secret` in the extension policy is wrong for this server. Repaste it from **Add hosts**. |
| An empty node key error | Fleet accepted the enrollment and returned no node key. That is a server-side anomaly rather than a policy or network fault. |
| A node-invalid response | Fleet rejected the host's node key, usually because the host was deleted or transferred. The extension clears the key and re-enrols, and Fleet may match an existing host or place a new one. |
| The database fails to initialise, then restarts | A rare in-memory database fault that the worker recovers from by re-initialising. Repeated faults are worth reporting. |
| A report shows as failing rather than empty | A query named a table the extension does not implement, or a Chrome API errored, so its status is 1. Failing and empty mean opposite things: the first is an error, the second is a host with nothing to report. |

A host that appears but sits on an old extension version has an update problem rather than an enrollment one; see [Keeping the extension current](#keeping-the-extension-current).

## Who owns it afterwards

**The Chrome extension policy**, which lives in Google's console rather than in Fleet. Nobody looking at Fleet can see it, and it holds an enroll secret.
