# Manage fleetd, Orbit, and updates

Once fleetd is installed it keeps itself current without being asked, unless it was told not to. What it updates to is decided by a channel rather than a version number, and changing that channel **centrally, without touching each host**, is a Fleet Premium capability; changing it on a host is a flag or an environment variable and costs nothing.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers what fleetd is made of, how its components decide which version to run, how often they check, and how to see what a host is actually running. Getting fleetd onto a device in the first place is [3.1](3.1-enrollment-design-and-host-lifecycle.md) and the platform chapters before this one.

[1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) establishes the channels fleetd talks over. This chapter is about the agent itself rather than its traffic.

## What fleetd contains

![Reference](../_assets/icons/reference.svg) fleetd is a bundle rather than a program, which is why a sentence like "fleetd and osquery" reads oddly until you know what sits inside what.

| Component | What it does |
|---|---|
| **osquery** | Answers questions about the machine |
| **Orbit** | Manages osquery's version and configuration, and performs host-side work such as installing software and running scripts |
| **Fleet Desktop** | The end-user-facing surface. **Optional**, included by `fleetctl package --fleet-desktop` |

**ChromeOS is not in this bundle and not in this chapter.** *Fleetd for Chrome* is a separate browser extension carrying none of the components above; **Chrome** updates it, from an update manifest Fleet publishes, rather than Orbit updating it from the TUF repository. So channels, update intervals, retry cooldowns and agent options apply to it not at all, and its version moves when Chrome decides ([3.7](3.7-enroll-chromeos-devices.md)).

**Fleet Desktop is an optional component of the bundle**, which Fleet's own architecture documentation describes exactly that way, and `fleetctl package --fleet-desktop` puts it in the package. It is the end-user-facing piece and it is a packaging choice rather than a given, so a deployment can have fleetd everywhere and Fleet Desktop nowhere.

Orbit is the part worth understanding, because it is what makes the rest self-managing. It decides which osquery to run, fetches it, and replaces itself when a new Orbit is published.

## How a version gets chosen

![Explanation](../_assets/icons/explanation.svg) Orbit, osquery and Fleet Desktop each follow an update channel, and a channel is a standing instruction rather than a pinned version.

A channel is a path in the update repository, and Fleet publishes two kinds. It is not a closed set: Fleet accepts an arbitrary channel name in agent options, and an organisation running its own repository can publish whatever tags it likes, which `fleetctl updates add` will do for it on macOS and Linux, the platforms that command supports; it declares the Fleet EE licence in its own help and requires an EE subscription, rather than carrying a Premium validation of the kind `update_channels` has. What follows is the conventional set Fleet itself publishes.

Three prefix forms, each narrower than the last:

1. `4` tracks any `4.x.x`.
2. `4.6` tracks any `4.6.x`.
3. `4.6.0` pins that exact version.

And two named tracks, `stable` and `edge`, which are not version prefixes at all.

The distinction between the two named tracks is a real release process rather than a label. A new osquery version lands on `edge` for beta testing, Fleet tests it and feeds results back to the osquery technical steering committee, and once that committee declares the version stable Fleet promotes it to `stable`.

So `stable` means the most recent osquery version Fleet considers stable, which moves. **A prefix moves too**: `4` follows every `4.x.x` and `4.6` follows every `4.6.x`. Only the full three-part version pins a component to something that does not move.

Channels are set with `--orbit-channel`, `--desktop-channel` and `--osqueryd-channel` when the installer is built.

## Changing channels after deployment

![How-to](../_assets/icons/howto.svg) **Changing a channel centrally requires Fleet Premium.** The `update_channels` block in agent options sets them for `orbit`, `osqueryd` and `desktop` across an estate, and Fleet Free rejects the block with a licence error. What Free still has is the per-host route: Orbit reads `--orbit-channel`, `--osqueryd-channel` and `--desktop-channel`, and the matching `ORBIT_*_CHANNEL` environment variables, so a channel can be changed on a host by editing its service configuration and restarting. That is a per-host operation, which is exactly what Premium buys you out of.

```yaml
agent_options:
  update_channels:
    orbit: stable
    osqueryd: '5.10.2'
    desktop: edge
```

**Remote channel configuration needs fleetd 1.20.0 or later.** Older agents ignore the block entirely and stay on whatever they were packaged with, which looks identical to a change that did not apply. And Fleet documents a hazard when crossing that boundary downwards: a packaged channel and a server channel that disagree across it can put Orbit into a restart loop. An estate old enough to be affected by the 1.38.1 stepping stone below is old enough to be affected by this.

That block sits directly under `agent_options` rather than under `config`, unlike the osquery options in [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md). The rule behind the difference is that Fleet passes `config` through to osquery, and reads everything else itself.

**Agent options win over what the installer was built with, including downwards.** Fleet's documentation is explicit that an agent generated at one version will move to the version the channel specifies even when that means downgrading. A package built at Orbit 1.53.1 enrolling into a deployment whose `update_channels.orbit` says 1.50.0 will end up on 1.50.0.

That makes agent options the lever for a rollout ring: point a pilot fleet at `edge` or a newer prefix, leave everything else on a fixed version, and move the rest once the pilot has run long enough to mean something.

**Two things to know before building one.** A host in a fleet gets **that fleet's agent options instead of the global ones**, not merged with them, so a pilot fleet's options have to carry every other option those hosts need and not only `update_channels`. And writing agent options at either scope is an administrator or GitOps operation; the read-only and technician roles cannot do it ([1.4](../01-foundations/1.4-identity-and-roles.md)).

## How often fleetd checks

![Explanation](../_assets/icons/explanation.svg) Two different clocks are at work, and confusing them leads to waiting on the wrong one.

**A channel change you make in Fleet travels fast**, and it does so by a route worth knowing, because it is the reason the two clocks do not both apply. Orbit polls Fleet for its configuration roughly every thirty seconds, **unless its recent configuration cycles have been erroring**: from fleetd 1.58.0 a run of failures backs the interval off exponentially with jitter, up to a five-minute ceiling, and a single success returns it to thirty seconds. Any error from that cycle triggers the backoff, including a failure applying the configuration it just received, not only a server or network error. So a change made while Fleet was unhealthy can take several minutes longer to land than a change made while it was not.

A new `update_channels` value is written to disk and triggers an Orbit restart, and **the restart performs an update check before it starts anything else**: Orbit does that early check first, deliberately, so that a bug in another subsystem cannot interfere with fetching an update. If the update is to Orbit itself, it exits and comes back on the new binary. So the gap between saving a channel change and the host acting on it is **one configuration poll plus the time to download and restart**, and the poll is the part that varies.

**Finding new content on a channel you are already following is the slower loop.** After that startup check, the update runner waits: the next check is one `update-interval`, which defaults to fifteen minutes, plus a random amount so agents do not all reach the update server together. The randomisation is capped at the smaller of the interval and ten minutes, so at the default it is up to ten and a deployment that shortened the interval gets proportionally less. On a large estate that spread is the difference between a rolling update and a stampede.

**Both of those depend on updates being enabled at all.** An agent packaged with updates disabled performs no startup check and runs no update loop, so neither clock applies to it and a channel change reaches it and does nothing.

**A failing download backs off, and the backoff is narrower than it first appears.** Orbit retries up to three consecutive times, then waits 24 hours before trying that same thing again. The retry count and the cooldown are tracked **per target**, keyed by the artifact's hash, rather than for the agent as a whole. One consequence is genuinely useful: publishing a corrected build creates a new target, which is not subject to the old one's cooldown, so a fix can reach hosts without waiting out the day.

**Do not draw the other consequence that per-target keying seems to invite.** It is tempting to read it as "one broken artifact is not silenced for everything else", and that is wrong. The runner walks its targets in a fixed order, Orbit first, then osquery, then Desktop when it is installed, and it returns from the whole pass as soon as one target's lookup or update fails. So while the *cooldown* is per target, the *pass* is not: a target that keeps failing prevents the ones behind it from being examined at all. A bundle where osquery and Desktop are both stale behind a stuck Orbit is one problem wearing three faces.

**Restarting the agent clears the cooldown too.** The retry counts live in memory rather than on disk, so a new Orbit process starts with none. That makes an agent restart a reasonable first move on a single stuck host, and it is the reason a host can look fixed after a reboot without anything else having changed.

## The update server moved, and old agents cannot cross the gap

![Troubleshooting](../_assets/icons/troubleshooting.svg) Fleet moved its update server from `tuf.fleetctl.com` to `updates.fleetdm.com`, and the current default in the agent is the new address.

**Orbit versions below 1.38.1 cannot upgrade directly to a current release.** 1.38.1 itself is the exception and the way across.

> **The migration code is in 1.38.0 and the version to step through is 1.38.1.** Both releases carry the change to the new update server, three days apart, and Fleet's own configuration reference names 1.38.1 as the bridge. Fleet also shipped a rollback to the old server with 1.38.0 in case it needed one, and removed it afterwards. **Use 1.38.1**: the difference costs nothing and the documented number is the one Fleet supports. They look for files at an address that no longer serves them, and the symptom in the Orbit logs is specific enough to identify without guessing:

```
update failed error="lookup failed: lookup orbit: tuf: file not found
```

The route across is to upgrade to 1.38.1 first, wait for agents to reach it, then upgrade to the version you actually want. An estate carrying agents old enough to be affected needs two rollouts rather than one, and a channel pointed straight at a modern version will leave those hosts stranded rather than failing loudly.

## Running your own update repository

![How-to](../_assets/icons/howto.svg) An organisation that cannot reach `updates.fleetdm.com`, that ships its own osquery extensions, or that wants to pin in-house builds can run its own update repository and point fleetd at it instead. `fleetctl updates` builds and maintains that repository. Every subcommand works on a local directory named by `--path`, and none of them contacts a Fleet server, so this is a signing-and-publishing workflow on a build host rather than anything your Fleet instance mediates.

It is a macOS and Linux command; on Windows the whole family is a single entry that refuses and tells you to use a Linux environment. And its help text declares the Fleet EE licence, while nothing in the command checks a licence at runtime, because with no Fleet server in the loop there is nothing to check one against. Read that line as a subscription statement, which is how [a.2](../09-appendices/a.2-platform-capability-matrix.md) records it.

**Five subcommands, run in this order the first time.**

`fleetctl updates init` creates the repository and the four signing keys it needs, one each for the root, targets, snapshot and timestamp roles. Each key is encrypted with its own passphrase, taken from a `FLEET_<ROLE>_PASSPHRASE` environment variable or an interactive prompt. It refuses to run when a repository or a `keys` directory already exists, so it never overwrites key material you already have.

`fleetctl updates roots` prints the repository's root metadata. That is the trust anchor a host pins so it will accept everything else the repository serves, so capture its output: you hand it to the agents you build below.

`fleetctl updates add` publishes one artifact. It takes `--target`, `--name`, `--platform` and `--version`, and any number of repeatable `--tag` values, copies the file into the repository under the layout fleetd expects, and signs the new metadata. The tags are the channel names hosts follow, so this is where your own `stable`, `edge` or a pinned version comes from, the same channels described in [How a version gets chosen](#how-a-version-gets-chosen) above.

`fleetctl updates timestamp` re-signs the repository's timestamp metadata and nothing else. It exists because that metadata expires 14 days after it is generated, and an expired timestamp makes clients reject the whole repository as stale even when every artifact in it is current. Treat the 14 days as a hard maximum rather than a safe interval: schedule the re-timestamp well inside it, so a failed or delayed job still leaves room before hosts start refusing metadata. This is the one piece of routine upkeep a live repository needs.

`fleetctl updates rotate <role>` replaces the signing key for one role, for a compromised key or a scheduled retirement. It generates a new key, re-signs the root, regenerates the dependent metadata and commits. The rotation commits reliably; the cleanup that removes its backups afterwards is the one place to watch, because a cleanup failure prints a warning and still exits zero while retired private-key material may be left on disk. [a.7](../09-appendices/a.7-fleetctl-command-reference.md#the-exit-zero-register) records this as Z27: when you see that warning, check the named backup directory by hand rather than trusting the exit code. It is maintenance you run against an existing repository, not a first-time step.

**A worked first run**, one repository path throughout:

```sh
export FLEET_ROOT_PASSPHRASE='<choose a passphrase for the root key>'
export FLEET_TARGETS_PASSPHRASE='<choose a passphrase for the targets key>'
export FLEET_SNAPSHOT_PASSPHRASE='<choose a passphrase for the snapshot key>'
export FLEET_TIMESTAMP_PASSPHRASE='<choose a passphrase for the timestamp key>'

fleetctl updates init --path ./repo

fleetctl updates roots --path ./repo > ./repo-root-metadata.json

fleetctl updates add --path ./repo \
  --target ./orbit-1.35.0-macos --name orbit --platform macos \
  --version 1.35.0 --tag stable
```

Skip the four exports and `init` prompts for each passphrase interactively instead; either way, the same four variables unlock the corresponding key again for every later `add`, `timestamp`, or `rotate` against this repository. Repeat `add` once per component and platform you publish, orbit, osqueryd, and desktop across macos, linux, and windows, each with its own built `--target` file and real `--version`; the `--tag` values are the channels hosts follow, so tag a build `stable` (or `edge`, or a pinned version string) to put it on that channel. Then finish the publish with the one command that has to run again on a schedule:

```sh
fleetctl updates timestamp --path ./repo
```

**Pointing hosts at it.** Building the repository is half the job. Two more steps put agents on it.

Serve the directory over TLS. What `fleetctl updates` writes is a static tree of metadata and target files, so any web server or object store that serves those files over HTTPS will do, and the address you serve it at is what agents aim their update traffic at.

Then bootstrap agents against it when you build their installers with `fleetctl package`:

- `--update-url` sets the address the agent fetches updates from, in place of the default `updates.fleetdm.com`.
- `--update-roots` carries the root metadata you printed with `fleetctl updates roots`, so the agent trusts your repository's keys and no others.
- `--update-tls-certificate` supplies a certificate to trust for that connection, for the case where your server presents one the agent would not otherwise chain to a public root.

```sh
fleetctl package --type=pkg \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="$FLEET_ENROLL_SECRET" \
  --update-url=https://updates.example.internal \
  --update-roots="$(fleetctl updates roots --path ./repo)" \
  --update-tls-certificate=./updates-ca.pem
```

An agent built with those flags updates from your repository from first launch. Once it is enrolled, the channel model and the two update clocks described earlier in this chapter apply unchanged: you have substituted the source, not the mechanism.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) Fleet reports each host's osquery and Orbit versions in its host details, and those are the values to check rather than what the installer contained. A host that was packaged at one version and has since followed a channel elsewhere will disagree with the installer, and the host record is the one telling the truth.

Worth confirming after any channel change:

- A **pilot host has actually moved**, rather than the change having been saved and not yet reached anything. Allow one configuration poll, thirty seconds ordinarily and up to five minutes after repeated configuration-cycle errors, plus the download and restart. New content on an unchanged channel is the slower case, and there the first interval plus its jitter is what to allow before concluding anything.
- The **spread across the estate closes** over the following hours. A long tail of hosts on the old version has several possible causes worth separating in the agent logs rather than assuming: an unreachable update server, repeated failure on one artifact, agents below 1.38.1, or updates disabled at packaging time.
- **Fleet Desktop is where you expect it**, since it is an optional component, included in the package only when it was built with `--fleet-desktop`, and can be absent without anything appearing wrong.

Ownership sits with whoever owns the agent rather than whoever owns the Fleet server. The two questions to settle are who decides when a channel moves, and who watches the version spread afterwards. On the free tier there is a third: who changes a channel at all, since without agent options it means either rebuilding installers or setting the channel on the host itself, through the flags or environment variables Orbit reads at startup.

## Precedence and edge cases

![Reference](../_assets/icons/reference.svg) A few behaviours here are easy to meet without recognising them.

Agent options override the installer, so a package built with a specific channel does not keep that channel if the deployment says otherwise.

A channel can move an agent backwards. Downgrading is a supported outcome of setting a lower version, not an error.

**Three different things can happen to a component's channel, and they are worth telling apart because two of them look like the third.**

- **A component omitted from `update_channels`** is not left alone. It is treated as `stable`, so a block naming only `orbit` moves osquery and Fleet Desktop to `stable` as well.
- **Removing the `update_channels` block entirely** is a no-op rather than a reset. Orbit treats an absent block as the server not using the feature and leaves each host on the channel it last recorded, so this is how you stop managing channels centrally and **not** how you undo a pin. To undo a pin, set the channel you want.
- **Naming a channel that does not exist** produces host-side errors and stops that component updating until the channel exists or the value is corrected. A typo therefore freezes a component quietly rather than failing loudly in Fleet.

**On a host without Fleet Desktop, the desktop channel is ignored rather than applied.** Orbit drops it from the comparison entirely when Desktop is not enabled on that host, so setting it neither takes effect nor causes a restart. A `desktop` value that appears to do nothing on some hosts and not others is this, not a failed rollout.

**Turning updates off is normally a packaging decision and is not only one.** Building with updates disabled bakes it into the service configuration, which is the usual route, but Orbit also accepts `--disable-updates` and `ORBIT_DISABLE_UPDATES` at startup, so it can be set by editing the service on a host. What matters either way is that **Fleet cannot undo it**: an agent with updates disabled does not resume updating because agent options changed, so neither clock in this chapter applies to it and a channel change reaches it and does nothing.

## Version notes

![Reference](../_assets/icons/reference.svg) Verified against Fleet 4.90.1. The default update interval, the jitter, and the three-retry cooldown are agent behaviour and move with fleetd rather than with the Fleet server, so an old agent may not match this description.

The 1.38.1 stepping stone is a consequence of a one-time server migration. It matters only for estates carrying agents from before that change, and it will matter less as those age out.
