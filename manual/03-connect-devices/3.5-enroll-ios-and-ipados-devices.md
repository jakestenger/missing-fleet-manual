# Enroll iOS and iPadOS devices

![Explanation](../_assets/icons/explanation.svg) iPhones and iPads have **one channel to the device and it is MDM**. There is no fleetd for these devices at this release, so no osquery, no live reports, no scripts, and no vitals in the sense the other platforms mean.

**"Everything Fleet knows arrived over MDM" is not quite true, and the gap matters when you are reading a host page.** Fleet can hold a record of a device before the device has ever spoken to it: an ABM sync creates a `Pending` host, and the enrollment link's exchange creates the host from its serial, product and UDID *before* MDM enrollment begins. So detail on a host page is not by itself evidence of an MDM check-in.

That is the single fact to carry into this chapter. Enrolling an iPhone is not "half done" until an agent shows up, the way a Mac or a Windows machine is. When MDM is on, the device is fully connected.

[3.2](3.2-enroll-macos-devices.md) covers the Mac. The Apple prerequisites are shared and belong to [2.7](../02-administer-and-deploy-fleet/2.7-apple-mdm-configuration.md); this chapter is about which of four paths to use, and what each one costs.

## The decision you are making

**Who owns the device, and do you have it in Apple Business?**

| Path | Use it when | Fleet Premium? | What the console shows |
|---|---|---|---|
| **Automated Device Enrollment (ADE)** | Company-owned, purchased into Apple Business | **Yes.** Fleet Free refuses to upload, list, renew or count Apple Business tokens, so there is no ADE without Premium | On (company-owned) |
| **Enrollment URL, company-owned** | Company-owned, not in Apple Business, or already deployed | No | On (manual) |
| **Enrollment URL, personal (BYOD)** | The device belongs to the person carrying it | No | On (manual - personal) |
| **Account-driven user enrollment** | Personal devices, where you want the person to sign in with a **Managed Apple Account** rather than follow a link | **Yes** | On (manual - personal) |

The database and the API spell the first one `On (automatic)`, and the host filter spells it `automatic`; [8.6](../08-troubleshooting/8.6-server-state.md#one-status-three-vocabularies) has the mapping.

### The path decides whether you can ever lock the device

This is the sharpest consequence of the choice above and the one worth settling before a rollout, because it cannot be revised without re-enrolling:

| Path | Lock | Wipe |
|---|---|---|
| ADE | Yes | Yes |
| Enrollment URL, company-owned | **No** | Yes |
| Enrollment URL, personal (BYOD) | **No** | **No** |
| Account-driven user enrollment | **No** | **No** |

**Fleet refuses to lock any manually enrolled iPhone or iPad**, company-owned included, with a message saying so. That is narrower than the macOS rule, where only personal enrollment loses lock and erase. And personal enrollment on any Apple platform loses both, because the profile the device holds was built without those rights ([3.2](3.2-enroll-macos-devices.md)).

So if remote lock is part of why you are managing these devices, **ADE is the only path that provides it**, and that is a purchasing decision rather than a configuration one.

**The first three look like the choice a Mac faces and are not quite it.** [3.2](3.2-enroll-macos-devices.md) explains the shared part: a personal enrollment profile is built with device lock and device erase removed from its MDM access rights, baked into the profile the device holds rather than into a Fleet-side permission you can revise. What is different here is that **a company-owned enrollment by link also loses lock**, which has no macOS equivalent. The table above has it.

**The fourth exists only here.** Account-driven user enrollment is iOS and iPadOS only at this release: Fleet checks the device's product string and refuses anything that is not an iPhone, iPad or iPod, and a Mac attempting it is told so. Worth knowing because the error a person sees on the device is generic, and the source says as much: there is no good way for Fleet to surface the real reason, so the device just reports that it could not get an enrollment profile.

## The enrollment URL, and what it does before MDM starts

![Explanation](../_assets/icons/explanation.svg) The URL you hand out is your Fleet server's `/enroll` path with an enroll secret in it, and `byod=true` added when you picked personal. That is the whole configuration: no profile to build, no per-device work.

What happens underneath is more interesting than the link suggests. It is Apple's over-the-air enrollment, which is two requests to the same endpoint rather than one:

1. The device presents a certificate chained to Apple's own CA. Fleet answers with a SCEP payload, and the device gets a keypair from it. **This keypair is not the identity certificate MDM will use later**; it exists only to sign the second request.
2. The device comes back signed with that certificate, and Fleet answers with an ordinary enrollment profile. Regular MDM enrollment proceeds from there.

The reason Fleet takes the long way round is what the second request carries: the serial number and hardware UUID, before the device is enrolled in anything. Fleet uses that window to **create the host record and place it in a fleet, from the enroll secret in the URL**, and to associate an identity-provider account when personal enrollment with an IdP is configured.

So an iPhone gets its fleet the same way a laptop running fleetd does, from an enroll secret, even though it runs no agent. Two practical consequences:

- **Each link targets exactly one fleet**, because the secret in it belongs to one. That is not a limit of one link: a fleet can hold up to 50 enroll secrets, so several live links are normal for staged rotation or for separate distribution channels. What it does mean is that handing one link to everybody puts everybody in the same fleet.
- **The link is a credential.** It carries an enroll secret in a query parameter, which means browser history, chat logs and help-desk tickets. [3.1](3.1-enrollment-design-and-host-lifecycle.md) covers rotation.

This path carries **no licence check**, so it is available on Fleet Free.

### What the person holding the device actually does

The page the link opens walks them through it, and it is worth knowing because it is four steps with two places people stop.

1. **Open the link in Safari.** The page refuses to proceed in any other browser and offers to copy the URL so it can be pasted into Safari. A link opened from a chat client's in-app browser lands here, which is worth saying in the message that carries the link.
2. **Tap Download, then Allow** when iOS asks.
3. **Go to Settings, then Profile Downloaded, and tap Install.** iOS shows a red **Not Verified** warning at this point. It is expected, and saying so in advance is worth more than explaining it afterwards. Tap Install again when prompted.
4. **Tap Trust** on the Remote Management screen.

The page also tells the person what the ownership choice means for them: on the personal path, that the organisation can remove work data and settings but cannot wipe the device or lock them out; on the company-owned path, that the organisation can see and delete all device information. That is a useful thing to be able to quote when someone asks before installing.


## Automated Device Enrollment

For devices bought into Apple Business and assigned to Fleet as their MDM server. The sequence is the one [3.2](3.2-enroll-macos-devices.md) sets out, and the ADE-specific troubleshooting is [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md).

**An ABM token carries four separate default fleets, not one.** macOS, iOS, iPadOS, and **BYOD**, set independently. A device syncing in from Apple Business is placed by the setting matching its platform rather than by a single default for the token, so if iPads are landing somewhere unexpected that setting is the place to look and no enroll secret is involved.

**The fourth one is the one people miss, because it has nothing to do with ADE.** The BYOD default is what places an **account-driven** enrollment: Fleet finds the token from the enrollment challenge and uses that setting. Leave it unset and those devices land unassigned, and the iOS and iPadOS defaults you were looking at have no bearing on them.

There is **no agent install to wait for**, which removes the half-enrolled failure that macOS has on every MDM path ([3.2](3.2-enroll-macos-devices.md)). Fleet's post-enrollment work on these devices is narrower, but it is not nothing: it reconciles the host's configuration profiles, and on Premium installs any setup-experience App Store apps. On the ADE path it then waits on those commands, profiles and setup-experience results before releasing the device. So a device sitting in Setup Assistant longer than expected may be waiting on that work rather than on enrollment, and the post-enrollment queue is worth checking before the enrollment itself.

## Account-driven user enrollment

![Explanation](../_assets/icons/explanation.svg) The personal-device path where the person signs in rather than following a link. It is **Fleet Premium**, and it has one prerequisite that surprises people.

**It needs Apple Business, even though the devices are personal.** Apple locates your MDM server by a *service discovery* URL registered against your Apple Business organisation, and Fleet registers that URL for you: the `mdm_service_discovery` schedule walks every ABM token you have uploaded once an hour, asks Apple what discovery URL it currently holds, and assigns Fleet's if it differs. With no ABM token uploaded it logs that there is nothing to do and stops, and enrollment has no way to find you.

Two consequences of it being registered rather than configured:

- **The discovery URL is derived from your Fleet server URL.** Change the server URL and the registered value is stale for up to an hour, until the schedule next runs and corrects it. `cron_stats` for `mdm_service_discovery` is where you confirm it ran ([8.6](../08-troubleshooting/8.6-server-state.md)).
- **Not every Apple Business organisation supports it.** When Apple says so, Fleet logs it and skips that token rather than failing, so the symptom is that one organisation's users cannot enroll while another's can.

**It needs an identity provider, and it needs Managed Apple Accounts.** There are **two** authentications, and testing only the first is how this path appears to work and then does not:

1. **To your identity provider.** The device's first request arrives without credentials, and Fleet answers with a `401` naming an SSO URL for it to open. Only after that sign-in does the device come back with a reference Fleet exchanges for an enrollment profile. There is no version of this path without an IdP configured ([2.2](../02-administer-and-deploy-fleet/2.2-identity-providers-sso-scim-and-role-sync.md)).
2. **To Apple, with a Managed Apple Account.** Fleet writes the assigned Managed Apple Account into the profile it returns, along with a BYOD enrollment mode. A personal Apple Account is not a substitute, and this is the half that a rollout planned around "an Apple ID and SSO" discovers late.

**What Fleet gets about the device is also different.** This is a user enrollment, so Fleet receives an enrollment identifier rather than a serial number and UDID, and profiles are scoped to the user rather than the device. That is Apple's privacy boundary rather than a Fleet limitation, and it means these hosts do not reconcile against a hardware asset register. Note that the personal **link** path is not the same: its exchange supplies a serial and UDID before enrollment, even though both paths show `On (manual - personal)`.

**Identity is not what distinguishes this path**, which is worth saying because it is the obvious reason to reach for it. The enrollment link can carry an identity too: with end-user authentication turned on, `/enroll` sends the person to your identity provider first and Fleet associates the returned account with the host, exactly as it does on macOS ([3.2](3.2-enroll-macos-devices.md), [2.2](../02-administer-and-deploy-fleet/2.2-identity-providers-sso-scim-and-role-sync.md)). **Both are Premium, though.** Turning end-user authentication on is itself a Premium setting, so the enrollment link gives you owner mapping without account-driven enrollment and not without a licence. What the free link gives you is enrollment, not identity.

**That identity is also what makes app licensing per-user.** The two personal paths are not equivalent here, and it is the reason to pay for this one. A device enrolled through the personal *enrollment URL* is a device-channel host: App Store and in-house apps install to the device, exactly as a company-owned manual enrollment does. **User-scoped licensing is reserved for account-driven user enrollment.** If the point of your BYOD programme is that an app licence follows a person rather than a handset, the URL path will not give you that.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) There is one channel, so there is one thing to check, and you check it from Fleet rather than from the device.

**The host appears, with an MDM status matching the path you used.** `Pending` means Apple Business has told Fleet about a device that has not enrolled yet, which is the expected state before someone unboxes it.

**Host detail comes from the protocol, not from queries, and on Premium it arrives on a schedule rather than at enrollment.** Fleet asks the device for its inventory over MDM, and the asking is done by the `apple_mdm_iphone_ipad_refetcher` cron, which picks up freshly enrolled hosts on its next tick; enrollment itself deliberately does not trigger it, so a newly enrolled iPhone with a thin host page has not necessarily failed.

That is consistent with the opening: what Fleet **does** to the device is MDM, and some of what Fleet **knows** about it, the ABM record and the serial and UDID the enrollment exchange supplied, arrived before any of this. `cron_stats` for that schedule is where you confirm it ran.

**That schedule is Premium-only.** Fleet registers it inside the Premium set and returns without registering anything when the licence is not Premium, so on Fleet Free it does not exist and there is no `cron_stats` row to look for. Since the enrollment link is the Free path, this combination is easy to walk into: a Free deployment enrolling iPhones by link has no periodic refetch and should not spend time troubleshooting a schedule that was never started ([8.6](../08-troubleshooting/8.6-server-state.md)).

**Fleet gives you no shell and no agent to run anything with**, so most of the evidence is server-side: the command queue and Apple's push channel, which is [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md). **The device is not silent, though.** A **sysdiagnose** carries the MDM client's own logs, and Fleet's troubleshooting guidance names it as the thing to collect for command and profile delivery problems on these platforms. Ask for one before escalating rather than after ([8.13](../08-troubleshooting/8.13-escalation.md)).

## Who owns it afterwards

**The APNs certificate**, which expires annually and takes every Apple device's MDM channel with it. Renewed with the same Apple Account that created it. [2.7](../02-administer-and-deploy-fleet/2.7-apple-mdm-configuration.md) owns the renewal calendar.

**The ABM token**, if you use ADE or account-driven enrollment, and its four default-fleet settings: macOS, iOS, iPadOS and BYOD.

**The enrollment links**, if you use them, because each one carries an enroll secret and secrets outlive the people who were handed them.
