# Enroll Linux devices

![Explanation](../_assets/icons/explanation.svg) Fleet gives Linux administrators a shared view of their devices, software, and security state alongside the organization’s other platforms. Enrollment starts with the fleetd package, which connects the host to inventory, reports, and supported management actions. Linux uses the agent throughout and has no separate MDM enrollment.

The agent uses four traffic families: osquery distributed, configuration, and logging endpoints, plus Orbit’s API ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). These paths can fail independently at the network layer, although the three osquery paths share a process and node key. Plan the capabilities and license tier you need using the table below.

| Not available on Linux | Available, over the agent |
|---|---|
| Configuration profiles, MDM commands, App Store apps | The osquery reading surface, and scripts, both on Free |
| | **Orbit-driven software installs**, on Fleet Premium |
| | **Disk-encryption key escrow**, on Fleet Premium |
| | **Lock and wipe**, on Fleet Premium. Fleet runs them as scripts rather than as MDM commands, so they need scripts enabled on the host |

Linux lock and wipe run as scripts through the agent, so enable script support when you need those actions. Windows also uses an agent script for lock, while its wipe uses MDM. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) compares the delivery paths.

<a id="the-decision-you-are-making"></a>

## Choose an enrollment approach

Choose the package format for your distribution, then decide how you will manage fleetd’s startup configuration on the host.

| Package | For | Built with |
|---|---|---|
| `.deb` | Debian, Ubuntu and derivatives | `--type=deb` |
| `.rpm` | RPM-based distributions: Fedora, RHEL and derivatives, and OpenSUSE | `--type=rpm` |
| `.pkg.tar.zst` | Arch and derivatives | `--type=pkg.tar.zst` |

All three accept `--arch=arm64` as well as the default `amd64`.

```sh
fleetctl package --type=deb \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --enable-scripts \
  --outfile=fleet-osquery.deb
```

`--outfile` gives the artifact a name you choose (it must keep the type's extension: `.deb`, `.rpm`, or `.pkg.tar.zst`). Without it the version and architecture land in the filename, so the install step below can then target that one exact path instead of a wildcard that may match more than one build in the directory.

`--enable-scripts` sets the initial script-support value. On Linux, you can later change `ORBIT_ENABLE_SCRIPTS` in the environment file and restart Orbit. This also controls whether Fleet can run Linux lock and wipe, because both use scripts.

`--fleet-desktop` adds the employee-facing My Device page and Self Service interface. My Device’s Details and Software tabs work on Free; Self Service installation and Fleet Desktop’s summary endpoint require Premium. Disk-encryption escrow runs through Orbit and does not require the Desktop component.

**If Fleet's TLS certificate comes from an internal authority**, add `--fleet-certificate` with that chain. Orbit loads and validates the file at startup, and without it an agent on a private-CA deployment will not connect.

<a id="the-configuration-is-a-file-you-can-edit-and-the-secret-is-in-it"></a>

### Edit and protect the local configuration

![Explanation](../_assets/icons/explanation.svg) Linux exposes fleetd’s startup settings in an editable environment file. You can manage them with your existing configuration-management tool and restart the service to apply changes.

The Linux packages write a systemd unit at `/usr/lib/systemd/system/orbit.service` and an environment file at `/etc/default/orbit`. The unit's `ExecStart` takes no arguments at all: **Orbit's own startup options are environment variables read from that file**, including `ORBIT_FLEET_URL`, `ORBIT_ENROLL_SECRET`, `ORBIT_ENABLE_SCRIPTS` and `ORBIT_DEBUG`.

Not everything lives there. Certificates, `osquery.flags`, and the update client's state are files under `/opt/orbit` and are not reachable from the environment file ([8.2](../08-troubleshooting/8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory)).

This determines where you will rotate the enroll secret and change startup options:

- **There is no `secret.txt` on Linux.** The macOS and Windows packagers can write one into Orbit's root directory, though neither always does; the Linux packagers never do, and put `ORBIT_ENROLL_SECRET` in `/etc/default/orbit` instead. Anything you read about hunting stale secrets in `secret.txt` ([3.1](3.1-enrollment-design-and-host-lifecycle.md)) points at the wrong file on this platform.
- **You can re-point a host, or turn scripts on, without rebuilding a package.** Edit `/etc/default/orbit`, then `systemctl restart orbit`. Each of the three platforms has an answer to this: macOS has `--use-system-configuration` and a profile, Windows has MSI properties, and this is the one that needs no artifact and no delivery. It is also why a configuration-management tool is a reasonable owner of fleetd's startup configuration on Linux.

The environment file is written mode `0600`, which is the protection the enroll secret gets. Treat that file as a credential and keep it out of anything that copies `/etc` around.

## Installing and removing it

![How-to](../_assets/icons/howto.svg) One privileged command per package type. The post-install script reloads systemd, enables `orbit.service`, and starts it.

```sh
sudo dpkg -i ./fleet-osquery.deb            # Debian family
sudo rpm -i ./fleet-osquery.rpm             # RHEL family
sudo pacman -U ./fleet-osquery.pkg.tar.zst  # Arch family
```

These install the exact file named by `--outfile` above. If you kept the default names instead, list the directory first and install the one path you meant, rather than a `*.deb` glob that can expand to several artifacts at once.

**Systemd is assumed.** The maintainer scripts test for `systemctl` before using it, so on a non-systemd distribution the files install and nothing starts, quietly. Starting Orbit is then yours to arrange.

**One upgrade case behaves differently, and it is the one Fleet itself drives.** When the package is being installed *by Orbit*, which is what happens when you deploy a fleetd upgrade through Fleet's own software installation, restarting the service immediately would kill the process running the installation. The Linux script detects that case from `INSTALLER_PATH` and schedules the restart 60 seconds later with `systemd-run`. If `systemd-run` is absent it **prints a message and does not restart at all**, leaving the host on the old Orbit until something else restarts it or the machine reboots. That is one explanation for a fleet-wide fleetd upgrade that looks half-applied, and it is not the only one. The maintainer script's own output is captured as software-install output rather than written to the agent log, so `systemctl is-active orbit` on an affected host is a faster answer than reading logs.

**Removing it** is the package manager's ordinary removal, and it is what [3.1](3.1-enrollment-design-and-host-lifecycle.md) means by stopping the enrollment source. The package's own scripts are supposed to disable and stop `orbit.service`, kill Fleet Desktop, and then delete `/opt/orbit`, `/var/lib/orbit`, `/var/log/orbit`, `/usr/local/bin/orbit`, `/etc/default/orbit` and the unit file. Do that **before** deleting the host in Fleet, not after, or the agent re-enrols and you get a second host record.

**On RPM-based systems the stop step does not run on uninstall, and does run on upgrade.** The pre-removal script branches on the argument the package manager gives it. RPM passes `0` for an uninstall and `1` for an upgrade, which the script's own comment states correctly, directly above a branch that disables the service for `1` and does nothing for `0`. The two are the wrong way round for RPM. Debian and Arch are unaffected, because Debian passes words rather than numbers and the Arch script disables unconditionally.

So on a `.rpm` host, expect an uninstall to leave `orbit.service` enabled and running while the files it needs are deleted from under it, and expect an upgrade to stop the service and rely on the post-install script to start it again. **Check `systemctl is-enabled orbit` after removing the package**, and disable it by hand if it is still there.

## Disk encryption escrow

![Explanation](../_assets/icons/explanation.svg) Fleet can escrow a recovery key for an already encrypted Linux root disk on a supported distribution. This gives administrators a recovery option while the existing encryption setup stays in place. Fleet does not enable LUKS itself. Prepare the encrypted disk first, then configure the agent, required dialog tools, license, and escrow request described below.

On the passphrase path, Fleet validates the user’s existing passphrase locally, generates a separate random passphrase, and adds it in a new key slot. On the snapd path, it obtains a dedicated recovery key. The user’s passphrase is unchanged. To withdraw access, remove Fleet’s added key slot on the passphrase path; for snapd, rotate the recovery key because its API and CLI provide no deletion operation. Rotation also repairs a failed snapd escrow on the next attempt.

### What the host has to be

| Requirement | Fixable later? |
|---|---|
| The root disk is encrypted with **LUKS2** | **Not by Fleet, and not by a package.** Fleet cannot enable it, and refuses the escrow outright on an unencrypted host. The version matters: Fleet documents LUKS2 and Orbit reads LUKS2 metadata, so a LUKS1 volume is not covered. Fleet tests the disk's reported state, not how it got that way, so a host encrypted by any means becomes eligible |
| The distribution is one Fleet supports | Not without reinstalling. Ubuntu, Zorin, Fedora, Arch, Arch ARM, Manjaro, Manjaro ARM, CachyOS. **Not** Debian, and not the rest of the RHEL family. Fedora is matched on its name in the reported OS version, because osquery reports its platform as `rhel`, which is why it works and its relatives do not |
| `cryptsetup` is installed | Yes, it is a package. Required on both escrow paths |
| A desktop dialog tool is installed | Yes, also a package. `zenity` or `kdialog`, and **only on the passphrase path**. See below |

A host becomes eligible once osquery reports its disk encrypted, even if encryption was enabled after enrollment. The disk state can therefore be prepared separately from installing fleetd.

<a id="two-escrow-paths-and-only-one-needs-a-person"></a>

### User-assisted and TPM-backed escrow

Orbit picks between them when Fleet asks for an escrow:

| Path | When Orbit takes it | What it needs |
|---|---|---|
| **Recovery key**, silent | The host uses snapd-managed TPM-backed full-disk encryption, as on recent Ubuntu | `cryptsetup`. **No dialog and no person**: Orbit obtains a recovery key over the snapd socket and escrows it |
| **Passphrase**, interactive | Everything else | `cryptsetup`, **and** `zenity` or `kdialog`. Orbit prompts the end user for their existing passphrase, validates it against any key slot, then adds Fleet's key in a separate slot |

Orbit checks for snapd first, and treats a failure of that check as fatal rather than falling through: a metadata read failure could mean the host *is* snapd-managed but unconfirmable, and prompting for a passphrase the person does not have would be worse than failing.

Orbit runs escrow even when the package omits Fleet Desktop. The passphrase path requires `zenity` or `kdialog` to prompt the user; either can be installed later. Without a supported dialog tool, Orbit returns `No supported dialog tool found`.

The snapd path can escrow on a headless host without a person present.

A host that satisfies everything above still escrows nothing until all of this holds:

- **Fleet Premium.** Escrow is a Premium capability.
- **A configured server private key.** Fleet refuses to enable disk encryption at all without one, because that key is what encrypts the escrowed material ([2.11](../02-administer-and-deploy-fleet/2.11-configure-windows-management.md)). It is also the key you must not lose or change ([7.7](../07-operate-fleet/7.7-production-readiness-checklist-and-handoff.md)).
- **Disk encryption enabled for the host's scope**, globally for a host in no fleet, or on the host's fleet. Fleet names whichever one is missing.
- **A fleetd new enough for the path the host will take.** Fleet's server-side gate is **1.36.0**, and below it the end user is told to upgrade fleetd, refetch and try again. That floor is the passphrase path's. **Snapd recovery-key escrow arrives in fleetd 1.58.0**, so a snapd-managed host on an older agent passes the server's version check and has no snapd path to take. What it does instead is not established here; what is, is that 1.58.0's own code detects snapd first and its comment says falling through to the passphrase path on such a host would prompt for a passphrase the user does not have. Treat anything between 1.36.0 and 1.58.0 on snapd-managed encryption as untested rather than as working.
- **Fleet observing the disk as encrypted**, which comes from an ordinary osquery detail query rather than from anything escrow-specific. A host that has not reported yet is refused with "Please encrypt your disk first", which is misleading if the disk is in fact encrypted and simply unreported.

After the prerequisites are met, request escrow from the host’s device context, normally through the employee’s **My Device** page. Fleet rejects a request if a key is already stored or pending; otherwise it queues work for Orbit’s next configuration poll. Meeting the prerequisites alone does not queue that request.

Encryption reporting is available independently of escrow. osquery reports whether the root disk is encrypted without a dialog tool or Premium license. The additional requirements above apply when you want Fleet to hold a recovery key.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Verify the service and each communication path after installation. These five checks cover the four traffic families and confirm the host can report inventory, receive configuration, return scheduled results, and perform an agent action.

**1. The service is up and stayed up.**

```sh
systemctl status orbit
sudo cat /etc/default/orbit
journalctl -u orbit -n 100
```

`Restart=always` is set on the unit, so a crashing Orbit reappears as running. A recent start time with low uptime, or a restart counter that climbs, is a crash loop rather than health, and [8.4](../08-troubleshooting/8.4-host-side-investigation.md) reads the rest.

**2. The osquery distributed channel works.** The host appears in Fleet with vitals, and answers a live report. Vitals arriving proves distributed read and write and the ingestion behind them; a live report returning proves the same path end to end and nothing about the others ([8.7](../08-troubleshooting/8.7-live-query-introspection.md)).

**3. The osquery logging channel works.** Configure a scheduled report and confirm results reach the intended destination ([8.2](../08-troubleshooting/8.2-log-surfaces.md)). This exercises a separate endpoint from live reports. If live results arrive but scheduled results do not, check the logging path and the report’s forwarding configuration, including automations where required ([4.2](../04-know-your-devices/4.2-run-queries-and-reports.md)).

**4. The osquery configuration channel works.** This is the third osquery endpoint and the quiet one: it is how the host fetches its query schedule and agent options in the first place. Change something in agent options and confirm the host picks it up, or read the flags actually in effect on the host ([8.4](../08-troubleshooting/8.4-host-side-investigation.md)). A host whose configuration fetch is broken keeps answering live reports with whatever schedule it last received, which looks like health.

**5. Orbit's own channel works.** Run a trivial script against the host. That is the channel scripts, software installs and disk-encryption escrow all travel on, and it is authenticated separately from osquery's, so it can fail on its own. If scripts are disabled you will be told, which is itself the answer to a different question.

Linux hosts have no `host_mdm` row. A direct query returns no row, while a left join can return `NULL` for `enrollment_status`. Neither represents a Linux MDM state. Use the agent checks above to assess enrollment, regardless of how the console presents an empty MDM field.

## Who owns it afterwards

**The environment file**, because it is a credential and because it is editable. Decide whether fleetd's configuration is owned by your configuration-management tool or by hand, and write it down. This is the platform where "somebody edited it on the host" is a realistic explanation for a host talking to the wrong server.

**The relationship with whatever already manages these machines.** On headless Linux an existing configuration-management tool often already owns system configuration, and Fleet does not need to displace it to be useful ([1.1](../01-foundations/1.1-what-fleet-is.md)). Deciding that boundary early avoids two tools fighting over the same files.

**Hardware-backed host identity**, if you use it. It is Linux-only, Fleet Premium, needs TPM 2.0 and kernel 4.12 or later, and a host without a TPM will fail to enroll once the option is in the package. [3.1](3.1-enrollment-design-and-host-lifecycle.md) covers it, including the fact that a host which loses its TPM state has no way back except re-enrollment.
