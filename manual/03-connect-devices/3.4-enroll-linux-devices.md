# Enroll Linux devices

![Explanation](../_assets/icons/explanation.svg) Linux is the platform with **no MDM channel**. Fleet has none for it, so enrollment is entirely the fleetd story: install the package, the agent enrolls, and there is no second enrollment to wait for.

That does not make it a single-channel platform. A Linux host still talks to Fleet over the osquery distributed channel, the osquery logging channel, and Orbit's own API, which are separately authenticated and can fail separately ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). What is missing is the profile-and-command channel, and what that costs is narrower than it sounds:

| Not available on Linux | Available, over the agent |
|---|---|
| Configuration profiles, MDM commands, App Store apps | The osquery reading surface, scripts, Orbit-driven software installs, disk-encryption key escrow |
| *(nothing else)* | **Lock and wipe**, on Fleet Premium. Fleet runs them as scripts rather than as MDM commands, so they need scripts enabled on the host |

**Lock and wipe on Linux is the fact most likely to be missed**, because every other platform gets them from MDM and Linux has none. Fleet's own source says it plainly: Windows and macOS require MDM enrollment for a wipe, Linux uses scripts. The practical consequence is at packaging time, below.

## The decision you are making

**Which package, and where does its configuration live?** Both answers are different from the other platforms in ways that matter.

| Package | For | Built with |
|---|---|---|
| `.deb` | Debian, Ubuntu and derivatives | `--type=deb` |
| `.rpm` | Fedora, RHEL and derivatives | `--type=rpm` |
| `.pkg.tar.zst` | Arch and derivatives | `--type=pkg.tar.zst` |

All three accept `--arch=arm64` as well as the default `amd64`.

```sh
fleetctl package --type=deb \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --enable-scripts
```

`--enable-scripts` decides whether this host will run scripts, **and on Linux it is a default rather than a decision.** Orbit reads the same setting from `ORBIT_ENABLE_SCRIPTS` in the environment file below, so a host packaged without the flag can be given scripts by editing one line and restarting the service. That matters more here than elsewhere, because **Fleet's Linux lock and wipe are scripts**: a host with scripts disabled cannot be locked or wiped, and the fix is a file edit rather than a new package.

`--fleet-desktop` gives the end user the My Device page and Self Service. It is **not** what disk-encryption escrow depends on, despite the obvious guess.

**If Fleet's TLS certificate comes from an internal authority**, add `--fleet-certificate` with that chain. Orbit loads and validates the file at startup, and without it an agent on a private-CA deployment will not connect.

### The configuration is a file you can edit, and the secret is in it

![Explanation](../_assets/icons/explanation.svg) This has no equivalent on macOS, and it changes what you can do to a deployed host without rebuilding anything.

The Linux packages write a systemd unit at `/usr/lib/systemd/system/orbit.service` and an environment file at `/etc/default/orbit`. The unit's `ExecStart` takes no arguments at all: **Orbit's own startup options are environment variables read from that file**, including `ORBIT_FLEET_URL`, `ORBIT_ENROLL_SECRET`, `ORBIT_ENABLE_SCRIPTS` and `ORBIT_DEBUG`.

Not everything lives there. Certificates, `osquery.flags`, and the update client's state are files under `/opt/orbit` and are not reachable from the environment file ([8.2](../08-troubleshooting/8.2-log-surfaces.md#827-the-rest-of-the-orbit-root-directory)).

Two consequences follow, and they are the reason to read this before building anything:

- **There is no `secret.txt` on Linux.** The macOS and Windows packagers write one into Orbit's root directory; the Linux packagers do not, and put `ORBIT_ENROLL_SECRET` in `/etc/default/orbit` instead. Anything you read about hunting stale secrets in `secret.txt` ([3.1](3.1-enrollment-design-and-host-lifecycle.md)) points at the wrong file on this platform.
- **You can re-point a host, or turn scripts on, without rebuilding a package.** Edit `/etc/default/orbit`, then `systemctl restart orbit`. Each of the three platforms has an answer to this: macOS has `--use-system-configuration` and a profile, Windows has MSI properties, and this is the one that needs no artifact and no delivery. It is also why a configuration-management tool is a reasonable owner of fleetd's startup configuration on Linux.

The environment file is written mode `0600`, which is the protection the enroll secret gets. Treat that file as a credential and keep it out of anything that copies `/etc` around.

## Installing and removing it

![How-to](../_assets/icons/howto.svg) One privileged command per package type. The post-install script reloads systemd, enables `orbit.service`, and starts it.

```sh
sudo dpkg -i fleet-osquery_*.deb          # Debian family
sudo rpm -i fleet-osquery-*.rpm           # RHEL family
sudo pacman -U fleet-osquery-*.pkg.tar.zst  # Arch family
```

**Systemd is assumed.** The maintainer scripts test for `systemctl` before using it, so on a non-systemd distribution the files install and nothing starts, quietly. Starting Orbit is then yours to arrange.

**One upgrade case behaves differently, and it is the one Fleet itself drives.** When the package is being installed *by Orbit*, which is what happens when you deploy a fleetd upgrade through Fleet's own software installation, restarting the service immediately would kill the process running the installation. The Linux script detects that case from `INSTALLER_PATH` and schedules the restart 60 seconds later with `systemd-run`. If `systemd-run` is absent it **prints a message and does not restart at all**, leaving the host on the old Orbit until something else restarts it or the machine reboots. That is one explanation for a fleet-wide fleetd upgrade that looks half-applied; it is not the only one, and the agent log says which happened.

**Removing it** is the package manager's ordinary removal, and it is what [3.1](3.1-enrollment-design-and-host-lifecycle.md) means by stopping the enrollment source. The package's own scripts are supposed to disable and stop `orbit.service`, kill Fleet Desktop, and then delete `/opt/orbit`, `/var/lib/orbit`, `/var/log/orbit`, `/usr/local/bin/orbit`, `/etc/default/orbit` and the unit file. Do that **before** deleting the host in Fleet, not after, or the agent re-enrols and you get a second host record.

**On RPM-based systems the stop step does not run on uninstall, and does run on upgrade.** The pre-removal script branches on the argument the package manager gives it. RPM passes `0` for an uninstall and `1` for an upgrade, which the script's own comment states correctly, directly above a branch that disables the service for `1` and does nothing for `0`. The two are the wrong way round for RPM. Debian and Arch are unaffected, because Debian passes words rather than numbers and the Arch script disables unconditionally.

So on a `.rpm` host, expect an uninstall to leave `orbit.service` enabled and running while the files it needs are deleted from under it, and expect an upgrade to stop the service and rely on the post-install script to start it again. **Check `systemctl is-enabled orbit` after removing the package**, and disable it by hand if it is still there.

## Disk encryption escrow

![Explanation](../_assets/icons/explanation.svg) Linux disk encryption in Fleet is **escrow only**. Fleet cannot turn LUKS on for a host that was installed unencrypted, so whether a machine can ever be escrowed is settled when the image is built. Everything else about escrow is configuration you can change afterwards, and the chapter separates the two because getting the image right and still receiving no key is a common and confusing outcome.

**What Fleet escrows is a key of its own, not the user's.** On the passphrase path Fleet validates the passphrase the person already has, generates a fresh random one, and adds *that* in a new key slot. On the snapd path it obtains a dedicated recovery key. Either way Fleet never learns the user's own passphrase, and revoking Fleet's access means removing a key slot rather than changing anyone's password.

### Decided when you build the image

| Requirement | Why it is an image decision |
|---|---|
| The root disk is encrypted with LUKS | Fleet cannot enable it later. Fleet refuses the escrow outright on an unencrypted host |
| The distribution is one Fleet supports | Ubuntu, Zorin, Fedora, Arch, Arch ARM, Manjaro, Manjaro ARM, CachyOS. **Not** Debian, and not the rest of the RHEL family. Fedora is matched on its name in the reported OS version, because osquery reports its platform as `rhel`, which is why it works and its relatives do not |
| `cryptsetup` is installed | Required on both escrow paths |
| A desktop dialog tool is installed | `zenity` or `kdialog`, and **only on the passphrase path**. See below |

### Two escrow paths, and only one needs a person

Orbit picks between them when Fleet asks for an escrow:

| Path | When Orbit takes it | What it needs |
|---|---|---|
| **Recovery key**, silent | The host uses snapd-managed TPM-backed full-disk encryption, as on recent Ubuntu | `cryptsetup`. **No dialog and no person**: Orbit obtains a recovery key over the snapd socket and escrows it |
| **Passphrase**, interactive | Everything else | `cryptsetup`, **and** `zenity` or `kdialog`. Orbit prompts the end user for their existing passphrase, validates it against any key slot, then adds Fleet's key in a separate slot |

Orbit checks for snapd first, and treats a failure of that check as fatal rather than falling through: a metadata read failure could mean the host *is* snapd-managed but unconfirmable, and prompting for a passphrase the person does not have would be worse than failing.

**This is Orbit's work, not Fleet Desktop's.** The escrow runner is registered on the Orbit client itself, so a package built without `--fleet-desktop` escrows normally. On the passphrase path, what has to be present is a dialog tool, which is a property of the image your distribution ships. On a host with neither, Orbit fails with `No supported dialog tool found` rather than hanging.

**A headless host is therefore not automatically excluded**, which is the opposite of the obvious guess: on the snapd path it escrows with nobody present.

### Configured afterwards, and every one of these can leave you with no key

An image that satisfies everything above still escrows nothing until all of this holds:

- **Fleet Premium.** Escrow is a Premium capability.
- **A configured server private key.** Fleet refuses to enable disk encryption at all without one, because that key is what encrypts the escrowed material ([2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md)). It is also the key you must not lose or change ([2.12](../02-administer-and-deploy-fleet/2.12-production-readiness-and-handoff.md)).
- **Disk encryption enabled for the host's scope**, globally for a host in no fleet, or on the host's fleet. Fleet names whichever one is missing.
- **fleetd 1.36.0 or later.** Below that, Fleet tells the end user to upgrade fleetd, refetch, and try again.
- **Fleet observing the disk as encrypted**, which comes from an ordinary osquery detail query rather than from anything escrow-specific. A host that has not reported yet is refused with "Please encrypt your disk first", which is misleading if the disk is in fact encrypted and simply unreported.

**Encryption status and escrow are separate.** Fleet learns whether the root disk is encrypted from osquery on every host, with no escrow, no dialog tool and no Premium licence involved. If what you need is *reporting*, you already have it; the requirements above are the price of holding a recovery key.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) There is no MDM status to check, but there is more than one thing to verify: **a running process is not a working agent.** Check the three separately.

**1. The service is up and stayed up.**

```sh
systemctl status orbit
sudo cat /etc/default/orbit
journalctl -u orbit -n 100
```

`Restart=always` is set on the unit, so a crashing Orbit reappears as running. A recent start time with low uptime, or a restart counter that climbs, is a crash loop rather than health, and [8.4](../08-troubleshooting/8.4-host-side-investigation.md) reads the rest.

**2. The osquery channels work.** The host appears in Fleet with vitals, and answers a live report. Vitals arriving proves the distributed channel and ingestion; a live report returning proves the same path end to end and nothing about the others ([8.7](../08-troubleshooting/8.7-live-query-introspection.md)).

**3. Orbit's own channel works.** Run a trivial script against the host. That is the channel scripts, software installs and disk-encryption escrow all travel on, and it is authenticated separately from osquery's, so it can fail on its own. If scripts are disabled you will be told, which is itself the answer to a different question.

A Linux host showing MDM `Off` is not a finding: there is no Linux MDM, and `Off` is what `host_mdm.enrollment_status` yields for a host with no MDM record at all ([8.6](../08-troubleshooting/8.6-server-state.md#one-status-three-vocabularies)).

## Who owns it afterwards

**The environment file**, because it is a credential and because it is editable. Decide whether fleetd's configuration is owned by your configuration-management tool or by hand, and write it down. This is the platform where "somebody edited it on the host" is a realistic explanation for a host talking to the wrong server.

**The relationship with whatever already manages these machines.** On headless Linux, an existing configuration-management tool is frequently the right owner of system configuration, and Fleet does not need to displace it to be useful ([1.1](../01-foundations/1.1-what-fleet-is.md)). Deciding that boundary early avoids two tools fighting over the same files.

**Hardware-backed host identity**, if you use it. It is Linux-only, Fleet Premium, needs TPM 2.0 and kernel 4.12 or later, and a host without a TPM will fail to enroll once the option is in the package. [3.1](3.1-enrollment-design-and-host-lifecycle.md) covers it, including the fact that a host which loses its TPM state has no way back except re-enrollment.
