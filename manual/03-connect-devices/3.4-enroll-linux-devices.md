# Enroll Linux devices

![Explanation](../_assets/icons/explanation.svg) Linux is the only platform where there is **one channel and no second one to wait for**. There is no Linux MDM, in Fleet or anywhere else, so enrollment is entirely the fleetd story: install the package, the agent enrolls, and that is the whole of it.

That makes this the shortest of the four enrollment chapters and the one where the interesting questions move elsewhere. What you get is the osquery reading surface, scripts, software installs driven by Orbit, and disk-encryption key escrow. What you do not get is profiles, MDM commands, lock, or wipe. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) sets out that boundary; this chapter is about getting across it.

## The decision you are making

**Which package, and where does its configuration live?** Both answers are different from the other platforms in ways that matter.

| Package | For | Built with |
|---|---|---|
| `.deb` | Debian, Ubuntu and derivatives | `--type=deb` |
| `.rpm` | Fedora, RHEL and derivatives | `--type=rpm` |
| `.pkg.tar.zst` | Arch and derivatives | `--type=pkg.tar.zst` |

All three accept `--arch=arm64` as well as the default `amd64`.

```sh
fleetctl package --type=deb \
  --fleet-url=https://fleet.example.com \
  --enroll-secret=<secret> \
  --enable-scripts
```

`--enable-scripts` decides whether this host will run scripts, and a package built without it produces hosts you cannot run a script against later. `--fleet-desktop` is available and is the flag to think hardest about here, for the reason in the escrow section below.

### The configuration is a file you can edit, and the secret is in it

![Explanation](../_assets/icons/explanation.svg) This is the single most useful thing to know about fleetd on Linux, and it has no equivalent on macOS.

The Linux packages write a systemd unit at `/usr/lib/systemd/system/orbit.service` and an environment file at `/etc/default/orbit`. The unit's `ExecStart` takes no arguments at all; **every setting is an environment variable read from that file**, including `ORBIT_FLEET_URL`, `ORBIT_ENROLL_SECRET`, `ORBIT_ENABLE_SCRIPTS`, `ORBIT_DEBUG` and the rest.

Two consequences follow, and they are the reason to read this before building anything:

- **There is no `secret.txt` on Linux.** The macOS and Windows packagers write one into Orbit's root directory; the Linux packagers do not, and put `ORBIT_ENROLL_SECRET` in `/etc/default/orbit` instead. Anything you read about hunting stale secrets in `secret.txt` ([3.1](3.1-enrollment-design-and-host-lifecycle.md)) points at the wrong file on this platform.
- **You can re-point a host without rebuilding a package.** Edit `/etc/default/orbit`, then `systemctl restart orbit`. This is Linux's answer to what macOS needs `--use-system-configuration` for and Windows solves with MSI properties, and it is the least ceremonious of the three. It is also the reason a configuration-management tool is a perfectly good way to own fleetd's configuration on Linux, which is not true of the other platforms.

The environment file is written mode `0600`, which is the protection the enroll secret gets. Treat that file as a credential and keep it out of anything that copies `/etc` around.

## Installing it

![How-to](../_assets/icons/howto.svg) Install the package the way you install packages. The post-install script reloads systemd, enables `orbit.service`, and starts it.

**Systemd is assumed.** The maintainer scripts test for `systemctl` before using it, so a non-systemd distribution will install the files and never start anything, quietly. If you are on one, starting Orbit is yours to arrange.

**One upgrade case behaves differently, and it is the one Fleet itself drives.** When the package is being installed *by Orbit*, which is what happens when you deploy a fleetd upgrade through Fleet's own software installation, restarting the service immediately would kill the process running the installation. The post-install script detects that case and schedules the restart 60 seconds later with `systemd-run` instead. If `systemd-run` is not available it **prints a message and exits without restarting at all**, leaving the host on the old Orbit until something else restarts it or the machine reboots. A fleet-wide fleetd upgrade that appears to have half-applied is worth checking against this before looking anywhere else.

## Disk encryption escrow, which is decided at enrollment

![Explanation](../_assets/icons/explanation.svg) Linux disk encryption in Fleet is **escrow only**. Fleet cannot turn LUKS on for a host that was installed unencrypted; it can take a copy of the key for a host that already has it. That makes it a provisioning decision rather than a policy you can apply later, which is why it belongs in an enrollment chapter.

Two conditions gate it, and both are easy to get wrong at the moment you are choosing an image.

**The distribution has to be on Fleet's list**, and the list is shorter than "Linux":

| Escrow supported | Not on the list |
|---|---|
| Ubuntu, Zorin, Fedora, Arch, Arch ARM, Manjaro, Manjaro ARM, CachyOS | Debian, RHEL, CentOS, Rocky, Alma, openSUSE, and anything else |

Fedora is recognised by matching its name in the reported OS version rather than by platform, because osquery reports Fedora's platform as `rhel`. The practical effect is that Fedora works and the other members of that family do not, which is not something you would guess from the outside.

**Fleet Desktop has to be running, with a person at the machine.** The escrow flow prompts the end user for their existing LUKS passphrase, validates it, and only then adds Fleet's escrow key in a separate key slot. Fleet never learns the user's own passphrase and cannot proceed without someone typing it. So:

- A package built without `--fleet-desktop` can never escrow a key.
- A headless server can never escrow a key, no matter how it was packaged, because there is nobody to prompt.

If disk-encryption reporting on Linux matters to you, decide both of these before you build the image, not after the estate is deployed.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) There is only one channel, so there is only one thing to check, and systemd will tell you most of it.

```sh
# Is the agent running, and did it stay running?
systemctl status orbit

# What is it configured to talk to?
sudo cat /etc/default/orbit

# What has it said recently?
journalctl -u orbit -n 100
```

`Restart=always` is set on the unit, so a crashing Orbit reappears as running. `systemctl status` showing a recent start time and a low uptime, or a restart counter that keeps climbing, is the shape of a crash loop rather than a healthy agent, and [8.4](../08-troubleshooting/8.4-host-side-investigation.md) reads the rest of it.

**From Fleet**, the host appears with vitals and answers a live report. There is no MDM status to check, and a Linux host showing MDM `Off` is not a finding: [8.6](../08-troubleshooting/8.6-server-state.md) covers where that value comes from and why it means nothing here.

## Who owns it afterwards

**The environment file**, because it is a credential and because it is editable. Decide whether fleetd's configuration is owned by your configuration-management tool or by hand, and write it down. This is the platform where "somebody edited it on the host" is a realistic explanation for a host talking to the wrong server.

**The relationship with whatever already manages these machines.** On headless Linux, an existing configuration-management tool is frequently the right owner of system configuration, and Fleet does not need to displace it to be useful ([1.1](../01-foundations/1.1-what-fleet-is.md)). Deciding that boundary early avoids two tools fighting over the same files.

**Hardware-backed host identity**, if you use it. It is Linux-only, Fleet Premium, needs TPM 2.0 and kernel 4.12 or later, and a host without a TPM will fail to enroll once the option is in the package. [3.1](3.1-enrollment-design-and-host-lifecycle.md) covers it, including the fact that a host which loses its TPM state has no way back except re-enrollment.
