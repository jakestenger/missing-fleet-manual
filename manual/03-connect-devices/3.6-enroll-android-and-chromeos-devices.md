# Enroll Android and ChromeOS devices

![Explanation](../_assets/icons/explanation.svg) Two platforms in one chapter because they share nothing with the other four and very little with each other. Neither runs fleetd. Both involve Google, in completely different senses.

| | Android | ChromeOS |
|---|---|---|
| What manages the device | Google's Android Management API, reached through a proxy Fleet operates | Nothing manages it through Fleet. Google's own console does |
| What Fleet gets | Whatever Google chooses to push | Live report results, against eleven tables the extension implements itself |
| How a device is configured | An enrollment token, one per device | Extension policy in the Google Admin console |
| Prerequisite | An Android Enterprise bound to your Fleet server URL | A managed Chrome estate |

The Android Enterprise binding, and everything it commits you to, is [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md). Read it before enrolling anything, because two of its consequences are effectively permanent: your Fleet server URL is fixed once Android is on, and one server URL supports one enterprise.

## Android: choosing a path

**Ownership decides the path, and the path decides what you can do**, more sharply than on any other platform.

| Path | Use it when | What the console shows |
|---|---|---|
| **Work profile** | The device belongs to the person carrying it. Fleet manages a work profile beside their personal one | On (manual - personal) |
| **QR code at initial setup** | The device is company-owned and factory-fresh, or has been reset | On (company-owned) |
| **Google account based** | Named as a supported path in Fleet's own checklist and **not documented beyond that** | **No expected status established.** Record what Fleet actually shows ([8.13](../08-troubleshooting/8.13-escalation.md)) |

**The QR path exists only at the initial setup screen.** A device that has finished setup cannot take it without a factory reset. That is Google's constraint rather than Fleet's, and nothing in Fleet's source enforces or describes it, so it is Fleet's documented guidance about Android rather than a Fleet behaviour. It is the way a company-owned Android rollout most often stalls: the devices were unboxed and handed out before anyone thought about management.

**Ownership also decides whether you can wipe the device.** Fleet refuses a wipe on a personally-owned Android host and says to unenroll instead, which is not a workaround so much as the same outcome by the supported route: unenrolling a work profile runs Google's own wipe of that profile underneath. Lock works on both. So the table above is also the lock-and-wipe table:

| Path | Lock | Wipe |
|---|---|---|
| Work profile (personal) | Yes | **No.** Unenroll instead, which removes the work profile |
| QR code (company-owned) | Yes | Yes |

Both need Android management configured, and lock additionally needs Fleet to consider the host connected.

Work profile enrollment does not become company-owned later either, for the same reason. Decide before the device reaches a person.

### What both paths actually do

You do not build a package or deliver a profile. You ask Fleet for an **enrollment token** and give it to the device: as a link on the work-profile path, as a QR code on the other.

| Fact | Value |
|---|---|
| Where the token comes from | Fleet, which asks Google's API through its proxy |
| What Fleet puts inside it | Your enroll secret, and an identity-provider UUID where one applies |
| Reuse | **One device per token.** Fleet marks it single-use |
| Lifetime | One hour, which is Google's default and Fleet does not override it |

That payload is how a device Fleet has never seen ends up in the right fleet and attached to the right person. It also means **a wrong enroll secret fails when the token is created, before any device is involved**, which is a much better place for it to fail than on a phone in someone's hand.

The one-hour lifetime is the other thing to plan around. A QR code printed into a provisioning runbook on Monday does not work on Tuesday.

[8.10](../08-troubleshooting/8.10-android-diagnostics.md#8108-enrollment-paths) has the token endpoint, the exact settings, and the enrollment failures worth recognising.

### What you get, and what you do not

There is no agent and no osquery on Android. Fleet never asks an Android device anything: Google pushes an enrollment event when a device enrolls and a status report when its state changes, and everything Fleet knows arrived unsolicited.

So no live reports, no scheduled reports, no scripts, and no host-side investigation of any kind. When an Android host misbehaves, the evidence is in Fleet's own tables and in the return path from Google, which is [8.10](../08-troubleshooting/8.10-android-diagnostics.md).

**One identity consequence belongs at enrollment time**, because what it breaks is your asset process rather than Fleet: on a personally owned device with a work profile, the serial number and UUID Fleet reports are not hardware identifiers. They are an enterprise-specific ID, unique to that work profile in your organisation and stable across factory resets. [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) covers it.

## ChromeOS: an extension, and only on ChromeOS

![Explanation](../_assets/icons/explanation.svg) Fleet does not manage ChromeOS. Google's console does. What Fleet gets is a reporting agent, and that agent is a Chrome extension deployed the way you deploy any managed extension.

No MDM, no enrollment profile, no package. Two things have to be true:

1. **The extension is force-installed** on the ChromeOS devices you want, from Fleet's published update URL.
2. **Its policy carries `fleet_url` and `enroll_secret`.** The extension reads both out of Chrome's managed storage, which is to say out of the extension policy set in the Google Admin console. That is the entire configuration, and it is also your fleet placement: the enroll secret decides which fleet these hosts land in, exactly as it does for fleetd.

**The Fleet URL has to present a certificate the device already trusts.** There is no equivalent of packaging your own certificate authority into the agent here.

**It refuses to run anywhere but ChromeOS.** The extension checks the platform at startup and stops, logging that it will not run on a non-ChromeOS device under a managed install. Pushing it to your users' desktop Chrome browsers does nothing at all, and does it quietly. A development install is the only exception.

### What ChromeOS can actually answer

This is the part that gets misjudged in both directions, so it is worth being exact.

**Live reports work.** The extension enrolls at the ordinary osquery enrollment endpoint with the enroll secret and the device's serial number, then polls the same distributed read and write endpoints a real osquery agent uses. From Fleet's side a Chromebook is an osquery host on [channel 1](../01-foundations/1.2-how-fleet-reaches-a-device.md).

**Against a virtual database, not osquery.** There is no osqueryd here. The extension carries an in-memory SQLite database with **eleven tables of its own**, backed by Chrome's enterprise APIs, and this is all of them: `chrome_extensions`, `disk_info`, `geolocation`, `network_interfaces`, `os_version`, `osquery_info`, `privacy_preferences`, `screenlock`, `system_info`, `system_state`, `users`. Anything outside that set returns nothing, so a query written for a Mac will not run here.

**It polls on its own clock.** A one-minute alarm drives the whole cycle, so `distributed_interval` and the rest of osquery's agent options do not reach it.

**Scheduled reports do not work**, because the extension never posts to the logging endpoint. There is no result or status stream from a Chromebook.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Both platforms are verified from Fleet, because on neither can you go and look at the device.

**Android.** The host appears once Google pushes the enrollment event. If the device says it enrolled and Fleet has no host, the notification did not arrive, and the place to look is the return path rather than the device ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)). A device landing in the wrong fleet means the enroll secret inside the token belonged to a different one.

**ChromeOS.** The host appears and answers a live report against one of the eleven tables. `SELECT * FROM os_version` is the cheapest confirmation that the whole path works. A device with the extension installed and no host in Fleet either could not reach the URL, could not verify its certificate, or was given a secret Fleet does not recognise, and the extension's own console output on the device is where that shows.

## Who owns it afterwards

**The Android Enterprise binding**, and the Google account that created it. A Google account binds one enterprise, and deleting the enterprise removes the work profile from every enrolled device, which makes it a poor thing to reach for while troubleshooting ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)).

**The Fleet server URL**, which Android fixes. If a hostname change is anywhere in your plans, make it first.

**The Chrome extension policy**, which lives in Google's console rather than in Fleet. Nobody looking at Fleet can see it, and it holds an enroll secret.

## Reference and troubleshooting

Android diagnosis, including the tables, the two crons, the return path from Google and app installation through Managed Google Play, is [8.10](../08-troubleshooting/8.10-android-diagnostics.md). Setting up the enterprise is [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md).

There is no ChromeOS troubleshooting chapter, because there is little to troubleshoot: the extension either reaches Fleet with a good secret or it does not, and the answers are in the extension's own console output.
