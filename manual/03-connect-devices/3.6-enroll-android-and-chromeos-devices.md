# Enroll Android and ChromeOS devices

![Explanation](../_assets/icons/explanation.svg) Two platforms in one chapter because they share nothing with the other four and very little with each other. Neither runs the native fleetd bundle, though ChromeOS gets a browser extension confusingly named after it. Both involve Google, in completely different senses.

| | Android | ChromeOS |
|---|---|---|
| What manages the device | Google's Android Management API. A default deployment reaches it through a proxy Fleet operates, and Fleet also supports talking to Google directly | Nothing manages it through Fleet. Google's own console does |
| What Fleet runs on it | A narrow Fleet app, added with the host's policy, which enrols with Fleet and handles certificate installation. The **certificate templates it consumes are Fleet Premium**, so on Free the app is present with nothing to deliver | **Fleetd for Chrome**, a browser extension. Same name, none of the fleetd bundle: no Orbit, no osqueryd, no Fleet Desktop |
| What Fleet gets | Events Google pushes, plus certificate results from Fleet's own app and an hourly reconciliation Fleet initiates | Live report results, against eleven tables the extension implements itself |
| How a device is configured | An enrollment token, one per device | Extension policy in the Google Admin console |
| Prerequisite | An Android Enterprise bound to your Fleet server URL | A managed Chrome estate |

The Android Enterprise binding, and everything it commits you to, is [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md). Read it before enrolling anything, because two of its consequences are effectively permanent: your Fleet server URL is fixed once Android is on, and one server URL supports one enterprise.

## Android: choosing a path

**Ownership decides the path, and the path decides what you can do**, more sharply than on any other platform.

| Path | Use it when | What the console shows |
|---|---|---|
| **Work profile** | The device belongs to the person carrying it. Fleet manages a work profile beside their personal one | On (manual - personal) |
| **QR code at initial setup** | The device is company-owned and factory-fresh, or has been reset | On (company-owned) |

**The QR path exists only at the initial setup screen.** A device that has finished setup cannot take it without a factory reset. That is Google's constraint rather than something Fleet enforces, and Fleet's own material states it plainly: its enrollment page tells the reader to use a new or factory-reset device and tap the very first screen, and the contributor API reference says the QR contents can be used only there. It is a common way for a company-owned Android rollout to stall, because the devices were unboxed and handed out before anyone thought about management.

**Ownership also decides whether you can wipe the device.** Fleet refuses a wipe on a personally-owned Android host and says to unenroll instead, which is not a workaround so much as the same outcome by the supported route: unenrolling a work profile runs Google's own wipe of that profile underneath. Lock works on both. So the table above is also the lock-and-wipe table:

| Path | Lock | Wipe |
|---|---|---|
| Work profile (personal) | Yes, **Fleet Premium** | **No.** Unenroll instead, which removes the work profile |
| QR code (company-owned) | Yes, **Fleet Premium** | Yes, **and this one is free** |

Both need Android management configured, and **both** need Fleet to consider the host connected, on Free and Premium alike.

**Wipe on a company-owned Android host is the one lock-or-wipe operation Fleet Free has.** Every lock operation Fleet offers is Premium, and so is every wipe except this one; the free implementation refuses any host that is not Android and then applies the personal-ownership rule above. Read "every platform" as every platform Fleet supports the operation on at all, which does not include ChromeOS: there is no lock or wipe there to license. Worth knowing if a Free deployment needs a remote-wipe story, because Android company-owned is the only place it exists.

Work profile enrollment does not become company-owned later either, for the same reason. Decide before the device reaches a person.

**A third path exists and this manual cannot describe it.** Fleet's own MDM bug checklist names *Google account based* enrollment alongside the two above and says nothing else about it, and nothing at this release establishes how it is initiated or what MDM status it produces. It is left out of the table deliberately rather than guessed at; if you are using it, record what Fleet actually shows and treat that as the local answer ([8.13](../08-troubleshooting/8.13-escalation.md)).

### What both paths actually do

You do not build a package or deliver a profile. You ask Fleet for an **enrollment token** and give it to the device: as a link on the work-profile path, as a QR code on the other.

| Fact | Value |
|---|---|
| Where the token comes from | Fleet, which asks Google's API through its proxy |
| What Fleet puts inside it | Your enroll secret, and an identity-provider UUID where one applies |
| Reuse | **One device per token.** Fleet marks it single-use |
| Lifetime | One hour, which is Google's default and Fleet does not override it |

That payload is how a device Fleet has never seen ends up in the right fleet, and, **when an identity-provider UUID is included**, attached to a person. The UUID is optional: Fleet accepts an empty one where authentication is not required, and creates the person-to-device association only when it is present. An enrollment URL emailed round without it produces managed devices with no owner recorded.

It also means **a wrong enroll secret fails when the token is created, before any device is involved**, which is a much better place for it to fail than on a phone in someone's hand.

The one-hour lifetime is the other thing to plan around. A QR code printed into a provisioning runbook on Monday does not work on Tuesday.

[8.10](../08-troubleshooting/8.10-android-diagnostics.md#8108-enrollment-paths) has the token endpoint, the exact settings, and the enrollment failures worth recognising.

### Doing it

![How-to](../_assets/icons/howto.svg) Open **Add hosts**, choose **Android**, and pick **Personal (BYOD)** or **Company-owned (fully-managed)**. Fleet generates a different enrollment URL for each: the company-owned one carries `fully_managed=true`, which is what turns off personal usage on the resulting token. Copy the URL and send it to the person, or take the QR code for the company-owned path.

If the tab tells you to turn Android MDM on instead of showing a URL, the enterprise is not bound yet and [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) is where that happens.

### What you get, and what you do not

There is no osquery on Android and nothing resembling fleetd. Google pushes enrollment events and status reports to Fleet; Fleet also polls Google hourly to reconcile which devices still exist; and Fleet's Android app talks to Fleet directly for certificate work.

**Two exceptions to "Fleet only listens" matter.** Fleet ships a **narrow Android app**, added while assigning the host's policy, which enrols with Fleet, installs certificates and reports the results. The **certificate templates it consumes are Fleet Premium**, so on Free it is a device-side component with no work to do rather than one that is absent ([2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) explains why it exists: Google's API has no call for installing a client certificate). And Fleet **polls Google hourly** to reconcile which devices still exist, rather than relying only on being told. So a certificate problem has a device-side component, and a device's disappearance can be noticed without any notification.

What genuinely is absent: no live reports, no scheduled reports, no scripts. When an Android host misbehaves the evidence is mostly in Fleet's own tables and the return path from Google, which is [8.10](../08-troubleshooting/8.10-android-diagnostics.md), and partly on the device, in Android Device Policy's own screens.

**One identity consequence belongs at enrollment time**, because what it breaks is your asset process rather than Fleet: on a personally owned device with a work profile, the serial number and UUID Fleet reports are not hardware identifiers. They are an enterprise-specific ID, unique to that work profile in your organisation and stable across factory resets. [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) covers it.

## ChromeOS: an extension, and only on ChromeOS

![Explanation](../_assets/icons/explanation.svg) Fleet does not manage ChromeOS. Google's console does. What Fleet gets is a reporting agent, and that agent is a Chrome extension deployed the way you deploy any managed extension.

No MDM, no enrollment profile, no package. Two things have to be true:

1. **The extension is force-installed** on the ChromeOS devices you want, from Fleet's published update URL.
2. **Its policy carries `fleet_url` and `enroll_secret`.** The extension reads both out of Chrome's managed storage, which is to say out of the extension policy set in the Google Admin console. That is the entire configuration. The enroll secret places the host exactly as it does on the fleetd path, **which means it places a genuinely new host and does not move one Fleet already knows** ([3.1](3.1-enrollment-design-and-host-lifecycle.md)). Repointing the policy at another fleet's secret does not by itself move anything, and does not by itself re-enrol anything: the extension enrols when it has no node key, and re-enrols when a request is refused. A host that already holds a node key carries on where it is.

### Doing it

![How-to](../_assets/icons/howto.svg) Open **Add hosts**, choose **ChromeOS**, and Fleet gives you three things to paste into the Google Admin console: the **extension ID**, the **installation URL** of Fleet's update manifest, and a small **policy JSON** carrying `fleet_url` and `enroll_secret` already filled in for your server and the fleet you selected.

In Google Admin, scope those to the organisational unit you want and set the extension to **force install**. That is the whole of the deployment: there is nothing to run on the device and nothing to build.

**The policy JSON contains an enroll secret**, so treat the paste like the credential it is, and remember that it then lives in Google's console rather than in Fleet.

**The Fleet URL has to present a certificate the device already trusts.** There is no equivalent of packaging your own certificate authority into the agent here.

**It refuses to run anywhere but ChromeOS.** The extension checks the platform at startup, logs an error saying it will not run on a non-ChromeOS device under a managed install, and stops. So pushing it to your users' desktop Chrome browsers produces no Fleet host and leaves a message in the service-worker console. Whether anything is visible to the person at the machine is Chrome's business rather than the extension's, since a force-installed extension appears in the browser either way. A development install is the only exception.

### What ChromeOS can actually answer

This is worth being exact about, because the platform table's row of **no**s reads as though nothing can be asked.

**Live reports work.** The extension enrols at the ordinary osquery enrollment endpoint with the enroll secret and the device's serial number, then polls the same distributed read and write endpoints a real osquery agent uses. **It does this without running osqueryd**, which is the distinction to hold: Fleet's distributed channel is in use, osquery is not ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)).

**Against a virtual database, not osquery.** There is no osqueryd here. The extension carries an in-memory SQLite database with **eleven tables of its own**, and this is all of them: `chrome_extensions`, `disk_info`, `geolocation`, `network_interfaces`, `os_version`, `osquery_info`, `privacy_preferences`, `screenlock`, `system_info`, `system_state`, `users`.

Most are backed by Chrome's own APIs, and not all of those are enterprise ones: `disk_info` reads Chrome's storage API and **`geolocation` calls an external web service**, which is worth knowing before you run it across an estate.

**A query naming a table that is not there fails; it does not come back empty.** The extension catches the SQLite error and returns a status of 1 with the message, so Fleet shows the host as failing that report rather than as having nothing to say. That distinction matters because an empty result and an error mean opposite things about the host.

**It polls on its own clock, every ten seconds.** The main loop reschedules itself on a ten-second timer; the one-minute alarm people notice in the manifest exists to stop Chrome suspending the service worker, not to drive the cycle. Fleet's own host page reports the ChromeOS distributed interval as ten seconds and it is not configurable, so `distributed_interval` and the rest of osquery's agent options do not reach these hosts.

**Scheduled reports do not work**, because the extension never posts to the logging endpoint. There is no result or status stream from a Chromebook.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Both are verified from Fleet first, because neither gives you a shell. Neither is a black box either: Android has Android Device Policy's own screens and the Fleet app, ChromeOS has the extension's service-worker console, and both matter most in the case where Fleet has no host record to look at.

**Android.** Fleet can create the host from an `ENROLLMENT` notification, but receiving one is not sufficient. If the device says it enrolled and Fleet has no host, **the notification not arriving is one explanation and not the only one**: Fleet also validates the payload, re-checks the enroll secret embedded in the token, and does database work after receipt, any of which can fail on a notification that arrived perfectly. A status report for an unknown device can also enrol it, so the enrollment event is not the only path in. Start at the return path ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)) and rule out a received-but-rejected payload before concluding Google never called.

**A device landing in the wrong fleet does not necessarily mean the wrong secret.** On re-enrollment Fleet restores the device's **last known fleet** in preference to the token's, and does so even if the host row was deleted in between. So a device returning to where it used to be is Fleet working as designed; the secret decides placement for a device Fleet has genuinely never seen.

**ChromeOS.** The host appears and answers a live report against one of the eleven tables. `SELECT * FROM os_version` is the cheapest confirmation that the whole path works.

A device with the extension installed and no host in Fleet has not necessarily failed at the network. Before it ever makes a request the extension can refuse the platform, fail to initialise its database, or fail the two queries it uses to build the enrollment details; after that it can fail to reach the URL, fail to verify the certificate, or be refused the secret. **The service worker's console is where those separate, as far as they separate at all**: several of them log distinctly, and a failed request can collapse into a generic failure that does not say whether it was the URL, the certificate or the secret. Reach it from `chrome://extensions` on the device with developer mode on, through the extension's service-worker link, which is the path Fleet's own extension documentation describes. Go there before the firewall, and check the policy in Google Admin alongside it, because a value that never reached the extension looks the same from the console as a value it could not use.

## Who owns it afterwards

**The Android Enterprise binding**, and the Google account that created it. Deleting the enterprise makes Fleet delete it at Google, drop its own record, turn Android MDM off and mark every Android host unenrolled; Fleet's guidance is that the work profiles go from the devices too, which is Google's behaviour rather than something the checkout establishes. Either way it is a poor thing to reach for while troubleshooting ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)).

**The Fleet server URL**, which Android fixes. If a hostname change is anywhere in your plans, make it first.

**The Chrome extension policy**, which lives in Google's console rather than in Fleet. Nobody looking at Fleet can see it, and it holds an enroll secret.

Android diagnosis, including the tables, the two crons, the return path from Google and app installation through Managed Google Play, is [8.10](../08-troubleshooting/8.10-android-diagnostics.md).
