# Enroll Android devices

![Explanation](../_assets/icons/explanation.svg) Android is managed through Google's Android Management API, which a default deployment reaches through a proxy Fleet operates; Fleet also supports talking to Google directly. There is no fleetd here: what Fleet runs on the device is a narrow Fleet app, added with the host's policy, which enrols with Fleet and handles certificate installation, and the certificate templates it consumes are Fleet Premium, so on Free the app is present with nothing to deliver. A device is configured with an enrollment token, one per device, and the prerequisite is an Android Enterprise bound to your Fleet server URL.

The Android Enterprise binding, and everything it commits you to, is [2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md). Read it before enrolling anything, because two of its consequences are effectively permanent: your Fleet server URL is fixed once Android is on, and one server URL supports one enterprise.

## Android: choosing a path

**Ownership decides the path, and the path decides what you can do**, more sharply than on any other platform.

| Path | Use it when | What the console shows |
|---|---|---|
| **Work profile** | The device belongs to the person carrying it. Fleet manages a work profile beside their personal one | On (manual - personal) |
| **QR code at initial setup** | The device is company-owned and factory-fresh, or has been reset | On (company-owned) |

**The QR path exists only at the initial setup screen.** A device that has finished setup cannot take it without a factory reset. That is Google's constraint rather than something Fleet enforces, and Fleet's own material states it plainly: its enrollment page tells the reader to use a new or factory-reset device and tap the very first screen, and the contributor API reference says the QR contents can be used only there. It is a common way for a company-owned Android rollout to stall, because the devices were unboxed and handed out before anyone thought about management.

**Ownership also decides whether you can wipe the device.** Fleet refuses a wipe on a personally-owned Android host and says to unenroll instead, which is not a workaround so much as the same outcome by the supported route: unenrolling a work profile runs Google's own wipe of that profile underneath. Lock works on both. So the table above is also the lock-and-wipe table:

| Path | Lock | Wipe |
|---|---|---|
| Work profile (personal) | Yes, **Fleet Premium** | **No.** Unenroll instead, which removes the work profile |
| QR code (company-owned) | Yes, **Fleet Premium** | Yes, **and this one is free** |

Both need Android management configured, and **both** need Fleet to consider the host connected, on Free and Premium alike.

**Wipe on a company-owned Android host is the one lock-or-wipe operation Fleet Free has.** Every lock operation Fleet offers is Premium, and so is every wipe except this one; the free implementation refuses any host that is not Android and then applies the personal-ownership rule above. Read "every platform" as every platform Fleet supports the operation on at all, which does not include ChromeOS: there is no lock or wipe there to license. Worth knowing if a Free deployment needs a remote-wipe story, because Android company-owned is the only place it exists.

Work profile enrollment does not become company-owned later either, for the same reason. Decide before the device reaches a person.

**A third route appears only in Fleet's triage notes, not as a described path.** Fleet's own MDM bug checklist lists *Google account based* enrollment beside the two above and says nothing else about it, and nothing at this release establishes how it is initiated or what MDM status it produces. It is an open reference in Fleet's own notes rather than a capability this manual can teach, so it stays out of the table deliberately rather than being guessed at. If you are using it, record what Fleet actually shows and treat that as the local answer ([8.13](../08-troubleshooting/8.13-escalation.md)).

### What both paths actually do

You do not build a package or deliver a profile. You ask Fleet for an **enrollment token** and give it to the device: as a link on the work-profile path, as a QR code on the other.

| Fact | Value |
|---|---|
| Where the token comes from | Fleet, which asks Google's API through its proxy |
| What Fleet puts inside it | Your enroll secret, and an identity-provider UUID where one applies |
| Reuse | **One device per token.** Fleet marks it single-use |
| Lifetime | One hour, which is Google's default and Fleet does not override it |

That payload is how a device Fleet has never seen ends up in the right fleet, and, **when an identity-provider UUID is included**, attached to a person. The UUID is optional: Fleet accepts an empty one where authentication is not required, and creates the person-to-device association only when it is present. An enrollment URL emailed round without it produces managed devices with no owner recorded.

It also means **a wrong enroll secret fails when the token is created, before any device is involved**, which is a much better place for it to fail than on a phone in someone's hand.

The one-hour lifetime is the other thing to plan around. A QR code printed into a provisioning runbook on Monday does not work on Tuesday.

[8.10](../08-troubleshooting/8.10-android-diagnostics.md#8108-enrollment-paths) has the token endpoint, the exact settings, and the enrollment failures worth recognising.

### Doing it

![How-to](../_assets/icons/howto.svg) Open **Add hosts**, choose **Android**, and pick **Personal (BYOD)** or **Company-owned (fully-managed)**. Fleet generates a different enrollment URL for each: the company-owned one carries `fully_managed=true`, which is what turns off personal usage on the resulting token. Copy the URL and send it to the person, or take the QR code for the company-owned path.

If the tab tells you to turn Android MDM on instead of showing a URL, the enterprise is not bound yet and [2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md) is where that happens.

### What you get, and what you do not

There is no osquery on Android and nothing resembling fleetd. Google pushes enrollment events and status reports to Fleet; Fleet also polls Google hourly to reconcile which devices still exist; and Fleet's Android app talks to Fleet directly for certificate work.

**Two exceptions to "Fleet only listens" matter.** Fleet ships a **narrow Android app**, added while assigning the host's policy, which enrols with Fleet, installs certificates and reports the results. The **certificate templates it consumes are Fleet Premium**, so on Free it is a device-side component with no work to do rather than one that is absent ([2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md) explains why it exists: Google's API has no call for installing a client certificate). And Fleet **polls Google hourly** to reconcile which devices still exist, rather than relying only on being told. So a certificate problem has a device-side component, and a device's disappearance can be noticed without any notification.

What genuinely is absent: no live reports, no scheduled reports, no scripts. When an Android host misbehaves the evidence is mostly in Fleet's own tables and the return path from Google, which is [8.10](../08-troubleshooting/8.10-android-diagnostics.md), and partly on the device, in Android Device Policy's own screens.

**One identity consequence belongs at enrollment time**, because what it breaks is your asset process rather than Fleet: on a personally owned device with a work profile, the serial number and UUID Fleet reports are not hardware identifiers. They are an enterprise-specific ID, unique to that work profile in your organisation and stable across factory resets. [2.12](../02-administer-and-deploy-fleet/2.12-bind-android-enterprise.md) covers it.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) An Android enrollment is verified from Fleet first, because the platform gives you no shell. It is not a black box either: the device has Android Device Policy's own screens and the Fleet app, and they matter most in the case where Fleet has no host record to look at.

Fleet can create the host from an `ENROLLMENT` notification, but receiving one is not sufficient. If the device says it enrolled and Fleet has no host, **the notification not arriving is one explanation and not the only one**: Fleet also validates the payload, re-checks the enroll secret embedded in the token, and does database work after receipt, any of which can fail on a notification that arrived perfectly. A status report for an unknown device can also enrol it, so the enrollment event is not the only path in. Start at the return path ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)) and rule out a received-but-rejected payload before concluding Google never called.

**A device landing in the wrong fleet does not necessarily mean the wrong secret.** On re-enrollment Fleet restores the device's **last known fleet** in preference to the token's, and does so even if the host row was deleted in between. So a device returning to where it used to be is Fleet working as designed; the secret decides placement for a device Fleet has genuinely never seen.

## Who owns it afterwards

**The Android Enterprise binding**, and the Google account that created it. Deleting the enterprise makes Fleet delete it at Google, drop its own record, turn Android MDM off and mark every Android host unenrolled; Fleet's guidance is that the work profiles go from the devices too, which is Google's behaviour rather than something the checkout establishes. Either way it is a poor thing to reach for while troubleshooting ([8.10](../08-troubleshooting/8.10-android-diagnostics.md)).

**The Fleet server URL**, which Android fixes. If a hostname change is anywhere in your plans, make it first.
