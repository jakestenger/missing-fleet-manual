# Enroll macOS devices

![Explanation](../_assets/icons/explanation.svg) A Mac arrives in Fleet over two channels. **fleetd** brings queries, scripts, software and vitals. **MDM enrollment** brings profiles, commands, lock and wipe. Disk encryption needs both and is the clearest case for the split: MDM delivers the FileVault configuration, and the agent is what moves the recovery key into escrow ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). A Mac can have either channel without the other, and both states are normal for a while.

The thing to get right before anything else is **who delivers the agent**, because the obvious answer is wrong:

> **Fleet sends the agent to Macs it enrols in MDM, on the manual path as well as the automated one.** Both queue a post-enrollment task, and on macOS that task sends an `InstallEnterpriseApplication` command carrying Fleet's own agent package. Manual enrollment always sends it; ADE sends it unless you have turned that off. So delivering a package by hand is not the default step it looks like, and what Fleet guarantees is that the **command is sent**, not that the agent arrives.

That changes what this chapter is about. The decision is not "which path delivers the agent" but **"is this Mac being MDM-enrolled at all, is the agent-install command being sent, and did it land?"** Those are three questions rather than one, because a fleet using ADE's opt-out has deliberately stopped sending it.

[3.1](3.1-enrollment-design-and-host-lifecycle.md) covers what enrollment establishes in general: the host record, the fleet assignment, and the credentials. This chapter covers the macOS-specific part.

## The decision you are making

**How does MDM get turned on?** Decided by how the Mac was bought and how it reaches you.

| Path | Use it when | What the console shows |
|---|---|---|
| **Automated Device Enrollment (ADE)** | The Mac is in Apple Business and company-owned, and enrollment happens during Setup Assistant. **Needs Fleet Premium**, because operating an Apple Business token does | On (company-owned) |
| **Enrollment link, company-owned** | The Mac is not in Apple Business, or it is already deployed | On (manual) |
| **Enrollment link, personal (BYOD)** | The Mac belongs to the person using it | On (manual - personal) |

Those strings are what the **console** displays. The database and the API spell the first one `On (automatic)`, and the host filter spells it `automatic`; [8.6](../08-troubleshooting/8.6-server-state.md#one-status-three-vocabularies) has the mapping, and it matters the first time you write a query from something you read on screen.

**On all three, Fleet sends the agent-install command**, and on the two link paths it always does. ADE is the one with an opt-out, `setup_experience.macos_manual_agent_install`, which suppresses the command so a bootstrap package can deliver the agent instead; it is Fleet Premium and Fleet will not accept it without a bootstrap package configured. Building a package yourself is for the cases in the next section rather than as a matter of course.

### What personal enrollment actually changes

This is a capability boundary rather than a label. Fleet builds a personal enrollment profile with a **reduced set of MDM access rights**: it takes the full set and removes device lock and device erase. A company-owned profile carries all thirteen rights, a personal profile carries eleven.

So on a personally-enrolled Mac, Fleet cannot lock the device and cannot wipe it, and that is enforced by the profile the device is holding rather than by a Fleet-side permission you could change afterwards. Treat the choice as one you cannot expect to undo in place. Fleet exposes no way to change a delivered profile's access rights, and Apple's rules on narrowing rights in place are its own; nothing in Fleet's source establishes a supported path from one to the other.

The mechanism explains the status string. Fleet appends a `byod` parameter to the MDM server URL inside the personal profile. The MDM stack surfaces URL parameters to the check-in handler, which reads it during `Authenticate` and records it on the host record, where it becomes `host_mdm.is_personal_enrollment`. That is also why the distinction survives on the host rather than living only in whatever you clicked.

### What each path needs first

| Path | Prerequisites |
|---|---|
| ADE | Apple Business connected with an ABM token uploaded, an APNs certificate, and the device assigned to Fleet as its MDM server in Apple Business. [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md) covers all three |
| Either link | An APNs certificate. No Apple Business involvement |
| Anything | A Fleet URL the Mac can reach over TLS |

**Who can get the link matters more than it looks.** The enrollment link carries an enroll secret, and reading an enroll secret needs global or fleet-scoped admin or maintainer. Technicians, observers, Observer Plus and GitOps users cannot read one. If your help desk is expected to enroll machines, that is a role decision to take before the rollout rather than during it ([1.4](../01-foundations/1.4-identity-and-roles.md)).

## Enrolling by link, which is the ordinary manual path

![How-to](../_assets/icons/howto.svg) With Apple MDM configured, Fleet's **Add hosts** modal stops offering a package command for macOS and offers an **enrollment link** instead, with a company-owned or personal choice beside it. That link is the artifact: send it to the person holding the Mac.

The link is your Fleet URL's `/enroll` path carrying an enroll secret, plus `byod=true` when you picked personal. Underneath it is Apple's over-the-air enrollment, the same mechanism [3.5](3.5-enroll-ios-and-ipados-devices.md) describes for iPhones, and one consequence is worth carrying over: **the enroll secret in the link is what places the host.** Each link selects one placement scope, a named fleet or the global Unassigned scope, since an enroll secret may be global rather than fleet-scoped. That is not one link per scope: up to 50 secrets are supported, so several links can point at the same fleet, which is what makes staged rotation and separate distribution channels possible. The link is a credential.

The three paths above are the ordinary ones, distinguished by what the console then shows. They are not every artifact Fleet can hand a Mac: Premium also exposes an endpoint that downloads an unsigned manual enrollment profile, company-owned or personal, which is a way to enrol a Mac without the link and is described with the licence boundaries below.

**The link path is not licence-gated, and it is the one that makes Fleet Free usable for Macs.** The over-the-air enrollment service carries no licence check. What *is* Premium is the separate endpoint that downloads an unsigned manual enrollment profile, downloading the default Setup Assistant profile, and **Apple Business itself**: Fleet Free refuses to upload, list, renew or count ABM tokens, so ADE is out of reach on Free. Those are different artifacts from the link, and conflating them is how a Free deployment concludes it cannot enrol Macs at all.

**If end-user authentication is turned on** for the destination fleet, `/enroll` sends the person to your identity provider before it hands over anything, and the identity that comes back is attached to the host. **Turning it on is Fleet Premium**, so on Free the link enrols the Mac and tells you nothing about who has it. Decide and test that before sending links, because it changes what the end user sees and what you get ([2.5](../02-administer-and-deploy-fleet/2.5-identity-providers-sso-scim-and-role-sync.md)).

**Two prompts, not one.** macOS asks once to download the profile and once to install it in System Settings. A profile downloaded and never installed is the "it did not work" to rule out first on this path, because it costs one question to the person holding the Mac.

## The ADE sequence, in order

Worth reading once even if you never drive it by hand, because an ADE support question resolves to which of these did not happen.

1. The Mac is assigned to Fleet as its MDM server in Apple Business. Fleet learns about it on its next sync.
2. Fleet assigns the device an enrollment profile, which is what makes Setup Assistant offer, or require, enrollment.
3. The device reaches Setup Assistant and retrieves that profile from Apple.
4. It enrolls.
5. Fleet runs its post-enrollment work: the fleetd install command, unless this is ADE and the opt-out above is set, then a bootstrap package if you have one, and the setup experience. Sending the command is not the same as the install succeeding, which is the failure the rest of this chapter is about.

Steps 2 and 3 each leave a visible timestamp, and the gap between them is where ADE problems live. **Read the second one carefully: Fleet's own tooltip defines the pushed time as the last time Apple reported the host *retrieved* its assigned profile.** So an assignment time with no push time says the device has not collected the profile, not that Fleet failed to send anything. [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md#886-assignment-time-but-no-push-time) covers it.

**Setup Assistant behaviour is configured, not inherited.** Whether enrollment is mandatory, which panes are skipped, and whether the MDM profile can be removed are set by the profile Fleet sends Apple. [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md) owns that.

**Fleet placement on this path does not come from an enroll secret.** An ADE device is placed by the fleet configured against the ABM token for its platform, or by a move made before it enrolls ([3.1](3.1-enrollment-design-and-host-lifecycle.md), [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md)).

## Migrating a Mac from another MDM

![Explanation](../_assets/icons/explanation.svg) Moving a Mac that is already enrolled in another vendor's MDM, a Jamf, Intune, Workspace ONE or Kandji, into Fleet without wiping it is its own enrolment path. The constraint that shapes the whole feature is that Fleet cannot pull a Mac out of another MDM by itself: only the user or the old MDM holds that authority. So Fleet's part is to notice that a host is eligible, prompt the person through Fleet Desktop, and fire a webhook your own automation uses to release the Mac from its old MDM. When the Mac comes back unmanaged, it enrols into Fleet.

**Turning migration on is Fleet Premium, and it is a global setting rather than a per-fleet one.** It is a `macos_migration` block in the Apple MDM configuration with three fields: `enable`, the `mode` (`voluntary` or `forced`), and a `webhook_url`. Set it through the app configuration, either in the UI's MDM settings or as the `macos_migration` block in a GitOps organization-settings file. Set `enable` true, choose the mode, and give a `webhook_url` Fleet can call. Fleet validates all three the moment you enable it: Fleet Free is refused with a licence error, the mode has to be `voluntary` or `forced`, and the `webhook_url` has to parse as an `http` or `https` URL. That block is part of the wider Apple MDM configuration in [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md); how the mode then behaves on the Mac is the next section.

### Voluntary and forced decide how hard the prompt pushes

The mode is copied to Fleet Desktop, which decides on the client how insistent the prompt is. In **voluntary** mode the migration dialog waits in the Fleet Desktop tray until the person opens it. In **forced** mode Fleet Desktop shows the dialog at every interval and keeps bringing it back.

**Forced is insistent, not silent.** The dialog carries a Start and a Later button, and the migration begins only when the person clicks Start. Fleet has no way to migrate a Mac without that click, because it does not hold the old MDM's authority to unenrol the device. So forced buys persistence, and the end user is still the one who sets the migration going.

### Which Macs are eligible, and the version floor

Eligibility splits two ways, and the split matters because only one branch carries a macOS-version floor. Both branches need the Mac to be osquery-enrolled and currently managed by an MDM other than Fleet.

- A Mac **assigned to Fleet in Apple Business** is eligible for **ADE migration**. There is no macOS-version floor on this branch.
- A Mac that is **not** assigned in Apple Business is eligible for **manual migration**, and here Fleet requires the macOS version to be **strictly above 14.0.0**. So macOS 13 and exactly 14.0.0 are not offered manual migration, while 14.0.1 and later, and 15, are. The internal check is named as though the intent were "macOS after 14", but the comparison it actually makes admits 14.0.1 upward, and that literal behaviour is what a host is judged against.

### The device flow, and the two branches after unenrolment

Worth reading in order, because a migration support question resolves to which of these did not happen:

1. Fleet finds the host eligible and tells fleetd, which raises the migration prompt in Fleet Desktop.
2. In forced mode the prompt reappears at every interval; in voluntary mode it waits in the tray.
3. The person clicks Start, and Fleet Desktop asks Fleet to migrate the device over a device-authenticated request.
4. Fleet **posts your webhook**, carrying a small payload that identifies the host by id, UUID and hardware serial with a timestamp, and opens a **three-minute window** in which it refetches the host's critical queries to catch it leaving the old MDM. A successful post also suppresses another migration request for that host for those three minutes, so a second press inside the window returns success without re-firing.
5. Your automation, the receiver of the webhook, releases the Mac from its old MDM. Fleet only signals; the release is external.
6. Fleet detects the Mac is now unmanaged, and here the branches diverge into three routes, because ADE eligibility carries no version floor while the automatic re-enrolment screen is a Sonoma-and-later capability:
   - **Manual migration:** Fleet Desktop records the migration as manual and opens the **My Device** instructions, walking the user through the rest by hand.
   - **ADE on Sonoma (macOS 14) or later:** Fleet records the migration as ADE and the Mac proceeds toward the **Remote Management** flow, the Setup-Assistant-style screen that re-enrols an Automated Device Enrollment device.
   - **ADE before Sonoma (macOS 13 or earlier):** Fleet records the migration as `pre-sonoma` and opens the same by-hand instruction flow, since the Mac cannot take the Remote Management screen.
7. The Mac enrols into Fleet.

Know which branch a fleet is on, and which macOS versions it runs, before the prompts go out, because step 6 is the one place the end-user experience visibly differs.

The webhook contract, and its place among Fleet's other senders, is [6.5](../06-automate-fleet/6.5-integrations-webhooks-and-external-workflows.md#understand-each-webhook-contract). This migration press is one of the deliveries Fleet does not replay, so your receiver's own durability is the whole of your recovery if a post is missed. The equivalent for Windows is a separate feature and lives with Windows enrolment in [3.3](3.3-enroll-windows-devices.md); keep the two apart.

## When you do build a package

![How-to](../_assets/icons/howto.svg) Four cases. Three are planned, and the fourth is the one you meet after something went wrong.

- **Macs you are not putting in MDM at all.** An agent-only host is a perfectly good state if queries, scripts and software were what you wanted.
- **ADE, with the agent install deliberately turned off.** `setup_experience.macos_manual_agent_install` tells Fleet not to send the fleetd command on the ADE path, for deployments that would rather deliver the agent themselves. **Fleet will not let you set it without a bootstrap package**, and refuses with a message saying so, which is consistent: something has to carry the agent instead. **There is no equivalent switch on the manual path**, which always sends the command.
- **Getting the agent on before MDM**, or into a fleet the MDM path would not have chosen.
- **Recovering a half-enrolled Mac**, where the command was sent and the agent did not arrive. That is the fourth case, it applies to either enrollment path, and it is the one below.

```sh
fleetctl package --type=pkg \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="$FLEET_ENROLL_SECRET" \
  --fleet-desktop \
  --enable-scripts
```

The two optional flags are worth deciding rather than copying. `--fleet-desktop` includes Fleet Desktop, which is what gives the end user a menu bar item and the **My Device** page; without it the other components still run and the person on the Mac has no Fleet-facing surface at all. My Device works on Free, with Details and Software; **Self Service installation is Fleet Premium**, and so is Fleet Desktop's summary endpoint, so on Free the menu bar item has less to report.

`--enable-scripts` is **not** the permanent decision it is on other platforms. A Mac started without the flag polls Fleet's own fleetd configuration profile and turns scripts on from its `EnableScripts` value, which Fleet always sets to true in the profile it generates. So on an MDM-enrolled Mac carrying that profile, scripts end up enabled either way; on a Mac without it, the flag is the only answer. Check for the profile before rebuilding a package over this.

### Taking the URL and secret from a configuration profile

`--use-system-configuration` builds a package carrying no secret and no Fleet URL, reading both from an Apple configuration profile.

```sh
fleetctl package --type=pkg --use-system-configuration
```

Reach for it when you do not want the credential sitting inside an installer in a software repository. **It does not impose an installation order.** Orbit loops, logging at debug that the values are not there yet and retrying every thirty seconds, so a package installed before its profile waits rather than failing. If such a host is not enrolling, deliver the profile; do not reinstall the agent.

Once the values arrive, Orbit writes them into the Orbit root as `secret.txt` and `fleet_url.txt`. **`secret.txt` is not a reliable test of anything on macOS**, and it is worth abandoning the idea that its presence or absence classifies the host. An ordinary packaged secret may be moved into the Keychain and the file deleted. A `--use-system-configuration` package ships without the file, writes it when it reads the profile, and may migrate it to the Keychain on a later start. So absence is consistent with a healthy host of either kind, and does not establish that a profile has never arrived. Verify enrollment from the node key and the running processes instead.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Check both channels, because either can be the one that failed.

**From Fleet.** The host appears and its MDM status matches the path you used. A status of `Pending` means Apple Business has told Fleet about a device that has not enrolled yet, which is the expected state between steps 1 and 4 above.

**From the Mac**, with a shell or a script:

```sh
# Is MDM on, and to whom?
sudo profiles status -type enrollment

# Did fleetd install and enroll?
sudo ls -la /opt/orbit
sudo launchctl print system/com.fleetdm.orbit
```

`profiles status` answers the MDM half: whether the device came through Automated Device Enrollment, whether MDM enrollment is on and user-approved, and which server owns it. The presence of `secret-orbit-node-key.txt` in Orbit's root answers the fleetd half, and it is the file to look for rather than `secret.txt`. **`secret.txt` tells you nothing either way on macOS.** A packaged secret may be moved into the Keychain and the file deleted ([3.1](3.1-enrollment-design-and-host-lifecycle.md)); a `--use-system-configuration` host starts without the file, writes it once it reads its profile, and may then migrate it to the Keychain in turn. [8.4](../08-troubleshooting/8.4-host-side-investigation.md#844-macos-mdm-truth-from-the-host) reads both in detail.

**The two answers disagreeing is information, not a fault.** MDM on with no Orbit root is the half-enrolled state below. An Orbit root with no MDM is an ordinary agent-only host.

### The half-enrolled state is not an ADE problem

Because the agent is sent by MDM command on both enrollment paths, unless ADE's opt-out is set, and because that command is issued once with nothing retrying it, a Mac can complete enrollment perfectly and end up with **MDM on and no agent** whichever way it enrolled. On a fleet using the opt-out, the same end state is the configuration working rather than a failure, so establish which you are looking at first. The shape is the same and so is the recovery: build a package and install the agent, and leave the enrollment alone. That is the fourth package case above.

Audit for it after any bulk enrollment rather than assuming both channels arrived together. [8.1](../08-troubleshooting/8.1-diagnostic-method.md#the-half-enrolled-state) describes the shape and [8.4](../08-troubleshooting/8.4-host-side-investigation.md#845-the-half-enrolled-state-mdm-without-an-agent) covers detection and recovery.

## Who owns it afterwards

**The APNs certificate**, which Apple issues for a year and which takes every Apple device's MDM channel with it when it lapses. It is renewed with the Apple Account that created it, and Fleet's guidance is that losing that account means re-enrolling the estate. Those are Apple's rules rather than Fleet's, and the manual states them because they decide the renewal calendar; [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md) owns it.

**The gap between the two channels.** A count of Macs with MDM on and no recent osquery check-in is worth putting somewhere you look at regularly, rather than running it after someone complains.

## Reference and troubleshooting

The endpoints are in [a.8](../09-appendices/a.8-api-action-and-endpoint-reference.md), including the **three** a Mac enrolling by link needs on top of the MDM protocol paths: `/enroll`, the over-the-air enrollment profile endpoint, and the enrollment endpoint that profile then sends the device to. All three are shared with iOS and iPadOS rather than being mobile-only, which matters when a reverse proxy is deciding what to expose, and omitting the third leaves an enrollment that starts and never finishes.

When enrollment does not work, the split at the top of this chapter decides where to look. MDM problems, including APNs, the command queue and ADE sync, are [8.8](../08-troubleshooting/8.8-apple-mdm-diagnostics.md). fleetd problems, including an agent that never arrived, are [8.4](../08-troubleshooting/8.4-host-side-investigation.md).
