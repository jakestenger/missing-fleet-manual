# Enrollment design and host lifecycle

Enrollment is where a device acquires an identity inside Fleet. Which fleet it lands in, what identifier Fleet knows it by, and how it proves who it is on every later request are all settled here.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers what an enroll secret determines, how Fleet identifies a host, what happens when two devices claim the same identity, and how a host leaves. The per-platform procedures follow it, from [3.2](3.2-enroll-macos-devices.md) through [3.6](3.6-enroll-android-and-chromeos-devices.md).

**Three paths lead into Fleet, and most of this chapter describes one of them.**

| Path | Placed by | Identity carried by |
|---|---|---|
| **fleetd**, on macOS, Windows and Linux | The enroll secret used at install | Separate orbit and osquery node keys, optionally signed with a hardware certificate |
| **Apple and Android management enrollment** | A default fleet configured against the Apple Business token, or the Android enrollment flow | The management channel itself |
| **The fleetd Chrome extension**, on ChromeOS | The enroll secret configured in the extension | The extension's own enrollment |

Everything below about enroll secrets, host identifiers and hardware-backed identity is the fleetd path. Where a rule does not carry to the others, the text says so.

[1.3](../01-foundations/1.3-hosts-fleets-labels.md) establishes what a host record and a fleet are. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) establishes the channels a host talks over. Both are assumed here.

## What enrollment establishes

![Explanation](../_assets/icons/explanation.svg) Three things, and they have different lifetimes.

**A host record**, Fleet's durable representation of the device, which survives the agent being reinstalled.

**A fleet assignment**, which decides what configuration the device receives. On the fleetd path the enroll secret determines it. On automatic Apple enrollment it is instead the default fleet set per platform against the Apple Business token, as [2.7](../02-administer-and-deploy-fleet/2.7-apple-mdm-configuration.md) covers, so the secret is not the universal answer to where a host lands.

**Credentials for later requests.** The enroll secret authenticates the enrollment itself and nothing after it. What each component uses afterwards is its own node key: Fleet issues an **orbit node key** and an **osquery node key** separately, and they are stored separately, the first in a root-only file and the second inside osquery's own database. A hardware-backed certificate, where you use one, is an additional signature layered onto those requests rather than a replacement for them.

The middle one is the most commonly misread, so it is worth being exact: **an enroll secret places a genuinely new host, and does nothing to a host Fleet already knows.** Re-enrolling an existing device with a different fleet's secret leaves it where it is. Moving a host between fleets is a separate action, covered in [1.3](../01-foundations/1.3-hosts-fleets-labels.md).

## Enroll secrets

![How-to](../_assets/icons/howto.svg) An enroll secret belongs to a fleet, or to the global scope. Both Fleet Free and Fleet Premium allow more than one, and Premium allows them per fleet as well as globally, which is what makes rotation possible without a flag day.

**Revoking a secret is not only about new enrollments, which is the part that makes rotation hard to call finished.** Fleet documents that a host which enrolled with a revoked secret stops receiving `command_line_flags` updates. The route is indirect, and knowing it tells you when to expect the symptom: fleetd's ordinary config fetches authenticate with the Orbit node key rather than the secret, so flags keep flowing normally after a revocation. They stop at the point the host is forced to re-enrol and cannot, because the secret it still holds is no longer accepted. Everything else on that host keeps working, so the loss is silent and shows up later as hosts that ignore a flag change.

That gives rotation a real stop condition rather than a vague one. Before revoking, find every place the old secret is embedded: installer packages, configuration profiles, imaging and provisioning workflows, and any documented rebuild path. Distribute the replacement, confirm a fresh enrollment works with it, then revoke and watch for hosts that stop tracking flag changes. Fleet does not report which secret a given host enrolled with, so the check is behavioural rather than a list you can pull.

Where the secret lives on the device matters as much as which secret it is. On macOS and Windows, fleetd writes it into the system keystore at first launch, Keychain on macOS and Credential Manager on Windows, and reads it from there afterwards. Packaging with `--disable-keystore` opts out.

Two consequences follow, and both are easier to plan for than to diagnose.

**On macOS, a later fleetd installation must be signed by the same organization as the original** to read the secret back out of the Keychain. An installer signed by a different identity cannot reach it.

**The Keychain is not used when the enroll secret arrives through an MDM profile.** Fleet documents Keychain support for that path as coming, so at this release a profile-delivered secret is held only by the profile.

That has a sharp edge for config-less deployments, where the server URL and secret arrive entirely through a profile rather than being built into the package. Remove that profile and fleetd stops working until an equivalent one is installed. If the profile is delivered by MDM and MDM is later turned off, the profile goes with it.

## How Fleet tells two devices apart

![Explanation](../_assets/icons/explanation.svg) Fleet identifies a host by a hardware identifier, and the interesting cases are the ones where that identifier is not unique.

**By default, two devices sharing an identifier take turns owning one host record.** Fleet logs a warning and lets the newer enrollment overwrite the existing data. The visible symptom is a single host whose serial, hostname or platform keeps changing, rather than an error.

Cloning a virtual machine from a template that already has fleetd installed is the usual way to produce this. So is a mainboard replacement that reuses a hardware UUID.

**For a deliberate dual-boot or shared-identifier setup, tell fleetd not to use the hardware identifier.** Fleet's guidance is to install fleetd built with `--host-identifier=instance` on each operating system, which enrolls them as two separate hosts rather than one contested record.

**Switching a workstation's operating system is a delete-and-re-enroll.** Fleet's instruction is to delete the host before the switch and enroll it again afterwards, rather than letting the new installation inherit the old record.

## Hardware-backed identity on Linux

![Explanation](../_assets/icons/explanation.svg) Fleet Premium can issue each host a certificate whose private key lives in the machine's TPM, and require every request to carry a signature made with it.

The support boundary is narrow at this release. **Linux only**, from the `.deb`, `.rpm` and `.pkg.tar.zst` installers, on hardware with **TPM 2.0** or a vTPM, running **kernel 4.12 or later**. Package the agent with `--fleet-managed-host-identity-certificate` to use it.

The certificate lasts a year, and fleetd renews it at 180 days using a fresh TPM key. **Renewal does not need the enroll secret**, because it proves possession of the existing certificate's private key instead. That is the practical gain over a node key: a long-lived shared credential stops being the thing standing between an attacker and a working agent.

Four constraints are worth settling before committing to it.

1. **A host without TPM 2.0 fails to enroll** once the option is in the package. Fleet publishes a report for checking the estate first, which looks for `/dev/tpmrm0`.
2. **It cannot be combined with `--fleet-tls-client-certificate`.** The two client-certificate mechanisms are alternatives.
3. **Signing costs the server.** The signatures use P384 elliptic curve cryptography by default, which Fleet documents as requiring roughly 50 percent more CPU on the Fleet server. That is a capacity input for [2.9](../02-administer-and-deploy-fleet/2.9-self-hosting-architecture-and-capacity.md).
4. **Certificate requests are throttled** by the same `osquery.enroll_cooldown` server setting that throttles ordinary enrollments, so a mass rollout paces itself.

Adoption is per host rather than all at once. Once a host has requested a certificate, Fleet expects everything from that host to be signed, which lets certificate-carrying and ordinary hosts coexist during a migration. When the migration is finished, `auth.require_http_message_signature` makes signing mandatory server-wide, and hosts without a certificate stop being able to talk to Fleet.

Two request types are exempt from signing: the Orbit ping endpoint, and Fleet Desktop's own requests.

## Retiring a host

![How-to](../_assets/icons/howto.svg) Deleting a host in Fleet removes the record and uninstalls nothing. Whatever was putting that host into Fleet is still doing so, and the record comes back.

**What you have to stop first depends on the path the host arrived by**, which is the practical reason the paths are worth separating.

- On the **fleetd path**, a device with a working agent and a valid secret re-enrolls within minutes. Stop the agent, then delete.
- On **automatic Apple enrollment**, there is no agent to stop on iOS and iPadOS, and the device is assigned to your Fleet server in Apple Business. Deleting the Fleet record while that assignment stands means the next sync brings it back. The assignment upstream is the thing to change.

The shape is the same in both cases and the remedy is not: deletion alone does not retire a host. The platform chapters cover what stopping means on each.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) A host appearing in the list has enrolled. That is a smaller claim than it looks, and these checks separate it from a host that is working.

- The host appears with the **expected fleet** rather than in Unassigned, which confirms the secret you think was used is the one that was used.
- Its **identifier looks right**: a real serial where you expect one, and a stable value across two refreshes rather than one that alternates.
- **Inventory has arrived**, which on macOS, Windows and Linux means fleetd is running rather than merely installed.
- If you use host identity certificates, the host has **both certificate files on disk**, which is what Fleet's published policy checks for.
- A **representative action completes**. Enrollment establishes that the host reached Fleet and authenticated, which is a weaker claim than the host being able to do work. [2.1](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md) covers why that distinction decides whether a pilot has succeeded.

Ownership divides in a way worth adding to the record from [2.1](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md). Enroll secrets are credentials and need a named owner and a rotation plan. The signing identity used for macOS packages needs one too, because it is what lets a future installer read the Keychain. Whoever builds installers owns the packaging flags, which is where the identity decisions in this chapter are actually made.

## Precedence and edge cases

![Reference](../_assets/icons/reference.svg) A few behaviours here follow from the sections above and still catch people.

An enroll secret decides placement for new hosts, so re-issuing installers with a different secret does not reorganise an existing estate.

A deleted host with a live agent comes back, which is the mechanism behind most reports of hosts reappearing after a cleanup.

Two devices sharing a hardware identifier raise no error by default, so an estate can carry the problem for a long time before anyone notices a host whose details keep changing.

Once host identity certificates are enforced server-wide, a host that loses its TPM state has no path back except re-enrollment.
