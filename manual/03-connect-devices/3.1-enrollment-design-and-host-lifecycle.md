# Enrollment design and host lifecycle

Enrollment is where a device acquires an identity inside Fleet. Which fleet it lands in, what identifier Fleet knows it by, and how it proves who it is on the requests that follow are all settled here.

## Purpose and scope

![Explanation](../_assets/icons/explanation.svg) This chapter covers what an enroll secret determines, how Fleet identifies a host, what happens when two devices claim the same identity, and how a host leaves. The per-platform procedures follow it, from [3.2](3.2-enroll-macos-devices.md) through [3.7](3.7-enroll-chromeos-devices.md).

**Several paths lead into Fleet, and most of this chapter describes one of them.**

| Path | Placed by | Identity carried by |
|---|---|---|
| **fleetd**, on macOS, Windows and Linux | The enroll secret used at install, which places a host Fleet has not seen before. A **global** secret places it in Unassigned rather than a named fleet | Separate orbit and osquery node keys, optionally signed with a hardware certificate |
| **Apple automated enrollment (ADE), and account-driven enrollment**. **Both Fleet Premium**, since Free refuses ABM tokens and the account-driven service outright | A default fleet configured against the Apple Business token. That token carries four: macOS, iOS, iPadOS, and BYOD, which is the one a **tokenized** account-driven enrollment uses. This release still serves a legacy tokenless account-driven path, whose challenge names no token and therefore has no token-derived fleet ([3.5](3.5-enroll-ios-and-ipados-devices.md)) | The management channel itself |
| **Apple enrollment by link**, on macOS, iOS and iPadOS | **The enroll secret in the link**, exactly as on the fleetd path. No Apple Business token is involved | The management channel itself |
| **Windows MDM enrollment** | Not placed by this channel. A Windows host gets its fleet from the fleetd row above. MDM enrollment is separate: Fleet can start it from the agent on any edition, while the Settings-app and Entra-backed paths need Entra tenant and client IDs that **Fleet Free rejects** ([3.3](3.3-enroll-windows-devices.md)) | The management channel itself |
| **Android management enrollment** | The enroll secret Fleet puts inside the enrollment token, **for a device Fleet has not seen before**; on a re-enrollment Fleet restores the device's last known fleet instead ([3.6](3.6-enroll-android-devices.md)) | The management channel itself |
| ***Fleetd for Chrome***, the browser extension, on ChromeOS | The enroll secret in the extension's policy, and only for a host Fleet has not seen before | The extension's own enrollment |

Everything below about enroll secrets, host identifiers and hardware-backed identity is the fleetd path. Where a rule does not carry to the others, the text says so.

[1.3](../01-foundations/1.3-hosts-fleets-labels.md) establishes what a host record and a fleet are. [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) establishes the channels a host talks over. Both are assumed here.

## What enrollment establishes

![Explanation](../_assets/icons/explanation.svg) Three things, and they have different lifetimes.

**A host record**, Fleet's durable representation of the device, which survives the agent being reinstalled.

**A fleet assignment**, which decides what configuration the device receives. On the fleetd path the enroll secret determines it. On automatic Apple enrollment it is instead the default fleet set per platform against the Apple Business token, as [2.10](../02-administer-and-deploy-fleet/2.10-apple-mdm-configuration.md) covers, so the secret is not the universal answer to where a host lands.

**Credentials for later requests.** The enroll secret authenticates the enrollment itself and nothing after it. What each component uses afterwards is its own node key: Fleet issues an **orbit node key** and an **osquery node key** separately, and they are stored separately, the first in a root-only file and the second inside osquery's own database. A hardware-backed certificate, where you use one, is an additional signature layered onto those requests rather than a replacement for them.

The middle one is the most commonly misread, so it is worth being exact: **an enroll secret places a genuinely new host, and does nothing to a host Fleet already knows.** Re-enrolling an existing device with a different fleet's secret leaves it where it is. Moving a host between fleets is a separate action, covered in [1.3](../01-foundations/1.3-hosts-fleets-labels.md).

## Enroll secrets

![How-to](../_assets/icons/howto.svg) An enroll secret belongs to a fleet, or to the global scope. Both Fleet Free and Fleet Premium allow more than one, and Premium allows them per fleet as well as globally, which is what makes rotation possible without a flag day.

**Revoking a secret does not disturb hosts that already enrolled with it**, and that is the part that makes rotation hard to call finished. An enrolled host authenticates its ordinary work with the node key it was issued, not with the secret, so revoking the secret neither invalidates that key nor prompts a re-enrollment. The host carries on exactly as before.

What revocation does is close the door behind it. A host that later needs to enrol again, for any reason, presents a secret Fleet no longer accepts and cannot get back in. That is a latent failure rather than an immediate one, and it surfaces at a moment you did not choose.

**Fleet does not record which secret a given host enrolled with**, so there is no list to pull and no clean behavioural test either. Treat rotation as an inventory problem instead: before revoking, find every place the old secret is embedded, in installer packages, configuration profiles, imaging and provisioning workflows and any documented rebuild path. Distribute the replacement, confirm a fresh enrollment works with it, and keep the old secret valid until you are satisfied that nothing still hands it out.

Where the secret lives on the device matters as much as which secret it is. On macOS and Windows, fleetd writes it into the system keystore at first launch, Keychain on macOS and Credential Manager on Windows, and reads it from there afterwards. Packaging with `--disable-keystore` opts out.

Two consequences follow, and both are easier to plan for than to diagnose.

**On macOS, a later fleetd installation must be signed by the same organization as the original** to read the secret back out of the Keychain. An installer signed by a different identity cannot reach it.

**A profile-delivered enroll secret does not go straight into the Keychain**, and Fleet documents Keychain support for that path as coming rather than available.

**It is not held only by the profile, though.** When Orbit reads the values out of the configuration profile it **writes them to local files** in its root directory, `secret.txt` and `fleet_url.txt`, and on a later start it falls back to those files when no profile is present. So removing the profile from a host that has already read it does not stop fleetd, and on macOS the secret may by then have been migrated into the Keychain and the file removed anyway. What the missing profile does break is a host that has never read one, which is the state a config-less package ships in ([3.2](3.2-enroll-macos-devices.md)).

## How Fleet tells two devices apart

![Explanation](../_assets/icons/explanation.svg) Fleet identifies a host by a hardware identifier, and the interesting cases are the ones where that identifier is not unique.

**By default, two devices sharing an identifier take turns owning one host record.** Fleet logs a warning and lets the newer enrollment overwrite the existing data. The visible symptom is a single host whose serial, hostname or platform keeps changing, rather than an error.

Cloning a virtual machine from a template that already has fleetd installed is the usual way to produce this. So is a mainboard replacement that reuses a hardware UUID.

**For a deliberate dual-boot or shared-identifier setup, tell fleetd not to use the hardware identifier.** Fleet's guidance is to install fleetd built with `--host-identifier=instance` on each operating system, which enrolls them as two separate hosts rather than one contested record. **It does not survive Apple MDM.** On macOS, iOS and iPadOS, Fleet matches hosts by serial during Apple MDM enrollment, and the tagged tests call that combination incompatible and verify that the records merge anyway.

**Switching a workstation's operating system is a delete-and-re-enroll.** Fleet's instruction is to delete the host before the switch and enroll it again afterwards, rather than letting the new installation inherit the old record.

## Hardware-backed identity on Linux

![Explanation](../_assets/icons/explanation.svg) Fleet Premium can issue each host a certificate whose private key lives in the machine's TPM, and require the host's requests to carry a signature made with it. "Every request" is close but not exact: the signature middleware covers the Orbit, osquery and certificate-request routes, and Orbit's ping is deliberately outside it.

The support boundary is narrow at this release. **Linux only**, from the `.deb`, `.rpm` and `.pkg.tar.zst` installers, on hardware with **TPM 2.0** or a vTPM, running **kernel 4.12 or later**. Package the agent with `--fleet-managed-host-identity-certificate` to use it.

The certificate lasts a year, and fleetd renews it once **180 days of life remain**, which is around day 185 rather than day 180, with jitter so an estate does not renew in lockstep. It uses a fresh TPM key each time. **Renewal does not need the enroll secret**, because it proves possession of the existing certificate's private key instead. That is the practical gain over a node key: a long-lived shared credential stops being the thing standing between an attacker and a working agent.

Four constraints are worth settling before committing to it.

1. **A host without TPM 2.0 fails to enroll** once the option is in the package. Fleet publishes a report for checking the estate first, which looks for `/dev/tpmrm0`.
2. **It cannot be combined with `--fleet-tls-client-certificate`.** The two client-certificate mechanisms are alternatives.
3. **Signing costs the server.** The signatures use P384 elliptic curve cryptography by default, which Fleet documents as requiring roughly 50 percent more CPU on the Fleet server. That is a capacity input for [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md).
4. **Repeat certificate requests are throttled** by the same `osquery.enroll_cooldown` server setting that throttles ordinary enrollments. It rejects a fresh request for a certificate name whose existing certificate is still recent, so it protects against a host looping rather than pacing a rollout: a thousand hosts asking for the first time are a thousand first requests and none of them is throttled.

Adoption is per host rather than all at once. Once a host has a certificate, Fleet requires a matching signature on the Orbit and osquery traffic it protects, which lets certificate-carrying and ordinary hosts coexist during a migration. When the migration is finished, `auth.require_http_message_signature` makes signing mandatory server-wide, and hosts without a certificate stop being able to talk to Fleet.

Two request types are exempt from signing: the Orbit ping endpoint, and Fleet Desktop's own requests.

## Retiring a host

![How-to](../_assets/icons/howto.svg) Deleting a host in Fleet removes the record and uninstalls nothing. Whatever was putting that host into Fleet is still doing so, and the record comes back.

**What you have to stop first depends on the path the host arrived by**, which is the practical reason the paths are worth separating.

- On the **fleetd path**, a device with a working agent and a valid secret re-enrolls within minutes. Stop the agent, then delete.
- On **automatic Apple enrollment**, there is no agent to stop on iOS and iPadOS, and the device is assigned to your Fleet server in Apple Business. Deleting the Fleet record while that assignment stands brings it straight back: the deletion invokes the MDM lifecycle, which restores the pending host immediately rather than waiting for a sync. The assignment upstream is the thing to change.

The shape is the same in both cases and the remedy is not: deletion alone does not retire a host. The platform chapters cover what stopping means on each.

## Verification and ownership

![How-to](../_assets/icons/howto.svg) A host appearing in the list has usually enrolled, and on Apple it may not have: an Apple Business sync creates a pending record before the device has contacted Fleet at all. Even where it has enrolled, that is a smaller claim than it looks, and these checks separate it from a host that is working.

- The host appears with the **expected fleet**. Do not read Unassigned as proof of the wrong secret: an enroll secret can be global rather than fleet-scoped, and a global one legitimately places a new host in Unassigned.
- Its **identifier looks right**: a real serial where you expect one, and a stable value across two refreshes rather than one that alternates.
- **Inventory has arrived**, which on macOS, Windows and Linux means fleetd is running rather than merely installed.
- If you use host identity certificates, the host has **both certificate files on disk**, which is what Fleet's published policy checks for.
- A **representative action completes**. Enrollment establishes that the host reached Fleet and authenticated, which is a weaker claim than the host being able to do work. [2.1](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md) covers why that distinction decides whether a pilot has succeeded.

Ownership divides in a way worth adding to the record from [2.1](../02-administer-and-deploy-fleet/2.1-administration-model-and-deployment-choices.md). Enroll secrets are credentials and need a named owner and a rotation plan. The signing identity used for macOS packages needs one too, because it is what lets a future installer read the Keychain. Whoever builds installers owns the packaging flags, which is where the identity decisions in this chapter are actually made.

## Precedence and edge cases

![Reference](../_assets/icons/reference.svg) A few behaviours here follow from the sections above and still catch people.

An enroll secret decides placement for hosts Fleet has not seen before, so re-issuing installers with a different secret does not reorganise an existing estate. Android goes further and restores a device's previously recorded fleet on re-enrollment in preference to the secret's ([3.6](3.6-enroll-android-devices.md)).

A deleted host with a live agent comes back, which is the mechanism behind most reports of hosts reappearing after a cleanup.

Two devices sharing a hardware identifier raise no error by default, so an estate can carry the problem for a long time before anyone notices a host whose details keep changing.

Once host identity certificates are enforced server-wide, a host that loses its TPM state has no path back except re-enrollment.
