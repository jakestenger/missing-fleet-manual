# Enroll Windows devices

![Explanation](../_assets/icons/explanation.svg) Windows arrives in Fleet over two independent channels, which it shares with macOS and not with Linux, since Linux has no MDM at all ([1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md)). **fleetd** brings queries, scripts, software and vitals. **Windows MDM** brings profiles and commands.

The channels stay independent, exactly as [1.2](../01-foundations/1.2-how-fleet-reaches-a-device.md) describes: either can arrive without the other and a host can sit half-enrolled indefinitely. What Windows adds is **conditional automation between them**, in both directions:

- **fleetd enrolls, and Fleet starts MDM enrollment.** With Windows MDM turned on, automatic enrollment left on, and the host eligible, Fleet's reply to an ordinary agent check-in tells fleetd to register the device for management. Nobody delivers a profile and nobody clicks anything.
- **MDM enrolls, and Fleet pushes fleetd.** On the Microsoft Entra ID paths, where the device reaches Fleet before any agent exists, Fleet queues an install command.

Neither is guaranteed, and both have conditions this chapter sets out. So the useful question on Windows is **"which channel arrived first, and did the automation for the other one fire?"**

**Disk encryption is the clearest case of the two channels being separate.** BitLocker enforcement is **Fleet Premium**, and it is not an MDM command: Fleet sets it in the **Orbit configuration response** and the agent does the encrypting locally. MDM enrollment is only a gate on Fleet setting it. So a host with fleetd and no MDM gets no enforcement, and a host with MDM and no agent gets none either, and neither failure appears in the MDM command queue.

## The decision you are making

**How does the device first reach Fleet?** That is the choice, and it is made by how the machine is provisioned rather than by a setting you pick afterwards.

| Path | Use it when | What the console shows |
|---|---|---|
| **Agent-driven** | Fleet's default, and the one to plan for. You can get fleetd onto the machine by any means you already have | On (manual) |
| **Autopilot / Entra** | New hardware you want provisioned at first boot, through Microsoft's out-of-box experience | On (company-owned) |
| **Settings app** | The person holding the device turns management on themselves, under **Settings > Access work or school** | On (manual) |

Those strings are what the **console** shows. The database and the API spell the Autopilot case `On (automatic)`, and the host filter spells it `automatic`; [8.6](../08-troubleshooting/8.6-server-state.md#one-status-three-vocabularies) has the mapping, and it matters the first time you write a query from something you read on screen.

**Company-owned is narrower than "enrolled through Entra".** Fleet marks a Windows host as automatically enrolled only when the enrollment type is automatic **and** the enrollment happened during the out-of-box experience. An Entra-driven enrollment on a machine that has already finished setup does not qualify, however it was initiated, and lands as `On (manual)`. That is the mechanism behind the Settings-app row above, and the reason a device that missed Autopilot at first boot cannot be given company-owned status by enrolling it afterwards.

**There is no personal enrollment on Windows.** Fleet records personal enrollment as false for every Windows host, so `On (manual - personal)` is a status these devices cannot reach. The ownership distinction macOS, iOS and Android all carry does not exist here.

**Two of the three need Microsoft Entra ID** and a connection between Entra and Fleet that [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) sets up. **Those two are Fleet Premium as well as Microsoft-licensed**, since Fleet Free rejects the Entra tenant and client IDs outright, so a Free deployment has the agent-driven path and nothing else. They also need Microsoft licences, per person, and Fleet's own Autopilot notes describe the end-user requirement as its **current understanding** rather than something verified end to end, so price the rollout against Microsoft's terms rather than against 2.8's summary. The agent-driven path needs none of it, which is why it is the one to start with and the one to fall back to when an Entra problem is blocking a rollout.

### What Windows MDM needs before any of this

A WSTEP certificate and key supplied to the server, and Windows MDM turned on. Both are [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md). Until Windows MDM is on, fleetd still enrolls and everything agent-side works; there is simply no MDM channel to be on.

Fleet's guidance is that turning Windows MDM on **disables Windows tamper protection** on the host. That is a claim about Windows rather than about Fleet, and **nothing in Fleet's source at this release establishes it**, so treat it as a thing to confirm on a test machine rather than a fact to quote in a compliance answer. It is worth raising early either way, because the answer changes a security posture.

## Agent-driven enrollment, which is the default

![Explanation](../_assets/icons/explanation.svg) This is the path that needs nothing outside Fleet, and it is worth understanding as a mechanism because almost none of it is visible as a step you perform.

With Windows MDM on **and automatic enrollment left enabled**, Fleet decides on **every Orbit configuration check-in** whether that host should be enrolled. Turning on `enable_turn_on_windows_mdm_manually`, which is the Premium setting described later in this chapter, switches this whole mechanism off, so treat it as a fifth condition sitting above the four below. When it holds, four more conditions have to hold as well:

| Condition | What it means when it does not hold |
|---|---|
| The host's platform is Windows | Nothing happens |
| The host is **enrolled with osquery** | fleetd installed but not yet enrolled is not enough. This is the ordering that matters |
| The host is **not a Windows Server** | Servers are excluded, and the check happens twice, see below |
| The host is **not enrolled in any MDM**, Fleet's or anyone else's | A host still attached to its previous manager is skipped, unless migration is turned on |

When all four hold, Fleet's reply to that check-in carries a flag and a discovery URL. Orbit calls into Windows' own management registration API, and the device runs the enrollment exchange against Fleet from there.

**The hourly throttle is narrower than it reads.** Orbit records the time of its last enrollment attempt **only when the registration call succeeds**, and compares the hour against that. A call that returns an error leaves the recorded time unchanged, so the next configuration check-in tries again, which on the default cadence is thirty seconds later rather than an hour. The hour applies to the other case: registration returned success and Fleet still considers the host unenrolled, so Orbit is asked again and waits before repeating itself.

So a persistently failing Windows enrollment produces a **fast** loop in the agent log rather than an hourly one, with nothing in the console to say so. That is the contrast with macOS, where Fleet issues the fleetd install once and nothing retries it ([3.2](3.2-enroll-macos-devices.md)).

**One error does stop it.** If the device reports that it is a Windows Server, Orbit records that in memory and makes no further registration call for the life of the process. Every other error retries.

**The Windows Server exclusion is checked in two places, and they are not the same check.** Fleet's side reads what osquery reported about the host. Orbit's side reads the installation type from the machine itself before doing anything, refuses if it says server, and remembers that answer for the life of the process. So a Windows Server that Fleet has not correctly identified will be told to enroll, will refuse locally, and will look from the console exactly like a host that is failing to enroll.

Fleet's own record starts out saying the host is not a server and lets osquery correct it from the reported installation type, with a source comment saying exactly that. So on a genuinely new host the two sides can disagree for one detail-query cycle, which is a window rather than a fault. [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md) reads the host side.

### Turning the automatic behaviour off

There is a setting for estates that do not want enrollment happening unasked: `enable_turn_on_windows_mdm_manually`. Turn it on and Fleet stops sending the flag, leaving the end user to enroll through **Settings > Access work or school**. Either way the resulting MDM status is `On (manual)`; what changes is who initiates.

The setting has three constraints:

- It is **Fleet Premium**. Fleet Free rejects it with a licence error.
- It cannot be set unless Windows MDM is already on. Fleet refuses the combination.
- It is **mutually exclusive with Windows MDM migration**, and Fleet refuses both at once with a message saying to enable only one. That is consistent rather than arbitrary: migration exists to move hosts without asking anyone.

Fleet documents it as configurable only for all fleets rather than per fleet.

## Installing fleetd

![How-to](../_assets/icons/howto.svg) You build an MSI, then deliver it with whatever already delivers software to your Windows estate.

```sh
fleetctl package --type=msi \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --fleet-desktop \
  --enable-scripts
```

`--fleet-desktop` includes Fleet Desktop, which gives the end user a tray item and the **My Device** page. My Device works on Free, with its Details and Software tabs; **Self Service installation is Fleet Premium**, as is Fleet Desktop's summary endpoint, so on Free the tray item has less to report. Without the flag, the other components still run and the person on the machine has no Fleet-facing surface at all. `--enable-scripts` sets whether this host will run scripts by default.

**On Windows both of those are defaults rather than decisions**, which is the difference from the other platforms. The MSI exposes `FLEET_DESKTOP` and `ENABLE_SCRIPTS` as installer properties, and a value supplied at install time overrides whatever the package was built with, as the property table below shows. So a package built without `--enable-scripts` does not produce hosts you can never run a script against; it produces hosts that will not run scripts unless somebody passes the property.

Two flags behave differently here than on macOS. `--arch` accepts `arm64` for MSI packages, so Windows on ARM is a supported target. And `--use-system-configuration`, which is how a Mac takes its URL and secret from a configuration profile, is **rejected for MSI**: Fleet accepts it only for `pkg`. Windows has its own answer to the same problem, below.

### Build one base MSI and supply the rest at install time

![Explanation](../_assets/icons/explanation.svg) An MSI built by `fleetctl package` is not a sealed artifact the way the macOS `pkg` is. Six of its settings are exposed as **installer properties**, so the tool pushing the file supplies them at install time and overrides whatever was baked in:

| Property | What it sets |
|---|---|
| `FLEET_URL` | The Fleet server the agent talks to |
| `FLEET_SECRET` | The enroll secret, written into `secret.txt` during install |
| `ENABLE_SCRIPTS` | Whether this host will run scripts |
| `FLEET_DESKTOP` | Whether Fleet Desktop runs |
| `END_USER_EMAIL` | The address recorded against the host |
| `EUA_TOKEN` | End-user attribution on the Entra paths. Fleet sets this one, not you |

**Getting a credential-free installer takes a specific build, and the command above is not it.** You can omit both `--fleet-url` and `--enroll-secret`; what `fleetctl package` rejects is one without the other. But omitting them is the wrong move, because the MSI carries the `--enroll-secret-path` argument **only when a build-time secret was supplied**. A package built without one writes `secret.txt` at install time and never reads it. The build Fleet's own contributor documentation uses passes the literal string `dummy` for both:

```sh
fleetctl package --type=msi --fleet-url=dummy --enroll-secret=dummy
```

`dummy` is a recognised sentinel rather than a value. It suppresses writing the secret into the artifact while keeping the command-line path in place, so the resulting MSI has no credential in it and is ready to be told one:

```powershell
msiexec /i fleet-osquery.msi /quiet FLEET_URL="https://fleet.example.com" FLEET_SECRET="<secret>" ENABLE_SCRIPTS="True"
```

That is one artifact in the software repository with no credential inside it, or one artifact serving several fleets with a different secret per deployment group. It is the same problem `--use-system-configuration` solves on macOS, solved by the platform's own installer mechanism rather than by a configuration profile.

**The same sentinel is a trap at install time.** `FLEET_SECRET` defaults to `dummy`, and the install-time script that writes `secret.txt` skips the write when the value is empty **or literally `dummy`**. A deployment tool that passes the placeholder through, or a scripted install where the variable expanded to nothing, runs cleanly and enrolls with whatever secret was baked in at build time, or with none at all. Nothing reports the substitution. When a batch of hosts lands in the wrong fleet or does not appear, this is one of the things to check, and it is cheap because the answer is in the deployment tool's own command line.

**Everything else is build-time.** The update URL, the TUF channels, `--insecure`, `--debug`, the host identifier, the osquery database path and the setup-experience switch are written into the service's command line when the package is built. Changing any of those means building another package.

### When Fleet installs fleetd for you

On the Entra paths the device is in MDM before any agent exists, so Fleet pushes one down. The rule for when this happens is precise, and knowing it explains why the mechanism appears to be missing on the agent-driven path:

**Fleet enqueues the fleetd install only for enrollments that carry a user principal name**, which is to say the Entra ones. Agent-driven enrollments authenticate with Orbit's node key instead, and Fleet treats those as already having an agent, which they do.

When it does fire, it fires on a **management session from a device Fleet believes has no working agent**, and that check is stricter than "is fleetd installed". Fleet also wants an agent check-in recent enough relative to the enrollment: a check-in counts as evidence of a working agent if it happened at any time after the enrollment, **or up to 90 seconds before it**. That grace window is what stops a device re-enrolling moments after a normal check-in from being sent a redundant installer. A device whose last check-in predates its enrollment by more than that gets the install enqueued again.

Four properties of that install are decided for you:

- **The MSI is fetched by the device from Fleet's download service**, and the server hands the device a SHA-256 taken from a metadata document the server fetches itself. Two separate egress paths therefore have to work: Fleet outbound to the download service, and the device outbound to wherever the MSI is served. Fleet failing to fetch the metadata is a warning in the log and not an error, and the session continues without the install.
- **Scripts are enabled.** The install command sets `ENABLE_SCRIPTS="True"` unconditionally, whatever your own packages do.
- **A global enroll secret has to exist, and Fleet uses the first of them.** With none configured, Fleet logs a warning and returns without building an install command at all, which is a silent no-op rather than an error. With several, it takes the first in the order the datastore returns them. So this is a prerequisite for the Entra paths, not a detail.
- **That secret places only new hosts.** A host Fleet has never seen lands where a global secret puts it, which is **no fleet at all**, because a global secret is one with no fleet attached; a host Fleet already knows keeps the fleet it has, because re-enrolling does not move a host between fleets ([3.1](3.1-enrollment-design-and-host-lifecycle.md)). If placement matters for new devices, install fleetd yourself with the secret you want and let the agent-driven path do the rest.

The install is guarded by a fixed identifier so Windows applies it once rather than on every session.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Check both channels separately, because either can arrive without the other.

**From Fleet.** The host appears and its MDM status matches the path you used. [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) records Fleet's guidance that Windows completes MDM enrollment in the context of a signed-in user, so a machine sitting at a lock screen reporting MDM **Off** is not necessarily broken. **Note the boundary that guidance draws and this manual cannot:** Fleet's source establishes that the agent check-in is what *starts* registration, since Orbit runs as a system service and calls the registration API without inspecting who is logged in, and establishes nothing about when Windows *completes* it. The sign-in dependency and the thirty-second figure are Fleet's account of Windows' behaviour, not something checkable here.

**From the device**, in an elevated PowerShell:

```powershell
# Is the agent installed and running?
Get-Service -Name "Fleet osquery"

# Is the device Entra-joined, and was it handed an MDM URL?
dsregcmd /status
```

**`dsregcmd` is Entra evidence, not proof of enrollment in Fleet.** It tells you whether the device is joined and which MDM URL Entra gave it, which is a step on two of the three paths and no part of the third. The device's own record of being managed by Fleet lives in the registry, under the enrollment whose `ProviderID` is `Fleet`, and it is a **non-zero `EnrollmentState`** there that fleetd itself reads as enrolled. [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md#8910-host-side-checks) reads those keys and the certificate store.

An empty `MdmUrl` on the Autopilot path is not one problem. Fleet's own notes give three documented causes: the enrolling user has no Entra ID P1 licence, a licence was assigned and has not yet propagated, or the Fleet application's MDM user scope in Entra is `None`. Buying a licence fixes one of the three and waiting fixes another, so establish which before spending anything.

**The two answers disagreeing narrows the search rather than naming a cause.** Agent running with MDM off is consistent with the agent-driven path not having completed, and the eligibility conditions above are the checklist for that; it is also what a host looks like whose MDM enrollment was meant to come from somewhere else, or was turned off afterwards. The state narrows the search without naming the path. MDM on with no agent means the two channels currently disagree; it does not establish which path the device took, and the agent may have been removed after an agent-driven enrollment. If it *was* an Entra enrollment, check that a global enroll secret exists before you check egress, because with none Fleet never built an install command at all.

## Migrating from another MDM

Fleet can move Windows hosts off another manager with no end user interaction at all, which is the difference from Apple. **It is Fleet Premium.** [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) covers turning it on, and the residue from the previous manager that Fleet ships a repair script for.

The ordering is the same as the agent-driven path and for the same reason: **fleetd first, then Fleet moves the host.** A Windows host with no agent is invisible to the mechanism, because Fleet decides on the agent's own check-in.

## Who owns it afterwards

**The WSTEP certificate and key**, which are also Fleet's escrow key for Windows disk-encryption recovery keys ([2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md)). Losing them costs more than the MDM channel.

**The Entra application**, if you use the Autopilot or Settings-app paths. Its permissions, its scope, and the licences the enrolling users hold belong to whoever administers Microsoft identity, and none of it is visible from Fleet.

**The gap between the two channels.** A count of Windows hosts with MDM on and no recent agent check-in, and the reverse, is worth putting somewhere you look at regularly rather than running it after someone complains.
