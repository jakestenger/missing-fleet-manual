# Enroll Windows devices

![Explanation](../_assets/icons/explanation.svg) Windows arrives in Fleet over the same two channels as macOS, and they are wired to each other in a way macOS's are not. **fleetd** brings queries, scripts, software and vitals. **Windows MDM** brings profiles, commands and disk-encryption enforcement.

On a Mac the two are independent, which is why [3.2](3.2-enroll-macos-devices.md) spends its length on choosing a path for each. On Windows they pull each other along:

- **fleetd installs, and MDM follows.** With Windows MDM turned on, the agent's own check-in is what triggers enrollment. Nobody delivers a profile and nobody clicks anything.
- **MDM enrolls, and fleetd follows.** On the Microsoft Entra ID paths, where the device reaches Fleet before any agent exists, Fleet pushes fleetd down as an install command.

So the practical question on Windows is rarely "which of these do I do?" It is **"which one happened first, and did the other one follow?"**

## The decision you are making

**How does the device first reach Fleet?** That is the choice, and it is made by how the machine is provisioned rather than by a setting you pick afterwards.

| Path | Use it when | What the console shows |
|---|---|---|
| **Agent-driven** | Fleet's default, and the one to plan for. You can get fleetd onto the machine by any means you already have | On (manual) |
| **Autopilot / Entra** | New hardware you want provisioned at first boot, through Microsoft's out-of-box experience | On (company-owned) |
| **Settings app** | The person holding the device turns management on themselves, under **Settings > Access work or school** | On (manual) |

Those strings are what the **console** shows. The database and the API spell the Autopilot case `On (automatic)`, and the host filter spells it `automatic`; [8.6](../08-troubleshooting/8.6-server-state.md#one-status-three-vocabularies) has the mapping, and it matters the first time you write a query from something you read on screen.

**Company-owned is narrower than "enrolled through Entra".** Fleet marks a Windows host as automatically enrolled only when the enrollment type is automatic **and** the enrollment happened during the out-of-box experience. An Entra-driven enrollment on a machine that has already finished setup does not qualify, however it was initiated, and lands as `On (manual)`. That is the mechanism behind the Settings-app row above, and the reason a device that missed Autopilot at first boot cannot be given company-owned status by enrolling it afterwards.

**There is no personal enrollment on Windows.** Fleet records personal enrollment as false for every Windows host, so `On (manual - personal)` is a status these devices cannot reach. The ownership distinction macOS, iOS and Android all carry does not exist here.

**Two of the three need Microsoft Entra ID**, its per-person licensing, and a connection between Entra and Fleet that [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) sets up. The agent-driven path needs none of it, which is why it is the one to start with and the one to fall back to when an Entra problem is blocking a rollout.

### What Windows MDM needs before any of this

A WSTEP certificate and key supplied to the server, and Windows MDM turned on. Both are [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md). Until Windows MDM is on, fleetd still enrolls and everything agent-side works; there is simply no MDM channel to be on.

Turning Windows MDM on **disables Windows tamper protection** on the host. That is Windows' behaviour rather than Fleet's, and it is worth raising before someone else finds it in a compliance report.

## Agent-driven enrollment, which is the default

![Explanation](../_assets/icons/explanation.svg) This is the path most Windows estates use, and it is worth understanding as a mechanism precisely because almost none of it is visible as a step you perform.

With Windows MDM on, Fleet decides on **every Orbit configuration check-in** whether that host should be enrolled. Four conditions have to hold:

| Condition | What it means when it does not hold |
|---|---|
| The host's platform is Windows | Nothing happens |
| The host is **enrolled with osquery** | fleetd installed but not yet enrolled is not enough. This is the ordering that matters |
| The host is **not a Windows Server** | Servers are excluded, and the check happens twice, see below |
| The host is **not enrolled in any MDM**, Fleet's or anyone else's | A host still attached to its previous manager is skipped, unless migration is turned on |

When all four hold, Fleet's reply to that check-in carries a flag and a discovery URL. Orbit calls into Windows' own management registration API, and the device runs the enrollment exchange against Fleet from there.

**Orbit retries, at most once an hour, indefinitely.** That is worth sitting with, because it is the opposite of the macOS Automated Device Enrollment behaviour where Fleet issues the fleetd install once and nothing ever retries it ([3.2](3.2-enroll-macos-devices.md)). On Windows a transient failure heals itself without anyone noticing, and a persistent one produces an hourly attempt in the agent log forever, with nothing in the console to say so.

**The Windows Server exclusion is checked in two places, and they are not the same check.** Fleet's side reads what osquery reported about the host. Orbit's side reads the installation type from the machine itself before doing anything, refuses if it says server, and remembers that answer for the life of the process. So a Windows Server that Fleet has not correctly identified will be told to enroll, will refuse locally, and will look from the console exactly like a host that is failing to enroll.

Fleet's own record starts out saying the host is not a server and lets osquery correct it from the reported installation type, with a source comment saying exactly that. So on a genuinely new host the two sides can disagree for one detail-query cycle, which is a window rather than a fault. [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md) reads the host side.

### Turning the automatic behaviour off

There is a setting for estates that do not want enrollment happening unasked: `enable_turn_on_windows_mdm_manually`. Turn it on and Fleet stops sending the flag, leaving the end user to enroll through **Settings > Access work or school**. Either way the resulting MDM status is `On (manual)`; what changes is who initiates.

Three things about it are easy to get wrong:

- It is **Fleet Premium**. Fleet Free rejects it with a licence error.
- It cannot be set unless Windows MDM is already on. Fleet refuses the combination.
- It is **mutually exclusive with Windows MDM migration**, and Fleet refuses both at once with a message saying to enable only one. That is consistent rather than arbitrary: migration exists to move hosts without asking anyone.

Fleet documents it as configurable only for all fleets rather than per fleet.

## Installing fleetd

![How-to](../_assets/icons/howto.svg) You build an MSI, then deliver it with whatever already delivers software to your Windows estate.

```sh
fleetctl package --type=msi \
  --fleet-url=https://fleet.example.com \
  --enroll-secret="<secret>" \
  --fleet-desktop \
  --enable-scripts
```

`--fleet-desktop` includes Fleet Desktop, which is what gives the end user a tray item, the **My Device** page and self-service software; without it the other components still run and the person on the machine has no Fleet-facing surface at all. `--enable-scripts` decides whether this host will run scripts, and a package built without it produces hosts you cannot run a script against later.

Two flags behave differently here than on macOS. `--arch` accepts `arm64` for MSI packages, so Windows on ARM is a supported target. And `--use-system-configuration`, which is how a Mac takes its URL and secret from a configuration profile, is **rejected for MSI**: Fleet accepts it only for `pkg`. Windows has its own answer to the same problem, below.

### The MSI takes arguments at install time, which is the useful part

![Explanation](../_assets/icons/explanation.svg) An MSI built by `fleetctl package` is not a sealed artifact the way the macOS `pkg` is. Six of its settings are exposed as **installer properties**, so the tool pushing the file supplies them at install time and overrides whatever was baked in:

| Property | What it sets |
|---|---|
| `FLEET_URL` | The Fleet server the agent talks to |
| `FLEET_SECRET` | The enroll secret, written into `secret.txt` during install |
| `ENABLE_SCRIPTS` | Whether this host will run scripts |
| `FLEET_DESKTOP` | Whether Fleet Desktop runs |
| `END_USER_EMAIL` | The address recorded against the host |
| `EUA_TOKEN` | End-user attribution on the Entra paths. Fleet sets this one, not you |

```powershell
msiexec /i fleet-osquery.msi /quiet FLEET_SECRET="<secret>" ENABLE_SCRIPTS="True"
```

Reach for this when you want **one installer in the software repository with no credential inside it**, or one installer serving several fleets with a different secret per deployment group. It is the same problem `--use-system-configuration` solves on macOS, solved by the platform's own installer mechanism rather than by a configuration profile, and without the ordering constraint that makes the macOS version fiddly.

**The sentinel is the string `dummy`, and it fails silently.** The MSI ships with `FLEET_SECRET` defaulting to `dummy`, and the install-time script that writes `secret.txt` skips the write when the value is empty **or literally `dummy`**. A deployment tool that passes the placeholder through, or a scripted install where the variable expanded to nothing, produces an installer that runs cleanly and enrolls with whatever secret was baked in at build time, or fails to enroll with no secret at all. Nothing reports the substitution. When a batch of hosts lands in the wrong fleet or does not appear, check this before anything else.

**Everything else is build-time.** The update URL, the TUF channels, `--insecure`, `--debug`, the host identifier, the osquery database path and the setup-experience switch are written into the service's command line when the package is built. Changing any of those means building another package.

### When Fleet installs fleetd for you

On the Entra paths the device is in MDM before any agent exists, so Fleet pushes one down. The rule for when this happens is precise, and knowing it explains why the mechanism appears to be missing on the agent-driven path:

**Fleet enqueues the fleetd install only for enrollments that carry a user principal name**, which is to say the Entra ones. Agent-driven enrollments authenticate with Orbit's node key instead, and Fleet treats those as already having an agent, which they do.

When it does fire, it fires on a **management session from a device Fleet believes has no working agent**, and that check is stricter than "is fleetd installed". Fleet also requires an agent check-in recent enough to postdate the enrollment itself, with a 90-second grace period. So a device that re-enrolled and has not checked in since gets the install enqueued again rather than being assumed healthy.

Three properties of that install are decided for you:

- **The MSI is fetched by the device from Fleet's download service**, and the server hands the device a SHA-256 taken from a metadata document the server fetches itself. Two separate egress paths therefore have to work: Fleet outbound to the download service, and the device outbound to wherever the MSI is served. Fleet failing to fetch the metadata is a warning in the log and not an error, and the session continues without the install.
- **Scripts are enabled.** The install command sets `ENABLE_SCRIPTS="True"` unconditionally, whatever your own packages do.
- **The secret is a global enroll secret**, so these hosts land wherever a global secret puts them rather than in a fleet you chose. If fleet placement matters, install fleetd yourself with the secret you want and let the agent-driven path do the rest.

The install is guarded by a fixed identifier so Windows applies it once rather than on every session.

## Verifying an enrollment

![How-to](../_assets/icons/howto.svg) Check both channels, because on Windows the failure is nearly always that one arrived and the other did not.

**From Fleet.** The host appears and its MDM status matches the path you used. Remember what [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) establishes: Windows completes MDM enrollment in the context of a signed-in user, so a machine sitting at a lock screen reports MDM **Off** and is not broken. Enrollment usually completes within about thirty seconds of the next sign-in.

**From the device**, in an elevated PowerShell:

```powershell
# Is the agent installed and running?
Get-Service -Name "Fleet osquery"

# Is MDM on, and to whom?
dsregcmd /status
```

`dsregcmd /status` answers the MDM half, including whether the device is Entra-joined and which MDM URL it was handed. An empty `MdmUrl` on the Autopilot path is the licensing signature rather than a Fleet problem. [8.9](../08-troubleshooting/8.9-windows-mdm-diagnostics.md#8910-host-side-checks) reads the registry and the certificate store in detail, and [8.4](../08-troubleshooting/8.4-host-side-investigation.md) reads the agent side.

**The two answers disagreeing tells you which direction failed.** Agent running with MDM off is the ordinary agent-driven case that has not completed yet, and the first thing to check is whether anyone has signed in. MDM on with no agent is an Entra enrollment whose fleetd install did not land, and the first thing to check is egress.

## Migrating from another MDM

Fleet can move Windows hosts off another manager with no end user interaction at all, which is the difference from Apple. [2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md) covers turning it on, and the residue from the previous manager that is the usual reason it fails.

The part worth repeating here is the ordering, because it is the same ordering as the agent-driven path and for the same reason: **fleetd first, then Fleet moves the host.** A Windows host with no agent is invisible to the mechanism.

## Who owns it afterwards

**The WSTEP certificate and key**, which are also Fleet's escrow key for Windows disk-encryption recovery keys ([2.8](../02-administer-and-deploy-fleet/2.8-windows-and-android-management-configuration.md)). Losing them costs more than the MDM channel.

**The Entra application**, if you use the Autopilot or Settings-app paths. Its permissions, its scope, and the licences the enrolling users hold belong to whoever administers Microsoft identity, and none of it is visible from Fleet.

**The gap between the two channels.** A count of Windows hosts with MDM on and no recent agent check-in, and the reverse, is worth putting somewhere you look at regularly rather than running it after someone complains.
