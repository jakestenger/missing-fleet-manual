# How Fleet reaches a device

Fleet reaches devices through the mechanism each platform makes available. On macOS, Windows, and Linux, fleetd provides the host-side agent path, **fleetd**. On supported managed platforms, the operating system's **MDM** client provides a separate and/or additional device-management path.

This model is useful because it makes Fleet's behaviour easy to reason about. Query and inventory work belongs to **osquery**. Host-side management work belongs to **Orbit**. Profiles and MDM commands belong to the operating system's **MDM** client.

Most confusion about Fleet, and most of the time spent in Part VIII, comes from a single assumption: that a device is either "connected to Fleet" or not. It is not one connection. It is several independent ones, and a device can be perfectly healthy on some and silent on others at the same moment. Once you grasp that, a great deal of otherwise puzzling behaviour becomes more understandable.

## The host-side bundle

![Explanation](../_assets/icons/explanation.svg) **fleetd** is the name of Fleet's host-side bundle and installer package. On macOS, Windows, and Linux the bundle contains three coordinated components:

1. **Orbit** is the one that matters most, because it is the one the operating system starts and the one that starts everything else. It handles enrollment, keeps the bundle updated, and carries out host-side work: running scripts, installing software, updating fleetd itself. It runs as `orbit`, or `orbit.exe` on Windows.

2. **osquery** is the reading half. It answers live reports, returns scheduled results, and supplies host vitals and software inventory. It runs as `osqueryd`. Fleet did not write osquery; it is an independent open-source project that Fleet configures and talks to, which is why so much of Fleet's query behaviour follows osquery's rules rather than Fleet's.

3. **Fleet Desktop** is the part an end user actually sees: the menu bar item, the My Device page, and any dialog that needs a person present to respond. It runs as `fleet-desktop`, and only when someone is logged in, since there is nothing for it to do otherwise.

The chain of custody runs one way. The operating system's service manager starts Orbit, and Orbit starts the other two. If Orbit is not running, neither osquery or Fleet Desktop are running either, which makes it the first thing to check and the reason it gets its own attention in Part VIII.

There is no process called `fleetd`. The name covers the set of components that ship and update together; `orbit`, `osquery`, `fleet-desktop`.

**ChromeOS is the exception.** In ChromeOS, fleetd is a Chrome extension with a service worker. No Orbit, no osqueryd, no Fleet Desktop.

## Which component owns which kind of work

![Explanation](../_assets/icons/explanation.svg) The division of labour is clean enough to memorise, and doing so pays for itself the first time something goes wrong.

Anything that answers **what is on the host right now** belongs to osquery. Live reports, scheduled results, host vitals, software inventory, file carves. If the question is a question, osquery owns it.

Anything Fleet **does to the host through its own agent** belongs to Orbit. Enrollment, scripts, software installs, fleetd updates, the setup experience, and the supported disk-encryption workflows.

Anything that uses **the platform's native management** belongs to the OS MDM client. Profiles, MDM commands, managed app delivery, lock, and wipe. Fleet composes the instruction; the operating system carries it out.

Anything that **involves the person using the device** belongs to Fleet Desktop, which Orbit launches. My Device, Self Service, and end-user dialogs.

The practical value of knowing this is that it tells you where to look first. A query that returns nothing is an osquery question. A software install that never lands is an Orbit question. A profile that doesn't get delivered is an MDM question. Three different investigations and three different starting points.

## The five channels

![Explanation](../_assets/icons/explanation.svg) A managed host does not hold just a single connection to Fleet; it holds five genuinely independent channels: different owners, different protocols, different schedules, and different failure modes.

| Channel             | Carries | Typical cadence |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| osquery distributed | Live reports and host-detail queries. By default, this is the "heartbeat" process that determines if a host shows online or not. | `distributed_interval`, commonly 10–30 seconds          |
| osquery config TLS  | Scheduled query configuration and agent options              | `config_refresh`; Fleet sets this to 60 seconds         |
| osquery logger TLS  | Query results                                                | `logger_tls_period`                                     |
| Orbit API           | Scripts, software, setup experience, agent configuration, and host-side workflows | 30-second configuration poll plus request/response work |
| MDM protocol        | Profiles, MDM commands, managed apps, lock, and wipe         | Platform-specific push or poll                          |

Three of them belong to osquery, and they split the work the way osquery always has. One carries questions to the host and answers back. One fetches the host's configuration, meaning its query schedule and agent options. One ships results outward, and only outward.

The fourth is Orbit's own API conversation with the Fleet server, which is how installs, scripts, and disk-encryption keys move. Orbit checks in on a thirty-second cycle for configuration, and makes ordinary request-and-response calls as work arrives.

The fifth is the platform's MDM protocol, and it is the one that behaves least like the others. Fleet does not control its timing. Apple and Microsoft do, through push notifications or a device-side poll, and a device that has gone quiet on MDM may still be perfectly responsive on the other four.

Although the three osquery channels share one process, they are separate conversations against separate endpoints, so a proxy or content filter can break one and leave the others working normally.

**One channel can affect another, in exactly one direction.** A Windows host on a relaxed MDM poll is woken by Orbit. If Orbit is wedged, queued MDM commands can sit for hours with nothing wrong in the MDM subsystem at all. It is the a case where the channels are not fully independent.

## What “online” tells you

![Explanation](../_assets/icons/explanation.svg) Fleet marks a host online when it has checked in through osquery within its normal check-in window, plus a 60-second grace period. The window uses the shorter of the host’s `distributed_interval` and `config_refresh` values.

In Fleet’s standard configuration, `config_refresh` is 60 seconds and `distributed_interval` is commonly 10–30 seconds. In practice, this means a host normally continues to show as online for about 70–90 seconds after its most recent osquery check-in.

Both values are osquery options in the agent-options `options` block. Hosts receive a changed value at their next configuration refresh, without an osquery restart:

```yaml
agent_options:
  options:
    config_refresh: 60
    distributed_interval: 30
```

Lower intervals give a fresher online signal and faster live report pickup. Higher intervals reduce check-in traffic and extend the time Fleet treats the last successful check-in as current. Choose values that match the responsiveness and network profile of the fleet.

The online signal gives administrators a reliable view of query and inventory availability. The MDM path and Orbit path are independently visible through the status of the work they perform.

For example, a host can answer a live report while an MDM command is awaiting the platform’s next check-in. An MDM-enrolled device can report MDM status before fleetd has been installed. The diagnostic method is therefore to identify the channel associated with the requested action, then inspect that channel’s evidence.

## Where there is no agent at all

![Reference](../_assets/icons/reference.svg) Several platforms run no fleetd, and a surprising amount of downstream behaviour follows from that one fact.

| Platform | Orbit | osquery | Fleet Desktop | MDM | Management path |
|---|---|---|---|---|---|
| macOS | yes | yes | yes | Apple MDM | Full bundle plus MDM |
| Windows | yes | yes | yes | OMA-DM | Full bundle plus MDM |
| Linux | yes | yes | yes | **none** | Orbit and osquery only |
| iOS / iPadOS | **no** | **no** | **no** | Apple MDM | MDM protocol only |
| Android | **no** | **no** | **no** | AMAPI | AMAPI, plus an optional narrow-scope Fleet app |
| ChromeOS | **no** | **no** | **no** | none | Chrome extension |

**iOS and iPadOS do not run Orbit**, so there is no polling loop and no step-by-step setup display. No scripts, no software installs beyond App Store and in-house delivery, no osquery vitals, no Fleet Desktop. Everything Fleet knows about an iPhone arrived in an MDM command response, and everything Fleet does to one is an MDM command.

**Linux has no MDM.** Everything Fleet does on a Linux host arrives over the osquery channels or the Orbit API. That is why disk encryption on Linux is escrow-only: Fleet cannot switch LUKS on for a host that was installed unencrypted, so it escrows a key for hosts that already had LUKS at install time.

**Android has neither fleetd nor osquery.** Management is Google's Android Management API: Fleet pushes policies and managed apps to it, and device events return over a Google Cloud subscription. Two consequences worth settling before the first device enrolls, because both are difficult to reverse: the Fleet server URL must be publicly reachable for those events to arrive, and it cannot be changed afterwards, because the subscription is created against one URL.

There is a Fleet Android app, and it is not fleetd. It is a narrow-scope application whose job is to enroll and then deliver certificates into the device keystore. It gives you certificates on Android. It gives you no inventory, no reports, and no scripts.

**ChromeOS runs the extension and nothing else**, configured with a Fleet URL and an enroll secret, and the Fleet URL must present a valid TLS certificate.

## How the agent updates itself

![Explanation](../_assets/icons/explanation.svg) Orbit updates the whole bundle, including itself, from its configured update repository. **This path does not go through the Fleet server**, which is worth knowing because it means agent updates continue working when the Fleet server is unreachable, and it means blocking that repository silently freezes agent versions.

Each of the three components tracks its own **channel**, and a channel is just a pointer. `stable` and `edge` exist, and **a literal version string is also a valid channel**, which is what makes pinning possible.

Channels are set when a package is built, and can be changed centrally afterwards through agent options, which is a Fleet Premium capability:

```yaml
agent_options:
  update_channels:
    orbit: stable
    osqueryd: '5.10.2'
    desktop: edge
```

That combination is what turns agent versions into something you manage rather than something that happens to you:

| You want | Set the channel to |
|---|---|
| Track the current agent | `stable`, which is also what an omitted component means |
| Validate the next agent before it reaches stable | `edge`, on a small fleet |
| Hold a known-good version while investigating a regression | the literal version, for example `'5.10.2'` |
| Roll back a bad agent across the estate | the literal previous version |
| Upgrade osquery without touching Orbit | the `osqueryd` key alone |

Three properties make this practical. **Central configuration beats whatever was compiled into the package, including when that means a downgrade**, so a rollback needs no new installer. Hosts pick the change up on their next thirty-second poll and restart themselves. And because these are fleet-level agent options, your canary group is a fleet, which is the same scoping tool covered in [1.3](1.3-hosts-fleets-labels.md).

Two things to know before relying on it. **Removing the `update_channels` key does not revert anything**, so when a pin is finished, write `stable` explicitly rather than deleting the key. And **a channel that does not exist produces host-side errors with nothing to see server-side**, so a typo in a version string presents as "that fleet stopped updating" and nothing more specific.

`edge` is for validating the next agent on hosts you own. Once a version reaches `stable` there is nothing more current about it.

## Rolling out the agent and MDM separately

![Explanation](../_assets/icons/explanation.svg) They run on different channels, they can be done in either order, and each is useful without the other.

| What the host has | You get | You do not get |
|---|---|---|
| fleetd, no MDM | Live and scheduled reports, vitals, software inventory, scripts, Orbit-driven software installs, LUKS escrow on Linux | Profiles, MDM commands, App Store apps, lock, wipe |
| MDM, no fleetd | Profiles, MDM commands, App Store apps, lock, wipe | Reports, vitals, inventory, scripts, Orbit installs |
| Both | Everything in this manual | |

This is why an agent rollout does not have to wait for an MDM migration, and why you can install fleetd through your existing MDM provider, or any package tool you already run, while MDM enrollment proceeds on its own schedule.

It is also why a rollout plan should verify **both** channels per host rather than one. A host that is MDM enrolled with no agent looks healthy in the MDM column and is invisible everywhere else.

## What only Fleet Desktop can do

![Explanation](../_assets/icons/explanation.svg) Fleet Desktop is the only end-user-facing surface fleetd has. It carries the My Device link, Self Service, and every dialog that needs a human answer, including the macOS MDM migration prompt and the Linux passphrase prompt without which LUKS escrow cannot happen at all.

It also has a requirement the rest of the bundle does not: **a logged-in desktop session**. On servers, kiosks, and any host sitting at the login window, Fleet Desktop doesn't run.

That makes it a per-fleet decision rather than a global one. A laptop fleet wants Desktop. A server fleet has no user to show it to and no reason to run a third process.

## Edge cases and precedence

![Reference](../_assets/icons/reference.svg) **Orbit cannot reach Fleet.** The configuration poll backs off gradually from thirty seconds to a ceiling of five minutes, and one success resets it. Nothing is dropped server-side: queued scripts and installs are picked up on the first successful poll. osquery is unaffected and keeps its own buffers, so the host can still answer live reports and will replay buffered results with their original timestamps once the logger channel recovers. Network errors are logged sparingly, so log volume is not a measure of severity.

**Enrollment fails.** Orbit retries a limited number of times with a growing delay. There is an option that silences enrollment error logging, which is worth knowing because its presence makes a broken host look quiet rather than loud.

**An update fails.** Failure is per component, not per host, so the others keep updating. The part that surprises people is the cooldown: repeated failures on one component buy a **24-hour pause** on that component, and a restart does not clear it. Publishing a new version does.

**Updates partially succeed.** A host can run a new Orbit against an older osquery for a while, which is normal rather than a broken state.

**A configured channel does not exist.** That component is skipped and the host logs errors for it. Nothing distinct appears server-side, which is why a typo in a version string is invisible until you look at the host.

**Empty is not the same as absent, for osquery flags.** Absent from agent options means Orbit leaves the host's flag file alone. Explicitly set to empty means Orbit clears it and restarts osquery without those flags. Orbit only writes when the result would actually differ, so re-applying unchanged configuration does not cause a restart.

**Building a package without supplying a flag file blanks an existing one.** This is the opposite of the agent-options behaviour above, and it catches people who maintain osquery flags locally. If you do, always pass the flag file when packaging.

**Restoring an agent directory onto different hardware.** Orbit compares the live hardware identity against what it recorded. On a mismatch it clears its enrollment state and exits so the host enrolls again cleanly, which means imaged or cloned machines recover on their own rather than fighting over one host record.

**The half-enrolled state: MDM enrolled, no agent.** This is structural rather than a bug in any component. Enrollment and agent installation are separate steps on separate channels, so the install can fail while the enrollment succeeds. The result reports MDM status as on, never checks in on the other channels, and quietly accumulates unacknowledged MDM commands. It is the single most common confusing state in Fleet, and it exists because of the separation this chapter describes.

**Fleet Desktop with no desktop session.** Orbit retries and logs that it is skipping the start. Nothing else is affected: Orbit and osquery are fully functional at the login window, while Self Service and My Device are not.
