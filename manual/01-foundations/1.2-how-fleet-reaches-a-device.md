# How Fleet reaches a device

Fleet reaches devices through the mechanism each platform makes available. On macOS, Windows, and Linux, fleetd provides the host-side agent path, **fleetd**. On supported managed platforms, the operating system’s **MDM** client provides a separate and/or additional device-management path.

This model is useful because it makes Fleet's behaviour easy to reason about. Query and inventory work belongs to **osquery**. Host-side management work belongs to **Orbit**. Profiles and MDM commands belong to the operating system's **MDM** client.

Most confusion about Fleet, and most of the time spent in Part VIII, comes from a single assumption: that a device is either "connected to Fleet" or not. It is not one connection. It is several independent ones, and a device can be perfectly healthy on some and silent on others at the same moment. Once you grasp that, a great deal of otherwise puzzling behaviour becomes more understandable.

## The host-side bundle

**fleetd** is the name of Fleet’s host-side bundle and installer package. On macOS, Windows, and Linux the bundle contains three coordinated components:

1. **Orbit** is the one that matters most, because it is the one the operating system starts and the one that starts everything else. It handles enrollment, keeps the bundle updated, and carries out host-side work: running scripts, installing software, updating fleetd itself. It runs as `orbit`, or `orbit.exe` on Windows.

2. **osquery** is the reading half. It answers live reports, returns scheduled results, and supplies host vitals and software inventory. It runs as `osqueryd`. Fleet did not write osquery; it is an independent open-source project that Fleet configures and talks to, which is why so much of Fleet's query behaviour follows osquery's rules rather than Fleet's.

3. **Fleet Desktop** is the part an end user actually sees: the menu bar item, the My Device page, and any dialog that needs a person present to respond. It runs as `fleet-desktop`, and only when someone is logged in, since there is nothing for it to do otherwise.

The chain of custody runs one way. The operating system's service manager starts Orbit, and Orbit starts the other two. If Orbit is not running, neither osquery or Fleet Desktop are running either, which makes it the first thing to check and the reason it gets its own attention in Part VIII.

## Each kind of work has a clear owner

The division of labour is clean enough to memorise, and doing so pays for itself the first time something goes wrong.

Anything that answers **what is on the host right now** belongs to osquery. Live reports, scheduled results, host vitals, software inventory, file carves. If the question is a question, osquery owns it.

Anything Fleet **does to the host through its own agent** belongs to Orbit. Enrollment, scripts, software installs, fleetd updates, the setup experience, and the supported disk-encryption workflows.

Anything that uses **the platform's native management** belongs to the OS MDM client. Profiles, MDM commands, managed app delivery, lock, and wipe. Fleet composes the instruction; the operating system carries it out.

Anything that **involves the person using the device** belongs to Fleet Desktop, which Orbit launches. My Device, Self Service, and end-user dialogs.

The practical value of knowing this is that it tells you where to look first. A query that returns nothing is an osquery question. A software install that never lands is an Orbit question. A profile that doesn't get delivered is an MDM question. Three different investigations and three different starting points.

## The five channels

A managed host does not hold one connection to Fleet; it holds five genuinely independent channels: different owners, different protocols, different schedules, different failure modes.

| Channel             | Carries | Typical cadence |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| osquery distributed | Live reports and host-detail queries. By default, this is the "heartbeat" process that determines if a host shows online or not. | `distributed_interval`, commonly 10–30 seconds          |
| osquery config TLS  | Scheduled query configuration and agent options              | `config_refresh`; Fleet sets this to 60 seconds         |
| osquery logger TLS  | Query results                                                | `logger_tls_period`                                     |
| Orbit API           | Scripts, software, setup experience, agent configuration, and host-side workflows | 30-second configuration poll plus request/response work |
| MDM protocol        | Profiles, MDM commands, managed apps, lock, and wipe         | Platform-specific push or poll                          |

Three of them belong to osquery, and they split the work the way osquery always has. One carries questions to the host and answers back. One fetches the host's configuration, meaning its query schedule and agent options. One ships results outward, and only outward.

The fourth is Orbit's own API conversation with the Fleet server, which is how installs, scripts, and disk-encryption keys move. Orbit checks in on a thirty-second cycle for configuration, and makes ordinary request-and-response calls as work arrives.

The fifth is the platform's MDM protocol, and it is the one that behaves least like the others. Fleet does not control its timing. Apple and Microsoft do, through push notifications or a device-side poll, and a device that has gone quiet on MDM may still be perfectly responsive on the other four.

## What “online” tells you

Fleet marks a host online when it has checked in through osquery within its normal check-in window, plus a 60-second grace period. The window uses the shorter of the host’s `distributed_interval` and `config_refresh` values.

In Fleet’s standard configuration, `config_refresh` is 60 seconds and `distributed_interval` is commonly 10–30 seconds. In practice, this means a host normally continues to show as online for about 70–90 seconds after its most recent osquery check-in.

Both values are osquery options in the agent-options `options` block. Hosts receive a changed value at their next configuration refresh, without an osquery restart:

```yaml
agent_options:
  options:
    config_refresh: 60
    distributed_interval: 30
```

Lower intervals give a fresher online signal and faster live report pickup. Higher intervals reduce check-in traffic and extend the time Fleet treats the last successful check-in as current. Choose values that match the responsiveness and network profile of the fleet.

The online signal gives administrators a reliable view of query and inventory availability. The MDM path and Orbit path are independently visible through the status of the work they perform.

For example, a host can answer a live report while an MDM command is awaiting the platform’s next check-in. An MDM-enrolled device can report MDM status before fleetd has been installed. The diagnostic method is therefore to identify the channel associated with the requested action, then inspect that channel’s evidence.
