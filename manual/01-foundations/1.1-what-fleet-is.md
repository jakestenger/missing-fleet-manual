# What Fleet is

Fleet is an endpoint management platform for seeing the state of devices, deciding which devices need attention, and making controlled changes across an estate. It brings endpoint operations, security, and infrastructure automation into one control plane.

If you have run an endpoint estate before, you have almost certainly run two tools: something that tells you what is out there, and something that changes it. A reporting system and an MDM. They rarely agree, and the gap between them is where the work goes. Fleet's premise is that those are two halves of one job, and that they get much easier when the thing reporting the state and the thing changing it share a single view of every device.

That framing explains the shape of this manual. Fleet has a reading half and a writing half. Part IV covers reading. Part V covers writing. Nearly everything else exists to serve one or the other.

## Three questions

Fleet is built to answer three practical questions:

1. **What is on this device, and what is its current state?**
2. **Which devices need a configuration, remediation, or software change?**
3. **How can we make and audit that change across the estate?**

It answers them with osquery-based device data, host management through fleetd, and the device-management protocols available on each operating system.

Fleet answers the first question with host vitals, software inventory, and reports (live or scheduled). Ask what version of a browser is installed across ten thousand machines and you can get an answer in seconds. Schedule that report to run on a regular cadence and you will have an historical record of remediations across your estate.

The second question is the one that decides whether the first was worth asking. Knowing that four hundred devices are out of date matters only if you can describe *which* four hundred in terms Fleet can act on. That is what labels, policies, fleets, and vulnerability data are for: turning an observation into a defined set of devices.

The third question is where Fleet changes something. Software, scripts, configuration profiles, MDM commands, OS settings, and disk-encryption workflows all deliver work to the devices the second question identified.

Two more layers sit underneath. **Automation** through GitOps, fleetctl, the REST API, policy automations, and integrations makes the work reviewable and repeatable rather than clicked through by hand. **Operation** covers what it takes to run the service itself: agent channels, update controls, audit history, logs, and server maintenance.

The rest of this manual follows that progression. Connect devices, understand them, manage them, automate the work, and operate the service.

## Fleet in your environment

Fleet is not intended to be the only system you run. It is opinionated about devices and deliberately incurious about everything else. In addition to Fleet, you should also consider:

Your **identity provider** stays the source of truth for who people are. Fleet authenticates administrators against it and can use identity context in device workflows, rather than maintaining a second directory.

**Configuration-management tools** keep the ground they already hold. This comes up most often with headless linux servers, where an existing configuration management tool is frequently the right owner of system configuration and there is no reason to move it. Fleet is happy to observe a machine it does not configure.

**SIEMs, data lakes, and security tooling** are great ways to store and analyze the data Fleet generates. These tools exist downstream of Fleet, ingesting its steady stream of device data, report results, logs, and audit records. Fleet is intentionally designed to hand that off for longer retention, correlation, and response somewhere better suited to it.

**Apple MDM, Windows OMA-DM, and the Android Management API** are the platform-native management paths. Fleet coordinates them rather than replacing them, which is a distinction that shapes a great deal of this book. When Fleet applies a configuration profile to a Mac, it is asking Apple's management channel to do it.

**IT asset systems** hold ownership, procurement, and lifecycle records that Fleet has no view into. Fleet contributes the live device facts and leaves the business record alone. Your IT asset management system stores the expected state of your devices, Fleet reports on the actual state.

The effect is that Fleet slots into an existing operating model while giving endpoint teams a common view of hosts and the work being done to them.

## Platform capability starts with the available path

Fleet aims for a consistent administrative experience across platforms, but it can only ever use the mechanism each operating system actually offers. Under the hood, Windows, Android, Linux, macOS and even iOS can have wildly different deployment paths. Fleet tries to bridge those paths into a single UI. Where you see a capability missing for a platform in this manual, the reason is nearly always that the platform provides no path for it.

| Device class | Device-data path | Device-management path | What this enables |
|---|---|---|---|
| macOS | fleetd and osquery | Apple MDM | Inventory, queries, scripts, software, profiles, and MDM commands |
| Windows | fleetd and osquery | Windows OMA-DM | Inventory, queries, scripts, software, profiles, and MDM commands |
| Linux | fleetd and osquery | Agent management | Inventory, queries, scripts, software, and Linux-specific workflows |
| iOS / iPadOS | MDM-reported inventory | Apple MDM | Apple device-management actions and inventory |
| Android | AMAPI-reported inventory | Android Management API | Android policy, managed applications, and supported device data |
| ChromeOS | Fleet Chrome extension | Extension management | Fleet's ChromeOS management capability |

macOS, Windows, and Linux run fleetd, so they get the full osquery reading surface. iOS, iPadOS, and Android do not run fleetd at all, and what Fleet knows about them arrives through the management protocol itself.

The platform chapters in Part III cover enrollment and prerequisites. Feature chapters call out the platform differences that change an administrator's decision, and [a.2 Platform capability matrix](../09-appendices/a.2-platform-capability-matrix.md) holds the full per-feature breakdown.

## A useful mental model

Think of Fleet as a control plane with several device-side executors, each with one job.

**osquery** observes. It turns a running machine into something you can query, and it is the reason Fleet can answer questions about devices in seconds rather than crawling them one at a time.

**Orbit** acts. It is Fleet's agent, and it handles the host-side work that osquery has no business doing: installing software, running scripts, updating fleetd itself.

**Fleet Desktop** talks to the person. Some work needs a human in the loop, whether that is showing someone why their laptop is failing a policy or letting them install an approved application themselves.

**The OS MDM client** applies platform-native management. Fleet does not implement it; the operating system does, and Fleet sends it instructions.

**The Fleet service** holds the desired state, receives results, and coordinates the rest.
