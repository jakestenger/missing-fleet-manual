# The Fleet server

The Fleet server coordinates device management, but it keeps its durable information in purpose-built infrastructure services. This design lets an organization run Fleet behind a load balancer, replace a Fleet server instance, and scale the service while keeping the shared device-management record available.

The short version, and the thing worth carrying out of this chapter: **the Fleet server itself holds almost nothing.** Everything that matters lives in MySQL, Redis, or object storage. A Fleet server process is close to disposable, and that is deliberate. You can stop one, start three more, replace them all during an upgrade, and the deployment carries on, because none of them was holding anything the others needed.

That single property is what makes the rest of the operational picture work: how Fleet scales, what a restart costs, what a backup has to include, and what actually constitutes an outage.

## Where the state actually lives

Three stores sit behind the Fleet server, and each one holds a different kind of thing for a different reason.

**MySQL is the system of record.** If it is written down and expected to survive, it is here: hosts, fleets, labels, policies, reports, the MDM command queues, activity history, and the configuration you set. When people talk about backing up Fleet, this is overwhelmingly what they mean.

**Redis holds work in progress.** Live report campaigns, the host authentication cache, rate limits, in-flight SSO workflow state, and the cursors that reconcilers use to track where they had reached. The useful way to think about Redis is that it holds things Fleet would rather not lose but can survive losing. A live report running when Redis restarts is gone, and the correct response is to run it again.

**Object storage holds the large files.** Software installers, bootstrap packages, title icons, and file-carve blocks. These are big, they are read by many Fleet instances and sometimes by devices, and they have no business occupying a database.

TLS protects communication with the Fleet service. Those three stores plus certificates are the infrastructure dependencies to plan for in a production deployment, and they are what Parts II and VII spend their time on.

## Why the state is split

A single database could technically hold all of it. The split exists because the three kinds of state have incompatible requirements, and forcing them together makes each one worse.

Configuration and history need durability and careful consistency, and they are read far more often than written. Live report coordination needs to be fast and is worthless a minute later, so paying for durability would be paying for nothing. Installers are large, immutable, and read repeatedly by many readers at once, which is the one workload a relational database handles least gracefully.

Matching each kind of state to a store built for it is what lets Fleet stay responsive during a live report against thousands of hosts while a software package downloads and an administrator reads a year of activity history, without any of those three getting in each other's way.

## The two flows administrators operate

Everything Fleet does resolves into one of two flows, running in opposite directions.

**Desired state flows outward.** It starts with an intention: an administrator in the UI, a GitOps change, an API request, or a scheduled workflow. It ends with a policy, script, software item, profile, or command sitting ready for the hosts it was scoped to. Note where it ends. Desired state ends at *available to the device*, not at *applied on the device*. The gap between those two is where a great deal of troubleshooting lives.

**Observed state flows inward.** It starts at the device: a check-in, a report result, an MDM response, an agent report. It ends as updated host details, an activity record, a result status, report data, or a line in an external log.

The two never meet directly. Fleet writes what you want into MySQL and reads what is true out of device reports, and the interesting questions in this book are almost always about the distance between them.

The Fleet service coordinates those flows; the device paths described in [1.2 How Fleet reaches a device](1.2-how-fleet-reaches-a-device.md) carry the work to and from hosts.

## What to plan for

When designing or operating a Fleet deployment, establish ownership for:

- Fleet server configuration, availability, and TLS certificates
- MySQL capacity, backups, and restoration
- Redis availability and monitoring
- Object-storage access, retention, and software/package delivery
- Logs, audit-event export, metrics, and tracing
- Release management for the Fleet service and fleetd

Parts II and VII expand these topics into deployment, day-two operations, and release-management guidance. This chapter provides the model needed to understand why those operational pieces fit together.
