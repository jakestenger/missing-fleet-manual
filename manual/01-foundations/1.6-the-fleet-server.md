# The Fleet server


The Fleet server coordinates device management and keeps almost none of the results.

Almost everything durable lives in MySQL, Redis, or object storage. The exception is the **server private key**, which lives in the server's own configuration and is what decrypts the sensitive material held in MySQL, so it is neither in the three stores nor recoverable from them ([2.12](../02-administer-and-deploy-fleet/2.12-production-readiness-and-handoff.md)). That makes a Fleet server process close to disposable: stop one and start three more and the deployment carries on, because nothing another instance depends on was only in that process. Replacing all of them at once is a different matter, since an upgrade requires every instance down for the migration, and that section says what the window costs. Two things do live inside a process, and both are covered below: a cache in front of MySQL, and, if you have configured no object storage, files on local disk. The first mostly costs you staleness. The second is why a single-instance deployment behaves differently from a scaled one.

Most of what follows is a consequence of that: how Fleet scales, what a restart costs, what a backup has to cover, and what counts as an outage.

## Where the state actually lives

![Explanation](../_assets/icons/explanation.svg) Three stores sit behind the Fleet server, and each one holds a different kind of thing for a different reason.

**MySQL is the system of record.** If it is written down and expected to survive, it is here: hosts, fleets, labels, policies, reports, the MDM command queues, activity history, and the configuration you set. It is the store a Fleet backup has to cover.

**Redis holds work in progress**, and most of it is genuinely disposable: live report campaigns, the host authentication cache, rate limits, in-flight SSO state, and the cursors reconcilers use to track where they had reached. A live report running when Redis restarts is simply gone. Run it again.

**Some of it is not reconstructible, and the distinction that matters is between Redis being unavailable and Redis losing what it held.** Plenty sits in Redis that nothing else holds a copy of, live-report campaigns and in-flight SSO state among it. These three are the ones whose loss is quiet enough to matter afterwards:

| What | If Redis is unavailable | If the data is actually lost or flushed |
|---|---|---|
| Pending recipients for failing-policy automations | The worker cannot read them, and a host that starts failing during the outage may fail to be registered at all rather than queueing | The owed notifications are not reconstructed from anywhere |
| Recorded server errors | Not recordable and not readable while Redis is away. Unavailability does not itself delete what was stored, though those keys carry a TTL and can expire during the interval | The record of what went wrong before the incident is gone too |
| With asynchronous host processing on, pending last-seen, label, policy and query-stat updates | Writes fail and are logged, while the check-in itself carries on | Those particular observations do not arrive in MySQL |

None of that makes Redis a system of record. **Unavailability does not itself erase what is stored**, though Redis-dependent writes attempted during it can fail and TTLs keep running. **Actual data loss** is the other column: it removes pending work already stored, including owed notifications, the recorded error history and queued asynchronous observations, and nothing reconstructs any of them.

**Object storage holds the large files.** Software installers, bootstrap packages, title icons, organisation logos, and file-carve blocks. Large, read by many instances at once, and no business occupying a database. "Immutable" fits the installers and the carve blocks rather than the set: logos and title icons can be uploaded, replaced and deleted through the ordinary interface, so treat them as objects with a lifecycle rather than as write-once artifacts.

TLS protects communication with the service. **The server private key is the fourth thing to plan for and the one most often left off the list**, because it is not a store: it lives in the server's configuration, it decrypts the sensitive material held in MySQL, and a backup of all three stores without it restores data nobody can read. Give it an owner, a copy somewhere that is not the Fleet host, and a place in the handover document ([2.12](../02-administer-and-deploy-fleet/2.12-production-readiness-and-handoff.md)). Parts II and VII spend most of their time on these four.

### The in-process cache nobody configures

Each Fleet process keeps a cache in front of MySQL for values read very frequently. It is wider than the agent options people know about: application configuration, a fleet's agent options and features, packs and scheduled queries, fleet and default-fleet MDM configuration, query lookups and result counts, YARA rules, MDM assets, and Fleet-maintained app names. Expirations run from about a second for configuration to fifteen minutes for the longest of them. Live queries keep a separate in-memory cache of their own.

It is per process, and nothing invalidates it across instances. So if you change a fleet's agent options, a request landing on a different instance can still be answered from that instance's older copy until its entry expires.

**The breadth matters when you are diagnosing staleness.** A stale pack, a query definition that will not update, an app name that will not change: these have the same shape as the agent-options case and none of them is fixed by looking at agent options. Suspect the cache before you suspect the write.

**MDM assets are the exception, and a useful one to know.** They are cached too, but the cache key includes the asset's checksum and Fleet fetches the current hashes each time, so an updated asset does not read from the old entry. A stale MDM asset is not a cache-expiry problem, and looking for one there is a dead end.

That is what an "I changed it and only some hosts got the new value" report often turns out to be, and it is the kind that resolves itself before anyone finishes investigating. A configuration change that applies inconsistently and then settles within the cache's expiry is this, and nothing is broken.

### What happens if you configure no object storage

**Your licence turns some of these features off before storage is even a question**, so read this table with that in front of it. Software installers, software title icons and Apple bootstrap packages are all Fleet Premium: the base service returns a licence error on upload, and their stores are only constructed when the licence is Premium. File carves and organisation logos are not gated that way, and carve storage is initialised outside that block entirely. So on Free, three of the five rows below describe artifacts you cannot create.

For the features your licence does include, configuring no bucket does not turn them off. Five kinds of artifact fall back, and they split along a line that decides what happens when you add a second instance.

| Artifact | Falls back to | Shared between instances |
|---|---|---|
| File carves | MySQL | Yes |
| Apple bootstrap packages | MySQL | Yes |
| Organisation logos | MySQL | Yes |
| Software installers | Local filesystem, a temporary directory by default | **No** |
| Software title icons | Local filesystem | **No** |

Organisation logos are easy to leave off a migration plan, because they do not feel like stored artifacts. They use the software-installers bucket when there is one.

The database-backed three keep working across any number of instances, because every instance reaches the same database. What they cost is database growth, and carve blocks are the ones that grow it fastest.

The filesystem-backed two use a **filesystem fallback rooted at a configurable directory, defaulting to the system temporary directory**. Fleet writes to deterministic paths under that root, so whether a second instance can read what the first wrote, and whether either survives a restart, is a property of the filesystem you point them at rather than of Fleet. On the default temporary directory the answer to both is usually no, which is why Fleet logs that it is using a local store and that this is not suitable for production, once for installers and once for icons. That log line is not boilerplate.

## Why the state is split

![Explanation](../_assets/icons/explanation.svg) One database could hold all of it. The split exists because the three kinds of state want incompatible things, and forcing them together makes each one worse.

Configuration and history need durability and consistency, and their access pattern is read-heavy. Live report coordination needs to be fast, and its value is bounded by the life of the campaign rather than by the retention of a record, so durability there buys little. Fleet is not treating that state as ephemeral in the strict sense, incidentally: live-query metadata carries a seven-day TTL in Redis rather than expiring with the campaign. Installers are large, immutable, and read by many readers at once, which is the workload a relational database handles least gracefully.

Give each one a store built for it and Fleet can run a live report against thousands of hosts while a package downloads and someone reads a year of activity history, without those three fighting each other.

### Recorded errors can be read without destroying them

Fleet records internal errors into Redis, deduplicated, retained about a day by default.

**Reading them is not destructive unless you ask for it to be.** The retrieval takes a flush argument that defaults to off, and the command line client only sets it when explicitly told to. So you can look, look again, and hand the same errors to somebody else.

The stored errors carry a TTL of their own, and the destructive read is the right thing to run once you have captured what you need. Knowing which of the two you are performing matters more during an incident than either behaviour on its own: a colleague who believes every read is destructive will hesitate to look at all.

## Deployment constraints this design imposes

![Reference](../_assets/icons/reference.svg) Everything above is what the split buys. This is what it costs. These are constraints, not preferences, and two of them shape a deployment plan directly.

### Fleet supports exactly one database writer

One writable primary, with read replicas. Multi-writer and group-replication setups are not supported, and that one sentence reaches further into a deployment plan than anything else in this chapter.

**No active-active across regions.** Fleet instances need a writer in the same datacentre. A second region can hold a warm standby for failover. It cannot serve writes at the same time.

Write capacity therefore scales vertically. More Fleet instances add API and check-in capacity, and they all point at the same writer, so when the writer saturates the answer is a bigger writer. Fleet's own reference sizings do exactly that, stepping one database instance class up as host counts grow.

Failover is a genuine interruption: Fleet instances have to reconnect, and work in flight against the old primary does not survive it. How much else it costs is a property of your database topology and your failover mechanism rather than of Fleet, and this manual does not establish it; treat a failover as an outage of unknown length and plan the rest from your own testing. What the upgrade section says about buffering and about ADE enrollments applies to the documented upgrade procedure specifically, and should not be carried over here as though it described every database interruption.

Check your MySQL version against Fleet's, in both directions. Fleet requires a recent MySQL 8 and is tested against a specific set of releases, and at least one newer release has been incompatible. MariaDB and other variants are unsupported, and known problems with variants may not get fixed.

If your platform standard is a multi-writer cluster, settle that before you deploy rather than after.

### Read replicas help some deployments and not others

Once a replica is configured, reads go to it automatically. Nothing needs annotating per query, and the code paths that must read their own writes ask for the primary themselves.

The benefit is specific rather than general. Heavy API polling, automation, and reporting is the case that pays. A deployment whose load is mostly host check-ins mostly does not, because check-ins write.

The trap: **the replica configuration inherits nothing from the primary.** Address, credentials, TLS, and pool settings are all separate, and a half-filled replica section written by someone who assumed the rest carried over gives you one of two quite different outcomes.

If the replica **address** is empty, Fleet does not configure a replica at all and the reader connection is simply the writer connection. Everything works, reads land on the primary, and the replica you are paying for is receiving nothing. Nothing announces this. If the address is set but something else in the section is wrong, you get the failures that actually look like a broken replica. Check which of the two you have before you go looking at replication lag.

### The pub/sub buffer is a scale limit that arrives early

Redis enforces an output buffer limit per subscriber, and Fleet is a subscriber. Fill that buffer and Redis drops the subscriber's data.

**It is not silent, though, and knowing that changes where you look.** Fleet returns errors from failed publishes and from publishing to a channel nobody is subscribed to, logs receive errors and passes them down the output channel, and deliberately emits a specific interruption error because the interface relies on it to say the results are incomplete. So the evidence exists in the logs and in what the UI reports.

What is misleading is the *shape*: a live report returning fewer hosts than you targeted reads as a host coverage problem rather than a Redis one, and that is why this is a commonly misdiagnosed scale limit. Read the campaign's errors before concluding the hosts were offline. The fix is to lift the limit for pub/sub clients.

It is harder to find than it should be for two reasons. A managed Redis service may split the setting across several differently named parameters, so searching for the Redis name, finding nothing, and concluding it does not apply is an easy and wrong path. And the limit is about result volume, not host count. A fleet-wide report against a wide table is a completely different sizing exercise from a policy check against the same hosts.

### Redis standalone or cluster, and how Fleet decides

You do not tell Fleet which mode to use. It attempts cluster operation at startup and falls back to standalone if the server does not support it.

Cluster mode costs something. Multi-key operations have to land in one slot, fan-out operations visit every node, and subscriber counts have to be summed across nodes. Fleet handles all of it, and Fleet's own reference architectures still specify plain Redis for deployments well into six figures of hosts.

Reach for cluster mode when one node cannot hold your working set or serve your throughput. Not as a default posture.

### What is coordinated across instances, and what is not

Fleet instances are interchangeable, and hold no state another instance needs. "Stateless" is doing a lot of work in that sentence, so here is what it actually covers. The one piece of state that does not travel by itself is the object-storage fallback, whose sharing and persistence depend on the filesystem you give it. Configuring a bucket removes that question rather than answering it.

**Scheduled jobs are coordinated, through MySQL.** Each named schedule takes a lock before running, so only one instance runs a given job in a given window. That lock lives in the database, not in Redis, so the bookkeeping survives a Redis flush.

Fleet also records which instance ran a job, alongside an identifier that appears in that process's logs. The pairing is how you get from "this job behaved oddly" to "these are that node's logs." The identifier is generated at process start, so it names a process, not a machine. One that shows up in the job record but in no current log belongs to a process that has since restarted.

**API and check-in traffic is not coordinated at all.** Any instance answers any request. That is the point, and it produces a failure mode that is expensive to diagnose: a fault that lives on one node. One instance with a stale cache. One that cannot reach the object store. One with a broken path to Apple's push service. The symptom is intermittent, roughly proportional to that instance's share of traffic, and reproducible only by luck.

So when a Fleet problem is intermittent at a stable rate, ask which instance served it early, not late.

Node-local storage stops being shared as soon as there is a second instance. The local-disk installer fallback writes to whichever instance handled the upload, so a later request served by a different one finds nothing. Whether a restart also loses the files depends on your deployment rather than on Fleet: the default is a temporary directory, you can point installers and icons at explicit directories instead, and whether those survive a container restart is a question about your volumes. That is what the "not suitable for production" log line is telling you.

### Losing Redis and losing MySQL fail very differently

The symptoms differ, which is often faster than checking both stores directly.

**MySQL unavailable is a hard stop.** No fallback, no local copy of anything durable. Check-ins fail, because authenticating a host needs a row. The interface and API fail. The server does not exit, it just returns errors until the database comes back. New instances refuse to start at all, because the startup migration check cannot run.

**Redis unavailable degrades in parts**, and the parts are specific:

- **Live reports stop.** Campaigns cannot be created and results have nowhere to go. It is an unusually visible symptom, because it fails in the interface while someone is watching.
- **Sign-on attempts that depend on Redis fail**, because Fleet holds in-flight SSO state there for the duration of one attempt, with an expiry. A retry once Redis is back starts a fresh attempt; that is a new sign-on rather than a resumed one.
- **Error recording stops**, because Fleet's recorded server errors are themselves Redis data, with their own TTL, and reading them can flush them. The outage does not delete what was already stored, though entries can expire on their own clock while it lasts. What you certainly cannot get is a record of the outage itself, which is the period you will most want to read about.
- **Host check-ins keep working and get more expensive.** The host authentication cache is a cache; a miss falls through to MySQL. Functionality is preserved while MySQL absorbs the traffic the cache was absorbing, so watch for MySQL saturating as a secondary effect.
- **Reconcilers may repeat work**, because their cursors live in Redis. Desired state is in MySQL, so this costs a repeated pass rather than correctness.
- **Pending failing-policy notifications are at risk**, because the recipients waiting to be sent are held in Redis sets rather than reconstructed from MySQL. They survive an outage; they do not survive the data being discarded.
- **With asynchronous host processing enabled, pending observations do not arrive.** Last-seen, label, policy and scheduled-query-stat updates queue through Redis, and their write failures are logged while the check-in continues, so the host looks healthy and Fleet's picture of it quietly stops advancing ([8.14](../08-troubleshooting/8.14-degradation.md)).
- **Scheduled jobs keep coordinating**, because that lock is in MySQL.

The overall health endpoint checks both, so it cannot tell you which one is down. It also accepts a parameter to check a single dependency, and that is the fastest way to answer "which store". Wire the two checks into monitoring separately instead of using the combined endpoint only as a load balancer probe.

## Desired state out, observed state in

![Explanation](../_assets/icons/explanation.svg) Everything Fleet does resolves into one of two flows, running in opposite directions.

**Desired state flows outward.** It starts with an intention: an administrator in the UI, a GitOps change, an API request, or a scheduled workflow. It ends with a policy, script, software item, profile, or command sitting ready for the hosts it was scoped to. Note where it ends. Desired state ends at *available to the device*, not at *applied on the device*. The gap between those two is where a great deal of troubleshooting lives.

**Observed state flows inward.** It starts at the device: a check-in, a report result, an MDM response, an agent report. It ends as updated host details, an activity record, a result status, report data, or a line in an external log.

**They do meet, and the clearest case is worth knowing.** Fleet writes what you want into MySQL and reads what is true out of device reports, and for the most part those are two separate flows whose distance is where most of the interesting questions in this book live. But when policy results arrive, Fleet drives work off that observation directly: running a script, reporting compliance to an identity provider, installing software or a VPP app, and registering the notification that later becomes a webhook or a ticket. Most of those act on policies that have just *started* failing, though a policy set to act continuously acts on every failing result, and one identity-provider path evaluates at sign-in time instead. That is the loop closing, observed state producing desired state, and it is why a script can run on a host that nobody asked to run a script on ([5.9](../05-manage-devices/5.9-automate-remediation-with-policies.md)).

The Fleet service coordinates those flows; the device paths described in [1.2 How Fleet reaches a device](1.2-how-fleet-reaches-a-device.md) carry the work to and from hosts.

## What a deployment needs owners for

![How-to](../_assets/icons/howto.svg) When designing or operating a Fleet deployment, establish ownership for:

- Fleet server configuration, availability, and TLS certificates
- **Server private-key custody, distribution, backup, and recovery**, which is separate from the three stores and is what makes a MySQL restore readable
- MySQL capacity, backups, and restoration
- Redis availability and monitoring
- Object-storage access, retention, and software/package delivery
- Logs, audit-event export, metrics, and tracing
- Release management for the Fleet service and fleetd

Parts II and VII expand these topics into deployment, day-two operations, and release-management guidance. This chapter provides the model needed to understand why those operational pieces fit together.

### Backing up three stores that cannot be captured together

No supported procedure backs up all three together, and a plain snapshot of each will not be consistent with the others unless you arrange for that yourself.

**Back up MySQL.** It is the whole system of record. Take a backup before every upgrade, because **Fleet exposes no supported rollback**: the operational CLI runs forward table and data migrations and offers no downgrade command, so rolling back a schema change means restoring the pre-upgrade database. Individual migrations may carry `Down` functions internally, which is not the same as a way for you to use them.

**Back up the installer bucket, or accept re-uploading.** MySQL holds a software installer's metadata and the bucket holds its bytes. Restoring the database to an earlier point while the bucket moves on leaves rows pointing at objects that are not there. Neither store is wrong; they simply disagree, and for installers the repair is re-uploading.

**File carves are the exception, and they are the reason "just re-upload it" is not a general answer.** Carve blocks can live in object storage too, uploaded by the reporting host during the carve session. Nobody can re-upload those: the evidence came off a machine at a moment that has passed, and if the objects disappear, reconciliation marks the carve expired. If you carve for investigations, carve storage belongs in your retention and disaster-recovery requirements alongside the database, not in the "administrator can re-supply it" category.

**Redis is not backed up**, and no supported procedure asks you to. Be aware of what that means rather than treating it as costless: if Redis data is discarded rather than merely unreachable, pending failing-policy notifications, the recorded error history and any queued asynchronous observations go with it, and none of them is reconstructed. Whether a given maintenance operation discards data is a property of how you run Redis; know which kind yours is before you schedule one.

### Upgrades take the service offline, and the window scales with your data

The documented procedure is to stop **every** Fleet instance, back up the database, run the migration, then start the new version. Fleet requires all instances down for the migration, so this is a full outage rather than a rolling restart. Typical upgrades are minutes.

**What buffers is host logs, and that is narrower than "device workflows are safe".** Fleet's own upgrade guidance promises that hosts buffer the logs they generate and send them when the server returns, which is a claim about osquery logging rather than about everything a device might be doing. One case fails badly: **an Apple ADE enrollment in progress can fail outright when Fleet is down for an upgrade**, and Fleet's own guidance says the remedy is sometimes an automatic retry and otherwise a remote wipe, or physical access to reinstall macOS from Recovery if the Mac is not on Wi-Fi. So do not schedule an upgrade window across device provisioning. The cost of the window is a gap in log freshness for enrolled hosts, and a failed or stuck enrollment for a Mac that was mid-provisioning, which Fleet's guidance says may need a wipe or a Recovery reinstall to clear.

Treat the typical figure as a median rather than a bound. Migrations that touch large per-host tables scale with how much of that data you have, and at least one release has shipped a fix for a migration that took hours on deployments with a lot of it. Before a production upgrade, run the migration against a restored copy of your own database and time it. Nothing else gives you a figure that reflects your data.
