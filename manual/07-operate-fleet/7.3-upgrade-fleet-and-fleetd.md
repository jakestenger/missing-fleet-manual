# Upgrade Fleet server and coordinate fleetd releases

An upgrade is the operation most likely to be done by following a procedure somebody else wrote. This chapter is about which parts of that procedure are Fleet's contract, which are your platform's, and which are decisions nobody has made for you.

A successful start proves only that the new binary opened against the new schema. Host check-ins, scheduled work, and a representative read and write are the evidence that the upgrade actually landed.

> **Read this before your first upgrade of a production Fleet.** Fleet's documented procedure and its bundled Helm chart do not behave the same way about instances staying up during migration, migrations do not reverse, and the old binary will start against the new schema with only a generic warning and then fail in ways nothing diagnoses. Each of those is below.

## Treat the release trains for what they are

![Reference](../_assets/icons/reference.svg) Two trains, not three, and the distinction matters for what you have to coordinate.

**The server and `fleetctl` share a release train.** They version together, though nothing forces you to deploy them together, and a mismatch produces a warning rather than a refusal ([6.4](../06-automate-fleet/6.4-use-fleetctl.md)).

**fleetd is an independent train**, with its own versions and its own update channels. [3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md) owns the channel mechanics: how a host learns about a version, what it does with it, and what precedence applies. **This chapter owns the coordination**: which versions you have decided to run together, how you promote a new one, and how you stop.

**Record the combination you tested.** Not the versions you intend, the versions you have actually run together and verified, because that is the thing you can go back to.

**If you run the Fleet MCP server, it is not a train at all.** `cmd/fleet-mcp` carries no release tag of its own ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)); it lives in the same repository as the server and tracks whichever tag you build it from. Rebuild and redeploy it from the target tag as part of the upgrade, restart it, and reverify the path exactly as first setup does: a single authenticated read from the assistant confirms tool discovery and the Fleet token together, and the bearer as well when the server runs over SSE, without running anything on a device.

## Assess migrations and measure the window

![Troubleshooting](../_assets/icons/troubleshooting.svg) The part of an upgrade you cannot undo.

**Migrations are forward-only.** Fleet does not down-migrate, and down-migrations at this version do nothing.

**That does not by itself decide whether the old binary can run.** A binary rollback is safe only while the current database state, including the migrations applied and anything the new release has written, has been established as backward-compatible with the old binary. Where that has not been established, the way back is a database restore.

### There is no duration model

Nothing in Fleet predicts how long a migration will take, and no formula exists. Cost is a query plan rather than a row count, so a table's size tells you less than you would like. (Fleet 4.90.0 shipped one migration that could run for hours on deployments with many host certificates; 4.90.1 fixes that particular migration, not the general unpredictability.)

**The only defensible estimate is rehearsal**: run the exact migration set for your source-to-target version pair against restored production-sized data, on the same database version with the same configuration and statistics. Measure that, then add your drain time, your replication catch-up, your startup time and your acceptance checks. That total is your window; anything shorter is a hope.

Fleet publishes a typical duration. **Treat it as an observation of somebody else's deployment**, not as a bound on yours.

### There is no migration lock

**Nothing prevents two instances migrating at once.** There is no advisory lock, and no uniqueness constraint on the record of which migrations have applied.

**Your procedure is the only thing guaranteeing exactly one runner.** That is worth stating explicitly in whatever runbook you write, because it is the kind of guarantee that quietly disappears when a deployment is automated by someone who did not know it was load-bearing.

> ### The failure that reports success
>
> If a migration with a **lower** number is missing while a higher-numbered one is already recorded as applied, the runner skips the missing one. It does this on every rerun.
>
> **The preparation command reports success. The server then refuses to start, on every attempt.** Rerunning the preparation does not help, because it skips the same migration again.
>
> This is the state to recognise rather than to fight: a successful preparation and a server that will not serve mean the applied-migration record needs inspecting, not another rerun.

**And if migration status reports either of the two known-bad states** Fleet names for a historical fix, stop. Do not rely on the preparation command continuing past its warning. That is a support conversation or a restore.

## Prepare the change and the recovery point

![How-to](../_assets/icons/howto.svg) The decisions to make while nothing is broken.

1. **Read the release notes for every version between yours and the target**, not just the target's. Upgrade-specific steps, a minimum agent version, and ordering requirements all live there and nowhere else.
2. **Take a backup and verify it**, in the sense [7.2](7.2-back-up-and-restore-service-state.md) defines: proven restorable, not merely taken.
3. **Record your baselines.** Whatever indicators you declared in [7.1](7.1-define-the-service-operating-model.md), measured now, so "returned to baseline" means something afterwards.
4. **Count what is in flight**, using the section below.
5. **Freeze high-risk work.** Anything irreversible you would not want half-applied.
6. **Declare the rollback data-loss point**, in writing, before you start.

> **The rollback data-loss point is the moment after which recovery means restoring the database.** Everything written between your backup and that restore is lost. Deciding it in advance turns an incident decision into a plan.

## Account for work in flight

![Explanation](../_assets/icons/explanation.svg) Less is lost than people fear, and what is lost is specific.

Most of Fleet's work is pull-based. An agent that could not check in checks in later; a queued item that was not delivered is delivered next time. **The restart itself is not what loses work.**

What genuinely does not survive:

| | What happens |
|---|---|
| **Live query results** | Held as messages rather than records. **A lost subscriber discards them.** An orphaned campaign may be closed a minute later by an arriving result, and otherwise waits for cleanup |
| **Worker jobs** | Re-run from the start, which can mean **a duplicate ticket** where one was already created |
| **Scheduled jobs** | A graceful stop records pending runs as cancelled, though a surviving lock can delay another runner for that schedule's interval. **After an ungraceful stop, stale pending state can delay work for longer**, so verify rather than assuming one interval is the bound |

**Count before and after.** Queued activities, pending MDM commands, worker jobs. The point is not that the numbers match exactly, it is that you can tell a queue that resumed from one that did not.

> **One queue state deserves its own attention.** An activity that was activated but never got a result survives the restart and can be fetched again. **If no result and no cancellation ever arrives, it blocks that host's later work indefinitely**, because Fleet has no reaper that gives up on age. A host whose queue stopped advancing after an upgrade is worth looking at directly ([5.1](../05-manage-devices/5.1-plan-target-and-govern-device-changes.md)).

## Upgrade every instance and migrate offline

![How-to](../_assets/icons/howto.svg) Where Fleet's documentation and Fleet's own automation part company.

**Fleet's documented procedure is: stop every instance, replace the release, run the database preparation once, then start the new version.**

> ### Fleet's own Helm chart does not do that
>
> In its default configuration, with an external database and automatic migrations enabled, **the chart declares the migration as a pre-upgrade hook and does not stop the existing pods before it runs.** They can therefore go on serving while the migration changes their schema.
>
> **After the hook succeeds the deployment is updated**, and because the chart specifies no strategy, the platform supplies its default rolling replacement, during which old and new pods can overlap. Those are two distinct periods and they fail differently.
>
> **Those lifecycle semantics belong to Helm and to Kubernetes, not to Fleet.** They do not establish a zero-downtime or mixed-version guarantee, and the rolling replacement is **not** the schema-isolated canary that [7.1](7.1-define-the-service-operating-model.md) rules out.
>
> The DigitalOcean example likewise declares a pre-deploy migration job, though what that platform does with serving instances is not established by Fleet's source. The AWS example calls an external migration module whose lifecycle is not in this repository at all.
>
> **Keeping the reference behaviour is a tested operational choice, not Fleet's contract.** Decide it deliberately rather than inheriting it.

**Migrate exactly once**, whichever you choose, because nothing else enforces that.

## Prove the service resumed

![Reference](../_assets/icons/reference.svg) Eight rungs, in order, because each one makes the next meaningful.

| | Rung | Where the answer comes from |
|---|---|---|
| 1 | **Every serving node reports the intended release** | The version each instance reports, checked per instance rather than through the load balancer |
| 2 | **Migrations are current** | The migration status check, which needs an authenticated serving server |
| 3 | **Health and dependency checks pass** | The health endpoint, remembering it does not check everything ([7.4](7.4-observe-progress-and-service-health.md)) |
| 4 | **A bounded read and a reversible write work** | Your own choice, made in advance |
| 5 | **Agent check-ins resume** | Host counts and last-seen times moving |
| 6 | **Scheduled work resumes** | Not just that a job ran: see below |
| 7 | **Queue throughput resumes** | The counts from the previous section, moving rather than merely present |
| 8 | **Declared indicators return to baseline** | 7.1's indicators, against the numbers you recorded |

> **A scheduled job recorded as completed is not proof it worked.** Check its recorded errors as well, and then check that the thing it was supposed to advance actually advanced. A job that ran and achieved nothing looks identical at rung six otherwise.

**The migration status check, `fleetctl debug migrations`, needs an authenticated and serving server**, as does its HTTP equivalent. Neither can diagnose the case you most want diagnosed, which is a server that will not start. And **the preparation command is not a read-only status check**: do not reach for it to find out where you are.

If a rung fails, that is [Part VIII](../08-troubleshooting/8.1-diagnostic-method.md)'s work. This chapter's job ends at knowing which rung failed.

## Roll out fleetd through established channels

![How-to](../_assets/icons/howto.svg) A separate train, a separate decision, and the same discipline.

[3.8](../03-connect-devices/3.8-manage-fleetd-orbit-and-updates.md) owns how a version reaches a host. What belongs here:

- **Promote in rings.** A pilot group, then a broader one, then the estate.
- **Watch the version distribution**, not the rollout's own status. The question is how many hosts are actually running the new version.
- **Decide the stop condition first**, and who may invoke it.
- **Expect a long tail.** Hosts that are off, travelling, or rarely used will arrive whenever they arrive, and the distribution's last few percent is not a problem to be solved on the day.

**Do not couple a fleetd rollout to a server upgrade window.** They are separate trains with separate risks, and combining them means an incident in either is an incident in both.

## Recover from a failed upgrade

![Troubleshooting](../_assets/icons/troubleshooting.svg) Two different operations, and the boundary between them is not where people assume.

### The old binary will start

This is the part that catches people. **An older Fleet started against a newer schema does not refuse.** It emits a generic warning about migrations it does not recognise, and then serves.

**Then it fails partially, and quietly.** The concrete case on the way to 4.90: a migration copies the retained content out of a Windows configuration-profile table and drops it. The previous release still inserts into, reads from and cleans that table in its Windows profile removal and reconciliation paths, **so those paths can fail while the server goes on answering other requests.**

> **So "did the migrations run" is the wrong question.** The one that matters is **"is the current database state backward-compatible with the old binary"**, and a dropped table is only one way it might not be: a data transformation or something the new release has written can invalidate an old assumption just as effectively.
>
> **Fleet gives you a generic unknown-migrations warning and no compatibility verdict.** The question has to be answered per upgrade, from the migration set, before you rely on a binary rollback.

### Which recovery you are doing

**Before any migration applied**: put the old binary back. This is quick and loses nothing.

**After any migration applied**: a binary rollback is safe **only if** you have established that the current database state is backward-compatible with the old binary, which means the intervening migrations *and* what the new release has already written. Where you have not established that, the recovery is **restoring the database to its pre-migration state**, and everything written since is lost. That is why you declared the point before you started.

**Whichever you do, verify with the same eight rungs.** A recovery that has not been proven is a second incident waiting.
