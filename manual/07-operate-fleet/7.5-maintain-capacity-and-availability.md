# Maintain capacity and availability

![Explanation](../_assets/icons/explanation-light.svg) Fleet's application tier can grow horizontally as your device estate and workload expand. Additional instances share the database, Redis, and storage, so capacity planning needs to consider those dependencies together.

Fleet does not publish a universal instance count, sizing formula, or recovery-time target. Its reference architecture gives you a starting point. Use measurements from your deployment to decide when to add capacity, where to add it, and how much headroom to preserve for a failure.

This chapter covers those decisions for an existing service. [2.2](../02-administer-and-deploy-fleet/2.2-self-hosting-architecture-and-capacity.md) covers the initial topology.

## Start from Fleet's topology constraints

![Reference](../_assets/icons/reference-light.svg) Four properties shape the available scaling and recovery options:

1. The stateless application tier supports multiple instances behind a load balancer.
2. Every instance uses the shared database and Redis.
3. The database has one writable primary; replicas serve reads.
4. Application instances need low-latency access to that writer, and Fleet's architecture places them together.

For cross-region recovery, the architecture supports an active-passive design with writer promotion. It does not establish an active-active deployment serving simultaneously from distant regions.

## Turn telemetry into a capacity decision

![How-to](../_assets/icons/howto-light.svg) First establish whether the work is progressing under pressure or has stalled. A stuck queue, a schedule that stopped running, or a lagging replica needs investigation before you decide that more Fleet instances will help. Use the progress signals in [7.4](7.4-observe-progress-and-service-health.md).

Then work through four questions:

1. Is the pressure sustained, or was it a temporary spike?
2. Which component is constrained: the application tier, MySQL, Redis, or storage?
3. Can tuning the existing deployment recover useful headroom?
4. When does projected growth require additional capacity?

Collect internal resource signals through Fleet's export pipeline as well as request metrics. The metrics endpoint can show slowing requests while omitting the connection-pool waits that help explain them ([7.4](7.4-observe-progress-and-service-health.md)).

Rising latency, pool waits, queue age, and replication lag can provide an early indication of pressure. Errors, timeouts, and failed check-ins show that users or devices are already affected. For diagnosing active degradation, use [8.14](../08-troubleshooting/8.14-degradation.md).

## Scale Fleet instances safely

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Before increasing the instance count, calculate the database connections the larger application tier could open.

Each Fleet instance has a writer pool with a default maximum of fifty connections. If a replica is configured, it has a separate pool whose maximum independently defaults to fifty. These are concurrent-connection ceilings, rather than a count of connections held open at rest.

Calculate the two endpoint budgets separately:

| Endpoint | Maximum potential connections from Fleet |
|---|---|
| Primary | Writer-pool maximum × Fleet instance count |
| Replica | Replica-pool maximum × Fleet instance count |

The primary does not absorb the replica pool's share, and the two maxima should not be added together as a budget for either endpoint. Set each pool maximum against the capacity of the endpoint it uses before scaling out.

Keep configuration consistent across instances so they can serve interchangeably. Configure the load balancer to use Fleet's health check, with the coverage limits described in [7.4](7.4-observe-progress-and-service-health.md).

### Drain requests before stopping an instance

Fleet allows about thirty seconds for work to finish after shutdown begins. It accepts requests whose permitted duration is considerably longer, so the shutdown window cannot guarantee that every accepted request will finish.

Use both parts of this operating procedure:

1. Remove the instance from the load balancer's rotation and allow in-flight requests to finish before signalling the process.
2. Give the platform a termination allowance longer than thirty seconds after the signal, sized with the longest accepted request in mind.

Pre-draining provides the opportunity for long requests to complete. Extending the platform's termination allowance alone does not extend Fleet's internal shutdown window. Check how your platform removes traffic and signals termination, then test the combined procedure.

## Scale MySQL, Redis, and object storage by their own limits

![Reference](../_assets/icons/reference-light.svg) Each dependency has its own capacity constraints and scaling procedure.

MySQL has one writer, so write capacity scales vertically. Read replicas can provide read capacity, but they also add the availability dependency described below.

For Redis, monitor memory, connections, and evictions through Redis or its provider. Eviction behavior comes from Redis configuration, and Fleet does not expose a signal for it.

Object storage serves several features through two buckets. Fleet supplies no storage-health signal and imposes no timeout of its own on the agent download path. Slow storage can therefore appear as an installation that hangs. Any timeout comes from the underlying layers, and a content-delivery layer can also degrade without a Fleet-side signal.

Use the relevant provider's procedure to resize or tune the constrained dependency, then check the effect on Fleet. A database resize, for example, may change connection limits and require new pool budgets.

## Design failure domains and regional recovery

![Troubleshooting](../_assets/icons/troubleshooting-light.svg) Plan for the effect of each component loss, including whether the remaining components can carry the workload.

| Component lost | Effect |
|---|---|
| **Fleet instance** | Other instances can continue if they have enough headroom. The failed instance's in-flight requests fail, and an ungraceful stop can lose accepted work ([7.3](7.3-upgrade-fleet-and-fleetd.md)) |
| **Database primary** | Fleet stops until a writer is available. Promotion time depends on the database platform |
| **Redis** | Live query results and pending notification sets are lost; most other transient state can recover ([7.2](7.2-back-up-and-restore-service-state.md)) |
| **Object storage** | Software delivery and bootstrap are affected. Monitor availability from the storage side because Fleet supplies no health signal ([7.4](7.4-observe-progress-and-service-health.md)) |
| **Read replica** | Health checks fail on every instance, with no automatic fallback to the writer |

A configured read replica is an availability dependency. If it fails, a load balancer using Fleet's health result can remove every instance from service. Prepare and test a procedure for removing the replica from configuration, and establish whether the primary can handle the additional reads. Both the configuration change and the capacity check belong in the recovery plan.

For regional recovery, use an active-passive plan that includes writer promotion, traffic redirection, DNS, certificates, secrets, and object data. Arrange for each item to move or be available in advance. Measure your recovery time through rehearsal; Fleet does not supply a target ([7.2](7.2-back-up-and-restore-service-state.md)).

## Test load and failover assumptions

![How-to](../_assets/icons/howto-light.svg) Test the workload and failure conditions your capacity plan needs to support. Fleet includes `osquery-perf` to generate traffic resembling a managed estate: enrolment, configuration polling, distributed-query polling, log submission, and separate Apple MDM, declarative device management, and Platform SSO check-ins.

The tool fabricates query results from built-in OS templates. It can help measure the server's response to a larger agent workload, but it does not run osquery on real devices.

Fleet's repository also includes load-test results. Read those with their version, workload, duration, and infrastructure in view. They describe the tested deployment and provide context for your own measurements.

Exercise these failure cases under load:

- Lose one Fleet instance and confirm that the others have enough headroom.
- Lose a read replica and run the recovery procedure described above.
- Deploy a replacement and check whether requests are dropped during the rollout.
- Fail over the database and measure the interruption.

For each case, continue measuring after the process starts answering requests. Confirm that agents resume reporting and queues resume draining, using the signals in [7.4](7.4-observe-progress-and-service-health.md).

### Run osquery-perf

The `osquery-perf` command lives in Fleet's source tree and requires a working Go toolchain; the repository builds with Go 1.26.5. Run `go run ./cmd/osquery-perf` from the checkout without a separate build step or downloaded binary. Use `go run ./cmd/osquery-perf --help` to inspect its flags.

It authenticates with an enrol secret like a real agent, with no edition or licence restriction. Retrieve the secret from the Fleet UI or `fleetctl get enroll_secret`, then use it to enrol simulated hosts:

```sh
git clone --branch fleet-v4.90.0 https://github.com/fleetdm/fleet.git
cd fleet                                   # go run resolves ./cmd/osquery-perf from here
go run ./cmd/osquery-perf \
  -server_url "https://fleet.example.com" \
  -enroll_secret "<secret>" \
  -host_count 500
```

When one generator machine is insufficient, run several copies with distinct slices of the simulated population. `-total_host_count` sets the size of the whole population, while `-host_index_offset` sets where a copy starts. This avoids collisions between simulated host identities.

The default platform template is `macos_14.1.2`. Use `-os_templates` with a comma-separated selection from the built-in templates to model your platform mix. Review the flags for check-in cadence, failure injection, and inventory size before a substantial test.

Run the tool against a disposable test server on an isolated network. Its client unconditionally disables TLS certificate verification, so it will trust an impersonating server. It also opens a [pprof](../09-appendices/a.6-glossary-and-release-compatibility.md#pprof) server on `localhost:6060` on the generator machine. These behaviors need to be accounted for in the test environment.

### What osquery-perf cannot tell you

Because the tool fabricates results, it cannot measure agent CPU consumption or query cost on a real endpoint. Measure device performance separately.

It also omits read-heavy REST API traffic from integrations and the Fleet MCP server. One assistant question can make a Fleet call per fleet or matching item, and a live query can reach several hundred hosts ([6.6](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md)). Include that workload in a separate capacity assessment.

Review the generated workload before extrapolating from it. Failure-injection defaults, including a high software-query failure probability, are generator fixtures rather than estimates of real device failure rates. Traffic comes from one or a few machines sharing a source IP and follows the intervals you configure. It does not exercise per-device TLS, IP-based behavior, or push-driven check-in timing.

The generator produces traffic without calculating a capacity result. Collect the response through Fleet's [telemetry](7.4-observe-progress-and-service-health.md) and your database and Redis metrics. Record the workload and infrastructure alongside the measurements so later comparisons remain useful.

## Review capacity after material change

![How-to](../_assets/icons/howto-light.svg) Re-measure after significant host growth, an estate-wide automation, a cadence change, a Fleet upgrade, or a dependency resize. Do the same when an integration or the [MCP server](../06-automate-fleet/6.6-connect-fleet-to-an-ai-assistant.md) introduces substantial API or live-query traffic.

An upgrade can change the amount of work performed per host or interval even when your configuration stays the same. Compare the result with the baseline recorded for the [upgrade procedure](7.3-upgrade-fleet-and-fleetd.md).

Whenever the Fleet instance count changes, recalculate both database connection budgets and verify that the primary and replica can support them.
