# How Fleet reaches a device

Fleet reaches devices through the mechanism each platform makes available. On macOS, Windows,
and Linux, fleetd provides the host-side agent path. On supported managed platforms, the
operating system’s MDM client provides a separate device-management path.

This model is useful because it makes Fleet’s behaviour easy to reason about: query and
inventory work belong to osquery; host-side management work belongs to Orbit; and profiles
and MDM commands belong to the operating system’s MDM client.

## The host-side bundle

**fleetd** is the name of Fleet’s host-side bundle and installer package. On macOS, Windows,
and Linux the bundle contains three coordinated components:

| Component | Primary role | Process name |
|---|---|---|
| **Orbit** | Enrolls and manages the host-side bundle; coordinates scripts, software installs, updates, and other agent workflows | `orbit` / `orbit.exe` |
| **osquery** | Provides live queries, scheduled results, host vitals, and software inventory | `osqueryd` / `osqueryd.exe` |
| **Fleet Desktop** | Provides the user-facing menu bar experience, My Device link, and dialogs that need a logged-in person | `fleet-desktop` / `fleet-desktop.exe` |

The operating system’s service manager starts Orbit. Orbit starts osqueryd and, when a user
session is available, Fleet Desktop.

## Each kind of work has a clear owner

| Administrative question | Owner | Examples |
|---|---|---|
| What is on the host right now? | **osquery** | Live queries, scheduled results, vitals, inventory, and file carves |
| How does Fleet carry out host-side work? | **Orbit** | Enrollment, scripts, software installs, fleetd updates, setup experience, and supported encryption workflows |
| How does Fleet apply native device management? | **OS MDM client** | Profiles, MDM commands, managed app delivery, lock, and wipe |
| How does Fleet interact with the person using the device? | **Fleet Desktop**, launched by Orbit | My Device, Self Service, and end-user dialogs |

This division makes the right place to look clear. A query question starts with osquery; a
script or software question starts with Orbit; a profile or device command starts with the
platform MDM path.

## The five channels

The host and Fleet service communicate over five channels. The first three are osquery
conversations, the fourth is Orbit’s API, and the fifth is the platform’s MDM protocol.

| Channel | Owner | Carries | Typical cadence |
|---|---|---|---|
| osquery distributed | osqueryd | Live queries and host-detail queries | `distributed_interval`, commonly 10–30 seconds |
| osquery config TLS | osqueryd | Scheduled query configuration and agent options | `config_refresh`; Fleet sets this to 60 seconds |
| osquery logger TLS | osqueryd | Query results | `logger_tls_period` |
| Orbit API | Orbit | Scripts, software, setup experience, agent configuration, and host-side workflows | 30-second configuration poll plus request/response work |
| MDM protocol | OS MDM client | Profiles, MDM commands, managed apps, lock, and wipe | Platform-specific push or poll |

## What “online” tells you

Fleet marks a host online when it has checked in through osquery within its normal check-in
window, plus a 60-second grace period. The window uses the shorter of the host’s
`distributed_interval` and `config_refresh` values.

In Fleet’s standard configuration, `config_refresh` is 60 seconds and
`distributed_interval` is commonly 10–30 seconds. In practice, this means a host normally
continues to show as online for about 70–90 seconds after its most recent osquery check-in.

Both values are osquery options in the agent-options `options` block. Hosts receive a changed
value at their next configuration refresh, without an osquery restart:

```yaml
agent_options:
  options:
    config_refresh: 60
    distributed_interval: 30
```

Lower intervals give a fresher online signal and faster live-query pickup. Higher intervals
reduce check-in traffic and extend the time Fleet treats the last successful check-in as
current. Choose values that match the responsiveness and network profile of the fleet.

The online signal gives administrators a reliable view of query and inventory availability.
The MDM path and Orbit path are independently visible through the status of the work they
perform.

For example, a host can answer a live query while an MDM command is awaiting the platform’s
next check-in. An MDM-enrolled device can report MDM status before fleetd has been installed.
The diagnostic method is therefore to identify the channel associated with the requested
action, then inspect that channel’s evidence.
