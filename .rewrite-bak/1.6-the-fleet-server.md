# The Fleet server

The Fleet server coordinates device management, but it keeps its durable information in
purpose-built infrastructure services. This design lets an organization run Fleet behind a
load balancer, replace a Fleet server instance, and scale the service while keeping the shared
device-management record available.

## The state model

| Component | Role in Fleet | Examples of what it holds |
|---|---|---|
| **Fleet server** | Receives requests, serves the UI and API, and coordinates device work | Stateless application processes and short-lived local caches |
| **MySQL** | System of record | Hosts, fleets, labels, policies, queries, MDM queues, activities, and configuration |
| **Redis** | Fast coordination and temporary workflow state | Live-query campaigns, host-auth cache, rate limits, SSO workflow state, and reconciler cursors |
| **Object storage** | Durable storage for large binary objects | Software installers, bootstrap packages, title icons, and file-carve blocks |

TLS protects communication with the Fleet service. MySQL, Redis, object storage, and
certificates are the core infrastructure dependencies to plan for in a production deployment.

## Why the state is split

Each component has a clear job:

- **MySQL** preserves the administrative record: the configuration you set, the hosts Fleet
  knows, the work Fleet has queued, and the history administrators need to review.
- **Redis** makes interactive and high-frequency workflows responsive, including live-query
  coordination and host authentication caching.
- **Object storage** provides a durable, scalable home for installer packages and other large
  files that devices and Fleet instances may need to read.

This separation lets Fleet use the right storage pattern for configuration, real-time
coordination, and binary delivery.

## The two flows administrators operate

Fleet’s state model supports two complementary flows:

| Flow | Starts with | Ends with |
|---|---|---|
| Desired state | An administrator, GitOps change, API request, or scheduled workflow | A policy, script, software item, profile, or command available to the selected hosts |
| Observed state | A device check-in, query result, MDM response, or agent report | Updated host details, activity, result status, report data, or an external log record |

The Fleet service coordinates those flows; the device paths described in
[1.2 How Fleet reaches a device](1.2-how-fleet-reaches-a-device.md) carry the work to and
from hosts.

## What to plan for

When designing or operating a Fleet deployment, establish ownership for:

- Fleet server configuration, availability, and TLS certificates
- MySQL capacity, backups, and restoration
- Redis availability and monitoring
- Object-storage access, retention, and software/package delivery
- Logs, audit-event export, metrics, and tracing
- Release management for the Fleet service and fleetd

Parts II and VII expand these topics into deployment, day-two operations, and release-management
guidance. This chapter provides the model needed to understand why those operational pieces
fit together.
