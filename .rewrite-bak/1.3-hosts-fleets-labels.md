# Hosts, fleets, labels, and targeting

Fleet gives administrators two complementary ways to organize a device estate:

- **Fleets** define the configuration and administrative scope a host belongs to.
- **Labels** select hosts globally or within a fleet for a particular action.

Together, they let you give a group of devices a shared operating model without giving up
precise targeting.

## Hosts are the records Fleet manages

A host record is Fleet’s durable view of a device. It collects identity, inventory, query
results, policy status, software activity, and management history as the device interacts with
Fleet.

Fleet uses device identity information during enrollment to recognize returning devices and
maintain a continuous host record where possible. A re-enrollment refreshes the host’s
credentials while preserving its assigned fleet. Moving an existing device to another fleet is
an explicit administrative action, so administrators can see and control changes in scope.

The detailed identity rules, node-key lifecycle, and re-enrollment behaviour belong in the
host identity reference and troubleshooting material.

## Fleets define configuration scope

A host belongs to one named fleet or to the **Unassigned** scope. Fleets are peers: a host in
one fleet receives the configuration assigned to that fleet, while Unassigned is its own
useful scope for devices that are being evaluated, enrolled, or awaiting assignment.

| Scope | Use it for | Examples of scoped configuration |
|---|---|---|
| Named fleet | Devices that share an owner, operating model, or lifecycle | Policies, software, profiles, queries, agent options, enrollment secrets, and roles |
| Unassigned | Devices before intentional placement or devices managed with a common baseline | Its own policies, software, profiles, and controls |

Choose fleets for a durable administrative boundary. Good candidates are device purpose,
ownership, management posture, or a distinct service level—not every technical attribute a
host happens to have.

## Global and fleet scopes work together

Fleet has an organization-wide scope for work that should be shared across the estate and a
fleet scope for work that belongs to one operating environment. Use global policies, labels,
and reports for requirements, selections, and observations that genuinely apply across the
organization. Use fleet-scoped policies, labels, scripts, software, profiles, and settings
when a device group needs its own operating model.

A global label is available across fleets; a fleet label is available only in its fleet. In
either case, label targeting narrows the recipients of the item you are configuring. This is
why a durable difference in configuration or ownership is a reason for a new fleet, while a
temporary rollout ring or shared device characteristic is usually a label.

## Fleets are also delegation boundaries

Fleet Premium lets an administrator assign a user a role on one or more specific fleets.
That user can work with the hosts and fleet-scoped resources their role permits, without being
given access to the other fleets merely because they administer one of them.

For example, a computer-lab fleet can have its own policies, software, and settings, while lab
employees receive an appropriate role for that fleet. The central endpoint team retains global
access and can manage organization-wide configuration; the lab team can manage the lab within
the responsibilities assigned to its fleet role.

## Labels select hosts flexibly

A host can belong to many labels. Labels provide flexible selections for a rollout, policy,
report, query, software title, profile, or other fleet-scoped item.

| Label type | Membership comes from | Good use |
|---|---|---|
| Dynamic label | A SQL query evaluated on the host | Operating-system, hardware, software, or configuration characteristics |
| Manual label | An administrator-maintained host list | A deliberate pilot, exception group, or project cohort |
| Host vitals label | Criteria evaluated against reported host vitals | Department, end-user, model, or other available vital data |
| Built-in label | Fleet-owned membership | A supported platform or Fleet-defined device condition |

Use a label when the selection can change over time or is narrower than the fleet’s enduring
purpose. For example, a **Canary ring** label can select a few devices inside a Workstations
fleet without creating another configuration scope.

## Targeting combines the two

Fleet-scoped managed items begin with their fleet scope; global items begin with the
organization-wide scope. Label targeting then narrows the recipients within that scope.

| Targeting mode | Meaning |
|---|---|
| Include any | Deliver to hosts with at least one listed label |
| Include all | Deliver only to hosts with every listed label |
| Exclude any | Deliver to the scoped hosts except those with a listed label |

This gives you a practical rollout pattern:

1. Put the shared configuration in the fleet that owns it.
2. Use a canary label for an initial ring.
3. Expand or remove the label target after validation.
4. Keep the fleet boundary stable unless the device’s long-term operating model changes.

## Design scopes for people, not just devices

The most useful question is: **who should be able to make which decisions for these devices?**

Use a separate fleet when the answer changes configuration ownership, access delegation,
software catalog, enrollment path, or lifecycle. Use a label when the answer is a temporary
or cross-cutting selection such as platform, hardware architecture, department, rollout ring,
or a policy condition.

| Situation | Prefer | Why |
|---|---|---|
| A group needs its own profiles, software, or administrators | A fleet | It has a distinct operating model |
| A subset is testing a change | A label | The membership is a rollout choice inside the existing scope |
| A report should include all devices with a shared property | A label | The property can span fleets |
| A device changes organizational ownership | A fleet transfer | The durable scope is changing |

## Terms you will encounter

Fleet renamed **teams** to **fleets** in the user interface. The database and many API
endpoints still use `team` terminology. They refer to the same scoping concept.

The detailed targeting validation rules, label refresh timing, GitOps identity rules, and
scope-precedence examples belong in the GitOps and reference chapters. Part VIII contains the
diagnostic material for delayed membership and enrollment identity questions.
